# Quickstart: проверка фикса PROCESS_COUNT_WAITING вручную

**Дата**: 2026-08-12
**Фича**: 177-fix-process-count-waiting-spam
**Связанные документы**: [spec.md](./spec.md), [plan.md](./plan.md),
[research.md](./research.md), [data-model.md](./data-model.md),
[contracts/sse-payload.md](./contracts/sse-payload.md)

## Prerequisites

- Admin-машина с запущенным `karaoke-app` контейнером.
- Браузер с DevTools (Chrome/Edge/Firefox — все подойдут).
- SSH-доступ к admin-машине (для rebuild/restart, если фикс уже
  влит в код).

## Setup

### Шаг 1. Сборка и перезапуск (после имплементации фикса)

```bash
# На admin-машине, от пользователя, уполномоченного перезапускать karaoke-app
cd /sm-karaoke/system/deploy
./build_app.sh          # пересборка только karaoke-app (gradle)
./restart_app.sh        # или docker compose restart karaoke-app
```

Подробности по сборке — в `AGENTS.md` § «Сборка и запуск».

### Шаг 2. Подготовка браузера

1. Открыть **любую** страницу админки (например, `/songs`).
2. Включить DevTools → **Network** → фильтр `subscribe` (или
   `EventStream`/`SSE` в зависимости от браузера).
3. Убедиться, что SSE-подписка установлена (одно `pending`-соединение
   на `/api/subscribe?tabId=...`).

## Сценарий 1: проверка устранения спама (SC-001)

**Цель**: убедиться, что в SSE-канал не идут повторные
`PROCESS_COUNT_WAITING` с одинаковым `countWaiting`.

### Шаги

1. Убедиться, что очередь пуста: `countWaiting == 0` (нет
   заданий со статусом `WAITING`, кроме `command = "tail"`).
2. В DevTools → Network → EventStream оставить фильтр на
   `subscribe`.
3. В поле фильтра **payload type** ввести `PROCESS_COUNT_WAITING`
   (если DevTools это позволяет — Chrome DevTools фильтрует
   по URL, не по payload type; тогда пропускаем шаг).
4. Засечь время. **Ничего не делать 5 минут.**
5. После 5 минут — посчитать количество
   `PROCESS_COUNT_WAITING`-сообщений с `countWaiting == 0`.

### Ожидание

**0 сообщений** (SC-001).

До фикса: тысячи сообщений за 5 минут (десятки в секунду).

### Если ожидание не выполнилось

Если сообщения всё ещё приходят — это означает, что один из
call-sites шлёт в обход `sendCountWaitingMessage` (теоретически
не должно быть, но если что-то поменялось — проверить):

```bash
# На admin-машине, в stdout контейнера karaoke-app:
docker logs karaoke-app 2>&1 | grep -c "PROCESS_COUNT_WAITING"
```

Если логи показывают большое число — это значит, продьюсер
всё ещё шлёт. Проверить `KaraokeProcessWorker.sendCountWaitingMessage`
на наличие правок и `@Volatile var lastSentCountWaiting`.

## Сценарий 2: проверка доставки реальных изменений (SC-002)

**Цель**: убедиться, что при реальном изменении `countWaiting`
фронт получает событие в течение 1–2 секунд.

### Шаги

1. В DevTools держать открытым EventStream на `subscribe`.
2. Создать длительное задание в очереди:
   - Например, в админке открыть песню → запустить рендер
     `RENDER_MP4_DEMO` или `RENDER_MP4_LYRICS`.
3. Засечь время от нажатия «Запустить» до появления
   `PROCESS_COUNT_WAITING`-сообщения с ненулевым `countWaiting`.
4. Дождаться завершения задания (статус `DONE`).
5. Засечь время до появления сообщения с уменьшенным
   `countWaiting`.

### Ожидание

- Первое сообщение (новое задание появилось в очереди) — в
  течение **1–2 секунд** (SC-002).
- Второе сообщение (задание завершилось) — в течение **1–2 секунд**.
- Между этими двумя событиями — **0** промежуточных сообщений
  с тем же значением `countWaiting` (если только состояние не
  менялось между ними).

## Сценарий 3: проверка FR-007 (одно начальное сообщение)

**Цель**: убедиться, что после ручного запуска воркера бэкенд
отправляет **ровно одно** начальное `PROCESS_COUNT_WAITING`,
даже если значение совпадает с предыдущим.

### Шаги

1. Запомнить текущий `countWaiting` (например, `0`).
2. В админке или через API остановить воркер:
   `POST /api/processes/stopWorker` (или эквивалентный UI-контрол).
3. Дождаться остановки (SSE-событие `PROCESS_WORKER_STATE` с
   `isWork == false`).
4. Снова запустить воркер:
   `POST /api/processes/startWorker`.
5. Посчитать количество `PROCESS_COUNT_WAITING` сразу после
   старта воркера.

### Ожидание

**Ровно 1 сообщение** `PROCESS_COUNT_WAITING` (FR-007), даже
если значение совпало с известным до этого.

До фикса могло быть несколько (в зависимости от того, успело ли
значение поменяться между stop и start).

## Сценарий 4: проверка отсутствия регрессии в PROCESS_WORKER_STATE

**Цель**: убедиться, что фикс `PROCESS_COUNT_WAITING` не
затронул другие события.

### Шаги

1. Запустить/остановить воркер.
2. Убедиться, что приходят `PROCESS_WORKER_STATE`-сообщения
   с `isWork: true/false` как обычно.
3. Создать/изменить/удалить любую запись (например, отредактировать
   тег песни).
4. Убедиться, что приходит `RECORD_CHANGE` (или `RECORD_ADD`/
   `RECORD_DELETE`) как обычно.

### Ожидание

Все остальные SSE-события работают как раньше (FR-008, «без
изменений»).

## Диагностика (если что-то пошло не так)

### Проверка состояния JVM-поля

Если есть сомнения, что `@Volatile` инициализируется корректно —
через remote debug или через временный лог можно добавить
`println("lastSentCountWaiting = $lastSentCountWaiting")` в
`sendCountWaitingMessage` (после имплементации, в отдельном
debug-коммите, который потом откатить).

### Проверка call-sites

```bash
grep -n "sendCountWaitingMessage" karaoke-app/src/main/kotlin/ -r
```

Должно быть **ровно 5** мест вызова (один из них — само определение
функции; остальные 4 — call-sites в `KaraokeProcess.kt`,
`KaraokeProcessWorker.kt` × 2).

Если число отличается — при имплементации пропустили call-site;
все они должны идти через единую `sendCountWaitingMessage` с
дедупликацией, не плодить новых вызовов напрямую в `SNS.send`.

### Что НЕ нужно проверять

- Нагрузочное тестирование (фича не зависит от числа подписчиков).
- Сетевые задержки (формат wire не меняется).
- Совместимость со старыми версиями webvue3 (формат payload
  идентичен).
