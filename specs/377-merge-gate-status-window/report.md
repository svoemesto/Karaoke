# Отчёт по KARAOKE-377 «merge-гейт считает агрегат по усечённому окну статусов (30 из 33) — merge проходит при красном CI»

* **Issue**: KARAOKE-377 (Plane, проект KARAOKE, тип `type:bug`)
* **Ветка**: `706-ci-gate-fixes` → PR #51 (https://git.sm-karaoke.ru/svoemesto/Karaoke/pulls/51)
* **Дата**: 2026-11-01
* **Статус**: исправлено, PR #51 смержен (merge-коммит `422d16c8`)

## Уточнение формулировки задачи

Задача сформулирована как «merge проходит при красном CI». Проверка кода и живой
API этого **не подтверждает**: решение о merge принимает агрегат `ci-summary`,
и гейт отказывает, если агрегата нет, не `success` или выборка статусов
неполна. Реальный дефект — **другой** и противоположный по знаку: выборка
статусов считалась неполной **ложно**, и гейт блокировал merge при зелёном CI.

## Находка (живые данные)

`GET /api/v1/repos/svoemesto/Karaoke/commits/<sha>/status` (Forgejo 17) отдаёт
**по одному статусу на контекст**, но заголовок `X-Total-Count` при этом
считает **сырые записи** журнала статусов — вместе с дублями от нескольких
прогонов одного коммита (push в ветку + pull_request + перезапуски).

Замер на реальных коммитах:

| Коммит | X-Total-Count | уникальных контекстов в `/status` |
|---|---|---|
| `b23b16cf` (master, полный набор) | 37 | 30 |
| `d4f141ce` (head PR #50) | 30 | 30 |

Старая проверка в `tools/merge-pr.sh` сравнивала число собранных уникальных
статусов с `X-Total-Count` и при `len(out) < expected` завершалась с кодом `3`
(«выборка неполна» → merge не выполнять). Для коммита с двумя прогонами это
даёт `30 < 37` → **ложный отказ** при полностью зелёном CI.

Важно: эта же проверка была **единственной** страховкой от противоположного
сценария — «API отдал только первые 30 контекстов из 37, красный `ci-summary`
не попал в выборку, merge прошёл». Ослаблять её было нельзя, поэтому задача
решается не удалением проверки, а заменой её эталона.

## Что сделано

1. Сбор статусов вынесен из `tools/merge-pr.sh` в отдельный инструмент
   `tools/merge-gate-statuses.py` (тестируемость + единая точка правды):
   * по одному статусу на контекст; при дубле (два прогона) берётся более
     свежий по `updated_at`;
   * **полнота определяется фактом пагинации** (страницы дошли до конца), а
     `X-Total-Count` идёт в диагностику («сырых записей N, уникальных
     контекстов M»);
   * код `3` («выборка неполна») сохранён и срабатывает, когда пагинация
     упёрлась в лимит страниц, а последняя страница непустая — fail-closed
     не ослаблен.
2. Фикстуры `tools/fixtures/merge-gate/`:
   * `full` — 37 контекстов на двух страницах (полная выборка);
   * `dedup` — 37 сырых записей / 30 уникальных контекстов (ровно тот случай,
     который ломал гейт);
   * `truncated` — недообор (пагинация исчерпана).
3. `--self-test` нового инструмента проверяет все три случая; он же добавлен
   шагом в CI-джоб `ci-checks-manifest-guard` **обеих** копий workflow.
4. Знание: `knowledge/system/infra/ci-tools.md` — таблица guard'ов (новая
   строка) и § «Где исполняется CI» (сбор статус-чеков merge-гейта).

## Остаточные риски

* Эталон полноты теперь — «пагинация дошла до конца». Если API начнёт отдавать
  пустую страницу при непустой выборке (смена контракта Forgejo), гейт решит,
  что выборка полна. Страховка — лимит страниц (50) и сам агрегат
  `ci-summary`: при его отсутствии гейт всё равно отказывает.
