## Ключевые решения (приняты лидом, спека не менялась)

1. **Правило живёт в одном месте** — `config/ci/checks.yml` + `tools/ci-checks.py`.
   Workflow, pre-commit и компоненты маппинг «правка → проверки» не дублируют.
2. **Зона = то, что проверка реально инспектирует** (по внутренним паттернам её
   реализации), с доказательством `файл:строка`. Проверка, обходящая весь
   репозиторий, не получает зону `**`.
3. **FR-004 строгий**: путь вне объединения зон ⇒ полный набор проверок.
4. **Пропущенная проверка ≠ «зелёная»**: Forgejo не умеет статус `skipped`,
   поэтому единственный сигнал для решения — агрегат `ci-summary`.
5. **Проверка истории git не пропускается никогда** (вынесена в отдельный джоб).
6. **`known_unmapped`** — необязательная секция манифеста для путей, которые
   утверждённо не читает ни одна проверка. **По умолчанию пуста** ⇒ поведение
   строго по FR-004.

## CI на PR #41: что вскрыли прогоны

Первые прогоны на PR #41 (после пуша ветки) обнаружили два дефекта, которые
невозможно было увидеть без живого CI:

1. **Прогон 205 — все проверки пропущены.** Выходы джоба `changes` не попали в
   условия: act_runner (Forgejo) читает выходы шага **из файла `$GITHUB_OUTPUT`**,
   а не из stdout шага (как GitHub Actions). Итог: 34 проверки со статусом
   «Has been skipped», выполнились только три служебных джоба — фича молча не
   работала. Исправлено: `tools/ci-checks.py` при наличии `$GITHUB_OUTPUT`
   дописывает туда те же `key=value`, что печатает в stdout; добавлена фикстура
   self-test на запись в файл.
2. **Прогон 206 — красный джоб `ci-checks-manifest-guard`.** Его checkout был
   shallow (depth 1), а фикстура self-test правила считала изменения относительно
   `HEAD^` → merge-base не найден → код 2 → SELF-TEST red. Исправлено: фикстура
   не зависит от истории (база = `HEAD`), джоб чекинится с `fetch-depth: 0`.
3. **Промежуточный дефект — невалидный YAML.** В имени шага было «Checkout (полная
   история: …)»: двоеточие в некавычном скаляре роняет **весь** workflow до
   старта джобов. Исправлено сразу после обнаружения (прогон 207).

Урок для ревью: «зелёный» статус у Forgejo не означает «правила работали» —
пропущенный джоб отдаётся как `success`. Проверять надо **содержимое** прогона
(какие джобы выполнены, а какие помечены «Has been skipped»), а не агрегированный
статус.
