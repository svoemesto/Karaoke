# Feature Specification: Выбор поискового движка для текстов песен и обложек альбомов

**Feature Branch**: `015-search-engine-selection`

**Created**: 2026-07-27

**Status**: Draft

**Input**: User description: "Добавить настройки выбора поискового движка отдельно для поиска текстов песен (4 варианта: Яндекс синхронный, Яндекс асинхронный, SearXNG, 4get) и отдельно для поиска обложек альбомов (2 варианта: SearXNG, 4get). В механизме поиска текстов песен добавить вопрос «Выполнить поиск заново?» с очисткой старых результатов и выбором движка, плюс отдельную кнопку «Удалить результаты поиска»."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Настройка движка поиска по умолчанию (Priority: P1)

Администратор проекта задаёт в настройках приложения, какой поисковый движок
используется по умолчанию — отдельно для поиска текстов песен (один из
четырёх: Яндекс-синхронный, Яндекс-асинхронный, SearXNG, 4get) и отдельно для
поиска обложек альбомов (один из двух: SearXNG, 4get — варианты на основе
Яндекса для обложек не предлагаются, так как они физически не умеют искать
картинки, только текстовые веб-результаты).

**Why this priority**: Без этой настройки нечего выбирать в диалогах поиска —
это основа для остальных историй. У четырёх движков поиска текста разные
компромиссы по цене/скорости/точности (см. Assumptions), и оператор должен
иметь возможность поменять используемый по умолчанию движок без участия
разработчика.

**Independent Test**: Сменить в настройках движок поиска текстов песен на
другой из четырёх, запустить поиск текста для песни, у которой ещё нет
сохранённых результатов поиска, и убедиться, что использован именно вновь
выбранный движок. Аналогично для движка обложек альбомов (один из двух).

**Acceptance Scenarios**:

1. **Given** в настройках выбран определённый движок поиска текстов песен,
   **When** оператор запускает поиск текста для песни без ранее сохранённых
   результатов, **Then** поиск выполняется именно этим движком.
2. **Given** в настройках выбран определённый движок поиска обложек альбомов,
   **When** оператор запускает поиск обложки альбома, **Then** поиск
   выполняется именно этим движком.
3. **Given** список движков для обложек альбомов, **When** оператор открывает
   настройку, **Then** видит только 2 варианта (SearXNG, 4get) — варианты на
   основе Яндекса не показываются как выбор для обложек.

---

### User Story 2 - Повторный поиск текста песни с выбором движка (Priority: P2)

В окне результатов поиска текста песни (открывается из редактора текста песни)
оператор может явно запросить повторный поиск («Выполнить поиск заново?»).
Перед повторным поиском ранее сохранённые для этой песни результаты
удаляются, и оператор указывает, каким из четырёх движков искать на этот раз
— независимо от движка по умолчанию из настроек.

**Why this priority**: Сегодня, если для песни уже есть сохранённый результат
поиска (даже пустой или неудачный), система просто возвращает его и новый
поиск не запускает — единственный способ «переискать» другим движком.
Именно это стало причиной всей задачи: после смены движка по умолчанию старые
пустые результаты для уже проверенных песен не обновляются сами по себе.

**Independent Test**: Взять песню, для которой уже есть сохранённые (в т.ч.
неудачные/пустые) результаты поиска текста. Запросить повторный поиск, выбрать
другой движок в диалоге, подтвердить. Убедиться, что старые результаты
исчезли, а новые получены выбранным движком.

**Acceptance Scenarios**:

1. **Given** для песни уже есть сохранённые результаты поиска текста,
   **When** оператор нажимает «Искать заново» в окне результатов поиска,
   **Then** система спрашивает подтверждение («Выполнить поиск заново?») и
   предлагает выбрать один из четырёх движков.
2. **Given** оператор подтвердил повторный поиск и выбрал движок,
   **When** поиск запускается, **Then** ранее сохранённые результаты поиска
   для этой песни удалены, а новые результаты получены выбранным движком.
3. **Given** оператор открыл диалог повторного поиска, **When** он отменяет
   подтверждение, **Then** старые результаты остаются нетронутыми, новый
   поиск не запускается.

---

### User Story 3 - Удаление результатов поиска без повторного поиска (Priority: P3)

В том же окне результатов поиска текста песни оператор может нажать «Удалить
результаты поиска», чтобы просто очистить сохранённые (устаревшие/неверные)
результаты для этой песни — без обязательного немедленного нового поиска.

**Why this priority**: Отдельная, более простая операция очистки — полезна,
когда оператор хочет убрать мусорные результаты, но не готов сразу запускать
новый поиск (например, движок временно недоступен).

**Independent Test**: Для песни с сохранёнными результатами поиска нажать
«Удалить результаты поиска», подтвердить. Убедиться, что результаты исчезли
из окна и из данных песни, а новый поиск не был запущен автоматически.

**Acceptance Scenarios**:

1. **Given** для песни есть сохранённые результаты поиска текста,
   **When** оператор нажимает «Удалить результаты поиска» и подтверждает,
   **Then** все сохранённые результаты поиска для этой песни удаляются, новый
   поиск не запускается.
2. **Given** оператор нажал «Удалить результаты поиска», **When** он не
   подтверждает действие, **Then** результаты остаются без изменений.

---

### User Story 4 - Очистка результатов поиска для готовых песен (Priority: P4)

Как только песня становится «готовой» (статус ≥3 — тот же порог, что уже
используется для показа песни в публичном плеере), сохранённые результаты
поиска текста для неё автоматически удаляются — они больше не нужны и не
должны занимать место в таблицах результатов поиска. Для песен, ставших
готовыми ДО появления этой автоматической очистки, администратор может
запустить массовую очистку одной кнопкой на главной странице админки.

**Why this priority**: Это чисто эксплуатационная гигиена (место в таблицах),
не блокирует и не расширяет основной пользовательский сценарий поиска текста
— может быть добавлено последним, после того как остальные истории уже
работают.

**Independent Test**: Перевести песню в статус ≥3 (например, финальным этапом
обработки) и убедиться, что её результаты поиска исчезли из таблиц.
Отдельно — для набора уже готовых песен со старыми результатами поиска
нажать кнопку «Удалить результаты поиска готовых песен» на главной странице
и убедиться, что результаты этих песен удалены, а результаты песен со
статусом <3 не тронуты.

**Acceptance Scenarios**:

1. **Given** у песни есть сохранённые результаты поиска текста и статус <3,
   **When** статус песни меняется на ≥3, **Then** сохранённые результаты
   поиска для этой песни автоматически удаляются.
2. **Given** у песни статус уже был ≥3 и он остаётся ≥3 (не пересекает
   порог заново), **When** песня сохраняется по другой причине, **Then**
   автоматическая очистка результатов поиска повторно не запускается лишний
   раз (нет уже — нечего удалять; если есть — уже должны были быть удалены
   при первом пересечении порога).
3. **Given** на главной странице администратор нажимает «Удалить результаты
   поиска готовых песен», **When** операция выполняется, **Then** удалены
   результаты поиска ВСЕХ песен со статусом ≥3, результаты песен со статусом
   <3 не затронуты, администратор видит итоговое количество обработанных
   песен.

---

### Edge Cases

- Что если повторный/новый поиск запущен, пока предыдущий асинхронный запрос
  (Яндекс-асинхронный) ещё не завершился? Система не должна создать
  противоречивые/задвоенные записи результатов для одной песни.
- Что если оператор запрашивает повторный поиск, а выбранный движок временно
  недоступен (см. известные ловушки в `docs/features/llm-lyrics-search.md`)?
  Старые результаты уже удалены — оператор должен явно увидеть, что новых
  результатов не найдено, и не остаться без старых результатов «непонятно
  почему».
- Смена движка по умолчанию в настройках не должна задним числом менять или
  удалять уже сохранённые результаты поиска других песен, найденные ранее
  другим движком.
- Поиск обложек альбомов не получает в этой задаче собственного диалога
  «искать заново»/«удалить результаты» — только настройку движка по
  умолчанию (см. Assumptions, сознательно вынесено за рамки).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система ДОЛЖНА позволять выбрать в настройках приложения движок
  поиска текстов песен по умолчанию — один из четырёх: Яндекс (синхронный),
  Яндекс (асинхронный), SearXNG, 4get.
- **FR-002**: Система ДОЛЖНА позволять выбрать в настройках приложения,
  отдельно от FR-001, движок поиска обложек альбомов по умолчанию — один из
  двух: SearXNG, 4get.
- **FR-003**: При запуске поиска текста песни для песни без ранее сохранённых
  результатов система ДОЛЖНА использовать движок, заданный по умолчанию в
  настройках (FR-001).
- **FR-004**: При запуске поиска обложки альбома система ДОЛЖНА использовать
  движок, заданный по умолчанию в настройках (FR-002).
- **FR-005**: В окне результатов поиска текста песни система ДОЛЖНА
  предоставить действие «Выполнить поиск заново?», требующее явного
  подтверждения оператором.
- **FR-006**: Диалог подтверждения повторного поиска (FR-005) ДОЛЖЕН
  позволять оператору выбрать, каким из четырёх движков (см. FR-001) искать
  на этот раз — независимо от текущего движка по умолчанию.
- **FR-007**: При подтверждении повторного поиска система ДОЛЖНА сначала
  удалить все ранее сохранённые результаты поиска текста для этой песни, а
  затем запустить новый поиск выбранным движком.
- **FR-008**: В том же окне результатов поиска текста песни система ДОЛЖНА
  предоставить отдельное действие «Удалить результаты поиска», требующее
  подтверждения и удаляющее сохранённые результаты поиска для этой песни без
  запуска нового поиска.
- **FR-009**: Отмена подтверждения (FR-005 или FR-008) НЕ ДОЛЖНА приводить ни
  к удалению результатов, ни к запуску нового поиска.
- **FR-010**: Изменение движка по умолчанию в настройках НЕ ДОЛЖНО изменять
  или удалять уже сохранённые результаты поиска, полученные ранее другим
  движком.
- **FR-011**: Как только статус песни пересекает порог готовности (становится
  ≥3, придя из значения <3), система ДОЛЖНА автоматически удалить все
  сохранённые результаты поиска текста для этой песни.
- **FR-012**: Система ДОЛЖНА предоставить на главной странице администратора
  действие «Удалить результаты поиска готовых песен», удаляющее сохранённые
  результаты поиска текста для ВСЕХ песен со статусом ≥3 одним запуском.
- **FR-013**: Действие из FR-012 НЕ ДОЛЖНО удалять результаты поиска песен со
  статусом <3.

### Key Entities

- **Настройка движка поиска текстов песен**: одно из четырёх значений
  (Яндекс-синхронный / Яндекс-асинхронный / SearXNG / 4get), глобальное для
  приложения, изменяемое администратором.
- **Настройка движка поиска обложек альбомов**: одно из двух значений
  (SearXNG / 4get), глобальное для приложения, независимое от предыдущей.
- **Результаты поиска текста песни** (существующая сущность): набор
  найденных ссылок/текстов для конкретной песни; в рамках этой задачи
  добавляется возможность их массового удаления по запросу оператора для
  данной песни.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Администратор может независимо друг от друга сменить движок
  поиска текстов песен и движок поиска обложек альбомов через настройки, и
  следующий новый поиск каждого типа использует вновь выбранный движок — без
  участия разработчика/переразвёртывания.
- **SC-002**: Оператор может повторно найти текст песни, для которой уже
  были (в том числе неудачные) результаты, выбрав конкретный движок, — одним
  действием с подтверждением, без прямого вмешательства в базу данных.
- **SC-003**: Оператор может очистить сохранённые результаты поиска текста
  песни одним действием с подтверждением, не запуская при этом новый поиск.
- **SC-004**: В выборе движка для обложек альбомов никогда не показываются
  варианты на основе Яндекса (которые для этой цели физически не работают).
- **SC-005**: Ни одно из действий (смена настройки, повторный поиск, удаление
  результатов) не приводит к падению приложения или к порче результатов
  поиска других песен.
- **SC-006**: Таблицы результатов поиска не накапливают записи для песен,
  уже ставших готовыми (статус ≥3) — как автоматически (по мере готовности
  новых песен), так и по явному запросу администратора для уже готовых
  ранее песен.

## Assumptions

- Четыре движка поиска текстов песен — с разными компромиссами (по описанию
  пользователя): Яндекс-синхронный (быстро, но дорого), Яндекс-асинхронный
  (дешевле, но дольше), SearXNG (быстро, бесплатно, менее точно), 4get
  (быстро, бесплатно, точнее) — поэтому оба варианта Яндекса остаются
  раздельными пунктами выбора, а не объединяются в один.
- Поиск обложек альбомов сознательно ограничен 2 движками (SearXNG, 4get) —
  Яндекс-варианты возвращают только текстовые веб-результаты, а не картинки,
  и не рассматриваются как источник обложек в этой задаче (решение
  пользователя).
- Поиск обложек альбомов НЕ получает в этой задаче собственный UI
  «искать заново»/«удалить результаты» — только настройку движка по
  умолчанию; отдельный UI для обложек может быть будущей задачей.
- «Удалить результаты поиска» и «искать заново» действуют в рамках одной
  конкретной песни (по songId), не массово по всем песням.
- Отдельный путь поиска обложек через Яндекс.Музыку
  (`findYandexAlbumCovers`/Playwright, авторизованная сессия) этой задачей не
  затрагивается — это другой механизм, не входящий в 4/2 перечисленных
  движка.
- Конкретные названия настроек, эндпоинтов, UI-компонентов и структура
  данных — технические решения, принимаемые на этапе планирования
  (`/speckit-plan`), а не в этой спецификации.
- Проверка реализованного — вручную/в интеграционном режиме, по принятой в
  проекте практике (автотесты не требуются, см. `constitution.md`).
- «Порог готовности» (статус ≥3) в FR-011..FR-013 — тот же порог, что уже
  используется в проекте для показа песни в публичном плеере (не новое
  понятие, вводимое этой задачей).
- Если статус песни впоследствии понижается обратно ниже 3, результаты
  поиска НЕ восстанавливаются автоматически — оператор может запустить новый
  поиск обычным способом (US1/US2), если понадобится текст снова.
- Массовая очистка (FR-012) — тяжёлая по времени операция (проход по всем
  готовым песням) и выполняется в фоне, не блокируя интерфейс администратора
  (по аналогии с уже существующими фоновыми массовыми операциями на главной
  странице, например пересчётом готовности плеера).
