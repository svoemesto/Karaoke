# Отчёт по KARAOKE-378 «workflow_dispatch не создаёт commit-статусы — подсказка "перезапусти прогон" в merge-гейте не работает»

* **Issue**: KARAOKE-378 (Plane, проект KARAOKE, тип `type:bug`)
* **Ветка**: `706-ci-gate-fixes` → PR #51 (https://git.sm-karaoke.ru/svoemesto/Karaoke/pulls/51)
* **Дата**: 2026-11-01
* **Статус**: исправлено, PR #51 смержен (merge-коммит `422d16c8`)

## Находка

Гейт `tools/merge-pr.sh` при отказе печатал подсказку «Что делать», где
перезапуск прогона предлагался делать через **workflow_dispatch**:

```
curl -X POST ... /actions/workflows/lint.yml/dispatches  -d '{"ref":"<ветка PR>"}'
```

Но прогон, запущенный через `workflow_dispatch`, **статус-чеков не создаёт** —
а именно статус-чеки нужны гейту, чтобы увидеть новый результат `ci-summary`.
Предлагался способ, который не может изменить состояние, на которое смотрит
гейт, — подсказка была бесполезной.

Проверка на живом прогоне (старый прогон `598`, коммит `d4f141ce`):

```
POST /api/v1/repos/svoemesto/Karaoke/actions/runs/598/rerun   → http 204
```

Через ~100 с статус-чеки коммита обновились (`updated_at` стал свежим, состав
контекстов пересчитан: 25 skipped/5 success → 27 skipped/3 success), то есть
`rerun` статус-чеки создаёт и обновляет.

## Что сделано

1. `tools/merge-pr.sh`: в подсказке «Что делать» перезапуск теперь предлагается
   рабочим способом — `POST /actions/runs/<run_id>/rerun`; если rerun
   недоступен — обычный прогон пустым коммитом в ветку PR
   (`git commit --allow-empty; git push`), потому что push создаёт статус-чеки.
2. В подсказке пояснено, что `run_id` — **внутренний** id прогона из
   `GET /actions/runs`, а не число, показанное в интерфейсе (интерфейсный
   номер даёт 404). Указана ссылка на
   `knowledge/guidelines/runbooks/forgejo-access.md`.
3. Уточнена формулировка предупреждения: `workflow_dispatch` статус-чеков не
   создаёт; агрегат `ci-summary` появляется после обычного прогона (push/PR)
   **или** rerun.
4. Знание: `knowledge/system/infra/ci-tools.md` — § «Где исполняется CI» и
   таблица guard'ов (KARAOKE-376/377/378).

## Проверка

* `POST /actions/runs/598/rerun` → http 204; статус-чеки коммита `d4f141ce`
  обновились (свежий `updated_at`) ✓ — команда в подсказке рабочая.
* `bash -n tools/merge-pr.sh` — синтаксис в порядке ✓.
* Подсказка покрыта теми же локальными проверками, что и весь гейт
  (`tools/merge-pr.sh` — точка входа в master, поведение при отказе).

## Остаточные риски

* `rerun` перезапускает прогон на **том же** коммите и с тем же набором
  джобов; если причина сбоя — в самом коммите, повторный прогон снова будет
  красным (это ожидаемое поведение, подсказка прямо говорит «разбор с
  владельцем, не merge»).
