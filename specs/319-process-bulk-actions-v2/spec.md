## Context

В admin-SPA (`webvue3`) для сущности «Песни» (`SongsTable`) реализован набор массовых
действий над выборкой из текущего фильтра: «массовый демукс», «массовое создание
караоке», «массовый поиск текста» и т. п. Каждое действие работает с **множеством
объектов**, отобранных фильтром, и подтверждается отдельным диалогом.

Для сущности «Процессы» (`ProcessesTable`) аналогичных массовых действий нет: чтобы
изменить приоритет с 0 на −1 или удалить ERROR-процессы, администратор открывает
каждую запись вручную через `ProcessEditModal` / `ProcessDeleteModal`. Это неудобно
при работе с большими пачками legacy-хвостов (после миграции `48_chain_id_backfill`
на проде осталось 13 169 «хвостовых» процессов), ручных чистках и массовых ретраях
упавших задач.

WP #68 просит **первые два** массовых действия (явно помечено «для начала»), по
симметрии с паттерном песен:

1. **Изменение поля** у всех процессов в выборке (упомянутые примеры: приоритет
   `0 → −1`, статус `ERROR → WAITING`).
2. **Удаление** всех процессов в выборке.

Каркас должен быть **расширяемым**: новые массовые действия (например, ретрай,
восстановление из soft-delete, смена `chainId` пачкой) добавляются позже без
переделки архитектуры.

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Массовое изменение поля процессов (Priority: P1)

Администратор хочет единым жестом понизить приоритет у большой группы процессов —
например, у всех ERROR-процессов старше 7 дней с приоритетом 0, отобранных
текущим фильтром в `ProcessesTable`. Сейчас это требует ручного прохода по
каждой строке и открытия `ProcessEditModal`. С новой фичей администратор:

1. Задаёт фильтр (как обычно).
2. Видит в `ProcessesTable` счётчик «отобрано N процессов».
3. Нажимает кнопку «Массовое действие → Изменить поле».
4. В диалоге выбирает поле (приоритет / статус / …) и вводит новое значение
   (с валидацией — см. FR-003).
5. Видит превью: «Будет изменено: N процессов, поле X, старое значение Y».
6. Подтверждает.
7. Видит прогресс (сколько из N уже обработано, сколько ошибок).
8. По завершении получает отчёт: «Изменено: K из N. Ошибки: M (см. список)».

**Why this priority**: P1 — основная боль, ради которой заведена задача. Без
этого фича не имеет смысла.

**Independent Test**: На dev-стенде создать 5 ERROR-процессов, отобрать их
фильтром, изменить статус на WAITING, проверить в БД, что у всех 5 статус = WAITING,
а другие процессы не затронуты.

**Acceptance Scenarios**:

1. **Given** фильтр отобрал 10 процессов, **When** админ выполняет «изменить поле» на priority,
   **Then** все 10 процессов получают новое значение priority, в `ProcessesTable` видно обновление,
   в audit-trail — 10 записей с actor=admin, action=bulk_update_field.
2. **Given** фильтр отобрал 10 процессов, **When** админ вводит невалидное значение
   (например, status = "НЕ_СУЩЕСТВУЕТ"), **Then** диалог показывает ошибку валидации,
   backend-вызов не выполняется.
3. **Given** во время bulk-операции у одного из процессов сменился статус
   (параллельная правка), **When** операция завершается, **Then** затронуты
   остальные 9; по 10-му — отчёт «пропущен (конфликт версии)».
4. **Given** фильтр отобрал 0 процессов, **When** админ открывает меню массовых действий,
   **Then** кнопка «Изменить поле» disabled с tooltip «нет процессов в выборке».

### User Story 2 — Массовое удаление процессов (Priority: P1)

Администратор хочет за один раз избавиться от большой пачки мусорных процессов
(ERROR-процессы без связанных файлов, дубликаты после миграции, отменённые задачи).
Сейчас — только по одному через `ProcessDeleteModal`.

1. Задаёт фильтр.
2. Нажимает «Массовое действие → Удалить».
3. Диалог предупреждает: «Будет удалено N процессов. Действие **необратимо**
   (см. Assumptions про soft vs hard delete)».
4. Требует ввести слово-подтверждение (например, имя операции «УДАЛИТЬ») при
   N > 100 — для защиты от случайного клика.
5. Подтверждает.
6. Видит прогресс и финальный отчёт.

**Why this priority**: P1 — равноценная боль с bulk-edit, и задача WP #68
явно их объединяет в первой итерации.

**Independent Test**: На dev-стенде создать 10 «мусорных» процессов, отобрать
фильтром, выполнить bulk-удаление, проверить, что 10 процессов отсутствуют в
выдаче (soft-delete: отсутствуют в живом списке; см. Assumptions).

**Acceptance Scenarios**:

1. **Given** фильтр отобрал 50 процессов, **When** админ подтверждает удаление,
   **Then** все 50 исчезают из таблицы, в audit-trail — 50 записей `bulk_delete`.
2. **Given** фильтр отобрал 50 процессов, среди которых 5 «активных»
   (WORKING/DONE с недавней активностью), **When** админ подтверждает удаление,
   **Then** диалог показывает предупреждение «5 активных процессов будут удалены»;
   финальный отчёт: «Удалено: 50, активных среди удалённых: 5».
3. **Given** фильтр отобрал 0 процессов, **When** админ открывает меню,
   **Then** кнопка «Удалить» disabled.
4. **Given** админ ввёл неверное слово подтверждения, **When** нажимает «Подтвердить»,
   **Then** ничего не происходит + сообщение об ошибке.

### User Story 3 — Отчёт и аудит массовых операций (Priority: P2)

После любой массовой операции администратор должен иметь возможность увидеть,
**что именно** было изменено: какие процессы, какие поля, старые/новые значения,
когда, кем. Это нужно и для отката (вручную через SQL/audit-trail), и для
расследования спорных ситуаций.

1. После завершения bulk-операции появляется уведомление «Готово: K из N.
   Открыть отчёт».
2. По клику — таблица/экран с детальным отчётом (можно отдельной страницей
   или модалкой).
3. Каждая строка отчёта содержит: ID процесса, действие, старое значение,
   новое значение, timestamp, результат (ok/error).
4. Отчёт можно выгрузить в CSV.

**Why this priority**: P2 — не блокирует основной сценарий, но без него
bulk-операции страшно запускать на больших выборках. Достаточно минимального
варианта: счётчик + список ID с результатом.

**Independent Test**: Запустить bulk-edit на 100 процессов, после завершения
открыть отчёт, проверить, что ровно 100 строк, каждая содержит ID + diff.

**Acceptance Scenarios**:

1. **Given** bulk-edit завершился успешно, **When** админ открывает отчёт,
   **Then** он содержит ровно K строк (K = число успешно изменённых).
2. **Given** часть операций завершилась ошибкой, **When** админ открывает отчёт,
   **Then** строки разделены на «Успех» и «Ошибки», для каждой ошибки — причина.

### Edge Cases

- **Параллельная правка** во время bulk-операции (оптимистичная блокировка по `version`/
  `updated_at`, если поле есть в схеме; иначе — best-effort, отчёт о расхождениях).
- **Изменение фильтра во время выполнения** — операция идёт по **снимку** ID на момент
  старта, не по динамическому фильтру.
- **Очень большая выборка** (10 000+ процессов) — UI должен показывать прогресс,
  backend должен работать пачками (см. Assumptions).
- **Админ закрыл вкладку / потерял сессию во время операции** — операция либо
  завершается на backend, либо отменяется по таймауту (см. FR-007).
- **Один и тот же процесс попал в выборку дважды** (теоретически возможно при
  определённых фильтрах) — не должен быть обработан дважды.
- **Удаление процесса, на который ссылается другой процесс** (связь через `chainId`
  / `threadId`) — проверить, нет ли FK-блокировки; если есть — отчёт с понятной ошибкой.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: System MUST отображать в `ProcessesTable` группу кнопок «Массовые действия»
  с пунктами «Изменить поле» и «Удалить», enabled только когда фильтр вернул ≥ 1 процесс.
- **FR-002**: System MUST показывать счётчик «отобрано: N процессов» рядом с группой
  кнопок, обновляющийся синхронно с фильтром.
- **FR-003**: System MUST валидировать значение поля ДО отправки на backend: для перечислений
  (статус) — только допустимые значения; для чисел (приоритет) — целое в допустимом диапазоне
  (см. Assumptions про priority).
- **FR-004**: System MUST работать по **снимку ID** на момент запуска операции, не по
  динамическому фильтру — изменение фильтра во время выполнения не должно менять выборку.
- **FR-005**: System MUST записывать каждую bulk-операцию в существующий audit-trail
  (`tbl_processes_audit`): actor, action (`bulk_update_field` / `bulk_delete`),
  process_id, old_value, new_value, batch_id (общий UUID операции), created_at.
  **Важно**: для bulk_delete каскадное удаление (FK ON DELETE CASCADE,
  см. A-001) стирает audit-записи вместе с процессом. Это согласованное поведение
  для hard-delete («без следов в БД»), но админ должен это понимать. Если в будущем
  потребуется сохранять audit-trail после hard-delete — отдельная миграция
  (FK → ON DELETE SET NULL).
- **FR-006**: System MUST для bulk-edit возвращать отчёт с числом успешно изменённых,
  числом ошибок и списком ошибок (process_id + причина).
- **FR-007**: System MUST для bulk-операций > 1000 процессов работать асинхронно
  (запуск через существующий механизм `KaraokeTask`), показывать прогресс в UI
  и сохранять результат до явного закрытия админом.
- **FR-008**: System MUST для bulk-delete показывать confirm-диалог с текстом
  «Будет удалено N процессов. Действие необратимо». Без ввода слова — на любом
  размере выборки (см. Clarifications Q2, 2026-09-08).
- **FR-009**: System MUST для bulk-edit поддерживать как минимум поля `priority`,
  `status`, `threadId` (прецедент — поля в `ProcessEditModal`). Архитектура
  должна позволять добавить другие поля (например, `chainId`) без breaking changes.
- **FR-010**: System MUST при bulk-edit применять те же transition-правила, что и
  single-record edit (FR-017 спеки #315): запрещённые переходы отклоняются, валидные — проходят.
- **FR-011**: System MUST для bulk-edit и bulk-delete быть доступным только
  аутентифицированному админу (текущая модель — один админ, Constitution V).

### Key Entities

- **Process** (существующая сущность): id, priority (Int), status (enum: CREATING/WAITING/
  WORKING/DONE/ERROR), threadId (UUID?), chainId (UUID?), process_deleted_at (timestamp?),
  audit-fields. Все атрибуты редактируются через существующие single-record потоки.
- **Bulk Operation Report** (новое представление, не новая таблица): batch_id (UUID),
  started_at, finished_at, actor, action (bulk_update_field | bulk_delete),
  requested_count, success_count, error_count, errors (list of {process_id, reason}).
  Хранится в существующем `tbl_processes_audit` (одна строка = одно действие над одним
  процессом; batch_id — общая группировка).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Администратор может изменить поле у выборки **из 1000 процессов**
  одним жестом, время от старта до финального отчёта ≤ 60 секунд (UI-измеримо).
- **SC-002**: Администратор может удалить выборку **из 1000 процессов** одним жестом
  за ≤ 60 секунд (с учётом confirm-диалога).
- **SC-003**: Bulk-edit на выборке из N процессов меняет **ровно N записей** в БД
  (или N − errors, если были ошибки — с детальным отчётом); посторонние процессы не затронуты.
- **SC-004**: 100% bulk_update_field операций оставляют записи в `tbl_processes_audit`
  с заполненным `batch_id`, доступные для отчёта и выгрузки в CSV. Bulk_delete НЕ
  оставляет записей в audit (FK CASCADE стирает их вместе с процессом — согласовано
  с Clarifications Q1 «без следов в БД»); см. FR-005.
- **SC-005**: При сбое на одном из этапов bulk-операции (например, ошибка БД на процессе № 50
  из 100) — операция **не откатывается** полностью, а продолжается; в отчёте процесс № 50
  помечен ошибкой с понятной причиной.
- **SC-006**: Закрытие вкладки / потеря сессии админа во время bulk-операции **не приводит**
  к потере данных: операция либо завершается, либо отменяется по таймауту с отчётом.

## Assumptions

- **A-001 Hard-delete для процессов (владелец, 2026-09-08; **уточнено после
  исследования** 2026-09-08)**: Bulk-удаление — физическое
  `DELETE FROM tbl_processes WHERE id IN (...)`. Строка стирается из БД.
  **Sync-миграция НЕ требуется**: `tbl_processes` отсутствует в `SyncRegistry.all`
  (`karaoke-app/.../sync/SyncTarget.kt:503-523`); процессы — локальные, не
  синхронизируются на сервер. Constitution III в этой части неприменима.
  **Audit-trail**: FK `tbl_processes_audit.process_id REFERENCES tbl_processes(id)
  ON DELETE CASCADE` уже настроен миграцией `47_admin_process_audit.sql:35` —
  при hard-delete процесса соответствующие audit-записи каскадно удаляются.
  Это согласовано с явной формулировкой миграции (line 30-32): «если процесс
  hard-deleted вне scope MVP, audit идёт с ним». Решение владельца
  («Hard-delete, без следов в БД») делает это поведение штатным для bulk.
  Single-record `ProcessDeleteModal` остаётся на soft-delete (см. pre-existing
  `KaraokeProcessAdminService.deleteProcess`); явно зафиксировано — два режима
  удаления сосуществуют, это known asymmetry.
- **A-002 Поля для bulk-edit (владелец, 2026-09-08, Clarifications Q3)**: v1
  покрывает ТОЛЬКО `priority`, `status`, `threadId` (поля, доступные в существующем
  `ProcessEditModal`). `chainId` **не входит** в v1 — это отдельная фича с
  превью diff и обязательным подтверждением (риск нарушения целостности цепочки).
  Архитектура bulk-edit расширяема для добавления других полей без breaking
  changes (FR-009).
- **A-003 Диапазон priority**: целое число (включая отрицательные — WP #68 явно просит
  «приоритета с 0 на -1» как пример; в текущей схеме нет ни верхней, ни нижней границы).
- **A-004 Transition-правила status**: те же, что в single-edit (FR-017 спеки #315).
  Прямой переход `DONE → ERROR` через bulk-edit запрещён.
- **A-005 Аудитория**: один админ (Constitution V). Multi-user / RBAC — вне scope.
- **A-006 Размер батча для async**: ≥ 1000 процессов идёт через `KaraokeTask` (UI получает
  прогресс через существующий polling-механизм). Меньше — синхронно.
- **A-007 Производительность**: 1000 процессов за 60 секунд — целевой, не SLO.
  При превышении — оптимизация в отдельной задаче.
- **A-008 Оптимистичная блокировка**: если в `tbl_processes` есть `updated_at` /
  `version` — использовать; если нет — best-effort, в отчёте фиксировать конфликты.
- **A-009 Каркас расширяемый**: backend-эндпоинты и UI-меню спроектированы так, чтобы
  добавление нового массового действия (ретрай, восстановление из soft-delete,
  перепривязка `chainId`) не требовало переделки.

---

## Out of scope (для v1)

- **Bulk-retry** (повторный запуск упавших процессов) — отдельная фича, не в WP #68.
- **Bulk-restore** (снятие `process_deleted_at`) — отдельная фича.
- **Undo bulk-операций** (автоматический откат) — audit-trail даёт возможность
  ручного восстановления, но автоматического undo нет.
- **Workflow-обход transition-валидации в bulk-update** — v1 применяет те же правила,
  что и single-edit (FR-017 спеки #315).
- **Атомарность для батчей > 10 000** — отдельная задача с pagination и chunking.
- **Per-user authorization** (в текущей инсталляции один admin, Constitution V).
- **Замена / перенос существующих single-record `ProcessEditModal` / `ProcessDeleteModal`**
  — они остаются для точечных правок.

## Clarifications

### Session 2026-09-08

- Q1: Bulk-удаление процессов — soft-delete (флаг `process_deleted_at`) или hard-delete
  (`DELETE FROM tbl_processes`)?
  **A: Hard-delete** (владелец, 2026-09-08). Физически удаляем строку.
  Уточнение после исследования (Stage 3): `tbl_processes` НЕ в `SyncRegistry.all`
  → миграция по sync не нужна. FK на `tbl_processes_audit` уже `ON DELETE CASCADE`
  → audit-строки удаляются вместе с процессом (согласовано с решением
  «без следов в БД»). Single-record `ProcessDeleteModal` остаётся на soft-delete —
  явно зафиксированная asymmetry, не баг.
- Q2: Bulk-delete — confirm-word «УДАЛИТЬ» при N > 100, или всегда обычный confirm-диалог?
  **A: Только confirm-диалог** (владелец, 2026-09-08). Без ввода слова ни на каком
  размере выборки. FR-008 упрощён: любой bulk-delete подтверждается обычным
  confirm-диалогом. Согласовано с симметрией single-record `ProcessDeleteModal`.
- Q3: `chainId` — в v1 bulk-edit или нет?
  **A: НЕ в v1** (владелец, 2026-09-08). v1 покрывает `priority`/`status`/`threadId`
  только. `chainId` — отдельная фича с превью diff и обязательным подтверждением.
