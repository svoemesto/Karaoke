# Как сделать так, чтобы AI-агент не нарушал правила проекта

> **Дата введения**: 2026-10-31.
> **Источник опыта**: проект Karaoke — карта решений KARAOKE-339, плагин
> `agent-command-guard`, ADR `local-0016`.
> **Канон правил проекта**: `AGENTS.md` (у нас v3.9.0). Этот файл — **не** ещё
> один список правил, а описание **механики их защиты** и инструкция по переносу
> в другой проект.
> **Как пользоваться**: коллега с агентом в своём проекте читает разделы 1–3,
> выполняет рецепт раздела 4 и проверяет себя по чек-листу раздела 8.
> Разделы 5–7 — про переносимость стека и о наших ошибках; их стоит прочитать
> **до** внедрения, а не после.

## 1. Главное, что нужно понять до начала

**Инструкция «не делай X» не работает.** Мы это знаем не теоретически: за
2026-08…2026-10 разбор инцидентов нашёл 8 подтверждённых нарушений Hard Gates
собственными агентами — при том, что правила были написаны, опубликованы в
`AGENTS.md` и проверялись человеком на ревью.

**Цель формулировки меняется.** «Сделать нарушение невозможным» — недостижимо:
исполнение можно увести в обход рантайма, текст команды можно переписать
(`d''ocker`, `$(echo docker)`, запуск из скрипта-файла, `podman`, `systemctl`,
`kill`, `docker exec`). Реалистичная цель — **остановить, спросить и оставить
след**. Именно так переформулирована цель в нашем `AGENTS.md` (v3.9.0) и в
ADR `local-0016`.

**Защита правила — это не одна проверка, а лестница.** Чем ниже уровень, тем
дешевле он ловит и тем меньше пропускает:

| Уровень | Что ловит | Чего не ловит | Стоимость |
|---|---|---|---|
| 1. Инструкция (`AGENTS.md`) | ошибку в понимании агента | ничего: агент может не соблюдать | бесплатно |
| 2. Pre-commit / линтер в рабочей копии | **намерение** изменить код в запрещённый способ | исполнение вне git (запуск команд, работа с контейнерами) | секунды |
| 3. Runtime-перехват (хост-агента) | **исполнение** команды до её запуска | команды вне перехватываемых инструментов; исполнение вне рантайма агента | единицы миллисекунд |
| 4. CI + защита ветки + merge-гейт | попадание непроверенного кода в основную ветку | всё, что не попадает в репозиторий | минуты |
| 5. Публичный record (тикет/метка) | нарушения, которые не остановили | ничего — это след, а не барьер | бесплатно |

**Правило без enforcement — это пожелание.** Если у правила нет автоматической
проверки, оно держится на дисциплине агента и на ревью человека. Это не
«строгость», это статистика: в инцидентах 2026-09-15 и 2026-10-26 нарушились
именно те правила, у которых не было машинной проверки исполнения.

### 2.1. Чем именно ловит runtime-плагин

Плагин подписан на событие `tools/pre-execute` хоста агента: проверка идёт **до
диспетчеризации вызова**, текст команды виден целиком. Решение — `deny`
(запретить) или `ask` (спросить владельца через approval-канал хоста; при
отсутствии канала — запрет, fail-closed).

Политика — JSON в `~/.dsh/policies/deny-commands.json`, перечитывается **по
mtime** (правка политики применяется без перезапуска). Ключ правила:

```json
{
  "id": "container-restart",
  "severity": "high",
  "mode": "deny",
  "pattern": "^docker\\s+(restart|stop|start)\\s+([\\w-]+\\s+)*karaoke-[a-z0-9-]+",
  "reason": "R-374: контейнеры Karaoke — только через deploy/do.sh и только с согласия владельца."
}
```

Наши восемь правил и их режимы (финальный перечень — KARAOKE-343):

| Правило | Что ловит | Режим |
|---|---|---|
| `container-restart` | прямой `docker restart/stop/start` контейнеров проекта | **deny** |
| `do-sh-consent` | вызовы `deploy/do.sh`, меняющие состояние (`stop_app`, `start_app`, `restart_app`, `build_app`) | **ask** + окно согласия |
| `compose-mutation-karaoke` | `docker compose up/down` в репозитории (обход `do.sh`) | ask |
| `git-force-push` | `git push --force/--force-with-lease/-f` | ask |
| `git-no-verify` | `git commit --no-verify` | ask |
| `git-commit-on-master` | `git commit/rebase/merge` при ветке `master` | ask |
| `git-push-master-refspec` | `git push <remote> master` / `HEAD:master` | ask |
| `branch-protection-mutation` | `gh api -X DELETE/PUT/PATCH … branches/…/protection` | ask |

Два приёма, которые дали качество, а не «ещё правил»:

- **Сегментный разбор.** Команда режется по `&&`, `||`, `;`, `|`, переводу строки,
  и правило проверяет каждый сегмент **отдельно**, с учётом текущего каталога
  (`cd`). Иначе `grep` по тексту правила или `gh pr create --base master`
  ловятся как нарушение.
- **Состояниезависимые правила.** Ветка читается из `.git/HEAD` **рабочего
  каталога** (с учётом worktree через `gitdir:`), а не из текста команды:
  `git commit` в ветке фичи и `git commit` в master неразличимы по строке.

### 2.2. Окно согласия: как фиксируется «владелец разрешил»

Отдельный класс: команда **санкционированная** (`deploy/do.sh`), но вызвана
**без согласия** владельца. По тексту это не отличить от разрешённого вызова —
это состояние, а не текст. Решение: источник согласия отдельный.

| Элемент | У нас |
|---|---|
| Где | `~/.dsh/policies/consent/<session-id>.json` (вне reach агента, рядом с политикой) |
| Формат | `{"session": "<id>", "grantedAt": "<ISO>", "ops": ["restart_app"], "by": "owner"}` |
| Кто пишет | агент — **только по прямому слову владельца**, **до** вызова |
| Кто читает | guard: идентификатор сессии доступен как `exec.agent?.session.id` |
| Срок | до конца сессии; новая сессия — новое окно |
| Не покрывает | прямой `docker restart` и `docker compose` — иначе обход `do.sh` был бы возможен «по окну» |
| Нет сессии | вызов без агента → окно не действует, вопрос задаётся |

### 2.3. Журнал: 12 полей, append-only, NDJSON

Одна строка на вызов `bash`, файл `~/.dsh/ledger/agent-commands.ndjson` (0600):

| Поле | Смысл |
|---|---|
| `ts`, `tool`, `workdir` | время, инструмент, рабочий каталог |
| `command` | полный текст команды; секреты замаскированы **до** записи |
| `rule`, `segment`, `severity` | что сработало, на каком сегменте, насколько серьёзно |
| `verdict`, `mode` | `allow` / `deny` / `ask` и режим правила |
| `test` | флаг пробного нарушения (в Plane не попадает) |
| `session` | идентификатор сессии — связь с окном согласия и журналом сессий |
| `consent` | какая запись согласия действовала в момент вызова |

Полей «кто одобрил» и «какая задача Plane» нет — и это не недоработка:
событие `approval/decided` содержит только `{id, outcome}` (идентификатора
одобрившего в рантайме нет), а задачу знает агент, не плагин.

### 2.4. Сверка процесса: пропуск шагов ловится при закрытии

`tools/check-tracker-workflow.sh` проверяет, что задача прошла обязательные
шаги: исполнитель назначен (claim), комментарий-отчёт опубликован
(add-comment), задача была в состоянии «готово к проверке» (mark-review). Плюс
мягкий сигнал: были ли изменения в `knowledge/` за время жизни задачи.

| Режим | Когда | Что даёт |
|---|---|---|
| `--issue <ID>` | из `close-issue`, перед переводом в «сделано» | живая проверка: состояние задачи на момент закрытия |
| `--sweep --limit N` | вручную или по расписанию | разбор недавно закрытых задач, включая закрытые руками в UI |
| `--step <имя> --issue <ID>` | из CLI трекера | отметка шага в журнале |

Сверка **не блокирует** закрытие: нарушения уходят следом и отчётом, а
публичный record заводит агент. Почему не fail-stop: проверка опирается на
состояние трекера, а трекер не отдаёт историю состояний; блокировка закрытия
из-за сбоя проверки заблокировала бы работу, а агент начал бы искать обход.

### 2.5. Публичный record: нарушение видно не только в файле

Тикет с меткой `type:governance-violation`, родитель — исходная задача,
заводит агент по факту блокировки. Отдельное состояние трекера не нужно:
фильтр «открытые» смотрит на группу состояния, а метку не видит; тикет,
созданный сразу в «сделано», из потока открытых выходит.

## 3. Порядок внедрения: почему именно такой

Мы шли от инцидентов к механизму, и порядок шагов повторяет этот путь.

| Шаг | Что делаем | Почему так |
|---|---|---|
| 1 | Собираем **инциденты**, а не «хочки» | Механизм должен закрывать реальный класс, иначе он — бессмысленная сложность |
| 2 | Классифицируем: правило или процесс | Правило можно закрыть машиной; процесс (пропуск шага workflow) — только сверкой |
| 3 | Раскладываем правило на **уровни защиты** | Инструкция + pre-commit + runtime + CI + record |
| 4 | Проверяем механизм на **реальных данных** | Сначала нашлись 236 ложных срабатываний из 30 335 реальных команд — и только потом механизм стал пригодным |
| 5 | Согласовываем с владельцем **формат и границы** | Публичный record и «деградация агента» — продуктовые решения, не технические |
| 6 | Переносим в **канон** (`AGENTS.md`) с semver-бампом | Правило без ссылки в каноне — это забытое правило |
| 7 | Заводим **критерий измеримости** | «Ноль нарушений» недостижим; измеримо «ноль срабатываний в наблюдаемом канале + ноль необъяснённых изменений среды» |

## 4. Рецепт для своего проекта

Ниже — минимальный набор, который даёт работающий результат. Шаги 1–3
обязательны, шаги 4–6 дают полноту.

### Шаг 1. Инвентаризация правил и их защиты

Возьмите канон правил вашего проекта (`AGENTS.md` / `CLAUDE.md` / системный
промпт агента) и составьте таблицу: **правило | чем защищено | уровень | где
след**. Пустая колонка «чем защищено» — это ваш список работы.

Правило, которое нельзя проверить автоматически, честно помечайте как
процессное: не все правила должны быть машинными, но у каждого должно быть
видно, что оно не защищено.

### Шаг 2. Разделите правила на «текстовые» и «состояниезависимые»

- Текстовые («не пиши `docker restart`») ловятся регуляркой по команде.
- Состояниезависимые («не коммить в master», «не запускай без согласия») по
  тексту неотличимы от легитимного вызова — их надо проверять по окружению
  (`.git/HEAD`, наличие записи согласия) или вообще оставлять на человека.

Разложите команду на сегменты и проверяйте каждый отдельно. Иначе ловятся
`grep` по тексту правила, `gh pr create --base master` и `docker compose` чужих
проектов — это были наши 236 ложных срабатываний.

### Шаг 3. Ловите намерение в pre-commit (уровень 2)

Самая дешёвая защита: скрипт проверяет рабочую копию до коммита.

Упрощённый образец (наш настоящий guard умеет больше — игнорирует markdown и
codeblock'и, имеет режим `--self-test` и коды возврата 0/1/2):

```bash
#!/usr/bin/env bash
# tools/check-container-restart.sh — Pass 374: контейнеры только через deploy/do.sh
set -uo pipefail
TEXT=$(git diff --cached -U0 | grep '^+' | grep -v '^+++')
if printf '%s' "$TEXT" | grep -nE '^\+.*docker[[:space:]]+(restart|stop|start)[[:space:]]'; then
  echo "ERROR: docker restart/stop/start запрещён — только через deploy/do.sh (AGENTS.md, Pass 374)" >&2
  exit 1
fi
```

Требования к таким guard'ам, которые мы вынесли из практики:

- **Exit code ≠ 0 при нарушении** (один из наших guard'ов вечно печатал «OK» и
  возвращал 0 — проверка была декоративной).
- **Только POSIX ERE** (`grep -E`), без `-P`: на сборках без PCRE проверка
  молча падала, stderr глушился, счётчик становился пустым, сравнение давало
  «integer expression expected» — и скрипт завершался с кодом 0.
- **Ошибка проверки ≠ «нарушений нет»**: если проверка не смогла выполниться,
  код возврата должен быть ненулевым («не знаю» ≠ «чисто»).
- **Self-test**: у каждого guard'а есть режим `--self-test`, который проверяет,
  что guard ловит нарушение и **не** ловит чистый случай. Иначе поломка
  guard'а выглядит как «всё хорошо».

Подключение — в `.pre-commit-config.yaml`:

```yaml
repos:
  - repo: local
    hooks:
      - id: container-restart-guard
        name: container-restart guard (Pass 374)
        entry: bash tools/check-container-restart.sh --quiet
        language: system
        files: '.*'
```

### Шаг 4. Ловите исполнение в рантайме (уровень 3)

Это главное, чего нет у большинства проектов. У нас — host-плагин агента;
если ваш рантайм не даёт такой точки, ищите её в таком порядке:

1. **Хук до вызова инструмента.** Наш путь: событие `tools/pre-execute` хоста
   DeepSeek Harness, решение `deny`/`ask`/`cancel`. Аналог: обёртка
   tool-call'ов, middleware агентного фреймворка, pre-execute hook в
   Claude Code / Cursor / OpenHands.
2. **Обёртка shell-инструмента.** Если агент ходит только через один
   shell-тул, перехват можно сделать в нём — проще и переносимее.
3. **Свой MCP-сервер-шлюз.** Если инструменты агента — MCP, логику удобно
   держать в одном шлюзе: он видит и команду, и вызывающего.

Минимальная логика перехвата (наш `index.js`, сокращённо):

```js
return ctx.on('tools/pre-execute', async (exec, next) => {
  if (!SHELL_TOOLS.has(exec.name)) return next()
  const command = exec.arguments?.command
  if (typeof command !== 'string') return next()

  const { hit, verdict, consent } = evaluateCommand(command, rules(), {
    workdir: exec.arguments?.workdir ?? '',
    sessionId: exec.agent?.session?.id ?? null,
    consentDir, defaultMode: 'ask',
  })

  writeJournal(journalPath, {
    ts: new Date().toISOString(), tool: exec.name, command: redact(command),
    rule: hit?.id ?? null, verdict, mode: hit?.mode ?? 'ask',
    session: exec.agent?.session?.id ?? null, consent,
  })

  if (!hit || verdict === 'allow') return next()
  if (verdict === 'deny') return { kind: 'deny', reason }
  return { kind: 'ask', reason, displayReason }
})
```

Обязательные свойства реализации:

- **Политика вне reach агента** (файл в домашнем каталоге, 0600) и
  перечитывание **по mtime** — правка политики применяется без перезапуска
  хоста.
- **Маскирование секретов до записи** в журнал.
- **Ошибка записи в журнал не отменяет решение** (запрет остаётся запретом),
  но пишется в stderr.
- **Решение вынесено в чистую функцию** — иначе его нечем тестировать без
  рантайма.
- **Журнал append-only**, права 0600, каталог 0700.

### Шаг 5. Фиксируйте согласие владельца отдельно (если есть «разрешённые, но опасные» команды)

Если в проекте есть санкционированные действия, требующие одобрения
(перезапуск, деплой, миграция), понадобится источник согласия:

| Вопрос | Ответ |
|---|---|
| Где живёт | файл вне reach агента, по идентификатору сессии |
| Кто пишет | агент — **только по прямому слову владельца**, до вызова |
| Что в нём | список разрешённых операций (+ срок, если нужно) |
| Кто читает | перехватчик, до выполнения команды |
| Чего не покрывает | «опасные» действия в обход санкционированного пути |

Если ваш рантайм не даёт идентификатор сессии — используйте идентификатор
рабочего каталога, процесса или окна времени; общее требование: **согласие
нельзя вывести из текста команды** и агент не может выдать его себе сам.

### Шаг 6. Добавьте проверку процесса (уровень 5, если процессные правила есть)

Если ваш workflow из нескольких шагов (в нашем — 4 шага трекера), пропуск
шагов не оставляет следов в коде — нужен отдельный след шагов и сверка перед
финальным шагом. Реализация: пишем отметку шага в локальный журнал при
выполнении шага, сверяем перед закрытием. Важно: **не подменяйте проверку
своей историей трекера** — если трекер не отдаёт историю состояний (у нас
`history/` и `activities/` отдают 404), доказательством будет ваш журнал, а
для старых задач честный ответ — «не подтверждено», а не «нарушение».

### Шаг 7. Сделайте нарушение публичным (уровень 5)

Тикет с меткой в трекере + связка с исходной задачей. Правило: **заводит
агент по факту блокировки**, а не сам плагин (иначе в плагине нужен токен
трекера и появляется риск дублей).

### Шаг 8. Не блокируйте работу из-за сбоя проверки

Сверка, которая роняет закрытие задачи при сбое, хуже, чем отсутствие сверки:
агент начинает искать обход, а владелец теряет время. Правило: **след +
отчёт + публичный record**, а блокировка — только там, где она безопасна
(запрет явно опасного действия).

## 5. Переносимость: что у нас привязано к стеку

Наш стек: трекер Plane, git Forgejo, реестр образов Harbor, контейнеры Docker,
рантайм DeepSeek Harness, pre-commit. У вас может быть другое. Ниже — карта
привязок: **механизм → где он привязан → что делать в другом стеке**.

| Механизм | Привязка в нашем стеке | В другом стеке |
|---|---|---|
| Сверка шагов workflow | Plane: состояния «New / In progress / In review / Done», комментарии, поле `parent`, метки | Jira: workflow-схема с теми же состояниями (REST API v3), комментарии, `parent`/`issuelinks`, метки (`labels`) или тип issue «governance-violation». Смысл — тот же: нужен **сигнал «шаг сделан»** и **связь с родителем** |
| Публичный record | Plane: метка `type:governance-violation` + `parent` | Jira: метка/компонент «governance-violation», связь «blocks»/«relates to» на исходную задачу |
| Отметки шагов в журнале | локальный файл `~/.dsh/ledger/workflow.ndjson` | файл у вас — но на второй машине агента его не будет: держите журнал в трекере (комментарий-сигнал) или в общем хранилище |
| Merge-гейт | Forgejo: branch protection + `tools/merge-pr.sh` (зелёные статус-чеки head-коммита, одобрение служебным аккаунтом, merge) | GitLab: approval rules + «pipeline must succeed» + merge-бот или API; GitHub: required checks + CODEOWNERS. Важно: статус-чеки **не должны** быть в branch protection, если раннер живёт на машине разработчика — иначе остановка раннера блокирует работу |
| Правила про образы | Harbor: теги `nginx:stable`, `node:22-alpine` | Другой реестр — правило обычно то же (допустимые теги/дигесты), меняется только команда проверки (`crane`/`skopeo`/`docker`) |
| Перехват команд | DSH: событие `tools/pre-execute`, `ctx.tools.guard()` | См. шаг 4: хук tool-call, обёртка shell-тула, MCP-шлюз |
| Идентификатор сессии | `exec.agent?.session?.id` | У другого рантайма может не быть — тогда используйте идентификатор рабочего каталога или процесса |
| Маскирование секретов | набор регулярок в коде плагина | перенесите набор из своего проекта; проверьте на реальных примерах (`--password`, `-u user:pass`, `Authorization:`, `*_TOKEN=`) |
| Проверки документации | 9 структурных проверок + cross-links + lint | свои (у нас — `tools/check-knowledge-structure.sh`, `check-knowledge-cross-links.sh`, `lint-knowledge.py`) |
| Сборщик следа вне рантайма | journald + `~/.bash_history` с метками времени + снимки docker | аналог: системный журнал процессов (`auditd` — мы его сознательно **не** ставили: нужен root и постоянная нагрузка), история shell с метками времени, снимки состояния контейнеров |

### 5.1. Три отличия трекеров, которые ломают перенос «как есть»

1. **Историю состояний отдают не все.** Plane — не отдаёт (`history/`,
   `activities/` — 404). Если ваш трекер отдаёт — сверка может опираться на
   трекер, а не на локальный журнал шагов; это дешевле.
2. **Фильтр «открытые» смотрит на группу состояния, а не на метку.** Тикет с
   меткой «нарушение», созданный сразу в «сделано», из потока открытых
   выходит — это нужно учитывать при построении отчётов.
3. **Есть «состояние-группа» и «состояние».** «Готово к проверке» должно быть
   отдельным состоянием в группе «начато», иначе его не отличить от
   «в работе».

## 6. Ошибки, которые мы совершили (чтобы вы их не повторили)

| Ошибка | Последствие | Что делаем теперь |
|---|---|---|
| Первая версия правил на regex по всему тексту | 236 ложных срабатываний на 30 335 реальных командах | сегментный разбор, якоря, состояниезависимые правила; проверка на корпусе реальных команд **до** включения |
| Правило «`git … master`» ловило `gh pr create --base master` | ложная блокировка работы | правило по состоянию ветки, а не по тексту |
| Правило «`docker compose`» ловило чужие проекты | то же | область — только репозиторий проекта (маркер каталога, не путь) |
| Guard'ы смотрели только в `git diff HEAD` | ловили намерение, но не исполнение | добавлен runtime-перехват |
| Один guard всегда печатал «OK» и возвращал 0 | проверка была декоративной | exit code ≠ 0 при нарушении; ошибка проверки ≠ «чисто» |
| Подсчёт через `grep -cP` | на машине без PCRE счётчик был пустым, сравнение падало, скрипт завершался с кодом 0 | POSIX ERE + проверка «ответ — число» |
| Правило читалось как «`git commit` в master запрещён», а состояние бралось из корня репозитория | в worktree фичи коммит считался коммитом в master | учёт каталога сегмента + чтение `.git` файла worktree (`gitdir:`) |
| Первая проверка «живого» перехвата была неверной | вывод «механизм не работает», хотя не работала методика | проверять на заглушке: каталог `deploy` с `do.sh` и маркером, боевой скрипт не трогать |
| Сверка workflow требовала `mark-review` даже там, где ревью прошло в переписке | ложное «нарушение» у человека | «не подтверждено» ≠ «нарушение»; для старых записей — честное «не подтверждено» |

## 7. Что переносить нельзя (и почему)

- **«Сделать нарушение невозможным»** — формулировка, которую мы убрали из
  канона. Она обещает больше, чем даёт, и провоцирует ложное чувство
  защищённости.
- **Автоматическая «деградация агента»** (блокировка после N нарушений) — мы
  сознательно не вводили: она сама становится источником ложных блокировок.
  След и публичный record дают факты без этого риска.
- **Правила, дублирующие уже закрытые pre-commit'ом.** Если путь gradle уже
  проверяется в рабочей копии, не надо дублировать его в рантайме: лишнее
  правило — лишние ложные срабатывания.
- **`auditd` как «обязательное условие».** Мы его не ставили: нужен root и
  постоянная нагрузка. Текущего набора источников хватает для критерия
  «ноль необъяснённых изменений среды».
- **Запрет на все контейнеры машины.** Область — ваш проект: чужие проекты на
  той же машине ломаются от ваших правил.

## 8. Чек-лист приёмки (прогоните у себя)

**Базовый уровень (правило → намерение):**
- [ ] Для каждого правила канона указано, чем оно защищено; пустых нет.
- [ ] Guard'ы возвращают ненулевой код при нарушении и на ошибке проверки.
- [ ] У каждого guard'а есть self-test: ловит нарушение, не ловит чистое.
- [ ] Guard'ы работают на машине без PCRE и без GNU-специфичных флагов.
- [ ] Правило «не коммитить в основную ветку» обеспечено и branch protection,
      и скриптом merge, и проверкой CI.

**Продвинутый уровень (правило → исполнение):**
- [ ] Есть перехват команд до выполнения; проверено на заглушке, боевые команды
      не выполняются.
- [ ] Политика лежит вне reach агента; правка применяется без перезапуска.
- [ ] В журнале есть: время, команда (секреты замаскированы), правило, вердикт,
      идентификатор сессии.
- [ ] Согласие владельца на опасные санкционированные команды фиксируется
      отдельной записью; агент не может выдать её себе сам.
- [ ] Нарушение получает публичный record (метка + связь с исходной задачей).
- [ ] Проверка процессных правил не блокирует закрытие задачи.

**Измерение:**
- [ ] Есть измеримый критерий (у нас: ноль срабатываний в наблюдаемом канале +
      ноль необъяснённых изменений среды).
- [ ] Наблюдение запускается на реальных данных корпуса, а не на синтетике.
- [ ] Ложных срабатываний нет на корпусе реальных команд; доля срабатываний
      объяснима: у нас новое правило дало 42 срабатывания на 30 335 команд, и
      все они настоящие; общие совпадения — 1.19%, из них большинство пришлось
      на правило «коммит в master», сработавшее потому, что корпус был собран
      в ветке master (правило состояниезависимое).
