# Data Model: Ложная неактуальность mp3-стемов

Схема БД не меняется. Модель ниже описывает правило проверки и данные, которые она читает.

## Сущности

### HealthReport (без изменений полей)

| Поле | Значение для storage-only mp3 |
|---|---|
| `description` | `<KaraokeFileType>/<LOCATION>` (например, `MP3_ACCOMPANIMENT/LOCAL_STORAGE`) |
| `healthReportType` | `FILE_VIOLATION` |
| `healthReportStatus` | `OK` / `WARNING` (расхождение хранилищ) / `IN_PROGRESS` / `FATAL_ERROR` |
| `canResolve` | `false` при расхождении хранилищ |
| `problemText` | «Размеры файлов в локальном и удалённом хранилищах различаются» |
| `solutionText` | «Приведите хранилища к согласию вручную» |
| `solutionActions` | пусто при расхождении |

### StorageFileInfo (без изменений)

`bucketName`, `fileName`, `etag`, `size`. Для сравнения используется только `size`; `null` (нет данных) трактуется как «не расхождение».

### Признак «диск — эталон»

`KaraokeFileType.willBeInFileSystem` (`locations.contains(LOCAL_FILESYSTEM)`). Для пяти mp3-типов — `false`, для аудио- и графических типов — `true`.

## Правила (state transitions)

| LOCAL object | REMOTE object | Дисковая копия | Результат |
|---|---|---|---|
| есть | есть | любая | `size` равны → OK; различаются → WARNING (без actions) |
| есть | нет | любая | прежнее поведение: ERROR + загрузка из локального в удалённое |
| нет | есть | любая | прежнее поведение: ERROR + восстановление из удалённого в локальное |
| нет | нет | есть | прежнее поведение: ремонт из дисковой копии (не меняется) |
| нет | нет | нет | FATAL_ERROR (не меняется) |

## Валидация

- `size` сравнивается как `Long`; `null` → сравнение не выполняется, расхождение не фиксируется.
- `etag` не участвует.
- Для типов с `LOCAL_FILESYSTEM` таблица не применяется — поведение прежнее.

## Миграции

Не требуются.
