# Quickstart: Валидация «Санитайзинг имён файлов + каскадное переименование»

**Feature**: [spec.md](./spec.md) | **Date**: 2026-08-03

Ручная валидация (в проекте нет CI-тестов для этого модуля — см.
`plan.md` → Technical Context → Testing). Выполняется пользователем в
production-like окружении (admin-машина с реальным Demucs/MinIO).

## Предпосылки

- Локальный стек поднят (`deploy/do.sh`, см. `DEVELOPMENT.md`).
- Доступна папка импорта с правами на запись.
- В webvue3 открыт SongEdit хотя бы для одной существующей песни с уже
  посчитанными стемами и загруженной в оба хранилища (для сценария 3).

## Сценарий 1 — Импорт файла с `!` (User Story 1, Acceptance Scenario 1-2)

1. Создать альбомную папку `2012 - Название альбома` внутри папки импорта.
2. Положить внутрь файл `2012 (01) [Ария] - Дай жару!.mp3`.
3. Запустить импорт из папки (существующая кнопка/эндпоинт импорта в webvue3).
4. **Ожидается**:
   - Новая песня создана, поле «Название» = `Дай жару!` (с `!`).
   - Реальный файл на диске: `2012 (01) [Ария] - Дай жару.flac` (без `!`).
   - Автоматически поставленные `KEY_BPM_FROM_FILE` и `DEMUCS2` завершаются
     `DONE`, не `ERROR` (проверить в разделе «Процессы» webvue3).

## Сценарий 2 — Прочие проблемные символы (Acceptance Scenario 3)

1. Импортировать файл с `?`, `:`, `*`, `"` в названии (в пределах шаблона
   `Порядковый (Номер) [Автор] - Название`).
2. **Ожидается**: имя файла на диске не содержит этих символов; «Название»
   песни сохраняет их как есть.

## Сценарий 3 — Коллизия имён при импорте (Acceptance Scenario 4)

1. В одну альбомную папку положить два файла, которые после санитайзинга
   дают одинаковое имя (например, отличаются только символом `!`/`?`, который
   будет удалён).
2. Запустить импорт.
3. **Ожидается**: обе песни импортированы, второй файл получил суффикс
   `" (2)"` в имени на диске, ни один файл не перезаписан.

## Сценарий 4 — Каскадное переименование через SongEdit (User Story 2, Acceptance Scenario 1-2)

1. Открыть в SongEdit песню с уже существующими: аудиофайлом, стемами,
   `.kdenlive`-проектом, субтитрами; убедиться, что песня загружена в
   локальное и удалённое хранилище (например, через существующий Health
   Report — все `OK`).
2. Изменить поле «Имя файла» на новое значение, сохранить.
3. **Ожидается**:
   - Все перечисленные файлы на диске переименованы, файлов под старым
     именем не осталось (проверить `ls` в `rootFolder`).
   - Объекты в обоих хранилищах доступны под новым ключом (проверить через
     MinIO console/`mc ls` или существующий Health Report — снова все `OK`
     под новым именем).
   - Под старым именем в хранилищах ничего не «висит».

## Сценарий 5 — Санитайзинг при переименовании (Acceptance Scenario 3)

1. В SongEdit ввести в «Имя файла» значение с проблемными символами.
2. Сохранить.
3. **Ожидается**: реальное имя файла — санитайзированное, без запрошенных
   проблемных символов (те же правила, что при импорте).

## Сценарий 6 — Отсутствующие производные файлы не блокируют переименование (Acceptance Scenario 4)

1. Взять песню, у которой ещё не посчитаны стемы (только основной аудиофайл).
2. Переименовать файл через SongEdit.
3. **Ожидается**: операция завершается успешно (не падает из-за отсутствия
   стемов), аудиофайл переименован.

## Сценарий 7 — Коллизия при переименовании (FR-011, SC-005)

1. В одной `rootFolder` — две песни, A и B.
2. В SongEdit песни A ввести «Имя файла», совпадающее (после санитайзинга) с
   именем файла песни B.
3. **Ожидается**: сохранение отклонено, пользователь видит понятное
   сообщение об ошибке; данные обеих песен не повреждены (файлы не
   переименованы).

## Сценарий 8 — Блокировка при активной фоновой обработке (FR-013)

1. Запустить для песни длительную обработку (например, поставить в очередь
   пересчёт стемов).
2. Пока процесс в статусе `WAITING`/`WORKING`, попытаться в SongEdit изменить
   «Имя файла» и сохранить.
3. **Ожидается**: сохранение отклонено с сообщением «дождитесь завершения
   текущей обработки»; после того как процесс перейдёт в `DONE`, повторная
   попытка сохранения проходит успешно.

## Сценарий 9 — Частичный отказ каскада (FR-010)

Симулировать сложнее без изменения кода (например, временно отключив доступ
к одному из хранилищ во время сохранения). Если такая проверка невозможна
без вмешательства в инфраструктуру — допустимо пропустить при ручной
валидации и полагаться на code review логики best-effort-forward, описанной
в `data-model.md` (`RenameAttempt`).
