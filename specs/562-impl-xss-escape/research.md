## D1 — Гибрид: экранирование на входе + текстовый режим по умолчанию

**Decision**: реализуем оба рубежа из решения владельца от 2026-10-24:
(a) пользовательские значения экранируются при сборке текста подтверждения в 43 местах;
(b) общий компонент `CustomConfirm.vue` по умолчанию **не принимает сырую разметку** — HTML-режим
включается только явно.

**Rationale**: правило линтера `vue/no-v-html` выключено (`webvue3/.eslintrc.cjs:56`) с
фактически неверным обоснованием («пользовательский ввод не передаётся напрямую»). Только
правка мест вызова оставляет ловушку для новых вызовов: новый подтверждение с e-mail снова
станет XSS, и линтер промолчит. Текстовый режим по умолчанию превращает «ловушку» в
«безопасный по умолчанию режим»: новое подтверждение без явного `allowHtml: true` вообще не
может выполнить чужой код.

**Alternatives considered**: (а) только правка мест вызова — отклонён владельцем;
(б) только текстовый режим без экранирования на входе — отклонён: ломает оформление
(жирное начертание подставляемого значения — FR-009) и оставляет данные в неэкранированном
виде в HTML-буфере.

## D2 — Имя и форма флага: `params.allowHtml`

**Decision**: в объекте `customConfirmParams` появляется булево поле `allowHtml`.
Значение `true` → заголовок и текст выводятся как HTML; отсутствие поля или `false` → как текст.

**Rationale**: `params` — единственный канал, через который подтверждение получает содержимое;
флаг рядом с содержимым читается одновременно с ним и не требует второго параметра
компонента. Имя `allowHtml` однозначно говорит «здесь сознательно разрешена разметка».

**Alternatives considered**: (а) отдельный проп `html` у компонента — отклонён: разъезжается
с `params`, легко забыть при передаче в `<CustomConfirm>`; (б) переименование `body` → `bodyHtml`
— отклонён: ломает 137 блоков и делает «текстовый» вариант неявным; (в) санитайзер (DOMPurify) —
отклонён: добавляет зависимость в админку и не входит в решение владельца (возврат правила
линтера и санитайзер — отдельная задача).

## D3 — Текстовый режим = `v-text`, HTML-режим = `v-html` под `v-if`

**Decision**: в шаблоне `CustomConfirm.vue` — две пары элементов:

```html
<div :style="styleHeader" v-if="params.allowHtml" v-html="params.header" />
<div :style="styleHeader" v-else v-text="params.header" />
<div :style="styleBody" v-if="params.allowHtml" v-html="params.body" />
<div :style="styleBody" v-else v-text="params.body" />
```

**Rationale**: `v-text` пишет через `textContent` — разметка в значении не создаёт элементов
и не выполняет сценариев (FR-001). Структура DOM и стили (`styleHeader`/`styleBody`) не
меняются — оформление подтверждения сохраняется (FR-009). `v-if`/`v-else` вместо вычисляемого
выражения — потому что `v-html` и `v-text` на одном элементе mutually exclusive: Vue не
запрещает их формально, но поведение зависит от порядка директив, что хрупко.

**Alternatives considered**: (а) `:innerHTML` в методе с ручным `if` — отклонён: теряется
декларативность и привычный вид шаблона; (б) `v-html` + санитайзер — отклонён (см. D2б).

## D4 — Инвариант «`allowHtml` ⇔ в тексте есть разметка»

**Decision**: блок `customConfirmParams` обязан объявлять `allowHtml: true` **тогда и только
тогда**, когда в его `header`/`body` есть статичная разметка (`<strong>`, `<br>`, `<hr>`).
Блоки с чистым текстом остаются в текстовом режиме и `allowHtml` не объявляют.

**Rationale**: (а) «только тогда, когда есть разметка» — иначе оформление подтверждения
потеряется (FR-009); (б) «и только тогда» — лишний `allowHtml: true` без нужды расширяет
доверенную поверхность: текстовый режим безопаснее, а выигрыша в нём нет. Инвариант
проверяется автоматически (FR-014, D8) — это делает «забытый флаг» и «лишний флаг»
одинаково заметными.

**Alternatives considered**: «всегда `allowHtml: true`» — отклонён: тогда рубеж (b) из D1
деградирует в номинальный.

## D5 — Экранирование на входе, а не на выходе

**Decision**: значение экранируется **внутри** интерполяции, в момент входа в HTML-буфер:

```js
body: `Удалить песню <strong>«${escapeHtml(this.song.songName)}»</strong>?`
```

**Rationale**: прямое правило проекта (`knowledge/domains/integration/components/song-public-dto.md`,
прецедент спеки #215) и FR-010 (экранирование ровно один раз). Экранирование готовой
HTML-строки целиком сломало бы статичную разметку («съело» бы `<strong>`), а экранирование
на выходе (в компоненте) — тем более.

**Alternatives considered**: экранирование в компоненте (на выходе) — отклонён по FR-009/FR-010
и по правилу проекта.

## D6 — Канонический модуль экранирования

**Decision**: `escapeHtml` живёт в новом файле `webvue3/src/utils/escapeHtml.js`;
`webvue3/src/utils/highlightWords.js` импортирует его и **реэкспортирует** (публичный
`escapeHtml` из `highlightWords.js` не ломается — `SubsEdit.vue` и его тест продолжают
работать как прежде).

**Rationale**: `highlightWords.js` — модуль про подсветку слов; тянуть его в восемь
компонентов ради одной функции неправильно. Реэкспорт сохраняет обратную совместимость
и не меняет поведение существующего кода (тест `highlightWords.test.js` продолжает
проходить без правок).

**Alternatives considered**: (а) оставить `escapeHtml` в `highlightWords.js` и импортировать
оттуда — отклонён: семантически неверно; (б) продублировать реализацию в новом файле —
отклонён: две реализации расходятся (в проекте это уже было с
`AiTextEditorModal.vue:133`).

## D7 — Безопасный список выражений (что экранировать НЕ надо)

**Decision**: перечень выражений, которые **не** являются пользовательскими данными, живёт в
явном файле `config/frontend/confirm-safe-expressions.txt` — по одному выражению в строке,
рядом — причина. Всё, что не перечислено и не является очевидно безопасным (числовой
литерал, обращение к `.length`), считается пользовательскими данными и обязано быть
экранировано.

**Rationale**: спека явно исключила 32 места («счётчики, id, enum, ключи настроек») из
охвата (FR-012 — их подтверждения не меняются). Чтобы и проверка (FR-014), и код были
согласованы, нужен **явный** список: он одновременно (а) удерживает 32 места вне охвата,
(б) заставляет нового разработчика сознательно решать, что он добавляет в список, и
(в) делает сами 32 места документированными («почему это не экранируется»).

**Alternatives considered**: (а) экранировать всё подряд — отклонён: выходит за согласованный
владельцем охват (43 места) и трогает подтверждения, которые FR-012 требует не менять;
(б) эвристика «похоже на счётчик» — отклонён: эвристика в guard'е опасна (пропуск дефекта).

## D8 — Проверка FR-014: guard-скрипт + pre-commit + CI

**Decision**: `tools/check-confirm-escape.py` проверяет три инварианта:

- **R1 (компонент)**: `CustomConfirm.vue` не содержит безусловного `v-html="params.header"` /
  `v-html="params.body"`; текстовый режим — по умолчанию.
- **R2 (формат)**: блок объявляет `allowHtml: true` ⇔ в его `header`/`body` есть разметка.
- **R3 (данные)**: в блоке с `allowHtml: true` каждая интерполяция небезопасного выражения
  обёрнута в `escapeHtml(...)`; интерполяции в локальных переменных, на которые ссылается
  `header`/`body`, разворачиваются рекурсивно.

Скрипт подключается в `.pre-commit-config.yaml` (хук `confirm-escape-guard`) и в
`.github/workflows/lint.yml` (отдельный job `confirm-escape-guard`).

**Rationale**: FR-014 требует проверку, которая (а) падает на коде до правки и (б) проходит
после, и включена в проверки проекта. Pre-commit + CI — единственные два места, через
которые «проверки проекта» действительно исполняются (см. `.github/workflows/lint.yml`).
Линтер `vue/no-v-html` остаётся выключенным (FR-015) и защитой не считается.

**Alternatives considered**: (а) только ESLint-правило — отклонён: FR-015 запрещает считать
линтер гарантией, и ESLint не различает «статичную разметку» и «пользовательское значение»
внутри шаблонной строки; (б) только unit-тест — отклонён: unit-тест не видит все 137 блоков
подтверждений в 18 файлах.

## D9 — Тесты «до/после» по образцу спеки #215

**Decision**: две группы тестов.

1. `webvue3/src/utils/__tests__/escapeHtml.test.js` — «регресс-контроль» из спеки #215:
   для значения **без спецсимволов** результат экранирования побайтово совпадает с исходным
   (baseline совпадает); для значения с `&` получается ровно одна `&amp;` (нет
   `&amp;amp;` — двойного экранирования); `null`/`undefined` → пустая строка.
2. `tools/check-confirm-escape.py` — сам является проверкой «до/после»: на заведомо
   уязвимом коде (фикстура) он обязан завершиться отказом, на исправленном — успехом.
   Фикстуры лежат в `tools/fixtures/confirm-escape/` и проверяются скриптом
   `tools/check-confirm-escape-fixtures.sh`.

**Rationale**: спека #215 закрыл свой дефект именно так — «выдача совпадает с базовой линией
+ 0 двойных экранирований». SC-004 требует того же для этой задачи.

**Alternatives considered**: скриншот-регрессия — отклонён: в проекте нет инфраструктуры
визуальных тестов для админки; Playwright есть, но e2e-сценариев подтверждений нет.

## D12 — Как выглядит «пользовательское значение» для guard'а

**Decision**: guard классифицирует выражение как безопасное, если оно
(а) числовой литерал, (б) содержит `.length`, (в) перечислено в
`config/frontend/confirm-safe-expressions.txt`. Всё остальное — пользовательское значение
и обязано быть экранировано.

Выражения, которые разворачиваются рекурсивно (guard умеет их искать): локальные переменные
метода, на которые ссылается `header`/`body` (`body` в `SmartCopyModal.vue`/`SyncTable.vue`,
`scope` в `HomeView.vue`, `lines` в `SyncTable.vue`). Параметры методов (`title` в
`SyncTable.vue`) неразрешимы — они перечисляются в safe-list с причиной.

**Rationale**: deny-by-default (всё не перечисленное — пользовательское) ловит **новые**
источники пользовательских данных, а не только регрессию перечисленных (SC-003).
