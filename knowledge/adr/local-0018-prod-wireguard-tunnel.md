# Local ADR-0018: Постоянный туннель к прод-хосту (WireGuard) — владельцем является приложение

* **Status**: Accepted
* **Date**: 2026-11-09
* **Deciders**: владелец Karaoke (спека 733, задача Plane `KARAOKE-407`)

> **Note**: this is a **local** ADR — describes a specific subsystem
> convention (vs global ADR-0001..0008 which describe project-wide decisions).

## Context

Админская машина `nsa-i9` ходит к прод-хосту `188.127.240.124` по трём каналам:
L4 `5433` (прод-БД), L4 `9000` (MinIO) и HTTP-эндпоинты `/changerecords`,
`/api/properties/setproperty`. Доступ был разрешён allow-list'ом по адресу:
в конфигурации host-nginx прод-хоста стоял текущий публичный адрес админской
машины.

Внешний адрес админской машины плавает (пул провайдера; раньше — ещё и выход
VPN). Три инцидента за 9 дней: 2026-10-30, 2026-11-02 (80 минут простоя
конвейера), 2026-11-08 («и снова сменился айпишник»). Автоматизация allow-list
(ADR `local-0015`, спека 731) чинит доступ, но конфигурация прод-хоста меняется
при каждой смене адреса, а сама защита остаётся «знаешь адрес — имеешь доступ».

Разбор 2026-11-09 (runbook § 1d) установил вторую, независимую причину сбоев:
обрывается WAN шлюза `10.0.1.1` (LAN жив, наружу не выпускает, ~30–80 с раз в
~11 минут). Удаление AmneziaVPN убрало лишний churn, но причину не устранило.
Значит, туннель снимает зависимость от плавающего IP, но **не** от доступности
WAN — это ограничение фиксируется явно (FR-034).

## Решения владельца (2026-11-09)

1. Спека 733 утверждена.
2. Транспорт — **WireGuard** (вариант A). Allow-list по IP для прод-канала
   уходит.
3. Туннель обязан работать при смене адреса клиента, без ручных правок на проде.
4. Админские HTTP-каналы (`setproperty`, `changerecords`) идут **внутрь** туннеля.
5. Туннелем владеет и управляет само приложение `karaoke-app`.
6. Туннель должен быть пригоден и для приложения, и для подключения с хоста
   (DBeaver) по одному постоянному внутреннему адресу.

## Decision

1. **Адресация.** Подсеть `10.77.0.0/24`. Сторона приложения — `10.77.0.1/24`
   (этот адрес прод видит как источник; в allow-list прод-хоста — ровно одна
   строка `allow 10.77.0.1;`). Сторона прода — `10.77.0.2/24` — **постоянный
   внутренний адрес прод-каналов**, который используют и приложение, и
   оператор с хоста. Подсеть не пересекается с `tun0` (`172.28.3.0/24`),
   docker-сетями (`172.18.0.0/16`, `172.21.0.0/16`, `172.23.0.0/16`), VPN-маршрутами
   (`10.128.0.0/16`) и LAN `10.0.1.0/24` — проверяется guard'ом и unit-тестом.

2. **Размещение интерфейса.** Интерфейс `wg0` живёт **в сетевом пространстве
   контейнера `karaoke-app`**: контейнер получает `NET_ADMIN` и `/dev/net/tun`,
   приложение само выполняет `ip`/`wg` и следит за туннелем. Хост админской
   машины получает маршрут в подсеть туннеля через контейнер
   (`karaoke-tunnel-host-route.service`), а контейнер делает SNAT хостового
   трафика в `10.77.0.1` — поэтому прод видит один и тот же адрес источника
   независимо от потребителя.

3. **Рукопожатие.** Прод слушает UDP `51820`; админская сторона инициирует
   соединение с `persistent-keepalive = 25` (натуральный keepalive
   NAT-маппинга). Смена публичного адреса → новое рукопожатие, правок на проде
   не требуется.

4. **HTTP-каналы при неизменном имени хоста.** Пока туннель поднят, имя
   `sm-karaoke.ru` резолвится в `10.77.0.2` (переопределение в файле резолвинга
   контейнера, управляется приложением). SNI и заголовок `Host` не меняются —
   сертификат сервера остаётся прежним, проверка сертификата включена. Туннель
   не поднят — переопределение снимается, приложение возвращается на публичный
   путь (откат).

5. **mTLS к прод-БД.** Доступ требует клиентского сертификата, выпущенного
   доверенным центром проекта; `pg_hba.conf` переводится на
   `hostssl … scram-sha-256 clientcert=verify-ca` — **пароль остаётся** как
   запасной путь до отдельного осознанного решения владельца. Клиент
   (`karaoke-app`) задаёт `sslmode=verify-full` и параметры
   `sslcert`/`sslkey`/`sslrootcert` — сертификат сервера проверяется по полной
   цепочке.

6. **Наблюдаемость.** Отдельные коды событий `TUNNEL-001…007` и `DB-CERT-001`
   и отдельная проверка мониторинга `prod.tunnel`: состояние туннеля видно
   отдельным признаком, каждый отказ прод-канала атрибутирован конкретному
   участнику (туннель / сертификат / БД / сайт).

7. **Автоматика allow-list.** В режиме `ALLOWLIST_MODE=tunnel` скрипт не
   определяет и не пишет публичный адрес — он только проверяет (read-only), что
   постоянный внутренний адрес на месте, и сообщает владельцу о расхождении.
   Покрыто self-test-сценарием.

8. **Переключение — по фазам.** Подготовка → пир на проде → allow-list →
   переключение каналов (перезапуск `karaoke-app` по Pass 380) → закрытие
   публичных портов. До последней фазы прежний публичный путь остаётся
   рабочим; откат каждой фазы — не дольше 15 минут.

## Отклонённые альтернативы

| Альтернатива | Почему отклонена |
|---|---|
| Интерфейс туннеля в сетевом пространстве хоста, приложение управляет им через helper-демон | Фактически двумя владельцами; хост-демон стал бы «настоящим» владельцем туннеля — нарушение FR-027 |
| `network_mode: host` для `karaoke-app` | Ломает published-порты и сетевую изоляцию контейнера |
| Расширить `AllowedIPs` пира на проде до docker-подсети, чтобы обойтись без SNAT | В allow-list прод-хоста пришлось бы держать адрес docker-сети — нарушение FR-005 («ровно один постоянный внутренний адрес») |
| Политика маршрутизации по публичному IP прода вместо внутреннего адреса | Приложение обращалось бы к публичному адресу, а не к постоянному внутреннему (FR-031) |
| Свой DNS-резолвер (dnsmasq) в контейнере | Лишний демон; переопределение резолвинга управляется тем же процессом, который владеет туннелем |
| Отдельный туннель для оператора с хоста | Два адреса в allow-list и два владельца — прямо противоречит FR-031 |
| Просто выключить таймер allow-list после перехода | Теряется диагностика: при пропаже туннеля агент молчал бы |
| Оставить публичный IP в allow-list «на всякий случай» | Возвращает прежнюю уязвимость (доступ по «узнавшему адрес») и противоречит FR-005 |

## Consequences

1. **Запрет**: туннель MUST NOT менять маршрут по умолчанию админской машины и
   MUST NOT ломать `tun0` (OpenVPN к pfSense), `xray` и SSH к прод-хосту.
2. **Запрет**: публичный адрес админской машины MUST NOT попадать в allow-list
   прод-хоста после перехода на туннель (FR-009).
3. **Инвариант**: в allow-list прод-хоста — ровно один адрес, и это `10.77.0.1`.
4. **Инвариант**: имя хоста `sm-karaoke.ru` и сертификат сервера не меняются.
5. **Инвариант**: приватные ключи и файлы сертификатов не попадают в
   репозиторий, в журнал и в `argv`.
6. **Инвариант**: обрыв WAN прерывает канал — это НЕ решено туннелем (FR-034);
   защита — устойчивость приложения (задание в очередь, а не в ошибку) и
   различение причин в наблюдаемости.
7. **Required Update**: `knowledge/system/infra/deploy-overview.md`,
   `knowledge/guidelines/runbooks/prod-config-delivery.md`,
   `knowledge/guidelines/runbooks/log-correlation.md` (коды событий),
   `knowledge/product/features/admin-ip-allowlist.md`,
   `knowledge/product/features/prod-tunnel.md` (per-feature, FR-009),
   runbook `knowledge/guidelines/runbooks/prod-tunnel.md`.
8. **Требует отдельного окна владельца**: установка пира на проде, выпуск
   ключей и сертификатов, переключение каналов (перезапуск `karaoke-app` по
   Pass 380), закрытие публичных портов.
