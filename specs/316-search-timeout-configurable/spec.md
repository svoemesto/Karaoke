## User Scenarios & Testing *(mandatory)*

### User Story 1 — Backend-configurable delay between search requests (Priority: P1)

Администратор Karaoke запускает массовый поиск текстов песен в интернете — при импорте файлов из папки (`HomeView.vue` → `createfromfolder`) или по кнопке в компоненте «Песни» (`SongsTable.vue` → `searchsongtextall`). Между запросами поисковая система отбрасывает слишком частые обращения (защита от DDoS на стороне внешнего поискового сервиса). Чтобы массовый поиск не «проваливался» и пользователь мог экспериментально подобрать оптимальный интервал, приложение должно: (а) перед каждым запуском массового поиска показывать **существующее** модальное окно подтверждения (выбор поискового движка в «Песни» / информация о формате файлов в импорте папки) с **дополнительным полем** «таймаут между запросами, секунды» рядом с другими полями, (б) использовать введённое значение как минимальный интервал между запросами внутри одной сессии массового поиска, (в) тут же сохранять последнее введённое значение в backend-настройке `KaraokeProperties` (глобально, single-user), (г) при следующем запуске любой точки входа предлагать последнее сохранённое значение как default, (д) при отсутствии сохранённого значения использовать default 10 секунд.

**Why this priority**: Это единственный user story задачи WP #61. Без него массовый поиск систематически теряет часть запросов и администратор вынужден подбирать задержку наугад. Блокирует эффективное использование admin-инструмента поиска в **обоих** UI потоках.

**Independent Test**: Можно проверить изолированно: (1) запустить массовый поиск из «Песни» — существующий диалог «Подтвердите поиск текста» с дополнительным полем таймаута (default = 10); (2) ввести, например, 7, нажать «Да» — между запросами наблюдается задержка ≥ 7 секунд; (3) завершить поиск, запустить снова через импорт папки — в диалоге «Добавление файлов из папки» default поля таймаута = 7; (4) ввести 0 или `-3` — диалог отвергает ввод (для обеих точек входа), default остаётся прежним; (5) в backend проверить ключ `lyricsSearchTimeoutSeconds = 7` (через API `GET /api/lyrics-search-timeout` → `{"value": 7}`, или напрямую в `Karaoke.properties` через `KaraokeProperties.getInt(...).takeIf { it >= 1 } ?: 10`).

**Acceptance Scenarios**:

1. **Given** пользователь ещё ни разу не запускал массовый поиск (нет сохранённого значения в KaraokeProperties), **When** он инициирует массовый поиск (любой из двух точек: импорт из папки или кнопка в компоненте «Песни»), **Then** существующий диалог подтверждения содержит поле таймаута с default `10` (fallback на код).
2. **Given** пользователь ранее ввёл значение таймаута `7` и оно сохранено в KaraokeProperties, **When** он инициирует новый массовый поиск (любой из двух точек), **Then** существующий диалог содержит поле таймаута с default `7` (читается из backend).
3. **Given** пользователь ввёл значение `12` в поле таймаута и нажал «Да», **When** массовый поиск выполняется для списка из N песен (любой из двух точек), **Then** между последовательными запросами проходит **не менее 12 секунд**, а после завершения поиска введённое значение `12` сохранено в KaraokeProperties и предлагается как default при следующем запуске **любой** точки.
4. **Given** пользователь ввёл в поле таймаута `0`, `-3`, `abc` или оставил поле пустым, **When** он нажимает «Да», **Then** диалог отвергает ввод с понятным сообщением об ошибке и предложением исправить, default в поле таймаута остаётся прежним.
5. **Given** администратор запускает массовый поиск двумя разными способами (импорт из папки **и** кнопка в компоненте «Песни»), **When** он отвечает на диалог в каждом случае, **Then** оба сценария применяют таймаут одинаково (между запросами ≥ N сек), независимо от типа пути (серийный цикл в searchsongtextall, параллельный executor с rate-limit в createfromfolder).
6. **Given** завершён массовый поиск с ≥ 2 успешными запросами подряд, **When** backend завершает цикл, **Then** (а) в KaraokeApp-логе печатается строка с `minIntervalMs` (минимальное время между двумя подряд успешными `getLyricsSearch`); (б) в admin-SPA приходит SSE-нотификация типа `massSearchSummary` с payload `{ count: N, successfulCount: M, minIntervalMs: X, totalDurationMs: Y }`.

---

### Edge Cases

- **Что если пользователь ввёл таймаут 0?** Серверная защита от DDoS почти наверняка отклонит слишком частые запросы; кроме того, 0 не имеет смысла как «минимальный интервал». Значение должно быть ≥ 1 (см. acceptance scenario 4).
- **Что если сохранённое значение в KaraokeProperties устарело или повреждено?** Приложение должно корректно откатиться к default `10` и предложить его в поле таймаута.
- **Что если несколько вкладок admin-SPA открыты одновременно?** Каждая вкладка показывает диалог независимо при запуске массового поиска; сохранённое значение — общее на пользователя (single-user, KaraokeProperties — глобально), последнее записанное выигрывает.
- **Что если запрос внутри массового поиска упал по серверной причине (timeout / 5xx)?** Приложение должно сохранить таймаут в KaraokeProperties для следующей попытки и не сбрасывать его в default. Упавший запрос **не учитывается** в подсчёте `minIntervalMs` (только успешные пары).
- **Что если в `createfromfolder` параллельный executor (4 потока) получит таймаут 0?** Rate-limit не применяется (`Thread.sleep(0)` = no-op). Поведение идентично текущему — все 4 потока шлют запросы одновременно. Защита от DDoS в этом случае зависит от внешнего сервиса.
- **Что если KaraokeProperties файл заблокирован или не читается?** Backend логирует warning и использует default 10; UI диалог показывает fallback.
- **Что если в массовом поиске только 0 или 1 успешный запрос?** `minIntervalMs` не вычисляется (нет пары), в логе/SSE поле `null`.
- **Что если все запросы в массовом поиске упали (0 успешных)?** Логируется `successfulCount=0`, `minIntervalMs=null`. SSE-нотификация всё равно отправляется.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: При инициации массового поиска (любой из двух точек входа: импорт файлов из папки через `HomeView.vue` → `createfromfolder`, кнопка в компоненте «Песни» через `SongsTable.vue` → `searchsongtextall`) система MUST показать пользователю **существующее** модальное окно подтверждения (с полем выбора поискового движка в «Песни» / с информацией о формате файлов в импорте) с **дополнительным полем** «Таймаут между запросами, сек» рядом с другими полями. Новые отдельные модальные окна ЗАПРЕЩЕНЫ (принцип «сделай так же, как рядом»).
- **FR-002**: Поле таймаута MUST быть pre-filled последним сохранённым значением из backend-настройки `KaraokeProperties.lyricsSearchTimeoutSeconds`, либо `10` (если значение отсутствует или повреждено).
- **FR-003**: Если пользователь подтверждает диалог кнопкой «Да», система MUST передать введённое значение таймаута в backend как параметр вызова (query-param или body). Backend MUST использовать его как минимальный интервал между последовательными запросами внутри одной сессии массового поиска.
- **FR-004**: Сразу после завершения (или подтверждения) поиска backend MUST сохранить введённое значение в `KaraokeProperties.lyricsSearchTimeoutSeconds` (через существующий UI/API редактирования настроек, без прямых правок файла в обход UI).
- **FR-005**: При следующей инициации массового поиска любым пользователем система MUST предложить в поле таймаута только что сохранённое значение (см. FR-002). Так как в Karaoke один admin-пользователь, это эквивалентно «для всех последующих запусков».
- **FR-006**: Система MUST отвергать ввод в поле таймаута, который не является положительным целым числом ≥ 1, с понятным сообщением об ошибке; default в поле при этом MUST оставаться прежним.
- **FR-007**: Система MUST применять таймаут одинаково ко **всем** точкам входа массового поиска:
  - **Путь A**: `searchsongtextall` (кнопка в «Песни», серийный цикл в `ApiController.kt:4771`) — `Thread.sleep(timeout * 1000)` между `getLyricsSearch` вызовами (кроме последней итерации).
  - **Путь B**: `createfromfolder` (импорт папки, параллельный executor в `ApiController.kt:5302`, пул из 4 потоков) — rate-limit между `lyricsSearchExecutor.submit` вызовами (задержка перед `submit`, кроме последнего).
  Сохранённое значение — единое (глобально, в `KaraokeProperties`).
- **FR-008**: Backend MUST читать значение таймаута в момент запуска поиска (не кэшировать на старте JVM), чтобы изменения через Properties UI применялись без перезапуска.
- **FR-009** (rev 3): В процессе массового поиска (оба пути A и B) backend MUST замерять **время между двумя подряд успешными** запросами `getLyricsSearch` (оба вернули результат без ошибки) и сохранять **минимальное** такое время в локальной переменной цикла. Упавшие запросы (исключение, 5xx, timeout, null result) НЕ учитываются — только успешные пары.
- **FR-010** (rev 3): После завершения цикла массового поиска (Path A или Path B) backend MUST:
  - **(a)** записать в KaraokeApp-лог строку формата `[lyrics-search-summary] path=A|B count=N successful=M minIntervalMs=X|null totalDurationMs=Y`.
  - **(b)** отправить SSE-нотификацию через `SseNotificationService.send(...)` с типом `massSearchSummary` и payload `{ path: "A"|"B", count: N, successfulCount: M, minIntervalMs: Long?, totalDurationMs: Y }`. Тип события `massSearchSummary` MUST быть добавлен в broadcast-типы `SseNotificationService.addressedTypes` (по умолчанию broadcast, не addressed).

### Key Entities *(include if feature involves data)*

- **MassSearchTimeoutSetting** (глобальная backend-настройка). Атрибуты:
  - ключ: `lyricsSearchTimeoutSeconds` в `KaraokeProperties` (существующий класс в `karaoke-app/.../KaraokeProperties.kt`, хранится в `/sm-karaoke/system/Karaoke.properties`, base64-encoded);
  - значение: целое число ≥ 1 (в секундах);
  - default: `10` (если ключ отсутствует);
  - редактирование: через существующий Properties UI/API (ApiController.kt:5874 `getProperties()` + `webvue3/src/views/PropertiesView.vue`) — НЕ через прямые правки файла в обход UI.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% запусков массового поиска (любой из двух точек входа) начинаются с показа **существующего** модального окна подтверждения с дополнительным полем таймаута.
- **SC-002**: Между двумя последовательными запросами внутри одной сессии массового поиска проходит **не менее** выбранного пользователем значения таймаута (в секундах). Проверяется для обоих путей: A (searchsongtextall, серийный) и B (createfromfolder, параллельный с rate-limit).
- **SC-003**: При повторном запуске массового поиска тем же пользователем default в поле таймаута равен последнему введённому значению (round-trip: ввёл → диалог закрыт → запустил снова → default = введённое). Значение читается из `KaraokeProperties.lyricsSearchTimeoutSeconds`.
- **SC-004**: При первом запуске (нет сохранённого значения в KaraokeProperties) default = `10`.
- **SC-005**: Диалог отвергает невалидный ввод (0, отрицательные числа, нечисловые значения, пустое поле) и сообщает об ошибке понятным текстом; default при этом не меняется.
- **SC-006**: Изменение таймаута в одной точке входа (например, через импорт из папки) отражается в default при запуске через другую точку входа (кнопка в компоненте «Песни»), и наоборот. Single-user, единое значение в KaraokeProperties.
- **SC-007**: После изменения таймаута через Properties UI новые запуски поиска используют обновлённое значение (без перезапуска JVM).
- **SC-008** (rev 3): После завершения массового поиска с ≥ 2 успешными запросами в KaraokeApp-логе есть строка `[lyrics-search-summary]` с корректным `minIntervalMs`; в admin-SPA через SSE приходит событие `massSearchSummary` с тем же payload.

## Assumptions

- **Хранение настройки**: backend, через существующий класс `KaraokeProperties` (`karaoke-app/.../KaraokeProperties.kt:25`, файл `/sm-karaoke/system/Karaoke.properties` — `PATH_TO_KARAOKE_PROPERTIES_FILE` стр. 18, base64-encoded, **НЕ** в Constants.kt). Новое поле `lyricsSearchTimeoutSeconds` — в `Karaoke.kt` companion object рядом с `checkSearchAsync` (:159-162 — существующий паттерн). Редактирование — через существующий Properties UI/API (ApiController.kt:5874 + `PropertiesView.vue`). Никаких новых БД-таблиц, миграций или web-storage не требуется. Прямые правки файла в обход UI — только с согласия владельца.
- **Single-user**: в текущей инсталляции Karaoke один admin-пользователь, поэтому глобальная настройка (а не per-user) — корректное решение. Если появятся несколько пользователей — потребуется расширение (out of scope).
- **UI placement (rev 3, по решению владельца)**: поле таймаута — **в существующих** `<custom-confirm>` (SongsTable.vue:1289-1314 «Подтвердите поиск текста» + HomeView.vue:255-268 «Добавление файлов из папки»). **Никаких** отдельных модальных окон (принцип «сделай так же, как рядом»). `<custom-confirm>` уже поддерживает массив полей `params.fields` (boolean/select/textarea/text) — добавляем новое text-поле.
- **Массовый поиск уже работает** в обоих путях: (a) `ApiController.getSearchSongTextAll` (kнопка «Песни»), (b) `ApiController.doCreateFromFolder` → `lyricsSearchExecutor.submit` (импорт папки). Эта фича добавляет паузу/rate-limit на основе `KaraokeProperties.lyricsSearchTimeoutSeconds`.
- **Путь A** (searchsongtextall): серийный цикл `ids.forEach { getLyricsSearch }` (ApiController.kt:4786). Вставляем `Thread.sleep(timeout * 1000)` между вызовами (кроме последней итерации).
- **Путь B** (createfromfolder): параллельный пул `Executors.newFixedThreadPool(4)` (ApiController.kt:209). Search идёт через `lyricsSearchExecutor.submit { getLyricsSearch }` (ApiController.kt:5302). Rate-limit — задержка перед каждым `submit` (кроме последнего). Thread.sleep в main-thread блокирует submit-цикл — допустимо (single-admin, не критично к latency).
- **Авто-подбор (rev 3)**: `minIntervalMs` — это **диагностическая метрика** для пользователя («нащупать» нужный таймаут), а не автоматическое обновление `lyricsSearchTimeoutSeconds`. Пользователь сам решает, менять ли таймаут на основе логов/SSE-нотификаций.
- **SSE notification** (rev 3): используем существующий `SseNotificationService` (`karaoke-app/.../services/SseNotificationService.kt:89`). Новый тип события `massSearchSummary` добавляется в broadcast-типы (по умолчанию, как `recordChange`/`processWorkerState`). Frontend (`webvue3/src/App.vue:281` `EventSourcePolyfill`) уже подписан на broadcast — дополнительного wiring не требуется, только новая ветка `case 'massSearchSummary'` в switch'е.
- **Livedoc по конвенции фич**: создать `livedocs/features/316-search-timeout-configurable.md` (прецеденты 304/305/307/310/315 — нумерованный формат `NNN-name`), **НЕ** `docs/features/`. В `livedocs/INDEX.md` добавить строку-ссылку на новую фичу.
- **5-step verification применим** к обоим модулям: `karaoke-app` (поиск + KaraokeProperties + SSE), `webvue3` (custom-confirm с timeout). На nsa-i9: допустим 3-step subset (compile + lint + bootJar) для правок в `karaoke-app`/`webvue3` без `karaoke-public`.
- **Code Standards (Constitution VI)**: новые публичные функции/компоненты MUST сопровождаться KDoc/JSDoc; линтеры ktlint и ESLint MUST проходить без новых baseline-нарушений.
- **Git workflow**: фича разрабатывается в ветке `316-search-timeout-configurable`, прямые коммиты в `master` ЗАПРЕЩЕНЫ (Constitution §Рабочий процесс; CI-gate Karaoke AGENTS.md).
- **Дефолт 10 секунд** — взят из описания WP #61 verbatim. Это выбор владельца; никаких других дефолтов в спеке не предлагается.
- **Валидация ввода**: «положительное целое число ≥ 1». Верхняя граница намеренно не ограничивается (например, 9999 секунд валиден).
- **Out of scope для этой фичи**: (а) серверная защита от DDoS (она внешняя), (б) автоматическое обновление `lyricsSearchTimeoutSeconds` на основе `minIntervalMs` (только метрика, решение за пользователем), (в) персист нескольких таймаутов на пользователя (история), (г) расширение пула `lyricsSearchExecutor` с 4 потоков (если понадобится больше — отдельная задача).
