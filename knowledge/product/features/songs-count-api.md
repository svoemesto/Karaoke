# Публичный API: счётчик песен по фильтрам

> **Status**: active
> **Feature Key**: songs-count-api
> **Last Updated**: 2026-11-14
> **Spec**: [specs/390-songs-count/report.md](../../../specs/390-songs-count/report.md)
> Per-feature документ по [Constitution VI FR-009](../../../.specify/memory/constitution.md).

## Что делает

Даёт публичный счётчик: сколько песен подпадёт под фильтры поиска — без того чтобы
тянуть сами песни. Ответ — ровно одно поле `{"count": N}`.

Счётчик отвечает на те же фильтры, что и список песен: по названию, по автору (включая
алиасы — солист, участник группы), по тексту, по альбому. Правило видимости то же:
посетитель сайта видит только опубликованные песни, редактор — все.

## Зачем

Публичный поиск возвращает страницу песен, а пагинация показывает «найдено N» — то самое N,
которое клиент и так берёт из ответа списка. Отдельный эндпоинт нужен там, где список
запрашивать невыгодно или нельзя:

- превью фильтра до отправки запроса (показать «найдено 12 песен» по набору полей);
- подсчёт для кнопок и бейджей, где сама выборка не нужна;
- места, где список песен отдавать нельзя, а показать «ничего не найдено» — нужно.

До этой фичи единственным источником числа был `totalCount` в ответе списка, то есть
счётчик всегда стоил полной выборки песен.

## Как работает

1. Клиент спрашивает `GET /api/public/songs/count` с теми же параметрами фильтра, что и
   `GET /api/public/songs` (`songName`, `author`, `text`, `album`).
2. Ответ — `{"count": N}`: ровно одно поле, без списка песен.
3. Значение совпадает с `totalCount` из ответа списка для тех же фильтров: оба считаются
   одним и тем же способом по одной и той же карте условий, поэтому расхождение между
   плашкой «найдено N» и реальным числом песен на странице невозможно.
4. Слишком короткий запрос (суммарно меньше 3 символов в фильтрах) даёт `count = 0` —
   как и пустой список у `/songs`.
5. Мусорные значения в фильтрах дают `count = 0`, а не ошибку.

## Инварианты

- Число из счётчика равно числу песен, которое вернёт список с теми же фильтрами.
- Посетитель сайта не видит неопубликованные песни ни через счётчик, ни через список:
  правило видимости одно и то же.
- Редактор видит в счётчике столько же песен, сколько в списке, — включая черновики.
- Короткий запрос (меньше 3 символов) не обращается к базе и не пишет событие фильтра.
- Счётчик сам по себе не искажает статистику фильтров: в аналитике фильтр считается
  один раз — по списку.

## Известные ловушки

- Счётчик и список обязаны собирать фильтр **одной** функцией. Если условия начнут
  расходиться (например, счётчик перестанет учитывать алиасы автора), цифры начнут
  расходиться с реальностью — внешне это выглядит как «врёт счётчик».
- Короткий запрос отсекается **до** резолва автора и до запроса в базу: если это
  изменить, короткий запрос начнёт нагружать базу (и «повесит» её на частых кликах).
- Счётчик не пишет событие фильтра в аналитику. Если добавить такое событие, фильтры будут
  посчитаны дважды за один просмотр — и статистика фильтров станет неверной.
- Порог «3 символа» — общий для списка и счётчика. Менять его в одном месте нельзя.
- Алиас автора резолвится по таблице авторов: если совпадений нет, поиск идёт по строгому
  совпадению имени. Это поведение унаследовано от списка песен и должно оставаться
  одинаковым у обоих.
