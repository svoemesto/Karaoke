# Отчёт: #210 — O(n) поиск индекса маркера

**Work package:** #210
**PR:** #603 (https://github.com/svoemesto/Karaoke/pull/603), ветка `511-marker-index-binary-search`
**Merged:** коммит `5f4aaad5`
**Severity:** S2 (неверное поведение — лишняя нагрузка, не потеря данных)

## Проблема

`getCurrentMarkersIndex` и `getCurrentSyllablesIndex` перебирали **все** маркеры
линейным циклом. На тестовой песне 11718 «Говорит Деметра» — 2170 маркеров и
1822 слога. Обе функции вызываются на каждой смене текущего маркера и на каждом
`timeupdate`, то есть десятки раз в секунду.

`getCurrentSyllablesIndex` дополнительно вызывала `filter()` по всему массиву
при **каждом** вызове — то есть на каждый чих создавался новый массив из 1822
элементов.

## Решение

Маркеры отсортированы по времени, поэтому ответ находится двоичным поиском за
O(log n) без выделения памяти.

- `webvue3/src/utils/markerIndex.js` — чистая функция `findMarkerIndexByTime`.
- `getCurrentMarkersIndex()` — один вызов этой функции.
- `getCurrentSyllablesIndex()` — то же по отфильтрованным слогам.
- `visibleSyllables` — **computed**, пересчитывается один раз на изменение
  `sourceMarkers`, а не на каждый вызов.

Поведение не изменилось ни на один индекс.

## Доказательство эквивалентности

Не рассуждением, а фаззингом. Тест переписывает прежнюю линейную реализацию как
независимый эталон и сверяет:

- 4000 случайных случаев (1000 массивов × 4 позиции playhead)
- 500 случаев на реальной форме маркеров (2170 штук, 604 с)
- края допуска `diff = 0.02` с обеих сторон
- маркеры с одинаковым временем (соседние слоги)
- монотонность индекса по времени
- попадание точно в маркер при `t == markers[i].time`

## Побочно найденное и исправленное в том же PR

1. **`el.innerText` всегда был длиннее модели на один символ.** При отрисовке мы
   ставим хвостовой `<br>` (без него пустой contenteditable схлопывается по
   высоте), и `innerText` возвращает из-за него лишний `'\n'`. Гард
   `el.innerText === this.sourceText` в `syncSourceTextDom` **никогда не
   срабатывал** — редактор перерисовывался на каждом нажатии.

2. **Каретка сохранялась не во всех путях рендера.** Рендер вынесен в
   `renderSourceHtmlWithCaret()`; раньше каретку сохранял только
   `rehighlightSourceText`, а `syncSourceTextDom` перерисовывал вслепую.

## Честная часть: один тест изначально врал

Тест «каретка не прыгает в начало» падал с `Expected: 3, Received: 117`.
Инструментирование показало, что виноват не редактор: каретка стоит на позиции 2
и **не двигается ни на одном из 20 замеров за секунду**, `htmlLen` не меняется,
перерисовки нет. Но и `keyboard.type`, и `keyboard.insertText` вставляли символ
на позиции 116 — то есть «2 → 117» было артефактом измерения (`startOffset`
узлозависим, текст разбит на узлы). Тест переписан на клик мышью с проверкой
результата в тексте.
