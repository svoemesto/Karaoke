# Contract: видимость песен на публичных read-путях прода

Эта фича не добавляет новых endpoint'ов и не меняет форму
request/response — она сужает содержимое (behavioral contract) четырёх уже
существующих публичных read-путей модуля `karaoke-web` (единственный
backend-модуль, разворачиваемый на проде).

## Затрагиваемые поверхности

| Поверхность | Метод/путь | Кто использует |
|---|---|---|
| Закрома автора | `GET /api/public/zakroma?author=...` | `karaoke-public` (Vue SPA) |
| Спецзаказная плашка | `GET /api/public/zakroma?specialBucket=true` | `karaoke-public` (Vue SPA) |
| Поиск | `GET /api/public/songs?songName=...&author=...&text=...&album=...` | `karaoke-public` (Vue SPA) |
| Закрома (legacy) | `GET /zakroma?author=...` | Legacy Thymeleaf-страница `karaoke-web` |
| Поиск (legacy) | `GET /filter?songName=...&author=...&text=...&album=...` | Legacy Thymeleaf-страница `karaoke-web` |

## Контракт "было" → "стало"

**Было**: перечисленные endpoint'ы возвращали песни/альбомы/авторов
независимо от `id_status` — включая песни, ещё не прошедшие производственный
пайплайн (частично размеченные, без рендера и т.п.).

**Стало**: каждый элемент (песня) в ответе этих endpoint'ов MUST иметь
`id_status >= 3`. Автор/альбом, у которого после фильтрации не осталось ни
одной песни, MUST отсутствовать в ответе целиком (не должно быть
альбомов/авторов с пустым списком песен).

Форма JSON (поля DTO), HTTP-статусы, коды ошибок — без изменений. Клиенты
(`karaoke-public`), которые уже умеют работать с "автор без результатов"
(пустая выдача поиска) и "альбом без песен не показывается", дополнительных
изменений на фронте не требуют.

## Явно НЕ входит в контракт этой фичи

- `GET /api/public/song/{id}` (детальная карточка одной песни по прямой
  ссылке) — не меняется, остаётся отдельной зоной ответственности (см.
  Assumptions в `spec.md`).
- Любые admin-facing endpoint'ы (`webvue3`, `karaoke-app`) — контракт видимости
  песен там не меняется: все статусы остаются видимыми.
