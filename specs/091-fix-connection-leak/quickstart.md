# Quickstart: проверка устранения утечки соединений с БД

**Feature**: [spec.md](./spec.md) | **Data model**: [data-model.md](./data-model.md)

Автотестов нет — поведение зависит от реального PostgreSQL и реального
количества обработанных заданий. Проверка — вручную на `dev-pc`/`dev`.

## Предусловия

- Локальный стек поднят (`db`, `karaoke-app`).
- В очереди должно быть много (десятки-сотни) `WAITING`-заданий — на этом
  стенде их уже тысячи после предыдущих сессий, дополнительно готовить не
  нужно.
- После правок — пересобрать и перезапустить **только** модуль `app`:

```bash
cd deploy
bash do.sh build_app
bash do.sh start_app
```

## Сценарий 1 — воспроизведение утечки ДО фикса (baseline, опционально)

Если есть время — зафиксировать baseline на текущем (сломанном) коде перед
правкой, чтобы явно увидеть разницу:

1. Замерить текущее число соединений: `select count(*) from pg_stat_activity;`
2. Запустить очередь (`POST /api/processes/workerstartstop`), дать
   обработать несколько десятков заданий (пару минут).
3. Замерить снова — число соединений должно заметно вырасти (примерно на
   число обработанных за это время заданий, минус повторное использование
   одного и того же соединения внутри одного потока на несколько своих
   собственных вызовов).
4. Остановить очередь.

## Сценарий 2 — после фикса число соединений не растёт с числом обработанных заданий (US1, FR-001/FR-002/FR-004)

1. Замерить текущее число соединений: `select count(*) from pg_stat_activity;`
2. Запустить очередь, дать обработать несколько десятков-сотен заданий
   (несколько минут непрерывной работы).
3. **Ожидаемый результат**: число соединений с БД (`pg_stat_activity`)
   остаётся стабильным — колеблется в пределах числа реально одновременно
   работающих потоков (потоки Tomcat + `doStart()` + активные в моменте
   `KaraokeProcessThread`), а не растёт монотонно с каждым новым
   обработанным заданием.
4. Проверить лог `karaoke-app` — ошибок `too many clients` быть не должно.
5. Остановить очередь.

## Сценарий 3 — переиспользуемые потоки не деградировали (US1, FR-003)

1. Выполнить подряд 20-30 запросов к любому HTTP-эндпоинту админки,
   использующему `WORKING_DATABASE` (например, `POST /api/processes/workerstatus`).
2. **Ожидаемый результат**: число соединений с БД не растёт с каждым
   запросом (тот же тест, что уже проводился в specs/087/quickstart.md,
   Сценарий 3 — подтверждает, что фикс этой фичи не сломал переиспользование).
3. Дать очереди поработать некоторое время параллельно с этими
   HTTP-запросами — убедиться, что `doStart()`'s собственное соединение
   тоже не закрывается ошибочно (очередь продолжает обрабатывать задания
   без необъяснимых обрывов).
