## Сверки

Спорное/недоказанное и подтверждения уже заведённых BR, без severity и без нового ID.

1. **BR-176 подтверждается** (`KaraokeDbTable.kt:138–158`, реестр: `null-as-string:db`, DATA S2). В этой порции дефект воспроизводится на **штатном админском пути**, а не только в теории: `webvue3/src/components/News/NewsTable.vue:350–352` (`saveEdit`: `clearPublishAt: !this.form.publishAt`) → `NewsController.kt:113–114` (`item.publishAt = null`) → `item.save()` (`:118`) → diff `publish_at` уходит в `else -> ps.setString(index, it.recordDiffValueNew.toString())` (`KaraokeDbTable.kt:148`) → `UPDATE … publish_at = 'null'` → PostgreSQL `invalid input syntax for type timestamp: "null"` → UPDATE не применяется, `save()` возвращает управление, контроллер отдаёт `item.id` (`:119`) — ложный успех. Второй сценарий того же корня: очистка ссылки (`link=""` → `item.link = null`, `:112`) при непустом `link` в БД пишет в `varchar` литерал `null`. Новый BR не завожу.
2. **BR-181 подтверждается** (`createDbInstance` гасит `SQLException`/UNIQUE-нарушение и возвращает `null`, реестр: `unique-race:pictures`, ERR S3). Дополнительные потребители того же корня: `Dictionary.createNewDictionaryItem` (`Dictionary.kt:108–112`) рассчитывает на проброс (ветка `catch` → повторный `getItem`), но `createDbInstance` не бросает — защита от гонки по `uq_tbl_dictionaries_name_value` мертва; `PublicCartController.toggle` (`PublicCartController.kt:107–108`) игнорирует результат `CartItem.createNew` и отвечает `200 {"inCart": true}` при неудавшемся INSERT. Не дублирую. Отдельный вопрос лиду: `KaraokeDbTable.delete`/`deleteIn` (`:817–820`, `:845–847`) имеют тот же паттерн (`catch` → `println` → `false`/`0`), из-за чего `SongEditorController`/`PublicSongEditorController` отдают `ok: true, deleted: 0` и при сбое DELETE — расширять BR-181 или заводить отдельный BR?
3. **`RecordChangeMessage.getSetString` и `null`** (`Messages.kt:126–139`): «`'${recordDiff.recordDiffValueNew.toString().replace("'","''")}'`» превращает `null` в `'null'` при push в SERVER (`Utils.kt:1401`). Проверенного пути нет: `save()` сейчас не умеет записывать NULL (BR-176), `INSERT` через `getSqlToInsert` опускает null-поля, а строка LOCAL с NULL при значении на SERVER возможна только при внешней записи в БД. Если такой путь появится — для текстовых колонок на SERVER запишется литерал `null`, для типизированных UPDATE упадёт.
4. **Lost update в diff-UPDATE** (`KaraokeDbTable.kt:102–128`): два писателя одного поля читают состояние и перетирают друг друга (compare-and-set нет). Это задокументированный компромисс (`knowledge/domains/persistence/domain.md`, «Решение 2: Diff-based UPDATE»), а не отдельная находка без инцидента.
5. **`CrossSong.publications` — unchecked-каст** (`CrossSong.kt:78–99`): `(fields.get(songItem) as Map<*, *>)[columnField] as String` даст `TypeCastException`, если `Song.fields` не содержит ключ (`Song.kt:8192` кладёт `DATE` только при непустом `publish_date`). Сегодня все вызывающие списки отфильтрованы `date != "" && time != ""` (`Publication.kt:1790–1791`), поэтому путь недостижим; при новом вызове — 500.
6. **`GuitarString.fretNextString`** (`GuitarString.kt:36–48`): `currString = strings[currStringIndex]` не продвигает индекс, для `GS1` значение совпадает с `GS2`. На поведение не влияет: `MusicChord.kt:597` клампит `Integer.min(fretNextString, maxDiffBetweenFrets)` (3–4), то есть значение не используется. Мёртвая логика без риска — не находка.
7. **KDoc `invalidateSchemaCache`** (`KaraokeDbTable.kt:405–410`) предупреждает о `ConcurrentModificationException` на `schemaCache.keys.removeAll { … }`, но `ConcurrentHashMap.KeySetView` даёт weakly-consistent итератор; предупреждение, вероятно, неверно. Не дефект поведения, но KDoc вводит в заблуждение.
8. **`Author.countWithNewAlbum` / `loadIdsByNames`** (`Author.kt:510–527`, `:320–346`) при SQL-ошибке возвращают `0`/частичную map — тот же класс «ошибка = пусто», что P-15-03, но доказанного пути к порче данных нет (только неверный бейдж/неполный резолв имени).
