# Админский редактор: SubsEdit

> **Домен**: system (frontend)
> **Компонента**: `webvue3/src/components/Songs/edit/SubsEdit.vue` —
> редактор караоке-разметки поверх Wavesurfer.js. Публичный (волонтёрский)
> редактор вынесен в `composable-karaoke-editor.md`.

## Файл

`webvue3/src/components/Songs/edit/SubsEdit.vue`

## Назначение

Раскладка текста песни на слоги и таймкоды: разметка, привязка к аудио,
пересчёт при правке текста, предпросмотр. Пользователь — администратор.

## Блок исходного текста — contenteditable

Текст песни правится **не** через `textarea`, а через

```html
<div id="editor" ref="sourceTextEditor" contenteditable="true">
```

Причина: подсвеченные слова из словаря (см. ниже) требуют форматирования
внутри текста, а `textarea` его не умеет.

### Инварианты contenteditable-блока

- **Хвостовой `<br>` обязателен.** Без него пустой contenteditable схлопывается
  по высоте.
- **Чтение нормализовано.** Из-за хвостового `<br>` `el.innerText` возвращает
  лишний `'\n'` и всегда на один символ длиннее модели. Поэтому текст читается
  только через `readEditorText()`; прямое `el.innerText` использовать нельзя.
  Пока чтение шло мимо метода, гард в `syncSourceTextDom` не срабатывал **никогда**,
  и содержимое перерисовывалось на каждом нажатии.
- **Любая запись в `innerHTML` сохраняет каретку.** Перерисовка идёт через
  `renderSourceHtmlWithCaret()`, который запоминает смещение в координатах
  документа и восстанавливает его. Запись в `innerHTML` в обход этого метода
  выбрасывает выделение, и Chrome восстанавливает его рядом — символ ввода
  попадает не туда, куда печатали.
- **CSS-специфичность блока нельзя понижать.** Блок исходного текста — элемент
  родительской сетки, и правило `[class^='se-grid-item'] { display: grid }`
  делает его потомков grid-элементами. CSS **блокифицирует** их ПОСЛЕ каскада:
  `display: inline` на `<span>` превращается в `block`, и каждое подсвеченное
  слово встаёт на отдельную строку. Отсюда `.se-grid-item-sourcetext.se-sourcetext-ce`
  — два класса, чтобы перебить правило по специфичности.

## Подсветка слов из словаря

- Словарь: **«Слова для внимания»**, новая запись в `tbl_dictionaries`.
- Подсветка — `<span class="se-hl-attention">` (жирный, жёлтый фон), а **не**
  `<mark>`: bootstrap-reboot задаёт `mark` жёлтый фон и перебивает его.
- Совпадение точное, регистронезависимое. **`е` и `ё` — разные слова**: взаимная
  заменяемость намеренно не поддержана.
- Пересчёт — с debounce; словарь подгружается асинхронно и не блокирует
  показ редактора.
- Правка слова снимает подсветку на лету: если после правки оно перестало
  входить в словарь, подсветка исчезает без перезагрузки.
- Добавление и удаление слов идут через модалку-вопрос — там же выбирается
  словарь, как при выборе поискового движка.

## Перерисовка регионов: обновление на месте

`redrawMarkers()` обновляет регионы **инкрементально**, через
`syncRegionsInPlace()`: у каждого маркера есть ссылка `marker.region`, и она
переживает вызовы, потому что объекты маркеров не пересоздаются
(`Object.assign` в `updateMarkersBySyllables` закомментирован намеренно).

Полная перерисовка (`redrawMarkersFull()`) применяется только когда регионы
создавать нельзя — до готовности аудио. Это инвариант: `addRegion()` до получения
длительности необратимо ставит `start = 0`.

**Полная перерисовка на нажатии клавиши недопустима.** Замерено на песне
11718 (2170 маркеров): `clearRegions()` — 1978 мс, создание всех регионов заново —
127 мс, `setOptions` по всем — 8.9 мс. То есть удаление дороже создания в 15
раз, и полная перерисовка стоила ~2.1 с на каждое нажатие.

## Стоимость нажатия клавиши

Цепочка на каждое нажатие:

```text
sourceText -> getSyllables -> updateMarkersBySyllables
            -> syncMarkersFromSpecTags -> redrawMarkers
            -> tail / textFormatted / notesFormatted / chordsFormatted
```

Бюджет задержки ввода — **16 мс** (один кадр). После перевода регионов на
обновление на месте p50 упал с 2365 мс до 234 мс.

Остаток распределён, единственного узкого места нет:

| | мс на нажатие |
|---|---|
| `redrawMarkers` | 80 |
| `syncMarkersFromSpecTags` | 77 |
| `updateMarkersBySyllables` | 47 |
| форматтеры (computed) | ~30 |

Форматтеры пересчитываются **два-три раза за нажатие**: их вызывает и watcher
`sourceText`, и `sourceMarkers` (который триггерит сам `updateMarkersBySyllables`),
и `currentSyllablesIndex`. Дальнейшее сокращение требует debounce или
инкрементального пересчёта, а не точечных правок.

## Инварианты

- **У маркера с показанным типом есть `region`**; `region === null` допустим для
  скрытого типа и до готовности аудио. Нарушение даёт `TypeError` на нажатии.
- **`save()` выстраивает сохранения в очередь** (`saving` / `saveQueued`). Два
  параллельных `POST /api/song/savesourcetextmarkers` могут перетереть друг друга.
- **Эндпоинты изменения размера долей вызываются один раз.** `/api/song/diffbeatsinc`
  и `diffbeatsdec` **мутируют БД** (`diffBeats ± 1` и `saveToDb()`), а не читают.
- **Индекс маркера ищется двоичным поиском** по отсортированному времени
  (`findMarkerIndexByTime`); фильтр слогов — computed `visibleSyllables`, а не
  `filter()` внутри функции.

## Экранирование перед v-html

`getFormattedText`, `getFormattedNotes`, `getFormattedChords` и `getTail`
конкатенируют пользовательский текст песни в HTML-строки, которые рендерятся
через `v-html`. Весь пользовательский ввод экранируется `escapeHtml` — и в
тексте слогов, и в `txtHtml` / `chordHtml` (`marker.chord`) / `noteHtml`
(`marker.note`), и в `textCurr` / `textNext` / `textEnd`.

Экранируется **HTML-форма**, а не исходные значения: `chord` и `note` нужны
для сравнений в логике.

## Тесты редактора

Тесты админки живут в двух слоях, и оба выполняются в CI (`npm run test:unit`).

### Unit (node --test, без браузера и без стенда)

- `webvue3/src/utils/__tests__/` — экранирование, подсветка слов, индекс
  маркера, форматирование даты.
- `webvue3/src/composables/__tests__/` — разметка маркеров на сохранение и
  обратно.
- `webvue3/src/components/Songs/edit/__tests__/subsEdit-invariants.test.js` —
  **статическая** проверка инварианта #194: `computed lstIndexesTabsVariant` и
  метод `getStringsForAllNotesInSong` не присваивают свойства компонента, а
  кламп индекса варианта строя живёт в watcher. Проверить это браузером нельзя:
  разница между старой и новой реализацией — момент применения клампа (render
  против watcher), а проверяемое значение одинаково.
- `webvue3/src/__tests__/e2e-suite-guard.test.js` — страж содержательности
  e2e-набора: запрещает спецификацию без утверждений, тавтологичное утверждение
  «положительное время», зашитый id песни, абсолютный адрес вместо `baseURL` и
  фиксированные ожидания в десятки секунд.

### E2E (Playwright, нужен стенд админки)

- Набор — `webvue3/e2e/*.spec.js`, общая оснастка — `webvue3/e2e/fixtures/song.js`.
- **id песни задаётся переменной окружения `E2E_SONG_ID`** (по умолчанию 11718 —
  «Говорит Деметра» на локальном стенде), адрес приложения — `E2E_BASE_URL`.
  Набор не привязан к содержимому одной боевой песни: опорные точки и
  ожидания выводятся из фактических данных, а не из констант.
- Готовность редактора определяется по состоянию компонента (маркеры загружены,
  аудио декодировано), а не по `waitForTimeout`: набор идёт параллельно
  (`fullyParallel`, 2 воркера по умолчанию, `E2E_WORKERS` переопределяет) и
  прогоняется за ~1.5 мин вместо ~4.6 мин. Воркеров больше двух ставить нельзя:
  пул соединений БД стенда не выдерживает нескольких одновременных редакторов с
  2170 маркерами. Ретраев нет (`retries: 0`) — в CI повторный прогон маскировал
  бы нестабильность.
- **Измерялки — не тесты.** Замер задержки ввода (#205) и стоимости вставки
  HTML форматтера (#214) вынесены из набора в `webvue3/scripts/`:
  `measure-input-latency.mjs` и `measure-formatter-vhtml.mjs` (npm-скрипты
  `measure:input-latency` и `measure:formatter-vhtml`). В наборе они были
  спецификациями без утверждений и давали «зелёный» результат там, где ничего
  не проверялось.
- Проверка «до/после» — `webvue3/scripts/e2e-regression-check.mjs`
  (npm-скрипт `check:e2e:regressions`): поднимает админку из исходников
  (vite dev server + прокси к стенду), ломает код точечной мутацией и требует,
  чтобы соответствующий тест УПАЛ; после отмены мутации — прошёл.
