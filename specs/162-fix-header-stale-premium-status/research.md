# Phase 0 Research: Устаревший премиум-статус в шапке сайта

Спецификация (`spec.md`, Assumptions) намеренно оставила механизм и интервал
автообновления статуса открытыми — «предмет решения на этапе планирования».
Ниже — решения по всем пунктам, требовавшим исследования.

## Decision 1: Механизм обновления — клиентский поллинг существующего эндпоинта

**Decision**: Периодически вызывать уже существующий `GET /api/public/auth/me`
из `useAuth.js` (через уже существующую `fetchMe()`), пока пользователь залогинен.
Никаких новых backend-эндпоинтов, WebSocket или SSE.

**Rationale**:
- `GET /api/public/auth/me` (`PublicAuthController.me`) уже возвращает свежий
  `SiteUser.toDTO()` на каждый вызов — сервер ничего не кэширует
  (см. `SiteUserResolver`: «Не кэшируется — бан/снятие премиума должны
  действовать немедленно, а не по TTL какого-то локального кэша» — тот же
  принцип действует и здесь, проблема чисто в том, что клиент его редко
  вызывает).
- В стеке проекта уже есть прецедент того же паттерна — `ChatView.vue`
  обновляет непрочитанные сообщения периодическим поллингом
  (`fetchMessages`), а не через WebSocket/SSE. Push-инфраструктуры (Redis
  pub/sub, WebSocket-канал) в проекте нет и её введение ради одного
  статус-флага непропорционально задаче.
- Ноль изменений на backend — меньше поверхность фикса для бага, который
  целиком клиентский (данные на сервере всегда были верны).

**Alternatives considered**:
- *WebSocket/SSE от сервера при изменении подписки* — отклонено: требует
  новой инфраструктуры реального времени, которой в проекте нет (Redis не
  используется, см. Конституцию, «Технологический стек»); несоразмерно
  задаче с неточной точностью в единицы минут.
- *Обновление только при переходах между страницами (`router.afterEach`)* —
  отклонено как единственный механизм: не покрывает edge case «пользователь
  долго сидит на одной странице (например `/song` или `/player`) без
  переходов» (FR-002 требует обновления и без явных действий пользователя).
- *Обновление только вручную по клику* — отклонено: противоречит FR-002
  («без обязательного требования вручную перезагрузить страницу»).

## Decision 2: Интервал поллинга — 5 минут

**Decision**: Фоновый вызов `fetchMe()` раз в 5 минут, пока `isLoggedIn === true`.

**Rationale**:
- Спека определяет «разумный срок» как «минуты, а не часы» (Assumptions) —
  5 минут заведомо укладывается.
- Премиум-статус меняется биллинговыми событиями (истечение подписки,
  оплата), не требующими секундной точности — в отличие от, например,
  live-чата.
- Держит частоту обращений к `WORKING_DATABASE` (через
  `SiteUserTokenService.resolveToken`) на разумном уровне даже при большом
  числе одновременно открытых залогиненных вкладок.

**Alternatives considered**:
- *30 секунд* — отклонено: избыточная нагрузка на БД ради статуса, для
  которого секундная точность не нужна.
- *30+ минут* — отклонено: пользователь, у которого подписка только что
  закончилась и который продолжает активно пользоваться сайтом, слишком
  долго видел бы неверный статус — не ощущается как «автоматическое»
  обновление.

## Decision 3: Где стартует таймер — один раз, внутри `useAuth.js`

**Decision**: Ленивый module-level старт (guard-флаг вида `started`) внутри
`useAuth.js`, при первом вызове `useAuth()` из залогинённого состояния — не в
`App.vue`, не в каждом компоненте отдельно.

**Rationale**:
- `token`/`user` в `useAuth.js` уже являются module-level singleton
  (комментарий в файле: «паттерн useDesign.js — одно состояние на всё
  приложение»). Таймер обновления того же состояния логично живёт там же.
- `AuthStatusWidget.vue` монтируется заново на нескольких view
  (`HomeView`, `SearchView`, `ZakromaView`, `SongView`) — если бы таймер
  стартовал в `onMounted` компонента без guard'а, при повторных
  переходах между этими страницами плодились бы дублирующиеся интервалы.
- `App.vue` сегодня вообще не импортирует `useAuth` и не несёт
  cross-cutting auth-логику — вводить туда эту ответственность значило бы
  завести второе место, отвечающее за жизненный цикл сессии, вместо
  единственного (`useAuth.js`).

**Alternatives considered**:
- *Старт в `App.vue` (`onMounted`)* — отклонено: `App.vue` сегодня не знает
  про auth вообще; пришлось бы дублировать guard-логику, которая и так
  естественно живёт как module-level флаг в `useAuth.js`.
- *Старт в каждом компоненте, использующем `useAuth()`* — отклонено: без
  явного singleton-guard'а даёт дублирующиеся таймеры (утечка).

## Decision 4: Обработка сетевых сбоев фонового обновления

**Decision**: Фоновый (периодический) вызов `fetchMe()` оборачивается в
`try/catch`; при сетевой ошибке (`authGet` реджектит промис на
`xhr.onerror`, см. `authApi.js`) — тик молча пропускается, `user.value` не
трогается. Существующая логика внутри `fetchMe()` и так не пишет
`user.value = ...` ни при какой ветке кроме `status === 200`, а очищает
сессию только на `status === 401` — это уже соответствует FR-005 (не
изобретать «премиум», которого нет); недостающая часть — не дать
необработанному отклонённому промису прервать периодический таймер/всплыть
как unhandled rejection в консоль.

**Rationale**: FR-005 требует, чтобы временная недоступность проверки не
приводила к ложному показу премиума. Оставление старого (возможно,
устаревшего) значения при сбое — безопасное поведение по умолчанию (не
хуже, чем до фикса), а не попытка угадать новое состояние. Следующий тик
через 5 минут естественным образом выступает повтором — отдельный
retry-with-backoff избыточен.

**Alternatives considered**:
- *Retry с backoff при сбое* — отклонено: следующий плановый тик через 5
  минут уже даёт эффект повтора; отдельный механизм — лишняя сложность для
  некритичного по времени статуса.

## Decision 5: Кросс-вкладочная синхронизация — не требуется

**Decision**: Не синхронизировать состояние между вкладками мгновенно
(например, через `storage`-event или `BroadcastChannel`); каждая вкладка
независимо поллит `fetchMe()` со своим 5-минутным интервалом.

**Rationale**: Явно снято в Assumptions спецификации: «синхронизация
статуса между вкладками допустима с той же задержкой, что и обновление в
рамках одной вкладки; мгновенная кросс-вкладочная синхронизация не
требуется». Каждая вкладка и так сойдётся к актуальному статусу за то же
время (≤5 минут).

**Alternatives considered**:
- *`storage`-event / `BroadcastChannel` для мгновенной синхронизации между
  вкладками* — отклонено как избыточное для этой спеки; можно рассмотреть
  отдельной фичей, если станет реальной жалобой пользователей.
