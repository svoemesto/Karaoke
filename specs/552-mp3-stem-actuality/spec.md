## Контекст дефекта (проверено 2026-10-23)

1. specs/544 убрал `LOCAL_FILESYSTEM` из `locations` у пяти mp3-типов и удаляет локальную копию после успешной загрузки в оба хранилища.
2. Рендер демо открывает headless-плеер; тот при `init()` грузит `/api/song/{id}/fileminus.mp3` и `filevoice.mp3`, и `convertFlacToMp3()` создаёт локальную копию заново — другим кодировщиком (VBR `-qscale:a 2` вместо 320k CBR) и без перезаливки объекта в хранилище.
3. `HealthReport` видит появившуюся дисковую копию и сравнивает её размер с объектом в LOCAL (`HealthReport.kt:775`) и REMOTE (`HealthReport.kt:1133`) → 4 ERROR на песню.
4. Пока дисковой копии нет, тот же код сравнивает LOCAL↔REMOTE и даёт OK — поэтому до рендера записей не было.
5. Подтверждение на живых песнях 8243 и 18517: объекты в хранилищах 3 618 525 Б, дисковая копия 1 724 357 Б, ctime 2026-10-23 11:00:41.

## User Scenarios & Testing *(mandatory)*

### User Story 1 — После рендера демо нет ложных записей (Priority: P1)

Администратор переводит песню в статус 6, запускается рендер демо и публикация. Открыв отчёт HR, он видит «всё хорошо»: ни одной записи о неактуальности mp3-стемов, и перезагружать файлы в хранилища не нужно.

**Why this priority**: это ровно жалоба владельца (#328) и единственный сценарий, который ломает доверие к HR.

**Independent Test**: у песни есть согласованные объекты mp3 в LOCAL и REMOTE, дисковой копии нет. Выполнить сценарий «плеер создал дисковую копию» (запрос `fileminus.mp3`/`filevoice.mp3`) и пересчитать HR → записей о неактуальности нет.

**Acceptance Scenarios**:

1. **Given** объекты LOCAL и REMOTE совпадают по размеру и дисковой копии нет, **When** плеер создаёт дисковую копию и HR пересчитывается, **Then** для mp3-типов нет ни ERROR, ни WARNING об актуальности.
2. **Given** то же состояние, но размеры LOCAL и REMOTE различаются, **When** HR пересчитывается, **Then** расхождение по-прежнему показывается (WARNING), без действий, требующих дисковой копии.
3. **Given** дисковая копия есть, а объекты в хранилищах совпадают, **When** HR пересчитывается, **Then** статус OK — наличие или отсутствие дисковой копии не меняет вердикт.

---

### User Story 2 — Настоящая рассинхронизация хранилищ видна (Priority: P2)

Администратор видит предупреждение, когда объекты в локальном и удалённом хранилищах действительно различаются по размеру, и понимает, что именно не так.

**Why this priority**: фикс не должен превратиться в «всегда OK» — иначе HR перестанет ловить реальные расхождения.

**Independent Test**: подменить размер объекта в одном хранилище (или взять песню с реальным расхождением) → HR показывает WARNING с текстом о расхождении хранилищ.

**Acceptance Scenarios**:

1. **Given** LOCAL size ≠ REMOTE size, **When** HR пересчитывается, **Then** есть WARNING с текстом о расхождении размеров между хранилищами (без упоминания отсутствующего диска).
2. **Given** объект есть только в одном хранилище, **When** HR пересчитывается, **Then** поведение прежнее: предлагается восстановление/загрузка из доступного источника.

---

### User Story 3 — Единое правило для всех mp3-типов (Priority: P3)

Правило «диск не является источником» действует для всех пяти storage-only mp3-типов, а не только для аккомпанемента и вокала.

**Why this priority**: следующий рендер/экспорт может создать копию bass/drums, и баг вернётся в другом типе.

**Independent Test**: прогнать сценарий US1 для `MP3_BASS`/`MP3_DRUMS` (экспорт стема) → записей нет.

**Acceptance Scenarios**:

1. **Given** любой из пяти mp3-типов и согласованные хранилища, **When** на диске есть копия, **Then** статус OK.

---

### Edge Cases

- **Дисковой копии нет вообще** — сравнение LOCAL↔REMOTE (текущая ветка), поведение не меняется.
- **Оба хранилища недоступны** — circuit breaker даёт FATAL_ERROR, как сейчас.
- **Размер объекта неизвестен (`null` из кеша)** — не считать расхождением (текущее правило «null → актуально» сохраняется).
- **Multipart-etag** — etag между хранилищами не сравнивается, поэтому расхождение `…-2` не даёт ложного предупреждения.
- **Исторически «вылеченные» вручную песни** (в оба хранилища залита VBR-копия) — размеры совпадают, записей нет; качество не пересматривается.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Для типа файла, у которого `locations` не содержит `LOCAL_FILESYSTEM`, HealthReport MUST NOT использовать файл на диске как эталон актуальности: при наличии объекта в обоих хранилищах сравнение идёт только между хранилищами. Существующие ветки восстановления из дисковой копии, когда объектов в хранилищах нет, сохраняются (это ремонт, а не проверка актуальности).
- **FR-002**: Для таких типов при наличии объекта в обоих хранилищах актуальность MUST определяться сравнением размеров объектов LOCAL и REMOTE.
- **FR-003**: Если размеры совпадают, отчёт MUST иметь статус OK.
- **FR-004**: Если размеры различаются, отчёт MUST иметь статус WARNING с текстом о расхождении размеров между локальным и удалённым хранилищами; текст MUST NOT ссылаться на отсутствующий файл на диске.
- **FR-005**: Правило FR-001…FR-004 MUST применяться ко всем пяти mp3-типам: `MP3_ACCOMPANIMENT`, `MP3_VOCAL`, `MP3_BASS`, `MP3_DRUMS`, `MP3_OTHER`.
- **FR-006**: Для типов, у которых `LOCAL_FILESYSTEM` есть, поведение MUST остаться прежним: дисковая копия остаётся источником, сравнение с хранилищами сохраняется.
- **FR-007**: При наличии объекта в обоих хранилищах наличие или отсутствие дисковой копии для storage-only типа MUST NOT влиять ни на статус отчёта, ни на набор предлагаемых действий.
- **FR-008**: Проверка MUST продолжать использовать кеш метаданных (`StorageMetadataCache`) и MUST NOT добавлять новых обращений к MinIO на каждый пересчёт.

### Key Entities

- **HealthReport** — строка отчёта «проблема/решение» по одному файлу песни; для mp3-типов описывает согласованность хранилищ.
- **mp3-стем** — производный аудиофайл песни (`<name>-accompaniment.mp3` и т.п.); каноническое представление — объект в хранилище, не файл на диске.
- **StorageMetadataCache** — вечный кеш `exists`/`size`/`etag`; единственный источник размеров для проверки.

## Success Criteria *(mandatory)*

- **SC-001**: В сценарии «согласованные хранилища → плеер создал дисковую копию → пересчёт HR» число записей об актуальности mp3-стемов равно 0 (сейчас 4).
- **SC-002**: Ручная перезагрузка файлов в хранилища после рендера демо не требуется ни для одной песни с согласованными хранилищами.
- **SC-003**: При искусственно созданном расхождении размеров LOCAL↔REMOTE отчёт по-прежнему содержит предупреждение (100 % проверенных случаев).
- **SC-004**: Правило покрыто регрессией для всех пяти mp3-типов; тест падает, если тип снова начнёт учитывать диск.
- **SC-005**: Число обращений к MinIO на один пересчёт HR для mp3-типов не растёт относительно текущего (используется кеш).

## Assumptions

- Локальное и удалённое хранилища получают один и тот же файл; расхождение размеров означает реальную рассинхронизацию.
- Сравнение по размеру достаточно: etag у multipart-загрузок не является MD5 и различается между путями заливки.
- Дисковая копия mp3 может появляться в любой момент (плеер, экспорт, импорт) и удаляться штатной чисткой — это нормальный фон, а не версия файла.

## Non-Goals

- Единый кодировщик/битрейт mp3 (320k CBR vs VBR q2) и восстановление 320k-качества.
- Пересмотр specs/544 (удаление локальных mp3 после загрузки).
- Перенос ленивой генерации в отдельный кеш-каталог и его жизненный цикл.
- Лечение исторических рассинхронизаций и backfill.
- Рендер демо и Telegram-публикация.
