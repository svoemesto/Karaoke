# Phase 0: Research — замена поискового бэкенда для текстов песен

## Вопрос 1: Каким self-hosted движком заменить SearXNG для поиска URL с текстами песен?

**Decision**: [4get](https://git.lolcat.ca/lolcat/4get) — самостоятельно хостируемый
мета-поисковик (агрегатор поверх нескольких движков-источников), развёрнутый как
отдельный Docker-контейнер рядом с существующим `searxng` (не вместо него).

**Rationale**:
- 4get — та же архитектурная категория, что и SearXNG (мета-поиск, агрегирующий
  результаты нескольких источников), а не единичный скрейпер одного движка — то есть
  не наследует проблему нынешнего fallback на DuckDuckGo HTML (rate-limited,
  задокументировано в `docs/features/llm-lyrics-search.md` как известная ловушка).
- 4get явно поддерживает **Yandex** как один из движков-источников. Это напрямую
  бьёт по вероятной причине «мало/пустых результатов»: запросы вида «автор текст
  песни название» на русском лучше индексируются Yandex, чем Google/Bing/
  DuckDuckGo — если движок SearXNG сегодня не использует Yandex (или Yandex у него
  заблокирован/недоступен из текущей конфигурации), это объясняет низкий hit rate.
- Лёгкий (PHP, минимум JS), Docker-friendly, отдаёт JSON-ответ — как и сегодняшний
  SearXNG (`format=json`), что упрощает адаптацию парсинга в Kotlin без изменения
  внешнего контракта `searchUrls(query: String): List<String>` (FR-004).
- Сообщество (HN/LowEndTalk-обсуждения самохостинга) описывает 4get как «лучшую
  альтернативу Searx» по практическому опыту эксплуатации.
- Полностью самостоятельно хостируется — соответствует явному решению пользователя
  (self-hosted, не внешний SaaS) и Principle I конституции.

**Alternatives considered**:
- **YaCy** — независимый краулер/индекс, а не агрегатор поверх чужих движков. Для
  небольшого self-hosted инстанса без собственного полноценного краулинга всего
  веба покрытие будет заведомо хуже, чем у мета-поисковика — отклонено, так как
  напрямую противоречит цели «больше результатов».
- **Whoogle** — скрейпит только Google (единственный источник). Та же категория
  хрупкости, что и уже опробованный fallback на DuckDuckGo HTML (единая точка
  отказа/бан). Отклонено.
- **Websurfx** (Rust, мета-поиск, похожая категория на 4get) — жизнеспособный
  запасной вариант, если 4get не оправдает себя на практике; не выбран первым
  из-за менее очевидной поддержки Yandex и меньшей зрелости сообщества на момент
  анализа. Зафиксировать как fallback-опцию для этапа реализации/тестирования.
- **Yandex Cloud Search API** (`getYandexSearch`/`searchSongInYandex` в
  `UtilsAI.kt` — уже реализован в кодовой базе, но не используется в потоке
  `getSearXNGSearch`) — отклонено: это платный внешний облачный SaaS (требует
  IAM-токен Yandex Cloud), пользователь явно выбрал self-hosted замену, а не
  внешний API.
- **Донастройка самого SearXNG** (включить больше движков/повысить rate-limit) —
  отклонено, так как пользователь явно попросил заменить сам SearXNG, а не
  донастроить его; к тому же документированный fallback-путь тоже не спасает
  (DuckDuckGo rate-limited), что говорит о структурной проблеме текущего
  инстанса/набора движков.

**Note for implementation**: точный HTTP-путь и параметры JSON API 4get (эндпоинт
поиска, имя параметра выбора движка-источника, формат ответа) необходимо сверить
с документацией/исходниками развёрнутого инстанса 4get на этапе реализации —
в этом плане фиксируется только необходимый функциональный контракт (см.
`contracts/lyrics-search-backend.md`), а не точная wire-схема стороннего проекта.

## Вопрос 2: Как избежать конфликта с уже существующим использованием SearXNG для обложек альбомов?

**Decision**: новый бэкенд получает собственное Spring-свойство
(`lyrics-search.base-url`, отдельно от `searxng.base-url`) и отдельный
docker-compose сервис. Существующий сервис `searxng` и свойство `searxng.base-url`
остаются без изменений — их продолжает использовать только
`AlbumCoverService.searchSearxngImages` (FR-007, вне рамок задачи).

**Rationale**: `SearchTool` (поиск текстов) и `AlbumCoverService` (поиск обложек)
сегодня оба читают одно и то же свойство `searxng.base-url` / `SEARXNG_BASE_URL` —
но обслуживают разные цели. Замена общей точки конфигурации сломала бы поиск
обложек, который явно исключён из рамок этой задачи пользователем.

**Alternatives considered**:
- Переиспользовать `searxng.base-url` и для нового бэкенда — отклонено: ломает
  независимость двух фич и делает диплой одной фичи риском для другой.

## Вопрос 3: Что считать «интерфейсом без изменений» (FR-004) при разных форматах ответа?

**Decision**: контракт по-прежнему `fun searchUrls(query: String): List<String>` —
вход (строка запроса) и выход (список URL) идентичны сегодняшним. Вся адаптация
формата ответа 4get к `List<String>` инкапсулируется внутри интеграционного слоя
(аналог сегодняшнего `SearchTool`), вызывающий код (`LyricsFinderService`, поток
`getSearXNGSearch` в `UtilsAI.kt`) не меняется.

**Rationale**: прямое требование FR-004/FR-005 спецификации — минимизировать
блэст-радиус замены, не трогая скрейпинг/LLM-анализ после получения списка URL.

**Alternatives considered**: расширить сигнатуру (возвращать заголовки/сниппеты
вместе с URL) — отклонено на этом этапе как расширение вне рамок задачи; при
необходимости может быть отдельной будущей фичей.
