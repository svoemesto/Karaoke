# Data Model: Устранить утечку соединений с БД от одноразовых потоков очереди

**Feature**: [spec.md](./spec.md) | **Research**: [research.md](./research.md)

Схема БД не меняется — эта фича целиком про жизненный цикл физических
JDBC-соединений, без новых таблиц/колонок.

## Физическое соединение с БД (существующая сущность — `java.sql.Connection`, кешируемое в `ThreadLocal` внутри `KaraokeConnection`)

| Атрибут | До фикса | После фикса |
|---|---|---|
| Освобождение для одноразовых потоков | Никогда — соединение остаётся в `ThreadLocal`-слоте потока даже после того, как поток завершился и умер | Явно закрывается и удаляется из `ThreadLocal` через `closeThreadConnection()`, вызываемый в `finally` в конце `run()` |
| Освобождение для долгоживущих потоков | Переиспользуется между обращениями (specs/087) | Не меняется — `closeThreadConnection()` для них не вызывается |
| Self-healing (`isClosed`/`isValid(3)`) | Не меняется | Не меняется — применяется только к ещё не закрытым соединениям долгоживущих потоков |

## Тип потока (концептуальная классификация — не отдельная сущность)

| Тип потока | Пример | Вызывает `closeThreadConnection()`? |
|---|---|---|
| Одноразовый/недолговечный | `KaraokeProcessThread` — создаётся заново на каждое задание очереди, никогда не переиспользуется | Да, в `finally` в конце `run()` |
| Долгоживущий/переиспользуемый | Поток `KaraokeProcessWorker.doStart()` (единственный, живёт всё время работы очереди) | Нет |
| Долгоживущий/переиспользуемый | Поток из пула Tomcat (обрабатывает много HTTP-запросов за свою жизнь) | Нет |

## Валидационные правила (из Functional Requirements)

- FR-001/FR-002: `closeThreadConnection()` вызывается ровно один раз, в
  `finally`, оборачивающем всё тело `run()` для `karaokeProcess != null` —
  гарантированно срабатывает при любом исходе (успех/ошибка/форс-стоп/
  непредвиденное исключение).
- FR-003: метод не вызывается ни в `doStart()`, ни где-либо в коде,
  относящемся к обработке HTTP-запросов — их кеш соединения (specs/087)
  остаётся нетронутым.
- FR-004: поскольку каждый `KaraokeProcessThread` теперь гарантированно
  закрывает своё единственное соединение по завершении, число
  одновременно открытых соединений от очереди в любой момент времени
  ограничено числом **одновременно активных** (ещё не завершившихся)
  потоков заданий — а не общим числом когда-либо обработанных заданий.
