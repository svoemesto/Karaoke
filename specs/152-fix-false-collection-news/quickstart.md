# Quickstart: проверка фикса ложной новости «в коллекции»

Ручная проверка (в CI автотестов для этой области нет — см. constitution.md, «Тесты: в CI
нет»). Выполняется на LOCAL-сэндбоксе, не на проде: `Connection.remote()` в karaoke-app
всегда указывает на реальную серверную БД, поэтому прогонять сценарии ниже напрямую через
prod-подключение нельзя без явного согласия пользователя на каждое действие.

## Предпосылки

- Локальный docker-стек поднят (`db`, `karaoke-web`, `karaoke-app`), см.
  `docs/onboarding.md`.
- Доступ к LOCAL Postgres (`tbl_songs`, `tbl_news`).

## Сценарий 1 — воспроизведение бага ДО фикса (regression baseline)

1. Выбрать (или подготовить) песню `id_status >= 6` со всеми флагами готовности `true`
   в `player_readiness_flags` (т.е. реально готовую), у которой **уже есть** строка в
   `tbl_news` с `category='air'` и этим `song_id`.
2. Убрать из её `player_readiness_flags` ключ `newsAvailableAnnounced` (или выставить
   `false`) — искусственно эмулирует «эта копия БД ещё не видела флаг», при том что
   контент по факту давно готов.
3. Отправить в `POST /changerecords` батч `dataUpdate` для этой песни, содержащий SQL,
   который заново выставляет `player_readiness_flags` с `newsAvailableAnnounced=true`
   (эмулирует sync-батч с сервера/локали, «досылающий» уже истинное значение).
4. **До фикса**: ожидается лишняя новая строка `tbl_news` с `category='premium'` для
   этой песни — воспроизводит инцидент.

## Сценарий 2 — после фикса, тот же батч

Повторить шаги 1-3 после применения фикса.

**Ожидаемый результат**: новая строка `tbl_news` с `category='premium'` **не создаётся**
(шаг 5 контракта — уже есть `category='air'`). `SELECT count(*) FROM tbl_news WHERE
song_id = <id> AND category = 'premium'` — без изменений относительно состояния до батча.

## Сценарий 3 — легитимное первое появление по-прежнему работает

1. Взять песню, у которой `newsAvailableAnnounced` ещё никогда не было `true`, и
   `category='premium'`/`category='air'` новостей по ней ещё нет.
2. Довести её до полной готовности контента (все флаги `true`) через обычный путь
   (`saveToDb()` — например, штатное сохранение в редакторе), затем отправить batch
   в `POST /changerecords`, как в реальном sync-цикле.
3. **Ожидаемый результат**: ровно одна новая строка `tbl_news` с `category='premium'`.
   `SELECT count(*) ...` до → 0, после → 1.

## Сценарий 4 — идемпотентность при повторном батче

1. Взять песню из сценария 3, у которой новость `category='premium'` уже создана.
2. Повторно отправить тот же (или похожий) `dataUpdate`-батч в `POST /changerecords`.
3. **Ожидаемый результат**: количество строк `tbl_news` с `category='premium'` для этой
   песни остаётся равным 1 (не растёт).

## Контрольная точка

Все 4 сценария в одном прогоне — минимальная проверка, что фикс закрывает
FR-001…FR-007 из [spec.md](./spec.md): ложные срабатывания устранены (Сценарий 2), а
легитимные (Сценарий 3) и повторные (Сценарий 4) сохраняют корректное поведение.
