# Research: Устойчивый импорт файлов из папки

**Feature**: [spec.md](./spec.md) | **Plan**: [plan.md](./plan.md)

Technical Context не содержит открытых `NEEDS CLARIFICATION` — стек и
архитектура уже зафиксированы существующим кодом. Задача Phase 0 для этой
фичи — диагностика первопричины OOM и проверка формирования кортежа заданий
(это баг-фикс + верификация), а не выбор технологий. Ниже — находки по коду
(текущее состояние на момент создания плана) и решение по подходу.

## Находка A — `getListFiles` материализует весь обход дерева в память, без фильтрации на этом шаге и без закрытия `Stream` (главная причина OOM)

**Код** (`Utils.kt:2408-2463`):

```kotlin
fun getListFiles(pathToFolder: String, extension: String = "", startWith: String = ""): List<String> =
    try {
        Files.walk(Path(pathToFolder))
            .filter(Files::isRegularFile)
            .map { it.toString() }
            .filter { it.endsWith(extension) && it.startsWith("$pathToFolder/$startWith") }
            .toList()
            .sorted()
    } catch (_: Exception) { emptyList() }

fun getListFiles(pathToFolder: String, extensions: List<String> = listOf(), ...): List<String> {
    val preRes = getListFiles(pathToFolder)   // extension="" по умолчанию!
    // ...несколько .filter{}.addAll() проходов по preRes...
}
```

Вызов из `Song.createFromPath` — `getListFiles(startFolder, listOf("flac","mp3","m4a"))` —
уходит во вторую (multi-extension) перегрузку, которая вызывает первую
**без указания расширения** (`extension` по умолчанию `""`). Поскольку
`"".endsWith("")` истинно для любой строки, первая перегрузка возвращает
**абсолютно все обычные файлы** дерева (не только flac/mp3/m4a) —
изображения, видео, служебные файлы, что угодно, — и сразу же:

1. `.toList()` материализует их **все одним `List<String>` в памяти**, не
   потоково — при большой/глубоко вложенной папке (сотни тысяч файлов любых
   типов) это и есть прямая причина `OutOfMemoryError` независимо от того,
   сколько из них реально flac/mp3/m4a.
2. `Stream`, который возвращает `Files.walk(...)`, **не закрывается**
   (`.use { }`/try-with-resources отсутствует) — по контракту
   `Files.walk` в JDK это утечка открытого файлового дескриптора на каждый
   вызов, что дополнительно деградирует систему при повторных импортах.
3. Вторая перегрузка добавляет ещё несколько полных проходов
   (`filteredEndRes`, `filteredStartRes`, `result`) поверх уже
   материализованного `preRes` — лишние копии списка, хоть и меньшего
   размера после фильтрации.

**Decision**: Переписать однорасширенческую `getListFiles` на **однопроходную**
обработку: фильтровать по расширению/префиксу **во время** обхода (внутри
цепочки `Stream`, до какой-либо материализации), закрывать `Stream` через
`.use { stream -> ... }` (Kotlin extension для `AutoCloseable`), и убрать
скрытый вызов "без расширения" из multi-extension перегрузки — она должна
делать один обход с фильтром "any of extensions" внутри `Stream`, а не звать
однорасширенческую версию с пустым фильтром. Возврат — по-прежнему
`List<String>` (вызывающий код, `createFromPath`, уже проходит по нему
`forEach`), но без промежуточного полного "все файлы папки" списка.

**Alternatives considered**:
- Оставить `List<String>`, но добавить верхний лимит числа файлов
  (например, обрывать импорт после N файлов) — отклонено как основное
  решение: пользователь явно просил «работать не падая при большом
  количестве», а не «отказывать при большом количестве»; жёсткий лимит
  можно держать в уме как защитную сетку, но не как замену устранению
  корневой причины (лишняя буферизация нефильтрованного списка).
- Перевести возврат `getListFiles` на `Sequence<String>`/`Flow<String>` по
  всей цепочке вызовов (включая `createFromPath`) — рассмотрено, но
  расширяет blast radius на все существующие вызовы `getListFiles` в
  проекте без явной необходимости; текущая находка объясняется не самим
  типом `List`, а буферизацией **нефильтрованного** списка и отсутствием
  закрытия `Stream" — точечный фикс (пункт Decision выше) достаточен.

## Находка B — тяжёлая пост-обработка каждой новой песни не ограничена по конкурентности в рамках одного HTTP-запроса

**Код** (`ApiController.kt:5204-5323`, `doCreateFromFolder`): после
`Song.createFromPath(...)` (которая возвращает список **всех** новых песен
сразу) идёт `createdList.forEach { newSettings -> ... }` — сам цикл
последовательный (не параллельный), но внутри него для каждой песни без
найденного текста запускается:

```kotlin
if (!textResolved) {
    thread(start = true) {
        try { getLyricsSearch(settings = newSettings, ...) }
        catch (e: Exception) { println(...) }
    }
}
```

`thread(start = true)` — fire-and-forget, без пула/семафора/лимита. При
массовом импорте (сотни новых песен без текста одновременно) это порождает
**столько же параллельных фоновых потоков**, каждый из которых делает
сетевой запрос к SearXNG — неограниченный рост числа одновременных потоков
и сетевых соединений, отдельно от находки A (не главная причина OOM на
типичных объёмах, но реальный риск при по-настоящему больших партиях —
FR-004 в `spec.md`).

Дополнительно: `Song.createFromPath` (синхронный шаг перед `forEach`) сам
по себе держит в памяти `MutableList<Song>` (`result`) со всеми только что
созданными объектами `Song` на весь остаток HTTP-запроса — при очень
большом числе новых песен это не главная причина OOM (после фикса Находки A
размер этого списка равен реальному числу подходящих файлов, а не всех
файлов дерева), но усиливает пиковое потребление памяти во время
пост-обработки.

**Decision**: Ограничить число одновременных фоновых потоков поиска текста
бounded-исполнителем (например, фиксированный `ExecutorService`/семафор с
небольшим лимитом параллелизма — конкретное число подбирается при
реализации по аналогии с уже существующими батч-константами проекта,
`SyncRegistry`: `chunked(10)`/`DELETE_CHUNK_SIZE=200`/`rowChunkSize
25-500`), вместо `thread(start = true)` без ограничения. `try/catch` вокруг
пост-обработки одной песни уже есть (строка 5307) — сохранить эту
изоляцию, чтобы ошибка на одной песне не прерывала обработку остальных
(FR-005).

**Alternatives considered**:
- Полностью убрать синхронный `MutableList<Song>` и перейти на
  потоковую обработку "файл → песня → пост-обработка → освобождение" за
  один проход без промежуточного накопления — рассмотрено как более полное
  решение, но увеличивает blast radius (пришлось бы менять контракт
  `createFromPath`, который используется в двух местах — `ApiController` и
  `MainController` — с разной пост-обработкой после него). Отклонено для
  этой итерации: главный вклад в OOM — Находка A; данная находка (B) —
  вторичный риск, для которого точечное ограничение конкурентности
  (Decision выше) достаточно и меньше по blast radius.

## Находка C — `KEY_BPM_FROM_FILE` из импорта в отдельном лейне от `DEMUCS2`: подтверждено пользователем, что это НАМЕРЕННО, не баг

**Код** (`Song.kt:7608-7622`, `createFromPath`):

```kotlin
KaraokeProcess.createProcess(
    settings = settings, action = KaraokeProcessTypes.KEY_BPM_FROM_FILE,
    doWait = true, prior = -1, threadId = 2,   // ← THREAD_LANE_STEM_JOBS
)
KaraokeProcess.createProcess(
    settings = settings, action = KaraokeProcessTypes.DEMUCS2,
    doWait = true, prior = -1, threadId = 1,   // ← THREAD_LANE_HEALTH_REPORT
)
```

Первый проход планирования ошибочно классифицировал это как
рассогласование лейна, требующее исправления (расхождение с
`HealthReport.kt:1174-1176` и `ApiController.kt:6383-6386`, где
`KEY_BPM_FROM_FILE` создаётся с `threadId=1`). **Правка пользователя**:
`KEY_BPM_FROM_FILE` при импорте намеренно ставится в отдельный лейн — он
не входит в кортеж (`демукс → mp3 → upload local → upload remote`, см.
`spec.md` FR-006, который **не упоминает** `KEY_BPM_FROM_FILE`), от него не
зависят дальнейшие шаги кортежа, и его можно и нужно выполнять независимо,
не занимая слот в лейне, где идёт сам кортеж. Расхождение с
`HealthReport.kt`/`createKeyBpmFinderProcess` — это два разных пути
постановки одного и того же типа задания в разных контекстах (сразу при
импорте vs через каскад автоисправления/ручной эндпоинт), а не одна и та же
линия кода, обязанная быть идентичной; само по себе это не нарушает ни
один FR `spec.md`.

**Действительно значимая проверка для US2** — сам кортеж, как он определён
в `spec.md` FR-006: `DEMUCS2` → `FF_MP3_ACCOMPANIMENT`/`FF_MP3_VOCAL` →
`UPLOAD_TO_LOCAL_STORE` → `UPLOAD_TO_REMOTE_STORE`. Все эти шаги уже
корректно единообразны — `threadId = KaraokeProcess.THREAD_LANE_HEALTH_REPORT` (=1):
- `DEMUCS2` — явно, в самом `createFromPath` (строка ~7621).
- `FF_MP3_ACCOMPANIMENT`/`FF_MP3_VOCAL`/`UPLOAD_TO_LOCAL_STORE`/
  `UPLOAD_TO_REMOTE_STORE` создаются позже каскадом
  `HealthReport.startRepairAll`/`onRepairProcessFinished`
  (`actionsLocalFileSystem`/`actionsLocalStorage`/`actionsRemoteStorage`),
  где `threadId` по умолчанию — `THREAD_LANE_HEALTH_REPORT` (строка 335), с
  единственным исключением — наследование `threadId` уже запущенного
  «родителя» (строка 348, `inProgressParentProcess.first().threadId`). Для
  этой цепочки «родитель» — всегда предыдущий шаг **того же** кортежа
  (например, `DEMUCS2` для `FF_MP3_ACCOMPANIMENT`), сам уже в
  `THREAD_LANE_HEALTH_REPORT` — наследование не может увести кортеж в
  другой лейн. `KEY_BPM_FROM_FILE` никогда не выступает «родителем» для
  этих шагов (health-report проверяет зависимость по наличию файла на
  диске, а не по завершению `KEY_BPM_FROM_FILE`) — риска, что его лейн (2)
  "просочится" в кортеж через этот механизм, нет.

**Decision**: Кода менять не нужно — кортеж (`DEMUCS2` → `FF_MP3_*` →
`UPLOAD_*`) уже корректно и единообразно формируется в
`THREAD_LANE_HEALTH_REPORT`. Вместо правки `threadId` — добавить явный
комментарий в `Song.createFromPath` рядом с постановкой
`KEY_BPM_FROM_FILE`, объясняющий, что отдельный лейн — осознанное
архитектурное решение (задание не входит в кортеж и не должно
конкурировать за его слот), чтобы не спровоцировать повторную ошибочную
"починку" в будущем — именно так эта находка была неверно
классифицирована при первом проходе планирования. User Story 2 остаётся
задачей **верификации** (кортеж уже корректен, но это не было явно
подтверждено тестом/ручной проверкой до этой фичи) и документирования
инварианта, а не задачей исправления бага.

**Alternatives considered**:
- Всё же выровнять `KEY_BPM_FROM_FILE` под `threadId=1` — отклонено по
  прямому указанию пользователя: задание намеренно независимо от кортежа,
  перенос в общий лейн без необходимости увеличил бы очередь лейна кортежа
  заданиями, от которых он не зависит.

## Итоговый подход

1. Переписать `Utils.getListFiles` на однопроходный, фильтрующий во время
   обхода, закрываемый обход (Находка A) — покрывает FR-001/FR-002/FR-003
   (основная причина OOM).
2. Ограничить конкурентность фоновых `thread(start = true)`-запусков поиска
   текста в `ApiController.doCreateFromFolder` (Находка B) — покрывает
   FR-004/FR-005 (защита от вторичного риска на по-настоящему больших
   партиях, устойчивость к частичным сбоям).
3. Подтвердить (без правки кода) и задокументировать, что кортеж `DEMUCS2`
   → `FF_MP3_*` → `UPLOAD_*` уже корректно и единообразно формируется в
   `THREAD_LANE_HEALTH_REPORT`, а отдельный лейн `KEY_BPM_FROM_FILE` —
   намеренная изоляция независимого задания, не входящего в кортеж
   (Находка C) — покрывает FR-006/FR-007/FR-008 (US2: корректный кортеж
   заданий в одном лейне), напрямую отвечает на запрос пользователя
   «проверить, что… правильно формируется кортеж заданий в рамках одного
   лейна». Добавляется поясняющий комментарий в коде, чтобы намеренная
   изоляция не была снова ошибочно принята за баг.

Все три пункта — точечные правки внутри уже существующих файлов/паттернов,
без новых зависимостей, без миграций схемы БД, без изменений фронтенда.
