# Сообщения об ошибках: контракт публичного API и логирование

> **Домен**: system (cross-cutting)
> **Компонента**: как в Караоке принято сообщать об ошибке наружу и в лог.
> Составлено по разбору закрытых задач проекта (374 задачи, 201 комментарий).

## Зачем

Обработка ошибок — самая частая тема в закрытых задачах: **86 из 201
комментария**. Повторяющиеся дефекты одни и те же:

- причина сбоя терялась (`catch` без логирования) — «восстановление глушило
  сбой, причина ERROR терялась»;
- наружу уходил Java-стектрейс вместо кода — «приложения при ошибках забиты
  стектрейсами, читать их тяжело»;
- не различались «не найдено» и «нет доступа» — «401/403/5xx трактовались как
  „Плейлист не найден“».

## Правило 1. Публичный API отдаёт `errorCode`, а не текст исключения

Ответ с ошибкой — JSON с **одним** полем `errorCode` и человекочитаемым
значением в виде `область.причина` (camelCase во второй части):

```kotlin
return ResponseEntity.status(HttpStatus.BAD_REQUEST)
    .body(mapOf("errorCode" to "share.tokenMissing"))
```

Существующие значения (не выдумывать новые без нужды):
`share.tokenMissing`, `share.notFound`, `share.notOwner`, `share.notEditor`,
`share.leaseExpired`, `share.internal`, `site.remote_unavailable`.

**Failure**: тело с `exception.message`, HTML-страница ошибки в ответе JSON-эндпоинта,
стектрейс в теле ответа.

## Правило 2. Код состояния различает класс причины

| Ситуация | Статус |
|---|---|
| Некорректный ввод | 400 |
| Нет аутентификации | 401 |
| Нет прав | 403 |
| Объекта нет (или скрыт от этого пользователя) | 404 |
| Внешний сервис недоступен | 502 |
| Внутренняя ошибка | 500 |

Скрытый от пользователя объект отдаётся как **отсутствующий** (404), а не 403:
иначе существование объекта утекает.

**Failure**: 401/403 отдаются как 404 («Плейлист не найден» при истёкшей сессии),
5xx трактуется как «не найдено», 500 на некорректный ввод.

## Правило 3. Причину не глушить

`catch` обязан либо пробросить исключение, либо залогировать его **с причиной**.
Причина в логе — это **тип и сообщение** исключения, а не кадры стека
(см. Правило 4 и спеку 732):

```kotlin
// ПЛОХО: причина исчезает, в лог попадает только факт
catch (e: Exception) { logger.error("sync failed") }

// ПРАВИЛЬНО: причина в логе одной строкой, стек — по требованию (LOG_STACKTRACES=true)
catch (e: Exception) {
    AppLog.error(
        category = "infra.sync",
        code = "SYNC-001",
        event = "sync.failed",
        fields = mapOf("stage" to "restore"),
        error = e,
    )
    throw SyncException("sync.restore_failed", e)
}
```

**Failure**: `catch (e: Exception) { }`, `catch` с `printStackTrace()` и без
логирования, статус в БД без причины; передача исключения в обычный логгер
(`logger.error("…", e)`) — это печать стектрейса, см. Правило 4.

## Правило 4. В лог — нормальное сообщение, стект — по требованию

Пользователю — одна строка с кодом и понятным текстом. В лог — тоже нормальное
сообщение: **тип и сообщение исключения (с цепочкой причин)**, а не простыня
кадров `at com.svoemesto…`.

* **Как это сделано сейчас (спека 732, KARAOKE-387).**
  * `AppLog.error/warn` — одна строка `event=… code=… key=value cause=Тип: сообщение <- Тип: сообщение`;
    полный стек — только при `LOG_STACKTRACES=true`.
  * **Глобальный «пол»**: конвертер `causeChain`
    (`karaoke-app/.../logging/CauseChainConverter.kt`, подключён в
    `logback-spring.xml`) печатает исключение **одной строкой** — цепочкой
    причин, без кадров, — для ВСЕХ логгеров, включая Spring и Tomcat.
    Тот же флаг `LOG_STACKTRACES=true` возвращает полный стек.
  * Поэтому обычный `logger.error("…", e)` больше **не** даёт простыни кадров:
    причина видна, разбор не страдает.
* **Что всё ещё нельзя**: `e.printStackTrace()` (прямой вывод в stdout) и
  `println(...)` с текстом исключения вместо структурированной записи.

**Failure**: `e.printStackTrace()` в новом коде; технический текст исключения
в пользовательском сообщении; десятки строк `at …` в рабочем логе.

## Правило 5. Ошибка не должна выглядеть успехом

Пустой ответ, частичный результат и «нет данных» — разные вещи. Если выборка
упала, прежние результаты не выдаются за результат нового запроса.

**Failure**: при ошибке поиска отдаются результаты предыдущего запроса;
пустой список без признака ошибки там, где ожидался сбой.
