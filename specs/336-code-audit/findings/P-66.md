### P-66-06: webvue3/src/player/KaraokePlayer.js:302–312 — ERR (S3)

- Зеркало: BR-304 (P-44).
- Что не так: `catch` в `init()` не различает отмену/уничтожение и не проверяет, что ошибка
  относится к текущей загрузке: он безусловно пишет «Ошибка: …» в `#kp-loading` контейнера. В
  karaoke-public этот же код опасен при быстром переключении трека (сообщение попадает в DOM
  следующего трека); в webvue3 сценарий другой и уже — писать приходится в отсоединённый

   → RangeError. Достижимо только при ручном URL с пустым DEMO-фрагментом (пп. 2); в офлайн-рендере
   `_buildWaveforms` не вызывается вовсе (`:292`).
9. **В DEMO-режиме ползунки громкости не влияют на звук:** `_renderFrame` каждый кадр
   перезаписывает `accGain/vocGain` (`:2619–2626`) по формуле фейда, игнорируя
   `this.accGain.gain.value`, выставленный ползунком (`:966–977`). Косметика; в офлайн-рендере
   аудио вообще не используется.
10. **Премиум-гейтов в этой копии нет by design.** `_mode === 'api'` здесь — админский API
    (`/api/song/{id}/playerdata`, `ApiController.kt:8187`), а не публичный `/api/public/player`;
    пункты «Экспорт аудио…»/«Сохранить файл» — штатные админские функции, отдельный гейт
    `canExport` не требуется (в karaoke-public он есть, потому что там публичный периметр).
    Известный нерабочий путь в этом блоке — P-66-02.
11. **Согласованность `_demoFadeInSeconds` с серверным `demoFragmentFadeInSeconds`:** клиент
    считает фейд-ин как время первого текстового слота после сдвига (`:275–279`), сервер
    (`Song.demoFragmentFadeInSeconds`) — как «куplet минус отступ под фейд-ин». В MP4 фейд-ин
    применяет ffmpeg по серверному значению (`PlayerMp4MuxService.kt:105–116`), клиентский
    `_demoFadeInSeconds` в офлайне на звук не влияет; в браузере (DEMO по ручному URL) при
    первой строке, начавшейся до `demoStart`, клиент даст 0 вместо серверного значения.
    Сверка, не запись.
