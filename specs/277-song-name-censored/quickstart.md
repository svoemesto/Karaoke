# Quickstart: проверка фичи «Поле `song_name_censored` в `tbl_songs`»

В проекте нет CI-тестов для этого слоя — проверка выполняется вручную, в
админке + прямые SQL-запросы + браузер (опционально, для публичного API).
Все шаги — после реализации задач из `tasks.md`.

## Предпосылки

- Локальный docker-стек поднят (`db`, `karaoke-app`, `karaoke-web`, `webvue3`)
  — см. `deploy/do.sh`.
- Миграция `deploy/karaoke-db/42_song_name_censored.sql` применена на
  LOCAL Postgres (`psql … -f 42_song_name_censored.sql` или через
  pgAdmin).
- `karaoke-app`/`karaoke-web` пересобраны и перезапущены; `webvue3`
  пересобран (`npm run build` или через `do.sh`).
- БД содержит ≥100 песен (любой реальный датасет подойдёт; для чистоты
  эксперимента желательно ≥1000).

## Сценарий 1 — миграция заполняет колонку копией song_name (US4)

1. ДО миграции: `SELECT COUNT(*) FROM tbl_songs WHERE song_name = '';`
   — запомнить число N.
2. Применить миграцию `42_song_name_censored.sql`.
3. Выполнить:
   ```sql
   SELECT COUNT(*) FROM tbl_songs
   WHERE song_name_censored = '' OR song_name_censored IS NULL;
   ```
   Должно вернуть ровно N (пустые `song_name` ⇒ пустые
   `song_name_censored`).
4. Выполнить:
   ```sql
   SELECT COUNT(*) FROM tbl_songs
   WHERE song_name_censored != song_name AND song_name != '';
   ```
   Должно вернуть 0 (для НЕ-пустых `song_name` колонка копия).
5. Выполнить `SELECT sync LOCAL↔SERVER` (через админку «Синхронизация»
   или CLI) — должно пройти без ошибок recordhash (новая колонка учтена
   в md5).

**Ожидаемо**: SC-001 — выполнено; миграция безопасна, без потери данных.

## Сценарий 2 — фоновый реckan через CustomFunction (US1)

1. В словаре `tbl_dictionaries WHERE dict_name='Censored'` есть слова
   «бдсм», «война» (или добавить вручную через `DictionariesView.vue`).
2. Выбрать 3-5 песен с `song_name`, содержащим эти слова
   (`SELECT id, song_name FROM tbl_songs WHERE song_name ILIKE '%бдсм%'
   OR song_name ILIKE '%война%' LIMIT 5`).
3. Открыть `webvue3` → Главная → нажать кнопку
   «Пересканировать цензурированные названия песен» → подтвердить.
4. Дождаться SSE-тоста «Обработано N песен за M секунд».
5. Повторно выполнить запрос из шага 2 — `song_name_censored` этих
   песен должен содержать маски `█` вместо «бдсм»/«война».
6. Повторно нажать кнопку → убедиться, что ответ `"OK"`, функция
   отрабатывает идемпотентно (`song_name_censored` не меняется для
   уже-обработанных строк).

**Ожидаемо**: SC-002 — выполнено (после реckana все строки имеют
актуальное цензурирование); гонок нет.

## Сценарий 3 — гонки при параллельном запуске (US1-AC2)

1. Запустить реckan (как в Сценарии 2, шаг 3), НЕ дожидаясь
   завершения (он работает в фоне).
2. Сразу же повторно нажать кнопку → должно появиться сообщение
   «Уже запущено, дождитесь завершения», новый поток НЕ стартует.
3. Дождаться завершения первого запуска (SSE-тост).
4. Нажать кнопку ещё раз — должно стартовать заново (флаг сброшен).

**Ожидаемо**: один процесс за раз, идемпотентный повторный запуск.

## Сценарий 4 — ручное редактирование в SongEdit (US2)

1. Открыть `webvue3` → Песни → выбрать любую песню → редактирование.
2. Под полем «Композиция» должно появиться поле «Композиция
   (цензурированная)» с авто-заполненным значением из БД (после
   миграции = `song_name`, после реckana = цензурированная форма).
3. Навести курсор на label поля → должен появиться браузерный тултип
   с предупреждением о публикации без фильтрации.
4. Ввести в поле строку «Кастомное Название», нажать «Сохранить».
5. Перезагрузить страницу редактирования — значение должно
   сохраниться («Кастомное Название»).
6. Запросить публичный API: `GET /api/song/<id>` — поле
   `songNameCensored` должно содержать «Кастомное Название».
7. Перезагрузить страницу редактирования ещё 9 раз — значение
   остаётся «Кастомное Название».

**Ожидаемо**: SC-004 — выполнено; ручная правка переживает
перезагрузку и видна в публичном API.

## Сценарий 5 — ручная правка переживает переименование song_name (US2-AC3)

1. В SongEdit выбрать песню, у которой уже есть ручное значение
   `songNameCensored = «Кастомное Название»» (из Сценария 4).
2. Изменить поле «Композиция» на что-то другое, например «Другое
   название песни».
3. Нажать «Сохранить».
4. Переоткрыть карточку — поле «Композиция (цензурированная)»
   должно остаться «Кастомное Название» (НЕ пересчитанным из нового
   `songName`).

**Ожидаемо**: SC-005 — выполнено; ручная правка сохранена.

## Сценарий 6 — пустое значение не пересчитывается (US2-AC2)

1. В SongEdit выбрать любую песню.
2. Очистить поле «Композиция (цензурированная)» (пустая строка),
   сохранить.
3. Переоткрыть — пустое значение сохранено, НЕ заполнено заново из
   словаря.
4. Запустить реckan — `song_name_censored` этой песни будет
   перезаписана (это by design, см. Edge Cases спеки).

**Ожидаемо**: до CustomFunction пустое значение остаётся пустым;
CustomFunction ПЕРЕЗАПИСЫВАЕТ (см. политику Overwrite).

## Сценарий 7 — устранение обращений к tbl_dictionaries (US3)

1. Включить SQL-логирование в `karaoke-app` (или поставить breakpoint в
   `CensoredWordsDictionary.dict` через IDE).
2. Выполнить `GET /api/public/songs?limit=100` через браузер или curl.
3. Подсчитать число запросов `SELECT … FROM tbl_dictionaries WHERE
   dict_name='Censored'` в логах.
4. **До фичи**: ~100 вызовов (по одному на каждую песню в списке).
5. **После фичи**: 0 вызовов на этапе сборки DTO-списка (словарь не
   загружается вообще, `songNameCensored` берётся из БД-колонки).

**Ожидаемо**: SC-003 — выполнено; 0 словарных запросов на горячем пути.

## Сценарий 8 — новые песни автоматически получают цензурированное имя (FR-003)

1. Через `karaoke-app` CLI или админку создать новую песню с
   `song_name = 'Тестовая песня про войну'`.
2. Сразу после создания (без реckana) проверить
   `SELECT song_name_censored FROM tbl_songs WHERE song_name = 'Тестовая
   песня про войну';` — должно вернуть
   `'Тестовая песня про [██████]'` (или похожая маскированная форма),
   НЕ `'Тестовая песня про войну'`.

**Ожидаемо**: авто-заполнение в `saveToDb()` работает для новых песен
без необходимости CustomFunction.

## Сценарий 9 — recordhash включает новую колонку (US4-AC2)

1. После миграции выполнить:
   ```sql
   SELECT song_name, song_name_censored, recordhash
   FROM tbl_songs LIMIT 5;
   ```
2. Затем:
   ```sql
   UPDATE tbl_songs SET song_name_censored = song_name_censored || '_test'
   WHERE id = (SELECT MIN(id) FROM tbl_songs);
   ```
3. Снова выполнить запрос из шага 1 для этой строки — `recordhash`
   должен измениться.
4. Откатить: `UPDATE tbl_songs SET song_name_censored = REPLACE(song_name_censored, '_test', '') WHERE id = (SELECT MIN(id) FROM tbl_songs);`.

**Ожидаемо**: `recordhash` реагирует на изменение `song_name_censored`
(включена в md5).
