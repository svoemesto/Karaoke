# Phase 1 Data Model: Редактор видит все песни независимо от статуса

Фича не вводит новых сущностей, полей или БД-миграций. Она переиспользует
два уже существующих поля на двух уже существующих сущностях.

## Song (существующая сущность, без изменений схемы)

| Поле | Тип | Значение для этой фичи |
|---|---|---|
| `id_status` (`idStatus`) | целочисленный статус производственного пайплайна | Порог видимости для не-редактора остаётся `>= 3` (specs/013). Для редактора это поле не используется как фильтр вовсе — видны все значения. |

## SiteUser (существующая сущность, без изменений схемы)

| Поле | Тип | Значение для этой фичи |
|---|---|---|
| `is_editor` (`isEditor`) | `Boolean` | Единственный признак, по которому определяется исключение из правила `id_status >= 3`. `true` → пользователь видит все статусы; `false`/пользователь не резолвится (аноним, невалидный токен) → действует прежний фильтр `>= 3`. |

Резолв `SiteUser` из запроса — уже существующий `SiteUserResolver.resolve(request): SiteUser?`
(по заголовку `Authorization: Bearer <token>`; `null` для анонимных запросов
или невалидного/просроченного токена).

## Производное правило видимости (используется во всех трёх точках фильтрации)

```text
onlyPublished = (siteUserResolver.resolve(request)?.isEditor != true)
```

- `onlyPublished == true` → применяется существующий фильтр `id_status >= 3`
  (закрома, спецзаказная плашка, счётчик в подписи, поиск).
- `onlyPublished == false` → фильтр по статусу не применяется — видны все
  строки `tbl_songs` для соответствующего автора/запроса.

Это правило не хранится как отдельная сущность/состояние — вычисляется на
каждый запрос заново (без кэша), чтобб изменение `is_editor` или разлогин
отражались немедленно (Edge Case spec.md, FR-007 spec.md).

## Связи

- `SiteUser.isEditor` уже используется в admin-контексте (`webvue3`,
  `SiteUsersTable`/фильтр `isEditor`) для управления и просмотра — эта фича
  не меняет его семантику, только добавляет ещё одно место чтения
  (публичный сайт).
- Изменений в `SyncRegistry`/`KaraokeProperties.kt` не требуется — оба поля
  (`id_status`, `is_editor`) уже участвуют в существующей синхронизации.

## State transitions

Нет новых переходов состояний. Существующий переход «статус песни меняется»
(specs/013, FR-005/FR-007) и «пользователь получает/теряет роль редактора»
(уже существующее admin-действие в `webvue3`) оба уже покрыты тем, что
правило видимости пересчитывается на каждый запрос без кэша.
