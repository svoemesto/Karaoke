# Дополнение к контракту спецтегов: инвариант идемпотентности `syncMarkersFromSpecTags`

**Базовый контракт**: `specs/010-lyrics-spec-tags/contracts/tag-registry.md` (раздел «Инварианты»).
Этот файл не заменяет базовый контракт, а формализует инвариант 3 («дубликат не создаётся»),
который на практике оказался нарушаемым (см. `../research.md` §2) — чтобы обе независимые
реализации (`SubsEdit.vue`, `useKaraokeEditor.js`) проверялись на него одинаково.

## Инвариант

Для любых `markers` (массив `Marker`, см. `../data-model.md`) и `sourceText`:

```
syncMarkersFromSpecTags(markers, sourceText)
syncMarkersFromSpecTags(markers, sourceText)  // повторный вызов, ничего не менялось между ними
```

Длина `markers` и мультимножество `(markertype, label, time)` его элементов ДОЛЖНЫ быть одинаковы
до первого и после второго вызова (второй вызов — no-op).

Это должно оставаться верным независимо от того, совпадает ли вычисленное время нового
тег-маркера (`gap >= 1.0 ? nextStartTime - 1.0 : prevEndTime + gap / 2`) с временем соседнего
маркера, и независимо от того, как `sortMarkers()` разрешает равенство `time` между разными
`markertype`.

## Почему это не следует автоматически из существующих трёх инвариантов

Существующий инвариант 3 контракта («дубликат не создаётся») формулируется через проверку окна
`markers.slice(windowStart, insertPos)` НА МОМЕНТ вызова. Он не гарантирует, что вставленный
маркер останется внутри этого же окна ПОСЛЕ `sortMarkers()` при следующем вызове — а именно это
условие фактически необходимо для идемпотентности (см. `../research.md` §2 — конкретный сценарий,
где `sortMarkers()` переносит новый `'setting'`-маркер за границу окна из-за лексикографического
тай-брейка с `'syllables'` при равном `time`).

## Требование к реализации фикса

Реализация ДОЛЖНА гарантировать идемпотентность одним (или обоими) из способов:
1. Гарантировать, что вычисленное время нового маркера НИКОГДА не совпадает точно с временем
   соседнего маркера, участвующего в определении окна дедупликации (аналогично уже сделанному в
   `SubsEdit.vue` фиксом `#018`, который в этом же файле переиспользуется для СВОЕЙ независимой
   исходной причины «слипания в нуле» — здесь способ переносится по аналогии, а не потому что
   исправляется тот же баг).
2. И/ИЛИ переопределить окно дедупликации так, чтобы оно оставалось согласованным с фактической
   позицией маркера после `sortMarkers()`, а не только с позицией на момент вставки.

Выбор конкретного способа — на усмотрение реализации; тесту подлежит только сам инвариант
(см. `../quickstart.md`, сценарий «идемпотентность»), не способ его достижения.

## Область действия

Применяется к ОБЕИМ независимым реализациям `syncMarkersFromSpecTags`:
`webvue3/src/composables/useKaraokeEditor.js` (обязательный фикс, источник бага 1) и
`webvue3/src/components/Songs/edit/SubsEdit.vue` (регрессионная проверка — фикс `#018` уже смягчает
проблему для реальных, полученных через forced-alignment временных меток, но формальный инвариант
должен проверяться и там, см. `../research.md` §3 «Известный связанный риск»).

**НЕ применяется** к `karaoke-public/src/composables/useKaraokeEditor.js` (третья независимая
копия, публичный сайт) — вне скоупа этой фичи (см. Assumptions `../spec.md`, пользователь описал
баг только «в админке»). Оставлено как известный риск на будущее, не как часть этой фичи.
