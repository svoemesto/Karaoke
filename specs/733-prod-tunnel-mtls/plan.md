## Summary

Админ-машина `nsa-i9` теряет доступ к прод-хосту `188.127.240.124` при каждой смене
внешнего адреса и при каждом обрыве WAN шлюза `10.0.1.1`. Туннель WireGuard между
админ-машиной и прод-хостом снимает зависимость от allow-list и от плавающего IP;
клиентский сертификат (mTLS) закрывает прод-БД криптографически, а не по IP.

**Технический подход** (решения владельца 2026-11-09 — входные данные):

1. **Транспорт** — WireGuard (вариант A), поверх существующего WAN. Публичный IP
   админ-машины плавает — WireGuard это переживает: прод-хост слушает UDP, а
   админская сторона инициирует рукопожатие с `PersistentKeepalive = 25` (натуральный
   keepalive NAT-маппинга). Смена адреса → новое рукопожатие, правок на проде нет.
2. **Владелец туннеля — приложение** `karaoke-app` (FR-027): интерфейс `wg0` живёт
   в сетевом пространстве контейнера приложения, поднимается, проверяется и
   восстанавливается самим приложением.
3. **Доступ из хоста (DBeaver) — через тот же туннель и тот же постоянный адрес**
   (FR-031/FR-032): хост получает маршрут в подсеть туннеля через контейнер,
   контейнер делает SNAT — прод всегда видит один и тот же адрес источника.
4. **Админские HTTP-каналы** (`/changerecords`, `/api/properties/setproperty`) идут
   внутри туннеля; имя хоста `sm-karaoke.ru` и серверный TLS-сертификат **не
   меняются** (FR-022) — меняется только транспорт.
5. **Прямой (публичный) канал сохраняется как откат** до отдельного окна
   владельца (FR-017), переключение — по фазам, каждая с контрольной проверкой.

**Что НЕ входит в эту итерацию**: любые изменения на прод-хосте (установка WireGuard,
выпуск ключей и сертификатов, правка nginx/БД, рестарт контейнеров) — только по
отдельному согласию владельца. Подготовка, код, скрипты, runbook и локальная проверка —
в этой итерации.

## Technical Context

**Language/Version**: Kotlin 1.x / JDK 17 (модуль `karaoke-app`, Spring Boot), Bash 5
(скрипты `deploy/`), SQL (PostgreSQL `pg_hba.conf`/postgresql.conf на проде — под
согласие владельца).

**Primary Dependencies**: PostgreSQL JDBC (`org.postgresql`), `wireguard-tools`
(`wg`, `wg-quick`) в образе `karaoke-app`, `iproute2`, `iptables`; на проде —
`wireguard-tools`, PostgreSQL 16 (контейнер `karaoke-db`).

**Storage**: PostgreSQL (прод-БД `karaoke`, пользователь `SvoeMestoKaraokeUser905`),
MinIO (прод-хранилище), локальные файлы контейнера.

**Testing**: JUnit 5 (Kotlin, `karaoke-app/src/test`), `bash` self-test-ы
(`deploy/*.sh --self-test`, `tools/check-*.sh`), изолированная проверка туннеля в
сетевых namespace'ах (`ip netns` + `unshare --user --map-root-user --net`).

**Target Platform**: Linux (админ-машина `nsa-i9`, Ubuntu; прод-хост `188.127.240.124`,
Ubuntu 26.04), Docker + docker-compose, ядро с поддержкой WireGuard.

**Project Type**: monorepo (Gradle multi-module: `karaoke-app`, `karaoke-web`,
`karaoke-public`, `webvue3`) + каталог `deploy/` (Docker/nginx/скрипты).

**Performance Goals**: восстановление канала после обрыва ≤ 60 с (SC-002); опрос
состояния туннеля — раз в 30 с; детект «устаревшего рукопожатия» — 180 с
(3 × keepalive-интервал).

**Constraints**:
- Туннель MUST NOT менять маршрут по умолчанию и MUST NOT ломать `tun0` (OpenVPN к
  pfSense) и `xray` (SOCKS/HTTP-прокси) — FR-007.
- Подсеть туннеля MUST NOT пересекаться с `tun0` (`172.28.3.0/24`), Docker-сетями
  (`172.18.0.0/16`, `172.21.0.0/16`, `172.23.0.0/16`), VPN-маршрутами
  (`10.128.0.0/16`) и LAN (`10.0.1.0/24`) — измерение 2026-11-09.
- Приватные ключи, корневые сертификаты и файлы сертификатов MUST NOT попадать в
  репозиторий (FR-013) — доставка только монтированием с правами 600.
- Прод-канал доступен и приложению, и оператору по **одному** постоянному
  внутреннему адресу (FR-031).

**Scale/Scope**: 34 функциональных требования, 13 критериев успеха, 6 пользовательских
историй; 1 контейнер (`karaoke-app`), 1 прод-хост, 3 прод-канала (БД, MinIO, HTTP-каналы).

                     ┌─────────────────────────────────────────▼─▼───────┐
                     │ прод-хост 188.127.240.124                          │
                     │   wg0 10.77.0.2/24  (ListenPort 51820)             │
                     │   nginx: 5433 → 127.0.0.1:8832  (БД)              │
                     │           9000 → 127.0.0.1:8890  (MinIO)           │
                     │           443  → 127.0.0.1:8897  (HTTP-каналы)    │

### Ключевые решения (design decisions)

- **DD-1. Адресация туннеля**: `10.77.0.1/24` (админская сторона, в контейнере
  приложения) и `10.77.0.2/24` (прод). `10.77.0.2` — **постоянный внутренний адрес
  прод-каналов**; его используют и приложение, и оператор с хоста (FR-031).
  `10.77.0.1` — **единственный** адрес, который прод видит в allow-list (FR-005).
- **DD-2. Размещение**: интерфейс `wg0` — в сетевом пространстве контейнера
  `karaoke-app`; контейнер получает `NET_ADMIN` и `/dev/net/tun`. Приложение само
  выполняет `wg-quick up`, следит за возрастом рукопожатия и перезапускает туннель
  при устаревании (FR-002, FR-027, edge case «рукопожатие устарело»).
- **DD-3. Доступ с хоста**: host-route unit `karaoke-tunnel-host-route.service`
  держит маршрут `10.77.0.0/24 via <IP контейнера>`; SNAT внутри контейнера приводит
  адрес источника к `10.77.0.1`. Хост и контейнер используют **один** адрес
  назначения `10.77.0.2` — это и есть «проброс адреса в хост» из FR-032.
- **DD-4. HTTP-каналы**: имя хоста и сертификат не меняются. Пока туннель поднят,
  приложение переключает резолвинг `sm-karaoke.ru` на `10.77.0.2` (запись в
  `/etc/hosts` контейнера, управляется приложением); SNI и Host остаются
  `sm-karaoke.ru` — сертификат валиден, проверка включена (FR-021, FR-022).
  Туннель не поднят → запись удаляется → приложение возвращается на публичный путь
  (откат, FR-017, edge case «UDP-порт закрыт»).
- **DD-5. mTLS**: корневой CA проекта; сертификат сервера БД (SAN включает
  `10.77.0.2`) и клиентский сертификат приложения/оператора. `pg_hba.conf`:
  `hostssl ... scram-sha-256 clientcert=verify-ca` — **пароль остаётся** как
  запасной путь до отдельного решения владельца (FR-015). Клиент:
  `sslmode=verify-full` + `sslcert`/`sslkey`/`sslrootcert` (FR-011, FR-012).
- **DD-6. Наблюдаемость**: коды `TUNNEL-001…007` (состояние туннеля) и
  `DB-CERT-001` (отказ по сертификату с причиной) в реестре
  `knowledge/guidelines/runbooks/log-correlation.md`; отдельная проверка
  мониторинга `ProdTunnelCheck` (ключ `prod.tunnel`) — состояние туннеля видно
  отдельным признаком, а не «прод недоступен» (FR-028, SC-010).
- **DD-7. Устойчивость к обрыву WAN**: классификатор канальных отказов
  (`ChannelFailureClassifier`) переводит задание из `ERROR` в `WAITING` при
  сетевом/канальном отказе (ограниченное число попыток) — FR-033, SC-013.
  FR-034 фиксирует: туннель **не** снимает зависимость от WAN.
- **DD-8. Allow-list в режиме туннеля**: `deploy/admin-ip-allowlist.sh` получает
  режим `ALLOWLIST_MODE=tunnel`: он **не** определяет и **не** записывает публичный
  адрес, а только проверяет (read-only), что во всех блоках прод-хоста ровно один
  адрес `10.77.0.1`; расхождение — событие в журнал и уведомление владельцу
  (FR-009). Покрыто self-test-сценарием.

### Откат

Прежний (публичный) путь остаётся рабочим до последней фазы (FR-017):

| Фаза | Что делается | Откат |
|---|---|---|
| Ф1. Подготовка | код, скрипты, ключи на админской машине, проверка в namespace'ах | ничего на проде — откат не нужен |
| Ф2. Установка пира на прод | `wg-quick up wg0` на проде, allow-list прод-хоста = `10.77.0.1` | `wg-quick down wg0` + восстановление allow-list из бэкапа (≤ 15 мин, SC-006) |
| Ф3. Переключение каналов | `DB_REMOTE_HOST=10.77.0.2`, `STORAGE_REMOTE_ENDPOINT=…:9000`, резолвинг `sm-karaoke.ru` | вернуть env на публичные значения и перезапустить контейнер по Pass 380 (очередь → стоп → дренаж → старт → старт очереди) |
| Ф4. Закрытие публичных портов | закрыть 5433/9000 для интернета, убрать публичный адрес из allow-list | открыть порты, вернуть allow-list из бэкапа |

Каждая фаза — с записью фактов проверок в отчёт задачи `KARAOKE-407` (FR-020, SC-007).

## Verification strategy

| Что | Чем проверяется | Где |
|---|---|---|
| Туннель поднимается и пропускает трафик | изолированный стенд: два netns + veth + `wg0` (без прода) | `deploy/prod-tunnel/selftest.sh` |
| Туннель не ломает `tun0`/`xray`/прямой канал | стенд не трогает netns хоста; сверка `ip route`/`ip addr` до и после | `selftest.sh` + ручная сверка в отчёте |
| Хост видит тот же адрес, что и приложение | стенд: третий netns («хост») → route + SNAT → тот же source | `selftest.sh` |
| Приложение поднимает/восстанавливает туннель | unit-тесты `ProdTunnelTest` (подменённый `TunnelCommandRunner`) | `karaoke-app/src/test/.../tunnel/` |
