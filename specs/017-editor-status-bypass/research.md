# Phase 0 Research: Редактор видит все песни независимо от статуса

Все технические неизвестные из Technical Context были разрешены прямым
изучением существующего кода (без внешних библиотек/выбора технологий —
фича точечно расширяет уже работающий механизм). Ниже — зафиксированные
решения.

## 1. Как определить, что текущий пользователь — «редактор»

**Decision**: Использовать существующий `SiteUserResolver.resolve(request)`
(`karaoke-web/.../services/SiteUserResolver.kt`) — он уже читает
`Authorization: Bearer`-заголовок, резолвит токен через
`SiteUserTokenService` и возвращает `SiteUser?` (без 401, для анонимных —
`null`). Признак роли — уже существующее поле `SiteUser.isEditor`
(колонка `tbl_site_users.is_editor`, см. `SiteUser.kt:132-133`).

**Rationale**: Это ровно тот же механизм, который уже используется в этих
же трёх методах контроллера (`zakroma`, `songs`) для регистрации
событий (`mainController.doRegisterEvent(..., siteUserResolver.resolve(request)?.id ?: 0)`),
и в `authorsTiles` его достаточно один раз добавить в сигнатуру. Не
кэшируется (специально — см. комментарий в `SiteUserResolver.kt`: бан/снятие
премиума должны действовать немедленно), что нам и нужно — потеря роли
редактора должна сразу понижать видимость до обычной (Edge Case из spec.md).

**Alternatives considered**:
- Новый отдельный auth-механизм/claim для «редактора» — отклонено: роль уже
  существует и используется в другом месте системы (admin `webvue3`
  `SiteUsersTable`/фильтр `isEditor`); дублирование понятия противоречит
  FR-008 spec.md.
- Кэширование результата резолва на время сессии — отклонено: тот же
  аргумент «должно действовать немедленно», что и для существующего кода;
  не усложняем.

## 2. Как переключить фильтр статуса на бэкенде

**Decision**: Все три точки фильтрации уже параметризованы булевым флагом:

- `Zakroma.getZakroma(..., onlyPublished: Boolean = false)` (`Zakroma.kt:28-46`)
- `Zakroma.getZakromaBySpecialOrder(..., onlyPublished: Boolean = false)` (`Zakroma.kt:60-84`)
- `Song.loadAuthorSongCounts(..., onlyPublished: Boolean = false, ...)` (`Song.kt:6804-6824`)
- `PublicApiController.songs()` — сейчас безусловно `attr["id_status"] = ">=3"` (`PublicApiController.kt:238`)

Во всех вызовах в `PublicApiController` сегодня жёстко передаётся
`onlyPublished = true` (или безусловно ставится `id_status`). План — заменить
константу на вычисленное значение
`val onlyPublished = siteUserResolver.resolve(request)?.isEditor != true`
(или эквивалент) в каждом из трёх методов, и передавать/использовать её
вместо литерала `true`.

**Rationale**: Ни один из этих методов не требует менять сигнатуру — они уже
спроектированы для двух режимов (admin передаёт `false` по умолчанию, прод —
`true`). Комментарий в `Zakroma.kt:22-25` прямо описывает семантику
`onlyPublished` в терминах «admin-путь оставляет значение по умолчанию
(false), чтобы редакторы видели все песни» — то есть данная фича переносит
уже существующую admin-семантику на публичный сайт для той же роли, а не
изобретает новую.

**Alternatives considered**:
- Добавить отдельный параметр запроса (`?asEditor=true`) от клиента —
  отклонено: небезопасно (клиент не должен сам заявлять о своей роли),
  противоречит существующему паттерну (роль всегда резолвится на бэкенде из
  токена).
- Фильтровать на фронтенде (скрывать/показывать уже загруженные песни) —
  отклонено: подтекало бы в браузер данные о неготовых песнях всем
  пользователям, только скрывая их в UI; не решает задачу (нужно, чтобы
  сами данные не отдавались не-редакторам).

## 3. Что делать с подписью количества песен (`authors-tiles`)

**Decision**: `authorsTiles()` сейчас не принимает `HttpServletRequest` и не
резолвит пользователя. Добавить `request: HttpServletRequest` в сигнатуру
(как уже сделано в `zakroma`/`songs`) и использовать тот же расчёт
`onlyPublished`, передавая его и в `Song.loadAuthorSongCounts(onlyPublished = ...)`,
и в фильтр `loadedAuthors.filter { (counts[it] ?: 0L) > 0L }` (этот фильтр
уже завязан на `counts`, посчитанный с тем же `onlyPublished`, так что
дополнительных изменений в самом фильтре не требуется — только источник
`counts`).

**Rationale**: Обеспечивает SC-003 spec.md (число в подписи совпадает с тем,
что редактор реально видит в закромах) — оба используют одно и то же
значение `onlyPublished`, посчитанное одинаково.

**Alternatives considered**: Отдельный «полный» и «редакторский» расчёт
count с последующим выбором на фронтенде — отклонено как избыточное
усложнение при наличии уже готового параметра `onlyPublished`.

## 4. Нужны ли изменения в `karaoke-public` (фронтенд)

**Decision**: Не требуются. `karaoke-public/src/services/api.js#apiGet`
уже безусловно прикладывает `Authorization: Bearer <km_auth_token>` (если
пользователь залогинен) ко всем публичным GET-запросам, включая
`/api/public/authors-tiles`, `/api/public/zakroma`, `/api/public/songs`
(вызовы — `store/modules/zakroma.js`, `store/modules/songs.js`,
`views/AuthorPlaylistView.vue`). Значит, как только бэкенд начнёт учитывать
`isEditor`, поведение для залогиненного редактора изменится автоматически,
без правок клиента.

**Rationale**: Минимизирует риск и объём изменений (Principle V — не
смешивать ответственности фронтендов, здесь дополнительная причина —
вообще не трогать фронтенд без необходимости).

**Alternatives considered**: Явно прокидывать признак «я редактор» в
каждый вызов с фронта — отклонено: избыточно, раз токен уже долетает и
роль резолвится на бэкенде.

## 5. Затрагиваемая per-feature документация (FR-009 Конституции)

**Decision**: `Zakroma.getZakroma`/`getZakromaBySpecialOrder` уже
задокументированы KDoc-ссылкой `@see docs/features/special-orders.md`
(единственный из 12 подсистем, прямо привязанный к этому коду). Обновить
`docs/features/special-orders.md` в том же PR, описав новое поведение
`onlyPublished` для роли «редактор» на публичном сайте.

**Rationale**: Прямое требование FR-009 — правка кода подсистемы обязана
сопровождаться обновлением её документа. `stats.md` (#11) не выбран как
основной, так как подпись счётчика — производная того же `onlyPublished`,
а не отдельная логика статистики, но стоит перепроверить на этапе
имплементации, ссылается ли `stats.md` на `loadAuthorSongCounts` и требует
ли отдельной правки.

**Alternatives considered**: Не обновлять документацию — отклонено,
прямое нарушение NON-NEGOTIABLE FR-006/FR-009.

## Outcome

Все пункты Technical Context разрешены без введения новых зависимостей,
таблиц или API-контрактов. NEEDS CLARIFICATION отсутствуют.
