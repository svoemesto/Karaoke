# Research: Автоматические новости о выходе песни в эфир

## 1. Где именно «происходит синхронизация таблиц» на PROD

**Вопрос**: спецификация требует, чтобы механизм срабатывал «когда происходит синхронизация
таблиц» на проде — но `karaoke-app` (владелец `updateDatabases`/`collectSyncOps`, Utils.kt) никогда
не разворачивается на PROD (Constitution Principle I). Где физически исполняется код на PROD в
момент синхронизации?

**Находка**: LOCAL→SERVER push НЕ пишет в PROD БД напрямую по JDBC. `updateDatabases` (вызывается
только вручную, через `/api/sync/oneclick` или `/api/sync/run` в `ApiController.kt`, запускается на
LOCAL) для цели `SERVER` шифрует SQL-операции (`INSERT`/`UPDATE`/`DELETE`) и отправляет их по HTTP
на `https://sm-karaoke.ru/changerecords`. Этот эндпоинт реализован в
`karaoke-web/.../controllers/MainController.kt:265` (`doChangeRecords`) — **единственное место,
которое реально выполняется на PROD** и применяет присланные операции к
`WORKING_DATABASE` (PROD БД) через сырой JDBC, расшифровывая каждую операцию (`Crypto.decrypt`) и
последовательно выполняя `PreparedStatement.executeUpdate()`.

**Decision**: Хук для детекции «песня стала публично доступна» ставится в конец
`doChangeRecords(...)`, после применения `dataCreate`/`dataUpdate`/`dataDelete`, — это единственная
точка кода, которая (а) реально исполняется на PROD и (б) совпадает по времени с «синхронизацией
таблиц», как требует спецификация. Никакого отдельного `@Scheduled`/cron не заводится (см. Edge
Cases/Assumptions в spec.md — уже согласовано с пользователем).

**Rationale**: Это не новая точка входа, а естественная — она уже вызывается многократно за один
«1 клик»-прогон (один раз на каждый чанк на каждый sync-target), поэтому проверка полностью
покрывает FR-001 без изменения протокола/контракта синхронизации.

**Alternatives considered**:
- Отдельный `@Scheduled`-джоб в `karaoke-web`, опрашивающий БД по таймеру — отклонено: пользователь
  явно подтвердил (Clarifications), что механизм должен быть завязан на момент синхронизации, а не
  на отдельное расписание; к тому же `karaoke-web` и без того уже имеет несколько `@Scheduled`
  сервисов (см. `StatsCacheScheduler` и др.) — плюс одна лишняя точка входа увеличивает риск двойной
  логики детекции.
- Хук внутри `updateDatabases`/`collectSyncOps` на стороне LOCAL (`karaoke-app`) — отклонено:
  `karaoke-app` не выполняется на PROD, а условие готовности («статус >= 6 И наступила дата эфира И
  готовы стемы/обложки/маркеры») должно проверяться относительно PROD-таймзоны/PROD-данных именно в
  момент, когда песня реально стала видна пользователям сайта, — то есть на PROD.

## 2. Риск синхронизации: почему авто-новости не могут участвовать в обычном `news`-sync scope

**Вопрос**: можно ли просто вставлять авто-новость как обычную строку `tbl_news` и полагаться на
существующий `NewsSyncTarget` (LOCAL_TO_SERVER)?

**Находка**: `collectSyncOps` (Utils.kt) для направления LOCAL→SERVER считает
`idsToDelete = list_с_SERVER.filter { id не найден в списке_с_LOCAL }` и, если
`sync_news_push_delete_allowed = true`, удаляет такие строки на SERVER как «удалённые в источнике».
Значения sync-флагов (`KaraokeProperties.kt:567-605`) — **operator-toggleable** через Properties UI
и хранятся в персистентном `/sm-karaoke/system/Karaoke.properties`; значение `defaultValue = false`
в коде — это только safe-fallback, а не гарантия текущего runtime-значения на реальном PROD.
Значит: если авто-созданная новость (существующая только на SERVER, никогда — на LOCAL) участвует в
обычном `listHashes`-сравнении для `news`, то **первый же следующий admin-триггерный «1 клик»
может тихо удалить её**, если в этот момент delete для `news` окажется разрешён. Это не
гипотетический edge case — это прямое следствие текущей архитектуры sync-движка (mirror-delete по
умолчанию для любой строки, которой нет в источнике).

**Decision**: `News.listHashes(...)`, используемый ТОЛЬКО `NewsSyncTarget` (generic sync engine),
получает дополнительный WHERE-фильтр, исключающий авто-созданные записи из scope сравнения (см.
data-model.md, поле `source`/`song_id`). Ручные новости (обычный путь через `NewsController`)
продолжают синхронизироваться как прежде, без каких-либо изменений поведения. Авто-новости живут
исключительно как PROD-native данные, вставленные напрямую через JDBC из кода `karaoke-web` — точно
так же, как сам `doChangeRecords` уже пишет в `WORKING_DATABASE` напрямую, без похода через sync-протокол.

**Rationale**: Исключение из generic-diff scope — это единственный способ сделать невозможной
потерю данных, а не полагаться на то, что конкретный чекбокс в Properties UI останется выключенным
навсегда. Соответствует Constitution Principle III в части «Наличие recordhash-триггера... не
означает участие в Синхронизации в 1 клик» — новые поля/строки таблицы могут существовать вне
sync-scope при явном документировании.

**Alternatives considered**: см. Complexity Tracking в plan.md (SERVER_TO_LOCAL pull-направление для
`news` — отклонено как избыточное усложнение, не решающее correctness, только «удобство просмотра»,
которое дешевле закрыть существующим `target=remote`).

## 3. Как администратор увидит авто-новость (User Story 2)

**Находка**: `NewsController` (`karaoke-app`, используется webvue3) уже поддерживает параметр
`target` — `target=remote` открывает соединение через `Connection.remote()` прямо к PROD БД (тот же
механизм, что уже используется для отладки других сущностей — `ChatController`,
`DictionariesController` и т.п.), минуя HTTP sync-протокол. Поскольку авто-новости физически живут
только на PROD, администратор должен смотреть их именно через `target=remote`.

**Decision**: Добавить в `webvue3` (`NewsView.vue`/`NewsTable.vue`) простой переключатель
«LOCAL / PROD» для списка новостей (использующий уже существующий параметр `target`), а не
изобретать новый API. Для авто-новостей `NewsDto` получает поле `source` (`"auto"`/`"manual"`), чтобы
в таблице можно было визуально их отличать (не обязательное, но дешёвое UX-улучшение по FR-007).

**Rationale**: Переиспользование существующего, уже проверенного пути (`target=remote`) не требует
нового сетевого протокола и не создаёт второго способа писать данные на PROD.

**Alternatives considered**: тянуть авто-новости назад на LOCAL отдельным pull-джобом — отклонено
(см. Complexity Tracking в plan.md).

## 4. Как не создать «третью копию» условия готовности песни

**Находка**: Условие «песня доступна пользователю» уже продублировано дважды — Kotlin
(`PublicPlayerController.stemsReady`/`canWatch`) и raw SQL (`StatBySong.CONTENT_READY_FILTER` +
ручная SQL-реконструкция `onAir`). Добавление третьей независимой реализации специально для
авто-новостей увеличило бы риск рассинхронизации логики при будущих изменениях (ровно то, от чего
предостерегает `feedback_verify_all_independent_implementations`: искать и учитывать ВСЕ независимые
реализации одного и того же алгоритма/условия).

**Decision**: Вынести единое computed-свойство (например `Song.isPubliclyWatchable` в
`karaoke-app/model/Song.kt`) на основе уже существующей логики `PublicPlayerController.stemsReady` +
`onAir`, и переиспользовать его (а) в `PublicPlayerController` (замена локального `stemsReady`/`canWatch`
на вызов общего свойства) и (б) в новом `SongReleaseAnnouncementService`. `StatBySong`
(raw-SQL-агрегаты для счётчиков) — отдельный, оправданный случай (агрегатный COUNT-запрос ради
производительности над множеством строк) и не рефакторится в рамках этой фичи, но должен быть явно
упомянут в KDoc нового свойства как «третья независимая реализация того же условия — при изменении
правил готовности проверить оба места».

**Rationale**: Снижает риск, что будущая правка (например, новое обязательное медиа-поле) обновит
"canWatch" в одном месте, но не в критерии для авто-новостей, из-за чего анонс будет либо запаздывать,
либо (хуже) публиковаться до того, как песню реально можно посмотреть.

## 5. Механизм идемпотентности и защиты от «лавины» исторических новостей (FR-004, FR-005)

**Decision**: Новая таблица `tbl_song_news_announced (song_id BIGINT PRIMARY KEY, news_id BIGINT
NULL, created_at TIMESTAMP)`, PROD-локальная (см. data-model.md). Логика в
`SongReleaseAnnouncementService`:

1. Загрузить кандидатов: `Song`, у которых `id_status >= 6` И наступила дата эфира (дёшево фильтруется
   в SQL/через существующий `Song.loadListFromDb` с `id_status` фильтром), затем в Kotlin отфильтровать
   по общему `Song.isPubliclyWatchable` (см. пункт 4) и по отсутствию строки в `tbl_song_news_announced`.
2. Для каждого найденного кандидата — в одной транзакции: `INSERT` в `tbl_song_news_announced` (по
   PK на `song_id` — защита от дублей при параллельных вызовах `doChangeRecords`) и `News.createNew(...)`
   с `song_id` = id песни.
3. Backlog при первом включении (FR-005, User Story 3): деплой фичи сопровождается ОДНОРАЗОВЫМ
   backfill-скриптом (SQL или разовый вызов сервиса в "silent" режиме — без создания News), который
   вставляет в `tbl_song_news_announced` строки для ВСЕХ песен, уже удовлетворяющих условию готовности
   на момент включения, БЕЗ параллельного создания записи в `tbl_news`. После этого backfill'а обычная
   логика (шаги 1-2) начинает работать только для по-настоящему новых переходов.

**Rationale**: `PRIMARY KEY (song_id)` в БД даёт гарантию «не более одной анонс-метки на песню» на
уровне данных, а не только на уровне кода (защищает и от повторных вызовов, и от гипотетической
параллельности). Backfill как отдельный одноразовый шаг (не часть постоянной бизнес-логики) —
самый простой способ обеспечить SC-003 (0 исторических новостей при включении), не вводя понятие
«дата включения фичи» как постоянное поле конфигурации.

**Уточнение по масштабу (обнаружено при реализации, 2026-07-29)**: пул «готовых по статусу» песен
(`id_status >= 6`) на реальных данных — многие тысячи строк (на локальном dev-стенде с
prod-подобным дампом — 14874), а не «единицы», как изначально предполагалось в Technical
Context плана. Наивная загрузка кандидатов одним вызовом `Song.loadListFromDb(id_status>=6)`
(загружает ВСЕ колонки, включая тяжёлые `source_text`/`result_text`/`source_markers`) на таком
объёме воспроизводит `OutOfMemoryError` — тот же класс бага, что уже был исправлен в
`specs/082-fix-import-folder-oom`. Исправлено: двухфазная загрузка — (1) дешёвый скан
`Song.listHashes(db, "WHERE id_status >= 6")` (только `id`+`recordhash`, путь sync-движка, без
тяжёлых полей) минус уже отмеченные в `tbl_song_news_announced`; (2) полные объекты грузятся пачками
по 25 (`Song.loadListFromDb(args = mapOf("ids" to chunk))`, тот же порядок, что
`SongSyncTarget.rowChunkSize`) и обрабатываются (фильтр `isPubliclyWatchable` + запись в
`tbl_song_news_announced`) СРАЗУ по каждому чанку, а не через `chunked(...).flatMap {...}` — этот
на первый взгляд эквивалентный вариант всё равно тихо собирает ВСЕ полные объекты по ВСЕМ чанкам в
один список до применения внешнего `.filter`, воспроизводя тот же `OutOfMemoryError` (проверено на
практике при реализации — см. tasks.md T012/T017). Это одновременно чинит и разовый backfill (сотни
чанков за один прогон, но без накопления) и делает повторные `checkAndAnnounce` дешёвыми в
установившемся режиме (после первого backfill остаток кандидатов на id-скане — обычно 0 или
единицы).

## 6. Текст/заголовок авто-новости и ссылка на песню

**Находка**: публичная страница песни на `karaoke-public` — маршрут `/song`, id передаётся через
query-параметр (`route.query.id`, см. `SongView.vue`), т.е. ссылка вида `/song?id={id}`.

**Decision**: Заголовок — `"Новая песня: {author} — {songName}"`, категория — `"air"` (см.
`News.category`, уже существующее значение), `link = "/song?id={id}"`. Текст (`body`) — короткий
шаблон, например `"Стала доступна песня «{songName}» ({author})."`; конкретная формулировка — на
усмотрение реализации в tasks.md, не влияет на архитектуру.
