## Что случилось

PR #88 (Pass 29, спека #017) исправил «залипание маркеров в нуле» на ПЕРВОМ открытии: маркеры на правильных позициях теперь появляются. Но остался **второй слой бага**: после первого `redrawMarkers()` пользователь видит, как **сверху на правильные маркеры накладываются красные newline-маркеры в позиции 0** (толстая красная линия на старте таймлайна).

Скриншот пользователя: «Костёр» Машина Времени — правильные syllables/eol/beat-маркеры распределены по таймкодам, но **красная линия в нуле** осталась.

## Первопричина (локализация)

Корень — в формуле расчёта времени для spec tag-маркера в `syncMarkersFromSpecTags()`:

```js
const time = gap >= 1.0 ? nextStartTime - 1.0 : prevEndTime + gap / 2
```

Сценарий, дающий `time ≈ 0`:
- `insertPos = syllablePositions[0] = 0` (первый syllables-маркер прямо в индексе 0 `sourceMarkers`)
- `prevMarker = null`
- `nextMarker = sourceMarkers[0]` с `time = 0.1` (или другая малая величина)
- `prevEndTime = 0`, `nextStartTime = 0.1`
- `gap = 0.1 < 1.0` → `time = 0 + 0.1/2 = 0.05`

**Симптом**: маркер с `time = 0.05` рендерится на расстоянии 0.05s от нуля, что **визуально неотличимо от позиции 0** (при стандартном zoom `<5px/sec`). Несколько таких маркеров (например, 3 `~newline~` тега в начале текста) накладываются друг на друга → пользователь видит «толстую красную полосу в нуле».

То же самое происходит, если `prevMarker.time = 0` (например, `endofline` или `setting` маркер в самом начале), а `nextMarker.time` маленький: `gap/2` всё равно даёт крошечное значение.

В #016/#017 защитный гард `if (this.sourceMarkers.length === 0) return` и поднятие `ws.on('decode')` в `mounted()` не помогают — `sourceMarkers` уже заполнен правильными маркерами, `sourceSyllables` посчитан корректно, формула выдаёт **положительное** значение, но **очень маленькое**.

## Что меняется в коде (дифф-мысль)

**Было (после #88)**:
```js
let time = gap >= 1.0 ? nextStartTime - 1.0 : prevEndTime + gap / 2
// ... newMarker.time = time, addRegion({ start: time })
```

**Стало (фикс #018)**:
```js
let time = gap >= 1.0 ? nextStartTime - 1.0 : prevEndTime + gap / 2
if (time < 0.5) {
  time = prevEndTime + 0.5
}
// ... newMarker.time = time, addRegion({ start: time })
```

**Обоснование порога 0.5**:
- 0.5s гарантированно видимо на стандартном zoom (`<5px/sec` → ≥2.5px от нуля).
- 0.5s < типичного расстояния между слогами (0.3-1.5s в зависимости от темпа), так что маркер не «наедет» на syllables-маркер.
- 0.5s ровно = `NEWLINE_LEAD_IN_SECONDS / 2` в backend, что согласуется с архитектурой спецтегов.

**Ключевые инварианты, которые НЕ должны быть нарушены**:
- Spec tag-маркеры остаются строго **аддитивными** (FR-007 спеки #016): не удаляют и не модифицируют существующие syllables/eol/beat-маркеры.
- Spec tag-маркеры по-прежнему вставляются **в правильную позицию** по `syllablePositions` (между syllables-маркерами).
- `createRegionMarker` вызывается **сразу** при создании маркера — порядок вставки в `sourceMarkers` тот же, что и в #017.
- Защитный гард `if (this.sourceMarkers.length === 0) return` (добавлен в #016) сохранён.

## Почему не добавляем console.log

В #016 и #017 спеки упоминали, что для диагностики может понадобиться `console.log` в `syncMarkersFromSpecTags`. Но в production-код такой лог не идёт — мы **уже знаем причину** (формула даёт крошечные положительные значения), фикс точечный, и не нужно оставлять диагностический код в проекте (см. AGENTS.md «Стандарты оформления кода» → `CONTRIBUTING.md`).
