# Отчёт: утечка зомби-процессов headless_shell в karaoke-app (issue #304)

> Это отчёт о выполнении, не спецификация. Задача маленькая (правка compose +
> запись ловушки в Knowledge), спека не заводилась — решение владельца «делай самому».

## Что сделано

Контейнер `karaoke-app` теперь стартует с init-процессом: в оба compose-файла,
которые его создают, добавлено `init: true`. Docker ставит в контейнер
`docker-init` (tini) как PID 1 — он пожинает осиротевших детей, и зомби больше
не накапливаются. Правка кода приложения не потребовалась: `browser.close()` в
`finally` (`PlayerMp4RenderService`) и так вызывается корректно.

Плюс ловушка записана в Knowledge-SSoT — в компонентный документ
`playwright-rendering`, который владеет этим знанием (ADR-0006-подобное правило
«контейнер обязан иметь init»).

## Причина (факты с диска, 2026-10-15, машина nsa-i9)

| Факт | Значение |
|---|---|
| Зомби в системе | 3480 (`ps -eo stat \| grep -c '^Z'`) |
| Из них дети контейнера | 3477, все `comm=headless_shell`, `PPID=47835` |
| PID 1 внутри контейнера | `java -Dfile.encoding=UTF-8 … -jar /app.jar` (без init) |
| Живых `headless_shell` | 0 — все процессы уже мертвы, но не пожаты |
| Возраст самых старых | ~1 сутки 17 часов (контейнер поднят 2 суток назад) |
| Источник | `PlayerMp4RenderService: Открываем headless-плеер для песни <id>` — по записи на рендер, рендеры идут непрерывно |

Механизм: `Playwright.create()` поднимает драйвер (node) дочерним к JVM, драйвер
запускает `headless_shell`. Когда рендер заканчивается, драйвер умирает раньше
браузера → браузер осиротевает и перевешивается на PID 1 контейнера. PID 1 — это
сам `java`, а JVM вызывает `waitpid` только для процессов, которые запустила
сама; чужих детей она не пожинает. Итог — один-два вечных зомби на каждый рендер.

## Артефакты

**Изменено**

- `deploy/docker-compose-app.yml` — `init: true` у сервиса `karaoke-app` (контейнер
  локальной/admin-машины, из этого файла создан работающий сейчас контейнер);
- `deploy/docker-compose.yml` — то же у однохостового сервиса (та же болезнь в
  других окружениях);
- `knowledge/domains/processing/components/playwright-rendering.md` — новый
  `[WARN]` в «Ловушки и предупреждения»: контейнер обязан стартовать с init.

**Новое**

- `specs/304-karaoke-app-zombie-headless/report.md` — этот отчёт.

## Проверка

До пересоздания контейнера:

```bash
docker inspect karaoke-app --format '{{.HostConfig.Init}}'   # до правки: <nil>
ps -eo stat | grep -c '^Z'                                    # до правки: 3480
```

После пересоздания контейнера (`do.sh start_app`, см. ниже):

```bash
docker inspect karaoke-app --format '{{.HostConfig.Init}}'   # ожидаем: true
docker exec karaoke-app sh -c 'cat /proc/1/cmdline | tr "\0" " "'; echo'   # ожидаем docker-init
ps -eo stat | grep -c '^Z'                                    # ожидаем: 0 (и не растёт после рендеров)
```

Накопленные 3477 зомби исчезнут вместе со старым контейнером — пожать их
post factum нельзя, это разрешение имеет только PID 1 (сам java).

## Что дальше (нужно слово владельца)

1. **Пересоздать локальный `karaoke-app`** — правка вступает в силу только при
   пересоздании. Перезапуск `karaoke-app` требует согласия (матрица машин) и
   процедуры Pass 380/381: сначала остановить очередь `KaraokeProcess`, дождаться
   фактического завершения активных заданий, потом `do.sh start_app`, потом
   включить очередь обратно.
2. **Прод не затронут**: на прод-хосте `sm-karaoke.ru` контейнера `karaoke-app`
   нет (там `karaoke-web`, `karaoke-public`, `karaoke-db`, `karaoke-storage`),
   поэтому прод-деплой для этой правки не нужен.
