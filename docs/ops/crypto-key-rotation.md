# Ротация ключа шифрования `CRYPTO_AES_KEY` / `CRYPTO_AES_IV` — `docs/ops/crypto-key-rotation.md`

**Дата**: 2026-10-26
**Привязка**: [specs/645-fix-connection-leak/spec.md](../../specs/645-fix-connection-leak/spec.md) — п. 2 сводки решений; крипта — отдельный контур, к контракту соединения
([`local-0009`](../../knowledge/adr/local-0009-thread-local-connection-lifecycle.md)) отношения не имеет.
**Статус**: подготовлено, **требует решения владельца** (пункт 2 сводки решений).
**Где мы**: оператор открывает документ и выполняет ротацию ключа без правки кода в проде.

---

## 1. Что зашифровано и чем это опасно

`Crypto` (единственный класс, `karaoke-app/src/main/kotlin/com/svoemesto/karaokeapp/Crypto.kt`)
защищает **транзитные** полезные нагрузки между сервисами:

| Что шифруется | Где | Данные в БД? |
|---|---|---|
| `sqlToInsert` / `sqlToDelete` | `Utils.kt` → передаётся в `karaoke-web` (`MainController`), там расшифровывается и исполняется | **нет** — значение живёт только в пределах одного запроса |
| кодовое слово (`Crypto.WORDS_TO_CHECK`) | `Utils.kt` → `karaoke-web` (`MainController:399`) | нет |

**Следствие**: смена ключа **не требует миграции данных** — в БД зашифрованного ничего нет.

## 2. Текущее состояние (проверено 2026-10-26)

| Факт | Источник проверки |
|---|---|
| `CRYPTO_AES_KEY` / `CRYPTO_AES_IV` **не заданы** в контейнере `karaoke-web` на проде | `docker exec karaoke-web printenv \| grep -c '^CRYPTO_AES'` → `0` |
| то же на локальной машине (`deploy/do.env` — 0 совпадений) | `grep -c CRYPTO_AES deploy/do.env` → `0` |
| при отсутствии env `Crypto.key()` **не падает**, а использует захардкоженный запасной вариант `LEGACY_KEY` / `LEGACY_INIT_VECTOR` и пишет предупреждение в лог | `Crypto.kt:104-132` |
| запасной вариант лежит в **публичном** git → «шифрование» этих полей не даёт защиты от постороннего | `Crypto.kt:54-56` |
| `deploy/docker-compose-web.yml` и `docker-compose-app.yml` **не передают** `CRYPTO_AES_*` в контейнеры | `grep CRYPTO_AES deploy/docker-compose-*.yml` → пусто |
| `karaoke-web` использует **тот же** класс `Crypto`, что и `karaoke-app` | `karaoke-web/build.gradle.kts:24` → `implementation(project(":karaoke-app"))` |
| `karaoke-app` работает на админ-машине (`nsa-i9`), `karaoke-web` — на проде (`188.127.240.124`): ключ нужен **на обоих хостах и одинаковый** | `deploy/prod-single-host/` |

Дополнительно: `Crypto.validateCurrentKeyMaterial()` вызывается на старте
(`KaraokeAppService.kt:87`) и проверяет длину (ключ 16/24/32 байта, IV — 16 байт);
неверная длина → `CryptoConfigurationException`, то есть «тихой» работы с битым
ключом не будет.

## 3. Что предлагается сделать

1. Сгенерировать **новые** ключ и IV (не переносить legacy-значения: смысл ротации —
   убрать секрет из публичного репозитория).
2. Передать их в окружение **обоих** сервисов (см. § 4).
3. Убрать из кода `LEGACY_KEY` / `LEGACY_INIT_VECTOR` и запасной путь в `Crypto.key()` /
   `Crypto.initVector()`: без env приложение обязано **не стартовать** (fail-fast),
   а не молча работать на опубликованном ключе.
4. Проверить, что админские операции (создание/правка песни) работают: `karaoke-app`
   шифрует `sqlToInsert`, `karaoke-web` расшифровывает.

## 4. Порядок действий (runbook)

### Шаг 1. Сгенерировать значения

```bash
# Ключ: 32 байта (AES-256) → 32 символа; IV: 16 байт → 16 символов
python3 - <<'PY'
import secrets
print("CRYPTO_AES_KEY=%s" % secrets.token_hex(16)[:32])
print("CRYPTO_AES_IV=%s"  % secrets.token_hex(8)[:16])
PY
```

Значения **не** записывать в репозиторий, в переписку и в трекер — только в
`deploy/do.env` на соответствующих хостах (файл вне git: `.gitignore:37`).

### Шаг 2. Пробросить в контейнеры (правка репозитория)

В `deploy/docker-compose-app.yml` и `deploy/docker-compose-web.yml` в блок
`environment` добавить:

```yaml
      - CRYPTO_AES_KEY=${CRYPTO_AES_KEY}
      - CRYPTO_AES_IV=${CRYPTO_AES_IV}
```

и то же самое в прод-варианте (`deploy/prod-single-host/docker-compose-web.yml`).
Проброс переменной, которой нет в `.env`, безопасен: compose подставит пустое
значение, а код (до fail-fast) продолжит работать на legacy-ключе.

### Шаг 3. Задать значения на хостах

- админ-машина (`nsa-i9`): `deploy/do.env` → добавить `CRYPTO_AES_KEY=…`, `CRYPTO_AES_IV=…`;
- прод (`188.127.240.124`): тот же файл там же (значения **те же**).

### Шаг 4. Перезапустить сервисы

Порядок важен: `karaoke-app` шифрует, `karaoke-web` расшифровывает. Между
перезапусками значения в операциях, которые идут через оба сервиса, не расшифруются
(запрос вернёт ошибку, данные не потеряются).

```bash
# админ-машина: очередь заданий — по Pass 380 (сначала остановить, потом перезапуск)
curl -s http://localhost:8898/process/stop
cd deploy && bash do.sh start_app

# прод: сначала web, чтобы расшифровка была готова раньше шифрования
cd deploy && bash do.sh start_web
```

### Шаг 5. Проверить

```bash
# 1) в логах НЕТ предупреждения о legacy-ключе
docker logs karaoke-app 2>&1 | grep -c "falling back to LEGACY"
# ожидание: 0

# 2) переменные видны в контейнере
docker exec karaoke-app printenv | grep -c '^CRYPTO_AES'   # ожидание: 2

# 3) админская операция проходит (шифрование → расшифровка)
#    создать/отредактировать любую песню в админке и убедиться, что правка сохранена

# 4) сайт жив
curl -s -o /dev/null -w '%{http_code}\n' http://localhost:7906/   # 200
```

### Шаг 6. Убрать legacy-ключ из кода

После успешной проверки шага 5 — отдельным PR:

- удалить `LEGACY_KEY`, `LEGACY_INIT_VECTOR` и запасной путь в `key()` / `initVector()`;
- при отсутствии env — бросать `CryptoConfigurationException` (проверка длины уже есть);
- обновить KDoc `Crypto.kt` и SSoT (`knowledge/domains/...` — раздел про секреты).

## 5. Риски и как их снять

| Риск | Как снять |
|---|---|
| сервисы стартуют с **разными** ключами (забыли один хост) → админские операции падают | шаг 5.3: проверить расшифровку **до** удаления legacy-пути; при сбое — вернуть оба сервиса на legacy (переменные убрать) |
| забыли `dev-pc` (вторая машина матрики) → там приложение не стартует после fail-fast | перед шагом 6 задать переменные и на `dev-pc`; либо делать шаг 6 отдельным релизом с проверкой обеих машин |
| legacy-ключ остаётся в истории git | переписывание истории (`git filter-repo`) — отдельная операция, ломает историю и все клоны; решает владелец |
| в логи попало значение ключа | `Crypto` пишет в лог только тип операции и класс исключения, значения не пишутся (`Crypto.kt:149,165`) |

## 6. Что делать, если владелец не подтверждает

Ничего не менять: текущее поведение (работа на опубликованном ключе) продолжает
работать и **не ломает** систему. Изменения без подтверждения не выполняются.
