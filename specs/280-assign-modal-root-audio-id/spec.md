# Feature Specification: 280 — AssignModal: фильтр по rootId и audioRootId

**Feature Branch**: `280-assign-modal-root-audio-id`

**Created**: 2026-08-31

**Status**: Draft

**Input**: User description: "Админка, задания редактора, модалка \"Назначить песню на разметку\". В фильтр к полям \"Автор\", \"Альбом\" и \"Название песни\" добавить rootId и audioRootId."

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Поиск кандидатов по ID семейства (Priority: P1)

Администратор открывает модалку «Назначить песню на разметку», вводит в новые поля фильтра числовой `root ID` и/или `A-root ID`, нажимает «Найти» — в результатах остаются только песни, у которых `root_id` (и/или `audio_parent_id`) совпадает с введённым значением; остальные текстовые фильтры («Автор», «Альбом», «Название песни») при этом продолжают работать как раньше, в комбинации с новыми числовыми.

**Why this priority**: основная ценность фичи — дать админу быстрый точечный поиск по «семейству» песен (root-цепочка и аудио-семейство), когда требуется назначить на разметку сразу несколько версий одной композиции / альбома; без этого приходится вручную перебирать большие списки по автору/альбому.

**Independent Test**: открыть `AssignModal.vue`, ввести в новое поле «root ID» значение существующего root-семейства → нажать «Найти» → список результатов содержит только песни с этим `root_id`, остальные фильтры не сломаны.

**Acceptance Scenarios**:

1. **Given** модалка открыта и в каталоге есть песни с разными `root_id`, **When** админ вводит «42» в поле `root ID` и нажимает «Найти», **Then** список результатов содержит только песни с `root_id == 42`, остальные поля фильтра применились как AND-условие.
2. **Given** модалка открыта и в каталоге есть песни с разными `audio_parent_id`, **When** админ вводит «17» в поле `A-root ID» и нажимает «Найти», **Then** список результатов содержит только песни с `audio_parent_id == 17`, остальные фильтры работают совместно.
3. **Given** в полях фильтра уже введены `Автор` и `root ID`, **When** админ нажимает «Найти», **Then** возвращаются песни, у которых одновременно совпадает автор И `root_id` (AND-логика).

---

### User Story 2 — Очистка новых полей фильтра (Priority: P2)

Админ хочет сбросить только числовые поля (`root ID`, `A-root ID`), не очищая остальные («Автор», «Альбом», «Название песни»); для этого в строку фильтра добавляются явные кнопки очистки рядом с каждым новым полем.

**Why this priority**: админу часто нужно «перебрать несколько root-семейств» в рамках одного сеанса назначения; без локальной очистки придётся очищать весь фильтр целиком и вводить заново автора/альбом/название.

**Independent Test**: ввести значение в `root ID` → нажать «X» рядом с этим полем → значение очищено, остальные поля не сброшены, повторный «Найти» отдаёт результат без учёта `root_id`.

**Acceptance Scenarios**:

1. **Given** в поле `root ID` введено «42», **When** админ нажимает кнопку очистки рядом с этим полем, **Then** поле становится пустым, прочие поля фильтра не меняются.
2. **Given** поля `Автор`, `Альбом`, `root ID` заполнены, **When** админ очищает `root ID` и нажимает «Найти», **Then** фильтрация по `root_id` не применяется (поле трактуется как пустое).

---

### User Story 3 — Поведение пустых числовых полей (Priority: P3)

Когда админ не вводит значения в `root ID` и/или `A-root ID`, поведение поиска должно оставаться прежним — фильтрация по этим полям не применяется, как если бы этих полей не было.

**Why this priority**: регрессионная гарантия: добавление полей не должно ужесточать фильтр для тех, кто ими не пользуется; иначе старые сценарии (поиск только по автору/альбому) сломаются.

**Independent Test**: открыть модалку → оставить новые поля пустыми → ввести только «Автор» → нажать «Найти» → результат совпадает с поведением до фичи.

**Acceptance Scenarios**:

1. **Given** поля `root ID` и `A-root ID` пусты, **When** админ ищет только по автору, **Then** числовые фильтры не применяются (никаких изменений относительно поведения до фичи).
2. **Given** в `root ID` введены только пробелы, **When** админ нажимает «Найти», **Then** значение трактуется как пустое (фильтр по `root_id` не применяется).

---

### Edge Cases

- **Нечисловой ввод**: в `root ID` / `A-root ID» введены буквы/спецсимволы — поле валидируется как число; при вводе `abc` запрос не отправляется (или отправляется с пустым значением, что эквивалентно «фильтр не применён»). Бэкенд ожидает строку — клиент отправляет `''` при невалидном вводе.
- **Очень большое число**: пользователь ввёл число больше `Long.MAX_VALUE` — клиент нормализует/обрезает до диапазона `Long`, иначе отправляет пустую строку.
- **Частичное совпадение vs точное**: фильтр работает по точному совпадению (`=`) на стороне БД; частичный поиск по подстроке для числовых ID не поддерживается и явно не требуется.
- **Чекбокс «Только кандидаты на разметку»**: новые поля фильтра комбинируются AND с существующим флагом `onlyStatus1` (по умолчанию `true`).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: В модалке `AssignModal.vue` (webvue3, админка → задания редактора → «Назначить песню на разметку») в строке фильтра песен (`<div class="se-search-row">`) добавляются **два новых поля ввода**: «root ID» и «A-root ID» (порядок: Автор — Альбом — Название — root ID — A-root ID, чтобы не ломать привычный визуальный порядок существующих трёх).
- **FR-002**: Каждое новое числовое поле имеет явную кнопку очистки (`<button class="se-btn-clear">` или эквивалент), которая сбрасывает только это поле, не затрагивая соседние.
- **FR-003**: Поля ввода имеют атрибут `type="text"` с `inputmode="numeric"` (валидация на стороне клиента — только цифры; пустое значение допустимо). Плейсхолдеры — `root ID…` и `A-root ID…` соответственно, по аналогии с существующими `Автор…` / `Альбом…` / `Название песни…`.
- **FR-004**: Метки полей — текстовые «root ID:» и «A-root ID:», в стилистике `SongsFilterModal.vue` (где уже есть аналогичные поля с теми же метками). Это обеспечивает визуальную консистентность между двумя фильтрами.
- **FR-005**: При нажатии «Найти» значения `rootIdQuery` и `audioRootIdQuery` включаются в payload action `searchCandidateSongs` в `webvue3/src/components/SongEditor/store.js` как `filterRootId` / `filterAudioParentId` (имя параметра — ровно как уже используется бэкендом и `SongsFilterModal.vue`; см. Assumption A-1 про терминологию `audioRootId ↔ audioParentId`).
- **FR-006**: Если поле пустое или содержит только пробелы — соответствующий query-параметр **не** передаётся в store (как уже сделано для `query` / `author` / `album`). Невалидное (нечисловое) значение → параметр не передаётся (трактовка как пустое).
- **FR-007**: Action `searchCandidateSongs` в store передаёт новые параметры в HTTP-POST `/api/songsdigests` как `filterRootId` и `filterAudioParentId` соответственно. Бэкенд уже принимает эти параметры (см. `ApiController.apisSongsDigests`, строки `filterRootId`/`filterAudioParentId`), отдельных изменений на бэкенде не требуется.
- **FR-008**: DTO-ответ `SongDTOdigest` уже содержит `rootId` и `audioParentId` — отдельной доставки значений в `AssignModal` не требуется; список результатов отображается как раньше (`#id · Автор — Альбом — Название · статус`), без вывода значений `rootId` / `audioParentId` в строке результата (только фильтрация).
- **FR-009**: Никаких изменений в логике назначения (`doAssign`), подтверждения `clearMarkers`, чекбокса `onlyStatus1`, валидации формы и кнопки «Назначить» — фича **только** расширяет фильтр.
- **FR-010**: Бэкенд: изменений не требуется. Endpoint `POST /api/songsdigests` уже принимает `filterRootId` и `filterAudioParentId`, маппит их в `filter_root_id` / `filter_audio_parent_id` в SQL-аргументы и фильтрует точным совпадением.
- **FR-011**: Поведение по умолчанию: поля `rootIdQuery` и `audioRootIdQuery` инициализируются пустой строкой при каждом открытии модалки; фича не вводит «запоминание» последнего значения между сессиями.
- **FR-012**: Сохранение состояния в localStorage (`localStorage` для фильтра) — **вне scope** этой фичи. Поведение совпадает с текущим (фильтр живёт только пока модалка открыта, новые поля — тоже).

### Key Entities

- **Песня-кандидат** (`SongDTOdigest`): расширена на фронте только в части фильтрации. Содержит `rootId: Long` и `audioParentId: Long`. Других изменений сущности нет.
- **Состояние фильтра модалки** (`AssignModal.data()`): добавляются два новых строковых поля `rootIdQuery: string` (по умолчанию `''`) и `audioRootIdQuery: string` (по умолчанию `''`). Они не сохраняются между сессиями (живут только пока модалка смонтирована).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Админ может отфильтровать список кандидатов на разметку по `root ID` за один клик «Найти», получив только песни с совпадающим `root_id`; список сокращается до ≤100 записей в типичной базе проекта (админ видит результат менее чем за 1 секунду после клика).
- **SC-002**: Очистка поля `root ID» / `A-root ID» через кнопку «X» не сбрасывает прочие поля фильтра (`Автор`, `Альбом`, `Название песни`) — проверено в 100% кликов в пределах одного открытия модалки.
- **SC-003**: Фильтр по `root ID» работает совместно (AND) с существующими фильтрами «Автор», «Альбом», «Название песни» и чекбоксом «Только кандидаты на разметку» — комбинированный поиск даёт ≤N₁∩N₂∩… записей в синтетическом тесте с известным набором данных.
- **SC-004**: При пустых значениях новых полей фильтрации поведение модалки идентично поведению до фичи (поиск по автору/альбому/названию работает без изменений) — регрессионный тест: 0 ложноположительных результатов при поиске только по автору.
- **SC-005**: Невалидный ввод (`abc`, `12.5`, `12e3`, `-1` если потребуется — допустимо ли отрицательное, см. Assumption A-2) в новое поле приводит к тому, что запрос отправляется без этого фильтра (а не с ошибкой HTTP 400) — UX не прерывается.

## Assumptions

- **A-1 (терминология)**: в постановке задачи поле названо «audioRootId», но в существующем API/UI проекта (`ApiController.apisSongsDigests`, `SongsFilterModal.vue`, `SongDTOdigest`) это поле называется **`audioParentId`**. В этой фиче используется каноническое имя `audioParentId` (бэкенд уже принимает `filterAudioParentId`, фронт в `SongsFilterModal.vue` уже использует переменную `songsFilterAudioParentId`). Метка в UI — «A-root ID:» по аналогии с `SongsFilterModal.vue` (где уже так подписано). Если требуется именно отдельное семантически новое поле `audioRootId` — потребуется расширение бэкенда, БД и миграция; это **out of scope** данной фичи.
- **A-2 (отрицательные значения)**: бэкенд хранит `root_id` и `audio_parent_id` как `Long`, валидация на отрицательные значения не реализована; клиент пропускает пустую строку иначе — отрицательные числа фильтруются как обычно (если БД такие содержит). Это считается приемлемым — задача фичи — точное совпадение ID, а не нормализация диапазона.
- **A-3 (точное vs частичное совпадение)**: фильтрация только по точному совпадению `=` (как уже сделано в `Song.loadListFromDb`). Поддержка префиксного/диапазонного поиска по числовому ID — out of scope.
- **A-4 (UI-стилистика)**: визуальный стиль (метка, ширина поля, кнопка очистки) наследуется от существующей строки фильтра `AssignModal.vue` и `SongsFilterModal.vue`. Никаких новых CSS-классов не вводится за пределами локальной стилизации `se-search-row` (если потребуется — переиспользуются `se-search-author` / `se-search-album` / `se-search-name` и их ширины пересчитываются пропорционально).
- **A-5 (хранение фильтра)**: фильтр не сохраняется между открытиями модалки (как сейчас). Если в будущем потребуется «запомнить последний фильтр» — отдельная фича.
- **A-6 (только admin-роль)**: модалка `AssignModal` доступна только администраторам (`hasRole('ADMIN')` в роутинге); дополнительных проверок прав на новый фильтр не требуется.
- **A-7 (Datalist для root_id не нужен)**: в отличие от автора (где есть `<datalist>` со списком существующих авторов), для числовых ID список значений заранее не известен и неограничен; `<datalist>` не используется.
- **A-8 (бэкенд неизменен)**: реализация только во фронтенде; никаких миграций БД, изменений DTO, изменения эндпоинтов и/или SQL не требуется.
