## User Scenarios & Testing *(mandatory)*

### User Story 1 — Правка родителя подтягивается в аудио-потомков автоматически (Priority: P1)

Владелец (или редактор) исправляет маркеры/текст песни-родителя (например, сдвинул
секцию, поправил слово). Песни-аудио-потомки (копии по звучанию, `audio_parent_id`
указывает на родителя) должны получить актуальный контент родителя, сдвинутый под
их собственный аудио-таймлайн, без ручных действий.

**Why this priority**: Это суть задачи #141 — сейчас правка родителя не отражается
на его потомках, и они остаются с устаревшей/неверной разметкой.

**Independent Test**: У родителя (статус ≥5) и потомка (статус 1–4, `audio_parent_id`
= родитель) правим маркеры родителя и сохраняем. Проверяем: контент потомка обновился
(со сдвигом), статус потомка стал 5, `.srt` перегенерированы.

**Acceptance Scenarios**:

1. **Given** родитель в статусе ≥5 с непустыми маркерами и потомок в статусе <6,
   **When** сохраняется изменение маркеров/текста родителя (content-diff),
   **Then** у потомка обновляются текст/маркеры/форматирование со сдвигом на дельту,
   статус → 5, перегенерируются `.srt`.
2. **Given** родитель в статусе <5, **When** сохраняются любые изменения родителя,
   **Then** механизм синхронизации НЕ запускается (потомки не затираются
   незрелым контентом).
3. **Given** родитель в статусе <5 и потомок в статусе <6, **When** статус родителя
   поднимается сразу в 5 или 6 (например, 2→5, 2→6), **Then** запускается
   синхронизация и потомок получает контент родителя.
4. **Given** родитель уже в статусе 5, **When** статус родителя меняется 5→6,
   **Then** повторная синхронизация НЕ запускается (контент уже синхронизирован).
5. **Given** повторная аудио-сверка пары даёт схожесть <95 %, **When** механизм
   отрабатывает, **Then** данные потомка не меняются, факт пропуска логируется.

---

### User Story 2 — Массовая синхронизация с главной страницы админки (Priority: P2)

Владелец нажимает кнопку на главной странице админки и запускает синхронизацию
потомков для ВСЕХ песен; операция идёт в фоне, по одному родителю за раз, с записью
результата по каждой песне в лог и итоговым уведомлением.

**Why this priority**: Даёт способ разово «догнать» весь каталог после включения
механизма, а также диагностику по конкретным песням.

**Independent Test**: Нажать кнопку → получить ответ «запущено», увидеть по завершении
SSE-уведомление со сводкой; в логе — строка на каждого обработанного потомка.

**Acceptance Scenarios**:

1. **Given** в каталоге есть потомки (`audio_parent_id <> 0`, статус <6), **When**
   владелец запускает функцию, **Then** запускается фоновый проход, внутри — строго
   последовательно (по одному родителю), HTTP-ответ возвращается сразу.
2. **Given** проход идёт, **When** он завершается, **Then** приходит SSE-уведомление
   со сводкой (обработано/синхронизировано/пропущено) и по каждой песне оставлена
   лог-строка.
3. **Given** запуск уже идёт, **When** владелец запускает функцию повторно,
   **Then** второй проход не стартует (общий single-flight с авто-синхронизацией).

---

### User Story 3 — Безопасность: без каскадов, гонок и порчи активных процессов (Priority: P3)

Механизм не должен зацикливаться (синхронизация сама пишет потомка), не должен
запускаться на фоновые сохранения без правок контента, и не должен ломать потомка,
у которого прямо сейчас идёт фоновая обработка (рендер/анализ).

**Why this priority**: Тяжёлая ffmpeg-сверка × тысячи песен + каскадные записи =
риск производительности и порчи данных. Защита обязательна, но вторична по отношению
к самому переносу.

**Independent Test**: (а) Прогнать сохранение потомка и убедиться, что оно не
породило повторный проход; (б) фоновое сохранение без изменения контента не
запускает сверку; (в) потомок с активным `KaraokeProcess` пропускается с логом.

**Acceptance Scenarios**:

1. **Given** синхронизация пишет контент потомка через save-путь, **When** запись
   завершается, **Then** порождённый записью триггер подавлен (нет каскада/цикла).
2. **Given** фоновый процесс сохраняет песню, не меняя content-поля, **When**
   сохранение проходит, **Then** аудио-сверка не запускается.
3. **Given** у потомка активный `KaraokeProcess`, **When** родитель синхронизируется,
   **Then** потomок пропускается с логом, его данные не меняются.

---

### Edge Cases

- **Пустые маркеры у родителя типа `song`**: не синхронизировать (маркеры обязательны
  для типа «Песня»); пропуск логируется.
- **Пустые маркеры у родителя типа `instrumental`/`poetry`**: допустимо, переносится
  как есть.
- **Тип потомка ≠ тип родителя**: всё равно синхронизировать (тип не блокирует).
- **Разное число голосов**: число голосов потомка приводится к числу голосов
  родителя (лишние обрезаются, недостающие добавляются пустыми), затем перенос
  по каждому индексу.
- **Нет аудио у пары** (ffmpeg-сверка не удалась): пропустить с логом.
- **Родитель удалён/не найден в момент обработки**: потомок пропускается.
- **Массовое повторное сохранение родителя подряд** (интерактивное редактирование):
  повторные постановки одного родителя в очередь схлопываются в одну обработку.
- **Исключение на одном потомке/родителе**: цикл не прерывается, ошибка логируется,
  обработка продолжается со следующего.

## Requirements *(mandatory)*

### Functional Requirements

**Триггер и ворота**

- **FR-001**: Система MUST запускать синхронизацию аудио-потомков при сохранении
  песни-родителя, если изменены content-поля (маркеры, исходный текст, результирующий
  текст, форматированный текст/табы/аккорды) **или** если статус родителя перешёл
  из значения <5 в 5/6.
- **FR-002**: Система MUST НЕ запускать синхронизацию, если у родителя статус <5
  (любые правки родителя при статусе <5 не отражаются на потомках).
- **FR-003**: Система MUST НЕ запускать повторную синхронизацию при переходе статуса
  родителя 5→6 (контент уже синхронизирован при переходе в 5).
- **FR-004**: Система MUST определять необходимость запуска по фактическому
  изменению content-полей (diff), а не по факту вызова сохранения — фоновые
  сохранения, не меняющие контент, синхронизацию не вызывают.
- **FR-005**: Система MUST, при наличии у родителя типа «Песня» (`song`) пустых
  маркеров, пропускать синхронизацию; для типов `instrumental`/`poetry` пустые
  маркеры допустимы.

**Кого синхронизируем**

- **FR-006**: Система MUST синхронизировать только прямых аудио-потомков
  (`audio_parent_id` = id родителя) со статусом <6; рекурсивный обход дерева
  MUST NOT выполняться.
- **FR-007**: Система MUST синхронизировать потомка независимо от того, совпадает
  ли его тип с типом родителя.
- **FR-008**: Система MUST пропускать потомка при наличии у него активной фоновой
  обработки (`KaraokeProcess`), не меняя его данные, и логировать пропуск.

**Что переносим**

- **FR-009**: Система MUST переносить в потомка набор контента, эквивалентный
  существующему механизму привязки аудио-родителя: исходный текст, результирующий
  текст, маркеры, форматированный текст песни/табы/аккорды.
- **FR-010**: Система MUST сдвигать маркеры родителя на вычисленную дельту и
  выставлять END-маркер по реальной длительности потомка.
- **FR-011**: Система MUST приводить число голосов (дублей) потомка к числу голосов
  родителя перед переносом: лишние голоса обрезать, недостающие дополнить пустыми.
- **FR-012**: Система MUST перегенерировать файлы субтитров (`.voice{N}.srt`) потомка
  после переноса маркеров (аналог существующих сценариев апрува/автопривязки).
- **FR-013**: Система MUST NOT переносить поля, не относящиеся к контенту (тональность,
  BPM, ссылки на площадки, картинки).

**Аудио-сверка**

- **FR-014**: Система MUST перед переносом выполнить повторную аудио-сверку пары
  (родитель ↔ потомок) и продолжать только при схожести не ниже порога 95 %.
- **FR-015**: При схожести ниже порога система MUST NOT менять данные потомка
  (включая статус) и MUST логировать факт пропуска с указанием процента.
- **FR-016**: При успешной сверке система MUST обновить у потомка сохранённые метрики
  аудио-пары (процент схожести, дельту) и историю сравнений.

**Статус потомка**

- **FR-017**: При успешной синхронизации система MUST перевести статус потомка в 5,
  если он отличался от 5.

**Механика и безопасность**

- **FR-018**: Система MUST выполнять синхронизацию асинхронно, не блокируя вызывающее
  сохранение.
- **FR-019**: Система MUST схлопывать повторные постановки одного родителя (очередь
  с дедупликацией по id) и обрабатывать родителей последовательно.
- **FR-020**: Система MUST подавлять триггеры, порождённые собственной записью
  синхронизации (защита от каскада/цикла).
- **FR-021**: Система MUST использовать общий механизм взаимного исключения для
  авто-синхронизации и массовой админ-функции (не более одного прохода одновременно).
- **FR-022**: Система MUST выполнять запись только в локальную рабочую БД (без
  автоматического push изменённых потомков на прод).
- **FR-023**: Система MUST продолжать обработку при исключении на отдельной песне,
  логируя ошибку (без прерывания всего прохода).

**Админ-функция**

- **FR-024**: Система MUST предоставлять на главной странице админки элемент запуска
  массовой синхронизации всех аудио-потомков (в идеологии существующей Custom Function).
- **FR-025**: Массовая синхронизация MUST перебирать потомков (`audio_parent_id <> 0`,
  статус <6), группируя их по родителю так, чтобы каждый уникальный родитель
  обрабатывался один раз.
- **FR-026**: Массовая синхронизация MUST идти в фоне (HTTP-ответ сразу), последовательно,
  с лог-строкой по каждой песне и итоговым SSE-уведомлением со сводкой.

### Key Entities

- **Song (родитель)**: песня-источник контента; идентифицируется `id`; несёт маркеры,
  текст, форматирование и статус.
- **Song (аудио-потомок)**: песня, у которой `audio_parent_id` указывает на родителя;
  хранит собственные аудио-метрики пары (процент схожести, дельту, историю сравнений)
  и собственный статус.
- **Маркеры (SourceMarkers)**: временные метки секций; переносятся со сдвигом на дельту.
- **Статус обработки (IdStatus)**: 1..6; ворота запуска — родитель ≥5, целевой статус
  потомка — 5.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: После правки родителя (статус ≥5) все его потомки со статусом <6
  получают актуальный контент без ручных действий; доля успешно синхронизированных
  пар с валидным аудио — 100 %.
- **SC-002**: Ни один потомок со схожестью <95 % не получает изменений контента
  (0 ложных переносов).
- **SC-003**: Правка родителя при статусе <5 не изменяет ни одного потомка
  (0 срабатываний).
- **SC-004**: Фоновые сохранения без изменения контента не порождают ни одной
  аудио-сверки (0 ложных запусков).
- **SC-005**: Массовая админ-функция обрабатывает каталог последовательно, не более
  одного прохода одновременно; по каждой песне в логе есть строка результата.
- **SC-006**: Сохранение родителя возвращает управление пользователю без ожидания
  синхронизации (асинхронность).

## Assumptions

- Существующие механизмы (`audio_parent_id`, аудио-сверка, привязка контента аудио-родителя)
  переиспользуются; новых колонок в БД не требуется.
- Порог схожести 95 % совпадает с уже принятым порогом аудио-родителя.
- Под «сохранением песни» понимаются пути, проходящие через общий save-метод `Song`
  (редактор, апрув, ручная правка статуса), а не только HTTP-эндпоинты.
- Синхронизация затрагивает только локальную рабочую БД; выравнивание прода —
  существующий механизм синхронизации, отдельным шагом.
- «Синхронно» в задаче означает «последовательно, по одному родителю», а не
  блокирующий HTTP-запрос.
- Формат файлов субтитров и способ их генерации уже существуют (`.voice{N}.srt`).
- Механизм не применяется к песням без аудио-родителя (`audio_parent_id = 0`).
