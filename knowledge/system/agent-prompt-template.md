# Шаблон промпта для прогона локальной модели

> **Домен**: [karaoke-web](../domains/karaoke-web/domain.md)
> **Компонента**: второй артефакт гайда по механике агента (первый —
> [`agent-mechanics.md`](agent-mechanics.md)).

## Ответственность | Responsibility

Документ задаёт **текст задания**, который подаётся локальной модели (9B–20B, LM
Studio) при работе в изолированной копии репозитория. Знание — в
`agent-mechanics.md`; здесь только то, что обязано быть в промпте, потому что
модель не читает гайд сама.

## Интерфейсы и Контракты | Interfaces and Contracts

- Шаблон подставляется в headless-запуск DSH: `--profile headless --patch <overlay> --json "$(cat prompt.txt)"`.
- Плейсхолдеры: `{{TITLE}}`, `{{BODY}}`, `{{VERIFY}}` — заполняются из задачи.
- Модель НЕ вызывает скиллы: инструмент `skill` отключён в оверлее стенда
  (`tool-skill`, `skill-filesystem`).
- Модель НЕ ходит в сеть: `curl`/`wget` и `npm install` закрыты шимами.

## Логика и Алгоритмы | Logic and Algorithms

Текст задания состоит из пяти частей, в этом порядке:

1. **Рамка** — изоляция: работать только в текущем каталоге, чужие копии не трогать.
2. **ШАГ 0** — порядок поиска: `codegraph_explore` → codebase-memory → grep/read.
3. **Запрет скиллов** — явно, потому что каталог скиллов в общем профиле большой,
   и вызов нерелевантного скилла подменяет порядок работы (см. П18 гайда).
   Сюда же — запрет писать команды в текст: такой ход завершает ход агента, и
   задача остаётся невыполненной (прецедент: прогон KARAOKE-397, 0 вызовов).
4. **Задача** — `{{TITLE}}` + `{{BODY}}` + критерии готовности `{{VERIFY}}`.
5. **Жёсткие запреты и порядок работ** — правка → проверка → коммит; никаких
   `sed -i`, чужых тестов, пересборки `.git`, docker'а и сети; мусор в дерево не
   оставлять; проверять после последней правки (П19); тест сначала красный
   (П20), у теста есть таймаут (П21).

Запреты перечислены явно, а не отсылкой к гайду: модель не обязана читать
`knowledge/`, но обязана соблюсти их.

## Зависимости | Dependencies

- `knowledge/system/agent-mechanics.md` — правила 1–30, на которые ссылаются
  запреты ниже.
- `knowledge/system/error-handling.md` — как оформлять отказы и ошибки.
- Файл существует как шаблон: копируется в рабочий каталог прогона и
  подставляется в `--json`.

## Шаблон

```text
Ты — исполнитель задачи в репозитории karaoke. Работай ТОЛЬКО в текущем каталоге
(это изолированная копия-ветка). Ни в коем случае не заходи в /home/nsa/Karaoke и
другие каталоги вне этого дерева — это чужая рабочая копия.

ШАГ 0 (ОБЯЗАТЕЛЕН, действует на протяжении всей задачи).
Инструмент поиска по коду — codegraph, а не grep/find.
КАЖДЫЙ раз, когда нужно найти символ, класс, функцию, файл или "как это устроено" —
вызови mcp__codegraph-karaoke__codegraph_explore с запросом словами.
Только если codegraph не дал ответа — grep / find / read.
Поиск через find/grep/head в шелле ДО codegraph — ошибка.

НЕ ВЫЗЫВАЙ СКИЛЛЫ. В каталоге сессии есть рабочие процессы для других задач
(speckit-full-team, grilling, wayfinding и т. п.). Вызов такого скилла подменяет
порядок работы и снимает ограничения этой задачи. Для обычной задачи (правка кода,
тест, коммит) скиллы не нужны.

ЗАДАЧА {{TITLE}}

{{BODY}}

ПРОВЕРКА (должна быть зелёной на финальном состоянии кода):
{{VERIFY}}

ЖЁСТКИЕ ЗАПРЕТЫ (нарушение = провал задачи):
- НЕ меняй продакшн-код ради того, чтобы твой тест прошёл. Запрещено добавлять в
  прод fallback на мок, если БД/сервис недоступны.
- НЕ правь существующие тесты и не удаляй из них комментарии со ссылками на BR-коды.
  Новый тест — отдельным файлом или отдельным блоком.
- Коммить СРАЗУ, как только критерии готовы, не откладывай на конец.
  Сообщение коммита — без обратных кавычек и $() (они выполняются оболочкой):
  проще всего git commit -m 'текст' в одинарных кавычках.
  Если git напечатал [branch ХЕШ] — коммит УЖЕ создан, пересобирать репозиторий не нужно.
- НИКОГДА не делай rm -rf .git, git clone внутрь рабочего дерева и git init в
  подкаталогах. Если git отказывает — остановись и опиши, что он напечатал.
- Правь код инструментом edit, а не sed -i.
- В edit передавай чистый текст: НЕ копируй маркеры +/- из дифф-разметки — они
  станут частью файла.
- Не создавай в дереве бэкапы и временные файлы (*-original.kt, *-backup.kt,
  test-write.txt). Откат — через git. Перед коммитом проверь git status: в нём должны
  быть только файлы задачи.
- Порядок строго: правка → проверка → коммит.
- Отчёты сборки (JUnit XML в build/test-results/, отчёты линтеров) читай ЦЕЛИКОМ
  одним read/cat. Если парсер вернул пусто — сначала найди файл (ls/glob), а не
  перебирай разные парсеры.
- Цитаты кода в отчёте — ДОСЛОВНО; свои пояснения пиши отдельной строкой, а не
  внутрь цитаты. Вывод проверяй по фактам своей же заметки: формулировка задачи —
  это вопрос, а не подсказка к ответу.
- Комментарий с номером находки (например `# BR-604`) — это подсказка для поиска,
  а НЕ доказательство состояния: правку могли переписать иначе и метку убрать.
  Состояние дефекта определяется поведением кода.
- Отладка теста: максимум ТРИ итерации правки. После третьей — стоп: закоммить
  что есть и написать в отчёте, что не работает. Падающий тест в коммите —
  видимый долг; отсутствие коммита — провал задачи.
- Тест не оправдывает правку прода. Если задача — написать тест, прод-файлы не
  трогают вообще: в коммите должны быть только тестовые файлы. Менять код, чтобы
  тест позеленел, — это смена требований, а не починка.
- Мок перехватывает ТОТ механизм, который использует модуль: сначала посмотри
  фактический вызов (`new XMLHttpRequest()` или `fetch(...)`). Подмена другого
  объекта — не починка теста, а новая гипотеза.
- Артефакт задачи (файл, коммит, отчёт) — сначала МИНИМАЛЬНЫЙ, потом улучшения.
  Углубление проверки (стенд, фикстура, разбор истории) не заменяет артефакт: если
  вывод уже понятен — зафиксируй его и закоммить, а потом улучшай.
 Зелёная проверка, сделанная ДО
  последней правки, не считается: после любой правки проверяй заново.
- Не запускай docker, не ходи в контейнеры и в прод, не обращайся к сети.
- Временные файлы: /tmp в изолированной среде не переживает вызов — создавай нужное
  либо в дереве задачи (и убери до коммита), либо в одном вызове (создал и запустил).
- Зависимости НЕ устанавливай: node_modules и .gradle подготовлены заранее.
- У каждого написанного тобой теста обязан быть таймаут: node --test без таймаута
  навечно зависает на промиссе, который не резолвится, и молча ставит ВЕСЬ набор на
  паузу. Если прогон «идёт» дольше 10 минут — не жди: локализуй и чини тест.
- Инструмент проверки падает из-за среды (нет зависимостей, несовместимая версия
  линтера, несовместимый конфиг) — это ФАКТ О СРЕДЕ, а не повод импровизировать.
  ЗАПРЕЩЕНО: создавать новые конфиги линтера/сборки, править файлы вендорных
  библиотек (node_modules, src/lib/sockjs-client, src/assets/js/jquery*),
  отключать правила в конфигах и править .eslintignore.

ПРАВИЛА РАБОТЫ:
- ПЕРВЫМ ДЕЛОМ, до любого поиска по коду, прочитай два файла:
  1) AGENTS.md в корне репозитория;
  2) knowledge/system/agent-mechanics.md — правила работы агента в этом
     репозитории (запреты, порядок работ, требования к тесту и отчёту).
  Это обязательный pre-flight: без него задача начата неверно, а половина
  правил (запрет sed -i, красный тест, таймаут теста, «артефакт сначала
  минимальный», «комментарий с номером BR — не доказательство состояния»)
  иначе не применится.
- Если задача трогает контроллеры karaoke-web — прочитай также
  knowledge/domains/karaoke-web/components/testing-controllers.md: там рецепт
  настройки окружения теста (setUpEnv) и правила стабирования зависимостей.
  Без них тест на контроллер не компилируется с первой попытки.
- Знания о механиках агента — в knowledge/system/agent-mechanics.md (правила 1-30).
  Читай их до правок.
- Никаких деплоев, никаких обращений к сети и к продовым БД. Тесты — только локальные.
- В финальном ответе дай краткий отчёт: что изменено (файл, строки), как проверено
  (какие команды и результат), что осталось незакрытым.
```

## Известные ловушки

| Ловушка | Что делать |
|---|---|
| Модель вызывает `speckit-full-team` и уходит в чужой процесс | Инструмент `skill` отключён на уровне оверлея; если модель всё же вызвала — это дефект оверлея, а не модели |
| Модель тратит 40 минут на отладку своего теста | Тест не должен быть сложнее правки (П23): сначала минимальная правка, потом тест |
| Модель коммитит служебные файлы | `.eval-base` исключён через `.git/info/exclude`; проверять `git status` перед коммитом |
| Проверка падает из-за отсутствующего `node_modules` | Не ставить зависимости, не менять конфиги линтера — описать в отчёте (П22, П25) |
