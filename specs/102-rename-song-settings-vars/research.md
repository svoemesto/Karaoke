# Phase 0 Research: Переименование `settings` → `song`

Все пункты Technical Context в `plan.md` определены без `NEEDS
CLARIFICATION` — открытые вопросы были закрыты уже на этапе
`/speckit-clarify` (см. `spec.md` → `## Clarifications`). Этот документ
фиксирует несколько технических решений, обнаруженных при дополнительной
разведке в ходе планирования, которые не требовали отдельного вопроса
пользователю (не меняют охват/риск задачи), но важны для `tasks.md`.

## Решение 1: `KaraokeProcessDTO.settingsId` не имеет фронтенд-потребителя

**Вопрос**: `KaraokeProcessDTO.settingsId` — DTO-поле, сериализуемое в JSON
(FR-010). Нужно ли синхронно править какой-либо файл `webvue3`?

**Решение**: Нет. Grep по `webvue3/src` (`Processes/ProcessesTable.vue`,
`Common/ProcessWorker.vue`, `views/ProcessesView.vue` и весь модуль
`Processes`) не находит обращений к `settingsId` — поле нигде не читается по
имени на фронтенде. Переименование в `songId` — чисто backend-side (JSON-ключ
меняется, но реального потребителя не существует), в отличие от
`HealthReportDTO.settingsId`/`settingsFileName` (5 конкретных мест в
`Common/HealthReport/*`) и SSE-ключа (`Songs/store.js:1779`).

**Rationale**: Экономит работу в `tasks.md` — не нужно искать/чинить
несуществующий вызов; при этом FR-010/FR-015 всё равно выполняются (сам DTO
переименован).

**Alternatives considered**: Оставить `KaraokeProcessDTO.settingsId` как
есть под предлогом «раз никто не использует, можно не трогать». Отклонено —
противоречит явному решению пользователя (Clarifications, вопрос 1: «Полный
охват включая DTO+фронтенд») и оставило бы несогласованность внутри одной и
той же кодовой базы (два похожих DTO с разными именами одного и того же
понятия).

## Решение 2: Объём правки per-feature документации (constitution FR-009)

**Вопрос**: Затрагиваемый код относится к подсистемам `async-process-queue`,
`dual-db-sync`, `sse-notifications`, `songs-table` (см. `docs/features/`).
Нужно ли обновлять все 4 документа?

**Решение**: Обновляется только `docs/features/premium-stems.md:44` —
единственное место среди per-feature документов, где встречается
переименовываемый Kotlin-идентификатор (`settingsId=0`) как часть
документированного инварианта, а не физическое имя колонки БД. Строка
одновременно использует устаревшее (уже до этой задачи) название
`Settings`/`tbl_settings` — обновляется на `Song`/`tbl_songs` заодно.
`async-process-queue.md:165` упоминает `settings_id`, но это физическое имя
колонки БД, которое эта задача не меняет (FR-005) — документ остаётся
корректным без правок. `dual-db-sync.md`, `sse-notifications.md`,
`songs-table.md` не содержат конкретных идентификаторов, устаревающих от
этого рефакторинга.

**Rationale**: FR-009 конституции требует обновлять per-feature документ при
правке кода фичи, если документ что-то утверждает про этот код; здесь это
буквально верно только для одной строки. Массовая правка остальных
документов «на всякий случай» была бы add-scope без содержательной пользы и
противоречила бы принципу «не делать больше, чем нужно».

**Alternatives considered**: Обновить все 4 документа с общей пометкой «поле
переименовано» — отклонено как избыточное: ни один из них не содержит кода,
который читатель мог бы скопировать и получить ошибку.

## Решение 3: Порядок переименования внутри единого PR

**Вопрос**: Как секвенировать ~35 файлов + контрактные пары внутри одного PR
(FR-016), чтобы минимизировать риск (единый PR не отменяет пошаговую
проверку компиляции).

**Решение**: Двухволновая последовательность:
1. **Волна А — изолированные Kotlin-идентификаторы** (FR-001, FR-002,
   FR-003, FR-013), не пересекающие границу backend↔frontend: `Utils.kt`,
   `UtilsAI.kt`, `UtilsPictures.kt`, `Functions.kt`, `mlt/**`,
   `KaraokePlatformPublication.kt`, `model/Song.kt`,
   `model/SongRenderContext.kt`, `model/Zakroma.kt`,
   `services/PlayerMp4MuxService.kt`, `HealthReport.kt` (конструктор),
   `KaraokeProcess.kt` (кроме `@KaraokeDbTableField`-аннотации),
   `KaraokeProcessWorker.kt`, `StemJobPollScheduler.kt`,
   `StemJobProcessing.kt`, контроллеры `karaoke-web`. Компилировать
   (`./gradlew build`) и `ktlintCheck` после каждого файла/группы.
2. **Волна Б — контрактные пары** (FR-010…FR-012): `HealthReportDTO.kt` +
   4 файла `webvue3/Common/HealthReport/*`; `KaraokeProcessDTO.kt` (без
   фронтенд-правки, см. Решение 1); `MainController.kt`
   (`/changesettingsstatus`) + `settings_context.js`; `SseNotification.kt` +
   `webvue3/Songs/store.js`; `/songs_update`-семейство в `MainController.kt`
   + три Thymeleaf-шаблона. Каждая пара правится и проверяется атомарно
   (backend+frontend в одном шаге), чтобы не оставлять временного
   рассинхрона даже локально при разработке.

**Rationale**: Одна ветка/PR (решение пользователя), но внутренняя
последовательность коммитов снижает риск слона-за-раз ошибки на 35+ файлах;
контрактные пары держатся вместе, чтобы grep-проверка (FR-015) была
осмысленной на каждом шаге, а не только в конце.

**Alternatives considered**: Переименовать всё одним проходом
(`sed`/IDE rename) без волнового порядка — отклонено: контрактные места
(FR-010…FR-012) требуют ручной проверки соответствия backend/frontend
построчно, что проще делать малыми, тематическими порциями, даже внутри
одного PR.
