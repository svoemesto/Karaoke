# Research: Таблица «FREE vs PREMIUM» на /premium (QW-1)

**Branch**: `005-free-vs-premium` | **Phase**: 0 | **Date**: 2026-07-25

---

## Decision 1: Список фичей — построчная верификация с кодом (12 → 9)

**Decision**: из 12 изначально предложенных в `spec.md` строк 9 подтверждены
кодом и вошли в финальный список (FR-003), 3 убраны, 1 заменена, 1 число
исправлено. Полное обсуждение прошло построчно с пользователем в сессии
2026-07-25 (тот же процесс, что и для `004-reasons-to-register`).

**Rationale и свидетельства по каждой убранной/изменённой строке**:

- **«Скачивание MP4 (3 версии)»** — убрана целиком. Причины две:
  1. Функции нет нигде в коде (`grep` по `karaoke-public`/`karaoke-web` на
     `download.*mp4` — 0 совпадений).
  2. Это не просто отсутствующая фича, а **прямое нарушение**
     `constitution.md` («Только онлайн» — оферта, MP4/скачивание нельзя
     упоминать даже в коде/комментариях, TOP-10 ловушек п.10). Даже если бы
     фича появилась, её нельзя было бы так рекламировать.
  Заменена на **«Непрерывное воспроизведение, повтор, случайный порядок»** —
  реальная премиум-фича, взята дословно из бэкенда:
  `PublicPlaylistController.kt` → `PREMIUM_BENEFITS` (константа, уже
  показывается пользователю при достижении лимита) содержит «Непрерывное
  воспроизведение, повтор и случайный порядок».

- **«История прослушиваний»** — убрана. Функция не существует вообще, ни для
  FREE, ни для PREMIUM: нет роута `/account/history` ни в одном из SPA, нет
  бэкенд-эндпоинта. Тот же вывод уже был сделан для `004-reasons-to-register`
  (там это был пункт 2 «История» — тоже убран).

- **«Уведомления о новых песнях»** — убрана. Тоже не существует — это `QW-12`
  («Подписка на новые песни автора», soft paywall) в бэклоге `growth.md`, не
  реализовано.

- **«Без рекламной метки при шаринге»** — убрана. `ShareButton.vue`
  (`003-about-page`, построен 2 дня назад) не содержит никакой концепции
  водяного знака/метки — делить нечего, различия FREE/PREMIUM в шаринге не
  существует.

- **Строка 1 «Просмотр эфирных песен (видео VK)»** — упоминание VK убрано,
  переформулирована в «Онлайн-плеер для песен «в эфире»». Причина —
  `constitution.md`: площадки (Sponsr/Dzen/VK/Max/TG) — технический канал
  распространения демо-контента, не элемент рекламы; упоминать их в публичных
  материалах запрещено (сайт-центричная модель). Дополнительно проверено:
  `.km-videos`-блок с VK-iframe в `SongView.vue` — явно помечен в комментарии
  как «старое место, только когда онлайн-плеер сам не может отобразиться»,
  то есть fallback, а не основной способ просмотра. Основной путь — свой
  плеер сайта (`KaraokePlayer.js`).

- **Строка 5 «Избранное»**: PREMIUM было «без лимита», исправлено на
  «до 500» — точное значение константы `PREMIUM_ITEMS_LIMIT = 500` в
  `PublicPlaylistController.kt`. `FREE_FAVORITES_LIMIT = 100` — совпало с
  исходной спекой без изменений.

- **Строка 6 «Свои плейлисты»**: `PREMIUM_PLAYLIST_LIMIT = 50` — точное
  совпадение с исходной спекой без изменений. Доп. подтверждение из
  doc-комментария того же контроллера: «не-премиум — только «Избранное» (до
  100 песен); премиум — до 50 плейлистов (включая «Избранное») × до 500
  песен в каждом» — совпадает дословно с итоговыми строками 5 и 6.

**Alternatives considered**: оставить 10-12 строк, «смягчив» формулировки
несуществующих фич (например, «скоро: история прослушиваний») — отклонено
пользователем в этой же сессии для аналогичного случая в
`004-reasons-to-register`: смешивать «что есть» с «что планируется» на одной
табличке сравнения тарифов — вводит в заблуждение сильнее, чем короткая
честная таблица.

## Decision 2: Числа (100/500/50) — hardcoded, не через API

**Decision**: значения лимитов записываются как статические числа в
`PremiumView.vue`, не запрашиваются у бэкенда динамически.

**Rationale**: `FR-011` из `spec.md` явно требует «список фичей хранится в
исходниках, не в БД (для простоты)» — это осознанное решение спеки, не
пересматривается в рамках planning. Технически можно было бы дёргать
`/api/public/account/subscription/tariffs` или добавить новый эндпоинт
«лимиты», но это расширяет скоуп фичи ради значений, которые меняются крайне
редко (константы в коде, не БД-конфиг).

**Alternatives considered**: новый `GET /api/public/limits`-эндпоинт,
отдающий `FREE_FAVORITES_LIMIT`/`PREMIUM_ITEMS_LIMIT`/`PREMIUM_PLAYLIST_LIMIT`
— отклонено как избыточное усложнение для значений, которые меняются вместе
с релизом кода (в этом случае таблицу и так надо будет обновлять вручную).

## Decision 3: Место вставки — между `.km-delivery-note` и первой картой тарифа

**Decision**: таблица вставляется в `PremiumView.vue` сразу после
`<p class="km-delivery-note">` и перед `<div class="km-card km-card-primary">`
(карта «Путь 1: подписка на сайт»).

**Rationale**: совпадает с рекомендацией `spec.md` (открытый вопрос №3: «над
тарифами, чтобы сначала «зацепить» фичами, потом «продать» цену»).
Соответствует структуре страницы: заголовок → пояснение про цифровую услугу →
**сравнение FREE/PREMIUM** → варианты оформления подписки.

**Alternatives considered**: под тарифами — отклонено (пользователь уже
принял решение о покупке раньше, чем понял ценность); между картами тарифов —
отклонено (разрывает целостный поток «путь 1/2/3»).

## Decision 4: Реализация без нового компонента

**Decision**: таблица — HTML `<table>` + статический массив из 9 объектов в
`data()`, без выделения в отдельный `.vue`-компонент. Согласуется с открытым
вопросом №2 spec.md (рекомендация: обычная `<table>`, не карточки/grid).

**Rationale**: используется в одном месте, контент статический — тот же
аргумент, что и в `004-reasons-to-register` Decision 4 (не вводить
абстракцию без переиспользования). `<table>`/`<thead>`/`<tbody>` даёт
семантический HTML «бесплатно» (NFR-002) без дополнительной вёрстки.

**Alternatives considered**: карточки-сравнения (2 колонки div'ов) —
отклонено, `<table>` проще для мобильной адаптации через
`display: block`/`overflow-x` паттерн, уже используемый в других таблицах
проекта (`webvue3` таблицы).
