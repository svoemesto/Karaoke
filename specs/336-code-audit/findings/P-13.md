## Сверки

1. **`BR-183` (P-15) — подтверждение механизма с уточнением по `&`.** Механизм подтверждается: `MltNode.toString()` не экранирует ни значения атрибутов, ни `body` (`model/MltNode.kt:35–50`), а `String.xmldata()` (`Extentions.kt:107`) экранирует только `<`, поэтому вложенный `xmldata` требует двойного экранирования. В P-13 по этому пути идут все `template().toString().xmldata()` (`MkoHeader.kt:52`, `MkoHorizon.kt:44`, `MkoFlash.kt:46`, `MkoCounter.kt:45`, `MkoFaderText.kt:43`, `MkoChordPictureImage.kt:58`, `MkoMelodyNote.kt:60`, `MkoChords.kt:61`), а также значения атрибутов в `MkoMainBin.kt:184,282` (путь/имя файла). **Уточнение:** для `&` в названии/авторе/альбоме достижимый путь LYRICS/KARAOKE не ломается — `Song.kt:3057–3063` заранее пишет `&amp;amp;` (двойное экранирование под вложенный XML): в реальных `.mlt` (2026-07-07, альбом «Глеб Самойлоff & The MatriXX») внешний и внутренний XML парсятся, текст содержит ровно `&`. Остаются: `<` в метаданных (в каталоге 0 из 26 864 песен — `POST /api/songsdigests`) и `"` в значениях атрибутов (`MkoMainBin.kt:184,282`; имена файлов санитизируются, путь — нет). То есть пример BR-183 «`&` в songName/author/album ломает `.mlt`» для `MkoHeader` не воспроизводится; запись не завожу, BR-183 остаётся с уточнённой областью действия.
