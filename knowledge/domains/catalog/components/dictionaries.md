# Component: dictionaries

> **Домен**: [catalog](../domain.md)
> **Компонент**: централизованное хранение магических кодов, enum'ов и
> соглашений по тегам домена. Любые литералы, упомянутые в коде или
> спецификациях, **обязаны** быть определены здесь.

## Ответственность | Responsibility

В catalog-домене часто возникают ситуации, когда:

- числовой код статуса `1..6` используется в БД, API, JS-фильтрах;
- строковое значение `song`/`instrumental`/`poetry` фигурирует в миграциях,
  фильтрах, DTO;
- магический тег `SKIP` управляет видимостью песни на публичном сайте.

Эта компонента — единственное место, где эти константы определены.
Использование литералов в L3-спецификациях и коде без ссылки на эту
страницу — **критический дефект** (см. `audit-living-docs` «Magic Codes»).

## Интерфейсы и Контракты | Interfaces and Contracts

### `IdStatus` — статус обработки Song

| Код | Имя | Описание |
| --- | --- | --- |
| 1 | `NEW` | Только что добавлена, обработка не начата. |
| 2 | `PROCESSING` | В обработке (`AudioAnalize` + смежные workers). |
| 3 | `STEMS_READY` | Стемы готовы, разметка не начата. |
| 4 | `MARKED` | Маркеры расставлены, рендер не запущен. |
| 5 | `RENDERED` | MP4 отрендерен, ждёт approve. |
| 6 | `APPROVED` | Approve выдан, публикация разрешена. |

**Место определения**: `karaoke-app/.../model/Song.kt`, поле `idStatus: Int`.

**Контракт**: стабильный, не должен меняться без миграционного эпика
(числовые коды записываются в БД и в JS-фильтры `webvue3`).

**Статусные ворота синхронизации аудио-потомков** (#141, specs/413): механизм
«Синхронизация аудио-потомков» запускается только при статусе родителя ≥ 5 и
переводит потомка в 5 (см. [audio-descendant-sync](audio-descendant-sync.md)).
Это не меняет сами коды `IdStatus` — только их использование в данном механизме.

**Использование в админских фильтрах публикаций** (OpenProject #326):
UNPUBLISH показывает только `idStatus = 6` (полностью готово, но публикация не
назначена); UNDONE — `idStatus < 6`, включая 5 («отрендерено, ждёт approve»).
См. [knowledge/product/features/publications-filters.md](../../../product/features/publications-filters.md).

**Запрещено**:

- Хардкод числовых литералов `1..6` в коде или SQL — только
  константы из словаря.
- Числовые диапазоны типа `idStatus >= 4` без ссылки на эту страницу.

### `SongType` — тип песни

| Значение | Описание |
| --- | --- |
| `song` | Обычная песня с вокалом. |
| `instrumental` | Инструментал (без вокала). |
| `poetry` | Поэзия (без музыки). |

**Место определения**: `Song.songType: String` (да, сейчас `String`,
а не enum — см. ADR `0002-…` TODO).

**Использование**:

- В БД: колонка `tbl_songs.song_type` (varchar).
- В API: поле `SongDTO.songType`.

**Запрещено**: другие литералы, кроме `song`/`instrumental`/`poetry`.

### Флаг `freeAfterOnAir` — не снимать с эфира (Pass 369, OpenProject #81)

| Значение | Описание |
| --- | --- |
| `true` | После наступления `dateTimePublish` песня остаётся публично доступной, не уходит в premium-only по таймеру стандартного окна. |
| `false` | Стандартное поведение: после окончания окна (1 календарный месяц) песня становится premium-only. Default. |

**Место определения**: `karaoke-app/.../model/Song.kt`, поле
`freeAfterOnAir: Boolean` (геттер/сеттер через `fields[SongField.FREE_AFTER_ON_AIR]`).

**Использование**:

- В БД: колонка `tbl_songs.free_after_on_air` (`BOOLEAN NOT NULL DEFAULT false`,
  миграция `deploy/karaoke-db/50_tbl_songs_free_after_on_air.sql`).
- В API: поле `SongDTO.freeAfterOnAir`.
- В UI: пара кнопок ДА/НЕТ «Не снимать с эфира (после окна доступа)» в
  `SongEdit.vue`.

**Контракт**:

- Действует **только после наступления эфира** (`dateTimePublish ≤ now`),
  см. clarification 2026-09-11 в `specs/369-free-after-onair-flag/spec.md`
  (Q2).
- Приоритет: `free=true` > `freeAfterOnAir=true` (оба флага независимы и
  хранятся раздельно — см. clarification Q1).
- `exclusive=true` > всё остальное (`premium-only` по бизнес-решению).

**Запрещено**: использовать флаг как «всегда бесплатно» (для этого есть
`free=true`) или как «опубликовать досрочно» (флаг не действует до эфира).

### Тег `SKIP` — скрытая песня

| Значение | Описание |
| --- | --- |
| `SKIP` | Песня скрыта с публичного сайта (заглушка). |

**Использование**:

- В БД: колонка `tbl_settings.tags` (text[]), содержит `'SKIP'`.
- В API: фильтр в публичных контроллерах исключает песни с `SKIP`.
- В UI: отображается серым, без кнопки Play.

**Контракт**: добавление/удаление `SKIP` логируется в доменное
событие `SongSkipped` (см. [song-lifecycle](song-lifecycle.md)).

**Запрещено**: использовать `SKIP` как обычный жанр/тег. Это
флаг видимости, не классификация.

## Логика и Алгоритмы | Logic and Algorithms

### Сохранение и вставка Song: результат записи и DTO списка (аудит #336, PKG-S2-10)

С пакета `PKG-S2-10` (OpenProject #373) у `Song` зафиксированы контракты,
влияющие на целостность данных:

- **`saveToDb(): Boolean`** (BR-102) — `true` только если `UPDATE` реально
  выполнен (или писать было нечего). Ошибка биндинга/`executeUpdate`
  отменяет запись целиком и возвращает `false`; проглатывания исключений
  по параметрам больше нет. `saveToDbLocked()` коммитит только при
  `saveToDb() == true`, иначе делает `rollback()` и возвращает `false`.
- **`loadFromDbById` пробрасывает `SQLException`** (BR-101): `null` теперь
  означает только «строки нет», а не «ошибка чтения». `loadListFromDb`
  получил параметр `throwOnError` (по умолчанию `false` — списочные
  endpoint'ы сохраняют fail-soft поведение). `saveToDb` при пропавшей
  строке пишет WARN `song.save_skipped` и не выдаёт успех.
- **`toDTO()` не ходит в БД** (BR-104): `albumName` заполняется пакетно
  через `Song.toDTOsWithAlbumNames()` (один `SELECT` по `tbl_albums` на
  список, `Album.getAlbumsByIds`). Раньше каждая песня списка давала
  отдельный запрос — N+1 на таблице песен.
- **`getSqlToInsert()`** (BR-108) содержит `album_id`, `root_id`, `free`,
  `free_after_on_air`, `audio_parent_id`, `audio_similarity_percent`,
  `audio_delta_ms`, `audio_compare_history`, `player_readiness_flags`.
  Раньше список колонок отставал от схемы, значения молча уходили в
  `DEFAULT`, и `recordhash` вставленной строки не сходился с исходной.
  Колонка `exclusive` по-прежнему не переносится: в сущности `Song` нет её
  поля (см. отчёт `specs/373-pkg-s2-10/report.md`, «за владельцем»).

### DTO песни: состояние премиум-автопубликации (аудит #336, PKG-S2-17)

`SongDTO` — единственный контракт и `/api/song` (карточка), и `/api/songs`
(список). С пакета `PKG-S2-17` (OpenProject #380, BR-087) в нём отдаются
readiness-флаги премиум-цикла спеки 122:

| Поле DTO | Источник в `Song` | Смысл |
| --- | --- | --- |
| `newsPremiumPublishPending` | readiness-флаг | песня входит в премиум-цикл и публикация ещё не завершена |
| `newsPremiumTelegramSent` / `newsPremiumVkSent` | readiness-флаг | премиум-пост отправлен в соответствующий канал |
| `premiumAttemptCountTelegram` / `premiumAttemptCountVk` | readiness-строка → `Int` | число неудачных попыток по каналу |
| `premiumAutoPublishLastError` | readiness-строка | текст последней ошибки публикации |
| `telegramAutoPublishState` / `vkAutoPublishState` | readiness-строка | `rendering` / `publishing` / `published` / `error` |

**Контракт.** Поля обязаны доезжать до клиента: `SongEdit.vue` строит из них
`premiumTelegramPublishState`/`premiumVkPublishState` (FR-006/FR-007/FR-008). До
BR-087 их не было в DTO, компонент получал `undefined`, состояния всегда были
`null`, и блоки статуса с кнопками «Повторить» не рендерились никогда.

**Запрещено.** Добавлять новое поле `Song` в UI-логику без соответствующего поля
`SongDTO` — именно это расхождение и породило дефект: сущность знала о состоянии
публикации, а контракт молчал.

**Запись флагов — атомарная (BR-075, аудит #336, PKG-S3-22).** Все readiness-флаги
живут в одном JSON-поле `player_readiness_flags`. Флаг пишется точечным
compare-and-swap (`UPDATE … WHERE id = ? AND player_readiness_flags = ?`), а не
записью всего JSON: два потока (заливка стемов и планировщик автопубликации) больше
не затирают ключи друг друга. Дифф-обновление песни это поле **не пишет** —
иначе оно снова записало бы устаревший JSON. Формат хранения прежний:
компактный JSON без пробелов (`{"a":true}`) — от него зависят проверки в
`karaoke-web`. Подробности — [song-entity.md](song-entity.md#флаги-готовности-пишутся-атомарно-br-075-pkg-s3-22).

### «Пустой голос» и его удаление при сохранении (specs/547)

Голос песни — пара «текст + маркеры», адресуемая индексом с нуля
(`tbl_songs.source_text` — массив строк, `tbl_songs.source_markers` — массив
массивов маркеров).

**Пустой голос** — голос, у которого текст пуст (пустая строка или только
пробельные символы) **и** маркеров нет (0 маркеров). Любой маркер, включая
служебный (`SETTING`, `COMMENT`, `ENDOFLINE`), делает голос непустым.

Правило: при сохранении песни пустые голоса с индексом больше нуля удаляются,
оставшиеся нумеруются без дыр; первый голос сохраняется всегда. Детали и код —
[Song: нормализация голосов](song-entity.md#нормализация-голосов-при-сохранении-specs547).

### Производные значения `Song` и их fallback'ы (аудит #336, PKG-S3-22)

Часть «полей-словарей» `Song` не хранится в БД, а вычисляется геттером. У них
есть контракт «что вернуть, если источник недоступен» — его нельзя менять
молча, на нём держатся рендер и публикация.

- `durationInMilliseconds` — из `mediainfo` (`Audio/Duration`, секунды × 1000).
  При любом сбое (нет файла, таймаут `KARAOKE_MEDIAINFO_TIMEOUT_SECONDS`,
  ненулевой код, нечисловой ответ) возвращается `0`, а причина пишется `WARN`
  в лог `MediaInfo`. `0` — именно «неизвестно», а не «пустой трек»: MLT с таким
  значением даёт `out=00:00:00.000`, поэтому сбой внешнего CLI обязан быть
  виден в логе (BR-035).
- `durationTimecode` / `durationFrames` — производные от
  `durationInMilliseconds`; `0` каскадно даёт `00:00:00.000` и `0` кадров.
- `sourceMarkersList` и производные (`voices`, `markersNotes`, `indexTabsVariant`)
  разбираются из строки `sourceMarkers`; при отсутствии/некорректном значении
  возвращается пустой список, а не исключение (см. «Алгоритм парсинга
  `sourceMarkers`» ниже). Обратный контракт — «маркеры не заданы» —
  сообщается явной ошибкой рендера, а не `IndexOutOfBoundsException`.

### Счётчик голосов в DTO: «неизвестно» вместо «1» (BR-105, аудит #336, PKG-S3-22)

`SongDTO.countVoices` и `SongDTOdigest.countVoices` — `Int?`. Для песен, загруженных
без маркеров (списки, фильтры — `withoutMarkersAndText = true`), число голосов
**неизвестно**, и это отдаётся как `null`. Раньше геттер `sourceMarkers` для
незагруженного поля возвращал заглушку `"[[]]"`, откуда `countVoices == 1` у всех
песен списка: фильтр «Количество голосов» показывал всё при значении `1` и пусто
при `2+`. Реальный счётчик — `Song.countVoicesLoaded` (`null` — маркеры не загружены).

### Алгоритм парсинга `sourceMarkers`

`Song.sourceMarkers` — строка в формате `[mm:ss.xx]text`. Парсер:

1. Поиск всех пар `[time]text` через regex.
2. `time` парсится в миллисекунды (`mm * 60_000 + ss * 1000 + xx*10`).
3. Несколько маркеров в одной строке разделяются `\n` или `;`.
4. Невалидный формат → строка логируется, но не валит парсинг
  (используются только валидные маркеры).

### Алгоритм проверки эфирности

```kotlin
fun Song.isContentReady(): Boolean =
    idStatus == 6 && publishDate?.isBefore(Instant.now()) == true
```

Проверка вызывается на каждом публичном запросе; для производительности

### Вердикты классов артефактов (`ArtifactCleanupClass`, specs/544)

`ArtifactCleanupClass` (`karaoke-app/.../services/cleanup/ArtifactCleanupClass.kt`) —
реестр классов файлов песни: единственное место правды о том, что с каким артефактом
делаем. Им пользуются и автоматическая уборка на шагах жизненного цикла, и разовая
чистка истории (`/api/cleanup`).

| Вердикт | Смысл |
| --- | --- |
| `PROTECTED` | Не удаляется ничем и никогда (исходный flac, flac-стемы). |
| `KEEP` | Остаётся как есть — у артефакта есть читатель. |
| `STOP_CREATING` | Код перестал создавать артефакт. |
| `DELETE_AFTER_STAGE` | Удаляется на шаге жизненного цикла (например, в конце публикации). |
| `DELETE_EXISTING` | Удаляется разовой чисткой истории. |
| `NOT_TOUCH` | Есть читатель — руками не трогать. |

Порядок чистки (`cleanupOrder` 1..7) идёт от крупных низкорисковых классов к мелким:
демо-ролики → локальные mp3-стемы → публикационные картинки → проекты рендера →
sidecar-состояние → субтитры → гигиена.

**Вне модели `KaraokeFileType`.** Файлы `.song`/`.settings` (сериализованное состояние
песни), `.srt`/`.srt.backup`, `.mlt`/`.kdenlive`/`.run` в `KaraokeFileType` НЕ входят,
поэтому проверка здоровья их не аудирует. Состояние песни в них больше не пишется:
источник истины — БД (`Song.saveToDb`), а разметка голосов выгружается по запросу
функцией `Song.convertMarkersToSrt` (specs/544, FR-006/FR-008).

Значения вердиктов в БД и API не хранятся (схема БД не меняется) — это код.

### `sort_order` автора — порядок плашек на публичной странице (BR-541, аудит #336)

Магический код в `tbl_authors.sort_order` (`INTEGER NOT NULL DEFAULT 0`) задаёт
порядок плашек авторов на `/zakroma`:

| Значение | Смысл |
|---|---|
| `0` | алфавитный порядок по имени автора (поведение по умолчанию) |
| `≠ 0` | принудительный порядок **выше** нулевых: по возрастанию `sort_order`, затем по алфавиту |
| отрицательное | допустимо, идёт раньше нуля |

Спец-авторы (плашка «Отдельные песни разных авторов») показываются **первой** в
сетке — за это отвечает отдельный флаг `is_special_order`, а не `sort_order`.
Инвариант sync: `sort_order` обязан входить в канонический набор колонок
`deploy/recordhash_authors.sql` — до аудита #336 (BR-541) файл отставал от схемы
на семь колонок, и применение «канонического» файла откатывало формулу
(см. [persistence/domain.md](../../persistence/domain.md)).

### Формат даты и времени публикации (BR-191, аудит #336, пакет `PKG-S3-24`)

Инвариант: `publish_date` — строгий формат `dd.MM.yy`, `publish_time` —
`HH:MM`. Проверка выполняется в двух местах:

1. **На записи** — `Publication.validatePublishDateTime(date, time)`
   вызывается из `MainController.songsUpdate` / `songs2Update`; неверный
   формат отклоняется с `400` и понятным текстом.
2. **На чтении** — `Publication.parsePublishDate()` (регулярка + строгий
   разбор, `isLenient = false`): `31.02.26` — несуществующая дата и
   разбираться не должна. Песня с неразбираемой датой пропускается в
   сетке публикаций с предупреждением в журнал — страница публикаций
   больше не падает целиком из-за одного плохого значения.

Идентификатор строки сетки вычисляется через
`Publication.publicationIdFromDate()` (раньше — `split(".")[2]` без
проверки длины).

**[WARN]** Слот сетки публикаций — одна песня на `(publish_date,
publish_time)`. Конфликт (две песни на один слот) не затирает первую
песню молча: в журнал пишется предупреждение с id обеих песен. Ограничение
на уровне БД (частичный UNIQUE-индекс) не создано — нужна миграция и
дедупликация (за владельцем).


## 674: артефакты key/bpm и кортеж

Правки `model/Song.kt` (кортежное исполнение, `scopeId`) сопровождаются проверкой key/bpm по
sidecar-отпечатку источника: `<file> [key].json.meta` (размер, длительность, хеш первых/последних
64 КиБ). См. `knowledge/domains/processing/components/key-bpm-from-file.md`.
