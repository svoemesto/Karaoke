# Runbook: постоянный туннель к проду (WireGuard) — эксплуатация и диагностика

> Спека 733 (KARAOKE-407). Туннель между админской машиной `nsa-i9` и прод-хостом
> `188.127.240.124`. Туннелем владеет приложение `karaoke-app`.
> Per-feature: `knowledge/product/features/prod-tunnel.md`; ADR:
> `knowledge/adr/local-0018-prod-wireguard-tunnel.md`.

## 1. Что где

| Что | Где |
|---|---|
| Интерфейс `wg0` (админская сторона) | сетевое пространство контейнера `karaoke-app` |
| Ключ админского пира | `/etc/karaoke/tunnel/tunnel.key` на хосте (600) → `/run/karaoke/tunnel/` в контейнере (ro) |
| Пир «prod» | `/etc/wireguard/wg0.conf` на прод-хосте (600), `wg-quick up wg0` |
| Постоянный внутренний адрес прода | `10.77.0.2` (БД `5433`, MinIO `9000`, HTTPS `443`) |
| Адрес, который видит прод | `10.77.0.1` (единственная строка `allow` в конфигурации прода) |
| Маршрут хоста в подсеть туннеля | `deploy/prod-tunnel/karaoke-tunnel-host-route.service` |
| Скрипты и шаблоны | `deploy/prod-tunnel/` |
| Коды событий | `knowledge/guidelines/runbooks/log-correlation.md` § 1a (`TUNNEL-001…007`, `DB-CERT-001`) |

## 2. Диагностика по шагам

### 2.1 Туннель поднят?

```bash
docker exec karaoke-app wg show
docker exec karaoke-app wg show wg0 latest-handshakes
```

* `latest-handshakes` — непустая эпоха (секунды с 1970) → рукопожатие было;
* значение старше `PROD_TUNNEL_HANDSHAKE_TIMEOUT` (по умолчанию 180 с) →
  туннель «устарел», приложение пересоздаст его (событие `TUNNEL-003`);
* `0` или пусто → рукопожатия нет (событие `TUNNEL-002`).

### 2.2 Что говорит приложение

```bash
docker logs karaoke-app --since 30m 2>&1 | grep -E "TUNNEL-|DB-CERT-"
```

| Код | Смысл | Что делать |
|---|---|---|
| `TUNNEL-001` | туннель поднят | — |
| `TUNNEL-002` | туннель не поднят (`reason=`) | см. таблицу причин ниже |
| `TUNNEL-003` | устаревшее рукопожатие, идёт перезапуск | проверить WAN (п. 2.3) |
| `TUNNEL-004` | туннель восстановлен | — |
| `TUNNEL-005` | туннель выключен конфигурацией | канал идёт по публичному пути |
| `TUNNEL-006` | конфигурация не прошла валидацию (`rule=`) | исправить конфигурацию |
| `TUNNEL-007` | туннель недоступен, канал ушёл в fallback | `fallback=public` — доступен прежний путь; `disabled` — канал закрыт намеренно |
| `DB-CERT-001` | сервер БД отклонил клиентский сертификат (`certReason=`) | см. п. 4 |

Причины `TUNNEL-002`:

| `reason` | Значение | Что делать |
|---|---|---|
| `no_permission` | нет `NET_ADMIN`/`/dev/net/tun` | проверить `deploy/docker-compose-app.yml` и пересоздать контейнер (Pass 380) |
| `no_key` | не смонтирован каталог с ключом | `ls -l /etc/karaoke/tunnel` на хосте; монтирование `:ro` в compose |
| `config_invalid` | конфигурация не прошла валидацию | `TUNNEL-006` рядом в логе — там указано правило |
| `udp_blocked` | нет маршрута/таймаут до `188.127.240.124:51820` | проверить, не режет ли провайдер UDP |
| `command_failed` | прочие ошибки `ip`/`wg` | посмотреть сообщение команды в логе |

### 2.3 Туннель есть, а канала нет (или наоборот)

```bash
ping -c1 -W2 10.0.1.1        # LAN-шлюз
ping -c1 -W2 1.1.1.1         # интернет
ping -c1 -W2 188.127.240.124 # прод-хост
```

| Наблюдение | Вывод |
|---|---|
| LAN ОК, интернет и прод НЕ ОК | **пропал WAN на машине** (обрыв шлюза `10.0.1.1`, runbook § 1d). Туннель это НЕ лечит (FR-034) |
| Всё ОК, рукопожатия нет | UDP-путь закрыт провайдером или на проде не поднят `wg0` |
| Рукопожатие есть, `ping 10.77.0.2` не отвечает | на проде не поднят `wg0` либо allow-list прода не содержит `10.77.0.1` |

### 2.4 Прод-канал недоступен — что именно сломано

| Что | Код |
|---|---|
| туннель | `TUNNEL-002`/`TUNNEL-003`/`TUNNEL-006`/`TUNNEL-007` |
| сертификат | `DB-CERT-001` |
| БД (не туннель и не сертификат) | `DB-CONNECT-001` / `DB-UNAVAILABLE-002` |
| сайт | `MON-CHECK-001` с `check=ProdContainerCheck` |

В мониторинге состояние туннеля — отдельный признак (`prod.tunnel`), а проверка
прод-канала при упавшем туннеле пишет «Канал к проду недоступен (туннель не
поднят)», а не «Прод-сервер недоступен» — так ложный CRITICAL при живом проде не
возникает.

## 3. Операционные сценарии

### 3.1 Оператор подключается к прод-БД с админской машины (DBeaver)

```text
host: 10.77.0.2      port: 5433      dbname: karaoke
user: SvoeMestoKaraokeUser905        password: как в deploy/.env прод-хоста
SSL: verify-full
client certificate: /etc/karaoke/tunnel/db-client.crt
client key (PKCS-8 DER): /etc/karaoke/tunnel/db-client.key
root CA: /etc/karaoke/tunnel/ca.crt
```

Каталог `/etc/karaoke/tunnel` — `700 root`, поэтому читать его может только
root. Для рабочего места оператора сертификат и ключ копируются в личный
каталог с правами `600` (ключ) — например `~/.config/karaoke/tunnel/`.

Маршрут на хосте и SNAT в контейнере держит юнит
`karaoke-tunnel-host-route.service` + таймер (проверка раз в минуту): маршрут
`10.77.0.0/24` через IP контейнера и SNAT `-o wg0 → 10.77.0.1`. Таймер нужен
потому, что пересоздание контейнера меняет его IP и сбрасывает `iptables`
внутри. Состояние и ручной запуск:

```bash
bash deploy/prod-tunnel/host-route.sh --check     # маршрут и SNAT
sudo /usr/local/sbin/karaoke-tunnel-host-route.sh --apply
```

**Если маршрут есть, а связи нет** — почти всегда отсутствует SNAT: пакеты
доходят до контейнера, уходят в туннель с адресом docker-шлюза (`172.18.0.1`)
и молча отбрасываются на проде, потому что пир принимает только `10.77.0.1`
(`AllowedIPs`). Признак: `ping 10.77.0.2` не проходит, `wg show` в контейнере
показывает свежее рукопожатие.

### 3.2 Включение kill-switch публикации через туннель

```bash
# С админской машины; трафик идёт внутри туннеля (имя хоста прежнее).
curl -sS -X POST https://sm-karaoke.ru/api/properties/setproperty \
  -H "X-Internal-Secret: $INTERNAL_SECRET" \
  -H 'Content-Type: application/json' \
  -d '{"key":"<ключ настройки>","value":"<значение>"}'
```

Если туннель не поднят, вызов не пройдёт — причина будет видна в логе приложения
(`TUNNEL-002`/`TUNNEL-007`), а не как «403 от сервера».

### 3.3 Продление клиентского сертификата (FR-014) — автоматическое

Срок действия клиентского сертификата — 90 дней (решение владельца 2026-11-09:
срок подходит, продление автоматическое). Продление делает юнит
`karaoke-tunnel-cert-renew.timer` (ежедневно, 04:17 ± 10 мин): скрипт
`/usr/local/sbin/karaoke-tunnel-renew-cert.sh --apply` продлевает сертификат,
когда до истечения остаётся **21 день** или меньше.

Как устроено:

* новый приватный ключ генерируется **на админской машине** и её не покидает;
* на прод-хост уходит только CSR, возвращается подписанный сертификат — ключ CA
  с прода не снимается никогда;
* подпись проверяется по `ca.crt` до установки (битый ответ прода не заменит
  рабочий сертификат);
* ключ хранится в двух видах: `db-client.key.pem` (канон, для продления) и
  `db-client.key` (PKCS-8 DER — в этом виде его читает драйвер `pgjdbc`);
* предыдущие файлы остаются как `*.prev` — откат одной командой.

Проверка и ручной запуск:

```bash
/usr/local/sbin/karaoke-tunnel-renew-cert.sh --check    # сколько дней осталось
/usr/local/sbin/karaoke-tunnel-renew-cert.sh --apply    # продлить, если пора
systemctl list-timers karaoke-tunnel-cert-renew.timer
journalctl -u karaoke-tunnel-cert-renew.service -n 20
```

Приложение подхватывает новый сертификат на новых соединениях; перезапуск не
обязателен. Если нужен немедленный переход — Pass 380 (очередь → стоп → дренаж →
старт → старт очереди), задания не теряются.

Откат после неудачного продления:

```bash
cd /etc/karaoke/tunnel && mv db-client.crt.prev db-client.crt \
  && mv db-client.key.prev db-client.key && mv db-client.key.pem.prev db-client.key.pem
```

Если сертификат всё же просрочен — приложение пишет `DB-CERT-001` с
`certReason=expired`; задания возвращаются в очередь (канальный отказ), а не
падают.

Служебный доступ для продления — отдельный ключ `/root/.ssh/id_ed25519_karaoke_tunnel`
(публичная часть добавлена в `authorized_keys` на прод-хосте). Доступен только
root админской машины; ключ пользователя `nsa` для автомата не используется.

### 3.4 Переключение каналов на туннель и откат

Порядок (менять местами нельзя — потеряется доступ):

1. Поднять пир на проде, проверить рукопожатие.
2. Заменить в allow-list прод-хоста публичный адрес на `10.77.0.1`
   (во всех трёх местах), с бэкапом и `nginx -t`.
3. Переключить конфигурацию приложения: `DB_REMOTE_HOST=10.77.0.2`,
   `STORAGE_REMOTE_ENDPOINT=http://10.77.0.2:9000`, `PROD_TUNNEL_ENABLED=true`.
4. Перезапустить `karaoke-app` по Pass 380.
5. Проверить: БД, MinIO, синхронизация, kill-switch, DBeaver с хоста.
6. Только после этого — закрыть публичные порты `5433`/`9000` (FR-018).

Откат (процедура спеки): вернуть публичные значения в конфигурации приложения,
перезапустить контейнер по Pass 380, открыть порты, вернуть allow-list из
бэкапа. Ориентир — не дольше 15 минут (SC-006).

**Решение владельца (2026-11-12): эта процедура НЕ используется — публичным
откатом не пользуемся.** Канал к продук восстанавливается **только туннелем**:

* БД всегда идёт на `DB_REMOTE_HOST=10.77.0.2` — адрес собирает функция
  `connectionRemoteUrl()`
  (`karaoke-app/src/main/kotlin/com/svoemesto/karaokeapp/Connection.kt`);
  публичный адрес в конфигурацию не возвращается;
* HTTP-откат (снятие переопределения имени хоста) упирается в allow-list:
  публичного IP админской машины в списке нет, поэтому «откат на публичный
  путь» не заработает;
* **второй адрес в allow-list не держим** — это вернуло бы зависимость от
  плавающего IP провайдера, ровно та зависимость, из-за которой канал уже
  обрывался (спека 733 § Контекст: 2026-11-08, «сменился айпишник, и снова на
  это не отреагировало приложение правильно»).

Практический итог: восстановление канала — **починить туннель**, а не вернуть
публичный путь; задание, застигнутое обрывом, возвращается в очередь и
завершается повторной попыткой (FR-033), а обрыв WAN прерывает канал — и
обходного публичного пути для этого нет (FR-034).

### 3.5 Установка mTLS к БД на прод-хосте (однократно)

Вариант C спеки 733: доступ к прод-БД подтверждается клиентским сертификатом,
а не только адресом. Порядок (менять местами нельзя — потеряется доступ к БД):

1. Выпустить собственный CA и два сертификата (на прод-хосте, ключи наружу не
   уходят): сертификат сервера БД (SAN: `DNS:sm-karaoke.ru`, `IP:10.77.0.2`) и
   клиентский сертификат админ-машины (CN = `nsa-i9`, срок 90 дней).
2. Положить на прод-хосте в `deploy/certs/postgres/` (каталог прокинут в контейнер
   read-only): `ca.crt`, `server.crt`, `server.key` (ключ `600`).
3. Включить TLS в PostgreSQL: `DB_SSL_ON=on` в `.env` прод-хоста. В контейнере
   Postgres дополнительно нужен `ssl_ca_file` (`DB_SSL_CA_FILE`, по умолчанию
   `/certs/postgres/ca.crt`) — без него Postgres не может проверить клиентский
   сертификат по правилу `clientcert=verify-ca`.
4. Добавить правило в `pg_hba.conf` (файл в `PGDATA`, каталог данных БД):
   `hostssl karaoke SvoeMestoKaraokeUser905 172.18.0.1/32 scram-sha-256 clientcert=verify-ca`.
   Правило с паролем остаётся запасным путём (FR-015).

   **Адрес в правиле — `172.18.0.1`, а не `10.77.0.1` и не `127.0.0.1`.**
   Причина: канал приходит из туннеля в nginx (`:5433`), nginx проксирует на
   `127.0.0.1:8832` (docker-proxy), и только потом в контейнер БД; внутри
   контейнера источником виден **docker-шлюз `172.18.0.1`**. Правило на
   `10.77.0.1` не сработает никогда, правило на `127.0.0.1` — тоже (оно
   относится только к прямым локальным соединениям). Проверять фактический
   источник: `select client_addr from pg_stat_activity`.
5. Перезапустить `karaoke-db` (кратковременная недоступность БД — сайт переживает:
   правила для локальных подключений `trust`/`scram-sha-256` не меняются).
   Перечитывания конфигурации (`pg_reload_conf()`) достаточно для `pg_hba.conf`,
   но параметры `ssl*` применяются только перезапуском.
6. Доставить клиентский сертификат и ключ на админскую машину в
   `/etc/karaoke/tunnel` (`db-client.crt` `644`, `db-client.key` `600`, `ca.crt` `644`).

   **Ключ обязан быть в формате PKCS-8 DER (двоичный), не PEM.** Драйвер
   `pgjdbc` (в отличие от `libpq`/`psql`) читает `sslkey` только как PKCS-8 DER;
   на PEM-ключ он отвечает `Could not read SSL key file`. Конвертация:

   ```bash
   openssl pkcs8 -topk8 -inform PEM -outform DER -in db-client.key.pem -nocrypt -out db-client.key
   ```
7. Включить проверку на клиенте: `DB_REMOTE_SSL_MODE=verify-full`,
   `DB_REMOTE_SSL_CERT=/run/karaoke/tunnel/db-client.crt`,
   `DB_REMOTE_SSL_KEY=/run/karaoke/tunnel/db-client.key`,
   `DB_REMOTE_SSL_ROOT_CERT=/run/karaoke/tunnel/ca.crt`; перезапустить
   `karaoke-app` по Pass 380.
8. Проверить: приложение работает (`DB-CONNECT-001` = 0), а соединение **без**
   клиентского сертификата отклоняется — сервер отвечает
   `FATAL: connection requires a valid client certificate` (проверка из
   контейнера через туннель, см. п. 5 «Проверки»).

Откат: `DB_SSL_ON=off` + перезапуск `karaoke-db`, удаление правила `hostssl` из
`pg_hba.conf`, `DB_REMOTE_SSL_MODE=prefer` + перезапуск `karaoke-app`.

### 3.6 Автоматика allow-list в режиме туннеля: что проверяется

В режиме туннеля (`ALLOWLIST_MODE=tunnel`) автоматика на прод **ничего не
пишет**: публичный адрес админской машины в allow-list не попадает никогда.
Вместо этого выполняется read-only проверка — в каждом блоке с `deny all;`
должен стоять **ровно один** адрес, постоянный внутренний адрес туннеля
`10.77.0.1`. Расхождение — не «автоматический ремонт», а сигнал владельцу:
появление публичного адреса в списке означало бы возврат зависимости от IP
провайдера (§ 3.4).

Журнал: `/var/log/admin-ip-allowlist.log` (по умолчанию `ALLOWLIST_LOG_FILE`).
События режима туннеля: `event=tunnel status=ok|mismatch|unreachable`, при
расхождении — `event=decision reason=tunnel_address_mismatch action=skip`.

**Уведомления не используются.** Решение владельца (2026-11-12): **Telegram-токен
не выдаём** — сигналом о расхождении служит код выхода юнита (§ 3.7).

Что это значит технически: без токена скрипт пишет **только в журнал**:

```text
event:notify channel=none ok=false reason=token_absent
```

То есть в `/etc/admin-ip-allowlist.env` на хосте `ALLOWLIST_TELEGRAM_BOT_TOKEN`
не задаётся, и уведомлений не будет — наблюдение ведётся по журналу и по
состоянию юнита. Справочно: чат уведомлений брался бы из
`ALLOWLIST_NOTIFY_CHAT_ID` (не из `ALLOWLIST_TELEGRAM_CHAT_ID` — канал проекта
для служебных уведомлений не используется), прокси для вызова Bot API —
`ALLOWLIST_TELEGRAM_PROXY` (на хосте `socks5h://127.0.0.1:1080`, xray); токен и
адрес прокси не попадали бы ни в `argv`, ни в журнал — `curl` читает их из
конфиг-файла с правами `600`, который удаляется сразу после вызова.

### 3.7 Как заметить расхождение allow-list без Telegram-уведомлений

Сигнал — **ненулевой код выхода юнита**: systemd помечает
`admin-ip-allowlist.service` как `failed`, и это видно без Telegram.

Механика уже работает: в режиме туннеля скрипт возвращает `EXIT_DECLINED=3`
при расхождении, а `main` пробрасывает код выхода (`run_tunnel_check; return
$?`). Реальный случай 2026-11-12 13:16 MSK в журнале:

```text
event:decision reason=tunnel_address_mismatch action=skip files=2 mismatch=2
admin-ip-allowlist.service: Main process exited, code=exited, status=3/NOTIMPLEMENTED
Failed with result 'exit-code'
```

Коды выхода:

| Код | Что означает |
|---|---|
| `0` | расхождения нет (`event:tunnel status=ok`) |
| `3` | расхождение: в allow-list прод-хоста не ровно один адрес `10.77.0.1` |
| `1` | прод-хост недоступен — проверку выполнить не удалось (`event:tunnel status=unreachable`) |

Как увидеть:

```bash
systemctl --failed                                   # юнит в списке failed
systemctl status admin-ip-allowlist.service --no-pager
journalctl -u admin-ip-allowlist.service --since "1 hour ago"
tail -n 50 /var/log/admin-ip-allowlist.log
```

В списке `systemctl --failed` бывают **посторонние** failed-юниты — на хосте
замечены `casper-md5check.service` и `NetworkManager-wait-online.service`.
Смотреть надо **конкретно** `admin-ip-allowlist.service`, а не «есть ли вообще
что-то failed».

События в журнале: `event:tunnel status=mismatch` (файлы с расхождением) и
`event:decision reason=tunnel_address_mismatch action=skip` (правка не
применялась — автоматика в режиме туннеля ничего не пишет).

Проверка кода выхода (выполнена 2026-11-12; в режиме туннеля проверка
read-only — конфигурация прод-хоста не меняется):

```bash
# свой журнал и состояние — боевые файлы не трогаются
ALLOWLIST_MODE=tunnel ALLOWLIST_TUNNEL_ADDR=10.77.0.99 \
ALLOWLIST_LOG_FILE=/tmp/allowlist-check.log \
ALLOWLIST_STATE_FILE=/tmp/allowlist-check.state \
  bash deploy/admin-ip-allowlist.sh ; echo "rc=$?"   # rc=3 — расхождение (status=mismatch x2)

ALLOWLIST_MODE=tunnel ALLOWLIST_TUNNEL_ADDR=10.77.0.1 \
ALLOWLIST_LOG_FILE=/tmp/allowlist-check.log \
ALLOWLIST_STATE_FILE=/tmp/allowlist-check.state \
  bash deploy/admin-ip-allowlist.sh ; echo "rc=$?"   # rc=0 — расхождения нет (status=ok)
```

### 3.8 Обновление юнита на хосте (root)

Юнит лежит в репозитории (`deploy/admin-ip-allowlist.service`), на хосте
админской машины — `/etc/systemd/system/admin-ip-allowlist.service`. После
правки `Description` владелец обновляет юнит на хосте:

```bash
sudo cp deploy/admin-ip-allowlist.service /etc/systemd/system/admin-ip-allowlist.service
sudo systemctl daemon-reload
systemctl status admin-ip-allowlist.service --no-pager
```

**ExecStart после копирования возвращают к хостовому.** Репозиторный юнит
указывает `ExecStart=/home/nsa/Karaoke/deploy/admin-ip-allowlist.sh` — путь в
рабочем дереве, где есть незакоммиченные правки; на хосте юнит запускает
установленный экземпляр `/usr/local/sbin/admin-ip-allowlist.sh`. Поэтому
после копирования строку ExecStart возвращают к хостовой:

```bash
sudo sed -i 's#^ExecStart=.*#ExecStart=/usr/local/sbin/admin-ip-allowlist.sh#' \
  /etc/systemd/system/admin-ip-allowlist.service
sudo systemctl daemon-reload
```

Обновлённый `Description` виден в `systemctl --failed` прямо в списке:
«Karaoke: проверка allow-list прод-канала (расхождение → юнит в failed)» —
по нему юнит опознаётся без чтения самого файла.

## 4. Секреты

* Приватные ключи и сертификаты — только в `/etc/karaoke/tunnel` (каталог `700`,
  файлы `600`) на хосте; в контейнер монтируются read-only.
* В репозитории — только шаблоны с плейсхолдерами (`deploy/prod-tunnel/*.template`).
* Приватный ключ приложением **не читается**: его получает `wg` по пути файла
  (`wg set wg0 private-key <путь>`), поэтому ключ не попадает ни в лог, ни в `argv`.
* CA и корневой сертификат — вне репозитория (FR-013).

## 6. Ловушки выкладки конфигурации и доступа (факты 2026-11-12)

Четыре факта, добытых при переводе прод-каналов на туннель. Каждый стоил
простоя или тихой поломки, поэтому вынесены отдельно.

### 6.1 `reload` nginx не меняет listen-адрес — нужен полный рестарт

Смена `listen` на внутренний адрес туннеля (`10.77.0.2:5433`) — не изменение
поведения, а **смена адреса, на котором слушает сокет**. При
`systemctl reload nginx` (SIGHUP) новый master наследует listen-сокеты старого,
и рабочие новой конфигурации пытаются занять адрес заново:

```text
bind() to 10.77.0.2:5433 failed (98: Address already in use)
```

Адрес уже занят сокетом старого master'а (тот держит сокет на всём
интерфейсе). Практический итог: **откатывается весь reload** — включая
правку allow-list, которая ехала в том же конфиге. Конфиг на диске при этом
новый, а в работе старый: расхождение выглядит как «правка не применилась»,
хотя файл правильный.

Правило: **смена listen-адреса требует полного рестарта nginx**
(`systemctl restart nginx`), а не `reload`. Прочие правки (заголовки,
маршруты, allow-list) после рестарта доставляются обычным `reload` — он
работает, пока адреса не меняются.

`nginx -t` перед рестартом обязателен, но занятый адрес он не ловит: это
состояние сокета, а не синтаксис.

### 6.2 Бэкапы конфигурации не должны лежать в `sites-enabled`

`sites-enabled/*` подключается **include'ом** из `nginx.conf`:

```nginx
include /etc/nginx/sites-enabled/*;
```

Значит, бэкап конфига, оставленный рядом с рабочим файлом, **тоже попадает в
конфигурацию**. На проде это дало 6 «conflicting server name» — одинаковый
`server_name` в рабочем файле и в его копиях. Второе, менее заметное
последствие: бэкап старого allow-list, подхваченный include'ом, способен
вернуть в правила адрес, которого там быть не должно.

Правило: **бэкапы конфигурации — вне `sites-enabled`** (например,
`/etc/nginx/backups/`), а не «рядом с оригиналом». Проверка перед рестартом:

```bash
ls -1 /etc/nginx/sites-enabled/                 # только рабочие файлы
grep -rn "server_name" /etc/nginx/sites-enabled/ # один ответ на один файл
```

### 6.3 Drop-in `nginx.service`: `Wants` + `After`, а не `Requires`

Публичный сайт на проде не должен зависеть от туннеля: туннель поднимает
приложение, и его остановка (пересоздание контейнера, обрыв WAN) не должна
ронять сайт. Поэтому drop-in юнита nginx задаёт **мягкую** зависимость:

```ini
[Unit]
Wants=wg-quick@wg0.service
After=wg-quick@wg0.service
```

`Wants` — «начать, если ещё не начат», `After` — «после подъёма туннеля».
`Requires=` здесь недопустим: остановка туннеля уронила бы и публичный сайт.

Тонкость: в `Wants=` и `After=` имя юнита пишется **с суффиксом `.service`**.
Вариант без суффикса systemd не принимает:

```text
Failed to add dependency on wg-quick@wg0, ignoring: Invalid argument
```

Сообщение выглядит как «предупреждение, и так сойдёт», но зависимость при
этом не создаётся — порядок загрузки не гарантирован.

Drop-in кладётся в `/etc/systemd/system/nginx.service.d/`, после правки —
`systemctl daemon-reload`.

### 6.4 Переопределение резолвинга на админской машине: `/etc/hosts`

Когда прод переведён на туннель, публичный путь к `sm-karaoke.ru` закрыт:
allow-list разрешает **только** источник `10.77.0.1`, поэтому браузер и
операторские инструменты (curl, DBeaver) с админской машины получают `403`.
Чтобы те же инструменты ходили к прод-каналу через туннель, на **хосте
админской машины** нужна строка резолвинга:

```bash
# /etc/hosts на хосте админской машины
sudo sh -c 'echo "10.77.0.2 sm-karaoke.ru" >> /etc/hosts'
```

**Выполнено владельцем 2026-11-12 13:47.** Проверено после применения:

| Проверка | Результат |
|---|---|
| `getent hosts sm-karaoke.ru` | `10.77.0.2` |
| `POST /changerecords`, `POST /api/properties/setproperty` с хоста | `405` — было `403`: allow-list пускает, дальше отвечает метод (не POST) |
| `/` и `/api/public/songs` с хоста | `200` |
| `10.77.0.2:5433` и `10.77.0.2:9000` с хоста | `OK` — путь оператора (DBeaver, MinIO) |

Имя хоста и TLS-сертификат сервера при этом прежние — SNI и заголовок `Host`
не меняются, проверка сертификата остаётся включённой. Трафик с хоста идёт
по маршруту в туннель (§ 3.1) и приходит на прод с адресом источника
`10.77.0.1`. Внутри контейнера приложения ту же строку пишет само
приложение (FR-021/FR-022, класс `HostsOverride`); на хосте это делается
руками.

Оговорка: **при упавшем туннеле хост не достучится до `sm-karaoke.ru`** —
строка в `/etc/hosts` остаётся, а канала нет. Запасной путь по умолчанию
есть только внутри контейнера приложения (там переопределение имени хоста
снимается, и канал уходит по публичному пути). На хосте такого запасного
пути нет: при упавшем туннеле доступ к `sm-karaoke.ru` с админской машины
пропадает до восстановления туннеля. И даже внутри контейнера публичный путь
сейчас закрыт (публичного IP админской машины в allow-list нет, § 3.4), то
есть работающего запасного пути нет нигде: восстановление — это починить
туннель.
