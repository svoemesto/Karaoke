# Feature Specification: Идемпотентная санитиризация путей и имён файлов и папок

**Feature Branch**: `304-idempotent-path-sanitize`

**Created**: 2026-09-04

**Status**: Draft

**Input**: User description (OpenProject issue #53): «Если в имени папки альбома есть восклицательный знак, то при импорте из папки и при дальнейших действиях проблемы — восклицательный знак экранируется/удаляется при санитаризации пути и файлы не находятся. Возможно такое же поведение и при каких-то других символах. Задача — реализовать полностью идемпотентный алгоритм санитиризации путей и имён файлов и папок в проекте.»

## Контекст и корневая причина (pre-implementation analysis)

В проекте Karaoke санитиризация имён файлов и путей реализована тремя расширениями
в `karaoke-app/src/main/kotlin/com/svoemesto/karaokeapp/Extentions.kt`:

1. `String.rightFileNameSymbols()` — поэлементная подстановка «проблемных» символов:
   `'` → `` ` ``, `?` → удаление, `:` → `-`, `!` → удаление, `$` → `s`, `*` → `x`.
   Применяется и к «голым» именам, и к полным путям (24+ вызывающих мест
   в `StemJobProcessing.kt`, `KaraokeProcess.kt`, `KaraokeProcessWorker.kt`,
   `model/Song.kt`, `controllers/SongEditorController.kt`, `controllers/ApiController.kt`).
2. `String.sanitizeSongFileName()` — надстройка над `rightFileNameSymbols()`,
   дополнительно убирает `/`, `\` и `"`. Применяется только к «голому» фрагменту
   имени файла песни при импорте (`Song.createFromPath`) и в SongEdit
   (`SongUpdateMapper`, `ApiController.songs2Update`).
3. `String.rightFileName()` — обёртка над `rightFileNameSymbols()`, алиас.

### Выявленные дефекты текущей реализации

1. **Неидемпотентность по «восклицательному знаку» (история из issue #53).**
   Алгоритм удаляет `!` без замены. Если папка альбома содержит `!` в имени
   (например, `2012 - Лучшее!`), то:
   - При первом проходе импорта имя папки превращается в `2012 - Лучшее` —
     физическая папка не находится.
   - Если папка уже была однажды обработана и потеряла `!`, повторный
     импорт/перескан работает корректно. То есть **первый проход теряет данные,
     второй проход «работает»** — классический признак неидемпотентного
     преобразования «с потерями».
   - Симметричный баг — символ `?`, который тоже удаляется без замены.

2. **Неявная неидемпотентность при коллизиях.**
   Если в одной папке импорта лежат два файла, имена которых после санитайзинга
   совпадают (например, `Track 1!.mp3` и `Track 1.mp3`), то один из них
   получает числовой суффикс (`Track 1 (2)`). Это **нарушает** идемпотентность:
   повторный прогон санитайзинга даст другое имя для второго файла, что ломает
   кэши, lookup по `rootFolder + fileName` и любые «дедуплицирующие» механизмы.

3. **Неполный список «проблемных» символов.**
   Помимо `!`/`?` (удаление без замены), в текущей реализации не покрыты:
   - Управляющие символы (`\n`, `\r`, `\t`, `\0`).
   - Кавычки (`"`, `'`, `` ` ``) — `'` уже подменяется на `` ` ``, но `` ` ``
     остаётся как есть; для shell-команд `` ` `` сам по себе проблемен.
   - Символы перенаправления shell (`<`, `>`, `|`, `&`, `;`, `(`, `)`).
     Скобки `(`/`)` используются в шаблоне имени и не должны удаляться полностью,
     но в составе shell-команд (а `rightFileName()` используется и для путей
     в shell-командах в `KaraokeProcess.kt` — `listOf("mv", ..., ...rightFileName())`)
     они интерпретируются. Сейчас единственная защита — оборачивание
     в `wrapInQuotes()`; для надёжности надо дополнительно экранировать/заменять
     эти символы при первом проходе.
   - Unicode private use area и непечатные символы (BOM, ZWSP).

4. **Применение `rightFileName()` к «уже санитайзенным» строкам.**
   В `Song.kt` (`pathToFolder720Lyrics` и подобных) `rightFileName()` вызывается
   на `$author 720p`, где `$author` уже мог быть санитайзен ранее.
   Если `$` в авторе → `s`, то `rightFileName()` на строке вида `Queen $ 720p`
   даст `Queen s 720p` (первый проход). Второй проход — `Queen s 720p` —
   идемпотентен. Но если в `$author` есть `` ` `` (из замены `'`),
   то при `wrapInQuotes()` (вызываемом после `rightFileName()` в `KaraokeProcess.kt`)
   эта `` ` `` может быть потеряна либо сломать shell-quoting.

### Требование идемпотентности (формулировка)

Алгоритм санитиризации `sanitize` называется **идемпотентным** для множества
входных строк `S`, если для **любого** `s ∈ S`:

```
sanitize(sanitize(s)) == sanitize(s)
```

То есть повторное применение не должно изменять уже-санитайзенную строку.
Это свойство позволяет безопасно вызывать санитайзер в любом месте пайплайна
(включая повторные проходы, кросс-валидации, миграции) и не бояться
дополнительной потери данных.

## Clarifications

### Session 2026-09-04

- Q: Какой объём изменений — только исправление `!`/`?` или полный рефакторинг всех трёх функций? → A: **Полный рефакторинг в единый идемпотентный `SanitizePath`/`SanitizeFileName`** с явным контрактом. Это покрывает не только текущий баг, но и предотвращает аналогичные баги для других символов в будущем. Существующие `rightFileNameSymbols`/`sanitizeSongFileName`/`rightFileName` остаются как тонкие алиасы-обёртки (для обратной совместимости с 200+ вызывающих мест) над единым внутренним ядром.
- Q: Подход к замене «удаляемых» символов (`!`, `?`, `\n`, `\r` и т.п.) — drop, replace-with-space, replace-with-`_`? → A: **Заменить на `_`** (нижнее подчёркивание). Это сохраняет визуальную плотность имени (в отличие от drop, который сжимает соседние слова), и `_` безопасен во всех контекстах (файловые системы, shell, URL). Замена на пробел ломает парсинг шаблона имени файла «Порядковый (Номер) [Автор] - Название», где пробел разделяет компоненты.
- Q: Что делать с символами, которые уже подменяются (`'` → `` ` ``, `$` → `s`)? → A: **Сохранить текущее поведение как legacy-mapping** (для обратной совместимости с уже санитайзенными путями на проде, см. specs/124 FR-013 и существующие файлы), но **сделать его частью идемпотентного ядра**: после первого прохода строка не изменяется при повторном. Гарантия: `sanitize(sanitize_legacy(s)) == sanitize_legacy(s)` для всех `s`.
- Q: Нужно ли экранировать shell-метасимволы (`<`, `>`, `|`, `&`, `;`, `(`, `)`) при санитайзинге? → A: **Не экранировать, а заменять** (`(` → `(` без изменений, потому что используется в шаблоне имени файла; `<`, `>`, `|`, `&`, `;` → удалять или заменять на `_`, потому что в shell-командах они ломают парсинг). В shell-командах дополнительно применяется `wrapInQuotes()` — это второй уровень защиты, который остаётся. Решение по конкретным символам — в FR-002.
- Q: Что делать с неидемпотентностью из-за числовых суффиксов коллизий (пункт 2 корневой причины)? → A: **Эта проблема лежит вне санитайзера** и относится к дедупликации при импорте. Санитайзер **должен быть идемпотентным** (`sanitize(sanitize(s)) == sanitize(s)`), но **дедупликация при коллизиях** — отдельный механизм (см. specs/124 FR-005), который добавляет суффикс **после** санитайзинга, не внутри него. Граница ответственности: санитайзер не знает о коллизиях, дедупликатор не делает дополнительной санитиризации. В рамках этой спеки — зафиксировать контракт.

### Session 2026-09-04 (clarify)

- Q: Поведение санитайзера на пустой строке / строке из только «проблемных» символов (влияет на API-контракт, тип возврата, FR-001 и совместимость с `sanitized.isEmpty()` в `SongUpdateMapper.kt:229`)? → A: **Option A** — `sanitize("") == ""`, `sanitize("!?*") == "_"` (каждый проблемный символ заменяется на `_` индивидуально); `sanitize("!?!?") == "____"` (сохраняет плотность), тип API остаётся `String` (не `String?`), исключения не бросаются. Гарантия идемпотентности: `sanitize("") == ""` и `sanitize("_") == "_"`. Чек `sanitized.isEmpty()` в `SongUpdateMapper.kt:229` остаётся актуальным только для случая, когда вход был пустой строкой (что отдельно валидируется на уровне вызывающего).
- Q: Observability — логировать ли замены санитайзера (влияет на side-effect-чистоту функции, размер логов при импорте, возможность диагностики багов вроде issue #53)? → A: **Option C** — INFO-логирование через slf4j: при **каждой фактической замене** символа sanitizer пишет одну строку уровня INFO вида `Sanitize: "<before>" → "<after>"` (с указанием конкретной позиции/символа, например `Sanitize [pos=12, char='!']: "2012 - Лучшее!" → "2012 - Лучшее_"`). Если замен не было (вход уже идемпотентен) — **лог-запись НЕ пишется** (защита от шума на повторных прогонах). На импорте 100+ файлов это порождает 100+ строк в INFO — это **приемлемо**, потому что (а) для админа это подтверждение работы sanitizer'а, (б) для диагностики багов вроде issue #53 логи сразу указывают на проблемные имена. Side-effect ограничен файловым I/O логгера; идемпотентность результата (`sanitize(sanitize(s)) == sanitize(s)`) сохраняется, но **идемпотентность side-effect'ов** (количество лог-записей на повторный прогон) **тоже** должна соблюдаться — повторный прогон не плодит новых лог-записей.
- Q: Length truncation policy — обрезать ли sanitizer длинные имена (влияет на FR-001 контракт: обрезка по byte count может нарушить идемпотентность и UTF-8 multi-byte sequences)? → A: **Option A** — без обрезки, поведение как сейчас. Существующая закомментированная логика обрезки в `Extentions.kt:62-88` остаётся закомментированной. Ответственность за длину пути — на вызывающем коде (импорт/shell). Truncation может быть вынесена в **отдельную** задачу в будущем, если станет проблемой на проде (с char/byte-aware logic, чтобы не сломать UTF-8 и идемпотентность).

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Папка альбома с восклицательным знаком импортируется без потери данных (Priority: P1)

Администратор кладёт в корень импорта папку альбома `2012 - Лучшее!` с
MP3-файлами внутри. Сегодня при импорте из папки санитайзер удаляет `!`
из имени папки, и физические файлы внутри не находятся (lookup идёт
по `2012 - Лучшее`, реальная папка — `2012 - Лучшее!`). После исправления
санитайзер заменяет `!` на `_` (или эквивалентный сохраняющий символ),
и идемпотентный повторный проход не изменяет уже-санитайзенное имя.
Альбом импортируется, все треки — на месте.

**Why this priority**: Это **блокирующий баг из issue #53**: альбомы
с `!` в имени физически не импортируются. Без исправления администратор
вынужден вручную переименовывать папку до импорта, что нарушает
требование «всё в одном пайплайне».

**Independent Test**: Создать папку `2012 - Лучшее!` с двумя MP3-файлами
внутри, запустить импорт из папки. Проверить:
(а) в БД появились записи `tbl_albums.album_name = '2012 - Лучшее_'` (или
эквивалентный безопасный вариант), (б) `tbl_songs.file_absolute_path`
указывает на реальные файлы на диске, (в) повторный запуск импорта
не создаёт дублей и не теряет файлы (идемпотентность).

**Acceptance Scenarios**:

1. **Given** папка `2012 - Лучшее!` с двумя MP3-файлами, **When** запускается
   импорт из папки, **Then** создаётся альбом, все треки импортированы,
   файлы на диске найдены.
2. **Given** уже импортированный альбом с `!` → `_` в имени, **When**
   запускается повторный импорт той же папки, **Then** новых песен не
   появляется (дедупликация работает), `sanitize(sanitize(name)) == sanitize(name)`
   для всех затронутых путей.
3. **Given** в имени файла или папки присутствует `?` (вопросительный знак),
   **When** запускается импорт, **Then** `?` заменяется безопасным символом
   (не удаляется, чтобы сохранить плотность имени), повторный прогон
   не изменяет результат.
4. **Given** папка альбома `2024 - Top Hits` (без проблемных символов),
   **When** запускается импорт, **Then** имя папки сохраняется как есть
   (без изменений), повторный прогон даёт идентичный результат.

### User Story 2 — Единый идемпотентный санитайзер покрывает полный набор shell- и FS-опасных символов (Priority: P1)

Администратор кладёт папку с символами, которые сегодня не покрыты
(например, `<`, `>`, `|`, `&`, `;`, `\n`, `\r`, `\t`). Сегодня такие
символы проходят через санитайзер без изменений и ломают либо
shell-команды в `KaraokeProcess.kt`, либо пути в MinIO/SQL. После
исправления единый санитайзер покрывает все эти символы и заменяет
их на безопасные эквиваленты.

**Why this priority**: Это **превентивный фикс**: символы из issue #53
(`!`, `?`) — частный случай более широкой проблемы. Без единого
контракта любое появление нового «проблемного» символа в имени файла
приводит к повторению бага. Единый идемпотентный санитайзер закрывает
весь класс проблем.

**Independent Test**: Прогнать таблицу символов из FR-002 через санитайзер
дважды, убедиться что `sanitize(sanitize(x)) == sanitize(x)` для всех
символов, и что каждый символ заменён на безопасный.

**Acceptance Scenarios**:

1. **Given** строка, содержащая символ из таблицы FR-002 (например,
   `track<1>.mp3`), **When** применяется санитайзер, **Then** символ
   заменяется на безопасный (`track_1_.mp3` или эквивалент), повторный
   прогон не изменяет результат.
2. **Given** строка, содержащая только безопасные символы (буквы, цифры,
   `-`, `_`, кириллица, `()`/`[]`), **When** применяется санитайзер,
   **Then** строка не изменяется, повторный прогон не изменяет.
3. **Given** строка с Unicode BOM/ZWSP/управляющими символами, **When**
   применяется санитайзер, **Then** эти символы заменяются на `_`,
   повторный прогон не изменяет результат.

### User Story 3 — Существующие пути и файлы на проде остаются работоспособными после обновления алгоритма (Priority: P1)

На проде уже хранятся тысячи файлов с именами, санитайзенными по старому
алгоритму (`!` удалено, `?` удалено, `$` → `s`, `'` → `` ` `` и т.д.).
После обновления алгоритма эти файлы должны остаться доступными и
находиться по своим путям — без миграций и переименований на диске.

**Why this priority**: Идемпотентность — это свойство преобразования,
но в реальной системе уже есть данные, санитайзенные **по старому**
алгоритму. Если новый алгоритм выдаёт **другое** имя для тех же входов,
произойдёт рассинхронизация: код будет искать файл по новому имени,
а файл лежит по старому. Поэтому идемпотентность должна соблюдаться
не только «второй прогон = первый», но и **«новый алгоритм от старого
санитайзенного входа = старое санитайзенное»** — обратная совместимость
с уже существующими данными.

**Independent Test**: Взять 100 случайных имён файлов из существующей БД
(включая имена с `$`, `'` и удалёнными `!`/`?`), прогнать через новый
санитайзер, убедиться что результат совпадает с тем, что уже лежит на диске.

**Acceptance Scenarios**:

1. **Given** на проде есть файл `2012 - Daj zaru.flac` (импорт по старому
   алгоритму с `!` → удалено), **When** применяется новый санитайзер
   к строке `2012 - Daj zaru.flac`, **Then** результат равен
   `2012 - Daj zaru.flac` (без изменений).
2. **Given** на проде есть путь `Queen s` (импорт по старому алгоритму
   с `$` → `s`), **When** применяется новый санитайзер к строке `Queen s`,
   **Then** результат равен `Queen s` (без изменений).
3. **Given** на проде есть путь с `` ` `` (импорт по старому алгоритму
   с `'` → `` ` ``), **When** применяется новый санитайзер, **Then**
   `` ` `` сохраняется (для обратной совместимости), и в shell-командах
   путь дополнительно оборачивается в `wrapInQuotes()`.

### Edge Cases

- Что происходит, если на вход санитайзеру даётся пустая строка?
  → **`sanitize("") == ""`** (см. Clarifications Q1 / Option A, Session 2026-09-04 clarify).
  Идемпотентно: `sanitize(sanitize("")) == ""`. Пустая строка не считается
  ошибкой и не вызывает исключения; валидация «имя не пустое» остаётся
  на стороне вызывающего (как сейчас в `SongUpdateMapper.kt:229`).
- Что происходит, если на вход даётся строка, состоящая только из
  «проблемных» символов (например, `!?*`)?
  → **`sanitize("!?*") == "_"`** (каждый символ заменяется индивидуально;
  см. Clarifications Q1 / Option A, Session 2026-09-04 clarify).
  Идемпотентно: `sanitize(sanitize("!?")) == "_"`. Сохраняет визуальную
  плотность имени (в отличие от drop, который дал бы `""`).
- Что происходит, если строка содержит смесь legacy-замен (`$` → `s`,
  `'` → `` ` ``) и новых символов (`<`, `>`, `|`)? Не должно быть
  «двойной замены» (например, `s` обратно в `$`).
- Что происходит с длинными именами (>200 байт UTF-8)?
  → **Sanitizer НЕ обрезает** (см. Clarifications Q3 / Option A, Session 2026-09-04 clarify).
  Поведение как сейчас: если результат >255 байт — это ответственность
  вызывающего кода (импорт упадёт с `IOException: File name too long`,
  либо shell-команда вернёт ошибку). Существующая закомментированная
  логика обрезки в `Extentions.kt:62-88` остаётся закомментированной.
  Truncation может быть добавлена **отдельной** задачей в будущем,
  если станет проблемой на проде — потребуется char/byte-aware logic,
  чтобы не сломать UTF-8 multi-byte sequences и идемпотентность.
- Что происходит со строками, содержащими символы новой строки
  (приходят из copy-paste или внешних источников)?
- Что происходит при попытке санитайзить уже-санитайзенную строку
  (любую из существующих 200+ вызывающих мест) — это **не** должно
  ничего менять.
- Что происходит, если на проде встретится имя, санитайзенное **по
  старому** алгоритму, и в нём есть `_` (например, заменили `!` на `_`,
  а потом ещё раз прогнали)? Не должно быть двойной замены.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: В проекте MUST быть реализован единый идемпотентный санитайзер
  путей и имён файлов/папок, удовлетворяющий условию
  `sanitize(sanitize(s)) == sanitize(s)` для **любой** строки `s`
  (включая Unicode, кириллицу, управляющие символы, **пустую строку**
  и строку из только «проблемных» символов — поведение зафиксировано
  в Clarifications Q1 / Option A: `sanitize("") == ""`,
  `sanitize("!?*") == "_"`). API возвращает `String` (не `String?`),
  не бросает исключений.
- **FR-002**: Санитайзер MUST заменять (не удалять) следующие символы
  на `_` (нижнее подчёркивание):
  `!`, `?`, `\n`, `\r`, `\t`, `\0`, `<`, `>`, `|`, `&`, `;`, `"`.
  Замена на `_` вместо удаления сохраняет визуальную плотность имени
  и совместима с shell/FS/SQL без дополнительного экранирования.
- **FR-003**: Санитайзер MUST сохранять **без изменений** следующие
  символы (они либо структурно нужны для шаблона имени файла, либо
  не являются проблемными): буквы (любые Unicode-категории, включая
  кириллицу), цифры, `-`, `_`, `.`, `(`, `)`, `[`, `]`, `+`, `=`,
  `,`, `~`, `@`, `#`, `%`, `^`. (Скобки `(`/`)` и `[`/`]` нужны для
  шаблона «Порядковый (Номер) [Автор] - Название».)
- **FR-004**: Санитайзер MUST применять следующие **legacy-замены**
  (для обратной совместимости с уже-санитайзенными путями на проде,
  см. specs/124 FR-013), но **идемпотентно**: после первого прохода
  результат не изменяется при повторном:
  - `'` → `` ` `` (одноразовая замена; `` ` `` сохраняется без изменений).
  - `$` → `s` (одноразовая замена; результат не должен быть повторно
    конвертирован обратно).
  - `*` → `x`.
  - `:` → `-`.
- **FR-005**: Существующие функции `rightFileNameSymbols`,
  `sanitizeSongFileName`, `rightFileName` MUST остаться как тонкие
  обёртки над новым единым санитайзером (для обратной совместимости
  с 200+ вызывающих мест в `StemJobProcessing.kt`, `KaraokeProcess.kt`,
  `model/Song.kt`, `controllers/*.kt`, `karaoke-web/services/*.kt`).
  Изменение их **сигнатур** запрещено; изменение **поведения** —
  в сторону идемпотентности и расширенного покрытия символов (FR-002/003/004).
- **FR-006**: Санитайзер MUST быть доступен в двух вариантах:
  - `sanitizePathSegment(s)` — для «голого» фрагмента пути/имени файла/папки
    (без разделителей). Дополнительно убирает `/`, `\` (защита от выхода
    за пределы папки, как в существующем `sanitizeSongFileName`).
  - `sanitizePath(s)` — для полного пути, содержащего `/` или `\` как
    разделители. Сохраняет разделители, но санитайзит каждый сегмент
    между ними с помощью `sanitizePathSegment`.
- **FR-007**: Существующая логика проверки коллизий при импорте
  (specs/124 FR-005, числовой суффикс `(N)`) MUST остаться **снаружи**
  санитайзера. Санитайзер не знает о коллизиях и не генерирует суффиксы;
  дедупликатор работает на уже-санитайзенных именах. Это сохраняет
  идемпотентность санитайзера при наличии коллизий.
- **FR-008**: Для shell-команд в `KaraokeProcess.kt` (где `rightFileName()`
  используется на полных путях, передаваемых в `mv`/`chmod`/`ffmpeg`/
  `melt`/`docker run`) MUST быть сохранена защита через `wrapInQuotes()`
  для путей, содержащих пробелы или shell-метасимволы. Санитайзер
  по FR-002/003/004 уже убирает основные shell-метасимволы (`<`, `>`,
  `|`, `&`, `;`), но `wrapInQuotes()` остаётся вторым уровнем защиты
  (для пробелов, скобок, квадратных скобок).
- **FR-009**: Идемпотентность MUST быть покрыта unit-тестами
  (`karaoke-app/src/test/kotlin/...`): для каждого символа из таблицы
  FR-002/003/004, для комбинаций символов, для Unicode-строк,
  для пустых строк, для строк, состоящих только из заменяемых символов.
  Каждый тест проверяет `sanitize(sanitize(s)) == sanitize(s)` и
  что ожидаемая замена выполнена. Дополнительно — **side-effect
  идемпотентность** (FR-014): тест считает количество записей в логгере
  (через test-appendable) до первого прогона и после второго прогона
  той же строки, и проверяет что количество **не изменилось**.
- **FR-010**: В `docs/features/` (per-feature документ, FR-009 конституции)
  MUST быть обновлён или создан документ, описывающий таблицу замен
  FR-002/003/004, идемпотентный контракт и границу с дедупликатором
  (FR-007). Имя файла — `docs/features/idempotent-path-sanitize.md`
  (или обновление существующего, если такой уже есть).
- **FR-011**: В `AGENTS.md` (раздел «TOP-10 ловушек») MUST быть добавлен
  пункт «При правке санитайзера — соблюдать идемпотентность и обратную
  совместимость с уже-санитайзенными именами на проде» (cross-reference
  на FR-001 и FR-004).
- **FR-012**: Контракт «санитайзер идемпотентен» (`sanitize(sanitize(s)) ==
  sanitize(s)` для **любых** path/name sanitizer'ов в проекте) MUST быть

- **FR-014**: Санитайзер MUST логировать через slf4j (LoggerFactory) на уровне
  INFO каждую **фактическую** замену символа в формате
  `Sanitize [pos=N, char='X']: "<before>" → "<after>"`, где `N` — позиция
  символа в исходной строке, `X` — заменённый символ. Если замен не было
  (вход уже идемпотентен) — лог-запись НЕ пишется. Контракт идемпотентности

### Key Entities *(include if feature involves data)*

- **Имя файла песни (`Song.fileName`)**: хранится в БД, используется как
  основа для имён всех производных файлов (FLAC, стемы, проект видеоредактора,
  субтитры, метаданные) и ключей в MinIO. Должно быть идемпотентно-санитайзенным.
- **Имя папки альбома (`Album.albumFolderName` / корень импорта `rootFolder`)**:
  используется как часть пути ко всем файлам альбома. Должно быть
  идемпотентно-санитайзенным; санитайзер не должен удалять символы,
  а заменять их на безопасные (FR-002).
- **Полный путь (`Song.fileAbsolutePath`, `pathToFile*`)**: композиция
  из `rootFolder + segment + fileName + suffix`. Каждый сегмент должен
  быть санитайзен независимо; разделители (`/`) — сохраняются.
- **Shell-командная строка**: формируется в `KaraokeProcess.kt` путём
  конкатенации `path + " " + arg`, где `path` уже прошёл через
  `rightFileName()` и `wrapInQuotes()`. Санитайзер отвечает за FR-002/003/004,
  `wrapInQuotes()` — за второй уровень защиты (FR-008).

## Assumptions

- Текущий список «проблемных» символов (в `rightFileNameSymbols`) покрывает
  реальные кейсы из прода (см. issue #53 и specs/124), но не покрывает
  превентивно другие shell-метасимволы (`<`, `>`, `|`, `&`, `;`).
  Расширение покрытия — в FR-002.

  парсерами шаблона имени файла «Порядковый (Номер) [Автор] - Название»
  (см. specs/124 FR-003): `_` не является разделителем ни в одном из
  парсеров.
- Существующие 200+ вызывающих мест `rightFileName()`/`sanitizeSongFileName()`/
  `rightFileNameSymbols()` не должны быть переписаны в рамках этой спеки —
  только при необходимости (если обёртки ведут себя иначе). Бо́льшая
  часть вызывающих мест продолжит работать без изменений.
- Тесты пишутся как JUnit-тесты в `karaoke-app/src/test/kotlin/...`
  (даже несмотря на то, что бо́льшая часть существующих тестов
  `@Disabled` — см. AGENTS.md). Для FR-009 (идемпотентность) тесты
  могут быть включены и проверяться как в CI, так и локально.
- `wrapInQuotes()` остаётся без изменений и используется **после**
  `rightFileName()` для shell-команд — это второй уровень защиты,
  и он не конфликтует с новым санитайзером.
