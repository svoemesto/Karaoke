# Subscription payment idempotency (идемпотентность платежей и автопродления)

> **Status**: active
> **Feature Key**: subscription-payment-idempotency
> **Last Updated**: 2026-10-24
> **Spec**: [specs/365-pkg-money-idempotency/report.md](../../specs/365-pkg-money-idempotency/report.md) (OpenProject #365, аудит #336: BR-014, BR-020, BR-021, BR-514)
> Per-feature документ по [Constitution VI FR-009](../../.specify/memory/constitution.md).

## Что делает

Не даёт деньгам «задвоиться» или потеряться на всех путях оплаты ЮKassa:

| Путь | Что гарантируется |
|---|---|
| Webhook ЮKassa (`PublicPaymentController`) | повторная доставка и параллельный ретрай не продлевают премиум второй раз; сбой между статусом и начислением откатывает оба, и ЮKassa повторяет доставку |
| Оформление подписки (`PublicSubscriptionController.create`, SITE и SONG) | повторный клик переиспользует незавершённый заказ при любом не-`canceled` статусе платежа; `succeeded` = «уже оплачено», `null` = 503 (fail-closed, второй счёт не выставляется) |
| Checkout корзины (`PublicCartController.checkout`) | корзина очищается и заказ становится `PENDING` только после успешного создания платежа; при отказе заказ откатывается, корзина цела; незавершённый заказ переиспользуется по стабильному `orderId` |
| Автопродление (`SubscriptionRenewalScheduler`) | `Idempotence-Key` привязан к строке продления, а не к дате запуска; `result.id` сохраняется до начисления; статус и продление — одной транзакцией |

Общий инвариант вынесен в один сервис: `SubscriptionFulfillmentService.fulfillPaid` —
условный захват `UPDATE tbl_subscriptions ... WHERE id = ? AND status <> 'PAID'` и
начисление (`SELECT ... FOR UPDATE` по `tbl_site_users` + `UPDATE site_premium_until`)
в одной транзакции. «Мы первые» определяется числом обновлённых строк, а не проверкой
`if (status == PAID)` до записи.

## Зачем

Аудит кода #336 (волна C, пакет `PKG-MONEY-IDEMPOTENCY`) зафиксировал четыре S2-дефекта
одного класса — «деньги двигаются раньше, чем фиксируется результат»:

- **BR-020** — статус `PAID` сохранялся до начисления и вне транзакции: ретрай вебхука
  видел «все PAID» и отвечал 200 no-op → оплаченный период не начислялся никогда;
  два параллельных ретрая продлевали срок дважды.
- **BR-021** — повторное оформление переиспользовало заказ только при ровно `pending`:
  задержавшийся вебхук (`succeeded`) или недоступная ЮKassa (`null`) приводили к
  созданию второго платежа и второму списанию.
- **BR-014** — checkout удалял корзину до создания платежа: при отказе ЮKassa корзина
  пуста, а `CREATED`-подписки висят без платежа; `orderId` был новым `UUID` на каждый
  запрос, поэтому двойной submit создавал второй заказ и второй платёж.
- **BR-514** — автопродление отбрасывало `result.id` (вебхук не мог найти подписку),
  списывало деньги до фиксации и строило ключ идемпотентности от даты запуска: сбой
  после списания приводил к новой строке, новому ключу и повторному списанию за тот же
  период.

## Как работает

**Общий сервис начисления.** `fulfillPaid(sub, paymentId, paymentMethodId)`:

1. открывает соединение подписки, `autoCommit=false`;
2. `UPDATE tbl_subscriptions SET status='PAID', paid_at=?, ... WHERE id=? AND status<>'PAID'` —
   0 строк значит «подписку уже обработал параллельный вызов» → commit, `false`;
3. для `scope=SITE`: `SELECT site_premium_until ... FOR UPDATE`, затем
   `UPDATE tbl_site_users SET site_premium_until = max(now, текущая) + periodDays`;
4. commit; при любом исключении — rollback и проброс наверх (вебхук отвечает 5xx,
   ЮKassa повторяет доставку; начисление не может «потеряться» рядом с `PAID`).

**Вебхук.** Телу не доверяем: статус перезапрашивается `PaymentService.verifyAndFetch`.
Ранний no-op «все позиции PAID» остаётся, но теперь он безопасен: `PAID` и начисление
коммитятся вместе, поэтому `PAID ⇒ начисление уже было`. Для заказа корзины позиции
делят один `yookassa_payment_id`, каждая захватывается отдельно.

**Оформление подписки.** Незавершённый заказ ищется по `(site_user_id, tariff)` для
SITE и `(site_user_id, id_song)` для SONG, причём в статусах `CREATED` **и** `PENDING`
(строка создаётся до платежа). Решение о судьбе заказа — `PaymentOrderReuse.decide`:

| Статус платежа в ЮKassa | Действие |
|---|---|
| `pending`, `waiting_for_capture` | тот же `confirmationUrl`, новый платёж не создаётся |
| `succeeded` | `fulfillPaid` (начисление) и ответ `PAID`, второй платёж не создаётся |
| `canceled` | строка помечается `FAILED`, создаётся новый заказ |
| `null` / неизвестный статус | `503 payment_unavailable` — fail-closed, новый счёт не выставляется |

**Checkout корзины.** Порядок: строки `Subscription` (`CREATED`, общий `orderId`) →
`createCartPayment(orderId, ...)` → только при успехе `PENDING` и удаление позиций
корзины. При отказе строки удаляются (`DELETE ... WHERE id = ANY(?)`), корзина
остаётся. Два одновременных checkout сериализуются по пользователю (полоса блокировок
по `site_user_id`), второй видит заказ первого и переиспользует его.

**Автопродление.** Строка продления создаётся и коммитится до списания; она же несёт
ключ `renew-<userId>-sub<id>`. После ответа ЮKassa сначала сохраняется
`yookassaPaymentId` (деньги уже списаны — id нужен вебхуку), затем `fulfillPaid`
фиксирует `PAID` и продление одной транзакцией. Незавершённая строка прошлого тика
переиспользуется: тот же ключ → тот же платёж ЮKassa, второго списания нет.

## Инварианты

1. Статус `PAID` и начисление подписки фиксируются **одной транзакцией**; `PAID` без
   начисления невозможен.
2. Захват подписки — **условный** `UPDATE ... WHERE status <> 'PAID'`; «первый» —
   тот, кто обновил строку, а не тот, кто раньше прочитал статус.
3. Побочные эффекты заказа (очистка корзины, `PENDING`) — **только после** успешного
   создания платежа; отказ → откат заказа, корзина цела.
4. `Idempotence-Key` привязан к сущности: `order-<orderId>`, `sub-<id>-<createdAt>`,
   `renew-<userId>-sub<id>`. Привязка к дате запуска запрещена.
5. Неизвестный статус платежа или недоступная ЮKassa → **fail-closed** (5xx/503),
   а не «создадим ещё один платёж».
6. `scope=SONG` не трогает `sitePremiumUntil`; начисление для песни — сам факт
   `PAID`-записи.

## Известные ловушки

- **Не «упрощать» захват до `if (sub.status == PAID) return`.** Между проверкой и
  записью вклинивается параллельный вебхук — вернулась бы двойная продажа периода.
- **Не переносить очистку корзины выше создания платежа.** Именно этот порядок и был
  дефектом BR-014: при 503 пользователь терял корзину.
- **Не менять ключ автопродления на дату.** Любой сбой между списанием и `save()`
  превращается в повторное списание на следующем тике.
- **Строки `CREATED` без `yookassa_payment_id`** — не мусор, а «платёж не создался»:
  их надо досоздавать (тот же ключ `sub-<id>-<createdAt>`), а не заводить вторую строку.
- **`Subscription.save()` — autocommit-запись.** Внутри транзакции начисления
  использовать только прямые `UPDATE` на том же соединении (как в
  `SubscriptionFulfillmentService`), иначе изменение уйдёт вне транзакции.
- **Старые незавершённые автопродления** (созданные до этой правки, без
  `yookassa_payment_id`) требуют ручной сверки: их ключ идемпотентности был другим.
