**Дата**: 2026-09-23
**Тип**: research (только чтение и замеры, данные не копировались)
**Статус**: рекомендация готова, исполнение — только при cutover
**Автор**: research-субагент

## 1. Обзор

Задача: перенести бакет `karaoke` (444 GiB / 59 707 объектов) из удалённого
MinIO на сервере-источнике `89.125.103.63` в локальный MinIO-контейнер на новом
сервере `sm-karaoke` (188.127.240.124).

Ключевые вводные, установленные замерами:

| Параметр | Источник (`karaoke-storage`) | Назначение (`sm-karaoke`) |
|---|---|---|
| IP | 89.125.103.63 | 188.127.240.124 |
| hostname | r1216739 | sm-karaoke.ru |
| vCPU | 4 | 6 |
| RAM | 3.8 GiB | 3.8 GiB (swap 0, план — 8 GiB) |
| Диск | 485 GB, занято 94%, свободно **32 GB** | 985 GB, свободно **932 GB** |
| ОС | Ubuntu, ядро 6.8 | Ubuntu 26.04, ядро 7.0 |
| Docker | есть | **НЕ установлен** (`docker.io 29.1.3` в apt) |
| MinIO | запущен, `minio/minio:latest`, RELEASE.2025-09-07 | отсутствует |
| MinIO API | порт 9000 открыт | порт 9000 закрыт (нет сервиса) |
| `mc` | `/usr/local/bin/mc` RELEASE.2025-08-13 | нет |
| `rclone` | нет | нет (в apt 1.60.1) |
| `rsync` | есть (`/usr/bin/rsync`) | нет (в apt 3.4.1) |
| `nc`/`iperf3` | `nc` есть | **нет** |

Три вывода, определяющие весь план:

1. **SSH между самими серверами НЕ настроен.** Проверено в обе стороны:
   `ssh root@dest` с источника и `ssh root@source` с назначения дают
   `Permission denied (publickey)` / `Host key verification failed`.
   Оба сервера доступны по SSH **только с рабочей машины `nsa-i9`**.
   Следствие: rsync-метод «напрямую» невозможен без предварительной
   настройки доверия, а S3-методы (mc/rclone) работают по TCP:9000 и не
   зависят от SSH.
2. **Измеренный канал насыщается на ~180–200 Мбит/с** при 8–16 параллельных
   S3-потоках. Одиночный поток — всего ~39 Мбит/с. RTT между серверами
   ~2.6 мс (серверы близко, вероятно один провайдер/ЦОД).
3. **Диски не являются узким местом**: запись на источнике 389 МБ/с,
   на назначении 150 МБ/с; локальное чтение MinIO 229 МБ/с.

### 2.1. Целевые параметры бакета (через S3 API)

Точный объём (logical, сумма размеров объектов): **477 260 345 685 байт =

Каталог `/opt/minio/data` целиком: **477 299 277 358 байт (444.48 GiB)** —
разница ~37 МБ (это `.minio.sys`).

### 2.2. Распределение размеров объектов (важно для overhead)

Замер через S3 API (`mc ls --recursive --json`):

| Диапазон | Объектов | Суммарно | Доля объёма |
|---|---|---|---|
| `<64 KiB` | 3 268 | 0.02 GiB | ~0% |
| `64 KiB – 1 MiB` | 3 264 | 1.15 GiB | 0.3% |
| `1 – 5 MiB` | 6 370 | 21.11 GiB | 4.7% |
| **`5 – 20 MiB`** | **46 417** | **412.56 GiB** | **92.8%** |
| `>= 20 MiB` | 388 | 9.60 GiB | 2.2% |

Профиль благоприятный: **92.8% объёма — крупные объекты 5–20 MiB**
(это mp3 accompaniment/vocals). Мелких объектов (`<1 MiB`) всего 6 532,
и они дают лишь ~1.2 GiB. Overhead на request-per-object будет мал.
Максимальный объект — ~64 MiB (двухдорожечные треки).

Медиана размера объекта по S3-данным — около 2.7 MiB, но по объёму тон
задают объекты 5–20 MiB.

### 2.3. Физическая раскладка на диске (erasure `xl.meta`)

На диске источник хранит 59 707 S3-объектов, разложенных файловой системой
MinIO (format `xl`):

- каталогов: 119 060;
- файлов `xl.meta`: 59 707;
- файлов данных `part.N` (все прочие): 119 364;
- все объекты, кроме **2**, имеют **inline-метаданные** (`xl.meta < 128 KiB`),
  т.е. `xl.meta` содержит и метаданные, и, для мелких объектов, сами данные.

Пример дерева:

```
/opt/minio/data/karaoke/Арбалет/2023 - Наши парни (это Вагнер)/
    ...accompaniment.mp3/c28939c5-.../part.1
    ...accompaniment.mp3/c28939c5-.../part.2
    ...accompaniment.mp3/xl.meta
```

Вывод: прямое копирование файлов (`rsync`/`cp`) требует переносить и `part.N`,
и `xl.meta` как единое целое, а это внутренний формат, не контракт. Это
аргумент в пользу S3-уровня.

### 2.4. Служебный каталог `.minio.sys`

```
2.3M  /opt/minio/data/.minio.sys
├── buckets/     232K   (bucket policy, usage cache, .bloomcycle.bin)
├── config/       32K   (config.json + iam/)
├── format.json  232B   (формат диска — НЕ переносить поверх нового)
├── multipart/    20K   (незавершённые multipart-загрузки, 22.09)
├── pool.bin      8K
└── tmp/         2.0M
```

Содержимое: bucket policies и IAM. Через S3 API переносится командой
`mc mirror --preserve` (bucket policy/locking), а IAM-пользователи на
источнике **отсутствуют** (`mc admin user list` пуст; policies — только
встроенные `readonly/readwrite/writeonly/diagnostics/consoleAdmin`).

**Нельзя** копировать `.minio.sys` поверх/внутрь нового MinIO: `format.json`
и `pool.bin` привязаны к конкретному диску/кластеру и приведут к отказу
старта. IAM/root-креды задаются через env, а не копированием `.minio.sys`.

### 2.5. Активность записи (для окна cutover)

По `lastModified` объектов:

- за последние 24 часа изменено: **80 объектов**;
- за последние 7 дней: **499 объектов**;
- самый свежий объект: 2026-09-22 18:42 UTC.

Запись идёт, но с низкой интенсивностью. Это означает, что инкрементальный
второй проход (после bulk) будет коротким — новые/изменённые объекты
исчисляются десятками-сотнями, а не тысячами.

### 2.6. Где живут писатели

- На самом сервере-источнике запущен **только** контейнер `karaoke-storage`.
  Приложение там не работает.
- Писатели найдены на хосте `karaoke-prod` (188.119.64.111): контейнеры
  `karaoke-public`, `karaoke-web`, `karaoke-db` (PostgreSQL 16).
  `karaoke-app` на нём не обнаружен (вероятно, GPU-контейнер на `nsa-i9`,

- `docker-compose-storage.yml` (на источнике) монтирует `${STORAGE_FOLDER}:/data`

### 3.1. Сетевые ограничения (проверено)

- Порт `22` назначения — открыт (SSH).

## 4. Сравнение методов

| Критерий | A. `mc mirror` (S3→S3) | B. `rclone sync` (S3→S3) | C. `rsync` файлов | D. Физический диск |
|---|---|---|---|---|
| Транспорт | HTTP S3 API :9000 | HTTP S3 API :9000 | SSH/raw | offline/гипервизор |
| Требует SSH между серверами | **нет** | **нет** | **да** (сейчас не работает) | нет |
| Сохраняет S3-метаданные (content-type, ETag) | **да** | да | только raw-файлы | да (весь том) |
| Сохраняет bucket policy/anonymous | **да** (`--preserve`) | частично | нет | да (весь `.minio.sys`) |
| Нужен останов MinIO на источнике | нет | нет | **да (оба)** | **да** |
| Проверка целостности | встроенная (по размеру/ETag) | `--checksum` | нет S3-проверки | нет |
| Устойчивость/докачка | resume, идемпотентен | resume, идемпотентен | частично | нет |
| Двухпроходность (bulk + инкремент) | **естественная** (`--overwrite --remove`) | да | сложно | нет |
| Установка | `mc` уже есть на источнике, на dest — 1 бинарник | apt install rclone | apt rsync с двух сторон + настройка SSH | доступ к гипервизору |
| Риск неконсистентности | низкий | низкий | **высокий** (`part.N` + `xl.meta` врозь) | низкий, но простой |
| Оценка времени 444 GiB при ~200 Мбит/с | ~5.5–6.5 ч | ~5.5–6.5 ч | хуже (один поток, нет S3-параллелизма) | часы + простой |

### 4.1. Разбор

**Метод A — `mc mirror` (рекомендован).**
Плюсы: нативный для MinIO, сохраняет метаданные и (с `--preserve`) bucket
policy; уже установлен на источнике; идемпотентен, поддерживает
`--overwrite`, `--remove`, `--watch`; идеально ложится в двухпроходную схему.
Минусы: нужно поднять `mc` там, откуда видны оба S3-endpoint (назначение),
либо запускать на источнике после старта MinIO на назначении; требует
корректных кредов (на источнике alias настроен неверно).

**Метод B — `rclone sync`.**
Плюсы: мощный, `--transfers`/`--checkers`, контроль multipart, `--checksum`.
Минусы: `rclone` отсутствует на обоих, ставить на назначение; сохранение
bucket policy/anonymous хуже, чем `--preserve` у `mc`; по сути дублирует
метод A без преимуществ для этой задачи.

**Метод C — `rsync` файлов напрямую.**
Плюсы: копирует «как файлы», rsync есть на источнике.
Минусы (критические): требует остановки MinIO **на обоих** концах; требует
рабочего SSH source↔dest (сейчас **нет**); переносит внутренний формат
`part.N`/`xl.meta`, а не объекты — нет S3-проверки целостности; высокий риск
рассинхронизации при незавершённых multipart. Не рекомендуется.

**Метод D — физический диск / снапшот тома.**
Плюсы: максимально быстро на уровне блоков, переносит всё включая `.minio.sys`.
Минусы: требует простоя и доступа к гипервизору/панели VPS; том источника
485 GB (нельзя «вынуть» только 446 ГБ); не всегда доступно у VPS-провайдера.
Рассматривать только если провайдер даёт снапшот/клон диска.

## 5. Рекомендация по методу

**Рекомендуется Метод A — `mc mirror` source→target, запускаемый с
сервера назначения**, с двухпроходной схемой:

1. **Проход 1 (bulk, прод работает):**
   `mc mirror --preserve --overwrite src/karaoke dst/karaoke`
2. **Проход 2 (окно заморозки 15–30 мин):**
   остановить писателей, затем
   `mc mirror --overwrite --remove src/karaoke dst/karaoke`,
   проверить `mc diff` (должно быть пусто), переключить endpoint.

Обоснование выбора именно запуска с назначения:
- назначение уже видит `89.125.103.63:9000` (проверено);
- свой MinIO на назначении — локальный, поэтому запись/чтение целевых объектов
  идёт по loopback (быстро, диск 150 МБ/с);
- SSH source↔dest не нужен;
- `mc` ставится на назначение одним статическим бинарником.

Альтернатива (если удобнее): запускать `mc mirror` на источнике после старта
MinIO на назначении — источник тоже видит сеть, но целевая запись пойдёт по
сети, что может снизить агрегат. Предпочтительнее всё же назначение.

Критические условия перед запуском:
- пересоздать alias с **правильными** кредами
  (`${STORAGE_KEY}`/`${STORAGE_SECRET}` из env контейнера, а не `minio_key`/`minio_secret`);
- тот же root-пользователь/пароль задать новому MinIO на назначении, чтобы
  конфиги приложения (`STORAGE_KEY`/`STORAGE_SECRET`) не менялись;
- сначала поднять MinIO на назначении, создать бакет `karaoke`.

## 6. План двухпроходного переноса

### Фаза 0. Подготовка (заранее, прод работает)

1. Установить Docker на `sm-karaoke` (`docker.io` из apt), создать внешнюю
   сеть `karaokenet`.
2. Скопировать образ MinIO **той же** версии/дайджеста, что на источнике:
   `minio/minio:latest` = RELEASE.2025-09-07T16-13-09Z,
   digest `sha256:14cea493d9a34af32f524e538b8346cf79f3321eff8e708c1e2960462bd8936e`.
   Варианты: `docker pull` на назначении напрямую, либо `docker save | gzip`
   на источнике и перенос через рабочую машину.
3. Развернуть `karaoke-storage` на назначении по образцу
   `deploy/docker-compose-storage.yml`, с теми же
   `MINIO_ROOT_USER`/`MINIO_ROOT_PASSWORD` и `--console-address :9001`.
   Данные — на новом большом диске (932 GB свободно).
4. Установить `mc` на назначение (бинарник `dl.min.io` или копия с источника
   через рабочую машину).
5. Создать alias на оба S3-endpoint с корректными кредами.

### Фаза 1. Bulk-проход (прод работает, ~5.5–6.5 ч)

6. Запустить `mc mirror --preserve --overwrite src/karaoke dst/karaoke`.
   - Процесс идемпотентен; при обрыве сети — перезапуск продолжит с места.
   - `--preserve` перенесёт bucket policy и anonymous-настройки.
7. По завершении — `mc diff src/karaoke dst/karaoke`. Допустим непустой вывод,
   отражающий объекты, записанные во время bulk (единицы-сотни).

### Фаза 2. Окно заморозки (15–30 мин)

8. Остановить писателей в MinIO. Кандидаты: `karaoke-app`, `karaoke-web`
   (и, при необходимости, `karaoke-public`). Точный список согласовать с
   владельцем; `karaoke-db` не трогать.
9. Инкрементальный проход:
   `mc mirror --overwrite --remove src/karaoke dst/karaoke`.
   Ожидаемое время — минуты (новых/изменённых объектов десятки-сотни,
   см. 2.5), плюс обход списка 59 707 объектов.
10. Верификация: `mc diff src/karaoke dst/karaoke` (пусто),
    `mc stat dst/karaoke` (objects = 59 707, size = 444 GiB).
11. Переключить `STORAGE_KEY`/`STORAGE_SECRET` и endpoint приложения на
    локальный MinIO назначения (в т.ч. `STORAGE_PROXY_URL`/minio-proxy, см.
    `docker-compose-web.yml`), запустить `karaoke-app`/`karaoke-web` на новом
    сервере.
12. Убедиться в отсутствии ошибок в логах, после чего объявлять cutover
    завершённым. Источник MinIO остановить, но **не удалять** данные до
    подтверждённого окончания окна отката (например, 24–72 ч).

### Откат

Пока данные источника не удалены — откат сводится к возврату конфигов на
`89.125.103.63:9000`. Отдельный reverse-`mc mirror` не требуется, если
источник не получил изменений после cutover.

## 7. Оценка времени

### 7.1. Чистое время передачи 444 GiB (477.26 GB = 3 818 Гбит)

| Скорость канала | Время (чистое) | С overhead/неплотностью (+15%) |
|---|---|---|
| 100 Мбит/с | ~10.6 ч | ~12.2 ч |
| **200 Мбит/с (измерено)** | **~5.3 ч** | **~6.1 ч** |
| 500 Мбит/с | ~2.1 ч | ~2.4 ч |
| 1 Гбит/с | ~1.06 ч | ~1.2 ч |

Измеренные точки (S3 API, реальный путь dest→source):

| Режим | На поток | Агрегат | Примечание |
|---|---|---|---|
| 1 поток | 4.88 МБ/с (39 Мбит/с) | 39 Мбит/с | узкое место — один TCP-поток |
| 4 потока | 4.88 МБ/с | **~156 Мбит/с** | почти линейно |
| 8 потоков | 3.02 МБ/с | **~192 Мбит/с** | рост замедляется |
| 16 потоков | 1.62 МБ/с | **~195 Мбит/с** | плато ~200 Мбит/с |

Вывод: **практический потолок канала ~180–200 Мбит/с**. Для 444 GiB это
**~5.5–6.5 часа** полезной передачи. Рекомендуемая параллельность для
`mc mirror` — **8–12 потоков** (дальше только растёт число ошибок
`kex_exchange_identification`/снижение на поток, агрегат не растёт).

### 7.2. Overhead на мелкие объекты

- 6 532 объекта `<1 MiB` (из них 3 268 `<64 KiB`): при 8–12 потоках и
  latency S3 ~5–20 мс overhead составляет порядка десятков секунд — **менее
  1%** от общего времени.
- Листинг 59 707 объектов — секунды.
- Итог: overhead в основном от сетевого TLS/HTTP и неполной утилизации
  канала, заложен в +15% к чистому времени.

### 7.3. Время второго прохода

Новых/изменённых объектов ожидается порядка **сотен** (за 7 дней — 499).
Даже с учётом полного обхода списка инкремент укладывается в **2–5 минут**,
плюс 5–10 минут на верификацию `mc diff` и переключение конфигов. Окно
заморозки 15–30 минут выбрано с запасом.

## 8. Риски и митигация

| # | Риск | Вероятность | Влияние | Митигация |
|---|---|---|---|---|
| R1 | **SSH source↔dest не настроен** — блокирует rsync | высокая (факт) | среднее | Использовать S3-метод (mc), которому SSH не нужен |
| R2 | **Неверные креды `mc` на источнике** (`minio_key`) | высокая (факт) | среднее | Пересоздать alias с `${STORAGE_KEY}`/`${STORAGE_SECRET}` |
| R3 | **3.8 GiB RAM на назначении** — риску OOM при MinIO + JVM + PostgreSQL + nginx | средняя | высокое | Swap 8 GiB, `-Xmx1200m`, лимиты cgroup (см. `ram-profile.md`) |
| R4 | Запись в бакет во время bulk (медленная, но есть) | средняя | низкое | Двухпроходная схема: инкремент в окно заморозки |
| R5 | **Источник занят на 94% (32 GB free)** | высокая (факт) | среднее | `mc mirror` только читает источник; не использовать источник как staging; не писать туда |
| R6 | Копирование `.minio.sys` поверх нового MinIO сломает старт | низкая | высокое | НЕ копировать `format.json`/`pool.bin`; IAM задать env, policy — `mc mirror --preserve` |
| R7 | Несовпадение версий MinIO source/target | низкая | среднее | Использовать тот же дайджест образа `sha256:14cea493…` |
| R8 | `--remove` удалит «лишние» объекты на target | низкая | среднее | Это желаемое поведение; применять только во 2-м проходе после остановки писателей |
| R9 | Порт 9000 назначения по умолчанию закрыт/недоступен писателям | средняя | высокое | После старта MinIO проверить доступность 9000 с писателей; при блокировке — открыть в firewall/панели |
| R10 | Пропуск писателя при остановке → потеря/рассинхрон | средняя | высокое | Согласовать полный список писателей; проверить лог-обращения к MinIO перед окном |
| R11 | Обрыв канала на 5–6 ч bulk | средняя | низкое | `mc mirror` идемпотентен, перезапуск продолжает; запускать под `nohup`/`tmux` |
| R12 | Ошибка в `STORAGE_PROXY_URL`/minio-proxy при переключении | средняя | среднее | Проверить конфиги `docker-compose-web.yml` и nginx-proxy до окна; держать откат |
| R13 | Удаление данных источника до верификации | низкая | критическое | Не удалять данные источника 24–72 ч после cutover |

## 9. Команды (для исполнения при cutover)

> ВНИМАНИЕ: ниже — только для фазы cutover. В рамках research ничего не
> запускалось и не копировалось. Команды приведены с абсолютными путями и
> фактическими кредами из инвентаря.

### 9.1. Подготовка назначения (docker)

```bash
# на sm-karaoke (188.127.240.124), от root
apt-get update && apt-get install -y docker.io
docker network create karaokenet 2>/dev/null || true

# образ той же версии, что на источнике
docker pull minio/minio:latest
docker image inspect minio/minio:latest --format '{{index .RepoDigests 0}}'
# ожидаем: minio/minio@sha256:14cea493d9a34af32f524e538b8346cf79f3321eff8e708c1e2960462bd8936e
```

```yaml
# /opt/minio/compose/docker-compose.yml на sm-karaoke
services:
  karaoke-storage:
    image: minio/minio:latest
    container_name: karaoke-storage
    environment:
      - MINIO_ROOT_USER=${STORAGE_KEY}   # фактическое значение — в env контейнера источника
      - MINIO_ROOT_PASSWORD=${STORAGE_SECRET}   # фактическое значение — в env контейнера источника
    ports:
      - "9000:9000"
      - "9001:9001"
    command: server /data --console-address ":9001"
    volumes:
      - /opt/minio/data:/data
    restart: always
```

### 9.2. Установка `mc` и alias (на назначении)

```bash
curl -fsSL https://dl.min.io/client/mc/release/linux-amd64/mc -o /usr/local/bin/mc
chmod +x /usr/local/bin/mc

# ВАЖНО: корректные креды (не minio_key/minio_secret)
mc alias set src http://89.125.103.63:9000 "$STORAGE_KEY" "$STORAGE_SECRET"
mc alias set dst http://127.0.0.1:9000      "$STORAGE_KEY" "$STORAGE_SECRET"

mc ls src/          # должен показать bucket karaoke
mc admin info src   # 59 707 objects, 444 GiB
```

### 9.3. Проход 1 — bulk (прод работает)

```bash
# под tmux/nohup, 8-12 потоков
tmux new -s mirror
mc mirror --preserve --overwrite \
  --summary \
  src/karaoke dst/karaoke

# контроль
mc diff src/karaoke dst/karaoke | head
```

### 9.4. Проход 2 — окно заморозки (после остановки писателей)

```bash
# 1) ОСТАНОВИТЬ писателей (точный список согласовать):
#    karaoke-app, karaoke-web (при необходимости karaoke-public)

# 2) инкремент
mc mirror --overwrite --remove --summary \
  src/karaoke dst/karaoke

# 3) верификация
mc diff src/karaoke dst/karaoke          # ожидается пусто
mc stat dst/karaoke                      # 59 707 objects / 444 GiB
mc anonymous get dst/karaoke             # policy перенесена (download)

# 4) переключить конфиги приложения на локальный MinIO назначения
#    (STORAGE_KEY/STORAGE_SECRET/endpoint, STORAGE_PROXY_URL) и запустить писателей.
```

### 9.5. Откат (в окне 24–72 ч)

```bash
# вернуть конфиги приложения на http://89.125.103.63:9000
# источник не останавливать и данные не удалять до подтверждения
```
