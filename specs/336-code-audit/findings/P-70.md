## Сверки (без severity)

1. **Политика удаления пользователя сайта.** `ON DELETE CASCADE` на `tbl_subscriptions` (P-70-03) может быть осознанной политикой «удалил пользователя — удалил всё». Если да — запись P-70-03 уходит в `WONTFIX`, но тогда нужно решить, как выполняются требования по хранению платёжных документов и возвраты по удалённым пользователям. Одновременно `tbl_site_chat_messages.site_user_id` (`19:13`) вообще без FK — сообщения остаются осиротевшими; та же политика в схеме выражена двумя противоположными способами.
2. **`docker.sock` и root в контейнере `karaoke-app`.** `- /var/run/docker.sock:/var/run/docker.sock` (`deploy/docker-compose-app.yml:65`, комментарий про demucs и #126) вместе с отсутствием инструкции `USER` в `deploy/karaoke-app/Dockerfile` (образ работает от root) даёт контейнеру root-эквивалент на хосте; рядом смонтированы X11-сокет и `~/.Xauthority` (`deploy/docker-compose-app.yml:55–56`) — доступ к X-сессии пользователя. Признано рабочим компромиссом ради `docker run demucs`; вопрос владельцу: оставить (и зафиксировать в ADR), либо перейти на `docker-socket-proxy`/rootless и отдельный сервис demucs.
3. **nginx-конфиги вне порции.** Фокус «/changerecords, /api/properties, body size, таймауты, кеш, security-заголовки» в P-70 проверить нельзя: конфигов nginx в списке порции нет, есть только их монтирования (`docker-compose.yml:135`, `docker-compose-public.yml:10`, `docker-compose-web.yml:55`). Проверка `deploy/prod-single-host/80to8897`, `deploy/karaoke-webvue3/*.conf`, `deploy/karaoke-web/minio-proxy-local.conf` — за порцией, где эти файлы лежат.
4. **`03_events.sql:37` — `SET DEFAULT` на identity-колонке.** После `ADD GENERATED ALWAYS AS IDENTITY` (`:20`) идёт `ALTER COLUMN id SET DEFAULT nextval(...)`. По документации PostgreSQL identity-колонка не может иметь DEFAULT, ожидается `ERROR: column "id" … is an identity column`; проверить на PG 16 в этой порции нельзя (запрет на подключение к БД). Если ошибка подтвердится — это третья точка, ломающая инициализацию с нуля (к P-70-01), хотя на существующих БД оператор применяет файл вручную без `ON_ERROR_STOP`, и индекс с триггером создаются.
5. **`16_cart_and_orders.sql:76` снимает UNIQUE с `yookassa_payment_id`.** Для корзины это необходимо (несколько строк на один платёж), но инвариант «одна одиночная покупка = один платёж» всё ещё выразим частичным уникальным индексом (`WHERE order_id IS NULL AND yookassa_payment_id <> ''`). Сейчас идемпотентность держится только на проверке статуса в `PublicPaymentController.webhook` (`karaoke-web`, другая порция): при двух одновременных доставках вебхука обе видят `PENDING`, обе вызывают `verifyAndFetch` и обе делают read-modify-write `site_premium_until` от одного и того же значения — одно из продлений теряется (lost update), а при разных `periodDays` итог зависит от порядка записи. Передать лиду для сверки с порцией karaoke-web.
6. **`12`/`13`/`14`/`17` и `16:54` массово переписывают строки.** `UPDATE … SET recordhash = md5(…)` проходит по всем строкам `tbl_site_users`/`tbl_subscriptions` и через триггер `update_last_updated_*` ставит `last_update = now()` каждой строке (для `16` — всем подпискам). Потребителей `last_update` у этих таблиц не найдено (`grep` по `karaoke-app/src`: инкрементальные выборки есть только для `tbl_songs`, `tbl_processes`, `tbl_events`), поэтому следствий не зафиксировано — но при появлении инкрементального sync это даст массовый «грязный» набор.
