# Устойчивость админского SPA webvue3: ответы, выборки и автосохранение

> **Status**: active
> **Feature Key**: admin-web-client-robustness
> **Last Updated**: 2026-10-25
> **Spec**: [specs/380-pkg-s2-17/report.md](../../specs/380-pkg-s2-17/report.md)
> Per-feature документ по [Constitution VI FR-009](../../.specify/memory/constitution.md).

## Что делает

Не даёт админскому SPA `webvue3` применить чужой ответ, показать чужой набор строк или
потерять правку администратора: асинхронные ответы адресуются объекту запроса, массовые
операции работают только по подтверждённому серверному snapshot, автосохранение карточки
песни не теряет правки последней секунды, а лёгкий редактор разметки не стирает ноты,
аккорды и привязку к ладу.

## Зачем

Аудит #336, пакет `PKG-S2-17` (OpenProject #380, записи BR-087, BR-088, BR-093, BR-124,
BR-125, BR-370, BR-379, BR-380, BR-388, BR-399, BR-410, BR-411, BR-416, BR-417, BR-426).
До правки:

- `SongEdit` считал статус премиум-публикации из полей, которых не было в `SongDTO` —
  блоки статуса и кнопки «Повторить» не рендерились никогда (BR-087).
- Автосейв карточки песни откладывался на 1 с и нигде не сбрасывался: правка за секунду
  до перехода по стрелке или закрытия карточки в БД не уходила, а локальная копия песни
  выглядела сохранённой — после F5 правка исчезала (BR-088).
- Дайджест песен и HR-список коммитили любой пришедший ответ: таблица показывала строки
  прежнего фильтра, а «repair» в модалке HR отправлял ремонт ЧУЖОЙ песни (BR-093, BR-380).
- Массовое удаление процессов брало id из snapshot прошлого фильтра (BR-388).
- Ручная публикация в ВК вызывала несуществующий Vuex-action и брала id из
  `state.currentSongId`, которого нет (BR-124).
- Ответы `findAudioParent`/`showSubsEdit`/`loadCoAuthors` применялись к открытой сейчас
  песне, а не к той, для которой ушёл запрос (BR-125).
- Inline-сохранение `sort_order` автора отправляло payload, который бэкенд не принимает
  (HTTP 400 на каждое изменение колонки) (BR-370).
- `undefined` в параметрах сериализовался как `pageSize=undefined` — Spring отвечал 400,
  серверный фильтр истории прослушиваний и массовое удаление заданий не работали
  (BR-379, BR-426).
- `CustomConfirm` не выставлял `confirmed`, поэтому форма редактирования процесса
  закрывалась без сохранения (BR-399).
- Дайджест share-ссылок грузил только первую страницу из 25 строк (BR-410).
- Клик по штатной кнопке `EXCLUSIVE` отправлял дату `NaN.NaN.N` — грид публикаций падал
  с HTTP 500, а испорченный фильтр переживал F5 (BR-411).
- Лёгкий редактор разметки при каждом сохранении стирал у всех голосов ноты, аккорды и
  привязку к ладу (BR-416), а закрытие в течение 3 с теряло правку (BR-417).

## Как работает

1. **Адресность ответа.** Компонент фиксирует id на отправке (`requestedId`) и применяет
   ответ только если объект всё ещё тот же; сохранение получает явный адрес
   (`payload.songId`), а не читает `currentSongId` в момент ответа.
2. **Поколение запроса.** У загрузки — номер поколения (`createRequestGeneration` из
   `webvue3/src/lib/target-request-guard.js`); результат применяет только владелец
   текущего номера, флаг загрузки снимает тоже он, `finally` снимает его при ошибке.
3. **Готовность серверной выборки.** `fetchBulkSelectionIds` помечает выборку устаревшей
   до запроса, применяет snapshot своего поколения, при сбое оставляет пустой; массивные
   кнопки активны только при `bulkSelectionReady`. После операции snapshot пересчитывается.
4. **Очередь автосохранения.** `webvue3/src/lib/autosave-queue.js`: текущая задача + одна
   ожидающая, `whenIdle()` для flush. Карточка песни сохраняет непустой `diff` перед
   сменой песни и в `beforeUnmount`; при неудаче навигация не выполняется (fail-closed).
5. **DTO как контракт.** `SongDTO` отдаёт состояние премиум-автопубликации
   (`newsPremium*`, `premiumAttempt*`, `*AutoPublishState`, `premiumAutoPublishLastError`).
6. **Сериализация параметров.** `getParamStringToSend` пропускает `undefined`/`null` —
   «параметра нет» вместо строки `undefined`, и сервер применяет свой `defaultValue`.
7. **Серверная пагинация share-ссылок.** UI передаёт `page`/`pageSize`/`sortBy`/`sortDir`,
   рендерит ответ сервера; `perPage` приводится к диапазону бэкенда 1..100; сортировка —
   по белому списку колонок, неизвестная колонка не притворяется сортировкой.
8. **Дата окна публикаций.** Невалидная/пустая дата — это «границы нет»: `dateTo`
   очищается, на бэкенд уходит пустая строка, а контроллер отвечает 400 на некорректный
   формат вместо 500.
9. **Поля маркеров.** Payload маркеров собирает `markersToSave()`, который «проносит»
   `note`/`chord`/`stringLad`/`lockLad` без изменений.

## Инварианты

- Устаревший ответ не меняет состояние: применяет только владелец последнего поколения.
- Массовая операция невозможна без готового snapshot текущего фильтра.
- Несохранённая правка карточки песни либо сохраняется, либо блокирует навигацию с
  видимой ошибкой — молча не теряется.
- `SongDTO` содержит все поля, по которым UI принимает решение; новых полей «в обход
  DTO» не появляется.
- Параметр со значением `undefined` не попадает в тело запроса.
- Сохранение маркеров голоса не меняет `note`/`chord`/`stringLad`/`lockLad`.
- Подтверждение (`CustomConfirm`) всегда возвращает явный `confirmed: true|false`.

## Известные ловушки

- **Флаг загрузки нельзя снимать всем.** `setSongsDigestIsLoading(false)` в `.then`
  любого ответа возвращает «таблица пуста, но не загружается» — снимает только владелец
  поколения, иначе `finally` при ошибке.
- **`healthReportListSongId` — не то же, что `currentSongId`.** Это песня ПОКАЗАННОГО
  списка; сверка `item.songId` с ней — fail-closed защита «repair» от чужой песни. Не
  заменяйте её на текущий id модалки: именно расхождение этих двух значений и было
  дефектом BR-380.
- **Fallback массовой выборки на `items` запрещён.** Он превращает «операцию по фильтру»
  в «операцию по видимой странице»; при пустом snapshot кнопки обязаны быть неактивны.
- **`isSaving`-guard вместо очереди теряет вызов.** `if (this.isSaving) return` выглядит
  безопасно, но именно так терялся flush перед навигацией/размонтированием. Для flush
  нужен `whenIdle()`, а не повторный `executeSave()`.
- **`executeSave` в `beforeUnmount` работает, только если снимок `diff` берётся
  синхронно.** Метод читает `diff`/`this.song` до первого `await`; не переносите сбор
  params за `await` — после демонтажа компонента данных уже нет.
- **`markersToSave` обязателен и в модалке.** `SongKaraokeEditorView` и karaoke-public его
  используют, а локальная копия в `SongKaraokeEditorModal` осталась со старым поведением и
  стирала поля админа. Новая копия сборки payload — это возврат BR-416.
- **`status` в share-ссылках считается на клиенте** (`active`/`expiresAt`), поэтому
  серверной сортировки по нему нет; `sortable: true` вернул бы «сортировку по одной
  странице».
- **`NaN.NaN.N` — это не дата.** `stringDDMMYYaddDays('')` раньше возвращала такую строку;
  бэкенд отвечал 500, а значение сохранялось в `webvueProp` и переживало F5, поэтому
  сохранённый фильтр нужно чистить при загрузке, а не только не создавать заново.
- **`SongDTO` — общий контракт карточки и списка.** Добавление поля только в
  `/api/song` (отдельным endpoint'ом) оставило бы список без него; `toDTO()` не должен
  ходить в БД за новыми значениями (N+1 на 18k песен).
- **Статические тесты SFC проверяют исходник, а не поведение.** Для `SongEdit`,
  `SubsEdit` и `SongKaraokeEditorModal` нет `@vue/test-utils`; тесты читают `.vue` и
  сверяют инварианты. Комментарии в тесте нужно вырезать до анализа — иначе тест
  «находит» старый код в собственном объяснении дефекта.
