# Протокол порции аудита и ревью лида

> Карта #337 / задача #336. Контракт исполнения: одна порция — один цикл «аудитор → лид».
> Основание: `rubric.md`, `inventory.md`, `coverage-ledger.csv`. Снимок кода: `master` @ `1977838a`.

## 1. Роли

| Роль | Кто | Что делает | Чего не делает |
|---|---|---|---|
| Лид | основная сессия | выбирает порцию, ставит `IN PROGRESS`, проверяет каждую запись по диску, присваивает `BR-NN`, ведёт реестр и покрытие, собирает отчёт, пишет в трекер | не пишет код, не перезапускает контейнеры |
| Аудитор | read-only субагент | читает файлы порции, ищет дефекты по рубрике, пишет `findings/P-XX.md` | не правит код/конфиги/БД, не создаёт ветки и коммиты, не запускает docker |
| Владелец | владелец проекта | разбирает `NEEDS-VERDICT`, утверждает отчёт, закрывает #336 | — |

Параллелизм: 3 аудитора одновременно, по одной порции на аудитора. Лид не запускает новую порцию, пока не разобрал предыдущую пачку (иначе реестр расходится).

## 2. Жизненный цикл порции

1. **Выбор.** Лид берёт следующую порцию по `schedule.md`, отмечает в `status.md`: `P-XX | IN PROGRESS | <аудитор> | <дата>`.
2. **Брифинг.** Аудитор получает: ID порции, путь к `rubric.md` и `protocol.md`, SHA, список файлов из `coverage-ledger.csv`, релевантные домены `knowledge/` (knowledge-first), запрет на запись куда-либо, кроме своего `findings/P-XX.md`.
3. **Чтение.** Аудитор читает **все** файлы порции. Файл > 2 000 строк читается целиком, но допускается приоритет: публичные входы → запись данных → конкурентность → ошибки.
4. **Запись находок.** Формат — § 9 рубрики, временные ID `P-XX-NN`. В конце файла — раздел «Покрытие»: перечень всех файлов порции и по каждому «просмотрен / находок нет».
5. **Самопроверка аудитора.** Каждая запись имеет цитату, `path:line`, путь достижимости, автора по `git blame`; нет записей без доказательства; нет стилевых замечаний.
6. **Ревью лида.** Лид проверяет по диску (чек-лист § 5), принимает / возвращает на доработку (не более 2 кругов), присваивает `BR-NN`, вносит в `registry.csv`.
7. **Закрытие порции.** `status.md`: `P-XX | DONE | <BR найдено> | <LOC покрыто>`; лид сверяет покрытие с ведомостью.

## 3. Что обязан сделать аудитор

- Прочитать `rubric.md` и `protocol.md` до первой записи.
- Прочитать доменные документы, если порция их касается (`knowledge/domains/<domain>/domain.md` + компоненты; ADR).
- Для каждой записи: цитата, `path:line`, SHA `1977838a` (или иной, если лид указал), путь достижимости, автор `git blame --line-porcelain`.
- Проверить, не покрыт ли класс существующим guard'ом (`tooling-coverage.md`): если покрыт — не дублировать, а указать «покрыто guard'ом X» и не включать в отчёт.
- Отделять «дефект» от «сверки»; спорное — `NEEDS-VERDICT`, не выдумывать severity.
- Писать по-русски, без эмоций, без предложений по рефакторингу за рамками поправки.

## 4. Чего аудитор не делает

- Не меняет ни один файл, кроме `specs/336-code-audit/findings/P-XX.md`.
- Не создаёт ветки, коммиты, worktree, не делает `git checkout`.
- Не запускает `docker`, не перезапускает контейнеры, не пишет в БД, не меняет прод-данные.
- Не запускает долгие сборки; локальные тесты — только по указанию лида.
- Не включает в отчёт форматирование, naming, «мертвый код без риска», отсутствующие фичи.
- Не ставит S1 «на всякий случай»: S1 требует доказанного публичного/денежного/данных пути.

## 5. Чек-лист лида (по диску, не по ответу субагента)

Для каждой записи:

1. `path:line` существует; цитата совпадает с файлом на SHA (сверка `sed -n`).
2. Класс соответствует рубрике; severity обоснована и не завышена.
3. Путь достижимости описан; для S1 — публичный маршрут или денежный/данные-путь.
4. Автор подтверждён `git blame` по указанной строке.
5. Нет дубля в `registry.csv` (проверка по ключу «механизм + семейство файлов»).
6. Формат записи полный; `Статус` и `Проверено лидом` заполнены.
7. Запись не является стилем/вкусовщиной/уже покрытым guard'ом.

Если запись не проходит — возврат аудитору с конкретным пунктом; после 2 кругов лид правит сам и фиксирует это в `registry.csv` (`review: lead-rewrite`).

## 6. Покрытие

- Источник истины — `coverage-ledger.csv` (1 032 файла, 78 порций).
- В `findings/P-XX.md` раздел «Покрытие» перечисляет все файлы порции; лид сверяет множества: `comm -3` между файлами порции из CSV и списком в findings.
- Файл без строки в «Покрытии» = порция не принята.
- Итоговая сходимость: 78 порций `DONE`, 1 032 файла покрыты, 0 пропусков; проверка — скриптом в `status.md` § «Сходимость».

## 7. Реестр и дедупликация

`registry.csv`, колонки: `br_id,portion,class,severity,file,line_start,line_end,root_cause_key,status,review`.
`root_cause_key` — нормализованная строка «механизм + семейство файлов» (например, `jdbc-close-missing:karaokeapp/services`). При совпадении ключа новая находка не получает новый `BR`, а добавляется в `locations` существующей записи.

## 8. Эмпирика на `nsa-i9`

Разрешено без согласия:

- чтение логов `docker logs karaoke-app` (read-only);
- read-only API-запросы к запущенному контейнеру;
- Playwright против уже запущенной сборки (без изменения данных);
- локальные unit-тесты, не пишущие в прод-БД;
- SQL `EXPLAIN`/`SELECT` в локальной БД.

Требует согласия владельца (помечается, не блокирует):

- перезапуск/пересборка `karaoke-app` и любых контейнеров;
- запись в БД, миграции, изменение прод-данных;
- доступ к прод-серверу.

## 9. Сборка отчёта

`bug-report.md`:

1. Шапка: охват, SHA, методика, дата, авторство, число записей по severity/классам/модулям.
2. Сводка: таблица S1/S2/S3, классы, топ-риски.
3. Записи: сгруппированы по severity (S1 → S3), внутри — по модулю; сквозная нумерация `BR-001`.
4. Раздел «Требует решения владельца» (`NEEDS-VERDICT`).
5. Раздел «Тесты» (severity ≤ S3).
6. Приложение: покрытие (78 порций / 1 032 файла), исключения, реестр.

## 10. Доставка

1. Ветка `docs/336-code-audit` (номер ветки — `tools/reserve-branch-number.sh`, если политика требует), docs-only коммит: `rubric.md`, `protocol.md`, `inventory.md`, `coverage-ledger.csv`, `findings/*`, `bug-report.md`.
2. PR → CI → merge (без `--delete-branch`).
3. Вложение `bug-report.md` в #336 через `POST /api/v3/work_packages/336/attachments` (multipart, `metadata` не обязателен).
4. Комментарий в #336: ссылка на PR, md5 файла и вложения, число записей.
5. `mark-review`; закрытие #336 — после проверки владельцем.

## 11. Бюджет и остановка

- Темп: 3 порции параллельно, ревью после каждой пачки.
- Промежуточный отчёт после волны 1 (P-35…P-37, публичный периметр и деньги).
- Если бюджет исчерпан: режем в обратном порядке риска (тесты → build/CSS/доки → tools/deploy), публичный периметр и деньги не режем; глубина — только S1/S2 для низкорисковых модулей.
- Остановка только по слову владельца или при исчерпании бюджета с зафиксированным остатком в `status.md`.
