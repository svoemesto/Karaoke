# PKG-S2-10: целостность данных, ошибки и безопасность (аудит #336)

> **Status**: active
> **Feature Key**: pkg-s2-10-data-integrity
> **Last Updated**: 2026-10-24
> **Branch**: `593-pkg-s2-10`
> **Created**: 2026-10-24
> **Spec**: [`specs/373-pkg-s2-10/report.md`](../../specs/373-pkg-s2-10/report.md)
> **Source**: OpenProject #373 — пакет `PKG-S2-10` бэклога аудита #336

## Что делает

Пакет закрывает 15 записей аудита #336 в `karaoke-app`: гонки очереди
заданий (BR-030, BR-031), неатомарную цепочку шагов (BR-032), падение
воркера на пустых `process_args` (BR-033), инъекцию полей в
`copyfieldsfromanother` (BR-048), SSRF через прокси обложек (BR-049),
подмену `rootFolder` через `POST /api/song/update` (BR-050), перезапись
чужих изменений после сетевого вызова публикации (BR-063), sleep на
каждой итерации массового поиска текста (BR-064), NPE на неизвестном
аккорде (BR-071), «успех» при неудавшемся сохранении песни (BR-101,
BR-102), N+1 по альбомам в `toDTO()` (BR-104), неполный список колонок
`INSERT` (BR-108) и path traversal в SmartCopy (BR-109).

## Зачем

Все 15 дефектов — класса S2: они либо теряют пользовательские данные и
идентификаторы публикаций, либо останавливают очередь/лейн, либо дают
запись/чтение файлов и SSRF на admin-периметре. Часть из них
воспроизводилась штатными действиями оператора (ввод поля «Поля:» в UI,
кнопка массового поиска текста, импорт папки, Smart Copy), без подделки
HTTP.

## Как работает

### Очередь заданий

- `KaraokeProcess.saveProgress()` — узкий `UPDATE` percentage-колонок с
  гардом `process_status='WORKING'`; прогресс пишет только цикл воркера.
- `KaraokeProcess.claimForWorking()` — атомарный переход
  `WAITING → WORKING` с проверкой числа строк; поток без claim не работает.
- `createProcess()` не удаляет `WAITING`/`CREATING` (single-flight),
  пересоздаёт только терминальные задания и валидирует `args` до вставки.
- `separate()` нумерует шаги (`process_order`) и проставляет общий
  `process_chain_id`; при `ERROR` шага остальные шаги цепочки становятся
  `ERROR`, а статус песни агрегируется по завершении цепочки.

### Песни и файлы

- `Song.saveToDb(): Boolean` + `saveToDbLocked()` коммитит только при
  реально выполненном `UPDATE`; `loadFromDbById` пробрасывает
  `SQLException`.
- `Song.toDTO()` не обращается к БД; `Song.toDTOsWithAlbumNames()`
  заполняет `albumName` пакетно.
- `getSqlToInsert()` включает поля, которые раньше терялись на `DEFAULT`.
- `getFormattedChords()`/`getTransposingChord()` сохраняют исходный
  аккорд, если он вне справочника `MusicChord`.
- `SmartCopyPathPolicy` валидирует каталог экспорта и шаблон имени,
  `doSmartCopy` ставит права `755`/`644` вместо `777`/`666`.

### Контент и admin-эндпоинты

- `SongCopyFieldsPolicy` — фиксированный whitelist полей (без `ID`).
- `AlbumCoverUrlPolicy` — только публичные `http(s)`, порты 80/443, лимит
  тела и проверка сигнатуры картинки.
- `LibraryRootPolicy` — `rootFolder` read-only и только под разрешённым
  корнем библиотеки.
- `SongPublicationFlagsPolicy` — после сетевого вызова флаги публикации
  переносятся на свежую строку, чужие поля не перезаписываются.
- `LyricsSearchPacing` — пауза отсчитывается от последнего фактического
  запроса, а не от индекса в списке.

## Инварианты

1. На строку `tbl_processes` не более одного писателя терминальных полей;
   прогресс не может изменить `process_status`.
2. Шаг N+1 цепочки не стартует, пока N не `DONE`; `ERROR` останавливает
   цепочку, а песня получает терминальный статус только по её завершении.
3. `saveToDb() == true` означает, что `UPDATE` затронул строку; иначе
   `false` и (для locked) `rollback`.
4. `null` из `loadFromDbById` означает только «строки нет».
5. Список копируемых полей — только контентные поля из
   `SongCopyFieldsPolicy.allowed`; `ID` отклоняется всегда.
6. Прокси обложек не ходит в приватные/служебные адреса и не отдаёт
   не-изображения.
7. `rootFolder` нельзя изменить запросом на произвольный путь.
8. Экспортный каталог SmartCopy — абсолютный нормализованный путь вне
   системных каталогов и исходной библиотеки; имя файла без `..` и
   разделителей; права `755`/`644`.
9. Пауза массового поиска текста не выполняется, если запрос не
   отправляется.

## Известные ловушки

- **`process_chain_id` пишется узким `UPDATE`, а не `save()`.** Колонка
  намеренно не входит в полный `save()` (FR-019), иначе устаревший объект
  затирал бы её.
- **`saveProgress()` без `WORKING`-гарда бесполезен.** После `DONE`
  строка не обновляется — это защита от «воскрешения» задания, а не
  ошибка; не добавляйте `process_status` в SET прогресса.
- **`createProcess()` теперь single-flight.** Повторный вызов, пока
  задание `WAITING`/`WORKING`, возвращает `0` и не пересоздаёт его; не
  опирайтесь на прежнее «удалить и создать заново».
- **Цепочка и `process_order`.** Воркер выбирает `WAITING` по
  `(priority, order, id)`, поэтому нумерация шагов обязательна; ручная
  правка `order` в админке может нарушить порядок.
- **`saveToDb(): Boolean` обратно совместим по вызову, но не по смыслу.**
  Игнорировать `false` в новом коде нельзя: результат не применён.
- **`toDTO()` больше не заполняет `albumName`.** Для списков с названием
  альбома используйте `Song.toDTOsWithAlbumNames()`, иначе поле будет
  пустым.
- **`album_id` в `INSERT` пишется только при непустом значении.** Это
  сделано, чтобы `null` не превращался в строку `"null"`; не «оптимизируйте»
  обратно в безусловную колонку.
- **`exclusive` не переносится `getSqlToInsert()`.** В сущности `Song` нет
  поля; это осознанно оставлено владельцу (см. отчёт).
- **SSRF-политика не является доменным allowlist.** SearXNG отдаёт
  произвольные внешние хосты, поэтому разрешены любые публичные адреса;
  строгий список доменов — решение владельца.
- **`rootFolder` из формы приходит всегда.** UI присылает текущее
  значение; неизменённое значение принимается, любое другое — `400`.
- **`getFormattedChords()` рендерит только по маркерам строки.** Один
  `CHORD`-маркер без `ENDOFLINE`/`NEWLINE` не попадёт в вывод — это
  свойство рендера, а не регрессия.
- **Флаги публикации живут в `player_readiness_flags`.** `copyFlags`
  трогает только их; не заменяйте на копирование всего JSON-поля — потеряете
  флаги, выставленные параллельно.
