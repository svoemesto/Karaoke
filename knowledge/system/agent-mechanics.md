# Механика работы агента: 12 правил, на которых теряются шаги

> **Домен**: system (cross-cutting)
> **Компонента**: правила работы агента в этом репозитории. Подробные разборы и
> тексты ошибок — в [`agent-mechanics-cases.md`](agent-mechanics-cases.md).
> Составлено по разбору 276 сессий (55 031 шаг) и 26 прогонам локальных моделей
> (задачи KARAOKE-392…404, 2026-11-03…05).

## Зачем

Потерянные шаги — не про домен и не про незнание API, а про **механику**: правку
файлов, пути, запуск проверок и то, что считается сделанной работой. Ниже 12 правил,
сгруппированных по механизму: у каждого — действие, симптом нарушения и прецедент.

Основание — разбор 276 сессий (55 031 шаг):

| Класс ошибки | Случаев | Сессий |
|---|---|---|
| `cannot modify: file has not been read` | 242 | 83 |
| `file changed since it was read` | 125 | 52 |
| `old_string was not found` / `matched N times` | 94 | 43 |
| падение bash-команды (в т.ч. 523 — Gradle, 208 — нет пути) | 768 | — |

**Не делать вообще** (это не правила, а ограничения стенда): не вызывать скиллы;
не ставить зависимости; не ходить в сеть, docker и прод; не трогать файлы вне
задачи. Если задача требует чего-то из этого — это не задача для агента.

## 1. Правка — только инструментом

`read` → `edit`; новый файл — `write`. Не `sed -i`, не `cat > … <<EOF`, не патчи
руками, не форматирование вручную.

**Действие**: прочитать файл перед правкой (после `git checkout`/`reset`/`stash` —
перечитать); `old_string` брать с 3–5 строками контекста и уникальным
идентификатором; массовую замену — с `replace_all`, предварительно сверив число
вхождений.

**Failure**: `cannot modify: file has not been read`, `file changed since it was
read`, `old_string matched N times`. Через heredoc файл получается синтаксически
верным, но с испорченным содержимым — падение выглядит как ошибка теста, а не
записи.

**Что проверено замером (30 прогонов, 48 логов):**

| Запрет | Реальных нарушений | В прогонах, где читали гайд |
|---|---|---|
| `sed -i` | 27 | **2** |
| файл создан через `cat > … <<EOF` | 129 | **десять и больше** (16, 9, 7, 6 в отдельных прогонах) |

То есть **запрет `sed -i` работает**, а **запрет heredoc — нет**: модели
продолжают писать файлы через `cat >` даже прочитав правило. Причина, видимо, в
том, что `write` требует точного содержимого, а heredoc — «одна команда вместо
двух». Отсюда рабочий вывод: heredoc надо **ловить в стенде** (проверка, что файлы
дерева созданы инструментом `write`, или перечитывание файла после записи через
shell), а не уговаривать текстом.

**Прецедент**: файл, записанный через heredoc, получился синтаксически верным, но с
перепутанными `true`/`false` в утверждениях (KARAOKE-401). Прецеденты правила 1 →
[архив](agent-mechanics-cases.md#прецеденты-правила-1--правка-только-инструментом).

## 2. Гигиена дерева и отчёта

В дереве — только файлы задачи; в отчёте — только то, что реально сделано.

**Действие**: перед коммитом `git status --porcelain`; бэкапы, пробники и отчёты в
корне — убрать или положить туда, где им место; в отчёте писать сделанное и
проверенное, а не задуманное.

**Failure**: файлы-бэкапы рядом с кодом, отладочные пробники, отчёты, положенные в корень репозитория; «исправлено» при
нетронутом файле.

**Прецедент**: модель оставила `report.md` в корне репозитория (KARAOKE-401, A/B-прогон) —
не закоммичен, но в дереве.

## 3. Сначала найди, потом читай

Не читать файл в тысячу строк подряд и не перебирать парсеры: сначала найти место,
потом прочитать нужное — целиком и один раз.

**Действие**: поиск по символу (`codegraph`, `grep`) → чтение файла/фрагмента
одним вызовом. Артефакт сборки (JUnit XML, отчёт линтера) читается целиком; если
парсер вернул пусто — сначала найти файл, а не менять парсер.

**Failure**: 10 чтений `Song.kt` (10 174 строки); три парсера XML подряд на один
факт (KARAOKE-399).

## 4. Сбой инструмента — не сбой кода

Линтер, тесты, сборка могут падать из-за среды: нет зависимостей, версия
инструмента не проектная, конфиг не скопирован, каталог не тот.

**Действие**: отличить сбой инструмента от сбоя кода и **сообщить**, чего не
хватает. Не изобретать «починку»: не создавать конфиги, не править вендорные
файлы, не отключать правила.

**Failure**: `Could not download …`, `ESLint couldn't find a configuration file`,
`Cannot find module` — и попытка «исправить» это правкой проекта.

**Прецедент**: `lint:check` падал из-за отсутствия `.eslintrc.cjs` в копии, а не из-за
кода (проверка 2026-11-05); `--offline` без кэша дал «Could not download kotlin-build-tools-impl».

## 5. Чужая зона неприкосновенна

Задача задаёт область. Тест не оправдывает правку прода; найденный по пути дефект —
не разрешение; сломанное чужое — повод откатить свою правку, а не чинить чужое.

**Действие**: менять только файлы задачи; если задача — «только тест», прод-файлы не
трогаются вообще; если твоя правка сломала место, которого ты не касался, — откатить
её (`git checkout`) и проверить, что сломанное ожило, и только потом сужать правку.

**Failure**: переписан модуль с `XMLHttpRequest` на `fetch`, чтобы тест позеленел
(KARAOKE-400); удалены две посторонние зависимости, упал чужой файл (KARAOKE-404);
`return 128` в обход аудит-лога (KARAOKE-396).

## 6. Проверка — после последней правки; отчёт — по критериям

Зелёная проверка до последней правки не считается. Отчёт о готовности — это
перечисление критериев задачи с результатом каждого.

**Действие**: после любой правки — проверка заново; в отчёте — критерий → команда →
результат.

**Failure**: «тесты прошли» по прогону, сделанному до правки; отчёт без единой
команды.

## 7. Тест: красный, с таймаутом, не сложнее правки

Новый тест должен сначала упасть на текущем коде (иначе он ничего не проверяет).
У каждого теста есть таймаут — зависший тест останавливает весь набор. Мок ставится
на **тот** механизм, который использует модуль.

**Действие**: убедиться, что тест красный; задать таймаут; перед моком посмотреть
фактический вызов в модуле (`new XMLHttpRequest()` или `fetch(...)`); если тест
требует больше работы, чем правка, — упростить тест.

**Failure**: тест зелёный и до правки; набор висит на неразрешённом промисе; мок
`fetch` при модуле на XHR (KARAOKE-400).

## 8. Артефакт важнее полноты

Пока нет артефакта (файла, коммита, отчёта), задача не сделана, какой бы полной ни
была проверка. **Бюджет шагов задаёт среда, а не текст правила**: обрыв по числу
вызовов, а не по минутам.

Замерено на 30 прогонах (успех = есть работающий артефакт):

| Исход | Вызовов инструментов |
|---|---|
| успех | 12, 18, 18, 20, 21, 26, **31** — все ≤ 31 |
| провал | **30**, 33, 42, 46, 47, 58, 61, 65, 81, 93 |

По времени исходы не разделяются: успешный прогон шёл 95 минут, провальный — 120.
Поэтому формулировка «три итерации отладки — стоп» **не работала**: модели читали
её и продолжали — 2 часа отладки и ноль коммитов (KARAOKE-400), 65 минут на одно
неверное утверждение (KARAOKE-401). Работает только граница в среде — **40 вызовов**,
после которой успешные прогоны не усекаются (все ≤ 31), а долгие провалы
обрываются.

**Действие**: как только вывод понятен — минимальный артефакт и коммит, потом
улучшения. На границе бюджета — одно атомарное действие: `git add -A && git commit`
и короткий отчёт, что работает и что нет. **Падающие тесты коммитить разрешено**:
видимый долг лучше провала задачи. Обрыв даёт результат: 400 под лимитом оставил
WIP-коммит с 11 тестами (8 проходили) вместо двух часов пустоты.

**Коммит не доказывает успех.** Артефакт проверяется отдельно — компиляцией,
прогоном тестов в отдельной копии, сверкой пути файла. Три прогона дали коммит и
ноль работы: `checkpoint.md` вместо правки (KARAOKE-399, mellum), тест из одного
теста с `1 pass / 0 fail` (KARAOKE-403), `Unresolved reference` в закоммиченном
коде (тот же класс задачи на Q8_0).

**Failure**: два часа на стенд, ноль коммитов (KARAOKE-396, KARAOKE-400); 65 минут
на одно неверное утверждение (KARAOKE-401); коммит с нерабочим кодом, принятый за
успех. Прецеденты → [архив](agent-mechanics-cases.md#прецеденты-правила-8--артефакт-важнее-полноты).

## 9. Вывод — из факта, а не из догадки

Проверяй поведение кодом и запуском: находка может быть неактуальна, метка в
комментарии ничего не доказывает, цитата должна быть дословной, вывод — не
противоречить своим же доказательствам. Компилятор и код — арбитры, не рассуждение.

**Действие**: воспроизвести дефект в текущем коде; состояние определять поведением,
а не наличием комментария; цитировать дословно; при падении `assert` помнить, что
`assert.equal(actual, expected)` печатает `actual !== expected`, и смотреть строку,
которую дал раннер; проверять по подстроке только с границами.

**Failure**: «нет метки `# BR-604` → дефект не исправлен» и правка рабочего кода;
заголовок «дефект воспроизводится» при теле, доказывающем обратное; `false !== true`
прочитано наоборот и полчаса поиска причины в раннере (KARAOKE-401).

## 10. Среда и сборка

Известные факты, на которых теряются шаги:

- `GRADLE_USER_HOME` — внутрь дерева (`$PWD/.gradle`), задачи — точечно;
- кэш Gradle (`caches`, `wrapper`, `native`) не удалять — он подготовлен заранее;
- `/tmp` в изолированной среде не переживает вызов: временное — в дереве задачи или
  создал-и-запустил в одном вызове;
- рецепты тестового окружения — в `knowledge/domains/karaoke-web/components/testing-controllers.md`
  и `knowledge/system/frontend/karaoke-public-tests.md`.

**Failure**: `Файловая система доступна только для чтения` при сборке; трижды
пересозданный стенд в `/tmp` (KARAOKE-396); час на `setUpEnv()` (KARAOKE-399).

## 11. Диагностика не удаляется

Отладочный вывод, который мешает, переводится в логгер — а не вырезается из кода.
Удалённая диагностика — потерянная способность разбирать инцидент.

**Failure**: `println`/`console.log` удалён вместо перевода в `log.info`.

## 12. Git и коммит

Сообщение коммита — без обратных кавычек и `$()`: они выполняются оболочкой.
Признак успеха — строка `[branch ХЕШ]`, после неё репозиторий не пересобирать.

**Failure**: сообщение искажено подстановкой; после успешного коммита начата
«пересборка репозитория».

**Прецедент**: `git commit -m "… $(date) …"` — подстановка съела текст; `rm -rf .git`
как «починка» git-ошибки.

## Как проверялось

Правила 1–9, 11, 12 имеют прецеденты из разбора сессий и прогонов локальных моделей
(2026-11-03…05).

Два уточнения, чтобы не выдавать наблюдение за измерение:

- **Правило 9** вобрало бывшее правило «тест под гипотезу сначала её опровергает»,
  которое проверялось A/B (одна задача, одна модель, ветка без правила): без него
  модель сделала ту же работу вчетверо быстрее (21 мин против 1,5 ч) и полнее
  (59 тестов против 19), оба прогона с коммитом. Признаков пользы у отдельного
  правила нет — поэтому оно слито с «выводом из факта».
- **Правило 8** в части «три итерации — стоп» A/B **не проверялось**: порог нарушался
  в двух прогонах, хотя правило было прочитано. Это наблюдение, а не замер. Рабочий
  вывод из него: порог должен ставить стенд (лимит шагов на задачу), а не текст правила.

Полные разборы — [`agent-mechanics-cases.md`](agent-mechanics-cases.md).
