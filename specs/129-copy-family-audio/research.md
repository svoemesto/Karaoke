# Исследование: аудиоданные при выборе похожей версии песни

**Feature**: `129-copy-family-audio`
**Дата**: 2026-08-03

## Decision 1: Источник метрик и границы ручного сценария

**Решение**: Источником `audioSimilarityPercent` и `audioDeltaMs` является последний успешно завершённый результат сверки именно для выбранной строки в `FamilySongsModal`. Если сверка не выполнялась или завершилась ошибкой, для выбранной связи сохраняются нейтральные значения `0/0`.

**Rationale**:

- `FamilySongsModal.compareResults` уже хранит результат по ID кандидата (`webvue3/src/components/Songs/edit/FamilySongsModal.vue:124-179`).
- Результат сверки может быть корректным `0%/0 мс`, поэтому наличие результата определяется состоянием `done`, а не truthiness чисел.
- Это сохраняет существующий сценарий выбора строки без обязательной тяжёлой повторной сверки.
- Метрики другой строки нельзя перенести в новую связь.

**Альтернативы, которые рассмотрены**:

- Автоматически запускать сверку при каждом выборе строки — отклонено: добавляет скрытую длительную операцию и меняет текущий UX.
- Передавать отдельный `comparisonOk` — не требуется: наличие двух nullable-параметров различает отсутствие результата и валидные нулевые значения при меньшем изменении контракта.
- Считать значения ненулевыми только при `percent > 0` или `deltaMs != 0` — отклонено: теряются валидные нулевые результаты.

## Decision 2: HTTP-контракт

**Решение**: Расширить существующий `POST /api/song/selectfamilysong` одним новым nullable-параметром `audioSimilarityPercent`. Существующий `deltaMs` одновременно является сдвигом маркеров и результатом аудиосверки, поэтому отдельный `audioDeltaMs` в запросе не нужен.

Запрос сохраняет существующие параметры `id`, `idAnother`, `deltaMs` и получает:

- обе метрики отсутствуют — выбор без сверки, записывается `0/0`;
- `audioSimilarityPercent` и `deltaMs` присутствуют — сохраняются оба значения, включая нули и отрицательный `deltaMs`;
- присутствует только одна метрика — запрос отклоняется до изменения песни.

Ответ расширенного `SelectFamilySongResultDto` содержит `rootId`, `idStatus`, `audioParentId`, `audioSimilarityPercent`, `audioDeltaMs`. В ответе возвращаются фактически нормализованные и сохранённые значения, чтобы открытый редактор не пересчитывал их самостоятельно.

**Rationale**:

- `idAnother` уже однозначно определяет выбранную строку.
- Идентичность `deltaMs` для сдвига маркеров и аудиосдвига подтверждена `WaveformCompare` (`karaoke-app/src/main/kotlin/com/svoemesto/karaokeapp/WaveformCompare.kt:19-20`) и `applyFamilySongSelection` (`Utils.kt:4431-4438`).
- Контракт остаётся обратно совместимым для вызовов без новых параметров.

**Альтернативы, которые рассмотрены**:

- Добавить отдельные `comparisonOk` и `audioDeltaMs` — отклонено как избыточное дублирование при наличии nullable-пары и существующего `deltaMs`.
- Возвращать полный `SongDTO` — отклонено: существенно расширяет ответ и область изменения, тогда как редактору для немедленного обновления нужны только шесть полей результата.
- Принимать `audioParentId` от клиента — отклонено: сервер вычисляет его из загруженного `another.id`, чтобы клиент не мог подменить связь.

## Decision 3: Где устанавливать и сохранять поля

**Решение**: Устанавливать аудиополя внутри `applyFamilySongSelection` до существующего единственного `song.saveToDb()`. Для ручного endpoint передавать явно разрешённый `audioParentId = another.id`; значение по умолчанию для внутренних автоматических вызовов остаётся `null`, поэтому `autoAssignOriginalByWaveform` не начнёт менять аудиополя.

**Rationale**:

- Один `saveToDb()` формирует единый diff и один SQL `UPDATE` для текста, маркеров, root/status и трёх аудиополей (`Song.kt:5280-5338`).
- Поля уже участвуют в `Song.getDiff()` (`Song.kt:6885-6900`), recordhash и существующей синхронизации; миграция не нужна.
- Установка в контроллере после helper привела бы к нескольким сохранениям и частичной видимости.
- Автоматический caller `autoAssignOriginalByWaveform` использует тот же helper для текста/маркеров (`Utils.kt:4577`), поэтому ручной режим должен быть opt-in.

**Правило связи**: при ручном выборе `audioParentId` равен ID фактически выбранной строки, а не разрешённому аудиокорню кандидата. Метрики сверки относятся к этой же паре; автоматический flattening из `findAudioParentByWaveform` не применяется.

**Альтернативы, которые рассмотрены**:

- Безусловно брать `another.id` внутри helper — отклонено: изменило бы поведение автоматического caller.
- Всегда применять flattening по `another.audioParentId` — отклонено: ID и метрики могли бы описывать разные пары.
- Сохранять три поля отдельным frontend `/api/song/update` — отклонено: нарушает атомарность и создаёт дополнительный diff/sync.

## Decision 4: Валидация и ошибка сохранения

**Решение**: До мутаций проверять `id != idAnother`, наличие кандидата, диапазон процента `0..100` и парность nullable-метрик. После единственного `saveToDb()` перечитать текущую запись и убедиться, что три аудиополя равны ожидаемым значениям. Если сохранение не применилось, endpoint сообщает об ошибке, а frontend не закрывает модалку и показывает возможность повторить операцию.

**Rationale**:

- UI уже блокирует текущую строку, но backend должен защищать endpoint от прямого вызова.
- Текущий `Song.saveToDb()` логирует ошибки SQL и может не пробросить исключение (`Song.kt:5337-5355`), поэтому проверка результата нужна для честного HTTP-ответа без глобального рефакторинга.
- Все реальные изменения выполняются одним SQL-оператором PostgreSQL; проверка после записи закрывает локальный пробел в сигнализации ошибки.

**Ограничение**: Фича не меняет общий контракт `Song.saveToDb()` и не добавляет новую транзакционную инфраструктуру. Проверка подтверждает именно применённость результата выбора.

## Decision 5: Синхронизация открытого редактора

**Решение**: После успешного ответа `SongEdit` применяет `rootId`, `idStatus` и три аудиополя к открытому объекту. Vuex получает узкую mutation для одновременного обновления текущего объекта и snapshot сохранёнными полями; это предотвращает повторный autosave тех же значений через debounce.

**Rationale**:

- Поля редактора уже отображаются через `v-model` (`SongEdit.vue:454-516`).
- SSE обновляет digest, но не гарантирует обновление открытого `currentSong` и его snapshot.
- Ответ endpoint уже содержит нормализованные значения; дополнительный запрос загрузки песни не нужен.

**Альтернативы, которые рассмотрены**:

- Полагаться только на SSE — отклонено: открытый редактор не получает надёжного обновления.
- После ответа запускать обычный autosave — отклонено: backend уже сохранил данные, получится лишний запрос и дополнительное окно рассогласования.
- Возвращать полный объект песни — отклонено как избыточное расширение контракта.

## Decision 6: Ошибка UI и конкурентные клики

**Решение**: Модалка закрывается только после успешного ответа. На время запроса обработчик выбора блокирует повторную отправку; при ошибке модалка остаётся открытой и показывается toast с возможностью повторить.

**Rationale**:

- Текущий обработчик закрывает модалку до завершения запроса (`SongEdit.vue:3723-3734`), а `JSON.parse` может получить ошибку при HTTP reject.
- Один in-flight выбор исключает гонку A→B и устаревший ответ, перезаписывающий более новый выбор.

## Decision 7: История сравнений и документация

**Решение**: `audioCompareHistory` в этой фиче не изменяется. Обновляется `docs/features/songs-table.md`, поскольку ручной flow относится к админскому Songs/SongEdit-контексту; схема, `SongDTO`, recordhash-триггеры и SyncRegistry не меняются.

**Rationale**:

- Спецификация требует сохранить результат выбора, но не требует кэшировать ручную сверку.
- Запись истории добавила бы ещё одно изменение recordhash и расширила бы scope.
- FR-009 Конституции требует обновлять per-feature документ при правке кода соответствующей админской подсистемы.

## Decision 8: Проверка

**Решение**: Использовать ручной E2E quickstart как основную проверку поведения и обязательные статические/build-проверки проекта. Новая frontend unit-test инфраструктура не вводится: в `webvue3/package.json` нет test runner, а существующие backend-тесты интеграционные и требуют окружения.

Проверки:

- `./gradlew :karaoke-app:compileKotlin`
- `./gradlew ktlintCheck`
- `cd webvue3 && npm run lint:check && npm run format:check && npm run build`
- ручные сценарии из `quickstart.md`, включая API/SQL-проверку в локальной БД.

**Альтернативы, которые рассмотрены**:

- Добавить полноценный browser E2E runner — отклонено для этой фичи: отсутствует инфраструктура и это несоразмерно локальному изменению.
- Положиться только на компиляцию — отклонено: она не проверяет связку модалка → endpoint и сохранение нулевых/отрицательных значений.
