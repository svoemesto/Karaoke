Песня для замеров: `id=11718` «Говорит Деметра» — 2170 маркеров, 1822 слога, 604.55 с.

## Находка 1 — S1: HTML из текста песни не экранируется, отдаётся на публичный сайт

### Что

Три билдера формируют HTML из пользовательского текста песни и ни разу
не экранируют его:

| Билдер | Строки | Точки конкатенации сырого текста |
|---|---|---|
| `getTextFormatted()` | `Song.kt:4492` | `result.append(txt…)` — 4519, 4539, 4585 |
| `getFormattedChords()` | `Song.kt:4019` | `txtHtml` — 4100, 4104; `chordHtml` — 4184; сборка в `lineText` — 4185 |
| `getFormattedNotes()` | `Song.kt:4198` | `txtHtml` — 4244, 4248; `noteHtml` — 4267; сборка — 4318, 4319 |

Вход — `marker.label` (слог) и `marker.chord`. Обработка сводится к
`.replace("_", " ")` / `.replace("_", "&nbsp;")` — символы `< > &` не трогаются.

Экранирующего хелпера в `karaoke-app` нет вовсе: единственный
`String.xmldata()` (`Extentions.kt:107`) экранирует только `<`.

### Измерено

```
POST /api/song/textformatted  id=11718  →  193 167 символов, 1898 <span>, 0 &lt;
```

Ноль экранированных сущностей при 1898 тегах — экранирования нет ни в одной точке.

### Кто это рендерит

Не только админка:

- `webvue3/src/components/Songs/edit/SongEdit.vue:2436/2441/2446` — три `v-html`
- `webvue3/src/components/SongEditor/SongKaraokeEditorView.vue:317` — `v-html="formattedTextHtml"`
- **`karaoke-public/src/views/SongView.vue:309/313/317`** — страница песни публичного
  сайта, `v-html` на `formattedTextSong` / `Tabs` / `Chords`
- `karaoke-public/src/views/EditorWorkView.vue:317` — публичный лёгкий редактор

Данные туда приходят через `SongPublicDto`
(`karaoke-web/.../dto/SongPublicDto.kt:35-37, 116-117`).

### Решающий довод: то же поле в проекте уже экранируется — в другом месте

`karaoke-web/.../controllers/PublicOgSongController.kt:196`:

```kotlin
sb.append("    <pre>").append(escape(song.formattedTextSong)).append("</pre>\n")
```

OG-картинка экранирует. JSON-API и `v-html` — нет. То есть не «забыли про
экранирование вообще», аapply его в одном пути из двух.

### Граница доверия

Текст песни правит контрибьютор (публичный лёгкий редактор) и админ.
Результат рендерится всем посетителям сайта. Отсюда эскалация
«контрибьютор → публичная витрина».

Полезной нагрузки в разметке нет: `getTextFormatted` — это `<span>` со
style-атрибутами и `<br>`, ничего, что требовало бы сырого HTML от пользователя.

### Чего я не сделал и почему

Не воспроизводил эксплойт на живом эндпоинте: для этого нужен текст песни с
`<script>` в общей dev-базе, а она синхронизируется с продом (правило из #209 —
«не воспроизводить запись в общую dev-базу бездумно»).

Также не оставил юнит-тест: конструктор `Song()` тянет `lateinit KSS_APP`
с реальной БД, тест падает с `ExceptionInInitializerError` на этапе
инициализации класса, а не на утверждении. Тест, который не запускается, хуже
отсутствия теста — удалил его, а не оставил как ложное доказательство.

**Доказательная база — два независимых факта:** измерение (0 экранированных
сущностей при 1898 тегах) и код (`result.append(txt)` без экранирования).
Эндпоинт-эксплойт не воспроизводился.

## Находка 2 — S2: автосейв пишет в песню, взятую из стора в момент запроса

`store.js:1979`:

```js
saveSong(ctx, params) {
  params.id = ctx.state.currentSongId   // цель — из СОСТОЯНИЯ СТОРА
  let request = { method: 'POST', url: '/api/song/update', params: params }
```

`params` формируется в `executeSave` (`SongEdit.vue:5687-5690`) только из
значений изменённых полей — идентификатора песни в нём нет:

```js
let params = {}
for (let diffItem of this.diff) { params[diffItem.name] = diffItem.new }
```

Гонка:

1. Открыта песня A, изменено поле → `diff` непуст, взведён таймер на 1000 мс.
2. Пользователь уходит на песню B в пределах этого окна → `currentSongId = B`.
3. Таймер срабатывает. `currentSong`/`snapshotSong` ещё A (загрузка B — сетевой
   запрос), значит `diff` всё ещё содержит правку A.
4. `params.id = B` → правка A уходит в B.

`getSongDiff` (`store.js:391`) считает разницу `currentSong` vs `snapshotSong`,
поэтому после чистой загрузки песни diff пустеет — гонка живёт именно в окне
между сменой `currentSongId` и подстановкой нового `snapshotSong`.

Дополнительно `executeSave` (`SongEdit.vue:5703-5705`) перевзводит себя при
непустом diff, то есть цикл продлевается и после ухода со страницы.

**Не проверено в браузере.** Структурный дефект доказан кодом; факт срабатывания
зависит от того, уложится ли таймер в окно загрузки. Требует отдельного
воспроизведения с задержкой на маршруте `/api/song`.

Починка по существу: `params` должен нести `id` того же объекта, из которого
взят diff, а не читать цель из мутабельного стора в момент отправки.

## Находка 3 — S3: нет `beforeUnmount`; таймеры и слушатели переживают компонент

В `SongEdit.vue` нет ни `beforeUnmount`, ни `unmounted` (проверено: единственные
х lifecycle-хуки — `mounted` на 3737).

- `this.saveTimer = setTimeout(this.save, 1000)` (строка 3098) не гасится при
  уходе — сохранение срабатывает на размонтированном компоненте.
- Тот же таймер перевзводится в `executeSave` (5705).
- `addEventListener`/`removeEventListener` в компоненте не встречаются — этой
  части дефекта нет.

Watcher `song` (3099-3118) делает пять `dispatch(...).then(...)` без `.catch()`
и без проверки размонтирования. Отклонённый промис даст unhandled rejection.

## Находка 4 — S3: три форматтера перезапрашиваются на каждый автосейв

Watcher `song` дёргает `getTextFormattedPromise`, `getNotesFormattedPromise`,
`getChordsFormattedPromise`. `commit('saveSong', params)` заменяет `currentSong`
→ watcher срабатывает снова → форматтеры запрашиваются заново.

То есть каждое сохранение тянет три сетевых запроса и три полные вставки HTML.

### Измерено

Серверная часть быстрая, узкое место — payload и разбор DOM:

```
textformatted    0.013 / 0.012 / 0.017 с   197 911 байт
notesformatted   0.009 / 0.010 / 0.008 с       0 байт   (у этой песни нот нет)
chordsformatted  0.010 / 0.008 / 0.010 с       0 байт
```

Стоимость вставки в DOM (прогон `e2e/measure-formatter-vhtml.spec.js`,
7 итераций, `innerHTML` + форсированный layout):

```
payload: 193 167 символов, 1898 span
вставка v-html (median/min/max мс): 12.4 / 12.2 / 30.8
предыдущий прогон:                  14.3 / 11.0 / 30.5
```

Одна вставка — 12–14 мс, то есть почти целый кадр (порог владельца 16 мс).
У песни с нотами и аккордами все три форматтера непустые, и цикл
«сохранение → три запроса → три вставки» даёт ~40 мс блокировки главного потока
на каждое сохранение, плюс три сетевых запроса.

Замер сделан на одиночном payload; полный прогон в приложении не делался.
