# Contract: `/api/monitor/*` и список настроек — эффект удаления проверки

Эта фича не создаёт новых эндпоинтов и не меняет форму (схему) существующих
ответов. Ниже — контракт-дифф: что именно перестаёт появляться в уже
существующих ответах, чтобы это можно было проверить вручную (`quickstart.md`)
или в будущих тестах, если они появятся.

## `POST /api/monitor/alerts` (снапшот алертов, `MonitoringController`)

**До**: массив алертов мог содержать (при малом горизонте запланированных
Telegram-постов) элемент вида:

```json
{
  "key": "telegram.horizon",
  "severity": "WARNING",
  "title": "Мало запланированных постов в Telegram",
  "category": "Telegram",
  "detail": "горизонт ~<N> ч",
  "recommendations": "Подготовьте и запланируйте новые отложенные посты..."
}
```

**После**: элемент с `key = "telegram.horizon"` НИКОГДА не появляется в
ответе — ни при каком состоянии очереди публикаций (см. `spec.md` FR-001,
FR-002). Остальные элементы массива (алерты семи оставшихся проверок) —
без изменений по форме и условиям появления.

## `POST /api/monitor/resolve`, `markRead`, `markUnread`, `reset`

Форма запроса/ответа не меняется. Единственный эффект: вызов с
`key = "telegram.horizon"` (если такой когда-либо придёт от старого
клиента/кэша) не найдёт соответствующего алерта в свежем снапшоте — это
штатно обрабатывается существующей логикой ре-деривации resolve-действия по
ключу (см. `docs/features/monitoring.md`, п. 5) и не требует нового кода
обработки ошибок.

## Generic-эндпоинт списка настроек (`KaraokeProperties`/`listKaraokeProperties`)

**До**: ответ содержал запись с `key = "monitorTelegramHorizonDays"`
(`defaultValue = 2`, описание — «Мониторинг: минимальный горизонт (сутки)…»).

**После**: эта запись отсутствует в ответе — как и для любой другой удалённой
из `KaraokeProperties.kt` записи, отдельного контракта на «мягкое скрытие» не
существует (см. `feedback_karaoke_properties_registration`: регистрация в
`listKaraokeProperties` — единственный источник истины для отображения в
webvue3).

## Проверка отсутствия регрессии остальных проверок

Форма ответа `POST /api/monitor/alerts` для оставшихся семи проверок
(`TelegramPollingDisabledCheck`, `ProdContainerCheck`,
`RenderQueueStalledCheck`, `LaneStalledCheck`, `UnreadChatMessagesCheck`,
`SubmittedAssignmentsCheck`, `StemJobsStuckCheck`) не меняется — они не
затрагиваются этой фичей ни по коду, ни по конфигурации.
