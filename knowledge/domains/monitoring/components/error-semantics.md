# Component: error-semantics

> **Домен**: [monitoring](../domain.md)
> **Компонент**: семантика ошибок в `karaoke-app` — «сбой НЕ выглядит как штатный результат».

## Ответственность | Responsibility

Компонент фиксирует **сквозной инвариант** приложения, проверенный аудитом
#336 (волна E, пакет `PKG-S3-23`, 39 записей BR-117…BR-173):

> **Отказ хранилища, БД, сети или ФС не должен выдаваться за штатный
> результат.** «Нет данных», «нет файла», «нечего публиковать» и «проверка
> прошла» — это разные состояния, и код обязан их различать.

Инвариант особенно опасен там, где «пусто» и «сбой» имеют **одинаковое
представление** в API: клиент (админ, бот, health-report) принимает пустой
список за «всё в порядке» и не знает, что система уже не работает.

Компонент не меняет поведение кода — он **называет** правило, перечисляет
опознаваемые нарушения и указывает, где оно зафиксировано регресс-проверками.

## Интерфейсы и Контракты | Interfaces and Contracts

### Канонические признаки (что должно различаться)

| Штатный результат | Сбой (нельзя отдавать как штатный) |
| --- | --- |
| `false` — «объекта нет» (S3 `NoSuchKey`/`NoSuchBucket`) | `false` от недоступного хранилища (fast-fail/таймаут) |
| `0` — «записей нет» | `0` из-за `SQLException` |
| `emptyList()` — «кандидатов нет» | `emptyList()` из-за упавшего `SELECT` |
| `null` — «сервис не настроен» | `null` из-за 500/таймаута/битого JSON |
| `SCHEDULED` — «контент не готов, повторим» | `SCHEDULED` как вечный бесконечный retry |
| `Unit`/«успех» — «запись прошла» | `Unit` после `catch { println(e.message) }` |

### Механизмы различения в коде

- **Трёхзначный результат**: `Boolean?` — `null` означает «не ответили».
  Пример: `StorageApiClient.fileExistsReliable()` (BR-144).
- **Явный тип результата**: `sealed class Outcome { Transcribed; Failed(reason) }`.
  Пример: `WhisperAsrService.transcribeDetailed()` (BR-159).
- **`null` вместо пустого списка + прерывание фазы**: загрузчик возвращает
  `null` при сбое БД, а вызывающая фаза тика прерывается (`false`).
  Примеры: `VkAutoPublishScheduler`, `TelegramAutoPublishScheduler`,
  `PremiumAutoPublishScheduler` (BR-146, BR-152, BR-165).
- **Типизированное исключение**: сбой транспорта оборачивается в
  `VkNetworkException` / `VkNewsLookupException`, а не пролетает «сырым»
  (BR-153, BR-152).
- **Транзакция**: изменение и его след (audit-запись) — в одной транзакции,
  иначе «след» может не записаться при уже применённом изменении (BR-168).
- **Журнал до результата**: если след не записан, прогон считается
  `FAILED`, а не `DONE` (BR-170).

### Что считается «сломанным следом»

- `printStackTrace()` / `println(e.message)` вместо SLF4J — причина не попадает
  в структурированные логи (`infra.*`), диагностика теряется.
- Пустой `catch (e: SQLException) {}` — ошибка БД неотличима от пустого
  результата.
- `catch (_: Exception) { null }` — любая причина сводится к одному «нет».

## Логика и Алгоритмы | Logic and Algorithms

### Проверка на «отказ ≠ результат» (для нового кода)

1. Найти все места, где внешний источник (БД, S3, HTTP, ФС) может ответить
   «неизвестно».
2. Для каждого — решить, чем «неизвестно» отличается от «нет», и отразить это
   в типе (не в логе).
3. На границе (контроллер/тик) превратить «неизвестно» в **явную ошибку**
   (5xx/503, типизированное исключение, прерывание фазы), а не в пустой ответ.
4. Закрепить регресс-тестом: контрактный тест по исходникам (падает на старом
   коде) или поведенческий тест.
