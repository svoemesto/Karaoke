# Автоуборка артефактов песни (OpenProject #321, спека #544)

> **Status**: active
> **Feature Key**: song-artifact-cleanup
> **Last Updated**: 2026-10-16
> **Spec**: [specs/544-song-artifact-cleanup/spec.md](../../specs/544-song-artifact-cleanup/spec.md)
> **Issue**: OpenProject #321 (карта решений — #306, инвентаризация — #305)
> **Branch**: `544-song-artifact-cleanup`
> Per-feature документ (Constitution § VI FR-009).

## Что делает

Останавливает накопление лишних артефактов песни на дисках admin-машины и возвращает
место по истории: демо-ролики, локальные mp3-стемы, публикационные картинки, субтитры,
сериализованное состояние песни и файлы проектов рендера перестают создаваться либо
удаляются по завершении своего шага жизненного цикла, а уже накопленное (≈650 ГБ из
2,4 ТБ) убирается разовой чисткой классами — с отчётом, утверждением владельцем и
журналом.

## Зачем

Инвентаризация 2026-10-16 (#305) показала 2,4 ТБ артефактов, из которых ≈650 ГБ —
заведомо лишние: 17 885 демо-роликов (176,7 ГБ), 53 618 локальных mp3-стемов (445 ГБ,
побайтовые копии уже лежат в двух MinIO), 23 748 субтитров, 32 863 файла `.song`/`.settings`.
Кроме объёма, мёртвые артефакты создавали ложное ощущение работы: признак «есть аккорды»
считался по файлам субтитров, ни один из 20 288 живых `.srt` не содержал нужного маркера,
поэтому для современных песен признак всегда был ложным.

## Как работает

1. **Прекращение накопления** — удаление демо-ролика в конце шага публикации
   (`PremiumAutoPublishScheduler.closeIfBothChannelsDone`) и публикационных картинок при
   успехе обеих площадок; удаление локального mp3-стема после успешной загрузки в **оба**
   хранилища (`ArtifactCleanupAutomation.deleteLocalCopyIfBothStoresHave`); снятие
   писателей `.song`/`.settings`, `.srt`/`.srt.backup`, `.kdenlive`/`.run`.
2. **Снятие ожидания удалённого** — `KaraokeFileType.locations` для `MP3_*` больше не
   содержит `LOCAL_FILESYSTEM`, поэтому `HealthReport` не считает отсутствие локальной
   копии нарушением и не ставит `FF_MP3_*`-задачи (иначе после чистки начался бы шторм
   перекодирования по всей библиотеке).
3. **Разовая чистка истории** — `ArtifactCleanupPlanner` (сухой прогон, отпечаток набора),
   `ArtifactCleanupService` (применение по утверждённому отчёту, журнал), HTTP-контракт
   `/api/cleanup` (`classes`/`plan`/`apply`/`status`) и `CleanupJournal` — TSV
   `/sm-karaoke/system/cleanup-logs/<дата>-<класс>.tsv`.
4. **Гигиена и документация** — `HealthReport.symlinkFolderReports` обходит `symlink_*`
   целиком (битые ссылки, посторонние файлы); Knowledge приведён к факту.

Реестр `ArtifactCleanupClass` — единственное место правды о вердиктах, порядке чистки и
ожидаемых объёмах; словарь вердиктов — в
[`dictionaries.md`](../../knowledge/domains/catalog/components/dictionaries.md).

## Инварианты

1. **Исходники и flac-стемы неприкосновенны** (FR-010): классы `SOURCE_FLAC` и
   `STEMS_FLAC` имеют вердикт `PROTECTED`, и API чистки отклоняет их **всегда**,
   независимо от подтверждений.
2. **Уборка выключена по умолчанию** (FR-011): `cleanupEnabled=false`,
   `cleanupDryRun=true`. При выключенном флаге поведение системы идентично прежнему;
   сухой прогон не удаляет ни одного файла.
3. **Локальная копия mp3-стема удаляется только при успехе в оба хранилища** (FR-003);
   проверка второго хранилища fail-closed — неизвестность означает «не удалять».
4. **Каждое удаление попадает в журнал** с путём, размером, классом, датой, утвердившим и
   `runId` (FR-012); если журнал недоступен, удаление не выполняется.
5. **Разовая чистка идёт по отпечатку**: `apply` без отпечатка или с изменившимся составом
   отклоняется (409) — утверждается конкретный набор файлов, который владелец видел.
6. **Порядок классов обязателен** (FR-013): класс `STEMS_MP3_LOCAL` не удаляется, пока не
   выполнена правка модели ожидаемых файлов (FR-004).
7. **Уборка не идёт через авторемонт** (FR-014): `HealthReport` восстанавливает
   недостающее, а не удаляет лишнее; удаление — только через `ArtifactCleanupService` или
   `ArtifactCleanupAutomation`.
8. **MinIO — источник истины для mp3-стемов и картинок** (FR-016): видео, исходники,
   flac-стемы, субтитры и сериализованное состояние в MinIO не загружаются.

## Известные ловушки

- **Порядок работ**: удалить локальные mp3-стемы до правки `KaraokeFileType.locations` и
  `HealthReport` — значит получить шторм задач перекодирования по всей библиотеке
  (53 618 файлов). Поэтому модель ожиданий правится первой, а класс чистки гейтится 409-й.
- **`.mlt` не удалён из писателей**: FR-009 требует не создавать `.mlt`, но файл читает
  замороженный, однако живой melt-конвейер (типы процессов `MELT_*` создаются из
  `MainController` и `KaraokeProcessWorker.applyRenderSideEffect`). Пока MELT-процессы не
  выведены из эксплуатации, прекращение записи `.mlt` поставит их в падающее состояние —
  решение за владельцем (см. `tasks.md` §11).
- **Имя `[render]`-видео сохранено**, хотя файл практически мёртв (1 экземпляр на дисках):
  у него есть читатель — ручное воспроизведение через smplayer.
- **Гейт R-11**: в исходниках `karaoke-app/src/**/*.kt` запрещены новые упоминания
  расширения видео; расширение берётся из `SongOutputFile.VIDEO.extension`, а не литералом
  (baseline `tools/check-no-mp4-mentions.baseline` перегенерируется только словом владельца).
- **Приёмка требует включённых флагов**: чтобы проверить фактическое удаление (SC-001,
  SC-002), нужно выставить `cleanupEnabled=true` и `cleanupDryRun=false` — иначе файлы
  остаются по замыслу.
- **`SongRenderContext` стал недостижим**: после вырезания файлового ввода-вывода его
  никто не конструирует (был только побочный эффект записи `.srt`). Класс — кандидат на
  удаление отдельным решением.
