# Data Model: Спецтеги в тексте песни для авто-разметки маркеров

Новых таблиц, колонок или миграций эта фича не добавляет. Ниже — концептуальные сущности, которые появляются в коде (backend + frontend), но не персистятся отдельно от уже существующих полей.

## SpecTag (эфемерная, результат парсинга — не хранится)

Результат разбора одной строки текста лирики регулярным выражением `~([a-z]+)(?::([^~]*))?~`.

| Поле | Тип | Описание |
|---|---|---|
| `name` | String | Имя тега (например `newline`, `group`, `comment`), нижний регистр латиницей. |
| `value` | String? | Необязательное значение после `:` (например `"1"` для `group:1`, произвольный текст для `comment:...`). `null`, если тега без значения (`~newline~`). |
| `lineIndex` (backend) | Int | Индекс сырой строки исходного текста (0-based, включая пустые строки), на которой найден тег — используется как ключ группировки при построении маркеров. |
| `afterSyllableIndex` (frontend) | Int | Ординальный индекс слога (`sourceSyllables`), после которого стоит тег — используется как якорь при сопоставлении с уже существующими `syllables`-маркерами. |

**Валидация**: имя тега должно входить в реестр (см. ниже); если у записи реестра задан валидатор значения — значение обязано пройти его. Невалидная комбинация имя+значение = тег не распознан (см. `research.md` §6).

**Жизненный цикл**: существует только в момент обработки текста (авто-разметка или пересчёт в редакторе) — не сохраняется как отдельная запись; переживает только как факт своего присутствия в `sourceText` (который и так уже персистится как есть).

## TagRegistryEntry (реестр, статическая конфигурация в коде)

Одна запись реестра описывает, как один тег транслируется в маркер.

| Поле | Тип | Описание |
|---|---|---|
| `tagName` | String | Ключ реестра, совпадает с `SpecTag.name`. |
| `valuePattern` | Regex? / правило | Опциональная валидация значения (например `group` требует целое число в допустимом диапазоне групп; `comment` принимает любую непустую строку; `newline` не принимает значение). |
| `markertype` | `Markertype` (backend) / строка-константа (frontend) | Целевой тип маркера — переиспользует уже существующий enum `Markertype` (`NEWLINE`, `SETTING`), новых значений enum не добавляется. |
| `labelBuilder` | `(value: String?) -> String` | Как из значения тега строится `SourceMarker.label` (например для `group` — `"GROUP|$value"`, для `comment` — `"COMMENT|$value"`, для `newline` — `""`). |

**v1 реестр** (детально — см. `contracts/tag-registry.md`): `newline`, `group`, `comment`.

**Расширяемость**: новый тег = новая запись реестра (имя, опциональный валидатор значения, целевой `Markertype`, функция построения label) — без изменения кода парсинга строки или кода анкоринга (гэп между `lineIndex`/ординальный индекс слога).

## TagAlias (реестр, статическая конфигурация в коде)

Отдельная запись реестра, разрешающая фиксированное человекочитаемое имя (без значения) в ту же пару `(Markertype, label)`, что даёт конкретная параметризованная форма одного из базовых тегов.

| Поле | Тип | Описание |
|---|---|---|
| `aliasName` | String | Человекочитаемое имя (Unicode-буквы, регистронезависимое сопоставление), например `Куплет`. |
| `targetTagName` | String | Имя базового тега из `TagRegistryEntry`, в который резолвится алиас (например `group`). |
| `targetValue` | String | Фиксированное значение, подставляемое как если бы пользователь написал `~targetTagName:targetValue~` (например `"0"`). |

**v1 набор** (детально — см. `contracts/tag-registry.md`): `Куплет`→`group:0`, `Припев`→`group:1`, `Бридж`→`group:2`, `Приговор`→`group:3`. Для `group:4` алиаса нет.

**Инвариант**: алиас и его целевая параметризованная форма ДОЛЖНЫ давать идентичный `(Markertype, label)` — это гарантирует, что дедупликация "маркер уже стоит на этой позиции" (см. §5 в `research.md`) работает одинаково независимо от того, какой синтаксис использован в тексте.

## Существующие сущности, которые не меняются, но участвуют

- **`SourceMarker`** (`model/SourceMarker.kt`) — уже существующая структура персистентного маркера (`time`, `label`, `color`, `position`, `markertype`, и т.д.). Спецтег транслируется РОВНО в экземпляр этой структуры — новых полей на ней не появляется.
- **`Markertype`** (`model/Markertype.kt`) — уже существующий enum значений `markertype`. Новые теги v1 переиспользуют существующие значения `NEWLINE` и `SETTING` — новых значений enum эта фича не добавляет.
- **`Settings.sourceMarkersList` / `Settings.sourceText`** (`model/Settings.kt`) — существующие поля, где хранятся результат (список маркеров) и вход (текст с тегами) соответственно. Формат обоих полей не меняется.

## Диаграмма потока (текстовое описание)

```
sourceText (с тегами)
   │
   ├─(backend, авто-разметка)──▶ SpecTags.parseLine (по строке)
   │                                   │
   │                             lineIndex → List<SpecTag>
   │                                   │
   │                     buildMarkersFromSyllableTimes (гэп между TargetWord.lineIndex)
   │                                   │
   │                     реестр(tagName) → Markertype + label
   │                                   │
   │                                   ▼
   │                          List<SourceMarker>  (как и сегодня, просто больше типов
   │                                                на месте бывшего единственного NEWLINE)
   │
   └─(frontend, ручной пересчёт)──▶ getSpecTags() (по sourceSyllables-индексу)
                                         │
                                   реестр(tagName) → markertype + label
                                         │
                          syncMarkersFromSpecTags(): добавить отсутствующий
                          маркер на нужной ординальной границе (никогда не удалять)
                                         │
                                         ▼
                                 sourceMarkers (Vuex state → сохранение как сегодня)
```
