# Research: Кнопка «Типограф» в онлайн-редакторе

Технический контекст (`plan.md`) не содержит нерешённых `NEEDS CLARIFICATION` — все неизвестные
были закрыты прямым чтением существующего кода (эталонная реализация кнопки уже есть в
`SubsEdit.vue`). Ниже — зафиксированные решения и альтернативы.

## 1. Откуда брать правила замены текста

**Decision**: Переиспользовать существующий backend-эндпоинт `POST /api/replacesymbolsinsong`
(`karaoke-app/.../controllers/ApiController.kt:5129`, функция `replaceSymbolsInSong(txt)`) без
изменений. Он уже вызывается из классического редактора: `SubsEdit.vue:4287` →
`store.js:575 getReplacedSymbolsInText` → `POST /api/replacesymbolsinsong`.

**Rationale**: Пользовательский запрос прямо требует «ту же самую» кнопку, что и в SubsEdit —
переиспользование гарантирует идентичный результат замены и не дублирует бизнес-правила
типографики на фронтенде. Эндпоинт не в `/api/private/**` → `permitAll()` в `SecurityConfig.kt`,
доступен без авторизации обоим фронтендам «как есть».

**Alternatives considered**:
- Реализовать правила замены на фронтенде (JS) — отклонено: дублирование логики, риск
  расхождения с классическим редактором, нарушает цель «та же самая кнопка».
- Завести новый эндпоинт специально для онлайн-редактора — отклонено: избыточно, существующий
  эндпоинт уже публичный и универсальный (принимает произвольный `txt`, не привязан к сессии
  редактирования).

## 2. Как вызывать эндпоинт с каждого фронтенда

**Decision**: Прямой вызов `promisedXMLHttpRequest({method:'POST', url:'/api/replacesymbolsinsong',
params:{txt: ...}})` из компонента, как это делает `webvue3/.../Songs/store.js:575-581`.

**Rationale**: Ответ эндпоинта — «сырая» строка (`fun ...: String`), не JSON. В `karaoke-public`
есть готовый `services/api.js#apiPost()`, но он всегда делает `JSON.parse(response)` — это
сломается на обычном тексте песни (не валидный JSON). `promisedXMLHttpRequest` (есть в
`lib/utils.js` в обоих фронтендах) отдаёт ответ как есть, без парсинга — то же самое, что уже
работает в `webvue3` для того же эндпоинта.

**Alternatives considered**:
- `apiPost()` в `karaoke-public` — отклонено: ломает ответ через `JSON.parse` на не-JSON строке.
- Провести вызов через Vuex (`webvue3/.../Songs/store.js`) — отклонено:
  `SongKaraokeEditorView.vue`/`SongKaraokeEditorModal.vue` нигде не используют `this.$store`
  (проверено — 0 вхождений), это чисто presentational-компонент на props/emit. Заводить
  Vuex-зависимость ради одного вызова — лишняя связанность; прямой XHR-вызов проще и локальнее.

## 3. Как пересинхронизировать маркеры после замены текста

**Decision**: После получения нового текста — записать его в `sourceText` текущего голоса и
вызвать существующий обработчик `onTextInput()` (или воспроизвести его шаги:
`splitSyllables` → `relabelSyllables` → `syncMarkersFromSpecTags` → `scheduleRedraw`/
`scheduleAutosave`/`$emit('change')`), уже определённый в обоих компонентах
(`SongKaraokeEditorView.vue:843-849`, `EditorWorkView.vue:962-968`).

**Rationale**: Модель маркеров онлайн-редактора — **spec-tag-based** (маркеры выводятся из
inline-тегов вида `~newline~`/`~group:0~` прямо в тексте, см.
`composables/useKaraokeEditor.js#syncMarkersFromSpecTags`), а не region-based DOM-модель
WaveSurfer, которую использует `SubsEdit.vue`. Поэтому логика `doReplaceBrokenMarkers()` из
`SubsEdit.vue` (удаление «осиротевших» `GROUP|0`/`COMMENT|`-маркеров конкретно region-based
модели) неприменима один-в-один. `onTextInput()` — это уже существующий, проверенный практикой
путь пересинхронизации маркеров с текстом при ЛЮБОМ его изменении (используется, например, после
вставки спецтега через `onInsertSpecTag`), и выполняет ту же роль: гарантирует, что маркеры не
разъедутся с текстом.

**Alternatives considered**:
- Портировать `doReplaceBrokenMarkers()` как есть — отклонено: он манипулирует
  `marker.region`/DOM-объектами WaveSurfer, которых в модели онлайн-редактора нет; привело бы к
  рантайм-ошибкам.
- Не трогать маркеры вообще, полагаясь только на то, что правила замены не меняют структуру
  строк — отклонено: `replaceSymbolsInSong` — единая функция, гарантий «не тронет переносы
  строк» на уровне контракта нет; безопаснее явно пересинхронизировать, тем более что
  `onTextInput()` уже вызывается по каждому вводу в это же поле и стоимость вызова пренебрежимо
  мала.

## 4. Область действия (multi-voice)

**Decision**: Применять замену только к `sourceText` **текущего выбранного голоса**
(`this.sourceText` — computed-прокси на `voices[currentVoiceIdx].sourceText`, см.
`SongKaraokeEditorView.vue:425-430`, `EditorWorkView.vue:471-478`), не трогая остальные голоса.

**Rationale**: Это в точности повторяет область действия уже существующей кнопки «Очистить
маркеры» (`clearMarkers()`) в тех же компонентах — она тоже оперирует только текущим `markers`/
`sourceText` через тот же computed-прокси. Согласованность с существующим UX-паттерном важнее
гипотетического «применить сразу ко всем голосам», которого пользователь не просил.

**Alternatives considered**: Массовая замена по всем голосам разом — отклонено (не запрошено,
ломает паритет с «Очистить маркеры», усложняет UX неожиданным побочным эффектом).

## 5. Обработка ошибок сети

**Decision**: При ошибке `promisedXMLHttpRequest` (reject) — не менять `sourceText`, показать
пользователю сообщение об ошибке. Механизм показа ошибки — тот же, что уже используется в
компоненте для других сетевых операций: в `EditorWorkView.vue` уже есть индикатор состояния
сохранения (`saveState`, значения `idle`/`saving`/`saved`/`error` → текст «Ошибка сохранения»,
строки 404/461/1018/1094, стиль `.ke-save-error`) — переиспользовать тот же паттерн
уведомления об ошибке (свой текст, например «Ошибка Типографа»), не заводить новый UI-примитив.
В `SongKaraokeEditorView.vue` — эквивалентный паттерн `saving`/ошибок в
`SongKaraokeEditorModal.vue` (`saving`, `$emit('close')` и т.п.) — использовать локальный
аналог того же уровня, не изобретая новый компонент.

**Rationale**: FR-006 спецификации; не изобретать новый способ сообщать об ошибках там, где уже
есть работающий.

**Alternatives considered**: Тихий no-op без уведомления — отклонено, пользователь не поймёт,
почему текст не изменился.
