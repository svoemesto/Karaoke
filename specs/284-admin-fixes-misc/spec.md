## User Scenarios & Testing *(mandatory)*

### User Story 1 — Админ видит лейбл "Censored:" вместо "Композиция (цензурированная):" (Priority: P1)

Админ-редактор открывает карточку песни в админ-SPA (`SongEdit.vue`), находит поле
«цензурированное название песни». Лейбл над полем ввода должен читаться как `Censored:` —
коротко и в стиле остальных лейблов таблицы/формы карточки альбома (паттерн: английский
термин для машинного поля, понятный редактору из контекста).

**Why this priority**: лейбл непосредственно влияет на UX карточки песни — редактор каждый
раз смотрит на него при правке цензурированного названия; длинная русская формулировка
«Композиция (цензурированная):» занимает много места и дублирует смысл с обычным
полем «Название песни», а `Censored:` короче и однозначно.

**Independent Test**: открыть любую карточку песни в админке — лейбл отображает «Censored:»,
а длинная русская формулировка исчезла. Поле ввода и связанные кнопки (undo/copy/paste)
остались на месте и работают.

**Acceptance Scenarios**:

1. **Given** открыта карточка песни в `SongEdit.vue`, **When** редактор смотрит на блок
   «цензурированное название» (под полем обычного `Название песни`), **Then** лейбл над
   полем ввода — `Censored:`.
2. **Given** лейбл переименован, **When** редактор вводит значение в поле, **Then**
   `v-model` связан с тем же полем `song.songNameCensored`, что и раньше (поведение и
   кнопки undo/copy/paste не изменились).
3. **Given** лейбл переименован, **When** редактор наводит курсор на лейбл, **Then**
   всплывающая подсказка `title` с пояснением «Ручное значение используется в публикациях
   (VK/Telegram/News) и публичном API БЕЗ повторной фильтрации…» сохраняется.

### User Story 2 — Поле «Описание» в 2 раза ниже (Priority: P2)

Админ-редактор открывает карточку песни, поле «Описание» отображается в 2 раза ниже текущей
высоты. Текущая высота задаётся атрибутом `rows="4"` у `<textarea>` — уменьшаем до `rows="2"`
(вдвое меньше строк). Поведение (`v-model="song.description"`, кнопка undo) не меняется.

**Why this priority**: UI-уборка карточки — поле «Описание» слишком высокое для большинства
песен, занимает вертикальное место впустую; вдвое меньшая высота оставляет достаточно
места для коротких описаний и при необходимости легко растягивается мышью/контентом.

**Independent Test**: открыть карточку песни с длинным описанием — поле «Описание»
отображается высотой в 2 строки (`rows="2"`); если описание длиннее — содержимое
прокручивается/расширяется стандартным поведением `<textarea>`.

**Acceptance Scenarios**:

1. **Given** открыта карточка песни, **When** редактор смотрит на блок «Описание:», **Then**
   текстовая область визуально в 2 раза ниже, чем раньше (атрибут `rows="2"`).
2. **Given** высота уменьшена, **When** редактор печатает длинный текст, **Then** поле
   продолжает принимать ввод и корректно отображает многострочный текст через
   встроенную прокрутку `<textarea>`.
3. **Given** высота уменьшена, **When** редактор нажимает кнопку undo рядом с полем,
   **Then** значение сбрасывается к сохранённому, как и раньше.

### User Story 3 — Админ может переключать страницы в «Истории прослушиваний» (Priority: P1)

Админ-редактор открывает админ-страницу «История прослушиваний»
(`/listeninghistory`, компонент `ListeningHistoryTable.vue` в `webvue3`). В таблице приходит
большой объём строк, поэтому вверху/внизу таблицы виден `<b-pagination>` с общим числом
страниц. При клике на цифру страницы (или стрелку «вперёд/назад») — таблица перезагружает
данные с бэка с новым смещением, пользователь видит строки соответствующей страницы.

**Why this priority**: пагинация — единственный способ работать с большим списком
(>500 строк на страницу). Без неё админ видит только первую порцию; фича «История
прослушиваний» фактически непригодна, потому что ключевые сценарии (поиск конкретного
прослушивания, аудит удалённой песни) требуют пролистывания за пределы первой страницы.

**Independent Test**: на тестовой LOCAL-базе с числом строк > `perPage` (500) — открыть
страницу истории, кликнуть на цифру «2» в пагинаторе, дождаться обновления, увидеть
новые строки; повторить для других страниц; обновить страницу (F5) — последняя выбранная
страница восстанавливается (см. требование персистентности страницы в `AGENTS.md`).

**Acceptance Scenarios**:

1. **Given** таблица истории прослушиваний загружена, `totalCount > perPage`, **When**
   админ кликает на цифру «2» пагинатора, **Then** на бэк уходит POST-запрос
   `/api/listeninghistory/digest` с актуальным значением `offset`/`page` (или эквивалентным
   параметром пагинации), таблица обновляется строками второй страницы.
2. **Given** пагинация работает, **When** админ кликает «вперёд» / «назад» / «последняя»,
   **Then** аналогичный запрос на бэк уходит для выбранной страницы, таблица обновляется.
3. **Given** админ переключил страницу (например, на «3»), **When** страница перезагружена
   (F5) или админ ушёл на другую страницу админки и вернулся, **Then** пагинатор
   восстанавливается на последней выбранной странице (Vuex-стейт
   `listeningHistoryTableCurrentPage` сохраняется через `setWebvueProp` — паттерн
   персистентности страницы в `AGENTS.md`).
4. **Given** админ на странице > 1, **When** он меняет БД (`Локальная` → `Сервер`) или
   нажимает «Обновить», **Then** текущая страница сбрасывается на «1» и грузится
   первая страница для нового БД/фильтра (текущее поведение через `onTargetChange` /
   `reload`, расширяется на общий сброс при изменении фильтров/поиска).

## Edge Cases

- **Конкуренция: F5 во время клика по пагинатору.** Если админ кликает по странице и тут
  жмёт F5 — после перезагрузки в стейте уже будет лежать новая страница (мутация
  `setListeningHistoryTableCurrentPage` синхронна), загрузка пойдёт для неё — корректно,
  без гонки.
- **Страница превышает число страниц.** Если кто-то удалил строки так, что `currentPage`
  стал больше `Math.ceil(totalCount / perPage)`, пагинатор у `bootstrap-vue-next`
  автоматически сбрасывает на последнюю существующую страницу — поведение должно
  остаться совместимым.
- **`totalCount === 0` (нет ни одной строки).** Пагинатор скрывается (или показывает одну
  «пустую» страницу) — текущее поведение не должно сломаться, пустая заглушка «Истории
  прослушиваний нет» сохраняется.
- **Экран на 4K с большим пагинатором.** `limit="30"` — текущее значение, продиктованное
  `bootstrap-vue-next`; при N > 30 страниц показывается «…» — поведение сохраняем.
- **Описание пустое.** `rows="2"` на пустом `<textarea>` — высота всё равно = 2 строки
  (минимально занимаемая высота формы), поведение идентично другим полям формы.
- **Картинка клика по `Censored:` с тачскрина/уменьшенного окна.** Длинный лейбл
  переносился на 2 строки при узком окне — с коротким лейблом `Censored:` перенос
  исчезает, форма становится компактнее.

## Requirements *(mandatory)*

### Functional Requirements

#### SongEdit.vue (карточка песни в админ-SPA)

- **FR-001**: В компоненте `SongEdit.vue` (`webvue3/src/components/Songs/edit/SongEdit.vue`)
  лейбл блока «цензурированное название песни» MUST отображать текст **`Censored:`** —
  вместо `Композиция (цензурированная):`.
- **FR-002**: Лейбл `Censored:` MUST сохранять атрибут `title` с прежним пояснением
  («Ручное значение используется в публикациях (VK/Telegram/News) и публичном API БЕЗ
  повторной фильтрации…»), чтобы редактор не потерял контекст.
- **FR-003**: Изменение лейбла MUST быть чисто текстовой правкой: `v-model`,
  имя поля `song.songNameCensored`, кнопки undo/copy/paste, заголовок и tooltip —
  без изменений.
- **FR-004**: В блоке «Описание:» MUST быть установлен атрибут `rows="2"` у `<textarea>`
  (вместо текущего `rows="4"`), без изменения `v-model="song.description"` и кнопки undo.

#### ListeningHistoryTable.vue (пагинация)

- **FR-005**: При клике по `<b-pagination>` в компоненте
  `ListeningHistoryTable.vue` (`webvue3/src/components/ListeningHistory/ListeningHistoryTable.vue`)
  на бэк MUST уходить POST `/api/listeninghistory/digest` с актуальным параметром
  пагинации (страница/offset), и результат MUST отображаться в таблице.
- **FR-006**: Текущее значение `currentPage` (state Vuex
  `listeningHistoryTableCurrentPage`) MUST сохраняться через мутацию
  `setListeningHistoryTableCurrentPage` (поведение уже есть) — добавить **триггер
  перезагрузки даных** при изменении `currentPage` (например, через watcher
  `currentPage` → `dispatch('loadListeningHistoryDigest', { page: newPage, … })` или
  аналогичный механизм).
- **FR-007**: Формат запроса на бэк MUST передавать `page` (или `offset`), чтобы бэк
  выдавал соответствующий диапазон строк; при отсутствии параметра бэк ведёт себя как
  раньше (страница 1) — обратная совместимость с текущими вызовами.
- **FR-008**: При смене БД (`onTargetChange`) или по кнопке «Обновить» — `currentPage`
  MUST сбрасываться в `1`, и загрузка MUST идти для первой страницы (текущее
  поведение сохраняется/расширяется).
- **FR-009**: После F5/перезахода на страницу «История прослушиваний» — пагинатор
  MUST восстанавливаться на последней выбранной странице (Vuex и `setWebvueProp` —
  паттерн из `AGENTS.md`, раздел «Персистентность страницы пагинации в webvue3»; ныне
  используется `setListeningHistoryTableCurrentPage` мутация).
- **FR-010**: Пагинация НЕ должна запрашивать бэк, если `totalCount <= perPage`
  (одна страница) — избегаем лишних запросов; текущее поведение через `v-model`
  `<b-pagination>` уже вызывает `@update:model-value` только при изменении, но
  watcher должен идемпотентно не перезагружать, если новая страница = текущая.

### Key Entities

- **`song.songNameCensored`** (карточка песни, фронт-стейт) — цензурированное название;
  значение уже в модели, изменение лейбла не затрагивает сущность.
- **`song.description`** (карточка песни, фронт-стейт) — описание песни; `rows`
  меняется на `2`, длина строки не ограничивается иначе.
- **`listeningHistoryTableCurrentPage`** (Vuex state в `ListeningHistory/store.js`) —
  текущая выбранная страница таблицы истории прослушиваний. Стейт уже
  инициализирован (`1`) и используется `ListeningHistoryTable.vue` как `currentPage` —
  фича его только триггерит на перезагрузку.
- **`/api/listeninghistory/digest`** (бэк-эндпойнт, существующий) — POST-эндпоинт,
  возвращающий `listeningHistoryDigest[]` и `totalCount`. Параметры запроса расширяются
  параметром пагинации (страница/offset) — детализация на этапе `/speckit.plan`.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Лейбл `Censored:` отображается в карточке песни на странице редактирования
  для всех песен (100% случаев, проверка вручную — открыть любую карточку).
- **SC-002**: Атрибут `rows` у `<textarea>` «Описание:» = `2` (проверка через DevTools).
- **SC-003**: Клик по любой странице пагинатора в «Истории прослушиваний» приводит
  к POST `/api/listeninghistory/digest` с актуальным параметром страницы (DevTools →
  Network, 1 запрос на 1 клик, без дребезга).
- **SC-004**: При F5 на странице «Истории прослушиваний» после листания — пагинатор
  восстанавливается на последней выбранной странице и показывает строки соответствующей
  страницы (проверка вручную).
- **SC-005**: Изменения лейбла и высоты описания НЕ затрагивают остальные поля формы,
  бэк-логику, БД-миграции и публичный API — ноль ломающих изменений в смежных
  сценариях (проверка через стандартные сценарии редактирования песни).

## Assumptions

- **A-001**: Перевод лейбла на английский `Censored:` согласован с пользователем
  (запрос пришёл от пользователя — фиксируем как уточнение существующего
  решения).
- **A-002**: Уменьшение `rows` с `4` до `2` — буквально вдвое (UI-твик, никакой
  функциональной логики); auto-grow при фокусе/печати НЕ требуется (не заявлено).
- **A-003**: Параметр пагинации на бэке — `page` (1-based) и/или `offset`+`limit`;
  точное имя параметра и серверная обработка определяются на этапе `/speckit.plan`;
  обратная совместимость с текущим контрактом `/api/listeninghistory/digest`
  сохраняется.
- **A-004**: Текущая мутация `setListeningHistoryTableCurrentPage` в
  `ListeningHistory/store.js` остаётся — добавляется только триггер перезагрузки при
  изменении `currentPage` в `ListeningHistoryTable.vue` (через watcher).
- **A-005**: Пагинация фронта (= 500/стр) уже зафиксирована в `perPage=500` —
  не меняется; на бэке может быть `limit=500` с `offset = (page-1)*500`.
- **A-006**: Стейт `listeningHistoryTableCurrentPage` персистится в server-side
  storage через `setWebvueProp` (паттерн `AGENTS.md`) — текущая ситуация, не
  требует новых правок инфраструктуры. Если персистенция ещё не настроена — фиксируется
  как отдельная подзадача на этапе `/speckit.plan`.
- **A-007**: Файлы изменений: только `SongEdit.vue` и `ListeningHistoryTable.vue`
  (плюс, при необходимости, `ListeningHistory/store.js` для action-обёртки с
  `page`). Никаких изменений в `karaoke-app`, `karaoke-web`, бэк-контроллере
  `ListeningHistoryController.kt` (если бэк уже принимает нужные параметры; иначе —
  минимальный патч контроллера, определяется на плане).
- **A-008**: Ошибка в пагинации — клиентская: Vuex-стейт `currentPage` изменяется,
  но `dispatch('loadListeningHistoryDigest', …)` не вызывается при смене страницы
  (только на `mounted`/`reload`/`onTargetChange`). Пользователь диагностировал
  ровно это поведение.
- **A-009**: Соглашение о стиле лейблов в админке — короткие английские термины
  (паттерн: `id`, `root_id`, `id_status` в других карточках). `Censored:` — в этом
  паттерне. Дополнительный английский лейбл в карточке песни согласован с
  пользователем в этом тикете.
