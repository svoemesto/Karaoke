# Contract: `POST /api/utils/createfromfolder`

**Feature**: [spec.md](../spec.md) | **Data model**: [data-model.md](../data-model.md)

Проект — внутреннее приложение (не библиотека/публичный API). Затронутый
интерфейс — уже существующий HTTP-эндпоинт `ApiController.doCreateFromFolder`
(`karaoke-app/src/main/kotlin/com/svoemesto/karaokeapp/controllers/ApiController.kt:5204-5323`),
вызываемый кнопкой «Добавить файлы из папки» в `webvue3`
(`webvue3/src/components/Songs/store.js:2385-2389`, действие
`createFromFolderPromise`). Формат запроса/ответа **не меняется** — фикс
затрагивает только внутреннее поведение (устойчивость к памяти, полнота
сводки, лейн заданий), не контракт вызова.

Дополнительно существует легаси-дубликат того же пути в `MainController.kt:90`
(`@PostMapping("/utils/createfromfolder")`, без префикса `/api`) — использует
тот же `Song.createFromPath`, получает исправление автоматически; отдельно
не документируется как часть публичного контракта webvue3 (не вызывается
`store.js`), но проверяется в `quickstart.md`, чтобы не остаться сломанным.

## Запрос (без изменений)

```
POST /api/utils/createfromfolder
Content-Type: application/x-www-form-urlencoded (или multipart, как вызывает store.js)

folder=<абсолютный путь к папке на admin-машине>
```

## Поведение (до фикса → после фикса)

| Аспект | До фикса | После фикса |
|---|---|---|
| Обход папки | `Files.walk(...).toList()` — весь список путей всей папки в памяти, `Stream` не закрывается | Однопроходный, фильтрующий во время обхода, закрываемый `Stream` (FR-001/FR-002) |
| Папка с очень большим числом файлов | `OutOfMemoryError`, HTTP-запрос падает без ответа | Запрос успешно завершается, добавляет подходящие файлы (FR-003) |
| Файл с некорректным именем/форматом | Молча пропускается (уже сейчас, `matchResultAlbum`/`matchResultFile` == null → файл не попадает в `result`) | Поведение сохраняется, но учитывается в итоговой сводке как «пропущено» (FR-005) |
| Поиск текста без найденного родителя | `thread(start = true)` без ограничения — по одному потоку на каждую песню без текста | Ограниченный по конкурентности исполнитель (FR-004) |
| `threadId` у кортежа (`DEMUCS2`→`FF_MP3_*`→`UPLOAD_*`) | `THREAD_LANE_HEALTH_REPORT` (=1) — уже так | Без изменений; подтверждено верификацией (FR-006/FR-007/FR-008) |
| `threadId` у `KEY_BPM_FROM_FILE` | `2` (`THREAD_LANE_STEM_JOBS`) — намеренно отдельный лейн, задание не входит в кортеж | Без изменений; поведение подтверждено как корректное, добавлен поясняющий комментарий в коде |

## Ответ (без изменений структуры)

Эндпоинт возвращает `Unit` (`@ResponseBody` без явного тела) — результат
сообщается через существующий SSE-канал (`SNS.send(SseNotification.message(...))`,
тип `"info"`, заголовок «Добавление файлов из папки»). Текст сообщения
расширяется (не меняя тип/канал доставки): вместо «Добавлено файлов из
папки «X»: N» — «Добавлено файлов из папки «X»: N (пропущено: M)», где `M`
— файлы, не прошедшие разбор имени/конвертацию (SC-004). Формат SSE-события
(`type`/`head`/`body`) не меняется — фронтенд `webvue3` не требует правок.

## Постусловие: кортеж заданий

Для каждой успешно добавленной песни, сразу после ответа эндпоинта, в
`tbl_processes` ДОЛЖНА появиться запись `DEMUCS2` с
`thread_id = KaraokeProcess.THREAD_LANE_HEALTH_REPORT`, а по мере её
завершения (через каскад `HealthReport`) — `FF_MP3_ACCOMPANIMENT`,
`FF_MP3_VOCAL`, `UPLOAD_TO_LOCAL_STORE` (муз. + голос),
`UPLOAD_TO_REMOTE_STORE` (муз. + голос) — все в том же лейне (см.
`data-model.md`, диаграмма кортежа). Отдельно (параллельно, не как часть
кортежа) появляется `KEY_BPM_FROM_FILE` с
`thread_id = KaraokeProcess.THREAD_LANE_STEM_JOBS` — это ожидаемо и не
является багом (см. `research.md`, Находка C). Никаких новых полей
DTO/эндпоинтов для наблюдения за этим не вводится — переиспользуется
существующая таблица «Процессы» в `webvue3` (фильтр по `settings_id`).
