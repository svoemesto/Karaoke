## Что делает

Пакет закрывает 40 записей аудита #336 в модуле `karaoke-app` (модель, сервисы,
шаблоны Thymeleaf). Правки сгруппированы по трём партиям:

- **Партия 1** (BR-174…BR-187, 10 записей) — отчёт сухого прогона чистки строится вне
  HTTP-потока; курсор публичной ленты новостей согласован с сортировкой; SQL-сбои
  публичных чтений не выглядят как «пустые данные»; путь к картинке проверяется явно;
  перебор разбиений текста заменён динамикой; гонка при создании картинки больше не
  теряется; XML собирается в одном месте с экранированием; «нет данных» отличается от
  «сбой чтения»; картинки авторов грузятся одним запросом; базовый слой БД логирует
  через SLF4J.
- **Партия 2** (BR-189…BR-199, 10 записей) — конфликт слота публикации виден; имя
  ключа фильтра даты едино; дата публикации разбирается и проверяется; результаты
  поиска удаляются одним запросом; сбои чата не выглядят как пустой чат; флаг
  приветственного сообщения ставится только после успеха; пагинация статистики
  нормализована; uuid читаются пакетно; лимит очереди заданий атомарен; UPDATE uuid
  синтаксически валиден.
- **Партия 3** (BR-202…BR-215, 10 записей) — `<datalist>` читают реальные имена модели;
  пользовательский текст в редакторе субтитров экранируется; скорость редактора берётся
  у активной кнопки; «Сохранить» и «Удалить» работают с выбранной строкой и сообщают
  об ошибке; live-обновление страницы песен переведено на SSE; копирование работает вне
  secure-контекста; Telegram-фильтры попадают в URL.

Ещё 10 записей пакета (BR-182, BR-185, BR-188, BR-195, BR-200, BR-201, BR-205, BR-206,
BR-213, BR-214) закрыты волнами A–D — их правки не дублируются, ссылки на пакеты
приведены в отчёте.

## Зачем

Каждая запись аудита — это наблюдаемый дефект, а не стилистика:

- **Публичный периметр.** `/api/public/news` отдавал `200` с пустой лентой при сбое БД;
  чат показывал «переписку стёрта»; бейдж непрочитанных исчезал. Теперь это `503` с
  кодом ошибки, а «нет данных» и «сбой» различимы.
- **Данные.** Сетка публикаций молча затирала песню конфликтующей; справочник авторов
  тихо размножался при сбое чтения; `.mlt` для песен с `&` в названии был невалидным XML.
- **Ресурсы.** Отчёт чистки держал поток Tomcat десятки секунд (два полных обхода на
  один щелчок); перебор разбиений текста уводил CPU в минуты; на каждого автора шёл
  отдельный SELECT; на каждый ключ MLT — отдельный SELECT uuid.
- **Гонки.** Два параллельных «удалить» удаляли не ту строку; два параллельных
  `POST /create` задания обходили лимит очереди.

## Как работает

Изменения по слоям:

| Слой | Файлы | Что изменилось |
|---|---|---|
| Модель | `model/News.kt`, `model/Pictures.kt`, `model/Picture.kt`, `model/MltNode.kt`, `model/KaraokeDbTable.kt`, `model/Author.kt`, `model/Album.kt`, `model/Publication.kt`, `model/SiteChatMessage.kt`, `model/SiteUser.kt`, `model/StatBySong.kt`, `model/Uuids.kt`, `model/StemJob.kt`, `model/SearchResult.kt`, `model/SearchAsync.kt` | строгий режим чтения (`throwOnError`), безопасный разбор дат, единое экранирование XML, пакетная загрузка, атомарный лимит очереди |
| Сервисы | `services/cleanup/ArtifactCleanup{Planner,Service}.kt` | асинхронное построение отчёта, один `sizeOf` на файл, сверка состава в фоновом прогоне |
| Контроллеры | `controllers/{Cleanup,Chat,Main,Api}Controller.kt`, `karaoke-web/.../{PublicNews,PublicChat,PublicStemJob}Controller.kt` | `202`/`503`/`400` вместо «пустого успеха», проверка результата удаления, валидация даты публикации |
| Шаблоны | `templates/{main,songs,songs2,editsubs}.html` | `<datalist>`, экранирование, SSE, копирование, фильтры |
| Утилиты | `Extentions.kt`, `Uuids.kt` | `escapeXml()`, кеш uuid |

Общие принципы, которым подчинены правки:

1. **Сбой ≠ пустой результат.** Чтение, которое может упасть, либо пробрасывает
   исключение, либо возвращает явный признак ошибки (`COUNT_ERROR = -1`).
2. **Fail-closed.** Если состояние неизвестно (счётчик не получен, БД недоступна) —
   действие не выполняется: задание не создаётся, песня не удаляется, автор не
   создаётся.
3. **Одно место экранирования.** XML собирается в `MltNode.toString()`; ручные
   `replace("&", "&amp;")` из вызывающих убраны.
4. **Работа вне HTTP-потока.** Долгие обходы (отчёт чистки) идут в executor'е, клиент
   опрашивает состояние.

## Инварианты

| Инвариант | Где зафиксирован |
|---|---|
| Сбой чтения БД не выглядит как «строк нет»: `loadList(throwOnError = true)` пробрасывает `SQLException` | `model/KaraokeDbTable.kt` |
| Create-or-get не создаёт сущность при сбое чтения (`Album.findOrCreateForSongImport`, `Utils.getAuthorForRequest`) | `model/Album.kt`, `Utils.kt` |
| XML-экранирование выполняется только при сериализации узла (`MltNode.toString()` → `escapeXml()`) | `model/MltNode.kt`, `Extentions.kt` |
| Дата публикации — строгий формат `dd.MM.yy`, время — `HH:MM`; неверное значение отклоняется при записи и не роняет страницу | `model/Publication.kt`, `controllers/MainController.kt` |
| Не более одной песни на слот `(publish_date, publish_time)`: конфликт не затирает песню, а пишется в журнал | `model/Publication.kt` |
| Счётчик активных заданий пользователя известен точно (`COUNT_ERROR = -1` = неизвестен); лимит проверяется и применяется в одной транзакции под `pg_advisory_xact_lock` | `model/StemJob.kt` |
| Пары `(id, uuid)` читаются одним запросом и раздаются из кеша процесса | `model/Uuids.kt` |
| Пагинация статистики нормализована: `limit ∈ [1, 1000]`, `offset ≥ 0` | `model/StatBySong.kt` |
| Ключи MLT-моделей читаются из кеша, а не по одному SELECT'у на ключ | `Uuids.kt` |

## Известные ловушки

1. **Контракт `POST /api/cleanup/plan` изменился**: было `200` с отчётом, стало `202` с
   `planId`; отчёт забирается `GET /api/cleanup/plan/{planId}`. Проверка состава при
   `apply` перенесена в фоновый прогон: несовпадение отпечатка теперь даёт `FAILED`
   прогон (`errors[0] = "fingerprint_mismatch: …"`), а не HTTP `409`. Клиентский отпечаток
   по-прежнему проверяется синхронно (`409`). Контрактный документ
   `specs/544-song-artifact-cleanup/contracts/cleanup-api.md` **не обновлён** (чужой issue) —
   синхронизация за владельцем.
2. **Счётчики чата возвращают `-1` при сбое БД.** Любой новый потребитель
   `SiteChatMessage.count*` обязан проверять `-1` и отдавать `503`, а не показывать «0».
3. **`MltNode` экранирует сам.** Если кто-то добавит в `fields` или `body` уже
   экранированную строку, получится двойное экранирование (`&amp;amp;`). Экранировать
   вручную нельзя — ручные `replace` убраны из 20 мест.
4. **Пределы разбиения текста** (`MAX_SPLIT_WORDS = 24`, `MAX_SPLIT_LINES = 10`) влияют на
   вид длинных названий: сверх 24 слов разбиение не выполняется (однострочная
   раскладка) — это компромисс между качеством и временем рендера.
5. **SSE вместо STOMP.** Страница `/songs` теперь получает live-события по
   `GET /api/subscribe`; payload — `{type:"recordChange", data:{recordId,tableName,diffs}}`,
   таблица песен — `tbl_songs`. События приходят по всем таблицам — фильтруйте по `tableName`.
6. **Clipboard API работает только в secure-контексте.** Админка `karaoke-app` слушается
   по HTTP, поэтому копирование идёт через `copyToClipboardSafely` (fallback на
   `execCommand`). Новые кнопки копирования должны вызывать именно его.
7. **`GET /song/{id}/delete` — GET-мутация.** Ответ изменился с «всегда 0» на
   «1 — удалено, 0 — не найдено»; клиент проверяет результат. Сам эндпоинт остаётся
   GET-мутацией (это отдельная тема аудита).
8. **Кеш uuid живёт в процессе.** После перезапуска он перечитывается из БД; при
   появлении ключа другим процессом `getStoredUuid` перечитывает значение из БД, чтобы
   uuid в MLT совпадал с uuid в БД.
9. **Публичный UNIQUE-индекс на `(publish_date, publish_time)` и на `tbl_authors.author`
   не созданы** — нужны миграция и дедупликация (запись в БД пакетом запрещена).
10. **Легаси-страницы `/songs` и `/songs2` живут** — точечные фиксы сделаны, но полный
    перенос на webvue3 в этом пакете не выполнялся.
