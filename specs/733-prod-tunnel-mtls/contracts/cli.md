# Contract: CLI скриптов туннеля

> Часть Phase 1 (`/speckit-plan`). Скрипты живут в `deploy/prod-tunnel/`.
> Все команды безопасны по умолчанию: без `--apply`/`--install` ничего не меняется.

## 1. `deploy/prod-tunnel/selftest.sh`

Изолированная проверка механики туннеля **без прода и без прав root**.

```bash
bash deploy/prod-tunnel/selftest.sh            # полный прогон
bash deploy/prod-tunnel/selftest.sh --list      # только список сценариев
```

Сценарии:

| # | Сценарий | Ожидание |
|---|---|---|
| 1 | Два namespace'а + veth, `wg0` в каждом, рукопожатие | `wg show` показывает handshake, ping `10.77.0.2` отвечает |
| 2 | Маршрут по умолчанию не изменён | в namespace'ах `ip route show default` — пусто/не тронут |
| 3 | Третий namespace' («хост») + маршрут + SNAT | host видит `10.77.0.2`, источник пакета на пире — `10.77.0.1` (тот же адрес, что и у приложения) |
| 4 | Переопределение резолвинга имени хоста | `getent hosts sm-karaoke.ru` → `10.77.0.2`, SNI/Host не меняются |
| 5 | Устаревшее рукопожатие | при отсутствии рукопожатий состояние = `stale` (детектор работает) |
| 6 | Отсутствие ключа | конфигурация отклоняется с причиной `no_key` |

Код возврата: `0` — все сценарии прошли, `1` — есть проваливший сценарий.

Требования к среде: `ip`, `wg` (в PATH), ядро с WireGuard, разрешённые
unprivileged user namespaces (`unshare --user --map-root-user --net`).

## 2. `deploy/prod-tunnel/install-admin-tunnel.sh`

Подготовка админской стороны. По умолчанию — **только проверка**; изменения
требуют `--apply`.

```bash
bash deploy/prod-tunnel/install-admin-tunnel.sh --check    # что будет сделано (dry-run)
bash deploy/prod-tunnel/install-admin-tunnel.sh --apply    # создать ключи и конфиг
```

| Флаг | Действие |
|---|---|
| `--check` | Проверки: наличие `wg`, `/dev/net/tun`, свободна подсеть, конфликт подсетей, права каталога. Ничего не меняет. |
| `--apply` | Создаёт `/etc/karaoke/tunnel` (`700`), генерирует приватный ключ админского пира (`600`), пишет `wg0.conf` (`600`) с публичным ключом пира prod (передаётся переменной `PROD_TUNNEL_PEER_PUBLIC_KEY`), печатает **публичный** ключ админского пира (его нужно передать на прод). |
| `--print-public-key` | Печатает публичный ключ админского пира (нужен для конфига на проде). |
| `--help` | Справка. |

Коды возврата: `0` — ок; `1` — ошибка окружения/конфигурации; `2` — ошибка
использования.

**Секреты**: приватный ключ создаётся на месте и никогда не печатается и не
попадает в репозиторий; печатается только публичный ключ.

## 3. `deploy/prod-tunnel/install-prod-tunnel.sh`

Установка пира **на прод-хосте**. Запускается владельцем (или агентом — только по
отдельному согласию). Скрипт **сам** по себе ничего не делает на удалённом хосте:
он готовит файлы и печатает точные команды для выполнения.

```bash
bash deploy/prod-tunnel/install-prod-tunnel.sh --print-commands
```

Печатает (для владельца):

```bash
# 1. Установить wireguard-tools на проде
apt-get install -y wireguard-tools
# 2. Создать каталог и записать ключи/конфиг (содержимое — из подготовленных файлов)
install -d -m 700 /etc/wireguard
install -m 600 /tmp/prod-tunnel/wg0.conf /etc/wireguard/wg0.conf
# 3. Поднять туннель и проверить рукопожатие
wg-quick up wg0
wg show wg0
# 4. Откат
wg-quick down wg0
```

## 4. `deploy/prod-tunnel/host-route.sh`

Маршрут на хосте админской машины в подсеть туннеля (через контейнер
`karaoke-app`) — то, что делает туннель доступным оператору (DBeaver).

```bash
bash deploy/prod-tunnel/host-route.sh --check    # показать текущее состояние
bash deploy/prod-tunnel/host-route.sh --apply    # поставить/обновить маршрут
bash deploy/prod-tunnel/host-route.sh --remove   # снять маршрут (откат)
```

| Параметр | По умолчанию | Описание |
|---|---|---|
| `PROD_TUNNEL_SUBNET` | `10.77.0.0/24` | подсеть туннеля |
| `PROD_TUNNEL_CONTAINER` | `karaoke-app` | имя контейнера, чей IP используется как шлюз |
| `PROD_TUNNEL_GATEWAY_IP` | — | явный IP (если контейнер не найден) |

Требует root (маршрут в системном пространстве) — устанавливается юнитом
`karaoke-tunnel-host-route.service` (в репозитории, установку выполняет владелец).

## 5. `deploy/admin-ip-allowlist.sh --self-test` (дополнение)

Новый сценарий 9: **режим туннеля** (`ALLOWLIST_MODE=tunnel`):

- скрипт **не** определяет публичный адрес;
- скрипт **не** пишет в allow-list прод-хоста публичный адрес (проверяется, что
  в содержимом файла после прогона нет ни одного `allow <публичный ip>;`);
- скрипт проверяет, что в каждом блоке с `deny all;` ровно один адрес —
  `10.77.0.1` (адрес туннеля);
- при расхождении — событие `decision:reason=tunnel_address_mismatch` и
  ненулевой код возврата (без применения правки).

Коды возврата скрипта (существующие): `0` — ок, `1` — сбой, `2` — ошибка
использования, `3` — отказ (decline).
