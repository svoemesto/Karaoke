## Диагностика (факты, 2026-11-08)

Разбор — по журналу механизма `/var/log/admin-ip-allowlist.log`, по stream-журналу nginx на проде и по логам контейнера `karaoke-app` (`docker logs`).

**Факт 1 — механизм не сработал ни разу за смену адреса.** Журнал за 12:19–12:49 UTC (каждые 10 минут) содержит только:

```
event:address source=https://api.ipify.org    value=195.178.4.154
event:address source=https://ifconfig.me/ip   value=195.178.4.155
event:address source=https://icanhazip.com     value=95.31.39.146
event:skip    reason=sources_disagree detail=195.178.4.154_195.178.4.155_95.31.39.146_…
```

Внешние сервисы **расходятся**: `api.ipify.org` и `ifconfig.me` отвечают через VPN-туннель с ротацией адресов (`195.178.4.144…166`, новый адрес каждый цикл), остальные четыре — через адрес ISP (`95.31.39.146`, стабильный). Правило «все источники должны совпасть» (ADR local-0015, Decision п. 3) давало `sources_disagree` → цикл завершался кодом 3, **правка allow-list не выполнялась никогда**.

**Факт 2 — прод знает наш адрес, и он один.** `SSH_CLIENT` на прод-хосте: `95.31.39.146`. Stream-журнал nginx на проде (включён при разборе) показал, что и хост, и контейнер `karaoke-app` приходят к `188.127.240.124:5433/9000` **с того же адреса** `95.31.39.146`. То есть адрес, который видит прод на канале SSH, — и есть тот, который нужен в allow-list; внешние сервисы отвечали про другой (ротируемый) маршрут.

**Факт 3 — откат ломал конфиг прод-хоста.** При неудачной контрольной проверке вызывался `rollback_change remote "${PROD_CONF}" "${BACKUP_PATH}"`, где `PROD_CONF` — первый файл (`/etc/nginx/nginx.conf`), а `BACKUP_PATH` — бэкап **последнего** обработанного файла (`80to8897`). В итоге `/etc/nginx/nginx.conf` получал содержимое файла сайта: `nginx -t` падал (`"server" directive is not allowed here`), прод остался с неработающей конфигурацией (восстановлено вручную 2026-11-08, 16:00).

**Факт 4 — список разросся.** На проде было 9–10 адресов (`185.26.28.109`, `83.137.50.231`, `185.42.124.207`, …), накопленных «про запас» решением 2026-10-07. Доступ оставался открытым для всех, кто когда-либо был админ-машиной.

**Факт 5 — приложение зависит от этого канала.** `karaoke-app` ходит в прод-БД и MinIO с админ-машины; при закрытом allow-list очередь работает «вслепую» (синхронизация и загрузка файлов падают).

## Пользовательские истории

### US1 — как администратор (P1)

**Как** администратор Караоке, **я хочу**, чтобы при смене внешнего адреса админ-машины доступ к прод-каналу (5433/9000) восстанавливался автоматически, **чтобы** приложение не оставалось без прод-БД.

### US2 — как администратор (P1)

**Как** администратор, **я хочу**, чтобы в allow-list на проде был ровно один текущий адрес админ-машины, **чтобы** старые адреса не держали доступ открытым.

### US3 — как владелец (P1)

**Как** владелец, **я хочу**, чтобы механизм никогда не оставлял прод в нерабочей конфигурации, **чтобы** сбой автоматизации не превращался в outage.

## Функциональные требования

**FR-001 (US1)**: определение текущего адреса **приоритетно** берётся у самого прод-хоста (`SSH_CLIENT` в SSH-сессии к проду). Внешние сервисы определения IP используются как **запасной** источник.

**FR-002 (US1)**: расхождение внешних сервисов **не блокирует** правку, если адрес получен у прод-хоста. Расхождение фиксируется в журнале как факт (`event=address source=prod_ssh`).

**FR-003 (US1)**: перепроверка адреса перед применением (`confirm_address`) использует тот же источник, что и определение, — гонка смены адреса сохраняется невозможной.

**FR-004 (US2)**: подготовка конфигурации **заменяет** весь список allow-адресов в каждом блоке с `deny all;` на **ровно одну** строку `allow <текущий адрес>;`. Прежние адреса удаляются; правила вида `allow 10.0.0.0/8;` (подсети) не трогаются.

**FR-005 (US2)**: файл считается не требующим правки, только если в **каждом** его блоке с `deny all;` стоит ровно один allow-адрес — текущий.

**FR-006 (US2)**: проверка diff'а допускает изменение **только** строк `allow` с IPv4-адресами; всё остальное содержимое файла должно совпасть байт-в-байт.

**FR-007 (US3)**: откат восстанавливает **каждый** изменённый файл **из его собственного** бэкапа; бэкапы разных файлов не смешиваются.

**FR-008 (US3)**: контрольная проверка (5433/9000/HTTPS) при неудаче откатывает все уже применённые файлы и пишет в журнал `event=rollback ok=true` с указанием файла.

**FR-009 (US1)**: журнал содержит событие с источником адреса (`source=prod_ssh` / `source=<внешний сервис>`) — по журналу видно, откуда взят адрес, применённый к прод-хосту.

**FR-010 (US3)**: при откате файл восстанавливается тем же способом записи, которым был изменён (`mv` → атомарное переименование, `cat` → подмена содержимым).

## Нефункциональные требования

- **NFR-001**: самопроверка `--self-test` покрывает новые правила (сценарии 19–21) и остаётся полностью изолированной от сети.
- **NFR-002**: правка на прод-хосте остаётся хирургической: бэкап, `nginx -t`, reload, контрольная проверка, откат.
- **NFR-003**: правки в `knowledge/` выполняются синхронно с кодом (Knowledge SSoT).

## Критерии успеха

- **SC-001**: при расхождении внешних IP-сервисов механизм всё равно применяет правку (адрес взят у прод-хоста) — проверяется сценарием 19.
- **SC-002**: после правки в каждом блоке `deny all;` прод-конфига ровно один `allow` — проверяется сценарием 20 на реальных конфигах.
- **SC-003**: при неудачной контрольной проверке оба файла восстанавливаются из своих бэкапов — проверяется сценарием 21.
- **SC-004**: `bash deploy/admin-ip-allowlist.sh --self-test` — все сценарии пройдены (21).
- **SC-005**: на прод-хосте после цикла: `nginx -t` — успешно, список — один адрес, приложение не пишет `DB-CONNECT-001`.

## Допущения

- Канал к прод-хосту для SSH и для TCP 5433/9000 выходит с одного внешнего адреса (проверено 2026-11-08 по stream-журналу nginx).
- Прод-хост доступен по SSH с админ-машины (иначе правка невозможна в принципе — как и раньше).
- Адрес админ-машины — обычный публичный IPv4.

## За границами спеки

- **Смена транспорта**: постоянный туннель между админ-машиной и продом (WireGuard/Amnezia), mTLS вместо allow-list по IP, публикация БД только на loopback — это отдельное решение владельца, вынесенное на обсуждение после фикса (§ «Предложение владельцу» в `report.md`).
- Правка HTTP-части конфигурации сайта (CSP-заголовки и т. п.) — расхождение репозиторной копии и прода не входит в эту спеку.
- Ротация адресов у провайдера сама по себе не решается — решается доступность канала.
