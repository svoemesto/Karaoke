# Phase 1 Data Model: Убрать мониторинг запланированных публикаций

Эта фича не вводит новых сущностей данных — спецификация (`spec.md`, раздел
«Key Entities») явно отмечает раздел как неприменимый: фича удаляет
существующую проверку мониторинга и связанную настройку, ничего не заменяя.

## Существующие артефакты, которые убираются (не «данные», а поведение/конфигурация)

Для полноты — что именно перестаёт существовать как часть системы (это не
таблицы БД и не DTO с изменяемой схемой, а элементы уже существующих
in-memory/конфигурационных структур):

| Артефакт | Тип | Текущее место | Действие |
|---|---|---|---|
| `TelegramHorizonCheck` | реализация `MonitorCheck` (in-memory, Kotlin `object`) | `MonitorRegistry.checks` (список из 8 элементов) | удалить элемент → список из 7 |
| `monitorTelegramHorizonDays` | запись `KaraokeProperty` (персистится в `Karaoke.properties`, не в PostgreSQL) | `KaraokeProperties.kt`, список `listKaraokeProperties` | удалить запись целиком |
| `telegram.horizon` | значение поля `MonitorAlert.key` (алерт формируется только в рантайме, нигде не хранится как отдельная строка схемы) | генерируется внутри `TelegramHorizonCheck.run()` | перестаёт когда-либо формироваться (класс удалён) |

## Существующие сущности, которые НЕ меняются

- `MonitorAlert` (форма DTO алерта: `key`, `severity`, `title`, `body`,
  `category`, `detail`, `recommendations`, `resolveAction`) — схема не
  меняется, остаётся общей для всех проверок.
- `MonitorContext` (`localDb`/`storageService`/`storageApiClient`) — не
  меняется, продолжает передаваться в оставшиеся семь проверок.
- `KaraokeProperty` (общая модель настройки: `key`/`defaultValue`/
  `description`) — схема не меняется, убирается только одна конкретная запись.
- `Song` — модель не меняется; `TelegramHorizonCheck` был одним из
  потребителей `Song.loadListFromDb`, но сама модель/метод используются
  множеством других мест и остаются как есть.

## State transitions

Не применимо — фича не вводит и не меняет жизненный цикл/состояния
сущностей. Единственное «состояние», косвенно затронутое, — персистентная
JSON-карта `monitorDismissed` (`key -> contentHash` прочитанных алертов):
после удаления проверки в ней может остаться ранее записанный, но больше не
используемый ключ `telegram.horizon`. Это сознательно оставлено без миграции
(см. `research.md`, п. 2) — карта продолжает работать штатно для остальных
ключей, посторонний ключ не читается и не мешает.
