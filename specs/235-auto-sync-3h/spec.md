# Feature Specification: Автозапуск «Синхронизации в 1 клик» каждые 3 часа

**Feature Branch**: `235-auto-sync-3h`
**Created**: 2026-08-16
**Status**: Draft
**Input**: User description: "В админке \"Синхронизация в 1 клик\" должна запускаться автоматически каждые 3 часа."

## Clarifications

### Session 2026-08-16

- Q: Что должен видеть администратор, если он вручную кликнул «🔄 Синхронизация в 1 клик» в момент автозапуска? → A: HTTP `409 Conflict` с телом `{"error":"sync_in_progress",…}`; UI показывает alert «Автосинхронизация уже выполняется в фоне, дождитесь завершения»; автозапуск не прерывается. Зафиксировано в `FR-015`, `US1 AC2`, `A-006`.
- Q: Как UI страницы `/sync` узнаёт о статусе автозапуска — REST, SSE или polling? → A: только REST-эндпоинт `GET /api/sync/auto-status` (Vuex action `loadSyncAutoStatusPromise` в `mounted()` `SyncTable.vue`). SSE-push не нужен. Требование «обновление в течение 1 секунды» снято (SC-006 переформулирован). Зафиксировано в `FR-009`, `US3 AC1-AC3`, `A-009`.
- Q: Что делать автозапуску, если обе БД (или одна) недоступны в момент тика? → A: fail-fast — тело тика в `try/catch (Throwable)`, исключение логируется с полным стеком, тик помечается `FAILED` в истории, следующий тик через `fixedDelay` пытается снова. Без retry внутри тика. Зафиксировано в `FR-016`, `SC-009`, новый edge-case в `Edge Cases`.

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Админ не успевает кликать кнопку вручную (Priority: P1)

Администратор Karaoke работает за admin-машиной не круглосуточно. За время его отсутствия (ночь, выходные, поездка) изменения, сделанные другими редакторами/пользователями на SERVER-БД, не попадают в LOCAL-БД и наоборот. В понедельник утром приходится вручную нажимать «Синхронизация в 1 клик» и ждать окончания, прежде чем продолжить редактирование.

После фикса: пока admin-машина работает, синхронизация LOCAL↔SERVER запускается сама каждые 3 часа. Администратор возвращается — данные уже актуальны, кнопка осталась на месте для ручного форс-запуска «прямо сейчас».

**Why this priority**: это и есть смысл запроса («должна запускаться автоматически каждые 3 часа»). Без US1 фича не существует.

**Independent Test**: Запустить `karaoke-app`, дождаться ≥ 1 автотика, открыть `tbl_songs` обеих БД — отметка `last_modified` на SERVER-стороне отразилась в LOCAL. Повторно кликнуть кнопку вручную — работает как раньше, без конфликта с автозапуском.

**Acceptance Scenarios**:

1. **Given** `karaoke-app` запущен ≥ 3 часов, **When** системное время достигает очередной 3-часовой отметки, **Then** в логах появляется `[AutoOneClickSyncScheduler] tick=...` и выполняется `POST /api/sync/oneclick` для всех `SyncRegistry.all`.
2. **Given** автозапуск уже работает, **When** администратор вручную кликает «🔄 Синхронизация в 1 клик» в UI, **Then** ручной эндпоинт `POST /api/sync/oneclick` возвращает HTTP `409 Conflict` с телом `{"error":"sync_in_progress",…}`, UI показывает alert «Автосинхронизация уже выполняется в фоне, дождитесь завершения», автозапуск **не прерывается**.
3. **Given** `karaoke-app` только что стартовал, **When** прошло менее `initialDelay` (по умолчанию 5 минут), **Then** автозапуск **ещё не срабатывал** (не мешает штатному подъёму сервиса).
4. **Given** предыдущий автозапуск ещё выполняется (sync занял > 3 часов из-за большого объёма), **When** приходит время следующего тика, **Then** новый тик **пропускается** (не запускает вторую копию) и в лог пишется предупреждение `skipped — previous run still in progress`.

### User Story 2 — Админ хочет отключить автосинхронизацию (Priority: P2)

Администратор работает над большой миграцией `tbl_songs` локально и не хочет, чтобы каждые 3 часа его незакоммиченные правки уезжали на SERVER. Он отключает автосинхронизацию, продолжая иметь возможность кликнуть вручную.

**Why this priority**: безопасность и контроль. Без возможности выключить фича может навредить (см. feature 092, где sync-окна специально выключают). Минимальный MVP без US2 рискует «поломать» workflow миграции.

**Independent Test**: Выставить настройку `karaoke.autoOneClickSync.enabled=false`, перезапустить `karaoke-app`, дождаться ≥ 3 часов — автозапуск не сработал; кнопка вручную работает.

**Acceptance Scenarios**:

1. **Given** `karaoke.autoOneClickSync.enabled=false` в настройках, **When** прошло ≥ 3 часов, **Then** автозапуск **не** срабатывает, в логах при старте — `[AutoOneClickSyncScheduler] disabled by config`.
2. **Given** автозапуск выключен, **When** администратор вручную кликает «🔄 Синхронизация в 1 клик», **Then** ручной запуск работает как обычно (настройка влияет **только** на автозапуск).
3. **Given** администратор снова включает `enabled=true`, **When** проходит `initialDelay`, **Then** автозапуск возобновляется в штатном режиме.

### User Story 3 — Админ видит историю и время последнего автозапуска (Priority: P3)

Администратор открывает страницу синхронизации в админке и хочет сразу видеть: «когда последний раз автосинхронизация отработала и сколько записей прошло» — чтобы не гадать, актуальны ли данные, и не запускать лишний ручной sync.

**Why this priority**: наблюдаемость. US3 — это улучшение UX, не блокер MVP. Без неё фича всё равно работает, просто админу придётся лезть в логи.

**Independent Test**: Открыть UI страницы `/sync`, в новом блоке видно: «Последний автозапуск: 2026-08-16 12:00:00 (добавлено X, изменено Y, удалено Z)» либо «Никогда ещё не запускался».

**Acceptance Scenarios**:

1. **Given** автозапуск отработал ≥ 1 раз, **When** администратор открывает страницу `/sync` (или обновляет её), **Then** Vuex action `loadSyncAutoStatusPromise` дёргает `GET /api/sync/auto-status`, в UI отображается `lastRun.startedAt` (время) и `lastRun.totals` (`created/updated/deleted`).
2. **Given** `karaoke-app` только что стартовал, **When** администратор открывает `/sync`, **Then** UI показывает «автозапуск ещё не выполнялся с момента старта» (отсутствие записи в `lastRun`).
3. **Given** автозапуск был пропущен (US1.4) из-за параллельного выполнения, **When** открыт `/sync`, **Then** UI показывает `lastRun.reason="previous run still in progress"` (последний тик в `last10`).

### Edge Cases

- **App не работает в момент тика** — desktop-приложение, его выключили в 02:00 и включили в 09:00. Что произойдёт в 05:00 / 08:00? Планировщик не может выполниться вне JVM → пропуск без ошибки, при старте `initialDelay` откладывает первый запуск.
- **Sync длиннее 3 часов** — например, миграция 50 000 песен. US1.4: следующий тик пропускается (lock), а не запускает параллельную копию и не «догоняет».
- **Ручной клик во время автозапуска** — что видно пользователю? Вариант A: ручной клик получает `409 Conflict` с понятным сообщением; вариант B: оба идут параллельно, финальные данные идемпотентны благодаря `recordhash`. Выбираемый вариант — см. Assumptions.
- **`SyncRegistry.all` пуст** (например, при первом старте до инициализации) — autotick не падает, логирует `no targets registered` и no-op.
- **Исключение в одном из `target`** — один упавший `SyncTarget` не должен ломать весь тик: исключение логируется, остальные сущности продолжают. Это уже поведение существующего `postSyncOneClick` (он не имеет `try/catch` per-target, см. Open Questions).
- **Смена часового пояса / DST** — `fixedDelay` отсчитывает от момента завершения предыдущего, поэтому смена пояса не «перепрыгивает» тик. Сценарий безопасен.
- **Очень долгий `initialDelay`** — если `initialDelay` задан больше `fixedDelay`, тик всё равно произойдёт один раз; в нашей реализации дефолт `initialDelay=5 мин`, `fixedDelay=3 ч`, конфликта нет.
- **БД недоступна в момент тика** — Postgres-контейнер упал, диск отвалился, нет сети до SERVER. Scheduler ловит исключение (FR-016), помечает тик `FAILED`, пишет полный стек в лог. Следующий тик через `fixedDelay` попробует снова. **Без retry внутри тика** — fail-fast безопаснее, ретраи усложняют код.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система MUST запускать существующую бизнес-логику «Синхронизации в 1 клик» (эквивалент `POST /api/sync/oneclick`) автоматически каждые **3 часа**, пока запущен `karaoke-app`.
- **FR-002**: Интервал 3 часа MUST быть реализован как `fixedDelay` от момента **завершения** предыдущего тика (не `fixedRate` от начала), чтобы длинные синхронизации не накапливались в очереди.
- **FR-003**: Первая синхронизация после старта MUST быть отложена на `initialDelay` (по умолчанию 5 минут), чтобы не нагружать БД во время подъёма сервиса.
- **FR-004**: Должна быть настройка `karaoke.autoOneClickSync.enabled` (дефолт `true`), позволяющая полностью отключить автозапуск без влияния на ручную кнопку.
- **FR-005**: Должна быть настройка `karaoke.autoOneClickSync.intervalMs` (дефолт `10800000` = 3 ч) для возможности изменения интервала без перекомпиляции.
- **FR-006**: Должна быть настройка `karaoke.autoOneClickSync.initialDelayMs` (дефолт `300000` = 5 мин).
- **FR-007**: Автозапуск MUST использовать in-process `ReentrantLock` (или эквивалент) на время выполнения тика, чтобы один и тот же sync не запустился параллельно по двум причинам (ручной клик + автотик) одновременно. Поведение при попытке параллельного ручного клика — см. Assumptions.
- **FR-008**: Каждый тик MUST логировать: `start time`, `end time`, `duration`, `targets processed`, `records created/updated/deleted/moved` (суммарно), `skipped reason` (если был пропуск).
- **FR-009**: Сведения о последних автозапусках MUST быть доступны через новый REST-эндпоинт `GET /api/sync/auto-status`, возвращающий JSON: `{enabled: bool, lastRun: AutoOneClickSyncRunDto|null, last10: AutoOneClickSyncRunDto[] (≤10 записей), nextRunEstimate: ISO-8601|null}`. `AutoOneClickSyncRunDto` — `{startedAt, finishedAt, status, reason, totals: {created,updated,deleted,moved}, perTarget: [{key, displayName, skipped, created, updated, deleted, moved}]}`. Срок хранения истории — **минимум 10 последних тиков в памяти процесса** (in-memory `ConcurrentLinkedDeque`, при перезапуске процесса история начинается заново — это ожидаемо). **Push-уведомления (SSE) НЕ требуются**: UI обновляет блок «Автозапуск» при монтировании `SyncTable.vue` через `loadSyncAutoStatusPromise` (Vuex action) + `mounted()` hook, и затем по F5. См. `US3 AC1-AC3`.
- **FR-010**: Существующее ручное поведение кнопки «🔄 Синхронизация в 1 клик» MUST быть сохранено без изменений в UI-контракте.
- **FR-011**: Если `SyncRegistry.all` пуст, автозапуск MUST логировать `no targets registered` и завершаться как no-op, без исключения.
- **FR-012**: Ошибка в одной `SyncTarget` MUST изолироваться (try/catch вокруг per-target вызова), чтобы упавшая сущность не ломала остальные в том же тике. В лог пишется `target=... failed: <message>`, остальные продолжают.
- **FR-013**: При выключенной фиче (`enabled=false`) scheduler-бин либо не запускает `@Scheduled`-метод, либо метод сразу выходит; в лог при старте пишется `disabled by config`.
- **FR-016**: При недоступности БД (или любом другом исключении во время тика — `SQLException`, `IOException`, `RuntimeException`) scheduler MUST **fail-fast**: тело `@Scheduled`-метода обёрнуто в `try/catch (Throwable)`, исключение логируется с полным стеком (`[AutoOneClickSyncScheduler] tick=... FAILED`), тик помечается `status=FAILED, reason="<exception class>: <message>"` в `AutoOneClickSyncHistory`. Следующие тики продолжают работать (Spring не «отключает» `@Scheduled` после одного исключения). **Без retry**: неудачный тик не перезапускается, ждём следующего `fixedDelay`. Это безопаснее, чем сложная логика ретраев, и админ видит проблему в логе и в UI-блоке.
- **FR-014**: На странице `/sync` админки MUST отображаться блок «Автозапуск» с: статус (`enabled/disabled`), `lastRunAt`, `nextRunAt` (оценка), краткая сводка последнего тика.
- **FR-015**: При параллельной попытке ручного клика во время автозапуска система MUST отдавать **HTTP `409 Conflict`** с телом `{"error":"sync_in_progress","message":"Автосинхронизация уже выполняется в фоне, дождитесь завершения"}`. Эндпоинт `POST /api/sync/oneclick` обязан захватывать тот же in-process `ReentrantLock`, что и автозапуск; если lock занят — вернуть `409` **до** старта какой-либо обработки. UI показывает ошибку как alert (паттерн `showResultAlert` / `isAlert:true, alertType:'error'` в `SyncTable.vue`).

### Key Entities

- **AutoOneClickSyncConfig** (настройка): `enabled: Boolean`, `intervalMs: Long`, `initialDelayMs: Long`. Источник: `KaraokeProperties` (как у `editorAssignmentDefaultTarget`).
- **AutoOneClickSyncRun** (запись о тике): `startedAt: Instant`, `finishedAt: Instant?`, `status: "RUNNING"|"SUCCESS"|"SKIPPED"|"FAILED"`, `reason: String?` (для SKIPPED), `totals: {created, updated, deleted, moved}`, `perTarget: Map<key, SyncOneClickResultDto>`.
- **AutoOneClickSyncHistory** (in-memory store): `List<AutoOneClickSyncRun>` длиной ≤ 10, потокобезопасный (`Collections.synchronizedList` или `ConcurrentLinkedDeque`).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: В течение 3 часов ± 5 минут после старта `karaoke-app` в логах появляется как минимум **1** запись `[AutoOneClickSyncScheduler] tick=... SUCCESS ...` (если `enabled=true`).
- **SC-002**: При ручном клике «🔄 Синхронизация в 1 клик» после внедрения фичи **100%** ручных запусков завершаются так же, как до внедрения (тот же JSON-ответ, та же кнопка, та же длительность ±20%).
- **SC-003**: При двух одновременных попытках запуска (ручной + автотик) **не более 1** фактически выполняется, вторая корректно отбивается сообщением `sync_in_progress` (или эквивалент) — измеримо по количеству `[AutoOneClickSyncScheduler] acquired lock` записей.
- **SC-004**: Если `karaoke-app` непрерывно работает 24 часа, в логах **ровно 8 ± 1** записей `tick=... SUCCESS` (24/3 = 8). Если работает 6 часов — **2 ± 1**.
- **SC-005**: При `enabled=false` за 24 часа непрерывной работы — **0** записей `tick=... SUCCESS`, при ручном клике запись `[AutoOneClickSyncScheduler]` не появляется (только обычные логи sync-движка).
- **SC-006**: В UI `/sync` обновлённый `lastRunAt` отображается при следующем монтировании компонента `SyncTable.vue` или при F5. **Требование «в течение 1 секунды» (live-push) НЕ предъявляется** — админ увидит обновление при первом заходе на страницу. Если в будущем потребуется live-обновление — это отдельная фича (SSE-push).
- **SC-007**: Упавшая `SyncTarget` (например, `tbl_x` бросает исключение) НЕ ломает остальные сущности в тике — измеримо по тому, что в логах для **других** сущностей того же тика записаны их нормальные `created/updated/deleted`.
- **SC-008**: Нагрузка от автозапуска **не превышает** нагрузку от ручного клика более чем на 5% (по числу JDBC-операций и суммарному времени) — автозапуск идёт ровно по той же логике `SyncRegistry.all`, что и ручной клик.
- **SC-009**: При полностью недоступной БД (LOCAL и SERVER падают одновременно) scheduler **не падает** и **не отключается**: тело тика обёрнуто в `try/catch (Throwable)` (FR-016), тик помечается `FAILED`, в лог пишется полный стек, следующий тик через 3 часа **отрабатывает штатно** (если БД уже поднялась). Проверяется по логам: между двумя тиками с интервалом `~3 ч` один может быть `FAILED`, второй `SUCCESS`.

## Assumptions

- **A-001**: `karaoke-app` работает на admin-машине как desktop-приложение, не как always-on сервис. Это означает, что 3-часовой интервал — это «пока машина жива». Если машина выключена — тик просто пропускается, без попыток catch-up (как у `SponsrSyncScheduler`, `MonitoringService`).
- **A-002**: Поведение «как у ручного клика»: тот же набор `SyncRegistry.all`, те же `oneClickDirection`, те же флаги `push_*_allowed` / `pull_*_allowed` per-target. Автозапуск — это просто обёртка над `postSyncOneClick()`.
- **A-003**: Интервал «каждые 3 часа» интерпретируется как `fixedDelay = 3h` (от завершения). Альтернатива «ровно в 00:00 / 03:00 / 06:00 / ...» (`cron`) — НЕ требуется по тексту запроса и добавляет сложности с timezone/DST.
- **A-004**: «Админка» в запросе = webvue3 на admin-машине. Уже есть `@EnableScheduling` в `KaraokeAppApplication.kt:18` и примеры scheduler'ов (`SponsrSyncScheduler.kt`, `VkAutoPublishScheduler.kt`) — фича просто добавляет ещё один `@Component` с `@Scheduled`.
- **A-005**: Способ отключения фичи — property в `KaraokeProperties` (база — base64-файл, паттерн: `editorAssignmentDefaultTarget`, `sponsrSubscribersUrl`). Дефолт `enabled=true` (соответствует тексту «должна запускаться»).
- **A-006**: При параллельной попытке ручного клика во время автозапуска выбираем **вариант A** (`409 Conflict` + `sync_in_progress`) как более безопасный — sync LOCAL↔SERVER не идемпотентен по «середине» (запись могла приехать с одной стороны и не уехать с другой). Альтернатива (параллельные sync) оставлена как Open Question.
- **A-007**: Хранение истории — in-memory `ConcurrentLinkedDeque` длиной 10. Персистентность в БД не требуется: admin-машина — desktop, история «до перезапуска» не нужна.
- **A-008**: Метрики/prometheus — out of scope. Достаточно логов и UI-блока.
- **A-009**: Способ отображения статуса в UI — добавить блок «Автозапуск» в существующую страницу `/sync` (рядом с таблицей `SyncTable.vue`); данные берутся из нового REST-эндпоинта `GET /api/sync/auto-status` через Vuex action `loadSyncAutoStatusPromise`, вызываемый в `mounted()` хуке. **SSE-push НЕ используется** (см. `SC-006`).

## Open Questions

- **OQ-1** *(resolved)*: При попытке ручного клика во время автозапуска эндпоинт возвращает HTTP `409 Conflict` с телом `{"error":"sync_in_progress", …}`. UI показывает понятный alert. Автозапуск не прерывается. Вариант зафиксирован в `FR-015` и `US1 AC2`.
- **OQ-2**: Нужен ли «ручной запуск с подтверждением» в дополнение к автозапуску (то есть вручную с тем же эффектом, как сейчас) — или достаточно, что кнопка остаётся без изменений? **Default**: кнопка остаётся без изменений.
- **OQ-3**: Нужно ли уведомление (toast/banner) в UI **при** автозапуске, или автозапуск должен быть полностью «невидимым»? **Default**: невидимый (только статус в блоке), чтобы не отвлекать админа.
- **OQ-4**: Что делать, если `SyncRegistry.all` содержит сущности с `oneClickDirection = null`? Сейчас `target.oneClickDirection` бросает NPE — нужен фильтр. **Default**: такие сущности skip + warn в лог.
- **OQ-5**: Должна ли фича отключаться в каком-то особом режиме (`dev` / `staging`)? **Default**: управляется общей настройкой `enabled`; отдельный env-флаг не нужен.
