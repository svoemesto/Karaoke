# Data Model: VK preview warmup

## 1. Общая модель

Фича не вводит новую персистентную сущность и не меняет схему PostgreSQL. В ней участвуют существующая песня, существующее состояние VK-публикации и временный результат HTTP-проверки.

## 2. Сущности

### Song / VK publication

Источник истины для публикации песни — существующая запись `Song`.

| Поле/свойство | Назначение | Изменение |
|---|---|---|
| `id` | Идентификатор песни, вход в URL изображения | Не меняется |
| `idVk` | Идемпотентность AIR и PREMIUM-публикаций | Записывается только после успешного поста согласно текущему типу публикации |
| `newsPremiumVkSent` | Идемпотентность PREMIUM, когда `idVk` оставляется для будущего AIR | Текущее поведение сохраняется |
| `player_readiness_flags.vkAutoPublishState` | Состояние операции | Используются существующие значения |
| `player_readiness_flags.vkAutoPublishLastAttemptAt` | Время последней попытки | Записывается существующим flow |
| `player_readiness_flags.vkAutoPublishLastError` | Диагностика ошибки | Для prewarm используется префикс `preview prewarm failed:` |

Новые колонки, миграции и новые sync targets не требуются.

### Preview asset

Логическое представление готового превью песни на публичном вебе. Оно не является строкой в БД.

| Атрибут | Правило |
|---|---|
| `songId` | Положительный id песни |
| `publicUrl` | `vkPreviewWarmupUrl` + `songId`; это тот же адрес, который указывает HTML для VK |
| `mediaType` | Должен быть `image/png` или совместимый вариант PNG-типа |
| `content` | Ненулевые байты, успешно декодируемые как PNG |
| `cacheLocation` | Текущий кэш веба `/tmp/vk_<songId>.png`; приложение не читает его напрямую |
| `ready` | Истина только после HTTP 200 и полной проверки тела ответа |

Ответ HTTP считается подтверждением готовности: веб записывает файл до отправки успешного ответа. Запись файла на вебе выполняется атомарно, чтобы параллельный читатель не увидел частичный результат.

### Preview warmup attempt

Временный результат одного вызова из `karaoke-app` в `karaoke-web`; отдельно в БД не сохраняется.

| Поле | Значения/правило |
|---|---|
| `status` | `SUCCESS` или `FAILED` |
| `songId` | Песня, для которой выполнялся прогрев |
| `attempts` | Фактическое количество HTTP-попыток, не больше настройки |
| `httpStatus` | Полученный HTTP-код, если ответ дошёл |
| `contentType` | Полученный MIME-тип, если ответ дошёл |
| `bytes` | Размер ответа; ноль означает ошибку |
| `durationMs` | Время прогрева для диагностики гипотезы |
| `error` | Краткая причина, без токенов и секретов |

`SUCCESS` допускается передавать в следующий этап только при валидном PNG. `FAILED` переводит существующую публикацию в `SEND_FAILED` и не допускает вызов `wall.post`.

### VkAutoPublishResult

Существующий синхронный результат остаётся совместимым:

- `state=PUBLISHED` и `postId` появляются только после успешного поста;
- при ошибке прогрева `state=SEND_FAILED`, `postId=null`, `error` начинается с `preview prewarm failed:`;
- отдельное поле для результата прогрева не добавляется в первой версии: фаза определяется по стабильному префиксу ошибки и логам, а длительность логируется отдельно.

## 3. Состояния и переходы

```text
SCHEDULED/READY
  ├─ idVk заполнен → PUBLISHED (skip, prewarm не вызывается)
  ├─ нужен demo-MP4 → RENDERING → callback
  └─ финальный этап публикации
       ├─ prewarm SUCCESS → PUBLISHING → PUBLISHED
       └─ prewarm FAILED → SEND_FAILED

RENDERING
  ├─ render ERROR → SEND_FAILED
  └─ render DONE → проверка идемпотентности → prewarm → PUBLISHING → PUBLISHED

SEND_FAILED
  └─ следующий ручной/плановый запуск → повторная проверка/prewarm
```

Состояние `PUBLISHING` устанавливается перед финальной операцией публикации; ошибка прогрева немедленно заменяет его на `SEND_FAILED`. Нового состояния `PREWARMING` в первой версии нет, чтобы не расширять существующие UI и state-потребители.

## 4. Связи и ограничения

- Одна песня может иметь не более одного общего AIR-поста по существующей идемпотентности `idVk`; PREMIUM использует существующий флаг `newsPremiumVkSent`.
- Несколько одновременных попыток одной песни сериализуются process-local блокировкой в `karaoke-app`; состояние и файл не должны повреждаться.
- Кэш превью эфемерен и может исчезнуть при перезапуске `karaoke-web`; следующий prewarm заново создаёт его.
- Публикация новости без связанной песни не имеет `songId` для построения URL и остаётся существующим legacy-исключением; при наличии распознаваемого id песни может использовать общий помощник.
