# Contract: Санитайзинг при импорте + переименование файла песни

**Feature**: [../spec.md](../spec.md) | **Date**: 2026-08-03

Проект — не публичная библиотека/REST API для внешних потребителей; «контракт»
здесь — поведенческая спецификация двух существующих внутренних точек входа
(`karaoke-app`, admin-only), которые эта фича меняет.

## 1. `Song.createFromPath(startFolder, database, storageService, storageApiClient): FolderImportResult`

**Не меняется сигнатура.** Меняется внутреннее поведение.

**Pre-conditions**: `startFolder` содержит `.flac`/`.mp3`/`.m4a` файлы в
альбомных подпапках, распознаваемых `regexAlbum`/`regexFile`.

**Post-conditions (новые/уточнённые по сравнению с текущим поведением)**:
- Для каждого импортированного файла: `song.fileName` = результат
  `fileName.rightFileName()` (санитайзированный), не «сырое» `file.nameWithoutExtension`.
- Реальный файл на диске после (при необходимости) перекодирования в FLAC
  назван по санитайзированному имени — **без** расхождения между
  `song.fileName` и физическим именем файла.
- `song.fields[SongField.NAME]` — оригинальный (не санитайзированный) фрагмент
  названия из regex-группы, символы вроде `!` сохраняются.
- Если в рамках одного вызова два файла из одной `rootFolder` после
  санитайзинга дали бы одинаковый `fileName` — второй (и последующие)
  получают уникальный `fileName` с числовым суффиксом `" (N)"` перед
  сохранением/переименованием; импорт не прерывается, ручного вмешательства
  не требуется.
- Поведение при отсутствии коллизий и «чистых» именах файлов — не меняется
  (обратная совместимость с уже существующими сценариями импорта).

**Error handling**: не меняется — как и раньше, файл, для которого не найден
`matchResultAlbum`/`matchResultFile`, тихо пропускается (существующее
поведение, вне скоупа этой фичи).

## 2. `POST /song/update` (`ApiController.songs2Update`) — параметр `fileName`

**Не меняется сигнатура эндпоинта** (список `@RequestParam` тот же). Меняется
поведение при непустом `fileName`, отличном от текущего `song.fileName`.

**Request** (релевантные параметры): `id` (обязателен), `fileName` (опционален —
если `null`, поведение не меняется вообще), `rootFolder`.

**Pre-conditions / Validation** (в порядке проверки, любая неудача → **rename
NOT applied**, остальные поля из запроса — существующее поведение не трогается):

1. `fileName.rightFileName()` не пустая строка после санитайзинга → иначе reject.
2. Нет другой песни с тем же `(rootFolder, rightFileName(fileName))` (кроме
   самой себя) → иначе reject (FR-011).
3. Нет `KaraokeProcess` для `song.id` со статусом `WAITING`/`WORKING` → иначе
   reject (FR-013).

**Response (текущий контракт)**: эндпоинт сегодня возвращает `Boolean`
(`albumLinkValid` — семантика "альбом валиден"). Эта фича добавляет ещё один
источник `false`/отказа: любая из трёх причин reject выше **тоже** должна
привести к `false` и (новое) — понятному сообщению об ошибке, различимому от
`albumLinkValid=false`. Поскольку сигнатура `Boolean` слишком узкая для
нескольких разных причин отказа, при реализации необходимо решить: либо (a)
расширить возвращаемый тип до объекта с полем `error: String?` (breaking change
для существующих вызывающих во `webvue3/src/components/Songs/store.js`,
`updateSong`/аналогичный dispatch), либо (b) добавить отдельный `GET`/`POST`
эндпоинт предварительной валидации, вызываемый из `SongEdit.vue` перед
сохранением. **Решение фиксируется на этапе `/speckit-tasks`/implement** — вне
формального объёма этого документа, т.к. требует expлицитного просмотра всех
вызывающих `songs2Update` на фронтенде (задача для implementation, не для
plan).

**Post-conditions (успех)**: все существующие на момент вызова производные
артефакты (аудиофайл, стемы, `.kdenlive`, субтитры, sidecar-метаданные,
объекты в локальном+удалённом хранилище) переименованы под новый
`fileName`; `song.fileName` обновлён и сохранён (`saveToDb()`+`saveToFile()`,
как и сегодня).

**Post-conditions (частичный отказ на шаге cascade rename)**: уже
переименованные артефакты остаются под новым именем (не откатываются);
песня не помечается как «переименована успешно» — при следующем вычислении
`HealthReport` для этой песни несоответствие «ожидаемый файл под новым
именем отсутствует» проявляется как `ERROR`/`FATAL_ERROR`, видимый в
`HealthReportTable.vue` (см. `data-model.md`).

## Инварианты, которые НЕ должны быть нарушены реализацией

- `rightFileName()` остаётся единственной функцией, определяющей «безопасное»
  имя файла — используется идентично в обоих контрактах выше.
- Коллизия проверяется только в пределах `rootFolder`, не глобально.
- Никакой код-путь не выполняет rollback уже переименованных артефактов.
