# Feature Specification: Закрома автора — отрисовка списка песен без N×3 фоновых запросов

**Feature Branch**: `239-zakroma-author-songs-batch-render`

**Created**: 2026-08-25

**Status**: Draft

**Input**: User description: «Найден точный алгоритм, приводящий к зависанию сайта, которое мы так и не смогли победить в более ранних спеках. У автора "Машина Времени" - почти 2500 песен. Если в закромах зайти на карточку автора "Машина Времени" пользователем-редактором (для которого загружаются все песни, а не только готовые) обилие запросов (как я понимаю минимум по 3 запроса на песню: доступность плеера, наличие песни в избранном, наличие песни в плейлистах, итого минимум 7500 запросов) как раз и приводят к зависанию. Визуально на странице это видно по тому, что при пролистывании списка песен вниз с какого то момента у песен вечно крутятся спиннеры плеера, избранного и плейлистов. Если в этот момент перейти на главную страницу - то в статистике отобразятся нули. При обновлении страницы - сайт недоступен. Проведи анализ и подтверди мою догадку. Необходимо реализовать такой механизм отображения списка песен автора в закромах, который бы не "вешал" весь сайт. Мысли на эту тему: а зачем нам вообще эти запросы на каждую песню? Готовность плеера приходит с каждой песней во флагах. Надо только, в зависимости от пользователя (аноним / зарегистрированный / премиальный) и "эфирности" песни показывать "зеленый" значок полноценного плеера или "золотой" демо (или серый задизейбленный для редакторов если песня ещё не готова). Избранное и плейлисты можно получать с бэка по необходимости и хранить их в локальном сторе, а при подгрузке списка песен проверять их вхождение в избранное и плейлисты для отрисовки правильной иконки избранного и плейлистов. Таким образом мы полностью избавляемся от множественных запросов.»

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Редактор открывает автора с 2500 песен (Priority: P1)

Редактор заходит в «Закрома», кликает по плашке автора «Машина Времени» (≈2500 песен). Список песен автора отрисовывается полностью, **без спиннеров «вечно загружается»** у иконок плеера/избранного/плейлистов. Иконки сразу показывают правильный цвет: серый задизейбленный плеер для неготовых песен (`id_status < 6`), зелёный/золотой — для готовых (по обычной логике «эфир/премиум/демо»). Клики по иконкам избранного/плейлистов мгновенно обновляют локальное состояние (без re-fetch всей карты).

**Why this priority**: Это исходный репорт бага. Без исправления публичный сайт «лежит» (см. SC-001), админка непригодна для редакторов на крупных авторах. Другие сценарии (аноним/премиум на крупных авторах) — те же симптомы, поэтому фикс покрывает всех.

**Independent Test**: Открыть `/zakroma`, кликнуть «Машина Времени», пролистать до конца списка (~2500 строк). На DevTools Network — **ровно 2-3 запроса к серверу** на загрузку страницы (стрим песен + один bulk-fetch избранного/плейлистов, если юзер залогинен), **никаких per-row фоновых запросов** после отдачи стрима. На каждой строке иконки плеера/избранного/плейлистов сразу показывают финальный цвет, спиннеров нет.

**Acceptance Scenarios**:

1. **Given** редактор зашёл на страницу `/zakroma?author=Машина Времени` (без залогина, токена нет), **When** стрим отдал все песни, **Then** у всех 2500 строк иконки плеера сразу показывают финальное состояние: зелёный/золотой для песен с `id_status >= 6` (по контексту анона — без входа это «всегда демо» → золотой), серый disabled для песен с `id_status < 6`. Никаких спиннеров, никаких per-row `/access` или `/readiness` запросов.
2. **Given** зарегистрированный пользователь (без премиума) открыл «Машина Времени», **When** стрим отдал все песни, **Then** иконки избранного (★) и плейлистов (▶|) сразу показывают правильный цвет (на основе membership-карты, загруженной **одним** запросом), спиннеров нет.
3. **Given** список песен уже отрисован, **When** пользователь кликает по иконке «В избранное» на любой песне, **Then** иконка мгновенно меняет цвет, membership-карта обновляется локально, broadcast по `BroadcastChannel('km-favorites')` рассылает изменение в другие вкладки. Дополнительный запрос к серверу — один (`POST /api/public/account/favorites/toggle`), без re-fetch всей карты membership.
4. **Given** пользователь кликает по зелёной/золотой иконке плеера на готовой песне, **When** открывается плеер, **Then** поведение не отличается от текущего (iframe `/player/{id}` с токеном).
5. **Given** страница полностью отрисована, **When** посетитель уходит на главную, **Then** главная страница загружается мгновенно (статистика читается из локального `tbl_events` без блокировок).

### User Story 2 — Премиум-пользователь на крупном авторе (Priority: P2)

Премиум-пользователь открывает «Машина Времени». Все песни, к которым у него есть полный доступ (премиум/в эфире/бесплатные/подписка на плейлист автора), показывают **зелёную** иконку плеера, остальные готовые — **золотую** (демо-фрагмент). Логика определения «watchable» — чисто клиентская (на основе флагов из песен + кэша прав пользователя), без per-row запроса `/access`.

**Why this priority**: Премиум-юзер — основная монетизационная аудитория, для него лаг на крупных авторах ощутим сильнее всего. Этот сценарий зависит от US1 (та же базовая архитектура), но добавляет проверку «зелёный vs золотой».

**Independent Test**: Залогиниться как премиум, открыть `/zakroma?author=Машина Времени`, найти премиум-песню (например, недавнюю PREMIUM-публикацию) и обычную «в эфире» песню — у обеих зелёная иконка; найти обычную готовую песню, не в эфире — золотая. Перезагрузить страницу — те же цвета, без мигания через серый/спиннер.

**Acceptance Scenarios**:

1. **Given** премиум-пользователь открыл крупного автора, **When** стрим отдал песни, **Then** песни в статусе «в эфире» (`is_in_air = true`) или `flag_free = true` или с активной премиум-подпиской пользователя — сразу **зелёная** иконка плеера (без ожидания per-row проверки).
2. **Given** премиум-пользователь, **When** у песни `is_in_air = false`, `flag_free = false`, нет персональной подписки, **Then** иконка плеера **золотая** (демо-фрагмент), но кликабельная — `PlayerIcon.onOpen` открывает плеер, плеер сам ограничивает контент по водяному знаку.
3. **Given** премиум-пользователь, **When** песня с `id_status < 6`, **Then** иконка плеера **серая disabled** (как и для редактора/анона), клик не открывает плеер.

### User Story 3 — Аноним на крупном авторе (Priority: P2)

Анонимный посетитель (без токена) открывает «Машина Времени». Готовые песни показывают золотую иконку плеера (демо — всегда доступно), неготовые — серую disabled. Иконки избранного/плейлистов для анонима скрыты (нет персиональных membership-ов) или показаны как «гостевые» — без per-row запросов.

**Why this priority**: Аноним — самый массовый сегмент трафика (боты/SEO/первый визит). Тот же fix, что и для US1, но отдельно проверим: для анонима membership-fetch вообще не делается.

**Independent Test**: Открыть `/zakroma?author=Машина Времени` в инкогнито. На DevTools Network — только стрим песен. Никаких запросов `/playlists/membership`, `/playlists`, `/favorites/...`. Золотые иконки плеера у всех готовых песен, серые у неготовых.

**Acceptance Scenarios**:

1. **Given** анонимный посетитель, **When** стрим отдал песни, **Then** на DevTools Network **нет** запросов `/api/public/account/playlists*` или `/api/public/account/favorites*` — membership-fetch пропущен, т.к. токена нет.
2. **Given** аноним, **When** у песни `id_status >= 6`, **Then** иконка плеера — **золотая** (демо-фрагмент всегда доступен).
3. **Given** аноним, **When** у песни `id_status < 6`, **Then** иконка плеера — **серая disabled**.
4. **Given** аноним, **When** посетитель кликает по иконке избранного/плейлиста, **Then** редирект на `/login?redirect=...` (как сейчас).

### Edge Cases

- **Стрим оборвался на полпути** (бэк упал / nginx таймаут): фикс не меняет поведение — спека 181 уже покрывает Retry/AbortController. После восстановления стрима иконки сразу правильные (нет per-row запросов, которые могли бы тоже зависнуть).
- **Membership-fetch упал** (5xx/сеть): иконки избранного/плейлистов остаются в нейтральном состоянии («off», серый outline) и не блокируют отрисовку. Retry НЕ выполняется (см. Clarification Q3, 2026-08-25) — состояние фиксируется до logout/login/reload, при смене токена store сбрасывается и грузится заново (FR-011). При клике по «off»-иконке — обычный `toggleFavorite`/`addSongToPlaylist` обработает ошибку штатно.
- **Membership-fetch медленный** (> 2 сек): пользователь видит песни с иконками в loading-состоянии ≤ 2 сек, потом переход в финальное. Спиннер показывается **один раз** на приложение (пока membership не загрузился), а не 2500 раз.
- **Совпадение membership с загруженным стримом в момент перехода автора** (юзер переключился с X на Y, membership X ещё в процессе): фильтруем устаревшие membership-ответы по `latest`-requestId (паттерн уже есть в `usePlaylistMembership.js`). Никаких утечек из X в Y.
- **BroadcastChannel не поддерживается** (старый браузер): `favoritesChannel = null` → `setFavorited` сработает только в текущей вкладке. Поведение тихо деградирует, без падений.
- **Очень много песен + низкая скорость сети** (2500 песен, EDGE): стрим уже отдаёт первые чанки через 200 мс TTFB (см. спеку 181), первые 20-40 песен сразу отрисовываются с правильными иконками. Остальной список подгружается постепенно, без блокировки UI.
- **Войти/выйти во время просмотра списка песен** (смена токена): membership-store реактивно перезагружается при смене токена (или сбрасывается на пустой при logout), иконки перерисовываются без перезагрузки списка.
- **Стрим вернул 0 песен** (новый автор): UI показывает «У этого автора пока нет доступных песен» (или эквивалент из спеки 181). Никаких membership/per-row запросов.

## Requirements *(mandatory)*

### Functional Requirements

#### A. Источник истины для готовности плеера

- **FR-001**: Иконка плеера (`PlayerIcon`) MUST получать своё состояние (`watchState` + `contentReadyState`) **только** из флагов самой песни (поля `id_status`, `is_in_air`, `flag_free`, персистентные `player_ready_*` флаги из БД), без отдельного запроса `/api/public/player/readiness` или `/api/public/player/{id}/access` на каждую песню.
- **FR-002**: Иконка плеера MUST показывать:
  - **зелёный** (`active`) — если `contentReadyState === 'ready'` AND (`is_in_air === true` OR `flag_free === true` OR пользователь премиум OR `songId ∈ userSongSubscriptions`);
  - **золотой** (демо) — если `contentReadyState === 'ready'` AND ни одно из условий зелёного не выполнено (включая анонимов);
  - **серый disabled** — если `contentReadyState === 'notready'` (то есть `id_status < 6` или отсутствуют персистентные `player_ready_*` флаги).
- **FR-003**: Зелёная и золотая иконки MUST быть кликабельны (открывают `/player/{id}` через `playerLauncher.openPlayer`); серая MUST не иметь обработчика клика и иметь `title="Плеер недоступен"`.
- **FR-004**: `usePlayerReadiness` composable MUST оставаться **только для неподдерживаемых сценариев** (например, страница песни, где серверная `/access` нужна ради токена `kp_token_*`) — на странице списка песен MUST НЕ вызываться ни для одного id.
- **FR-005**: `PublicPlayerController.stemsReady` эндпоинт (`/api/public/player/readiness`) MUST остаться доступным для страниц одиночной песни (SongView, если она его использует), но не вызываться со страниц списка (`ZakromaView`, `SearchView`, `AuthorPlaylistView`).

#### B. Источник истины для membership (избранное/плейлисты)

- **FR-006**: Избранное пользователя MUST быть загружено **одним** запросом `GET /api/public/account/favorites/ids` (новый endpoint, если отсутствует) или расширенным `GET /api/public/account/playlists/membership?scope=all` (если существующий endpoint можно расширить), возвращающим **плоский Set/List id песен**, в избранном у пользователя. Результат сохраняется в module-level `favoriteIds: Set<number>` в `usePlaylistMembership.js` (или новом composable).
- **FR-007**: Членство песен в плейлистах пользователя MUST быть загружено **одним** запросом `GET /api/public/account/playlists/membership?ids=...&scope=current` (новый или расширенный endpoint), возвращающим `Map<songId, playlistId[]>`. Результат сохраняется в module-level `playlistMembership: Map<number, number[]>`.
- **FR-007a**: Персональные подписки пользователя на песни MUST быть загружены **одним** запросом `GET /api/public/account/song-subscriptions/ids` (новый endpoint), возвращающим **плоский Set/List id песен** с активной подпиской у пользователя. Результат сохраняется в module-level `userSongSubscriptions: Set<number>` в `usePlayerAccess.js` (или новом composable `useSongSubscriptions`). Используется как условие «зелёного» плеера наряду с `is_in_air`/`flag_free`/premium.
- **FR-008**: `usePlaylistMembership` MUST подгружать membership **один раз** при входе в приложение (или при смене автора на крупного — `> 100 песен`), а не на каждое монтирование `ZakromaView`/`SearchView`. Membership-store — module-level singleton, переживает browser back и переходы между view. Аналогично `useSongSubscriptions` подгружает подписки **один раз** на сессию.
- **FR-009**: Запрос membership MUST быть **skip'нут** для анонимов (токена нет) — иконки избранного/плейлистов для анонима отображаются как «гостевые» (без логина → disabled или скрыты; см. UI-уточнение в разделе Assumptions).
- **FR-010**: При `toggleFavorite` / `addSongToPlaylist` / `removeSongFromPlaylist` локальная карта MUST обновляться **до** отправки запроса (optimistic update), откатываться при ошибке. BroadcastChannel `'km-favorites'` MUST рассылать изменение в другие same-origin вкладки/iframe (паттерн уже есть, расширяется на playlist-membership).
- **FR-011**: Membership-store MUST инвалидироваться при смене токена (logout/login): `watch(token, ...)` сбрасывает `favoriteIds`/`playlistMembership` в пустое состояние, при логине — фоновая подгрузка.

#### C. Серверные endpoint'ы

- **FR-012**: Backend MUST предоставлять endpoint `GET /api/public/account/favorites/ids` (или эквивалентный), возвращающий **полный список id песен** в избранном у пользователя (для премиум-юзеров — без лимита; для free — все их избранные). Параметр `premium_only` НЕ нужен — endpoint приватный, отдаёт только свои.
- **FR-013**: Backend MUST предоставлять endpoint `GET /api/public/account/playlists/membership?ids={csv}` (расширение существующего), который возвращает `Map<songId, playlistId[]>` для запрошенных id — принадлежность к НЕ-избранному плейлистам пользователя (т.к. избранное уже отделено в FR-012). Endpoint используется только если у пользователя > 0 не-избранных плейлистов; иначе фронт пропускает запрос.
- **FR-014**: Backend MUST поддерживать запрос membership **для произвольного набора id** (до ~2500 за раз) одним SQL-запросом через существующий паттерн `WHERE song_id IN (...)` в `tbl_site_playlist_songs` (или эквивалентной таблице связи). O(1) запросов к БД независимо от размера списка.
- **FR-015**: Эндпоинт `/api/public/player/readiness` MUST остаться в backward-compat режиме (страница одиночной песни не должна сломаться), но MUST быть **исключён** из всех страниц списка песен.

#### D. UI-компоненты (PlayerIcon / FavoriteIcon / PlaylistIcon)

- **FR-016**: `PlayerIcon` MUST принимать новые props: `contentReadyState` (`'ready' | 'notready'`) и `premium` (`bool`), `inAir` (`bool`), `flagFree` (`bool`), `personalAccess` (`bool`). Если все флаги приходят с сервера в стриме — props MUST быть необязательными (computed-фолбэк на store).
- **FR-017**: `PlayerIcon` MUST перестать принимать `watchState`/`contentReadyState` в формате `'loading'` — это состояние больше не нужно (нет асинхронной подгрузки). Если какой-то старый call-site шлёт `'loading'` — трактуется как `'notready'` (defensive default).
- **FR-018**: `FavoriteIcon` и `PlaylistIcon` MUST читать своё состояние **только** из module-level `usePlaylistMembership` store (не из per-row `fetchMembership`), без вызовов `load(ids)` на каждое монтирование.
- **FR-019**: `FavoriteIcon` для анонима MUST отображать «гостевую» иконку (серая звезда, `title="Войдите, чтобы добавить в избранное"`) и по клику делать `router.push('/login?redirect=...')` (как сейчас). Аналогично `PlaylistIcon`.
- **FR-020**: Компоненты MUST поддерживать optimistic update: `FavoriteIcon.onClick` обновляет локальный store ДО сетевого запроса; если сервер вернул `limitReached=true` — откатываем store и открываем premium-модалку.
- **FR-021**: При отсутствии membership в store (ещё не загружен) `FavoriteIcon`/`PlaylistIcon` MUST показывать **нейтральное** состояние (outline-иконка), НЕ спиннер. Спиннер на приложение — **один**, в углу статус-бара (или вообще скрыт, см. Assumptions).

#### E. Стрим песен (`/api/public/zakroma/stream`)

- **FR-022**: Сообщения NDJSON-стрима MUST включать в каждый объект песни дополнительные поля: `id_status`, `is_in_air`, `flag_free`, `player_ready_full` (или эквивалент — персистентные `player_ready_*` флаги из БД). Без отдельного readiness-endpoint'а иконки плеера должны иметь всю нужную информацию из самого сообщения.
- **FR-023**: Стрим MUST отдавать эти поля **для всех песен автора**, включая редакторские (status 0..6), поскольку редакторский view — основной сценарий фикса. Для публичного (onlyPublished=true) — те же поля, просто с `id_status >= 6` фильтром на бэке.

#### F. Производительность и наблюдаемость

- **FR-024**: Загрузка страницы `/zakroma?author=Машина Времени` (2500 песен) MUST порождать **≤ 4 HTTP-запроса** на фронте: (1) NDJSON стрим песен, (2) `GET /api/public/account/favorites/ids` (если залогинен), (3) `GET /api/public/account/playlists/membership?ids=...` (если залогинен и есть не-избранные плейлисты), (4) `GET /api/public/account/song-subscriptions/ids` (если залогинен). Никаких per-row `readiness`/`access`/`membership` запросов.
- **FR-025**: Время до отрисовки первой страницы песен (TTFP — Time To First Paint для трека) MUST быть **≤ 500 мс** на типичной сети (после `181-zakroma-author-load-progress` уже есть TTFB ≤ 200 мс + рендер первых 20-40 песен).
- **FR-026**: Backend MUST логировать метрику `readiness_calls_total` (counter) — счётчик вызовов `/api/public/player/readiness`. После выкатки фикса счётчик на проде для обычных users MUST стремиться к 0 (только страницы одиночной песни).
- **FR-027**: Backend MUST логировать `membership_calls_total` (counter) — счётчик вызовов `/api/public/account/playlists/membership`. После фикса MUST быть **1-2 вызова** на пользователя за сессию (а не по одному на каждый id).

### Key Entities

- **Song (в стриме)**: расширена полями `is_in_air`, `flag_free`, `player_ready_full`, `player_ready_demo` (или эквивалент по БД-схеме). Эти поля читаются из `tbl_songs` (Pass 100) и добавляются в NDJSON-сообщение.
- **FavoriteSet (новый)**: module-level `Set<number>` — id песен в избранном у текущего пользователя. Singleton, переживает browser back, реактивный (Vue ref/reactive).
- **PlaylistMembershipMap (новый)**: module-level `Map<number, number[]>` — для каждой песни id плейлистов пользователя, в которых она состоит (НЕ включая «Избранное»). Singleton.
- **SubscriptionSet (новый)**: module-level `Set<number>` — id песен, на которые у пользователя активная персональная подписка (см. Clarification Q1, 2026-08-25). Загружается одним bulk-fetch параллельно favorites/playlists. Используется как условие «зелёного» плеера в `PlayerIcon` (наряду с `is_in_air`/`flag_free`/premium). Singleton.
- **PlayerIconState (computed)**: композиция `contentReadyState × premium × inAir × flagFree × personalAccess` → `'active' | 'demo' | 'disabled'`. Вычисляется per-render, без сетевых вызовов.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Загрузка `/zakroma?author=Машина Времени` (≈2500 песен) **НЕ приводит к зависанию сайта**: главная страница во время/после загрузки доступна, обновление страницы не даёт «site down». Проверяется вручную: открыть две вкладки — `/zakroma?author=Машина Времени` (как редактор) + `/` (главная), убедиться, что главная отвечает за ≤ 1 сек пока загружается закрома.
- **SC-002**: Количество HTTP-запросов с фронта при `/zakroma?author=Машина Времени` **≤ 4** (стрим + до 3 membership/subscription запросов: favorites/ids, playlists/membership, song-subscriptions/ids) — проверяется DevTools Network. До фикса — сотни/тысячи.
- **SC-003**: Все 2500 строк списка песен в редакторском view отрисовываются **без вечных спиннеров** у иконок плеера/избранного/плейлистов — каждый значок сразу показывает финальное состояние (зелёный/золотой/серый для плеера, ★/☆ для избранного, ▶|/⊟ для плейлистов). Проверяется визуально + проверкой, что в Network нет late-arriving per-row запросов.
- **SC-004**: Время от клика по плашке автора до первой отрисовки полного списка **≤ 5 сек** для 2500 песен (стрим + рендер + применение membership-карты). До фикса — сценарий «висим минутами».
- **SC-005**: Backend-счётчик `readiness_calls_total` для обычных users **снижается на ≥ 95%** после выкатки фикса (исключение — страницы одиночной песни). Проверяется Prometheus-метрикой или grep по логам за день до/после выкатки.
- **SC-006**: Логика монетизации (зелёный для премиума/в эфире/подписки, золотой для остальных) **сохранена** — регрессий по доступу нет. Проверяется вручную на 3-х типах юзеров (аноним/зарегистрированный/премиум) на 3-х типах песен (не готова / готова + в эфире / готова + не в эфире + не премиум).
- **SC-007**: Тест производительности: 2500 песен в списке, прокрутка до конца — **60 FPS** без видимых лагов на средней машине (Chromium DevTools Performance). До фикса — observable jank при подгрузке membership-чанков.

## Clarifications

### Session 2026-08-25

- Q: Как определить «personalAccess» (персональная подписка) для зелёного/золотого плеера — без per-song API? → A: Отдельный bulk-fetch, параллельно избранному и плейлистам. Endpoint возвращает плоский список id песен, на которые у пользователя активная подписка; фронт кладёт его в module-level Set и проверяет вхождение per-render, без per-song запросов.
- Q: Иконки избранного/плейлистов для анонима — «гостевые» (серая + редирект) или скрыть? → A: «Гостевые» иконки (серая ★ / серая ▶\|) с `title="Войдите, чтобы добавить в избранное"`, по клику → `/login?redirect=...`. Видно фичу, конверсионно.
- Q: При падении membership-fetch (5xx/сеть) — retry или фиксировать «off»? → A: «Off» фиксируется до logout/login/reload, без retry/таймеров. При смене токена store сбрасывается и грузится заново (FR-011). Минимум движущихся частей.

## Assumptions

- **FR-006/FR-012 endpoint `/api/public/account/favorites/ids`** — если существующий API не предоставляет плоский список id песен в избранном, добавляется новый минимальный endpoint. Альтернатива — расширить существующий `/api/public/account/playlists/membership` параметром `scope=favorites-only` или `scope=all`. Конкретный endpoint выбирается на этапе планирования (зависит от того, есть ли уже похожий эндпоинт).
- **Подписки на песни (Clarification Q1)**: добавляется новый endpoint `GET /api/public/account/song-subscriptions/ids` (параллельно `/favorites/ids`), возвращающий `Set<number>` id песен с активной персональной подпиской у пользователя. Используется как ещё одно условие «зелёного» плеера наряду с `is_in_air`/`flag_free`/premium.
- **FR-013 endpoint membership для не-избранных плейлистов** — у большинства пользователей 0-2 обычных плейлиста. Endpoint MUST быть skip'нут, если пользователь залогинился, но у него нет не-избранных плейлистов (фронт проверяет наличие плейлистов после первого fetch).
- **«Гостевая» иконка для анонима** — UI-вариант (серая звезда + редирект на login vs. полное скрытие иконок) — на усмотрение дизайна; функционально требование одно: 0 запросов membership для анонимов.
- **`flag_free`, `is_in_air` уже есть в `tbl_songs`** (используются в спеках 005, 122, 143, 169 и др.) — должны быть включены в NDJSON-сообщение спеки 181. Если каких-то полей нет в текущей схеме — расширение на backend минимальное (одна миграция + projection).
- **Персистентные `player_ready_*` флаги** (см. спеку 100) уже хранятся в `tbl_songs` и используются `Song.markNewsAvailableIfReady`. Достаточно прочитать их в `Song.getZakroma` projection и добавить в JSON-ответ — отдельная логика не нужна.
- **`watchState` prop в `PlayerIcon`** остаётся в API компонента для backward-compat (если какие-то места ещё не перешли), но MUST NOT использоваться в Zakroma/Search/AuthorPlaylist view. Старые call-site'ы переводятся на новые props в этом PR.
- **Текущие call-site'ы `usePlayerReadiness` и `usePlaylistMembership.load()`**:
