# Research: Спецтеги в тексте песни для авто-разметки маркеров

Спецификация не содержит нерешённых `[NEEDS CLARIFICATION]` — все ключевые развилки (синтаксис, область применения, набор тегов v1) были согласованы с пользователем до написания `spec.md` (см. `plan.md`/Technical Context). Ниже — технические решения, принятые на основе разведки существующего кода (`WhisperMarkerAligner.kt`, `SubsEdit.vue`), оформленные в стандартном формате Decision/Rationale/Alternatives.

## 1. Синтаксис тега и разделитель значения

- **Decision**: `~имя~` (без значения) или `~имя:значение~` (значение — свободный текст до закрывающей `~`), регекс вида `~([a-z]+)(?::([^~]*))?~`.
- **Rationale**: Тильда предложена пользователем изначально и не используется в проекте ни для маркеров, ни для legacy inline-тегов (`[G0]`, `[C]`, `[E]`, `[RS]/[RE]/[RR]`, `[TS]/[TE]/[TR]` в `model/Song.kt`) — коллизий нет. Двоеточие как разделитель значения выбрано, чтобы не путать со уже занятым `|` (используется и в `Constants.kt` DELIMITER_* для сериализации многоголосых полей, и в конвенции `SETTING`-маркера `"TYPE|VALUE"`, см. `Functions.kt:53-93`) — если бы тег использовал тот же `|`, визуально сливался бы с этой конвенцией при чтении сырого текста.
- **Alternatives considered**: (a) переиспользовать формат `TYPE|VALUE` внутри тильд (`~newline~`, `~GROUP|1~`) — отклонено, чтобы не заставлять автора текста печатать заглавные буквы/пайп внутри и без того непривычного синтаксиса; (b) квадратные скобки как в legacy `Song.kt` (`[group:1]`) — отклонено во избежание коллизии с уже существующим (хоть и другим кодовым путём) `[G0]`-конвеншеном, который живёт в другом, независимом импорте subtitle/`.srt`.

## 2. Область применения тега в тексте

- **Decision**: Тег распознаётся только тогда, когда он — единственное содержимое отдельной строки (после `trim()` строка равна самому тегу). Инлайн-теги в середине/конце обычной строки лирики — не поддерживаются в этой версии.
- **Rationale**: Существующий механизм уже работает на уровне строк: `buildTargetWords` (`WhisperMarkerAligner.kt:352-404`) проверяет `line.isBlank()` целой строкой (строка 355), а `buildMarkersFromSyllableTimes` (строки 93-148) вычисляет разрыв между строками через `lineIndex`-гэп. Ограничение "тег = вся строка" позволяет буквально подставить проверку "стала ли строка пустой после снятия тега" в то же самое место кода — без переписывания логики сопоставления слов ASR/Whisper и без риска, что тег будет случайно принят за часть спетого слова. Пользователь подтвердил этот вариант явно (AskUserQuestion).
- **Alternatives considered**: Разрешить тег в начале/конце строки лирики (привязка к границе слова) — даёт больше гибкости (например, комментарий сразу к конкретной строке без отдельной строки под него), но требует отдельного анкоринга "после последнего слова строки N" в дополнение к анкорингу "между строками N и N+1", и отдельной обработки на фронтенде без явного прецедента в текущем коде. Отклонено как избыточное для заявленных сценариев (newline/group/comment все естественно ложатся на границу между блоками текста).

## 3. Набор тегов v1 и реестр

- **Decision**: `newline` → `Markertype.NEWLINE`; `group:N` → `Markertype.SETTING`, `label="GROUP|N"`; `comment:текст` → `Markertype.SETTING`, `label="COMMENT|текст"`. Реестр — простая мапа `имя тега → (валидатор значения, функция построения Markertype+label)`, легко расширяемая новой записью.
- **Rationale**: `group`/`comment` напрямую отражают уже существующую ручную конвенцию `SETTING|GROUP|N` и `SETTING|COMMENT|текст`, которую сегодня расставляют вручную через клавиши в `SubsEdit.vue` (см. `Functions.kt:53-93`, `SubsEdit.vue` `addMarker('setting', 'GROUP|N')`) — тег просто даёт текстовый способ получить тот же результат. `newline` — явный синоним уже работающего сегодня "пустая строка → NEWLINE".
- **Alternatives considered**: Сразу добавить теги для `unmute`/`chord`/`note`/`beat` — отклонено пользователем (выбран вариант "только newline+group+comment для v1"), реестр спроектирован так, чтобы такие типы можно было добавить одной записью без переработки парсера/анкоринга.

## 4. Точка врезки в существующий алгоритм (backend)

- **Decision**: Расширить `buildTargetWords` так, чтобы для каждой строки сначала запускался `SpecTags.parseLine(line)`, а решение "пропустить как пустую" принималось по строке-после-снятия-тегов; найденные теги накапливаются в `Map<Int /* lineIndex */, List<SpecTag>>`, возвращаемой вместе с `List<TargetWord>`. `buildMarkersFromSyllableTimes` при обнаружении гэпа `nextWord.lineIndex - word.lineIndex > 1` (строка 132) вместо жёсткой вставки одного `NEWLINE` перебирает все пропущенные `lineIndex` в этом диапазоне и для каждого — либо вставляет маркер(ы) по найденным на этой строке тегам, либо (если тегов на этой строке нет) вставляет `NEWLINE`, как сегодня.
- **Rationale**: Минимальная по площади врезка — использует уже существующие структуры (`TargetWord.lineIndex`, `newLineMarkerTime`-интерполяцию времени) без переписывания алгоритма сопоставления слов. Гарантирует byte-for-byte совпадение при отсутствии тегов, потому что в отсутствие тегов каждая "пропущенная" строка не даёт своего тега — код проходит по старой ветке.
- **Alternatives considered**: Отдельный полностью независимый пре-процессинг текста (снять все теги, построить список "инструкций" заранее, потом сшивать с результатом обычного алгоритма постфактум) — отклонено как более громоздкое и с более высоким риском разойтись по подсчёту слогов, чем точечная правка в уже единственном месте, которое считает `lineIndex`.

## 5. Точка врезки в редакторе (frontend) — ручная синхронизация

- **Decision**: Новая функция `syncMarkersFromSpecTags()` в `SubsEdit.vue`, вызываемая там же, где сегодня `updateMarkersBySyllables()` (~3136-3194, на изменение `sourceText`/`sourceMarkers`). Тег анкорится по тому же принципу ординальной позиции, что уже использует `updateMarkersBySyllables` для сопоставления `syllables`-маркеров с `sourceSyllables` по индексу — то есть "тег стоит после слога с индексом K" → якорь на границе между `syllables`-маркером K и K+1. Функция только добавляет отсутствующий маркер (проверка "маркер такого типа+label уже стоит на этой границе" перед вставкой), никогда не удаляет.
- **Rationale**: Единственный существующий способ сегодня связывать позицию в тексте с позицией в списке маркеров — именно ординальный (не посимвольный) индекс, это уже установленный в проекте паттерн (`SourceMarker.position` — это визуальное top/bottom, а не текстовый offset). Повторное использование этого паттерна не требует вводить новый вид привязки текст↔маркер.
- **Alternatives considered**: Ждать полного переприменения "Точные маркеры" на каждое изменение текста с тегами — отклонено, так как явно противоречит User Story 3 из спеки (автодобавление маркера при ручном редактировании без повторного форс-алаймента).

## 6. Обработка неизвестных/некорректных тегов

- **Decision**: Тег, чьё имя не входит в реестр, или чьё значение не проходит валидацию для известного имени (например `~group:abc~`) — не распознаётся вообще: строка обрабатывается так, как если бы тега не было (т.е. если это была единственная содержимая строки — как обычная пустая строка → `NEWLINE` по умолчанию).
- **Rationale**: Безопасный дефолт — опечатка в теге не должна тихо "съедать" авторский текст и не должна ронять весь процесс разметки/форс-алаймента. Совпадает с уже принятым в проекте стилем защитного парсинга (см. комментарии в `WhisperMarkerAligner.kt` про `MIN_WORD_CONFIDENCE`/`MIN_INSERTION_CONFIDENCE` — предпочтение "не гадать" при неуверенности).
- **Alternatives considered**: Бросать явную ошибку валидации, показываемую пользователю в UI — отклонено для v1 как излишнее усложнение (нет текущего UI-канала для показа предупреждений по конкретной строке текста); можно добавить в будущей итерации.

## 7. Человекочитаемые алиасы для параметризованных тегов

- **Decision**: Алиас — отдельная запись реестра: фиксированное имя (без значения), которое разрешается в ТУ ЖЕ пару `(Markertype, label)`, что и конкретная параметризованная форма другого тега. v1: `Куплет`≡`group:0`, `Припев`≡`group:1`, `Бридж`≡`group:2`, `Приговор`≡`group:3` (набор и нумерация подтверждены пользователем явно, `group:4` без алиаса). Грамматика имени тега расширяется с `[a-z]+` до Unicode-букв (`\p{L}+`), сопоставление имени — регистронезависимое (`Куплет`/`куплет`/`КУПЛЕТ` — одно и то же). Алиас не принимает значение — `~Куплет:2~` не распознаётся (обрабатывается как нераспознанный тег, см. §6).
- **Rationale**: Раз алиас резолвится в те же `(markertype, label)`, что и его каноническая параметризованная форма, дедупликация "маркер уже стоит на этой границе" (см. §4/§5, FR-006 в spec.md) работает автоматически без отдельной логики — `~group:0~` и `~Куплет~` в одной песне не создадут два маркера, потому что итоговый `label` идентичен ("GROUP|0" в обоих случаях). Расширение грамматики имени на Unicode-буквы необходимо, так как алиасы — русские слова с большой буквы; отдельная грамматика "для алиасов" усложнила бы контракт без выгоды, поэтому используется одна и та же грамматика для всех имён тегов.
- **Alternatives considered**: (a) Сделать алиасы настраиваемыми через UI/Karaoke.properties — отклонено для v1 как избыточное усложнение при отсутствии текущей потребности в персонализации; реестр — часть кода, расширяется новой записью при необходимости (см. `contracts/tag-registry.md`). (b) Разрешить алиасу собственное значение (например `~Куплет:2~` → "второй куплет", группа/подномер) — отклонено, чтобы не вводить неоднозначную семантику "алиас + модификатор" без конкретного востребованного сценария; при появлении такой потребности это отдельное расширение реестра, не меняющее существующий контракт.

## 8. Третья независимая реализация контракта — краудсорсинг-редактор `karaoke-public`

- **Decision**: Контракт (грамматика/реестр/алиасы, `contracts/tag-registry.md`) реализован не в двух, а в **трёх** местах — обнаружено постфактум, по прямому вопросу пользователя ("а в karaoke-web/karaoke-public ничего менять не надо?") уже после того, как backend+webvue3 были реализованы и протестированы. `karaoke-public/src/composables/useKaraokeEditor.js` содержит `splitSyllables()` — документированную самим файлом "точную копию `getSyllables` из `SubsEdit.vue`" — используемую краудсорсинг-редактором заданий (`EditorWorkView.vue`) для того же слогоделения. Задание в этом редакторе получает `sourceText` как прямую копию официального текста песни из `tbl_settings` (см. `PublicSongEditorController.kt` — чистый JSON-passthrough, сам не парсит текст) — то есть текст задания уже может содержать спецтеги, расставленные админом, даже если волонтёр их не печатал. Без фикса `splitSyllables` был бы точно тем же баг-классом, что чинился в backend/webvue3: тег-строка ломает подсчёт слогов → съезжают все последующие маркеры. Добавлены: снятие тег-только строк перед слогоделением, `specTagAnchors`/`syncMarkersFromSpecTags` (аддитивный, зеркало `SubsEdit.vue`), подключены в `loadTask`/`onTextInput` (`EditorWorkView.vue`).
- **Rationale**: Инвариант "отсутствие тегов не меняет поведение" и "тег добавляет отсутствующий маркер" из `spec.md` — универсальные требования к системе в целом, а не только к admin-редактору; раз в системе есть третье место, где текст песни превращается в слоги/маркеры, оно обязано соблюдать тот же контракт, иначе экспортированный волонтёром результат при аппруве конфликтовал бы с тем, что ожидал бы увидеть админ.
- **Урок на будущее (зафиксировано явно по просьбе пользователя)**: `karaoke-web` (`PublicSongEditorController.kt`) — НЕ требует изменений (чистый passthrough, не парсит текст). `karaoke-public` — требует изменений **только в этой одной фиче** (`useKaraokeEditor.js`/`EditorWorkView.vue`) и только потому, что она содержит собственную копию слогоделения; это не общее правило "трогать oba фронтенда для любой фичи markers" — но для ЛЮБОЙ будущей правки именно контракта слогоделения/спецтегов нужно помнить про все три копии (см. предупреждение в `contracts/tag-registry.md`).
- **Alternatives considered**: Ничего не менять в `karaoke-public` и просто задокументировать ограничение ("спецтеги не поддерживаются в краудсорсинг-редакторе") — отклонено: это было бы скрытым источником багов при первом же назначении задания на песню с уже расставленными тегами (что неизбежно, если админ пользуется новой фичей в обычной работе), а не гипотетическим краевым случаем.

## 9. Четвёртое независимое место — форс-алаймент сервис `alignment-ml/syllables.py`

- **Decision**: `syllables.py` (функция `split_text_into_words`, используется `align.py`/`serve.py` — реальный HTTP-сервис форс-алаймента за кнопкой "Точные маркеры") получил ту же логику "снять спецтег-токен перед проверкой пуста ли строка", что и `WhisperMarkerAligner.buildTargetWords` (Kotlin). В отличие от мест 1-3 (см. `contracts/tag-registry.md`), сюда НЕ перенесён реестр/алиасы — этому модулю нужно только количество/границы "слов" для forced-alignment по словам (`align_words`), конкретный тип итогового маркера ему не важен: он не строит `SourceMarker`, только `(start_sec, end_sec)` тайминги слогов. Поэтому здесь достаточно самой ГРАММАТИКИ тега (`~([^\W\d_]+)(?::([^~]*))?~` — Python-эквивалент `\p{L}+` без стороннего пакета `regex`), без резолвинга имени/значения в конкретный маркер.
- **Rationale (как эта дыра появилась и почему её не поймали раньше)**: Исходное исследование (Phase 0/1 этой фичи) сравнивало сигнатуры "кто строит слоги из текста" только по grep'у `WhisperMarkerAligner.kt`/`SubsEdit.vue`/(затем) `useKaraokeEditor.js` — но НЕ по фактическому потоку данных внутри `buildMarkersFromSyllableTimes`: эта функция получает `syllableTimes` СНАРУЖИ (параметр, а не вычисляет сама) и полагается на то, что вызывающая сторона (`SongEditorController.editForcedAlignMarkers` → `AlignmentServiceClient.align` → HTTP → `align.py`/`serve.py`) вернула РОВНО столько таймингов, сколько слогов даёт `buildTargetWords` для того же текста — то есть контракт "количество слогов" неявно распределён МЕЖДУ backend и внешним Python-сервисом, а не замкнут внутри одного файла/языка. Комментарий над `_SYLLABLE_RE` в исходном `syllables.py` прямо предупреждал "Должна давать ИДЕНТИЧНУЮ разбивку" — но предупреждение относилось к трём МЕСТАМ на момент его написания (до этой фичи), и при добавлении тегов в Kotlin про этот файл просто не подумали, т.к. он физически находится в другом каталоге/языке/репутационно воспринимается как "ML-тренировка", а не "текстовый редактор".
- **Как обнаружено**: не через ревью/тесты, а через реальную ошибку пользователя в проде: "Число слогов в тексте не совпало с результатами выравнивания (внутренняя ошибка)" при клике "Точные маркеры" на тексте с тегами — тот же текст без тегов выравнивался нормально. Симптом прямо указывал на рассинхрон подсчёта слогов между Kotlin (уже поддерживает теги) и тем, что реально вернул сервис форс-алаймента (ещё не поддерживал).
- **Урок на будущее (зафиксировано явно по прямому запросу пользователя)**: при работе с любым контрактом типа "текст → слоги/слова", где подсчёт слогов расходится МЕЖДУ независимым сервисом и Kotlin/JS-кодом (не только "два фронтенда + backend", а буквально любой процесс, читающий `sourceText` и производящий с ним операции, зависящие от разбивки на слова/слоги) — искать ВСЕ такие места через сам факт использования `sourceText`/текста песни как входа в word/syllable-алгоритм, а не только по языку/директории. См. обновлённый практический чек-лист в `contracts/tag-registry.md`.
- **Alternatives considered**: Заставить `align.py` тоже резолвить реестр/алиасы (полная 4-я реализация, не частичная) — отклонено как избыточное: этому сервису конкретный тип маркера действительно не нужен ни для чего (он даже не знает про `Markertype`/`SourceMarker` на уровне типов), а лишний код увеличивает площадь будущего рассинхрона без выгоды.

## 11. Пятое независимое место — лёгкий admin-редактор `SongKaraokeEditorView.vue`

- **Decision**: `webvue3` содержит СВОЮ ОТДЕЛЬНУЮ копию `useKaraokeEditor.js` (`webvue3/src/composables/useKaraokeEditor.js`, физически другой файл, НЕ импорт из `karaoke-public`), используемую лёгким модальным редактором песни `SongKaraokeEditorView.vue`/`SongKaraokeEditorModal.vue` — отдельным от полновесного `SubsEdit.vue`. В неё портирован тот же набор (грамматика/реестр/алиасы/`syncMarkersFromSpecTags`/`insertSpecTagAtCursor`), что и в `karaoke-public`, плюс кнопки быстрой вставки в `SongKaraokeEditorView.vue` (панель `ske-spectag-toolbar`, идентичная по функциям панелям в `SubsEdit.vue`/`EditorWorkView.vue`).
- **Rationale**: Тот же принцип, что и везде в этом контракте — если место читает `sourceText` и строит из него слоги/маркеры, оно обязано honor'ить спецтеги, иначе пользователь получает противоречивые результаты в зависимости от того, через какой из ДВУХ admin-редакторов он открыл песню.
- **Как обнаружено**: пользователь прислал скриншот модалки "редактирование песни" в ответ на вопрос "где кнопки" — на скриншоте не было ни кнопок, ни узнаваемого UI `SubsEdit.vue` (там иконки-тулбар с `se-group-button`), а был layout, идентичный `EditorWorkView.vue` (краудсорсинг): слайдеры зум/скорость/громкость, кнопки "Показать клавиатуру"/"Очистить маркеры". Это было прямым сигналом, что существует ещё один UI-компонент.
- **Урок на будущее (главный, зафиксирован по прямому запросу пользователя)**: пакет/директория (`webvue3`) — НЕ равно "один редактор". Внутри одного фронтенд-пакета может быть несколько НЕЗАВИСИМЫХ реализаций одного и того же паттерна (здесь — целых два: `SubsEdit.vue` и `SongKaraokeEditorView.vue`, у каждого своя копия слогоделения). При словах "добавлено в `webvue3`" всегда проверять, есть ли там более одного компонента/composable с похожей ответственностью — `grep -rn "getSyllables\|splitSyllables" <пакет>` до того, как считать место покрытым, а не после первого найденного файла.
- **Alternatives considered**: Ничего не менять и считать `SongKaraokeEditorView.vue` "устаревшим"/неиспользуемым — отклонено без проверки: скриншот пользователя прямо показывает, что этот компонент активно используется в реальной работе, отказ от фикса означал бы тот же баг-класс (сломанный подсчёт слогов на тексте с тегами) прямо там, где пользователь фактически работает.

## 12. Тестирование при отсутствии CI-гейта на тесты

- **Decision**: Добавить unit-тесты только для чистых функций без внешних зависимостей (`SpecTags.parseLine`, `buildMarkersFromSyllableTimes` на фикстурных данных) — быстрые, детерминированные, не требуют сети/БД/браузера.
- **Rationale**: Конституция явно предупреждает не полагаться на существующие интеграционные тесты (`@Disabled`, требуют сеть/браузер) как на проверку — но не запрещает новые изолированные unit-тесты, а строгое требование обратной совместимости (FR-004/005/010 в spec.md) — ровно тот случай, где регрессия молча меняет тайминг/список маркеров у уже размеченных песен, что крайне неприятно обнаружить постфактум. Точечные тесты здесь дают несоразмерно высокую защиту относительно их размера.
- **Alternatives considered**: Полагаться только на ручную приёмку пользователем (`quickstart.md`) — оставлено как обязательный финальный шаг, но не как единственный, учитывая цену регрессии.
