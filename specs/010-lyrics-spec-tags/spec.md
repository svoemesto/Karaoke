# Feature Specification: Спецтеги в тексте песни для авто-разметки маркеров

**Feature Branch**: `010-lyrics-spec-tags`

**Created**: 2026-07-26

**Status**: Draft

**Input**: User description: "Механизм спецтегов в тексте песни для авто-разметки маркеров. Синтаксис: ~имя~ (без значения) или ~имя:значение~. Место в тексте — только отдельной строкой. Набор тегов v1: ~newline~, ~group:N~, ~comment:текст~. Обязательная обратная совместимость: теги только добавляют отсутствующие маркеры, никогда не удаляют/не трогают существующие."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Явный маркер новой строки через тег (Priority: P1)

Редактор песни печатает текст лирики и хочет явно обозначить разрыв между блоками текста (куплет/припев), не оставляя пустую строку "на глазок", а вписав явный тег `~newline~` на отдельной строке. При следующем запуске автоматической разметки ("Точные маркеры") в этом месте должен появиться маркер новой строки — как если бы там стояла обычная пустая строка.

**Why this priority**: Это прямая генерализация уже работающего сегодня механизма (пустая строка → маркер новой строки) и минимальный жизнеспособный кусок фичи — без него остальные теги не имеют смысла.

**Independent Test**: Взять текст песни с одной пустой строкой (сегодняшнее поведение) и с одним `~newline~` на отдельной строке вместо неё, прогнать через "Точные маркеры" — итоговый список маркеров должен совпадать (маркер новой строки в той же позиции).

**Acceptance Scenarios**:

1. **Given** текст песни, где между двумя строками лирики стоит строка с единственным содержимым `~newline~`, **When** запускается автоматическая разметка "Точные маркеры", **Then** в разметке между соответствующими строками появляется маркер новой строки.
2. **Given** текст песни без каких-либо спецтегов, но с обычной пустой строкой между блоками, **When** запускается "Точные маркеры", **Then** результат идентичен поведению системы до появления этой фичи (один маркер новой строки, как сегодня).

---

### User Story 2 - Границы групп и комментарии через тег (Priority: P2)

Редактор песни хочет разметить границу группы (куплет/припев/бридж) или оставить комментарий прямо в тексте лирики, вписав `~group:N~` или `~comment:текст~` на отдельной строке, вместо того чтобы искать нужный момент на аудио-таймлайне и нажимать соответствующую клавишу вручную.

**Why this priority**: Расширяет пользу P1 на реально нужные в проекте типы маркеров (группы уже используются для навигации по песне), но не блокирует базовый сценарий newline.

**Independent Test**: Взять текст с `~group:1~` перед куплетом и `~comment:трек барабанов~` перед бриджем, прогнать через "Точные маркеры" — в разметке должны появиться соответствующие маркер группы и маркер комментария в нужных позициях, без побочного эффекта на остальные маркеры.

**Acceptance Scenarios**:

1. **Given** строка с единственным содержимым `~group:2~` между двумя блоками лирики, **When** запускается "Точные маркеры", **Then** в разметке в этой позиции появляется маркер группы №2.
2. **Given** строка с единственным содержимым `~comment:какой-то текст~`, **When** запускается "Точные маркеры", **Then** в разметке появляется маркер комментария с текстом "какой-то текст".
3. **Given** строка с некорректным значением тега (например `~group:abc~`, нечисловое значение), **When** запускается "Точные маркеры", **Then** тег не распознаётся и игнорируется, разметка остальной песни не нарушается и процесс не завершается ошибкой.
4. **Given** строка с единственным содержимым `~Куплет~` (человекочитаемый алиас для `group:0`), **When** запускается "Точные маркеры", **Then** в разметке появляется тот же маркер группы №0, что и от `~group:0~` — без различий в результате.
5. **Given** в одной песне на разных строках использованы и `~group:0~`, и `~Куплет~` (тот же номер группы), **When** запускается "Точные маркеры" или пересчёт в редакторе, **Then** дублирующий маркер не создаётся — оба тега распознаются как эквивалентные.

---

### User Story 3 - Автодобавление маркера по тегу при ручном редактировании (Priority: P3)

Редактор песни правит уже размеченную песню в редакторе маркеров (без повторного запуска "Точные маркеры") и добавляет в текст лирики спецтег. Он ожидает, что при следующем сохранении/пересчёте соответствующий маркер появится в разметке автоматически, если его там ещё нет — так же, как если бы он нажал соответствующую клавишу вручную.

**Why this priority**: Расширяет применимость тегов на самый частый рабочий сценарий (ручное редактирование уже размеченной песни), но не критична для первого релиза механизма — можно временно жить с тем, что теги применяются только через полный прогон "Точные маркеры".

**Independent Test**: В уже размеченной песне добавить `~newline~` в текст лирики между двумя строками, где маркера новой строки ещё нет, сохранить/пересчитать разметку в редакторе — маркер должен появиться в нужном месте без повторного запуска "Точные маркеры" и без изменения остальных существующих маркеров.

**Acceptance Scenarios**:

1. **Given** уже размеченная песня, в тексте которой добавлен спецтег без соответствующего маркера в разметке, **When** редактор сохраняет/пересчитывает разметку в интерфейсе, **Then** соответствующий маркер добавляется автоматически в правильную позицию.
2. **Given** уже размеченная песня, где маркер для данного тега уже расставлен вручную, **When** редактор пересчитывает разметку, **Then** дублирующий маркер не создаётся.

---

### Edge Cases

- Строка содержит тег вместе с обычным текстом лирики (не единственное содержимое строки) — тег на такой строке не поддерживается в этой версии; строка обрабатывается как обычный текст лирики (тег остаётся как есть).
- Несколько тегов подряд на разных строках (например `~group:1~`, затем `~newline~`) между двумя блоками текста — каждый должен дать свой маркер в разметке.
- Неизвестное имя тега (не входящее в реестр поддерживаемых) — не распознаётся, разметка не нарушается.
- Тег стоит в самом начале или в самом конце текста песни (нет соседнего блока текста с одной из сторон) — не должен приводить к ошибке; поведение аналогично сегодняшнему поведению пустой строки в начале/конце текста.
- Один и тот же тег указан на нескольких соседних пустых-после-тега строках подряд (например дважды `~newline~`) — не должно приводить к появлению более одного маркера на одну и ту же логическую границу дважды в результате повторных прогонов.
- Песня с несколькими "голосами" (multivoice) — правило применяется независимо к тексту каждого голоса.
- Регистр букв в имени тега/алиаса (`~куплет~`, `~Куплет~`, `~КУПЛЕТ~`) — распознавание не должно зависеть от регистра.
- Алиас с указанным значением (например `~Куплет:2~`, значение не ожидается для алиаса) — не распознаётся как валидный тег, обрабатывается как нераспознанный (см. FR-008).
- Запуск "Точные маркеры" на тексте со спецтегами — форс-алаймент сервис (внешний Python-процесс) должен посчитать то же число слогов, что и backend, иначе разметка отказывает целиком с ошибкой несовпадения счётчика слогов, хотя тот же текст без тегов размечался бы нормально (см. FR-012; реальный воспроизведённый баг, исправлен).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система ДОЛЖНА распознавать спецтег вида `~имя~` (без значения) или `~имя:значение~` (со значением), расположенный на отдельной строке текста лирики (строка, всё содержимое которой — один спецтег).
- **FR-002**: Система ДОЛЖНА поддерживать как минимум следующие спецтеги: `newline` (маркер новой строки), `group:N` (маркер границы группы №N), `comment:текст` (маркер комментария с указанным текстом).
- **FR-002a**: Система ДОЛЖНА поддерживать человекочитаемые алиасы для параметризованных тегов вида `group:N` — фиксированное имя без значения, эквивалентное конкретной паре тег+значение. В v1: `Куплет` ≡ `group:0`, `Припев` ≡ `group:1`, `Бридж` ≡ `group:2`, `Приговор` ≡ `group:3`. Для `group:4` алиас не определён в v1 (доступен только через числовую форму). Алиас и его каноническая параметризованная форма ДОЛЖНЫ давать идентичный маркер (совпадающие `markertype`+`label`) — использование того или другого варианта не создаёт различий в разметке и не приводит к дублированию, если оба встречаются в одной песне (см. FR-006).
- **FR-003**: При автоматической разметке ("Точные маркеры") система ДОЛЖНА вставлять в разметку маркер, соответствующий каждому распознанному спецтегу, в позицию, соответствующую месту тега в тексте.
- **FR-004**: Обычная пустая строка без спецтега ДОЛЖНА продолжать давать маркер новой строки — точно так же, как до появления этой фичи (полная обратная совместимость поведения по умолчанию).
- **FR-005**: Система НЕ ДОЛЖНА удалять или изменять уже существующий в разметке маркер только на основании того, что соответствующий спецтег отсутствует или был удалён из текста.
- **FR-006**: Система НЕ ДОЛЖНА добавлять повторный/дублирующий маркер, если маркер, соответствующий спецтегу, уже присутствует в разметке в этой же позиции (независимо от того, был ли он расставлен вручную или ранее автоматически).
- **FR-007**: При ручном редактировании уже размеченной песни (без повторного полного запуска "Точные маркеры") система ДОЛЖНА, при сохранении/пересчёте разметки, добавлять отсутствующие маркеры для спецтегов, найденных в тексте, не трогая остальные существующие маркеры.
- **FR-008**: Нераспознанный спецтег (неизвестное имя, либо некорректное/недопустимое значение для известного имени) НЕ ДОЛЖЕН приводить к ошибке или сбою разметки — он должен игнорироваться, а строка обрабатываться так, как если бы тега не было (т.е. как пустая строка → поведение по умолчанию, маркер новой строки).
- **FR-009**: Набор поддерживаемых спецтегов ДОЛЖЕН быть расширяемым — добавление нового типа тега в будущем не должно требовать переработки существующей логики обработки текста.
- **FR-010**: Механизм ДОЛЖЕН одинаково работать независимо от того, есть ли в тексте песни спецтеги или нет — их полное отсутствие не должно менять ни один из результатов разметки по сравнению с поведением системы до появления этой фичи.
- **FR-011**: В текстовых редакторах (admin `SubsEdit.vue` и краудсорсинг-редактор `karaoke-public`) ДОЛЖНЫ быть доступны кнопки быстрой вставки спецтега в позицию курсора — для `newline`, каждого алиаса группы (`Куплет`/`Припев`/`Бридж`/`Приговор`), группы №4 (без алиаса, по номеру) и комментария (с запросом текста). Кнопка вставляет тег как единственное содержимое отдельной строки независимо от того, где стоял курсор (это не альтернативный способ распознавания — просто способ не печатать синтаксис руками).
- **FR-012**: Форс-алаймент сервис, используемый автоматической разметкой ("Точные маркеры"), ДОЛЖЕН исключать тег-только строки из подсчёта слогов/слов ТОЧНО ТАК ЖЕ, как это делает backend — расхождение в счётчике слогов между сервисом форс-алаймента и backend на тексте со спецтегами НЕ ДОЛЖНО приводить к отказу авто-разметки на текстах, которые без тегов размечались бы нормально.

### Key Entities *(include if feature involves data)*

- **Спецтег (Spec Tag)**: аннотация внутри текста лирики песни в формате `~имя~` или `~имя:значение~`, стоящая на отдельной строке. Атрибуты: имя тега, необязательное значение, позиция в тексте (какую строку/границу между блоками текста она обозначает).
- **Маркер (существующая сущность)**: элемент разметки песни с типом, временем и, для некоторых типов, значением/подписью (например маркер новой строки, маркер группы, маркер комментария). Спецтег транслируется в конкретный тип и значение маркера согласно реестру поддерживаемых тегов.
- **Реестр тегов**: сопоставление "имя тега (+ правило для значения)" → "тип маркера и как из значения тега строится содержимое маркера". Используется одинаково при автоматической разметке и при ручном пересчёте разметки.
- **Алиас тега**: фиксированное человекочитаемое имя без собственного значения (например `Куплет`), которое разрешается в ту же пару "тип маркера + содержимое", что и конкретная параметризованная форма другого тега (например `group:0`). Хранится как часть реестра тегов, не является отдельным типом маркера.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: На песнях без единого спецтега в тексте результат авто-разметки ("Точные маркеры") и ручного пересчёта разметки не отличается от результата до внедрения фичи — 0 расхождений на существующем корпусе размеченных песен, использованных как регрессионный набор.
- **SC-002**: Для текста с тегом `~newline~`, `~group:N~` или `~comment:текст~` на отдельной строке автоматическая разметка добавляет соответствующий маркер в правильной позиции в 100% тестовых случаев.
- **SC-003**: Повторный запуск авто-разметки или пересчёта разметки на одном и том же тексте с тегами не создаёт дублирующихся маркеров ни в одном из тестовых случаев.
- **SC-004**: Редактор может добавить новый тип спецтега в реестр поддерживаемых без изменения кода, отвечающего за поиск тегов в тексте и за обработку уже существующих типов тегов (изолированность расширения).

## Assumptions

- Спецтеги поддерживаются только как единственное содержимое отдельной строки текста лирики; расположение тега внутри строки лирики вместе с обычным текстом (инлайн-теги) — вне рамок этой версии.
- Набор тегов v1 ограничен `newline`, `group:N` (N — целое число, диапазон значений группы соответствует уже существующему в системе диапазону) и `comment:текст`; остальные типы маркеров пока не получают тег-эквивалента.
- Набор алиасов v1 фиксирован в коде (`Куплет`≡`group:0`, `Припев`≡`group:1`, `Бридж`≡`group:2`, `Приговор`≡`group:3`; для `group:4` алиаса нет) и не редактируется через UI — расширение набора алиасов в будущем не должно требовать переработки механизма распознавания тегов, только добавления записей в реестр.
- "Автоматическая разметка" в этой спецификации — существующий в системе механизм "Точные маркеры" (forced-alignment); механизм не меняет поведение других, не связанных с построением маркеров из текста, процессов.
- Ручное редактирование уже размеченной песни выполняется в существующем редакторе разметки; данная фича добавляет туда дополнительный, строго аддитивный шаг синхронизации маркеров из тегов текста — без изменения остального пользовательского интерфейса редактора.
- «Существующий редактор разметки» из требований этой спецификации — это ЛЮБОЕ место в системе, которое строит слоги/маркеры из текста песни, а не только admin-редактор (`webvue3`/`SubsEdit.vue`). На момент написания это два места: `webvue3` (админ) и краудсорсинг-редактор заданий в `karaoke-public` (`EditorWorkView.vue`/`useKaraokeEditor.js`) — последний получает текст песни как прямую копию официального `sourceText` и поэтому должен распознавать те же теги. См. предупреждение в `contracts/tag-registry.md` — при следующей правке этого контракта нужно проверить все места, где есть собственная копия слогоделения, не только backend+один фронтенд.
- «Автоматическая разметка» (FR-003) физически состоит из ДВУХ процессов, которые должны согласованно считать слоги: сам backend (`WhisperMarkerAligner.buildTargetWords`) И внешний форс-алаймент сервис (`alignment-ml/syllables.py`, Python, отдельный процесс за HTTP `AlignmentServiceClient`), который возвращает тайминг каждого слога. Если эти два места расходятся в подсчёте слогов на тексте со спецтегами — авто-разметка целиком отказывает с ошибкой "Число слогов в тексте не совпало с результатами выравнивания" (реальный баг, воспроизведённый пользователем и исправленный — `alignment-ml/syllables.py` теперь тоже снимает тег-только строки перед подсчётом, см. `research.md` §9, `contracts/tag-registry.md`).
- Символ `~` не используется в реальных текстах песен как обычный печатный символ; если это когда-либо потребуется, потребуется отдельный механизм экранирования (вне рамок этой версии).
- Кнопки быстрой вставки (FR-011) — чисто UX-слой над уже существующим распознаванием тегов: они вставляют готовую тег-строку в текстовое поле тем же способом, каким её мог бы напечатать пользователь, и не участвуют в парсинге/резолвинге. Правки этого слоя не требуют синхронного изменения контракта распознавания (`contracts/tag-registry.md`), но НАБОР кнопок ДОЛЖЕН оставаться в синхроне с реестром/алиасами v1 — при добавлении нового тега в реестр стоит добавить и кнопку (иначе тег остаётся доступен только "печатанием руками", что противоречит духу FR-011).
