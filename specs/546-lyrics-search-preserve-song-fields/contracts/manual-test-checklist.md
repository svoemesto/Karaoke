# Contract: ручной чек-лист приёмки

**Feature**: `546-lyrics-search-preserve-song-fields`
**Когда выполнять**: разработчиком перед merge и проверяющим при ревью PR.
**Где**: dev-хост/контейнер `karaoke-app` (не прод).

## 0. Подготовка

1. Ветка собрана: `GRADLE_USER_HOME=/home/nsa/Karaoke/.gradle ./gradlew :karaoke-app:compileKotlin`.
2. Unit-тесты зелёные: `GRADLE_USER_HOME=/home/nsa/Karaoke/.gradle ./gradlew :karaoke-app:test --tests '*SongWritePlan*' --tests '*SongFieldUpdateSql*'`.
3. ktlint: `GRADLE_USER_HOME=/home/nsa/Karaoke/.gradle ./gradlew :karaoke-app:ktlintCheck`.
4. Тестовая папка: 3 `.flac` с именами вида `2020 (01) [Тест] - Песня один.flac`, у песен
   заведомо нет родителя в базе (проверить поиском по названию в админке).

## 1. Воспроизведение дефекта на `master` (доказательство)

1. Собрать и запустить контейнер на `master`.
2. Импортировать тестовую папку.
3. Сразу после старта открыть первую песню в `SongEdit.vue`, поменять название и тональность
   (`song_tone`), сохранить.
4. Дождаться окончания поиска текста. **Ожидаемо на master**: название/тональность вернулись
   к старым значениям, в логе `song.locked_save_diff_overlap`.

Зафиксировать: SQL-состояние строки до/после (см. §4) и строку лога.

## 2. Проверка фикса (ветка)

1. Собрать ветку, перезапустить `karaoke-app` — **сначала остановить очередь** (Pass 380:
   `curl -s http://localhost:8898/process/stop`, дождаться пустого списка `WORKING`/`CREATING`).
2. Импортировать ту же папку.
3. Сразу поменять у первой песни название и тональность, сохранить.
4. Дождаться завершения поиска. **Ожидаемо**: `song_name` и `song_tone` — значения
   администратора, `source_text` — найденный текст, `id_status = 1`.
5. Повторить 3 раза (SC-001 — 10 прогонов суммарно, допустимо партиями).

## 3. Регрессия фоновых заданий

1. При импорте дождаться `KEY_BPM_FROM_FILE` до окончания поиска (`tbl_processes.status = DONE`).
2. Проверить: `song_tone`/`song_bpm` заполнены и не обнулились после подстановки текста.
3. Дождаться `DEMUCS2`; проверить, что `audio_*` не пусты после подстановки текста.

## 4. Проверка «ни одного лишнего поля» (SC-002)

До импорта снять снимок строки, после подстановки — сравнить:

```sql
-- до
COPY (SELECT * FROM tbl_songs WHERE id IN (<ids>)) TO '/tmp/songs_before.csv' CSV HEADER;
-- после подстановки текста
COPY (SELECT * FROM tbl_songs WHERE id IN (<ids>)) TO '/tmp/songs_after.csv' CSV HEADER;
```

Ожидаемо в диффе только: `source_text`, `id_status`, `recordhash`, `last_update` (если
колонка обновляется триггером). Любая другая колонка в диффе — провал проверки.

## 5. Граничные случаи

| Сценарий | Как воспроизвести | Ожидаемо |
|---|---|---|
| Текст уже есть | Во время поиска вставить текст вручную через SongEdit | Текст не перезаписан, `song.field_update_skipped reason=existing_text` |
| Статус ушёл вперёд | Во время поиска перевести песню в статус 2 | Статус остался 2, текст подставлен |
| Песня удалена | Удалить песню во время поиска | Ошибок нет, `song.field_update_not_found`, строки в БД нет |
| Два поиска | Запустить «Найти тексты для всех песен» и импорт одновременно по одной песне | Ровно одна подстановка, второй — skip |

## 6. Откат

1. `git revert <merge-commit>` (или переключить образ на предыдущий тег).
2. Перезапуск — снова через остановку очереди (Pass 380).
3. Убедиться, что `saveToDbLocked()` продолжает работать для сервисов публикации (они не
   затронуты).

## 7. Что считается провалом

- Любая изменённая колонка вне набора из [lyrics-write-policy.md](lyrics-write-policy.md) §5.
- Отсутствие `source_text` после успешного поиска.
- Понижение `id_status`.
- Исключение/500 в импорте при удалённой песне.
- Появление новых `KEY_BPM_FROM_FILE` в очереди после подстановки текста.
