# Quickstart: проверка расширенного жизненного цикла статуса песни

Проверка делается вручную (в CI автотестов на этот слой нет, см. `plan.md` →
Technical Context → Testing). Использовать локальный sandbox-стек
(`deploy/do.sh`) или production-like окружение, не прод напрямую — миграция
необратима без ручного отката.

## Предусловия

- Локальный стек поднят: `db`, `karaoke-app`, `karaoke-web`, `webvue3`,
  `karaoke-public`.
- Известен список (или запрос) песен с `id_status >= 3` **до** миграции —
  чтобы после сравнить, что набор «готовых» не изменился (SC-001 spec.md).
  Например: `SELECT id, song_name, id_status FROM tbl_songs WHERE id_status
  >= 3;` — сохранить результат.
- Есть хотя бы одна песня с `id_status = 0`, одна с `1`, одна с `2` — для
  проверки, что миграция их не трогает.

## Сценарий 1 — миграция данных (порядок выката, `contracts/song-status-lifecycle.md` раздел 3)

1. Применить `deploy/karaoke-db/32_song_status_lifecycle.sql` на sandbox-БД.
2. **Ожидаемо**: все песни из предусловий (`id_status>=3` до миграции)
   теперь имеют `id_status=6`. Песни со статусом 0/1/2 — без изменений.
3. Повторно применить тот же SQL-файл.
4. **Ожидаемо**: повторный прогон не меняет ничего (идемпотентность,
   `data-model.md`).

## Сценарий 2 — порог готовности не ломает существующую публичную выдачу (SC-001)

1. **После** миграции и деплоя кода с новым порогом (`>=6`), открыть
   `karaoke-public` → закрома / поиск / онлайн-плеер для песен из
   сохранённого списка предусловий.
2. **Ожидаемо**: те же самые песни видны/играют, что и до изменения — набор
   не сократился и не расширился (сравнить со списком, сохранённым в
   предусловиях).
3. Проверить `GET /api/public/stats` — счётчик «в коллекции» (`onSponsr`
   в `karaoke-public/store/modules/stats.js`) не должен резко упасть после
   деплоя (может незначительно измениться из-за естественного течения
   времени между снятием предусловий и проверкой).

## Сценарий 3 — SongEdit: полный диапазон статусов доступен и подписан правильно

1. В `webvue3` открыть SongEdit для любой песни.
2. **Ожидаемо**: в блоке «Статус» видно 7 кнопок (0-6, включая
   ранее отсутствовавшую кнопку 5), без пометок «Легаси»/`group-button-legacy`.
   Названия соответствуют `data-model.md` (Новая / Текст найден / Текст
   проверен: орфография / Текст проверен: слова / Маркеры расставлены /
   Маркеры проверены / Готова).
3. Кликнуть по каждой из 7 кнопок по очереди, сохранить.
4. **Ожидаемо**: после каждого сохранения `idStatus` песни соответствует
   выбранному значению и корректно отображается при повторном открытии
   SongEdit (без отката/расхождения).
5. Установить песне статус 6, затем понизить до 4.
6. **Ожидаемо**: сохраняется 4; песня перестаёт быть видна/играть на
   `karaoke-public` (см. Сценарий 2) — понижение статуса администратором
   работает (FR-007), в отличие от автоматических процессов (Сценарий 4).

## Сценарий 4 — автоматические переходы не перепрыгивают и не понижают статус (FR-010, FR-011)

1. Взять песню со статусом 1 (текст найден, этапы 2/3 не пройдены).
2. Запустить автоматическую расстановку маркеров (forced-align, кнопка
   «Точные маркеры» в SubsEdit или фоновый эндпоинт
   `/song/forcedalignmarkers`).
3. **Ожидаемо**: маркеры фактически расставляются (видны в редакторе), но
   `idStatus` НЕ становится 4 — остаётся на прежнем значении, пока этапы 2
   и 3 не пройдены (см. `spec.md` User Story 3, сценарий 4).
4. Взять другую песню со статусом 3 (текст проверен по обоим пунктам),
   запустить тот же forced-align.
5. **Ожидаемо**: `idStatus` становится 4 (маркеры расставлены), не 6.
6. Взять песню со статусом 5 или 6, инициировать более ранний автоматический
   шаг конвейера (например, повторный автопоиск текста через
   `/utils/customfunction` или аналог).
7. **Ожидаемо**: `idStatus` не понижается автоматически.

## Сценарий 5 — легаси MLT-пайплайн больше не трогает `idStatus`

1. Взять песню с любым `idStatus` (например, 2).
2. В SongEdit нажать «Создать караoke» (легаси MLT-рендер-кнопка,
   `createKaraoke`).
3. **Ожидаемо**: рендер стартует как раньше (создаются
   `KaraokeProcess`-задания `MELT_LYRICS`/`MELT_KARAOKE`), но `idStatus`
   песни НЕ меняется на 3 автоматически (Decision 1, `research.md`).
4. Дождаться завершения обоих MELT-процессов.
5. **Ожидаемо**: `idStatus` по-прежнему не меняется автоматически на 6 как
   побочный эффект завершения рендера (раньше срабатывало только при
   `idStatus==4`, что после этой фичи не должно происходить в принципе).

## Сценарий 6 — regression guard: admin-инструменты синхронизированы с новым порогом

1. В `webvue3` → таблица песен, для песни со статусом 4 или 5, проверить
   иконку «Открыть онлайн-плеер».
2. **Ожидаемо**: иконка показана как недоступная (плеер откроется только
   при `idStatus>=6`), а не как доступная (что было бы UI-ложью, см.
   `research.md` Decision 3).
3. Кнопка «Точные маркеры» в SongEdit должна быть недоступна для песен с
   `idStatus>=4` (а не `>=3`, как раньше — это отдельный гейт «маркеры уже
   расставлены», не порог публичной готовности, см. `research.md` Decision
   6) — проверить на песне со статусом 3 (кнопка активна) и 4 (кнопка
   неактивна).

## Критерий готовности

Все 6 сценариев проходят так, как описано выше → фича соответствует
SC-001…SC-004 `spec.md`.
