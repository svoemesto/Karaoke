# Phase 0 Research: Доп. поля Author/Album/Song + новый UI Закромов

## §1. Формат поля «Описание» (форматированный текст)

**Decision**: Поле `description` хранится и передаётся как обычный многострочный
**plain text** (без HTML-тегов). «Форматирование» реализуется на фронте через
CSS `white-space: pre-wrap` (сохраняет пустые строки/переносы, оборачивает
длинные строки) — без разметки, без rich-text редактора, без `v-html`.

**Rationale**:
- В webvue3 нет ни одной WYSIWYG-библиотеки (quill/tiptap/ckeditor и т.п. —
  0 совпадений в `package.json`/`src`) — добавление такой зависимости ради трёх
  коротких текстовых полей непропорционально по сложности.
- Единственный существующий в проекте прецедент «форматированного текста»
  (`formattedTextSong/Tabs/Chords`) — это HTML, **генерируемый бэкендом** из
  структурированных данных (маркеры/аккорды), а не вводимый вручную
  администратором. Здесь источник другой: `description` — свободный ручной ввод
  админа. Рендерить произвольный HTML от ручного ввода через `v-html` на
  публичном сайте — риск stored-XSS, тем более что у webvue3 нет авторизации
  (`permitAll()`, Принцип V) — угроза не гипотетическая.
- `white-space: pre-wrap` даёт «читаемый текст с абзацами» (именно то, что
  просил пользователь: «интересные факты») без какого-либо нового кода на
  бэкенде и без риска на фронте.

**Alternatives considered**:
- Полноценный WYSIWYG (Tiptap/Quill) → отклонено: новая зависимость,
  избыточно для 3 коротких полей, не входит в текущий стек.
- Markdown с рендером на фронте → отклонено: тоже требует новой библиотеки
  парсинга + экранирования; plain text + CSS проще и не имеет риска инъекции.
- HTML + `v-html` (как formattedText*) → отклонено: XSS-риск при отсутствии
  авторизации в админке.

## §2. Показ описания в тултипе при наведении

**Decision**: Нативный HTML-атрибут `title` на элементе имени автора/названия
альбома/названия песни. Поскольку `description` — plain text (§1), браузерный
`title`-тултип корректно показывает многострочный текст (переносы `\n`
поддерживаются всеми целевыми браузерами) без дополнительного кода.

**Rationale**: В проекте нет ни одного существующего тултип-компонента
(ни Bootstrap `data-bs-toggle="tooltip"`, ни `bootstrap-vue-next` `<BTooltip>` —
0 совпадений в `karaoke-public`/`webvue3`), хотя Bootstrap уже установлен как
зависимость. Нативный `title` — нулевая стоимость реализации, нулевой риск,
достаточен, т.к. содержимое — plain text (§1).

**Alternatives considered**: Bootstrap JS tooltip (`new bootstrap.Tooltip(...)`)
— отклонено как избыточное для простого текста; было бы оправдано только при
необходимости HTML-контента в тултипе, чего теперь не требуется (§1).

## §3. Recordhash-триггеры и добавление колонок

**Decision**: Одна миграция `deploy/karaoke-db/31_entity_description_fields.sql`
добавляет по 3 колонки (`description TEXT`, `short_description VARCHAR(255)`,
`warning VARCHAR(255)`, все `DEFAULT ''`) к `tbl_authors`, `tbl_albums`,
`tbl_songs`, и пересобирает (`CREATE OR REPLACE FUNCTION`)
`update_tbl_authors_recordhash()`, `update_tbl_albums_recordhash()`,
`update_tbl_songs_recordhash()`, включив новые колонки в конец md5-конкатенации
(сохраняя порядок уже существующих колонок — иначе беспричинно пересчитается
recordhash существующих строк, что безвредно, но избыточно). Завершается
backfill'ом recordhash для существующих строк.

**Rationale**: Точная копия уже дважды применённого в проекте паттерна —
`27_author_special_order.sql` (добавление `is_special_order` к `tbl_authors` +
пересборка функции + backfill) и `29_albums.sql`/`30_song_coauthors.sql`
(аналогично для `tbl_albums`/`tbl_songs`). Все три таблицы уже участвуют в
sync (Принцип III: `AuthorsSyncTarget` key=`"authors"`, `AlbumsSyncTarget`
key=`"albums"`, Song key=`"settings"`, `SyncTarget.kt:280-497`) — новых
sync-таргетов/флагов заводить не нужно, только пересборка recordhash, без
которой LOCAL↔SERVER diff не увидит новые поля как расхождение (конституция,
Принцип II/III).

**Alternatives considered**: Отдельная миграция на каждую таблицу (3 файла) —
отклонено, не даёт преимуществ, три ALTER логически — одна фича, один applied-раз
шаг разворачивания.

## §4. Единый источник правды для русских подписей типа альбома

**Decision**: `AlbumType` (`karaoke-app/.../model/AlbumType.kt`) получает два
новых поля рядом с уже существующим `description` (используемым как подпись
«под названием альбома»): `groupLabel` (для заголовка группы: «Студийные
альбомы», «Синглы», «Концертные альбомы», «Сборники», «Бутлеги») и
`filterLabel` (для кнопки быстрого фильтра: «Студийные», «Синглы»,
«Концертные», «Сборники», «Бутлеги»). `ZakromaPublicDto` дополняется полем
`albumTypeCounts: List<AlbumTypeSummaryDto>` — по одному элементу на КАЖДЫЙ тип,
у которого count > 0 для этого автора, в фиксированном порядке (studio, single,
live, compilation, bootleg), с полями `dbValue`, `groupLabel`, `filterLabel`,
`count`. Фронт (`ZakromaView.vue`) полностью убирает свою текущую
рассинхронизированную RU-мапу (см. текущий код, строка ~450) и рендерит
заголовки групп/кнопки фильтров/счётчики целиком из этого списка.

**Rationale**: Сейчас `ZakromaView.vue` дублирует и рассинхронизирует русские
подписи типа альбома со своей локальной мапой (`{ live: 'концерт', ... }`,
отличается по регистру/числу от бэкендового `AlbumType.description`) — FR-018
явно требует единства. Подсчёт количества альбомов по типу логичнее делать на
бэкенде (там уже есть полный список альбомов автора), чем дублировать
group-by-count на фронте.

**Alternatives considered**: Фронт сам считает count из уже присланного списка
альбомов и хранит свою мапу подписей → отклонено, это и есть текущая
проблема (дублирование, рассинхронизация); перенос на бэкенд устраняет её
раз и навсегда.

## §5. Персистентность режима отображения/фильтров

**Decision**: `localStorage`, по автору отдельно не персистится (общий для всех
авторов ключ — «глобальная» пользовательская настройка режима просмотра, как
и переключатель темы).

**Rationale**: Прямой прецедент в этом же файле — `.km-theme-toggle` уже
хранит выбор темы в `localStorage` (дублируется в `ZakromaView.vue`,
`SongView.vue`, `SearchView.vue`). Второй одинаковый механизм для нового
переключателя — минимальный когнитивный люфт для разработчика, поддерживающего
код.

**Alternatives considered**: Хранение на сервере через `setWebvueProp`/
аналогичный API → отклонено, это API конкретно webvue3 (admin), для
публичного сайта нет прецедента серверной персистентности пользовательских UI-
настроек анонимного посетителя; `localStorage` достаточен и на порядок проще.
