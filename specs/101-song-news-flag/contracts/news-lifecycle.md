# Контракт: три точки жизненного цикла авто-новостей о песне

Внутренние (не HTTP-публичные) контракты между тремя независимыми точками
кода, которые вместе реализуют оба вида авто-новости. Ни один REST-эндпоинт
не добавляется и не меняется этой фичей — три точки ниже уже существуют
(`Song.saveToDb()`, `MainController.doChangeRecords` / `POST /changerecords`,
`SongReleaseAnnouncementScheduler`), меняется только их внутреннее поведение.

## 1. `Song.saveToDb()` — выставление флага «доступна» (LOCAL и/или SERVER, в зависимости от того, где вызван save)

**Вход**: текущее состояние объекта `Song` перед записью в БД (тот же процесс,
что вызывает `saveToDb()` — редактор, апрув, пайплайн-автоматика).

**Поведение**:
- Если `idStatus == 6 && stemAccompanimentReady && stemVocalReady &&
  pictureAlbumReady && pictureAuthorReady && sourceMarkersList.isNotEmpty() &&
  !newsAvailableAnnounced` — устанавливает `newsAvailableAnnounced = true` на
  сохраняемом объекте **до** вычисления diff, чтобы изменение попало в тот же
  `UPDATE`/INSERT и в тот же цикл синхронизации.
- Если условие не выполняется, или флаг уже `true` — не делает ничего
  дополнительного (идемпотентно, безопасно вызывать многократно).

**Выход**: `player_readiness_flags` (и, соответственно, `recordhash`) может
измениться как часть обычного сохранения строки. Никакой новости на этом шаге
не создаётся — это исключительно локальная (по отношению к БД, в которую
идёт `save()`) бухгалterия.

**Гарантии**:
- Не создаёт видимых побочных эффектов (никакой новости, никакого сетевого
  вызова).
- Одноразовое, необратимое переключение `false → true` (никогда обратно).

## 2. `MainController.doChangeRecords` (`POST /changerecords`) — детекция перехода и создание новости «доступна»

**Вход**: тот же батч `dataCreate`/`dataUpdate`/`dataDelete`, что и сегодня
(зашифрованные SQL-фрагменты от sync-движка).

**Поведение** (новое, взамен старого прямого вызова `checkAndAnnounce` для
«в эфире», который отсюда убирается):
1. Для каждой записи `dataUpdate` с `tableName == "tbl_songs"` — до
   выполнения её `UPDATE`, прочитать текущее значение
   `newsAvailableAnnounced` этой строки на сервере (`SELECT` по PK).
2. Выполнить `UPDATE` как обычно (без изменений в этой части).
3. Прочитать/разобрать новое значение флага после применения.
4. Если старое значение было `false`/отсутствовало, а новое — `true` —
   вызвать `News.createAutoAnnouncement(songId, title, body, link,
   category="premium", source="auto", ...)` ровно один раз для этой песни.
5. Для `dataCreate`, затрагивающих `tbl_songs` — «старое» значение считается
   `false` по определению; если вставленное значение флага — `true`,
   применяется тот же шаг 4.

**Выход**: 0 или 1 новая строка `tbl_news` на каждую песню, чей флаг реально
перешёл `false → true` в этом конкретном вызове.

**Гарантии** (идемпотентность):
- Повторный вызов `/changerecords` с тем же (или другим) диффом для той же
  песни, у которой сервер уже хранит `newsAvailableAnnounced = true`, никогда
  не создаёт вторую новость — переход просто не обнаруживается повторно
  (сервер сравнивает со своим текущим, уже обновлённым значением).
- Сбой создания новости (например, ошибка БД при вставке в `tbl_news`) не
  должен откатывать уже применённые изменения синхронизации — логируется и
  не пробрасывается наружу (тот же принцип, что и у старого
  `checkAndAnnounce`).

## 3. `SongReleaseAnnouncementScheduler.checkOnAir()` — плановая проверка «в эфире» (~раз в 5 минут, PROD)

**Вход**: нет (периодический таймер, без параметров).

**Поведение** (новое, взамен старого вызова `checkAndAnnounce` с
`tbl_song_news_announced`):
1. Дешёвый первый проход: `id`, `publish_date`, `publish_time`, `id_status`
   для всех строк с `id_status >= 6` (без текста/маркеров/base64).
2. В Kotlin вычислить `dateTimePublish` для каждой и оставить только
   попадающие в окно `(now - 10 минут, now]`.
3. Полностью загрузить только эти кандидаты (чанками), отфильтровать по
   `isPubliclyWatchable`.
4. Для каждого кандидата — если в `tbl_news` уже есть строка с этим `song_id`
   и `category = 'air'` (создана автоматически на предыдущем тике или
   вручную администратором) — пропустить. Иначе создать одну новость
   (`category="air"`, `source="auto"`).

**Выход**: 0..N новых строк `tbl_news`, где N — число песен, чьё время эфира
попало именно в это окно и у которых такой новости ещё не было.

**Гарантии**:
- Никогда не создаёт вторую новость для одной песни (existence-check внутри
  окна).
- Никогда не создаёт новость задним числом для песни, чья дата эфира
  наступила раньше текущего окна (в т.ч. сразу после очистки `tbl_news`) —
  такая песня физически не попадает в первый проход п.2.
- Если проверка не выполнялась в момент, когда дата эфира песни попадала в
  окно (например, сервис был недоступен), и с тех пор окно уже сдвинулось —
  новость для этой песни автоматически не создаётся; администратор может
  создать её вручную (ручная новость той же категории `"air"` с тем же
  `song_id` также будет обнаружена existence-check'ом в п.4, если песня
  всё же попадёт в более позднее окно повторно — что не должно происходить,
  так как `dateTimePublish` у песни не меняется).

## Что НЕ входит в контракт (явно не создаёт новость «в эфире»)

- Синхронизация (`doChangeRecords`) — после этой фичи создаёт только новость
  «доступна» (см. п.2), не «в эфире».
- Апрув задания редактора (`SongEditorController.approve()`) — после этой
  фичи не создаёт напрямую ни одной из двух новостей (флаг «доступна»
  выставляется как побочный эффект обычного `saveToDb()` внутри `approve()`,
  но сама новость появится позже, при следующей синхронизации, через
  контракт п.2).
