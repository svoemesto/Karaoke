# Feature Specification: Восстановить поиск родителя при добавлении файлов из папки

**Feature Branch**: `279-fix-parent-search-folder-add`

**Created**: 2026-08-31

**Status**: Draft

**Input**: User description: "Админка, главная страница, «Добавленить файлы из папки». Перестал работать поиск родителей. Пример: добавляется песня группы «Король и Шут» с названием «Камнем по голове (Epic Orchestral, Cover-2)» — для неё в качестве родителя должна была быть найдена и подставлена песня группы «Король и Шут» с названием «Камнем по голове», но этого не произошло, rootId остался нулевым."

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Поиск родителя у того же автора при импорте из папки (Priority: P1)

Администратор на главной странице админки нажимает «Добавить файлы из папки» и указывает папку, в которой лежат аудиофайлы в формате `YYYY (NN) [Автор] - Песня.flac`. Для каждого файла создаётся новая песня, после чего автоматически ищется «родитель» — уже существующая в базе песня того же автора с тем же названием без учёта содержимого в скобках, знаков препинания и различия «е»/«ё», у которой уже заполнен текст. Если такой родитель найден, новая песня получает его `id` в поле `root_id` (rootId), и в неё копируется текст и маркеры родителя. Администратор открывает карточку новой песни и видит, что она уже привязана к родителю («семья» песен), а поля «Текст песни» / «Метки» / «Форматированный текст» заполнены.

**Why this priority**: Без автоматической привязки к родителю каждая свежеимпортированная песня требует ручной работы в карточке (открыть FamilySongsModal, найти оригинал, привязать, дождаться копирования). На массовом импорте (десятки/сотни файлов из одной папки) это умножает время оператора и приводит к тому, что многие песни остаются без текста до тех пор, пока оператор не дойдёт до них вручную.

**Independent Test**: Подготовить папку с 3 аудиофайлами одной группы, где у каждой новой песни в формате имени файла есть суффикс в скобках (например, «Камнем по голове», «Камнем по голове (Epic Orchestral, Cover-2)», «Камнем по голове (Instrumental)»), и в БД уже существует базовая песня «Камнем по голове» с заполненным `source_text`. Запустить «Добавить файлы из папки». После завершения операции для каждой из 3 импортированных песен поле `root_id` должно быть равно `id` базовой песни, а `source_text` / `source_markers` / `result_text` / `formatted_text_song` / `formatted_text_tabs` / `formatted_text_chords` — скопированы от родителя.

**Acceptance Scenarios**:

1. **Given** в БД существует песня «Король и Шут» — «Камнем по голове» с заполненным `source_text`, **When** администратор импортирует файл `[Король и Шут] - Камнем по голове (Epic Orchestral, Cover-2).flac` из папки, **Then** для новой песни автоматически заполняются `root_id = <id базовой песни>`, `source_text = <текст базовой песни>`, `source_markers = <маркеры базовой песни>`, `result_text` / `formatted_text_*` — скопированы от родителя, `id_status = 1`.

2. **Given** в БД существуют две песни одного автора с одинаковым нормализованным названием и заполненным текстом («Камнем по голове» с `id=50` и «Камнем по голове (Live)» с `id=80`), **When** импортируется файл `[Король и Шут] - Камнем по голове (Cover).flac`, **Then** родителем выбирается запись с наименьшим `id` (`id=50`), а не «Live»-версия.

3. **Given** в БД НЕТ песни того же автора с тем же нормализованным названием и заполненным текстом, **When** администратор импортирует файл `[Новый Автор] - Новая Песня.flac`, **Then** новая песня получает `root_id = 0` (родитель не найден, как и должно быть при отсутствии оригинала), `source_text` остаётся пустым до успешного интернет-поиска (`findYandexSongLyrics` синхронно, при отсутствии результата — фоновый `lyricsSearchExecutor`).

4. **Given** в БД есть базовая песня, но у неё `source_text` пуст или состоит только из пробелов, **When** администратор импортирует файл с суффиксом в скобках того же автора, **Then** новая песня НЕ привязывается к этой базовой (поскольку у базовой нет текста, копировать нечего), `root_id = 0`. Это согласуется с прежним поведением — привязка только к записям с уже заполненным текстом.

5. **Given** в БД есть базовая песня с заполненным текстом, **When** администратор импортирует файл с суффиксом того же автора, **Then** после полного цикла `doCreateFromFolder` (включая `findDuplicateOriginal`, `applyDuplicateOriginal`, `findAudioParentByWaveform`):
   - В БД `root_id` указывает на `id` базовой песни (НЕ сброшен в 0 после `findAudioParentByWaveform`).
   - `textResolved = true` ИЛИ (если родитель не применён) `findYandexSongLyrics`/`lyricsSearchExecutor` запустились.
   - НИКОГДА: `root_id = 0` И поиск текста не запущен (текущая регрессия).

### User Story 2 — Поиск родителя НЕ пересекает авторов (Priority: P2)

Администратор импортирует файл автора «Кино» с названием «Звезда по имени Солнце (Cover by Other Artist)». В БД есть песня автора «Король и Шут» с тем же нормализованным названием «Звезда по имени Солнце» и заполненным текстом. После импорта новая песня НЕ должна быть привязана к чужому автору — `root_id` остаётся нулевым, и интернет-поиск текста запускается в обычном порядке.

**Why this priority**: Привязка к чужому автору приводит к ложному наследованию текста/маркеров и порче карточки песни. Это требование существовало раньше (см. спеку 238 «родители только у того же автора») и должно сохраняться независимо от исправления основной проблемы поиска.

**Independent Test**: Подготовить папку с файлом автора «Кино» — «Звезда по имени Солнце (Cover).flac», в БД — запись «Король и Шут» — «Звезда по имени Солнце» с заполненным текстом. Запустить импорт. Проверить, что `root_id` новой песни = 0, а `source_text` пуст.

**Acceptance Scenarios**:

1. **Given** в БД есть «Король и Шут» — «Камнем по голове» с текстом, **When** импортируется файл другого автора с тем же нормализованным названием, **Then** `root_id = 0`, привязки к чужому автору не происходит.

2. **Given** в БД есть несколько песен разных авторов с одинаковым нормализованным названием, **When** импортируется песня одного из этих авторов, **Then** родителем становится только запись того же автора; записи других авторов игнорируются.

### User Story 3 — Поиск родителя устойчив к написанию автора (Priority: P3)

Администратор импортирует файлы, в имени файла автор указан в одной форме (например, «Король и шут» с маленькой буквы), а в БД существующая песня того же автора записана в другой форме («Король и Шут» с большой буквы). После импорта родитель всё равно находится и привязка выполняется корректно.

**Why this priority**: Регистр и форма написания имени автора в имени файла и в БД могут различаться — это нормальная ситуация, которая не должна блокировать поиск родителя. Без этого фикса даже тривиальное различие в регистре приводит к тому, что родитель не находится.

**Independent Test**: Импортировать файл `[Король и шут] - Камнем по голове (Cover).flac` при наличии в БД песни «Король и Шут» — «Камнем по голове» с заполненным текстом. Проверить, что `root_id` новой песни указывает на базовую песню.

**Acceptance Scenarios**:

1. **Given** в БД автор записан как «Король и Шут», в имени файла — «Король и шут», **When** администратор импортирует файл, **Then** родитель находится и привязывается (сравнение по имени автора регистронезависимо).

2. **Given** в БД автор записан как «Кино», в имени файла — «кино» или «КИНО», **When** администратор импортирует файл, **Then** родитель находится и привязывается.

---

### Edge Cases

- **Что если у базовой песни `root_id` уже указывает на другую песню (родитель сам — часть чужой семьи)?** — при импорте нового файла того же автора с тем же нормализованным названием должна использоваться запись с минимальным `id` среди подходящих, как и раньше; переход по цепочке `root_id` к настоящему корню семьи НЕ требуется (прежнее поведение).
- **Что если в БД уже есть несколько песен одного автора с одинаковым нормализованным названием И у всех заполнен текст?** — выбирается запись с наименьшим `id` (прежнее правило).
- **Что если файл импортируется с именем, в котором есть только содержимое в скобках, а само название пустое (например, `[Король и Шут] - (Instrumental).flac`)?** — нормализованное название пустое, поиск родителя не выполняется (прежнее поведение, зафиксировано в `normalizeSongNameForSearch`).
- **Что если в имени файла автора нет (формат файла нестандартный)?** — песня всё равно создаётся, но без автора; поиск родителя при пустом поле автора не находит ничего, `root_id = 0`.
- **Что если у базовой песни `source_text` есть, но песня имеет тег `SKIP` или другие признаки «не для наследования»?** — прежнее поведение: тег `SKIP` влияет только на отображение в публичной части, но не блокирует привязку в `findDuplicateOriginal`. Сохраняем это поведение.
- **Что если родитель найден, но в момент `applyDuplicateOriginal` параллельный процесс успел обновить `song_tone` / `song_bpm` / URL'ы стемов?** — ранее введённая защита (перезагрузка объекта из БД перед `saveToDb`, спека 278) должна продолжать работать: `root_id` и текст записываются, а параллельно найденные тональность/стемы не перетираются.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: При добавлении файлов из папки через `POST /api/utils/createfromfolder` (и эквивалентный `POST /utils/createfromfolder`) для каждой вновь созданной песни ДОЛЖЕН выполняться автоматический поиск «родителя» — песни того же автора с тем же нормализованным названием (без содержимого в скобках, без знаков препинания, регистронезависимо, «е»/«ё» эквивалентны), у которой `source_text` не пуст (после `TRIM`). Поиск ДОЛЖЕН использовать существующую логику `findDuplicateOriginal` / `applyDuplicateOriginal` в `karaoke-app/.../utils/Utils.kt` либо её эквивалент с тем же контрактом (см. спек 238 и FR-001..FR-004 `specs/238-import-folder-author-album-cover/spec.md`).

- **FR-002**: При наличии нескольких подходящих родителей в БД (одинаковый автор, одинаковое нормализованное название, непустой `source_text`) должна выбираться запись с наименьшим `id` — прежнее правило, зафиксированное в `findDuplicateOriginal` (`ORDER BY id ASC`).

- **FR-003**: При успешном нахождении родителя для новой песни ДОЛЖНЫ быть заполнены поля `root_id = <id родителя>`, `source_text`, `source_markers`, `result_text`, `formatted_text_song`, `formatted_text_tabs`, `formatted_text_chords` (скопированы от родителя), `id_status = 1` (TEXT_CREATE). Поведение совпадает с `applyDuplicateOriginal` в `Utils.kt`.

- **FR-004**: Поиск родителя ДОЛЖЕН быть ограничен записями того же автора (сравнение `LOWER(song_author) = LOWER(?)`). Привязка к чужому автору НЕ ДОЛЖНА происходить — это требование зафиксировано в спеке 238 и должно сохраняться.

- **FR-005**: Сравнение имён песен должно использовать `normalizeSongNameForSearch` (см. `Utils.kt:4383`): удаление содержимого в скобках, приведение к нижнему регистру, замена «ё»→«е», удаление знаков препинания (только буквы/цифры/пробелы остаются), схлопывание и тримминг пробелов. Сравнение ДОЛЖНО быть регистронезависимым и устойчивым к различиям «е»/«ё».

- **FR-006**: Сравнение имени автора должно быть регистронезависимым (разные формы написания имени автора в имени файла и в БД не должны блокировать поиск).

- **FR-007**: Существующая защита от race condition при записи (перезагрузка объекта из БД перед `saveToDb` в `applyDuplicateOriginal`, спека 278) ДОЛЖНА сохраняться. После нахождения родителя и копирования полей в новую песню параллельно найденные процессом `KEY_BPM_FROM_FILE` `song_tone`/`song_bpm` и процессом `DEMUCS2` URL'ы стемов НЕ ДОЛЖНЫ перетираться пустыми значениями.

- **FR-007a**: После `applyDuplicateOriginal` (и аналогично `applyAudioParentMarkers`) объект `newSong` (соответственно `song`) в памяти ДОЛЖЕН быть синхронизирован с записанным состоянием — `newSong.rootId = original.id`, `newSong.sourceText = original.sourceText`, и т.д. Без этой синхронизации последующий вызов `song.saveToDb()` (например, внутри `findAudioParentByWaveform`, `Utils.kt:4879/4898/4919/4933`) видит расхождение между `this.rootId = 0` (в памяти) и `savedSong.rootId = original.id` (из БД) → diff включает `root_id = 0` → UPDATE перезатирает только что записанный `root_id` обратно в 0. Это регресс после спеки 278: до спеки 278 присваивание шло напрямую в `newSong`, и `newSong`/`savedSong` были согласованы; после спеки 278 — присваивание идёт в новый объект `songToSave`, и `newSong` остаётся «грязным» в памяти.

- **FR-008**: Поведение для случая «родитель не найден» (`root_id = 0`) НЕ ДОЛЖНО изменяться: запускается интернет-поиск текста (`findYandexSongLyrics` синхронно, затем `lyricsSearchExecutor` фоновый поиск через `SearXNG`/`fourget`), как в `doCreateFromFolder` (`ApiController.kt:5390`). Никаких ошибок или предупреждений в этом случае не требуется — это нормальный сценарий для действительно новых песен.

- **FR-009**: Поведение для случая «родитель найден, но найден и аудио-родитель» (по схожести звучания, `findAudioParentByWaveform`) НЕ ДОЛЖНО изменяться: при успешном акустическом сходстве ≥ 95% и `id_status` аудио-родителя ≥ 6 применяются его маркеры (`applyAudioParentMarkers`), статус переходит в `MARKERS_CHECK (5)`. Это независимая от FR-001 ветка логики.

- **FR-010**: Поведение кнопки «Custom Function» на главной странице админки (`customFunction` в `Utils.kt:96`), которая гоняет повторный поиск родителей и аудио-родителей по всем песням с `root_id = 0` и `id_status < 6`, ДОЛЖНО продолжать работать как прежде и использовать ту же исправленную логику поиска родителя.

- **FR-011**: Существующие эндпоинты `/api/utils/createfromfolder` и `/utils/createfromfolder`, UI-компонент `webvue3/src/views/HomeView.vue` (кнопка «Добавить файлы из папки», вызов `createFromFolderPromise`), и action в `webvue3/src/components/Songs/store.js` НЕ ДОЛЖНЫ менять свой публичный контракт (HTTP-метод, параметры, формат ответа). Изменения локализованы в backend-логике.

### Key Entities

- **Song (песня)**: доменная сущность в `tbl_songs`. Ключевые поля для этой спеки: `id`, `song_name`, `song_author`, `source_text` (содержимое текста песни), `source_markers`, `result_text`, `formatted_text_song`, `formatted_text_tabs`, `formatted_text_chords`, `root_id` (id родителя в «семье»), `id_status` (статус пайплайна: 0=NONE, 1=TEXT_CREATE, 5=MARKERS_CHECK, 6=READY).
- **«Родитель» / «семья» песен**: логическая группировка. Родитель — запись, на которую указывает `root_id` дочерней песни. У самого родителя `root_id` либо равен 0 (он — корень своей семьи), либо указывает на истинный корень. Поле `findFamilySongIds` (см. `Utils.kt:4683`) находит все песни той же семьи для UI модалки «Похожие версии песни».

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: При импорте 5+ файлов одной группы, где каждый файл имеет суффикс в скобках (например, «Камнем по голове», «Камнем по голове (Epic Orchestral, Cover-2)», «Камнем по голове (Instrumental)», и т.д.), и в БД существует базовая песня «Камнем по голове» с непустым `source_text`, — для 100% импортированных файлов поле `root_id` указывает на `id` базовой песни, а поля `source_text`/`source_markers`/`result_text`/`formatted_text_*` заполнены значениями от родителя. Проверяется через `SELECT id, song_name, root_id, source_text FROM tbl_songs WHERE song_name LIKE '%Камнем по голове%'`.

- **SC-001a**: При импорте файла, для которого `applyDuplicateOriginal` не отработал (исключение, пустой diff, и т.п.), `findYandexSongLyrics` ВСЁ РАВНО запускается. Проверяется через логи контейнера `karaoke-app`: должна быть строка `findYandexSongLyrics` для импортированной песни. Если `findDuplicateOriginal` не нашёл — `lyricsSearchExecutor.submit` тоже запускается.

- **SC-002**: Ни одна из импортированных песен в тестовом сценарии SC-001 НЕ привязывается к чужому автору: `SELECT id FROM tbl_songs WHERE song_author <> 'Король и Шут' AND root_id IN (SELECT id FROM tbl_songs WHERE song_author = 'Король и Шут' AND song_name = 'Камнем по голове')` возвращает 0 строк.

- **SC-003**: После применения фикса повторный запуск кнопки «Найти и обработать дубликаты» / `customFunction` для песен с `root_id = 0` и `id_status < 6` корректно находит родителей по тем же правилам (тот же автор, нормализованное имя, непустой `source_text`, минимальный `id`).

- **SC-004**: Поведение кейса «родитель не найден» (новая песня с уникальным названием) НЕ изменяется: `root_id = 0`, дальше работает интернет-поиск текста (`findYandexSongLyrics` → `lyricsSearchExecutor` → фон), как и до фикса.

- **SC-005**: Существующая защита от race condition (спека 278) сохраняется: если параллельно с `applyDuplicateOriginal` процесс `KEY_BPM_FROM_FILE` уже записал `song_tone`/`song_bpm`, эти поля НЕ перетираются при `saveToDb()` после нахождения родителя. Проверяется через `SELECT song_tone, song_bpm FROM tbl_songs WHERE id = <id импортированной песни>` сразу после операции.

- **SC-006**: Никаких регрессий в существующих сценариях импорта из папки: импорт папки без дубликатов (все песни уникальные), импорт папки с уже существующими в БД файлами (должны пропускаться через `loadListFromDb` по `file_name`/`root_folder`), импорт папки с разными авторами — все эти сценарии работают как прежде.

- **SC-007**: Числовой отчёт после фикса: при тестовом импорте папки с 10 файлами одного автора (9 файлов с суффиксами в скобках + 1 базовый) — 9 из 10 новых песен имеют `root_id <> 0` (привязаны к базовой), 1 базовая имеет `root_id = 0`. Это проверяемый, повторяемый сценарий.

## Assumptions

- Причина текущего сбоя поиска родителей находится в backend-логике (`Utils.findDuplicateOriginal`, `Utils.applyDuplicateOriginal`, либо в SQL/условиях внутри них), а не в UI или HTTP-слое. Конкретная причина — задача плана (`/speckit.plan`), здесь фиксируется только ЧТО должно работать.
- Существующая логика нормализации имени `normalizeSongNameForSearch` (`Utils.kt:4383`) и сравнения автора по `LOWER(...)` корректны; проблема — либо в условиях SQL, либо в порядке вызовов, либо в порядке полей в `applyDuplicateOriginal`, либо в условиях, при которых результат отбрасывается.
- Поведение `customFunction` (`Utils.kt:96`) уже использует ту же логику поиска родителя (через `findParentCandidateId` + `applyDuplicateOriginal`), поэтому фикс в `findDuplicateOriginal` автоматически покроет и `customFunction`, если в `findParentCandidateId` нет собственных отличий (или они идентичны по семантике).
- Существующая защита от race condition (спека 278, перезагрузка объекта из БД перед `saveToDb` в `applyDuplicateOriginal` и `applyAudioParentMarkers`) продолжает работать. Никаких изменений в `Song.saveToDb()` не требуется.
- Тестирование — ручное, на стороне пользователя (см. Constitution § «Тесты»), в production-like окружении. Существующие интеграционные тесты в `karaoke-app/src/test` помечены `@Disabled` и не полагаемся на них как на автоматическую проверку.
- Базовая песня («Камнем по голове» без суффикса) уже существует в БД и имеет непустой `source_text` — это предусловие сценария пользователя, без него привязка и не должна происходить (FR отражает это в виде «ищется только среди песен с непустым `source_text`»).
- Никаких миграций схемы БД не требуется: поля `root_id` и связанные с текстом уже существуют в `tbl_songs`.
- Решение не затрагивает публичный frontend (`karaoke-public`): для пользователей сайта наличие/отсутствие `root_id` приватно и не влияет на отображение.
