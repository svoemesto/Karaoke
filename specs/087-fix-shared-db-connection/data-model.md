# Data Model: Изоляция соединений с БД по потокам + устойчивость очереди к сетевым сбоям

**Feature**: [spec.md](./spec.md) | **Research**: [research.md](./research.md)

Схема БД (PostgreSQL) не меняется — эта фича целиком про транспортный
уровень соединения с БД и устойчивость главного цикла очереди, без новых
таблиц/колонок. Ниже — концептуальные сущности из спеки (`Key Entities`) в
привязке к реальным классам/полям, все non-persistent (in-memory).

## Соединение с БД (существующая сущность — `java.sql.Connection`, кешируемое в `KaraokeConnection`)

| Атрибут | До фикса | После фикса |
|---|---|---|
| Хранение | `KaraokeConnection.connection: java.sql.Connection?` — одно поле, `@Volatile`, общее на весь инстанс | `KaraokeConnection.connection: ThreadLocal<java.sql.Connection?>` — своё значение на каждый обратившийся поток |
| Область видимости | Один физический канал на весь `KaraokeConnection`-инстанс (= на всё приложение для `WORKING_DATABASE`) | Один физический канал на пару (`KaraokeConnection`-инстанс, поток) |
| Self-healing | `getConnection()`: если `null`/`isClosed`/`!isValid(3)` → пересоздать | Не меняется — та же проверка, но применяется к значению `ThreadLocal` текущего потока |
| Время жизни | Пока приложение работает (или пока не станет невалидным) | То же самое, но per-thread: пока жив поток (для потоков пула Tomcat — практически всё время жизни приложения) |

## Поток выполнения (концептуальная сущность — не отдельный класс, `Thread.currentThread()` в момент вызова `getConnection()`)

| Источник потока | Роль | Ожидаемое число одновременных соединений от этого источника |
|---|---|---|
| Пул потоков Tomcat (`server.tomcat.threads.max`) | Обработка HTTP-запросов админки | ≤ настроенный максимум потоков (см. Кандидат A, `research.md` — рекомендация снизить до разумного значения) |
| Выделенный поток `KaraokeProcessWorker.doStart()` | Главный цикл очереди заданий | Ровно 1 (один долгоживущий поток на весь цикл работы очереди) |
| Пул Spring `@Scheduled` (по умолчанию 1 поток) | Периодические задачи (`MonitoringService`, `StemJobPollScheduler` и др.) | 1 (или больше, если явно сконфигурирован `TaskScheduler` с несколькими потоками — вне scope этой фичи, менять не требуется) |

## Главный цикл очереди заданий (существующая сущность — `KaraokeProcessWorker.doStart()` + обёртка в `start()`)

Не меняет свою внутреннюю логику (обработку `KaraokeProcess`/`tbl_processes`)
— меняется только то, как `start()` реагирует на его аварийное завершение.

**Переходы состояния `isWork`, относящиеся к этой фиче** (дополняют уже
существующие из specs/029-fix-queue-lane-stall):

```text
doStart() падает с исключением
        │
        ▼
попыток retry не исчерпано? ──да──> подождать (нарастающая пауза) ──> doStart() заново (isWork остаётся true)
        │ нет (попытки исчерпаны)
        ▼
isWork = false, sendStateMessage()  (как и раньше — safety-net specs/029)
        │
        ▼
RenderQueueStalledCheck (тик раз в минуту) обнаруживает isWork=false + есть WAITING → алерт, one-click resume
```

Новое состояние «идёт повторная попытка» не персистентно (не пишется в БД,
не отдельное поле `KaraokeProcess`) — существует только как локальная
переменная внутри `start()` на время работы retry-цикла; для внешнего
наблюдателя (UI/мониторинг) в течение retry `isWork` остаётся `true` (как
будто очередь всё ещё работает — что по сути верно, она пытается
продолжить).

## Валидационные правила (из Functional Requirements)

- FR-001/FR-002: каждый поток получает собственное соединение через
  `ThreadLocal` — гарантируется самой конструкцией (по определению
  `ThreadLocal`), без дополнительной логики.
- FR-003: self-healing (`isClosed`/`isValid(3)`) сохраняется дословно, лишь
  переносится в контекст `ThreadLocal.get()`/`.set()`.
- FR-004: число соединений ограничено числом потоков, которые когда-либо
  обращались к `KaraokeConnection`-инстансу — конечно и предсказуемо, пока
  ограничен сам пул потоков (Tomcat max threads).
- FR-005/FR-006: retry в `start()` — ограниченное число попыток с
  нарастающей паузой; после исчерпания — существующий safety-net не
  убирается, а становится следующим уровнем защиты.
