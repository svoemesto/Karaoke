# Local ADR-0014: Превентивные меры против исчерпания памяти в `karaoke-app`

* **Status**: Accepted
* **Date**: 2026-10-30
* **Deciders**: команда Karaoke (решение владельца от 2026-10-30)

> **English version**: `../../../livedocs-en/decisions/local-0014-heap-memory-guardrails-karaoke-app.md`
>
> **Note**: this is a **local** ADR — describes a specific subsystem
> convention (vs global ADR-0001..0006 which describe project-wide decisions).

## Context

Инцидент 2026-10-23 на admin-машине `nsa-i9`: `OutOfMemoryError: Java heap space`
в `karaoke-app` (в `Publication.getUnPublicationList()`), одновременно умерли четыре
selector-потока JDK `HttpClient`, и 5+ часов держался **ложный** CRITICAL «Прод-сервер
недоступен» при живом прод-сайте (297 тиков `ping:failed`, `curlDiagnostic ok` за
92..168 мс). Первопричина устранена не была.

Разбор вскрыл три системных пробела, из-за которых OOM прошёл незамеченным и дорого
обошётся:

1. **У контейнера `karaoke-app` не было предела памяти.** Значение `-Xmx8g` жило
   только в **неотслеживаемом** `deploy/.env` — в git его нет, значит связь
   «heap < предел контейнера» нельзя было проверить из репозитория. JVM без
   cgroup-лимита вытесняла память хоста: хост уходил в swap, страдали соседние
   сервисы.
2. **Не было дампа состояния heap при OOM.** Разбор инцидента начинался с догадок,
   а не со снимка состояния процесса.
3. **Загрузка heap не наблюдалась.** О-operator узнавал о приближении к падению
   post-mortem'ом, а не по алерту за минуту до.

Дополнительно: ADR `local-0013` («внешних оповещений нет — journal-only») относится
к **infra-серверу**; для `karaoke-app` канал доставки — журнал/SLF4J плюс уже
существующие SSE и `GET /api/monitor/alerts`. Сам `local-0013` **не переписывается**
(ADR в этом репозитории append-only) — уточнение области решения фиксируется здесь.

## Decision

Три превентивные меры, объявленные в **отслеживаемой** конфигурации
(`deploy/docker-compose-app.yml`) и проверяемые автоматическим guard'ом.

### 1. Предел памяти контейнера и связь «heap ↔ предел»

| Параметр | Значение | Почему |
|---|---|---|
| `mem_limit` | `8g` | cgroup-потолок: без него JVM вытесняет память хоста |
| `-Xmx` | `6g` | запас ~2 ГБ на метапространство, native-память и потоки |
| `-XX:+HeapDumpOnOutOfMemoryError` | — | снимок состояния heap при OOM |
| `-XX:HeapDumpPath=/dumps` | том `./karaoke-db/dumps` | дамп переживает рестарт контейнера |

**Порядок флагов**: `-Xmx6g` объявляется **после** `${APP_JAVA_OPTS}` — последний
`-Xmx` побеждает (`java -Xmx8g -Xmx6g` → `MaxHeapSize` = 6 GiB). Так устаревшее
`-Xmx8g` из неотслеживаемого `deploy/.env` перекрывается, остальные флаги из
окружения сохраняются, а фактический лимит задаёт **репозиторий**, а не файл вне git.

### 2. Источник данных о загрузке heap

`Runtime.getRuntime()`: `maxMemory()` (потолок ≈ `-Xmx`) и
`totalMemory() - freeMemory()` (занято).

**Обоснование**: не зависит от состава JRE/JDK и от наличия модуля
`java.management` (образ `karaoke-app` — `ubuntu:22.04` + `openjdk-17-jre-headless`);
MXBean для процента от максимума heap точнее не даёт; чтение `Runtime` не имеет
побочных эффектов и не блокирует — инвариант «проверка читает, а не пишет».

### 3. Политика хранения дампов

Последние **2** дампа, суммарный лимит тома **20 ГБ**, вытеснение **по возрасту**,
защита 60 минут (файл моложе — возможно не дописанный дамп — не удаляется).
Исполнитель — host-side `deploy/heap-dump-retention.sh` (+ опциональные systemd-юниты,
установка которых — действие владельца).

**Почему на стороне хоста**: JVM при OOM **умирает** — встроенная в приложение
уборка не отработает в самый нужный момент. Хостовый таймер работает всегда.

**Почему только `*.hprof`**: каталог дампов общий с SQL-дампами БД (BR-046), любая
политика «удалить старые файлы» без фильтра по расширению снесла бы дампы БД.

**Приоритет при конфликте ограничений**: лимит тома важнее «последних двух» —
если два свежих дампа сами не помещаются в 20 ГБ, вытеснение идёт по возрасту
дальше. При `-Xmx6g` (дамп ≈ 6 ГБ) два дампа ≈ 12 ГБ и конфликт недостижим; при росте
`-Xmx` выше ~9–10 ГБ лимит тома нужно пересчитать.

### 4. Маппинг severity алерта → уровень журнала

| Severity | Уровень SLF4J |
|---|---|
| INFO | INFO |
| WARNING | WARN |
| ERROR | ERROR |
| CRITICAL | ERROR |

**Обоснование**: уровня CRITICAL в SLF4J нет, а внешних оповещений у мониторинга
нет — уровень журнала остаётся **единственным машинно-читаемым признаком
эскалации** для оператора. Проверки с единственным уровнем (WARNING) логируют свои
алерты на WARN — это согласовано с тем же правилом.

## Рассмотренные альтернативы

### Отвергнуто: поднять своп на admin-машине (64 → 128 ГБ)

**Решение владельца (2026-10-30): своп не поднимаем.** Факт на дату решения:
62 ГБ RAM (25 занято, 36 доступно), `/swapfile` 64 ГБ с 21,7 ГБ занято, подкачки
сейчас нет (`vmstat`: si≈0, so=0) → занятый своп — это припаркованные холодные
страницы, а не признак давления.

Обоснования отказа:

1. **Проблема инцидента не «мало RAM», а «контейнер без cgroup-лимита».** Своп её
   не лечит: лимит памяти контейнера и есть то, что должно ограничивать процесс.
2. **В cgroup v2 лимит RAM и лимит свопа — разные ограничения.** При наличии
   свопа контейнер может уйти в подкачку хоста **вместо** OOM-kill: вместо быстрого
   явного отказа получается медленная деградация. Для этого приложения
   (ffmpeg/melt/Playwright + HTTP/SSE) тихое подвисание хуже рестарта и повторяет
   класс ложной тревоги «прод недоступен» из инцидента 2026-10-23.
3. **Место.** Своп и том дампов на одном разделе NVMe (86 % занято) — рост свопа
   приближает сценарий «том переполнен».

Выбранное решение — **ограничение контейнера** (`mem_limit: 8g` + `-Xmx6g`), а не
увеличение свопа.

### Отвергнуто: источник данных о heap — `MemoryMXBean` (JMX)

Зависимость от модуля `java.management` в составе рантайм-образа и создание
MBean-ов как побочный эффект; выигрыша в точности процента нет.

### Отвергнуто: уборка дампов внутри приложения

Приложение не может убрать дамп после того, как само умерло от OOM. Кроме того,
продуктовый код, удаляющий файлы, — лишний риск.

### Отвергнуто: sidecar-контейнер для уборки в `docker-compose-app.yml`

Новый контейнер в критичном compose + новый образ на admin-машине; `do.sh
start_app` поднимает все сервисы файла, то есть контейнер поехал бы в
прод-окружение без отдельного решения владельца.

### Отвергнуто: inline-скрипт в `entrypoint` контейнера

Изменение способа старта OOM-критичного сервиса (риск «контейнер не стартует»).

### Отвергнуто: CPU-лимит (`cpus`) для контейнера

CPU-лимит для контейнера с ffmpeg/melt/Playwright — эксплуатационный риск вне
контракта задачи (FR-006/FR-007 требуют только предел памяти). Оставлен владельцу
как возможное отдельное решение.

## Consequences

1. **Запрет**: `-Xmx` контейнера `karaoke-app` не может превышать предел памяти
   контейнера; значение `-Xmx` в `deploy/.env` (вне git) на фактический лимит не
   влияет.
2. **Инвариант**: пара «heap ↔ предел» объявлена в репозитории и проверяется
   автоматическим guard'ом `tools/check-memory-guardrails.sh` (pre-commit + CI).
3. **Инвариант**: политика хранения дампов не трогает ничего, кроме `*.hprof`.
4. **Инвариант**: состояние проверки мониторинга — только в памяти; новых
   персистентных ключей не появляется.
5. **Required Update**: при изменении `-Xmx` — пересчитать лимит тома дампов; при
   изменении порогов — обновить `deploy/docker-compose-app.yml` и
   `knowledge/domains/monitoring/components/monitor-checks.md`.
6. **Остаётся за владельцем**: установка и включение systemd-таймера уборки дампов;
   очистка `deploy/.env` от устаревшего `-Xmx8g`; решение по CPU-лимиту.
