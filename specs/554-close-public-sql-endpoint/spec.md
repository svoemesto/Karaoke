## User Scenarios & Testing *(mandatory)*

### User Story 1 — Публичный интернет не может исполнить SQL на боевой БД (Priority: P1)

Анонимный посетитель сайта (любой, без учётной записи и без ключа) пробует вызвать эндпоинт, который принимает SQL-действия, с публичного адреса. До правки такой запрос выполнялся на боевой БД. После правки — отказ, ничего не выполнено, и попытка видна в журнале.

**Why this priority**: это единственный пользовательский сценарий, ради которого задача и заведена — неаутентифицированное исполнение произвольного SQL на проде. Остальные сценарии (US2, US3) защищают от регрессии рабочего пути.

**Independent Test**: с внешнего адреса без ключа выполнить один запрос к эндпоинту → ожидается отказ, тело ответа не содержит текста ошибки SQL, в логах есть запись об отказе; проверяется отдельно, без участия внутреннего клиента.

**Acceptance Scenarios**:

1. **Given** эндпоинт опубликован в интернете, **When** анонимный клиент отправляет запрос с корректным по форме телом (зашифрованное кодовое слово + список SQL-действий), **Then** запрос отклоняется, ни одна SQL-команда не выполняется, клиент получает отказ (403/404), а не «OK».
2. **Given** эндпоинт опубликован в интернете, **When** анонимный клиент отправляет произвольный текст в поле кодового слова, **Then** отказ тот же, и в ответе нет текста ошибки базы данных.
3. **Given** попытка отклонена, **When** администратор смотрит журнал, **Then** в журнале есть запись об отказе с указанием времени и источника, но без содержимого присланного SQL.

---

### User Story 2 — Внутренняя синхронизация песен продолжает работать (Priority: P2)

Служба на боевом хосте периодически отправляет изменения песен в боевой БД через тот же эндпоинт. После правки эта служба должна продолжать работать: изменения применяются, а при временной сетевой ошибке поведение остаётся прежним (одна повторная попытка, без падения процесса).

**Why this priority**: без этого правка ломает основную функцию — двуx-БД синхронизацию песен. Это регрессионный риск, который важнее косметики.

**Independent Test**: в тестовом окружении выполнить один успешный обмен с корректным внутренним ключом и одну искусственную сетевую ошибку → ожидается: успешный обмен применён, при сетевой ошибке — одна повторная попытка и отсутствие исключения наружу.

**Acceptance Scenarios**:

1. **Given** внутренний клиент с корректным ключом, **When** он отправляет изменения песен, **Then** изменения применяются, клиент получает подтверждение, метрика успешных обменов растёт.
2. **Given** внутренний клиент без ключа или с неверным ключом, **When** он отправляет изменения, **Then** изменения не применяются, клиент получает отказ и не повторяет запрос (это не сетевая ошибка).
3. **Given** временная сетевая ошибка при корректном ключе, **When** клиент повторяет запрос, **Then** поведение прежнее: одна повторная попытка, затем тихий отказ без исключения.

---

### User Story 3 — Отказ виден и не выдаёт деталей (Priority: P3)

Администратор должен видеть попытки внешнего доступа к закрытому эндпоинту, при этом наружу не должны утекать ни тексты ошибок БД, ни детали внутренней схемы.

**Why this priority**: полезно для эксплуатации, но не блокирует устранение уязвимости — поэтому P3.

**Independent Test**: один отклонённый запрос → в журнале есть запись категории безопасности; в ответе клиенту нет ни текста ошибки SQL, ни имён таблиц.

**Acceptance Scenarios**:

1. **Given** отклонённый запрос, **When** открыт журнал приложения, **Then** в нём есть запись об отказе (категория безопасности), без тела присланного запроса.
2. **Given** отклонённый запрос, **When** получен ответ, **Then** в теле ответа нет текста ошибки БД и нет имён таблиц.

---

### Edge Cases

- Внутренний секрет не задан (пустой/не сконфигурирован) → доступ закрыт всегда (fail-safe), синхронизация не проходит, но и дыры нет; в журнале — отдельная запись о неверной конфигурации.
- Секрет совпадает, но запрос пришёл с внешнего адреса → отказ на уровне публичного периметра (сетевой фильтр), даже если ключ верен: ключ — второй, сетевой фильтр — первый рубеж.
- Клиент прислал пустой список SQL-действий → поведение как сейчас (успех/«OK»), никакого исполнения.
- Тело запроса не является JSON → отказ с кодом 400, без текста исключения наружу.
- Одновременные запросы синхронизации → поведение не меняется (правка не должна менять порядок/транзакционность применения действий; существующая транзакционность — вне рамок задачи, см. BR-012).
- Запрос с корректным ключом, но с чужого IP → отказ на сетевом рубеже; ключ не помогает.
- Адрес админской машины сменился у провайдера и нового адреса ещё нет в списке → синхронизация с этого адреса не проходит (отказ на сетевом рубеже) до добавления адреса; это ожидаемое поведение, а не регрессия, и проверяется по журналу отказа.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система MUST отклонять любой запрос к эндпоинту исполнения SQL, не содержащий корректного внутреннего ключа, и не выполнять ни одной команды из тела запроса.
- **FR-002**: При неверном или отсутствующем внутреннем ключе система MUST закрывать доступ (fail-safe), в том числе когда секрет не настроен вовсе.
- **FR-003**: Система MUST принимать запрос с корректным внутренним ключом и применять переданные действия без изменения их состава и порядка.
- **FR-004**: Система MUST передавать внутренний ключ тем же способом, каким уже защищён внутренний эндпоинт скачивания исходников (`X-Internal-Secret`), и задавать его одинаково на обеих сторонах.
- **FR-005**: Публичный сетевой контур MUST отклонять запросы к эндпоинту, пришедшие не с адреса админской машины — тем же способом, каким уже закрыты внутренние порты базы и хранилища: список разрешённых адресов админской машины (`allow` для актуального и двух предыдущих адресов провайдера: `185.26.28.109`, `83.137.50.231`, `185.26.28.199`) и запрет для всех остальных (`deny all`). Образец — уже работающие блоки внутренних портов (5433 — доступ к прод-БД для двуx-БД синхронизации, 9000 — MinIO).
- **FR-006**: При отказе система MUST возвращать клиенту отказ (403 или 404) и MUST NOT возвращать текст ошибки базы данных или детали внутренней схемы.
- **FR-007**: Каждая отклонённая попытка MUST попадать в журнал приложения с указанием времени и источника запроса; тело присланного запроса в журнал не пишется.
- **FR-008**: Отказ по ключу (неверный ключ) MUST NOT трактоваться как сетевая ошибка — повторная попытка не выполняется.
- **FR-009**: Временная сетевая ошибка при корректном ключе MUST сохранять прежнее поведение клиента: одна повторная попытка с паузой и тихий отказ без исключения.
- **FR-010**: Должен существовать автоматический регрессионный тест, который падает на текущем коде и проходит после правки: проверяются оба состояния — с корректным ключом (действия применяются) и без ключа (отказ, ничего не применено).
- **FR-011**: Правка MUST NOT менять формат тела запроса и семантику применения SQL-действий (партнёрская сторона — клиент синхронизации — обновляется в том же изменении).
- **FR-012**: Правка MUST NOT затрагивать другие эндпоинты и не должна менять публичное поведение сайта.

### Key Entities

- **Внутренний ключ (shared secret)**: симметричный секрет, задаваемый администратором одинаково на стороне отправителя и стороне сервиса; при отсутствии закрывает доступ.
- **Запрос на изменение данных**: тело с зашифрованным кодовым словом и списком действий (создать/изменить/удалить) над записями песен.
- **Журнал безопасности**: записи об отклонённых попытках (время, источник, причина отказа) без содержимого запроса.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Ни один запрос к эндпоинту исполнения SQL, пришедший извне сети сервиса, не приводит к выполнению команд — 0 успешных внешних исполнений за 7 суток наблюдения после развёртывания.
- **SC-002**: Внутренняя синхронизация песен продолжает работать без потерь: 0 неуспешных обменов, вызванных этой правкой, за 7 суток; доля успешных обменов не ниже уровня до правки.
- **SC-003**: 100 % отклонённых попыток видны в журнале приложения в течение 60 секунд с момента запроса.
- **SC-004**: Ни один ответ клиенту не содержит текста ошибки базы данных — 0 таких ответов за 7 суток.
- **SC-005**: Автоматический регрессионный тест закрывает оба сценария (с ключом / без ключа) и падает на коде до правки.
- **SC-006**: Проверки проекта проходят полностью (линтеры, guard-ы, сборка) — 7 из 7.

## Assumptions

- Эндпоинт по замыслу внутренний (server-to-server двуx-БД синхронизации), поэтому изменение его периметра не ломает публичные функции сайта.
- Защита строится на уже принятом в проекте образце: общий секрет в заголовке `X-Internal-Secret` + сетевой фильтр по адресам (как у внутренних портов базы и хранилища).
- Внутренний клиент синхронизации запускается на админской машине — это единственный легитимный вызывающий; сетевой контур закрывает маршрут для всех прочих адресов тем же способом, каким уже закрыты внутренние порты 5433 и 9000 (список адресов + `deny all`).
- Адрес админской машины у провайдера плавает: по решению владельца (2026-10-07) в списке остаются все три исторических адреса, чтобы при смене адреса доступ не терялся. Пока новый адрес не добавлен, синхронизация с этого адреса не пройдёт — это принятый операционный риск, компенсируемый вторым рубежом (внутренний ключ) и своевременным добавлением адреса.
- Значение секрета задаётся при развёртывании через существующий механизм настройки; в репозиторий секрет не попадает.
- Существующая транзакционность применения действий и семантика кодированного слова слова не меняются (см. отдельную задачу по транзакциям).
- Развёртывание на боевой контур — отдельное решение владельца; до него правка проверяется в тестовом окружении.
