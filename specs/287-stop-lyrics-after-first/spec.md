# Feature Specification: 287 — Прекращение извлечения текста после первого успеха + ручная попытка по ссылке

**Feature Branch**: `287-stop-lyrics-after-first`

**Created**: 2026-08-31

**Status**: Draft

**Input**: User description: "Задача - модификация поиска текста песни в интернете.
Сейчас алгоритм следующий: отправляется поисковый запрос, в результате получается список ссылок. Далее по каждой ссылке получается страница. Если страница получена - пытаемся из неё извлечь текст песни. Если текст песни удалось получить - запоминаем его. В качестве найденного текста для песни берем первый удачно найденный текст, но при этом продолжаем искать и хранить все остальные тексты. Далее в SubsEdit можно открыть модалку "Поиск текста песни в интернете", посмотреть найденные ссылки и для каждой ссылки полученный из неё текст песни (если удалось получить текст).
Необходима модификация: после того, как найден первый текст песни - дальше уже не пытаемся получить текст. То есть если для песни найдено 20 ссылок и на 2-й ссылке удалось получить текст, то текст будет только для этой ссылки, а для остальных не будет, но ссылки остаются. В модалке "Поиск текста песни в интернете" только вторая ссылка будет с текстом, а остальные "серые" и пусты. Но для каждой ссылки нужно добавить возможность попытки получения текста - но только для этой ссылки. Добавить этот функционал на кнопку "Получить текст по ссылке", разместить её под кнопкой "Открыть на сайте"."

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Алгоритм поиска останавливается на первой успешной ссылке (Priority: P1)

Администратор в админке на странице песни нажимает кнопку «Найти текст песни в интернете». Backend отправляет поисковый запрос и получает, например, 20 ссылок-кандидатов. Начиная с первой ссылки, последовательно пытается получить страницу и извлечь из неё текст песни. **Как только для одной из ссылок успешно извлечён непустой текст, обработка остальных ссылок ПРЕКРАЩАЕТСЯ** — больше ни для одной ссылки не делается HTTP-запрос за страницей и не запускается парсинг. В результате в таблице результатов поиска для 20 ссылок только у одной (той, на которой первой удалось извлечь текст) поле «текст песни» будет заполнено, а у остальных 19 ссылок будет сохранён только URL, без текста и без обращения к исходной странице.

**Why this priority**: основная модификация, которую явно запросил пользователь; снижает нагрузку на исходные сайты и время поиска; минимизирует «шум» в БД и в UI модалки.

**Independent Test**: выбрать песню без текста; запустить «Найти текст песни в интернете» с движком, который гарантированно находит несколько рабочих ссылок (например, FOURGET). После завершения поиска открыть модалку «Поиск текста песни в интернете»: визуально и через БД убедиться, что только у одной ссылки заполнено поле `text`, у остальных `text = ""`. Проверить логи backend: после первого успешного `extractLyricsFromUrl` больше нет HTTP-запросов `GET` к доменам остальных ссылок.

**Acceptance Scenarios**:

1. **Given** песня без текста и 20 ссылок-кандидатов, найденных Яндексом/FOURGET, **When** запускается поиск текста, **When** обработка дошла до 2-й ссылки и для неё успешно извлечён непустой текст, **Then** обработка прекращается, для 1-й ссылки (если для неё ещё не было HTTP-запроса) и для всех последующих 3..20 ссылок НЕ делается HTTP-запрос `GET` за HTML страницы и НЕ запускается парсинг; в БД сохраняется ровно одна запись с непустым `text` (для 2-й ссылки), остальные 19 записей имеют `text = ""`.

2. **Given** песня без текста и 20 ссылок, для всех ссылок парсинг вернул пустой результат (не нашлось ни одной рабочей), **When** поиск завершается, **Then** все 20 ссылок имеют `text = ""`, в UI модалки все 20 ссылок отображаются «серым» (визуально выделены как ссылки без извлечённого текста), ни одна из них не подсвечена как «успешная».

3. **Given** песня без текста и 5 ссылок, **When** для 1-й ссылки успешно извлечён текст, **Then** ссылки 2..5 имеют `text = ""` и НЕ делают HTTP-запросов; повторный клик по ссылке 4 в UI запускает HTTP-запрос ТОЛЬКО к этой 4-й ссылке (см. US3).

### User Story 2 — В модалке только одна ссылка содержит текст, остальные «серые» (Priority: P1)

В модалке «Поиск текста песни в интернете» в SubsEdit список найденных ссылок выглядит так: ссылка, для которой был успешно извлечён текст песни, визуально отличается от остальных (например, белый фон / выделение как сейчас для ссылок с непустым `text`); все остальные ссылки отображаются «серыми» (визуально приглушённый стиль + пустое поле текста справа). При клике на любую из «серых» ссылок в правой колонке поле с текстом остаётся пустым.

**Why this priority**: визуальное отображение результата US1; без него пользователь не понимает, для каких ссылок был реальный поиск, а для каких — нет.

**Independent Test**: открыть модалку «Поиск текста песни в интернете» для песни, по которой только что отработал поиск; убедиться визуально, что только одна (первая успешная) ссылка имеет визуальное выделение «успешная», остальные — «серые»; клик на любую «серую» ссылку НЕ показывает текст.

**Acceptance Scenarios**:

1. **Given** модалка открыта для песни с одной успешно извлечённой ссылкой и N ссылками без текста, **When** пользователь смотрит на список ссылок, **Then** ровно одна ссылка визуально выделена как «с текстом» (например, белый/светлый фон), все остальные N ссылок — «серые» (приглушённый фон/стиль); правая колонка с текстом изначально пуста.

2. **Given** модалка открыта, **When** пользователь кликает на «серую» ссылку, **Then** правая колонка остаётся пустой (визуально показывает пустую `<textarea>`), кнопки «Открыть на сайте» и «Получить текст по ссылке» доступны для этой ссылки.

3. **Given** модалка открыта и пользователь кликнул на «успешную» ссылку, **When** правая колонка показывает ранее извлечённый текст, **Then** кнопка «Получить текст по ссылке» либо скрыта, либо заблокирована (текст уже есть — повторная попытка не имеет смысла).

### User Story 3 — Кнопка «Получить текст по ссылке» запускает попытку только для одной ссылки (Priority: P1)

В модалке «Поиск текста песни в интернете», в правой колонке (где показывается текст текущей выбранной ссылки), под существующей кнопкой «Открыть на сайте» появляется новая кнопка «Получить текст по ссылке». При клике на эту кнопку выполняется попытка извлечения текста только для той ссылки, которая сейчас выбрана в левом списке. Если извлечение успешно — поле с текстом заполняется найденным текстом, ссылка визуально переходит в состояние «с текстом», кнопка «Получить текст по ссылке» становится недоступной (либо скрывается). Если извлечение неуспешно — пользователь видит уведомление об ошибке/предупреждение, ссылка остаётся «серой», поле с текстом остаётся пустым, кнопка остаётся доступной для повторной попытки.

**Why this priority**: основной сценарий «ручной fallback» — пользователь может сам выбрать любую ссылку и попробовать получить из неё текст, не дожидаясь автоматического перебора.

**Independent Test**: открыть модалку для песни с результатами поиска, выбрать «серую» ссылку в левом списке, нажать «Получить текст по ссылке»; убедиться, что запрос отправляется только на backend и в ответ приходит либо текст (тогда правая колонка заполняется, ссылка становится «успешной»), либо ошибка (тогда правая колонка остаётся пустой, ссылка остаётся «серой»). Проверить в логах backend, что HTTP-запрос ушёл ровно к одному URL.

**Acceptance Scenarios**:

1. **Given** модалка открыта, в списке «серых» ссылок пользователь выбрал одну, **When** нажата кнопка «Получить текст по ссылке», **Then** backend получает запрос «извлечь текст по конкретной ссылке» (searchResultId или url+songId), выполняет HTTP-запрос за страницей, парсит, сохраняет результат в БД (`text` либо заполняется, либо остаётся пустым + сообщение об ошибке), возвращает обновлённую запись; UI обновляется — либо правая колонка показывает текст, либо показывается уведомление об ошибке.

2. **Given** для выбранной ссылки текст успешно извлечён (вручную), **When** пользователь снова кликает на эту же ссылку, **Then** кнопка «Получить текст по ссылке» либо скрыта, либо disabled (повторно извлекать нечего).

3. **Given** для выбранной ссылки попытка извлечения неуспешна (HTTP-ошибка / пустой результат), **When** пользователь снова нажимает «Получить текст по ссылке», **Then** кнопка остаётся доступной, можно повторить попытку (например, после таймаута).

---

### User Story 4 — Совместимость с «Поиском текстов для всех песен» и фоновым воркером (Priority: P2)

Изменение алгоритма «остановка после первого успеха» применяется ко всем трём движкам поиска (YANDEX_SYNC, YANDEX_ASYNC, SEARXNG/FOURGET) и к фоновому воркеру `KaraokeProcessWorker`, который доводит YANDEX_ASYNC до завершения. После изменения для каждой песни в БД хранится: список всех найденных ссылок, и только у одной (первой успешной) — заполненный `text`. Поведение для админки «Найти тексты для всех песен» и для других существующих сценариев (Pass 278, Pass 281) сохраняется: `Song.sourceText` подставляется из первого непустого `text`, параллельно найденные `key`/`bpm`/URL'ы стемов не перезатираются.

**Why this priority**: регрессионная гарантия — изменение должно покрывать все пути одной правкой; иначе пользователь увидит разное поведение в зависимости от того, каким движком искал.

**Independent Test**: повторить US1 для каждого из 4 движков + фоновый YANDEX_ASYNC: результат одинаков — текст только у одной ссылки, остальные «серые». Повторить Pass 278 и Pass 281 acceptance scenarios — `key`/`bpm` сохраняются.

**Acceptance Scenarios**:

1. **Given** песня с уже найденным `key="Am"`/`bpm=120`, **When** запускается любой из 4 движков через `/api/songs/searchsongtextall`, **Then** для песни найдено N ссылок, у одной — `text`, у остальных `text = ""`; `Song.sourceText` подставлен из первой успешной; `key="Am"`/`bpm=120` сохранены.

2. **Given** YANDEX_ASYNC стартовал, воркер `KaraokeProcessWorker` доводит его до `done=true`, **When** обрабатываются результаты, **Then** алгоритм «остановка после первого успеха» применяется (только одна запись с `text`).

---

### Edge Cases

- **Все ссылки «не нашли» текст** (например, домен вернул HTTP 200, но текста на странице нет): все N ссылок имеют `text = ""`, ни одна не помечена как «успешная», модалка показывает N «серых» ссылок; пользователь может вручную попробовать каждую через «Получить текст по ссылке».
- **HTTP-ошибка при автоматической обработке** (страница не получена): для этой ссылки `text = ""` (как сейчас — поведение сохранено); HTTP-запрос НЕ повторяется автоматически (пользователь может повторить вручную через кнопку «Получить текст по ссылке»).
- **HTTP-ошибка при ручной попытке** (пользователь нажал «Получить текст по ссылке»): пользователь видит уведомление об ошибке, `text` остаётся пустым, кнопка остаётся доступной для повторной попытки.
- **Пользователь нажал «Получить текст по ссылке», а в этот момент другой запрос уже прислал текст для этой же ссылки**: запрос идемпотентный — результат не хуже, чем был; защита от race condition через reload-from-db-before-save (как в Pass 281) при записи `Song.sourceText`.
- **Между ручными попытками пользователь переключает выбор ссылок**: предыдущие успешные результаты для уже обработанных ссылок сохраняются в БД; правая колонка показывает текст выбранной сейчас ссылки.
- **Песня удалена между выбором ссылки в UI и кликом «Получить текст по ссылке»**: backend возвращает ошибку «песня не найдена», UI показывает уведомление и закрывает модалку.

## Requirements *(mandatory)*

### Functional Requirements

**Алгоритм поиска (FR-1xx)**

- **FR-001**: При автоматическом поиске текста для песни (любой из движков: YANDEX_SYNC, YANDEX_ASYNC, SEARXNG, FOURGET; а также фоновое завершение в `KaraokeProcessWorker`), после того как для очередной ссылки успешно извлечён НЕпустой текст, обработка остальных ссылок ПРЕКРАЩАЕТСЯ — больше НЕ выполняется HTTP-запрос `GET` за страницей и НЕ запускается парсинг для остальных ссылок из списка. Условие «успешного извлечения» — результат парсинга не `null` и не пустая строка после `trim()`.
- **FR-002**: Для каждой необработанной ссылки всё равно создаётся запись в таблице результатов поиска с заполненным `url`, но с пустым `text` и `html = ""`. Это нужно, чтобы модалка могла показать весь список ссылок, а не только «успешную».
- **FR-003**: Поведение сохранения в БД (создание записи результата поиска для каждой ссылки — успешной и неуспешных) сохраняется; записи создаются ДО перехода к следующей ссылке, чтобы при возникновении ошибки посередине уже обработанные ссылки не потерялись.
- **FR-004**: Алгоритм применяется единообразно во всех 4 точках вызова автоматического поиска: `UtilsAI.getYandexSearch` (YANDEX_SYNC), `UtilsAI.getYandexSearch` + `KaraokeProcessWorker` (YANDEX_ASYNC завершение), `UtilsAI.getLyricsSearchViaSearchTool` (SEARXNG/FOURGET). Правка делается в общем месте так, чтобы один и тот же алгоритм применялся во всех путях (НЕ дублировать логику в 4 функциях).

**Подстановка в `Song.sourceText` (FR-2xx)**

- **FR-010**: Поведение подстановки найденного текста в `Song.sourceText` сохраняется: из списка непустых `text` берётся первый, проверяется `song.haveSourceText` (Pass 020), затем применяется reload-from-db-before-save (Pass 281). Это всё делается ровно один раз — на первой успешной ссылке — и далее не повторяется, потому что других непустых `text` просто нет.
- **FR-011**: Семантика «первая успешная ссылка — это и есть применённый текст» сохраняется: для админских сценариев Pass 020 и Pass 281 поведение не меняется.

**Ручная попытка по ссылке (FR-3xx)**

- **FR-020**: Должен быть новый backend-эндпоинт «получить текст по конкретному результату поиска», который принимает идентификатор записи результата поиска (или комбинацию `songId + url`) и выполняет попытку извлечения текста только для этой ссылки. Результат (успех с текстом / неуспех) сохраняется в БД и возвращается в UI.
- **FR-021**: При ручной попытке HTTP-запрос за страницей и парсинг выполняются ровно один раз для указанной ссылки; никакого перебора остальных ссылок нет (это ключевое отличие от автоматического режима).
- **FR-022**: Если для ссылки уже есть непустой `text` (ранее успешно извлечённый — автоматически или вручную), ручная попытка НЕ выполняет HTTP-запрос и НЕ перезаписывает `text` (защита от лишних обращений к исходному сайту); эндпоинт возвращает текущее состояние записи.
- **FR-023**: При ручной попытке если HTTP-запрос за страницей или парсинг вернули пустой результат — `text` остаётся пустым, эндпоинт возвращает запись с пустым `text` + признак «неуспех» (например, HTTP 200 с пустым `text` + сообщение в ответе, ИЛИ HTTP 4xx/5xx с описанием ошибки). UI показывает уведомление.
- **FR-024**: Ручная попытка НЕ подставляет текст в `Song.sourceText` (это остаётся прерогативой кнопок «Вернуть текст и выйти» / «Скопировать текст и выйти»); она только обновляет запись результата поиска.

**UI модалки «Поиск текста песни в интернете» (FR-4xx)**

- **FR-030**: В модалке визуальное состояние ссылок должно соответствовать их состоянию в БД: ссылка с непустым `text` — визуально выделена (как сейчас — белый/светлый фон); ссылка с пустым `text` — «серая» (приглушённый фон/стиль). Это поведение уже реализовано в текущем коде через `backgroundColor` (`SearchTextResultsTable.vue:6-9`) — должно сохраниться без изменений.
- **FR-031**: В правой колонке модалки (где показывается текст выбранной ссылки) под существующей кнопкой «Открыть на сайте» добавляется новая кнопка «Получить текст по ссылке». Размещение — непосредственно под «Открыть на сайте», в одной группе с ней (визуально — кнопки рядом или подряд).
- **FR-032**: Кнопка «Получить текст по ссылке»:
  - Доступна, когда выбрана «серая» ссылка (с пустым `text`);
  - Либо скрыта, либо disabled, когда выбрана «успешная» ссылка (с непустым `text`) — на усмотрение реализации, главное — не позволять повторно обращаться к сайту без пользы;
  - Не отображается, когда в модалке вообще нет ссылок (поиск ещё не завершён или результаты удалены).
- **FR-033**: После клика на «Получить текст по ссылке»:
  - Кнопка показывает состояние «загрузка» (например, `disabled` + изменённый текст/иконка), пока идёт запрос;
  - В случае успеха — правая колонка заполняется текстом, ссылка в левом списке переходит в состояние «с текстом» (визуально), кнопка становится недоступной для этой ссылки;
  - В случае ошибки — показывается уведомление (toast / alert / сообщение в правой колонке), ссылка остаётся «серой», кнопка снова доступна для повторной попытки.
- **FR-034**: Список ссылок в модалке обновляется после ручной попытки (если ссылка стала «успешной» — она визуально меняется на «с текстом» без перезагрузки модалки).

**Существующее поведение не меняется (FR-5xx)**

- **FR-040**: Кнопка «Открыть на сайте» в правой колонке сохраняется; её поведение (открыть URL в новой вкладке) не меняется.
- **FR-041**: Кнопки «Вернуть текст и выйти» / «Скопировать текст и выйти» / «Искать заново» / «Удалить результаты поиска» / «Выйти» сохраняются без изменений.
- **FR-042**: Алгоритм `applyFoundLyricsIfMissing` (Pass 281, `UtilsAI.kt:142`) сохраняет свою защиту reload-from-db-before-save; для автоматического поиска он по-прежнему вызывается ровно один раз с одним непустым текстом.
- **FR-043**: Поведение `forceResearch=true` (кнопка «Искать заново») сохраняется — удаляются все `SearchResult` и `SearchAsync` для песни, запускается новый поиск.

### Key Entities

- **SearchAsync** (без изменений в схеме): родительская запись поискового запроса для песни; хранит `song_id`, `query`, `raw_data` (список URL), `done`.
- **SearchResult** (без изменений в схеме): запись результата обработки одной ссылки; хранит `search_async_id`, `song_id`, `url`, `html`, `text`, `wrong_result`. Изменение логики — НЕ схемы: для большинства ссылок `text` остаётся пустым, `html` тоже остаётся пустым (т.к. HTTP-запрос не делается).
- **Song** (без изменений): как только `applyFoundLyricsIfMissing` подставил `sourceText` из первой успешной ссылки, поведение Pass 020 / Pass 281 сохраняется.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: При автоматическом поиске для песни, у которой движок вернул N ссылок, в БД создаётся ровно N записей `tbl_search_results`, но ровно 1 запись (первая успешная) имеет непустой `text`. Для остальных N-1 записей `text = ""` и `html = ""`.
- **SC-002**: HTTP-запросы к исходным сайтам при автоматическом поиске прекращаются сразу после первого успешного извлечения текста. Проверяется через логи backend: после строки «успешного извлечения» нет ни одного `GET <url>` для остальных URL из списка.
- **SC-003**: Время автоматического поиска сокращается пропорционально количеству ссылок после первой успешной. Для типичного сценария (20 ссылок, успех на 2-й) время HTTP-этапа сокращается примерно в 10 раз по сравнению с полным перебором.
- **SC-004**: Модалка «Поиск текста песни в интернете» после автоматического поиска визуально показывает 1 ссылку «с текстом» и N-1 «серых» ссылок. Проверяется визуально + через инспектор DOM (backgroundColor/стиль ссылок).
- **SC-005**: Клик на «серую» ссылку НЕ показывает текст в правой колонке. Правая колонка пуста, кнопка «Получить текст по ссылке» доступна.
- **SC-006**: Клик на «Получить текст по ссылке» отправляет ровно один запрос на backend, обрабатывающий ровно одну ссылку. После успеха — правая колонка заполняется текстом, ссылка становится «успешной», кнопка становится недоступной. После ошибки — уведомление, ссылка остаётся «серой», кнопка доступна для повторной попытки.

## Assumptions

- **A-1**: Записи `tbl_search_results` для «серых» ссылок остаются в БД (с пустым `text`/`html`) — это даёт пользователю возможность вручную попробовать любую из них через кнопку «Получить текст по ссылке». Это сознательное решение: оставить «след» всех найденных ссылок, а не только успешной.
- **A-2**: Под «успешным извлечением» понимается: HTTP-запрос за страницей вернул непустой HTML, парсер нашёл в HTML непустой текст после `trim()`. Это соответствует текущему поведению (полю `text` присваивается результат, если он непустой после `trim`).
- **A-3**: Поведение «поиск возобновляется с того же места при повторном открытии модалки» (т.е. если поиск был запущен и завершён — модалка показывает его результаты, а не запускает заново) сохраняется; это уже работает через `searchAsyncList` (берётся последний `done=true`).
- **A-4**: Условие «остановка после первого успеха» НЕ применяется к фоновому воркеру `KaraokeProcessWorker` отдельно от `getYandexSearch` — это один и тот же код-путь (`SearchResult.getSearchResultsForSearchAsync` в `UtilsAI.kt:421` для YANDEX_SYNC и в `KaraokeProcessWorker.kt:898` для YANDEX_ASYNC). Правка делается в общем месте `getSearchResultsForSearchAsync` (либо в эквивалентной общей функции, через которую идут оба пути), чтобы оба пути получили изменение одной правкой.
- **A-5**: Под «первой успешной ссылкой» в контексте автоматического режима понимается первая по порядку в списке URL (как их вернул движок). Никакой ранжировки «по качеству» или «по длине текста» не делается — пользователь явно сказал «первый удачно найденный».
- **A-6**: Кнопка «Получить текст по ссылке» работает ТОЛЬКО в модалке «Поиск текста песни в интернете» (внутри `SubsEdit`). Никаких новых кнопок в других местах админки не добавляется.
- **A-7**: Backend-эндпоинт для ручной попытки возвращает обновлённую запись `SearchResult` (с новым `text` либо с тем же пустым + признак ошибки). UI использует этот ответ для обновления списка ссылок и правой колонки без полной перезагрузки модалки.
- **A-8**: Правка в backend делается так, чтобы не сломать существующие эндпоинты (`/api/song/searchasync`, `/api/song/searchresult`, `/api/song/deletesearchresults`, `/api/songs/searchsongtextall`) — только их поведение становится «остановка после первого успеха», что соответствует обратно совместимому изменению для всех существующих клиентов (админка ожидает, что в `text` будет лежать первый успешный).
