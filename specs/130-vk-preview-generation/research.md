# Research: Предварительная подготовка превью перед публикацией в ВК

**Feature**: `specs/130-vk-preview-generation`
**Date**: 2026-08-03

## 1. Текущий поток публикации

- `VkAutoPublishService.publishToVk` принимает публикации типов `AIR` и `PREMIUM`, сначала проверяет готовность песни и идемпотентность по `Song.idVk`.
- Если шаблон содержит `{demoVideo}`, публикация проходит через готовый MP4 и `VkApiClient.sendPostWithVideo`; в конце всё равно вызывается `wallPost`.
- Если видео не требуется, `VkAutoPublishService.publishTextOnly` сразу вызывает `VkApiClient.wallPost` с текстом и ссылкой.
- Автоматический `AIR`-путь запускается `VkAutoPublishScheduler`, ручные `AIR`/`PREMIUM`-публикации входят через существующие endpoint'ы `ApiController`.
- `VkApiClient.wallPost` публикует текст и ссылку через VK API; формат текста и параметры VK API менять для этой фичи не требуется.

## 2. Источник задержки превью

- `PublicOgSongController.ogSongHtml` (`karaoke-web/.../PublicOgSongController.kt`) отдаёт HTML для парсера VK и указывает картинку `/api/public/song-vk-image/{id}`.
- `PublicApiController.songVkImage` (`karaoke-web/.../PublicApiController.kt`) при отсутствии кэша загружает изображения альбома и автора из MinIO, собирает PNG 537×240 и записывает его в `/tmp/vk_<id>.png`.
- При последующих обращениях уже готовый файл читается с диска контейнера `karaoke-web`.
- `karaoke-app` и `karaoke-web` работают в разных контейнерах и на разных окружениях; локальный диск admin-машины не является диском публичного веба.
- Вызов HTML-эндпоинта сам по себе не прогревает PNG, поэтому прогрев должен обращаться непосредственно к `song-vk-image`.

## 3. Решение: синхронный prewarm существующего endpoint'а

**Decision**: Перед фактическим созданием поста `karaoke-app` синхронно вызывает существующий публичный URL изображения песни. Публикация продолжается только после успешного ответа, подтверждающего готовый PNG.

**Rationale**:

- Используется тот же URL, который затем получает VK, поэтому проверяется именно нужная публичная поверхность.
- Ответ endpoint'а приходит после записи результата на диск; следующий запрос VK попадает в быстрый путь чтения кэша.
- Не требуется новый публичный endpoint, миграция БД, загрузка фото в VK или отдельный user-token.
- Один общий шаг можно применить к `AIR` и `PREMIUM`, а также к веткам с видео и без видео.

**Validation rules**:

- HTTP-редиректы не следовать автоматически: ответ 3xx считается ошибкой готовности, чтобы fallback-логотип не был ошибочно принят за превью песни.
- Успех: HTTP 200, ненулевое тело, `Content-Type` изображения и успешное декодирование как PNG.
- Ошибка: тайм-аут, сетевое исключение, HTTP-код не 200, пустое тело, не-изображение или повреждённый PNG.
- Использовать ограниченное число попыток и отдельный тайм-аут prewarm; не переиспользовать длительный backoff `wall.post` для прогрева.
- Повторный prewarm допустим: сам web-endpoint возвращает существующий кэшированный файл без повторной сборки.

## 4. Настройки и откат

**Decision**: Добавить в существующий список `KaraokeProperties` следующие настройки:

- `vkPreviewWarmupEnabled` — включатель нового шага, по умолчанию `true`.
- `vkPreviewWarmupUrl` — базовый URL endpoint'а, по умолчанию `https://sm-karaoke.ru/api/public/song-vk-image/`.
- `vkPreviewWarmupTimeoutMs` — тайм-аут одного запроса, по умолчанию 30000 мс.
- `vkPreviewWarmupMaxAttempts` — число попыток, по умолчанию 2.

**Rationale**: URL и тайм-аут нельзя оставлять неявными для раздельных admin/prod окружений; флаг позволяет быстро вернуть старое поведение без отката сборки. Значение URL является публичным доменом и не содержит секретов.

## 5. Состояние и ошибки

**Decision**: Не добавлять отдельную колонку и новый enum-state. Ошибка prewarm записывается через существующий `VkAutoPublishState.SEND_FAILED` и `vkAutoPublishLastError` с однозначным префиксом `preview prewarm failed:`; `VkAutoPublishResult.error` получает то же описание.

**Rationale**:

- Существующая JSON-область `player_readiness_flags` уже хранит состояние VK-публикации и участвует в UI без миграции.
- Новый state потребовал бы изменений во всех потребителях effective-state и дополнительных тестов, но не добавил бы ценности для первой проверки гипотезы.
- Префикс отделяет сбой подготовки картинки от ошибки VK API и сохраняется между тиками/перезапусками.
- При ошибке `wall.post` не вызывается, `Song.idVk` не заполняется, следующий ручной или плановый запуск может повторить попытку.

## 6. Идемпотентность и конкурентные вызовы

**Decision**: Сохранить существующую проверку `Song.idVk` и дополнить её процессной блокировкой по `song.id` вокруг критической секции публикации в `karaoke-app`. Вызов, увидевший состояние уже выполняющейся подготовки/публикации, не должен запускать второй финальный пост или второй рендер.

**Rationale**: Проверка пустого `idVk` сама по себе не защищает два одновременных вызова в одном процессе. Приложение запускается как один admin-процесс, поэтому process-local lock покрывает ручной endpoint и scheduler без новой БД-блокировки и без изменения схемы.

Состояние `RENDERING` должно по-прежнему позволять планировщику дождаться существующей задачи; оно не должно приводить к постановке ещё одной задачи. Callback `onRenderCompleted` должен повторно проверить `idVk` под той же блокировкой перед prewarm и публикацией.

## 7. Кэширование на web

**Decision**: Сделать запись нового PNG в `PublicApiController.songVkImage` атомарной для параллельных запросов: сначала записать временный файл рядом с целевым, затем заменить целевой файл.

**Rationale**: Prewarm гарантирует, что его собственный ответ дождался записи, но второй запрос может прийти параллельно. Атомарная замена исключает чтение частично записанного файла и делает FR-009 проверяемым.

Существующий путь `/tmp/vk_<id>.png` и формат 537×240 PNG сохраняются. При отсутствии исходных картинок ответ-редирект не считается успешным prewarm; fallback-логотип не маскируется под полноценное превью песни.

## 8. Область публикаций без связанной песни

**Decision**: Обычные `AIR`/`PREMIUM`-посты с известным `songId` являются областью фичи. Редкий legacy-путь `publishNewsWithoutVideo` для новости без `song_id` и без распознаваемого id песни сохраняет текущее текстовое поведение: у него нет корректного адреса изображения для прогрева.

**Rationale**: Нельзя подготовить превью песни, если публикация не связана с песней. Изменение такого пути потребовало бы отдельной модели изображения новости и выходит за цель проверки задержки генерации обложки песни.

Если в ссылке такой новости присутствует распознаваемый id песни, scheduler может использовать общий prewarm-помощник; если id нет, публикация остаётся legacy-исключением и документируется в per-feature файле.

## 9. Тестирование

**Decision**: Добавить офлайн-тесты нового HTTP-помощника с локальным JDK HTTP-сервером или подменяемым транспортом; полноценную проверку VK и prod-кэша оставить ручной.

**Rationale**: В проекте нет CI-безопасного покрытия VK-кода, а существующие интеграционные тесты требуют сети, credentials и браузера. Локальный тест позволяет проверить успех, редирект, ошибку HTTP, пустое/повреждённое тело и повторные попытки без внешних сервисов.

Минимальный набор:

1. 200 + корректный PNG → успех.
2. 3xx/302, 404 и 5xx → ошибка с причиной; публикация не должна начинаться.
3. Повреждённое или пустое тело → ошибка.
4. Первый вызов и повторный вызов → оба успешны, второй не требует изменения контракта.
5. Тайм-аут → ограниченное число попыток и понятная ошибка.

End-to-end проверка выполняется ручным запуском существующего endpoint'а публикации и проверкой поста в группе, логов `karaoke-app` и отсутствия `idVk` при сбое prewarm.

## 10. Рассмотренные альтернативы

| Вариант | Решение | Причина отказа или отложенного выбора |
|---|---|---|
| Прогрев через `/api/public/og/song` | Отказ | Endpoint отдаёт HTML и не генерирует PNG. |
| Генерация PNG на admin-машине | Отказ | Файл admin-контейнера недоступен публичному `karaoke-web` и VK. |
| Новый internal endpoint с shared secret | Отложен | Для первой проверки достаточно существующего публичного endpoint'а; новый secret и контракт увеличивают scope. |
| Загрузка фото через `photos.saveWallPhoto` | Отложен | Требует user-token с правом `photos` и отдельного VK OAuth/модерации; описано в `specs/123-vk-og-preview-fix`. |
| `wall.repost`/изменение OG-разметки | Отказ | Не проверяет гипотезу о задержке генерации и ранее не решило проблему бот-публикации. |
| Новая колонка состояния | Отказ | Существующего `player_readiness_flags` и `SEND_FAILED` достаточно; не нужны миграция и sync-флаги. |

## Итоговые разрешённые неизвестные

- **Где прогревать**: в `karaoke-app` непосредственно перед финальным VK-вызовом.
- **Что прогревать**: `/api/public/song-vk-image/{songId}`, не HTML OG endpoint.
- **Как определить успех**: HTTP 200 + валидный PNG без автоматического follow-redirect.
- **Что делать при ошибке**: не вызывать `wall.post`, сохранить `SEND_FAILED` и диагностическую ошибку.
- **Как хранить состояние**: существующий `player_readiness_flags`, без новых таблиц/колонок.
- **Как проверить**: офлайн-тесты помощника плюс ручной end-to-end сценарий; живые VK credentials в автоматические тесты не добавлять.
