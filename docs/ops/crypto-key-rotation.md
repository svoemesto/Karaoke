# Ротация ключа шифрования `CRYPTO_AES_KEY` / `CRYPTO_AES_IV` — `docs/ops/crypto-key-rotation.md`

**Дата документа**: 2026-10-26
**Статус**: ротация **выполнена**; ключ живёт только в окружении, запасного (захардкоженного) ключа в коде нет.
**Где мы**: `karaoke-app` (шифрует) и `karaoke-web` (расшифровывает) поднимаются **только** с ключом из окружения; без него сервис не стартует.

---

## 1. Что зашифровано и чем это опасно

`Crypto` (единственный класс, `karaoke-app/src/main/kotlin/com/svoemesto/karaokeapp/Crypto.kt`)
защищает **транзитные** полезные нагрузки между сервисами:

| Что шифруется | Где | Данные в БД? |
|---|---|---|
| `sqlToInsert` / `sqlToDelete` | `Utils.kt` → передаётся в `karaoke-web` (`MainController`), там расшифровывается и исполняется | **нет** — значение живёт только в пределах одного запроса |
| кодовое слово (`Crypto.WORDS_TO_CHECK`) | `Utils.kt` → `karaoke-web` (`MainController:399`) | нет |

**Следствие**: смена ключа **не требует миграции данных** — в БД зашифрованного ничего нет.

## 2. Текущее состояние

| Факт | Где проверить |
|---|---|
| Ключ и IV задаются только через `CRYPTO_AES_KEY` / `CRYPTO_AES_IV` в окружении | `deploy/do.env` на каждом хосте (файл вне git) |
| В коде значения ключа **нет**: константы legacy удалены, `Crypto.resolveOrThrow` бросает `CryptoConfigurationException`, если переменная не задана | `Crypto.kt` |
| Compose прокидывает переменные в контейнеры | `deploy/docker-compose-app.yml`, `deploy/docker-compose-web.yml`, `deploy/prod-single-host/docker-compose-web.yml` |
| `karaoke-web` использует **тот же** класс `Crypto`, что и `karaoke-app` | `karaoke-web/build.gradle.kts` → `implementation(project(":karaoke-app"))` |
| `karaoke-app` работает на админ-машине (`nsa-i9`), `karaoke-web` — на проде (`188.127.240.124`): ключ нужен **на обоих хостах и одинаковый** | `deploy/prod-single-host/` |
| Длина ключа (16/24/32 байта) и IV (16 байт) проверяется при старте | `Crypto.validateCurrentKeyMaterial()` → `CryptoConfigurationException` |
| Ошибки шифрования/расшифрования логируются через SLF4J; значения и ключи в лог не попадают | `crypto: encrypt failed op=encrypt` / `crypto: decrypt failed op=decrypt` |

**Инвариант**: значения ключа не должны появляться в репозитории, в переписке и в трекере.
Проверяется тестом `CryptoKeyConfigurationTest` (fail-fast + отсутствие значения ключа в
production-коде).

## 3. Как проверить, что всё в порядке

```bash
# 1) переменные видны в контейнере (ожидание: 2 на каждом хосте)
docker exec karaoke-app printenv | grep -c '^CRYPTO_AES'
ssh root@188.127.240.124 'docker exec karaoke-web printenv | grep -c "^CRYPTO_AES"'

# 2) предупреждения о legacy-ключе нет (ожидание: 0)
docker logs karaoke-app --since 10m 2>&1 | grep -c "falling back to LEGACY"

# 3) раундтрип шифрования: автосинхронизация шифрует на app, веб расшифровывает
docker logs karaoke-app --since 10m 2>&1 | grep "AutoOneClickSyncScheduler" | tail -2
# ожидание: SUCCESS (created/updated/moved > 0) и отсутствие ошибок расшифровки в логе веба
```

Если в логе `CRYPTO_AES_KEY is not set` — переменная не задана на этом хосте: см. § 5.

## 4. Процедура следующей ротации

Ротация нужна, если ключ утёк (например, попал в репозиторий или в переписку) или
истёк срок его использования. Шаги те же, что применялись 2026-10-26.

### Шаг 1. Сгенерировать значения

```bash
# Ключ: 32 байта (AES-256) → 32 символа; IV: 16 байт → 16 символов
python3 - <<'PY'
import secrets
print("CRYPTO_AES_KEY=%s" % secrets.token_hex(16)[:32])
print("CRYPTO_AES_IV=%s"  % secrets.token_hex(8)[:16])
PY
```

Значения **не** записывать в репозиторий, в переписку и в трекер — только в
`deploy/do.env` на соответствующих хостах (файл вне git).

### Шаг 2. Задать значения на хостах

- админ-машина (`nsa-i9`): `deploy/do.env` → `CRYPTO_AES_KEY=…`, `CRYPTO_AES_IV=…`;
- прод (`188.127.240.124`): тот же файл там же (значения **те же**);
- **вторая машина матрицы (`dev-pc`)**: там же — без неё приложение не стартует
  (fail-fast). Это единственное место, где легко забыть: проверьте до шага 3.

Проброс переменных в compose уже настроен — правки репозитория не нужны.

### Шаг 3. Перезапустить сервисы

Порядок важен: `karaoke-app` шифрует, `karaoke-web` расшифровывает. Между
перезапусками значения в операциях, которые идут через оба сервиса, не расшифруются
(запрос вернёт ошибку, данные не потеряются).

```bash
# админ-машина: очередь заданий — по Pass 380 (сначала остановить, потом перезапуск)
curl -s http://localhost:8898/process/stop
cd deploy && bash do.sh start_app
cd deploy && bash do.sh start_web

# прод: сначала web, чтобы расшифровка была готова раньше шифрования
cd deploy && bash do.sh start_web
```

### Шаг 4. Проверить

Проверки — § 3. Дополнительно: создать/отредактировать любую песню в админке и
убедиться, что правка сохранилась (это сквозной путь «шифрование → расшифровка →
запись в удалённую БД»).

## 5. Что делать при ошибке

| Симптом | Причина | Что делать |
|---|---|---|
| в логе `CRYPTO_AES_KEY is not set — ключ шифрования обязателен` | переменная не задана на этом хосте | задать в `deploy/do.env` хоста, перезапустить сервис |
| ошибка расшифровки в логе `karaoke-web` | на хостах **разные** ключи | сверить значения на обоих хостах (не выводя их в переписку) и перезапустить оба сервиса |
| `CryptoConfigurationException: CRYPTO_AES_KEY must be 16, 24 or 32 bytes long` | длина ключа неверна | перегенерировать по § 4 (шаг 1) |

Откат: если после ротации что-то сломалось, вернуть на обоих хостах **одни и те же**
прежние значения и перезапустить оба сервиса — миграции данных не требуется
(зашифрованного в БД нет).

## 6. Известный остаток

- legacy-ключ остался в **истории git** (публичный репозиторий). Переписывание истории
  (`git filter-repo`) — отдельная операция, ломает историю и все клоны; решает владелец.
  На безопасность это не влияет: legacy-ключ больше не используется ни одним сервисом.
- значения в `deploy/do.env` — вне git, но файл на хостах доступен владельцу машины;
  на проде права `600` (rw-------).
