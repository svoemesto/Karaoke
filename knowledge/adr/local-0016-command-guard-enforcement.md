# Local ADR-0016: Механизм enforcement для правил AI-агента — перехват команд, след и сверка процесса

* **Status**: Accepted
* **Date**: 2026-10-31
* **Deciders**: владелец Karaoke (решения 2026-10-31, карта KARAOKE-339)

> **Note**: this is a **local** ADR — describes a specific subsystem
> convention (vs global ADR-0001..0006 which describe project-wide decisions).

## Context

Hard Gates в `AGENTS.md` сформулированы как **инструкция агенту**: «контейнеры —
только через `deploy/do.sh`», «`git commit` — не в `master`», «merge только через
PR». Guard'ы репозитория (`tools/check-container-restart.sh` и соседние) смотрят
только в `git diff HEAD` — они ловят **намерение закоммитить**, а не **исполнение**
команды.

Разбор инцидентов (2026-09-15 … 2026-10-30) показал, что инструкция сама по себе
не удерживает:

1. **Исполнение без следа.** Агент выполнял запрещённое действие — и в журнале
   сессий DSH записи об этом не оставалось.
2. **Санкционированная команда без согласия.** `deploy/do.sh stop_app/start_app`
   — разрешённый путь, поэтому по тексту команды «без одобрения владельца» и
   «с одобрением» неразличимы. Это состояние, а не текст.
3. **Обход по форме.** `d''ocker`, `$(echo docker)`, запуск из скрипта-файла,
   `podman`, `systemctl`, `kill <pid>`, `docker exec` — правило, написанное как
   regex по тексту, обходится переписыванием текста.
4. **Процессные нарушения.** Пропуск шагов Plane-workflow (claim → add-comment →
   mark-review → close) вообще не оставлял следа: в Plane нет истории состояний
   (`history/`, `activities/` — 404).

По разбору подтверждено 8 нарушений (рестарт контейнера без согласия 2026-09-15;
5 git-гейт-случаев; обход `do.sh` 2026-10-26; `--no-verify`; force-push
2026-10-30). Отдельный прогон KARAOKE-341 показал, что журнал DSH полон, а
пропуск 2026-09-15 12:35 — исполнение **вне DSH**: канал вне сессий агента
наблюдаем частично.

**Следствие для формулировки цели.** Сделать нарушение «невозможным» нельзя:
исполнение в обход рантайма и подмена текста команды остаются доступными. Значит,
реалистичная цель — **остановить, спросить и оставить след**.

## Решения владельца (2026-10-31)

- **Д-1**: слой запрета — **host-плагин DSH** (`tools/pre-execute`,
  `ctx.tools.guard()`), режимы `deny` и `ask`, умолчание для новых правил — `ask`.
- **Д-2**: область — **только репозиторий Karaoke**; чужие `docker compose` и
  проекты других машин не затрагиваются.
- **Д-3**: закрыть класс «санкционированная команда без согласия» — правило
  `do-sh-consent` в режиме `ask` **плюс окно согласия**: владелец даёт согласие
  словом в чате, агент пишет `~/.dsh/policies/consent/<session-id>.json` **до**
  вызова `deploy/do.sh`; окно действует до конца сессии и **не** покрывает прямой
  `docker restart` и `docker compose` (иначе обход `do.sh` становится возможен
  «по окну»).
- **Д-4**: след — машинный журнал (`~/.dsh/ledger/agent-commands.ndjson`, NDJSON,
  12 полей, срок хранения без ограничения, ротация по размеру 50 МБ) и
  независимый сборщик (journald, shell-история, снимки docker). Секреты
  маскируются, пути и имена хостов сохраняются.
- **Д-5**: публичный record нарушения — задача Plane с меткой
  `type:governance-violation` (родитель — исходная задача), заводит **агент** по
  факту блокировки; **только** для режима `deny`.
- **Д-6**: процессные нарушения — сверка перед `close-issue`
  (`tools/check-tracker-workflow.sh`: claim, add-comment, mark-review). Сверка
  **не блокирует** закрытие: след + отчёт + тикет.
- **Д-7**: автоматическая **деградация агента не вводится** — след и record её
  заменяют.
- **Д-8**: границы перехвата **зафиксированы** (только инструмент `bash`);
  `auditd` не нужен.
- **Д-9**: критерий измеримости — «ноль срабатываний guard'а в наблюдаемом канале
  + ноль необъяснённых изменений состояния контейнеров и образов».

## Отвергнутые альтернативы

| Альтернатива | Почему отвергнута |
|---|---|
| `auditd` (системный аудит `execve`) | Требует root и постоянной нагрузки; текущих источников достаточно для критерия Д-9 |
| Автоматическая деградация агента (блокировка после N нарушений) | Сама станет источником ложных блокировок; след и record дают факты без риска |
| `fail-stop` на сверке перед `close-issue` | Сбой проверки блокировал бы работу; агент начал бы искать обход. Вместо этого — след + тикет |
| Тикет-нарушение заводит сам плагин | Понадобился бы токен Plane в конфигурации плагина; источник правды один — агент |
| Политика на все docker-контейнеры машины | Задевает чужие проекты; решение Д-2 — узко |
| Политика на gradle/docker-config/npm-пути | Уже чинится Pass 372–375 и pre-commit guard'ами; дублирование в рантайме даёт ложные блокировки |

## Последствия

**Хорошо**

- Нарушение команды останавливается **до** исполнения, а не обнаруживается после.
- У каждого вызова есть запись: время, команда, правило, вердикт, сессия,
  действовавшее согласие.
- Появляется **публичный record** в Plane, а не только локальный файл.
- Пропуск шагов workflow больше не остаётся незамеченным.

**Плохо / ограничения**

- Запрет по тексту **обходим** (Д-1 — это «остановить, спросить, оставить след»).
- Покрыт только `bash`; `terminal`, persistent-bash, PTC, CUA и внутренние
  действия MCP не проходят через перехват.
- Канал вне DSH наблюдаем частично: критерий Д-9 — утверждение о наблюдаемом, а не
  о всей машине.
- Plane не отдаёт историю состояний: «был ли mark-review» доказывается
  локальным журналом шагов; для задач, закрытых до появления журнала, —
  «не подтверждено», а не нарушение.
- Согласие владельца **не определяется по тексту** — его источник отдельный
  (окно согласия), и его нельзя выдать изнутри агента без прямого слова владельца.
