# Contract: проверка содержимого артефактов и автоматический повтор

**Feature**: `674-kortege-execution` · **Тип**: контракт финализаторов шагов
**Владелец**: `Utils.executeFinalizeDemucs`, `Utils.executeGetKeyBpmFromFile`, `model/Song.kt`
(`applyKeyBpmFromFileIfExists`, `getKeyBpmFromFile`), `tuple/ArtifactIntegrity.kt`
**Связанные FR**: FR-008, FR-009, FR-012, FR-013, FR-016

---

## 1. Принцип

`DONE` ставится только тогда, когда артефакт **принадлежит этой песне** и **создан из её файла**.
Факт существования файла и ненулевой размер — недостаточны (это и было «тихим успехом», `Utils.kt:4570`).
Проверка выполняется в финализирующем шаге (`runFunctionWithArgs`), а не в отдельном шаге, потому что
только финальный шаг видит весь кортеж.

## 2. Стемы (DEMUCS2 / DEMUCS5)

**Ожидаемый набор**: `accompaniment`, `vocals` (+ `drums`, `bass`, `other` для `DEMUCS5`).

Проверки для каждого стема (в порядке):

| № | Проверка | Провал |
|---|---|---|
| 1 | файл существует | `missingStem` |
| 2 | `length > 0` | `missingStem` |
| 3 | `|duration(stem) − duration(source)| ≤ 500 мс` | `foreignDuration` |
| 4 | `mtime(stem) ≥ mtime(source)` | `staleArtifact` |

- `duration(x)` — фактическая длительность по `ffprobe -v error -show_entries format=duration -of
  csv=p=0 <file>`; **не** кэш `Song.ms` (он может быть пуст или устарел).
- `source` — `song.fileAbsolutePath` (исходный файл песни), `duration(source)` измеряется в том же
  вызове; если измерить не удалось — проверка не проходит (fail-closed), шаг `ERROR`.
- Допуск 500 мс фиксирован спекой (SC-002) и не настраивается.
- Проверка 4 защищает от «артефакт старше источника» (edge case спеки) — такой артефакт не готов,
  но и не удаляется безвозвратно (см. §4).

**Итог:**

| Условие | Результат шага |
|---|---|
| все стемы прошли 1–4 | `true` → кортеж идёт дальше / завершается `DONE` |
| есть провал, это GPU-попытка (`retriedOnCpu != true`), источник жив | `false` + постановка **одного** CPU-retry-кортежа; исходный кортеж → `ERROR` с причиной «стемы не подтверждены, поставлен повтор без GPU» |
| есть провал, это уже повтор (`retriedOnCpu=true`) или источника нет | `false` → `ERROR` без нового повтора (FR-016) |

## 3. CPU-retry (FR-009)

| Свойство | Значение |
|---|---|
| Когда | только `DEMUCS2`/`DEMUCS5`, только после провала проверки §2, только при существующем источнике |
| Сколько | ровно один на кортеж (маркер `retriedOnCpu=true` в финальном шаге повтора) |
| Чем | новый кортеж (`createChain`), новый `scopeId`, свой `cp` источника первым шагом |
| Лейн/приоритет | лейн родителя, приоритет родителя |
| Зависимость от чужих файлов | отсутствует (не читает чужой `file.flac`) |
| Результат | повтор проходит те же проверки §2; второй повтор не ставится |

Повтор не «продолжает» исходный кортеж: исходный остаётся `ERROR` с причиной. Приёмка SC-001
считается по артефактам (см. план, риск №1).

## 4. Чужие и битые артефакты («не удалять безвозвратно»)

Если проверка не прошла и повтор исчерпан:

1. каждый негодный стем переименовывается в `<stem>.rejected-<yyyyMMdd-HHmmss>` в том же каталоге;
2. scope-каталог кортежа удаляется владельцем;
3. шаг возвращает `false` (кортеж `ERROR`);
4. `.rejected-*` живут до следующего успешного ремонта/уборки (janitor их не трогает — они в каталоге
   песни, а не в tmp; очистка — отдельным решением, вне рамок).

## 5. key/bpm (`KEY_BPM_FROM_FILE`)

### 5.1 Sidecar-отпечаток

Финальный шаг (`executeGetKeyBpmFromFile`) после успешного `mv` результата в
`<file> [key].json` пишет рядом `<file> [key].json.meta`:

```json
{
  "schema": 1,
  "scopeId": 1650737,
  "sourcePath": "<song>.flac",
  "sourceSize": 12345678,
  "sourceDurationMs": 275044,
  "sourceSha256HeadTail": "<sha256 первых 64 КиБ + последних 64 КиБ>",
  "computedAt": "2026-10-29T09:22:36Z"
}
```

`sourceSha256HeadTail` — дешёвый отпечаток содержимого: хэш конкатенации первых и последних 64 КиБ
файла (не полный хэш: файлы flac ~100 МБ, полный хэш на каждую проверку дорог).

### 5.2 Применение

| Вызов | Условие применения | При провале |
|---|---|---|
| `Song.applyKeyBpmFromFileIfExists()` | файл разбирается **и** sidecar есть **и** `sourceSize`/`sourceDurationMs`/`sourceSha256HeadTail` совпадают с текущим источником | `false` (не применяет); `createProcess` поставит кортеж пересчёта |
| `executeGetKeyBpmFromFile` | файл разбирается, `key` непустой, `bpm > 0` | `false` → кортеж `ERROR`, значения в песню **не** пишутся |
| `Song.getKeyBpmFromFile(reFind)` | файл есть; при отсутствии — `false` (перезапуск keybpmfinder **удалён**) | ошибка шага |

`parseKeyBpmFileOrNull` остаётся единственным парсером; sidecar читается отдельно и не ломает
формат `[key].json` (внешний контракт файла — `{"bpm": <int>, "key": "<str>"}`).

### 5.3 Запись в песню

Только через `saveToDbLocked()` (race с `SongEdit`), только после §5.2. Поля: `SongField.KEY`,
`SongField.BPM`. Это единственный путь, которым key/bpm пересекают границу двух БД (через
`SongSyncTarget`), поэтому «непроверенное» туда не попадает (FR-013/FR-017).

## 6. Периодическая проверка целостности

`ArtifactIntegrity.verifySong(songId)` — read-only:

| Находка | Условие |
|---|---|
| `missingStem` | ожидаемый стем отсутствует/пуст |
| `foreignDuration` | `|duration(stem) − duration(source)| > 500 мс` |
| `staleArtifact` | `mtime(stem) < mtime(source)` |
| `missingSidecar` | `[key].json` есть, `.meta` нет |
| `sidecarMismatch` | отпечаток в `.meta` не совпадает с источником |
| `emptyKeyBpm` | `[key].json` не разбирается, `key` пуст или `bpm ≤ 0` |

Отчёт: `PATH_TO_LOGS/artifact-integrity/<yyyy-MM-dd>.json` + последний отчёт в памяти +
SSE-уведомление. Правки запрещены (FR-014); ремонт — `SongArtifactRepairService` по явному вызову
(`dryRun=true` по умолчанию).

## 7. Границы

- Проверка не скачивает и не пересчитывает артефакты (кроме явного ремонта).
- Проверка не трогает прод-БД и не запускает docker.
- `ffprobe` вызывается с таймаутом; ошибка измерения — fail-closed (шаг `ERROR`), а не «успех».
