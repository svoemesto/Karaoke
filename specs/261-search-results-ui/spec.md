# Feature Specification: Исправление иконки плеера и редизайн строк результатов поиска

**Feature Branch**: `261-search-results-ui`
**Created**: 2026-08-28
**Status**: Draft
**Input**: User description: "В результатах поиска плеер всегда отображается недоступным, хотя песни в эфире и доступны - если перейти на страницу песни в этом можно убедиться. Так же таблицу результатов поиска нужно визуально сделать похожей на то, как песни отображаются в избранном и плейлистах: чёрная плашка с превью альбома и автора, потом название песни и под названием автор, год и альбом. А потом уже иконки плеера, избранного и плейлистов."

## Clarifications

### Session 2026-08-28

- Q: Должен ли новый layout строки применяться и к мобильному виду, или только к десктопной таблице? → A: Унифицированный row-паттерн через CSS — отдельная card-ветка удаляется, одна и та же разметка строки в десктопе и на мобилке.
- Q: Как поступить с источниками URL превью альбома/автора в строке поиска, раз в `SongPublicDto` этих полей сейчас нет? → A: Расширить `SongPublicDto` (добавить `albumPictureUrl` + `authorPictureUrl` по образцу `ZakromaPublicDto`), полное визуальное совпадение с `PlaylistEditView`, backend-дифф остаётся в одном DTO-файле (плюс `contentReady`).

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Иконка плеера в поиске отражает фактическую доступность (Priority: P1)

Гость (или зарегистрированный пользователь) вводит запрос в поиске на
`/search` и получает список песен. Для каждой песни, которая находится
«в эфире» (свободно доступна прямо сейчас), иконка плеера отображается
**зелёной** (полный доступ), как на странице песни и в «Закромах». Для
премиум-доступной, но не в-эфире песни — **золотой** (демо-фрагмент).
Для песни, контент которой ещё не готов — серой disabled. Сейчас иконка
всегда серая независимо от состояния — это вводит в заблуждение и
вынуждает переходить на страницу песни, чтобы убедиться в наличии плеера.

**Why this priority**: Главная жалоба пользователя, ломает базовый
сценарий «нашёл песню через поиск → открыл плеер» — сейчас иконка
системно врёт пользователю.

**Independent Test**: Открыть `/search`, ввести запрос, который возвращает
хотя бы одну песню «в эфире» (`freelyAvailableNow=true`), и хотя бы одну
«не в эфире» (готовую или нет). Визуально проверить: иконка плеера у
песни «в эфире» — зелёная (полный доступ); у готовой не-в-эфире — золотая
(демо); у неготовой — серая. Сейчас все три отображаются серой.

Тест проходит, если **все** песни «в эфире» из результатов поиска
получают зелёную иконку плеера, и одновременно ни одна «не в эфире»
или неготовая песня не ошибочно отображается зелёной.

**Acceptance Scenarios**:

1. **Given** пользователь ввёл запрос, вернувший песни со статусом
   «в эфире»,
   **When** он смотрит на результаты,
   **Then** **каждая** такая песня показывает **зелёную** иконку плеера
   (полный доступ), клик открывает плеер, как на странице песни.

2. **Given** запрос вернул готовую песню, не находящуюся «в эфире»,
   **When** пользователь смотрит на результаты,
   **Then** такая песня показывает **золотую** иконку (демо-фрагмент),
   клик открывает модалку оформления подписки/покупки — **не** серую.

3. **Given** запрос вернул песню с неготовым контентом,
   **When** пользователь смотрит на результаты,
   **Then** такая песня показывает серую disabled иконку (как сейчас) —
   это поведение сохраняется и НЕ является частью бага.

4. **Given** результаты поиска только что отрисовались,
   **When** состояние песни (in-air / готовность) меняется
   позднее (например, через механизм подписки или покупки),
   **Then** иконка плеера отражает новое состояние без перезагрузки
   страницы (контракт с «Закромами» уже есть).

5. **Given** пользователь кликает по зелёной/золотой иконке плеера
   в строке поиска,
   **When** открывается плеер,
   **Then** открывается именно тот `songId`, чей ряд был нажат
   (без путаницы индексов, без открытия «другой» песни).

### User Story 2 — Строка поиска выглядит как в плейлисте/избранном (Priority: P1)

Строка каждого результата в таблице поиска визуально совпадает со строкой
«Избранного»/плейлиста (`PlaylistEditView`): слева — чёрная плашка с
превью обложки альбома (квадрат 48×48) и превью автора (горизонтальная
карточка 5:2), далее — название песни, под ним — автор, год и альбом
(в одну строку через разделитель « - »), далее иконки действий
(плеер, корзина/премиум-иконка, избранное, плейлисты).

**Why this priority**: Единообразие UI между разделами поиска,
закромами и плейлистами — требование пользователя; снижает когнитивную
нагрузку и формирует узнаваемый паттерн навигации.

**Independent Test**: Открыть `/search` с непустыми результатами,
открыть «Избранное» (`/account/playlists/<favorites-id>`). Сравнить
визуально структуру строк: блок превью (чёрный, 2 картинки+заглушки),
блок с названием и подписью, набор иконок справа. Должны совпадать
по геометрии и стилю.

Тест проходит, если:
- в обеих местах слева одинаковый чёрный блок с превью (одного размера и формы);
- под названием песни видна строка «Автор» (или ссылки на закрома) « - год, альбом»;
- справа одинаковый набор действий.

**Acceptance Scenarios**:

1. **Given** пользователь открыл результаты поиска,
   **When** он смотрит на строку конкретной песни,
   **Then** строка содержит: (а) чёрную плашку с превью альбома и автора;
   (б) название песни крупным шрифтом; (в) под ним подпись «Автор - год, альбом»
   (как в плейлисте); (г) иконки действий справа.

2. **Given** превью альбома или автора отсутствуют в БД,
   **When** строка рендерится,
   **Then** вместо картинки показывается плейсхолдер («♪» для альбома,
   «👤» для автора), как в `PlaylistEditView`. Секция превью не
   «проваливается» (размер не схлопывается), плашка остаётся чёрной
   и скруглённой.

3. **Given** URL превью 404/timeout/network-error,
   **When** `<img>` ловит ошибку,
   **Then** рендерится тот же плейсхолдер без падения DOM и без
   перезапросов — поведение идентично `PlaylistEditView`.

4. **Given** пользователь нажимает на название песни в строке поиска,
   **When** срабатывает нативная навигация,
   **Then** открывается страница этой песни (`/song?id=<id>`); back-link
   из `SongView` ведёт на «Закрома» этого автора (как зафиксировано
   в спецификации 259).

5. **Given** пользователь нажимает на имя автора в строке поиска,
   **When** автор резолвится через кэш `authorTiles`,
   **Then** открывается `/zakroma/<authorId>` именно этого автора
   (как в спеке 259). Если автор удалён из БД — имя показывается
   обычным текстом без ссылки (Edge Case из спеки 259).

6. **Given** пользователь нажимает на иконку плеера / избранного /
   плейлиста в строке поиска,
   **When** срабатывает соответствующий обработчик,
   **Then** клик имеет тот же эффект, что и в существующей реализации:
   иконка плеера — открытие плеера; избранное — переключение закладки;
   плейлист — открытие модалки добавления в плейлист.

### User Story 3 — Все текущие функции поиска продолжают работать (Priority: P2)

Все сценарии, существующие в `SearchView` до изменения, продолжают работать:
- поиск по названию песни / автору / тексту (по любой комбинации);
- префилл формы из query-параметров (`?songName=...&author=...&text=...`)
  при первом заходе;
- модалка оформления подписки на конкретную песню при клике по золотой
  иконке плеера;
- подпись со сроками эфира («Будет в эфире с ДД.ММ.ГГГГ» / «В эфире до ДД.ММ.ГГГГ»);
- иконка «В корзину» (CartIcon) — для премиум-контента без активной
  подписки;
- состояние «Ничего не найдено»;
- два дизайна (classic/modern) — корректно используются CSS-переменные `--km-*`;
- мобильный вьюпорт (карточки) — новая вёрстка не ломает мобильный layout.

**Why this priority**: Изменение UI в поиске затрагивает много кода
в `SearchView`; важно, чтобы регресс по функциональности не появился.

**Independent Test**: Открыть `/search`, прогнать вручную все сценарии
выше. Каждый из них должен работать идентично до изменения.

**Acceptance Scenarios**:

1. **Given** URL `/search?author=<name>&songName=<title>`,
   **When** пользователь открывает страницу,
   **Then** форма предзаполнена и автоматически запускается поиск —
   идентично текущему поведению.

2. **Given** запрос вернул премиум-песню без подписки для не-премиум
   пользователя,
   **When** он смотрит на строку,
   **Then** отображается монета (`PremiumIcon`) и иконка «В корзину»
   (`CartIcon`); клик по золотой иконке плеера открывает модалку
   оформления подписки.

3. **Given** запрос не нашёл ни одной песни,
   **When** результаты отрисовываются,
   **Then** показывается блок «Ничего не найдено» (как сейчас).

4. **Given** дизайн переключён на `modern` (через `localStorage`),
   **When** пользователь просматривает результаты,
   **Then** цвета/фон/границы строк берутся из существующих
   CSS-переменных `--km-*`, без хардкода цветов.

---

### Edge Cases

- **Альбом/автор без превью** (`albumPictureUrl`/`authorPictureUrl`
  пустой или `null`): показывается плейсхолдер «♪» / «👤» в той же
  чёрной плашке. Размеры строки НЕ схлопываются.
- **Картинка не грузится** (404/timeout/CORS): `<img @error>` переключает
  на плейсхолдер, как в `PlaylistEditView`. Поведение идемпотентно
  (повторная ошибка не рекурсирует).
- **Длинное название песни** (>1 строки): название обрезается через
  overflow-ellipsis (одна строка, без расширения высоты).
- **Длинное имя автора/альбома** (>1 строки): подпись «Автор - год, альбом»
  обрезается overflow-ellipsis.
- **Пустой список результатов**: показывается «Ничего не найдено» (как сейчас);
  никакие строки не рендерятся.
- **Автор удалён из БД** (`author` есть в песне, но нет в `tbl_authors`):
  имя автора не становится ссылкой, отображается обычным текстом
  (контракт спеки 259).
- **Анонимный пользователь** (без токена): клик по иконке плеера
  открывает плеер «как есть» (плеер сам решает по токену); клики
  по избранному/плейлисту — переводят на login (как сейчас).
- **Премиум-пользователь**: иконки плеера показывают зелёную
  для всех готовых песен (как на странице песни), даже не в эфире.
- **Совпадение результатов со страницей одной песни**: пользователь
  кликнул название песни в поиске → попал на `/song?id=X` → нажал
  back-link → попал в «Закрома» автора (не назад в поиск) —
  обеспечено спецификацией 259 и не регрессирует.
- **Переключение темы (classic ↔ modern)** во время отображения
  результатов: ререндер берёт актуальные CSS-переменные.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Иконка плеера в каждой строке результатов поиска MUST
  показывать фактический статус доступа: зелёная — если песня готова
  И (в эфире ИЛИ премиум ИЛИ пользователь имеет подписку на эту
  песню); золотая (демо) — если песня готова, но полный доступ
  отсутствует; серая disabled — если песня не готова. Логика MUST
  совпадать с `PlayerIcon` для тех же входных данных (тот же компонент,
  та же формула в `isActive`/`isDemo`).
- **FR-002**: Данные `contentReady` MUST быть доступны во фронте для
  каждого элемента `searchResults` (один элемент массива = одна песня),
  чтобы `SearchView` мог передать их в `<PlayerIcon :content-ready-state>`.
  Источник — флаг готовности плеера, существующий на бэкенде
  (`Song.isContentReady`); источник НЕ должен дублироваться или
  рассчитываться независимо.
- **FR-003**: Данные `freelyAvailableNow` MUST корректно передаваться
  из бэка в каждом элементе `searchResults` без потери (сейчас контракт
  есть — должно продолжать работать после рефакторинга).
- **FR-004**: Визуальная структура строки результата поиска MUST
  совпадать со структурой строки `PlaylistEditView` (плейлист /
  «Избранное»): (a) чёрная плашка с превью альбома (квадрат) и
  превью автора (горизонтальная карточка), с margin/gap, как в
  `PlaylistEditView`; (b) название песни кликабельной ссылкой;
  (c) под ним строка «Автор - год, альбом» с разделителями
  по правилам спеки 259; (d) иконки действий в том же порядке
  (плеер, корзина или премиум-иконка — как сейчас, избранное,
  плейлисты). Структура MUST применяться одинаково на десктопе
  и мобильных вьюпортах — отдельной card-ветки в `SearchView`
  НЕ остаётся, одна разметка строки адаптивна через CSS
  (как в `PlaylistEditView`). Существующий `<div class="km-card">`
  mobile-fallback удаляется, desktop `<table>` заменяется на
  ту же семантически-нейтральную структуру (или используется
  один общий row-компонент, если это окажется чище).
- **FR-005**: Превью альбома и автора в строке поиска MUST иметь
  `@error`-фолбэк на плейсхолдер («♪» / «👤») внутри той же чёрной
  плашки, без падения DOM и без retry-цикла, идентично `PlaylistEditView`.
- **FR-006**: Превью альбома/автора MUST получать URL-ы из полей
  `albumPictureUrl` и `authorPictureUrl` DTO поискового ответа.
  Эти поля добавляются в `SongPublicDto` в рамках этой спеки
  (по образцу `ZakromaPublicDto`); до получения URL с бэка фронт
  показывает плейсхолдер «♪» / «👤» (FR-005). Никаких дополнительных
  HTTP-запросов на каждую песню ради превью в строке поиска не делается
  (загрузка идёт пакетом в составе `/api/public/songs`).
- **FR-007**: Название песни в строке поиска MUST быть кликабельной
  ссылкой на `/song?id=<songId>` (контракт спеки 259, FR-001/FR-008),
  не запускающей встроенный плеер.
- **FR-008**: Имя автора в строке поиска MUST быть кликабельной ссылкой
  на `/zakroma/<authorId>` при условии, что автор резолвится в
  `authorTiles`; иначе — отображаться как обычный текст (контракт
  спеки 259, FR-002/FR-006 и Edge Case).
- **FR-009**: Подпись «Автор - год, альбом» MUST использовать тот же
  формат и условные разделители, что и `PlaylistEditView`: год
  показывается только если `>0`; альбом показывается только если
  непустой; разделитель « - » показывается, только если есть год
  или альбом; запятая между годом и альбомом, только если оба
  присутствуют.
- **FR-010**: Иконка плеера MUST продолжать открывать плеер при клике
  (зелёная/золотая → открытие плеера / модалки; серая disabled →
  клик не имеет эффекта). Никаких других действий (например,
  переход на страницу песни) кроме текущих.
- **FR-011**: Иконка избранного и иконка добавления в плейлист MUST
  продолжать работать без регрессий (тот же `FavoriteIcon` /
  `PlaylistIcon`).
- **FR-012**: Монета/корзина (`PremiumIcon` + `CartIcon`) MUST
  показываться в тех же условиях, что и сейчас (только не-премиум
  пользователю + контент не в свободном доступе).
- **FR-013**: Подпись со сроками эфира («Будет в эфире с ДД.ММ.ГГГГ»
  / «В эфире до ДД.ММ.ГГГГ») MUST сохраняться ровно для тех песен,
  для которых она показывалась до изменения, и быть скрыта для остальных
  (контракт `showDate(song)` + `dateLabel(song)`).
- **FR-014**: Бэкенд MUST отдавать `contentReady`, `albumPictureUrl` и
  `authorPictureUrl` в составе ответа `/api/public/songs`. Эти поля
  заполняются в `SongPublicDto.fromSong(s: Song, ...)` через
  `s.isContentReady` и URL-строители по образцу `ZakromaPublicDto`.
  Поля опциональны для других потребителей (FR-015).
- **FR-015**: Никакие существующие эндпоинты / контроллеры бэкенда
  MUST не изменяться: единственный файл с правками —
  `karaoke-web/.../dto/SongPublicDto.kt` (расширение DTO).
  Другие DTO (`ZakromaPublicDto`, `SitePlaylistItemDto`,
  `SongAssignmentBriefDto` и пр.) MUST остаться без изменений;
  прочие потребители `/api/public/songs` (если есть) получают
  три новых опциональных поля без обязательной реакции.

### Key Entities *(include if feature involves data)*

- **SearchResult (UI, фронт)**: элемент массива `searchResults` в
  Vuex-сторе `songs`. Должен содержать (помимо существующих полей)
  три новых обязательных поля DTO-контракта: `contentReady: Boolean`
  — фактический статус готовности плеера, зеркало флага бэкенда
  `Song.isContentReady`; `albumPictureUrl: String` — URL превью
  обложки альбома (или пустая строка → плейсхолдер «♪»);
  `authorPictureUrl: String` — URL превью автора (или пустая
  строка → плейсхолдер «👤»). Все три — часть контракта DTO
  поиска после расширения в FR-014.

- **SongPublicDto (бэк)**: DTO поискового ответа
  (`/api/public/songs`). Расширяется тремя новыми полями
  (`contentReady: Boolean`, `albumPictureUrl: String`,
  `authorPictureUrl: String`), заполняемыми в
  `fromSong(s: Song, ...)` через `s.isContentReady` и URL-строители
  по образцу `ZakromaPublicDto` (Clarification Q2 → A, 2026-08-28).
  Default — `false` / `""` для null/пустого входа. Контракт:
  `contentReady = true` означает, что все файлы для онлайн-плеера
  залиты в хранилище; `albumPictureUrl`/`authorPictureUrl` — строки
  URL (или пустые), фронт мапит `""` на плейсхолдер `♪` / `👤`.

- **Song (бэк, существующая сущность)**: модель песни. Содержит
  персистентный флаг готовности, читаемый через `Song.isContentReady`
  — этот getter уже используется в `PublicPlayerController.stemsReady()`.
  Никаких изменений на уровне `Song` не требуется; используется
  существующий источник истины.

- **ZakromaAlbumSongPublicDto (бэк, существующий)**: DTO закромов,
  УЖЕ содержит `contentReady` (через `zakromaAlbumSong.contentReady =
  song.isContentReady`). Используется как «референсный контракт» —
  новый DTO поиска становится его единообразным зеркалом для песен,
  присутствующих в обоих ответах.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% песен «в эфире» (`freelyAvailableNow === true`) в
  результатах поиска показывают зелёную иконку плеера. Проверка:
  ручной сценарий — запрос из ≥3 песен, ≥2 из которых «в эфире»,
  → все «в эфире» песни имеют зелёную иконку, ни одна из них —
  серую.
- **SC-002**: 0 ложных срабатываний иконки плеера для неготовых песен:
  ни одна песня с `contentReady === false` не показывается с зелёной
  или золотой иконкой. Проверка: запрос из неготовых песен →
  все иконки серые.
- **SC-003**: 100% строк результатов поиска имеют структуру
  (чёрная плашка превью + название + подпись + иконки), идентичную
  строкам `PlaylistEditView`. Проверка: визуальное сравнение одной
  и той же песни в `/search` и `/account/playlists/<favorites-id>`
  — пиксельное соответствие блока превью, типографики названия,
  формата подписи, набора иконок.
- **SC-004**: Все ранее работавшие функции поиска (`showDate`,
  `showCoin`, `showCartIcon`, `onSubscribeClick`, префилл формы
  из query, пустой результат) продолжают работать без регрессий.
  Проверка: ручной сценарий по каждой функции; ни одна не сломалась.
- **SC-005**: Кликабельные ссылки названия песни и имени автора
  работают идентично спецификации 259: 100% названий ведут на
  `/song?id=<songId>`, 100% имён авторов, присутствующих в
  `authorTiles`, ведут на `/zakroma/<authorId>` корректного
  автора, удалённые авторы — без ссылки и без падения.
- **SC-006**: Минимальный дифф бэкенда: расширен один DTO
  (`SongPublicDto.fromSong`) и контроллер не изменён (новые
  поля попадают в JSON автоматически через Jackson). Проверка:
  `git diff karaoke-web/src/main/kotlin` показывает изменение
  только файла `SongPublicDto.kt` (3 новых поля: `contentReady`,
  `albumPictureUrl`, `authorPictureUrl`). Никаких миграций БД,
  изменений контроллеров, изменений других DTO
  (`ZakromaPublicDto`, `SitePlaylistItemDto` и пр.).
- **SC-007**: Нет деградации производительности на крупных
  результатах: запрос из 200 песен рендерится без видимой задержки
  (та же отзывчивость, что и сейчас — браузерный layout приемлем
  в обоих дизайнах). Проверка: ручной сценарий, 200 песен в
  `/search` → страница интерактивна без видимого «лага».

## Assumptions

- Иконка плеера в строке поиска использует ровно тот же `PlayerIcon`,
  что и в других местах (`ZakromaView`, `AuthorPlaylistView`,
  `PlaylistEditView`), с теми же проп-именами — никаких отдельных
  компонентов «для поиска» не заводим.
- Контракт полей DTO для поиска (`freelyAvailableNow`, `contentReady`,
  `onAir`, `alwaysFree`, `airTimestamp`, `datePublish`,
  `songPictureUrl`, `author`, `album`, `year`, `songName`,
  `songSubscriptionAvailable`, `id`) пополняется тремя новыми
  полями — `contentReady`, `albumPictureUrl`, `authorPictureUrl`
  (FR-014). Остальные поля бэкенда не трогаем.
- Существующая бизнес-логика «кто видит демо/полный доступ»
  (`isSongActiveForUser`) на фронте остаётся без изменений —
  единственная правка в `SearchView.vue` касается передачи
  правильных значений в уже существующий `PlayerIcon`.
- Модель строки `PlaylistEditView` (чёрная плашка с 2 превью,
  название ссылкой, подпись «Автор - год, альбом», набор действий
  справа) считается эталонной и переиспользуется без изменений
  по геометрии/стилю. Никакой новый CSS-стиль для строки поиска
  не пишется с нуля, только копируется (или выносится в общий
  компонент, если это окажется чище — выбор Implementation Notes).
- Картинки альбома/автора поставляются бэкендом в составе DTO
  `/api/public/songs` через новые поля `albumPictureUrl` /
  `authorPictureUrl` в `SongPublicDto` (FR-014, Clarification Q2 → A,
  2026-08-28). Строятся тем же URL-строителем, что и в
  `ZakromaPublicDto`. Дополнительных GET-запросов «на превью»
  ради рендера строки не делаем.
- Мобильный layout (карточки) на текущий момент существует в
  `SearchView.vue` как `<div class="km-card">` фолбэк
  (внутри `<table>` для десктопа и div-карточки для мобильного —
  по media-query). Редизайн унифицирует обе ветки через общий
  row-паттерн: одна разметка строки применяется в десктопе и
  на мобилке адаптивно через CSS, отдельная card-ветка
  удаляется (Clarification Q1 → A, 2026-08-28).
- Текущие CSS-переменные `--km-accent`, `--km-bg`, `--km-card`,
  `--km-border`, `--km-text`, `--km-text2`, `--km-hover`,
  `--km-input` остаются источником всех цветов — никаких
  хардкодов цветов в новой разметке.
- В рамках спецификации не меняются: store `songs` (`searchResults`),
  `usePlayerReadiness`, `usePlaylistMembership`, `useSongSubscriptions`,
  `useCart`, `useAuth`. Если для корректной доставки `contentReady`
  в `<PlayerIcon>` потребуется подписка/обогащение стора — это
  отдельный вопрос Implementation Notes; контрактно `contentReady`
  просто должен прийти из бэка.
