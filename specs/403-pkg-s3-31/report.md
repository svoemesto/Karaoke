# PKG-S3-31 — webvue3: админка врала «всё хорошо», теряла правки и грузила чужое

**OpenProject:** #403 · **Волна:** E · **Записей:** 40 · **Модуль:** `webvue3` (админское SPA)

Сквозной корень пакета: **админка не различала «не знаю» и «знаю, что плохо»**, а её
состояние менялось от чужих ответов. Отказ выглядел как успех, пустой список — как
«нарушений не найдено», устаревший ответ затирал свежий, полный снимок записи
затирал чужие правки, а фильтр, применённый один раз, терялся при следующей загрузке.

Семь классов дефектов: **гонки ответов** (RACE), **неразличимые состояния**
(ERR), **ложные «успехи»** (COMPAT), **потерянные/испорченные данные** (DATA),
**тихие отказы** (RULE), **незакрытые ресурсы** (LEAK), **лишняя работа на каждый
ввод** (PERF).

### BR-090 · `SongEdit.vue:3218–3242` · DATA — `idSponsr` получал строку «manage»

**Было.** Watcher `song.idSponsr.value`: `value.replace(prefixLinkSponsrPlay, '')

(`https://sponsr.ru/smkaraoke/<id>`), а кнопка «open» открывает **edit-URL**

`/\/smkaraoke\/(?:manage\/post\/)?(\d+)(?:[/?#]|$)/` — допускает оба вида URL;

**Тест.** `pkg-s3-31-songedit.test.js` → «id поста Sponsr извлекается из обоих видов

### BR-092 · `SongEdit.vue:186, 259, 293, 498, 515, 536, 557` · DATA — числовые поля — свободный текст

**Было.** `<input v-model="song.year">` (и `track`, `bpm`, `rootId`, `audioParentId`,
`audioSimilarityPercent`, `audioDeltaMs`) без валидации. Сервер принимает строку как
есть, но мягкий парсер `Song.kt` (`fields[SongField.YEAR]?.toLongOrNull() ?: 0L`)
превращал опечатку (`20x4`, `2024—2025`) в **0**, и UPDATE **затирал** прежнее
значение. Клиент получал успех, клал в `snapshotSong` исходную строку и показывал её
как сохранённую; после F5 в поле оказывался 0, ошибки админ не видел.

**Стало.** Клиентская валидация до отправки: новый модуль
`webvue3/src/lib/song-numeric-fields.js` (`isValidNumericSongField`,
`findInvalidNumericSongFields`, `SONG_NUMERIC_FIELDS`). В `performSave()` невалидное
числовое поле **не включается в diff** (сервер его не получает), пользователь видит
тост с названием поля. Повторный автосейв не перевзводится, пока в diff осталось
невалидное число (иначе получился бы цикл тостов). Пустое значение допустимо.

**Тест.** `pkg-s3-31-songedit.test.js` → «числовые поля валидируются до сохранения»:
поведенческий кейс на `isValidNumericSongField`/`findInvalidNumericSongFields`
(«20x4» → false, «2024—2025» → false, пусто → true, не-числовое поле → true) и
контрактный — `performSave` обязан звать валидацию.

### BR-096 · `Songs/store.js:1969–2001` (`changeToSync`) · RACE — инверсия флага после ответа

**Было.** Мутация `changeToSync` делала сетевой запрос и переключала `state.toSync` в
`.then` — **после** ответа, а `dictAction` вычислялся из флага **до** запроса. Два
быстрых клика давали два одинаковых действия (`add`+`add` или `remove`+`remove`) и два
переключения флага: UI оставался в состоянии, противоположном серверу. Отказ запроса
не обрабатывался (unhandled rejection), чекбокс молча не менялся.

**Стало.** Запрос перенесён в **action** `changeToSync`: действие вычисляется один раз и
фиксируется; параллельный повтор блокируется флагом `toSyncRequestInFlight`; флаг
ставится по подтверждённому сервером результату (`setToSync(action === 'add')`); отказ
не меняет состояние и пишется в консоль. `SongEdit.toSyncRemote()` показывает тост при
отказе.

**Тест.** `pkg-s3-31-songs-store.test.js` → «смена признака sync»: мутации
`changeToSync` больше нет (в мутациях нет сети), action фиксирует `dictAction`,
блокирует повтор, коммитит `setToSync` и имеет `catch`.

### BR-097 · `Songs/store.js:1099–1219` + `App.vue:195–260` · RULE — запись настроек из мутации

**Было.** 14 мутаций `setLast*` писали `POST /api/setwebvueprop` прямо из мутации и без
`.catch`: побочный эффект в мутации нарушает контракт Vuex, отказ уходил в unhandled
rejection, а в памяти значение было новым, на сервере — старым. `App.vue` при старте
читал 13 значений и тут же диспатчил `set*` — ещё 13 лишних POST-записей тех же
значений на каждую загрузку SPA.

**Стало.** Мутации — только `state.x = value`. Запись перенесена в actions
(`async setLastPriorX(ctx, payload) { commit(...); await persistWebvueProp(key, value) }`),
отказ обрабатывается (`persistWebvueProp` логирует предупреждение, возвращает `false`).
Восстановление при старте — отдельная мутация `restoreLastSettings(state, values)`,
которая НЕ пишет на сервер; `App.vue` вызывает `dispatch('restoreLastSettings', …)`.
Значения читаются **параллельно** (`Promise.allSettled`) вместо 13 последовательных RTT.

**Тест.** `pkg-s3-31-songs-store.test.js` → «запись настроек: без сети в мутациях»:
в разделе `mutations` нет `url: '/api/setwebvueprop'`; есть `persistWebvueProp` с
`catch`; `App.vue` не диспатчит `setLastSettingType`.

### BR-099 · `Songs/store.js:1857–1960` (`setCurrentSongId`) · RULE — запись в state в обход мутаций (TOCTOU)

**Было.** Action писал `ctx.state.toSync = …`, `ctx.state.freeTimeSlots = …`,
`ctx.state.songPages[…].splice(…)` напрямую (подписчики `store.subscribe` и
Vuex-devtools этого не видели). Хуже: проверка актуальности стояла **до** двух
последовательных `await` (`/api/getdict`, затем `/api/getfreetimeslots`) — между
проверкой и присвоением успевала выбраться другая песня: `state.toSync` оказывался от
песни A, а `currentSongId` — от песни B (TOCTOU); клик по чужому флагу вычислял
`add`/`remove` из него, но применял к B. Тот же приём — в `loadHealthReportBatch`
(`song.healthReportText = '?'`).

**Стало.** Все записи — через мутации (`setToSync`, `setFreeTimeSlots`,
`replaceSongInPage`, `setSongHealthReportPending`). Вынесен отдельный action
`applySongSyncState(ctx, currId)`: после **каждого** `await` актуальность
перепроверяется (`currId !== ctx.state.currentSongId` → результат отбрасывается).

**Тест.** `pkg-s3-31-songs-store.test.js` → «состояние меняется только через мутации»:
в `setCurrentSongId` нет прямых записей в `ctx.state`; `applySongSyncState` содержит
≥ 2 проверки актуальности; `loadHealthReportBatch` коммитит, а не пишет в объект.

### BR-126 · `SongEdit.vue:4400–4470` (`publishToTelegramNow`) · COMPAT — `messageId` терялся

**Было.** При успешной ручной публикации (`success=true`, `state=published`, непустой
`data.messageId`) обработчик показывал тост и ничего не писал в `song.idTelegramDemo`.

### BR-127 · `SongEdit.vue:4060–4100, 5150–5225` (`findAudioParent`, `showSubsEdit`, `closeSubsEdit`, `doDeleteSong`) · ERR — отказы не обрабатывались

**Было.**
- `findAudioParent()` — `try/finally` без `catch` вокруг `JSON.parse(data)`: эндпоинт
  отдаёт пустое тело при «песня не найдена» → `SyntaxError`; при 500 — unhandled
  rejection.
- `showSubsEdit()` — `JSON.parse(await …).voices` без проверки: при «песня не найдена»
  ответ `{}` → `voices === undefined` в обязательном prop `SubsEdit`; при 500 —
  unhandled rejection и модалка не открывается.
- `closeSubsEdit()` — три `.then` без `.catch` и без проверки `isUnmounted`.
- `doDeleteSong()` — `dispatch('deleteCurrentSong')` без `await`/`.catch` и сразу
  `$emit('close')`: при отказе карточка закрывается как при успехе, песня остаётся.

**Стало.** `findAudioParent` — `JSON.parse` в защищённом `try`, `catch` с тостом;
`showSubsEdit` — проверка `voices` (без них модалка не открывается) и `catch` с
тостом; `closeSubsEdit` — общий `fetchInto` с `.catch` и проверкой `isUnmounted`;
`doDeleteSong` — `await`, `$emit('close')` только в `.then`, отказ → тост.

**Тест.** `pkg-s3-31-songedit.test.js` → «асинхронные операции обрабатывают отказ»:
четыре кейса — по `catch`/тосту/проверке `voices`/закрытию только при успехе.

## 4. За владельцем

1. **Async-мутации в `Songs/store.js` (`updateSongsAndDictionaries`,
   `updateSong`).** Они делают `await this.dispatch('getToSyncFromRest')` и пишут
   `state.toSync`/`state.freeTimeSlots` прямо внутри мутации — тот же корень, что у
   BR-099, но в мутациях. В этом пакете не трогал: BR-099 в карточке указывает на
   action `setCurrentSongId`, а перенос сетевых вызовов из мутаций — отдельная
   правка со своим риском (эти мутации вызываются из `updateSongsAndDictionaries`).
   Решение: **за владельцем** — расширять ли пакет или завести отдельную запись.
2. **Бэкенд: `SongUpdateMapper` мягко читает числа** (`toLongOrNull() ?: 0`) —
   корень BR-092 наполовину в бэкенде. Здесь закрыт клиентский слой (поле не
   уходит на сервер). Серверная защита (400 + понятная ошибка вместо тихого 0) —
   **за владельцем**: пакет `PKG-S3-31` ограничен `webvue3`.
3. **`POST /api/authors/updateauthor` — не patch.** BR-367/BR-377 закрыты на клиенте
   (перечитывание / diff). Серверная patch-семантика или оптимистичная блокировка
   (`updated_at`/version + 409) — **за владельцем**: это изменение контракта API.
4. **Сторы фильтров импортируют `lib/utils` без расширения** (`'../../../lib/utils'`).
   Vite это резолвит, Node ESM — нет, поэтому такой модуль нельзя импортировать в
   `node --test` (в контрактном тесте словарей пришлось читать текст исходника).
   Массовая правка импортов на `'../../../lib/utils.js'` — **за владельцем**: она
   затронет много файлов вне пакета.
5. **Раздел «Картинки» теперь грузит весь дайджест при открытии** (BR-390). Если
   таблица картинок разрастётся до тысяч записей, понадобится серверная пагинация —
   сейчас её нет. Наблюдение, не блокер.
