# Research: Устранить утечку соединений с БД от одноразовых потоков очереди

**Feature**: [spec.md](./spec.md) | **Plan**: [plan.md](./plan.md)

Technical Context не содержит открытых `NEEDS CLARIFICATION` — стек и
архитектура зафиксированы. Задача Phase 0 — подтвердить диагноз (баг-фикс
активного инцидента) и выбрать способ освобождения соединения, наименее
рискованный для уже проверенного поведения specs/087.

## Кандидат A — `closeThreadConnection()` в `KaraokeConnection` + вызов в `finally` у `KaraokeProcessThread.run()` (выбран)

**Находка**: `class KaraokeProcessThread(...) : Thread()` (`KaraokeProcessWorker.kt:62`)
создаётся заново на каждое задание очереди:

```kotlin
// doStart(), внутри главного цикла
threadsMap[threadId] = KaraokeProcessThread(karaokeProcess)
threadsMap[threadId]!!.start()
```

Каждый экземпляр — новый OS-поток, который запускается один раз
(`Thread.start()` можно вызвать только один раз за объект) и никогда не
переиспользуется для другого задания. Внутри `run()` (`KaraokeProcessWorker.kt:74-376`)
БД используется как минимум в двух местах на каждый прогон:
- `karaokeProcess.save()` — при переводе в `WORKING` (начало, строка ~79) и
  при финальном статусе (`DONE`/`ERROR`/`WAITING`, несколько веток внутри
  `try/catch` для `runFunctionWithArgs`-заданий и для subprocess-заданий).
- `KaraokeProcess.getCountWaiting(database = karaokeProcess.database)`
  (строка ~204) — при старте subprocess-задания, для обновления бейджа
  счётчика ожидающих в хедере `webvue3` (это и есть механизм, на который
  указал пользователь при описании инцидента).

`karaokeProcess.database` — тот же `KaraokeConnection`-инстанс
(`WORKING_DATABASE`), что используется и `doStart()`, и HTTP-обработчиками.
После specs/087 у него один `ThreadLocal`-слот на каждый когда-либо
обратившийся поток. Поскольку `KaraokeProcessThread` никогда не вызывает
`getConnection()` повторно ПОСЛЕ завершения своей единственной задачи (сам
поток заканчивает выполнение и умирает), физическое `java.sql.Connection`,
записанное в его слот `ThreadLocal`, никогда не проверяется на
`isClosed`/`isValid()` снова и никогда не закрывается — типичная утечка
ресурса «открыл и забыл» на каждое обработанное задание.

**Decision**: добавить в `KaraokeConnection` метод `closeThreadConnection()`,
закрывающий и удаляющий из `ThreadLocal` соединение **вызывающего потока**
(не общий сброс — каждый поток управляет только своей записью, что
безопасно по конструкции `ThreadLocal`). Вызвать его один раз, в `finally`,
оборачивающем всё тело `if (karaokeProcess != null) { ... }` в `run()` —
после этого момента поток `KaraokeProcessThread` больше не обращается к
БД, поэтому закрытие в конце безопасно и ничего не блокирует. `finally`
(а не просто «последняя строка кода») нужен, чтобы закрытие происходило
даже при непредвиденном исключении внутри `run()` — иначе часть утечки
осталась бы неустранённой ровно в тех случаях, которые чаще всего и
приводят к длинным сериям заданий (ошибки, форс-стопы).

**Почему не трогать другие потоки**: `doStart()` — единственный долгоживущий
поток очереди, продолжающий работать (и переиспользовать соединение) все
время, пока очередь запущена — вызывать для него `closeThreadConnection()`
было бы неверно (разрушило бы кеш ровно в тот момент, когда он больше всего
нужен — специально решённая задача specs/087). Пул потоков Tomcat —
аналогично переиспользуемый, HTTP-обработчики не должны закрывать
соединение после каждого запроса (иначе теряется вся выгода кеширования).

**Alternatives considered**:
- **Не кешировать соединение вообще для `KaraokeProcessThread`** (например,
  через отдельный `Connection.local()`-инстанс, создаваемый и явно
  закрываемый внутри `run()`, минуя `ThreadLocal` `WORKING_DATABASE`
  целиком) — отклонено: `karaokeProcess.database` используется глубоко
  внутри `karaokeProcess.save()`/`KaraokeProcess.getCountWaiting()` как
  параметр, переданный из `doStart()` — подменить его локально означало бы
  расхождение между тем, какое соединение видит поток задания и какое
  видит остальной код, работающий с тем же `KaraokeProcess`-объектом.
  Добавление одного метода в уже существующий класс — намного меньший
  blast radius.
- **Финализатор/`AutoCloseable` на `KaraokeProcessThread`** (закрывать
  соединение через `use {}`-подобный паттерн вокруг `.start()`/`.join()`)
  — отклонено: `Thread.start()` асинхронный, вызывающий код (`doStart()`)
  не ждёт завершения потока синхронно (`.join()` не вызывается — это и есть
  весь смысл асинхронной очереди) — обернуть в `use{}` снаружи невозможно
  без блокировки главного цикла. Закрытие изнутри самого `run()` — в
  `finally` — единственное место, которое естественно знает, что «эта
  единственная задача потока полностью завершена».
- **Периодическая фоновая очистка «старых» соединений** (например, cron-like
  проверка и закрытие соединений от потоков, которые уже не `isAlive`) —
  отклонено как избыточно сложное и с задержкой: `ThreadLocal` не даёт
  простого способа перечислить «все когда-либо использованные слоты» без
  отдельного реестра потоков, что добавляет постоянно поддерживаемое
  состояние ради задачи, которая тривиально решается закрытием в `finally`
  в момент, когда и так известно, что поток закончил работу.

## Итоговый подход

1. `KaraokeConnection.closeThreadConnection()` — новый метод, закрывает и
   удаляет соединение вызывающего потока из `ThreadLocal` (Кандидат A) —
   покрывает FR-001/FR-002.
2. `KaraokeProcessThread.run()`: обернуть тело `if (karaokeProcess != null)`
   в `try/finally`, вызвать `karaokeProcess.database.closeThreadConnection()`
   в `finally` — покрывает FR-001/FR-002/FR-004.
3. Долгоживущие потоки (`doStart()`, Tomcat) не трогать — покрывает FR-003.

Все пункты — точечные правки внутри уже существующих файлов/паттернов, без
новых зависимостей, без миграций схемы БД, без изменений фронтенда/HTTP-контракта.
