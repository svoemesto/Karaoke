# Contract: жизненный цикл статуса готовности песни (`idStatus`)

Эта фича не добавляет новых endpoint'ов и не меняет форму request/response —
она (а) меняет поведенческий порог «готовности» на уже существующих
публичных read-путях, (б) расширяет допустимый диапазон значений, которые
администратор может выставить вручную через уже существующий
save-эндпоинт SongEdit, (в) выполняет одноразовую data-миграцию значения уже
существующего поля.

## 1. Публичные read-пути: порог готовности `>=3` → `>=6`

| Поверхность | Метод/путь | Кто использует |
|---|---|---|
| Готовность онлайн-плеера | `GET /player/{id}/access` (и смежные, `stemsReady`) | `karaoke-public` (плеер) |
| Публичные счётчики коллекции | `GET /api/public/stats` (кеш `StatBySong`/`StatsCacheScheduler`) | `karaoke-public` (главная) |
| Закрома / поиск / спецзаказная плашка | `GET /api/public/zakroma`, `GET /api/public/songs` (+ legacy `/zakroma`, `/filter`) | `karaoke-public`, legacy Thymeleaf |

**Было**: элемент (песня) считается «готовой»/видимой/проигрываемой при
`id_status >= 3`.

**Стало**: тот же признак вычисляется как `id_status >= 6`. Форма
JSON-ответов, HTTP-статусы, коды ошибок — без изменений. Набор полей DTO не
меняется.

**Гарантия обратной совместимости данных**: перед тем, как это поведенческое
изменение попадает в прод, миграция (раздел 3 ниже) обязана быть применена —
иначе набор «готовых» песен временно сократится (регрессия, которую
предотвращает порядок выката: сначала миграция данных, потом деплой кода с
новым порогом, см. `quickstart.md`).

## 2. SongEdit: допустимый диапазон ручного изменения статуса

**Поверхность**: `POST /api/song/songs2update` (сохранение формы SongEdit,
webvue3), поле `idStatus`.

**Было**: endpoint технически уже принимал любое значение (generic
`idStatus?.let { sett.fields[SongField.ID_STATUS] = it }`), но UI (кнопки
статуса в SongEdit) размечал 4 и 6 как «легаси, не влияет на онлайн-плеер»,
создавая у администратора ложное впечатление, что выставлять их вручную для
нового жизненного цикла бессмысленно/неправильно; кнопки для значения 5 не
было вовсе.

**Стало**: UI (webvue3 SongEdit) MUST предлагать администратору все 7
значений (0-6) с лейблами по таблице `data-model.md`, без пометки
«легаси» — каждое из них теперь означает конкретный шаг ИМЕННО этого
(единственного) жизненного цикла. Backend-контракт endpoint'а
(`songs2update`) не меняется — он уже был generic.

## 3. Data-миграция (не HTTP-контракт, но наблюдаемый эффект)

**Было**: `id_status` содержит значения `0..3` для всех существующих песен
(значения 4-6 встречаются только у песен, прошедших легаси
MLT-рендер-пайплайн — количество таких записей неизвестно заранее, аудит —
на этапе `/speckit-tasks`).

**Стало**: после однократного применения `deploy/karaoke-db/32_song_status_
lifecycle.sql` на LOCAL и на SERVER, ни одна песня не имеет `id_status` в
диапазоне `[3..5]`, если до миграции у неё было `id_status>=3` — все такие
записи получают `id_status=6`. Песни с `id_status` `0`, `1` или `2` не
затрагиваются миграцией.

**Наблюдаемый эффект для клиентов**: до миграции ни один потребитель не
видит новых промежуточных значений `3`-`5` в осмысленном (не-легаси) виде;
эти значения начинают появляться в данных только по мере того, как
конвейер (ручной или автоматический, см. `research.md` Decision 5) реально
проводит песню через новые стадии — контракт не гарантирует и не требует
одномоментного появления «недоделанных» песен в диапазоне 3-5 сразу после
миграции (сама миграция только поднимает уже готовые записи до 6).

## Явно НЕ входит в контракт этой фичи

- Форма/схема любых DTO (`SongDTO`, `SongPublicDto`, `StatBySongDto` и
  т.п.) — без изменений.
- `GET /api/public/song/{id}` (детальная карточка по прямой ссылке) — если
  ранее не проверяла `idStatus` как условие доступа, эта фича не добавляет
  такую проверку (см. Assumptions spec.md — только места, уже проверявшие
  `>=3`).
- Легаси MLT-рендер-эндпоинты (`/song/{id}/createkaraoke`,
  `KaraokeProcessTypes.MELT_LYRICS`/`MELT_KARAOKE`) — их HTTP-контракт
  (запрос/ответ) не меняется; меняется только то, что они прекращают писать
  в `id_status` как побочный эффект (см. `research.md` Decision 1) —
  наблюдаемо только через `data-model.md`, не через форму ответа.
