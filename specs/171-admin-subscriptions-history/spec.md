# Feature Specification: Админ-таблицы «Подписки», «История прослушиваний» и «Временные ссылки»

**Feature Branch**: `171-admin-subscriptions-history`

**Created**: 2026-08-11

**Status**: Draft

**Input**: User description: "Задача - в админку добавить компоненты "Подписки" и "История прослушиваний". Так же - компонент "Временные ссылки". Работай в новой ветке."

## Контекст и мотивация

**Текущее состояние.** В админ-SPA (`webvue3`) уже есть 22 пункта меню (Песни, Пользователи сайта, Тарифы, Плейлисты и т.д.). Три класса данных публичного сайта при этом **доступны только из карточки пользователя**:

1. **Подписки** (`tbl_subscriptions`) — `UserSubscriptionsModal.vue` в `SiteUserEdit.vue` показывает список подписок **одного** пользователя. Глобального списка нет.
2. **История прослушиваний** (`tbl_listening_history`) — пользовательская фича `009-listening-history` отдаёт историю **самому пользователю** через `GET /api/public/account/history`. Админ-списка нет вообще.
3. **Временные ссылки** (`tbl_song_share_links`, гостевая шарилка песен премиум-пользователями) — `shareLinkStore.js` грузит ссылки **одного** пользователя через `/api/siteusers/share/links`. Глобального списка нет.

Все три таблицы живут в PROD-БД (`tbl_subscriptions`, `tbl_listening_history`, `tbl_song_share_links`) — данные реальные, но без админ-таблицы саппорт и аудит «кто когда что слушал / купил / расшарил» идут через прямой SQL.

**Цель.** Добавить в админку три новых пункта меню (рядом с существующими «Пользователи сайта», «Тарифы», «Плейлисты»), каждый — read-only таблица с фильтрами по пользователю/песне/дате/статусу и target-aware (local/remote).

**Связь с другими фичами:**
- `specs/009-listening-history/` — публичная история для **пользователя**. Здесь — **админ-таблица** той же таблицы `tbl_listening_history` для всех пользователей.
- `specs/164-complete-guest-share-link/` + `167-fix-share-claim-500` — публичный флоу шаринга. Здесь — **админ-таблица** `tbl_song_share_links` для саппорта и аудита.
- `docs/features/subscriptions.md` (если есть) — публичный флоу подписок. Здесь — **админ-таблица** `tbl_subscriptions` для саппорта и аудита.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Админ видит глобальный список подписок (Priority: P1)

Администратор сайта открывает новый пункт меню «Подписки» в админке и видит таблицу со **всеми** записями `tbl_subscriptions` (всех пользователей сайта), отсортированными от самых новых к самым старым. В каждой строке — дата создания, имя пользователя, scope (Сайт/Песня), название тарифа или песни, сумма, статус, автопродление, дата оплаты, номер заказа.

**Why this priority**: подписки — финансовая запись. Без глобального списка саппорт отвечает на «где мой платёж?» только через прямой SQL.

**Independent Test**: открыть `/subscriptions` — таблица отрисовалась, по 5+ подписок в день создаются на проде (видно по `MonetizationStats`), фильтр «scope=SONG, status=PAID» оставляет только оплаченные покупки песен.

**Acceptance Scenarios**:

1. **Given** админ открывает пункт меню «Подписки», **When** страница загружается, **Then** отображается таблица со всеми записями `tbl_subscriptions` из выбранной БД (`local`/`remote`), отсортированная по `created_at` DESC.
2. **Given** в таблице 1000+ записей, **When** админ прокручивает таблицу и использует пагинацию, **Then** таблица показывает страницы по 25 строк, переход между страницами сохраняет выбранные фильтры.
3. **Given** админ применяет фильтр `scope=PAID, status=PAID`, **When** таблица перезагружается, **Then** видны только оплаченные подписки, счётчик строк в footer обновляется.
4. **Given** админ кликает по имени пользователя в строке, **When** событие срабатывает, **Then** открывается карточка этого пользователя (`/siteusers` с фокусом на нём) — НЕ новая вкладка (в рамках SPA).
5. **Given** админ переключает target «Local/Remote», **When** таблица перезагружается, **Then** данные соответствуют выбранной БД, фильтры сохраняются.

### User Story 2 - Админ видит глобальный список истории прослушиваний (Priority: P1)

Администратор открывает пункт меню «История прослушиваний» и видит таблицу со **всеми** записями `tbl_listening_history` (по всем пользователям), с обогащением через JOIN к `tbl_songs` (название, исполнитель, альбом). В каждой строке — пользователь, песня, исполнитель, альбом, дата последнего прослушивания, счётчик прослушиваний.

**Why this priority**: «Кто и что слушал» — базовая аналитика для саппорта и для решения споров «я слушал это вчера, а сегодня уже нет». Без админ-таблицы это только через SQL.

**Independent Test**: открыть `/listeninghistory` — таблица отрисовалась, JOIN к `tbl_songs` работает, фильтр по `userId` оставляет только прослушивания этого пользователя.

**Acceptance Scenarios**:

1. **Given** админ открывает «Историю прослушиваний», **When** страница загружается, **Then** отображаются все записи `tbl_listening_history` из выбранной БД, JOIN с `tbl_songs` для названия/исполнителя/альбома, сортировка по `last_played_at` DESC.
2. **Given** песня была помечена тегом `SKIP`, **When** админ смотрит таблицу, **Then** такая песня в списке **не появляется** (фильтр на чтении — те же правила, что и в публичном `getForUser`).
3. **Given** админ применяет фильтр по `userId`, **When** таблица перезагружается, **Then** видны только прослушивания этого пользователя; счётчик `play_count` показывает, сколько раз пользователь слушал песню.
4. **Given** админ применяет фильтр по диапазону дат, **When** таблица перезагружается, **Then** видны только прослушивания в этом диапазоне (по `last_played_at`).
5. **Given** админ кликает по песне в строке, **When** событие срабатывает, **Then** открывается карточка этой песни (`/songs?focus=ID`) в той же SPA-сессии.

### User Story 3 - Админ видит и управляет глобальным списком временных ссылок (Priority: P1)

Администратор открывает пункт меню «Временные ссылки» и видит таблицу со **всеми** записями `tbl_song_share_links` (по всем пользователям), с обогащением через JOIN к `tbl_songs` и `tbl_site_users`. В каждой строке — владелец ссылки, песня, дата создания, дата истечения, активна/отозвана, причина отзыва (если отозвана), текущая активная сессия (если есть).

Админ может **отозвать** активную ссылку прямо из таблицы (с подтверждением), аналогично действию «Ban» в `SiteUsersTable`.

**Why this priority**: share-ссылки — механизм гостевого доступа к премиум-песням. Без глобального списка и управления саппорт не может «отобрать» ссылку у нарушителя иначе как прямым UPDATE в БД. Уже существующий `revokeSiteUserShareLink` action (`/api/siteusers/share/links/revoke`) переиспользуется.

**Independent Test**: открыть `/sharelinks` — таблица отрисовалась, активная ссылка имеет зелёный бейдж «Активна», отозванная — красный с причиной. Кнопка «Отозвать» работает для активных.

**Acceptance Scenarios**:

1. **Given** админ открывает «Временные ссылки», **When** страница загружается, **Then** отображаются все записи `tbl_song_share_links` из выбранной БД, с JOIN к `tbl_songs` (название) и `tbl_site_users` (email/displayName владельца), сортировка по `created_at` DESC.
2. **Given** ссылка активна (`active=true`, `expires_at > now()`), **When** админ нажимает «Отозвать» и подтверждает, **Then** ссылка переводится в `active=false`, `revoked_at=now()`, `revoke_reason='admin'`; таблица обновляется без перезагрузки.
3. **Given** ссылка уже отозвана (`active=false`), **When** админ смотрит таблицу, **Then** строка показывает причину отзыва (`expired` / `premium_lost` / `song_unavailable` / `admin`) и дату отзыва.
4. **Given** у ссылки есть активная сессия (`active_session_token_hash IS NOT NULL`, `active_session_lease_until > now()`), **When** админ смотрит таблицу, **Then** в строке отображается «есть активная сессия» (бейдж).
5. **Given** админ применяет фильтр «только активные», **When** таблица перезагружается, **Then** видны только `active=true` ссылки (плюс фильтр `expires_at > now()` для исключения «не отозванных, но истёкших»).
6. **Given** админ кликает по владельцу или песне в строке, **When** событие срабатывает, **Then** открывается соответствующая карточка (`/siteusers` или `/songs`) в той же SPA-сессии.

### User Story 4 - Сохранение позиции в таблице при переключении пунктов меню (Priority: P2)

Админ фильтрует подписки по `scope=SITE, status=PAID`, открывает страницу 3, переходит на «Песни», затем возвращается на «Подписки» — таблица открывается на той же странице 3 с теми же фильтрами.

**Why this priority**: тот же паттерн, что в `SiteUsersTable`, `SitePlaylistsTable`, `ProcessesTable` (см. AGENTS.md «Персистентность страницы пагинации»). Без этого админ теряет позицию при любом переключении — стандартное требование проекта.

**Independent Test**: открыть таблицу, применить фильтр, перейти на страницу 3, перейти на `/songs`, вернуться — таблица показывает страницу 3 с тем же фильтром.

**Acceptance Scenarios**:

1. **Given** админ на странице 3 таблицы подписок с фильтром `scope=SITE`, **When** он переключается на другой пункт меню и возвращается, **Then** таблица показывает страницу 3 с тем же фильтром.
2. **Given** админ на странице 5 таблицы истории с фильтром по пользователю, **When** количество строк уменьшилось (например, фильтр ужесточили), **Then** `currentPage` сбрасывается только если выходит за пределы `Math.ceil(count/perPage)` (паттерн из `SongsTable`).

---

### Edge Cases

- **Тысячи записей в `tbl_listening_history`** — у одного пользователя может быть тысячи прослушиваний за годы. Админ-таблица должна показывать **первые N** строк (например, 500 на страницу, не 25 — это список всех пользователей) с явным сообщением «показаны первые 500 из M», чтобы админ знал, что есть ещё.
- **Подписка `scope=SITE` без `tariff_id`** — старая запись до введения тарифов. Таблица должна показывать её как «тариф #NULL» (та же логика, что в существующем `UserSubscriptionsModal`).
- **Share-ссылка на удалённую песню** (`song_id` указывает на несуществующую запись) — JOIN даёт NULL. Таблица показывает «песня удалена» (id оставить для отладки).
- **Share-ссылка на SKIP-помеченную песню** — `ShareLinkSweeper` уже отзывает такие ссылки (`revoke_reason='song_unavailable'`). Таблица показывает это как «отозвана автоматически».
- **Параллельные операции** — админ открывает таблицу «Подписок» на PROD-данных, в это время другой админ (или сам бэк через `PublicSubscriptionController.create`) создаёт новую подписку. Без SSE-события для `tbl_subscriptions` таблица обновится только при ручном F5. Это нормально — `SitePlaylists` тоже не обновляется live.
- **`tbl_subscriptions` 0 строк** — таблица показывает понятную заглушку «Подписок нет», не пустой `<table>`.
- **Очень длинный `secret` в `tbl_song_share_links`** — отображается усечённым с `title` для полного (как `orderId` в `UserSubscriptionsModal`).
- **Target=remote + локальный URL** — ошибка сети при `local()`-соединении. Дропается 500 на бэкенде. Фронт показывает «Не удалось загрузить данные» — тот же паттерн, что везде.

## Requirements *(mandatory)*

### Functional Requirements

**Подписки (Subscriptions):**

- **FR-001**: Админка MUST предоставлять отдельный пункт меню «Подписки» с роутом `/subscriptions`.
- **FR-002**: Таблица MUST показывать все записи `tbl_subscriptions` из выбранной БД (`local`/`remote`) с обогащением (JOIN к `tbl_site_users` для email/displayName, к `tbl_songs` если `scope=SONG` для song_name, к `tbl_tariffs` если `scope=SITE` для tariff_name).
- **FR-003**: Колонки таблицы: дата создания, пользователь (id + email/displayName), scope (Сайт/Песня), название (тариф/песня), сумма (finalPrice), базовая цена + скидка (если есть, с подсказкой), статус (PAID/PENDING/CREATED/FAILED/REFUNDED/CANCELED), автопродление (Да/Нет/—), дата оплаты, номер заказа (первые 8 символов + tooltip).
- **FR-004**: Таблица MUST поддерживать фильтры: `scope` (Все/SONG/SITE), `status` (Все/PAID/PENDING/CREATED/FAILED/REFUNDED/CANCELED), `userId` (числовой id пользователя), `songId` (числовой id песни), диапазон дат `createdFrom..createdTo`.
- **FR-005**: Таблица MUST иметь пагинацию по 25 строк на страницу с BPagination, сортировка по умолчанию `created_at DESC`.
- **FR-006**: Таблица MUST сохранять текущую страницу и фильтры в Vuex (паттерн «Персистентность страницы пагинации» из AGENTS.md), восстанавливать при возврате на роут.
- **FR-007**: Клик по пользователю MUST открывать `/siteusers` с фокусом на этом пользователе (та же SPA-сессия, не новая вкладка).

**История прослушиваний (Listening History):**

- **FR-008**: Админка MUST предоставлять отдельный пункт меню «История прослушиваний» с роутом `/listeninghistory`.
- **FR-009**: Таблица MUST показывать все записи `tbl_listening_history` с JOIN к `tbl_songs` (song_name, song_author, song_album). SKIP-помеченные песни MUST быть исключены на чтении (та же логика, что в `ListeningHistory.getForUser`).
- **FR-010**: Колонки таблицы: дата последнего прослушивания, пользователь (id + email/displayName через JOIN), песня (id + name), исполнитель, альбом, счётчик прослушиваний.
- **FR-011**: Таблица MUST поддерживать фильтры: `userId` (числовой id), `songId` (числовой id), диапазон дат `lastPlayedFrom..lastPlayedTo`.
- **FR-012**: Таблица MUST иметь пагинацию по 500 строк на страницу (больше чем у подписок — данные менее «жирные» и часто нужны целиком для аналитики), с явным footer «показано X из Y» если Y > X.
- **FR-013**: Таблица MUST сохранять текущую страницу и фильтры в Vuex.
- **FR-014**: Клик по песне MUST открывать `/songs?focus=ID` (карточка песни в редакторе), клик по пользователю — `/siteusers` с фокусом.

**Временные ссылки (Share Links):**

- **FR-015**: Админка MUST предоставлять отдельный пункт меню «Временные ссылки» с роутом `/sharelinks`.
- **FR-016**: Таблица MUST показывать все записи `tbl_song_share_links` с JOIN к `tbl_songs` (song_name) и `tbl_site_users` (email/displayName владельца).
- **FR-017**: Колонки таблицы: дата создания, владелец (id + email/displayName), песня (id + name), дата истечения (с подсветкой «истекла» если `< now`), статус (Активна/Истекла/Отозвана), причина отзыва (если отозвана), наличие активной сессии (бейдж), secret (первые 8 символов + tooltip).
- **FR-018**: Таблица MUST поддерживать фильтры: `activeOnly` (чекбокс — только активные), `ownerId` (id пользователя), `songId` (id песни), диапазон дат `createdFrom..createdTo`.
- **FR-019**: Для каждой активной строки таблица MUST показывать кнопку «Отозвать» (с `custom-confirm` — та же модалка подтверждения, что в `SiteUsersTable.ban`).
- **FR-020**: Действие «Отозвать» MUST вызывать существующий эндпоинт `POST /api/siteusers/share/links/revoke` (`revokeSiteUserShareLink` action в `shareLinkStore.js`), при успехе — обновлять строку в таблице без F5.
- **FR-021**: Таблица MUST иметь пагинацию по 25 строк на страницу, сортировка по `created_at DESC`.
- **FR-022**: Таблица MUST сохранять текущую страницу и фильтры в Vuex.

**Общие требования (все три таблицы):**

- **FR-023**: Все три таблицы MUST быть target-aware — переключатель «Local/Remote» в toolbar (тот же паттерн, что `SiteUsersTable.onTargetChange`). Default = `local`.
- **FR-024**: Backend-эндпоинты MUST принимать параметр `target` (`local`/`remote`) и явно выбирать `Connection.local()` / `Connection.remote()` (паттерн из `SiteUsersController`).
- **FR-025**: Пустой результат MUST показывать понятную заглушку («Подписок нет», «Истории прослушиваний нет», «Временных ссылок нет»), а не пустой `<table>`.
- **FR-026**: Все три компонента MUST иметь KDoc/JSDoc с `@see` на этот документ (FR-006 из constitution).
- **FR-027**: Никаких новых миграций БД не требуется — все три таблицы уже существуют (`tbl_subscriptions` из миграции `15_monetization.sql`, `tbl_listening_history` из `27_listening_history.sql`, `tbl_song_share_links` из `38_song_share_links.sql`).

### Key Entities

- **Subscription** (`tbl_subscriptions`) — существующая сущность. Колонки для отображения: `id`, `site_user_id`, `scope` (SONG/SITE), `id_song` (nullable), `tariff_id` (nullable), `base_price`, `discount`, `final_price`, `promo_applied`, `status`, `auto_renew`, `created_at`, `paid_at`, `order_id`.
- **ListeningHistoryEntry** (`tbl_listening_history`) — существующая сущность. Колонки для отображения: `site_user_id`, `song_id`, `play_count`, `last_played_at`. Обогащение через JOIN с `tbl_songs` (`song_name`, `song_author`, `song_album`).
- **SongShareLink** (`tbl_song_share_links`) — существующая сущность. Колонки для отображения: `id`, `owner_site_user_id`, `song_id`, `secret`, `created_at`, `expires_at`, `active`, `revoked_at`, `revoke_reason`, `active_session_token_hash` (наличие = «есть активная сессия»).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Админ открывает `/subscriptions`, видит таблицу не позднее 2 секунд при 10 000 записей в `tbl_subscriptions` на PROD-БД.
- **SC-002**: Админ открывает `/listeninghistory`, видит таблицу не позднее 3 секунд при 50 000 записей в `tbl_listening_history` на PROD-БД (включая JOIN к `tbl_songs`).
- **SC-003**: Админ открывает `/sharelinks`, видит таблицу не позднее 2 секунд при 5 000 записей в `tbl_song_share_links` на PROD-БД.
- **SC-004**: Админ может отфильтровать «только оплаченные подписки на песни» (scope=SONG, status=PAID) за 3 клика: открыть фильтр → выбрать scope → выбрать status. Без ручного SQL.
- **SC-005**: После отзыва share-ссылки из таблицы админом таблица обновляется без F5 в течение 1 секунды (in-place обновление строки).
- **SC-006**: При переключении target «Local ↔ Remote» таблица перезагружается за 2 секунды, фильтры сохраняются.
- **SC-007**: Все три таблицы проходят `lint:check` (ESLint webvue3) и `npm run build` без warning'ов, ktlint — без новых baseline-нарушений.
- **SC-008**: KDoc покрытие новых публичных компонентов — 100% (FR-006 constitution).

## Assumptions

- **Только чтение** для подписок и истории прослушиваний (как `SitePlaylists`). Подписки — финансовая запись; ручное редактирование из админки не нужно и опасно (история платежей, аудит). История — только накопление событий, ручное удаление не предполагается. **С исключением** для share-ссылок: для них есть действие «Отозвать» (переиспользуется существующий `revokeSiteUserShareLink`).
- **Без экспорта в CSV/Excel** — не запрашивалось, в скоуп не входит. Если понадобится — отдельная фича.
- **Без live-обновлений через SSE** — как у `SitePlaylists`. SSE для `tbl_subscriptions`/`tbl_listening_history`/`tbl_song_share_links` сейчас не настроен, добавление в скоуп не входит. Админ обновляет F5 вручную.
- **Пагинация подписок 25 строк, истории 500 строк, share 25 строк** — разумные дефолты. История менее «жирная» (одна строка = одна пара user×song, без денежных/юридических полей), больший размер страницы полезен для аналитики.
- **Дефолтный `target` = `local`** — то же, что во всех остальных админ-таблицах (кроме глобальных read-only по БД).
- **JOIN к `tbl_site_users` для email/displayName** — отдельный запрос или подзапрос в `digest`. Не индексируется отдельно (id пользователя — PK), для 10k записей подписок — допустимая нагрузка. Если упрёмся в перф — отдельная фича.
- **Реализация read-only через тот же SQL-паттерн**, что в существующем `Subscription.loadByUser` и `ListeningHistory.getForUser` — расширением через `whereList`/фильтры, без нового ORM/Hibernate (конституция II).
- **Без новых миграций БД** — все три таблицы уже есть (см. FR-027). `tbl_song_share_sessions` (сессии шаринга) тоже есть, но в админ-таблицу «Временные ссылки» НЕ выносится — это технические записи, отдельный drill-down если понадобится.
- **Существующий `revokeSiteUserShareLink` action** переиспользуется без изменений — он уже умеет принимать `shareLinkId` + `reason`. `reason='admin'` для действия из админ-таблицы.
- **Кликабельные ссылки на `/siteusers` / `/songs`** — реализуется через `router.push` с `query.focus=ID` (тот же паттерн, что в `SitePlaylistsTable` для перехода к владельцу плейлиста).

## Out of Scope (явно не в этой фиче)

- Редактирование подписок из админки (только чтение).
- Удаление/очистка истории прослушиваний из админки.
- Создание share-ссылок из админки (только чтение + revoke).
- Экспорт данных в CSV/Excel.
- Графики/аналитика по подпискам, истории, шарам (только простые таблицы).
- SSE-уведомления для этих таблиц.
- Корзина (`tbl_cart_items`) — отдельный пункт меню, если понадобится.
- Сессии шаринга (`tbl_song_share_sessions`) — отдельный drill-down.
- Drill-down к конкретной share-ссылке с историей сессий (отдельная фича).
