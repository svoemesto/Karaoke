# Feature Specification: Порядок плашек в Закромах и явная сортировка спец-авторов

**Feature Branch**: `307-special-authors-zakroma-order`
**Created**: 2026-09-06
**Status**: Draft
**Input**: User description (задача №56 в OpenProject):
> У авторов есть поле в базе данных логическое поле is_special_order. Если оно установлено то автор отображается не собственной плашкой в Закромах, а внутри группы "Отдельные песни разных авторов".
>
> В закромах плашка для "Отдельные песни разных авторов" отображается картинкой папки и находится среди плашек авторов самой последней.
>
> Нужно чтобы плашка "Отдельные песни разных авторов" была первой.
>
> Так же нужно реализовать возможность порядка показа плашек авторов в закромах. Надо добавить в таблицу авторов поле sort_order, по-умолчанию 0. В закромах сначала отображается плашка "Отдельные песни разных авторов". Потом по возрастанию sort_order те авторы, у которых sort_order не равен 0. Потом все остальные авторы (sort_order = 0) с сортировкой по алфавиту названия авторов (как сейчас).

## Clarifications

### Session 2026-09-06

- Q1. Поведение сортировки для отрицательных значений `sort_order`: что делать, если редактор задал отрицательное число (например `-1`)? → A: отрицательные значения допустимы и идут «выше» нуля: сортируем по `sort_order ASC` (так что `-10` идёт раньше `-1`, который идёт раньше `0`). Это согласовано с требованием «по возрастанию sort_order» и позволяет редактору вставить автора «выше стандартных», не вытесняя его из блока «принудительный порядок».
- Q2. Что делать с плашкой «Отдельные песни разных авторов», если в БД нет ни одного автора с `is_special_order=true` (например, в редакторской выборке, где `includeSkipped=true` отдаёт только не-спец-заказных)? → A: плашка НЕ отображается вообще (это уже поведение слота `#trailing`, гейтящегося по `specialBucket.length > 0`). В редакторском сценарии, где `specialBucket` пустой, скрытие плашки сохраняется. Никаких новых проверок «всегда ли есть» не нужно.
- Q3. Должна ли сортировка по `sort_order` действовать и в админ-таблице `AuthorsTable.vue`? → A: на этом раунде НЕ трогаем. Админ-таблица продолжит использовать свою серверную пагинацию/сортировку по колонкам. Поле `sort_order` только появится как редактируемая колонка (по аналогии с `is_special_order`), без изменения дефолтной сортировки. Это сужает скоуп: спека не про админ-таблицу как таковую, а про публичную сетку тайлов.
- Q4. Контракт синхронизации схемы LOCAL↔PROD для миграции `46_author_sort_order.sql`: как обеспечить, что обе БД получат колонку `sort_order`? → A: миграция применяется вручную на LOCAL и на PROD в одном PR; чек-лист PR явно фиксирует «миграция применена на обеих сторонах» (см. добавленный FR-013). Это согласуется с текущей практикой проекта (миграция 27 — единый файл, руками на обе стороны) и удерживает скоуп узким (без новой инфраструктуры автоматических миграций). Sync-механизм оперирует записями, не DDL, поэтому рассинхрон схемы (если кто-то забыл применить) проявится немедленно: первый push LOCAL→SERVER или SERVER→LOCAL на строке `tbl_authors` упадёт с `column "sort_order" does not exist` — это и есть наш естественный «canary» для обнаружения рассинхрона.
- Q5. Поведение кеша `authorsTilesCache` при изменении `sort_order` через админку: достаточно ли TTL ≤60с, или нужен явный hook-инвалидации? → A: TTL ≤60с достаточно; нового механизма инвалидации НЕ добавляем. Это соответствует текущей практике для других полей `tbl_authors` (`is_special_order`, `aliases`, `warning`) и удерживает скооп узким — не вводим новый hook в `StatBySong` или отдельный endpoint только ради одной фичи. 60-секундное окно несогласованности приемлемо, т.к. редактор правит `sort_order` не часто (1-2 раза в день); посетители видят изменения в течение минуты. Sync LOCAL→SERVER при изменении `sort_order` сам по себе может НЕ триггерить `StatBySong.consumeDirty()` (это событие про счётчики песен, не про `tbl_authors` напрямую), поэтому полагаемся именно на TTL, а не на dirty-флаг.
- Q6. Нужен ли особый визуальный/UX-эффект для спец-плашки в её новой роли «первый тайл»? → A: НЕТ — никаких новых визуальных эффектов не вводим. Текущего отличия через иконку 📁 (вместо `<img>` автора) достаточно для категоризации «это не обычный автор». Рамок, badges, smooth-scroll/focus на перенос не добавляем — задача №56 про **порядок**, не про дизайн; UX-доработки дизайна требуют отдельного ревью. Состояние `at-selected` для обычных тайлов работает как раньше — спец-плашка в нём не участвует (она использует свой `at-selected`-модификатор только при переходе в табличный режим `/zakroma/special-bucket`, см. существующий `.km-special-tile.at-selected`).

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Плашка «Отдельные песни разных авторов» отображается первой в сетке Закромов (Priority: P1)

Посетитель, открывший публичную страницу «Закрома» (`/zakroma`), видит сетку тайлов авторов. Виртуальная плашка «Отдельные песни разных авторов» (папка с иконкой 📁) отображается **первой** в сетке — слева сверху, в начале первой строки, — а не последней, как сейчас.

**Why this priority**: Это явное требование пользователя (задача №56) и самая заметная часть изменения. Сейчас плашка спрятана в слот `#trailing` после всех тайлов и визуально воспринимается как «случайный остаток», а не как легитимная категория. Перенос её в начало делает Закрома честной композицией «обычные авторы — отдельная группа спецзаказных».

**Independent Test**: Открыть `/zakroma` в браузере, убедиться, что в первой строке сетки первым тайлом идёт «Отдельные песни разных авторов» (с иконкой 📁), затем — обычные авторы. На тайле спец-плашки по-прежнему виден счётчик суммарного количества песен в группе (как сейчас).

**Acceptance Scenarios**:

1. **Given** посетитель открыл `/zakroma` и в БД есть хотя бы один автор с `is_special_order=true`,
   **When** страница отрендерилась и `authorTiles` пришли с бэкенда,
   **Then** в первой строке сетки первым DOM-элементом (по порядку отрисовки) является тайл «Отдельные песни разных авторов» (с иконкой 📁 и счётчиком `totalSpecialSongs`),
   **And** визуально он ничем не отличается от обычных тайлов по размеру и стилю (та же сетка `.at-grid`, тот же `.at-tile`).

2. **Given** посетитель открыл `/zakroma` и в БД нет ни одного автора с `is_special_order=true`,
   **When** страница отрендерилась,
   **Then** тайл «Отдельные песни разных авторов» НЕ отображается (поведение не изменилось — слот гейтится наличием `specialBucket`).

3. **Given** посетитель уже на `/zakroma/special-bucket` (табличное представление спец-группы),
   **When** он кликает по ссылке «← К списку авторов» в шапке,
   **Then** он возвращается на `/zakroma`,
   **And** плашка снова отображается первой в сетке (а не последней, как до фикса).

### User Story 2 — Авторы с заданным `sort_order` отображаются перед неотсортированными (Priority: P1)

Посетитель, открывший `/zakroma`, видит, что авторы, для которых в БД установлено поле `sort_order` (отличное от 0), идут **раньше** авторов с `sort_order = 0` (текущее поведение). Внутри обеих групп сохраняется порядок: для ненулевого `sort_order` — сортировка по возрастанию `sort_order`, для `sort_order = 0` — сортировка по алфавиту имени автора (как сейчас).

**Why this priority**: Это даёт редактору возможность управлять порядком плашек в Закромах, не прибегая к ручным правкам рендера. Приоритет — на одном уровне с переносом плашки, потому что без `sort_order` перенос плашки не имеет большого смысла (читатель всё равно увидит неупорядоченный список авторов).

**Independent Test**: Создать/обновить в БД нескольких авторов с `sort_order` 100, 5, -1. Открыть `/zakroma` и убедиться, что в сетке после плашки «Отдельные песни разных авторов» сначала идут авторы с `sort_order != 0` (в порядке -1, 5, 100), затем — авторы с `sort_order = 0` в алфавитном порядке.

**Acceptance Scenarios**:

1. **Given** в БД есть автор A (`sort_order = 5`), B (`sort_order = 100`), C (`sort_order = -1`), D (`sort_order = 0`),
   **When** посетитель открывает `/zakroma`,
   **Then** порядок тайлов в сетке (после плашки «Отдельные песни разных авторов»): C, A, B, D — независимо от того, какое имя у автора,
   **And** если добавить ещё автора E (`sort_order = 0`, имя начинается на «A…»), он идёт среди группы `sort_order = 0` в алфавитном порядке, после D и E — все остальные авторы с `sort_order = 0`.

2. **Given** ни у одного автора в БД нет ненулевого `sort_order` (все `sort_order = 0`),
   **When** посетитель открывает `/zakroma`,
   **Then** порядок тайлов совпадает с текущим поведением (алфавит по имени автора).

3. **Given** автор с `sort_order = 100` имеет `is_special_order = true`,
   **When** посетитель открывает `/zakroma`,
   **Then** этот автор НЕ отображается собственной плашкой (он попадает в группу «Отдельные песни разных авторов», как и раньше),
   **And** поле `sort_order` у него НЕ влияет на порядок в основной сетке (его там просто нет).

### User Story 3 — Редактор может менять `sort_order` у автора из админки (Priority: P2)

Зарегистрированный редактор в админ-таблице `webvue3/src/components/Authors/AuthorsTable.vue` видит новую колонку `sort_order` и может её редактировать (по аналогии с уже существующей `is_special_order`).

**Why this priority**: Без UI-возможности задать `sort_order` фича бесполезна: редактору пришлось бы править БД вручную. Приоритет P2, потому что фича может быть реализована поэтапно (сначала бэкенд + фронт Закромов, потом админка), но если её отложить — фича не закрыта до конца.

**Independent Test**: В админ-таблице `Authors` отредактировать `sort_order` у какого-нибудь автора (поставить 100), сохранить. Перезагрузить `/zakroma` на публичном сайте — автор должен подняться в начало (после плашки «Отдельные песни разных авторов», но перед всеми авторами с `sort_order = 0`).

**Acceptance Scenarios**:

1. **Given** редактор открыл `/authors` в `webvue3`,
   **When** страница отрендерилась,
   **Then** в таблице видна новая колонка `sort_order` со значением, совпадающим с БД (по умолчанию `0` для всех существующих авторов).

2. **Given** редактор кликнул на ячейку `sort_order` автора X и ввёл значение `50`,
   **When** он подтвердил сохранение,
   **Then** в БД `tbl_authors.sort_order = 50` у автора X,
   **And** после рефреша `/zakroma` (в т.ч. после инвалидации кеша `authorsTilesCache`) автор X появляется среди ненулевых `sort_order` в порядке возрастания.

3. **Given** редактор ввёл в `sort_order` нечисловое значение или пустую строку,
   **When** он пытается сохранить,
   **Then** UI блокирует сохранение с понятной ошибкой валидации (поле целое число, опционально — отрицательное).

### Edge Cases

- **Что если `sort_order` есть, но автор `is_special_order=true`?** — В основной сетке (`scope=main`) он не отображается; `sort_order` на него не действует. В сценарии `scope=all` (если редактор использует) — он появится в основной части сетки, но по `sort_order`. Решено в US2 acceptance 3.
- **Что если у двух авторов одинаковый ненулевой `sort_order`?** — Тай-брейкер — алфавит по имени (текущее правило), чтобы порядок был детерминирован. Закладываем в SQL: `ORDER BY sort_order ASC, author ASC` (см. SC-002).
- **Что если у всех авторов `sort_order = 0`?** — Порядок — алфавит по имени (как сейчас). US2 acceptance 2.
- **Что если плашка «Отдельные песни разных авторов» единственная (все остальные — `is_special_order=true`)?** — Тогда в `scope=main` основная сетка пустая, плашка всё равно первая (и единственная). Соответствует US1.
- **Что если посетитель был на `/zakroma/50` (выбран обычный автор), а потом переходит на `/zakroma` — спец-плашка первая, его автор пятидесятый. Визуальное состояние «выделенности» обычных тайлов (`at-selected`) конфликтует?** — Нет. Состояние `at-selected` устанавливается только для выбранного автора (`selected === t.author` в `AuthorTiles.vue`); спец-плашка в этот селектор не входит (она рендерится через слот/отдельный `<button>` в `ZakromaView.vue`). Спец-плашка имеет свой класс `at-selected`, но он активируется только при переходе в табличный режим `/zakroma/special-bucket` (см. Clarification Q6).
- **Что если `sort_order` принимает отрицательные значения?** — Допустимо (см. Clarification Q1); сортируются раньше нуля в `ORDER BY ASC`. Удобно для «принудительно поднять» автора.
- **Что если редактор сохранил автора с очень большим `sort_order` (например, 999_999_999)?** — Поведение корректное: автор уезжает в конец блока ненулевых. Ограничений сверху не закладываем (INTEGER в Postgres позволяет до 2³¹-1).
- **Что если применить миграцию дважды?** — `ADD COLUMN IF NOT EXISTS` уже идемпотентен в существующей миграции 27; новый скрипт пишем так же. `CREATE OR REPLACE FUNCTION` тоже идемпотентен. Recordhash-триггер пересоздаётся через `CREATE OR REPLACE FUNCTION` — повторный запуск безопасен.
- **Что если кеш `authorsTilesCache` старый (не учитывает новый порядок)?** — Кеш инвалидируется при изменениях через `StatBySong.consumeDirty()` (см. существующую логику). После деплоя нового бэкенда кеш заполнится свежими данными с новым `ORDER BY` при первом запросе; TTL — 60 секунд, так что максимум 60-секундное окно несогласованности (это приемлемо). Помимо этого, добавление нового поля в `recordhash` (через миграцию) делает любое изменение `sort_order` поводом для инвалидации по `consumeDirty`. Контракт явно зафиксирован в Clarification Q5: нового механизма инвалидации НЕ добавляем — TTL ≤60с достаточно (соответствует текущей практике для других полей `tbl_authors` — `is_special_order`, `aliases`, `warning`).
- **Что если миграция `46_author_sort_order.sql` применена только на одной стороне (LOCAL или PROD), а sync-механизм пытается push/pull `tbl_authors`?** — Sync сломается с ошибкой `column "sort_order" does not exist` на стороне, которая ещё не мигрирована. Это естественный canary (см. FR-013, Clarification Q4). Восстановление — докатить миграцию на отстающую сторону (`ADD COLUMN IF NOT EXISTS` идемпотентен, см. SC-004).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: System MUST добавить колонку `sort_order INTEGER NOT NULL DEFAULT 0` в таблицу `tbl_authors` (LOCAL и PROD отдельно). Миграция должна быть идемпотентной (повторный запуск не падает). См. [Миграции БД](#миграции-бд).
- **FR-002**: System MUST добавить колонку `sort_order` в `recordhash`-триггер для `tbl_authors` (LOCAL и PROD отдельно). Без этого изменения в `sort_order` не будут считаться расхождения LOCAL↔SERVER и не будут инициировать инвалидацию sync. См. Constitution Principle II/III.
- **FR-003**: System MUST обновить SQL в `Author.loadAuthorTilesWithCounts` так, чтобы ORDER BY был `sort_order ASC, author ASC` вместо текущего `author`. Это относится только к основной части запроса (после `WHERE is_special_order = false` / `WHERE is_special_order IS NULL`-аналога для `scope=main`). Для `scope=special` (если он ещё где-то используется) — поведение сортировки внутри спец-блока остаётся прежним (по алфавиту), потому что плашка с папкой — это единственная сущность, рендерящаяся из этого набора.
- **FR-004**: System MUST добавить поле `sortOrder: Int = 0` в `karaoke-app/.../model/Author.kt` (с аннотацией `@KaraokeDbTableField(name = "sort_order")`) и прокинуть его в `AuthorDTO` (имя JSON: `sortOrder`, camelCase по аналогии с `isSpecialOrder`). Аналогично — в `karaoke-web/.../dto/AuthorTilePublicDto.kt`, поле `sortOrder: Int = 0` (для консистентности payload, хотя публичный UI его сейчас не отображает).
- **FR-005**: System MUST перенести рендеринг плашки «Отдельные песни разных авторов» из слота `<template #trailing>` в начало сетки в `karaoke-public/src/views/ZakromaView.vue`. После переноса: (a) `<template #trailing>` в `ZakromaView.vue` удаляется; (b) в `AuthorTiles.vue` слот `#trailing` больше не используется (опционально — оставить на будущее, либо удалить, см. SC-005); (c) первый тайл сетки — это виртуальная плашка с иконкой 📁 и счётчиком `totalSpecialSongs`. Контракт явно зафиксирован в Clarification Q6: **никаких новых визуальных эффектов не вводим** — текущего отличия через иконку 📁 (вместо `<img>` автора) достаточно для категоризации. Рамок, badges, smooth-scroll/focus на перенос не добавляем (узкий скоуп: задача №56 про **порядок**, не про дизайн).
- **FR-006**: System MUST обновить публичный API `GET /api/public/authors-tiles`, чтобы DTO `AuthorTilePublicDto` отдавал `sortOrder` (Int), прокинутый из БД. Это требуется для консистентности payload (на случай, если публичный код когда-нибудь будет принимать решения по `sort_order`), и для будущего дебага в DevTools без обращения к БД.
- **FR-007**: System MUST оставить API-контракт `authorsTiles` обратно-совместимым: добавление поля `sortOrder` — это расширение JSON, существующие клиенты не должны ломаться (поля нет — значит `0`, см. дефолт DTO). Никаких breaking changes в URL, query-параметрах, статусах ответа.
- **FR-008**: System MUST добавить редактируемую колонку `sortOrder` в таблицу `webvue3/src/components/Authors/AuthorsTable.vue` (по аналогии с `isSpecialOrder`): отображение значения в ячейке + возможность редактирования (input type=number). Сохранение — через существующий механизм изменения полей автора. См. сценарий US3.

## Assumptions

- Решение о переносе плашки «Отдельные песни разных авторов» в начало **не** противоречит существующим UI-инвариантам проекта (сетка тайлов, размер тайла, иконка 📁 остаются теми же).
- Поле `sort_order` — `INTEGER` (4 байта, диапазон Postgres `INTEGER`: от -2³¹ до 2³¹-1). Это более чем достаточно для каталога авторов (тысячи записей).
- Существующая инфраструктура `recordhash` (Postgres-триггер `update_tbl_authors_recordhash`, см. миграцию `27_author_special_order.sql`) может быть переиспользована с минимальными изменениями: добавляем строку `COALESCE(NEW.sort_order::TEXT, '')` в md5-формулу.
- Существующая ORM-инфраструктура `KaraokeDbTable.loadList` (см. `karaoke-app/.../KaraokeDbTable.kt`) автоматически читает и пишет поля с аннотацией `@KaraokeDbTableField` — никаких изменений в самом `KaraokeDbTable` не требуется, только добавить аннотированное поле в `Author.kt`.
- Кеш `authorsTilesCache` НЕ нуждается в изменении cache key: новый порядок будет получен при следующем cache-miss (≤60 секунд) или при первой инвалидации `consumeDirty()`. Альтернатива (включение `sort_order` в cache key) — overkill.
- Дефолтный `sort_order = 0` для всех существующих авторов (бэкфилл в миграции) делается автоматически через `DEFAULT 0` в `ADD COLUMN`. Никаких ручных UPDATE'ов не нужно.
- Имя файла миграции: `46_author_sort_order.sql` (следующий свободный номер после 45). Это соглашение проекта (см. существующий список миграций — все они в формате `NN_<slug>.sql`).
- В админ-таблице `AuthorsTable.vue` редактирование `sort_order` будет происходить через тот же общий механизм сохранения полей автора, который уже используется для `is_special_order` (через `saveField`-style API, см. существующую логику вокруг `fld-isSpecialOrder`). Никаких новых endpoint'ов или DTO не потребуется, только добавление колонки в массив `fields` (или эквивалентную конфигурацию, см. `fldName: 'isSpecialOrder'` на строке 528 как референс).
- Логика «что делать, если спец-плашка единственная» (т.е. все видимые авторы — `is_special_order=true`) останется как есть: плашка отображается первой, остальная сетка пустая. Это естественно следует из текущего поведения `#trailing` (она показывалась единственной, если другие авторы не отдавались).

## Миграции БД

Создаём новый файл `deploy/karaoke-db/46_author_sort_order.sql`:

```sql
-- Сортировка авторов в публичной сетке Закромов.
--
-- Позволяет редактору задавать порядок плашек авторов в Закромах: ненулевые
-- sort_order идут перед нулевыми (внутри обеих групп — по алфавиту для нулевых
-- и по возрастанию sort_order для ненулевых).
--
-- Один раз на LOCAL и PROD отдельно.
-- Колонка входит в recordhash tbl_authors (FR по конституции).

ALTER TABLE public.tbl_authors
    ADD COLUMN IF NOT EXISTS sort_order INTEGER NOT NULL DEFAULT 0;

-- Обновляем recordhash-триггер: ВАЖНО включить новое поле в md5,
-- иначе изменения sort_order не будут считаться расхождениями LOCAL↔SERVER.
CREATE OR REPLACE FUNCTION public.update_tbl_authors_recordhash() RETURNS trigger
    LANGUAGE plpgsql
AS $$
BEGIN
    NEW.recordhash = md5(
                                COALESCE(NEW.id::TEXT, '') ||
                                COALESCE(NEW.author, '') ||
                                COALESCE(NEW.ym_id, '') ||
                                COALESCE(NEW.vk_id, '') ||
                                COALESCE(NEW.last_album_ym, '') ||
                                COALESCE(NEW.last_album_vk, '') ||
                                COALESCE(NEW.last_album_processed, '') ||
                                COALESCE(NEW.watched::TEXT, '') ||
                                COALESCE(NEW.skip::TEXT, '') ||
                                COALESCE(NEW.aliases, '') ||
                                COALESCE(NEW.is_special_order::TEXT, '') ||
                                COALESCE(NEW.sort_order::TEXT, '')
        );
RETURN NEW;
END;
$$;

-- Backfill recordhash для существующих строк (триггер сработает только на новые UPDATE/INSERT).
UPDATE public.tbl_authors SET recordhash = md5(
    COALESCE(id::TEXT, '') ||
    COALESCE(author, '') ||
    COALESCE(ym_id, '') ||
    COALESCE(vk_id, '') ||
    COALESCE(last_album_ym, '') ||
    COALESCE(last_album_vk, '') ||
    COALESCE(last_album_processed, '') ||
    COALESCE(watched::TEXT, '') ||
    COALESCE(skip::TEXT, '') ||
    COALESCE(aliases, '') ||
    COALESCE(is_special_order::TEXT, '') ||
    COALESCE(sort_order::TEXT, '')
) WHERE id > 0;
```
