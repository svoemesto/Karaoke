# Phase 0 Research: Поле `song_name_censored` в `tbl_songs`

## §1. Длина колонки `song_name_censored`

**Decision**: `VARCHAR(255) NOT NULL DEFAULT ''` — та же длина, что и
исходная `song_name`.

**Rationale**:
- В текущей схеме `tbl_songs.song_name VARCHAR(255)` (проверено через `psql
  \d tbl_songs` на LOCAL; соответствует шаблону `31_entity_description_fields.sql`,
  где новые колонки в `tbl_songs` имеют `VARCHAR(255)`).
- Цензурированная форма по построению НЕ длиннее исходной (замены слов на
  маски `█` той же или меньшей длины; максимум — добавление скобок `[ ]`
  из `getCensoredPair`, всё равно в пределах длины исходного слова).
- 255 — конвенция проекта для однострочных текстовых полей (использована в
  `short_description`, `warning`, и др. в `31_entity_description_fields.sql`).
- TEXT не используется — поле однострочное по смыслу (название песни).

**Alternatives considered**:
- `TEXT` (без ограничения длины) → отклонено: избыточно, нарушает
  единообразие схемы, в случае ручного ввода длинного текста увеличивает
  риск неожиданного переноса в публикациях.
- `VARCHAR(512)` или больше → отклонено: ни одно название в проде не
  превышает 255; проверка `MAX(LEN(song_name))` подтверждает запас.

## §2. Подход к миграции: одна SQL или миграция + фоновая функция

**Decision**: Два этапа:
1. **DDL + бэкфилл-копия** (одна SQL-миграция `42_song_name_censored.sql`):
   `ALTER TABLE` + `UPDATE tbl_songs SET song_name_censored = song_name`
   + пересборка `update_tbl_songs_recordhash()` + бэкфилл recordhash.
2. **Фоновая функция** (`Utils.rescanAllCensoredNames()`, endpoint
   `/api/utils/rescanallcensorednames`, кнопка CustomFunction в
   `HomeView.vue`): ПОСЛЕ деплоя кода — реckan по словарю.

**Rationale**:
- Миграция остаётся чисто DML/DDL — она не зависит от состояния
  `tbl_dictionaries` на момент применения (словарь может быть пустым
  после восстановления из бэкапа; миграция должна быть идемпотентной).
- Бэкфилл копией `song_name` гарантирует, что после миграции
  `song_name_censored != ''` (за исключением песен с пустым
  `song_name`); фронт/публичный код сразу читают корректное значение
  (просто ещё не цензурированное).
- Реальное цензурирование требует уже задеплоенного `karaoke-app` с
  функцией `Utils.rescanAllCensoredNames()` — это пользовательское
  действие ("нажми кнопку в админке"), а не часть миграции.
- Применение цензурирования в момент миграции было бы рискованно:
  требовало бы загружать `CensoredWordsDictionary` из Java-кода миграции,
  а миграция — это чистый SQL.

**Alternatives considered**:
- `UPDATE tbl_songs SET song_name_censored = regexp_replace(song_name,
  ..., '█', 'gi')` прямо в SQL → отклонено: регексп не повторит
  `String.censored(database)` точь-в-точь (там сложная логика: lookbehind/
  lookahead с `\p{L}\p{N}_`, два варианта с заглавной буквой; см.
  `Extentions.kt:214-230`); риск рассинхронизации между SQL и Kotlin.
- Применить цензурирование через триггер `BEFORE INSERT OR UPDATE` →
  отклонено: PostgreSQL pgsql-функция с полной логикой цензурирования
  будет дублировать Kotlin-код (хрупкость, см. выше); и триггер
  блокирует ручное редактирование `song_name_censored` (а оно нужно по
  US2).

## §3. Поведение авто-заполнения при `saveToDb()`

**Decision**: В `saveToDb()`, при формировании diff'а для UPDATE, ЕСЛИ
`fields[SongField.SONG_NAME_CENSORED]` пустое/отсутствует, но
`fields[SongField.NAME]` (т.е. `songName`) непустое — подставить
`songName.censored(database)` как baseline. Если `songNameCensored` уже
заполнено (из БД или ручным вводом) — НЕ трогать (FR-003).

**Rationale**:
- Соответствует US2-AC3: «переименование основного названия не
  перетирает ручную правку».
- Делает поведение идемпотентным: новые песни получают корректное
  цензурированное название без необходимости ждать CustomFunction.
- Покрывает кейс «запись прочитана без колонки (старый код)» — после
  апгрейда первое же сохранение проставит значение.

**Alternatives considered**:
- Авто-заполнять всегда (перезатирать ручные правки) → отклонено:
  нарушает US2-AC1/AC3 (ручной ввод теряется при любом сохранении).
- Не заполнять автоматически вообще → отклонено: требует обязательного
  прогона CustomFunction для каждой новой песни (плохой UX, плюс
  race-condition если песня публикуется до CustomFunction).
- Заполнять всегда через DEFAULT в БД (`DEFAULT censored(song_name)`) →
  невозможно: DEFAULT в Postgres — константа, нельзя вызвать функцию
  цензурирования.

## §4. Защита от гонок в `rescanAllCensoredNames()`

**Decision**: `@Volatile private var isRescanInProgress: Boolean = false`
на уровне `object Utils` (или companion). При входе — `if
(isRescanInProgress) return "ALREADY_RUNNING"`. В `finally` —
`isRescanInProgress = false`. Используется тот же паттерн, что и в
существующей `Utils.customFunction()` (см. строки 96-120).

**Rationale**:
- In-memory флаг достаточен: функция работает на одной JVM
  (`karaoke-app` — single-instance на admin-машине, см. Конституцию
  «Технологический стек»).
- В многопользовательском сценарии (несколько админов жмут кнопку
  одновременно) — flag честно сериализует попытки; второй получит
  немедленный ответ `ALREADY_RUNNING` без ожидания.
- Альтернатива (lock в БД через `pg_try_advisory_lock`) — избыточно:
  `karaoke-app` single-instance, race невозможна технически.

**Alternatives considered**:
- Без защиты → отклонено: может стартовать 2+ фоновых потока, оба
  пишут в `tbl_songs`, теряются UPDATE, удваивается нагрузка.
- Persist в KaraokeProperties (`rescanInProgress=true`) → отклонено:
  избыточно (JVM-уровень достаточен), плюс при крэше флаг застрянет.
- `pg_try_advisory_lock` → отклонено: одно-инстанс JVM, advisory lock
  не даёт преимущества, добавляет SQL-запрос на каждый вход.

## §5. Пакетная обработка в `rescanAllCensoredNames()`

**Decision**:
1. Сначала собрать ВСЕ `id` через `SELECT id FROM tbl_songs ORDER BY id`
   (один запрос).
2. Затем для каждого `id` (один за другим, последовательно) —
   `Song.loadFromDbById(id, database, ...)` (один SELECT с JOIN'ами по
   FK), сравнить `songNameCensored` в БД с `songName.censored(database)`;
   если отличается — `UPDATE tbl_songs SET song_name_censored = ? WHERE id
   = ?` (один UPDATE).
3. По завершении — SSE-тост с числом обработанных/изменённых строк и
   длительностью.

**Rationale**:
- Прямой SQL UPDATE без `loadFromDbById` (через
  `UPDATE tbl_songs SET song_name_censored = censored(song_name)` где
  `censored()` — pgsql-функция) — невозможно: нет pgsql-эквивалента
  Kotlin `String.censored()`.
- Загрузка полной `Song` через `loadFromDbById` — накладно (тянет FK,
  `result_text` и т.д.), но соответствует существующему паттерну
  (`Utils.customFunction` делает то же самое). Альтернатива — лёгкий
  SELECT только нужных колонок:
  ```sql
  SELECT id, song_name, song_name_censored FROM tbl_songs WHERE id IN (?, ?, ...)
  ```
  Это ускоряет реckan в ~5-10 раз; будет реализовано как
  оптимизация, если первая версия окажется медленной (>10 минут на
  проде).
- Последовательная обработка (не параллельная) — упрощает логику
  логирования и не создаёт конкурентных UPDATE на одну строку.

**Alternatives considered**:
- Один UPDATE на ВСЕ строки через `CASE WHEN ...` → невозможно: словарь
  «Censored» имеет сотни записей (см. `tbl_dictionaries WHERE
  dict_name='Censored'`), такой `UPDATE` синтаксически невозможен.
- Параллельные потоки по id-диапазонам → отклонено: не даёт выигрыша
  (узкое место — JDBC round-trip, а не CPU), усложняет логирование.

## §6. Tooltip в `SongEdit` для предупреждения редактора

**Decision**: Нативный атрибут `title="..."` на `<input>` поля
«Композиция (цензурированная)». Текст: «Ручное значение используется в
публикациях (VK/Telegram/News) и публичном API БЕЗ повторной фильтрации.
Редактируйте на свой страх и риск.»

**Rationale**:
- `title` — единственный нативный браузерный тултип без зависимостей
  (см. `research.md` в `specs/012-entity-description-fields` §2, тот же
  подход).
- Текст короткий, помещается в стандартный браузерный тултип (3 строки
  максимум); HTML внутри не используется (XSS-нейтрально).

**Alternatives considered**:
- Bootstrap JS tooltip (`new bootstrap.Tooltip(el, { html: true })`) →
  отклонено: требует инициализации в `mounted()`, HTML в тултипе — риск
  инъекции (наш `text` от разработчика, но паттерн опасен).
- Кастомный Vue-компонент `<HintTooltip>` → отклонено: 0 прецедентов в
  проекте (см. §2 в `012`), новый компонент ради одного места — избыточно.

## §7. Место нового поля в `SongEdit.vue`

**Decision**: В первом столбце тела (`column-1`) СРАЗУ под полем
«Композиция» (строки 106-126 `SongEdit.vue`). Тот же набор кнопок
(undo/copy/paste), что и у «Композиция»; `v-model="song.songNameCensored"`.

**Rationale**:
- Логическая близость: «Композиция» (исходник) и «Композиция
  (цензурированная)» (производное) рядом — редактор видит связь.
- Ширина/стиль — как у существующего поля, чтобы не ломать layout.
- Не добавлять в `fieldSongParams` в `webvue3-store` — поле НЕ должно
  быть отдельной колонкой в `SongsTable` (см. Assumptions в
  `spec.md`).

**Alternatives considered**:
- Поместить во второй столбец (`column-2`, рядом с датой/временем
  эфира) → отклонено: визуально далеко от «Композиции», путает
  редактора.
- Отдельная вкладка/модальное окно → отклонено: спека прямо просит
  «добавить в SongEdit», модалка избыточна.

## §8. Длина `song_name_censored` после цензурирования vs ручного ввода

**Decision**: Никаких ограничений на длину ручного ввода в SongEdit
(стандартный `<input maxlength>` НЕ ставим). Если редактор ввёл строку
> 255 символов — `INSERT`/`UPDATE` упадёт с DB-ошибкой «value too long for
type varchar(255)», пользователь увидит стандартное сообщение об ошибке.

**Rationale**:
- 255 — запас для всех разумных кейсов (цензурированные названия
  коротки; ручные правки редко превышают 100 символов).
- Сознательное ограничение «длинный текст не пройдёт» — фича, а не
  баг: предотвращает случайный ввод многострочного описания в
  однострочное поле.

**Alternatives considered**:
- `VARCHAR(1024)` или `TEXT` → отклонено: см. §1.
- `maxlength="255"` на `<input>` → отклонено: пользователь может
  обойти через paste из другого источника; пусть БД даст честную
  ошибку.
