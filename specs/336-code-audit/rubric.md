# Рубрика аудита кода Karaoke

> Контракт для всех порций аудита по карте #337 / задаче #336.
> Утверждено владельцем 2026-10-23 («продолжай без остановки»); правки — только словом владельца.
> Снимок: `master` @ `1977838a`. Охват: 1 032 файла / 259 827 строк, 78 порций (`inventory.md`, `coverage-ledger.csv`).

## 1. Что считается дефектом

Дефект — свойство кода, которое при достижимом сценарии приводит хотя бы к одному из:

- неверному результату (ответ API, поле DTO, сортировка, расчёт, отображение данных);
- потере или порче данных (БД, файлы, кэш, маркеры, метаданные, очередь);
- отказу или недоступности (необработанное исключение, зависание, deadlock, исчерпание пула);
- утечке ресурсов (JDBC-соединения, потоки, executor'ы, файловые дескрипторы, память, подписки, листенеры);
- нарушению безопасности (обход доступа, инъекция, XSS, утечка секрета, CSRF, небезопасный путь);
- нарушению MUST-инварианта (конституция, `AGENTS.md`, R-04…R-44, инварианты доменов `knowledge/`) с поведенческим или операционным следствием.

Достижимость обязательна: аудитор описывает сценарий или путь вызова. «Теоретически возможно» без пути — не дефект, а «сверка» (§ 7).

## 2. Что дефектом не считается

- форматирование, отступы, naming, порядок импортов (ktlint, Prettier, ESLint-стиль);
- вкусовщина и «можно красивее»;
- отсутствующая функциональность;
- косметика UI без влияния на поведение и данные;
- уже зафиксированные baseline-нарушения (на 2026-10-23 — одна запись ktlint, см. `tooling-coverage.md`);
- опечатки в документации, не ведущие к неверному использованию API;
- мёртвый код без риска (не считаем, если нет утечки/неверного поведения).

## 3. Классы

| Класс | Что покрывает | Минимальное доказательство |
|---|---|---|
| `SEC` | authn/authz, инъекции (SQL, HTML, команда), XSS, секреты, десериализация, CSRF, open redirect, path traversal | точный путь от входной точки до опасного sink; для authz — какой субъект и какое право |
| `DATA` | неверная запись, потеря/порча, отсутствие транзакции, усечение/кодировка, lost update в БД, рассинхрон кэша, миграция | путь записи/чтения и что именно портится; для миграций — DDL и порядок |
| `RACE` | гонки на общем состоянии, check-then-act, `ThreadLocal`, deadlock, двойное выполнение, порядок async | два потока/вызова и чередование, при котором ломается |
| `LEAK` | JDBC, потоки, executor'ы, файлы, память, подписки/листенеры, кэш без вытеснения | место захвата и место (не)освобождения; для JDBC — путь `getConnection()` |
| `ERR` | проглоченное исключение, потерянный throwable/стек, неверный HTTP-код, null/пустое значение, неограниченный retry, молчаливый fallback | цитата catch/лога и что теряется для диагностики или пользователя |
| `PERF` | O(n²), N+1, блокировка в async/SSE, неограниченная память, повторный I/O в цикле, огромный payload | горячий путь и оценка роста; замер — если дёшево |
| `COMPAT` | контракт DTO↔UI, поле API, `ignoreUnknownKeys`, тип колонки БД, рассинхрон версий, регистр в именах | обе стороны контракта: продюсер и потребитель |
| `RULE` | нарушение MUST/архитектурного правила с поведенческим или операционным следствием | правило + следствие; без следствия — не запись |
| `TEST` | неверный assert, `@Disabled`, скрывающий дефект, flaky, тест не в CI, тест не может упасть | тест + что он на самом деле проверяет; severity ≤ S3 |
| `BUILD` | Dockerfile/nginx/compose/gradle/package: невоспроизводимость, небезопасный образ, сломанный build-контракт | конфиг + следствие для сборки/деплоя; severity ≤ S2 |

Класс — свойство находки, не файла. Одна находка — один класс; если корень один, а следствия разных классов, запись идёт по наиболее тяжёлому следствию, остальные перечисляются в тексте.

## 4. Severity

| Уровень | Когда | Примеры |
|---|---|---|
| `S1` | публичный периметр, обход auth, утечка/порча данных, деньги, отказ прода, утечка секрета; обхода нет | XSS на публичной странице; платёж без идемпотентности; исчерпание пула до отказа |
| `S2` | сломанная функция или серьёзная деградация, есть обходной путь; админский периметр; ограниченный радиус; медленная утечка | массовая операция теряет часть записей; редактор сохраняет не ту песню; утечка соединений при нагрузке |
| `S3` | редкий/краевой сценарий, админская косметика, гигиена тестов/сборки, defense-in-depth без достижимого пути | неверный код в недостижимой ветке; `printStackTrace` в редком catch; baseline-механизм с абсолютным путём |

Правила калибровки:

- сомневаешься между S1 и S2 — ставь S2 и помечай `severity: под вопросом`;
- сомневаешься между S2 и S3 — ставь S3 и помечай;
- `TEST` — не выше S3; `BUILD` — не выше S2;
- severity нарушения правила = severity следствия, а не важность правила;
- S1 без эмпирики допустим, только если путь доказан статически и помечен `эмпирика: требует согласия`.

## 5. Источники правил (приоритет)

1. `.specify/memory/constitution.md` — Principles I–IX.
2. `AGENTS.md` Tier-1 MUST и Hard Gates.
3. `knowledge/guidelines/architecture-conventions.md` — R-04…R-44.
4. `knowledge/guidelines/code-style.md`.
5. `knowledge/domains/**` — инварианты домена; `knowledge/adr/**` — принятые решения.

Конфликт источников не разрешается молча: запись уходит в «Требует решения владельца» с обеими трактовками.

## 6. Доказательства

- **Статика (обязательна)**: точный `path:line` на зафиксированном SHA, цитата не длиннее 5 строк, объяснение «почему это дефект», при необходимости — путь вызова.
- **Эмпирика (где дёшево)**: команда, окружение, ожидаемое/фактическое. Локальные unit-тесты — можно, с командой и результатом. Playwright/API — только против уже запущенной сборки, read-only.
- **Запрещено без согласия владельца**: перезапуск/пересборка `karaoke-app`, запись в БД, изменения прод-данных, `docker restart`. Если проверка требует этого — `эмпирика: требует согласия`, запись не блокируется.
- Ссылка на существующий тест доказательством не является: тесты не гоняются в CI (см. `tooling-coverage.md`); нужен локальный прогон лида.

## 7. «Требует решения владельца»

Формат: вопрос, две (или более) трактовки, доказательство, почему важно. Пример: «`read`-метод требует право `create` — намеренная политика или копипаста из create-метода?». Такие записи не получают severity до вердикта; в отчёте идут отдельным разделом. Владелец разбирает пакетом после отчёта.

## 8. Дедупликация

Одна причина — одна запись. Зеркала (один корень в нескольких местах) перечисляются в одной записи списком локаций. Дубли между порциями сводит лид через реестр `registry.csv` по ключу «механизм + семейство файлов». Если два аудитора нашли одно и то же — выживает запись с более полным доказательством, вторая уходит в её «Найдено также».

## 9. Шаблон записи

```markdown
### BR-001: path/File.kt:120–135 — SEC (S2)
- Что не так: <одно-два предложения>
- Доказательство: «<цитата ≤5 строк>» (path:line, SHA)
- Путь: <входная точка → ... → sink/запись>
- Поправка: <что сделать, без реализации>
- Найдено в: порция P-XX, аудитор <id>
- Автор (git blame): <имя> (<email>, <дата>, <path:line>)
- Severity: S2 — <почему именно S2, одна строка>
- Статус: TODO
- Проверено лидом: да/нет
```

## 10. Статусы

- `TODO` — подтверждённый дефект, ждёт отдельной задачи на исправление;
- `NEEDS-VERDICT` — «баг или задумано», ждёт владельца;
- `FIXED` / `WONTFIX` — в отчёт аудита не попадают (это уже не дефект).

## 11. Калибровочные примеры

1. **S1, SEC.** HTML собирается из пользовательского текста и уходит в `v-html` на публичной странице без экранирования → XSS. Доказательство: sink + источник + публичный маршрут.
2. **S2, LEAK.** `getConnection()` на поток без гарантированного освобождения; при переключении страниц пул исчерпывается. Доказательство: путь захвата, отсутствие `close()` в ветке.
3. **S3, TEST.** ESLint-baseline хранит абсолютный `filePath` — механизм даст ложные «новые» нарушения при непустом baseline. Доказательство: поле в JSON + код сравнения.
4. **S3, ERR.** `printStackTrace()` вместо логгера в редкой ветке — стек не попадает в централизованные логи. Если ветка достижима из публичного обработчика — повышается до S2.
