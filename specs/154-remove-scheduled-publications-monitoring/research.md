# Phase 0 Research: Убрать мониторинг запланированных публикаций

Технический контекст (`plan.md`) не содержит нерешённых `NEEDS CLARIFICATION` —
область фичи была однозначно определена через `codegraph_explore` до написания
плана (единственная проверка, соответствующая описанию «мониторинг
запланированных публикаций», — `TelegramHorizonCheck`). Ниже — решения,
принятые при проектировании точечного удаления.

## 1. Полное удаление проверки vs. отключение флагом

**Decision**: удалить `TelegramHorizonCheck.kt` целиком и убрать его из
`MonitorRegistry.checks`, а не добавлять флаг «включена/выключена».

**Rationale**: пользователь явно попросил убрать этот тип мониторинга, потому
что сам отслеживаемый концепт (ручное планирование публикаций «наперёд»)
устарел — публикации теперь генерируются системой в нужный момент. Флаг
«выключить, но оставить код» оставил бы недостижимый мёртвый код и лишнюю
настройку без функционального смысла, что усложняет чтение `MonitorRegistry`
и противоречит принципу «не добавлять код ради гипотетического будущего».

**Alternatives considered**:
- *Оставить проверку, но выключить по умолчанию через существующий паттерн
  `KaraokeProperties.getBoolean(...)` (как у `TelegramPollingDisabledCheck`)* —
  отклонено: сама проверка/её настройка порога перестают иметь смысл (нечего
  измерять), а не временно нежелательны; оставлять «мёртвый» тумблер без
  причины — источник путаницы (тот же класс проблемы, которую фича должна
  устранить).
- *Пометить `@Deprecated`, но не удалять из реестра* — отклонено: проверка
  продолжала бы выполняться на каждом тике и потенциально формировать алерты,
  что напрямую противоречит FR-001/FR-002 спецификации («не должна
  выполняться и не должна показываться»).

## 2. Судьба ранее сохранённого состояния `monitorDismissed["telegram.horizon"]`

**Decision**: не писать отдельную миграцию/очистку значения `KaraokeProperty
monitorDismissed` (JSON-строка `key -> contentHash`) — оставить как есть.

**Rationale**: после удаления `TelegramHorizonCheck` новых алертов с ключом
`telegram.horizon` формироваться не будет, поэтому старая запись в JSON-карте
никогда больше не читается и не сравнивается ни с чем (см.
`MonitoringService`/`docs/features/monitoring.md`, механизм «прочитано» —
хэш вычисляется только для алертов из актуального снапшота проверок).
Оставшийся ключ — инертный «мусор» в служебном JSON-поле, не влияющий на UI и
не вызывающий ошибок; отдельная задача на очистку добавляла бы риск (ручной
парсинг/перезапись пользовательских настроек) без функциональной пользы.

**Alternatives considered**:
- *Одноразовый скрипт/код при старте приложения, вычищающий ключ
  `telegram.horizon` из `monitorDismissed`* — отклонено: несоразмерная
  сложность ради поля, которое никогда больше не читается; соответствует
  принципу «не добавлять код ради проблемы, которая не возникает».

## 3. Обновление `docs/features/monitoring.md` (FR-009)

**Decision**: обновить нумерацию («восемь проверок» → «семь проверок») и
убрать пункт «Горизонт запланированных постов в Telegram (< N дней)» из
списка проверок в разделе «Как работает (кратко)». Отдельная запись в разделе
«Ссылки на ключевые классы/файлы» для этой проверки отсутствовала изначально
(там перечислены только общие файлы фреймворка + `LaneStalledCheck.kt` как
пример нетривиальной проверки) — значит, ссылок удалять не требуется.

**Rationale**: `docs/features/monitoring.md` — per-feature документ подсистемы
«monitoring» (один из 9 ключевых, см. `docs/features/README.md`); Принцип VI
(FR-009) требует обновить его в том же PR, где меняется код фичи.

**Alternatives considered**: не рассматривались — обновление обязательно по
Конституции, вариативности в подходе нет.

## 4. Связь со `specs/153-fix-app-oom-crash` (параллельная фича)

**Decision**: не редактировать артефакты `specs/153-fix-app-oom-crash/` в
рамках этой фичи.

**Rationale**: `specs/153` упоminает `TelegramHorizonCheck` только как один из
*примеров* проверки, читающей список песен (иллюстрация общего паттерна
«плановая проверка тянет `Song.loadListFromDb`», а не зависимость от
конкретного класса) — устранение этого класса не меняет сути и обоснованности
той фичи (общая защита `MonitoringService.tick()` от `OutOfMemoryError` для
ЛЮБОЙ проверки, включая оставшиеся семь). Правка чужой уже согласованной
спецификации без отдельного запроса — вне рамок этой фичи.

**Alternatives considered**:
- *Заменить упоминания `TelegramHorizonCheck` в `specs/153/*.md` на другой
  пример* — отклонено как избыточное для этой фичи; при реализации `specs/153`
  (если это ещё не сделано) достаточно, чтобы автор той фичи заметил
  расхождение по ходу работы — риск минимален, т.к. упоминания носят
  иллюстративный, а не нормативный характер.

## Итог

Все решения приняты, `NEEDS CLARIFICATION` не осталось. Переходим к Phase 1.
