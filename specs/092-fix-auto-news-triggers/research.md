# Research: Триггеры авто-новостей независимо от синхронизации + альбом/год в тексте

## 1. Три триггера = три вызова уже существующей идемпотентной функции

**Decision**: Не создавать новую бизнес-логику детекции «песня публично доступна» и новую
идемпотентность. Все три триггера (синхронизация — уже существует; эфир по расписанию — новый;
апрув/сохранение — новый) вызывают ровно одну и ту же функцию —
`SongReleaseAnnouncementService.checkAndAnnounce(database, storageService, storageApiClient)`
(specs/089-auto-news-song-release), без изменений в её внутренней логике детекции.

**Rationale**: Функция уже инкапсулирует и строгий критерий готовности (`Song.isPubliclyWatchable`),
и идемпотентность (`SongNewsAnnounced`/`tbl_song_news_announced`, `PRIMARY KEY(song_id)`). Вызов её из
трёх разных точек автоматически даёт FR-006/FR-010 spec.md (ровно одна новость на событие, независимо
от того, какой триггер сработал первым) бесплатно — конкурентная защита уже встроена в
`ON CONFLICT (song_id) DO NOTHING` внутри `SongNewsAnnounced.markAnnounced`.

**Alternatives considered**:
- Отдельная копия критерия готовности/идемпотентности для каждого триггера — отклонено: прямое
  нарушение `feedback_verify_all_independent_implementations`-класса риска (несколько независимых
  копий одного и того же условия неизбежно расходятся со временем).
- Событийная шина (message queue) между тремя триггерами и единым обработчиком — избыточно для
  масштаба проекта (единицы событий готовности в месяц, см. spec.md Scale/Scope) и добавляет новую
  инфраструктурную зависимость без реальной необходимости.

## 2. Где физически может (и не может) сработать «мгновенный» апрув-триггер

**Находка**: `SongEditorController.approve()` (`karaoke-app`, admin-машина) всегда применяет
`id_status = 6` к **LOCAL**-копии песни (комментарий в коде: «применение разметки... и подъём
id_status ВСЕГДА идёт в LOCAL, независимо от target — karaoke-app умеет писать .srt и резолвить
rootFolder только на локальном диске админ-машины»). Затем, если `Karaoke.allowUpdateRemote == true`,
метод best-effort пушит именно эту песню на сервер через `updateRemoteSongFromLocalDatabase(id)` →
`updateDatabases(fromDatabase=Connection.local(), toDatabase=Connection.remote(), keys=["settings"], ...)`.

Прослежен путь `updateDatabases()` для случая `toDatabase.name == "SERVER"`: фактическая запись
(`INSERT`/`UPDATE`) идёт **не** прямым JDBC, а батчем зашифрованных SQL-выражений через
`POST https://sm-karaoke.ru/changerecords` — тот же самый HTTP-эндпоинт (`MainController.doChangeRecords`,
`karaoke-web`, PROD), который уже сегодня вызывает `checkAndAnnounce` в конце обработки (specs/089).

**Вывод**: `karaoke-web` в момент клика администратора «Апрувить» вообще не выполняется — единственный
код, реально исполняющийся в этот момент, — `karaoke-app` на admin-машине. `karaoke-web` реагирует
(если вообще реагирует) только позже, асинхронно, при получении HTTP-запроса от push-механизма — и
именно поэтому «хук на `save()`», расположенный в `karaoke-web`, был бы физически не в состоянии
сработать мгновенно: события, отправленного от approve(), там просто нет как отдельного события — есть
только очередной вызов `/changerecords` с диффом, неотличимый от обычной синхронизации.

## 3. Почему нельзя просто положиться на уже существующий вызов `checkAndAnnounce` внутри `/changerecords`

**Находка**: раз push от `approve()` в итоге доходит до `/changerecords`, а тот уже вызывает
`checkAndAnnounce` — теоретически новость могла бы уже создаваться сегодня почти сразу после апрува,
**если** одновременно выполнены два независимых runtime-условия:
1. `Karaoke.allowUpdateRemote == true` (общий тумблер «разрешить пуш на сервер», тот же, что у кнопки
   «Обновить на сервере» в `SongEdit.vue`);
2. per-key sync-разрешение push/update для сущности `settings` (`Song`) в `KaraokeProperties`
   (`sync_settings_push_update_allowed` — управляется отдельно, тем же тумблером, что и обычная
   «Синхронизация в 1 клик», и может быть выключено намеренно, чтобы избежать случайного массового
   перезаписывания данных на PROD при обычной синхронизации).

Оба условия — **orthogonal** к этой фиче: они существуют для общего механизма синхронизации, а не для
гарантии видимости конкретной новости. Наблюдаемый пользователем разрыв («апрув делает песню доступной
на проде, но новость не появляется без отдельной синхронизации») с высокой вероятностью объясняется
именно тем, что одно из этих двух условий на PROD сейчас не выполняется (пуш либо выключен, либо
молча не проходит — `approve()` **сознательно** проглатывает ошибку пуша: «best-effort, ошибка пуша не
должна откатывать уже совершённый апрув»).

**Decision**: не полагаться на этот путь. Вместо этого — явный, отдельный вызов `checkAndAnnounce`
прямо в `approve()`, **напрямую** на `Connection.remote()`, выполняемый только если push реально
подтверждённо применился (`updateRemoteSongFromLocalDatabase(id)` возвращает непустой `SyncResult` —
`created`/`updated` непусты). Это устраняет зависимость от двух orthogonal-тумблеров и делает
поведение детерминированным и не зависящим от конфигурации, не связанной с этой фичей.

Технически это не новый прецедент: тот же метод `approve()` **уже сегодня** пишет напрямую в
`Connection.remote()` — при `target == "remote"` статус апрува `SongAssignment` (`aRead.adminStatus`,
`aRead.save()`) читается и пишется прямо на remote-соединении, в обход `SyncRegistry`. Прямой JDBC
доступ из `karaoke-app` к PROD Postgres — уже используемый, принятый в кодовой базе паттерн.

**Alternatives considered**:
- Дожидаться и полагаться на существующий путь через `/changerecords` — отклонено (см. выше,
  недетерминированность из-за orthogonal runtime-тумблеров).
- Проверять готовность песни асинхронным фоновым потоком сразу после approve() — отклонено как
  избыточное усложнение: `checkAndAnnounce` уже достаточно дешёвая синхронная операция (двухфазный
  id-скан + полная загрузка только кандидатов), синхронный вызов не создаёт заметной задержки ответа
  HTTP-запроса `approve`.

## 4. Периодическая проверка эфира — новый `@Scheduled`-компонент в `karaoke-web`

**Decision**: Новый Spring-компонент `SongReleaseAnnouncementScheduler` в
`karaoke-web/src/main/kotlin/com/svoemesto/karaokeweb/services/`, по образцу уже существующих
`StatsCacheScheduler` (`@Scheduled(cron = "0 0 * * * *")`) и `StemJobTempCleanupScheduler`
(`@Scheduled(fixedDelay = ...)`). Метод помечен `@Scheduled(fixedDelay = 5 * 60_000L, initialDelay = ...)`
и вызывает `SongReleaseAnnouncementService.checkAndAnnounce(WORKING_DATABASE, storageService, storageApiClient)`
— ту же функцию, что и `MainController.doChangeRecords`, с теми же Spring-инжектируемыми бинами
(`WebKaraokeStorageServiceImpl`/`StorageApiClientWeb`, уже используемые `MainController`).

**Rationale**: `karaoke-web` — единственный backend-модуль, реально и непрерывно работающий на PROD
(Constitution Principle I: `karaoke-app` на PROD не разворачивается вовсе) — соответственно, только
там может жить процесс, не зависящий от того, зашёл ли администратор и запустил ли что-то вручную.
Паттерн `@Scheduled`-компонента с фиксированной задержкой уже устоялся в проекте (два похожих примера
в том же пакете) — переиспользование паттерна снижает риск и объём ревью.

**Alternatives considered**:
- Cron на уровне ОС/systemd timer, дёргающий HTTP-эндпоинт (например, обёртку над `/changerecords`)
  — отклонено как избыточное усложнение по сравнению с уже принятым в проекте `@Scheduled`-подходом;
  добавляет внешнюю точку отказа (нужно ещё и следить, что cron-джоб на сервере вообще настроен).
- Уменьшать периодичность существующего вызова внутри `/changerecords`, вместо отдельного джоба —
  отклонено: он по-прежнему зависел бы от факта запуска синхронизации, что прямо противоречит FR-001
  spec.md («не должно быть завязано на механизм синхронизации»).

## 5. Альбом и год в тексте новости

**Decision**: Расширить построение `title`/`body` внутри
`SongReleaseAnnouncementService.checkAndAnnounce()` (единственное место, формирующее текст для всех
трёх триггеров) — использовать уже существующие read-only свойства `Song.album: String` (пустая
строка, если не заполнено) и `Song.year: Long` (`0L`, если не заполнено). Если значение пустое/0 —
соответствующая часть текста не добавляется (без плейсхолдера, FR-008 spec.md).

**Rationale**: Единая точка формирования текста для всех триггеров — правки формата делаются один раз
и автоматически применяются везде. Данные уже присутствуют на объекте `Song`, загруженном
`checkAndAnnounce` для проверки готовности — дополнительных запросов к БД не требуется.

**Alternatives considered**: н/д — тривиальное расширение существующей строки, альтернативных
источников данных нет (`Song.album`/`Song.year` — единственные существующие поля с этим смыслом, см.
`SongField.ALBUM`/`SongField.YEAR`).

## 6. Формат текста при отсутствующих альбоме/годе

**Decision**: Собирать текст конкатенацией непустых частей, например:
`"${author} — ${songName}" + (if (album.isNotBlank()) " (альбом «$album»" else "") + (if (year > 0) ", $year" else "") + (if (album.isNotBlank()) ")" else "")`
— конкретная пунктуация уточняется на этапе реализации (`tasks.md`), но правило неизменно: ни один из
трёх случаев (оба заполнены / только альбом / только год / ни один) не должен давать пустых
плейсхолдеров вида «Альбом: » или висящих скобок.

**Rationale**: Соответствует FR-008/User Story 3 spec.md — новость всегда читается как связный текст
независимо от того, какие поля у песни заполнены.

**Alternatives considered**: н/д — единственное разумное поведение, все альтернативы («показывать
плейсхолдер», «не создавать новость без полного набора данных») были явно отклонены в spec.md
(Edge Cases, FR-008).
