# Feature Specification: Кликабельные название песни и автор в плейлисте/избранном

**Feature Branch**: `259-playlist-clickable-links`
**Created**: 2026-08-27
**Status**: Draft
**Input**: User description: "В избранном/плейлисте название песни сделать кликабельным - переход на страницу песни. Автор тоже кликабелен - переход в закрома этого автора."

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Переход из строки плейлиста на страницу песни (Priority: P1)

Зарегистрированный пользователь открывает свой плейлист (или «Избранное»),
видит список песен. Название каждой песни в строке теперь является ссылкой.
Клик по названию открывает страницу этой песни (`/song?id=<songId>`) в новой
вкладке (модификатор не требуется — обычный клик) с сохранением истории
браузера и работающим back-link из SongView обратно на страницу песен автора.

**Why this priority**: Это центральное действие пользователя — «узнал песню в
списке → захотел посмотреть подробности/послушать → перешёл». Без этого
плейлист остаётся «слепым списком», из которого невозможно попасть на саму
страницу песни без перехода в «Закрома» или «Поиск».

**Independent Test**: Залогиниться, добавить 2-3 песни в «Избранное», открыть
`/account/playlists/<favorites-id>`. В каждой строке списка название песни
должно быть визуально ссылкой (цвет/подчёркивание/hover) и при клике
переводить на `/song?id=<songId>` для соответствующей песни. Тест проходит,
если для всех песен в плейлисте клик по названию открывает страницу именно
этой песни (а не какой-то другой / не 404 / не остаётся в плейлисте).

**Acceptance Scenarios**:

1. **Given** пользователь залогинен и открыл плейлист с N песнями,
   **When** он кликает по названию песни в любой строке,
   **Then** открывается страница этой песни (`/song?id=<songId>` той самой
   песни), back-link SongView ведёт на страницу песен её автора
   (`/zakroma/<authorId>`), плеер не запускается автоматически.

2. **Given** пользователь находится на странице редактирования плейлиста,
   **When** он кликает по названию песни,
   **Then** встроенный в страницу iframe-плеер НЕ запускается от этого
   клика (только кнопка `▶` в строке должна его запускать, как и сейчас).

3. **Given** пользователь нажимает на название песни с зажатым Ctrl/Cmd
   (или средней кнопкой мыши),
   **When** срабатывает системный «открыть в новой вкладке»,
   **Then** страница песни открывается в новой вкладке, исходная вкладка
   остаётся на плейлисте без изменений.

### User Story 1.b — Back-link SongView ведёт на страницу песен автора (Priority: P1)

На странице песни (`/song?id=X`) левая ссылка в шапке (динамический back-link)
должна вести на страницу песен того автора, чья это песня
(`/zakroma/<authorId>`), а не на общий список авторов. Это работает для
любого сценария входа на `/song`: плейлист, поиск, закрома, прямой URL,
share-сессия.

**Why this priority**: Без правильного back-link кликабельные ссылки в
плейлисте/поиске (US1, US2) создают «чёрную дыру» — пользователь уходит
на страницу песни, но back ведёт в общий каталог, теряя контекст автора.
Это ломает основной сценарий «нашёл песню → послушал → вернулся к автору».

**Why через DTO, а не referrer**: ID автора однозначно известен по самой
песне — `Song.author` это свободный текст, FK на `tbl_authors` отсутствует,
но имя однозначно резолвится в `tbl_authors.id`. Простой batch-запрос
`Author.loadIdsByNames([name], db)` даёт `authorId`, который фронт
использует напрямую. Никаких referrer'ов через Vuex, никаких race в
`mounted` (vue-router 4 переиспользует инстанс компонента при смене
маршрута на тот же), никакой логики «откуда пришёл пользователь».

**Independent Test**: Открыть любую песню из любой точки (плейлист,
поиск, закрома, прямой URL). Левая ссылка в шапке должна вести на
`/zakroma/<authorId>` для автора этой песни. Тест проходит, если back
всегда указывает на страницу песен того же автора, чья песня открыта.

**Acceptance Scenarios**:

1. **Given** пользователь открыл песню автора X любым способом (из
   плейлиста, поиска, закромов, прямого URL, share-сессии),
   **When** он смотрит на шапку SongView,
   **Then** back-link указывает на `/zakroma/<authorId>` для автора X
   (label: `← К песням «X»`).

2. **Given** пользователь кликнул по названию песни в плейлисте,
   **When** он попал на `/song?id=X` и нажал back-link в шапке,
   **Then** он возвращается на `/zakroma/<authorId>` (страница песен
   автора этой песни), а НЕ на плейлист или общий `/zakroma`.

3. **Given** автор песни удалён из `tbl_authors` (имя есть в `tbl_songs`,
   но нет соответствующей записи в `tbl_authors`),
   **When** пользователь открывает эту песню,
   **Then** `SongPublicDto.authorId = null` → back-link fallback на
   `/zakroma` (общий каталог), без падения и без 404.

### User Story 2 — Переход из строки плейлиста в «Закрома» автора (Priority: P1)

В той же строке плейлиста имя автора (например, «Кино») тоже является
ссылкой. Клик по нему открывает «Закрома» именно этого автора
(`/zakroma/<authorId>`), где можно увидеть все его песни, доступные на сайте.

**Why this priority**: Это второй базовый сценарий исследования музыки
через плейлист: «нравится один трек → посмотреть, что ещё у этого автора».
Без этого пользователь вынужден возвращаться в «Поиск» или «Закрома» и
искать автора вручную.

**Independent Test**: Залогиниться, открыть «Избранное» с песнями разных
авторов (минимум 2 разных имени). Кликнуть по имени автора в строке.
Должно открыться `/zakroma/<authorId>` для этого автора, и в тайтлах
«Закромов» этот автор должен быть помечен как выбранный. Тест проходит,
если имя автора в строке резолвится в правильный `authorId` и открывает
закрома именно этого (а не другого) автора.

**Acceptance Scenarios**:

1. **Given** пользователь открыл плейлист, в котором есть песни 2+ разных
   авторов,
   **When** он кликает по имени автора в строке одной песни,
   **Then** открывается страница «Закрома автора» (`/zakroma/<authorId>`),
   где authorId соответствует именно этому автору (определяется по
   резолвингу `author` → `id` через кэш `authorTiles` Vuex).

2. **Given** пользователь открывает плейлист анонимно (не залогинен),
   **When** отображается LoginRequired вместо списка песен,
   **Then** ссылки из этого сценария не появляются (страница не показывает
   контент плейлиста, а значит и нет кликабельных ссылок).

3. **Given** автор песни больше не существует в БД (запись удалена из
   `tbl_authors`, но осталась в плейлисте),
   **When** пользователь кликает по имени такого автора,
   **Then** система НЕ открывает «не ту» страницу и НЕ валится с 404:
   кликабельность отключается (имя отображается как обычный текст), либо
   клик показывает уведомление «Автор больше не доступен» и остаётся на
   плейлисте.

### User Story 3 — Единообразие поведения в «Избранном» и пользовательских плейлистах (Priority: P2)

Поведение должно быть одинаковым и в системном плейлисте «Избранное»
(`playlist.favorites === true`), и в любом пользовательском плейлисте.
Визуальное оформление ссылок (цвет, hover, focus) — единое, без
разделения по типу плейлиста.

**Why this priority**: В проекте один компонент (`PlaylistEditView.vue`)
обслуживает и «Избранное», и пользовательские плейлисты. Различие в
поведении ссылок между ними — лишняя когнитивная нагрузка на пользователя
источник багов.

**Independent Test**: Сравнить поведение клика по названию/автору в
«Избранном» и в обычном плейлисте — должно быть идентичным.

**Acceptance Scenarios**:

1. **Given** пользователь открыл «Избранное»,
   **When** он кликает по названию песни или по имени автора,
   **Then** реакция полностью совпадает с реакцией в обычном плейлисте
   (одинаковые маршруты, одинаковая визуальная обратная связь).

---

### Edge Cases

- **Автор с пустым именем** (`item.author === ''`): имя автора не должно
  рендериться как ссылка; либо вообще скрыто. Сценарий US2 не применяется.
- **Автор не найден в `authorTiles`** (резолв `name → id` не дал результата):
  клик по имени автора НЕ открывает «Закрома». Либо имя показывается как
  обычный текст, либо показывается короткое уведомление «Автор больше не
  доступен» (но без перехода).
- **Длинное название песни** (занимает >1 строки или обрезается в строке):
  ссылка должна оставаться работоспособной, hover/click работают по всей
  области текста, а не только по первой строке.
- **Длинное имя автора** (занимает >1 строки или обрезается): аналогично
  предыдущему — ссылка работоспособна.
- **Список песен пуст** (только что созданный плейлист без песен): блок
  ссылок не рендерится (там нечего оборачивать в `<a>`).
- **`authorTiles` ещё не загружены** к моменту рендера строки плейлиста:
  кликабельность откладывается до завершения загрузки (показать как обычный
  текст), без ошибки в консоли.
- **Картинки-превью** (cover/author pic) кликабельны отдельно или нет — НЕ
  входит в этот scope. Меняется только текст «название песни» и текст
  «автор».

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: System MUST рендерить название песни в каждой строке
  плейлиста/избранного как интерактивный элемент (кликабельная ссылка),
  при клике переходящий на страницу этой песни.
- **FR-002**: System MUST рендерить имя автора в каждой строке
  плейлиста/избранного как интерактивный элемент (кликабельная ссылка),
  при клике переходящий на страницу «Закрома» именно этого автора.
- **FR-003**: System MUST НЕ менять поведение клика по кнопке `▶` в строке
  плейлиста (запуск встроенного плеера с этой песни) и НЕ менять поведение
  drag-drop, mute и удаления из плейлиста.
- **FR-004**: System MUST НЕ запускать встроенный iframe-плеер при клике
  по названию песни или по имени автора (только переход на соответствующую
  страницу).
- **FR-005**: System MUST поддерживать открытие ссылки в новой вкладке
  нативным способом браузера (Ctrl/Cmd+клик, средняя кнопка мыши,
  контекстное меню «Открыть в новой вкладке»).
- **FR-006**: System MUST резолвить `author` (имя) в `authorId` через уже
  существующий кэш `authorTiles` в Vuex (никаких дополнительных
  HTTP-запросов на каждый клик). Если резолв не удался — клик по имени
  автора НЕ открывает «Закрома» (см. Edge Case «автор не найден»).
- **FR-007**: System MUST визуально отличать ссылки от окружающего текста
  (цветом акцента и/или подчёркиванием при hover), без агрессивного
  изменения layout (без выделения рамкой, без сдвига строк).
- **FR-008**: System MUST быть совместимым с текущим маршрутом страницы
  песни: переход ведёт на `/song?id=<songId>` (без `authorId` в URL — это
  сохраняет существующий контракт, зафиксированный в спеке 258).
- **FR-009**: System MUST быть совместимым с текущим маршрутом «Закромов
  автора»: переход ведёт на `/zakroma/<authorId>` (по числовому ID).
- **FR-010**: System MUST работать одинаково в обоих дизайнах
  (`classic`/`modern`), используя существующие CSS-переменные `--km-*`.
- **FR-011**: System MUST НЕ нарушать персистентность порядка песен
  (drag-drop), mute-флагов и настроек плейлиста (`continuous`,
  `repeatMode`, `shuffle`): новые обработчики кликов изолированы от
  существующих.
- **FR-012**: Бэкенд `karaoke-web` MUST возвращать `authorId: Long?` в
  `SongPublicDto` (заполняется в `PublicApiController.song()` через
  `Author.loadIdsByNames([s.author], db)`). Это даёт фронту однозначный
  back-link из SongView на страницу песен автора — без referrer'ов через
  Vuex, без race в `mounted`, без зависимости от «откуда пришёл
  пользователь». `authorId = null` допустим (автор удалён из
  `tbl_authors`) — SongView fallback на общий `/zakroma`.
- **FR-013**: System MUST НЕ использовать Vuex `zakroma.lastSongReferrer`
  (или любой подобный state) для back-link в SongView. Единственный
  источник истины — `currentSong.authorId` из `SongPublicDto`. (Старая
  логика спеки 258 — `lastSongReferrer` — удаляется вместе со state,
  getter и mutation в сторе.)

### Key Entities *(include if feature involves data)*

- **PlaylistItem (UI)**: элемент строки плейлиста. Содержит `songId`,
  `songName`, `author` (имя), `album`, `year`, `albumPictureUrl`,
  `authorPictureUrl`, `muted`, `position`. Источник — `SitePlaylistItemDto`
  (бэк не меняется).
- **SongPublicDto.authorId** (бэк): новый nullable-столбец в DTO. Резолвится
  из `Song.author` через `Author.loadIdsByNames([author], db)` — один
  batch-SELECT в `tbl_authors` (`SELECT id, author WHERE author IN (?)`).
  null если автора нет в `tbl_authors`.
- **Author (резолв имени → ID, для кликабельной ссылки имени в плейлисте)**:
  уже закэширован во Vuex как `state.zakroma.authorTiles` (массив
  `{ id, author, ... }`). Используется только для маппинга
  `item.author` → `authorId` для ссылки «имя автора» в строке плейлиста.
- **Song (назначение ссылки)**: страница `/song?id=<songId>` принимает
  только числовой `songId` (см. FR-008, спека 258).
- **Author zakroma (назначение ссылки)**: страница `/zakroma/:authorId`
  принимает только числовой `authorId` в path-параметре.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% строк плейлиста/избранного (где есть название песни и
  имя автора) имеют кликабельное название песни и кликабельное имя
  автора. Проверка: открыть плейлист с 50 песнями → все 50 строк имеют
  обе ссылки.
- **SC-002**: Клик по названию песни приводит на правильную страницу
  песни в 100% случаев (никаких «не той песни» / 404 / зацикливания
  внутри плейлиста). Проверка: для плейлиста из 30 случайных песен —
  каждый из 30 кликов открывает ожидаемую страницу.
- **SC-003**: Клик по имени автора приводит на «Закрома» именно этого
  автора в 100% случаев для всех авторов, присутствующих в `authorTiles`.
  Проверка: для плейлиста из песен ≥3 разных авторов — каждый из 3+ кликов
  открывает «Закрома» нужного автора.
- **SC-004**: Существующие действия (drag-drop, mute, удаление, play,
  переименование плейлиста, смена настроек) продолжают работать без
  регрессий после внедрения ссылок. Проверка: ручной сценарий + автотесты
  (если есть) проходят без изменений в поведении.
- **SC-005**: Back-link в шапке SongView ведёт на страницу песен автора
  (того, чья песня открыта) в 100% случаев — для всех сценариев входа
  (плейлист, поиск, закрома, прямой URL, share-сессия). Проверка:
  открыть 5 песен 5 разных авторов из 5 разных точек входа → back в
  каждом случае ведёт на `/zakroma/<authorId>` соответствующего автора.
- **SC-006**: Никаких регрессий в существующих API/контроллерах бэка:
  добавлен только новый optional-поле `authorId` в `SongPublicDto` (+1
  batch-SELECT в `PublicApiController.song()`). Все остальные эндпоинты,
  DTO, контроллеры — без изменений. Проверка: ревью diff'а
  `karaoke-web/src/main/kotlin` показывает только `SongPublicDto.kt` и
  `PublicApiController.kt`.

## Assumptions

- Зарегистрированный пользователь — единственный пользователь списков
  плейлиста/избранного; аноним видит `LoginRequired` и не имеет доступа к
  списку (тогда ссылок нет в DOM, сценарий не применяется).
- Бэкенд возвращает `item.author` (имя автора) в `SitePlaylistItemDto`
  (это уже подтверждено в `SitePlaylistItemDto.kt:26`). Никаких изменений
  бэка в этой части DTO не требуется.
- `Song.author` (свободный текст, НЕ FK) однозначно резолвится в
  `tbl_authors.id` по `WHERE author = ?` — это контракт данных (имя
  автора в песне всегда совпадает с записью в `tbl_authors`). Если
  автор удалён из `tbl_authors` — `authorId = null`, SongView fallback
  на общий `/zakroma`.
- `authorTiles` (Vuex, модуль `zakroma`) уже загружается до
  `PlaylistEditView` (через глобальный bootstrap `App.vue` или
  `PlaylistEditView.onMounted`); если кэш пуст — догружаем по требованию
  (как в `ZakromaView` и `router.beforeEach`).
- Все авторы, чьи песни есть в плейлистах, присутствуют в `tbl_authors` и
  отдаются через `/api/public/authors-tiles`. Если автора удалили из БД —
  Edge Case US2.3 / US1.b.3 обрабатывается мягко (без падения).
- Текущий визуальный стиль строки плейлиста (Bootstrap 5 + CSS-переменные
  `--km-*`) остаётся; ссылка наследует цвет акцента `var(--km-accent)` и
  получает подчёркивание при hover/focus.
- Маршрут страницы песни `/song?id=<songId>` (без `authorId`) — это
  устоявшийся контракт, который менять в этой спеке не нужно (см. спеку
  258, FR-A8).
