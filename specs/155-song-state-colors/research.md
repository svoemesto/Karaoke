# Research: актуализация статусов и цветов песен

## Контекст исследования

Фича меняет производную классификацию песни, которая рассчитывается в `karaoke-app`, передаётся через `SongDTO`/`SongDTOdigest` и используется `webvue3` для окраски строк. Текущий расчёт дополнительно учитывает наличие публикаций в Telegram, VK, Dzen и других каналах, поэтому не соответствует модели онлайн-плеера.

## Решения

### Decision 1: Сохранить единый источник классификации

- **Decision**: оставить `SongState` единственным набором состояний песни, а `Song.state` — единой точкой расчёта.
- **Rationale**: таблица песен и сетка публикаций уже получают цвет через DTO песни; отдельный статус для каждого UI-модуля создаст расхождения.
- **Alternatives considered**: рассчитывать цвет отдельно во Vue и в сетке публикаций — отклонено из-за дублирования бизнес-правил и риска разных результатов.

### Decision 2: Использовать приоритеты онлайн-доступности

- **Decision**: применять порядок `IN_WORK` → `ON_AIR` для `free` или текущего бесплатного окна → `EXCLUSIVE` для готовой песни без действительного расписания → `TODAY` для сегодняшнего будущего эфира → `DONE` для остальных готовых песен с расписанием.
- **Rationale**: `idStatus < 6` всегда означает работу; постоянная бесплатность не зависит от даты; исторический эфир после окончания бесплатного окна не должен оставаться `ON_AIR`.
- **Alternatives considered**: считать любую дату в прошлом постоянным `ON_AIR` — отклонено, поскольку это противоречит действующему окну бесплатного доступа и правилу `DONE`.

### Decision 3: Сделать расчёт времени тестируемым

- **Decision**: сохранить публичное свойство состояния песни, но вынести вычисление в чистый внутренний путь с явным значением текущего времени для тестов.
- **Rationale**: тесты границ «эфир ещё не наступил», «эфир наступил» и «окно завершилось» не должны зависеть от реальных часов запуска.
- **Alternatives considered**: строить тесты только на относительных датах и системных часах — отклонено из-за нестабильности на границе минут/дней и часовых поясов.

### Decision 4: Удалить старый fallback цвета для `IN_WORK`

- **Decision**: при пустом цвете `IN_WORK` передавать пустую строку, не подставляя цвет старого статуса `idStatus`.
- **Rationale**: спецификация требует отсутствия специальной окраски для `IN_WORK`; старые цвета по стадиям жизненного цикла визуально смешивают два разных понятия.
- **Alternatives considered**: оставить белый/стадийный fallback — отклонено требованиями FR-006 и FR-011.

### Decision 5: Сузить контракт цветовых кнопок до пяти состояний

- **Decision**: `/api/publications/date` и `PublishTableFooter.vue` используют только `STATE_DONE`, `STATE_TODAY`, `STATE_ON_AIR`, `STATE_EXCLUSIVE`, `STATE_IN_WORK`.
- **Rationale**: это сохраняет ровно пять состояний из спецификации и удаляет зависимость UI от старых кодов площадок и отдельных стадий.
- **Alternatives considered**: оставить `STATE_*` старых площадок и `STATUS_0..6` как дополнительные кнопки — отклонено, поскольку пользователь явно требует удалить остальные статусы и в интерфейсе останутся устаревшие варианты.

### Decision 6: Не менять схему и синхронизацию данных

- **Decision**: не добавлять миграции, колонки, sync-target или флаги синхронизации.
- **Rationale**: состояние и цвет являются производными значениями; изменяются только правила вычисления и потребители уже существующего цвета.
- **Alternatives considered**: хранить новый статус в БД и синхронизировать его между LOCAL/SERVER — отклонено как дублирование источника истины и потенциальная рассинхронизация по времени.

### Decision 7: Покрыть классификацию офлайн-тестами

- **Decision**: добавить JUnit 5 unit-тесты в `karaoke-app/src/test/kotlin/com/svoemesto/karaokeapp/model/SongStateTest.kt`, а UI/API проверить отдельным ручным quickstart-сценарием.
- **Rationale**: вычисление не требует БД, сети или Spring-контекста; существующий `SpecTagsTest.kt` показывает принятый офлайн-паттерн.
- **Alternatives considered**: полагаться только на интеграционные тесты или ручную проверку — отклонено, потому что матрица из пяти состояний и временные границы должны регрессионно проверяться автоматически.

## Разрешённые неизвестные

- Тестовый стек определён существующим `spring-boot-starter-test`, JUnit Platform и офлайн-тестами в модуле `karaoke-app`.
- Внешние интеграции отсутствуют: меняется только внутренний административный endpoint и его Vue-потребитель.
- Новая per-feature документация должна быть добавлена при реализации по правилу Constitution VI/FR-009; это не отдельная модель данных и не миграция.
