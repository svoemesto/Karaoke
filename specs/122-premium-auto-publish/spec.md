# Feature Specification: Премиум-автопубликация в Telegram и ВК при появлении песни в коллекции

**Feature Branch**: `122-premium-auto-publish`

**Created**: 2026-08-03

**Status**: Draft

**Input**: User description: "Когда песня апрувится в заданиях редактора она становится "готовой" и происходит создание новости на проде и публикации в вк, но не происходит публикации в телеграм - а должна. В этот момент у песни ещё нет демо-видео - но должно сформироваться задание на рендер этого видео а после его окончания - опубликоваться в телеграм."

## Контекст

Когда администратор апрувит задание редактора (`SongEditorController.approve`),
песня получает `idStatus=6` и полный набор readiness-флагов. Это событие
одновременно триггерит **два независимых, ранее задокументированных**
механизма:

1. **Новость «доступна» / «в коллекции»** (`category="premium"`,
   `specs/101-song-news-flag`) — `Song.markNewsAvailableIfReady()` внутри
   `saveToDb()` при первом переходе `newsAvailableAnnounced` false→true
   создаёт запись `tbl_news`; сама новость появляется на проде при
   следующей серверной синхронизации
   (`SongReleaseAnnouncementService.detectAndAnnounceAvailability`,
   вызывается из `MainController.doChangeRecords`).
2. **ВК-текст «в коллекции»** — тот же переход одновременно (в том же
   `markNewsAvailableIfReady()`) выставляет `newsPremiumPublishPending=true`,
   что забирает `PremiumAutoPublishScheduler` (тик каждые 30 сек) и
   публикует пост в группу ВК через `VkAutoPublishService.publishToVk(song,
   PublicationType.PREMIUM, persistPostId=false)`.

**Важное открытие, сделанное при подготовке этой спецификации**: третий
канал — **Telegram-премиум** — уже реализован в коде (тот же
`PremiumAutoPublishScheduler` вызывает
`TelegramAutoPublishService.publishToTelegram(song, publicationType=PREMIUM,
persistMessageId=false)`), и код многократно ссылается на несуществующий
`specs/122-premium-auto-publish` (см. `PremiumAutoPublishScheduler.kt`,
`TelegramAutoPublishService.kt`, `KaraokeProperties.kt`) — то есть фича
**уже смёржена в master** (коммиты `1386f063`, `59d13e72`), но никогда не
имела собственной спеки. Эта спецификация:

- **Backfill** — задним числом документирует уже реализованное поведение
  (чтобы ссылки `specs/122-premium-auto-publish` в коде наконец указывали
  на реальный документ);
- **Fix** — фиксирует конкретный симптом из баг-репорта (Telegram-премиум
  публикация не происходит для песни без готового демо-видео) и превращает
  найденные при разборе кода подозрительные места в проверяемые
  требования.

При разборе выяснено, что конфигурационные флаги на момент репорта были:
`telegramAutoPublishEnabled=true`, `vkAutoPublishEnabled=false` (не влияет
на премиум-канал — `PremiumAutoPublishScheduler` не проверяет этот флаг),
`premiumAutoPublishEnabled=true`. То есть баг-репорт **не** объясняется
простой невключённой настройкой — расхождение поведения ВК/Telegram имеет
структурную причину:

- **ВК-премиум публикуется синхронно и мгновенно**, потому что дефолтный
  шаблон `vkTemplatePremium` не содержит маркера `{demoVideo}` (community
  token не имеет прав на `video.save`, см. `KaraokeProperties.kt`) —
  `VkAutoPublishService.publishTextOnly` отправляет пост без видео в тот же
  тик, без какой-либо зависимости от рендера.
- **Telegram-премиум всегда требует готового демо-MP4** (у Bot API
  `sendVideo` нет текстового fallback). Если файла нет,
  `TelegramAutoPublishService.startRenderAndReturn` ставит задачу
  `RENDER_MP4_DEMO` и переводит песню в состояние `rendering`
  (`telegramAutoPublishState`), **не завершая публикацию в этом тике**.
- Завершение отложенной публикации (`onRenderCompleted`) сегодня вызывается
  **только** из `TelegramAutoPublishScheduler.resumeRenderingSongs()` —
  планировщика, исторически принадлежащего Phase 2 «в эфире»
  (`specs/113-telegram-demo-publish`), который сам по себе гейтится флагом
  `telegramAutoPublishEnabled` и не имеет отношения к премиум-циклу по
  смыслу. `PremiumAutoPublishScheduler` не содержит собственной логики
  «продолжить рендерящуюся премиум-песню» — он полагается на побочный
  эффект чужого тика. Если администратор захочет выключить Phase 2
  (`telegramAutoPublishEnabled=false`), оставив включённым только премиум
  (`premiumAutoPublishEnabled=true`), премиум-рендеры Telegram зависнут в
  состоянии `rendering` навсегда — молча, без ошибки.
- Администратор сегодня **не видит** в `webvue3` состояние
  премиум-публикации по конкретной песне (`newsPremiumPublishPending` /
  `newsPremiumTelegramSent` / `newsPremiumVkSent` / `premiumAutoPublishState`
  / `premiumAutoPublishLastError`) нигде, кроме одного одноразового диалога
  бэкфилла на `HomeView.vue` — в карточке песни (`SongEdit.vue`) или таблице
  песен эти поля не отображаются и не редактируются. Это ровно то, из-за
  чего баг-репорт вообще стало возможно составить только предположительно
  (без единого способа посмотреть на реальное состояние конкретной песни).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Telegram-премиум публикуется автоматически и надёжно, включая рендер отсутствующего демо (Priority: P1)

Когда песня апрувится редактором и становится «доступна» (переход
`newsAvailableAnnounced` false→true), в Telegram-канал автоматически
появляется премиум-пост с демо-видео песни — точно так же надёжно, как уже
происходит для новости на проде и для текстового поста ВК. Если демо-MP4
ещё не существует, система сама ставит задачу рендера и публикует пост
сразу после его завершения, без участия администратора и без зависимости
от того, включён ли отдельно Phase 2 (`telegramAutoPublishEnabled`).

**Why this priority**: Это единственная причина, по которой эта
спецификация вообще написана — административный баг-репорт: «должно
происходить, но не происходит». Без надёжного завершения этого пути
остальные user stories (видимость/мониторинг) лечат симптом, а не причину.

**Independent Test**: Подготовить песню без отрендеренного демо-MP4,
апрувить задание редактора (или иначе перевести `newsAvailableAnnounced` в
`false→true`) при `premiumAutoPublishEnabled=true` и
`telegramAutoPublishEnabled=false` (специально выключен, чтобы исключить
скрытую зависимость от Phase 2). Дождаться завершения рендера. Убедиться,
что в Telegram-канале появился пост с демо-видео и подписью по
`telegramTemplatePremium`, `Song.newsPremiumTelegramSent=true`,
`Song.idTelegramDemo` при этом остаётся пустым (FR-004
`specs/113-telegram-demo-publish` — слот зарезервирован для будущей
AIR-публикации).

**Acceptance Scenarios**:

1. **Given** песня апрувлена, полностью готова (readiness-флаги + маркеры),
   но демо-MP4 ещё не существует, **When** происходит переход
   `newsAvailableAnnounced` false→true, **Then** система ставит задачу
   `RENDER_MP4_DEMO` в очередь и, после её успешного завершения,
   автоматически публикует пост с этим видео в Telegram-канал — без
   ручного нажатия какой-либо кнопки.
2. **Given** `telegramAutoPublishEnabled=false` (Phase 2 «в эфире»
   выключена администратором), а `premiumAutoPublishEnabled=true`,
   **When** премиум-Telegram-публикация нуждается в рендере демо-MP4,
   **Then** рендер всё равно завершается публикацией в Telegram — эта
   завершающая логика не должна зависеть от флага, управляющего другой
   фичей (Phase 2).
3. **Given** демо-MP4 уже существует и укладывается в лимит размера
   Telegram на момент перехода `newsAvailableAnnounced` false→true,
   **When** срабатывает премиум-тик, **Then** пост публикуется в течение
   одного тика `PremiumAutoPublishScheduler` (без ожидания рендера).
4. **Given** Telegram-премиум для песни уже выполнен
   (`newsPremiumTelegramSent=true`), **When** происходит повторный тик
   планировщика (рестарт, ручной вызов), **Then** повторный пост в канал
   не создаётся (идемпотентность сохраняется, FR-008
   `specs/113-telegram-demo-publish`, наследуется без изменений).

### User Story 2 - Администратор видит статус премиум-публикации песни в карточке песни (Priority: P1)

Администратор открывает карточку песни (`SongEdit.vue`) и видит, в каком
состоянии находится премиум-автопубликация по каждому каналу отдельно:
ожидает / рендерится / публикуется / опубликовано / ошибка — вместо
единственного способа сегодня (смотреть в БД напрямую или полагаться на
одноразовый диалог бэкфилла на `HomeView.vue`).

**Why this priority**: Баг-репорт этой спецификации стало возможным
составить только предположительно — администратор не мог отличить
«ещё рендерится» от «зависло» от «упало с ошибкой». Без видимого статуса
любая будущая проблема снова будет обнаруживаться только через жалобу
пользователей канала, а не через интерфейс администратора.

**Independent Test**: Открыть карточку песни, для которой
`newsPremiumPublishPending=true` и `telegramAutoPublishState="rendering"`.
Убедиться, что в карточке виден статус «Рендерится» для Telegram-премиум
канала отдельно от статуса ВК-премиум канала. Дождаться завершения —
статус переходит в «Опубликовано»/«Ошибка отправки».

**Acceptance Scenarios**:

1. **Given** песня, у которой `newsPremiumPublishPending=true`, **When**
   администратор открывает её карточку в `webvue3`, **Then** он видит два
   независимых статуса — «Telegram (премиум)» и «ВК (премиум)» — каждый
   в одном из состояний: «Ожидает» / «Рендерится» / «Публикуется» /
   «Опубликовано» / «Ошибка отправки».
2. **Given** `premiumAutoPublishState="FAILED"` и заполнено
   `premiumAutoPublishLastError`, **When** администратор открывает
   карточку песни, **Then** он видит текст последней ошибки и канал(ы), в
   которых публикация не удалась.
3. **Given** оба канала (`newsPremiumTelegramSent` и `newsPremiumVkSent`)
   уже `true`, **When** администратор открывает карточку песни, **Then**
   отображается «Опубликовано» для обоих каналов, без действий
   доступных администратору (идемпотентно, повторной публикации не
   предлагается).

### User Story 3 - Администратор может вручную перезапустить упавшую премиум-публикацию (Priority: P2)

Если премиум-публикация в одном из каналов окончательно провалилась
(`premiumAutoPublishState="FAILED"` после исчерпания попыток,
FR-013 `PremiumAutoPublishScheduler`), администратор может вручную
повторить попытку прямо из карточки песни, не прибегая к прямым
SQL-правкам или обращению к разработчику.

**Why this priority**: Без ручного пути восстановления единственный выход
сегодня — правка полей в БД напрямую (что и происходило раньше, судя по
существующему одноразовому диалогу бэкфилла на `HomeView.vue`). Это
менее приоритетно, чем сама надёжность (User Story 1) и видимость
(User Story 2), потому что уже существуют "сырые" ручные endpoint'ы
(`/api/song/publishPremiumTelegram`, `/api/song/publishPremiumVk`), просто
без UI поверх них.

**Independent Test**: Довести тестовую песню до `premiumAutoPublishState="FAILED"`
(например, временно указав пустой `telegramAutoPublishChannelId`, дождавшись
исчерпания попыток). Восстановить конфигурацию, нажать кнопку «Повторить»
в карточке песни. Убедиться, что публикация проходит успешно и статус
меняется на «Опубликовано».

**Acceptance Scenarios**:

1. **Given** `premiumAutoPublishState="FAILED"` для конкретного канала,
   **When** администратор нажимает «Повторить» в карточке песни, **Then**
   система сбрасывает состояние этого канала в исходное («Ожидает») и
   немедленно инициирует попытку публикации заново (через существующие
   `/api/song/publishPremiumTelegram` / `/api/song/publishPremiumVk`).
2. **Given** повторная попытка успешна, **When** администратор обновляет
   карточку песни, **Then** статус канала — «Опубликовано».

### Edge Cases

- **ВК-премиум публикуется мгновенно (синхронно, без видео), Telegram —
  асинхронно (с рендером)** — эта асимметрия каналов должна быть видна
  администратору явно (User Story 2), а не восприниматься как «баг»
  каждый раз, когда Telegram отстаёт от ВК на время рендера.
- **`telegramAutoPublishEnabled=false` при `premiumAutoPublishEnabled=true`**
  — завершение отложенного премиум-рендера Telegram не должно зависеть от
  флага чужой фичи (Phase 2 «в эфире») — см. User Story 1, сценарий 2.
- **Одновременный рендер для AIR и PREMIUM одной и той же песни** — оба
  типа публикации рендерят один и тот же файл (`RENDER_MP4_DEMO`,
  `RenderVersion.DEMO`); если процесс уже идёт, повторная постановка в
  очередь не создаёт дубль задачи (существующая защита
  `KaraokeProcess.createProcess` — `processId <= 0` при уже работающей
  задаче), и любой из завершившихся тиков корректно продолжает публикацию
  через динамическое переопределение `effectivePublicationType`/`effectiveType`
  по `newsPremiumPublishPending` (уже реализовано, см.
  `TelegramAutoPublishService.onRenderCompleted`,
  `VkAutoPublishService.onRenderCompleted`) — эта логика остаётся без
  изменений, но должна быть покрыта тестом (сегодня не покрыта, см.
  Assumptions).
- **`premiumAttemptCount` — общий счётчик на два канала** — одна неудачная
  попытка в Telegram и одна в ВК суммарно быстрее достигают
  `premiumAutoPublishMaxAttempts`, чем если бы у каждого канала был свой
  счётчик. При независимом сбое одного канала (не обоих) это может
  привести к преждевременному `FAILED` для канала, который в
  действительности ещё не исчерпал разумное число попыток. Требует
  явного решения при планировании (раздельные счётчики на канал, либо
  задокументированное намеренное поведение "на два канала суммарно").
- **Рендер завершается с ошибкой (`ERROR`)** — оба сервиса
  (`TelegramAutoPublishService`/`VkAutoPublishService`) уже фиксируют
  `SEND_FAILED` с текстом ошибки рендера — это поведение остаётся, но
  должно быть видно администратору (User Story 2).
- **Файл демо-MP4 превышает лимит канала** — существующая логика
  перерендера с уменьшенными параметрами (`specs/113`/`specs/121`
  аналог) переиспользуется без изменений для премиум-типа.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система ДОЛЖНА автоматически публиковать премиум-пост с
  демо-видео песни в Telegram-канал при первом переходе
  `Song.newsAvailableAnnounced` false→true (то же событие, что уже
  создаёт новость «в коллекции» на проде и текстовый пост ВК), без
  ручных действий администратора — независимо от того, существует ли
  на этот момент демо-MP4-файл.
- **FR-002**: Если демо-MP4-файл для песни отсутствует или превышает лимит
  размера Telegram Bot API на момент срабатывания FR-001, система ДОЛЖНА
  поставить задачу рендера `RENDER_MP4_DEMO` в асинхронную очередь и
  опубликовать премиум-пост в Telegram сразу по её успешному завершению —
  без дополнительного участия администратора и без ожидания следующего
  ручного триггера.
- **FR-003**: Завершение отложенного премиум-рендера Telegram (FR-002)
  НЕ ДОЛЖНО зависеть от состояния флага `telegramAutoPublishEnabled`
  (управляющего отдельной фичей `specs/113-telegram-demo-publish`,
  Phase 2 «в эфире»). Если `premiumAutoPublishEnabled=true`, премиум-канал
  Telegram должен надёжно доводить до конца любой рендер, который сам же
  инициировал, вне зависимости от того, включена ли Phase 2.
- **FR-004**: Идемпотентность премиум-публикации Telegram ДОЛЖНА
  сохраняться в точности как реализовано сегодня: `Song.idTelegramDemo`
  НЕ заполняется премиум-публикацией (слот зарезервирован для будущей
  AIR-публикации при выходе песни в эфир); признак «премиум в Telegram
  уже отправлен» — отдельное поле `Song.newsPremiumTelegramSent`. Если
  оно уже `true` — повторная публикация не выполняется.
- **FR-005**: Если `Song.idTelegramDemo` уже заполнено (AIR-публикация
  уже произошла раньше премиум-тика) на момент срабатывания FR-001,
  премиум-публикация Telegram ДОЛЖНА считаться выполненной без
  повторной отправки (существующее поведение `publishToTelegram` —
  без изменений).
- **FR-006**: Администратор ДОЛЖЕН видеть в карточке песни (`SongEdit.vue`
  в `webvue3`) текущее состояние премиум-автопубликации раздельно по
  каналам Telegram и ВК: одно из «Ожидает» / «Рендерится» / «Публикуется»
  / «Опубликовано» / «Ошибка отправки» — выведенное из существующих полей
  `telegramAutoPublishState`/`vkAutoPublishState` (с учётом того, какой из
  двух типов публикации — AIR или PREMIUM — эти поля сейчас описывают,
  см. FR-009) и `newsPremiumTelegramSent`/`newsPremiumVkSent`.
- **FR-007**: При `premiumAutoPublishState="FAILED"` администратор
  ДОЛЖЕН видеть в карточке песни текст последней ошибки
  (`premiumAutoPublishLastError`) и то, какой из каналов не смог
  опубликоваться.
- **FR-008**: Администратор ДОЛЖЕН иметь возможность вручную повторить
  премиум-публикацию по конкретному каналу прямо из карточки песни —
  используя существующие endpoint'ы `/api/song/publishPremiumTelegram` /
  `/api/song/publishPremiumVk` (новых endpoint'ов для самой публикации не
  требуется, требуется только UI поверх уже существующих).
- **FR-009**: Отображение статуса (FR-006) ДОЛЖНО корректно различать,
  относится ли текущее значение `telegramAutoPublishState`/`vkAutoPublishState`
  к AIR-публикации или к PREMIUM-публикации данной песни (общие поля
  используются обоими типами последовательно во времени, см. Edge Cases
  `specs/113`/`specs/121`) — если `newsPremiumPublishPending=true` и
  `idTelegramDemo`/`idVk` ещё пусты, состояние трактуется как
  премиум-статус; после выхода песни в эфир то же поле начинает отражать
  AIR-статус.
- **FR-010**: Счётчик попыток `premiumAttemptCount` и итоговое состояние
  `premiumAutoPublishState="FAILED"` ДОЛЖНЫ корректно отражать независимые
  сбои по каналам — точный механизм (раздельные счётчики на канал, либо
  документированное намеренно общее поведение) определяется на этапе
  планирования, но независимый временный сбой одного канала не должен
  преждевременно переводить в `FAILED` канал, который сам по себе ещё не
  исчерпал лимит попыток.
- **FR-011**: Изменения этой спецификации НЕ ДОЛЖНЫ менять уже
  реализованное и работающее поведение: разбивку `markNewsAvailableIfReady()`
  на независимые блоки «новость доступна» / «премиум-публикация ожидает»,
  идемпотентность по `Song.idVk`/`Song.idTelegramDemo` для AIR, шаблоны
  `telegramTemplatePremium`/`vkTemplatePremium` с плейсхолдерами, ручные
  endpoint'ы `/api/song/publishPremiumTelegram`/`/api/song/publishPremiumVk`,
  и текстовый (без видео) режим ВК-премиум при отсутствии `{demoVideo}` в
  шаблоне.
- **FR-012**: Бэклог — фикс применяется только к будущим переходам
  `newsAvailableAnnounced` false→true (и к будущим срабатываниям премиум-тика
  для песен, уже находящихся в состоянии `newsPremiumPublishPending=true`
  на момент выпуска фичи). Ранее одобренные песни, для которых
  премиум-Telegram публикация не состоялась и застряла (например,
  `telegramAutoPublishState="rendering"` без завершения из-за FR-003) —
  ДОЛЖНЫ быть подхвачены этим же фиксом при следующем тике
  (это не «исторический бэклог» в смысле `specs/121` FR-012, а просто
  ещё не завершённая работа уже включённого механизма), но система НЕ
  ДОЛЖНА специально сканировать полностью завершённые/пропущенные ранее
  песни (`premiumAutoPublishState="COMPLETE"`/`"FAILED"` не переоткрываются).

### Key Entities

- **Флаги премиум-автопубликации песни** (существующие поля в
  `player_readiness_flags`, без новых миграций): `newsPremiumPublishPending`,
  `newsPremiumTelegramSent`, `newsPremiumVkSent`, `premiumAutoPublishState`
  (`""`/`"RUNNING"`/`"COMPLETE"`/`"FAILED"`), `premiumAttemptCount`,
  `premiumAutoPublishLastError`. Эта спецификация не вводит новых полей —
  описывает уже существующие и, при необходимости (FR-010), уточняет их
  семантику (раздельные счётчики на канал).
- **PremiumAutoPublishScheduler** — существующий плановый тик (30 сек),
  единственная точка автоматического запуска премиум-публикации по обоим
  каналам. Эта спецификация фиксирует требование к его надёжности
  (FR-003) без изменения общей структуры тика.
- **TelegramAutoPublishService / VkAutoPublishService** — существующие
  сервисы полного цикла публикации (рендер-или-использование-существующего
  → отправка с ретраями → запись/невыставление id), уже поддерживающие
  `PublicationType.PREMIUM` с `persistMessageId=false`/`persistPostId=false`.
  Изменения касаются только устранения зависимости завершения рендера от
  чужого флага (FR-003) и, при необходимости по итогам FR-010, раздельного
  учёта попыток.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Для песни без готового демо-MP4 премиум-пост в Telegram
  появляется автоматически после завершения рендера — без единого
  ручного действия администратора — независимо от значения
  `telegramAutoPublishEnabled`.
- **SC-002**: Администратор может определить статус премиум-публикации
  (по каждому каналу отдельно) для любой песни, открыв её карточку в
  `webvue3`, без обращения к БД или к разработчику.
- **SC-003**: Окончательно провалившуюся премиум-публикацию по каналу
  можно повторить одним действием администратора в UI — без
  прямых правок в БД.
- **SC-004**: 0% случаев, когда премиум-рендер Telegram виснет в
  состоянии «Рендерится» дольше, чем занимает сам рендер плюс один тик
  планировщика (после успешного завершения `RENDER_MP4_DEMO`) —
  независимо от состояния флага `telegramAutoPublishEnabled`.
- **SC-005**: Существующее поведение (новость на проде, ВК-текст без
  видео, идемпотентность AIR по `idVk`/`idTelegramDemo`) не регрессирует —
  подтверждается неизменным поведением уже покрытых сценариев
  `specs/113-telegram-demo-publish` и `specs/121-vk-news-auto-publish`.

## Assumptions

- Ссылки на `specs/122-premium-auto-publish` в коде (`PremiumAutoPublishScheduler.kt`,
  `TelegramAutoPublishService.kt`, `VkAutoPublishService.kt`,
  `KaraokeProperties.kt`) относятся к этой спецификации — номер `122`
  выбран сознательно (совпадает с уже существующими ссылками в коде), а
  не по следующему свободному порядковому номеру в `specs/`.
- Оба флага (`telegramAutoPublishEnabled`, `premiumAutoPublishEnabled`) на
  момент составления этой спецификации были включены
  (`telegramAutoPublishEnabled=true`, `premiumAutoPublishEnabled=true`);
  `vkAutoPublishEnabled=false`, что не влияет на премиум-канал ВК
  (`PremiumAutoPublishScheduler` не проверяет этот флаг). То есть
  наблюдаемый баг — не следствие невключённой настройки, а структурная
  проблема (FR-003) плюс отсутствие видимости (FR-006).
- Раздельные счётчики попыток на канал (если будет выбрано такое решение
  для FR-010) — это уточнение существующего поля `premiumAttemptCount`
  до пары полей (например, `premiumAttemptCountTelegram`/`premiumAttemptCountVk`)
  без миграции БД (то же JSON-поле `player_readiness_flags`, тот же
  паттерн, что и остальные флаги готовности, `specs/101-song-news-flag`).
- Текстовый (без видео) режим ВК-премиум — временное ограничение
  (community token не имеет прав на `video.save`); эта спецификация не
  меняет это ограничение и не добавляет video-прикрепление для ВК —
  видео-приложение к ВК премиум-посту остаётся отдельной будущей задачей
  (см. `vkUserAccessToken`/`{demoVideo}` в `KaraokeProperties.kt`).
- UI-паттерн отображения статуса (FR-006/FR-007) — на усмотрение
  планирования: бейдж/иконка рядом с существующими индикаторами
  готовности песни в `SongEdit.vue`, по образцу того, как уже отображается
  `idTelegramDemo`/`idVk` для AIR-публикации.

## Out of Scope

- Видео-приложение к ВК-премиум посту (`{demoVideo}` в `vkTemplatePremium`)
  — заблокировано отсутствием video-прав у community-токена; отдельная
  будущая задача.
- Изменение самого события-триггера (`newsAvailableAnnounced` false→true,
  `markNewsAvailableIfReady()`) — эта спецификация фиксирует надёжность
  и видимость уже существующего триггера, а не меняет условия его
  срабатывания.
- Новый плановый мониторинг/алерт (светофор в хедере `webvue3`,
  `MonitorRegistry`) для зависших премиум-публикаций — полезное развитие
  идеи SC-004, но не обязательно для этой спецификации; может быть
  предложено отдельной небольшой фичей после того, как FR-003 устранит
  саму причину зависаний.
- Изменение AIR-путей публикации (`specs/113-telegram-demo-publish`,
  `specs/121-vk-news-auto-publish`) — переиспользуются как есть.
