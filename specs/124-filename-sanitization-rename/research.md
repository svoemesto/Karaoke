# Research: Санитайзинг имён файлов при импорте и переименование при редактировании

**Feature**: [spec.md](./spec.md) | **Date**: 2026-08-03

Все пункты Technical Context в `plan.md` были однозначными (нет `NEEDS CLARIFICATION`).
Ниже — архитектурные решения, необходимые до Phase 1 design, полученные прямым
чтением текущего кода (не предположениями).

## 1. Набор символов для санитайзинга и точка расширения

**Decision**: Расширить существующую `String.rightFileNameSymbols()`
(`karaoke-app/src/main/kotlin/com/svoemesto/karaokeapp/Extentions.kt:20`), а не
создавать параллельную функцию.

**Текущее состояние** (уже в коде):
```kotlin
fun String.rightFileNameSymbols(): String =
    this
        .replace("'", "`")
        .replace("?", "")
        .replace(":", "-")
        .replace("!", "")
        .replace("$", "s")
        .replace("*", "x")
```
Уже покрыты `!`, `?`, `:`, `*`, `'`, `$`. **Не покрыты** (нужно добавить): `/`, `\`
(path traversal / выход за пределы папки — Edge Case из спецификации), и двойные
кавычки `"` (сейчас есть только экранирование одинарной кавычки). Скобки `(` `)`
`[` `]` — намеренно НЕ трогать (FR-003, структурно значимы для regex-парсинга
`createFromPath`). Кириллица и прочие не-ASCII буквы — не трогать (FR-012, уже
верно: функция ничего не удаляет за пределами явного списка).

**Rationale**: Единая точка правды для правил санитайзинга (Assumptions
спецификации: «правило единое для импорта и SongEdit»); `rightFileName()` уже
используется в 24 местах кодовой базы (stems, symlink-логика, publichный
контроллер и т.д.) — расширение семантики автоматически подхватывается везде,
где уже вызывается эта функция, без риска рассинхронизации двух копий логики.

**Alternatives considered**: Написать новую функцию `sanitizeFileName()` —
отклонено, т.к. создаёт два источника правды и не устраняет корневой баг (см. п.2).

## 2. Точка применения при импорте (корень бага "!")

**Decision**: В `Song.createFromPath()`
(`karaoke-app/src/main/kotlin/com/svoemesto/karaokeapp/model/Song.kt:7935`)
применить `.rightFileName()` к `fileName` **сразу после парсинга regex**, ДО
блока перекодирования в FLAC (строки 7976-7989), и использовать
санитайзированное значение и для реального `ffmpeg`-вывода (переименования
файла на диске), и для `song.fileName` (строка 7991). Оригинальные символы
(включая `!`) остаются только в `song.fields[SongField.NAME] = songNameStr`
(строка 7993, парсится из **той же** regex-группы, но не переприсваивается).

**Root cause (подтверждено чтением кода)**: сегодня `fileName` (из
`file.nameWithoutExtension`, строка 7946) никогда не проходит через
`rightFileName()` в `createFromPath()`. Ffmpeg получает на вход путь с `!` и
создаёт на диске `....Дай жару!.flac`. Позже, при копировании в demucs temp-папку,
`.rightFileName()` применяется к целевому пути — но не к реальному имени файла
на диске, которое так и осталось с `!`. `cp` не находит несуществующий (для него)
санитайзированный источник → падение Demucs. Фикс: санитайзировать **один раз,
в момент создания**, а не точечно перед каждым использованием ниже по пайплайну.

**Rationale**: Единственное место, где decision «как назвать файл на диске»
принимается один раз и распространяется на все последующие шаги (FR-004).

## 3. Область проверки коллизии имени файла

**Decision**: SQL-запрос `WHERE root_folder = ? AND file_name = ?` (плюс `id <> ?`
при проверке в контексте существующей песни) — согласно клэрификации Q3
(в пределах одной папки/альбома). Не full-table сравнение — соответствует
Principle II Конституции (`associateBy`/batch, не `.any()` по всей таблице).

**Rationale**: Коллизия имени файла физически возможна только внутри одной
папки на диске; глобальная уникальность не требуется и создала бы ложные
блокировки для одинаково названных треков из разных альбомов.

## 4. Алгоритм авто-суффикса при коллизии импорта (FR-005)

**Decision**: При коллизии — числовой суффикс перед расширением:
`"$fileName (2)"`, при повторной коллизии `"$fileName (3)"` и т.д., инкрементируя
до первого свободного в рамках `rootFolder`. Формат `(N)` выбран для консистентности
с уже существующим паттерном `(01)`/`(14)` (порядковый номер трека) в имени файла
— визуально не путается с номером трека, т.к. добавляется в конец, после названия.

**Rationale**: Минимальное вмешательство, не требует участия администратора
(клэрификация Q4), не меняет распознанные метаданные (номер/автор/название),
меняет только физическое имя файла на диске.

## 5. Каскадное переименование: локальная ФС + оба хранилища

**Decision**: Порядок операций в `songs2Update` (или выделенном методе,
вызываемом из него) для каждого существующего производного артефакта:

1. Переименовать локальный файл на диске (`File.renameTo` / `Files.move`) —
   быстрая атомарная операция в пределах одной ФС.
2. Если объект существует в хранилище (`storageService.fileExists` /
   `storageApiClient.fileExists` под старым ключом) — загрузить копию под новым
   ключом из уже переименованного локального файла (`uploadFile(... pathToFileOnDisk)`),
   затем удалить старый ключ (`deleteFile`).

**Важно**: ни `KaraokeStorageService`, ни `StorageApiClient` (оба клиента MinIO)
не предоставляют метода `rename`/`move` — только `uploadFile`/`downloadFile`/
`deleteFile`/`listFiles` (подтверждено чтением интерфейсов). Server-side copy в
MinIO SDK существует (`CopyObjectArgs`), но не обёрнут в проектный интерфейс —
для этой фичи проще и надёжнее переиспользовать уже читаемый локальный файл
(шаг 1 уже его переименовал), а не добавлять новый метод в оба интерфейса ради
одного вызывающего места.

**Best-effort-forward семантика (клэрификация Q1/FR-010)**: шаги выполняются
последовательно по списку артефактов; если шаг N падает — шаги 1..N-1 не
откатываются, шаг N+1 и далее не выполняются в эту попытку. Список
«что осталось не переименованным» пересчитывается заново при повторной
попытке (нет отдельного persisted-состояния «докуда дошли», см. п.7).

**Rationale**: Соответствует существующему паттерну "best-effort вперёд, без
отката" уже принятому в проекте для очереди `KaraokeProcess`
([[feedback_karaokeprocess_inconsistent_sqlexception_handling]],
[[project_queue_swallowed_errors_fix]]).

## 6. Проверка активной фоновой обработки (FR-013)

**Decision**: Перед началом каскадного переименования — запрос
`KaraokeProcess.loadList(args = mapOf("song_id" to song.id), database = ...)`,
отфильтрованный по `process_status IN ('WAITING','WORKING')`. Если список не
пуст — отклонить сохранение, вернуть пользователю сообщение «дождитесь
завершения текущей обработки» (клэрификация Q2), не применяя ни санитайзинг,
ни переименование.

**Rationale**: `tbl_processes` уже хранит `song_id`+`process_status`
(`KaraokeProcessStatuses`: CREATING/WAITING/WORKING/DONE/ERROR) — не требует
новых полей, запрос дешёвый (индексируемый).

## 7. Механизм явной пометки ошибки без новой миграции БД

**Decision**: Переиспользовать существующий фреймворк `HealthReport`/
`HealthReportStatus` (`karaoke-app/.../HealthReport.kt`,
`karaoke-app/.../HealthReportStatus.kt`) вместо добавления нового персистентного
поля/колонки в `tbl_songs`. `HealthReport` уже реализует ровно нужную семантику:
вычисляет несоответствие «ожидаемое состояние файла в данной локации» (LOCAL_FILESYSTEM
/ LOCAL_STORAGE / REMOTE_STORAGE) vs фактическое, возвращает статус
(OK/WARNING/IN_PROGRESS/ERROR/FATAL_ERROR) и список `solutionActions` для
самовосстановления — и уже отображается в `HealthReportTable.vue`, который
уже встроен и вызывается из `SongEdit.vue` (кнопка/модалка «Health Report»).

Если после каскадного переименования часть артефактов осталась под старым
именем (сбой на середине), это уже обнаруживается существующей логикой
`HealthReport` при следующем её вычислении для этой песни (ожидаемый файл под
новым `song.fileName` отсутствует → `ERROR`/`FATAL_ERROR` с
`solutionActions`), — то есть повторная попытка «доведения до нового имени»
(FR-010) естественно ложится на уже существующий механизм резолва
health-report-проблем, включая ручной re-run через UI. Отдельная персистентная
колонка "renameError" не нужна.

**Impact on Constitution Check**: снимает ⚠️ по Principle III — миграция БД
не требуется, `tbl_songs.file_name`/`root_folder` не меняют тип/семантику,
recordhash-триггер пересоздавать не нужно.

**Rationale**: Не изобретать вторую систему трекинга «песня в плохом
состоянии» рядом с уже существующей и уже интегрированной в UI SongEdit.

## 8. Per-feature документация (FR-009, Principle VI)

**Decision**: Эта фича не вписывается в готовые 16 подсистем `docs/features/README.md`
один-в-один — затрагивает: `async-process-queue` (правки `Song.createFromPath`,
проверка `KaraokeProcess` из п.6), `premium-stems` (переименование файлов стемов
на диске/в хранилище) и не документированную ранее логику `HealthReport`
(сейчас упоминается только как `@see docs/features/premium-stems.md` в
`KaraokeStorageService`, хотя фактически это общий кросс-song механизм).
Решение: обновить `docs/features/async-process-queue.md` (правка
`createFromPath`) и `docs/features/premium-stems.md` (каскадное переименование
стемов) точечными секциями в момент имплементации (`/speckit-implement`), а не
заводить 17-ю подсистему только ради этой фичи — переименование не образует
самостоятельную продуктовую подсистему, это сквозная правка двух существующих.

**Rationale**: Соответствует правилу FR-009 (обновлять документ фичи, код
которой меняется) без искусственного разрастания реестра подсистем.
