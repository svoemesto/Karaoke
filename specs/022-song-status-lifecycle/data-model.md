# Data Model: Расширенный жизненный цикл статусов готовности песни

Новых сущностей, полей или SQL-миграций схемы (DDL) эта фича не вводит —
только data-миграция (`UPDATE`) существующей колонки и уточнение её
семантики. Ниже — модель поля и производных признаков, релевантная для
реализации.

## Song.idStatus (существующее поле, `tbl_songs.id_status integer DEFAULT 0`)

Числовое поле производственного статуса песни. Уже существует, уже
синхронизируется LOCAL↔SERVER как часть `tbl_songs` (`SyncRegistry`,
`recordhash`-триггер) без изменений состава колонок.

### Новая шкала значений (FR-001 spec.md)

| Значение | Лейбл (было / легаси) | Новый лейбл | Смысл |
|---|---|---|---|
| 0 | `NONE` | `NONE` (без изменений) | Новая песня, текста нет |
| 1 | `TEXT_CREATE` | `TEXT_CREATE` (без изменений) | Текст найден |
| 2 | `TEXT_CHECK` | `TEXT_CHECK` (уточнённый смысл) | Текст проверен: орфография и пунктуация |
| 3 | `PROJECT_CREATE` (легаси MLT) | `TEXT_WORDS_VERIFIED` (новый) | Текст проверен: слова соответствуют звучанию песни |
| 4 | `PROJECT_CHECK` (легаси MLT) | `MARKERS_CREATED` (новый) | Маркеры расставлены |
| 5 | `RENDERING` (легаси MLT, не было кнопки) | `MARKERS_VERIFIED` (новый) | Маркеры проверены |
| 6 | `DONE` (легаси MLT) | `READY` (новый) | Песня готова — новый порог публичной готовности |

Значения 0-2 численно не меняются (только уточняется смысл 2). Значения 3-6
переиспользуют уже существующие в коде числа, но со **сменой владельца
смысла**: раньше это была терминология легаси MLT-рендер-пайплайна
(см. `research.md` Decision 1), теперь — единственная терминология
жизненного цикла текст/маркеры/готовность.

### Производный признак «готова»

```
song.isReady == (song.idStatus >= 6)
```

Раньше: `song.idStatus >= 3`. Единственное место, из которого должна
логически выводиться готовность (используется как формула на всех read-путях
из `research.md` Decision 3 — сам признак нигде не хранится отдельным полем,
вычисляется на лету из `idStatus` при каждом обращении, как и сейчас).

### Ограничения/инварианты

- **Монотонность автоматических переходов (FR-010/FR-011)**: любой
  автоматический (не инициированный явным кликом администратора) переход
  ДОЛЖЕН удовлетворять `newStatus == currentStatus + 1` И применяться только
  если `currentStatus == newStatus - 1`. Ручные переходы (SongEdit, FR-007)
  этому ограничению не подчиняются — администратор может установить любое
  значение 0-6 в любом направлении.
- **Идемпотентность миграции**: `UPDATE tbl_songs SET id_status=6 WHERE
  id_status>=3` — при повторном запуске не меняет уже мигрированные строки.
- **Отсутствие нового CHECK-constraint**: поле остаётся обычным `integer` без
  ограничения диапазона на уровне БД (соответствует текущему стилю проекта —
  ограничение только в UI/бизнес-логике; см. `research.md` Decision 2,
  Alternatives).

## Затрагиваемые функции/компоненты (без изменения формы данных)

- `Song.status: String` (`karaoke-app/model/Song.kt:360-371`) — лейбл-геттер,
  меняется тело `when(idStatus)` под новую таблицу выше. Тип возвращаемого
  значения не меняется (`String`).
- `SongEdit.vue` `setStatus(idStatus)`/шаблон кнопок статуса — тот же паттерн
  (JS `switch`, зеркалирующий Kotlin-геттер), новые строковые лейблы, кнопка
  для значения 5 добавляется по аналогии с существующими.
- `StatBySong.CONTENT_READY_FILTER` (`karaoke-web/StatBySong.kt:50`) —
  строковая SQL-константа, `"id_status >= 3 AND ..."` → `"id_status >= 6 AND
  ..."`, форма (какие ещё условия участвуют — `source_markers`) не меняется.
- `PublicPlayerController.stemsReady(settings: Song): Boolean`
  (`karaoke-web/controllers/PublicPlayerController.kt:116-122`) — булево
  условие, меняется только один операнд (`3`→`6`), сигнатура и остальные
  условия (`stemAccompanimentReady`, `stemVocalReady`, `pictureAlbumReady`,
  `pictureAuthorReady`, `sourceMarkersList.isNotEmpty()`) не меняются.
- `Zakroma.getZakroma`/`getZakromaBySpecialOrder` (`onlyPublished` параметр,
  добавлен в specs/013) — значение строки-фильтра `">=3"` → `">=6"`,
  сигнатура функций не меняется.

## Данные, требующие явного продуктового решения при реализации (не data-модель как таковая)

См. `research.md` Decision 4 и Decision 5 (таблицы «задача аудита») — три
места (`Utils.kt:102`/`4548`, `Publication.kt` `fromnotcheck`,
`SongEditorController.editSave`), где целевое значение не выводится
однозначно из текста спецификации и требует решения на этапе
`/speckit-tasks`. Эта модель фиксирует лишь то, что для них состав данных
(колонка/тип) не меняется — меняется только то, какое конкретно значение
0-6 записывается в уже существующее поле.
