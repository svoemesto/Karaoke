### P-68-05: webvue3/e2e/save-race.spec.js:83,102 — TEST (S3)

- Что не так: главное утверждение теста — «сохранения не должны пересекаться» — **не может упасть**. Первый вызов идёт через `callComponent`, который делает `page.evaluate(...)` и **возвращает результат вызова метода**: `return inst.proxy[m](a)` → `inst.proxy.save()` — а `save()` объявлен `async` (`SubsEdit.vue:3156`, так с 2026-09-30, коммит `d784eb2a`), поэтому `page.evaluate` **await'ит** возвращённый промис (документированное поведение Playwright). Значит, первый `POST /api/song/savesourcetextmarkers` полностью завершается (включая искусственную задержку 400 мс в заглушке) **до** того, как вызывается второй `save()`. Два сохранения физически не могут пересечься ни при какой реализации — утверждение `maxInFlight === 1` истинно всегда, в том числе если очередь `saving`/`saveQueued` (тот самый фикс #189) убрать из компонента. Исторически тест ловил баг: на старом коде `save()` был **не** `async` (голый dispatch), `evaluate` возвращался мгновенно, и два POST'а пересекались (`maxInFlight = 2`). После фикса механизм теста перестал воспроизводить гонку — регрессионная защита #189 фактически обнулена.
- Доказательство:
  ```
    await callComponent(page, 'save')
  ```
  (`webvue3/e2e/save-race.spec.js:83`, SHA 1977838a) и
  ```
    expect(maxInFlight, 'сохранения не должны пересекаться').toBe(1)
    expect(total, 'второе сохранение должно выполниться, а не потеряться').toBe(2)
  ```
  (`:102–103`); определение `callComponent` — «`return inst.proxy[m](a)`» (`:50`); компонент — «`async save() {` / `  this.addEndMarker()` / `  if (this.saving) {`» (`webvue3/src/components/Songs/edit/SubsEdit.vue:3156–3159`).
- Путь: `npm run test:e2e -- save-race` → `callComponent(page,'save')` → `page.evaluate` → `SubsEdit.save()` (async) → Playwright ждёт промис → `dispatch('saveSourceTextAndMarkers')` → заглушка `page.route` (400 мс) → ответ → `await` снят → **после этого** вызывается второй `save()` → пересечения нет → `maxInFlight = 1` при любом коде.

## Сверки (без severity)

1. **`webvue3/e2e/xss.spec.js:115–124` — имя теста обещает больше, чем проверяется.** Тест назван «HTML из текста песни не исполняется, а показывается как текст», но утверждение `window.__XSS_FIRED` **намеренно отсутствует** (это разобрано в комментарии `:117–121`: разбивка на слоги рвёт тег, и «скрипт не выполнился» проходило бы и на уязвимом коде). Фактически проверяется три вещи: наличие `&lt;img` в `textFormatted/notesFormatted/chordsFormatted/tail`, отсутствие сырого `<img` в них же и отсутствие элементов `img` в четырёх селекторах DOM. Это проверка **«сырой HTML пользовательского текста не попадает в DOM через v-html»**, а не «не исполняется». Само свойство (экранирование) при этом проверяется по существу — экранированная форма обязана присутствовать, иначе тест падает. Запись не заводят: расхождение «имя ↔ проверка» задокументировано автором и не оставляет дефект непроверенным. Для сведения лида: полный набор экранируемых символов (`& < > " '`) покрыт модульным тестом `highlightWords.test.js:15–20`; «частичного экранирования» в компоненте нет — `SubsEdit.vue` использует общий `escapeHtml` (`highlightWords.js:44–51`), покрывающий все пять символов.
2. **`webvue3/src/utils/__tests__/dateFormat.test.js:39–55` — TZ-зависимое «золотое» ожидание с ослабленной fallback-веткой.** Тест сравнивает результат с точным локальным временем только для `Europe/Moscow`, `Asia/Vladivostok` и `America/*`; для любой другой TZ (в т.ч. `UTC` в CI) срабатывает ослабленная ветка `assert.match(out, /^11\.08\.2026 \d{2}:57$/)` — то есть при появлении CI-джоба сильная часть проверки не выполнится. Формально это «soft skip» по окружению, но он задокументирован в шапке файла (`:5–8`: «тесты инвариантны от TZ машины… для конкретного TZ смотрите TZ-specific тесты ниже») и не оставляет дефект непроверенным (формат, минуты и дельта в 1 час проверяются всегда).
