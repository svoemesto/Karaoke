# Data Model: Показ на проде только песен со статусом готовности >= 3

Новых сущностей, полей или SQL-миграций эта фича не вводит. Ниже —
уточнение семантики уже существующего поля, релевантное для реализации.

## Song.idStatus (существующее поле, `tbl_songs.id_status`)

Числовое поле производственного статуса песни (уже существует, уже
синхронизируется LOCAL↔SERVER как часть `tbl_songs`, участвует в
`SyncRegistry`/`recordhash` без изменений).

| Диапазон | Значение | Видимость на проде (после этой фичи) |
|---|---|---|
| `id_status < 3` | Песня в процессе производства (транскрипция/разметка/рендер и т.п. ещё не завершены) | Скрыта из закромов и поиска на проде; видна в админке без ограничений |
| `id_status >= 3` | Песня прошла стадии, необходимые для показа посетителю («в коллекции» — то же определение, что уже используется в `StatBySong`/`StatsCacheScheduler`) | Видна в закромах, спецзаказной плашке и поиске на проде |

Изменение — не в семантике поля (она не меняется), а в том, что 4
публичных read-пути начинают её учитывать так же, как уже учитывает
подсчёт публичных счётчиков (см. research.md Decision 3).

## Затрагиваемые функции (без изменения сигнатуры данных, только видимость)

- `Zakroma.getZakroma(author, database, storageService, storageApiClient)` →
  добавляется опциональный параметр `onlyPublished: Boolean = false`,
  влияющий только на `args`, передаваемые в `Song.loadListFromDb` (не на
  форму возвращаемого `List<Zakroma>`).
- `Zakroma.getZakromaBySpecialOrder(database, storageService,
  storageApiClient)` → аналогично, тот же новый параметр.
- `Song.loadListFromDb(args, ...)` → без изменения сигнатуры; вызывающий код
  (`PublicApiController.songs`, legacy `MainController.filter`) добавляет
  `"id_status" to ">=3"` в `args` перед вызовом.

Форма DTO (`ZakromaPublicDto`, `SongPublicDto` и т.д.) не меняется — меняется
только состав элементов в списках, которые эти DTO оборачивают.
