# Research: SEO-HTML endpoint для ботов (specs/180-og-seo-html)

**Дата**: 2026-08-13
**Задача**: заменить генерацию PNG (`/api/public/song-vk-image/{id}`) на
полноценный SEO-HTML ответ endpoint'а `/api/public/og/song` — без обращения
к MinIO, с полным набором мета-тегов и структурированных данных.

## Решённые вопросы (Phase 0 research)

### R1. Schema.org JSON-LD: какой `@type` для караоке-песни?

**Decision**: `@type: "MusicRecording"` (как primary), с fallback на
`"Song"` если Schema.org его deprecate в будущем.

**Rationale**:
- `MusicRecording` (https://schema.org/MusicRecording) — стандартный
  Schema.org-тип для «звукозаписи песни». Google Rich Results
  поддерживает его для музыкального контента, Yandex тоже
  поддерживает расширенные сниппеты.
- Свойства `name`, `byArtist`, `inAlbum`, `datePublished`,
  `inLanguage`, `genre`, `lyrics` (через `CreativeWork`),
  `isAccessibleForFree` — точно соответствуют нашему контенту.
- Альтернатива `Song` (https://schema.org/Song) — менее распространён,
  Google не использует для rich snippets.
- Альтернатива `CreativeWork` — слишком общий, теряем
  специализированные свойства.

**Alternatives considered**:
- `Song` — отвергнут: менее распространён, нет специализированных полей.
- `CreativeWork` — отвергнут: слишком общий, не передаёт суть «песня».
- Без JSON-LD, только OG-теги — отвергнут: Yandex и Google всё активнее
  используют JSON-LD для расширенных сниппетов (поиск по жанру, дате,
  автору), OG-теги — для соцсетей. Нужны ОБА.

### R2. Где размещать текст песни в JSON-LD?

**Decision**: В свойстве `lyrics` как
`{ "@type": "CreativeWork", "text": "..." }` — стандартный паттерн
schema.org для текста песни.

**Rationale**:
- Schema.org не имеет прямого свойства `text` у `MusicRecording`,
  но допускает `lyrics` (типа `CreativeWork`).
- Альтернатива — хранить в `description` (но description зарезервирован
  для краткого описания песни, до 250 символов — Google отрубает
  description в сниппете после ~155–170 символов).
- Альтернатива — хранить в `keywords` (но keywords — это список
  строк-тегов, не подходит для полного текста).

**Alternatives considered**:
- `description` — отвергнут: перегрузка и обрезка Google.
- `keywords` — отвергнут: не тот формат данных.
- Отдельный объект `hasPart` — избыточно для нашего случая.

### R3. Оптимальный формат HTML для быстрой генерации

**Decision**: StringBuilder с экранированием через
`org.springframework.web.util.HtmlUtils.htmlEscape()` (или собственный
`escape()` helper, уже есть в `PublicOgSongController.kt:100` и
`PublicVkAuthController.kt:144`, `PublicVkIdAuthController.kt:386`).

**Rationale**:
- Существующий helper `escape()` в `PublicOgSongController.kt:100` —
  экранирует `&<>"'` (5 символов), покрывает все случаи
  HTML-инъекций.
- StringBuilder дешевле чем String concatenation в Kotlin при
  большом количестве конкатенаций (Groovy-стиль менее эффективен).
- Для JSON-LD дополнительно экранируем `"` в JSON-строках
  (это часть escape() и так).
- Без шаблонизатора (Thymeleaf, Mustache) — endpoint должен
  возвращаться за миллисекунды, лишний dependency и парсинг
  шаблона избыточен.

**Alternatives considered**:
- Thymeleaf template — отвергнут: добавляет ~5–10 мс на парсинг,
  требует шаблон-файл в `resources/templates/`, лишний dependency.
- JSON object → render через Jackson — отвергнут: HTML содержит
  вложенные структуры, JSON→HTML сложнее, чем StringBuilder.
- Библиотека `kotlinx.html` — отвергнут: дополнительный dependency
  для одного endpoint'а, не нужен.

### R4. URL обложки альбома — где брать?

**Decision**: Строим абсолютный URL по шаблону
`https://sm-karaoke.ru/minio/karaoke/{author}/{year} - {album}/{author} -
{year} - {album}.album.png` БЕЗ проверки существования файла в MinIO.
Если файла нет — fallback на `https://sm-karaoke.ru/KARAOKE_LOGO.png`.

**Rationale**:
- Тот же шаблон, что используется в `PublicApiController.songVkImage()`
  (line 440) и `SongShareLinkService` (line 1016) — единая конвенция.
- nginx проксирует `/minio/` напрямую в MinIO
  (`proxy_pass http://89.125.103.63:9000/`), без участия Java —
  проверка существования файла в MinIO не нужна (если файла нет,
  nginx вернёт 404, что для OG-тегов приемлемо).
- **Главное**: endpoint НЕ обращается к MinIO вообще (FR-007 спеки),
  генерация HTML — чистый StringBuilder по полям БД, latency < 100 мс.
- Fallback URL `KARAOKE_LOGO.png` — это уже используется в
  `PublicApiController.songVkImage()` (line 462) при отсутствии
  обложки/автора, согласовано с шаблонами `main.html`,
  `filter.html`, `zakroma.html`, `testpage.html` (где `KARAOKE_LOGO.png`
  отображается напрямую без префикса `/minio/karaoke/`).

**Alternatives considered**:
- Проверять существование в MinIO через HEAD-запрос — отвергнут:
  добавляет ~50–100 мс на запрос, ломает SC-001 (<100 мс TTFB).
- Использовать `/api/public/song-picture/{id}` — отвергнут: тот же
  endpoint тоже лезет в MinIO для генерации `BufferedImage`, лишняя
  работа для OG-тегов.
- Использовать публичный URL без nginx-прокси — отвергнут: nginx
  прокси `/minio/` уже работает, нет смысла плодить сущности.

### R5. nginx-кэширование endpoint'а — нужно ли?

**Decision**: НЕ включаем `proxy_cache` для `/api/public/og/song` в этой
версии фичи.

**Rationale**:
- TTFB endpoint'а < 100 мс (SC-001) — пользователь не заметит разницы
  между кэшированным и некэшированным ответом.
- Кэширование усложняет инвалидацию: при изменении песни
  (редактирование текста, обложки, метаданных) нужно сбрасывать
  кэш — нетривиально.
- Боты обходят страницы песен с интервалом в дни/недели —
  кэширование на часы не даёт ощутимого выигрыша для ботов.
- Если в будущем нагрузка вырастет — `proxy_cache` легко добавить
  отдельным изменением в `80to8897` с TTL ~1 час и purge через
  `Song.saveToDb()` event listener (по образцу других кэшей).

**Alternatives considered**:
- `proxy_cache_valid 200 1h` в nginx — отвергнут для первой версии,
  можно добавить позже по результатам нагрузочного тестирования.
- Кэш в `AtomicReference<String>` в Spring — отвергнут: stateful
  endpoint, лишний код для проблемы, которой нет.

### R6. Что делать с существующим endpoint'ом `/api/public/song-vk-image/{id}`?

**Decision**: Оставляем в коде без изменений. Новый SEO-endpoint его
НЕ вызывает.

**Rationale**:
- Endpoint может быть полезен для ручных публикаций в будущем
  (Twitter card_image, превью в email-рассылках и т.п.).
- Удаление может сломать потенциально кэшированные ссылки в VK
  (если кто-то запостил прямую ссылку на PNG в группе ВК до
  изменения подхода).
- Стоимость поддержки endpoint'а — ~50 строк кода, ноль runtime-cost
  если его никто не вызывает.
- Endpoint уже есть в `PublicApiController.kt:407` и хорошо
  задокументирован (включая KDoc про specs/130-vk-preview-generation).

**Alternatives considered**:
- Удалить endpoint — отвергнут: цена удаления (потенциальные битые
  ссылки) выше цены поддержки (50 строк кода).
- Сделать deprecated и не вызывать — отвергнут: endpoint не
  публичный API для пользователей, это внутренний
  сгенерированный URL, deprecation note не поможет.

### R7. Кэширование результата fetch `description` для длинных текстов

**Decision**: Вставляем `formattedTextSong`/`formattedTextChords` в
HTML как есть, с маркером `[...фрагмент текста песни усечён для
индексации]` при превышении **1 МБ** (1 048 576 символов).

**Rationale**:
- Длинный текст — нормальное явление для песен (рок-оперы,
  многосерийные композиции, стихи). Обрезка на 50 КБ
  (как было предложено в спеке) обрежет контент раньше, чем
  нужно.
- 1 МБ — это больше, чем реальный размер текста песни
  (даже у самой длинной песни в коллекции не больше
  100–200 КБ). Запас на случай экстремально длинного контента.
- HTML размером > 1 МБ — это риск для nginx (default
  `large_client_header_buffers`) и для бота (timeout на парсинг).
- Маркер `[...усечён...]` явно говорит боту, что контент
  сокращён, чтобы не вводить в заблуждение (полезно для
  индексации — бот может пометить страницу как
  «частично проиндексирована»).

**Alternatives considered**:
- Никогда не обрезать — отвергнут: защита от DoS через
  гигантский HTML.
- Обрезать на 50 КБ — отвергнут: слишком агрессивно для
  реальных данных (теряется контент).
- Обрезать на 10 МБ — отвергнут: nginx/бот всё равно не
  справится, защита должна быть раньше.

### R8. Поле `inLanguage` для русских песен

**Decision**: `inLanguage: "ru"` для всех песен (проект полностью
русскоязычный, см. AGENTS.md «Всё общение с пользователем — ТОЛЬКО на
русском языке»).

**Rationale**:
- Проект на 100% русскоязычный (русский рок, исполнители, каталог).
  Англоязычных песен в каталоге нет.
- Если в будущем появятся англоязычные — нужно будет добавить поле
  `language` в `Song` (миграция БД), отдельно от этой фичи.

**Alternatives considered**:
- `inLanguage: "ru-RU"` (полный BCP-47) — отвергнут: schema.org
  рекомендует короткий код (`ru`) для большинства случаев.
- Не указывать `inLanguage` — отвергнут: schema.org рекомендует
  указывать всегда, без этого Google не показывает расширенный
  сниппет с информацией о языке.

## Открытые вопросы для следующих фаз

- **Где физически хранится `KARAOKE_LOGO.png`?** — предположительно
  в корне MinIO bucket'а `karaoke` (как `KARAOKE_LOGO.png` без
  подпапки). Проверить на этапе реализации через
  `curl https://sm-karaoke.ru/KARAOKE_LOGO.png` или
  `minio ls karaoke/`. Если не существует — fallback URL не работает,
  нужно создать логотип или использовать другую заглушку.
- **Что делать с песнями, у которых `idStatus` ровно 3, 4 или 5
  (между TEXT_WORDS_VERIFIED и READY)?** — текущая спека говорит
  «idStatus < 3 — без текста/аккордов». Это корректно для
  status=0..2 (текст ещё не верифицирован). Для status=3..5
  текст есть, но контент не финализирован. Решение: для status ≥ 3
  отдаём текст (как и для status ≥ 6), но **без** отметки
  «готово» — это согласуется с поведением `Pictures.pictureAlbum`
  (доступен сразу при наличии файла в MinIO, независимо от статуса).
- **CSS-классы для `<body>` — нужны ли?** — спека не упоминает
  inline-стили для видимого контента. Ботам (Yandex/Google)
  CSS безразличен, они читают только текст + структуру. Inline
  `style="..."` минимален (только warning-блок для красного
  цвета). Уточнить в плане, если потребуется — на этапе
  реализации.
