# Feature Specification: Управление заданиями редактора в личном кабинете и админке

**Feature Branch**: `154-editor-tasks-manage`
**Created**: 2026-08-05
**Status**: Draft
**Input**: User description: "На проде: личный кабинет - редактор караоке. Список заданий редактора отсортировать так, чтобы готовые были в самом низу. Добавить кнопку 'Удалить' для одобренных заданий и 'Отказаться' для других типов. Добавить кнопку 'Удалить все одобренные'. В админке в компоненте 'Задания редактора' так же добавить кнопку 'Удалить все одобренные'."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Задания в личном кабинете отсортированы: готовые — внизу (Priority: P1)

Редактор-волонтёр публичного сайта открывает страницу «Редактор караоке» в личном кабинете (`/account/editor`, `karaoke-public/src/views/EditorTasksView.vue`) и видит список своих заданий, в котором одобренные (`status = approved`) задачи всегда расположены ниже задач в активной работе (`assigned`, `in_progress`, `submitted`, `rejected`). Активная часть списка, на которой сосредоточена работа редактора, оказывается визуально приоритетной и не «съезжает» под массой уже завершённых.

**Why this priority**: Это самое заметное поведенческое изменение списка — редактор каждый раз при заходе в кабинет видит порядок строк. Без него появляется обратная проблема: после нескольких успешно закрытых задач новые назначения уходят вниз под длинный шлейф одобренных, и редактор их пропускает (визуальная «потеря» свежих задач среди завершённых — репортировано пользователем как «список неудобен, одобренные забивают верх»).

**Independent Test**: На стенде подготовить аккаунт редактора с 8+ заданиями, из которых минимум 3 одобрены и минимум 2 находятся в активной работе (`assigned` / `in_progress` / `submitted`). Залогиниться, открыть `/account/editor`. В DOM-порядке карточек все карточки со статусом `approved` расположены строго после карточек со всеми остальными статусами; внутри обеих групп порядок стабилен (детерминирован по id или по `assigned_at` — фиксируется на этапе планирования). При наличии только одобренных или только активных — деградация «тихая», без падений вёрстки.

**Acceptance Scenarios**:

1. **Given** у редактора есть задания в смешанных статусах (`assigned`, `in_progress`, `submitted`, `rejected`, `approved`), **When** он открывает `/account/editor`, **Then** в DOM-порядке списка все карточки со статусом `approved` идут строго после карточек со всеми остальными статусами.
2. **Given** у редактора есть только одобренные задания, **When** он открывает `/account/editor`, **Then** все карточки показываются в обычном порядке (нет «пустого верха» / ломающейся вёрстки) — единственная группа фактически не пуста.
3. **Given** у редактора есть только активные задания (без одобренных), **When** он открывает `/account/editor`, **Then** список выглядит как обычно — никаких заглушек/«временных» сортировок не появляется.
4. **Given** редактор только что отправил задание на проверку (`status` сменился на `submitted`) или получил одобрение (`status` сменился на `approved`), **When** список перезагружается, **Then** карточка сразу занимает правильное место в отсортированном порядке (без необходимости F5 вручную).
5. **Given** редактор сортирует список по дате/имени кликом по колонке, **When** он применяет сортировку, **Then** колонка-переключатель работает как и раньше (эта фича НЕ ломает существующую клиентскую сортировку по другим полям — речь только про дефолтный порядок и порядок «активные выше одобренных»; конкретный UX-выбор фиксируется на этапе планирования, см. Assumptions).

### User Story 2 - Редактор может «Отказаться» от любого активного задания (Priority: P1)

Редактор-волонтёр на странице `/account/editor` для каждой карточки в активном статусе (`assigned`, `in_progress`, `submitted`, `rejected`) видит кнопку «Отказаться». По клику (после подтверждения) задание удаляется из его списка, черновик (`tbl_song_assignment_drafts`) тоже удаляется; администратор увидит, что задание больше не существует (или — для черновика на проверке — больше не сможет его одобрить/отклонить). После отказа редактор больше не видит эту карточку в кабинете, и эта же песня становится снова доступной для назначения через админский селектор «Назначить…».

**Why this priority**: Сейчас у редактора нет легитимного способа снять с себя задание: ни на UI, ни через API — задание можно только «пройти до конца» или ждать, пока админ его снимет. На практике это приводит к тому, что редактор перестаёт заходить в кабинет из-за «висящего» хвоста заданий, на которые у него нет сил/времени, а админ тратит время на ручное «Отозвать» через админку для каждого случая. Это — самый частый сценарий из репорта пользователя.

**Independent Test**: Залогиниться редактором, у которого есть хотя бы одно задание в активном статусе. Нажать «Отказаться» → подтвердить в диалоге. Карточка исчезает из списка; повторный заход в `/account/editor` (или перезагрузка страницы) её не возвращает; в админке `webvue3/src/components/SongEditor/SongEditorTable.vue` этой записи больше нет (в том же виде БД); если у задания был черновик — он тоже удалён.

**Acceptance Scenarios**:

1. **Given** у редактора есть задание со статусом `assigned` (назначено, ещё не начинал), **When** он нажимает «Отказаться» и подтверждает, **Then** карточка исчезает из `/account/editor`; в `tbl_song_assignments` этой записи больше нет; черновика (`tbl_song_assignment_drafts`) для неё нет (или был удалён, если существовал).
2. **Given** у редактора есть задание со статусом `in_progress` (есть черновик, не отправлен), **When** он нажимает «Отказаться» и подтверждает, **Then** карточка исчезает, `tbl_song_assignments` запись удалена, `tbl_song_assignment_drafts` запись для этого задания удалена (никаких «висящих» orphan-записей).
3. **Given** у редактора есть задание со статусом `submitted` (отправлено на проверку, админ ещё не вынес вердикт), **When** он нажимает «Отказаться» и подтверждает, **Then** карточка исчезает из его списка; задание и его черновик удалены; админ в `SongEditorTable.vue` этой записи больше не видит.
4. **Given** у редактора есть задание со статусом `rejected` (админ отклонил с комментарием), **When** он нажимает «Отказаться» и подтверждает, **Then** карточка исчезает; задание и его черновик удалены; комментарий админа теряется вместе с удалением (это намеренно — редактор явно отказался от дальнейшей работы по этой песне).
5. **Given** редактор кликнул «Отказаться», **When** в диалоге подтверждения он нажимает «Отмена», **Then** ничего не происходит — карточка остаётся в списке, бэкенд не вызывался.
6. **Given** редактор случайно дважды кликнул «Отказаться» по одной и той же карточке, **When** приходит второй клик, **Then** бэкенд возвращает `not_found`/`assignment_not_found` и UI тихо обрабатывает это как «уже удалено» (карточка просто исчезает, без красного сообщения об ошибке).

### User Story 3 - Редактор может «Удалить» одобренное задание (Priority: P1)

Редактор-волонтёр на странице `/account/editor` для каждой карточки со статусом `approved` (одобрено админом, разметка применена к песне) видит кнопку «Удалить». По клику (после подтверждения) задание удаляется из его списка как «архивная» запись — самой песни это не касается, разметка уже применена и доступна в плеере.

**Why this priority**: После апрува задание формально «закрыто» для редактора, но всё ещё висит в его списке как карточка со статусом «Одобрено». Это не несёт рабочей ценности, а только копится и мешает. Удаление одобренного — это «почистить историю», без побочных эффектов на саму песню (разметка применена, песня в эфире, новости уже вышли). Это самый простой и безопасный сценарий — по нему нечего «отзывать», только снимать карточку.

**Independent Test**: Залогиниться редактором, у которого есть хотя бы одно одобренное задание. Нажать «Удалить» → подтвердить. Карточка исчезает из списка. Песня (через `id`) остаётся доступной в каталоге/поиске/плеере как обычно — разметка не откатывается.

**Acceptance Scenarios**:

1. **Given** у редактора есть задание со статусом `approved`, **When** он нажимает «Удалить» и подтверждает, **Then** карточка исчезает из `/account/editor`; в `tbl_song_assignments` этой записи больше нет; песня в каталоге остаётся доступной как была (`tbl_songs` не тронут, `id_status` не меняется, разметка/маркеры не откатываются).
2. **Given** редактор только что получил одобрение по заданию и видит его внизу списка со статусом «Одобрено», **When** он нажимает «Удалить» и подтверждает, **Then** карточка исчезает без следов; если других одобренных заданий нет — внизу списка становится пусто (без «фантомных» заглушек).
3. **Given** у редактора есть задание со статусом `approved` без черновика (например, после ретрая синхронизации), **When** он нажимает «Удалить» и подтверждает, **Then** карточка исчезает, `tbl_song_assignment_drafts` записи для этого задания нет (как не было — ничего не ломается, если её нет).
4. **Given** редактор кликнул «Удалить» и подтвердил, **When** запрос на сервер завершился ошибкой (например, 5xx/сеть), **Then** карточка остаётся в списке и показывается короткое ненавязчивое сообщение об ошибке («Не удалось удалить, попробуйте ещё раз»).

### User Story 4 - Редактор может «Удалить все одобренные» одним кликом (Priority: P2)

Редактор-волонтёр на странице `/account/editor` видит кнопку «Удалить все одобренные» рядом с заголовком/вводом списка (вне карточек). По клику (после подтверждения) ВСЕ его одобренные задания удаляются из списка за один запрос; карточки активной работы не трогаются.

**Why this priority**: Это массовый сценарий «почистить хвост одобренных» — то же самое, что пройтись по каждой одобренной карточке вручную и нажать «Удалить», но в один клик. Низкий риск (только `approved` — сама песня уже обработана, разметка применена, ничего не сломается), высокая полезность для регулярной «уборки». P2 — потому что ручной обход карточек работает (US-3), а массовая кнопка — это удобство.

**Independent Test**: Залогиниться редактором с 5+ одобренными заданиями и 2+ активными. Нажать «Удалить все одобренные» → подтвердить. Все карточки со статусом `approved` исчезают; карточки активных задач остаются на своих местах. Песни, к которым относились удалённые задания, остаются в каталоге как обычно.

**Acceptance Scenarios**:

1. **Given** у редактора есть N ≥ 1 одобренных заданий и есть активные, **When** он нажимает «Удалить все одобренные» и подтверждает, **Then** все одобренные карточки исчезают; активные остаются; в `tbl_song_assignments` этих N записей больше нет.
2. **Given** у редактора нет ни одного одобренного задания, **When** он видит страницу `/account/editor`, **Then** кнопка «Удалить все одобренные» отображается как неактивная (`disabled`) или скрыта (конкретный UX-выбор фиксируется на этапе планирования, см. Assumptions) — клик по ней невозможен / не делает запрос.
3. **Given** редактор нажал «Удалить все одобренные», **When** в диалоге подтверждения он нажимает «Отмена», **Then** ничего не происходит — карточки остаются, бэкенд не вызывался.
4. **Given** в момент массового удаления один из запросов завершился ошибкой (частичный успех), **When** UI получает ответ, **Then** пользователю показывается короткое сообщение («Удалено X из Y, повторите для остальных») и неудавшиеся карточки остаются в списке; ни одна успешно удалённая не «откатывается».

### User Story 5 - В админке «Задания редактора» есть кнопка «Удалить все одобренные» (Priority: P2)

Администратор открывает компонент «Задания редактора» (`webvue3/src/components/SongEditor/SongEditorTable.vue`) и видит в его тулбаре кнопку «Удалить все одобренные». По клику (после подтверждения) ВСЕ одобренные задания из текущей выборки (с учётом фильтров — статус, исполнитель, автор) удаляются за один запрос; прочие статусы не трогаются.

**Why this priority**: Симметрично US-4 на стороне редактора. Админу тоже нужен способ за один клик почистить копившийся хвост одобренных. Сейчас это можно сделать только ручным «Отозвать» по каждой строке, что долго и неудобно при больших объёмах. P2 — потому что ручной обход работает, а кнопка — удобство.

**Independent Test**: Залогиниться в админку, открыть раздел «Задания редактора». Убедиться, что в выборке есть хотя бы 2 одобренных задания. Нажать «Удалить все одобренные» → подтвердить. Все строки со статусом «Одобрено» исчезают; строки других статусов остаются на своих местах. Если активен фильтр «Все статусы» — удаляются все одобренные во всей выборке. Если активен фильтр «Одобрено» — фактически удаляется вся видимая страница (после подтверждения остаётся «нет строк»).

**Acceptance Scenarios**:

1. **Given** в таблице заданий редактора есть N ≥ 1 строк со статусом «Одобрено» (фильтр «Все статусы»), **When** админ нажимает «Удалить все одобренные» и подтверждает, **Then** все одобренные строки исчезают из таблицы; прочие статусы остаются; в `tbl_song_assignments` этих N записей больше нет; сами песни (`tbl_songs`) не тронуты.
2. **Given** активен фильтр по статусу «Одобрено» и в таблице видно N строк, **When** админ нажимает «Удалить все одобренные» и подтверждает, **Then** удаляются все эти N строк; таблица переходит в пустое состояние.
3. **Given** активен фильтр по исполнителю (например, конкретный редактор) и в таблице видно M одобренных строк, **When** админ нажимает «Удалить все одобренные» и подтверждает, **Then** удаляются только эти M строк (одобренные у конкретного исполнителя); одобренные у других редакторов не затрагиваются.
4. **Given** активен фильтр по автору, **When** админ нажимает «Удалить все одобренные» и подтверждает, **Then** удаляются только одобренные строки, попадающие под фильтр автора; остальные одобренные строки в выборке «Все статусы» не затрагиваются.
5. **Given** в текущей выборке (с учётом всех фильтров) нет ни одной строки со статусом «Одобрено», **When** админ смотрит на тулбар, **Then** кнопка «Удалить все одобренные» отображается как неактивная (`disabled`) или скрыта — клик невозможен / не делает запрос.
6. **Given** админ работает в режиме просмотра серверной БД (`target=remote`), **When** он нажимает «Удалить все одобренные» и подтверждает, **Then** удаляются записи именно в серверной БД (та же логика target-aware, что у существующих кнопок «Удалить»/«Отозвать» в `SongEditorTable.vue`).
7. **Given** в момент массового удаления часть запросов завершилась ошибкой, **When** UI получает ответ, **Then** админу показывается короткое сообщение («Удалено X из Y, повторите для остальных») и таблица остаётся в согласованном состоянии (UI не «разъезжается»: либо все целевые строки убраны, либо только успешно удалённые, без полуудалённых).

### Edge Cases

- Что если редактор нажимает «Отказаться» по заданию, которое прямо сейчас (в момент запроса) одобрил админ? Бэкенд должен быть устойчив к гонке: либо отказать (`conflict`/`not_editable` — админ уже одобрил, см. существующую логику `canEdit()` в `PublicSongEditorController.kt`), либо успешно удалить (если задание уже одобрено, его нет смысла «отзывать» — карточка исчезает как при обычном «Удалить»). Конкретное правило фиксируется на этапе планирования, но в любом случае UI не должен «висеть» или показывать невнятную ошибку.
- Что если редактор нажимает «Отказаться» по заданию, которого больше нет в БД (например, оно удалено админом параллельно)? Бэкенд возвращает `assignment_not_found`; UI тихо убирает карточку из списка (если она ещё видна после локальной перезагрузки) — без красного сообщения об ошибке.
- Что если у редактора 0 заданий вообще (пустой список)? Кнопки массовых операций скрыты/disabled; карточек нет; вёрстка не ломается.
- Что если все одобренные задания редактора уже были удалены ранее (например, кэш браузера показывает их, а в БД их нет)? Массовое удаление должно быть идемпотентным — повторный клик не падает, а возвращает «уже удалено» или «0 удалено», UI не показывает ошибку.
- Что если в админке фильтр «Все статусы» + сортировка по статусу, и таблица показывает строки вперемешку? Массовое удаление должно работать по всему набору, а не только по видимой странице (если в таблице есть пагинация — пагинация НЕ ограничивает область действия, иначе пользователю пришлось бы прокликивать каждую страницу; см. Assumptions).
- Что если запрос «Удалить все одобренные» для админа превышает разумный таймаут (например, 1000+ одобренных записей)? Бэкенд может резать на батчи (по 100/500), и фронт показывает прогресс «Удалено X из Y» (конкретная реализация — на этапе планирования, см. Assumptions).
- Что если в момент подтверждения «Удалить все одобренные» редактор случайно нажал «Отказаться» по одной из карточек? После выполнения обоих запросов карточка однозначно отсутствует; никаких полуудалённых состояний.
- Что если редактор вошёл, видит «Отказаться» по карточке со статусом `submitted`, отказывается, и тут же передумал (нажал F5)? Задание уже удалено, откатить нельзя — об этом сказано в тексте подтверждения (см. FR-008).
- Что если в карточке редактора изменился статус (например, с `submitted` на `rejected`) между загрузкой страницы и кликом «Отказаться»? Кнопка остаётся видимой/работоспособной (статус может смениться в любой момент), но сервер может вернуть конфликт — UI отображает короткое сообщение и перезагружает список.
- Что если у пользователя нет роли «редактор» (`user.isEditor == false`)? Кнопка не показывается (страница `/account/editor` вообще не открывается по существующей логике в `EditorTasksView.vue:74`); бэкенд отдаёт 404 на эндпоинты удаления для не-редакторов.
- Что если в браузере редактора нет JS / сломался JS-бандл? Карточки без JS вообще не отображаются (это SPA), но серверные эндпоинты удаления всё равно защищены авторизацией — чужие/анонимные запросы отвергаются.

### Key Entities

- **Задание (`SongAssignment`)** — уже существующая сущность `tbl_song_assignments`. Никаких структурных изменений эта фича не вносит — она только ДОБАВЛЯЕТ операции удаления (для одной записи и батчем) над уже существующими записями.
- **Черновик задания (`SongAssignmentDraft`)** — уже существующая сущность `tbl_song_assignment_drafts`. Удаляется каскадно за заданием при «Отказаться» (orphan-cleanup) и НЕ трогается при «Удалить» для одобренных (черновика там может уже не быть — он был «сожжён» при апруве).
- **Карточка задания в UI редактора** (`EditorTasksView.vue`, `SongEditorTable.vue`) — представление сущности `SongAssignment` с вычисляемыми полями (`status`, `songName`, `author`, …). Эта фича добавляет к карточке 1-2 кнопки действия (в зависимости от статуса) и не меняет остальные элементы карточки.
- **Массовое действие «Удалить все одобренные»** — новое серверное действие, не являющееся отдельной персистентной сущностью. Семантически — это итерация удаления по списку `id`, попадающих под фильтр. Конкретная реализация (один SQL `DELETE … WHERE status = 'approved' AND assignee_id = ?` vs. батч из N одиночных `delete` через цикл — см. Assumptions) решается на этапе планирования с учётом производительности и паттернов существующего кода.

Проверяется сравнением `tbl_songs` до/после `delete` — должно быть идентично.

- **SC-009**: При ошибке запроса на любое из новых действий (5xx/сеть/timeout) UI MUST показывать короткое ненавязчивое сообщение об ошибке и оставлять UI в согласованном состоянии — никаких «пустых списков» из-за непрочитанного ответа, никаких «зависших» карточек в полусостоянии.

## Assumptions

- **Сортировка на клиенте vs. на сервере.** На сервере `SongAssignment.loadByAssignee` сейчас возвращает список, отсортированный по `id` (см. `SongAssignment.kt:105`). Добавление нового эндпоинта «Удалить все одобренные» и операции «Удалить»/«Отказаться» не требует менять серверную сортировку — сортировка «активные выше одобренных» может быть реализована на клиенте (`computed sortedDigest` / `sorted()` в `EditorTasksView.vue`). Это минимизирует изменения на бэкенде и держит поведение публичного и админского списков независимыми. Альтернатива (добавить `ORDER BY CASE WHEN admin_status='approved' THEN 1 ELSE 0 END, id DESC` в `SongAssignment.loadByAssignee`) — рассматривается на этапе планирования, но не обязательна.
- **HTTP-метод для эндпоинтов удаления.** В проекте преобладает `POST` (даже для операций удаления — см. `/api/songeditor/delete`, `/api/songeditor/revoke`), а REST-чистый `DELETE` не используется. Новые эндпоинты наследуют ту же конвенцию — `POST /api/public/account/editor/tasks/{id}/refuse`, `POST /api/public/account/editor/tasks/{id}/delete`, `POST /api/public/account/editor/tasks/delete-approved`, `POST /api/songeditor/delete-approved`. Альтернатива (семантический `DELETE`) — отвергнута ради консистентности.
- **Удаление «Удалить все одобренные» для редактора — один SQL vs. батч.** В рамках этой фичи допустимы оба варианта:
  - **Один SQL**: `DELETE FROM tbl_song_assignments WHERE assignee_id = ? AND id IN (SELECT assignment_id FROM tbl_song_assignment_drafts WHERE user_status = 'submitted' AND ...)` — нет, проще: вычислить список `id` через `SongAssignment.loadByAssignee` + композитный статус, потом `DELETE FROM tbl_song_assignments WHERE id IN (...) AND assignee_id = ?`. Параллельно удалить связанные `draft`-записи.
  - **Батч одиночных `delete`**: итерация по списку с использованием существующего `SongAssignment.delete(id, db)`.
  Конкретный выбор — на этапе планирования с учётом производительности (при N≤100 — без разницы; при N>500 — одиночный SQL быстрее).
- **Черновики при «Удалить все одобренные».** При апруве черновик уже был «сожжён» (применён к песне, запись остаётся в `tbl_song_assignment_drafts` как архив). Удалять ли его заодно с заданием — решается на этапе планирования. Безопасный дефолт: НЕ удалять (архив не мешает). Альтернатива — удалять заодно (чище БД, но требует доп. SQL).
- **Что считать «одобренным» в админской выборке.** В админке `SongEditorTable.vue` фильтр `filterStatus = 'approved'` — это композитный статус из `digest()` (`SongAssignmentStatus.resolve`). Массовое удаление в админке должно использовать ту же логику определения статуса, что и фильтр, чтобы не было расхождений «фильтр показывает 5, удалилось 3».
- **Disabled vs. hidden для пустой выборки.** Кнопка «Удалить все одобренные» при пустой выборке:
  - **`disabled`** (видна, но серая, с тултипом «нет одобренных заданий») — UX-прозрачно: пользователь видит, что такая кнопка вообще существует, и понимает, почему она не активна.
  - **`hidden`** (не видна вообще) — чище визуально.
  Выбор — на этапе планирования. В обеих редакциях (личный кабинет и админка) выбирается одинаковый вариант для UX-консистентности.
- **Сортировка списка в админке.** В админке `SongEditorTable.vue:117-123` уже есть `STATUS_ORDER` (`submitted=0, in_progress=1, assigned=2, approved=3, rejected=4`). Эта фича НЕ меняет эту сортировку — она работает только в личном кабинете редактора (`/account/editor`). Если в будущем понадобится та же сортировка «активные выше одобренных» в админке — это отдельная задача (не блокирует эту).
- **Размер батча при массовом удалении.** Если у редактора/в выборке админа > 1000 одобренных, единичный `DELETE` может затянуться. На этапе планирования решается, резать ли на батчи (`LIMIT 100` в цикле, прогресс «Удалено X из Y»). Для типичных объёмов (≤100 одобренных у одного редактора, ≤500 у админа в фильтре) — единичный запрос.
- **Подтверждение необратимости.** Текст диалога подтверждения («Это действие нельзя отменить» + «будут удалены записи о N назначениях, сами песни не пострадают») — обязателен и должен быть показан ДО отправки запроса (без автоподтверждения).
- **Никаких новых ролей и разрешений.** Кнопка «Удалить» в личном кабинете доступна любому редактору для СВОИХ заданий (без разделения на «может удалять свои vs. не может»). Кнопка «Удалить все одобренные» в админке доступна любому, у кого есть доступ к `SongEditorTable.vue` (там нет отдельной роли — это `permitAll()` в `SecurityConfig.kt`).
- **Связь с монитором.** Существующая проверка `SubmittedAssignmentsCheck` НЕ затрагивается — она считает только `submitted`, массовое удаление `approved` на неё не влияет.
- **Не ломаем существующий «Отозвать» в админке.** В админке остаются существующие кнопки «Отозвать» и «Удалить» в каждой строке — новая кнопка «Удалить все одобренные» лишь добавляет массовый сценарий.
- **Нумерация фичи.** Спека получает `154-editor-tasks-manage` (следующий свободный номер в `specs/`).
