# Feature Specification: Пагинация / динамическая подгрузка результатов поиска

**Feature Branch**: `262-search-pagination`
**Created**: 2026-08-28
**Status**: Draft
**Input**: User description: "Результатов поиска может быть очень много, поэтому нужно предусмотреть запросы с чанкованием и пагинацию или динамическую подгрузку результатов поиска на вебе."

## Clarifications

### Session 2026-08-28

- Q: Какой должна быть модель взаимодействия пользователя с большим списком результатов — классическая пагинация, бесконечная подгрузка (infinite scroll) или обе сразу (переключатель)? → A: **Бесконечная подгрузка (infinite scroll)** — кнопка «Загрузить ещё» внизу списка, без классических кнопок страниц; общее состояние страницы в URL — через `?page=N` для shareable-ссылок и F5-устойчивости (фактический срез — последняя загруженная страница).
- Q: Какой размер страницы (page size) использовать по умолчанию? → A: 35 — единообразно со стандартом проекта (см. `livedocs/features/093-news-pagination-top-35.md`, админка `/news` — 35/страница).
- Q: Должно ли состояние пагинации отражаться в URL (shareable-ссылки вида `/search?...&page=N`), или храниться только в памяти компонента? → A: В URL — чтобы можно было поделиться ссылкой на конкретную страницу результатов и сохранить позицию при F5. Параметры: `page` (1-based, default 1), `pageSize` (default 35, допустимые — 10/25/35/50/100). Для бесконечной подгрузки `page` в URL обозначает «последнюю загруженную порцию» — F5 восстанавливает её и автоматически подгружает всё, что выше неё.

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Поиск с большим числом результатов остаётся отзывчивым (Priority: P1)

Гость или зарегистрированный пользователь вводит запрос на странице
`/search` (название песни, автор, текст, альбом — в любой комбинации),
который возвращает **большое** количество совпадений (сотни/тысячи).
Список результатов загружается **порциями** (чанками), и UI остаётся
отзывчивым: первая порция появляется быстро, остальные подгружаются
по мере необходимости. В верхней части списка пользователь видит
счётчик «Показано X из Y» (где Y — общее число совпадений).

**Why this priority**: Главная проблема, заявленная пользователем —
«результатов может быть очень много». Без чанкования бэкенд возвращает
весь массив сразу (до ~18k песен на проде), фронт рендерит сотни строк
одним блоком — таймауты, лаги интерфейса, деградация UX. Это базовый
сценарий «нашёл → листаю».

**Independent Test**: Открыть `/search`, ввести запрос, возвращающий
≥500 песен (например, `text=любовь` или `author=михайлов` без
уточнения). Проверить, что:
- первая порция результатов появляется **быстро** (визуально ощутимо
  быстрее, чем до изменений — за счёт того, что бэк не возвращает
  весь массив сразу);
- счётчик «Показано X из Y» присутствует и корректен;
- прокрутка/переход по страницам работает без зависаний.

**Acceptance Scenarios**:

1. **Given** пользователь ввёл запрос, вернувший ≥500 песен,
   **When** он нажимает «Искать»,
   **Then** бэкенд отдаёт **первую порцию** (35 песен) с метаданными
   пагинации, фронт отрисовывает её; общее число результатов (Y)
   отображается в счётчике.

2. **Given** результаты содержат более одной страницы,
   **When** пользователь нажимает кнопку «Загрузить ещё» (или
   прокручивает список к низу, если включён auto-load — см. FR-014),
   **Then** подгружается **следующая порция** (35 песен) **без
   перезагрузки уже отрисованных строк** — новые строки дописываются
   в конец текущего списка; счётчик «Показано X из Y» обновляется;
   порядок песен в пределах и между страницами стабилен
   (не перемешивается); URL обновляется (`?page=N`, где N — последняя
   загруженная страница).

3. **Given** пользователь изменил параметры запроса (например, ввёл
   дополнительное слово в поле «по тексту»),
   **When** он запускает новый поиск,
   **Then** счётчик подгруженных страниц **сбрасывается на 1**; ранее
   подгруженные результаты заменяются новой первой порцией;
   `page` в URL сбрасывается на 1; счётчик Y обновляется.

4. **Given** пользователь поделился URL `/search?...&page=3` или
   обновил страницу (F5) после подгрузки 3 страниц,
   **When** страница загружается,
   **Then** фронт автоматически подгружает **все порции от page=1 до
   page=3** (чтобы пользователь оказался у того же среза, что и до
   F5); счётчик «Показано X из Y» и `page` в URL соответствуют
   срезу. Если auto-load всех трёх порций недопустим по UX-соображениям
   (мгновенный «flash» трёх подряд запросов), допускается
   восстановление среза через прямую загрузку **только** `page=3`
   и отрисовка «дыры» в списке с пометкой «Загрузите предыдущие
   страницы для просмотра всего среза» — Implementation Notes
   (контрактно достаточно, что `page=3` подгружается; остальное —
   UX-полировка).

5. **Given** пользователь просматривает N загруженных порций,
   **When** он вручную прокручивает список вниз к только что
   подгруженной порции,
   **Then** прокрутка остаётся плавной, без «прыжков»; если auto-load
   включён, при приближении к концу списка срабатывает следующая
   подгрузка без перекрытия уже отрисованных строк.

### User Story 2 — Существующие сценарии поиска не ломаются (Priority: P1)

Все ранее работавшие функции поиска (UI из спеки 261) продолжают
работать без регрессий:
- префилл формы из query-параметров (`?songName=...&author=...&text=...`)
  при первом заходе;
- модалка оформления подписки на конкретную песню при клике по
  золотой иконке плеера;
- подпись со сроками эфира («Будет в эфире с ДД.ММ.ГГГГ» / «В эфире
  до ДД.ММ.ГГГГ»);
- иконка «В корзину» (`CartIcon`) для премиум-контента;
- состояние «Ничего не найдено» (когда Y=0);
- два дизайна (classic/modern) через CSS-переменные `--km-*`;
- мобильный вьюпорт — та же адаптивная строка, что и в спеке 261.

**Why this priority**: Изменение формы данных в `searchResults` может
сломать все компоненты строки (`PlayerIcon`, `FavoriteIcon`,
`PlaylistIcon`, `PremiumIcon`, `CartIcon`, `showDate`, `dateLabel`,
превью альбома/автора). Это регресс-риск №1 — поэтому явно тестируется.

**Independent Test**: Открыть `/search`, прогнать вручную все сценарии
выше для запроса с 1–5 песнями (одна страница). Каждый из них должен
работать идентично до изменения.

**Acceptance Scenarios**:

1. **Given** запрос вернул 0 песен (Y=0),
   **When** результаты отрисовываются,
   **Then** показывается блок «Ничего не найдено», счётчик «Показано
   X из Y» скрыт или показывает «0 из 0», элементов пагинации нет.

2. **Given** запрос вернул 1–35 песен (одна страница),
   **When** страница загружена,
   **Then** все элементы UI работают как в спеке 261 (иконки,
   превью, ссылки, подписи, эфир-даты).

3. **Given** дизайн переключён на `modern` (через `localStorage`),
   **When** пользователь просматривает страницу 2,
   **Then** цвета/фон/границы берутся из тех же CSS-переменных
   `--km-*`, без хардкода цветов; визуально страница не отличается
   от стиля страницы 1.

### User Story 3 — Бэкенд отдаёт данные порциями и считает общее число (Priority: P2)

Эндпоинт `/api/public/songs` принимает параметры пагинации (`page`,
`pageSize`) и возвращает **обёртку** с массивом результатов и
метаданными: общее число (`totalCount`), число на текущей странице
(`pageSize`), номер страницы (`page`), флаг «есть ещё» (`hasMore`).
Сортировка **стабильна** между страницами (порядок не меняется при
повторных вызовах с тем же запросом).

**Why this priority**: Без этого UI не сможет показать «X из Y» и
корректно подгружать следующие страницы; без стабильной сортировки —
песни будут дублироваться или пропадать между страницами (классическая
проблема offset-пагинации на динамических данных).

**Independent Test**: Через `curl`/`Postman` вызвать `/api/public/songs?songName=...&page=1&pageSize=10`
и `/api/public/songs?songName=...&page=2&pageSize=10`. Проверить, что:
- оба ответа содержат `totalCount` одинаковое значение;
- `pageSize <= totalCount` (для page=2, если totalCount < 11, ответ
  содержит остаток);
- элементы в page=2 не пересекаются с элементами page=1 (по `id`);
- сортировка совпадает между запросами.

**Acceptance Scenarios**:

1. **Given** запрос с ≥35 совпадениями,
   **When** бэкенд обрабатывает `page=1&pageSize=35`,
   **Then** ответ содержит ровно 35 элементов (или меньше, если
   totalCount < 35), поля `totalCount`, `page`, `pageSize`, `hasMore`.

2. **Given** запрос с ≥70 совпадениями,
   **When** бэкенд обрабатывает `page=2&pageSize=35`,
   **Then** элементы не пересекаются с `page=1`, `hasMore = true`
   (если есть ещё).

3. **Given** запрос с <35 совпадениями,
   **When** бэкенд обрабатывает `page=1&pageSize=35`,
   **Then** ответ содержит все совпадения; `hasMore = false`.

4. **Given** запрос с 0 совпадений,
   **When** бэкенд обрабатывает любой `page`,
   **Then** ответ содержит пустой массив; `totalCount = 0`,
   `hasMore = false`.

### User Story 4 — Контроль ошибок и пустых страниц (Priority: P3)

Пользователь видит понятное поведение при ошибках сети / пустых
страницах / выходе за пределы:
- при сетевой ошибке подгрузки следующей порции — не падает весь
  список, а показывается «не удалось загрузить» с кнопкой «Повторить»;
- при переходе на несуществующую страницу (например, `page=999` для
  запроса с 50 результатами) — показывается «Страница не найдена»
  или автоматический редирект на page=1;
- при смене фильтров во время подгрузки — отменяется текущий
  in-flight запрос, инициируется новый (без race-условий).

**Why this priority**: Защита от UX-катастроф (зависший спиннер,
перемешанные результаты двух запросов). Не блокер, но обязательная
гигиена для продакшн-сценария.

**Independent Test**: Открыть DevTools → Network → заблокировать
запрос `/api/public/songs?page=2`, нажать «Загрузить ещё». Проверить
появление «не удалось загрузить» + кнопка retry; разблокировать —
retry работает.

**Acceptance Scenarios**:

1. **Given** следующая порция не загрузилась (network/timeout/5xx),
   **When** фронт обнаруживает ошибку,
   **Then** показывается inline-сообщение «Не удалось загрузить ещё»
   с кнопкой «Повторить»; ранее загруженные результаты остаются на
   экране, ничего не пропадает.

2. **Given** URL содержит `page=N`, где N > totalPages
   (например, `?page=999` для запроса с 50 результатами),
   **When** страница загружается,
   **Then** бэкенд отдаёт пустой массив + `totalCount=50`; фронт
   показывает пустое состояние «Страница не найдена» со ссылкой
   «К первой странице» (или автоматический сброс `page` в URL
   на 1 — решение Implementation Notes); кнопка «Загрузить ещё»
   скрыта (`hasMore=false`).

3. **Given** пользователь изменил фильтры во время подгрузки
   следующей порции,
   **When** новый поиск запущен,
   **Then** старый in-flight запрос отменяется; в результатах
   отображаются данные нового запроса, а не «смесь» старого и нового
   (защита от race-условий через requestId/token, как уже сделано
   в существующем `search` action — расширить паттерн).

### Edge Cases

- **Запрос с 0 результатов**: `totalCount=0`, массив пуст, UI
  показывает «Ничего не найдено», кнопка «Загрузить ещё» скрыта.
- **Запрос ровно на одну страницу** (35 результатов): кнопка
  «Загрузить ещё» скрыта (`hasMore=false`), но `hasMore=false`
  присутствует в ответе.
- **Запрос на границе страницы** (например, ровно 70 результатов,
  `page=2`): возвращается 35 элементов, `hasMore=false`.
- **Запрос с очень коротким term** (1–2 символа): на бэке уже есть
  правило `${term}.length < 3` → пустой результат (см. `PublicApiController.kt:686`);
  кнопка «Загрузить ещё» не показывается, счётчик Y=0.
- **Невалидный `page` или `pageSize`** (page=0, page=-1, pageSize=0,
  pageSize>100, нечисловые значения): бэк нормализует к defaults
  (page=1, pageSize=35) или отдаёт 400 — выбор Implementation Notes;
  контрактно: запрос НЕ падает, фронт получает валидный ответ.
- **Параллельные клики «Загрузить ещё»** (rapid double-click):
  защита от дублей — второй клик игнорируется, пока идёт первая
  подгрузка (флаг `isLoadingMore` в state, кнопка disabled).
- **Очень большой totalCount** (10 000+): кнопка «Загрузить ещё»
  продолжает работать — каждое нажатие добавляет 35 песен; auto-load
  при scroll near bottom срабатывает многократно; DOM-дерево
  постепенно растёт — допустимо для типичных сценариев поиска
  (1–3 порции), но для экстремальных (≥100 порций) в будущем может
  понадобиться виртуальный скролл (отдельная спека).
- **Сетевой сбой в момент перезагрузки страницы** (F5 на `page=3`):
  при ошибке первого запроса страница не падает, показывается «не
  удалось загрузить» + retry (тот же UX, что в Story 4).
- **Авторизация меняется во время просмотра** (пользователь залогинился
  / разлогинился): поведение иконок плеера/избранного/корзины
  обновляется через реактивные геттеры (`useAuth`, `useCart`) без
  перезагрузки списка — уже работает в спеке 261, регресс-недопустим.
- **Мобильный вьюпорт**: та же адаптивная разметка, что в спеке 261
  (одна строка через CSS); кнопка «Загрузить ещё» адаптируется
  (полная ширина на узких экранах, не sticky-header).

## Requirements *(mandatory)*

### Functional Requirements

#### Backend

- **FR-001**: Эндпоинт `GET /api/public/songs` MUST принимать
  опциональные query-параметры:
  - `page: Int` (1-based, default `1`, минимум `1`);
  - `pageSize: Int` (default `35`, допустимые значения — `10`, `25`,
    `35`, `50`, `100`).
  Невалидные значения нормализуются к defaults на бэке (или
  отклоняются с 400, Implementation Notes).

- **FR-002**: Эндпоинт MUST возвращать JSON-обёртку
  `PagedSongsDto` со следующей структурой (или эквивалентной —
  окончательное имя и формат в Implementation Notes):
  ```json
  {
    "items": [ SongPublicDto, ... ],
    "totalCount": 1234,
    "page": 1,
    "pageSize": 35,
    "hasMore": true
  }
  ```
  где `items.length <= pageSize`, `hasMore = (page * pageSize) < totalCount`.

- **FR-003**: При **отсутствии** параметров `page` и `pageSize`
  (для обратной совместимости с существующими потребителями, если
  такие есть — FR-016) бэкенд MUST возвращать ответ в **старом
  формате** (`List<SongPublicDto>`), а не в обёртке. Это позволяет
  не ломать существующих потребителей, если они есть (проверяется
  в Implementation Notes через grep по проекту).

- **FR-004**: Сортировка результатов MUST быть **стабильной**
  между страницами и между повторными вызовами с одним и тем же
  запросом. Конкретное поле сортировки — Implementation Notes
  (разумный default — `Song.id ASC`, что эквивалентно порядку
  добавления в БД и совпадает с поведением `Song.loadListFromDb`
  без явной сортировки — стабильно).

- **FR-005**: Подсчёт `totalCount` MUST выполняться **отдельным
  SQL-запросом** `SELECT COUNT(*) FROM tbl_songs WHERE <filter>`,
  а не высчитываться как `items.size` (что даёт неверный результат
  для страниц кроме последней). Тот же фильтр, что и для `items`,
  включая все специфичные условия: `id_status >= 6` для публичной
  поверхности (spec 013), `author_in` для резолва автора (spec 015),
  `text`, `song_album` и пр.

- **FR-006**: Запрос `items` MUST использовать `LIMIT pageSize OFFSET
  (page-1)*pageSize` (или эквивалент — `Song.loadListFromDb` +
  ручной `.drop(...).take(...)` в Kotlin). OFFSET для больших
  значений может быть медленным — Implementation Notes может
  предложить keyset-пагинацию как оптимизацию для будущего, **не
  в рамках этой спеки** (минимальный дифф).

- **FR-007**: Никаких дополнительных HTTP-запросов «ради пагинации»
  (например, отдельный эндпоинт `/songs/count`) — `totalCount`
  возвращается в составе того же ответа `/api/public/songs`.

#### Frontend (Vuex + SearchView)

- **FR-008**: Vuex-стор `songs` MUST содержать новое состояние
  `searchPagination` с полями:
  - `page: number` (текущая страница, 1-based);
  - `pageSize: number` (размер порции);
  - `totalCount: number` (общее число результатов);
  - `hasMore: boolean` (есть ещё страницы);
  - `isLoadingMore: boolean` (флаг защиты от дублей,
    параллельных запросов).
  Существующее состояние `searchResults: SongPublicDto[]` остаётся
  и хранит **все** загруженные элементы (нарастающий итог), а не
  только текущую страницу.

- **FR-009**: Action `search({ ...params, page, pageSize })` MUST
  вызывать `/api/public/songs` с параметрами пагинации и записывать
  результат в `searchResults` через `appendSearchResults` (новый
  mutation) — для `page > 1` массив дополняется, для `page === 1`
  — перезаписывается. Action также записывает `searchPagination`
  из ответа.

- **FR-010**: Action `loadMoreSearchResults()` MUST запрашивать
  следующую страницу (`page + 1`) с тем же набором фильтров и
  дополнять `searchResults`. Если `!hasMore` или `isLoadingMore`,
  action — no-op.

- **FR-011**: Action `search` MUST сбрасывать пагинацию на
  страницу 1 при **любом** изменении фильтров (songName/author/text/
  album). Если фильтры не изменились, но меняется `page` —
  пагинация не сбрасывается.

- **FR-012**: Query-параметры URL MUST включать `page` и `pageSize`
  для shareable-ссылок и восстановления позиции при F5. При
  первичной загрузке страницы URL парсится, и если `page > 1` —
  автоматически подгружается соответствующая страница.

- **FR-013**: UI MUST отображать счётчик «Показано X из Y» над
  списком результатов (или в верхней зоне списка). При `Y = 0`
  счётчик скрывается (показывается «Ничего не найдено»).

- **FR-014**: UI MUST использовать **бесконечную подгрузку**
  (infinite scroll): кнопка «Загрузить ещё» внизу списка подгружает
  следующую порцию (35 песен) и дописывается к уже отрисованному
  списку; URL обновляется (`?page=N`, где N — последняя загруженная
  страница). При ручной прокрутке к низу списка допускается
  автоматическая подгрузка (auto-load на scroll-near-bottom)
  — Implementation Notes; контрактно достаточно наличия кнопки
  как явного триггера. Кнопка скрывается, когда `hasMore === false`
  или идёт подгрузка (`isLoadingMore === true`). Никаких классических
  кнопок «1 2 3 … N» в UI нет. (Clarifications Q1 → B, 2026-08-28.)

- **FR-015**: При ошибке подгрузки следующей порции (network/5xx)
  UI MUST показывать inline-сообщение «Не удалось загрузить ещё»
  с кнопкой «Повторить», не сбрасывая уже отрисованные результаты.

- **FR-016**: Frontend MUST корректно работать с обратной
  совместимостью: если бэк возвращает ответ **без обёртки**
  (старый формат `List<SongPublicDto>` — FR-003), фронт воспринимает
  его как «все результаты на одной странице» (`totalCount = items.length`,
  `hasMore = false`). Это позволяет катить изменение бэка и фронта
  независимо.

- **FR-017**: UI MUST корректно отменять предыдущий in-flight запрос
  при смене фильтров (существующий паттерн с `requestId` в action
  `search` — расширить на `loadMoreSearchResults` при смене
  фильтров; в рамках одной сессии параллельные `loadMore` не
  отменяются, только при смене фильтров).

- **FR-018**: Все компоненты строки из спеки 261
  (`PlayerIcon`, `FavoriteIcon`, `PlaylistIcon`, `PremiumIcon`,
  `CartIcon`, превью альбома/автора, эфир-даты, ссылки на
  `/song` и `/zakroma`) MUST работать без регрессий — независимо
  от того, какая порция сейчас отображается.

### Key Entities *(include if feature involves data)*

- **PagedSongsDto (бэк, новый DTO)**: обёртка ответа
  `/api/public/songs` при пагинированном запросе.
  Поля:
  - `items: List<SongPublicDto>` — массив песен текущей страницы
    (порядок стабилен между страницами, FR-004);
  - `totalCount: Long` — общее число песен, удовлетворяющих
    фильтру (вычисляется отдельным `SELECT COUNT(*)`, FR-005);
  - `page: Int` — номер текущей страницы (1-based, echo из запроса
    после нормализации);
  - `pageSize: Int` — размер страницы (echo после нормализации);
  - `hasMore: Boolean` — `page * pageSize < totalCount`.

  Сериализуется через Jackson по образцу существующих DTO
  (`@JsonProperty` при необходимости). Поле `items` может быть
  пустым массивом (НЕ `null`), если совпадений нет.

- **searchPagination (UI, фронт, новый slice в `songs` store)**:
  состояние пагинации в Vuex. Поля:
  - `page: number` (1-based, default 1);
  - `pageSize: number` (default 35, допустимые — 10/25/35/50/100);
  - `totalCount: number` (обновляется из ответа);
  - `hasMore: boolean`;
  - `isLoadingMore: boolean` (флаг против дублей при rapid-click).
  Хранится **отдельно** от `currentSearchParams` (фильтры), чтобы
  можно было менять страницу, не сбрасывая фильтры.

- **searchResults (UI, фронт, существующий)**: нарастающий итог
  всех загруженных элементов. При `page=1` — перезаписывается;
  при `page>1` — дополняется. Не сбрасывается при подгрузке
  следующих страниц (только при смене фильтров, FR-011).

- **URL search params (новый slice в роутере)**: query-параметры
  URL страницы `/search` расширяются:
  - `page: number` (default 1);
  - `pageSize: number` (default 35).
  Совместимы с существующими `songName`, `author`, `text`, `album`
  (FR-012).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Запрос, возвращающий ≥500 песен, при первом обращении
  отдаёт **ровно `pageSize` элементов** (≤35), а не весь массив.
  Проверка: DevTools Network — ответ содержит ≤35 элементов в
  массиве `items`, а НЕ 500/1000/10000.

- **SC-002**: Полная задержка до отрисовки **первой порции**
  результатов сокращается по сравнению с текущим состоянием
  (где возвращается весь массив). Проверка: ручной сценарий,
  запрос с ≥500 песен — субъективно заметно быстрее; для
  объективной проверки — поле `Date` в DevTools для первого
  рендера списка сокращается на ≥50% по сравнению с baseline
  (до изменений). Baseline фиксируется в Implementation Notes
  перед началом работ.

- **SC-003**: 100% страниц (`page=1..totalPages`) возвращают
  **непересекающиеся** элементы (по `id`). Проверка: curl
  `page=1` и `page=2`, объединение `id` — без дубликатов.

- **SC-004**: `totalCount` **одинаков** для всех страниц одного
  запроса (не зависит от `page` / `pageSize`). Проверка:
  curl `page=1` и `page=2` → `totalCount` идентичен.

- **SC-005**: Сортировка **стабильна** — повторный вызов того же
  запроса с тем же `page` возвращает те же элементы в том же
  порядке. Проверка: два последовательных curl, сравнение
  массива `id` — побайтовое совпадение.

- **SC-006**: URL `/search?songName=X&page=3&pageSize=35` после
  F5 восстанавливает страницу 3, а не сбрасывается на 1.
  Проверка: ручной сценарий — зайти на `?page=3`, обновить
  страницу, убедиться, что отображается страница 3.

- **SC-007**: 100% функций UI из спеки 261 (иконки плеера,
  избранного, плейлистов, превью альбома/автора, эфир-даты,
  ссылки на `/song` и `/zakroma`, модалка подписки, иконка
  корзины) продолжают работать на любой странице без регрессий.
  Проверка: ручной сценарий по каждой функции на странице 1, 2 и
  последней.

- **SC-008**: При смене фильтра во время подгрузки следующей
  порции, **новый** запрос «побеждает» — в UI отображаются данные
  нового запроса, без «смеси» старого и нового. Проверка:
  DevTools Network — быстро сменить фильтр и нажать «Загрузить
  ещё» → отменённый старый запрос отменяется (Status: (canceled)),
  новый — успешен; в DOM — данные нового запроса.

- **SC-009**: Минимальный дифф бэкенда: расширен один контроллер
  (`PublicApiController.songs()`) и добавлен один новый DTO
  (`PagedSongsDto`). Проверка: `git diff karaoke-web/src/main/kotlin`
  показывает изменение файла `PublicApiController.kt` (добавлены
  параметры `page`/`pageSize`, `LIMIT`/`OFFSET`, `COUNT(*)`)
  и новый файл `PagedSongsDto.kt`. Никаких изменений в SQL-миграциях,
  других контроллерах, других DTO (`ZakromaPublicDto`,
  `SitePlaylistItemDto` и пр.).

- **SC-010**: Размер страницы по умолчанию — **35** (единообразие
  с `093-news-pagination-top-35`). Проверка: curl без `pageSize`
  → ответ содержит поле `pageSize: 35`.

## Assumptions

- Существующий `Song.loadListFromDb(attr, ...)` уже принимает
  `attr`-фильтр; добавляется **только** обёртка LIMIT/OFFSET и
  отдельный COUNT-запрос (FR-006, FR-005). Никаких изменений в
  SQL-фильтрах.
- Сортировка по умолчанию — `Song.id ASC` (стабильная, совпадает
  с поведением `loadListFromDb` без явной сортировки). Если
  на проде обнаружится проблема с дублированием между страницами
  (из-за нестабильного порядка), в Implementation Notes
  добавляется явный `ORDER BY id ASC` (без миграции).
- Бэкенд **не вводит новую таблицу/колонку** — все данные берутся
  из существующих `tbl_songs` и связанных; никаких миграций БД.
- Размер страницы по умолчанию — **35** (стандарт проекта,
  `livedocs/features/093-news-pagination-top-35.md`); допустимые
  альтернативы — `10`, `25`, `50`, `100`. Значения вне списка
  нормализуются к 35 (или отвергаются с 400 — Implementation Notes).
- URL состояние (`?page=N&pageSize=M`) — обязательно (FR-012) для
  shareable-ссылок и F5-устойчивости. Для выбранной модели infinite
  scroll (Clarifications Q1 → B) `?page=N` обозначает «последнюю
  загруженную порцию», не «текущую страницу» — пользователь видит
  срез всех песен до `page=N`.
- Модель взаимодействия — **бесконечная подгрузка** (infinite
  scroll) с кнопкой «Загрузить ещё» внизу списка (Clarifications
  Q1 → B, FR-014). Классические кнопки страниц НЕ отрисовываются;
  опционально допускается auto-load при scroll near bottom
  (Implementation Notes). URL — `?page=N` для shareable-ссылок.
- Обратная совместимость (FR-003, FR-016) — бэк и фронт умеют
  работать со «старым» форматом ответа (без обёртки) и «новым»
  (с обёрткой). Это позволяет катить изменения независимо и
  упрощает откат.
- Существующая защита от race-условий через `requestId` в action
  `search` расширяется на `loadMoreSearchResults` (FR-017) —
  паттерн уже есть, переиспользуем.
- Все ранее работавшие компоненты строки (спека 261) не
  затрагиваются — меняется только механизм **загрузки** и
  **отображения пагинации**, не сама разметка строки.
- Frontend **не вводит новых зависимостей** (библиотек для
  пагинации, виртуального скролла и т.п.) — реализация на
  существующем Vuex + Vue 3 + Bootstrap 5 (минимальный дифф).
- Если в будущем понадобится виртуальный скролл (для очень
  больших списков без пагинации), это **отдельная** спека —
  в рамках 262 идём по классической модели LIMIT/OFFSET.
