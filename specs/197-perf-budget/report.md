# #197 — бюджет производительности редактора

**Решение владельца 2026-09-30: приемлемая задержка ввода — 16 мс (один кадр).**

Раньше ответ был «сложно сказать» — это было отсутствие данных, а не отказ.
Данные получены в #205 (PR #614): одно нажатие клавиши блокирует главный поток
редактора примерно на **2.4 секунды** (три прогона, p50 2365 / 2500 / 2319 мс,
20–21 длинная задача по 2.1–3.0 с).

## Что означает выбранный бюджет

16 мс — длительность кадра при 60 Гц. Ниже этого отклик не воспринимается как
залипание, и это единственное значение, при котором ввод ощущается прямым.

Текущее значение превышает бюджет примерно в **150 раз**. Разница не в
константе, а в том, что на нажатие синхронно выполняется вся цепочка:

    sourceText -> getSyllables -> updateMarkersBySyllables -> redrawMarkers
                (плюс подсветка словаря)

Достичь 16 мс можно только настоящей оптимизацией цепочки, а не подстройкой.

## Важное следствие для метода

Ровно 16.7 мс даёт `requestAnimationFrame`-замер: он упирается в длительность
кадра и **не способен измерить ничего меньше**. Для проверки бюджета нужен
Event Timing API (`processingEnd - startTime`), как в #205. Иначе «достигли
16 мс» будет невозможно отличить от «ничего не изменилось».

## Открытый вопрос, который бюджет не закрывает

Бюджет говорит «сколько должно быть», но не «с чего начать». Локализация
2.4 секунд — работа #191.
