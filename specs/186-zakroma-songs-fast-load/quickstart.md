# Quickstart: Валидация ускорения загрузки песен в Закромах

**Spec**: [spec.md](./spec.md) | **Plan**: [plan.md](./plan.md) | **Date**: 2026-08-14

## Цель

Подтвердить end-to-end, что после фичи:
1. Загрузка автора с 2500 песен занимает ≤ 7 сек (SC-002), улучшение ≥ ×2 (SC-005).
2. Первая партия песен появляется за ≤ 2 сек (SC-001).
3. Прогрессометр отражает реальный прогресс (SC-003).
4. Переключение вкладки не «замораживает» прогрессометр (SC-004, FR-005/006).
5. Для малых авторов (≤ 200 песен) поведение не ухудшилось (SC-006).

## Предусловия

- Docker-стек `karaoke-public`, `karaoke-web`, `karaoke-app`, `karaoke-db` запущен (`deploy/do.sh start` или `cd deploy && docker compose up -d`).
- В БД есть как минимум:
  - **1 крупный автор** с ≥ 2000 песен (например, «Кино», «Аквариум», «Наутилус Помпилиус» — обычно есть в проде).
  - **1 малый автор** с 5-50 песен (для контрольного сценария SC-006).
- Браузер: Chrome / Edge / Firefox актуальной версии (для проверки бага с фоновой вкладкой — обязательно Chrome).
- DevTools открыты (для замеров и Network/Performance).

## Подготовка

1. Открыть `https://localhost:8897/zakroma` (или соответствующий URL окружения).
2. Войти как редактор (если требуется для тестирования не-published песен).
3. Открыть DevTools → Console.
4. Выполнить подготовительный скрипт для логирования метрик (см. ниже).

### Скрипт замера в Console (опционально)

```javascript
// Включить метрики стрима (уже есть в production через useZakromaStreamProgress).
// Просто наблюдаем в Network tab за /api/public/zakroma/stream response time.
// В Console — кликнуть на тайл крупного автора и засечь время:
console.time('zakroma-load-large')
// (после полной отрисовки)
console.timeEnd('zakroma-load-large')
```

## Сценарий 1: Полное время загрузки крупного автора (SC-002, SC-005)

**Предусловия**: открыта страница «Закрома», авторизация не требуется.

**Шаги**:
1. Кликнуть на тайл **крупного** автора (≥ 2000 песен).
2. **Засечь время** от момента клика до момента, когда **последняя песня** появилась в списке (можно ориентироваться на «100 %» в прогрессометре).
3. Записать результат.

**Ожидаемый результат (PASS)**:
- Время **≤ 7 секунд** (SC-002).
- Прогрессометр плавно растёт от 0 % до 100 % за это время.
- В списке видны все песни автора (без пропусков).

**Типичный результат до фичи (baseline)**: 12-17 секунд.

**Ожидаемое улучшение**: ×2-3 (минимум по SC-005).

---

## Сценарий 2: Время до первой отрисовки (SC-001)

**Предусловия**: те же, что в сценарии 1.

**Шаги**:
1. Очистить Network tab в DevTools.
2. Кликнуть на тайл **крупного** автора.
3. Наблюдать за Network → `/api/public/zakroma/stream` → записать `Time to First Byte` (TTFB).
4. Записать время появления **первой песни** в списке (можно ориентироваться на момент, когда `state.zakroma` стал непустым в Vue DevTools).

**Ожидаемый результат (PASS)**:
- TTFB ≤ 1 сек (backend сразу шлёт `meta` с `expectedCount`).
- Первая песня видна **≤ 2 секунд** с момента клика (SC-001).

**Типичный результат до фичи**: 5 секунд «пустой паузы» + потом появление первой песни (объясняется N+1 SQL в backend'е — `Zakroma.getZakroma()` синхронно грузит всё до отправки первого `song`-сообщения; на самом деле `meta` отправляется сразу, но первая `song` приходит только после полной загрузки).

## Сценарий 3: Прогрессометр real-time (SC-003)

**Предусловия**: те же.

**Шаги**:
1. Кликнуть на тайл крупного автора.
2. **Видеозаписать** экран (или скринкаст) — нужно видеть, как прогрессометр растёт.
3. После завершения загрузки проверить логи в Network tab: количество NDJSON-сообщений `song` должно соответствовать числу песен автора (например, 2500 сообщений для автора с 2500 песнями).

**Ожидаемый результат (PASS)**:
- Прогрессометр появляется в течение 100 мс после клика (FR-004, SC-003).
- Прогрессометр растёт **плавно** (не скачками).
- Значение прогрессометра = `receivedCount / expectedCount` — соответствует реально полученным NDJSON-сообщениям.

**Красный флаг (FAIL)**:
- Прогрессометр показывает фиксированное значение, потом скачком меняется на 100%.
- Прогрессометр показывает «X из N», где X заведомо меньше реально полученных сообщений (свидетельство синтетического прогресса).

## Сценарий 4: Переключение вкладки — прогресс не замораживается (SC-004, FR-005, FR-006)

**Предусловия**: те же. **Браузер — Chrome** (Firefox и Edge тоже подходят, но Chrome — основной target).

**Шаги**:
1. Кликнуть на тайл крупного автора.
2. **Сразу** (не дожидаясь загрузки) переключиться на другую вкладку браузера (например, открыть новую вкладку с `google.com`).
3. **Подождать 30 секунд**.
4. Вернуться на вкладку «Закroma».

**Ожидаемый результат (PASS)**:
- Прогрессометр **сразу** (в течение 500 мс) показывает актуальный процент (≥ 95 %, если загрузка завершилась).
- Если загрузка завершилась — прогрессометр **скрыт** (или показывает 100 % и скрывается в течение 500 мс — НЕ «доигрывает» по таймеру).
- В списке видны все песни автора (без пропусков).
- Никакого «застывания» на старом значении.

**Типичный результат до фичи (baseline, FAIL)**:
- Прогрессометр показывает ~1-5 % (прогресс, на котором ушли со вкладки).
- Через 5-10 секунд после возврата — медленно «доезжает» до 100 % (фронт обрабатывает накопленные сообщения с троттлингом 1000мс/yield).

**Детальная проверка через DevTools**:
1. До клика → Performance tab → Start recording.
2. Кликнуть на тайл → сразу переключиться.
3. Через 30 сек вернуться → Stop recording.
4. Проверить на timeline: между событиями `zakroma_stream_done` (отправлено в фоне) и `visibilitychange → visible` (возврат на вкладку) НЕ должно быть паузы > 1 сек.

## Сценарий 5: Отмена загрузки (FR-008)

**Предусловия**: страница «Закрома» открыта.

**Шаги**:
1. Кликнуть на тайл крупного автора → начинается загрузка.
2. **Сразу** (через 1-2 сек, пока идёт загрузка) кликнуть на тайл **другого** автора.

**Ожидаемый результат (PASS)**:
- Загрузка первого автора **отменяется** (нет накопления `albums.value` от первого).
- Список сразу показывает песни второго автора (или пустоту, если второй ещё не загружен).
- В Network tab видно: первый стрим прерван (`(canceled)`), второй — новый.
- В Console нет ошибок.

**Красный флаг (FAIL)**:
- Видны песни обоих авторов вперемешку.
- Прогрессометр «зависает» на 100 % после второго клика.

---

## Сценарий 6: Малый автор — нет регрессии (SC-006, FR-010)

**Предусловия**: есть автор с ≤ 50 песен.

**Шаги**:
1. Кликнуть на тайл малого автора.
2. Замерить время до полной отрисовки.

**Ожидаемый результат (PASS)**:
- Время ≤ 1 сек (или сопоставимо с baseline до фичи).
- Прогрессометр может **не появиться** (FR-007: для быстрых загрузок прогрессометр скрыт, чтобы не мелькать).

**Красный флаг (FAIL)**:
- Время увеличилось по сравнению с baseline (регрессия для малых авторов).

## Сценарий 7 (опциональный): Backend замеры

**Цель**: подтвердить, что R1 (batch SQL) и R2 (batched flush) работают как задумано.

**Шаги**:
1. Включить SQL-логирование на backend (если есть флаг `logging.level.org.hibernate.SQL=DEBUG` или аналог для `KaraokeConnection`).
2. Кликнуть на тайл крупного автора.
3. В логах backend'а подсчитать:
   - Число SQL-запросов к `tbl_pictures` для одного стрима.
   - Число SQL-запросов к `tbl_albums` для одного стрима.

**Ожидаемый результат (PASS)**:
- `tbl_pictures` — **≤ 2 запроса** (один для портретов авторов, один для обложек альбомов), независимо от числа альбомов.
- `tbl_albums` — **≤ 1 запрос** (один батч для всех `albumId`).

**Типичный результат до фичи (baseline, FAIL)**:
- `tbl_pictures` — `2 + 2 × numAlbums` запросов.
- `tbl_albums` — `numAlbums` запросов (по одному на альбом).
- Для автора с 30 альбомами: 2 + 60 + 30 = 92 запроса (вместо 3).

## Сценарий 8 (опциональный): Ловушка nginx

**Цель**: убедиться, что batched flush не ломается nginx-буферизацией.

**Предусловия**: задеплоен `deploy/80to8897` с `proxy_buffering off` для `/api/public/zakroma/stream` (должно быть после спеки 181).

**Шаги**:
1. Кликнуть на тайл крупного автора.
2. В DevTools → Network → `/api/public/zakroma/stream` → вкладка «Timing».
3. Проверить, что `Waiting (TTFB)` для **каждого** NDJSON-сообщения не растёт (т.е. данные идут потоком, а не буферизуются nginx'ом).

**Ожидаемый результат (PASS)**:
- Данные идут потоком, общее время ответа соответствует backend latency.

**Красный флаг (FAIL)**:
- Время ответа растёт линейно с числом песен (признак nginx-буферизации).

Если FAIL — увеличить `proxy_buffer_size` (например, до 16k) в `deploy/80to8897` и повторить. **Не блокирует PR**, но требует follow-up коммита.

## Когда что-то идёт не так

| Симптом | Вероятная причина | Что делать |
|---------|-------------------|-----------|
| Полное время не уменьшилось | R2 (batched flush) не сработал — frontend всё ещё yield'ит 2500 раз | Проверить Network tab: число flush должно быть ~82 (вместо 5064). Если нет — перепроверить `useZakromaStreamProgress.js` |
| 5-сек пауза осталась | R1 (batch SQL) не сработал — backend всё ещё делает N+1 | Проверить SQL-логи backend: должно быть ≤ 4 запросов вместо 92 |
| Tab-switching bug не ушёл | R3 (queueMicrotask) не применён — `setTimeout(0)` всё ещё там | Проверить `useZakromaStreamProgress.js:139-175`: `setTimeout` заменён на `queueMicrotask`? |
| Прогрессометр «завис» на 100 % | FR-008: AbortController не сработал, frontend обрабатывает отменённые сообщения | Проверить `useZakromaStreamProgress.js:cancel()`: `controller.abort()` вызывается? |
| Регрессия для малых авторов | R1/R2 overhead больше выигрыша для маленьких N | Если < 50 песен стало медленнее — откатить R1/R2 только для случая `expectedCount < 200`. Backlog. |
