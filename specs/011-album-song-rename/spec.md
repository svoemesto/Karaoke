# Feature Specification: Альбом как сущность + переименование Settings→Song

**Feature Branch**: `011-album-song-rename`

**Created**: 2026-07-26

**Status**: Draft

**Input**: User description: "Большое структурное изменение. Надо добавить сущность "Альбом" как отдельную синхронизирующуюся таблицу. У альбома есть автор, год, название, признак (студийный альбом / концертный альбом / сборник / бутлег), порядок сортировки внутри автора (альбомы одного года могут внутри этого года сортироваться не по названию). При работет с песнями предусмотреть это - песня ссылается на альбом. Также необходим рефакторинг названий - сейчас сущьность "песня" называется "settings" (так испорически сложилось), но правильно называть её "Song". Но сущьность Song уже есть - её надо будет тоже как-то переименовать."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Альбом как отдельная сущность, песня ссылается на альбом (Priority: P1)

Администратор каталога может видеть и настраивать альбомы как самостоятельные записи (автор, год, название, тип: студийный/концертный/сборник/бутлег), а не как повторяющийся свободный текст в каждой песне. Для альбомов одного автора, вышедших в один год, можно задать собственный порядок отображения, отличный от алфавитного. Существующие песни автоматически связываются с соответствующими альбомами без ручного ввода данных.

**Why this priority**: Это основной запрошенный функционал — без него невозможно корректно хранить метаданные альбома отдельно от песни и управлять порядком отображения альбомов одного года.

**Independent Test**: Можно полностью проверить, создав/отредактировав альбом в админке, привязав к нему песни, задав порядок сортировки для двух альбомов одного автора и года, и убедившись, что на публичном сайте (страница дискографии автора) альбомы показываются в заданном порядке.

**Acceptance Scenarios**:

1. **Given** у автора есть два альбома, вышедших в одном году, **When** администратор задаёт для них порядок отображения, отличный от алфавитного, **Then** страница дискографии на публичном сайте показывает альбомы именно в этом порядке.
2. **Given** в системе уже есть песни с заполненными текстовыми полями автор/год/альбом, **When** функциональность разворачивается, **Then** для каждой уникальной комбинации (автор, год, альбом) автоматически создаётся ровно одна запись альбома, и все соответствующие песни связываются с ней — без ручного вмешательства.
3. **Given** песня без указанного альбома (сингл), **When** функциональность разворачивается, **Then** песня остаётся без связи с альбомом и отображается так же, как раньше.
4. **Given** альбом, к которому привязаны песни, **When** администратор удаляет этот альбом, **Then** привязанные песни не удаляются и не ломаются — они переходят в состояние "без альбома".

---

### User Story 2 - У песни может быть несколько авторов (Priority: P2)

Администратор может указать у песни, помимо одного главного автора (как сейчас), любое количество дополнительных соавторов/участников (feat.) — без ограничения сверху. Соавторы не влияют на то, на чьей странице автора и по какому URL показывается песня — это по-прежнему определяется только главным автором.

**Why this priority**: Расширяет корректность модели данных (коллаборации/feat.), логически связано с проработкой сущности "песня" в рамках этой же структурной правки, но не блокирует ценность User Story 1.

**Independent Test**: Можно полностью проверить, добавив песне двух и более соавторов через админку и убедившись, что песня по-прежнему отображается только на странице главного автора, а список соавторов виден в деталях песни и может быть изменён (добавление/удаление по одному) в любом количестве.

**Acceptance Scenarios**:

1. **Given** песня с одним главным автором, **When** администратор добавляет двух дополнительных соавторов, **Then** в деталях песни отображаются все трое, но песня по-прежнему числится только за главным автором (страница/URL не меняются).
2. **Given** песня с несколькими соавторами, **When** администратор удаляет одного из них, **Then** остальные соавторы сохраняются, а информация о песне и её принадлежности альбому не меняется.
3. **Given** песня без единого соавтора, **When** её никто не редактирует, **Then** это допустимое состояние (соавторы не обязательны).

---

### User Story 3 - Согласованное именование сущности "песня" (Priority: P3)

Основная сущность "песня", исторически называвшаяся в коде "Settings", переименовывается в "Song" во всей кодовой базе (бэкенд, админ-фронтенд, публичный фронтенд). Существующий не связанный с базой данных класс, который сейчас называется "Song", переименовывается, чтобы не создавать конфликт имён. Отдельная, не связанная с песней функциональность общесайтовых настроек (например, конфигурация капчи) не затрагивается и сохраняет своё название.

**Why this priority**: Это внутреннее улучшение сопровождаемости кода, не видимое конечным пользователям и не блокирующее ценность User Story 1 и 2 — но выполняется в рамках той же структурной правки, поскольку два предыдущих пункта делают путаницу в имени "Settings" ещё заметнее.

**Independent Test**: Можно полностью проверить независимо от User Story 1/2 — поиском по кодовой базе убедиться, что сущность "песня" везде называется согласованно, а все существующие сценарии работы с песнями (синхронизация LOCAL↔SERVER, список, редактирование, воспроизведение) проходят без изменений в поведении.

**Acceptance Scenarios**:

1. **Given** кодовая база после переименования, **When** разработчик ищет сущность "песня" по имени, **Then** она называется согласованно во всех местах (кроме намеренно сохранённых физических идентификаторов в базе данных).
2. **Given** существующие сценарии синхронизации, редактирования и воспроизведения песен, **When** они выполняются после переименования, **Then** поведение идентично тому, что было до переименования.
3. **Given** отдельная функциональность общесайтовых настроек (конфигурация капчи и т.п.), **When** проводится переименование сущности "песня", **Then** эта функциональность не переименовывается и не меняет поведение.

---

### Edge Cases

- Что происходит с песней, у которой не указан альбом (сингл)? — Остаётся без связи с альбомом, отображается как раньше (см. US1, сценарий 3).
- Что происходит, если один автор выпустил два альбома в один год с разными (или похожими, но не идентичными) названиями? — Каждое уникальное название/год образует отдельный альбом; порядок между ними внутри года управляется заданной сортировкой.
- Что происходит при удалении альбома, к которому привязаны песни? — Песни не удаляются, переходят в состояние "без альбома" (см. US1, сценарий 4).
- Что происходит, если у песни меняют главного автора, а она уже привязана к альбому другого (прежнего) автора? — Система не должна допускать противоречивое состояние "автор песни" ≠ "автор её альбома".
- Что происходит, если администратор пытается добавить песне в соавторы того же человека, что уже указан как главный автор? — Не должно создаваться дублирующей/противоречивой записи.

## Requirements *(mandatory)*

### Functional Requirements

**Альбом как сущность**

- **FR-001**: Система ДОЛЖНА хранить альбомы как отдельные записи со следующими атрибутами: автор, год выпуска, название, тип (студийный альбом / концертный альбом / сборник / бутлег), порядок отображения внутри группы (автор, год).
- **FR-002**: Альбомы ДОЛЖНЫ синхронизироваться между базами LOCAL и SERVER тем же механизмом, что и остальные каталожные сущности (авторы, песни, картинки), с тем же уровнем ручного контроля направления синхронизации.
- **FR-003**: Администратор ДОЛЖЕН иметь возможность просматривать, создавать, редактировать и переупорядочивать альбомы через административный интерфейс, аналогично существующему управлению авторами.

**Песня → Альбом**

- **FR-004**: Каждая песня ДОЛЖНА иметь возможность ссылаться максимум на один альбом.
- **FR-005**: При выпуске функциональности система ДОЛЖНА автоматически создать записи альбомов и связать с ними существующие песни на основе уже имеющихся у песни текстовых данных автор/год/альбом, без ручного повторного ввода.
- **FR-006**: Песни без указанного альбома (синглы) НЕ ДОЛЖНЫ принудительно привязываться к какому-либо альбому.
- **FR-007**: Везде, где альбомы одного автора и года показываются пользователю (например, страница дискографии), их порядок ДОЛЖЕН определяться заданной сортировкой, а не алфавитом по названию.
- **FR-008**: Альбом, привязанный к песне, ДОЛЖЕН принадлежать тому же автору, который указан у песни как главный автор.

**Песня → Авторы (множественность)**

- **FR-009**: У песни, помимо одного главного автора, ДОЛЖНА быть возможность указать любое количество дополнительных соавторов/участников — без ограничения сверху и без обязательности (может не быть ни одного).
- **FR-010**: Дополнительные соавторы НЕ ДОЛЖНЫ влиять на группировку по автору, формирование страницы/URL автора на публичном сайте и на принадлежность песни альбому — во всех этих случаях используется только главный автор.
- **FR-011**: Администратор ДОЛЖЕН иметь возможность свободно добавлять и удалять соавторов песни по одному, в любом количестве.

**Переименование Settings → Song**

- **FR-012**: Основная сущность "песня", исторически называвшаяся в коде и в базе данных "Settings", ДОЛЖНА быть переименована в "Song" по всему стеку (бэкенд, административный и публичный фронтенды) **и в имени физической таблицы хранения**.
- **FR-013**: Конфликт имён с уже существующим компонентом, также называющимся "Song" (не являющимся сущностью песни), ДОЛЖЕН быть разрешён переименованием этого компонента.
- **FR-014**: Переименование НЕ ДОЛЖНО затрагивать значение и поведение отдельной, не связанной с песней функциональности общесайтовых настроек — она сохраняет текущее название (в том числе своё отдельное имя таблицы).
- **FR-015**: Переименование ДОЛЖНО быть выполнено без потери данных песен и без потери накопленного состояния синхронизации — переименование физической таблицы ДОЛЖНО быть выполнено одинаково и в согласованном порядке на LOCAL и SERVER базах данных, поскольку это структурное изменение, а не только косметическая правка кода.

### Key Entities *(include if feature involves data)*

- **Song** (переименовано из "Settings"): основная сущность "песня" — исходный/итоговый текст, маркеры разметки, статусы синхронизации, ссылка на главного автора, ссылка на альбом (опционально), список дополнительных соавторов.
- **Album** (новая сущность): музыкальный альбом — принадлежит одному автору, год выпуска, название, тип (студийный/концертный/сборник/бутлег), порядок отображения внутри пары (автор, год); содержит ноль или более песен.
- **Author** (существующая сущность, расширяется связями): теперь формально связана с множеством альбомов и множеством песен как главный автор, а также с множеством песен как дополнительный соавтор.
- **Соавторство песни** (новая связь): связь "песня × дополнительный автор" — чисто информационная, не влияет на группировку по автору, URL или принадлежность альбому.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Администратор может создать альбом и связать его с песнями через интерфейс, аналогичный по логике уже существующему для авторов, без необходимости изучать принципиально новый паттерн.
- **SC-002**: Для любого автора с несколькими альбомами одного года порядок их отображения настраивается независимо от алфавита и корректно отражается везде, где альбомы перечисляются пользователям на публичном сайте.
- **SC-003**: 100% ранее существовавших песен с непустыми значениями автор/год/альбом после выпуска функциональности автоматически связаны с соответствующим альбомом — без ручного ввода.
- **SC-004**: Наличие у песни нескольких авторов не меняет то, как эта песня отображается на странице её главного автора и в URL — поведение идентично поведению до внедрения множественности авторов.
- **SC-005**: Переименование сущности "песня" не вызывает ни одной видимой пользователю регрессии в существующих сценариях (синхронизация, список песен, редактирование, воспроизведение) — все они работают идентично поведению до переименования.

## Assumptions

- Связь "песня → альбом" реализуется как постоянная ссылка на альбом; уже существующие текстовые поля автор/альбом/год песни сохраняются для отображения/поиска и заполняются автоматическим бэкфиллом, но ссылка на альбом становится источником истины для новых операций.
- У альбома — один автор (не несколько); сборники "разные исполнители", если такие встретятся, привязываются к условному автору-сборнику, а не моделируются как множественная связь на уровне альбома.
- У песни главный автор остаётся единственным и управляет группировкой/URL/страницей автора; дополнительные соавторы — отдельная, чисто информационная связь без верхнего предела на количество.
- Автоматическое связывание существующих песен с альбомами при выпуске функциональности группирует песни по точному совпадению текста (автор, год, название альбома); похожие, но не идентичные написания не объединяются автоматически.
- Песни с пустым/отсутствующим значением альбома остаются без связи — фиктивный альбом для них не создаётся.
- Порядок отображения авто-созданных при бэкфилле альбомов по умолчанию соответствует нынешнему поведению (год, затем название по алфавиту), пока администратор не переупорядочит вручную.
- Тип авто-созданного при бэкфилле альбома по умолчанию — "студийный альбом", если иное не может быть однозначно определено из имеющихся данных.
- Переименование "Settings"→"Song" затрагивает имена сущности в коде, API **и физическое имя таблицы базы данных** (включая её служебную таблицу-спутник синхронизации). Это структурное изменение схемы, требующее согласованного применения на LOCAL и SERVER базах данных до/вместе с развёртыванием обновлённого кода — риск признан оправданным пользователем, несмотря на объём (десятки миграционных файлов, ссылающихся на текущее имя таблицы, дамп-файл для чистой установки, имена индексов/ограничений/триггеров/последовательности).
- Внутренний строковый ключ регистрации в реестре синхронизации (используемый в несохранённом в git локальном файле настроек администратора) переименованием физической таблицы не затрагивается — это независимая техническая деталь, смена которой создала бы отдельный риск потери уже настроенной локальной конфигурации, не связанный с целью данного переименования.
- Отдельная, не связанная с песней функциональность общесайтовых настроек (конфигурация капчи и т.п.) явно исключена из переименования и не рассматривается как часть этой функциональности.
