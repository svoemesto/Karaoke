## Цель

Этот документ — **руководство по ручной валидации** фичи end-to-end на dev/staging/prod. Никаких автоматизированных тестов в проекте нет (см. AGENTS.md — тесты в CI не запускаются, существующие интеграционные тесты `@Disabled`), поэтому проверка делается пользователем вручную через браузер и инструменты БД.

---

## Предусловия

1. Окружение Karaoke (admin + web + public + webvue3) развёрнуто и работает (см. `docs/onboarding.md`).
2. Сборка бэкенда: `./gradlew clean karaoke-app:bootJar karaoke-web:bootJar --parallel` → артефакты обновлены.
3. Сборка фронта: `cd webvue3 && npm run build` и `cd karaoke-public && npm run build` (или `bash deploy/do.sh build_start_public` для публичной части).
4. Контейнеры `karaoke-app` / `karaoke-web` / `webvue3` / `karaoke-public` перезапущены (см. AGENTS.md — на dev-pc под dev это разрешено без согласия; иначе — пользователь).
5. В БД есть хотя бы один редактор (`is_editor = true` в `tbl_site_users`) и хотя бы одно его задание в каждом из 5 статусов (`assigned`, `in_progress`, `submitted`, `rejected`, `approved`).
6. В `tbl_song_assignments` есть хотя бы 5 одобренных заданий у одного редактора (для проверки массового удаления).
7. В админке (`webvue3`) есть доступ к разделу «Задания редактора».
8. Браузер с DevTools (для проверки сетевых запросов и HTML/DOM).
9. Доступ к БД (psql или pgAdmin) для SQL-проверок.

## Сценарий 1: Сортировка — одобренные внизу

**Что проверяем**: карточки со статусом «Одобрено» идут строго после карточек с другими статусами в DOM-порядке.

### Шаги

1. Залогиниться редактором, у которого есть задания в смешанных статусах.
2. Открыть `https://<host>/account/editor`.
3. В DevTools → Elements проверить DOM-порядок карточек (`.ke-card`).

### Ожидаемый результат

| Проверка | Критерий |
|---|---|
| В DOM все `.ke-badge-approved` идут после всех остальных `.ke-badge-*` | FR-001 спеки, SC-001 |
| Внутри обеих групп порядок стабилен (id DESC) | FR-002 спеки |
| При наличии только одобренных — вёрстка не ломается | US-1.2 acceptance |
| При наличии только активных — список выглядит обычно | US-1.3 acceptance |

### SQL-проверка (опционально)

```sql
-- Источник данных — не должен зависеть от порядка сортировки
SELECT id, admin_status FROM tbl_song_assignments
WHERE assignee_id = <editor_user_id>
ORDER BY id DESC;
-- Сравнить с порядком в DOM: сортировка только на клиенте, бэкенд возвращает id DESC.
```

## Сценарий 2: «Отказаться» от задания со статусом `assigned`

**Что проверяем**: одиночное «Отказаться» для `assigned` удаляет задание, карточка исчезает из UI.

### Шаги

1. Залогиниться редактором, открыть `/account/editor`.
2. Найти карточку со статусом «Назначено», нажать «Отказаться».
3. Подтвердить в диалоге («ОК»).
4. Проверить UI: карточка исчезла.
5. Проверить БД:

```sql
-- Должно вернуть 0 строк
SELECT id FROM tbl_song_assignments WHERE id = <task_id>;
-- Должно вернуть 0 строк (черновика для assigned обычно нет)
SELECT id FROM tbl_song_assignment_drafts WHERE assignment_id = <task_id>;
```

### Ожидаемый результат

| Проверка | Критерий |
|---|---|
| Диалог подтверждения содержит имя песни + «нельзя отменить» | FR-005 спеки |
| Карточка исчезла из `/account/editor` за ≤2 сек | SC-002 спеки |
| В DevTools → Network — `POST /api/public/account/editor/tasks/<id>/refuse` со статусом 200 | FR-006 |
| В БД записи задания и черновика удалены | FR-006, US-2.1 |
| При F5 / повторном заходе — карточка не возвращается | идемпотентность |

## Сценарий 3: «Отказаться» от задания со статусом `in_progress` (с черновиком)

**Что проверяем**: orphan-cleanup черновика работает.

### Шаги

1. Создать задание через админку (назначить редактору).
2. Редактор открывает задание в редакторе (`/account/editor/<id>`), что-то правит, не отправляет.
3. Возвращается на `/account/editor` — карточка со статусом «В работе».
4. Нажать «Отказаться» → подтвердить.
5. Проверить БД:

```sql
SELECT id FROM tbl_song_assignment_drafts WHERE assignment_id = <task_id>;
-- Должно вернуть 0 строк (orphan-cleanup сработал)
```

### Ожидаемый результат

| Проверка | Критерий |
|---|---|
| Карточка исчезла | US-2.2 acceptance |
| Черновик удалён (orphan-cleanup) | US-2.2, FR-006 |
| Песня снова доступна через админский «Назначить…» (для той же песни нет другого задания этому редактору) | US-2 acceptance |

## Сценарий 4: «Отказаться» от задания со статусом `submitted`

**Что проверяем**: гонка «админ ещё не рассмотрел» — редактор всё равно может отказаться.

### Шаги

1. Создать задание, редактор отправляет на проверку (`status = submitted`).
2. Не дожидаясь админского вердикта, нажать «Отказаться» → подтвердить.
3. Проверить БД: запись удалена. В админке `SongEditorTable.vue` задания больше нет.

### Ожидаемый результат

| Проверка | Критерий |
|---|---|
| Карточка исчезла из `/account/editor` | US-2.3 |
| В админке строки этой записи больше нет | US-2.3 |
| Никаких «зависших» submitted-заданий в админке | идемпотентность |

## Сценарий 5: «Отказаться» от задания со статусом `rejected`

4. Нажать «Отказаться» → подтвердить.

### Ожидаемый результат

| Проверка | Критерий |
|---|---|

| Комментарий админа утерян вместе с удалением (намеренно) | US-2.4 |
| Черновик удалён (если был) | FR-006 |

## Сценарий 6: «Удалить» одобренное задание (с проверкой, что песня не пострадала)

**Что проверяем**: одиночное «Удалить» для `approved` удаляет ТОЛЬКО запись задания, песня и разметка остаются нетронутыми.

### Шаги

1. Создать задание, редактор отправляет, админ одобряет (`status = approved`).
2. Запомнить `song_id` этого задания.
3. Запомнить `id_status`, `source_markers`, `source_text` этой песни (для сравнения):

```sql
SELECT id, id_status, length(source_markers), length(source_text)
FROM tbl_songs WHERE id = <song_id>;
-- Запомнить значения: например (id=42, id_status=6, len(sm)=12345, len(st)=678)
```

4. Редактор открывает `/account/editor`, находит карточку со статусом «Одобрено», нажимает «Удалить» → подтверждает.
5. Проверить БД:

```sql
SELECT id FROM tbl_song_assignments WHERE id = <task_id>;
-- Должно вернуть 0 строк

SELECT id, id_status, length(source_markers), length(source_text)
FROM tbl_songs WHERE id = <song_id>;
-- Должны быть ИДЕНТИЧНЫЕ значения (задание не откатило разметку)
```

6. Открыть страницу песни `/song?id=<song_id>` — песня доступна как была.

### Ожидаемый результат

| Проверка | Критерий |
|---|---|
| Карточка исчезла за ≤2 сек | SC-003 спеки |
| `tbl_songs` идентичен до/после | FR-030 спеки, SC-007 |
| Песня доступна в плеере как была | FR-014 |
| В DevTools → Network — `POST /api/public/account/editor/tasks/<id>/delete` со статусом 200 | FR-012 |

## Сценарий 7: «Удалить все одобренные» в личном кабинете

**Что проверяем**: массовое удаление всех одобренных у текущего редактора.

### Шаги

1. Подготовить 5+ одобренных заданий у редактора (через админку + approve).
2. Открыть `/account/editor`.
3. Проверить: внизу списка видны все 5+ карточек со статусом «Одобрено».
4. Кнопка «Удалить все одобренные» активна (`disabled=false`).
5. Нажать кнопку → подтвердить в диалоге («Удалить 5 одобренных заданий?»).
6. Проверить UI: все одобренные карточки исчезли; активные карточки остались.
7. Проверить БД:

```sql
SELECT COUNT(*) FROM tbl_song_assignments
WHERE assignee_id = <editor_user_id> AND <композитный статус = approved>;
-- Должно вернуть 0

SELECT id, source_markers FROM tbl_songs WHERE id IN (<все song_id удалённых>);
-- Все песни остались нетронутыми
```

8. **Повторный клик** по кнопке «Удалить все одобренные» — должно пройти без ошибки (`deleted: 0`, см. SC-006).

### Ожидаемый результат

| Проверка | Критерий |
|---|---|
| В диалоге указано количество одобренных | FR-018 спеки |
| Все одобренные карточки исчезли за ≤3 сек (при N=5) | SC-004 спеки |
| Активные карточки остались на месте | FR-019, US-4.1 |
| `tbl_songs` нетронут | FR-030 |
| Повторный клик — не ошибка | SC-006 |

## Сценарий 12: «Удалить все одобренные» в админке (`target=remote`)

**Что проверяем**: target-aware — запись идёт в серверную БД.

### Шаги

1. В админке переключить «БД: Сервер» (`target=remote`).
2. Подготовить ≥1 одобренное задание на сервере.
3. Нажать «Удалить все одобренные» → подтвердить.
4. Проверить БД сервера: запись удалена.
5. Проверить БД локальную: запись осталась (sync подтянет удаление отдельно, см. SyncRegistry).

### Ожидаемый результат

| Проверка | Критерий |
|---|---|
| Удаление произошло в серверной БД | FR-023, US-5.6 |
| Локальная БД не тронута напрямую | существующий sync-механизм |
| После следующего sync — запись исчезнет и в локальной БД | sync (отдельный процесс) |

## Сценарий 13: Гонка — админ одобрил задание в момент «Отказаться»

**Что проверяем**: UI не «зависает», задание не «раздваивается».

### Шаги

1. Создать задание в статусе `submitted`.
2. В двух вкладках: одна открыта в админке (`ReviewModal` → нажать «Одобрить»), другая — в `/account/editor` редактора (нажать «Отказаться»).
3. Запустить одновременно (или с разницей в миллисекунды).
4. Проверить финальное состояние: либо задание одобрено (тогда в `/account/editor` карточка исчезает через `/delete`, а не `/refuse` — или вообще остаётся в статусе `approved`), либо отказано (тогда админ увидит «уже удалено»).

### Ожидаемый результат

| Проверка | Критерий |
|---|---|
| Нет «раздвоенных» состояний | US-Edge1 |
| UI не показывает красное сообщение об ошибке (тихая обработка) | FR-008, research.md п.10 |
| В БД финальное состояние консистентно | любое из двух разумных |

## Сценарий 14: Таймаут / сбой сети

**Что проверяем**: UI не «зависает», карточка остаётся, показывается короткое сообщение.

2. Нажать «Удалить» (или «Отказаться», или «Удалить все одобренные») → подтвердить.
3. Дождаться ответа (нет сети — будет network_error).

### Ожидаемый результат

| Проверка | Критерий |
|---|---|
| Карточка осталась в списке | FR-015 спеки (для одиночных), FR-021 (для батча) |
| Показано короткое сообщение об ошибке | FR-015, SC-009 |
| UI не «пустой» (не потерял состояние) | SC-009 |
| Кнопка снова активна (`disabled` снято) | research.md п.10 |

2. Запустить «Синхронизацию в 1 клик».
3. Проверить локальную БД: запись удалена.

### Ожидаемый результат

| Проверка | Критерий |
|---|---|
| Sync завершается без ошибок | FR-031 спеки |

## Метрики (для продакшена)

- **Время ответа батч-эндпоинта** (редактор, N≤10): ≤3 сек (SC-004).
- **Время ответа батч-эндпоинта** (админ, N≤100): ≤5 сек (SC-005).
- **Количество удалённых заданий за день** — через лог `[editor-tasks/...]` (FR-034).
- **Частота использования «Отказаться» vs. «Удалить»** — через лог `[editor-tasks/<action>]`.
