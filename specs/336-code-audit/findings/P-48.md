Проверить (read-only, требует доступа к БД, которого у аудитора нет): `SELECT id FROM tbl_songs WHERE (formatted_text_song||formatted_text_tabs||formatted_text_chords) ~ '<(script|img|iframe|svg|object|embed|a )[^>]*' AND NOT ...`; при находках — пересчёт `formatted_text_*` из `source_markers`/`source_text` (бэкфилл) и/или клиентский sanitizer. Если такие строки есть — это S1, но статикой по SHA существование payload не доказывается, поэтому запись не создаю. Второй, уже зафиксированный sink того же класса — клиентский `formatText`/`useReviewModalFormat` в webvue3 (`BR-312`, порция P-43).
2. **Клиентские premium-гейты обходятся, но доступа не дают.** `StemJobsView.isPremium` (`:238–240`) и `SongView` (`playerCanWatch`/`playerIsDemo` из `usePlayerAccess`) решают только о показе UI. 3. **Молчаливые загрузчики — тот же механизм, что `BR-322` (`errors-as-empty:views`), новые локации.** `StemJobsView.load` (`:318–327`) — `catch { /* оставляем прежний список */ }` и `loading=false`: при недоступности API страница показывает «Заданий пока нет» (или вечный старый список), а не ошибку. `SongView.setup` (`:384`) вызывает `cart.load()` без `catch`; `SongView` `watch $route.query.id` (`:514`) вызывает `loadSong`, у которого нет `catch` (`store/modules/songs.js:161–171`) — на 5xx/сети `currentSong=null` → ложное «Песня не найдена». 4. **Share-сессия уходит в query-строку URL.** `openPlayer()` кладёт `sessionTokenHash` в `?session=` (`ShareView.vue:145`), `PlayerView` читает его оттуда и сохраняет в `sessionStorage`, но **не убирает из URL** (`PlayerView.vue:170–174`). Хеш — учётная величина для `/playerdata`, `/heartbeat`, `/release`; он остаётся в истории браузера и в access-логах nginx. Кросс-доменной утечки через Referer по умолчанию нет (`strict-origin-when-cross-origin` отдаёт только origin), источник URL — сам лендинг, поэтому как дефект не квалифицирую; если владелец хочет строже — сохранять хеш в `sessionStorage` до навигации и делать `router.replace` без query.
