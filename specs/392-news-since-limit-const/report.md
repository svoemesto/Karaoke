# Отчёт по KARAOKE-392 «Вынести limit=50 в константу в PublicNewsController.since()»

> **Задача**: KARAOKE-392 (Plane, workspace `svoemesto`, проект `KARAOKE`).
> **Ветка**: `764-news-since-limit-const` (feature-ветка от `master`).
> **Дата**: 2026-11-14.
> **Статус**: реализовано, поведение не изменено.

## 1. Что требовалось

В `karaoke-web/src/main/kotlin/com/svoemesto/karaokeweb/controllers/PublicNewsController.kt`,
метод `since()` вызывал `News.loadPublishedSince(WORKING_DATABASE, id, limit = 50)` —
магическое число в вызове.

Требования задачи:

1. Вынести `50` в именованную константу (private companion object) с именем, отражающим
   смысл: сколько свежих новостей отдаём одному клиенту за один опрос.
2. Добавить краткий комментарий: почему именно такое значение (страховка от выдачи всего
   архива новому клиенту, BR-177) и что порядок выдачи по `id` не теряет непрочитанные.
3. Поведение не менять: значение остаётся `50`.

## 2. Как сделано

### 2.1. Константа

В `companion object` контроллера (рядом с уже существующей `MAX_PAGE_SIZE`) добавлена
константа:

```kotlin
const val SINCE_POLL_LIMIT = 50
```

Имя отражает смысл: это предел одной выдачи для одного клиента при опросе бейджа
(`GET /api/public/news/since`), а не размер страницы ленты (это `MAX_PAGE_SIZE`).

Вызов в `since()` теперь читает `limit = SINCE_POLL_LIMIT`.

### 2.2. Комментарий

KDoc константы объясняет обе причины, названные в задаче:

- **страховка от выдачи всего архива** — клиент, залогинившийся впервые за пару лет, имеет
  `id = 0`, и без `LIMIT` ему ушёл бы весь архив `tbl_news` одним ответом; UI бейджа
  рассчитан на свежие уведомления, остальное подтягивается постранично через `GET /news`;
- **порядок выдачи по `id` не теряет непрочитанные** (BR-177) — новости отдаются по
  возрастанию `id`, и курсор клиента — тоже `id`, поэтому `max(id)` выданного набора
  совпадает с последней выданной строкой, а следующий опрос продолжает с того же места.

### 2.3. Что НЕ менялось

- Значение лимита — по-прежнему `50`.
- SQL в `News.loadPublishedSince` не тронут (там `limit` подставляется как `LIMIT $limit`).
- Порядок выдачи, кеш `PollingCache` (TTL 60 с), ключ кеша, ответ `{count, items}` и код
  `503` при недоступной БД (BR-178) — без изменений.
- Фронтенд (`karaoke-public`) не трогался: там своя константа `COUNT_CAP = 50` в
  `useNewsUnreadCount.js` — это cap отображения бейджа («50+»), другое значение, его правка
  в задачу не входит.
