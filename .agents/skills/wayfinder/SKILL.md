# Wayfinder

## Overview

Свободная идея пришла — слишком большая для одной сессии агента, окутана
туманом: путь отсюда до **назначения** ещё не виден. Wayfinding — это
**про поиск пути**, не про добегание до точки. Строим путь как **общую
карту** в OpenProject (наш трекер, см. `knowledge/adr/0008-tracker-openproject-migration.md`),
а потом работаем её **тикеты-решения** (вопросы, чьё разрешение —
решение, а не кусок сборки) по одному, пока маршрут не станет ясен.

Назначение варьируется по effort-у, и **назвать его** — первый акт
картографирования: оно формирует каждый тикет. Это может быть спека для
передачи и итерации, решение для фиксации до начала планирования, или
изменение на месте вроде миграции структуры данных. Карта
**доменно-агностична**: инженерная работа, продуктовый контент, что
угодно подходящей формы.

## Plan, don't do

Wayfinder — это **планирование** по умолчанию: каждый тикет разрешает
решение, и карта готова, когда путь ясен и больше нечего решать до того,
как кто-то пойдёт делать. Желание «просто сделать» — обычно сигнал, что
ты дошёл до края карты и пора передавать. Effort может переопределить
это в своих **Notes**, затаскивая исполнение в саму карту; но по
умолчанию — решения, не deliverables.

## Refer by name

Каждая карта и тикет — это issue в OpenProject, у неё **имя**: её
заголовок. Во всём, что читает человек (наррация, «Decisions so far» в
карте), обращайся по **имени**, не по голому id/номеру/слугу. Стена
`#42, #43, #44` нечитаема; имена читаются с одного взгляда. id и URL не
пропадают — имя оборачивает ссылку, но они едут **внутри** имени, не
вместо него.

## The Map

Карта — это **один issue** в OpenProject, лейбл `[wayfinder:map]` в
subject (наш трекер пока не поддерживает custom labels — кодируем через
префикс в `subject` создания, см. ниже). Канонический артефакт. Тикеты —
это **child issues** карты (parent-link в OpenProject).

Карта — это **index**, а не store. Она перечисляет принятые решения и
указывает на тикеты с их деталями; решение живёт ровно в одном месте —
в своём тикете, поэтому карта никогда не пересказывает его, только
кратко gist-ит и линкует.

### Физическое размещение

- **Карта** = OpenProject issue (work package) с префиксом `[wayfinder:map]`
  в subject.
- **Тикеты** = child issues карты (parent = map-issue через связь
  «related to» / «parent of», задаётся в `tools/tracker.sh`).
- **Статусы** = `New` (открытый тикет) / `In progress` (claimed) /
  `Closed` (resolved).
- **Claim** = `tools/tracker.sh claim-issue <id>` — назначить на
  `ai-agent`, статус `In progress`.
- **Blocking** = поле `Blocks:` в description тикета (список
  ID, разделённых запятыми) + явный **frontier-query** через
  `tools/tracker.sh list-issues --assignee ai-agent --status open`
  плюс ручной разбор «какие из assigned не заблокированы».
  OpenProject-relations (`precedes/follows/blocks`) пока не
  автоматизированы в `tracker.sh` — кодируем в description.
- **Resolution** = `tools/tracker.sh add-comment <id> --file answer.md`
  (ответ-комментарий) + `tools/tracker.sh close-issue <id>` (закрыть).

### Тело карты

Вся карта в низком разрешении, грузится один раз за сессию. Открытые
тикеты **не перечислены**: они — открытые child issues, находятся query.

```markdown
<!-- описание (description) карты в OpenProject -->

## Destination

<что означает достижение конца карты: спека, решение или изменение, к
которому этот effort идёт. Одно-две строки; каждая сессия ориентируется
на это перед выбором тикета.>

## Notes

<домен; скиллы, которые каждая сессия должна подгрузить;
стоячие предпочтения для этого effort-а>

## Decisions so far

<!-- индекс: одна строка на закрытый тикет, достаточно, чтобы судить о
релевантности, потом zoom link на деталь тикета -->

- [<заголовок закрытого тикета>](#<id>): <однострочный gist ответа>

## Not yet specified

<!-- см. "Fog of war": in-scope туман, который ещё нельзя затикетить;
graduate-ится по мере продвижения фронтира -->

## Out of scope

<!-- см. "Out of scope": работа, явно выведенная за назначение; закрыта,
никогда не graduate-ится -->
```

### Тикеты

Каждый тикет — это **child issue** карты. ID в OpenProject — его
идентичность. Тело — это вопрос, sized под одну сессию агента (~100K
токенов):

```markdown
<!-- description тикета -->

## Question

<решение или исследование, которое этот тикет разрешает>

<!-- опциональные метаданные -->
Тип: [wayfinder:research | wayfinder:prototype | wayfinder:grilling |
wayfinder:task]
Блокирует: <список ID тикетов, которые ждут этого>
Заблокирован: <список ID тикетов, от которых зависит>
```

Каждый тикет несёт **префикс типа** `[wayfinder:<type>]` в subject, где
`type` ∈ `research`, `prototype`, `grilling`, `task`.

Тикет **claimed** = `tools/tracker.sh claim-issue <id>` (assignee =
`ai-agent`, статус `In progress`). Assignee и есть claim: открытый,
неприсвоенный тикет — не claimed.

Блокировка: **либо** через `Blocks:` в description (наш текущий
конвенциональный канал), **либо** через OpenProject `precedes/follows`
relations, когда они будут добавлены в `tracker.sh`. Сейчас —
`Blocks:` в description. Тикет **unblocked**, когда все тикеты из его
`Заблокирован:` закрыты. **Frontier** = открытые + unblocked + unclaimed
children — край известного.

Ответ — **не в теле тикета**: он записывается при resolution (см.
«Work through the map»). Артефакты, созданные во время разрешения,
линкуются из issue, а не вставляются в него.

## Ticket Types

Каждый тикет либо **HITL** (human in the loop — работается _с_
человеком, который говорит за себя), либо **AFK**, ведомый агентом
один. HITL-тикет разрешается **только** через живое взаимодействие;
агент никогда не стоит за сторону человека (grilling-агент, который
отвечает на свои вопросы, — сломал это).

- **Research** (AFK): чтение документации, сторонних API, локальных
  ресурсов (knowledge-base) ради факта, которого ждёт решение.
  Разрешается **субагентом**, который вызывает скилл `research`.
  Применяй, когда нужны знания **вне** текущей рабочей директории.
- **Prototype** (HITL): поднимает fidelity обсуждения через дешёвый,
  грубый, конкретный артефакт (набросок, черновик, stub или UI/logic
  код), через скилл `prototype`. Линкует прототип как asset.
  Применяй, когда «как должно выглядеть» или «как должно себя вести» —
  ключевой вопрос.
- **Grilling** (HITL): разговор. Default case. Всегда вызывай
  скилл `grilling` (наш Karaoke-адаптированный с дизайн-деревом и
  раундами).
- **Task** (HITL или AFK): ручная работа, которая **должна**
  случиться до того, как решение может быть принято: нечего решать,
  прототипировать или исследовать, но обсуждение заблокировано, пока
  это не сделано. Регистрация на сервисе чтобы судить его API,
  предоставление доступа, перенос данных чтобы увидеть их форму. Это
  единственный тип, который **делает** а не решает, и оправдан он
  тем, что разблокирует решение, а не доставляет назначение. Агент
  ведёт его сам где может (AFK); иначе передаёт человеку точный
  checklist (HITL). Разрешается когда работа сделана; ответ
  записывает, **что** было сделано и какие **факты** появились
  (credentials, новые URL-ы, row counts), от которых зависят
  следующие тикеты.

## Fog of war

Карта **умышленно** неполная: не чартируй то, чего ещё не видишь. За
живыми тикетами лежит **туман войны**: тусклый обзор решений и
исследований, которые ты понимаешь, что придут, но ещё не можешь
закрепить, потому что они висят на ещё-открытых вопросах. Разрешение
тикета расчищает туман впереди, **graduate-ит** всё, что теперь
специфицируемо, в свежие тикеты по одному, пока путь до назначения
ясен и тикетов не осталось.

Секция **Not yet specified** карты — туда записывается этот тусклый
обзор: предполагаемый вопрос, область для ревизии позже. Это
неоткрытый фронтир **в сторону** назначения: всё тут in scope, просто
недостаточно остро для тикета. Пиши настолько плотно или свободно,
насколько позволяет обзор; это и signpost для коллабораторов, видящих
куда effort идёт.

**Туман или тикет?** Тест — можешь ли ты **сформулировать** вопрос
сейчас точно, **не** можешь ли ты ответить сейчас.

- **Тикет когда** вопрос уже острый, даже если заблокирован и ты не
  можешь действовать по нему.
- **Not yet specified когда** ты ещё не можешь сформулировать так
  остро. Не пре-слайси туман в тикет-сайз: он крупнее тикета, и один
  патч может graduate-иться в несколько тикетов — или в ноль — когда
  фронтир его достигнет.

**Not yet specified** исключает уже решённое (Decisions so far),
уже-живые тикеты и out of scope (следующая секция).

## Out of scope

Туман собирается только **в сторону** назначения. Назначение
фиксирует scope, поэтому работа за ним — **out of scope**: это не
туман и не в **Not yet specified**. У него своя секция **Out of
scope** в карте: работа, осознанно выведенная за **этот** effort.
Scope, не sharpness, кладёт её сюда.

Out-of-scope работа никогда не graduate-ится (фронтир останавливается
на назначении), поэтому она возвращается, **только** если назначение
перерисовано — и тогда как свежий effort, а не возобновление.

Решить что-то как out of scope — это scoping-акт, не шаг маршрута.
Когда тикет, который уже существует, оказывается за назначением
(ошибочно in-scoped при чартировании, или обнаружен при resolution),
**закрой его** (закрытый тикет однозначно вне фронтира) и оставь
одну строку в **Out of scope**: gist плюс почему out of scope,
слинкованный с закрытым тикетом. Остаётся вне **Decisions so far**,
где записывается **пройденный** маршрут; scope-граница не шаг на
нём.

## Invocation

Два режима. В любом случае **никогда не разрешать больше одного
тикета за сессию**, исключая research-тикеты.

### Branch-first hard gate (NON-NEGOTIABLE)

**Rule**: до первого редактирования файла, создания тикета или любого
мутирующего действия — создать feature-ветку от текущего `master`
HEAD. **Никогда** не редактировать файлы и не держать некоммитнутые
изменения на `master`.

```bash
# Один раз, в начале сессии (или effort'а):
git checkout master
git pull --ff-only                              # синхронизироваться с origin
N=$(./tools/reserve-branch-number.sh my-slug)    # следующий свободный NNN
git checkout -b "${N}-my-slug" master
```

Дальше вся работа — на этой ветке. После merge через PR — удалить
локальную ветку (но НЕ origin — `git push origin --delete` тоже
не делаем; origin ветки живут в GitHub UI).

**Failure** (прецедент 2026-09-18, Pass 132): агент создал карту
Wayfinder и реализовал весь backend `#137` на `master`. Изменения
накопились как uncommitted modifications. На `git checkout master`
(для сбора оставшихся новых файлов) git «переносит» uncommitted
изменения в working tree новой ветки, потому что оба указывают на
тот же коммит. Результат: master working tree оказался загрязнён
чужими правками, готовый к случайному `git commit -A`. Чистая
правка в конце сессии — `git stash` + checkout + checkout +
`git stash pop`, но это хрупкий танец. **Дешевле**: сразу
feature-ветка.

**Failure mode «не сломал»** (что **строго нельзя**, что **OK**):

- ❌ Не `git commit` на `master`.
- ❌ Не `git push` на `master`.
- ❌ Не `git add` на `master` (можно случайно добавить untracked
  из чужой работы и закоммитить).
- ❌ Не редактировать файлы на `master` — даже временно «на посмотреть».
- ❌ Не merge `feature` → `master` без PR + CI.
- ✅ Редактировать, тестировать, коммитить на feature-ветке.
- ✅ `git status` показывает modifications — это **OK** на feature-ветке.
- ✅ Push feature-ветки на origin → PR → CI → merge → `master`.

**Источник**: AGENTS.md Tier-1 § «Hard Gate — Git — CI-gate для
master ⛔»; Pass 132 (Pass 2026-09-18) — реальный failure
(см. `specs/137-hrwaiting-pool/report.md` § Известные ограничения +
Post-mortem сессии).

### Chart the map

Владелец вызывает с свободной идеей.

1. **Назвать назначение.** Вызови скилл `grilling` (и при
   необходимости `triage` для классификации), чтобы закрепить к чему
   эта карта ищет путь: спека, решение, изменение. Назначение
   фиксирует scope, поэтому решается первым.
2. **Замапить фронтир.** Гриль снова, **breadth-first**: распахни
   веер по всему пространству, не углубляйся ни в одну нить,
   вытаскивая открытые решения и первые шаги, takeable сейчас.
   **Если тумана нет** (путь до назначения уже ясен, всё
   путешествие маленькое для одной сессии) — карта не нужна.
   Остановись и спроси владельца, как продолжить.
3. **Создать карту** (префикс `[wayfinder:map]` в subject): поля
   Destination и Notes заполнены, Decisions-so-far пуст, туман
   набросан в **Not yet specified**. Создаётся через
   `tools/tracker.sh create-issue --project-id <id> --type-id <id>
   --subject "[wayfinder:map] <название карты>" --description @body.md`.
4. **Создать тикеты, которые можешь специфицировать сейчас**, как
   child issues карты (parent = map-issue). Затем **wire blocking** во
   втором проходе (issues нужны ID прежде чем ссылаться друг на
   друга). Wiring сортирует их в фронтир и заблокированные; всё, что
   ещё не можешь специфицировать — остаётся в тумане: секция
   **Not yet specified**.
5. **Запустить research-субагентов.** На каждый `[wayfinder:research]`
   тикет, который только что создал, запусти субагент с
   `run_in_background: true`, который вызовет скилл `research`,
   чтобы разрешить его параллельно, захватив находки на throwaway
   `research/<name>` ветке с контекстным указателем из тикета.
6. **Стоп**: чартирование — работа одной сессии; руками ничего не
   разрешать.

### Work through the map

Владелец вызывает с картой (URL или ID). Тикет **опциональный**: без
него выбираешь следующее решение, не владельца.

1. Загрузи **карту**: low-res view, не каждое тело тикета.
2. Выбери тикет. Если владелец назвал — бери его. Иначе первый
   frontier-тикет по порядку. **Заяви** его:
   `tools/tracker.sh claim-issue <id>`.
3. Разреши его. **Zoom по надобности**: подгрузи полное тело любого
   связанного или закрытого тикета по требованию; вызови скилл,
   который блок **Notes** карты называет. В сомнениях — дважды:
   скилл `grilling` и скилл `triage`.
4. Запиши resolution: ответ — как **resolution-комментарий**
   (`tools/tracker.sh add-comment <id> --file answer.md`),
   **закрой** issue (`tools/tracker.sh close-issue <id>`), и
   **допиши контекстный указатель** в карту в
   `Decisions so far` (правкой description карты).
5. Добавь newly-surfaced тикеты (create-then-wire); graduate-и
   любой туман, который ответ сделал специфицируемым, очистив каждый
   graduated patch из **Not yet specified** чтобы он жил только как
   новый тикет. Если ответ показывает, что тикет (этот или другой)
   лежит за назначением — **rule out of scope**, а не разрешай его на
   маршруте. Если решение инвалидирует другие части карты — обнови
   или удали эти тикеты.

Владелец может запускать unblocked тикеты параллельно, так что
ожидай, что другие сессии редактируют трекер одновременно.

## Karaoke-специфика

### OpenProject как трекер

- **См.** `knowledge/adr/0008-tracker-openproject-migration.md`,
  `docs/tracker-setup.md`, `tools/tracker.sh`.
- **Workflow**: `claim-issue` → работа → `add-comment --file report.md`
  → `mark-review` → `close-issue` (см. `AGENTS.md` § Issue-tracker
  OpenProject, NON-NEGOTIABLE).
- **Лейблы через custom fields пока не реализованы** —
  кодируем `[wayfinder:map]`, `[wayfinder:research]`,
  `[wayfinder:prototype]`, `[wayfinder:grilling]`, `[wayfinder:task]`
  в `subject` создания. Когда OpenProject-relations
  (`precedes/follows/blocks`) будут добавлены в `tracker.sh`,
  мигрируем blocking туда.
- **Parent-link** для child-of карты: OpenProject API поддерживает
  `parent` field на work package; проверь поддержку в `tracker.sh` —
  если нет, используй `related to` (тоже поддерживается) +
  префикс `[wayfinder:child]` в subject.

### Knowledge-first MUST #0

- **См.** [`AGENTS.md` MUST #0](../../../AGENTS.md) — обязателен ДО
  wayfinder: без чтения `knowledge/README.md` + `knowledge/domains/`
  ты не знаешь, какие домены уже есть, какие ADR приняты, какие
  компоненты существуют. Wayfinder идёт **после** Knowledge.

### Конституция

- [`.specify/memory/constitution.md`](../../../.specify/memory/constitution.md) —
  последняя инстанция для governance-вопросов. Если wayfinder
  приходит к решению, противоречащему MUST/SHOULD, — failure-stop до
  отдельного `speckit-constitution` шага.

### Когда применять

- Effort явно больше одной сессии (например, миграция БД,
  visitor→registration воронка из `docs/strategy/growth.md`,
  стратегический рефакторинг bounded context).
- Много открытых решений, и неясно, какие из них блокируют какие.
- Нужна визуализация прогресса для владельца (OpenProject).

### Когда НЕ применять

- Задача — одна спека (через `speckit-specify`).
- Маленькая правка (через `speckit-clarify` → `speckit-implement`).
- Прямой bug-fix.
