# Feature Specification: 558 — Экранирование пользовательских данных в подтверждениях админки (`CustomConfirm`)

**Feature Branch**: `558-escape-song-name-confirm`

**Created**: 2026-10-24

**Status**: Draft

**Input**: User description: "Устранить дефект BR-123 (S1) из аудита кода (#336): stored XSS в админке. 25 обработчиков подтверждения в карточке песни собирают текст модалки подтверждения интерполяцией имени песни в HTML-строку, а общий компонент подтверждения рендерит её через `v-html`. Тот же корень (сборка HTML из пользовательских данных → `v-html` в общем компоненте подтверждения) зафиксирован аудитом в шести семействах мест: имя картинки, e-mail публично зарегистрированного пользователя, имя автора/слово/словарь, выделенный текст песни, текст ошибки синхронизации, — а обследование кода нашло ещё два (параметры Smart Copy и итоговые сообщения по словарю). Всего 43 места в 8 семействах значений. Требуется, чтобы пользовательские данные показывались как текст во всех подтверждениях админки."

### Прецедент

Задача — в волне правок по итогам аудита кода #336. Дефект BR-123 (`root_cause_key: stored-xss-songname-confirm:songedit`, S1) — один корень в разных местах: сам дефект заведён по имени песни в карточке песни (P-61-07), а лид при ревью слил в него «дополнительные локации» из порций P-43/P-52/P-54/P-57/P-64/P-65 (см. «Дополнительные локации (слито с этой записью)» в карточке BR-123 сводного отчёта `specs/336-code-audit/bug-report.md`).

**Ближайший прецедент по способу правки — спека #215 «экранирование пользовательского текста песни в HTML-билдерах»** (PR #619, `specs/215-escape-song-html/report.md`): там, где пользовательский текст собирался в HTML, принято решение «экранировать **на входе** в HTML-буфер, а не на выходе» (иначе ломается сама разметка), добавлен общий экранирующий хелпер и — что важно для этой задачи — **регресс-контроль**: выдача для эталонной песни без спецсимволов обязана совпасть с базовой линией байт-в-байт, а количество собственных сущностей (`&nbsp;`) должно остаться прежним (0 двойных экранирований). Эта задача должна быть закрыта тем же способом проверки.

Смежные уже заведённые дефекты того же класса, которые эта задача **не** закрывает: BR-312 (`marker-xss-editor:editor` — метки маркеров редактора в `ReviewModal.vue` / `useReviewModalFormat.js` / `karaoke-public`). Текст песни под `v-html` (поля `formattedText*`) — не дефект: там экранирование уже применено (спека #215).

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Пользовательские данные в подтверждениях админки показываются как текст, а не выполняются (Priority: P1)

Администратор работает с карточкой песни. В базе хранится песня, в имени которой есть разметка — например, имя песни содержит фрагмент `<img src=x onerror=…>`. Такое имя может попасть в базу не только через форму админки: через импорт списка песен, через двуx-БД синхронизацию, через вторую вкладку/второго администратора.

**До правки**: администратор нажимает любую из кнопок, открывающих подтверждение с именем песни — «Удалить песню», «Создать караоке», «Создать DEMUCS2/5», «Создать SHEETSAGE», «Создать картинку (Boosty/Sponsr/VK/KARAOKE/LYRICS/CHORDS/MELODY)», «Создать текст (KARAOKE/LYRICS/CHORDS/TABS)», «Скопировать поля из другой песни», «Запустить рендер из онлайн-плеера», «Создать SYMLINKs». В момент открытия подтверждения разметка из имени песни выполняется как код в браузере администратора — в origin админки, откуда доступны все административные действия (удаление песен, запуск процессов, работа с базой) без дополнительного подтверждения. Один клик по обычной рабочей кнопке приводит к выполнению чужого кода в привилегированной сессии.

**После правки**: в подтверждении имя песни показывается **как текст** — видны все символы, включая угловые скобки, но ничего не выполняется: страница не обращается посторонним адресам, в консоли нет обращений, запущенных из имени песни, и данные администратора не уходят наружу. Оформление подтверждения (жирное начертание имени, вопросительный знак, кнопки) остаётся прежним.

Тот же контракт — «пользовательские данные показываются как текст» — действует для всех остальных зеркал того же механизма: имя картинки при удалении, e-mail пользователя сайта при бане/разбане/удалении, имя автора, слово и название словаря, выделенный фрагмент текста песни, строки отчёта двуx-БД синхронизации (включая текст ошибки базы данных), название шаблона переименования и путь копирования в Smart Copy.

**Why this priority**: это ядро задачи BR-123 (S1) и единственный сценарий, ради которого она заведена: выполнение произвольного кода в сессии администратора по одному клику на рабочую кнопку. Остальные сценарии защищают от регрессии и от повторного появления дефекта.

**Independent Test**: в тестовой базе создать песню с именем, содержащим разметку (`<img src=x onerror=…>`), открыть её карточку, нажать «Удалить песню» → ожидается: подтверждение открывается, имя показано буквально, сетевых обращений из имени нет, удаление по кнопке «Да» работает как раньше. Проверяется отдельно, без участия других сценариев.

**Acceptance Scenarios**:

1. **Given** в базе есть песня, в имени которой содержится разметка (например, `<img src=x onerror=…>`), **When** администратор открывает карточку песни и нажимает «Удалить песню», **Then** подтверждение открывается, имя песни отображается как текст (символы `<`, `>` видны, но элемент не создаётся), посторонний запрос не выполняется, администратор может подтвердить удаление обычной кнопкой.
2. **Given** та же песня, **When** администратор нажимает любую из остальных 24 кнопок, открывающих подтверждение с именем песни (создание караоке, DEMUCS2/5, SHEETSAGE, картинки, тексты, SYMLINKs, копирование полей, рендер из онлайн-плеера), **Then** во всех подтверждениях имя показывается как текст и ничего не выполняется — поведение одинаковое во всех 25 местах.
3. **Given** имя песни содержит символы `&`, `<`, `>`, кавычки, **When** администратор открывает подтверждение, **Then** все символы показаны как в исходном имени, ровно один раз, без появления лишних символов (например, `&` не превращается в `&amp;` на экране).
4. **Given** имя картинки, e-mail пользователя сайта, имя автора, слово/словарь, выделенный текст песни, строка ошибки синхронизации или путь/шаблон Smart Copy содержат разметку, **When** администратор открывает соответствующее подтверждение, **Then** это значение показывается как текст, ничего не выполняется, а оформление подтверждения (жирное начертание, переносы строк) сохраняется.

### User Story 2 — Публично зарегистрированный посетитель сайта не может выполнить код в сессии администратора (Priority: P2)

Посетитель сайта регистрируется без учётной записи администратора и без каких-либо прав в системе. Он задаёт себе e-mail, в котором есть разметка. Сервер при регистрации проверяет лишь наличие символа `@` и минимальную длину — никакой другой проверки и никакого экранирования нет, поэтому значение сохраняется как есть.

**До правки**: администратор заходит в раздел «Пользователи сайта», открывает карточку этого пользователя и нажимает «Забанить», «Снять бан» или «Удалить». В момент открытия подтверждения e-mail выполняется как код в браузере администратора. Это самый опасный источник из всех: атакующему не нужна учётная запись и не нужно никакое внутреннее право — достаточно один раз зарегистрироваться. Исполненный код действует от имени администратора и может, например, разрушить данные (удалить песни, запустить тяжёлые процессы) или вынести содержимое базы наружу.

**После правки**: e-mail показывается в подтверждении как текст — администратор видит, что именно он банит, и может отличить нормальный адрес от подозрительного, но ничего из содержимого e-mail не выполняется. Проверка формата e-mail при регистрации в рамках этой задачи не меняется (см. «Решения, требующие владельца»).

**Why this priority**: это единственный путь, где атакующий не имеет никаких прав в системе, — то есть самый низкий порог входа и самое высокое последствие. Он же объясняет, почему аудит поднял дефект до S1: «периметр админки» здесь не спасает, потому что точка входа публичная.

**Independent Test**: зарегистрировать на сайте пользователя с e-mail вида `<img src=x onerror=…>@a.b` через публичную форму, затем в админке открыть его карточку и нажать «Забанить» → ожидается: e-mail показан буквально, посторонний запрос не выполняется, бан при этом применяется. Проверяется отдельно от остальных источников.

**Acceptance Scenarios**:

1. **Given** на сайте зарегистрирован пользователь с e-mail, содержащим разметку, **When** администратор открывает его карточку и нажимает «Забанить», **Then** e-mail отображается как текст, ничего не выполняется, бан применяется после подтверждения как обычно.
2. **Given** тот же пользователь, **When** администратор нажимает «Снять бан» и «Удалить пользователя», **Then** в обоих подтверждениях e-mail отображается как текст, ничего не выполняется, действия применяются как обычно.
3. **Given** публичная регистрация принимает e-mail без проверки формата, **When** выполняется правка, **Then** поведение публичной регистрации **не меняется** (принимаются те же значения, что и до правки), и новое значение не отвергается — изменение касается только отображения в админке.

### User Story 3 — Админские подтверждения работают как прежде, а линтер не защищает от возврата дефекта (Priority: P3)

**До правки**: правило линтера, запрещающее вывод сырой разметки в шаблоне, в проекте **выключено** — с пометкой, что «пользовательский ввод не передаётся напрямую». Это утверждение фактически неверно: пользовательский ввод передаётся напрямую в 43 местах, перечисленных в этой спецификации. Линтер молчит, регрессия не будет замечена, и следующий разработчик, добавляющий подтверждение с новым значением, повторит дефект.

**После правки**: (а) все административные подтверждения — от удаления песни до Smart Copy — продолжают работать и выглядят как раньше: те же заголовки, те же кнопки, те же таймауты, те же действия по кнопке «Да»; (б) существует автоматическая проверка, которая на текущем коде находит перечисленные места сборки текста подтверждения из пользовательских данных, а после правки подтверждает их отсутствие, и эта проверка включена в проверки проекта.

**Why this priority**: сценарий не устраняет уязвимость сам по себе, но без него правка закрывается на один коммит и через месяц возвращается в новом месте. Это P3, потому что основная защита — P1 и P2.

**Independent Test**: один прогон автоматической проверки до правки (должен находить перечисленные места и падать) и после правки (должен проходить) + ручной прогон пяти административных операций (удаление песни, создание картинки, бан пользователя, удаление картинки, синхронизация) → ожидается: операции выполняются, оформление не изменилось, проверка зелёная.

**Acceptance Scenarios**:

1. **Given** код до правки, **When** выполняется автоматическая проверка, **Then** она находит все перечисленные места сборки текста подтверждения из пользовательских данных и завершается отказом.
2. **Given** код после правки, **When** выполняется та же проверка, **Then** она находит 0 таких мест и завершается успешно; проверка запускается в составе проверок проекта.
3. **Given** правка применена, **When** администратор выполняет обычную операцию (удаление песни, создание картинки, бан/разбан/удаление пользователя, удаление картинки, запуск синхронизации, Smart Copy), **Then** операция выполняется как раньше: то же подтверждение, та же кнопка, тот же результат; оформление подтверждения не изменилось.
4. **Given** правка применена, **When** проверяется конфигурация линтера, **Then** запрет на вывод сырой разметки остаётся выключенным (возврат правила — отдельная задача), и правка не опирается на линтер как на защиту.

### Edge Cases

- В имени песни (или в другом пользовательском значении) есть символы `&`, `<`, `>`, одинарная и двойная кавычки → в подтверждении видны ровно те же символы, что и в исходном значении; двойного экранирования нет (`&` не превращается в `&amp;` на экране, `&lt;` не превращается в `&amp;lt;`).
- В пользовательском значении есть символы, похожие на HTML, но без обрамляющих тегов (`<b`, `a&b`, `"onclick=`) → показываются как текст, страница не ломается, элементы не появляются.
- Имя песни очень длинное (тысячи символов) → подтверждение открывается и показывает текст полностью либо обрезает его по тому же правилу, что и до правки; обрезка не должна «съесть» оформление и не должна приводить к зависанию модалки.
- В отчёте двуx-БД синхронизации несколько строк, одна из которых содержит текст ошибки базы данных со значением поля пользователя, а часть строк — обычные числа → переносы строк между строками отчёта сохраняются, каждая строка показывается как текст, порядок строк не меняется.
- В подтверждении используется статичная разметка (жирное начертание имени, перенос строки, цветные рамки заголовка) → правка не убирает оформление: жирное начертание и переносы остаются на месте.
- В заголовок подтверждения попадает значение (например, версия рендера в подтверждении запуска рендера из онлайн-плеера) → заголовок показывается как раньше, без изменений.
- Один и тот же пользовательский текст подставляется в два подтверждения подряд (например, e-mail в «Забанить» и в «Удалить») → в обоих он показан одинаково, без накопления экранирования.
- Администратор сам вводит значение с разметкой в поле «Автор» или «Слово» на главной странице и подтверждает массовую операцию → введённое значение показывается как текст; данные при этом не изменяются (операция применяется к тому, что ввёл администратор).
- В базе уже лежит «испорченное» значение (например, e-mail с разметкой, заведённый до правки) → правка не требует чистки данных: значение показывается как текст, само по себе оно не меняется.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Текст подтверждения, зависящий от данных, MUST отображаться как текст: символы разметки в нём MUST NOT превращаться в элементы страницы и MUST NOT приводить к выполнению сценария или к обращению браузера по постороннему адресу.
- **FR-002**: Имя песни в 25 подтверждениях карточки песни (удаление, создание караоке, DEMUCS2/5, SHEETSAGE, картинки Boosty/Sponsr/VK/VKlink/KARAOKE/LYRICS/CHORDS/MELODY, тексты KARAOKE/LYRICS/CHORDS/TABS, копирование полей из другой песни, рендер из онлайн-плеера, SYMLINKs) MUST отображаться как текст.
- **FR-003**: E-mail пользователя сайта в трёх подтверждениях карточки пользователя (бан, разбан, удаление) MUST отображаться как текст.
- **FR-004**: Имя картинки в подтверждении удаления картинки MUST отображаться как текст.
- **FR-005**: Строки отчёта двуx-БД синхронизации, включая текст ошибки базы данных (в нём могут быть значения полей пользователей), MUST отображаться как текст; переносы строк между строками отчёта MUST сохраняться.
- **FR-006**: Имя автора (5 подтверждений на главной странице админки) и слово с названием словаря (4 подтверждения, включая итоговые сообщения о добавлении и удалении слова) MUST отображаться как текст.
- **FR-007**: Выделенный фрагмент текста песни в подтверждениях добавления/удаления слова MUST отображаться как текст.
- **FR-008**: Название шаблона переименования и путь копирования в подтверждении Smart Copy MUST отображаться как текст.
- **FR-009**: Оформление подтверждения, не зависящее от данных (жирное начертание подставляемого значения, перенос строки, цветные рамки заголовка), MUST сохраниться — правка MUST NOT «съедать» статичную разметку.
- **FR-010**: Экранирование MUST применяться ровно один раз к подставляемому значению: значение, уже содержащее `&`, MUST отображаться как `&`, а не как `&amp;`.
- **FR-011**: Набор доступных подтверждений, их заголовки, кнопки, таймауты и действия по кнопке подтверждения MUST остаться прежними — правка меняет только способ отображения текста, но не поведение административных действий.
- **FR-012**: Значения, не являющиеся пользовательским текстом (числа, идентификаторы, справочные подписи, значения из закрытых перечислений), MUST отображаться как раньше; их подтверждения MUST NOT измениться.
- **FR-013**: Правка MUST NOT менять сами данные: имя песни, e-mail, имя картинки, имя автора, словарь и прочие значения MUST оставаться в базе ровно теми же, что и до правки; правка носит только характер отображения.
- **FR-014**: Должна существовать автоматическая проверка, которая (а) на коде до правки находит перечисленные места сборки текста подтверждения из пользовательских данных и (б) после правки подтверждает их отсутствие; проверка MUST быть включена в проверки проекта, чтобы возврат дефекта в новом месте был замечен.
- **FR-015**: Правило линтера, запрещающее вывод сырой разметки в шаблоне, остаётся **выключенным** (возврат правила — отдельная задача: в проекте 14 таких мест). Правка MUST NOT считать линтер гарантией защиты — защиту обеспечивает FR-014.

### Key Entities

- **Подтверждение (модалка админки)**: единый компонент подтверждения, через который проходят все административные подтверждения; содержит заголовок, текст, дополнительные поля, таймаут и обработчик действия.
- **Текст подтверждения**: строка, собираемая вызывающим кодом и показываемая в модалке; состоит из статичной части (формулировка вопроса, оформление) и подставляемых значений.
- **Подставляемое значение**: данные, зависящие от пользователя или внешней системы — имя песни, e-mail пользователя сайта, имя картинки, имя автора, слово и название словаря, выделенный фрагмент текста песни, текст ошибки синхронизации, название шаблона переименования и путь копирования Smart Copy.
- **Статичная разметка подтверждения**: оформление, не зависящее от данных (жирное начертание, перенос строки, рамки заголовка).
- **Проверка сборки текста подтверждения**: автоматическая проверка, отделяющая статичную разметку от подставляемых значений и сообщающая о местах, где пользовательские данные попадают в текст подтверждения как разметка.

## Решения владельца (2026-10-24)

### 1. Глубина защиты — гибрид (вариант c)

Значения экранируются при сборке текста подтверждения (43 места, FR-001…FR-011) **и**
общий компонент подтверждения по умолчанию не принимает сырую разметку — HTML-режим
включается только явно (FR-012…FR-014). Причина: правило линтера `vue/no-v-html` выключено,
поэтому «только правка мест вызова» оставляет ловушку для новых вызовов.

### 2. Серверная валидация e-mail при публичной регистрации — отдельная задача

В эту задачу не входит: правка меняет публичное поведение (какие значения принимает
регистрация) и не устраняет остальные источники пользовательских данных. Фиксируется как
отдельная задача волны бэклога; здесь ограничиться отображением.
