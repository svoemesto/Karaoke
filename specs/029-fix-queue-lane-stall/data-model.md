# Data Model: Устранение зависания очереди заданий по лейнам

**Feature**: [spec.md](./spec.md) | **Research**: [research.md](./research.md)

Схема БД не меняется (см. `research.md` — фикс не требует новых
колонок/миграций). Ниже — концептуальные сущности из спеки (`Key Entities`)
в привязке к уже существующим полям `tbl_processes`, плюс новая
(не персистентная, только in-memory) сущность мониторинга.

## Задание очереди (существующая сущность, `tbl_processes` / `KaraokeProcess`)

Изменений схемы нет. Значимые для этой фичи поля (уже существуют):

| Поле (домен) | Поле в БД | Роль в фиче |
|---|---|---|
| id | `id` | идентификатор задания, используется для защиты от повторного запуска (FR-007) |
| статус | `process_status` | `WAITING` \| `WORKING` \| `DONE` \| `ERROR` — FR-001/FR-003 требуют гарантированного перехода в терминальный статус |
| thread-лейн | `thread_id` | группировка в независимые под-очереди (FR-002) |
| приоритет/порядок | `process_priority`, `process_order` | не меняются этой фичей — используются уже существующим `getProcessesToStart()` |
| время старта | `process_start` | используется новой проверкой мониторинга для расчёта «сколько лейн простаивает» (FR-004) |

**Переходы статуса, относящиеся к этой фиче** (дополняет уже существующие
`WAITING → WORKING → {DONE|ERROR}` и `WORKING → WAITING` при форс-стопе):

```text
WORKING --(непредвиденный сбой запуска subprocess, Кандидат B)--> ERROR
WORKING --(осиротевшая запись, обработчик лейна не жив, при restart/resolve)--> WAITING
```

Оба перехода — не новые статусы, а закрытие существующих «дыр» в уже
предусмотренной модели статусов (`KaraokeProcessStatuses`).

## Thread-лейн (концептуальная сущность, не отдельная таблица)

Не хранится как строка БД — это группировка по значению `thread_id` среди
заданий `tbl_processes`, и in-memory состояние воркера
(`KaraokeProcessWorker.threadsMap: Map<Int, KaraokeProcessThread?>`).

| Атрибут | Источник | Роль в фиче |
|---|---|---|
| threadId | ключ `threadsMap` / `thread_id` в БД | единица независимости (FR-002); ключ синхронизации (Кандидат A) |
| активный поток-обработчик | значение `threadsMap[threadId]` | проверяется на `isAlive`, чтобы решить — стартовать следующее WAITING-задание или нет |
| «withoutControl» | `karaokeProcess.withoutControl` → глобальная переменная воркера | сейчас ошибочно общий для всех лейнов (Кандидат A); фикс не меняет семантику флага для конкретного задания, только изолирует его влияние per-лейн, где это возможно |

## Предупреждение о зависании (новая сущность — `MonitorAlert`, in-memory, не персистентная)

Не таблица БД — расширение существующего `MonitorAlert`
(`karaoke-app/.../monitor/MonitorAlert.kt`), формируемого новой проверкой
`LaneStalledCheck` (см. `contracts/lane-stalled-check.md`). Персистентность
уже даёт существующий механизм `MonitoringService`/`monitorDismissed`
(в `KaraokeProperties`) — отдельного стораджа для этой фичи не требуется.

| Поле `MonitorAlert` | Значение для `LaneStalledCheck` |
|---|---|
| `key` | стабильный ключ на лейн, например `"queue.lane.stalled.<threadId>"` — отдельный алерт на каждый зависший лейн, не один общий |
| `severity` | `WARNING` (по аналогии с `RenderQueueStalledCheck`) |
| `title`/`body` | человекочитаемое название лейна + сколько заданий ждёт |
| `detail` | «не выполняется уже N мин» — намеренно вне `contentHash()` (см. существующий комментарий в `MonitorAlert.kt`), чтобы не «мигало» read/unread на каждый тик |
| `resolveAction` | точечное восстановление лейна: вернуть осиротевшие `WORKING`-записи этого `threadId` в `WAITING` (Кандидат C) — НЕ глобальный `setWorkingToWaiting()` |

## Валидационные правила (из Functional Requirements)

- FR-001/FR-002: переход к следующему заданию лейна не зависит от статуса
  других лейнов — обеспечивается по конструкции (ключ `threadId`), фикс
  Кандидата A устраняет утечку через *общие* поля воркера, которые ранее это
  нарушали неявно.
- FR-003: любой выход из `KaraokeProcessThread.run()` (успех, ожидаемая
  ошибка, непредвиденное исключение) обязан перед завершением потока
  записать статус, отличный от `WORKING` (либо терминальный, либо `WAITING`
  при форс-стопе) — иначе поток считается «зависшим создателем сироты».
- FR-007: восстановление лейна (ручное или при старте) не должно запускать
  два потока для одного `karaokeProcess.id` одновременно — обеспечивается
  тем же механизмом синхронизации, что и Кандидат A (проверка
  «уже есть живой поток для этого threadId» и создание нового — атомарны).
