# Research: Пагинация ленты новостей

## 1. Стратегия пагинации: offset (LIMIT/OFFSET + total count) для обеих сторон

**Decision**: backend отдаёт ровно одну страницу за запрос через `LIMIT ?
OFFSET ?` (параметры `page`/`pageSize`, offset = `page * pageSize`), плюс
отдельный дешёвый `COUNT(*)` для общего числа записей/страниц.

**Rationale**:
- Admin-таблица (FR-005) должна уметь перейти на произвольную страницу «в
  любом порядке» — offset-пагинация даёт это тривиально (`OFFSET (N-1)*size`);
  keyset/cursor-пагинация такого произвольного прыжка не даёт без
  дополнительных costly-приёмов (материализовать все курсоры страниц заранее).
- Объём (19000+ строк, растёт медленно — по одной новости на первую
  публично доступную песню) не требует курсорной пагинации ради
  производительности: `OFFSET` на индексированном `ORDER BY publish_at DESC,
  id DESC` (или `id DESC` для админки) на таких объёмах остаётся быстрым при
  реалистичной глубине пролистывания (страницы считаются десятками, не
  тысячами).
- Совпадает с уже существующим в проекте паттерном постраничной загрузки
  (`webvue3/src/components/Songs/store.js`, `songPageSize`/`ApiController.kt`
  `pageSize`) — минимизирует новизну для будущих разработчиков.

**Alternatives considered**:
- *Keyset/cursor-пагинация* (курсор — последний увиденный `(publish_at, id)`
  предыдущей страницы). Отклонено: не даёт «прыжок на страницу N» для
  админки (FR-005), а выигрыш в производительности при текущих объёмах и
  глубине пролистывания не оправдывает усложнение контракта на обеих
  сторонах.
- *Повторение паттерна `/api/songs`/`ApiController.kt` («грузим ВЕСЬ
  отфильтрованный список и режем на `chunked(pageSize)` одним ответом»)*.
  Отклонено явно: это тот же самый класс проблемы, который эта фича чинит —
  весь `tbl_news` (19000+ строк) всё равно уедет в один HTTP-ответ и в память
  браузера, изменится только момент нарезки на страницы (на бэкенде вместо
  фронтенда), а не сам факт полной выгрузки. Для `Songs` этот паттерн
  терпим, т.к. таблица почти всегда используется с фильтрами, сильно
  сокращающими результат; у `News` полноценных отсекающих фильтров нет.

## 2. Размер страницы

**Decision**: публичная лента — 20 новостей за запрос (карточный UI,
паттерн «Показать ещё»); админка — 50 строк на страницу (табличный UI,
совпадает с существующим `songPageSize = 50` в `webvue3/Songs/store.js` для
единообразия с уже привычным администратору поведением).

**Rationale**: конкретное число не является бизнес-требованием (см.
Assumptions в spec.md) — выбраны разумные дефолты, отражающие разницу
карточного (крупнее, меньше на экран) и табличного (плотнее, больше строк)
UI.

**Alternatives considered**: единый размер страницы для обеих сторон —
отклонено, т.к. карточный и табличный UI имеют разную оптимальную плотность
информации на экран.

## 3. UX-паттерн на публичной стороне: «Показать ещё» вместо номеров страниц

**Decision**: `NewsView.vue` дозагружает следующую порцию по клику на кнопку
«Показать ещё» и добавляет её к уже показанным карточкам (без сброса
скролла), а не переключает «страницы» с заменой содержимого.

**Rationale**: хронологическая лента — типичный кейс для инкрементальной
подгрузки (как публичные ленты в большинстве продуктов); лучше сохраняет
контекст чтения посетителя, чем классическая пагинация с перезагрузкой
списка. Разрешено спецификацией (Assumptions, spec.md) как один из двух
равноценных вариантов.

**Alternatives considered**: классическая пагинация с номерами страниц —
отклонено как менее естественное для UX «читаю ленту сверху вниз», хотя
технически было бы не сложнее.

## 4. UX-паттерн в админке: `<b-pagination>` с серверной подгрузкой страницы

**Decision**: `NewsTable.vue` использует уже применяемый в проекте
компонент `bootstrap-vue-next` `<b-pagination>` (см. прецеденты —
`DictionariesTable.vue`, `SiteUsersTable.vue`, `AlbumsTable.vue`), но, в
отличие от них, **не** грузит весь список клиенту для последующей
клиентской нарезки (`:items`/`:per-page`/`:current-page` на b-table поверх
полного массива) — вместо этого при смене `currentPage` стор запрашивает у
бэкенда именно эту страницу (`total-rows` берётся из отдельного
серверного count, а не из `newsList.length`).

**Rationale**: существующие таблицы (`Dictionaries`, `SiteUsers`, `Albums`)
рассчитаны на существенно меньшие объёмы данных, где загрузка всего списка
клиенту не проблема — переиспользовать их паттерн «клиентская нарезка» для
`News` при 19000+ строках означало бы всё равно выкачивать всё разом. UI-виджет
(`<b-pagination>`) переиспользуется, но data-fetching — нет.

**Alternatives considered**: клиентская нарезка как у `Dictionaries` —
отклонено по той же причине, что и в п.1 (весь смысл фичи — перестать
выгружать всё сразу).

## 5. Устойчивый порядок сортировки при LIMIT/OFFSET

**Decision**: добавить `id DESC` вторым ключом сортировки к существующему
`ORDER BY publish_at DESC` в `News.loadPublished` (публичная сторона) и явно
задать `ORDER BY id DESC` в новом SQL-запросе для `News.loadAll`
(админка — сейчас там сортировка `sortedByDescending { it.id }` **в памяти
после** полной загрузки, что при переходе на `LIMIT/OFFSET` перестанет быть
корректным и должно уйти в SQL `ORDER BY`).

**Rationale**: `publish_at` не уникален — несколько авто-новостей,
созданных в рамках одного и того же прогона `checkAndAnnounce`, получают
очень близкие (иногда идентичные до миллисекунды) значения `publish_at`.
Без второго детерминированного ключа сортировки строки на границе
страниц могут как задваиваться, так и теряться между запросами (нарушение
edge case из spec.md «без дублей и пропусков»).

## 6. Контракт `/api/public/news`: смена формы ответа (breaking, но допустимо)

**Decision**: ответ `GET /api/public/news` меняется с плоского
`List<NewsDto>` на объект `{ items: NewsDto[], total: number, hasMore: boolean }`.

**Rationale**: единственный потребитель — `karaoke-public/src/services/newsApi.js`
в этом же репозитории, меняется в этом же PR; внешних потребителей нет
(эндпоинт не документирован как публичный API для интеграций). `/api/public/news/since`
(бейдж) не меняется — там объём всегда мал и обёртка `{count, items}` уже
существует.
