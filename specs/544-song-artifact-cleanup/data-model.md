# Phase 1 Data Model: Автоуборка артефактов песни

Сущности ниже — не таблицы БД (схема не меняется, Constitution II): это реестр классов
в коде, структуры отчёта/журнала и модель ожидаемых файлов, которая уже существует в
проекте (`KaraokeFileType`).

---

## 1. Реестр классов артефактов

Единственное место правды о том, что с каким артефактом делаем. Используется и
автоматической уборкой в пайплайне, и разовой чисткой истории.

**Вердикты**: `PROTECTED` (не удаляется ничем), `KEEP` (остаётся как есть),
`STOP_CREATING` (код перестаёт создавать), `DELETE_AFTER_STAGE` (удаляется на шаге
жизненного цикла), `DELETE_EXISTING` (удаляется разовой чисткой), `NOT_TOUCH`
(есть читатель — руками не трогать).

## 2. Модель ожидаемых файлов: до и после

`KaraokeFileType.locations` определяет, какие копии артефакта система считает
обязательными, а `HealthReport` — что делать при отсутствии.

| Тип | Локации сейчас | Локации после | Что это меняет |
|---|---|---|---|
| `MP3_ACCOMPANIMENT`, `MP3_VOCAL`, `MP3_DRUMS`, `MP3_BASS`, `MP3_OTHER` | `LOCAL_FILESYSTEM`, `LOCAL_STORAGE`, `REMOTE_STORAGE` | `LOCAL_STORAGE`, `REMOTE_STORAGE` | проверка здоровья перестаёт считать отсутствие локальной копии нарушением и перестаёт ставить `FF_MP3_*` |
| `AUDIO_SONG` (`<song>.flac`) | `LOCAL_FILESYSTEM` | без изменений | защищённый класс |
| `AUDIO_ACCOMPANIMENT` / `AUDIO_VOCAL` / `AUDIO_BASS` / `AUDIO_DRUMS` / `AUDIO_OTHER` (flac-стемы) | `LOCAL_FILESYSTEM` | без изменений | защищённый класс; авторемонт `DEMUCS2` сохраняется |
| `PICTURE_PUBLICATION`, `PICTURE_SONGVERSION` | `LOCAL_FILESYSTEM` | без изменений | публикационные картинки удаляются после публикации (FR-005); правка ожиданий не нужна: оба типа уже входят в `LEGACY_MLT_FILE_TYPES` (`HealthReport.kt:1363-1375`) и пропускаются циклом (`:1504-1505`) — авторемонт по ним не запускается |
| `VIDEO_SONGVERSION_1080P/720P` | `LOCAL_FILESYSTEM` | без изменений | видео (`[lyrics]`/`[karaoke]`) не входит в чистку |
| `.srt`, `.song`, `.settings`, `.mlt`, `.kdenlive` | в `KaraokeFileType` отсутствуют | без изменений | вне модели здоровья — удаляются без последствий для ремонта |

**Инварианты модели**:

1. Ни один тип с вердиктом `PROTECTED` не может быть удалён сервисом чистки.
2. Если тип перестал требовать локальную копию, `HealthReport` не должен порождать
   задачу восстановления только из-за её отсутствия (проверяется unit-тестом).
3. `canCreate` (возможность пересоздать) сохраняется там, где источник существует:
   mp3 из flac, картинки из данных песни.

## 3. Отчёт сухого прогона (`CleanupPlan`)

Результат `POST /api/cleanup/plan`. Владелец утверждает **именно этот** набор файлов.

| Поле | Тип | Смысл |
|---|---|---|
| `classId` | строка | идентификатор класса из реестра |
| `generatedAt` | дата-время | когда построен отчёт |
| `entries` | список | `path`, `sizeBytes`, `reason` (почему класс подлежит удалению) |
| `fileCount` | целое | сколько файлов будет удалено (сверяется с ожидаемым объёмом класса) |
| `totalBytes` | целое | суммарный объём |
| `fingerprint` | строка | хэш списка (путь+размер) — «печать» утверждённого набора |
| `warnings` | список | например: «класс `STEMS_MP3_LOCAL` требует правки модели здоровья — сначала код» |

**Правила**:

- Отчёт не удаляет ничего (FR-011) — это гарантируется отсутствием вызовов удаления
  в планировщике и проверяется тестом.
- Если `fileCount = 0`, `apply` отклоняется как бессмысленный.
- Суммарный объём класса должен попадать в ожидаемый диапазон из реестра; расхождение
  больше допустимого — предупреждение в отчёте (защита от «удалим не то»).

## 4. Журнал удалений (`CleanupJournal`)

Файл `/sm-karaoke/system/cleanup-logs/<YYYY-MM-DD>-<classId>.tsv`, одна строка на
удалённый файл (FR-012). Таблица БД не заводится (Constitution II/III).

| Колонка | Смысл |
|---|---|
| `path` | абсолютный путь обработанного файла |
| `sizeBytes` | размер до удаления |
| `classId` | класс из реестра |
| `result` | `deleted` или `failed:<причина>` — журнал фиксирует и неудачи |
| `deletedAt` | дата-время обработки |
| `approvedBy` | кто утвердил класс (владелец/агент по его слову) |
| `runId` | идентификатор прогона (связывает строки одного запуска) |

Строка дописывается сразу после обработки файла (write-behind на каждый файл). Принятое
ограничение: обрыв процесса может потерять запись максимум об одном файле — окно между
удалением и записью (write-ahead дал бы две строки на файл и вдвое больший журнал). Для
разовой чистки это осознанно допустимо: прогон идёт по утверждённому отчёту (полный список
путей сохраняется в отчёте), расхождение обнаруживается повторным `plan`, а сам факт обрыва
виден в логе процесса. Для автоматических удалений на шаге жизненного цикла окно ещё меньше
— удаляется один файл (демо) или один набор картинок.

## 5. Прогон чистки (`CleanupRun`)

Состояние живёт в памяти процесса; в журнал попадает `runId` и результат.

**Состояния**: `PLANNED` → `APPROVED` → `RUNNING` → `DONE` | `PARTIAL` | `FAILED`.

| Переход | Условие |
|---|---|
| `PLANNED` → `APPROVED` | предъявлен `fingerprint` из отчёта и явное подтверждение |
| `APPROVED` → `RUNNING` | запуск в фоне (не в HTTP-потоке, Constitution IV) |
| `RUNNING` → `DONE` | все файлы отчёта обработаны без ошибок |
| `RUNNING` → `PARTIAL` | часть файлов не удалось удалить (ошибки доступа/занятость) — перечислены в отчёте прогона |
| `RUNNING` → `FAILED` | отказ до первого удаления (например, нет прав на журнал) |

**Счётчики прогона**: `plannedCount`, `deletedCount`, `failedCount`,
`freedBytes`, `journalPath`.

## 6. Конфигурация (`KaraokeProperties`)

| Параметр | Тип | По умолчанию | Смысл |
|---|---|---|---|
| `cleanupEnabled` | boolean | `false` | автоматическое удаление после этапов жизненного цикла (FR-011) |
| `cleanupDryRun` | boolean | `true` | сухой прогон: логируем, что было бы удалено |
| `cleanupJournalDir` | строка | `/sm-karaoke/system/cleanup-logs` | куда пишется журнал |
| `cleanupPlanVolumeTolerancePercent` | int | `10` | допустимое расхождение объёма класса с ожидаемым |

Конвенция дефолтов — `knowledge/adr/local-0001-karaoke-properties-defaults.md`
(без секретов, значения по умолчанию безопасные).

## 7. Что НЕ меняется

- Схема БД и `SyncRegistry` — новых сущностей и sync-флагов нет.
- Таблица `tbl_storage_metadata_cache` — не участвует: чистка работает с файловой
  системой и не проверяет фактическое наличие объектов через кеш; после массового
  удаления рекомендуется штатный сброс/прогрев кеша хранилища (спеки #446/#449).
- Публичный API `karaoke-web` и фронтенды — не затрагиваются.
- Прод-сервер — не затрагивается этой поставкой.
