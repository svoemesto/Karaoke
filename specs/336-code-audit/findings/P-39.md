### P-39-08: karaoke-web/src/main/resources/templates/testpage.html:288, 544–548 — SEC (S3)

- **Что не так**: отформатированный текст песни сначала экранируется Thymeleaf (`th:text` → `&lt;…&gt;`), а потом **клиентский код снимает это экранирование**: `innerText` скрытого div'а возвращает уже декодированную разметку, а `innerHTML` разбирает её заново как HTML. Итог: любая неэкранированная разметка в `getTextFormatted()` становится живыми DOM-элементами (с обработчиками событий), а серверное экранирование при этом не имеет эффекта. Сегодня вход экранирован на продюсере (`Song.getTextFormatted()` → `marker.label.escapeHtml()`, `Song.kt:4659, 4676`; `escapeHtml` экранирует `& < > " '`, `Extentions.kt:119–125`), поэтому достижимого пути сейчас нет — запись оставлена как defense-in-depth: механизм «экранирование на входе» не является защитой этого sink'а, и любое новое поле в `getTextFormatted()` без `escapeHtml` станет XSS на странице.
- **Доказательство**: «`<div hidden="hidden" style="width: 0; height: 0" id="text_formatted_html" th:text="${song.getTextFormatted()}">`» (`karaoke-web/src/main/resources/templates/testpage.html:288`, SHA `1977838a`); «`        textFormatted.innerHTML = textFormattedHtml.innerText`» (`:547`). Эмпирика (Playwright/chromium): для `<div hidden>&lt;img src=x onerror="window.__x=1"&gt;&lt;b&gt;bold&lt;/b&gt;</div>` — `innerText` = `"<img src=x onerror=\"window.__x=1\"><b>bold</b>"`, после присваивания в `innerHTML` в целевом div'е создаются **живые элементы** `IMG` (с `onerror`) и `B`.
- **Путь**: `GET /testpage/{id}` → `MainController.doTestPage` (`MainController.kt:535–549`) → `model["song"]` → `templates/testpage.html:288` `th:text="${song.getTextFormatted()}"` → сервер отдаёт экранированную строку → `:545–547` `innerText` → `:547` `innerHTML` → разбор как HTML → исполняемый markup в origin страницы.
- **Поправка**: не «экранировать на входе», а разбирать на клиенте безопасно: выводить готовые `<span>/<br>` через `innerHTML` только для собственной разметки, а пользовательский текст — через `textContent`/`createTextNode`; либо (лучше) отдавать готовый HTML из сервера с санитизацией (allow-list тегов) и вставлять его как `innerHTML` осознанно, убрав двойной round-trip `th:text` → `innerText`.
- **Найдено в**: порция P-39, аудитор P-39.
- **Автор (git blame)**: nsa (svoemesto@gmail.com, 2025-02-13, `testpage.html:547`); строка `:288` — opencode (opencode@local, 2026-08-28, переименование `sett`→`song`).
- **Severity**: S3 — sink без экранирования, но достижимого пути сегодня нет (продюсер экранирует `escapeHtml`); по рубрике §4 — «defense-in-depth без достижимого пути». `severity: под вопросом` — если владелец считает `getTextFormatted()` полностью доверенным и не планирует менять его состав, запись можно закрыть как `WONTFIX`.

## Сверки (баг или задумано, без severity)

1. **`/webevents` и `/statbysong` — внутренние дашборды без авторизации.** `SecurityConfig.kt:26–34` (karaoke-web) — `anyRequest().permitAll()`; `MainController.doWebEvents` (`MainController.kt:522–533`) отдаёт наружу последние 500 событий веб-аналитики (`WebEventDto` содержит `clientIp`, `anonId`, `userAgent`, `restParameters`), а шаблон `webevents.html:164–178` печатает дату, тип, описание и `referer` посетителей. Вопрос: эти страницы задуманы публичными (тогда — решаем, что показывать) или внутренними (тогда — закрыть авторизацией/allow-list)? Трактовки: (а) дефект — неаутентифицированный доступ к внутренней аналитике; (б) задумано — страницы считаются отладочными и на публичном периметре не висят (на проде nginx отдаёт `/` в SPA, Thymeleaf-страницы доступны только на loopback и на `8897` админской машины). Почему важно: severity зависит от ответа, а сам вопрос закрыт в P-35 (контроллер) без записи — здесь только факт со стороны шаблона.

2. **`th:value` на `<select>` (zakroma.html:307).** «`                <select style="font-size: 14px; padding: 0;" class="form-control" type="text" id="field_author" name="field_author" th:value="${author_init}">`» — атрибут `value` у `<select>` не имеет смысла (браузер игнорирует; в выводе — `value=""`). Фактический выбор автора делает `th:selected` на `<option>` (`:309`), и он работает (проверено: в отрендеренной странице выбранный автор присутствует). Зафиксировано, чтобы при разборе «сбрасывания автора» не искали причину в шаблоне; по рубрике §2 (косметика) дефектом не считаю.

3. **Невалидная вложенность `<div th:each>` внутри `<table>`** (`statbysong.html:190`, `webevents.html:164`, `filter.html:376`). HTML5-парсер выносит `<div>` (foster parenting) перед таблицей, а `<tbody>/<tr>/<td>` — обрабатывает корректно; проверено эмпирически (`parse5`, HTML5-алгоритм разбора, таблица из двух итераций): строки попадают в таблицу, лишние пустые `<div>` визуально не видны. Дефекта отображения нет; отмечено, чтобы не переоткрывать вопрос и не «чинить» шаблон без нужды.

4. **`window.open(linkValue, '_blank')` без `noopener`** (`main.html:349`, `zakroma.html:549`, `filter.html:510`, `testpage.html:564`) — потенциальный reverse tabnabbing, но `linkValue` берётся из статических атрибутов шаблона (`linkValue="https://vk.com/…"`) либо из элементов `name="link"`, которых на этих страницах нет; управляемого источника нет → по §1/§2 дефектом не считаю (в P-39-06 зафиксирована другая — проверка схемы — пара: `n.link` из БД).

5. **Публичный `/registerevent` из клиента** (`main.html:347`, `zakroma.html:547`, `filter.html:508`, `testpage.html:562`) — POST без CSRF-токена и без авторизации. Для аналитики по замыслу это норма (см. P-35, Сверка 3 про IDOR `siteUserId` в query) — здесь только отмечено, что сам факт клиентского вызова из шаблонов дефектом не является.
