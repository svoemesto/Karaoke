# Phase 0 — Research: удаление пустых голосов при сохранении песни

**Спека**: [spec.md](spec.md) (`specs/547-drop-empty-song-voices`)
**Дата**: 2026-10-20
**Статус**: все NEEDS CLARIFICATION закрыты (в Technical Context их не осталось)

Каждое решение ниже проверено по коду и/или данным локальной БД. Формат: решение —
обоснование — рассмотренные альтернативы.

## R1. Точка применения правила: `Song.saveToDb()`, а не эндпоинты

**Решение**: нормализация голосов вызывается в начале `Song.saveToDb()`
(`karaoke-app/.../model/Song.kt:5258`), до вычисления diff. `saveToDbLocked()`
(`Song.kt:5641`) переиспользует `saveToDb()` внутри своей транзакции — отдельная
правка не нужна.

**Обоснование**:
- Через `saveToDb()` проходят все пути, которые владелец назвал «любым сохранением
  песни»: `/api/song/savesourcemarkers`, `/api/song/savesourcetext`,
  `/api/song/savesourcetextmarkers`, `/api/song/update` (`ApiController.kt:2986`),
  апрув черновика (`SongEditorController.kt:394`), фоновые задания
  (`KEY_BPM_FROM_FILE`, `DEMUCS2`), легаси-эндпоинты `MainController`.
- Одна проверка вместо четырёх+ дублирующих: при правке эндпоинтов легко пропустить
  путь (прецедент спек `278`/`299`, где лечили только одну ветку).

**Альтернативы**:
- *Нормализация в каждом эндпоинте сохранения голоса* — отвергнуто: фоновые
  сохранения (`saveToDb` из процессов) и апрув всё равно остались бы в стороне;
  дублирование правила в 4+ местах.
- *Нормализация только в `setSourceMarkers`/`setSourceText`* — отвергнуто: не
  покрывает уже испорченные песни, которые чистятся обычным сохранением карточки.

**Риск, который обязан быть закрыт (см. R2)**: `saveToDb()` вызывается и для песен,
загруженных с `withoutMarkersAndText = true` (`Song.kt:8142` — ветка, где поля
`source_text`/`source_markers`/`formatted_*` не читаются). У такой песни в
`fields` этих ключей нет, а геттеры отдают `""` / `"[[]]"`. Обращение к геттерам
внутри `saveToDb` построило бы diff «стереть текст» — существующая мина, которую
нормализация не должна активировать.

## R2. Парсинг голосов — чистая функция, без сайд-эффектов

**Решение**: новая чистая функция в
`karaoke-app/.../model/VoiceNormalization.kt`; разбор JSON-строк — отдельные
чистые парсеры, возвращающие `null` при неудаче. Существующий геттер
`Song.sourceMarkersList` (`Song.kt:444`) внутри `saveToDb` **не используется**.

**Обоснование**:
- Геттер `sourceMarkersList` при ошибке разбора **сам пишет поле и вызывает
  `saveToDb()`** (`Song.kt:455-457`). Вызов его из `saveToDb()` дал бы рекурсию.
- Чистая функция тестируется юнит-тестом без БД — ровно тот приём, что уже
  применён в `hasChordsInMarkers` + `HasChordsFromDbTest` (spec 544). Это прецедент
  проекта, а не изобретение.
- Fail-safe (FR-012): `null` от парсера → нормализация ничего не делает, пишется
  WARN, сохранение продолжается обычным путём.

**Альтернативы**:
- *Использовать `sourceMarkersList` + флаг-страж от рекурсии* — отвергнуто: скрытое
  состояние на объекте, который живёт в потоках воркеров; регресс труднее поймать.

## R3. Гард «песня загружена без текста и маркеров»

**Решение**: нормализация работает только если в `fields` присутствует хотя бы один
из ключей `SOURCE_MARKERS`/`SOURCE_TEXT`; перезаписываются только присутствующие
ключи.

**Обоснование**: прямые последствия R1 — иначе сохранение песни, загруженной
«облегчённо» (списки песен, фильтры, выборки для статистики), записало бы пустой
текст. Проверка идёт по `fields[...] == null`, а не по геттеру (геттер маскирует
`null` значениями по умолчанию).

**Альтернатива**: *не менять `saveToDb`, а нормализовать в `loadFromDbById`* —
отвергнуто: чтение не должно менять данные (и это добавило бы запись в hot path
списков).

## R4. Порядок записи текста и маркеров: один комбинированный сеттер

**Решение**: новый метод `Song.setSourceTextAndMarkers(voice, text, markers)`,
который меняет оба списка в памяти и делает **один** `saveToDbLocked()`.
Эндпоинты `/api/song/savesourcetextmarkers` и легаси `MainController` используют его.

**Обоснование** (это конкретный дефект, а не косметика):
- Сегодня `/savesourcetextmarkers` делает `setSourceMarkers(...)` (**save #1**),
  затем `setSourceText(...)` (**save #2**), затем `setIndexTabsVariant` (**save #3**).
- Если нормализация живёт в save #1 и удаляет только что записанный пустой голос,
  то save #2 вызывает `setSourceText(voice = 1, "")` при списке текстов длиной 1 —
  ветка «дописать в конец» (`Song.kt:3734-3741`) **возвращает пустой голос обратно**
  уже в `source_text`, и списки расходятся (2 текста / 1 маркеры). Это ломает FR-003.
- Один сеттер убирает и лишние сохранения (3 → 1), что помогает FR-014 (латентность).

**Альтернатива**: *сначала текст, потом маркеры* — тоже работает, но оставляет три
сохранения и по-прежнему допускает промежуточное состояние; комбинированный сеттер
проще проверять.

## R5. Контракт ответа эндпоинта сохранения голоса

**Решение**: `POST /api/song/savesourcetextmarkers` возвращает JSON
`{"ok": true, "voice": <новый индекс>, "countVoices": <сколько голосов осталось>}`;
`voice = -1`, если сохранённый голос был удалён как пустой (сценарий US1).

**Обоснование**:
- FR-010 требует, чтобы после сдвига нумерации следующие сохранения попадали в тот
  же голос. Сервер знает точное отображение индексов, клиент — нет.
- Единственный потребитель — `webvue3/src/components/Songs/store.js:2577`
  (действие `saveSourceTextAndMarkers`), вызов один: `SubsEdit.vue:3166`. Смена
  формы ответа безопасна; `promisedXMLHttpRequest` возвращает текст ответа, разбор
  добавляется в store.

**Альтернативы**:
- *Оставить `true`, а клиенту перечитывать `/api/song/voices` и угадывать индекс* —
  отвергнуто: при удалении голоса **перед** текущим угадывание невозможно без
  сравнения содержимого (хрупко); плюс лишний запрос.
- *Отдавать mapping через SSE `recordChange`* — отвергнуто: событие общее для всех
  вкладок, адресной семантики «куда переехал мой голос» в нём нет.

Совместимость: легаси-эндпоинты `MainController` (`/song/{id}/{voice}/savesourcemarkers`)
возвращают Thymeleaf-вью `text` и используются старым серверным UI; их контракт не
меняется, нормализация применяется через `saveToDb` (R1), mapping не отдаётся.

## R6. Производные текстовые поля пересчитываются только при фактическом удалении

**Решение**: если нормализация что-то удалила, в том же `saveToDb()` пересчитываются
`result_text`, `formatted_text_song`, `formatted_text_tabs`, `formatted_text_chords`
теми же методами, что и в `setSourceMarkers` (`getText()`, `getTextFormatted()`,
`getFormattedNotes()`, `getFormattedChords()`).

**Обоснование**: это персистентные колонки (геттеры/сеттеры поверх `fields`,
`Song.kt:165-190`), и `getText()` добавляет перевод строки на каждый голос
(`Song.kt:4717-4719`) — без пересчёта в БД остался бы «хвост» от удалённого голоса
(FR-008). Пересчёт выполняется только при удалении (событие редкое: сегодня это
1 песня из 26 864), поэтому стоимость не влияет на обычное сохранение (FR-014).

**Альтернатива**: *пересчитывать всегда* — отвергнуто: удорожает каждое сохранение
песни без пользы.

## R7. Побочный эффект: content-change → синхронизация аудио-потомков

**Решение**: принять как есть; убедиться, что цикла нет.

**Обоснование**: `saveToDb` после UPDATE вызывает
`SyncAudioDescendants.onSongSaved(...)` (`Song.kt:5527-5535`), а поле
`source_markers` входит в набор content-полей — значит удаление пустого голоса у
песни в статусе ≥ 5 поставит её в очередь синхронизации потомков
(`SyncAudioDescendants.kt:117-157`). Операция идемпотентна и редка; цикл невозможен:
потомок пишет себя, не родителя (`inSync` дополнительно глушит триггеры внутри
синхронизации).

**Проверка в приёмке**: песня с `audio_parent_id` — сохранение не порождает
бесконечной очереди (см. quickstart, шаг «регрессия аудио-потомков»).

**Альтернатива**: *подавлять хук при нормализации* — отвергнуто: тогда потомки
останутся с прежней (пустой) разметкой; поведение хука — существующий контракт.

без правки `dictionaries.md` уронит CI 7/7.

## R9. Схема БД и совместимость

**Решение**: схема не меняется (FR-013). Данные остаются JSON-текстом в
`tbl_songs.source_text` и `tbl_songs.source_markers`; список голосов — массив
массивов маркеров и массив строк.

**Обоснование**: 26 864 строки уже в этом формате; миграция не нужна и не
запрашивалась (владелец исключил разовую чистку).

**Альтернатива**: *отдельная таблица голосов* — отвергнуто: смена модели данных на
пустом месте, ломает sync/recordhash/DTL/рендер.

## R10. Тестирование

**Решение**: юнит-тесты JUnit 5 на чистую функцию (`VoiceNormalizationTest`) +
ручные проверки на локальной БД и в админке (quickstart). Интеграционные тесты,
требующие сети/браузера, не используются — большинство `@Disabled` (конституция
§ «Тесты»).

**Обоснование**: нормализация — чистое преобразование данных; именно его и надо
зафиксировать тестом, чтобы правило не отъехало при будущих правках `Song.kt`.
