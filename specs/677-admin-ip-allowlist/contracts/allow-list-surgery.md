# Contract: хирургическая правка allow-list на прод-хосте

> Phase 1 output. Контракт самой опасной части — изменения конфигурации прод-хоста.
> Требования: FR-006, FR-007, FR-008, FR-009, FR-015, FR-020.

## 1. Область изменения

Меняется **только** `/etc/nginx/nginx.conf` на прод-хосте, и только в двух местах: в
stream-блоке с `listen 5433;` и в stream-блоке с `listen 9000;` добавляется ровно одна
строка `allow <ip>;` непосредственно перед строкой `deny all;`.

Ничего больше: ни портов, ни TLS, ни маршрутизации, ни `proxy_pass`, ни других файлов
(FR-006, FR-015).

## 2. Подготовка нового содержимого

1. Читаем живой конфиг по ssh (целостностью, без интерпретации).
2. Находим оба stream-блока по `listen 5433;` и `listen 9000;`.
3. В каждом — строку `deny all;` (последняя `allow`-строка перед ней определяет отступ).
4. Вставляем `allow <ip>;` перед `deny all;` с тем же отступом (табуляция).
5. Если в блоке нет `deny all;` или блок не найден — **правка не выполняется**
   (конфигурация не соответствует ожидаемой; FR-020).

## 3. Проверка diff'а (FR-020)

Из нового содержимого удаляются **ровно добавленные** строки `allow <ip>;` (по числу и
содержинию). Результат MUST совпасть с исходным содержимым **побайтно**. Иное расхождение —
отказ от применения, уведомление владельцу, код возврата 3.

Это же правило закрывает edge case «прод-конфиг отличается от ожидаемого (правка вручную)»:
ручная правка сохраняется, а расхождение видно в diff'е до применения.

## 4. Порядок применения (FR-007, FR-008)

| # | Действие | Проверка |
|---|---|---|
| 1 | Новое содержимое записано во временный файл на прод-хосте | файл существует, размер совпадает с ожидаемым |
| 2 | `nginx -t -c <временный файл>` — синтаксис временного файла тем же nginx | код 0 ⇒ иначе отказ (код 3), прод не изменён |
| 3 | Бэкап: `cp nginx.conf nginx.conf.bak-<stamp>` | файл бэкапа существует |
| 4 | Подмена **содержимым** с сохранением inode: `cat <временный> > nginx.conf` | inode не изменился |
| 5 | `nginx -t` — синтаксис **живого** файла (канон runbook §4) | код 0 ⇒ иначе откат |
| 6 | `nginx -s reload` | код 0 ⇒ иначе откат |
| 7 | Контрольная проверка: TCP `5433`, TCP `9000`, HTTPS `health` | все ок ⇒ правка подтверждена; иначе откат |

**Почему `cat`, а не `mv`**: `mv` создаёт новый inode — контейнерные bind-mount'ы продолжают
видеть старый файл (runbook `prod-config-delivery.md` §3). Подмена содержимым сохраняет inode.

## 5. Откат

При сбое на шагах 4-7:

1. `cat nginx.conf.bak-<stamp> > nginx.conf` (inode сохраняется);
2. `nginx -s reload`;
3. в журнал — запись с признаком отката и причиной;
4. уведомление владельцу (FR-013);
5. код возврата 1.

Откат обязателен и **не зависит** от причины сбоя (синтаксис, reload, контроль).

## 6. Контрольная проверка (FR-009)

Проверяется **фактический результат**, а не код выхода:

- TCP-соединение к `5433` на прод-хосте устанавливается;
- TCP-соединение к `9000` устанавливается;
- HTTPS `https://sm-karaoke.ru/health` отвечает 2xx.

Проверка выполняется с админ-машины — то есть с того же адреса, который добавляли в
allow-list. Прежние адреса сохраняются (FR-011), автоматического удаления нет.

## 7. Ограничение частоты (FR-010)

Одна **применённая** правка за окно (30 минут по умолчанию). Проверка выполняется **до**
шага 2 подготовки: при нарушении окна правка не выполняется, фиксируется запись в журнал,
владельцу уходит уведомление (FR-013), код возврата 3.

## 8. Что автоматизация НЕ делает

- не удаляет адреса (FR-011) — только по слову владельца;
- не трогает allow-list у `/api/properties/setproperty` в `deploy/prod-single-host/80to8897`
  (владелец оставил его строгим осознанно — Out of Scope спеки);
- не трогает ни один конфигурационный файл, кроме `nginx.conf` (FR-015);
- не перезапускает контейнеры, не меняет маршрутизацию и TLS (Out of Scope);
- не включает `access_log` в stream-блоках (FR-019 — SHOULD, требует согласия владельца на
  изменение прода).

## 9. Что попадает в PR (FR-014)

В PR идёт **репозиторная копия** `deploy/prod-single-host/nginx.conf` **плюс только
недостающая строка `allow <ip>;`** — не всё содержимое прод-файла.

Посторонние расхождения между прод-файлом и репозиторной копией (например добавленный
вручную `87.58.202.244` из PR #24 — отдельная открытая ветка, ждёт одобрения владельца) в
PR **не выносятся**: это отдельный дрейф, который фиксируется в журнале и сообщается
владельцу. Репозиторная копия служит каноном; прод — оперативной истиной; автоматизация
синхронизирует **allow-list**, а не весь файл.
