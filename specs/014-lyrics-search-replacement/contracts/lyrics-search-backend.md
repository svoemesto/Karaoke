# Contract: интеграция с новым поисковым бэкендом (текстов песен)

Эта фича — внутренняя интеграция (не публичный API продукта), поэтому «контракт» —
это (а) неизменный внутренний Kotlin-контракт вызова и (б) функциональный контракт
к внешнему HTTP-бэкенду, которому он должен соответствовать. Точная wire-схема
самого 4get (пути, имена query-параметров) должна быть сверена с документацией/
исходниками развёрнутого инстанса на этапе реализации (см. `research.md`, "Note
for implementation") — здесь фиксируется то, что не должно измениться и то, что
интеграция обязана обеспечить независимо от конкретного бэкенда.

## Внутренний контракт (не меняется, FR-004)

```kotlin
fun searchUrls(query: String): List<String>
```

- **Вход**: непустая строка поискового запроса (например,
  `"$author текст песни $songNameForFind"`, как формирует `getSearXNGSearch` в
  `UtilsAI.kt`).
- **Выход**: список URL-кандидатов (может быть пустым, но не `null`).
- **Ошибки**: любая ошибка бэкенда (сеть, таймаут, не-200 статус, невалидный JSON)
  — НЕ бросает исключение наружу; логируется и возвращается `emptyList()`
  (FR-006, сохраняет сегодняшнее защитное поведение `SearchTool.searchUrls`).
- **Вызывающие места** (не меняются): `LyricsFinderService`
  (`karaoke-app/.../llm/LyricsFinderService.kt`), поток `getSearXNGSearch`
  (`karaoke-app/.../UtilsAI.kt:88`).

## Внешний функциональный контракт к новому бэкенду

| Требование | Обоснование |
|---|---|
| HTTP-эндпоинт принимает поисковый запрос и возвращает результаты в структурированном (JSON) виде | Нужно детерминированно парсить `url` из ответа, как сегодня из `SearxngImageSearchResponse`-аналога |
| Поддерживает как минимум один движок-источник, хорошо индексирующий русскоязычный контент (приоритет — Yandex) | Основная причина замены — мало/пустые результаты по русским запросам «автор текст песни …» (см. `spec.md` Assumptions) |
| Доступен по HTTP из контейнера `karaoke-app` внутри той же docker-сети (`karaokenet`) | Тот же паттерн развёртывания, что и сегодняшний `searxng` сервис — самостоятельный self-hosted контейнер, без внешнего SaaS (FR-002) |
| Адрес бэкенда конфигурируется отдельным свойством/env-переменной, НЕ переиспользует `searxng.base-url` | `searxng.base-url` должен остаться зарезервирован под `AlbumCoverService.searchSearxngImages` (FR-007, вне рамок) — см. `research.md` Вопрос 2 |
| Таймаут запроса задан явно (по аналогии с сегодняшними `Duration.ofSeconds(30)`) | Чтобы недоступность нового бэкенда не блокировала пайплайн дольше разумного (SC-004) |

## Конфигурация (предлагаемый паттерн, см. `plan.md` → Project Structure)

- Новое Spring-свойство: `lyrics-search.base-url` (по аналогии с существующим
  `searxng.base-url` в `application.yml:50-51`).
- Новая env-переменная в docker-compose (`deploy/docker-compose.yml`,
  `deploy/docker-compose-app.yml`, `deploy/new_comp/.../docker-compose-app-new-comp.yml`):
  например `LYRICS_SEARCH_BASE_URL=http://<новый-сервис>:<порт>`, по образцу
  сегодняшнего `SEARXNG_BASE_URL`.
- Новый docker-compose сервис для контейнера нового поискового бэкенда — рядом с
  существующим сервисом `searxng` (который остаётся для обложек), не вместо него.
