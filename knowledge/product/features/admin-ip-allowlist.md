# Автоматизация allow-list админ-машины (самовосстановление доступа к прод-каналу)

> **Status**: active
> **Feature Key**: admin-ip-allowlist
> **Last Updated**: 2026-11-08
> **Branch**: `678-admin-ip-allowlist`
> **Source**: Plane `KARAOKE-337` — «Автоматизация allow-list админ-машины на проде: детект смены внешнего IP и авто-добавление» (разбор инцидента 2026-10-30).
> Per-feature документ по [Constitution VI FR-009](../../../.specify/memory/constitution.md).

## Что делает

Скрипт `deploy/admin-ip-allowlist.sh` под systemd-таймером (`deploy/admin-ip-allowlist.timer`,
раз в 10 минут) проверяет с админ-машины доступность прод-канала и, если недоступность
вызвана allow-list, **сам добавляет текущий внешний адрес админ-машины** в allow-list
прод-хоста `188.127.240.124`.

Цикл:

1. **Пробы**: TCP `5433` (прод-БД), TCP `9000` (MinIO), HTTPS `https://sm-karaoke.ru/health`
   (код 2xx) — с админ-машины.
2. **Различение причины**: HTTPS не отвечает → причина не в allow-list, адрес не
   добавляется, владельцу уведомление. HTTPS отвечает, канал — нет → причина в
   allow-list, продолжаем.
3. **Определение адреса**: **приоритетно — сам прод-хост** (`SSH_CLIENT` в SSH-сессии
   к проду): прод знает, какой адрес мы имеем на том канале, который мы и чиним.
   Запасной источник — публичные HTTPS-сервисы определения внешнего адреса (обход по
   кругу). Расхождение внешних сервисов **не блокирует** правку, если адрес получен
   у прод-хоста (спека 731; инцидент 2026-11-08).
4. **Валидация**: публичный глобальный IPv4 (не loopback / private / multicast /
   broadcast / `0.0.0.0`; IPv6 не поддерживается).
5. **Проверка**: в каждом блоке с `deny all;` уже стоит **ровно один** allow-адрес и
   он текущий → никаких действий, включая перезагрузку.
6. **Правка**: в каждом блоке с `deny all;` список allow-адресов **заменяется** на
   ровно одну строку `allow <текущий ip>;` (прежние адреса удаляются — правило
   владельца 2026-11-08), с бэкапом, двойной проверкой синтаксиса тем же nginx'ом,
   перезагрузкой, контрольной проверкой фактического ответа и откатом при сбое.
7. **Журнал и уведомление**: запись в файл журнала и в journald, уведомление владельцу
   в Telegram.
8. **PR**: после успешного применения — PR через Forgejo API, приводящий
   репозиторную копию конфигурации в соответствие с продом (в PR идёт репозиторная
   копия **плюс только недостающая строка `allow`**). Слияние — за владельцем.

Режимы: основной цикл, `--diagnose` (FR-017: состояние и план без правок),
`--self-test` (FR-018: изолированная проверка правки без обращения к прод-хосту),
`--help`.

## Зачем

Внешний адрес админ-машины меняется двумя способами: пул провайдера плавает
ежемесячно, а при включённом VPN прод видит адрес VPS `87.58.202.244`, которого в
allow-list нет. Каждый разворот означал простой конвейера (синхронизация двух БД,
загрузка в MinIO) **и** ложный CRITICAL «Прод-сервер недоступен» при живом проде —
тот же механизм, что дал ложный CRITICAL 5+ часов 2026-10-23.

Ручная правка allow-list на проде требует доступа к хосту в момент, когда человек
может быть не в состоянии этим заниматься (инцидент случился ночью). Автоматизация
закрывает окно простоя и убирает ложную тревогу.

## Как работает

**Проба.** TCP — через `/dev/tcp` с таймаутом, HTTPS — `curl -w '%{http_code}'`.

**Определение адреса.** Сначала — **прод**: `SSH_CLIENT` в SSH-сессии к
прод-хосту (`detect_prod_seen_address`). Это авторитетный источник: прод видит
наш адрес на том самом канале, который мы и правим (проверено 2026-11-08 по
stream-журналу nginx на проде — хост и контейнер приложения приходят с одного
адреса). Только если прод недоступен по SSH — запасной путь: список
`ALLOWLIST_IP_SERVICES` (по умолчанию: ipify, ifconfig.me, icanhazip,
checkip.amazonaws, ifconfig.co, ipinfo.io) обходится по кругу, и расхождение
ответов означает отказ (адрес из постороннего источника не принимается).

Инцидент 2026-11-08, из-за которого порядок изменён: `api.ipify.org` и
`ifconfig.me` отвечали через VPN-туннель с ротацией адресов (`195.178.4.144…166`,
новый адрес каждый цикл), остальные четыре источника — через адрес ISP
(`95.31.39.146`). Источники расходились, механизм писал `sources_disagree` и **не
применял правку ни разу** за смену адреса — приложение осталось без прод-БД
(`DB-CONNECT-001` десятками в минуту). Внешние сервисы отвечают про маршрут
админ-машины, а нужен адрес маршрута к проду.

**Подготовка содержимого.** В каждом блоке с `deny all;` (stream-блоки
`listen 5433` / `listen 9000` и HTTP-локации сайта) список allow-адресов
заменяется на **ровно одну** строку `allow <текущий ip>;` непосредственно перед
`deny all;`, с тем же отступом, что у соседних строк; остальное — байт-в-байт.
Правила вида `allow 10.0.0.0/8;` (подсети) не трогаются: правило «один текущий
адрес» относится к адресам IP.

**Проверка diff'а (FR-020).** Из старого и нового содержимого убираются строки
`allow` с IPv4-адресами — остатки должны совпасть побайтно. Дополнительно
проверяется итог: в каждом блоке с `deny all;` ровно один allow и он текущий.
Любое иное расхождение — отказ от применения.

**Применение.** Порядок: перепроверка адреса (гонка смены адреса) → временный файл →
`nginx -t -c <temp>` → бэкап `nginx.conf.bak-<stamp>` → **подмена содержимым с
сохранением inode** (`cat`, не `mv`) → проверка целостности записи (sha256) →
`nginx -t` → `nginx -s reload` → контрольная проверка → уборка временного файла.
Откат: **каждый изменённый файл восстанавливается из СВОЕГО бэкапа** тем же
способом записи, которым был изменён, + reload + запись в журнал + уведомление.
Прежний код восстанавливал бэкап последнего файла в первый файл — из-за этого
`/etc/nginx/nginx.conf` получал содержимое файла сайта, `nginx -t` падал, и прод
оставался с нерабочей конфигурацией (инцидент 2026-11-08).

**Частота.** Не более одной применённой правки за 30 минут (`ALLOWLIST_MIN_INTERVAL_MINUTES`).
Состояние — в файле рядом с журналом, вне репозитория.

**Журнал.** Формат `event:key=value` (ADR `local-0005`), время — ISO-8601 UTC.
События: `probe`, `decision`, `address`, `skip`, `edit`, `syntax`, `reload`, `control`,
`rollback`, `notify`, `pr`, `mountpoint`, `drift`, `diagnose`. В журнал идут факты
(адрес, результаты проверок, путь бэкапа), **не** содержимое конфигурации и **не**
секреты.

**SSH-доступ сервиса.** Юнит работает под `root`; у root нет ни ключа, ни
`known_hosts` для прод-хоста, поэтому идентичность выбирается автоматически: явная
настройка (`ALLOWLIST_SSH_IDENTITY_FILE`, `ALLOWLIST_SSH_KNOWN_HOSTS`,
`ALLOWLIST_SSH_STRICT_HOST_KEY`) → кэш прошлого прогона → обычный `ssh` учётной
записи сервиса → перебор ключей оператора админ-машины (`/home/*/.ssh/id_rsa|id_ed25519`);
найденная пара запоминается в state-файле. Без них `ssh` падает с `rc=255`, механизм молча
ничего не применяет, и внешний IP админ-машины остаётся вне allow-list прод-хоста
(прецедент 2026-11-02: прод-БД недоступна 80 минут, владелец узнал из мониторинга).
Причина отказа пишется в журнал (`detail=`) и в уведомление; проверка «сможет ли
таймер применить правку» — `bash deploy/admin-ip-allowlist.sh --check-ssh`.

**Все места allow-list'а.** На проде список адресов админ-машины живёт в трёх
местах: stream-блоки 5433/9000 (`/etc/nginx/nginx.conf`) и HTTP-локации
`/changerecords`, `/api/properties/setproperty` (`/etc/nginx/sites-enabled/80to8897`).
Автоматика правит **все** файлы (`ALLOWLIST_PROD_CONF_FILES`), guard BR-631 требует
одинакового набора адресов во всех репозиторных копиях. Править только один файл
нельзя: остальные останутся со старым списком, и доступ (или синхронизация) будет
закрыт — так пропали одобрения редакторов 2026-11-02.

**Уведомление.** Telegram Bot API того же бота проекта, но в **отдельный служебный
чат** (`ALLOWLIST_NOTIFY_CHAT_ID`): канал проекта (`ALLOWLIST_TELEGRAM_CHAT_ID`)
публичный — публиковать туда служебную информацию о проде нельзя (инцидент
2026-11-01: сообщение «прод-хост недоступен по SSH» ушло в канал «Караоке на своём
месте»). Если служебный чат не задан — уведомление не отправляется, факт остаётся
в журнале (файл и journald).
Токен и chat_id — из окружения; токен не попадает в argv: запрос выполняется через
`curl -K` с конфиг-файлом `600`, который удаляется сразу.

С админ-машины `api.telegram.org` напрямую недоступен (нужен VPN), поэтому вызов
Bot API может идти через локальный SOCKS5-прокси: адрес задаётся переменной
`ALLOWLIST_TELEGRAM_PROXY` (по умолчанию пусто — прямой вызов) и передаётся в `curl`
тем же конфиг-файлом (`proxy = "…"`), не через argv. Прокси действует **только** на
вызов Bot API: определение внешнего адреса и пробы доступности идут напрямую
(`--noproxy '*'`), иначе через прокси определился бы адрес выхода прокси и в
allow-list прод-хоста попал бы не адрес админ-машины. Недоставленное уведомление
фиксируется в журнале и **не** проваливает цикл.

**PR.** Forgejo API: чтение репозиторной копии (contents API) → вставка только
недостающей строки `allow` → создание ветки → коммит файла → `POST /pulls`. Локальный
git не используется.

## Режим туннеля (спека 733, KARAOKE-407)

Когда канал к проду переведён на постоянный туннель WireGuard (ADR
`local-0018`), allow-list прод-хоста содержит **постоянный внутренний адрес**
туннеля `10.77.0.1` — и только его. Автоматика в этом режиме работает иначе:

| | Режим `public` (по умолчанию) | Режим `tunnel` (`ALLOWLIST_MODE=tunnel`) |
|---|---|---|
| Определение публичного адреса | да | **нет** — адрес не определяется вообще |
| Правка allow-list | да (по одному текущему адресу) | **нет** — только read-only проверка |
| Что проверяется | доступность канала | наличие `10.77.0.1` в каждом блоке с `deny all;` |
| При расхождении | правка применяется | событие `decision:reason=tunnel_address_mismatch` + уведомление владельцу, код возврата 3 |

**Почему так.** Правило FR-009: автоматика MUST NOT переписывать постоянный
внутренний адрес на публичный адрес админской машины — иначе она вернула бы
прежнюю уязвимость (доступ по «узнавшему адрес») и сломала бы доступ через
туннель. Таймер при этом не выключается: он продолжает **проверять**, что
постоянный адрес на месте, и сообщает владельцу, если правило нарушено.

Проверка покрыта self-test-сценарием «режим туннеля» в
`deploy/admin-ip-allowlist.sh --self-test`: публичный адрес в allow-list не
попадает, файл не изменяется, расхождение даёт отказ и событие в журнале.

В режиме туннеля allow-list задаётся **декларативно** (шаблон конфигурации
прод-хоста), а не правкой по IP: постоянный адрес не меняется при смене внешнего
адреса машины — значит, и править его незачем.

Подробности: per-feature `knowledge/product/features/prod-tunnel.md`,
runbook `knowledge/guidelines/runbooks/prod-tunnel.md`.

## Инварианты

- Меняется **только** allow-list: в каждом блоке с `deny all;` — ровно одна строка
  `allow <текущий ip>;`; ни портов, ни TLS, ни маршрутизации, ни других файлов.
- В allow-list прод-хоста держится **ровно один текущий адрес** админ-машины
  (решение владельца 2026-11-08). Прежние адреса удаляются: список «про запас»
  держал доступ открытым для всех, кто когда-либо был админ-машиной.
- Не более одной применённой правки за 30 минут.
- Перезагрузка nginx — только после успешной проверки синтаксиса живым nginx'ом.
- Любой сбой на шагах применения оставляет исходный файл (откат из бэкапа).
- Секреты не попадают в argv, в журнал, в уведомления и в репозиторий.
- Прокси — только для вызова Telegram Bot API; глобального прокси у скрипта нет:
  определение внешнего адреса и пробы доступности идут напрямую (`--noproxy '*'`).
- Прод не меняется, если недоступность вызвана не адресом (прод недоступен целиком).
- Рабочее дерево админ-машины автоматизацией не используется (PR — через API).

## Известные ловушки

- **Проба «порт открыт» не равна «доступ разрешён» (BR-631, инцидент 2026-11-02).**
  nginx в stream-блоке при `deny all` **принимает** TCP-соединение и сразу закрывает его,
  поэтому `connect()` успешен и простая TCP-проба показывает «доступно». На этом автоматика
  «зеленела», и новый адрес админ-машины (`185.42.124.207`) в allow-list не попадал, хотя
  канал был закрыт. Отсюда протокольные пробы: Postgres-прокси — SSLRequest и ожидание байта
  ответа (`probe_postgres`), MinIO — HTTP-запрос `/minio/health/live` и код `200`
  (`probe_http_ok`). Контрольная проверка после применения использует те же пробы.
- **Порядок `allow`/`deny` в stream-блоке.** nginx проверяет `allow`/`deny` по порядку,
  побеждает первое совпадение, поэтому `allow <ip>;` **после** `deny all;` не действует
  никогда. Прежняя вставка дописывала allow после deny: правка «применялась успешно», доступ
  оставался закрытым, а контрольная проверка этого не видела. Теперь вставка строго перед
  `deny all;`, «осиротевшие» allow после deny удаляются при нормализации, а `address_allowed`
  проверяет позицию строки, а не только её наличие в файле.
- **`mv` вместо `cat`**: `mv` создаёт новый inode — bind-mount'ы продолжают видеть
  старый файл (runbook `prod-config-delivery.md` §3). Для `/etc/nginx/nginx.conf`
  bind-mount'а нет (проверено `findmnt -T` 2026-10-30), но FR-007 требует сохранения
  inode, и скрипт пишет результат `findmnt` в журнал — переключение на атомарный
  rename станет одной правкой, если владелец его разрешит.
- **Токен в argv**: URL Bot API требует токен в пути — `curl https://api.telegram.org/bot<TOKEN>/…`
  покажет его в `ps`. Отсюда `curl -K` с файлом `600` (guard BR-551/552/605).
- **Определение адреса через прокси**: если бы `detect_address` шёл через прокси,
  источники вернули бы адрес выхода прокси — на 2026-10-30 это `87.58.202.244` вместо
  `185.26.28.199` админ-машины, — и в allow-list прод-хоста попал бы чужой адрес.
  Отсюда `--noproxy '*'` в прямых вызовах, запрет переменных прокси окружения и
  правило 7 guard'а BR-631.
- **`pre-commit run --all-files` в общем checkout**: если в рабочем дереве есть
  чужие изменения, хуки `ktlint`/`prettier` падают и переписывают чужие файлы —
  запускать гейты по своим файлам (`pre-commit run --files …`).
- **Путь `ExecStart` в юните** — абсолютный; при переносе каталога `deploy/` юнит
  надо переустановить.
- **`/tmp` в песочнице агента ≠ `/tmp` хоста**: если валидатор self-test'а работает
  в контейнере, рабочий каталог самопроверки должен лежать в смонтированном пути
  (`ALLOWLIST_SELFTEST_DIR`).
- **Список источников адреса**: ipify периодически недоступен с машины — поэтому
  источников шесть, а не один.
- **Ветка PR создаётся автоматически** (`auto/allowlist-<ip>-<stamp>`) — после
  неудачного применения она остаётся в репозитории; удаление — вручную.
