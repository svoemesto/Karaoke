# Public API contracts: публичный контракт karaoke-web

> **Домен**: [karaoke-web](../domain.md)
> **Компонента**: контракты публичного API — что и кому отдаёт `karaoke-web`.


## Ответственность | Responsibility

Фиксирует **правила видимости и формы** публичных ответов `karaoke-web` там, где
одни и те же данные отдаются несколькими способами (REST и NDJSON) или где
параметр запроса меняет смысл ответа.

Публичный API — контракт с внешним миром: его правка ломает чужой фронтенд.
Поэтому решения здесь принимаются явно и проверяются тестами, а не следуют из
побочных эффектов реализации.

## Файл

- `karaoke-web/.../controllers/PublicApiController.kt` — публичные выборки и NDJSON-стримы;
- `karaoke-web/.../controllers/PublicSubscriptionController.kt` — подписки и тарифы;
- `karaoke-web/.../dto/ZakromaPublicDto.kt`, `.../dto/SongPublicDto.kt` — формы ответов;
- `karaoke-web/.../services/SkipTag.kt` — единое правило разбора тега `SKIP`.

## Интерфейсы и Контракты | Interfaces and Contracts

### 1. Состояние SKIP: два разных факта и два разных правила

| Факт | Где живёт | Что отдаётся публично |
|---|---|---|
| Песня помечена тегом `SKIP` (контент снят правообладателем) | `SongPublicDto.contentRemoved` | **всем** — это не секрет: песня остаётся в каталоге, но её текст недоступен (`PlayerAccessService` блокирует воспроизведение) |
| Автор помечен `tbl_authors.skip = TRUE` (автор скрыт целиком) | `ZakromaPublicDto.authorSkip` | **только** пользователям с правом `canWorkWithSkipped`; остальным — `null` |

Правило едино для обоих представлений: **REST и NDJSON-стрим отдают одно и то же**.
`authorSkip` в REST считается по тому же правилу, что и в потоке
(`if (canSeeSkipped) … else null`), поэтому анонимный посетитель не получает
сведений о скрытых авторах ни в одном из двух путей.

Фронтенд `karaoke-public` показывает бейдж «SKIP» по правилу
`song.contentRemoved && canSeeSkipped` — то есть **отображение** регулируется
правом пользователя, а не формой ответа.

Отдельного поля `SongPublicDto.skipped` **нет**: состояние SKIP песни уже публикуется
полем `contentRemoved`. Второе поле с другим правилом видимости развело бы один факт
на два (часть данных отдаётся всем, часть — никому).

### 2. Публичный список тарифов

`GET /api/public/account/subscription/tariffs?scope=<SCOPE>` — **публичный** endpoint
(без авторизации): тарифы нужны анонимному посетителю до входа в оплату.

- `scope` — **обязательный** параметр из закрытого списка: `SONG`, `SITE`
  (значения взяты из модели `PriceTariff.SCOPE_*`, чтобы контракт не разошёлся с данными);
- неизвестный `scope` → **400** `{"error":"unknown_scope","scope":…,"allowedScopes":[…]}`;
- допустимый `scope` без настроенных тарифов → **200** с пустым списком.

Разделение 400 и пустого списка существенно: раньше опечатка в `scope` давала пустой
список, и фронт показывал «Тарифы пока не настроены» — ошибка запроса выглядела как
отсутствие тарифов.

## Логика и Алгоритмы | Logic and Algorithms

**Единый разбор SKIP.** Признак SKIP вычисляется в одном месте (`SkipTag.hasSkipTag`):
тег `SKIP` среди тегов песни, сравнение регистронезависимое, разделитель — пробел.
Три копии этого правила (доступ к плееру, публичный каталог, публичные страницы
автора) заменены на один вызов: иначе один из путей мог решить, что песня не SKIP.

**Проверка прав перед сборкой ответа.** `canSeeSkipped` считается один раз на запрос
(`siteUserResolver.resolve(request)?.canWorkWithSkipped ?: false`) и передаётся в
сборку DTO. Анонимный пользователь (`resolve` → null) получает `false` — и в REST,
и в потоке.

**Порядок проверок в публичных endpoint'ах.** Валидация параметров выполняется **до**
обращения к данным: неизвестный `scope` отвечает 400, не читая БД. Ошибка запроса
не должна выглядеть как «данных нет».
