# Data Model: Апрув задания редактора завершается ошибкой запроса, новость не появляется

**Feature**: [spec.md](./spec.md) | **Date**: 2026-07-30

Эта фича не вводит новых таблиц/колонок — она уточняет состояния и
переходы уже существующих сущностей (`SongAssignment`, `Song`,
`SongNewsAnnounced`/`News`) в рамках одного эндпоинта `approve()`, и вводит
один новый **логический** (не персистентный) тип — исход апрува,
возвращаемый клиенту.

## Существующие сущности (без изменений схемы)

### SongAssignment (`tbl_song_assignments`)

Поля, значимые для этой фичи (без изменений набора полей):

| Поле | Тип | Значение для апрува |
|---|---|---|
| `admin_status` | string (`open` / `approved` / `rejected`) | Единственный источник истины «одобрено ли задание». Переводится в `approved` ТОЛЬКО если `aRead.save()` реально выполнился (см. Requirements ниже — сейчас это не гарантировано). |
| `reviewed_at` | timestamp | Проставляется вместе с `admin_status = approved`. |
| `review_comment` | string | Очищается (`""`) при апруве. |

**Инвариант (новый, вводимый этой фичей)**: `admin_status = approved`
ДОЛЖЕН персистироваться атомарно с тем, что сервер сообщил клиенту
«успех» — то есть недопустимо состояние «клиент видит успех, а
`admin_status` всё ещё `open`» и симметрично недопустимо «клиент видит
ошибку, а `admin_status` уже `approved`» (см. FR-001/FR-005 spec.md).
Сегодня это НЕ гарантировано: `aRead.save()` — последняя операция в
`approve()`, и если он падает уже ПОСЛЕ того, как `Song` обновлена и
push/анонс отработали, клиент получает ошибку, а `admin_status` остаётся
`open` (что, по крайней мере, безопасно — задание не «зависает» одобренным
без реального сохранения статуса, но UX вводит в заблуждение и ведёт к
бессмысленному повторному клику).

### Song (`tbl_songs`)

Поля, изменяемые апрувом (без изменений набора — уже покрыты
`SongField`/`getDiff`): `id_status`, `source_text`, `result_text`,
`source_markers`, `formatted_text_song`, `formatted_text_tabs`,
`formatted_text_chords`, `status`, `color` (последние два — служебные
UI-поля прогресса, не входят в бизнес-diff, `useInDiff`-подобные пометки
не меняются).

**Инвариант (не меняется)**: `id_status` поднимается до `6` не более
одного раза за апрув (идемпотентно — повторный клик после успеха не
трогает уже применённое значение, см. `if (settings.idStatus < 6)`).

### SongNewsAnnounced (`tbl_song_news_announced`) / News (`tbl_news`)

Без изменений структуры. `PRIMARY KEY(song_id)` на
`tbl_song_news_announced` — уже существующий механизм идемпотентности
(FR-006 spec.md: повторный вызов `checkAndAnnounce()` для той же песни не
создаёт вторую новость). Эта фича не меняет условие «песня публично
доступна» (`Song.isPubliclyWatchable`) и не меняет текст новости
(`specs/092-fix-auto-news-triggers`, User Story 3 — не в скоупе 094).

## Новый логический тип: ApproveOutcome

Не персистентная сущность — форма JSON-ответа `POST
/api/songeditor/approve`, вводимая для того, чтобы клиент (`webvue3`)
мог различать три исхода, требуемых FR-001/FR-002/FR-005 (сегодня
эндпоинт либо возвращает `{"ok": true, "idStatus": N}`, либо
`{"ok": false, "error": "..."}` для штатных отказов до применения
изменений, либо — в багованном случае — вовсе не отвечает валидным JSON
из-за необработанного исключения).

| Состояние (`status`) | Когда наступает | HTTP-код | Что видит администратор |
|---|---|---|---|
| `success` | Локальное применение (разметка + `id_status`) прошло успешно, задание помечено `admin_status = approved`. Push на боевую копию и/или `checkAndAnnounce()` могли завершиться неудачей (best-effort, см. Clarifications) — на `status` это не влияет. | 200 | Явное сообщение об успехе (FR-001). |
| `already_approved` | Задание уже было `admin_status = approved` до этого клика (повторный/двойной клик). Изменения повторно не применяются (FR-006). | 200 | «Задание уже одобрено» (FR-002). |
| `error` | Локальное применение изменений к `Song` завершилось ошибкой, ИЛИ финальная запись `admin_status = approved` завершилась ошибкой (в т.ч. ранее необработанное исключение — теперь перехватывается и превращается в этот исход). | 200 (тело — типизированная ошибка; НЕ «сырой» HTTP 5xx без тела) | Сообщение об ошибке, задание остаётся `open` (FR-003). |

**Переходы (state machine, только для `admin_status` в рамках этого
эндпоинта)**:

```text
        (клик "Одобрить и премиить")
                    │
                    ▼
        ┌───────────────────────┐
        │ admin_status = open/  │
        │ rejected (ожидает)    │
        └───────────┬───────────┘
                     │ применение к Song: успех
                     │
        ┌────────────┴─────────────┐
        │                           │ применение к Song: ошибка
        ▼                           ▼
 запись admin_status         admin_status остаётся
 = approved                  open/rejected (без изменений)
        │                           │
   успех │ ошибка записи            │
        │      │                    │
        ▼      ▼                    ▼
   status=    status=error,   status=error,
   success    admin_status    admin_status
              остаётся        не менялся
              open/rejected
              (НЕ approved —
              см. инвариант
              выше)

        (повторный клик, admin_status уже approved)
                    │
                    ▼
            status=already_approved
            (Song/push/анонс не переприменяются)
```

## Связи между сущностями (не меняются)

`SongAssignment.songId → Song.id` (1:1 активное задание на песню в
рамках одного цикла редактирования); `SongNewsAnnounced.songId →
Song.id` (`PRIMARY KEY(song_id)` — не более одной анонс-записи на песню,
не зависит от `SongAssignment`).
