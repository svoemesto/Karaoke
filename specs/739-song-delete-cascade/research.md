## R-001. Каскад в БД: инвентарь FK на `tbl_songs`

**Решение.** Каскад удаления песни охватывает **две** группы таблиц: те, где FK
на `tbl_songs` уже есть (и потому блокируют удаление), и те, где FK нет (и потому
остаются сиротами). Проверено по `deploy/karaoke-db/*.sql` (grep `FOREIGN KEY`,
`ON DELETE`, `REFERENCES tbl_songs`).

Фактическая картина (на 2026-11-12):

| Таблица | FK на `tbl_songs` | Правило | Что делаем при удалении песни |
|---|---|---|---|
| `tbl_songs` | — | — | `DELETE` (LOCAL и SERVER) |
| `tbl_song_authors` | `song_id` | `ON DELETE CASCADE` | каскад БД сам; проверяем, что сработал |
| `tbl_news` | `song_id` | **NO ACTION** (по умолчанию) | **миграция** → `ON DELETE SET NULL` (FR-009) |
| `tbl_song_news_announced` | `song_id` | **NO ACTION** (по умолчанию) | **миграция** → `ON DELETE CASCADE` (см. R-002) |
| `tbl_song_assignments` | нет | — | явный `DELETE` (FR-005) |
| `tbl_song_assignment_drafts` | нет (`assignment_id` → assignments) | — | явный `DELETE` по `assignment_id` (FR-005) |
| `tbl_site_playlist_items` | нет | — | явный `DELETE` (FR-005) |
| `tbl_song_share_links` | нет | — | явный `DELETE` (FR-005) |
| `tbl_listening_history` | нет | — | явный `DELETE` (FR-006) |
| `tbl_search_results` | нет | — | явный `DELETE` (FR-006) |
| `tbl_search_async` | нет | — | явный `DELETE` (FR-006) |
| `tbl_events` | нет | — | `DELETE` **только** `song_id <> 0` (FR-007) |
| `tbl_songs.audio_parent_id` | нет (self-reference, без FK) | — | `UPDATE … SET audio_parent_id = NULL` у потомков (FR-008) |
| `tbl_albums` | `tbl_songs.album_id` → `tbl_albums(id)` `ON DELETE SET NULL` | — | при удалении последней песни альбома — `DELETE` записи альбома (FR-018) |
| `tbl_pictures` | нет (связь по `picture_name`) | — | `DELETE` записи картинки альбома (FR-019) |
| `tbl_songs_sync` | нет | — | `DELETE` строки на SERVER (решение владельца № 11) |

**Находка сверх карты.** В карте решений (KARAOKE-411) зафиксировано «FK на
`tbl_songs` всего два — соавторы (CASCADE) и новости (NO ACTION)». По миграциям
их **три**: третий — `tbl_song_news_announced.song_id`
(`deploy/karaoke-db/33_song_news_announced.sql:23`), тоже `NO ACTION`, тоже
блокирует удаление. Это таблица-метка «по этой песне уже принято решение об
анонсе» (`PRIMARY KEY(song_id)`, не в `SyncRegistry`, живёт только на PROD).
Без обезвреживания этого FK удаление любой песни с меткой «новость объявлена»
упадёт по FK-ошибке. Расхождение с картой — фиксирую как факт кода, спеку не меняю.

**Обоснование.** FK-правила `NO ACTION` — единственная причина, по которой
`DELETE FROM tbl_songs` падает для части песен. Схема обязана быть приведена к
`SET NULL`/`CASCADE` **до** включения нового кода (см. R-008).

**Альтернативы отклонены.**
- *Удалять новости каскадом*: прямо противоречит FR-009 («удалить новости песни из
  привязки к песне, но MUST NOT удалять сами новости») и решению владельца
  KARAOKE-419.
- *Оставить FK как есть и обходить через `SET CONSTRAINTS ALL DEFERRED`*: отложенная
  проверка всё равно упадёт в конце транзакции; не решает блокировку.
- *Ручной `UPDATE tbl_news SET song_id = NULL` перед `DELETE`*: работает, но прячет
  инвариант в коде вместо схемы; при любом другом пути удаления песни (sync-движок,
  ручной SQL) снова появится блокировка. Схема — правильное место.

## R-002. `tbl_song_news_announced`: `SET NULL` невозможен — нужен `CASCADE`

**Решение.** Для `tbl_song_news_announced` правило `ON DELETE SET NULL` технически
неприменимо: `song_id` — часть `PRIMARY KEY (song_id)` (`33_song_news_announced.sql:29`),
а `SET NULL` требует `NULL`-допустимости. Миграция пересоздаёт FK с
`ON DELETE CASCADE` и снимает `NOT NULL` с `song_id` не нужно — каскад удалит строку
целиком.

**Обоснование.** Таблица — метка «решение об анонсе принято», первичный ключ —
`song_id`. Строка без песни не имеет смысла и не несёт данных песни (в ней только
`song_id`, `news_id`, `created_at`). Удаление строки-метки вместе с песней —
семантически точное и не затрагивает ни новость, ни данные песни.

**Альтернативы отклонены.**
- *Оставить FK `NO ACTION`, а метку удалять вручную перед `DELETE` песни*: тот же
  дефект, что и в R-001, — инвариант в коде, а не в схеме.
- *`SET NULL` + составной PK `(song_id, created_at)`*: ломает смысл «не более одного
  решения на песню» (гарантия, которую комментарий миграции прямо называет
  причиной `PRIMARY KEY`).

**Открытый вопрос владельцу (В-02)**: правило `CASCADE` для таблицы-метки
подтвердить — это удаление строки служебной таблицы, а не данных песни.

## R-003. Правило владения артефактом: строгое для удаления, нормализованное — для разовой уборки

**Решение.** Нужны **два разных** матчера, а не один:

1. **Удаление артефактов песни (FR-010, FR-011) — строгое совпадение.**
   Файл принадлежит песне, только если `file.name == song.fileName + rest`, где
   `rest` — «продолжение артефакта»: пусто, `.расширение`, `-суффикс` или
   ` [метка]`. Сравнение — **точное**: регистр значим, `ё` ≠ `е`, тип кавычки
   значим, `01` ≠ `1`. Соседняя песня «Песня, длинная версия» не является
   продолжением: остаток `, длинная версия` не начинается ни с `.`, ни с `-`,
   ни с ` [`.
   База для реализации — готовая функция `SongArtifactRenamer.isArtifactContinuation`
   (`karaoke-app/.../model/SongArtifactRenamer.kt:50`) и обход
   `SongArtifactRenamer.artifactDirs` (корень + `hdemucs_mmi`, `done_files`,
   `done_chords`, `sheetsage` + все `symlink_*`).

2. **Разовая уборка (FR-042) — нормализованное совпадение, и оно ИСКЛЮЧАЕТ
   объект.** Если имя файла совпадает с именем живой песни после нормализации
   (регистр, `ё`/`е`, кавычки, `1`/`01`), объект **не** попадает в кандидаты на
   удаление. Измеренные 3 520 «похожих» файлов — именно этот случай.

**Обоснование.** Требования противоположны и не могут быть выражены одним
правилом: при удалении песни «чужая» песня с похожим именем не должна быть
тронута (FR-011), а при разовой уборке — наоборот, «почти своя» копия живой
песни не должна быть удалена (FR-042). Смешение правил даёт либо удаление чужих
песен, либо оставление собственных артефактов. В коде это два разных матчера с
общими таблицами-константами нормализации.

**Альтернативы отклонены.**
- *Одно правило «сравнивать по нормализации»*: нарушает FR-011 — удалит чужую
  песню.
- *Одно правило «сравнивать точно»*: нарушает FR-042 — разовая уборка снесёт
  near-match живых песен (те самые 3 520 файлов).
- *Взять имя из `storageFileName` целиком (`$author/$year - $album/$fileName`)*:
  не отличает артефакт от одноимённой соседней песни в том же альбоме.

## R-004. Варианты старого имени песни (FR-013) → нужна таблица истории имён

**Решение.** FR-013 требует удалять объекты «как по текущему имени, так и по ранее
использовавшимся вариантам имени». В БД хранится только текущее `file_name`;
история имён нигде не сохраняется — отсюда и 745 устаревших копий в MinIO
(дефект `renameAllArtifacts`, отдельная задача KARAOKE-428).

Чтобы FR-013 был исполнимым **на будущее**, добавляется таблица
`tbl_song_name_history(song_id, file_name, changed_at)`; при каждом переименовании
песни (`Song.renameAllArtifacts` / `Song.renameCascadeExtraArtifacts`) в неё
пишется прежнее имя. При удалении песни удаляются объекты по текущему имени **и**
по всем именам из истории.

**Обоснование.** Единственный надёжный способ узнать «прежние варианты имени» —
хранить их. Альтернатива (сканировать весь префикс `$автор/$год - $альбом/` и
удалять всё похожее) небезопасна: удалит артефакты соседних песен.

**Альтернативы отклонены.**
- *Считать, что разовая уборка 745 копий (KARAOKE-427) закрывает вопрос*: не
  закрывает — после следующего переименования снова появятся устаревшие копии, и
  FR-013 останется неисполнимым для будущих песен.
- *Хранить историю в JSON-поле `tbl_songs`*: правило Constitution III о
  `recordhash`-совместимых колонках и риск разрастания строки; отдельная
  таблица прозрачнее и удаляется каскадом вместе с песнёй.

**Открытый вопрос владельцу (В-03)**: подтвердить введение таблицы истории имён
как условие FR-013.

## R-005. Объекты хранилища песни: что удаляем, а что — нет

**Решение.** Ключ объекта песни в MinIO: `$автор/$год - $альбом/$имяПесни` + суффикс
(`Song.storageFileName`, `Song.kt:88`; бакет `karaoke`).

Состав того, что лежит в хранилищах у песни (по `KaraokeFileType` и
`PUBLICATION_PICTURE_NAME_SUFFIXES`):

| Объект | Ключ | Источник правила | Вердикт |
|---|---|---|---|
| mp3-стемы (5 видов) | `$author/$year - $album/$fileName.{accompaniment,vocals,bass,drums,other}.mp3` | `KaraokeFileType` (`MP3_*`, `LOCAL_STORAGE`+`REMOTE_STORAGE`) | **удаляем** |
| публикационные картинки (9 суффиксов) | `$author/$year - $album/$fileName [karaoke].png` и др. | `PUBLICATION_PICTURE_NAME_SUFFIXES` | **удаляем** (легаси-объекты, KARAOKE-421) |
| обложка альбома + превью | `$author/$year - $album/$author - $year - $album{.album,.preview.album}.png` | `KaraokeFileType.PICTURE_ALBUM`, `PICTURE_ALBUM_PREVIEW` | **НЕ удаляем** при удалении песни (FR-014); удаляется с альбомом (FR-019) |
| картинка автора + превью | `$author/$author{.author,.preview.author}.png` | `KaraokeFileType.PICTURE_AUTHOR`, `PICTURE_AUTHOR_PREVIEW` | **НЕ удаляем** никогда в этой фиче (FR-014) |
| видео, исходники, flac-стемы, субтитры, `.song`/`.settings`, проекты рендера | — | в MinIO не загружаются (FR-016 в `song-artifact-cleanup`) | в MinIO таких объектов нет; проверяется замером бакетов |

Правило «свой объект»: ключ начинается с `$author/$year - $album/$fileName`, а
остаток — продолжение артефакта (пусто / `.ext` / ` [метка]` / `-суффикс`).
Объекты обложки альбома и автора начинаются с другого префикса
(`$author - $year - $album...`, `$author...`), поэтому правило их отсекает
автоматически — это важно, потому что проверка FR-014 должна быть структурной,
а не «списком исключений».

**Обоснование.** `KaraokeFileType` — единственный реестр «что где лежит»
(`knowledge/domains/health/domain.md`), `PUBLICATION_PICTURE_NAME_SUFFIXES` —
единственный список суффиксов публикационных картинок, используемый и реестром
уборки, и переименованием. Использовать их — значит не изобретать второй реестр
(прецедент spec #339).

**Альтернативы отклонены.**
- *Свой список ключей в новом сервисе*: разойдётся с `KaraokeFileType` при любой
  правке; FR-037 (сброс кеша) уже опирается на `StorageCacheReset.storageFileNamesForSong`.
- *Удалять весь префикс альбома*: снесёт артефакты соседних песен альбома.

## R-006. Предпросмотр должен быть точным (SC-004): переиспользовать те же правила

**Решение.** Предпросмотр (FR-023…FR-027) и фактическая уборка используют **один
и тот же** код определения артефактов песни. Расхождение «файлов в окне» и
«файлов удалено» должно быть нулём (SC-004), и это достижимо только общим
правилом, а не двумя независимыми реализациями.

Состав предпросмотра: обход папки альбома на диске (файлы) + **листинг бакета с
префиксом** `$author/$year - $album/` в обоих хранилищах (объекты). Листинг по
префиксу — один сетевой запрос на хранилище, а не обход всего бакета.

**Обоснование.** «Расхождение не превышает 0 для удалённых файлов» — требование
точности, а не оценки. Общий код правил + реальный листинг дают точность;
приблизительные подсчёты по БД её не дают.

**Альтернативы отклонены.**
- *Считать по БД (`tbl_songs` + кеш хранилища)*: кеш метаданных вечный (TTL = ∞)
  и может врать; счёт «по кешу» расходится с фактом (в коде уже есть
  `DELETE /api/health/cache/refresh` — ручной сброс как раз из-за этого).
- *Отдельная реализация для предпросмотра*: гарантированный источник расхождения.

## R-007. Порядок операций и транзакционность

**Решение.** Операция разбита на три фазы с разными требованиями к атомарности.

**Фаза A — LOCAL-БД, синхронно, одна транзакция.** Удаляются строка `tbl_songs` и
все связанные записи (см. R-001), `audio_parent_id` у потомков обнуляется,
`tbl_news.song_id` обнуляется (схемой). Одна транзакция: `commit` при полном
успехе, `rollback` при любой ошибке. Возврат эндпоинта: `deleted` | `not_found` |
`db_error`.

**Фаза B — SERVER-БД, синхронно, отдельная транзакция.** Удаляются строка
`tbl_songs` на SERVER и строка из `tbl_songs_sync` на SERVER (решение владельца
№ 11). Ошибка здесь **не отменяет** фазу A: результат возвращается как
«удалено локально, сервер недоступен» — это ровно то, что требует FR-045
(«результат удаления MUST отражать это, а не показывать успех»).

**Фаза C — фоновые артефакты, отдельным заданием очереди.** Порядок строго по
FR-031: **диск → хранилища → альбом и его обложка → папка альбома**.

**Обоснование (почему LOCAL первым).** Если удалить только SERVER, а LOCAL оставить,
то следующий прогон sync (LOCAL→SERVER) увидит расхождение по `recordhash` и
**вернёт** песню на SERVER. Если удалить только LOCAL, а SERVER оставить — песня
продолжит жить на публичном сайте, но sync-движок с
`sync_songs_push_delete_allowed` её удалит. Удаление LOCAL первым делает
«направление» односторонним и предсказуемым.

**Транзакционность внутри фазы C невозможна** (диск, MinIO, две БД) — вместо неё
применяется правило **«строка удаляется только после того, как артефакты признаны
удалёнными или оставленными с причиной»**: журнал пишется на каждом шаге, прогон
получает терминальный статус (`DONE` / `PARTIAL` / `FAILED`), а частичный остаток
не теряется (FR-033, SC-009).

**Альтернативы отклонены.**
- *Удалить строку песни в самом конце (после уборки)*: противоречит решению
  владельца № 6 и US1 («песня исчезает из списка сразу»), плюс оставляет окно, в
  котором фоновый процесс всё ещё работает с удалённой песнёй.
- *Удалить строку песни и хранилища в одной транзакции*: MinIO не участвует в
  транзакциях Postgres; иллюзия атомарности вреднее её отсутствия.
- *Сделать фазу C синхронной*: нарушает FR-029 и инвариант storage № 4
  («MinIO-операции НЕ выполняются в HTTP-треде пользовательского запроса»).

## R-008. Фоновая уборка: новый тип `KaraokeProcess` + таблицы журнала в БД

**Решение.** Уборка — новое задание очереди:

- новый тип `KaraokeProcessTypes.SONG_DELETE_CLEANUP`;
- лейн — `THREAD_LANE_LIGHT_BACKGROUND` (`threadId = -1`), потому что операция
  сетевая и файловая, а не тяжёлый рендер;
- шаг исполняется через существующий механизм `runFunctionWithArgs`
  (`Utils.runFunctionWithArgs`, `Utils.kt:5047`): аргументы
  `["runFunctionWithArgs", "songDeleteCleanup", "songId=…", "runId=…"]`;
- переживание рестарта обеспечено существующим механизмом
  `KaraokeProcess.setWorkingToWaiting` (WORKING → WAITING при старте) — FR-030.

**Журнал уборки — в БД** (FR-034: «журнал уборки, который ведётся в базе данных»),
две новые таблицы:

- `tbl_song_cleanup_runs` — прогон: состояние
  (`PLANNED → APPROVED → RUNNING → DONE | PARTIAL | FAILED`), `song_id`,
  `initiator`, `started_at`, `finished_at`, счётчики, текст ошибки;
- `tbl_song_cleanup_entries` — действие: `run_id`, `kind`
  (`FILE | STORAGE_OBJECT | ALBUM | PICTURE | ALBUM_FOLDER`), `path_or_key`,
  `size_bytes`, `result` (`DELETED | KEPT | FAILED | SKIPPED`), `reason`,
  `created_at`, `initiator` (FR-035).

**Повторы.** Механизм очереди даёт retry только для `DEMUCS*`; для функционального
шага повтор с нарастающими паузами реализуется **внутри** шага: до 5 попыток,
паузы 2s → 60s (решение KARAOKE-414), после исчерпания — остаток пишется в
журнал, прогон получает статус `PARTIAL`/`FAILED`, доступен ручной добор (FR-032,
FR-033).

**Обоснование.** Отдельная подсистема не создаётся (Assumptions спеки): очередь
`KaraokeProcess` — штатный механизм, у неё уже есть лейны, single-flight,
восстановление после рестарта, цепочки и статусные лейты. TSV-журнал
`cleanup-logs/` (specs/544) остаётся за разовой уборкой — решение владельца
KARAOKE-423: «TSV-журналы `cleanup-logs/` — только для разовой уборки».

**Альтернативы отклонены.**
- *Отдельный планировщик на `@Scheduled`*: потеря переживания рестарта, дублирование
  очереди, свой формат статусов.
- *Переиспользовать `ArtifactCleanupService`*: он работает по классам файлов и
  корням, без привязки к песне, без контекста «что удалено по плану удаления
  песни» и без двух БД — решение владельца KARAOKE-412: «контура MinIO, повторов
  с backoff, привязки к песне и статуса остатка нет — писать заново».
- *Хранить журнал в файле (как `CleanupJournal`)*: FR-034 прямо требует БД;
  файл-журнал не переживает переустановку контейнера и не даёт выборок.

## R-009. Защита от удаления «не нашей» песни

**Решение.** Эндпоинт отказывается работать, если песня не проходит проверку
принадлежности проекту:

1. строка есть в LOCAL `tbl_songs` (иначе — `not_found`, и это **не** ошибка,
   а идемпотентный успех по FR-002/US1-edge);
2. `root_folder` начинается с одного из `PROJECT_ROOT_FOLDERS`
   (`/sm-karaoke/work`, `/sm-karaoke/done1`, `/sm-karaoke/done2`) — иначе запись
   указывает на чужой или временный каталог;
3. `file_name` непустой и не содержит разделителей пути (`/`, `..`) — иначе
   ключ в хранилище может выйти за префикс альбома.

**Обоснование.** Каскадная уборка трогает файлы и объекты по имени. Если запись
песни ссылается на каталог вне проекта, строка шаблона ключа может указать на
чужое хранилище. FR-046 запрещает удалять данные, не относящиеся к песне, —
эта проверка делает запрет структурным, а не «списком исключений».

**Альтернативы отклонены.**
- *Проверять только существование строки*: защиты от «чужой» записи нет.
- *Сверять папку с корнем альбома, вычисленным из автора/года/альбома*: имя
  альбома в БД может отличаться от имени папки (регистр, `ё`/`е`) — проверка
  дала бы ложные отказы.

## R-010. Порядок раскатки и обратимость

**Решение.** Раскатка в четыре шага, каждый — обратим:

1. **Миграции** `58_news_song_id_on_delete_set_null.sql`,
   `59_song_name_history.sql`, `60_song_cleanup_journal.sql` — вручную на LOCAL,
   затем на PROD (runbook `knowledge/system/infra/sql-migrations.md`, решение 4).
2. **Код** (эндпоинты, сервис уборки, журнал, UI) — с **выключенным** флагом
   `songDeleteEnabled` (по умолчанию `false`).
3. **Включение флага** на admin-машине, приёмка на тестовой песне.
4. (Отдельно, по решению владельца) — включение на проде.

**Миграционная безопасность.**

- *Старый код при новой схеме* — работает: `SET NULL` и `CASCADE` только ослабляют
  ограничения, семантика старого `DELETE` не меняется; новая таблица истории имён
  старому коду не мешает.
- *Новый код при старой схеме* — **сломан**: `DELETE` песни с новостью упадёт по
  FK-ошибке. Но «сломан» здесь безопасно: эндпоинт возвращает «отказ базы
  данных» (FR-002), а не ложный успех. Именно поэтому порядок «миграция → код»
  обязателен, а не «код → миграция».
- *Откат* — выключение флага `songDeleteEnabled` (правка конфигурации +
  перезапуск `karaoke-app`). Откат миграций не нужен: `SET NULL`/`CASCADE` —
  ослабление ограничений, безопасное для старого кода.

**Обоснование.** Feature flag — стандартный способ сделать релиз обратимым без
отката кода; фича затрагивает необратимые операции (удаление файлов), поэтому
включение по умолчанию выключено обязательно.

**Альтернативы отклонены.**
- *Откат миграциями обратно*: `DROP CONSTRAINT` + `ADD ... NO ACTION` вернёт
  блокировку удаления, но песни, уже удалённые при новой схеме, останутся удалёнными
  — откат неполон и вводит в заблуждение.
- *Включить сразу в проде*: необратимые операции без приёмки на LOCAL.

## R-011. Наблюдаемость: коды событий, журнал, метрики

**Решение.** Наблюдаемость — три слоя.

**Слой 1 — журнал в БД** (`tbl_song_cleanup_runs` + `tbl_song_cleanup_entries`):
по каждому действию — путь или ключ, размер, результат, дата, инициатор,
идентификатор прогона (FR-035). Прогон даёт сводку «что удалено, что осталось и
почему осталось» (US1-сценарий 4).

**Слой 2 — структурированные логи** категории `infra.song.delete`, формат
`event:key=value` (ADR `local-0005`). Коды событий:

| Код | Уровень | Когда |
|---|---|---|
| `song.delete.requested` | INFO | админ подтвердил удаление |
| `song.delete.blocked.process` | WARN | FR-004: идёт фоновая обработка |
| `song.delete.blocked.ownership` | WARN | R-009: запись вне проекта |
| `song.delete.db.local.ok` | INFO | фаза A завершена |
| `song.delete.db.local.failed` | ERROR | фаза A откатилась (FR-002) |
| `song.delete.db.server.ok` | INFO | фаза B завершена |
| `song.delete.db.server.failed` | WARN | SERVER недоступен (FR-045) |
| `song.cleanup.run.started` | INFO | начало фоновой уборки |
| `song.cleanup.step.done` | INFO | шаг удалён/оставлен |
| `song.cleanup.step.failed` | WARN | шаг не выполнен, есть остаток |
| `song.cleanup.run.finished` | INFO/WARN | терминальный статус прогона |

**Слой 3 — статус в админке** (FR-036): текущий статус прогона и остаток видны в
интерфейсе; SSE-уведомление при переходе прогона в терминальное состояние
(существующий механизм `SNS.send` / `SseNotification`).

**Обоснование.** ADR `local-0005` — конвенция проекта; `AppLog`/категории логов
используются повсеместно. Отдельный слой «метрики» в проекте не заведён —
наблюдаемость выражается логами + SSE + журналом в БД (см. также
`knowledge/domains/monitoring/domain.md`).

**Альтернативы отклонены.**
- *Только логи без журнала в БД*: FR-034 требует журнал в БД; логи не дают
  выборки «что осталось» по прогону.
- *Отдельная система метрик (Prometheus и т.п.)*: в проекте нет, добавление
  инфраструктуры вне объёма.

## R-012. Тестовая стратегия: правило владения — главный риск

**Решение.** Тесты строятся вокруг одного правила владения артефактом (R-003),
потому что именно оно определяет, чужое ли мы удаляем.

- **Unit** — чистые функции: правило владения (регистр, `ё`/`е`, кавычки,
  `1`/`01`, соседняя песня с префиксом), нормализация для разовой уборки,
  планировщик каскада по таблицам, машина состояний прогона, подсчёт
  предпросмотра, построение ключей хранилища.
- **Integration** — сквозной сценарий на тестовой БД и тестовом хранилище:
  удаление песни с полным набором артефактов; повторное удаление; отказ БД;
  недоступность хранилища с повторами; альбом-«близнец»; песня с новостью
  (регрессия FK); предпросмотр == факт (расхождение 0).

**Обоснование.** Требования SC-001, SC-002, SC-004, SC-005, SC-008 — все про
«ничего чужого не удалено» и «счётчики совпадают». Единственный способ это
доказать — проверять правило владения и равенство счётчиков.

**Альтернативы отклонены.**
- *Только интеграционные тесты*: `SongArtifactRenamer` уже показал, что правило
  владения — место с наибольшим числом скрытых дефектов (соседняя песня с
  префиксом, « [метка]» вместо любого пробела).
- *Ручная приёмка на проде*: необратимые операции без автоматической проверки
  недопустимы.

## R-013. Что из накопленного объёма входит в фичу, а что — в разовую уборку

**Решение.** Разделяем накопленный объём на две части (решения владельца
KARAOKE-418, KARAOKE-424, KARAOKE-425, KARAOKE-427).

| Объём | Величина | Куда |
|---|---|---|
| Истинные сироты в MinIO (объекты песен, которых нет в БД) | 310 ключей / 2,58 ГБ (LOCAL 182/1,21 ГБ, REMOTE 128/1,19 ГБ) | **FR-041 — разовая уборка**, отдельный проход по протоколу утверждённого набора |
| Устаревшие копии под старыми именами живых песен | 745 ключей / 4,38 ГБ | **FR-041 — разовая уборка**; дефект переноса ключей — KARAOKE-428 (вне объёма) |
| Обложки альбомов, которых больше нет в каталоге | 514 картинок | **FR-041 — разовая уборка** |
| Мусор в корне бакета | 471,9 МБ | **FR-041 — разовая уборка** |
| Осиротевшие файлы на диске | 1 927 файлов / 3,83 ГБ / 164 папки | **FR-041 — разовая уборка** |
| Near-match файлы на диске | 3 520 файлов | **не трогаем никогда** (FR-011, FR-042) |
| Черновики без задания | 1 424 | **FR-041 — разовая уборка** |
| Исторические строки (2 101, ≈53 МБ) | `search_results`, `listening_history`, `events` | **FR-041 — разовая уборка**; при этом при удалении **конкретной** песни её собственная история чистится каскадом (FR-006, FR-007) |
| Медиа АукцЫон-1996 и Сектор Газа-2023 | ≈244 МБ | **разовый проход** по протоколу утверждённого набора (Assumptions спеки) |
| Три пары «альбом-сирота ↔ близнец» | 5 альбомов-сирот | запись-сирота удаляется, канонический близнец остаётся (FR-022) |

**Ключевая связь с основной фичей.** Разовая уборка — это **тот же код
владения и тот же журнал**, но с другим источником набора (список кандидатов с
отпечатком вместо набора артефактов одной песни) и другим триггером (утверждение
владельцем вместо подтверждения админа). Поэтому реализация разовой уборки —
следующий шаг после основной фичи, а не параллельная работа: она переиспользует
матчеры R-003, журнал R-008 и отчётность R-011.

**Обоснование.** SC-007 требует «не менее 10 ГБ» освобождения — это объём разовой
уборки, а не следствие удаления одной песни. Смешивать две разные операции с
разными протоколами утверждения в одной фиче — риск потерять и то, и другое.

**Альтернативы отклонены.**
- *Включить разовую уборку в основную фичу*: разные протоколы утверждения
  (FR-039/FR-040 против FR-027), разные триггеры, разные наборы; объединение
  размывает и делает откат невозможным.
- *Оставить near-match на усмотрение оператора*: FR-042 и SC-008 запрещают
  удалять их; near-match — это живые песни с отличающимся написанием.

## R-014. `tbl_songs_sync` на SERVER: потребителя нет

**Решение.** `tbl_songs_sync` — таблица-очередь на **SERVER** (пишется
`Utils.setSongToSyncRemoteTable` через прямое соединение `Connection.remote()`
или через `/changerecords`; миграции 28/43/50/52/53). Поиск потребителей
(grep `tbl_songs_sync` по `*.kt`) показывает: **читающих её кода нет** — строки
пишутся и больше никуда не переносятся.

Действие при удалении песни: удалить строку из `tbl_songs_sync` на SERVER
(решение владельца № 11) и из локальной `tbl_songs_sync`, если такая таблица и
строка там есть. Это гигиена, а не корректность: мёртвая очередь на результат
не влияет, но решение владельца фиксирует именно такое поведение.

**Обоснование.** FR-001 требует удаления «из рабочей и из серверной базы
данных». Таблица `tbl_songs_sync` формально находится в серверной базе и может
содержать копию удаляемой песни — оставлять её означало бы, что после
включения потребителя (которого сегодня нет) удалённая песня «ожила» бы.

**Альтернативы отклонены.**
- *Не трогать `tbl_songs_sync`*: расходится с решением владельца № 11.
- *Удалять её в фазе A (LOCAL-транзакция)*: она не относится к LOCAL-транзакции
  песни; удаление в фазе B (SERVER) логичнее.

**Открытый вопрос владельцу (В-07)**: подтвердить удаление строки из
`tbl_songs_sync` на SERVER, учитывая, что потребителя у таблицы нет.

## R-015. Защита от «ложного успеха»: `Song.deleteFromDb` возвращает `Unit`

**Решение.** Текущая реализация `Song.deleteFromDb(withFiles, sync)`
(`Song.kt:6898`) **не возвращает признака результата**: при отсутствии соединения
она пишет WARN и делает `return`; при исключении — WARN и `return`; при
`deletedRows <= 0` — WARN и `return`. Вызывающий (`ApiController.doDeleteSong`,
`ApiController.kt:4357`) ничего не проверяет и отвечает `200` с пустым телом.

Это и есть источник «ложного успеха» (SC-003): админ видит, что карточка закрылась,
а песня осталась в базе.

Изменение: `deleteFromDb` получает возвращаемый результат
(`deleted: Boolean` либо тип-объект с кодом причины), а эндпоинт возвращает
структурированный ответ. Публичный контракт эндпоинта меняется — это нужно
отразить в контракте API (FR-002, FR-003, SC-003).

**Обоснование.** ADR `local-0002` требует, чтобы методы, возвращающие данные,
пробрасывали исключения, а слои сервисов не глотали ошибки. Текущее поведение —
нарушение этого правила, зафиксированное в `knowledge/domains/catalog/components/song-entity.md`
(«Удаление песни: сначала строка, потом файлы», BR-106): там описано, что ошибка
DELETE не должна приводить к удалению файлов, — но не описано, что вызывающий
узнаёт об отказе.

**Альтернативы отклонены.**
- *Оставить `deleteFromDb` как есть, а эндпоинту проверить наличие строки после
  вызова*: лишний запрос и «гонка» (строку могли удалить другие); источник истины
  — результат самой операции.
- *Бросать исключение из `deleteFromDb`*: ломает три других вызывающих
  (`Utils.kt`, `MainController.kt`, `SyncTarget.kt`), которым «нет дела» до результата;
  лучше явный результат.
