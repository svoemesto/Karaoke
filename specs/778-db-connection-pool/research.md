# Research: Ограниченный пул соединений к БД (Phase 0)

**Feature**: `specs/778-db-connection-pool/spec.md` | **Дата**: 2026-11-15 | **План**: [plan.md](./plan.md)

Phase 0 закрывает все `NEEDS CLARIFICATION` из Technical Context. Ниже — решения с обоснованием и альтернативами.

## R1. Библиотека пула: HikariCP 6.3.3

**Decision**: `com.zaxxer:HikariCP` версии **6.3.3** — управляется BOM'ом Spring Boot 3.5.6 (`spring-boot-dependencies`, `hikaricp.version>6.3.3`; подтверждено чтением POM в gradle-кэше). Подключение — `implementation("com.zaxxer:HikariCP")` в `karaoke-app/build.gradle.kts` без явной версии (BOM подставит).

**Rationale**:
- HikariCP — стандарт де-факто для ограниченного пула JDBC; покрывает ровно то, что нужно: `maximumPoolSize` (потолок), `minimumIdle`, `idleTimeout`, `maxLifetime`, `keepaliveTime`, `connectionTimeout` (ожидание слота), проверка живости при выдаче, метрики через `HikariPoolMXBean`.
- Версия **не** выбирается вручную: BOM Spring Boot уже управляет HikariCP во всех модулях проекта → единая версия без расхождений.
- Доступность сборки проверена: `repo1.maven.org/maven2/com/zaxxer/HikariCP/6.3.3/HikariCP-6.3.3.pom` → **HTTP 200 за 0,33 с**. В локальном gradle-кэше HikariCP нет — зависимость докачается (в gradle-кэше машины есть 5.0.1 от чужого проекта, но версия из BOM важнее).

**Alternatives considered**:
- *Свой пул* (~300 строк): отклонён — пришлось бы самому реализовать keepalive, maxLifetime, idle-eviction, health-check и метрики; это источник багов в критичном коде.
- *HikariCP 5.0.1* (есть в кэше): отклонён — версия из BOM новее и уже проверена в этом проекте; ручной pin в обход BOM создал бы расхождение с остальными Spring-зависимостями.
- *Spring `DataSource` + `JdbcTemplate`*: отклонён — запрещено ADR-0001 (сырой JDBC) и сломало бы 284 места вызова.

## R2. Модель владения: handle + реестр владельцев

**Decision**: `ThreadLocal` потока хранит **`PooledHandle`** (обёртку типа `java.sql.Connection`), а не физический канал. Физическим каналом владеет `DbPool`. Handle'ы учитываются в `PoolOwnerRegistry` (`handle → поток-владелец`). Рейпер возвращает handle'ы мёртвых владельцев в пул.

**Rationale** (три требования сходятся на одном решении):
- FR-002: `close()` handle'а должен **вернуть** канал в пул, а не закрыть TCP. Если бы в `ThreadLocal` лежал сам канал HikariCP, `close()` освобождал бы аренду, уже отданную другому потоку → `SQLException` в чужом потоке.
- FR-005: `getConnection()` обязан вернуть `java.sql.Connection` — handle реализует этот интерфейс делегирующим прокси (по образцу существующего `wrapForBrokenDetection`, BR-274). Прикладной код не отличает handle от канала.
- FR-013: рейпер обязан отличать «хозяин мёртв» от «хозяин жив». Без отдельного объекта handle это неразличимо.

**Alternatives considered**:
- *Отказ от ThreadLocal* (Q1=B): отклонён решением владельца — 284 места вызова пришлось бы переписывать.
- *`WeakReference<Thread>`*: отклонён — реестр удерживает Thread → объект не соберётся; ссылка на мёртвый Thread удерживает его `ThreadLocalMap` → удерживает handle → цикл. Понадобился бы отдельный обход по GC.
- *`PhantomReference`/`Cleaner` на handle*: отклонён — handle удерживается ThreadLocal мёртвого потока, поэтому GC не гарантирован вовремя; тайминг возврата слота неконтролируем (нужен «за 5 минут»).

## R3. Детекция смерти владельца: `Thread.isAlive()`

**Decision**: `ownerThread.isAlive() == false` ⇒ владелец мёртв ⇒ handle возвращается в пул.

**Rationale**: `isAlive()` — прямой факт о состоянии потока (`false` навсегда после `Thread.exit()`), читается без синхронизации и без GC. Гонки нет: мёртвый поток не может использовать handle; если поток умрёт сразу после проверки `true`, рейпер не тронет handle, и следующий проход его увидит.

**Alternatives considered**: `WeakReference` (см. R2), `UncaughtExceptionHandler` (не срабатывает при штатном завершении), `ThreadGroup` (нет обхода мёртвых).

## R4. Контракт рейпера в пуловом режиме

**Decision**: В пуловом режиме рейпер **возвращает в пул** handle'ы мёртвых владельцев — **независимо от времени простоя**, без дополнительного ожидания `idle-ms` — и **не трогает** handle'ы живых (никогда, даже если простаивают). В режиме без пула рейпер сохраняет текущее поведение (закрытие каналов по простою `idle-ms`), и `idle-ms` остаётся параметром этого режима.

**Rationale**: Канал принадлежит пулу и может быть отдан другому потоку → закрывать его по простою нельзя (портит чужую работу). Текущая логика «закрыть чужое соединение безопасно» опиралась на то, что канал принадлежал **самому** потоку; в пуловой модели это свойство исчезает. При этом текущая защита от «поток жив, но канал протух» сохраняется: handle помечается осиротевшим, и при следующем обращении владельца `getConnection()` сам вернёт канал и возьмёт новый.

**Alternatives considered**: *Оставить рейпер как есть* — отклонён: закрытие канала, отданного другому потоку, даёт `SQLException` в чужом потоке (риск R3 в плане). *Возвращать по простою с ожиданием `idle-ms`* — отклонён: handle мёртвого владельца никто не трогает, ждать незачем; ожидание увеличило бы худший случай возврата до `idle-ms + interval-ms` (20 минут) и разошлось бы со SC-005 («не позднее 15 минут»). Без ожидания худший случай = один цикл рейпера = 5 минут — SC-005 выполнен с трёхкратным запасом.

## R5. Размеры пулов

**Decision** (см. § «Размеры пулов и конфигурация» плана): app LOCAL **128**, app SERVER 20, web LOCAL **96**, web SERVER 10.

**Rationale**: При сохранении ThreadLocal-контракта (Q1=A) размер пула ограничен **числом существующих handle'ов**, а не числом одновременных обращений. Handle'ов больше: поток Tomcat, однажды тронувший БД, держит handle до своей смерти. Верхняя граница считается **от конфигурации** (потолок), а не от наблюдаемого числа потоков: app — 50 (`server.tomcat.threads.max`) + 36 (`Schedulers.parallel()` = nproc) + 30 (HealthReport: `POOL_SIZE=10` + `POOL_SIZE_WAITING=20`, оба ходят в БД) + 4 (лейны очереди) + 4 (`karaoke-scheduler`) ≈ 124 → **128**; web — 50 (Tomcat max) + 36 (пул MessageBroker = nproc) + 4 служебных ≈ 90 → **96**. Суммарный потолок: app 148, web 106 — оба ниже `max_connections=300` (FR-010). Стабильное состояние при этом не меняется (~40–60 соединений): потолок — ограничитель, а не заказ.

**Расхождение с SC-001** (утверждённая спека: «не более 120 на процесс»): app даёт 148 → решение за владельцем (поднять SC-001 до 160 или уменьшить потолки). Спека не меняется.

**Alternatives considered**: *Размер = пик активности (31/22)* — отклонён: меньше числа одновременно занятых handle'ов → взаимоблокировка (риск R1/R2 плана). *Размер = сумма всех потоков (50/40)* — отклонён: в 2–3 раза больше необходимого; при `max_connections=300` сумма пулов app и web (134) съела бы половину лимита прод-БД.

## R6. Нижняя граница: 4 лейна очереди

**Decision**: Минимальный допустимый размер пула app ≥ 4 + запас (лейны `KaraokeProcess` с `thread_id` = −1, 0, 1, 2 держат соединение минутами на транскрибации/демуксе). Размер 56 перекрывает это с запасом; отдельный тест фиксирует правило.

**Rationale**: Если пул меньше числа одновременно занятых handle'ов, воркер не сможет взять handle и встанет — регрессия «очередь перестала обрабатывать задания» серьёзнее, чем эффект пула.

## R7. Ожидание слота: 5 секунд, затем отказ (Q3=A)

**Decision**: `connectionTimeout` пула = `KARAOKE_DB_POOL_ACQUIRE_TIMEOUT_MS` (по умолчанию 5000). При исчерпании — событие `DB-POOL-002` (`target`, `waiting`, `busy`) и быстрый отказ приложения; ожидающие потоки не копятся.

**Rationale**: Решение владельца Q3=A. HikariCP сам реализует ожидание слота с таймаутом — отдельный код ожидания не нужен. Различение «отказ приложения» и «отказ БД» — разные коды событий (`DB-POOL-002` против `DB-CONNECT-001`).

**Alternatives considered**: *Ожидание 30 с* (копится очередь ожидающих, растёт задержка), *отказ сразу* (больше 503 на пиках) — отклонены решением владельца.

## R8. Ленивое создание пула

**Decision**: `DbPool` создаётся **лениво** — при первом `borrow()`, не в конструкторе `KaraokeConnection` и не в конструкторе `Connection`. Конструктор `KaraokeConnection` хранит только ссылку на фабрику пула.

**Rationale**: 10 тестовых подмен `KaraokeConnection` в двух модулях переопределяют `getConnection()` — при создании пула в конструкторе они бы попытались открыть соединение к несуществующей БД (`jdbc:postgresql://fake:5432/karaoke`). Ленивое создание гарантирует: подмена → пул не создаётся → сетевых подключений в тестах нет (требование задания).

**Alternatives considered**: *Создавать пул в конструкторе `Connection`* — отклонён по той же причине; *создавать пул в Spring-компоненте и внедрять* — отклонён: `Connection.local()` — singleton-фабрика, вызываемая и из не-Spring кода.

## R9. Конфигурация: env → свойства Spring

**Decision**: Параметры читаются как `@Value("\${karaoke.db.pool.*}")` — в стиле существующего рейпера (`karaoke.db.reaper.interval-ms`, PR #129). Значения по умолчанию заданы в `application.yml` каждого модуля (app и web — разные: см. R5), env перекрывает. Новых секретов нет.

**Rationale**: Единый механизм с рейпером; дефолты различаются по модулям без дублирования кода; откат = переменная env + рестарт (FR-011).

**Alternatives considered**: *Только `System.getenv`* — отклонён: расходится с принятым в проекте стилем и не даёт перекрытия из `application.yml`; *жёсткие константы в коде* — отклонён: sizing обязан настраиваться без пересборки.

## R10. Откат: флаг + revert

**Decision**: `KARAOKE_DB_POOL_ENABLED=false` (по умолчанию) → `KaraokeConnection` работает как сегодня (прямой `DriverManager`, без пула и реестра). Второй уровень — `git revert` PR.

**Rationale**: FR-011 требует откат без пересборки. Дефолт `false` дополнительно даёт безопасное включение по шагам (§ «Порядок внедрения»): код приезжает в прод выключенным, включение — изменением env.

## R11. SSL/mTLS: URL передаётся как есть

**Decision**: `DbPool` получает тот же `url`, что лежит в `KaraokeConnection`, и кладёт его в `HikariConfig.jdbcUrl` **без разбора и пересборки**.

**Rationale**: `Connection.remote()` в app строит URL с `sslmode`/`sslcert`/`sslkey`/`sslrootcert` (`buildRemoteJdbcUrl`, спека 733, ADR local-0018). Любой разбор URL рискует потерять параметры mTLS → прод-БД недоступна. Тест на равенство URL до/после.

**Alternatives considered**: *Разбор URL и пересборка параметров* — отклонён: хрупко (экранирование путей к сертификатам, `&` в значениях); *отдельный набор параметров для пула* — отклонён: дублирование источника правды.

## R12. Обрыв туннеля и перезапуск БД (FR-016)

**Decision**: Опираемся на механизмы HikariCP (`keepaliveTime` 60 с, `maxLifetime` 30 мин, проверка живости при выдаче, `validationTimeout` 3 с) + существующий BR-274 self-healing (`markConnectionBroken` → следующий `getConnection()` переоткрывает). Новых требований к приложению пул не вносит.

**Rationale**: Пул не должен ломать self-healing (specs/236) и не должен требовать ручного вмешательства при обрыве туннеля.

## R13. Наблюдаемость: три события

**Decision**: `DB-POOL-001` (выдан handle) — не пишется (шум), только метрики; `DB-POOL-002` (исчерпание пула: `target`, `waiting`, `busy`) — warn; `DB-POOL-003` (долгое удержание handle со стеком вызовов) — warn. Существующие `DB-CONNECT-001`/`DB-REAP-001`/`DB-REAP-002` сохраняются.

**Rationale**: FR-008 требует отличить отказ приложения от отказа БД; FR-009 требует видеть место утечки. События — в существующем формате `AppLog.warn(category, code, event, fields, error)`, поэтому логируются тем же парсером, что и остальные.

**Alternatives considered**: *Писать каждое выдавание handle* — отклонён: сотни событий в минуту, шум.

## R14. Что НЕ меняется

**Decision**: 284 места вызова `getConnection()` в прикладном коде — **ноль правок**; `OneShotThread.kt` — без изменений; сигнатуры `Connection.local()/remote()` — прежние; публичные HTTP-контракты, схема БД, `max_connections` — прежние.

**Rationale**: Q1=A (решение владельца) + FR-005 + FR-014. Главная проверка FR-005 — компиляция обоих модулей без правок в прикладном коде.

## Итог Phase 0

Все `NEEDS CLARIFICATION` закрыты: версия библиотеки (R1), модель владения (R2), детекция смерти (R3), контракт рейпера (R4), sizing (R5, R6), таймаут ожидания (R7), ленивое создание (R8), конфигурация (R9), откат (R10), SSL (R11), обрывы (R12), наблюдаемость (R13), неизменяемое (R14).
