# Feature Specification: Бейдж непрочитанных новостей рядом с ссылкой «Новости» в шапке

**Feature Branch**: `257-header-news-unread-badge`
**Created**: 2026-08-27
**Status**: Draft
**Input**: User description: "Так как сейчас у нас в шапке сайта всегда есть «Новости» (кроме узких экранов), то при появлении новой новости не нужно показывать отдельную нотификационную иконку, а кол-во непрочитанных новостей отображать бейджем около ссылки «Новости» в шапке сайта. Если непрочитанных новостей 50 (бек отдаёт не больше 50), в этом случае на бейдже должно быть «50+». Спека текущая."

## Clarifications

### Session 2026-08-27

- Q: Как бейдж должен вести себя для пользователя, у которого в `localStorage` ещё нет `km_news_last_seen_id` (первый визит, новое устройство, cleared storage)? → A: B — тихо поднимать `lastSeenId` до актуального максимального id при первом монтировании (когда ключа в `localStorage` нет). Бейдж сразу скрыт, появляется только при реально новых новостях после визита.
- Q: Нужен ли бейджу `aria-label` и/или `aria-live` для скрин-ридеров? → A: B — `aria-label="N непрочитанных новостей"` фиксированный (без `aria-live`). Скрин-ридер перечитывает при изменении числа без шума от повторяющихся объявлений на каждом polling-е.

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Бейдж с числом непрочитанных новостей рядом с ссылкой «Новости» (Priority: P1)

Залогиненный посетитель публичного сайта, открывший любую страницу (кроме `/news`, `/player/*`, `/share/*`), видит в шапке сайта (правый слот `<AppHeader>` → `AuthStatusWidget`) ссылку «Новости» рядом с компактным бейджем. Бейдж показывает количество непрочитанных новостей — целое число (например, «3») или «50+», если непрочитанных 50 или больше (бэкенд `/api/public/news/since` отдаёт максимум 50 элементов в `items`, и `count = items.size`). Если непрочитанных нет — бейдж не отображается, ссылка «Новости» остаётся обычной ссылкой без визуальной пометки.

**Why this priority**: основная бизнес-цель фичи — заменить отдельную плавающую иконку-колокольчик `NewsBell.vue` (📰 в правом верхнем углу поверх контента) на компактный бейдж, встроенный в существующую навигацию шапки. Это устраняет визуальный шум (плавающая кнопка поверх страницы) и дублирование смысла (ссылка «Новости» + иконка-колокольчик одновременно говорят об одном и том же). Без этой истории фича теряет смысл.

**Independent Test**: открыть `/` (или любую страницу с `<AppHeader>`) под залогиненным пользователем, у которого в `tbl_news` есть ≥1 новая запись относительно `localStorage['km_news_last_seen_id']`. В DOM видна ссылка `<RouterLink to="/news">` с текстом «Новости» и **рядом** (внутри той же ссылки или рядом с ней, inline) — `<span>` с числом или «50+». Плавающий `NewsBell.vue` в DOM отсутствует (или его корневой элемент `display: none`).

**Acceptance Scenarios**:
1. **Given** залогиненный пользователь с 3 непрочитанными новостями (count = 3) на любой странице с шапкой, **When** он смотрит в правый слот `<AppHeader>`, **Then** рядом с текстом ссылки «Новости» виден бейдж с текстом «3».
2. **Given** залогиненный пользователь с 50 непрочитанными новостями (count = 50 — cap бэкенда), **When** он смотрит на бейдж, **Then** на бейдже текст «50+».
3. **Given** залогиненный пользователь с 1 непрочитанной новостью (count = 1), **When** он смотрит на бейдж, **Then** на бейдже текст «1» (без «+», поскольку бэкенд вернул меньше cap-а).
4. **Given** залогиненный пользователь с 0 непрочитанных (count = 0), **When** он смотрит в правый слот `<AppHeader>`, **Then** бейдж не виден; ссылка «Новости» выглядит как обычная ссылка без декоративного элемента.
5. **Given** анонимный пользователь (без `km_auth_token` в `localStorage`), **When** он открывает любую страницу, **Then** ссылка «Новости» видна, бейдж не виден (бэкенд `/since` для анонима возвращает `count = 0`, см. `PublicNewsController.kt:81-83`).
6. **Given** пользователь на странице `/news` (лента новостей), **When** он открывает её, **Then** бэкенд не опрашивается вхолостую (polling приостановлен, как сейчас в `NewsBell.vue`), а после открытия ленты `localStorage['km_news_last_seen_id']` поднимается до максимального id — на следующем цикле polling-а `count = 0` и бейдж исчезает.
7. **Given** пользователь на любой странице сайта с шапкой (например, `/`), **When** он кликает по ссылке «Новости» в `<RouterLink to="/news">`, **Then** бейдж в `<AppHeader>` **исчезает в ту же секунду** (до завершения HTTP-запроса `/api/public/news`), а не после перезагрузки страницы или ручного рефреша (FR-015).
8. **Given** пользователь на странице `/player/<id>` (full-screen плеер) или `/share/<token>` (гостевой доступ), **When** он смотрит на экран, **Then** бейдж не виден (нет шапки на этих страницах, либо шапка есть, но бейдж скрыт — решение на этапе plan).
9. **Given** пользователь на узком экране (≤ 700px), **When** он смотрит в шапку, **Then** ссылка «Новости» уже скрыта по существующему правилу `AuthStatusWidget.vue:85-91` — бейдж также не виден (он часть ссылки).

### User Story 2 — Отсутствие отдельной плавающей иконки новостей (Priority: P1)

На любой странице публичного сайта пользователь **не видит** плавающую круглую кнопку 📰 в правом верхнем углу экрана (`position: fixed; top: 64px; right: 74px;` — существующий `NewsBell.vue`). Вся информация о новых новостях теперь передаётся через бейдж в шапке (US1).

**Why this priority**: это явное требование пользователя — «при появлении новой новости не нужно показывать отдельную нотификационную иконку». Без выполнения US2 US1 становится дополнением к колокольчику, а не его заменой.

**Independent Test**: открыть `/` (или любую страницу) в DevTools, найти элемент с `class="nwb-wrap"` или `class="nwb-btn"` — не находится; найти `<RouterLink to="/news">` в `<AppHeader>` — находится; проверить наличие бейджа внутри или рядом с этим `<RouterLink>`.

**Acceptance Scenarios**:
1. **Given** любая страница сайта (включая `/`, `/zakroma`, `/filter`, `/song/<id>`, `/account`, `/chat`), **When** пользователь смотрит в правый верхний угол viewport, **Then** плавающая кнопка `📰` отсутствует.
2. **Given** компонент `NewsBell.vue`, **When** он удалён из `App.vue`, **Then** файл `karaoke-public/src/components/NewsBell.vue` либо удалён, либо помечен как `@deprecated` (решение на этапе plan).

### User Story 3 — Polling бэкенда остаётся, но без UI-иконки (Priority: P2)

Логика опроса бэкенда `/api/public/news/since?id=<lastSeenId>` каждые 45 секунд **сохраняется**, но больше не привязана к видимости плавающей иконки. Polling активен для залогиненных пользователей (для анонимов — отключён по соображениям защиты от HikariCP exhaustion, как сейчас). Результат polling-а (`count` и `items`) используется **только** для обновления бейджа в шапке (US1).

**Why this priority**: без polling-а бейдж не сможет обновляться в реальном времени — пользователь увидит устаревшее число. Это техническая основа US1.

**Independent Test**: открыть `/`, дождаться 45 сек, создать новую запись в `tbl_news` напрямую (или через админку) — бейдж в шапке обновится без перезагрузки страницы.

**Acceptance Scenarios**:
1. **Given** залогиненный пользователь на `/`, **When** проходит 45 секунд, **Then** отправляется `GET /api/public/news/since?id=<lastSeenId>` (см. `NewsBell.vue:121 poll()`).
2. **Given** анонимный пользователь на `/`, **When** проходит 45 секунд, **Then** polling не происходит (защита `NewsBell.vue:106` — defense in depth против 3.5 MB ответов на каждый poll).
3. **Given** пользователь на странице `/news` (или `/player`, `/share`), **When** проходит 45 секунд, **Then** polling приостановлен до ухода со страницы (аналог `NewsBell.vue:91-97`).
4. **Given** polling возвращает `count = N`, **When** результат получен, **Then** бейдж в `<AppHeader>` обновляется на «N» (или «50+» если N = 50).

### User Story 4 — Smart reset: мгновенный сброс на `/news` и авто-сброс через 10 сек на главной (Priority: P1)

Залогиненный пользователь видит бейдж непрочитанных новостей **только пока это реально непрочитанное**: если он перешёл на `/news` или находится на главной странице `/` (где показан блок «Последние новости» через `<LatestNewsSection>`), бейдж должен исчезнуть автоматически — пользователь уже «увидел» новости.

**Two distinct reset paths**:
1. **Immediate reset на `/news`**: как только пользователь переходит на страницу `/news` (через клик по ссылке «Новости» в шапке или прямой URL), бейдж `count` сразу сбрасывается в 0, `localStorage['km_news_last_seen_id']` обновляется до максимального `id` из последнего успешного polling-а. Реактивно `showBadge = false` → `<span class="km-news-badge">` исчезает из DOM в ту же секунду.
2. **Auto-read через 10 секунд на `/`**: если пользователь находится на главной странице и бейдж только что появился (`count` перешёл 0 → N), через 10 секунд таймер срабатывает и выполняет тот же сброс (`lastSeenId = max(items.id)`, `count = 0`). Семантика: пользователь уже видел последние новости в блоке `<LatestNewsSection>` на главной.

**Why this priority**: без smart reset бейдж продолжает «висеть» после того, как пользователь уже посмотрел новости — это раздражающий «ложный сигнал» (UX regression vs прежней плавающей иконки, которая автоматически исчезала после клика). Это второй из двух P1-сценариев пользовательской фичи.

**Independent Test**:
- Под залогиненным с `count = 3` на любой странице (например, `/`) → клик по ссылке «Новости» → бейдж исчезает **до** того, как `/news` полностью отрендерится (визуально мгновенно, без «моргания»).
- Под залогиненным с `count = 3` на `/` (главная с `<LatestNewsSection>`) → подождать 10 секунд (без клика, без навигации) → бейдж исчезает. В DevTools Network не должно быть новых polling-запросов, только таймер.

**Acceptance Scenarios**:
1. **Given** залогиненный пользователь с `count = 3` на странице `/` (или `/zakroma`, `/about`, любой не-`/news` странице), **When** он кликает по ссылке «Новости» в `<RouterLink to="/news">`, **Then** в `<AppHeader>` бейдж исчезает в течение < 100 мс (до того как `NewsView` начнёт HTTP-запрос `/api/public/news`). `localStorage['km_news_last_seen_id']` обновлён до `max(items.id)` последнего polling-а.
2. **Given** залогиненный пользователь на `/` с `count = 0`, **When** polling возвращает `count = 5`, **Then** бейдж появляется («5») и стартует 10-секундный таймер; через 10 сек таймер срабатывает, `localStorage['km_news_last_seen_id']` обновляется, `count = 0`, бейдж скрывается.
3. **Given** залогиненный пользователь на `/` с активным 10-секундным таймером (прошло 5 сек из 10), **When** пользователь навигирует на `/zakroma`, **Then** таймер отменяется (новости на `/zakroma` не показываются — `LatestNewsSection` только на `/`).
4. **Given** залогиненный пользователь на `/` с активным таймером (прошло 5 сек из 10), **When** polling возвращает новое `count = 7` (новые новости поверх существующих), **Then** таймер перезапускается на 10 сек с момента получения нового числа (т.е. суммарно через ~15 сек от первого появления).
5. **Given** залогиненный пользователь на `/` с активным таймером, **When** он навигирует на `/news`, **Then** вызывается immediate reset (FR-015), таймер отменяется (не нужен).
6. **Given** залогиненный пользователь на `/`, **When** происходит polling и возвращает `count = 0` (например, после reset), **Then** таймер не запускается (бейдж не появился → нечего «прочитывать»).
7. **Given** пользователь на `/news`, **When** он возвращается на `/`, **Then** immediate reset уже выполнен на `/news` → `count = 0` → таймер не запускается.

### Edge Cases

- **Backend недоступен** (5xx, таймаут, network error): polling ловит исключение в `try/catch` (как сейчас `NewsBell.vue:127-129`), бейдж остаётся в последнем известном состоянии. Счётчик не сбрасывается в 0 на ошибке — иначе пользователь подумает, что новостей нет.
- **Network tab без credentials**: для анонимов `/since` возвращает `{count: 0, items: []}` (`PublicNewsController.kt:81-83`) — бейдж скрыт, поведение эквивалентно «нет непрочитанных». Аноним не должен видеть промежуточных состояний загрузки.
- **`localStorage['km_news_last_seen_id']` отсутствует** (первый визит, cleared storage, новое устройство): composable `useNewsUnreadCount` при первом монтировании определяет отсутствие ключа, делает **один** дополнительный запрос `GET /api/public/news?page=0&size=1`, берёт `id` первого элемента и **записывает его в `localStorage['km_news_last_seen_id']`** до начала основного polling-а. После этого `count = 0`, бейдж скрыт. Семантика: «непрочитанные = то, что появилось после моего первого визита».
- **`localStorage` недоступен** (SSR / privacy mode): `lastSeenId()` бросит, polling не запустится, бейдж не появится. Это безопасный дефолт.
- **Страница редактора `/account/editor/<id>`**: использует `<AppHeader>` через slot-ы (см. spec 250, FR-011), `AuthStatusWidget` не рендерится — бейдж не виден. Поведение согласуется с текущим.
- **Очень узкий экран (≤ 700px)**: ссылка «Новости» скрыта (`AuthStatusWidget.vue:86-91`) — бейдж тоже не виден.
- **Premium badge «🪙» в `AuthStatusWidget`**: продолжает работать (LiveDoc 162). Бейдж новостей — **отдельный** элемент, не должен пересекаться визуально с премиум-бейджем имени пользователя.
- **Polling cache на бэкенде** (`PollingCache`, TTL 60 сек): каждый пользователь видит свои `count` по `lastSeenId`. Бейдж в шапке синхронизирован с этим — никаких рассинхронов между пользователями.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: В `AuthStatusWidget.vue` (правый слот `<AppHeader>`, файл `karaoke-public/src/components/AuthStatusWidget.vue`) ссылка `<RouterLink to="/news" class="km-auth-link km-auth-link-news">Новости</RouterLink>` MUST оставаться видимой для всех пользователей на ширине > 700px (без изменений по сравнению с текущим поведением).
- **FR-002**: Рядом с текстом ссылки «Новости» MUST отображаться бейдж с количеством непрочитанных новостей. Бейдж виден только если `count > 0` (любое положительное число, включая 50). При `count = 0` или для анонимов бейдж скрыт.
- **FR-003**: Логика бейджа (получение `count` через polling `/since`, сохранение в реактивном состоянии, вычисление текста «N» или «50+») MUST быть вынесена в переиспользуемый composable (например, `useNewsUnreadCount`), который вызывается из `AuthStatusWidget.vue`. Это позволяет переиспользовать логику и упрощает тестирование.
- **FR-004**: Текст бейджа MUST формироваться по правилу:
  - `count === 0` → бейдж скрыт;
  - `0 < count < 50` → бейдж показывает число `count` (например, «1», «3», «49»);
  - `count >= 50` → бейдж показывает «50+».
- **FR-005**: Polling бэкенда MUST сохранять существующее поведение из `NewsBell.vue`:
  - интервал 45 секунд (`POLL_INTERVAL_MS = 45000`);
  - приостановка на скрытых маршрутах `/news`, `/player/*`, `/share/*` и при `route.query.share === '1'`;
  - отключение для анонимов (нет `localStorage.getItem('km_auth_token')`);
  - обработка ошибок через `try/catch` (без сброса `count` в 0 на исключении).
- **FR-006**: Источник истины для `lastSeenId` — `localStorage['km_news_last_seen_id']`. Записывается в **3 местах**: (a) `useNewsUnreadCount` при silent reset для нового пользователя (FR-013); (b) `useNewsUnreadCount` при immediate reset на `/news` и при auto-read на `/` (FR-015/FR-016, US4); (c) `NewsView.markAllSeen()` (existing) после загрузки данных — это по-прежнему нужно как «источник истины №2» на случай если composable ещё не успел сделать reset (например, race при первой загрузке). При первом монтировании composable читает текущее значение и использует его для первого запроса `/since`.
- **FR-007**: Компонент `NewsBell.vue` MUST быть удалён из `App.vue` (`<NewsBell />` убирается из template, `import NewsBell from './components/NewsBell.vue'` — из `<script>`, упоминание в `components: { ... }` — оттуда же). Сам файл `karaoke-public/src/components/NewsBell.vue` либо удаляется, либо рефакторится так, чтобы экспортировать только логику (например, переименовывается в `useNewsUnreadCount.js` — решение на этапе plan).
- **FR-008**: Авто-исчезающий тост (popup) `NewsBell.vue:142-147 showToast()` тоже удаляется как часть «отдельной нотификационной иконки» — пользователь явно сказал, что **никакая отдельная нотификация** не нужна, только бейдж в шапке. Поведение подтверждается US2 и согласуется с общим направлением «subtle UX, без overlays».
- **FR-009**: Бейдж MUST иметь визуальный стиль, согласованный с существующими бейджами в `AuthStatusWidget`:
  - цвет фона `#e05555` (как `NewsBell.vue:213`) или эквивалент `--km-accent-danger`;
  - белый текст;
  - скруглённые углы (`border-radius: 10px`), маленький шрифт (~`0.68rem`);
  - padding `0 0.35em`, вертикально выравнен по `text-top` относительно текста ссылки.
  Стиль описывается в `<style scoped>` `AuthStatusWidget.vue` (или отдельном CSS-модуле — решение на этапе plan), без дублирования.
- **FR-010**: На страницах editor (`/account/editor`, `/account/editor/<id>`) `AuthStatusWidget` не рендерится (см. spec 250, FR-011/FR-014/FR-015) — бейдж не виден автоматически. Никаких дополнительных проверок не требуется.
- **FR-011**: На узких экранах (≤ 700px) ссылка «Новости» уже скрыта через `AuthStatusWidget.vue:86-91`. Бейдж MUST находиться **внутри** этой ссылки (или в её непосредственном визуальном соседстве, не отдельно), чтобы автоматически наследовать правило `display: none`.
- **FR-012**: Live-логика `isPremium` (LiveDoc 162 — бейдж 🪙) MUST продолжать работать без изменений — composable `usePremiumLiveSync` независим от нового бейджа новостей.
- **FR-013** (clarified 2026-08-27): composable `useNewsUnreadCount` MUST при первом монтировании (когда `localStorage.getItem('km_news_last_seen_id')` возвращает `null`) выполнить **один** запрос `GET /api/public/news?page=0&size=1`, извлечь `id` первого элемента массива `items`, и **синхронно записать его в `localStorage['km_news_last_seen_id']`** до начала основного polling-а `/since`. После этого `count = 0` (бейдж скрыт). Если запрос `?page=0&size=1` падает (network error, 5xx), composable MUST запустить основной polling без изменения `localStorage` — это безопасно, т.к. вернётся поведение текущего `NewsBell` («50+» до первого открытия `/news`), что соответствует A-001 / fallback семантике.
- **FR-014** (clarified 2026-08-27): бейдж MUST иметь атрибут `aria-label="N непрочитанных новостей"` (фиксированный, без `aria-live`), где `N` — текущее число (например, «3 непрочитанных новости», «50 непрочитанных новостей», «50+ непрочитанных новостей»). Причина: фиксированный `aria-label` описывает состояние, а стандартное поведение ARIA автоматически перечитывает контент при его изменении (без шумных `aria-live` объявлений на каждом 45-сек polling-е, когда число могло не измениться). Склонение «новость / новости / новостей» по числу — обязательно.
- **FR-015** (US4, добавлено после фидбэка 2026-08-27): когда пользователь переходит на страницу `/news` (route name `news`), composable `useNewsUnreadCount` MUST **в ту же секунду** (в watcher `useRoute()` → `applyRouteState()`) выполнить immediate reset: `count.value = 0`, `localStorage['km_news_last_seen_id'] = String(Math.max(...items.map(i => i.id)))`. Это происходит **до** того как `NewsView.vue` начнёт HTTP-запрос `/api/public/news` — пользователь видит мгновенное исчезновение бейджа (без «моргания»). Если `items` пуст (например, на самом первом визите до первого успешного polling-а) — fallback: только `count.value = 0` (без записи в localStorage), `lastSeenId` обновит `NewsView.markAllSeen()` после загрузки данных.
- **FR-016** (US4, добавлено после фидбэка 2026-08-27): когда `count` переходит 0 → >0 и пользователь находится на странице с видимыми последними новостями (сейчас это только `/` — `route.path === '/'`, где `<LatestNewsSection>` рендерится), composable MUST запустить `setTimeout(performAutoRead, 10_000)`. При срабатывании таймера выполнить тот же reset что в FR-015 (записать `lastSeenId`, `count = 0`). Таймер MUST отменяться: при навигации со страницы с новостями; при `count → 0` (новости пропали); при навигации на `/news` (выполняется immediate reset вместо auto-read). Если polling возвращает новое `count > предыдущего` пока таймер активен — таймер перезапускается на полные 10 секунд.

### Key Entities

- **`useNewsUnreadCount` composable**: новая переиспользуемая функция (предположительно в `karaoke-public/src/composables/useNewsUnreadCount.js`), возвращает реактивный `count` (или `{ count, items }`). Инкапсулирует: чтение `lastSeenId` из `localStorage`, polling `/api/public/news/since` каждые 45 сек, приостановку на скрытых маршрутах и для анонимов, вычисление текста бейджа «N» / «50+» / `''`.
- **Бейдж «Новости»**: inline DOM-элемент (`<span class="km-news-badge">{{ badgeText }}</span>`) внутри `<RouterLink to="/news">` в `AuthStatusWidget.vue`. Текст: «N» (1..49) или «50+».
- **`lastSeenId`**: число в `localStorage['km_news_last_seen_id']`, обновляется существующим кодом в `NewsView.vue`. Используется как параметр `id` для `/since`.

## Assumptions

- **A-001**: Бэкенд `/api/public/news/since` отдаёт `count = items.size` (см. `PublicNewsController.kt:89`). Надёжный cap = 50 для залогиненных (`News.loadPublishedSince(WORKING_DATABASE, id, limit = 50)`). Анонимам возвращается `count = 0`. Эти ограничения **не меняются** в рамках данной фичи.
- **A-002**: Текст «50+» — точная формулировка по требованию пользователя («Если непрочитанных новостей 50... в этом случае на бейдже должно быть '50+'»). Альтернативы («50…», «99+», «50+» с пробелом) не рассматриваются.
- **A-003**: Авто-исчезающий тост (`NewsBell.vue showToast`) удаляется вместе с плавающей иконкой (FR-008). Пользователь явно сказал «не нужно показывать отдельную нотификационную иконку» — тост является частью того же «отдельного notification»-паттерна и не вписывается в новую концепцию «только inline бейдж». Если в будущем потребуется активное уведомление о конкретной новости — это отдельная фича с подтверждением пользователя.
- **A-004**: Edge case «первый визит пользователя → lastSeenId = 0 → бейдж «50+» сразу» решается **тихим сбросом**: при первом монтировании composable-а (когда `localStorage` ключа нет) делается один доп. запрос `/api/public/news?page=0&size=1`, берётся `id` первого элемента, записывается в `localStorage['km_news_last_seen_id']`. Бейдж сразу скрыт (`count = 0`). Решение принято в Clarifications Q1 (2026-08-27).
- **A-005**: Polling cache на бэкенде (`PollingCache`, TTL 60 сек) **не меняется** — каждый пользователь получает свой `count` по `lastSeenId`. Никаких оптимизаций (WebSocket / SSE) в рамках этой фичи не делается.
- **A-006**: Страница `/player/<id>`, `/share/<token>`, `/premium/return` не имеют `<AppHeader>` (см. spec 250, Edge Cases), поэтому бейдж там не виден. Никаких дополнительных правил скрытия не требуется.
- **A-007**: Существующий `AuthStatusWidget.vue` остаётся компонентом для бейджа (а не выносится в отдельный `<NewsBadge>`). Это минимизирует изменения и сохраняет визуальную группировку (ссылка «Новости» + бейдж — одна семантическая единица).
- **A-008**: Архитектура `composable` (Vue 3 Composition API) вместо миксина — соответствует существующему стилю проекта (см. `useAuth`, `useCart`, `usePremiumLiveSync`).
