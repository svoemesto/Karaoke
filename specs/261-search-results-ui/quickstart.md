# Quickstart — ручная валидация 261-search-results-ui

Документ описывает **ручные сценарии проверки** функциональности после применения изменений. Это не автоматизированные тесты — в проекте CI без тестов (см. AGENTS.md, раздел «Тесты»); проверка делается пользователем на production-like окружении (см. DEVELOPMENT.md).

## Предусловия

1. Среда развёрнута: `karaoke-web`, `karaoke-public`, Postgres, MinIO, контейнеры в обычном режиме (см. `deploy/do.sh`).
2. Бэкенд `karaoke-web` пересобран (`gradle bootJar`) и задеплоен с новым `SongPublicDto` (3 новых поля).
3. Фронт `karaoke-public` пересобран (`npm run build`) и задеплоен с обновлённой строкой поиска.
4. Браузер без блокировщиков картинок и JS. Готовы тестовые аккаунты:
   - **Гость** (без логина).
   - **Зарегистрированный бесплатный** (effective_premium = false).
   - **Премиум-подписчик** (effective_premium = true).
5. Тестовые запросы должны возвращать:
   - Песня **«в эфире»** (`freelyAvailableNow=true`, например «Кино / Звезда по имени Солнце» с активным окном бесплатного доступа).
   - Песня **готовая, не в эфире** (`contentReady=true`, `freelyAvailableNow=false`, например песня за рамками окна).
   - Песня **неготовая** (`contentReady=false`, у новой песни до финализации пайплайна).

## Сценарий A — Иконка плеера в поиске (баг-фикс)

**Цель**: проверить SC-001 (зелёная для «в эфире»), SC-002 (серая для неготовых).

1. Открыть `/search` без логина. Ввести запрос, возвращающий ≥3 песен, из которых:
   - ≥2 «в эфире» (`freelyAvailableNow=true`);
   - ≥1 готовая не-в-эфире;
   - (опц.) ≥1 неготовая.
2. Для каждой строки посмотреть иконку плеера:
   - **В эфире** → **зелёная** (клик открывает плеер в новой вкладке).
   - **Готовая не в эфире** → **золотая** (клик открывает модалку подписки).
   - **Неготовая** → **серая disabled** (клик не имеет эффекта).
3. Кликнуть по зелёной иконке одной из песен «в эфире» — откроется `/player/<id>` именно этой песни, плеер загрузится.
4. (Если есть неготовая песня) Убедиться, что серая иконка **никак не реагирует** на клик.

**Проходит, если**: все «в эфире» — зелёные, не в эфире — золотые, неготовые — серые; клики корректные.

**Проваливается, если**: хотя бы одна «в эфире» — серая (тогда `SongPublicDto.contentReady` не пришёл или не мапится — смотри логи `karaoke-web`).

## Сценарий B — Визуальное соответствие PlaylistEditView

**Цель**: проверить SC-003 (структура строки идентична плейлисту).

1. Открыть `/search` с непустыми результатами. Сделать скриншот строки одной песни.
2. Авторизоваться бесплатным аккаунтом. Открыть `/account/playlists/<favorites-id>` (это плейлист «Избранное»). Сделать скриншот строки **той же песни** (найти в списке).
3. Сравнить скриншоты попиксельно:
   - **Слева** — одинаковый чёрный блок с превью альбома (квадрат 48×48) и превью автора (горизонтальная карточка 120×48, аспект 5:2). Плейсхолдеры «♪»/«👤» при отсутствии URL — одинаковые.
   - **Центр** — название крупным шрифтом; под ним подпись «Автор - год, альбом» (или с разделителями « - » / «, »).
   - **Справа** — набор иконок (плеер, премиум/корзина/корзина, избранное, плейлисты — порядок и стиль одинаковые).

**Проходит, если**: визуальное соответствие «попиксельное» (с поправкой на то, что в плейлисте могут быть drag-handle и mute-кнопки, которых в поиске нет — это контракт спеки 259 US3).

## Сценарий C — Кликабельные ссылки (FR-007, FR-008)

**Цель**: проверить SC-005 (ссылки как в спеке 259).

1. Из `/search` кликнуть по **названию песни** (НЕ по иконке плеера) — открывается `/song?id=<id>` именно этой песни.
2. На странице песни проверить **back-link** в шапке — должен вести на `/zakroma/<authorId>` этого автора (контракт спеки 259 FR-A8).
3. Вернуться в поиск. Кликнуть по **имени автора** — открывается `/zakroma/<authorId>` этого автора (а не другой автор, не общий каталог).
4. Если в БД нет автора по имени (Edge Case) — клик НЕ открывает ничего, имя показывается как обычный текст.
5. Протестировать открытие в новой вкладке: Ctrl+клик (Windows/Linux) или Cmd+клик (macOS) по названию — должна открыться новая вкладка с `/song?id=<id>`.

**Проходит, если**: ссылки работают идентично спеке 259 (это критическая проверка — рассинхронизация с этой спекой ломает базовую навигацию).

## Сценарий D — Регресс: премиум-флоу

**Цель**: проверить SC-004 (`showCoin`, `showCartIcon`, `onSubscribeClick` без регрессий).

1. Открыть `/search` бесплатным аккаунтом. Найти в результатах **премиум-песню** (например, ещё не в эфире `freelyAvailableNow=false`, но `songSubscriptionAvailable=true`).
2. Убедиться, что в её строке видна **монета** (`PremiumIcon`, золотая/серая по готовности).
3. Убедиться, что в строке есть иконка **«В корзину»** (`CartIcon`).
4. Кликнуть по **золотой иконке плеера** — должна открыться модалка оформления подписки (`SongSubscriptionModal`).
5. Закрыть модалку, кликнуть по иконке «В корзину» — добавляется в корзину (или открывается корзина).

**Проходит, если**: все три действия повторяют до-переделочное поведение.

## Сценарий E — Регресс: префилл из URL + состояние «Ничего не найдено»

**Цель**: проверить SC-004 (префилл из query + пустой результат).

1. Открыть `/search?author=Кино&songName=Звезда` — форма должна быть предзаполнена, поиск стартует автоматически.
2. Ввести несуществующий запрос (например, `xxxveryunlikelyqueryxxx`).
3. Дождаться загрузки. Убедиться, что отрисован блок «Ничего не найдено».

**Проходит, если**: обе ситуации идентичны до-переделочному поведению.

## Сценарий F — Мобильный вьюпорт (Clarification Q1)

**Цель**: подтвердить SC-003 на мобильном (новая разметка должна работать на обоих вьюпортах).

1. С помощью DevTools (или физического устройства) переключить viewport на 375×812 (iPhone 12).
2. Открыть `/search` с результатами. Убедиться, что строки показываются как «горизонтальные карточки» — те же, что на десктопе, только картинки/info/иконки выстраиваются в доступную ширину.
3. Проверить, что нет «разлома»: картинки 48×48 не должны переноситься, текст обрезается ellipsis-ом.
4. Вернуться на десктоп-размер. Убедиться, что строки возвращаются к обычному виду.

**Проходит, если**: на мобильном та же структура, что на десктопе (отличия — только в пропорциях за счёт адаптивного flex).

## Сценарий G — Дизайн «modern» (FR/Edge Cases)

**Цель**: проверить, что цветовая схема использует CSS-переменные.

1. В localStorage браузера поставить `km_theme=modern` (или воспользоваться UI-переключателем, если он на странице). Перезагрузить `/search`.
2. Все цвета строки должны соответствовать modern-дизайну (фон, рамки, акценты — из `--km-*`).
3. Переключить обратно на `classic`. Цвета корректно перерисовываются.

**Проходит, если**: никаких хардкодов цветов в новой разметке.

## Сценарий H — Производительность (SC-007)

**Цель**: убедиться, что 200 песен рендерятся без видимого лага.

1. Создать тестово поисковый запрос, возвращающий 200+ песен (например, `text=лю` или короткую подстроку).
2. Замерить (субъективно): появление первой строки, скролл от начала до конца — оба должны быть плавными (без «задумчивых» пауз более ~200мс на пользовательское действие).
3. DevTools → Network → проверить, что все превью НЕ грузятся сразу для всех 200 песен (только видимая часть) — это работает за счёт `loading="lazy"`.

**Проходит, если**: страница интерактивна, скролл плавный, превью подгружаются по мере видимости.

## Сценарий I — Проверка backend diff (SC-006)

**Цель**: убедиться, что правки бэка минимальны.

1. `git diff karaoke-web/src/main/kotlin` — единственный изменённый файл: `dto/SongPublicDto.kt` (3 новых поля + маппинг в `fromSong`).
2. `git diff karaoke-web/src/main/kotlin/com/svoemesto/karaokeweb/controllers/PublicApiController.kt` — изменения только внутри метода `songs(...)` (batch-резолв альбомов/авторов), остальной контроллер не тронут.
3. `git diff` НЕ должен показывать изменений в `ZakromaPublicDto.kt`, `SitePlaylistItemDto.kt`, `AlbumDTO.kt`, миграциях БД, `Application.kt`, `application.yml`.

**Проходит, если**: diff соответствует SC-006 «только `SongPublicDto.kt` + batch-lookup в `songs()`».
