# Research: Апрув задания редактора завершается ошибкой запроса, новость не появляется

**Feature**: [spec.md](./spec.md) | **Date**: 2026-07-30

Спецификация (`Assumptions`) сознательно оставила диагностику точной
технической причины на этап планирования. Ниже — результат этой
диагностики, проведённой чтением текущего кода (`SongEditorController.kt`,
`Utils.kt`, `KaraokeDbTable.kt`, `SongReleaseAnnouncementService.kt`,
`KaraokeConnection.kt`/`Connection.kt`, `ReviewModal.vue`/`store.js`/`utils.js`)
и сопоставления с логами инцидента из `spec.md` («Контекст»).

## 1. Что именно происходит при клике «Одобрить и премиить»

**Decision**: Диагноз — цепочка синхронных сетевых операций внутри одного
HTTP-запроса `POST /api/songeditor/approve`, последний шаг которой не
защищён от исключений.

**Rationale**: Пошагово сопоставляя лог инцидента с кодом
`SongEditorController.approve()` (`karaoke-app/.../controllers/SongEditorController.kt:312-408`):

1. `Устанавливаем связь с базой данный LOCAL/SERVER...` + `Запрашиваем
   таблицу хэшей ... (Настройки песен)` + `Получено хешей: 1` (дважды) +
   `Изменяем запись в tbl_songs: id=23199...` + `Запрос на сервер на
   изменение.` + `Created: 0, Updated: 1, Deleted: 0` — это ПОЛНОСТЬЮ лог
   вызова `updateRemoteSongFromLocalDatabase(settings.id)`
   (`Utils.kt:566` → `updateDatabases` → `collectSyncOps`, с `whereText =
   "WHERE id = 23199"`, отсюда «записей: 1» на обоих концах). Строка
   `Created: X, Updated: Y, Deleted: Z` — это НЕ отдельный лог `karaoke-app`,
   а `println(response.body())` (`Utils.kt`, блок `listToUpdate.isNotEmpty()`)
   — эхо HTTP-ответа `/changerecords`, тело которого формирует
   `karaoke-web`'s `MainController.kt:313`. Этот шаг завершается
   **успешно** — песня реально обновлена и на LOCAL, и на SERVER.
2. `Запрос хешей...` / `Получено хешей: 15243` (без окружающих строк
   `Запрашиваем таблицу хэшей из базы данных X (target)...`) — это
   `Song.listHashes(database, whereText)` (`Song.kt:6934-6972`), вызванный
   **напрямую**, в обход `SyncTarget`-обёртки. Единственный вызывающий с
   такой сигнатурой без id-фильтра —
   `SongReleaseAnnouncementService.forEachNewlyReadyCandidate` (
   `SongReleaseAnnouncementService.kt:39-41`,
   `whereText = "WHERE id_status >= 6"`) — то есть это
   `SongEditorController.approve()`, строка 384,
   `SongReleaseAnnouncementService.checkAndAnnounce(Connection.remote(), ...)`,
   вызванная потому, что `pushResult.updated` из шага 1 непусто (условие
   `specs/092-fix-auto-news-triggers`, User Story 2 — «мгновенный» триггер
   новости при апруве). 15243 — размер кандидатного множества «готовых»
   песен на проде (`id_status >= 6`), а НЕ размер всей `tbl_songs`.
3. Дальше в предоставленном логе — тишина, затем в интерфейсе появляется
   «Ошибка запроса». Повторный клик: тот же запрос, но БЕЗ шага 1
   (`settings.idStatus < 6` уже `false` → локальный `saveToDb()` не
   вызывается; push находит запись уже синхронизированной → `listCreate` +
   `listUpdate` + `listDelete` = 0 → «Изменяем запись...» не печатается) и
   БЕЗ шага 2 (`pushResult.updated`/`created` пусты → условие
   `checkAndAnnounce` не выполняется). Модалка при этом просто закрывается.

Это расхождение логов между первой и второй попыткой само по себе не
объясняется случайностью — оно детерминированно следует из кода при
единственном предположении: **на первой попытке `approve()` не дошёл до
конца успешно** (иначе `aRead.adminStatus` уже был бы `APPROVED`, и вторая
попытка вернула бы «уже одобрено», а не тихо переиграла бы всю логику
заново без реального эффекта).

## 2. Почему первая попытка не долетает до конца успешно

**Decision**: Наиболее вероятная точка отказа — `aRead.save()`
(`SongEditorController.kt:397`), единственная операция записи в
`approve()`, не защищённая try/catch, выполняющаяся ПОСЛЕ уже трёх
использований `Connection.remote()` в рамках одного запроса.

**Rationale**:

- **Три отдельных подключения к прод-БД за один запрос.**
  `Connection.remote()` (`Connection.kt:89-95`) при каждом вызове создаёт
  **новый объект** `Connection`. `KaraokeConnection.threadLocalConnection`
  (`KaraokeConnection.kt:30`) — это `ThreadLocal`-поле ЭКЗЕМПЛЯРА, а не
  статическое/глобальное — специально сделано так в
  `specs/087-fix-shared-db-connection`, чтобы разные ПОТОКИ не делили одно
  соединение. Но это не защищает от повторного создания РАЗНЫХ инстансов
  `Connection` в ОДНОМ потоке: каждый `Connection.remote()` — это
  собственный, пустой `threadLocalConnection`, то есть **новое физическое
  TCP+JDBC-подключение** к `79.174.95.69:8832`. В рамках одного
  `approve()`-запроса (когда `target == "remote"`, что типично — реальные
  задания редактора живут на прод-БД, см. `SongAssignmentDraft.kt`
  комментарий) `Connection.remote()` вызывается МИНИМУМ трижды: (а) `readDb`
  на входе в `approve()`; (б) внутри `updateRemoteSongFromLocalDatabase` →
  `updateDatabases(toDatabase = Connection.remote())`; (в) внутри
  `checkAndAnnounce(Connection.remote(), ...)`. Соединение (а) переживает
  до конца запроса (используется повторно для `aRead.save()`), но (б) и (в)
  — одноразовые, открываются и остаются висеть до сборки мусора (никто их
  явно не закрывает в этом пути — `finally` в `approve()` закрывает только
  `readDb`).
- **`aRead.save()` не защищён.** Внешний `try { return withDb("local")
  {...} } finally {...}` в `approve()` — БЕЗ `catch`. Внутри блока только
  push+анонс (строки 371-390) обёрнуты в собственный `try/catch`; запись
  статуса задания (`aRead.adminStatus = ADMIN_APPROVED; ...; aRead.save()`,
  строки 393-397) — нет. Внутри `KaraokeDbTable.save()`
  (`KaraokeDbTable.kt:93-199`) вызов `ps.executeUpdate()` защищён
  try/catch (строки 157-162), но `connection.prepareStatement(sql)`
  (строка 132) и предшествующий `loadById(...)` (строка 99-108, тоже открывает
  соединение через `database.getConnection()`) — НЕТ. Если физическое
  соединение `readDb` протухло/сброшено сетью к моменту, когда до него
  доходит очередь (после уже двух других сетевых round-trip'ов к тому же
  серверу и тяжёлого 15k-скана из шага 2), `SQLException` из
  `prepareStatement`/`loadById` уйдёт необработанным из `KaraokeDbTable.save()`
  → из `aRead.save()` → из `approve()` → Spring вернёт HTTP 5xx без тела
  вида `{"ok": ...}`.
- **Фронтенд не различает «мы не получили ответ» от «получили ok:false».**
  `promisedXMLHttpRequest` (`webvue3/src/lib/utils.js:15-37`) НЕ
  устанавливает `xhr.timeout` — клиентского тайм-аута нет; `reject`
  происходит только при `xhr.onerror` (сетевая ошибка/обрыв соединения) или
  при HTTP-статусе вне `[200,300)` (`xhr.onload`, `status >= 400` →
  `reject(xhr.statusText)`). `ReviewModal.doApprove()`
  (`ReviewModal.vue:281-298`) в `catch(e)` всегда пишет одно и то же —
  `'Ошибка запроса'`, не различая «сеть оборвалась» и «сервер ответил
  500» — оба случая выглядят для администратора одинаково. Это
  ПОДТВЕРЖДАЕТ (не просто согласуется с) гипотезу необработанного
  исключения на бэкенде: `{"ok": false, "error": "..."}` (штатный путь
  ошибки в `approve()`, например `assignment_not_found`/`draft_not_found`/
  `bad_markers`) обрабатывается ОТДЕЛЬНОЙ веткой (`res.ok` falsy →
  `'Не удалось одобрить: ' + res.error`), а не `catch(e)`. Раз
  администратор увидел именно «Ошибка запроса», а не «Не удалось
  одобрить: ...» — запрос либо не получил HTTP-ответа вовсе, либо получил
  ответ вне `[200,300)` без корректного JSON-тела, что соответствует
  необработанному исключению/500, а не штатному `ok:false`.

**Alternatives considered**:
- *Клиентский/прокси тайм-аут без ошибки на бэкенде.* Отвергнуто как
  ОСНОВНАЯ причина (хотя не исключено как второстепенный фактор) —
  `promisedXMLHttpRequest` не задаёт `xhr.timeout`, а без явного тайм-аута
  на клиенте единственный правдоподобный источник обрыва — сам
  сервер/прокси (nginx) или реальная сетевая ошибка; в обоих случаях
  первопричина всё равно в бэкенде (запрос идёт по нескольким медленным
  сетевым JDBC-подключениям подряд, что и создаёт окно для обрыва).
  Независимо от точного механизма обрыва, FR-005 требует, чтобы `approve()`
  ВСЕГДА возвращал типизированный результат — это снимает необходимость
  точно диагностировать, кто именно оборвал соединение.
- *Ошибка в самом `checkAndAnnounce()`.* Отвергнуто как причина именно
  HTTP-ошибки — `checkAndAnnounce()` оборачивает свою логику в собственный
  `try/catch` (`SongReleaseAnnouncementService.kt:101-119`) и ДОПОЛНИТЕЛЬНО
  вызывается из `approve()` под ещё одним `try/catch` (строки 372-390) —
  исключения оттуда не могут дойти до клиента как 500. Но это же
  объясняет, почему новость не появилась: если `Song.listHashes(Connection.remote(),
  "WHERE id_status >= 6")` внутри `checkAndAnnounce()` вернул `null` (сбой
  ЭТОГО отдельного соединения — см. `Song.kt:6941-6945`,
  `database.getConnection() == null` → `return null`), `forEachNewlyReadyCandidate`
  подставляет `?: emptyList()` (`SongReleaseAnnouncementService.kt:40`) и
  молча не находит кандидатов — ни ошибки, ни новости, без единого
  сообщения об этом где-либо. Правдоподобно, что то же нестабильное
  сетевое подключение к прод-серверу, которое (предположительно) сломало
  финальный `aRead.save()`, точно так же могло тихо «занулить» и этот шаг.

## 3. Устаревшая документация `checkAndAnnounce` (сопутствующая находка)

**Decision**: KDoc-комментарий объекта `SongReleaseAnnouncementService`
(`SongReleaseAnnouncementService.kt:8-12`) утверждает: «Единственный
вызывающий — `karaoke-web` `MainController.doChangeRecords` (PROD-only...)».
Это неверно уже сейчас — `SongEditorController.approve()`
(`karaoke-app`, admin-машина) вызывает `checkAndAnnounce()` напрямую
(строка 384), и это ЕДИНСТВЕННЫЙ вызывающий, реально сработавший в
инциденте. Комментарий не был обновлён при добавлении этого вызова в
`specs/092-fix-auto-news-triggers`.

**Rationale**: Формально это нарушение Конституции (принцип VI, FR-006 —
KDoc должен соответствовать действительности) и косвенно FR-009 (per-feature
документ `dual-db-sync.md` уже обновлялся в 092, но неточность в самом коде
осталась). Не является причиной бага, но должно быть исправлено в этом же
PR заодно с правкой логики этой функции (Constitution Check, принцип VI).

**Alternatives considered**: Оставить как есть и завести отдельный тикет —
отклонено: правка тривиальна (один комментарий) и находится в файле,
который PR и так меняет.

## 4. Какие правки нужны, чтобы соответствовать FR-001…FR-006 (spec.md)

**Decision**: Минимальный набор направлений (детали — в `data-model.md` и
`contracts/approve-endpoint.md`, конкретные шаги — в будущем `tasks.md`):

1. `SongEditorController.approve()` — обернуть шаг «пометить задание
   одобренным» (`aRead.save()`) в try/catch, аналогично уже существующему
   паттерну вокруг push/анонса, и построить typed-результат
   (`success` / `already_approved` / `error`), который ВСЕГДА уходит клиенту
   как валидный JSON с HTTP 200 — вместо риска необработанного исключения.
   При повторном вызове для уже одобренного задания — вернуть
   `already_approved`, не повторяя `saveToDb()`/push/анонс (FR-002, FR-006).
2. Не открывать три отдельных `Connection.remote()` за один запрос — где
   возможно, переиспользовать одно соединение (`readDb`, если оно уже
   `Connection.remote()`) для push и/или `checkAndAnnounce`, сокращая число
   независимых сетевых JDBC-подключений к прод-серверу в рамках одного
   HTTP-запроса.
3. `webvue3` (`ReviewModal.vue`/`store.js`) — различать три исхода
   (успех / уже одобрено / ошибка) явными сообщениями, вместо одного
   `catch → 'Ошибка запроса'` (FR-001, FR-002, FR-005).
4. `SongReleaseAnnouncementService.kt` — актуализировать устаревший KDoc
   (п. 3 выше).
5. `docs/features/dual-db-sync.md` — обновить per-feature документ (FR-009,
   тот же файл, что редактировали 089 и 092).

**Rationale**: Прямо реализует FR-001…FR-006 из `spec.md`, не расширяя
скоуп за пределы описанных user stories/edge cases. Пункт 2 — не
самостоятельная performance-цель (Clarifications явно это исключают), а
следствие устранения конкретной находки п. 2 этого документа (меньше
независимых соединений = меньше окон для протухания соединения перед
`aRead.save()`).

**Alternatives considered**:
- *Просто обернуть весь `approve()` в общий try/catch, ничего не меняя в
  количестве соединений.* Отклонено как неполное — уберёт симптом
  «ложная ошибка на успешном апруве», но не уменьшит вероятность реального
  сбоя `checkAndAnnounce()`/итоговой записи статуса, оставляя `News`
  потенциально несоздающейся по тем же сетевым причинам.
- *Сделать `checkAndAnnounce()` полностью асинхронным (фоновый поток/очередь).*
  Отклонено для этой итерации — избыточное расширение скоупа за пределы
  описанных FR (спецификация прямо не требует смены исполнения на
  асинхронное, только достоверность результата, см. Clarifications); также
  ввело бы новый паттерн конкурентности, не предусмотренный текущей
  архитектурой `KaraokeProcess*`-очереди (принцип IV Конституции — очередь
  предназначена для ffmpeg/melt/Demucs-класса задач, не для лёгких
  DB-запросов). Можно рассмотреть отдельной фичей, если после этого фикса
  проблема с длительностью останется.
