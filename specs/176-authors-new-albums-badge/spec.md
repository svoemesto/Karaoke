# Feature Specification: Бейдж «новые альбомы» в пункте меню «Авторы»

**Feature Branch**: `176-authors-new-albums-badge`

**Created**: 2026-08-12

**Status**: Draft

**Input**: User description: "Админка, у компонета 'Авторы' в левом меню должен быть красный бейдж с количеством авторов у которых есть новые альбомы (если они есть), такой же, как у 'Чат' и 'Задания редактора'."

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Виджет счётчика в сайдбаре (Priority: P1)

Администратор проекта открывает админку `webvue3` и видит в левом меню пункт «Авторы». Если в системе есть авторы, у которых обнаружены новые альбомы (т.е. в БД есть `last_album_ym`/`last_album_vk`, не совпадающий с `last_album_processed`, автор помечен `watched = true`, и у него задан хотя бы один из `ym_id`/`vk_id`), то справа от надписи «Авторы» появляется красный бейдж с количеством таких авторов. Если таких авторов нет — бейдж скрыт.

**Why this priority**: Это основное требование задачи — без бейджа фичи нет. P1 — минимальный жизнеспособный срез.

**Independent Test**: Можно проверить изолированно: при наличии хотя бы одного автора с новым альбомом бейдж появляется в течение 20 секунд после открытия админки; при отсутствии — бейдж скрыт. Не зависит от других пунктов меню.

**Acceptance Scenarios**:

1. **Given** в БД есть 1 автор с `haveNewAlbum = true`, **When** администратор открывает админку, **Then** в сайдбаре рядом с пунктом «Авторы» виден красный бейдж с цифрой `1`.
2. **Given** в БД есть N авторов с `haveNewAlbum = true` (N > 1), **When** бейдж отображается, **Then** в нём показано число N.
3. **Given** в БД нет авторов с `haveNewAlbum = true`, **When** администратор открывает админку, **Then** бейдж на пункте «Авторы» отсутствует (DOM-элемент не отображается).
4. **Given** бейдж отображает значение N > 0, **When** администратор переходит на страницу «Авторы» и применяет фильтр «Новый альбом» = «Да», **Then** бейдж в сайдбаре продолжает показывать то же значение N (не пропадает, не меняется).
5. **Given** бейдж отображает значение N > 0, **When** администратор отмечает автора как просмотренного (или синхронизирует обработанный альбом), уменьшая количество новых, **Then** через ≤ 20 секунд бейдж обновится до нового значения (или скроется при 0).

---

### User Story 2 — Визуальная консистентность с другими бейджами (Priority: P1)

Бейдж «Авторы» оформлен так же, как бейджи пунктов «Чат» и «Задания редактора»: тот же красный цвет фона, тот же размер, та же скруглённая форма, тот же условный рендеринг (виден только при `count > 0`).

**Why this priority**: Требование явно сформулировано пользователем («такой же, как у 'Чат' и 'Задания редактора'»). Визуальная консистентность — половина смысла фичи.

**Independent Test**: Визуальное сравнение DOM/CSS трёх бейджей в DevTools — фон/цвет/размер/радиус совпадают (допускается разный текст числа и разная позиция счётчика внутри nav-link).

**Acceptance Scenarios**:

1. **Given** одновременно видны бейджи «Чат», «Задания редактора» и «Авторы», **When** администратор смотрит на левый сайдбар, **Then** все три бейджа выглядят одинаково по форме, размеру и цвету (оттенок красного совпадает в пределах восприятия).
2. **Given** бейдж «Авторы» отображается с числом, **When** ширина сайдбара вмещает число в одну цифру, **Then** бейдж имеет минимальную ширину, достаточную для отображения двузначного числа без переноса и без деформации высоты строки меню.

---

### User Story 3 — Автообновление счётчика без перезагрузки страницы (Priority: P2)

Значение бейджа обновляется автоматически в фоне (polling), не требуя от администратора действий: F5, переходов между страницами, ручного обновления. Интервал обновления совпадает с другими бейджами (≈ 20 секунд).

**Why this priority**: Существующие бейджи («Чат», «Задания редактора») уже работают через polling — добавить ещё один бейдж по той же схеме естественно и не плодит новой модели. Без polling-а пришлось бы перезагружать страницу, что неудобно.

**Independent Test**: Принудительно изменить `last_album_processed` автора в БД (или через UI пометить как просмотренного) — в течение одного интервала polling-а бейдж в сайдбаре изменится без действий пользователя.

**Acceptance Scenarios**:

1. **Given** админка открыта и работает, **When** проходит 20 секунд, **Then** фоновый запрос на сервер за новым значением счётчика выполняется автоматически (видно в DevTools → Network).
2. **Given** запрос за счётчиком упал с ошибкой (сеть/500), **When** polling продолжается, **Then** предыдущее значение бейджа остаётся видимым (не сбрасывается в 0).
3. **Given** пользователь закрыл вкладку админки, **When** через минуту открывает админку снова, **Then** бейдж сразу (на `mounted`) показывает актуальное значение из БД, без ожидания первого интервала.

---

### Edge Cases

- **Что если N = 0?** Бейдж не отображается (как у других пунктов меню). DOM-элемент `<span>` отсутствует, чтобы не занимать место и не шуметь.
- **Что если запрос за счётчиком возвращает ошибку?** Предыдущее корректное значение остаётся на бейдже; в консоль пишется ошибка (как у других опросов). Бейдж не «зависает» на старом значении навечно — следующий tick через 20с попробует снова.
- **Что если `haveNewAlbum` определено по сложной логике (`watched && (ym_id || vk_id) && (last_album_ym || last_album_vk != last_album_processed)`)?** Эта логика уже реализована в `Author.haveNewAlbum` getter (`karaoke-app/.../model/Author.kt:94`). Серверный endpoint ОБЯЗАН переиспользовать её, а не дублировать условие в SQL руками — иначе фильтр в AuthorsFilterModal и счётчик в бейдже разойдутся при малейшем изменении семантики.
- **Что если авторов тысячи?** Endpoint должен вернуть **только число** (int), а не список DTO — никакой JSON с `authorsDigests[]` на каждый tick. Это и есть основное отличие от существующего `/api/authors/authorsdigests` (который грузит полный список).
- **Что если админка свёрнута/вкладка неактивна?** Polling продолжается (как у других бейджей) — пользователь, вернувшись на вкладку, увидит актуальное значение после ближайшего тика.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: В левом сайдбаре админки (`webvue3/src/App.vue`) пункт меню «Авторы» ДОЛЖЕН содержать красный бейдж с количеством авторов, у которых `haveNewAlbum = true`, если это количество > 0.
- **FR-002**: Бейдж ДОЛЖЕН визуально соответствовать существующим бейджам «Чат» (`chat-nav-badge`) и «Задания редактора» (`songeditor-nav-badge`): тот же цвет фона `#d02c3a`, белый текст, скруглённые углы `border-radius: 10px`, минимальная ширина 18px, высота 18px, шрифт 11px. Допускается новый CSS-класс `authors-nav-badge` с теми же стилями.
- **FR-003**: Backend ДОЛЖЕН предоставлять endpoint `POST /api/authors/withnewalbumcount`, возвращающий целое число — количество авторов с `haveNewAlbum = true` (по модели `Author`, `tbl_authors`, та же логика, что в `Author.haveNewAlbum` getter).
- **FR-004**: Endpoint `/api/authors/withnewalbumcount` ДОЛЖЕН быть дешёвым (только count по индексу/фильтру, без загрузки DTO и без картинок). Ожидаемое время ответа — десятки миллисекунд на базе из ~18k авторов.
- **FR-005**: На стороне Vuex ДОЛЖЕН быть добавлен state-поле `authorsWithNewAlbumCount` (default `0`), getter `getAuthorsWithNewAlbumCount`, mutation `setAuthorsWithNewAlbumCount`, action `loadAuthorsWithNewAlbumCount`, по образцу `chatUnreadTotal` в `Chat/store.js` и `submittedAssignmentsCount` в `SongEditor/store.js`.
- **FR-006**: В `webvue3/src/App.vue` ДОЛЖЕН запускаться polling action `loadAuthorsWithNewAlbumCount` каждые 20 секунд (константа `AUTHORS_NEW_ALBUMS_POLL_INTERVAL_MS = 20000`, тот же интервал, что у `CHAT_UNREAD_POLL_INTERVAL_MS` и `SONGEDITOR_SUBMITTED_POLL_INTERVAL_MS`).
- **FR-007**: При размонтировании App.vue (`beforeUnmount`) таймер polling-а ДОЛЖЕН очищаться через `clearInterval` — без утечек таймеров при HMR/перезагрузке.
- **FR-008**: Бейдж ДОЛЖЕН показывать актуальное значение сразу при `mounted` (не ждать первого интервала polling-а) — первый вызов `loadAuthorsWithNewAlbumCount` синхронно после подключения SSE/прочей инициализации.
- **FR-009**: Бейдж НЕ ДОЛЖЕН ломать верстку сайдбара: при `count > 0` пункт меню «Авторы» остаётся в одну строку, без переноса «Авторы» на новую строку (тот же приём, что у `chat-nav-link` / `songeditor-nav-link` — `display: flex; justify-content: space-between`).
- **FR-010**: При падении запроса за счётчиком (network error / 5xx) предыдущее корректное значение бейджа ДОЛЖНО сохраняться (не сбрасываться в 0). Ошибка пишется в `console.log`, как в существующих опросах.

### Key Entities *(include if feature involves data)*

- **Author** (существующая сущность, `karaoke-app/.../model/Author.kt`): содержит поля `watched` (Boolean), `ymId` (String), `vkId` (String), `lastAlbumYm` (String), `lastAlbumVk` (String), `lastAlbumProcessed` (String). Вычисляемое свойство `haveNewAlbum` уже определено в модели: `watched && (ymId != "" || vkId != "") && (lastAlbumYm != lastAlbumProcessed || lastAlbumVk != lastAlbumProcessed)`. Бейдж использует это вычисляемое свойство как единственный источник истины — никаких собственных SQL-условий на клиенте.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: При наличии в БД ≥ 1 автора с `haveNewAlbum = true` в админке `webvue3` в левом сайдбаре рядом с пунктом «Авторы» в течение ≤ 20 секунд после открытия админки появляется красный бейдж с этим числом.
- **SC-002**: При отсутствии авторов с `haveNewAlbum = true` бейдж на пункте «Авторы» отсутствует (визуально и в DOM).
- **SC-003**: Изменение состояния автора (отметка `watched`, изменение `last_album_processed` и т.п.) отражается в бейдже в течение ≤ 20 секунд без перезагрузки страницы.
- **SC-004**: Endpoint `/api/authors/withnewalbumcount` отвечает за ≤ 100 ms на базе в 18k+ авторов (запрос — только count, без лишней работы).
- **SC-005**: Визуальное оформление бейджа «Авторы» совпадает с бейджами «Чат» и «Задания редактора» (один и тот же hex-цвет фона `#d02c3a`, белый текст, одинаковый размер/радиус — проверяется через DevTools или скриншот).
- **SC-006**: Polling не создаёт утечек таймеров: после многократных HMR-перезагрузок `App.vue` в DevTools нет накапливающихся интервалов (проверяется через `Performance Monitor` / `setInterval` count).
- **SC-007**: Пункт меню «Авторы» при `count > 0` остаётся в одну строку (не ломает верстку сайдбара), как и остальные пункты с бейджами.

## Assumptions

- Пользователь, для которого делается бейдж, — администратор проекта (внутренний пользователь), работающий в `webvue3`. Авторизация в админке не требуется (`permitAll()` в `SecurityConfig.kt`), отдельных ролей нет.
- Значение `haveNewAlbum = true` в `Author.kt` — это и есть «автор с новым альбомом» (та же логика используется в фильтре AuthorsFilterModal «Новый альбом = Да»). Никаких дополнительных источников истины не вводится.
- Авторы живут на одной БД (`WORKING_DATABASE = Connection.local()` в `karaoke-app`), endpoint `/api/authors/withnewalbumcount` НЕ принимает параметр `target` — в отличие от `/api/chat/unreadcount`, где есть выбор `local/remote` (чаты — PROD-only). Это согласуется с уже существующим `/api/authors/authorsdigests`, который тоже не принимает `target`.
- Polling-интервал 20 секунд согласован с другими бейджами. Меньший интервал не нужен — пользователь всё равно переходит в «Авторы» не чаще нескольких раз за сессию.
- Авторов много (десятки тысяч), поэтому endpoint возвращает **только число**. Не возвращается список id или DTO — это избыточно для счётчика.
- Реальный фильтр AuthorsFilterModal «Новый альбом» (через `getAuthorsFilterHaveNewAlbum`) и серверный фильтр (`Author.getWhereList` → SQL) — это отдельная, уже работающая фича; она не затрагивается и использует ту же логику `haveNewAlbum`, что и бейдж.
