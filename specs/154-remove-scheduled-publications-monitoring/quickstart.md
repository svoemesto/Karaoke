# Quickstart: проверка удаления мониторинга запланированных публикаций

Ручная валидация (в проекте нет CI-тестов для `MonitorRegistry`, см.
`plan.md`/Конституция, раздел «Рабочий процесс» → «Тесты»). Выполняется на
admin-машине (`dev-pc`/`dev`), где разрешена пересборка `karaoke-app`.

## Предпосылки

- Реализованы изменения по `tasks.md`: `TelegramHorizonCheck.kt` удалён,
  `MonitorRegistry.checks` содержит 7 элементов, запись
  `monitorTelegramHorizonDays` убрана из `KaraokeProperties.kt`,
  `docs/features/monitoring.md` обновлён.
- Локальный стек поднят (`deploy/do.sh`, см. `DEVELOPMENT.md`).

## Шаги

1. **Сборка и статические проверки**
   ```bash
   cd /home/dev/Karaoke
   ./gradlew ktlintCheck
   bash tools/check-kdoc-coverage.sh
   ./gradlew karaoke-app:bootJar
   ```
   Ожидаемо: оба линт/coverage-скрипта проходят (файл с непокрытым KDoc
   удалён, а не оставлен без документации); джар собирается без ошибок
   компиляции (импорт `TelegramHorizonCheck` в `MonitorRegistry.kt` убран).

2. **Пересборка/перезапуск `karaoke-app` локально**
   ```bash
   cd deploy && bash do.sh start_app
   ```
   Использовать именно scoped-команду `start_app` (не `build_start_app` —
   она поднимает контейнеры через «полный» `docker-compose.yml`, который не
   уважает `ENABLE_APP_GPU=0` и ломает `karaoke-web`, см.
   `feedback_do_sh_scoped_commands` в памяти агента; джар уже собран шагом 1,
   `do_start_app`/`start_app` сам пересоберёт образ при необходимости).
   (Разрешено без отдельного согласия пользователя только на `dev-pc`/`dev`
   — см. Конституцию, «Ограничения и доступы агента», п. 6.)

3. **Проверка панели мониторинга в webvue3**
   - Открыть админку → дождаться минутного тика `MonitoringService` (или
     обновить страницу, снапшот приходит по SSE/`GET`-эквиваленту сразу).
   - В списке алертов НЕ должно быть записи «Мало запланированных постов в
     Telegram» / категория «Telegram» с текстом про горизонт — ни при каком
     реальном состоянии очереди Telegram-публикаций на этот момент.
   - Остальные типы алертов (если они сейчас актуальны — например,
     остановленная очередь рендера или непрочитанные сообщения чата)
     продолжают отображаться как раньше.

4. **Проверка списка настроек**
   - Открыть раздел настроек (Properties UI, где рендерится
     `listKaraokeProperties`).
   - Убедиться, что записи `monitorTelegramHorizonDays` в списке больше нет.
   - Убедиться, что `monitorDismissed` и `monitorProdDownCriticalMinutes`
     (соседние по коду настройки) на месте и не пострадали.

5. **Проверка документации**
   - `docs/features/monitoring.md`: раздел «Как работает (кратко)» больше не
     перечисляет проверку горизонта Telegram-постов; количество проверок в
     шапке раздела соответствует фактическому (`MonitorRegistry.checks.size`).

## Ожидаемый результат

- Ни при каких условиях алерт `telegram.horizon` не появляется (SC-001).
- В списке настроек мониторинга стало на одну запись меньше (SC-002).
- Все остальные проверки мониторинга работают как прежде, без регрессий
  (SC-003).
