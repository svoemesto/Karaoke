# SSE Payload Contract: PROCESS_COUNT_WAITING

**Дата**: 2026-08-12
**Фича**: 177-fix-process-count-waiting-spam
**Статус**: Без изменений от исходного контракта (этот документ — справочник, не спецификация изменения)

## Endpoint

`GET /api/subscribe?tabId=<id>` — SSE-подписка на уведомления админки.
Реализовано через кастомный `SNS`-сервис (`com.svoemesto.karaokeapp.services.SNS`),
не стандартный `SseEmitter`. Подписчики регистрируются при подключении;
сообщения fan-out'ятся в каждого подписчика индивидуально.

## Тип события: PROCESS_COUNT_WAITING

### Payload (wire-формат, JSON)

```json
{
  "userId": 1,
  "payload": {
    "type": "PROCESS_COUNT_WAITING",
    "data": {
      "countWaiting": 0
    }
  },
  "timestamp": 1786542080962
}
```

### Поля

| Поле | Тип | Описание |
|---|---|---|
| `userId` | Long | ID пользователя-админа (на текущий момент в проекте все админы = userId 1) |
| `payload.type` | String (literal `"PROCESS_COUNT_WAITING"`) | Тип события; UI фильтрует по нему |
| `payload.data.countWaiting` | Long | Количество заданий со статусом `WAITING` в таблице `tbl_processes`, исключая `command = "tail"` |
| `timestamp` | Long (epoch millis) | Серверное время генерации события |

### Семантика

**Событие «оно изменилось»**, а не «текущее состояние».

- В SSE-канал отправляется **только при реальном изменении**
  `countWaiting` относительно последнего отправленного значения
  (после фикса фичи 177).
- Если значение не изменилось с прошлой отправки — событие **не
  отправляется** (подавление дублей на стороне продьюсера).
- При старте воркера (`/api/processes/startWorker`) — отправляется
  **ровно одно** начальное сообщение с актуальным `countWaiting`
  (даже если оно совпадает с последним отправленным до этого).

### Что **не** меняется в контракте

- Формат JSON.
- Имена полей, типы.
- HTTP-endpoint (`/api/subscribe`).
- Аутентификация (admin-машина, `permitAll` для админки).
- Поведение других типов событий в канале: `RECORD_CHANGE`,
  `RECORD_ADD`, `RECORD_DELETE`, `PROCESS_WORKER_STATE`, `MESSAGE`,
  и т.п.

### Что **меняется** в поведении продьюсера (не в контракте)

- Частота отправки: до фикса — десятки/секунду при простое; после —
  ≤1 сообщение за 5 минут простоя при пустой очереди (SC-001).
- В payload остаётся тот же JSON, те же поля, те же типы.

## Обратная совместимость

**100% обратная совместимость с webvue3.** UI продолжает получать
тот же JSON; просто получает его реже. Никаких изменений в
`webvue3/src/store/modules/processes.js` (или где там сейчас
обрабатывается `PROCESS_COUNT_WAITING`) не требуется — событие
по-прежнему обновляет бейдж счётчика.

Если в будущем понадобится heartbeat-эквивалент (US2, Priority P2) —
это будет **новый тип события** (`PROCESS_WORKER_TICK` или подобный),
а не изменение `PROCESS_COUNT_WAITING`.

## Тестовая проверка контракта

1. Открыть DevTools → Network → EventStream → `subscribe`.
2. Дождаться первого сообщения `PROCESS_COUNT_WAITING` (если воркер
   работает и очередь недавно стартовала).
3. Убедиться, что JSON парсится в `payload.data.countWaiting: Long`.
4. В течение 5 минут простоя убедиться, что новых сообщений с тем
   же `countWaiting` **нет**.
