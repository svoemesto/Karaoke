# Data Model: Ложное срабатывание новости «в коллекции» после синхронизации

Новых персистентных сущностей, полей или миграций эта фича не вводит (см.
[research.md](./research.md), Decision 4). Ниже — только те уже существующие поля двух
таблиц, которые участвуют в исправляемой логике, и правило перехода между ними.

## Song (`tbl_songs`, существующая)

| Поле | Тип | Роль в этой фиче |
|---|---|---|
| `player_readiness_flags` | JSON (text-колонка) | Хранит булев ключ `newsAvailableAnnounced` — «контент песни полностью готов» (выставляется `markNewsAvailableIfReady()` внутри `Song.saveToDb()`, необратимо `false → true`). Это поле читается (но по итогу этой фичи — уже не как единственный источник истины) в `doChangeRecords`. |
| `id_status`, `publish_date`, `publish_time` | int / text | Не меняются этой фичей; используются существующим механизмом «в эфире» (`checkOnAirWindow`) как признак того, что песня уже должна быть публично видна — косвенно участвуют в Decision 2 (наличие новости `"air"` как proxy того, что песня давно готова). |

**Инвариант (без изменений)**: `newsAvailableAnnounced` — монотонный, необратимый флаг
(`false → true`, никогда обратно), выставляется ровно один раз на той базе, где вызван
`saveToDb()`, и затем распространяется на другую базу через обычный dual-DB sync.

## News (`tbl_news`, существующая)

| Поле | Тип | Роль в этой фиче |
|---|---|---|
| `category` | text | `"premium"` — новость «в коллекции» (эта фича); `"air"` — новость «в эфире» (используется как **новый** входной сигнал, Decision 2). Значения не меняются. |
| `song_id` | bigint | Ключ дедупликации (вместе с `category`) — уже используется в `News.existsAnnouncement`. |
| `link` | text | Формат `/song?id={id}` — альтернативный ключ дедупликации (покрывает вручную созданные новости без `song_id`, см. существующий комментарий в `News.existsAnnouncement`). |

Схема таблицы не меняется — фикс лишь добавляет **ещё один вызов** уже существующей
функции `News.existsAnnouncement` (с `category="premium"` вместо/в дополнение к текущему
единственному месту использования с `category="air"`) в новом месте кода.

## Логическое правило (заменяет текущее «before/after по целевой БД»)

Новость `category="premium"` для `songId` создаётся тогда и только тогда, когда **все**
условия истинны:

1. `song.newsAvailableAnnounced == true` (после применения входящего изменения) — без
   изменений, существующее условие.
2. `News.existsAnnouncement(songId, link, category="premium") == false` — новое условие
   (Decision 1): ещё не публиковали.
3. `News.existsAnnouncement(songId, link, category="air") == false` — новое условие
   (Decision 2): песня ещё не вышла «в эфир» (если уже вышла — «в коллекции» точно не
   новое событие).

Это чисто функция от текущего состояния БД (той же, в которую применяется sync-батч) —
без зависимости от того, каким было это же поле секунду назад на этой конкретной копии.
