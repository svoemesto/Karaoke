# #215 — экранирование пользовательского текста песни в HTML-билдерах

**PR #619, коммит `7e330c70`, смёржен в `master` (`14d5fc3e`).**
Развёрнуто: образ пересобран, контейнер перезапущен с согласия владельца.

## Что было

`Song.getTextFormatted()`, `getFormattedNotes()`, `getFormattedChords()` собирали
HTML из пользовательского текста песни сырым. Обработка сводилась к
`replace('_', ' ')` и `replace('_', '&nbsp;')` — символы `< > & " '` не
трогались. Экранирующего хелпера в `karaoke-app` не было вовсе: единственный
`String.xmldata()` (`Extentions.kt`) экранирует только `<`.

Поля `formattedTextSong/Tabs/Chords` рендерятся через `v-html` на публичном
сайте (`karaoke-public/src/views/SongView.vue:309/313/317`), то есть правка
текста контрибьютором в лёгком редакторе уходила в HTML для всех посетителей.

Решающий довод, определивший severity: `PublicOgSongController.kt:196` это же
поле **уже экранировал** — `escape(song.formattedTextSong)`. Экранирование
было применено в одном пути из двух.

## Что сделано

1. `String.escapeHtml()` в `Extentions.kt`. Порядок замен: `&` первой — иначе
   вставленная `&lt;` развернулась бы в `&amp;lt;`.
2. Применено в **9 точках** трёх билдеров: `marker.label`, `marker.note`,
   `marker.chord`.
3. Экранирование на **входе** в HTML-буфер, а не на выходе: готовая строка уже
   содержит разметку, экранировать её целиком нельзя.
4. Документация: `knowledge/domains/integration/components/song-public-dto.md` —
   новый раздел «Экранирование» с указанием всех четырёх потребителей и
   требования к каждому новому `v-html`.

## Проверка

| Проверка | Результат |
|---|---|
| `EscapeHtmlTest` (5 тестов на хелпер) | зелёные |
| `:karaoke-app:ktlintCheck` | чисто |
| `:karaoke-app:test` (полный набор) | зелёный |
| `:karaoke-web:compileKotlin` | собирается |
| Регресс: выдача `textformatted` песни 11718 | **md5 совпал** с базовой линией |
| Двойное экранирование: `&nbsp;` / `&amp;nbsp;` в песне 11897 | 118 / **0** |

Регресс-контроль — главное: в тексте песни 11718 нет спецсимволов, поэтому
правильная починка обязана оставить выдачу байт-в-байт прежней. Совпало.

Проверка порядка операций: у песни 11897 118 собственных сущностей `&nbsp;`
и ноль `&amp;nbsp;` — сущности самого кода не экранируются повторно.

## Чего не сделано и почему

**Эксплойт на живом эндпоинте не воспроизводился.** Для этого нужен текст
песни с payload в общей dev-базе, а она синхронизируется с продом (#209).
Скан 60 песен показал, что в проверенных текстах спецсимволов нет, поэтому
положительное подтверждение экранирования на живых данных невозможно без
записи в базу.

Юнит-тест на билдер не оставлен: конструктор `Song()` тянет `lateinit KSS_APP`
(реальная БД) и падает с `ExceptionInInitializerError` на инициализации класса,
а не на утверждении. Тест, который не запускается, хуже отсутствия теста.

**Итог: дефект доказан измерением и кодом; эндпоинт-эксплойт не воспроизводился.**
Экранирование подтверждено юнит-тестом, регресс-контролем и проверкой порядка
операций.
