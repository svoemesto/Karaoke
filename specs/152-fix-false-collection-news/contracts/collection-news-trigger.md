# Контракт: детекция новости «в коллекции» (`category="premium"`)

Внутренний (не HTTP-публичный) контракт. Ни один REST-эндпоинт не добавляется и не
меняется этой фичей — `POST /changerecords` (`MainController.doChangeRecords`) сохраняет
тот же вход/выход (тело запроса `{word, dataCreate, dataUpdate, dataDelete}`, ответ —
строка статуса или сообщение об ошибке). Меняется только внутреннее поведение
`SongReleaseAnnouncementService.detectAndAnnounceAvailability`, вызываемого из этой точки.

Заменяет описание шага 2 в
[`specs/101-song-news-flag/contracts/news-lifecycle.md`](../../101-song-news-flag/contracts/news-lifecycle.md)
(п. «`MainController.doChangeRecords` — детекция перехода и создание новости «доступна»»)
в части гарантий идемпотентности — сама точка вызова (`doChangeRecords`) и её роль в
пайплайне синхронизации не меняются.

## `SongReleaseAnnouncementService.detectAndAnnounceAvailability`

**Вход**:
- `songId: Long` — песня, чья строка в `tbl_songs` была затронута текущим батчем
  синхронизации (создана или обновлена).
- `database: KaraokeConnection` — та же БД, в которую применяется батч (сервер, на
  котором физически исполняется `doChangeRecords`).
- (Параметр `wasAvailableBefore: Boolean`, ранее — единственный источник истины,
  остаётся сигнатурно для обратной совместимости вызова, но теперь используется только
  как **fast-path skip**, не как гейт корректности — см. ниже.)

**Поведение (новое)**:

1. Fast-path: если `wasAvailableBefore == true` — выйти без дальнейших действий
   (оптимизация: не грузить `Song`, если по локальному состоянию точно нечего проверять —
   поведение идентично старому для этого частного случая).
2. Загрузить `song = Song.loadFromDbById(songId, …)`. Если не найдена — выйти.
3. Если `!song.newsAvailableAnnounced` — выйти (контент ещё не готов, событие точно не
   произошло).
4. Если `News.existsAnnouncement(songId, link="/song?id=$songId", category="premium",
   database)` — выйти (новость уже была опубликована ранее — при любом количестве
   повторных обнаружений транзиции, с любой стороны синхронизации).
5. Если `News.existsAnnouncement(songId, link="/song?id=$songId", category="air",
   database)` — выйти (песня уже вышла «в эфир»; это возможно только если она уже
   давно доступна — новость «в коллекции» в этом случае заведомо не про новое событие).
6. Иначе — создать `News.createAutoAnnouncement(songId, …, category="premium",
   source="auto", …)`, вернуть `true`.

**Выход**: 0 или 1 новая строка `tbl_news` на вызов, для этой конкретной песни.

**Гарантии (идемпотентность и корректность)**:

- Ни одна песня никогда не получает более одной новости `category="premium"` —
  независимо от числа прогонов синхронизации, направления (LOCAL→SERVER или
  SERVER→LOCAL) или того, сколько раз целевая БД «переоткрывает» для себя уже известный
  факт (шаг 4).
- Новость `category="premium"` никогда не создаётся ПОСЛЕ уже существующей новости
  `category="air"` для той же песни (шаг 5) — устраняет конкретный класс инцидента,
  описанный в [spec.md](../spec.md).
- Песня, действительно становящаяся доступной впервые (и ещё не вышедшая в эфир),
  по-прежнему получает ровно одну новость `category="premium"` — шаги 4 и 5 не
  срабатывают для неё (обеих новостей ранее не существовало), FR-005 не нарушается.
- Сбой на любом шаге (в частности — сбой `News.createAutoAnnouncement`) логируется и не
  пробрасывается наружу — не откатывает уже применённые изменения синхронизации (без
  изменений относительно текущего поведения).

## `MainController.doChangeRecords` (`POST /changerecords`) — без изменений контракта

Вход/выход HTTP-эндпоинта не меняются. Единственное затрагиваемое место —
внутренний вызов `SongReleaseAnnouncementService.detectAndAnnounceAvailability` в конце
метода (уже обёрнут в `try/catch`, не влияющий на формат ответа — без изменений).
