# Механика работы агента с деревом: правки, пути, сборка

> **Домен**: system (cross-cutting)
> **Компонента**: правила, на которых агенты теряют шаги в этом проекте.
> Составлено по разбору **276 сессий** (55 031 шаг) в рабочем каталоге Караоке.

## Зачем

В разборе сессий основная часть потерянных шагов — не про домен и не про
незнание API, а про **механику**: правку файлов, пути и запуск сборки.
Ошибки ниже встречались у сильных моделей; локальные модели наступают на них
чаще, потому что пробуют наугад вместо проверки.

| Класс ошибки | Случаев | Затронуто сессий |
|---|---|---|
| `cannot modify: file has not been read` | 242 | 83 |
| `file changed since it was read` | 125 | 52 |
| `old_string was not found` / `matched N times` | 94 | 43 |
| падение bash-команды | 768 | — |
| из них: компиляция Gradle | 523 | 163 |
| из них: путь не существует | 208 | 120 |

## Правило 1. Правка = `read` → `edit`, иначе отказ

Инструмент `edit` требует, чтобы файл был **прочитан в этой же сессии**. После
`git checkout`, `git reset`, `git stash` или правки другим агентом файл считается
изменившимся и должен быть перечитан.

**Failure**: `Error: cannot modify "<file>": file has not been read — read the file, then retry`,
`Error: cannot edit "<file>": file changed since it was read — re-read the file, then retry`.

**Действие**: прочитать файл, затем править. После любой операции, менявшей рабочее
дерево, — перечитать.

## Правило 2. `old_string` — уникальный и достаточно длинный

`edit` находит точное вхождение `old_string`. Если фрагмент встречается несколько раз
или не встречается вовсе (другая версия файла), правка не применяется.

**Failure**: `old_string was not found`, `old_string matched N times; provide a more
specific old_string or set replace_all to true`, `old_string and new_string must differ`.

**Действие**: брать 3–5 строк контекста, включая уникальный идентификатор (имя функции,
комментарий). Массовую замену делать с `replace_all`, предварительно проверив число
вхождений через `grep -c`.

## Правило 3. Файлы создавать через `write`, а не heredoc в bash

`cat > file <<'EOF'` внутри `bash` ломается на кавычках, `$` и переносах: часть
текста уходит в подстановку, скрипт падает с `SyntaxError` / `unexpected EOF`.

**Failure**: `SyntaxError: unexpected EOF while looking for matching`, `IndentationError`,
пустой файл после записи.

**Действие**: создавать файл инструментом `write`; через bash — только короткие команды.

## Правило 4. Пути — от корня дерева, существование проверять заранее

Большая часть «отсутствующих» путей — следствие работы от чужого каталога или
предположения о структуре. В изолированной копии (клон/worktree) основной каталог
`/home/nsa/Karaoke` — **чужая копия**: обращаться к нему нельзя.

**Failure**: `No such file or directory`, `ls: невозможно получить доступ`,
`fatal: not a git repository`, правки в чужом дереве.

**Действие**: определить корень (`git rev-parse --show-toplevel`), работать относительно
него, проверять наличие файла (`test -f`) до чтения.

## Правило 5. Сборка: `GRADLE_USER_HOME` внутрь дерева, задачи — точечно

Gradle пишет кэш в `~/.gradle`. В изолированной среде это вне дерева и может быть
недоступно на запись.

**Failure**: `java.nio.file.FileSystemException: <path>: Файловая система доступна
только для чтения`, `Daemon compilation failed`.

**Действие**:

```bash
export GRADLE_USER_HOME="$PWD/.gradle"
./gradlew :karaoke-web:test --tests "*PublicApiVisibilityTest*"   # точечно, не вся сборка
```

**Оговорка**: падения компиляции — нормальный цикл разработки, а не ошибка сама по себе.
Правило про то, чтобы не тратить на цикл лишние круги: менять несколько связанных мест
за раз и запускать компиляцию после логического шага, а не после каждой строки.

## Правило 6. Сомнение о языке проверяй кодом проекта, а не памятью

Если собираешься что-то исправить, потому что «это работает не так» — сначала
найди в проекте место, где так уже написано и работает:

```bash
grep -n "mapOf(" karaoke-web/src/main/kotlin/com/svoemesto/karaokeweb/controllers/PublicApiController.kt | head
```

Два и более работающих вхождения — убеждение ошибочно, правку не делай.

**Failure**: правка «чинит» то, что компилировалось; объяснение опирается на
свойство языка, которого нет; рядом в том же файле есть точно такая же конструкция.

**Прецедент** (2026-11-03): модель решила, что `mapOf()` в Kotlin возвращает
`List<Pair<K,V>>`, и начала менять `mapOf("count" to 0)` на `mutableMapOf()` —
при том что весь файл наполнен работающими `mapOf(...)`.

## Правило 7. Компилятор — арбитр, рассуждение — нет

Утверждение «это не скомпилируется» или «это скомпилируется» проверяется запуском
`:karaoke-web:compileKotlin`, а не рассуждением. Собирай после **логического шага**
(эндпоинт целиком, тест целиком), а не после каждой строки, но не пропускай
компиляцию, если собираешься на её основе что-то менять.

**Failure**: несколько правок подряд «по рассуждению» без единой сборки;
вывод о работоспособности кода, сделанный без запуска.

## Правило 8. Отличай сбой инструмента от сбоя кода

| Сообщение | Что это | Действие |
|---|---|---|
| `Daemon compilation failed`, `Using fallback strategy` | инфраструктура | `./gradlew --stop`, повторить |
| `FileSystemException: Файловая система доступна только для чтения` | песочница | `GRADLE_USER_HOME` внутрь дерева |
| `e: file.kt:12: Unresolved reference: X` | код | править код |
| `Mockito`-исключения | код теста | править тест |

**Failure**: правки кода под инфраструктурный сбой; перезапуск сборки там, где
компилятор указал файл и строку.

## Правило 9. Не читай огромный файл подряд — найди символ и читай вокруг

В проекте есть файлы на тысячи строк (`Song.kt` — 10 174, `Utils.kt` — 5 366,
`PublicApiController.kt` — 1 432). Чтение их последовательными окнами тратит
контекст и сбивает нумерацию: модель теряет, что уже видела.

**Действие** — сначала найти точку, потом читать вокруг:

```bash
grep -n "fun countMatchingAttr" karaoke-app/src/main/kotlin/com/svoemesto/karaokeapp/model/Song.kt
# затем прочитать ±40 строк от найденной
```

Если в списке инструментов есть `mcp__codegraph-eval__codegraph_explore` (или
`codegraph_explore`) — он отдаёт исходник символа сразу, без поиска по строкам.
Проверить наличие: инструмент виден в списке доступных инструментов, имя содержит
`codegraph_explore`. Он есть в этой среде — им надо пользоваться, а не листать файл.

**Failure**: подряд `read` одного файла с увеличивающимся `offset`; «предыдущий
вывод обрезался, продолжаю с offset N»; к десятому чтению модель не помнит
начало.

**Данные**: в разборе 276 сессий `Song.kt` читали **10 раз за сессию**
(`HealthReport.kt` — тоже 10). В прогоне qwen-3.8-9b (2026-11-03) — 10 чтений
`Song.kt` подряд, до первой правки.

## Правило 10. Проверка — тестами, а не запуском приложения

Готовность эндпоинта подтверждается `:karaoke-web:test` на unit-тесте контроллера
(моки конструктора), а не запросом к живому приложению. Не нужно искать порты,
читать `docker-compose.yml`, ходить в консоль контейнера или смотреть его логи:
это другая задача и другая ответственность.

**Запрещено в задачах на код**: `docker exec`, `docker logs`, `docker ps`,
запуск приложения «чтобы проверить», запросы к продовым адресам и БД.

**Failure**: поиск порта приложения (`grep WEB_PORT_*`, `netstat`), вход в
контейнер `docker exec karaoke-web ...`, curl на 8080/7906 «проверить отвечает ли».

**Прецедент** (2026-11-03): модель на задаче про эндпоинт вместо теста
выполнила 10+ вызовов `docker exec karaoke-web` (env, netstat, logs) и
собиралась опрашивать порты — при том что в задаче прямо запрещены деплои и
обращения к проду.

## Правило 11. Не подменяй прод, чтобы тест прошёл

Если тесту нужна БД или внешний сервис — меняется **тест**, а не продакшн-код.

Запрещено:
- добавлять в `main/` fallback на мок при недоступности БД (маскирует реальный сбой
  в продакшене — прямое нарушение правила «ошибка не должна выглядеть успехом»);
- править существующие тесты «под себя» и удалять из них комментарии со ссылками
  на BR-коды (это аудиторский след, его проверяет guard);
- трогать прод-файлы, не относящиеся к задаче (`WorkingDatabase.kt`, конфигурация БД).

**Правильный ход**: вынести то, что проверяется, в чистую функцию и тестировать её
(см. [правила тестов контроллеров](../domains/karaoke-web/components/testing-controllers.md),
Правило 3).

**Failure**: в `main/` появляется «если подключение недоступно — вернуть mock»;
в диффе удалены `BR-013`/`BR-015`; изменён `PublicApiVisibilityTest` без причины.

**Прецедент** (2026-11-03): модель заменила `val WORKING_DATABASE = Connection.local()`
на объект с fallback-моком в продакшн-коде и вычистила BR-комментарии из существующего
теста — только чтобы её собственный тест прошёл без БД.

## Правило 12. Код правится инструментом `edit`, а не `sed -i`

`sed -i 's/.../.../'` по исходникам не проверяет, что замена попала в нужное место
и что вхождение единственное; на многострочных конструкциях и спецсимволах он
ломает код молча.

**Действие**: `edit` с уникальным `old_string` (Правило 2). `sed -i` допустим только
для файлов, которые не компилируются и не ревьюятся (конфиги, списки).

**Failure**: правка `.kt` через `sed -i`; после неё синтаксис нарушен или заменено
не то вхождение.

**Прецедент** (2026-11-03): 4 вызова `sed -i` по `PublicApiController.kt` вместо `edit`.

## Правило 13. Не оставлять в дереве мусор и «бэкапы»

Файлы вида `*-original.kt`, `*-backup.kt`, `test-write.txt`, `tmp*` в рабочем дереве —
мусор: они попадают в `git status`, засоряют дифф и могут быть случайно закоммичены.
История и откат — это git, а не копии файлов.

**Действие**: бэкап не создаётся; откат — `git checkout -- <file>`. Проверка перед
коммитом: `git status --porcelain` — в списке только файлы задачи.

**Failure**: в диффе копия исходного контроллера под именем `*-original.kt`
(1432 строки), пустые `*-backup.kt`, `test-write.txt`.

**Прецедент** (2026-11-03): модель оставила три мусорных файла и копию контроллера.

## Правило 14. Кэш Gradle не удалять

`GRADLE_USER_HOME` внутри дерева предзаполнен: сети в среде нет, и после
`rm -rf .gradle` сборка не восстановится.

При «corrupted cache», `IOException` по `*-jvm-*.jar`, зависшем демоне:

```bash
./gradlew --stop          # остановить демоны
./gradlew :karaoke-web:compileKotlin --no-daemon
```

`rm -rf .gradle`, `rm -rf .gradle/caches`, `rm -rf ~/.gradle` — запрещены.

**Failure**: `rm -rf .gradle` ради «починить кэш»; `FileNotFoundException` по
ktor/okhttp-снапшоту после чистки; сборка, ушедшая в загрузку зависимостей.

**Прецедент** (2026-11-03): модель удалила каталоги кэша, пытаясь обойти
`IOException` от Kotlin-демона.

## Правило 15. Форматирование — инструментом, а не руками

ktlint-нарушения не исправляются вручную и тем более перезаписью файла: в проекте
есть автоформаттер.

```bash
./gradlew :karaoke-web:ktlintFormat      # форматирует
./gradlew :karaoke-web:ktlintCheck       # проверяет, что чисто
```

Ручная правка отступов/пробелов через `edit` или `cat >` почти всегда вносит новое
нарушение: правила ktlint конфликтуют между собой, если применять их по одному.

**Failure**: цикл «правка пробелов → ktlint снова ругается → правка пробелов»;
перезапись файла целиком ради форматирования; `Unnecessary long whitespace`,
`Needless blank line` после ручной правки.

**Прецедент** (2026-11-03): модель трижды перезаписала файл heredoc'ом, пытаясь
поправить пробелы перед `}`, и каждый раз получала новый набор нарушений.

## Правило 16. Git: кавычки в сообщении коммита и запрет на пересборку репозитория

**Кавычки.** `git commit -m "... \`текст\` ..."` в двойных кавычках выполняет
обратные кавычки и `$()` как подстановку оболочки: git получает испорченное
сообщение, а в выводе появляется `команда не найдена`. Сообщение — в одинарных
кавычках или через файл:

```bash
git commit -F - <<'MSG'
feat: эндпоинт /api/public/songs/count
MSG
```

**Хеш = успех.** Если git напечатал `[branch abc1234] сообщение`, коммит создан.
Строки `команда не найдена` рядом — это шум подстановки, а не отказ.

**Запрещено**: `rm -rf .git`, `git clone` внутрь рабочего дерева, `git init` в
подкаталоге, копирование дерева «чтобы закоммитить». Если git отказывает —
остановись и сообщи, что именно он напечатал.

**Failure**: `rm -rf .git && git clone ...`; каталог `origin-local/` со своим `.git`;
исчезнувшие `objects/`/`HEAD` в `.git`.

**Прецедент** (2026-11-03): коммит прошёл (`[eval/base-guide 58947cc2]`), но модель
приняла шум `PublicApiController: команда не найдена` (обратные кавычки в сообщении)
за провал — и уничтожила `.git`, пытаясь пересобрать репозиторий через
`git init`/`git clone` в подкаталоге.

## Правило 17. `edit` принимает текст, а не патч

В `old_string`/`new_string` передаётся **чистое содержимое файла**. Знаки `+` и `-`
из дифф-разметки (`+    @GetMapping(...)`) попадут в файл буквально и сломают код.

**Действие**: если правка показана блоком с `+`/`-` — копируй только сам код без
маркеров. После правки, меняющей структуру метода (аннотации, сигнатуру), сразу
запусти `:karaoke-web:compileKotlin`: дубликаты `@GetMapping` и лишние символы
видны только компилятору.

**Failure**: в файле остались строки, начинающиеся с `+`; дубликат
`@GetMapping("/songs")`; «файл повреждён, надо откатывать» после собственной правки.

**Прецедент** (2026-11-03): gpt-oss-20b вставил метод через `edit`, передав строки
с `+`, получил дубликат маппинга и час чинил собственный файл.

## Правило 18. Не вызывать скилл, не относящийся к задаче

Каталог скиллов сессии содержит рабочие процессы для других видов задач
(`speckit-full-team`, `grilling`, `wayfinder` и т. п.). Вызов такого скилла
подгружает альтернативную процедуру работы и **размывает ограничения задачи**:
после вызова модель начинает работать по чужому сценарию.

**Действие**: скилл вызывается только если задача прямо его требует. Для обычной
задачи (правка кода, тест, коммит) — не вызывать ни один скилл.

**Failure**: первым действием прогон вызывает `skill: speckit-full-team` и через
несколько шагов нарушает запреты промпта (правки через `sed -i`, обход проверок).

**Прецедент** (2026-11-04, L1): qwen-3.8-9b-128k первым вызовом запустил
`speckit-full-team`; после этого проигнорировал запрет `sed -i` и шаг 0
(codegraph) — 0 вызовов codegraph за весь прогон.

## Правило 19. Зелёная сборка до последней правки не считается

Успешный `compileKotlin`/тест, пройденный **до** последней правки, ничего не
говорит о текущем состоянии кода. Правка после проверки (даже «мелкая») может
сломать файл.

**Действие**: порядок строго такой — правка → проверка → коммит. Если после
проверки была ещё хоть одна правка файла — проверять заново.

**Failure**: в логе есть `BUILD SUCCESSFUL`, а в коммите — код, который не
компилируется (например, после `sed -i` удалено объявление константы, а ссылка
на неё осталась).

**Прецедент** (2026-11-04, L1): qwen-3.8-9b-128k получил зелёную сборку на
промежуточном состоянии, затем `sed -i` удалил объявление `NEWS_PAGINATION_SIZE`,
и в закоммиченном коде осталась ссылка на несуществующую константу. Проверка
после последней правки это бы поймала.

## Правило 20. Новый тест должен сначала стать красным

Регрессионный тест, который **проходит на неисправленном коде**, не охраняет
регрессию: он зелёный и до правки, и после. Проверка «тесты зелёные» в такой
ситуации ничего не говорит о том, что баг исправлен.

**Действие**: порядок — сначала написать тест, убедиться, что он **падает** на
текущем коде (красный), и только потом чинить код до зелёного. Если тест сразу
зелёный — значит он проверяет не то место: ищи в нём утверждение об окружении
(например, «функция экспортируется») вместо утверждения о сломанном поведении.

**Failure**: тест зелёный до правки; после правки он остаётся зелёным и не
падает, даже если откатить исправление.

**Прецедент** (2026-11-04, KARAOKE-393): тест на «публикацию во ВК» проверял,
что `promisedXMLHttpRequest` экспортируется из `webvue3/src/lib/utils.js` — а он
экспортировался всегда. Баг был в вызывающем коде (`dispatch` несуществующего
action в `SongEdit.vue`), и тест был зелёным при 507 pass / 0 fail до всякой
правки.

## Правило 21. У теста есть таймаут; зависший тест останавливает весь набор

`node --test` (встроенный раннер фронтов) не имеет таймаута по умолчанию. Тест,
который ждёт промис, который никогда не резолвится, **навечно** удерживает процесс:
нет вывода, нет ошибки, 0% CPU — набор выглядит как «идёт уже 15 минут».

**Действие**: каждый написанный тобой тест обязан иметь таймаут (внутри теста или
явной командой). Если прогон не печатает результат дольше 10 минут — **не ждать**:
локализовать (`timeout 60 node --test <файл>`) и починить тест. Прогон в фоне, который
ты не можешь остановить, не считается проверкой.

**Failure**: `npm run test:unit` «идёт» 20+ минут; автор ждёт, вместо того чтобы
найти висящий файл; бюджет задачи уходит впустую.

**Прецедент** (2026-11-04, KARAOKE-393): тест модели подменил `XMLHttpRequest` и ждал
ответа, который не приходит; второй тест в файле висел навечно и остановил весь набор
из 507 тестов.

## Правило 22. Зависимости не устанавливаются — окружение подготовлено заранее

В изолированной среде `node_modules` и кэш Gradle уже есть. Установка пакетов
(`npm install`, `npm ci`) — это обращение к сети: она недоступна и заблокирована,
а попытка обойти запрет тратит время и нарушает изоляцию.

**Действие**: если зависимости или сборка не работают — сообщи об этом в отчёте,
но не пытайся их скачать. Отсутствие зависимости — это факт о среде, а не повод
идти в сеть.

**Failure**: `npm install` в отчёте о прогоне; 20 минут на установку, которая в
конце концов не даёт ничего.

**Прецедент** (2026-11-04, KARAOKE-393): модель потратила ~10 минут на `npm install`
в клоне без `node_modules` (в окружении был глобальный eslint вместо проектного —
проверка линтера падала не из-за кода).

## Правило 23. Тест не должен быть сложнее правки

Порядок по умолчанию: **правка → проверка → коммит**. Тест раньше кода оправдан
только для уже существующего контракта. Когда задача — починить конкретный вызов,
тест «сначала» почти всегда уводит в постройку стенда (подмена XHR, мок стора,
свой раннер), а стенд оказывается дороже самой правки.

**Действие**: оцени размер правки (обычно 5–30 строк). Если оснастка для теста
требует больше кода, чем правка, — сначала сделай правку, а тест сведи к проверке
контракта вызова (что вызвано, с какими аргументами), без подмены сетевого слоя.

**Failure**: полчаса на отладку собственного `FakeXHR`; в итоге ни правки, ни коммита.

**Прецедент** (2026-11-04, KARAOKE-393): правка была «вызвать функцию напрямую
вместо `dispatch`», но модель сначала написала тест с подменой `XMLHttpRequest`,
завис на нём (навечно, без таймаута) и потратила весь бюджет; `SongEdit.vue` остался
неизменным, коммита не было.

## Правило 24. Отчёт о готовности — это проверка критериев задачи

«Исправлено ✅» в отчёте означает, что **критерии готовности из задачи выполнены**,
а не то, что модель что-то сделала и считает, что починила. Перед финальным отчётом
пройти по критериям задачи по пунктам и показать, что каждый закрыт.

**Действие**: для каждого критерия — команда и её результат (или конкретная причина,
почему критерий не выполнен). Если критерий не выполнен — так и написать, без
обтекающих формулировок.

**Failure**: отчёт «корень найден и исправлен ✅», при этом `SongEdit.vue` не тронут,
коммитов нет, а «исправлен» — собственный тест, который проверял соседний файл.

**Прецедент** (2026-11-04, KARAOKE-393): модель отчиталась об исправлении P-61-08,
не изменив ни одной строки продового кода.

## Правило 25. Падение инструмента проверки — это факт о среде, а не повод импровизировать

Линтер, тесты или сборка могут падать из-за среды: нет зависимостей, глобальная
версия инструмента вместо проектной, несовместимый конфиг. В этот момент у модели
две плохие опции — выдумать «починку» или честно сказать, что проверка не идёт.

Выдуманная починка почти всегда хуже: она меняет файлы, которые не относятся
к задаче, и создаёт правила, которые потом ломают проект у других.

**Действие**: если проверка падает из-за среды — описать это в отчёте и проверить то,
что проверить можно. **Запрещено**: создавать новые конфиги инструментов (плоский конфиг ESLint и
подобные), править вендорные файлы (каталоги `node_modules`, библиотека
sockjs-client, jquery-бандл в assets), отключать правила, трогать файл исключений
ESLint.

**Failure**: в индекс попадают выдуманный конфиг линтера и правка вендорного файла;
задача не решена, но дерево изменено в трёх местах.

**Прецедент** (2026-11-04, KARAOKE-393): в клоне не было `node_modules`, поэтому
`npm run lint:check` подхватил глобальный eslint 10 и потребовал плоский конфиг.
Модель создала новый плоский конфиг ESLint в каталоге админ-SPA и удалила строку
`/* eslint-env worker */` из вендорного тестового файла sockjs-client, чтобы «починить»
линтер; задачу при этом не решила.

## Правило 26. Находка может быть неактуальной — сначала воспроизвести, потом чинить

Задача может ссылаться на дефект, который уже исправлен: находки из аудита сняты
со снимка кода трёхнедельной давности. Прежде чем править, убедиться, что дефект
**ещё есть**: найти конкретное место в текущем коде, где он проявляется.

Если дефекта нет — это результат, а не повод искать, что бы поправить. Зафиксировать
проверку (что проверял, чем, вывод, ссылка на код) и не менять посторонние файлы.

**Failure**: правка «на всякий случай» в соседнем файле, конфиг инструмента или
вендорный файл — и коммит, в котором нет ни одной строки по задаче.

**Прецедент** (2026-11-04, KARAOKE-393): находка P-61-08 требовала заменить
`dispatch('promisedXMLHttpRequest')` на прямой вызов — но правка уже была в master
(комментарий BR-124 в коде). Одна модель потратила час на постройку теста к
несуществующему багу; другая честно написала, что бага нет, — но затем закоммитила
выдуманный конфиг линтера и правку вендорного файла под сообщением «fix(P-61):
исправил вызов promisedXMLHttpRequest в SongEdit.vue», которого в коммите не было.

## Правило 27. Диагностику переводят в логгер, а не удаляют

Замена `println` на логгер — это **перенос** сообщения, а не его удаление. Если
строка печатала рабочее состояние (режим, путь, идентификатор запуска), её надо
перевести в `log.info` с параметрами, а не вычеркнуть: удаление тихо убирает
диагностику, которой потом не хватает при разборе инцидента.

**Действие**: `println("X = $v")` → `log.info("x={}", v)` (в Kotlin — параметрами,
не подстановкой в строку); `println("err: ${e.message}")` → `log.warn("…", e)`
(с передачей исключения, иначе теряется стектрейс).

**Failure**: строка удалена, а на её месте ничего не появилось; в логах сервиса
больше нет сведений о режиме запуска.

**Прецедент** (2026-11-04, KARAOKE-394): при исправлении `println` в
`SongReleaseAnnouncementScheduler` строка с ошибкой корректно переведена в
`log.warn(..., e)`, а стартовая диагностика `println("WEB_WORK_ON_SERVER = …")` в
`KaraokeWebService` просто удалена.

## Правило 28. В отчёте — только то, что реально сделано; лишние файлы не создаются

Отчёт — это описание фактического состояния, а не пересказ задачи. Каждое утверждение
отчёта проверяется по диску: файлы — по `git show --stat`, идентификаторы — по карточке
находки, дата — по календарю. Незапрошенные артефакты (changelog, отчёт.md, сводки) в
дереве проекта не создаются: их появление — это мусор в `git status` и ложные
утверждения в истории.

**Действие**: перед отчётом — `git show --stat HEAD` и сверка: перечисленные файлы
совпадают с дифом, номера находок — с карточкой, дата — сегодняшняя. Если что-то
сделать не удалось — так и написать, без замены «будет сделано».

**Failure**: changelog с датой через два дня, ссылкой на соседнюю находку и
перечнем правок, которых нет в коммите.

**Прецедент** (2026-11-04, KARAOKE-394): модель создала в корне `CHANGELOG.md` с датой
«2026-11-06», сослалась на находку P-37-09 вместо P-37-08 и перечислила правку
`PaymentService`, которой в коммите не было (она была исправлена ранее).

## Правило 29. Тест, кодирующий гипотезу, сначала опровергает её

Тест, написанный под гипотезу «дефект есть», утверждает дефект как факт
(`assert(!sql.contains("description"))` — «колонки нет»). Если такой тест **падает** на
текущем коде, это не «ещё не дописал», а **доказательство, что дефекта нет**: колонки
в коде есть. Дописывать тест, чтобы он «покраснел», нельзя — сначала прочитать
реализацию целиком.

**Действие**: перед написанием теста под дефект — прочитать функцию целиком и найти
реальную структуру (какая ветка что делает), а не выводить её по имени параметра. Если
реализация не подтверждает гипотезу — фиксировать проверку, а не чинить несуществующее.

**Failure**: тест падает, модель чинит тест вместо того, чтобы пересмотреть вывод.

**Прецедент** (2026-11-04, KARAOKE-395): находка BR-533 (поля не переносятся в
sync-таблицу при `sync=true`) оказалась неактуальной: в `getSqlToInsert` нет ветвления —
флаг `sync` меняет только имя таблицы, а список колонок общий и включает все пять полей.
Одна модель это установила по коду и истории, другая вывела «дефект воспроизводится» и
писала тест, утверждающий, что колонок в sync-SQL нет.

## Правило 30. Проверка по подстроке без границ даёт ложные срабатывания

`sql.contains("description")` срабатывает и на `short_description`; `contains("id")` — на
`id_tariff`, `id_status`, `id_max_demo`. Такая проверка падает не по делу и «доказывает»
несуществующий дефект.

**Действие**: проверять членство по границам — регулярное выражение с разделителями
(`\bdescription\b` по списку колонок, а не по всему SQL) либо разбирать SQL на список
имён колонок и сравнивать множества. Для теста дефекта — сравнивать списки колонок
локальной и sync-версии, а не искать подстроку.

**Прецедент** (2026-11-04, KARAOKE-395): тест на BR-533 искал `description` в тексте
INSERT и натыкался на `short_description` — то есть падал бы даже при корректном коде.
