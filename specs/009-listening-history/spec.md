# Feature Specification: История прослушиваний (QW-13)

**Feature Branch**: `[009-listening-history]`

**Created**: 2026-07-25

**Status**: Draft

**Input**: User description: "QW-13: История прослушиваний — для зарегистрированных пользователей
на karaoke-public, отдельная страница/раздел «что вы слушали», показывающая недавно
прослушанные песни. См. docs/strategy/growth.md (раздел Roadmap, Быстрые победы) и
docs/strategy/growth-audit.md для контекста гипотезы."

## Стратегический контекст

**Гипотеза** (H1.12, `docs/strategy/growth-audit.md`): у сайта нет «истории прослушиваний» —
зарегистрированный пользователь не получает видимой личной ценности от аккаунта, кроме
избранного. «Что вы слушали на прошлой неделе» — конкретный, понятный бонус за регистрацию.

**QW-13** — «Быстрая победа» в `docs/strategy/growth.md` (оценка 1-2 дня), сегмент
visitor→registration.

**Связь с `004-reasons-to-register`**: эта фича — одна из двух причин, из-за отсутствия
которых QW-2 («5 причин зарегистрироваться») была поставлена на паузу (см.
`specs/004-reasons-to-register/spec.md`, статус On Hold). После реализации QW-13 пункт
«История» в блоке «5 причин» снова станет правдой.

**Связанные документы:**
- [`docs/strategy/growth.md`](../../docs/strategy/growth.md) — роадмап, QW-13 в «Быстрых победах»
- [`docs/strategy/growth-audit.md`](../../docs/strategy/growth-audit.md) — гипотеза H1.12
- [`004-reasons-to-register: пауза QW-2`](../004-reasons-to-register/spec.md) — почему это разблокирует QW-2

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Зарегистрированный пользователь видит, что он слушал (Priority: P1)

Зарегистрированный пользователь заходит в раздел «История» личного кабинета и видит список
песен, которые он недавно слушал на сайте (название, исполнитель, когда), в порядке от
последней прослушанной к более старым. Может кликнуть на песню и перейти к ней (открыть
плеер / карточку песни).

**Why this priority**: это и есть сама фича — без списка «что я слушал» нет ценности для
пользователя и нет причины регистрироваться ради этого пункта.

**Independent Test**: зарегистрированный пользователь прослушивает 2-3 песни, заходит в
раздел «История», видит их в списке в правильном порядке.

**Acceptance Scenarios**:

1. **Given** зарегистрированный пользователь прослушал песню (плеер стартовал
   воспроизведение), **When** он открывает раздел «История», **Then** эта песня появляется
   в списке (название, исполнитель, дата/время).
2. **Given** пользователь слушал несколько песен в разное время, **When** открывает
   «Историю», **Then** список отсортирован от самой недавней прослушанной к самой старой.
3. **Given** пользователь видит песню в «Истории», **When** кликает по ней, **Then**
   переходит к этой песне (карточка песни или сразу плеер).

---

### User Story 2 - Пустая история не выглядит как ошибка (Priority: P2)

Новый зарегистрированный пользователь, ещё ничего не слушавший (или слушавший только
анонимно, до регистрации), открывает раздел «История» и видит понятное сообщение
«Вы пока ничего не слушали» с призывом перейти в каталог — а не пустую белую страницу.

**Why this priority**: без этого первое впечатление от новой фичи — «сломано» или «пусто»,
что снижает доверие к разделу.

**Independent Test**: новый пользователь без истории прослушиваний открывает раздел —
видит текст-заглушку и ссылку в каталог, не пустой список без пояснений.

**Acceptance Scenarios**:

1. **Given** у пользователя нет ни одной записи прослушивания, **When** он открывает
   «Историю», **Then** видит сообщение-заглушку и CTA «Перейти к каталогу»/«Найти песню».

---

### User Story 3 - Анониму раздел недоступен (Priority: P3)

Анонимный посетитель, попытавшись открыть раздел «История» напрямую по ссылке, видит
приглашение войти/зарегистрироваться — не пустую или падающую страницу.

**Why this priority**: раздел закрывает регистрационную ценность фичи (US1/`004`), поэтому
для анонима он не должен быть доступен как есть — но и не должен вести в тупик.

**Independent Test**: аноним открывает `/account/history` (или аналогичный путь) — видит
приглашение войти/зарегистрироваться, не ошибку и не пустую историю.

**Acceptance Scenarios**:

1. **Given** аноним (без активной сессии), **When** открывает раздел «История», **Then**
   видит сообщение «Доступно только зарегистрированным» с кнопками «Войти»/«Регистрация»
   (тот же паттерн `LoginRequired`, что и в `PlaylistsView.vue`).

---

### Edge Cases

- Пользователь слушал одну и ту же песню несколько раз — в истории она либо одна запись с
  «последний раз слушали: ...», либо несколько отдельных записей (см. Open Questions).
- Пользователь был анонимом, потом зарегистрировался — его анонимные прослушивания **не**
  переносятся в историю (нет связки anon_id→site_user_id, это отдельная будущая задача
  `M-3` в `growth.md`; см. Assumptions).
- Песня, которую пользователь слушал, была позже удалена/скрыта (`SKIP`-тег) — история не
  должна ломаться или показывать её как обычную; либо скрывается, либо показывается
  неактивной записью без ссылки.
- Очень длинная история (тысячи прослушиваний за годы) — показывается не вся, а ограниченный
  последний период/количество (см. FR-004).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система MUST предоставлять зарегистрированному пользователю раздел «История
  прослушиваний» в личном кабинете (`karaoke-public`).
- **FR-002**: Раздел MUST показывать список песен, которые пользователь прослушивал, с
  названием, исполнителем и датой/временем последнего прослушивания, отсортированным от
  самого недавнего к самому старому.
- **FR-003**: Каждая запись в списке MUST быть кликабельна и вести к соответствующей песне.
- **FR-004**: Список MUST быть ограничен разумным количеством записей на странице (не
  более 50-100 последних) — не выгружать всю историю пользователя без пагинации/лимита.
- **FR-005**: Раздел MUST быть доступен только зарегистрированным (аутентифицированным)
  пользователям; анонимам — приглашение войти/зарегистрироваться вместо содержимого.
- **FR-006**: Пустая история (ни одного прослушивания) MUST показывать понятное сообщение
  и предложение перейти в каталог, а не пустой список без пояснений.
- **FR-007**: Раздел MUST быть доступен по ссылке из личного кабинета (там же, где
  «Избранное»/«Плейлисты»).
- **FR-008**: Источник данных о прослушиваниях — существующий механизм трекинга событий
  сайта (не вводится новая система сбора данных «с нуля»; см. Assumptions).
- **FR-009**: Использует существующий дизайн (`--km-*` CSS-переменные), без новых
  глобальных стилей.

### Key Entities

- **PlayEvent (существующая сущность)** — событие прослушивания песни, уже фиксируется
  системой трекинга сайта при каждом старте воспроизведения; для зарегистрированного
  пользователя связано с его учётной записью. Эта фича не вводит новую сущность, а
  **отображает** уже существующие данные.
- **Song** — песня из каталога (уже существующая сущность), на которую ссылается запись
  истории (название, исполнитель).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Зарегистрированный пользователь, прослушавший песню, видит её в разделе
  «История» не позднее следующего открытия раздела (без задержки в часы/дни).
- **SC-002**: ≥70% зарегистрированных пользователей, открывших раздел «История» хотя бы
  раз, открывают его повторно в течение месяца (интерес к разделу подтверждён повторным
  использованием).
- **SC-003**: Раздел «История» становится честным пунктом в блоке «5 причин
  зарегистрироваться» (`004-reasons-to-register`) — 0 несуществующих фич, рекламируемых как
  причина регистрации.
- **SC-004**: Страница раздела загружается быстро — пользователь видит список (или
  заглушку) без ощутимой задержки при обычном количестве записей (до 100).

## Assumptions

- Реализуется **поверх уже существующего механизма трекинга** прослушиваний сайта
  (события воспроизведения уже фиксируются и, для залогиненных пользователей, уже
  связываются с учётной записью) — не вводится новая система сбора данных. Точный
  технический механизм — предмет `/speckit-plan`, не этой спецификации.
- Анонимные прослушивания **не** переносятся в историю после регистрации — связка
  anon_id → site_user_id ещё не реализована (`M-3` в `growth.md`, отдельная будущая
  задача). История начинается с момента входа в аккаунт.
- «Недавние» — последние 50-100 записей или ограниченный период (точная граница — на
  усмотрение реализации, не критична для ценности фичи для пользователя).
- Повторные прослушивания одной и той же песни — реализация вправе как схлопывать их в
  одну запись «слушали N раз, последний — ...», так и показывать отдельными записями;
  выбор не меняет пользовательскую ценность фичи существенно.
- Дизайн — переиспользует существующие компоненты личного кабинета (тот же паттерн, что
  «Избранное»/«Плейлисты»/«Чат»).
- Не требует новых миграций БД, если данные о прослушиваниях уже персистентны (см. первое
  допущение) — если это не так, `/speckit-plan` должен явно это зафиксировать как отход
  от допущения.

## Out of Scope (явно не в этой фиче)

- Перенос анонимных прослушиваний в историю после регистрации (см. Assumptions, `M-3`).
- Аналитика/статистика по истории (графики, тренды) — только простой список.
- Удаление отдельных записей из истории пользователем («забыть эту песню») — отдельная
  задача при необходимости.
- Публичная/расшариваемая история (только сам пользователь видит свою историю).
