# ADR-local-0011: Собственный git-хостинг Forgejo; тяжёлый CI — на машине разработчика

## Context & Problem

GitHub перестаёт быть основной площадкой проекта: нужен собственный git-хостинг
с контролем доступа, организациями и возможностью держать данные у себя.
Одновременно нужно сохранить PR-гейт (линтеры, guard'ы, сборки, тесты), но
исполнение чужого кода рядом с боевыми данными недопустимо.

## Decision | Решение

1. **Git-хостинг — Forgejo** на infra-сервере (`git.sm-karaoke.ru`). Реквизиты
   версии: **17.0.1** с 2026-11-01 (было 15.0.10; обновление выполнено владельцем
   при моём ведении, основание — ниже). Репозитории `svoemesto` перенесены с
   GitHub (heads/tags сверены); GitHub остаётся **push-зеркалом** до отдельного
   решения об отключении.
2. **Серверная сторона отвечает только за лёгкие правила**: защита `master`
   (прямой push отклоняется pre-receive hook'ом), обязательное ревью, защита
   тегов. Статус-чеки **не делаются обязательными** для merge: иначе
   выключенная машина разработчика блокирует любые мержи.
3. **Тяжёлые джобы (сборка, тесты, e2e, guard'ы) — на `nsa-i9`**: раннер
   Forgejo, зарегистрированный на репозиторий, docker-режим с образом
   `node:22-bookworm`, `docker.sock` монтируется в job-контейнеры для e2e.
4. **На infra-сервере раннер не живёт**: job-контейнер с `docker.sock` — это
   фактически root на хосте, а рядом лежат данные Forgejo, Plane и Harbor.
5. **Forgejo исполняет `.forgejo/workflows`**, если каталог есть; `.github`
   сохраняется для GitHub-зеркала. В `.forgejo`-копии `lint.yml` — правки под
   окружение: установка `jq`, абсолютные URL действий, снятый `concurrency`.

### Раскладка стека (проверено на сервере 2026-11-01)

- LXD-контейнер `infra` на хосте `msk-f896` (`sm@185.71.198.17:7487`).
- Compose стека Forgejo — `/srv/forgejo/docker-compose.yml`; данные —
  `/srv/forgejo/data` (SQLite); порты `127.0.0.1:3000` (веб) и `2222` (SSH);
  домен `git.sm-karaoke.ru`.
- Образ: `codeberg.org/forgejo/forgejo:17.0.1`, digest
  `sha256:fcd19ff4ebc85fb098a67e8e1d0d5a84d07dd6e8a23edcfdfd5b71a6178953be`.
  API отдаёт `version: 17.0.1+gitea-1.22.0`; `forgejo doctor check --all` —
  27 проверок, все OK; раннер (act_runner v13.0.0) подключился сразу.
- Бэкап: таймер `infra-backup.timer` (03:30 UTC) → `forgejo dump` →
  `/home/sm/backup-out/forgejo-YYYY-MM-DD.tar.gz` (~1 ГБ).

### Процедура обновления версии (проверено 2026-11-01)

1. **Бэкап** — дождаться или снять вручную `forgejo dump`; проверить, что архив
   создан и не пуст.
2. `forgejo manager flush-queues` — остановить обработку очередей перед сменой
   бинарника.
3. Сменить тег образа в `/srv/forgejo/docker-compose.yml`.
4. `docker compose up -d` в каталоге стека.
5. `forgejo doctor check --all` — все проверки OK.
6. **Смоук**: открыть `https://git.sm-karaoke.ru`, зайти в репозиторий, убедиться,
   что список PR и статус-чеки на месте; убедиться, что раннер подключился и
   выполняет задания.

### Откат (обязателен до начала обновления)

- Старый образ **15.0.10 остаётся в кэше** — откат = вернуть прежний тег в
  compose и поднять стек заново.
- **Откат требует `forgejo restore` из дампа**: версия 15 откажется стартовать с
  базой, обновлённой до 17 (миграция схемы необратима). Поэтому бэкап — шаг 1,
  а не «на всякий случай».

### Что дало обновление до 17.0.1 (проверено фактами, не по документации)

- **Появился API логов джобов**: `GET /repos/{owner}/{repo}/actions/jobs/{job_id}/logs`
  → `text/plain`; `GET /repos/{owner}/{repo}/actions/runs/{run_id}/logs` → ZIP со
  всеми логами прогона; `GET /repos/{owner}/{repo}/actions/runs/{run_id}/jobs` →
  список джобов с их id. В 15.0.10 эти эндпоинты отдавали 404.
- **Появилось состояние `skipped`**: на PR, меняющем только `AGENTS.md`, версия 17
  вернула 5 `success` и 32 `skipped` (описание «Has been skipped»). В 15
  пропущенный джоб отдавался как `success`, и «неприменимо» было неотличимо от
  «зелёного».

## Rationale | Обоснование

* **Оставить CI на GitHub Actions**: отклонено как долгосрочная схема — это
  зависимость от площадки, от которой уходим; допустимо лишь как временный
  резерв.
* **Раннер на infra-сервере**: отклонено из-за риска исполнения кода рядом с
  боевыми данными и конкуренции за CPU с git/трекером/registry.
* **Host-режим на `nsa-i9`** (без контейнеров): отклонено — `uses:`-действия
  в host-режиме не отработали; docker-режим проверен.

## Consequences | Последствия

1. **Инвариант**: прямой push в `master` в Forgejo запрещён; изменения — только
   через ветку, PR и merge.
2. **Запрет**: не размещать CI-раннер с доступом к Docker на infra-сервере.
3. **Известное ограничение**: при выключенном `nsa-i9` PR-прогоны стоят в
   очереди; merge не блокируется, «зелёный CI перед merge» — дисциплина.
4. **Инвариант**: автозапуск раннера на `nsa-i9` (cron `@reboot` + watchdog
   каждые 5 минут); ручной запуск — `start.sh` в каталоге раннера.
5. **Required Update**: `knowledge/system/infra/ci-tools.md`,
   `knowledge/system/infra/external-infra.md`,
   `knowledge/guidelines/runbooks/forgejo-access.md`.
6. **Инвариант (после 2026-11-01)**: обновление Forgejo выполняется по процедуре
   «бэкап → flush-queues → смена тега → `doctor check --all` → смоук»; откат
   возможен только с `forgejo restore` из дампа, поэтому бэкап обязателен.
7. **Инвариант**: версия платформы, раскладка стека и эндпоинты логов фиксируются
   в этом ADR, `ci-tools.md`, `external-infra.md` и runbook'е — иначе «логи недоступны»
   или «пропущенный джоб = зелёный» вернутся как ложные утверждения.
