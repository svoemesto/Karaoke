# Feature Specification: Закрома — корректное скрытие блока типов альбомов при скролле вниз по списку песен автора

**Feature Branch**: `252-fix-author-album-types-hide`

**Created**: 2026-08-27

**Status**: Draft

**Input**: User description: «при прокрутке вниз списка песен автора блок с типами альбомов не весь скрывается». Скриншот: на странице Закромов конкретного автора под шапкой «Быстрый фильтр по названию песни…» лежит sticky-блок с цветными кнопками типов альбомов («Студийные (19)», «Синглы (1)», «Концертные (11)», «Сборники (52)», «Бутлеги (1)», «Архивные (73)»); ниже идут карточки альбомов с таблицами песен.

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Посетитель, скролля список песен, не видит «хвост» блока типов альбомов (Priority: P1)

Посетитель открывает Закрома конкретного автора («Машина Времени», ~2500 песен) на десктопе/мобильном, выбирает альбом и начинает скроллить вниз по таблице песен. Когда окно браузера проскроллено далеко вниз (верхняя часть страницы с фильтром и блоком типов альбомов уже должна была скрыться), пользователь **не должен видеть никакой полосы/хвоста от блока типов альбомов** — ни сверху, ни «выглядывающего» из-под шапки или поля быстрого фильтра.

**Why this priority**: Это прямой баг-репорт. На скриншоте пользователя видно, что блок типов альбомов визуально пересекается с полем быстрого фильтра по названию песни — оба `position: sticky; top: 53px` (`.km-filter-bar` имеет `z-index: 90`, `.km-album-controls-bar` имеет `z-index: 89`). Поскольку у обеих панелей одинаковый `top`, при прокрутке блок альбомов «прибивается» к той же координате, что и поле поиска, и **хвост панели типов (заголовок «Студийные (19) Синглы (1) Концертные (11) Сборники (52) Бутлеги (1) Архивные (73)») выглядывает из-под фильтра**. Это ухудшает читаемость, перекрывает таблицу песен и выглядит как неисправный layout.

**Independent Test**: Открыть `/zakroma?author=Машина Времени` (или другого крупного автора с ≥3 типами альбомов и длинным списком песен). Убедиться, что у `.km-filter-bar` и `.km-album-controls-bar` одинаковый `top: 53px`. Сделать скриншот окна браузера при прокрутке вниз на 1000px. Визуально проверить: блок типов альбомов либо (а) **не виден вообще** (полностью уехал за верх экрана), либо (б) виден ровно **под** фильтром, без пересечения и без полосы-хвоста. Через DevTools: `offsetTop` блока типов ≥ `top` фильтра + `offsetHeight` фильтра (никакого overlap'а по вертикали).

**Acceptance Scenarios**:

1. **Given** пользователь на `/zakroma?author=…` с выбранным автором (≥3 типов альбомов), **When** страница загружена без скролла, **Then** оба sticky-блока видны полностью: сверху `.km-filter-bar` с полем «Быстрый фильтр по названию песни…», под ним `.km-album-controls-bar` с тумблером «Сквозной / По типам альбомов» и кнопками типов альбомов; вертикальное наложение отсутствует.
2. **Given** пользователь скроллит вниз на 1000px (верх страницы уже ушёл за viewport), **When** он смотрит на верхнюю часть окна, **Then** блок `.km-album-controls-bar` **НЕ виден** (если он сделан не-sticky) либо виден целиком **ровно под** `.km-filter-bar` без пересечения и хвоста (если sticky сохранён).
3. **Given** viewport ≤ 360px (мобильный), **When** пользователь скроллит таблицу песен вертикально, **Then** поведение sticky-блоков согласовано с десктопом: либо оба скрыты, либо оба видны без overlap'а — никакой полосы-хвоста от блока типов поверх таблицы песен.
4. **Given** пользователь скроллит обратно на самый верх, **When** полоса прокрутки в 0, **Then** `.km-filter-bar` и `.km-album-controls-bar` находятся в исходных DOM-позициях под шапкой `.km-header`, оба видны.
5. **Given** пользователь начинает тянуть страницу вверх, **When** блоки подходят к границе `top: 53px`, **Then** момент «прилипания» обоих блоков происходит без визуального скачка (никаких «дёрганий» из-за переупорядочивания z-index или смены offset'а).

### User Story 2 — Sticky-поведение блоков не зависит от числа типов альбомов автора (Priority: P2)

У автора может быть 1 тип (только «Студийные»), 3 типа, 6 типов (максимум — студийные / синглы / концертные / сборники / бутлеги / архивные / трибьюты). В каждом из этих случаев блок `.km-album-controls-bar` либо должен быть полностью скрыт при прокрутке, либо полностью виден без пересечения с `.km-filter-bar`. Поведение не должно «ломаться» на авторах с экстремальным числом типов (1 тип с длинным счётчиком или 6 типов в одну строку).

**Why this priority**: Сейчас высота блока зависит от `flex-wrap: wrap` — если 6 кнопок не помещаются в одну строку, блок становится 2-строчным, и хвост становится ещё заметнее. P1 фиксирует баг; P2 гарантирует, что фикс не привязан к размеру окна и числу типов.

**Independent Test**: Открыть `/zakroma?author=…` с автором, имеющим ровно 6 типов альбомов (или сгруппировать кнопки искусственно для теста). Замерить `getBoundingClientRect().height` у `.km-album-controls-bar` на десктопе (1280×800) и мобильном (375×667). Сделать скриншот при scrollY = 800 на обоих viewport'ах. Визуально: при прокрутке блок либо уезжает целиком, либо виден целиком под фильтром без полосы-хвоста.

**Acceptance Scenarios**:

1. **Given** автор с 6 типами альбомов и viewport 1280×800, **When** `.km-album-controls-bar` вышел за верх viewport, **Then** пользователь не видит никакой части блока (ни сверху, ни в виде хвоста поверх `.km-filter-bar`).
2. **Given** автор с 1 типом альбомов, **When** панель короткая (одна строка), **Then** поведение при прокрутке согласовано с P1: либо блок скрыт полностью, либо виден целиком без overlap'а с фильтром.
3. **Given** viewport 375×667 (мобильный) и автор с 6 типами, **When** `.km-album-controls-bar` занимает 2 строки из-за `flex-wrap: wrap`, **Then** при прокрутке обе строки либо уезжают за верх viewport, либо видны обе, без явных «срезов» по границе scroll.

### User Story 3 — Прогресс-бар и ошибки загрузки остаются видимыми во время стрима (Priority: P3)

Если во время загрузки песен автора поверх `.km-content` показан ещё и `.km-stream-progress` (полоса загрузки с прогрессом и кнопкой «Отмена» — спек `181`), он тоже `position: sticky; top: 56px; z-index: 50`. После фикса P1 поведение sticky-стека (filter-bar → album-controls-bar → stream-progress) должно оставаться консистентным: либо все три блока уезжают за верх, либо все три видны без пересечения (за прогресс-баром не должен «торчать» хвост блока типов альбомов).

**Why this priority**: Edge case — во время загрузки появляется третий sticky-блок; если фикс P1/P2 даст хвост у прогресс-бара, это будет ещё одна регрессия. P3 страхует P1/P2 от регрессии в сценарии стрима.

**Independent Test**: Открыть крупного автора с медленным стримом (или эмулировать задержку). В момент, когда активен `.km-stream-progress`, проскроллить к таблице песен. Визуально: прогресс-бар и блок типов альбомов не должны пересекаться по вертикали.

**Acceptance Scenarios**:

1. **Given** идёт стрим (`.km-stream-progress` виден), **When** пользователь скроллит, **Then** стек sticky-блоков не имеет визуальных пересечений: ни один блок не оставляет хвост поверх другого.
2. **Given** стрим завершился, **When** `.km-stream-progress` исчез, **Then** поведение `.km-filter-bar` и `.km-album-controls-bar` возвращается к описанному в US1 (без регрессий).

## Requirements *(mandatory)*

### Functional Requirements

#### A. CSS-layout sticky-блоков в `ZakromaView.vue`

- **FR-001**: `.km-album-controls-bar` MUST быть либо **полностью скрыт** при прокрутке вниз (не оставлять хвоста над/под `.km-filter-bar`), либо **виден целиком** ровно **под** `.km-filter-bar` без вертикального пересечения с ним. Никакая часть блока типов альбомов НЕ ДОЛЖНА рисоваться поверх `.km-filter-bar`, над ним или «выглядывать» из-за его верхней/нижней границы при `scrollY > 0`.
- **FR-002**: Если `.km-album-controls-bar` сохраняет `position: sticky`, его `top` MUST быть выставлен так, чтобы блок прилипал **ниже** `.km-filter-bar` (например, через CSS-переменную `--km-filter-bar-height` или прямой `top: calc(53px + <filter-bar-height>)`), а **НЕ** к той же координате `top: 53px`, что и `.km-filter-bar`.
- **FR-003**: `z-index` sticky-блоков MUST сохранять видимость «фильтр-над-типами»: `.km-filter-bar` (или объединённый контейнер обоих блоков) находится выше, чем `.km-album-controls-bar`. Допускается любой порядок стека, **но** при `position: sticky; top: X` для обеих панелей их видимые прямоугольники не должны пересекаться.
- **FR-004**: Альтернативный вариант реализации (допустимо вместо FR-002): объединить `.km-filter-bar` и `.km-album-controls-bar` в **один общий sticky-контейнер** (например, `<div class="km-author-header-sticky">…</div>` с `position: sticky; top: 53px`). Тогда контейнер целиком либо уезжает за верх viewport при прокрутке вниз, либо прилипает к шапке одной полосой — никаких overlap'ов между подблоками.

#### B. Регрессии на смежных sticky-элементах

- **FR-005**: `.km-stream-progress` (спек `181-zakroma-author-load-progress`, исправленный в спек `251`) MUST оставаться корректно видимым во время стрима: либо находится под `album-controls-bar` и `filter-bar`, либо уезжает вместе с ними — **никакого** overlap'а или хвоста от блока типов альбомов поверх полосы прогресса.
- **FR-006**: `.km-header` (AppHeader, спек `250-unify-site-header`) MUST оставаться на своём месте (`position: sticky` или фиксированный), его высота (~53 px) и `z-index` НЕ ДОЛЖНЫ меняться в рамках этой фичи; sticky-стек остальных блоков строится от его нижней границы.

#### C. Поведение на мобильных и при переносе

- **FR-007**: На viewport ≤ 480px (мобильный) при `flex-wrap: wrap` блок `.km-album-controls-bar` может занимать 2 строки; фикс MUST работать **одинаково** для 1-строчного и 2-строчного вариантов (никакого хвоста, отрезанного по границе строки).
- **FR-008**: При resize окна браузера (смена ориентации мобильного, drag-to-resize десктопа) sticky-поведение MUST оставаться корректным без перезагрузки страницы.

### Key Entities

Не применимо — это чисто CSS/HTML баг-фикс `ZakromaView.vue` без изменения DTO или бизнес-логики. Затрагиваемый артефакт:

- **`ZakromaView.vue`** (`karaoke-public/src/views/ZakromaView.vue`) — единственный файл, в котором живут `.km-filter-bar` и `.km-album-controls-bar`. Бэкенд (`karaoke-web/.../MainController.kt:zakroma`, `PublicApiController.kt`) и DTO (`ZakromaPublicDto.kt`) **не затрагиваются**.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: При `scrollY > 0` на странице `/zakroma?author=…` (автор с ≥3 типами альбомов, viewport 1280×800) **никакая** часть `.km-album-controls-bar` не имеет визуального пересечения с `.km-filter-bar` (проверка через DevTools: `getBoundingClientRect()` блоков не пересекаются по вертикали, или блок `album-controls-bar` целиком скрыт за верх viewport).
- **SC-002**: На скриншоте при scrollY = 800 на десктопе (1280×800) пользователь видит **ровно** те sticky-блоки, которые должны быть видны (`AppHeader` всегда, `Filter-bar` и `Album-controls-bar` — только если логика решила их оставить sticky), без полосы-хвоста от `Album-controls-bar` поверх `Filter-bar`.
- **SC-003**: На мобильном viewport (375×667) при scrollY = 400 поведение согласовано с десктопом: ни одного overlap'а между блоками; если `Album-controls-bar` 2-строчный — обе строки либо видны обе, либо скрыты обе.
- **SC-004**: `npm run build` (`karaoke-public`) — PASS.
- **SC-005**: `npm run lint` (`karaoke-public`) — 0 warnings (или 0 новых нарушений по baseline).
- **SC-006**: `tools/check-eslint-baseline.sh karaoke-public` — 0 новых нарушений относительно baseline.
- **SC-007**: Бэкенд `karaoke-app` и `karaoke-web` **не пересобираются** (`./gradlew :karaoke-app:bootJar :karaoke-web:bootJar` — UP-TO-DATE).

## Edge Cases *(include if feature involves data)*

- Что происходит, когда у автора только один тип альбомов (например, только «Студийные»)?
  → Блок `.km-album-controls-bar` отображается с одной кнопкой; фикс должен работать и в этом случае (никакого overlap'а не возникает даже на коротком блоке).
- Что происходит при resize окна во время скролла?
  → При смене ширины viewport (например, поворот мобильного) sticky-поведение пересчитывается автоматически (CSS), никаких артефактов перезагрузки не требуется.
- Что происходит во время стрима (`.km-stream-progress` виден)?
  → Стек `AppHeader → Filter-bar → Album-controls-bar → Stream-progress` остаётся визуально согласованным: нет overlap'ов, нет хвоста от `Album-controls-bar` над `Stream-progress`.

## Assumptions

- (a) Существующее sticky-поведение панелей в `ZakromaView.vue` (`top: 53px` для обеих) — **намеренное**, обе панели должны быть видны при прокрутке; текущий баг — **overlap**, а не «панель типов должна была скрываться». Фикс должен сохранить **намеренное** поведение (панели видны), убрав overlap. Если продукт решит, что панель типов НЕ ДОЛЖНА быть sticky — это отдельный UX-вопрос, не часть этой спеки.
- (b) Альтернативная гипотеза — пользователь имел в виду, что блок `.km-album-controls-bar` должен быть скрываться при прокрутке вниз, как это делают многие SPA (например, scroll-down-hides-toolbar). Если в реальном продуктовом решении этот вариант предпочтительнее — FR-002 должен быть заменён на «`.km-album-controls-bar` теряет `position: sticky` (становится обычным in-flow элементом)». В этой спеке оба варианта FR описаны (FR-002 «sticky под фильтром» vs FR-004 «общий sticky-контейнер»); конкретный выбор — план/таск.
- (c) Багфикс чисто клиентский (CSS-маркировка, опционально — перенос в общий контейнер). Никакие DTO/контроллеры/бэкенд не затрагиваются.
- (d) Базовый порядок загрузки проверки: после фикса линтер, сборка фронта, визуальная проверка в браузере на десктопе и мобильном viewport. Никаких автоматизированных тестов в проекте нет (см. AGENTS.md); приёмка — пользователем.
- (e) Связанные спеки: `012-entity-description-fields` (вводит sticky-controls-bar и быстрые фильтры по типу альбома), `181-zakroma-author-load-progress` (stream-progress sticky), `250-unify-site-header` (AppHeader). Фикс **затрагивает** CSS-разметку файла `ZakromaView.vue`, **не меняет** контракты этих спек.
