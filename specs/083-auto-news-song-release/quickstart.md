# Quickstart: проверка «Автоматические новости о выходе песни в эфир»

## Предпосылки

- Локальный docker-стек поднят (`db`/`karaoke-app`/`karaoke-web`/`webvue3`), см.
  `project_local_docker_setup` — можно проверять сценарий на этом стенде, эмулируя PROD (тот же код
  `karaoke-web`/`doChangeRecords`, просто на localhost вместо `sm-karaoke.ru`).
- Применены новые SQL-миграции (`ALTER TABLE tbl_news ...`, `CREATE TABLE tbl_song_news_announced`)
  на используемой для теста БД (`deploy/karaoke-db/33_song_news_announced.sql`).
- Одноразовый backfill (research.md п.5, шаг 3) уже выполнен на этой БД — иначе первый тест «поймает»
  весь существующий бэклог песен и создаст лавину новостей.

### Процедура запуска backfill (один раз, перед включением механизма)

Backfill реализован как обычный admin-эндпоинт `karaoke-app` (`NewsController`), а не отдельный
скрипт — по тому же паттерну, что остальные ручные admin-действия (`target` — опциональный параметр,
как в `ChatController`/`DictionariesController`):

```bash
# LOCAL (по умолчанию):
curl -X POST http://<admin-host>/api/news/backfill-announcements

# PROD — ТОЛЬКО по прямому согласию пользователя, см. Constitution → «Категорически запрещено»:
curl -X POST "http://<admin-host>/api/news/backfill-announcements?target=remote"
```

Ответ — `{"markedCount": N}` (сколько песен помечено). Выполняется РОВНО ОДИН РАЗ на каждую БД,
ДО того как на ней начнёт реально работать штатный вызов `checkAndAnnounce` внутри
`doChangeRecords` (т.е. до первого «боевого» `/changerecords` после релиза фичи на эту БД). Повторный
запуск безопасен (идемпотентен за счёт `PRIMARY KEY(song_id)` в `tbl_song_news_announced`), но
бессмысленен после первого успешного прогона.

## Сценарий 1 — песня становится доступна впервые (User Story 1)

1. В webvue3 найти/создать тестовую песню со статусом < 6 либо с датой эфира в будущем.
2. Довести песню до состояния «полностью готова»: `id_status = 6`, дата/время эфира — в прошлом
   (например, "вчера"), готовы стемы/обложки/маркеры (как для проверки `PublicPlayerController.canWatch`).
3. Синхронизировать эту песню на тестовый "PROD" (`/api/sync/oneclick` с целью SERVER либо точечный
   `/api/sync/run` только для песни) — это вызовет `POST /changerecords` на тестовом `karaoke-web`.
4. **Ожидаемый результат**: в `tbl_news` тестовой БД появилась новая строка с `source = 'auto'`,
   `song_id` = id тестовой песни, `publish_at` в прошлом/настоящем (видна как опубликованная). В
   `tbl_song_news_announced` — соответствующая строка.
5. Проверить публичный сайт (`karaoke-public`) — новость видна в ленте/бейдже (`News.loadPublished*`).
6. Проверить `webvue3` → раздел «Новости» с переключателем на PROD/`target=remote` — новость видна и
   редактируема, как обычная (User Story 2).

## Сценарий 2 — повторная синхронизация не дублирует новость (FR-004)

1. Повторно запустить `/api/sync/oneclick` (или `/changerecords` напрямую) без изменений в песне.
2. **Ожидаемый результат**: количество строк в `tbl_news` с `song_id` = id тестовой песни — не
   увеличилось (осталось 1).

## Сценарий 3 — backlog не создаёт лавину (User Story 3 / SC-003)

1. На тестовой БД с уже существующими "старыми" готовыми песнями (статус 6, дата эфира в прошлом,
   ДО применения backfill) — выполнить backfill-шаг.
2. Запустить `/changerecords` (через обычный sync-прогон).
3. **Ожидаемый результат**: 0 новых строк в `tbl_news` с `source = 'auto'` для этих старых песен —
   все они уже отмечены в `tbl_song_news_announced` без реальной новости (`news_id IS NULL`).

## Сценарий 4 — ручное понижение статуса не отзывает новость (FR-008)

1. Взять песню из Сценария 1 (уже анонсированную), понизить `id_status` ниже 6 через SongEdit.
2. Синхронизировать.
3. **Ожидаемый результат**: ранее созданная новость в `tbl_news` осталась (не удалена, не изменилась
   автоматически). Песня перестала отображаться как доступная на публичном сайте (это уже покрыто
   `022-song-status-lifecycle`, здесь только проверяем отсутствие побочного эффекта на новость).

## Сценарий 6 — несколько песен становятся готовы за одну синхронизацию (FR-006)

1. Взять две тестовые песни, обе полностью готовы по контенту (стемы/обложки/маркеры), но с датой
   эфира в будущем.
2. Перевести дату эфира ОБЕИХ песен в прошлое одновременно.
3. Запустить одну синхронизацию (`/changerecords`).
4. **Ожидаемый результат**: в `tbl_news` появляются ДВЕ отдельные строки `source='auto'` (по одной
   на каждую песню), а не одна сводная новость на обе.

_Проверено при реализации (2026-07-29) на песнях id=21005 и id=21014 — подтверждено: 2 отдельные
строки._

## Сценарий 5 — авто-новость не «съедается» обычной sync-синхронизацией (риск из research.md п.2)

1. После Сценария 1 включить (временно, для теста) `sync_news_push_delete_allowed = true` в
   Properties UI на тестовом стенде.
2. Запустить обычный LOCAL→SERVER «1 клик» (без ручного создания/удаления новостей на LOCAL).
3. **Ожидаемый результат**: авто-созданная новость на "PROD" НЕ удалена — `News.listHashes`,
   используемый sync-движком, не должен был вообще увидеть эту строку (см. data-model.md).
4. Вернуть `sync_news_push_delete_allowed` в исходное значение после теста.

## Чек-лист ручного деплоя на PROD

Все шаги ниже требуют прямого согласия пользователя на каждое отдельное действие (Constitution →
«Категорически запрещено», п. 2: деплой на сервер и прямые DDL/DML к серверной БД). Агент готовит
материалы, но не выполняет эти шаги на PROD самостоятельно.

1. [ ] Применить `deploy/karaoke-db/33_song_news_announced.sql` на PROD БД (отдельно от LOCAL —
   миграции применяются на каждой БД вручную, см. `20_news.sql`).
2. [ ] Выполнить одноразовый backfill на PROD: `curl -X POST
   "https://<prod-admin-host>/api/news/backfill-announcements?target=remote"` — **обязательно ДО**
   следующего шага, иначе первый же прогон сразу создаст лавину исторических новостей (FR-005).
3. [ ] Проверить ответ backfill (`markedCount`) — сверить с ожидаемым порядком величины (на
   dev-стенде с prod-подобным дампом было отмечено 11119 песен).
4. [ ] Задеплоить обновлённый `karaoke-web` на PROD (`deploy_web.sh` — см. известную push-ловушку
   `EOF`/`400 Bad request`, при сбое — без VPN).
5. [ ] Проверить `docker exec karaoke-web env | grep ...` и логи контейнера после деплоя — `Status:
   Downloaded newer image`, не `Image is up to date`.
6. [ ] Прогнать штатную синхронизацию («1 клик» LOCAL→SERVER) для одной тестовой песни и убедиться,
   что новых авто-новостей по историческим песням не появилось (backfill из шага 2 должен был их уже
   исключить).
7. [ ] Когда следующая по-настоящему новая песня выйдет в эфир — убедиться, что после очередной
   синхронизации по ней появилась ровно одна новость в публичной ленте `karaoke-public`.
