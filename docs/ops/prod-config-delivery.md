# Доставка конфигов на прод: как не «доставить не туда»

Практика, выведенная из инцидентов аудита #336 (BR-549, #558) и из правок
волны E. Все примеры — прод `sm-karaoke.ru` (хост `188.127.240.124`).

## 1. Прод — не git-чекаут

На проде `/root/Karaoke` — **каталог выкладки**, а не клон репозитория
(`.git` там нет). Файлы конфигурации копируются вручную. Отсюда правило:

> Любая правка в `deploy/prod-single-host/` доезжает на прод **только явным
> копированием** файла. «Оно в master — значит, оно на проде» — неверно.

Проверка перед выкладкой: сравнить живой файл с файлом из репозитория.

```bash
scp root@188.127.240.124:/etc/nginx/sites-enabled/80to8897 /tmp/prod-80to8897
diff /tmp/prod-80to8897 deploy/prod-single-host/80to8897
```

Если разница больше ожидаемой — значит на проде есть правка, которой нет в
репозитории (или наоборот). Сначала выяснить, чья правка, и только потом
перезаписывать.

## 2. Конфиг контейнера берётся с хоста — mount, а не COPY

Контейнер `karaoke-public` получает nginx-конфиг через **bind-mount**:

```
/root/Karaoke/deploy/nginx_karaoke-public.conf → /etc/nginx/nginx.conf
```

В образ его **нет**: Dockerfile (`deploy/karaoke-public/Dockerfile`) кладёт
только `dist` (`COPY --from=build-stage /app/dist /app`). Значит:

- правка конфига в репозитории не влияет на контейнер, пока файл не скопирован
  на хост;
- если в репозитории лежат **две копии** конфига, они рано или поздно разойдутся,
  и правка уйдёт не в ту. Отсюда правило: **один источник** + guard, который
  требует равенства копий (`tools/check-security-headers.py`, `MIRROR_PAIRS`).

## 3. Ловушка: замена файла через `mv` ломает bind-mount

`mv` создаёт **новый inode**. Контейнер держит **старый** inode (тот, что был
подмонтирован при старте) — и после `mv` он продолжает видеть прежнее
содержимое. Симптом выглядит как «правка не применилась», хотя на хосте файл
правильный:

```bash
# ТАК — контейнер НЕ увидит изменений (старый inode в mount)
cp new.conf /root/Karaoke/deploy/nginx.conf.new
mv /root/Karaoke/deploy/nginx.conf.new /root/Karaoke/deploy/nginx.conf

# ТАК — inode сохраняется, контейнер видит изменения сразу
cat new.conf > /root/Karaoke/deploy/nginx.conf
```

Если замена всё же сделана через `mv` (или `install`, `cp` с удалением), нужно
**пересоздать контейнер**, чтобы mount пере-resolve'ился на новый inode:

```bash
cd /root/Karaoke/deploy && DOCKER_CONFIG=/root/.docker bash do.sh start_public
```

(контейнеры трогаются только через `do.sh start_<c>` — см. AGENTS.md Tier-1.)

## 4. Порядок выкладки nginx-конфига

1. Скопировать новый файл **содержимоем** (`cat new > target`), предварительно
   сделав бэкап: `cp target target.bak-<ЧЧММ>`.
2. Проверить синтаксис **до** reload:
   ```bash
   nginx -t                      # host-nginx
   docker exec karaoke-public nginx -t   # контейнерный
   ```
3. `nginx -s reload`.
4. **Проверить фактический ответ**, а не только код выхода:
   ```bash
   curl -s -D- -o /dev/null http://127.0.0.1:7907/ | grep -iE 'x-frame|x-content|referrer'
   curl -s -D- -o /dev/null https://sm-karaoke.ru/ | grep -iE 'x-frame|x-content|referrer'
   ```
   Проверять оба слоя: контейнерный (прямой доступ) и внешний (через host-nginx).

## 5. Дубли защитных заголовков

Два слоя nginx, у каждого свои `add_header`, дают **дубли**: `X-Frame-Options`
приходил дважды — от host-nginx и от upstream'а (SPA-nginx). Значения
одинаковые, но сканеры репортуют дубликат, а валидаторы считают заголовок
невалидным.

Решение: в host-nginx в location'ах, которые проксируют на SPA, —
`proxy_hide_header X-Frame-Options;` (и два других). У самого SPA-nginx
заголовки остаются: он же обслуживает прямой доступ к контейнеру, где
host-nginx не участвует.

Отдельно про наследование `add_header` в nginx: директивы наследуются
(`http{}` → `server{}` → `location{}`) **только если в самом блоке нет ни
одной своей `add_header`**. Поэтому location, у которого есть свои
`add_header` (например, `Cache-Control`), теряет серверные заголовки — в таких
блоках набор повторяют явно. Это проверяет `tools/check-security-headers.py`.

## 6. Правило для выкладки в принципе

> Конфиг на проде — не «то, что в master», а «то, что лежит в конкретном файле
> на конкретном хосте». Перед выкладкой: сверить, скопировать **содержимоем**,
> проверить синтаксис, reload, проверить **ответ**, а не только код выхода.
> И пересоздать контейнер, если mount указывал на старый inode.

## 7. Как это должно быть: шаг синхронизации конфигурации

До 2026-10-25 конфиги на прод копировались руками — и однажды правка
nginx-заголовков (BR-549) осталась в репозитории, а на проде лежал старый файл:
guard проверял репозиторий и рапортовал «заголовки на месте», а живой контейнер
их не отдавал. Теперь шаг есть в обоих скриптах деплоя:

```bash
cd deploy
bash deploy_web.sh      # образ + СИНХРОНИЗАЦИЯ docker-compose-web.yml
bash deploy_public.sh   # образ + СИНХРОНИЗАЦИЯ docker-compose-public.yml и nginx_karaoke-public.conf
```

Общий шаг — `deploy/sync_prod_config.sh`. Для каждого файла он:

1. печатает **diff** (прод ← репозиторий) — видно, что изменится;
2. копирует файл **содержимым** (`cat new > target`), сохраняя inode: `mv`
   создаёт новый inode, и bind-mount в контейнере продолжает видеть старый файл;
3. делает **бэкап** с меткой времени (`<файл>.bak-YYYYmmdd-HHMMSS`);
4. **валидирует** конфиг на проде: compose — `docker compose config --quiet`
   (с `do.env` в окружении, как это делает `do.sh`), nginx — `nginx -t` тем же
   nginx'ом, что в контейнере;
5. при ошибке валидации **откатывает** бэкап и завершает деплой с ненулевым кодом;
6. печатает, что обновлено.

Проверить, что на проде разошлось с репозиторием, можно и без деплоя:

```bash
cd deploy && source ./sync_prod_config.sh && sync_prod_config web
```
