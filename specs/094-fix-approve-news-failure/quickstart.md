# Quickstart: проверка фикса «Апрув задания редактора»

**Feature**: [spec.md](./spec.md) | **Дата**: 2026-07-30

В CI автотестов нет (см. Конституцию) — проверка выполняется вручную,
пользователем (или агентом с явного согласия — прод-БД трогать без него
нельзя, см. `.specify/memory/constitution.md`, «Ограничения и доступы
агента», п.2). Ниже — сценарии, покрывающие User Story 1 и 2 из `spec.md`.

## Предпосылки

- Собран и запущен `karaoke-app` с изменениями этой фичи (локально, на
  `dev-pc` — пересборка/перезапуск локальных контейнеров разрешена
  агенту на этой машине без дополнительного согласия, см. Конституцию).
- Есть тестовое задание редактора в статусе «отправлено на проверку»
  (`SongAssignment.adminStatus = open`, `SongAssignmentDraft.userStatus =
  submitted`) с непустой корректной разметкой (`editedMarkers`).
- Доступ к логам: `docker logs -f karaoke-app` (или `deploy/do.sh`
  эквивалент) и к обеим БД (LOCAL — свободно, SERVER/прод — только если
  сценарий реально требует апрув с `target=remote`, и только с согласия
  пользователя на запись в прод).

## Сценарий 1 — успешный апрув больше не показывает ложную ошибку (User Story 1, SC-001)

1. Открыть «Задания редактора» в `webvue3`, найти тестовое задание,
   открыть карточку ревью (`ReviewModal`).
2. Нажать «Одобрить и премиить».
3. **Ожидаемо**: интерфейс показывает явное сообщение об успехе (не
   «Ошибка запроса»); модалка закрывается или явно сигнализирует успех —
   не «тихо» без сообщения.
4. Проверить в БД (та, откуда читалось задание — LOCAL или SERVER, в
   зависимости от `target`): `SELECT admin_status, reviewed_at FROM
   tbl_song_assignments WHERE id = <id>;` → `admin_status = 'approved'`.
5. Проверить `Song`: `SELECT id_status FROM tbl_songs WHERE id =
   <songId>;` → `>= 6`.

## Сценарий 2 — повторный клик после успеха не показывает ошибку и не дублирует работу (User Story 1, FR-002/FR-006, SC-004)

1. Сразу после Сценария 1 (то же уже одобренное задание) снова открыть
   его карточку (если UI это ещё позволяет для одобренного задания) или
   продублировать POST-запрос с тем же `id` (например, через devtools
   Network → Replay, или `curl`, с учётом cookie/CSRF, если применимо).
2. **Ожидаемо**: сообщение «Задание уже одобрено» (или эквивалент),
   НЕ «Ошибка запроса» и не тихое закрытие без сообщения.
3. Проверить логи `karaoke-app`: строк «Изменяем запись в tbl_songs...» и
   «Запрос хешей... Получено хешей: <большое число>» на этом повторном
   вызове быть НЕ должно (нет повторного push/анонса — FR-006).

## Сценарий 3 — новость появляется по факту готовности песни на боевой копии (User Story 2, SC-002)

1. Взять тестовое задание, апрув которого фактически переводит песню в
   статус «доступна на сайте» (`id_status >= 6`) НА БОЕВОЙ копии (то есть
   `target=remote`, либо `Karaoke.allowUpdateRemote = true` и push
   реально доходит до прод — согласовать с пользователем перед
   выполнением, см. Конституцию п.2 «Категорически запрещено»).
2. Выполнить апрув (Сценарий 1).
3. В течение нескольких секунд — минут (FR-004 spec.md, до ~5 минут по
   `specs/092`, обычно почти мгновенно) открыть публичную ленту новостей
   (`karaoke-public`, `/api/public/news` или страницу новостей) и
   убедиться, что появилась новость о новой песне с названием, автором и
   (если заполнены) альбомом/годом.
4. Проверить `tbl_song_news_announced`: `SELECT * FROM
   tbl_song_news_announced WHERE song_id = <songId>;` → ровно одна строка.

## Сценарий 4 — локальная ошибка не помечает задание одобренным (User Story 1, сценарий 2, FR-003)

Сложнее воспроизвести детерминированно (нужен реальный сбой записи) —
допустимо smoke-проверкой кода (ревью diff на предмет: любой путь ошибки
применения к `Song` действительно возвращает `status:"error"` и НЕ
доходит до `aRead.adminStatus = ADMIN_APPROVED`) вместо живого
воспроизведения, если пользователь не хочет намеренно ломать тестовые
данные.

## Сценарий 5 — контракт ответа (см. `contracts/approve-endpoint.md`)

Через devtools Network (или `curl -i`) убедиться, что ответ на
`/api/songeditor/approve` во всех трёх сценариях (1, 2, штатная ошибка
типа `assignment_not_found` на несуществующем `id`) — валидный JSON с
HTTP 200, с полем `status` из набора `success` / `already_approved` /
`error`.

## После проверки

Если сценарии 1-3 подтвердились — заполнить соответствующие пункты
`checklists/requirements.md` (если ещё не отмечены) и обновить
`docs/features/dual-db-sync.md` (FR-009), если правки уже не были туда
внесены в рамках реализации.
