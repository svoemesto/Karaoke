### P-74-01: build.gradle.kts:45 — BUILD (S3)

- **Что не так**: явный пин `jackson-databind:2.14.2` перебивает версию, управляемую BOM'ом Spring Boot 3.5.6 (2.19.2). В **поставляемом** артефакте оказывается смешанный стек Jackson: `jackson-databind-2.14.2` (сентябрь 2022) лежит рядом с `jackson-core-2.19.2`, `jackson-annotations-2.19.2`, `jackson-datatype-jsr310-2.19.2`, `jackson-datatype-jdk8-2.19.2`, `jackson-module-parameter-names-2.19.2`. Jackson требует совместимых версий внутри семейства и для этого публикует `jackson-bom` («You may, however, want to use `jackson-bom` to ensure compatible versions of dependencies» — README `jackson-databind`); комбинация `databind 2.14.2` + `core/annotations 2.19.2` — разные minor-версии одного семейства, поддержкой производителя не покрыта и не проверялась. Кроме того, оправдание пина в самом файле фактически неверно: комментарий `build.gradle.kts:12` утверждает «Jackson 2.14 (используется в проекте)», тогда как в проекте используется 2.19.2, а 2.14.2 — только этот пин (наследие 2023 года, когда BOM Spring Boot давал 2.14.x). Пин в корневом `build.gradle.kts:45` при этом **мёртв** — корневой проект не имеет исходников, `implementation` не наследуется в subprojects (см. P-74-04), то есть строка в корне не влияет ни на что, но закрепляет у читателя неверное представление о версии Jackson в проекте и служит «обоснованием» для пина в модулях.
- **Доказательство**: «`    implementation("com.fasterxml.jackson.core:jackson-databind:2.14.2")`» (`build.gradle.kts:45`, SHA `1977838a`); оправдание — «`// с Jackson 2.14 (используется в проекте) и Kotlin 2.x runtime.`» (`build.gradle.kts:12`). Фактическое состояние артефакта (`unzip -l karaoke-app/build/libs/karaoke-app-1.jar`, сборка от 2026-10-23): «`BOOT-INF/lib/jackson-annotations-2.19.2.jar`», «`BOOT-INF/lib/jackson-core-2.19.2.jar`», «`BOOT-INF/lib/jackson-databind-2.14.2.jar`», «`BOOT-INF/lib/jackson-datatype-jsr310-2.19.2.jar`», «`BOOT-INF/lib/jackson-module-parameter-names-2.19.2.jar`» — рядом с «`BOOT-INF/lib/spring-boot-3.5.6.jar`» и «`BOOT-INF/lib/spring-core-6.2.11.jar`».

Полного прогона приложения не было (docker/сборки запрещены).

### P-74-02: gradle/wrapper/gradle-wrapper.properties:1–7 — BUILD (S3)

- **Что не так**: в wrapper'е нет `distributionSha256Sum` — Gradle скачивает и **распаковывает** дистрибутив `gradle-8.14-bin.zip` (≈130 МБ) и запускает его в локальной JVM без какой-либо проверки целостности. `validateDistributionUrl=true` проверяет лишь доступность URL, а не подлинность содержимого; TLS защищает канал, но не содержимое на origin'е/зеркале. Единственный барьер — доверие к `services.gradle.org`; при подмене артефакта (скомпрометированный CDN/origin, MITM на корпоративном прокси, зеркало в локальной сети) произвольный код выполнится с правами разработчика или CI-раннера. Это же означает невоспроизводимость: один и тот же `distributionUrl` со временем может отдать другой бинарник. Отсутствие контрольной суммы — не локальная особенность файла, а **общее для всех wrapper'ов репозитория** места (см. «Найдено также»).
- **Доказательство**: полный файл — «`distributionBase=GRADLE_USER_HOME`» / «`distributionPath=wrapper/dists`» / «`distributionUrl=https\://services.gradle.org/distributions/gradle-8.14-bin.zip`» / «`networkTimeout=10000`» / «`validateDistributionUrl=true`» / «`zipStoreBase=GRADLE_USER_HOME`» / «`zipStorePath=wrapper/dists`» (`gradle/wrapper/gradle-wrapper.properties:1–7`, SHA `1977838a`); строки `distributionSha256Sum=` в файле нет. Проверка по репозиторию: `grep -rn "distributionSha256Sum" --include="gradle-wrapper.properties" .` → 0 совпадений (ни в одном из четырёх wrapper'ов).
- **Путь**: `./gradlew …` в корне (`deploy/do.sh:34` → `${GRADLE}=${BASE_DIR}/gradlew`; `deploy/do.sh:134, 188`) либо CI-job `backend-lint` (`.github/workflows/lint.yml` → `./gradlew ktlintCheck --no-daemon --stacktrace`) → `GradleWrapperMain` → HTTP-загрузка `gradle-8.14-bin.zip` в `GRADLE_USER_HOME/wrapper/dists` → распаковка и запуск Gradle в локальной JVM (права пользователя/CI-раннера) → сборка проекта (доступ к исходникам, к `~/.gradle`, к `~/.m2`, к секретам окружения).
- **Поправка**: зафиксировать `distributionSha256Sum=<sha256 дистрибутива gradle-8.14-bin.zip>` в каждом из четырёх wrapper'ов (хеш берётся из официального `gradle-8.14-bin.zip.sha256`); при несовпадении — отказ сборки. Проверку контрольной суммы вынести в pre-commit/CI, чтобы флаг не терялся при правках wrapper'а.

### P-74-03: gradle.properties:9 — SEC (S3)

- **Что не так**: Gradle-daemon запускается с `-XX:+HeapDumpOnOutOfMemoryError` и фиксированным `HeapDumpPath=/tmp/gradle-heap.hprof`. При OOM JVM пишет **полный дамп кучи** в общий каталог `/tmp` (режим 1777) с правами по umask (обычно 0644) → файл читается любым локальным пользователем; JVM его не удаляет, и он переживает последующие сборки (следующий OOM перезапишет). Дамп содержит heap daemon'а, а в нём — карта переменных окружения (`System.getenv()`), то есть **любые секреты, экспортированные в shell, который запустил сборку** (пароли БД, токены, ключи), плюс состояние build-скриптов и resolved-адреса зависимостей. Для CI это ещё и выгрузка в общий раннер-каталог.
- **Доказательство**: «`org.gradle.jvmargs=-Xmx4g -Dfile.encoding=UTF-8 -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/tmp/gradle-heap.hprof`» (`gradle.properties:9`, SHA `1977838a`).
- **Путь**: любой запуск Gradle (`deploy/do.sh:134, 188` → `${GRADLE}`; CI `backend-lint` → `./gradlew ktlintCheck`) → daemon с указанными `jvmargs` → OOM (для `:karaoke-app:compileKotlin` OOM задокументирован в комментарии `gradle.properties:3–6`) → JVM пишет `/tmp/gradle-heap.hprof` → чтение файла другим локальным пользователем/процессом. Переменные окружения попадают в heap через `System.getenv()` в daemon'е (в т.ч. всё, что экспортировано в сессии, запустившей сборку).
- **Эмпирика**: не проводилась (запуск сборки с намеренным OOM запрещён). Оценка прав файла и содержимого дампа — статика по флагам JVM и документации `-XX:HeapDumpPath`.
- **Поправка**: убрать `-XX:+HeapDumpOnOutOfMemoryError`/`HeapDumpPath` из общих `jvmargs` (или писать дамп в каталог с правами 0700 внутри `GRADLE_USER_HOME`, а не в общий `/tmp`); в CI — отключить дампы вовсе, а диагностику OOM вести по логам сборки; если дамп нужен — обеспечить его удаление и ограниченные права.
- **Найдено в**: порция P-74, аудитор read-only.
- **Автор (git blame)**: nsa (nsa@technokad.ru, 2026-08-11, `gradle.properties:9` — коммит `265a163fb`).
- **Severity**: S3 — утечка возможна только при OOM и только на машине с другими локальными пользователями (на `nsa-i9` пользователь один); секреты приложения (`Karaoke.properties`) в heap Gradle-daemon'а не попадают — там только переменные окружения запуска сборки.

## Сверки (без severity)

1. **detekt: конфигурация не готова к включению (плагин закомментирован — путь недостижим).** Четыре конкретных расхождения, которые помешают «просто раскомментировать плагин»:
   а. **Baseline не подхватится.** Закомментированный блок (`build.gradle.kts:140`) ждёт per-module файл `config/detekt/baseline-${project.name}.xml` — таких файлов в репозитории нет; лежит единый `config/detekt/baseline.xml` (21 строка, `<Manually>`/`<Current>` пусты), и комментарий `build.gradle.kts:17–18` утверждает, что подключится именно он («`config/detekt/` / `baseline.xml + detekt.yml уже готовы и подключатся»»). Фактически при включении baseline будет пустым, а `build.maxIssues: 0` (`detekt.yml:11`) → detekt падает на всём существующем бэклоге.
   б. **Несуществующий ID правила.** `config/detekt/detekt.yml:74–75` — «`  SwallowedExceptionIgnored:` / `    active: false`». В detekt 1.23.7 такого правила нет (см. detekt.dev/docs/1.23.7/rules/exceptions): у `SwallowedException` есть только `ignoredExceptionTypes` и `allowedExceptionNameRegex`. При `config.validation: true` (`:20`) detekt сообщит о неизвестном свойстве.
   в. **Неверный тип свойства.** `config/detekt/detekt.yml:116–122` — «`  ForbiddenComment:` / `    active: true` / `    values:` / `      - reason: 'Используется для TODO/FIXME-маркеров'` / `        value: 'TODO:'`». В detekt 1.23.7 `values` — deprecated-свойство типа `List<String>`, а формат `{reason, value}` поддерживается свойством `comments` (см. исходник `ForbiddenComment.kt` v1.23.7). → ошибка валидации типа.
   г. **Комментарий про `allRules` неверен.** `config/detekt/detekt.yml:4–5` — «`# allRules = false — берём только явно включённые правила, чтобы baseline` / `# не раздувался на нерелевантные для проекта проверки.`» — при `buildUponDefaultConfig = true` (`build.gradle.kts:141`) сохраняются все правила, **активные по умолчанию** (`PrintStackTrace`, `RethrowCaughtException`, `InstanceOfCheckForException`, `ExceptionRaisedInUnexpectedLocation`, `ReturnFromFinally`, `ThrowingExceptionsWithoutMessageOrCause` — по страницам правил detekt.dev), а `allRules` влияет только на правила, выключенные по умолчанию. Ожидаемого «чистого старта» не будет.
   **Вопрос владельцу**: чинить ли detekt-конфиг до включения (и тогда — какой формат baseline: per-module или единый) или удалить detekt-конфиг/baseline вместе с отложенным TODO из `constitution.md`?
2. **Разнобой версий Gradle в репозитории — зеркало BR-499 (`gradle-wrapper-outdated:build`), новый BR не завожу.** Корневой wrapper — `gradle-8.14-bin.zip` (`gradle/wrapper/gradle-wrapper.properties:3`), модульные — `gradle-9.1.0-bin.zip` (`karaoke-app/...:3`, `karaoke-web/...:3`) и `gradle-7.5.1-bin.zip` (`karaoke-db/...:3`). Фактическая сборка приложения и CI-job `backend-lint` идут через **корневой** wrapper (8.14), а запуск `./gradlew` из каталога модуля — через 9.1.0/7.5.1. Прошу лида добавить корневой wrapper (8.14) к локациям BR-499 (P-41-01) или завести отдельную запись с тем же `root_cause_key`.
3. **`org.gradle.parallel=true` при 4g heap'ов — риск OOM в CI (не проверялось).** `gradle.properties:16–18` — «`# Параллельная сборка модулей ускоряет CI, но удваивает потребление памяти.`» / «`# При 4g на daemon лучше оставить только когда памяти хватает.`» / «`org.gradle.parallel=true`». Файл сам фиксирует ограничение, но значение зашито: Gradle daemon `-Xmx4g` (`:9`) + Kotlin daemon `-Xmx4g` (`:14`) + параллельные воркеры на раннере `ubuntu-latest` (~7 ГБ RAM) → риск OOM/флакающего `backend-lint` (job с `timeout-minutes: 20`). Severity не ставлю: сборка не запускалась (запрет), эффект зависит от раннера.
