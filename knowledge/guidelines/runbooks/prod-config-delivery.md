# Доставка конфигов на прод: как не «доставить не туда»

Практика, выведенная из инцидентов аудита #336 (BR-549, #558) и из правок
волны E. Все примеры — прод `sm-karaoke.ru` (хост `188.127.240.124`).

## 1. Прод — не git-чекаут

На проде `/root/Karaoke` — **каталог выкладки**, а не клон репозитория
(`.git` там нет). Файлы конфигурации копируются вручную. Отсюда правило:

> Любая правка в `deploy/prod-single-host/` доезжает на прод **только явным
> копированием** файла. «Оно в master — значит, оно на проде» — неверно.

Проверка перед выкладкой: сравнить живой файл с файлом из репозитория.

```bash
scp root@188.127.240.124:/etc/nginx/sites-enabled/80to8897 /tmp/prod-80to8897
diff /tmp/prod-80to8897 deploy/prod-single-host/80to8897
```

Если разница больше ожидаемой — значит на проде есть правка, которой нет в
репозитории (или наоборот). Сначала выяснить, чья правка, и только потом
перезаписывать.

## 2. Конфиг контейнера берётся с хоста — mount, а не COPY

Контейнер `karaoke-public` получает nginx-конфиг через **bind-mount**:

```
/root/Karaoke/deploy/nginx_karaoke-public.conf → /etc/nginx/nginx.conf
```

В образ его **нет**: Dockerfile (`deploy/karaoke-public/Dockerfile`) кладёт
только `dist` (`COPY --from=build-stage /app/dist /app`). Значит:

- правка конфига в репозитории не влияет на контейнер, пока файл не скопирован
  на хост;
- если в репозитории лежат **две копии** конфига, они рано или поздно разойдутся,
  и правка уйдёт не в ту. Отсюда правило: **один источник** + guard, который
  требует равенства копий (`tools/check-security-headers.py`, `MIRROR_PAIRS`).

## 3. Ловушка: замена файла через `mv` ломает bind-mount

`mv` создаёт **новый inode**. Контейнер держит **старый** inode (тот, что был
подмонтирован при старте) — и после `mv` он продолжает видеть прежнее
содержимое. Симптом выглядит как «правка не применилась», хотя на хосте файл
правильный:

```bash
# ТАК — контейнер НЕ увидит изменений (старый inode в mount)
cp new.conf /root/Karaoke/deploy/nginx.conf.new
mv /root/Karaoke/deploy/nginx.conf.new /root/Karaoke/deploy/nginx.conf

# ТАК — inode сохраняется, контейнер видит изменения сразу
cat new.conf > /root/Karaoke/deploy/nginx.conf
```

Если замена всё же сделана через `mv` (или `install`, `cp` с удалением), нужно
**пересоздать контейнер**, чтобы mount пере-resolve'ился на новый inode:

```bash
cd /root/Karaoke/deploy && DOCKER_CONFIG=/root/.docker bash do.sh start_public
```

(контейнеры трогаются только через `do.sh start_<c>` — см. AGENTS.md Tier-1.)

## 4. Порядок выкладки nginx-конфига

1. Скопировать новый файл **содержимоем** (`cat new > target`), предварительно
   сделав бэкап: `cp target target.bak-<ЧЧММ>`.
2. Проверить синтаксис **до** reload:
   ```bash
   nginx -t                      # host-nginx
   docker exec karaoke-public nginx -t   # контейнерный
   ```
3. `nginx -s reload`.
4. **Проверить фактический ответ**, а не только код выхода:
   ```bash
   curl -s -D- -o /dev/null http://127.0.0.1:7907/ | grep -iE 'x-frame|x-content|referrer'
   curl -s -D- -o /dev/null https://sm-karaoke.ru/ | grep -iE 'x-frame|x-content|referrer'
   ```
   Проверять оба слоя: контейнерный (прямой доступ) и внешний (через host-nginx).

## 5. Дубли защитных заголовков

Два слоя nginx, у каждого свои `add_header`, дают **дубли**: `X-Frame-Options`
приходил дважды — от host-nginx и от upstream'а (SPA-nginx). Значения
одинаковые, но сканеры репортуют дубликат, а валидаторы считают заголовок
невалидным.

Решение: в host-nginx в location'ах, которые проксируют на SPA, —
`proxy_hide_header X-Frame-Options;` (и два других). У самого SPA-nginx
заголовки остаются: он же обслуживает прямой доступ к контейнеру, где
host-nginx не участвует.

Отдельно про наследование `add_header` в nginx: директивы наследуются
(`http{}` → `server{}` → `location{}`) **только если в самом блоке нет ни
одной своей `add_header`**. Поэтому location, у которого есть свои
`add_header` (например, `Cache-Control`), теряет серверные заголовки — в таких
блоках набор повторяют явно. Это проверяет `tools/check-security-headers.py`.

## 6. Правило для выкладки в принципе

> Конфиг на проде — не «то, что в master», а «то, что лежит в конкретном файле
> на конкретном хосте». Перед выкладкой: сверить, скопировать **содержимоем**,
> проверить синтаксис, reload, проверить **ответ**, а не только код выхода.
> И пересоздать контейнер, если mount указывал на старый inode.

## 7. Как это должно быть: шаг синхронизации конфигурации

До 2026-10-25 конфиги на прод копировались руками — и однажды правка
nginx-заголовков (BR-549) осталась в репозитории, а на проде лежал старый файл:
guard проверял репозиторий и рапортовал «заголовки на месте», а живой контейнер
их не отдавал. Теперь шаг есть в обоих скриптах деплоя:

```bash
cd deploy
bash deploy_web.sh      # образ + СИНХРОНИЗАЦИЯ docker-compose-web.yml
bash deploy_public.sh   # образ + СИНХРОНИЗАЦИЯ docker-compose-public.yml и nginx_karaoke-public.conf
```

Общий шаг — `deploy/sync_prod_config.sh`. Для каждого файла он:

1. печатает **diff** (прод ← репозиторий) — видно, что изменится;
2. копирует файл **содержимым** (`cat new > target`), сохраняя inode: `mv`
   создаёт новый inode, и bind-mount в контейнере продолжает видеть старый файл;
3. делает **бэкап** с меткой времени (`<файл>.bak-YYYYmmdd-HHMMSS`);
4. **валидирует** конфиг на проде: compose — `docker compose config --quiet`
   (с `do.env` в окружении, как это делает `do.sh`), nginx — `nginx -t` тем же
   nginx'ом, что в контейнере;
5. при ошибке валидации **откатывает** бэкап и завершает деплой с ненулевым кодом;
6. печатает, что обновлено.

Проверить, что на проде разошлось с репозиторием, можно и без деплоя:

```bash
cd deploy && source ./sync_prod_config.sh && sync_prod_config web
```

## 8. Модель управления allow-list админ-машины (BR-631)

§1–§7 описывают доставку конфигурации **вручную**. Для allow-list прод-канала
(`5433`/`9000`) появилась автоматика — спека 677 / KARAOKE-337, ADR
`knowledge/adr/local-0015-admin-ip-allowlist-automation.md`. Разница в модели:

| | Ручная доставка (§4) | Автоматизация allow-list |
|---|---|---|
| Кто меняет прод | человек | `deploy/admin-ip-allowlist.sh` под таймером (10 минут) |
| Что меняется | конкретный файл целиком | **только** одна строка `allow <ip>;` в каждом из двух stream-блоков |
| Порядок | копирование содержимым → `nginx -t` → reload → проверка ответа | перепроверка адреса → temp-файл → `nginx -t -c temp` → бэкап → подмена содержимым → проверка sha256 → `nginx -t` → reload → контроль → откат |
| Как попадает в репозиторий | копирование вручную | PR через Forgejo API (состав PR — репозиторная копия **плюс только недостающая строка `allow`**), сливает владелец |
| Откат | вручную из бэкапа | автоматически из `nginx.conf.bak-<stamp>`, затем уведомление владельцу |

### Что делать владельцу

1. **Установить юниты** (файлы лежат в репозитории, установка — действие владельца):

   ```bash
   cd /home/nsa/Karaoke
   sudo cp deploy/admin-ip-allowlist.timer deploy/admin-ip-allowlist.service /etc/systemd/system/
   sudo systemctl daemon-reload
   sudo systemctl enable --now admin-ip-allowlist.timer
   systemctl list-timers | grep admin-ip-allowlist
   ```

2. **Задать токены** — в файле с правами `600` (юнит читает его через
   `EnvironmentFile`): `/etc/admin-ip-allowlist.env`:

   ```
   ALLOWLIST_TELEGRAM_BOT_TOKEN=<токен бота проекта>
   ALLOWLIST_NOTIFY_CHAT_ID=<chat_id СЛУЖЕБНОГО чата для уведомлений>
   ALLOWLIST_FJ_TOKEN=<токен Forgejo>
   ALLOWLIST_FJ_URL=https://git.sm-karaoke.ru
   ```

   Токены в репозиторий не попадают (FR-016) и не видны в `ps` (Bot API вызывается
   через `curl -K` с конфиг-файлом `600`).

3. **ssh-доступ сервиса** — *желательно*, но не обязательно: механизм сам находит
   рабочий ключ (прецедент 2026-11-02: IP сменился, allow-list не обновился, прод-БД
   была недоступна 80 минут — виноват был `root` без ключа).

   Порядок выбора идентичности: явная настройка → кэш прошлого прогона → обычный `ssh`
   учётной записи сервиса → **автоподбор** ключа оператора админ-машины
   (`/home/*/.ssh/id_rsa|id_ed25519`), первый принятый продом запоминается в
   state-файле. Явная настройка нужна, если автоподбор не подходит (другой хост,
   нестандартный путь):

   ```
   ALLOWLIST_SSH_IDENTITY_FILE=/home/nsa/.ssh/id_rsa
   ALLOWLIST_SSH_KNOWN_HOSTS=/home/nsa/.ssh/known_hosts
   ALLOWLIST_SSH_STRICT_HOST_KEY=accept-new
   ```

4. **Проверить состояние без правок**: `bash deploy/admin-ip-allowlist.sh --diagnose`.

5. **Проверить, сможет ли таймер применить правку** (без правок):

   ```bash
   bash deploy/admin-ip-allowlist.sh --check-ssh
   # ожидается: event:check_ssh ok=true
   ```

   `ok=false` с `detail=…` — причина отказа (например `Permission denied (publickey)`
   или `Host key verification failed`). `identity_resolved=…` показывает, какая
   идентичность выбрана и откуда (`explicit` / `auto_or_cache` / `default`).

   Проверка **под учётной записью сервиса** (root) — то, что важно для таймера:

   ```bash
   sudo bash /home/nsa/Karaoke/deploy/admin-ip-allowlist.sh --check-ssh
   ```

   Проверено 2026-11-02 под root: дефолтного ключа у root нет, автоподбор нашёл
   `/home/nsa/.ssh/id_rsa` с его `known_hosts` — `event:ssh_identity source=auto`,
   `event:check_ssh ok=true`. Пара запоминается в state-файле
   (`ssh_identity=…`, `ssh_known_hosts=…`), поэтому **первый** прогон под новым service
   занимает дольше обычного (сначала неудачная попытка дефолтным ssh, затем перебор
   кандидатов — около 30 с), а дальше идентичность берётся из кэша.

### Где живёт allow-list админ-машины (все места!)

| Место на проде | Файл | Что ограничивает | Обновляет автоматика |
|---|---|---|---|
| stream-блоки 5433 (прод-БД) и 9000 (MinIO) | `/etc/nginx/nginx.conf` | L4-каналы к БД и MinIO | да |
| `location /changerecords` | `/etc/nginx/sites-enabled/80to8897` | эндпоинт двух-БД синхронизации (push одобренных правок на прод) | да (с 2026-11-02) |
| `location /api/properties/setproperty` | `/etc/nginx/sites-enabled/80to8897` | запись в публичные настройки | да (с 2026-11-02) |

**Инцидент 2026-11-02 (вечер):** автоматика обновила только stream-блоки, а
HTTP-локации остались со старым списком → nginx отдавал **403** на синхронизацию, и
одобренные редакторами песни не доезжали до прода («как будто не редактировали»).
Урок: список адресов живёт в нескольких файлах — правится должны **все** сразу.

Проверка после правки (без правок):

```bash
bash deploy/admin-ip-allowlist.sh --diagnose
```

Признак расхождения в репозитории — guard BR-631: «allow-list'ы в репозиторных копиях
РАСХОДЯТСЯ» (он же ловит, что в канон-копии попали не все адреса).

### Чего автоматизация не делает

* не удаляет адреса из allow-list (FR-011) — удаление только по слову владельца;
* не меняет ничего, кроме файла allow-list и его бэкапа (FR-015);
* не добавляет адрес, если прод недоступен целиком (FR-002);
* не включает `access_log` в stream-блоках (FR-019 — SHOULD, требует согласия на
  изменение прода);
* не сливает PR сама (Д-1).

### Если прод-хост недоступен по SSH (KARAOKE-382)

Симптом: в журнале `admin-ip-allowlist.service` — `event:skip reason=prod_unreachable_by_ssh`,
правка allow-list не применена. Прод при этом жив: `https://sm-karaoke.ru/health` — 200.

**Проверено на самом проде 2026-11-01 — фильтрации SSH на проде НЕТ:**
- `iptables -S`: политика `INPUT ACCEPT`, правил по порту 22 нет; `ufw` и `fail2ban`
  отсутствуют; `nftables` — только правила Docker;
- `sshd_config`: `Match Address`, `AllowUsers`, `DenyUsers` не заданы, `PermitRootLogin yes`;
- активные сессии `sshd` видны с адреса админ-машины — соединения доходят и работают;
- текущий внешний IP админ-машины (`185.26.28.199` на момент проверки) **уже есть** в
  allow-list прод-хоста (`/etc/nginx/nginx.conf`, оба stream-блока 5433/9000).

Значит, «прод недоступен по SSH» — это сеть между админ-машиной и продом: пул адресов
провайдера плавает, VPN переподключается, и в отдельные минуты соединения обрываются
на connect. В те же минуты недоступны и внешние HTTPS-сервисы определения адреса
(ipify/ifconfig/icanhazip — `unreachable`), а `checkip.amazonaws.com` отвечает: это
сетевой сбой, а не фильтрация.

**Как отличить «сеть» от «фильтрация»:** `ssh -vv root@188.127.240.124 true` — если
соединение установлено, но обмен ключами не идёт, это фильтрация на проде (по проверке
выше её нет); если `connect to address … port 22: Connection timed out` — до sshd пакет
не дошёл, вопрос в сети.

**Причина отказа теперь видна.** С 2026-11-02 stderr `ssh` не подавляется: последняя
строка ошибки попадает в журнал (`event:ssh_retry … detail=…`) и в уведомление.
Раньше в журнале было только `reason=prod_unreachable_by_ssh`, и отличить «нет
идентичности у учётной записи сервиса» от «сеть» было невозможно.

**Две разные причины, которые теперь различимы:**

| Симптом в журнале | Причина | Что делать |
|---|---|---|
| `detail=Permission denied (publickey)` | у учётной записи сервиса нет ключа для прода | задать `ALLOWLIST_SSH_IDENTITY_FILE` (см. «Что делать владельцу», п. 3) |
| `detail=Host key verification failed` | нет `known_hosts` (или ключ хоста сменился) | задать `ALLOWLIST_SSH_KNOWN_HOSTS` |
| `detail=Connection timed out` / `Connection refused` | сеть между машинами (пул провайдера, VPN) | см. ниже: это сетевой сбой, не фильтрация |

**Что сделано.** `run_ssh` делает до `ALLOWLIST_SSH_ATTEMPTS` (по умолчанию 3) попыток
с паузой `ALLOWLIST_SSH_RETRY_PAUSE` (5 с): кратковременный сетевой сбой больше не
выглядит как «прод недоступен» и не блокирует правку allow-list. Повтор идемпотентен —
чтение конфига и применение одной и той же строки `allow <ip>;`.

**Ограничение расследований.** sshd на прод-хосте **не пишет в journald**
(`journalctl _COMM=sshd` — пусто за сутки), поэтому ход SSH-сессий по журналу
прод-хоста не восстановить; источник фактов — журнал скрипта на админ-машине.

### Дрейф прод↔репозиторий

Если прод-конфигурация отличается от репозиторной копии, дрейф фиксируется в
журнале (`event:drift`) и сообщается владельцу, но применение не блокируется: прод —
операционная истина. В PR посторонние расхождения не выносятся — PR содержит
репозиторную копию плюс только недостающую строку `allow`.

### Смена адреса 2026-11-08: адрес берём у прода, в списке — один адрес

Инцидент: владелец 2026-11-08 — «и снова сменился айпишник, и снова на это не
отреагировало приложение правильно!». Приложение `karaoke-app` писало
`DB-CONNECT-001` к `188.127.240.124:5433` десятками раз в минуту: прод-БД закрыта
для админ-машины.

**Что показал журнал механизма.** Каждые 10 минут — `event=skip
reason=sources_disagree`: `api.ipify.org` и `ifconfig.me` отвечали через
VPN-туннель с ротацией адресов (`195.178.4.144…166`, новый адрес каждый цикл),
остальные четыре источника — через адрес ISP (`95.31.39.146`). Правило «все
источники должны совпасть» не давало применить правку **ни разу** за смену адреса.

**Как найти правильный адрес.** Прод знает наш адрес на том канале, который мы и
чиним: `SSH_CLIENT` в SSH-сессии к прод-хосту. Stream-журнал nginx на проде
(`access_log` в stream-блоках) подтвердил: и хост, и контейнер приложения приходят
к `188.127.240.124:5433/9000` с одного адреса `95.31.39.146`. Внешние сервисы
отвечали про маршрут админ-машины, а нужен был адрес маршрута к проду.

**Что изменено (спека 731).**

1. **Источник адреса** — приоритетно прод (`detect_prod_seen_address`), внешние
   сервисы — запасной путь; их расхождение больше не блокирует правку.
2. **В списке — ровно один текущий адрес** (решение владельца 2026-11-08). Прежние
   адреса удаляются: список «про запас» держал доступ открытым для всех, кто
   когда-либо был админ-машиной.
3. **Откат — из своего бэкапа для каждого файла.** Прежний код при неудачной
   контрольной проверке восстанавливал бэкап **последнего** файла в **первый**
   файл: `/etc/nginx/nginx.conf` получал содержимое файла сайта, `nginx -t` падал,
   и прод остался с нерабочей конфигурацией (восстановлено вручную 2026-11-08).

**Как проверить, что канал живой (без правок прода).**

```bash
# адрес, который видит прод:
ssh root@188.127.240.124 'echo $SSH_CLIENT'
# ответы сервисов определения IP (могут расходиться — это нормально):
for u in https://api.ipify.org https://icanhazip.com; do curl -fsS --noproxy '*' "$u"; echo; done
# состояние списка на проде (ожидается ровно одна строка allow в каждом блоке):
ssh root@188.127.240.124 "grep -cE '^\s*allow ' /etc/nginx/nginx.conf"
```

Если в проде больше одной строки `allow` — список надо свести к текущему адресу
