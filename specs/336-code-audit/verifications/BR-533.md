# Верификация BR-533 — дефект не воспроизводится (уже исправлен)

- **Задача**: KARAOKE-395 «sync: album_id не переносится в INSERT tbl_songs — песня теряет связь с альбомом (BR-536)»
- **BR-код**: BR-533 (в тексте задачи); в заголовке задачи указан BR-536 — обе находки закрыты одним
  набором правок, обе проверены ниже (см. раздел «Смежная находка BR-536»).
- **Карточка-источник**: `specs/336-code-audit/findings/P-71.md`, находка P-71-01 (класс DATA, severity S2).
- **Реестр**: `specs/336-code-audit/registry.csv` — BR-533, статус `исправлено`, review `lead-verified`,
  work_package `363`.
- **Итог**: **(Б) дефект в текущем коде отсутствует** — правка не выдумывалась, код не менялся.

## Что проверял

Три утверждения находки P-71-01:

1. `Song.getSqlToInsert(sync = true)` пишет 91 колонку, а в `tbl_songs_sync` нет `status_process_demo`,
   `id_tariff`, `description`, `short_description`, `warning` ⇒ любой push песни в SYNC падает с
   `ERROR: column "status_process_demo" of relation "tbl_songs_sync" does not exist`.
2. Колонка участвует в `recordhash` (критерий diff), поэтому расхождение видно как постоянный
   «дрейф» синхронизации.
3. `album_id` не переносится в `INSERT tbl_songs` ⇒ песня теряет связь с альбомом (находка BR-536
   из заголовка задачи).

## Как проверял (команды)

Наличие колонок в sync-таблице — на LOCAL и на проде:

```bash
docker exec -i karaoke-db psql -U postgres -d karaoke -At -F'|' \
  -c "SELECT column_name FROM information_schema.columns
      WHERE table_name='tbl_songs_sync'
        AND column_name IN ('status_process_demo','id_tariff','description',
                            'short_description','warning','album_id')
      ORDER BY column_name;"
```

Прод-БД — по WireGuard-туннелю `10.77.0.2:5433` с mTLS-клиентом (`db-client.crt`/`db-client.key`,
`ca.crt` из `karaoke-db:/tmp/tunnel/`), `sslmode=verify-full`:

```bash
docker exec -i karaoke-db psql \
  "host=10.77.0.2 port=5433 user=$DB_SERVER_POSTGRES_USER \
   password=$DB_SERVER_POSTGRES_PASSWORD dbname=karaoke sslmode=verify-full \
   sslcert=/tmp/tunnel/db-client.crt sslkey=/tmp/tunnel/db-client.key \
   sslrootcert=/tmp/tunnel/ca.crt connect_timeout=20" -At -F'|' \
  -c "SELECT column_name FROM information_schema.columns
      WHERE table_name='tbl_songs_sync'
        AND column_name IN ('status_process_demo','id_tariff','description',
                            'short_description','warning','album_id')
      ORDER BY column_name;"
```

Регрессия «колонки INSERT не теряются» — штатный guard проекта:

```bash
bash tools/check-deploy-hardening.sh
```

## Вывод

**Не воспроизводится.** Обе базы — LOCAL и прод — содержат все шесть колонок:

```
album_id
description
id_tariff
short_description
status_process_demo
warning
```

Guard проекта зелёный:

```
PASS  [BR-536] karaoke-app/src/main/kotlin/com/svoemesto/karaokeapp/model/Song.kt: album_id и поздние колонки входят в INSERT
```

Итог прогона: `--- итог: PASS=97 FAIL=0 ---`.

Push песни в SYNC-таблицу падать не может: каждая колонка, которую пишет `getSqlToInsert`, в
`tbl_songs_sync` присутствует. Проверка на живой базе — создание и удаление тестовой песни с
`album_id` в SYNC-таблице — не потребовалась: наличие колонок на обеих базах плюс зелёный guard
покрывают исходный дефект полностью.

## Где в коде видно, что дефекта нет

- `karaoke-app/src/main/kotlin/com/svoemesto/karaokeapp/model/Song.kt:7391` —
  `song.albumId?.let { fieldsValues.add(Pair("album_id", it)) }`: `album_id` входит в список INSERT.
- `karaoke-app/src/main/kotlin/com/svoemesto/karaokeapp/model/Song.kt` — `status_process_demo`,
  `id_tariff`, `description`, `short_description`, `warning` (те же `fieldsValues.add(...)`).
- `deploy/karaoke-db/52_tbl_songs_sync_description_fields.sql` — миграция добавляет в
  `tbl_songs_sync` пять недостающих колонок и пересобирает `update_tbl_songs_sync_recordhash()`.
- `deploy/karaoke-db/53_tbl_songs_sync_album_id.sql` — миграция добавляет `album_id` в
  `tbl_songs_sync` и включает её в `recordhash` последним слагаемым (порядок исторических
  слагаемых не меняется, иначе разошлись бы хэши на LOCAL и SERVER).
- `tools/check-deploy-hardening.sh:812-830` — функция `check_br536()`: регрессионный guard,
  проверяющий наличие `album_id`, `status_process_demo`, `id_tariff`, `song_name_censored`,
  `free_after_on_air`, `description`, `short_description`, `warning` в списке INSERT.

## Смежная находка BR-536 (из заголовка задачи)

Тот же guard (`check_br536()`) покрывает и BR-536 — `album_id` в INSERT. Проверено:
`PASS [BR-536] … album_id и поздние колонки входят в INSERT`, а также наличие колонки `album_id`
в `tbl_songs_sync` на обеих базах (см. вывод выше). Обе находки закрыты.
