# Research: Возврат выпадающего списка свободных слотов публикации в поле «Дата» (`SongEdit.vue`)

Технический контекст полностью определён существующим кодом и стеком проекта —
неразрешённых `NEEDS CLARIFICATION` в Technical Context плана нет. Ниже
зафиксированы решения по конкретным техническим вопросам, возникшим при чтении
текущей реализации и при анализе причин регрессии.

## Вопрос 1: Почему `<datalist>` перестал показываться в Chrome/Edge/Firefox — это регрессия фреймворка или поведение браузера?

**Decision**: Это документированное поведение современных браузеров — `<datalist>`
работает только когда у поля НЕ задействован собственный автокомплит браузера.
Если `<input>` не имеет атрибута `autocomplete="off"` (или `autocomplete="new-password"`,
что тоже подавляет), Chrome/Edge/Firefox показывают **сначала свой** dropdown
с историей заполнения поля, и datalist либо прячется под ним, либо не показывается
вовсе (зависит от версии браузера и ОС).

**Rationale**:
- Поведение воспроизводится на чистом HTML без JS — спецификация HTML Living Standard
  ([WHATWG](https://html.spec.whatwg.org/multipage/form-control-infrastructure.html#autofill))
  описывает автокомплит как «приоритетный» механизм подсказок, datalist — «опциональный»
  fallback.
- MDN рекомендует именно `autocomplete="off"` + уникальный `name` как канонический
  способ подавить browser-autofill для конкретного `<input>` (см. раздел
  «Autocomplete and the autocomplete attribute» на странице про `<input>`).
- Уникальный `name` важен: если у поля нет `name`, браузер всё равно может
  связать его с историей другого поля формы с тем же `name` (или безымянные
  поля могут попадать под общее правило); уникальный `name` явно отвязывает
  поле от любой «общей» истории.

**Alternatives considered**:
- Заменить `<input>` на `<input type="date">` / `type="datetime-local"` —
  отклонено: меняет UX (показ нативного datepicker), формат значения
  (`yyyy-MM-dd` vs `dd.MM.yy HH:mm`), требует миграции сохранения и форматирования
  `song.date`. Находится вне scope FR-006 («никаких изменений в логике сохранения/
  валидации, формате хранения»).
- Заменить `<datalist>` на кастомный bootstrap-vue-next `<BDropdown>` или
  `<select>` — отклонено: больше работы, требует нового компонента,
  UX-проработки, тестирования. Если минимальный фикс через `autocomplete="off"`
  окажется недостаточным в каком-то браузере — это будет отдельная спека
  с полным UX-редо. На текущей итерации минимальный фикс достаточен.
- Подавить автокомплит через JS (`input.setAttribute('autocomplete', 'off')` в
  `mounted`) — отклонено: менее надёжно (можно пропустить при пере-рендере),
  добавляет сайд-эффекты, требует JSDoc, нарушает NFR-001 («дифф только в
  одном файле, ≤25 строк»). Чисто HTML-атрибуты достаточно.

## Вопрос 2: Достаточно ли `autocomplete="off"` без `name`, или наоборот?

**Decision**: Применить **оба** атрибута: `name="song_date_field"` +
`autocomplete="off"` для поля «Дата»; `name="song_time_field"` +
`autocomplete="off"` для поля «Время».

**Rationale**:
- Надёжность: часть браузеров (особенно ChromeOS, мобильные Chrome) уважают
  только комбинацию `autocomplete="off"` + явный `name`; одного `autocomplete`
  без `name` может быть недостаточно, если браузер не может однозначно
  привязать поле к «не-истории».
- `name` всё равно нужен для `<input>` (стандартная практика форм), а в нашем
  случае `<form>` отсутствует — `name` используется только как идентификатор
  для браузерного autofill. Уникальные имена (`song_date_field`,
  `song_time_field`) исключают любое случайное пересечение с другими полями.
- Стоимость минимальная: 2 атрибута × 2 поля = 4 атрибута в diff, что укладывается
  в NFR-001 (≤25 строк).

**Alternatives considered**:
- `autocomplete="new-password"` — Chrome-специфичный трюк, не работает в Firefox/Safari
  одинаково. Отклонено.
- `autocomplete="chrome-off"` (Chrome-only) — в Firefox/Safari игнорируется,
  то есть не работает. Отклонено.

## Вопрос 3: Где в `SongEdit.vue` именно находятся проблемные `<input>` и что рядом?

**Decision**: Фикс — в строках 342 (Дата) и 359 (Время) исходного кода
(нумерация может сдвинуться после правки). Datalist-определения остаются в
строках 38-43 (`<datalist id="list_hours">` и `<datalist id="list_free_time_slots">`).

**Rationale**:
- Существующая структура `<datalist>` валидна, контент корректный (массивы
  `hours` (data) и `freeTimeSlots` (Vuex-геттер `getFreeTimeSlots` → API
  `/api/getfreetimeslots`) — оба потока данных работают, проверено чтением
  store.js:252-254 и Utils.kt:4787-4838).
- Менять datalist-определения не нужно — браузер отлично понимает связь
  `input[list="..."]` ↔ `datalist[id="..."]`. Проблема не в datalist, а в
  том, что браузерный autofill перебивает его подсказку.
- В исходных строках 38-43 каждый `<datalist>` занимает 2-3 строки — итоговая
  правка двух `<input>` (каждый в одну строку + комментарии) не конфликтует с
  существующим форматированием и сохраняет единообразный стиль кода.

**Alternatives considered**:
- Добавить `autocomplete="off"` ко всем `<input>` в `SongEdit.vue` —
  отклонено: расширяет scope за пределы FR-006 и SC-004 (дифф ≤25 строк);
  для полей «Исполнитель», «Альбом» и т.п. автокомплит браузера **полезен**
  (имена авторов, названия альбомов — это повторяющиеся значения). Не нужно
  ломать полезный UX в этих полях.

## Вопрос 4: Что с другими datalist-полями в проекте (`HomeView`, `SongsFilterModal`, `AlbumsFilterModal`, `AssignModal`, `SongEditorTable`)?

**Decision**: **НЕ трогать** их в рамках этой спеки.

**Rationale**:
- Все остальные datalist-поля используются для поиска по справочникам
  (имена авторов, словари, даты фильтрации), где контекст совсем другой:
  - пользователь обычно начинает ввод явно (печатает первые буквы имени),
    а не просто ставит фокус и ждёт подсказок;
  - регрессия «браузерный список вместо datalist» менее заметна, потому что
    дата/время — это конкретный формат, который часто пересекается с
    историей; имя автора — менее конфликтно;
  - пользовательского запроса на фикс этих полей не поступало.
- FR-006 спеки явно ограничивает фикс `SongEdit.vue`. Спека не претендует
  на полный аудит всех datalist в проекте — это разные UX-контексты и
  разные продуктовые решения (нужно ли подавлять браузерный автокомплит для
  поля «поиск по автору» — это отдельный вопрос, требующий обсуждения с
  пользователем).
- Если пользователь в будущем столкнётся с аналогичной проблемой в других
  datalist — будет отдельная спека (с возможно другим фиксом, например,
  кастомный combobox вместо `<input list>`).

**Alternatives considered**:
- Превентивный фикс всех datalist в одном PR — отклонено: scope creep,
  нарушает FR-006 и SC-004, не запрошено пользователем, требует отдельного
  обоснования и, возможно, отдельной UX-стратегии для полей поиска.

## Вопрос 5: JSDoc / KDoc требования Constitution FR-006

**Decision**: Изменение состоит **только из HTML-атрибутов** в шаблоне —
никаких новых `export default`, `function`, `const` на уровне JS. Существующие
JSDoc на компоненте `SongEdit.vue` (на `<script>`-блоке, на `data()`, на
`computed.freeTimeSlots`) остаются нетронутыми. JSDoc coverage не изменится.

**Rationale**:
- Текущая JSDoc coverage webvue3 — 100% (150/150) по
  `tools/check-jsdoc-coverage.sh webvue3`. Изменение не вводит новых
  символов, требующих документирования.
- Атрибуты HTML (`autocomplete`, `name`) задокументированы в самом
  изменении через комментарий-объяснение «почему» (в духе
  других мест `SongEdit.vue`, см. строку 178-180, 197-198, 622-625 и т.п.,
  где сложные места сопровождаются HTML-комментариями со ссылкой на спеку).

**Alternatives considered**: нет (изменение слишком маленькое для
альтернатив JSDoc).

## Вопрос 6: Какие проверки CI должны пройти после правки?

**Decision**: После реализации прогнать **локально** (per `AGENTS.md`,
раздел «Обязательная проверка после ЛЮБОГО изменения кода»):

1. **Линтеры**: `cd webvue3 && npm run lint` — никаких новых нарушений.
2. **Prettier**: `cd webvue3 && npx prettier --check
   "src/components/Songs/edit/SongEdit.vue"` — стиль соблюдён.
3. **Vite build**: `cd webvue3 && npm run build` — успешная сборка.

Kotlin-компиляция и Docker-образы **не запускаются** — наш diff только во
Vue-шаблоне, кросс-импортов нет, `karaoke-app`/`karaoke-public` не затронуты.
Это соответствует Pass 245 из `AGENTS.md` («Vite-build на хосте ≠ multi-stage
Docker: COPY ./webvue3/ . копирует ТОЛЬКО webvue3; кросс-импорты падают
внутри контейнера»): поскольку изменение не содержит кросс-импортов, локальный
`npm run build` достаточен.

**Rationale**:
- Минимальный diff (≤25 строк) в одном `.vue`-файле не может сломать
  backend, другой фронт, Docker-сборку.
- NFR-002 и NFR-003 спеки прямо требуют прохождения ESLint/Prettier/Vite
  без новых нарушений.

**Alternatives considered**:
- Прогнать все 5 шагов из `AGENTS.md` (включая Docker-образы) — отклонено:
  шаги 1 (Kotlin compile), 5 (Docker webvue3/public) избыточны для
  изолированного frontend-template-фикса без кросс-импортов. Это
  подтверждается текстом AGENTS.md, который подчёркивает важность Docker
  именно в контексте кросс-импортов (`Pass 245`).

## Вопрос 7: Нужен ли отдельный per-feature документ `docs/features/<slug>.md` (FR-009 Конституции)?

**Decision**: **Нет**, новый документ не заводится. Существующий
`livedocs/features/156-publish-slots-range.md` обновляется точечно
(одной правкой в секции «История» + одной ссылкой в начале), чтобы
отразить, что регресс datalist-маскировки закрыт фиксом 268.

**Rationale**:
- FR-009 Конституции требует per-feature документ при правке кода одной
  из 24 ключевых подсистем из `docs/features/README.md`. `SongEdit.vue`
  формально не входит в этот реестр (ближайший — `songs-table.md`, но
  тот — про таблицу песен, не про форму редактирования).
- Тем не менее, фронт-фикс datalist-маскировки логически связан с
  серверной фичей 156 (это её UI-потребитель). Поэтому корректное место
  для ссылки — **существующий** LiveDoc 156, а не новая запись в реестре.
- Минимальный diff, минимальный overhead на документацию.

**Alternatives considered**:
- Создать `docs/features/268-song-edit-date-datalist.md` —
  отклонено: добавляет обслуживающий груз для одно-строчного фикса;
  пользователь может создать отдельный документ позже, если потребуется.
- Ничего не документировать — отклонено: нарушает FR-009 в части
  актуализации существующего LiveDoc 156 (где упоминается `SongEdit.vue`,
  но не упоминается фронт-фикс datalist).

## Итог

Все технические вопросы разрешены. Подход:

1. Добавить `name="song_date_field"` + `autocomplete="off"` к `<input v-model="song.date" ...>`.
2. Добавить `name="song_time_field"` + `autocomplete="off"` к `<input v-model="song.time" ...>`.
3. К каждому изменению — HTML-комментарий со ссылкой на спеку и кратким объяснением.
4. Обновить `livedocs/features/156-publish-slots-range.md` (ссылка на спку 268 + правка пути `SongEdit.vue` → `edit/SongEdit.vue`).
5. Прогнать ESLint + Prettier + Vite build локально.

Никаких изменений в backend, store, API, других datalist-полях.
