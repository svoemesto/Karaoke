# Research: Изоляция соединений с БД по потокам + устойчивость очереди к сетевым сбоям

**Feature**: [spec.md](./spec.md) | **Plan**: [plan.md](./plan.md)

Technical Context не содержит открытых `NEEDS CLARIFICATION` — стек и
архитектура уже зафиксированы существующим кодом. Задача Phase 0 для этой
фичи — диагностика первопричины (баг-фикс по реальному инциденту) и выбор
подхода к исправлению, а не выбор технологий.

## Кандидат A — `ThreadLocal` вместо общего поля в `KaraokeConnection` (главный фикс, US1)

**Находка**: `KaraokeConnection.getConnection()` (`KaraokeConnection.kt:14-25`):

```kotlin
@Volatile private var connection: java.sql.Connection? = null

@Synchronized
fun getConnection(): java.sql.Connection? {
    val conn = connection
    if (conn == null || conn.isClosed || !conn.isValid(3)) {
        connection = DriverManager.getConnection(url, username, password)
    }
    return connection
}
```

`@Synchronized` защищает только сам момент выдачи/пересоздания соединения —
НЕ защищает использование уже полученного `Connection` после возврата из
метода. `WORKING_DATABASE = Connection.local()` (`Constants.kt:204`) —
**единственный** такой инстанс на всё приложение, и его `connection`
переиспользуется буквально всеми потоками: 43 файла в `karaoke-app`
напрямую обращаются к `WORKING_DATABASE`, включая:
- `KaraokeProcessWorker.doStart()` — выделенный поток очереди заданий,
  причём обращения к БД там очень частые: сохранение diff'а прогресса на
  **каждой итерации** главного `while(isWork)`-цикла
  (`KaraokeProcessWorker.kt:938`, `958`, `970` — три отдельных вызова
  `.save()` в разных ветках одной итерации).
- Каждый HTTP-запрос почти любого контроллера (`ApiController`,
  `MainController`, ...), выполняемый на одном из потоков пула Tomcat.

`java.sql.Connection`/`Statement` в PostgreSQL JDBC не поддерживают
конкурентное использование из разных потоков — при пересечении по времени
двух обращений к одному и тому же физическому TCP-соединению драйвер
получает рассинхронизированный ответ сервера, что и проявляется как
`SocketTimeoutException: Read timed out` в одном потоке и `PSQLException:
Соединение уже было закрыто` в другом (реальный лог с admin-машины,
2026-07-30, `KaraokeProcess.save():361` ← `doStart():970`, одновременно с
`Song.loadListFromDb():7258` ← `Pictures.toDTO()` ← HTTP-запрос
`apisPicturesDigest`). Ошибка в `doStart()` необработанно всплывает и роняет
главный цикл очереди (см. Кандидат B).

**Важная деталь**: KDoc класса `Connection` (`Connection.kt:18-21`)
**неверно** описывает поведение как «stateless wrapper... НОВОЕ соединение
при каждом вызове... закрывайте через `withDb{}`». Это описывает другой,
более новый и безопасный паттерн — приватные хелперы `withDb{}` в
`SponsrSyncController`/`SiteUsersController` (создают свежий `Connection` на
запрос через `resolveDb(target)`, закрывают в `finally`) — реально
используемый только в этих двух контроллерах, не в основном пути
(`WORKING_DATABASE`). Документация описывает желаемое общее поведение,
которое не было последовательно реализовано во всём приложении.

**Decision**: заменить `@Volatile private var connection` на
`ThreadLocal<java.sql.Connection?>` в `KaraokeConnection` — каждый поток
(HTTP-поток Tomcat, поток `KaraokeProcessWorker`, поток любого другого
фонового исполнителя) получает и переиспользует **своё** физическое
соединение, с той же логикой self-healing (`isClosed`/`isValid(3)` →
`DriverManager.getConnection(...)` заново) — только теперь per-thread, а не
глобально. Метод и его сигнатура (`fun getConnection(): java.sql.Connection?`)
не меняются — прозрачно для всех 43 вызывающих мест (FR-007). Каждый
`KaraokeConnection`-инстанс (`WORKING_DATABASE`, а также любые
`Connection.local()/remote()/virtual()`, создаваемые «на лету» в
`withDb{}`-паттерне) получает свой собственный `ThreadLocal`, поэтому
LOCAL/SERVER/VIRTUAL не путаются между собой даже в рамках одного потока
(каждый инстанс класса — своё `ThreadLocal`-поле).

**Ёмкость (число одновременных соединений)**: с `ThreadLocal` верхняя
граница числа физических соединений = число различных потоков, когда-либо
обращавшихся к данному `KaraokeConnection`-инстансу. Для `WORKING_DATABASE`
это практически = число активных потоков пула Tomcat (`server.tomcat.threads.max`,
по умолчанию Spring Boot — 200, в проекте не переопределено, проверено в
`application.yml`) + 1 (поток очереди) + единицы (Spring `@Scheduled`-пул,
по умолчанию 1 поток без явного `TaskScheduler`-бина). PostgreSQL в этом
проекте — `max_connections=100` (проверено `SHOW max_connections` на
dev-стенде, дефолт образа `postgres:16`, явно не переопределён в
`docker-compose-database.yml`). Теоретически 200 Tomcat-потоков могут
превысить лимит 100 — практически для self-hosted инструмента с одним
оператором такая конкурентность крайне маловероятна, но граница
существует. Решение — задать `server.tomcat.threads.max` консервативно
(например, 50) в `application.yml`, чтобы держать заведомый запас под
лимитом `max_connections`, не вводя отдельный механизм лимитирования числа
кешируемых соединений (что вернуло бы сложность полноценного пула, которую
сознательно избегаем — см. Alternatives).

**Alternatives considered**:
- **Настоящий пул соединений (HikariCP)** — отклонено для этого фикса:
  `spring-boot-starter-jdbc`/`starter-data-jpa` не подключены (Principle II,
  сырой JDBC), сейчас нет ни одной зависимости с пулом
  (`grep hikari` → пусто). Переход на пул потребовал бы: (а) добавить
  зависимость и настройку `DataSource`, (б) аудит и правку **всех** мест,
  которые сейчас держат `WORKING_DATABASE.getConnection()` открытым без
  `close()` (это большинство из 43 файлов) на borrow/return через
  try-with-resources — на порядок больший blast radius, чем позволяет
  точечный фикс инцидента. `ThreadLocal` даёт тот же практический эффект
  (нет конкурентного доступа к одному соединению) без этой переделки.
- **Синхронизация доступа к самому соединению** (например, общий
  `ReentrantLock` вокруг каждого запроса к `WORKING_DATABASE`) — отклонено:
  превращает и без того частые обращения потока очереди в узкое место,
  сериализуя вообще все запросы к БД во всём приложении через один лок;
  `ThreadLocal` даёт настоящий параллелизм без сериализации.
- **Connection per request** (создавать новый `java.sql.Connection` на
  каждый вызов, без кеширования) — отклонено: это именно то поведение,
  которое (согласно комментарию `Connection.kt`) уже когда-то приводило к
  «too many clients»; текущее кеширование намеренно, менять его — не цель
  этого фикса (см. Performance Goals в `plan.md`).

## Кандидат B — ограниченный retry с нарастающей паузой вокруг главного цикла очереди (US2)

**Находка**: `KaraokeProcessWorker.start()` (`KaraokeProcessWorker.kt:498-541`)
уже оборачивает `doStart()` в `try/catch/finally` (введено
specs/029-fix-queue-lane-stall) — при необработанном исключении лог
пишется, `isWork` гарантированно сбрасывается в `false`, шлётся
`sendStateMessage()`. Это НЕ оставляет зомби-состояние (цель 029), но и не
пытается возобновить работу — очередь остаётся остановленной до тех пор,
пока `RenderQueueStalledCheck` (`monitor/checks/RenderQueueStalledCheck.kt`,
тик раз в минуту) не покажет алерт и оператор не кликнет resolve
(`KaraokeProcessWorker.start(...)` заново).

**Decision**: обернуть текущий `Thread { try { doStart(...) } catch...
finally {...} }` в ограниченный цикл повторных попыток с нарастающей паузой
между ними (например: до 5 попыток, пауза 2с → 5с → 15с → 30с → 60с) —
после каждого падения `doStart()`, если попытки не исчерпаны, ждать паузу и
запустить `doStart()` заново (внутри того же демон-потока, без создания
нового `Thread`), не сбрасывая `isWork` между попытками (чтобы UI не мигал
«остановлено → снова работает» на каждую короткую заминку). Только после
исчерпания всех попыток — сработать существующий `finally` (`isWork=false`,
`sendStateMessage()`), и `RenderQueueStalledCheck` подхватывает как и
раньше. Реализация — правка только внутри `start()`, `doStart()` и
остальной код очереди не меняются.

**Alternatives considered**:
- **Немедленный бесконечный retry без паузы/лимита** — отклонено: при
  длительной недоступности БД (например, реальный даунтайм) это создаст
  безостановочный цикл попыток подключения, впустую расходующий CPU и лог
  (нарушает FR-006 `spec.md`).
- **Retry на уровне отдельных DB-вызовов внутри `doStart()`** (а не на
  уровне всего цикла) — отклонено как избыточно инвазивное для точечного
  фикса: `doStart()` — одна огромная функция с десятками мест обращения к
  БД; оборачивать каждое в try/retry — на порядок больший blast radius, чем
  retry всего цикла целиком на верхнем уровне. Кроме того, Кандидат A
  устраняет главный источник самих сбоев — retry в `start()` остаётся
  защитной сеткой на случай **любых прочих** непредвиденных ошибок, не
  основным механизмом.
- **Полагаться только на существующий `RenderQueueStalledCheck`** (ничего
  не менять в `start()`) — отклонено по прямому требованию `spec.md` (US2,
  FR-005): оператор не должен ждать до минуты и кликать вручную на каждый
  короткий сетевой сбой, если система может самостоятельно восстановиться
  за секунды.

## Итоговый подход

1. `KaraokeConnection.getConnection()`: `@Volatile var` → `ThreadLocal`
   (Кандидат A) — устраняет корневую причину, покрывает FR-001/FR-002/FR-003/FR-004.
2. `KaraokeProcessWorker.start()`: ограниченный retry с нарастающей паузой
   вокруг `doStart()` (Кандидат B) — покрывает FR-005/FR-006, сохраняет
   существующий safety-net как резерв.
3. Дополнительно — консервативно задать `server.tomcat.threads.max` в
   `application.yml`, чтобы держать запас под `max_connections` PostgreSQL
   (сопутствующая мера ёмкости для Кандидата A).
4. Поправить неверный KDoc класса `Connection` (`Connection.kt:18-21`), не
   соответствующий фактическому поведению `WORKING_DATABASE`.

Все пункты — точечные правки внутри уже существующих файлов, без новых
зависимостей, без миграций схемы БД, без изменений фронтенда/HTTP-контракта.
