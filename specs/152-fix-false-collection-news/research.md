# Phase 0 Research: Ложное срабатывание новости «в коллекции» после синхронизации

Все пункты Technical Context в plan.md были известны заранее из существующего стека проекта
(constitution.md) — открытых `NEEDS CLARIFICATION` не осталось. Ниже — исследование самой
проблемы (root cause) и обоснование выбранного решения, основанное на верифицированном
чтении текущего кода (`codegraph_explore`, актуальный `master`).

## Как воспроизводится баг сегодня

Код (`MainController.doChangeRecords`, karaoke-web):

```kotlin
dataUpdate.forEach { action ->
    ...
    if (tableName == Song.TABLE_NAME) {
        songAvailabilityBefore.add(idRecord.toLong() to Song.readNewsAvailableFlag(idRecord.toLong(), WORKING_DATABASE))
    }
    // ... затем реально выполняется UPDATE
}
...
songAvailabilityBefore.forEach { (songId, wasAvailableBefore) ->
    SongReleaseAnnouncementService.detectAndAnnounceAvailability(..., songId = songId, wasAvailableBefore = wasAvailableBefore)
}
```

`Song.readNewsAvailableFlag` читает `player_readiness_flags` **той же строки, на которую
сейчас будет применён входящий `UPDATE`, на целевой (принимающей) базе** — то есть значение,
которое ДО ЭТОГО МОМЕНТА было известно именно этой копии БД, а не некий глобальный факт
«когда именно флаг стал истинным в реальности».

`detectAndAnnounceAvailability`:

```kotlin
fun detectAndAnnounceAvailability(..., wasAvailableBefore: Boolean): Boolean {
    if (wasAvailableBefore) return false
    val song = Song.loadFromDbById(songId, ...) ?: return false
    if (!song.newsAvailableAnnounced) return false
    News.createAutoAnnouncement(..., category = "premium", ...)   // ← без проверки на дубликат!
    return true
}
```

Два независимых дефекта складываются в один наблюдаемый баг:

1. **«До» — не факт из реального мира, а состояние конкретной копии БД.** Если целевая база
   (в инциденте — судя по формулировке «после синхронизации локал-сервер», это SERVER, на
   которой и выполняется `doChangeRecords`) по любой причине узнаёт актуальное значение
   флага `newsAvailableAnnounced` **впервые именно сейчас** — будь то из-за того, что
   разовый Kotlin-backfill (`backfillNewsAvailableFlag`, specs/101) в своё время не покрыл
   эти 3 записи, будь то из-за того, что предыдущий push этого конкретного поля по каким-то
   причинам не прошёл — код не может отличить «песня только что стала доступна» от «база
   только что узнала о давно случившемся факте». Оба случая дают одинаковый локальный
   переход `false → true`.
2. **Нет защиты от дублей.** В отличие от `checkOnAirWindow` (проверяет
   `News.existsAnnouncement(..., category="air", ...)` перед созданием), у
   `detectAndAnnounceAvailability` такой проверки нет вовсе — единственная «защита» это
   пункт 1, которая, как показано выше, ненадёжна.

**Наблюдение из инцидента, объясняющее природу этих 3 песен**: перед ложной новостью «в
коллекции» по тем же песням уже вышла (корректно) новость «в эфире». Публикация «в эфире»
(`checkOnAirWindow`) требует `isPubliclyWatchable`, что подразумевает полную готовность
контента — то есть на момент выхода «в эфире» флаг `newsAvailableAnnounced` **логически уже
обязан быть истинным**. Появление «в коллекции» ПОСЛЕ «в эфире» для той же песни — это
само по себе достаточный признак того, что событие не новое.

## Решения

### Decision 1: Идемпотентность через `News.existsAnnouncement`, как у «в эфире»

**Что**: перед `News.createAutoAnnouncement(..., category="premium", ...)` в
`detectAndAnnounceAvailability` добавить проверку
`if (News.existsAnnouncement(songId, link, category="premium", database)) return false`.

**Почему**: это тот же самый паттерн, что уже используется и проверен в
`checkOnAirWindow` для категории `"air"` — минимальное расхождение с существующим кодом,
никакой новой инфраструктуры. Гарантирует FR-003/FR-004 (ни одна песня никогда не получит
вторую новость «в коллекции»), независимо от того, сколько раз/с какой стороны
обнаруживается транзиция.

**Альтернативы**:
- Отдельная таблица учёта (по образцу удалённой `tbl_song_news_announced`) — отклонено:
  тот же паттерн уже был признан избыточным и удалён в specs/101 (`tbl_news` сам себе
  журнал через `category`/`song_id`); повторное введение — шаг назад.

### Decision 2: Содержательный гейт «уже была новость "в эфире" → не публиковать "в коллекции"»

**Что**: перед созданием новости «в коллекции» дополнительно проверить
`News.existsAnnouncement(songId, link, category="air", database)` — если true, не создавать
новость «в коллекции» (событие уже не может быть «новым»: on-air ⇒ давно в коллекции).

**Почему**: единственный способ отличить «песня только что стала доступна» от «база только
что узнала об этом с опозданием», не добавляя нового состояния в схему — использовать уже
существующий, надёжный сигнал о том, что песня точно не новая: наличие новости «в эфире».
Это прямое кодирование доменного инварианта, выявленного из самого репортованного
инцидента (спецификация, раздел Assumptions).

**Альтернативы**:
- Добавить в `player_readiness_flags` метку времени `newsAvailableAnnouncedAt`/аналог и
  сравнивать с неким порогом «давности» — отклонено: требует определения произвольного
  порога («сколько часов считать «давно»?») и не решает проблему для песен, у которых нет
  даты эфира вовсе (публикуются без она «в эфире»/без Telegram); также усложняет формулу без
  выигрыша, так как сигнал «air уже есть» уже достаточен для конкретно этого класса
  инцидентов и строго безопаснее (никогда не подавляет реально новое событие для песни,
  ещё не вышедшей в эфир).
- Сверять с `Song.isContentReady`/`isPubliclyWatchable`, вычисленными на **исходной**
  (не целевой) базе, откуда пришёл sync-батч — отклонено: `doChangeRecords` получает уже
  сериализованные/зашифрованные SQL-фрагменты, а не объект `Song` с исходной базы;
  реконструкция «какой была исходная база» потребовала бы менять формат sync-протокола
  (нарушение Principle III — «не менять то, что синхронизируется»).

### Decision 3: Существующий before/after diff в `doChangeRecords` — остаётся, но как fast-path, не как гейт корректности

**Что**: `Song.readNewsAvailableFlag`/`songAvailabilityBefore` в `doChangeRecords` не
удаляются — они по-прежнему дёшево отсеивают строки, где флаг локально уже был `true`
(экономит `loadFromDbById` полного `Song` для большинства строк батча). Но решение
«создавать новость или нет» теперь принимается внутри
`detectAndAnnounceAvailability` через Decision 1+2, а не через этот флаг.

**Почему**: сохраняет текущие перформанс-характеристики (Principle II — не грузить полные
записи без необходимости) без отказа от единственного надёжного источника истины.

### Decision 4: Схема БД не меняется

**Что**: `tbl_news` уже имеет `category`/`song_id`/`link` (используются `existsAnnouncement`
уже сегодня); `player_readiness_flags` уже имеет `newsAvailableAnnounced`. Новых колонок,
таблиц, `recordhash`-триггеров не требуется.

**Почему**: Principle II/III (минимальный footprint синхронизируемой схемы) и прямое
следование прецеденту specs/101, где та же логика уже была применена (флаг — существующий
JSON-ключ, не новая колонка).

### Decision 5: Валидация — ручной replay инцидента на LOCAL-сэндбоксе

**Что**: в CI нет автотестов для этой области (constitution.md, «Тесты: в CI нет»).
Проверка — ручной сценарий (см. [quickstart.md](./quickstart.md)): смоделировать «целевая
БД содержит песню с давно истинной готовностью контента, но локально ещё не видела флаг
`newsAvailableAnnounced=true`», прогнать батч `doChangeRecords`, убедиться в отсутствии
новой строки `tbl_news`.

**Почему**: соответствует зафиксированной практике проекта; полноценный интеграционный тест
с реальным LOCAL↔SERVER sync потребовал бы двух живых БД и сетевого запроса — избыточно
для точечного фикса одного метода.
