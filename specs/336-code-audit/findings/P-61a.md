## Сверки (спорное, без severity)

1. **Guard премиум-статуса и реальный FAILED.** Даже после исправления P-61-01 ветка «Ошибка отправки» останется недостижимой: `PremiumAutoPublishScheduler` при исчерпании попыток выставляет `newsPremiumPublishPending=false` и `premiumAutoPublishState="FAILED"` (`services/PremiumAutoPublishScheduler.kt:311–315`), а guard (`SongEdit.vue:2742`, `:2784`) при `pending=false && sent=false` возвращает `null`. Вопрос: должен ли guard учитывать `premiumAutoPublishState === "FAILED"` (тогда FR-007/FR-008 станут выполнимы) или планировщик должен оставлять `pending=true`? Ответ нужен до правки, иначе P-61-01 закроют «вхолостую».
2. **Лимит попыток захардкожен.** `premiumAutoPublishMaxAttempts()` возвращает `3` (`SongEdit.vue:2822–2824`), тогда как сервер читает настраиваемое `KaraokeProperties.getLong("premiumAutoPublishMaxAttempts")` с дефолтом 3 (`KaraokeProperties.kt:2324–2328`, `PremiumAutoPublishScheduler.kt:365`). Сейчас код мёртв из-за P-61-01; после его исправления при значении свойства ≠ 3 бейдж «Ошибка отправки» и кнопка «Повторить» будут появляться не в тот момент. Спорно: тянуть свойство на фронт или считать статус по `premiumAutoPublishState`/`lastError` с сервера.
3. **Часовой пояс бейджа AIR-публикации.** `telegramPublishState` собирает дату через `new Date(year, month-1, day, hour, minute)` (`SongEdit.vue:2704–2712`) — это локальная зона браузера, а бэкенд парсит `dd.MM.yy HH:mm` явно в `Europe/Moscow` (`Song.kt:644–662`). Для админа вне MSK бейдж «Запланирована/Опоздавшая» может расходиться с решением бота; задумано ли, что админка эксплуатируется только в MSK?
4. **Мутация `saveSong` не проверяет id.** `saveSong(state, savedParams)` сливает параметры в текущий `snapshotSong` без сверки `savedParams.id` с `state.currentSong.id` (`Songs/store.js:1206–1232`). Если ответ на сохранение песни A придёт после переключения на B, snapshot B получит значения A: B подсветится как «изменённая», а `undoField` в B вернёт значение A. Корень — `store.js` (порция P-63) и `executeSave` (часть 2); в моём диапазоне только watcher, который ставит отложенный save. Передаю лиду для дедупликации.
5. **Замечено вне диапазона 1–3300 (указатели для части 2 / P-63, без severity).** (а) `publishToVkNow` берёт `currentSongId` на момент клика (`:4401`), но по ответу делает `setCurrentSongField({name:'idVk', value:data.postId})` (`:4429–4431`) в **текущую** песню — при переключении во время рендера/публикации (минуты) id поста чужой песни уйдёт в новую и будет сохранён автосейвом; (б) `deleteSong`/`copyFieldsFromAnother`/`createPicture*` подставляют `songName` в `customConfirmParams.body` (`:4134`, `:5037`), а `CustomConfirm.vue:6` рендерит `params.body` через `v-html` — потенциальный stored XSS по имени песни; (в) `showSubsEdit` (`:5047–5049`) грузит `getVoices` по `currentSongId` и только затем открывает модалку — при смене песни между кликом и ответом откроется чужой набор голосов.
6. **`v-html`-синки диапазона.** `textFormatted`/`notesFormatted`/`chordsFormatted` (`:2431`, `:2436`, `:2441`) — HTML, собранный на бэкенде (`Song.getTextFormatted/getFormattedNotes/getFormattedChords`). Неэкранированные `originalKey`/`newKey`/`noteOctave` уже описаны в **P-18-16** (S3, defense-in-depth; путь сейчас блокируется NPE P-18-01/P-18-06), поэтому отдельной записи здесь нет — не дубль, а ссылка на существующую.
