# Feature Specification: Локальная Jira для AI-агента

**Feature Branch**: `295-jira-local-integration`
**Created**: 2026-09-02
**Status**: Draft
**Input**: User description: "Работа с Jira. Надо локально установить и настроить Jira так, чтобы я мог заводить в ней задания, а ты их видеть, брать, исполнять в рамках отдельных спецификаций, а по окончанию - писать в джире отчёт по проделанной работе и закрывать задачу."

## Clarifications

### Session 2026-09-02

- Q: Какую стратегию бэкапа Postgres для Jira выбрать? → A: **A — ежедневный `pg_dump` в volume `jira-backups` с ротацией 7 дней** через `tools/jira-backup.sh`; restore — `pg_restore` / `psql -f dump.sql`.
- Q: Какой уровень логирования нужен для MVP? → A: **B — `docker logs jira` + структурированный лог CLI-агента `logs/jira-agent.log` с ротацией** (timestamp, команда, request-id, response code, длительность).
- Q: Как CLI должен реагировать на HTTP 429 от Jira API? → A: **B — экспоненциальный backoff 2s → 4s → 8s, до 3 retry, затем ошибка пользователю**.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Пользователь заводит задачу в Jira (Priority: P1)

Пользователь открывает локальный веб-интерфейс Jira (например, `http://jira.localhost:8080` или `http://localhost:8080`), создаёт новую задачу (тип Issue: Task / Story / Bug), заполняет заголовок, описание, приоритет, прикладывает ссылки на spec (`specs/<NNN>-*/spec.md`) или произвольные указания. Задача создаётся в проекте по умолчанию и появляется в Backlog.

**Why this priority**: Без возможности создать задачу пользователем вся остальная цепочка не имеет смысла. Это отправная точка workflow.

**Independent Test**: Открыть Jira UI → создать Issue типа Task с заголовком "Test task" → убедиться, что задача видна в backlog, имеет уникальный ключ (например, `KARAOKE-1`), сохраняется между перезапусками контейнера.

**Acceptance Scenarios**:

1. **Given** Jira запущена локально и пользователь авторизован, **When** пользователь создаёт новую Task с заголовком "Spec X: реализовать Y", **Then** задача получает ключ `KARAOKE-N`, появляется в backlog, доступна по прямой ссылке и видна через REST API.
2. **Given** Jira запущена, **When** пользователь вводит описание задачи с markdown-разметкой и ссылками, **Then** описание рендерится корректно в UI и доступно через REST API в виде структурированного ADF (Atlassian Document Format) или wiki-markup.
3. **Given** Jira запущена, **When** пользователь перезапускает docker-контейнер Jira, **Then** все ранее созданные задачи сохраняются (источник истины — внешний Postgres).

---

### User Story 2 - AI-агент видит задачи, назначенные на него, и берёт их в работу (Priority: P1)

AI-агент (через CLI / MCP / спец-скрипт) периодически или по запросу пользователя обращается к Jira REST API с персональным API-токеном, получает список задач со статусом `Open` / `To Do`, назначенных на аккаунт агента (например, `ai-agent` или конкретный пользователь). Агент читает описание, прикреплённую спецификацию, и приступает к исполнению в рамках отдельной спецификации (если её ещё нет — создаёт).

**Why this priority**: Это ядро интеграции — без двусторонней связи "пользователь → задача → агент" фича бесполезна.

**Independent Test**: Создать 3 задачи, 1 из них назначить на аккаунт `ai-agent` → запустить команду агента `jira fetch-assigned --user ai-agent` → получить список с одной задачей → перевести её в статус `In Progress` → убедиться, что изменение видно в UI.

**Acceptance Scenarios**:

1. **Given** у агента есть валидный API-токен и он знает `BASE_URL` Jira, **When** агент запрашивает список задач в статусе `Open` на своего пользователя, **Then** возвращается структурированный список (key, summary, description, priority, assignee).
2. **Given** агент получил задачу, **When** агент выполняет команду `claim-issue <KEY>`, **Then** статус задачи меняется на `In Progress`, в историю добавляется запись о смене assignee/status.
3. **Given** агент взял задачу, **When** пользователь открывает её в UI, **Then** он видит текущий статус `In Progress` и assignee = AI-агент.

---

### User Story 3 - Агент исполняет задачу и пишет отчёт по окончанию (Priority: P1)

Агент выполняет задачу (обычно — реализует спецификацию, описанную в описании задачи или в прикреплённой `spec.md`). По окончанию (или по явному запросу) агент публикует в задаче комментарий-отчёт: что было сделано, какие файлы изменены, какие тесты прошли, какие ограничения / известные проблемы, и переводит задачу в статус `Done` (или `Closed`).

**Why this priority**: Замыкает цикл. Без отчёта и закрытия задачи пользователь не знает о завершении и не может продолжить работу.

**Independent Test**: Агент берёт задачу "Fix X" → правит код → запускает тесты → вызывает `jira report <KEY> --file report.md` → вызывает `jira close <KEY>` → пользователь открывает задачу и видит комментарий с отчётом и статус `Done`.

**Acceptance Scenarios**:

1. **Given** агент выполнил задачу, **When** агент публикует отчёт через REST API, **Then** в задаче появляется комментарий с полным описанием проделанной работы, ссылками на изменённые файлы / PR, статус задачи остаётся `In Progress` до явного `close-issue`.
2. **Given** агент публикует отчёт, **When** пользователь открывает задачу, **Then** он видит комментарий в хронологическом порядке, отчёт читаем (markdown рендерится) и содержит достаточно информации, чтобы понять результат без чтения кода.
3. **Given** отчёт опубликован, **When** агент вызывает `close-issue <KEY>`, **Then** статус задачи меняется на `Done`, в истории фиксируется transition, и пользователь видит это в UI.

---

### User Story 4 - Агент создаёт спецификацию на основе задачи (Priority: P2)

Если в описании задачи есть указание "создать спецификацию" или задача содержит высокоуровневое требование (без чёткой спеки), агент запускает workflow `/speckit.specify`, создаёт директорию `specs/<NNN>-<slug>/`, пишет `spec.md` и ссылку на новую спеку добавляет в задачу как комментарий.

**Why this priority**: Полезно, но не критично — пользователь может сразу прикладывать готовую ссылку на спеку.

**Independent Test**: Создать задачу с описанием "Сделай спецификацию для фичи X" → агент запускает `/speckit.specify` → создаётся `specs/<NNN>-x/spec.md` → в задаче появляется комментарий со ссылкой на созданную спеку.

**Acceptance Scenarios**:

1. **Given** задача содержит фразу "создать спецификацию" или эквивалент, **When** агент её берёт, **Then** он запускает `/speckit.specify` с описанием из задачи и создаёт новую spec-директорию.
2. **Given** новая спецификация создана, **When** агент публикует обновление в задаче, **Then** в комментарии появляется относительная ссылка `specs/<NNN>-slug/spec.md` (или абсолютная — если известен корень проекта).

---

### User Story 5 - Пользователь отслеживает состояние задач агента (Priority: P3)

Пользователь открывает доску Jira (Kanban / Scrum), фильтрует по assignee = AI-agent, видит список активных и завершённых задач, читает отчёты, переоткрывает задачу (`Reopen`) если результат не устраивает.

**Why this priority**: Удобство, но не критично для MVP — пользователь и так может видеть список в UI по умолчанию.

**Independent Test**: Создать доску Kanban для проекта → назначить 2 задачи агенту → закрыть одну → убедиться, что доска отображает статусы корректно и поддерживает drag-and-drop.

**Acceptance Scenarios**:

1. **Given** Jira запущена и задачи созданы, **When** пользователь открывает Board проекта, **Then** он видит колонки `To Do` / `In Progress` / `Done` с задачами агента.
2. **Given** пользователь недоволен результатом, **When** он перетаскивает задачу обратно в `In Progress` и пишет комментарий, **Then** агент при следующем опросе видит изменение статуса и может снова взять задачу.

### Edge Cases

- **Что если Jira-контейнер упал во время работы агента?** — Команды агента должны возвращать понятную ошибку с просьбой проверить состояние Jira (например, `docker ps`). Агент не должен молча терять задачу.
- **Что если у задачи нет описания или оно пустое?** — Агент должен явно отказаться брать такую задачу и оставить комментарий "Описание пустое, требуется уточнение", оставаясь в статусе `Open`.
- **Что если две задачи ссылаются на одну спецификацию?** — Агент должен обрабатывать их последовательно (по ключу) и в каждом отчёте указывать, какая часть спеки затронута (если разбито).
- **Что если API-токен истёк или отозван?** — Агент должен вернуть ошибку `401 Unauthorized` с инструкцией пользователю обновить токен в `.env.local-jira` или переменных окружения.
- **Что если Postgres Jira повреждён?** — При запуске контейнера Jira должна логировать ошибку подключения к БД; агенту нужно явно отличать "Jira не запущена" от "Jira запущена, но БД недоступна".
- **Что если пользователь заводит задачу с типом, который workflow не поддерживает (например, Epic)?** — Агент должен уметь либо работать с произвольным типом Issue, либо явно фильтровать по типу при `fetch-assigned`.
- **Что если несколько агентов одновременно берут одну задачу?** — Используется Jira-механизм "Claim": первая транзакция `assignee = self + status = In Progress` выигрывает, остальные получают 409 Conflict и пропускают задачу.
- **Что если Jira API возвращает 429 Too Many Requests?** — CLI автоматически retry с экспоненциальным backoff (2s → 4s → 8s, до 3 попыток). Если все 3 попытки вернули 429 — CLI возвращает ошибку пользователю с понятным сообщением "Jira API rate-limit, попробуйте позже или уменьшите частоту polling".
- **Что если Postgres-том повреждён?** — Пользователь запускает `tools/jira-restore.sh` с указанием даты; скрипт берёт последний валидный дамп из `jira-backups`, восстанавливает схему через `pg_restore`, запускает Jira. Потеря данных ограничена последним успешным бэкапом (≤24 часа).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система MUST поднимать Jira Data Center в локальном Docker-контейнере с пробросом порта 8080 (HTTP) и подключением к внешнему (named-volume) Postgres 13+ для сохранности данных между перезапусками.
- **FR-002**: Система MUST использовать Jira Software Data Center (long-term support release), совместимую с JDK 11/17 и Postgres 13+.
- **FR-003**: Пользователь MUST иметь возможность через веб-интерфейс создать проект (например, ключ `KARAOKE`), создавать задачи типов Task / Story / Bug / Sub-task, заполнять поля summary / description / priority / assignee, прикладывать ссылки.
- **FR-004**: Система MUST предоставлять CLI-утилиту (или скрипт `tools/jira.sh`) для работы с Jira REST API v2/v3, принимающую в качестве параметров `BASE_URL`, `USER`, `API_TOKEN` (через переменные окружения `JIRA_URL`, `JIRA_USER`, `JIRA_TOKEN`).
- **FR-005**: CLI-утилита MUST поддерживать подкоманды: `list-projects`, `list-issues [--project K] [--assignee USER] [--status STATUS]`, `get-issue KEY`, `claim-issue KEY`, `add-comment KEY --file report.md`, `close-issue KEY`, `reopen-issue KEY`, `create-issue --project K --type Task --summary S --description D`.
- **FR-006**: Система MUST автоматически создавать учётную запись `ai-agent` (или использовать существующую, если задана переменная `JIRA_AGENT_USER`) при первоначальной настройке Jira с правами на создание / редактирование / закрытие задач в проекте.
- **FR-007**: Агент MUST уметь по команде пользователя (или по cron / событию) опрашивать Jira и получать список задач в статусе `Open` / `To Do`, назначенных на `ai-agent`.
- **FR-008**: При публикации отчёта агент MUST формировать структурированный markdown-документ с секциями: "Что сделано", "Изменённые файлы" (со ссылками), "Прогон проверок" (команды и результат), "Известные ограничения".
- **FR-009**: Система MUST обеспечивать секреты вне git (см. Constitution § VIII): `JIRA_TOKEN`, пароль БД Jira, admin-пароль Jira — хранятся в `.env.local-jira` (в `.gitignore`) или в переменных окружения shell, **не** в репозитории.
- **FR-010**: Система MUST предоставить документацию в `docs/claude-code-setup.md` (или отдельном `docs/jira-setup.md`) с пошаговой инструкцией: установка → запуск → создание проекта → создание API-токена → проверка через `jira.sh list-projects`.
- **FR-011**: Все docker-compose сервисы для Jira MUST быть описаны в отдельном файле `deploy/jira-docker-compose.yml` (или добавлены как новый профиль в `deploy/do.sh`) и НЕ затрагивать существующий стек Karaoke.
- **FR-012**: Система MUST быть устойчива к перезапуску контейнеров (Jira + Postgres) — данные задач, проектов, пользователей сохраняются в named-volume `jira-postgres-data`.
- **FR-013**: В рамках выполнения задачи агент SHOULD запускать существующие проверки Karaoke (см. AGENTS.md § «Обязательная проверка после ЛЮБОГО изменения кода») и упоминать их результат в отчёте.
- **FR-014**: Система SHOULD поддерживать webhook Jira → агент (через публичный endpoint или туннель типа ngrok), но это не обязательно для MVP — достаточно polling-модели через cron / ручной запуск.
- **FR-015**: Система MUST выполнять ежедневный бэкап Postgres Jira через `tools/jira-backup.sh` (cron в 03:00 локального времени) — `pg_dump -Fc jira_db > /backups/jira-YYYY-MM-DD.dump` в named-volume `jira-backups` с ротацией последних 7 файлов (более старые удаляются).
- **FR-016**: Система MUST предоставлять команду `tools/jira-restore.sh <date>` для восстановления из последнего (или указанного) дампа: останавливает Jira, заменяет схему через `pg_restore --clean --if-exists`, запускает Jira обратно.
- **FR-017**: CLI-агент (`tools/jira.sh`) MUST писать структурированный лог каждого вызова в `logs/jira-agent.log` (одна JSON-запись на строку: `timestamp`, `command`, `request_id`, `endpoint`, `http_status`, `duration_ms`, `error` если есть); ротация через `logrotate` (daily, 7 дней, compress).

### Key Entities *(include if feature involves data)*

- **Jira Project** (`KARAOKE`): контейнер для задач. Атрибуты: `key` (уникальный 2-10 символов), `name`, `lead`, `projectTypeKey` (`software`), `workflowScheme`.
- **Jira Issue**: задача. Атрибуты: `key` (`KARAOKE-N`), `summary`, `description` (ADF), `issueType` (`Task` / `Story` / `Bug`), `status` (`To Do` / `In Progress` / `Done`), `priority`, `assignee`, `reporter`, `created`, `updated`, `labels`, `comments[]`.
- **Jira Comment**: комментарий к задаче. Атрибуты: `id`, `author`, `body` (ADF), `created`, `issueKey`.
- **Jira User**: `ai-agent`, `admin`. Атрибуты: `username`, `email`, `displayName`, `active`, `groups[]`.
- **Jira Workflow**: схема переходов `To Do → In Progress → Done` (стандартная Kanban Software).
- **API Token**: персональный токен Atlassian для REST API, хранится в env-переменных (вне git).
- **Report (комментарий-отчёт)**: markdown-структура с секциями FR-008, прикрепляется как comment к Issue.
- **DB Backup Artifact**: `pg_dump` в custom-формате (`-Fc`), хранится в named-volume `jira-backups/jira-YYYY-MM-DD.dump`, размер типично 50-500 MB для пустого/среднего проекта.
- **CLI Audit Log Entry**: JSON-объект в `logs/jira-agent.log` — одна строка на каждый REST-вызов: `{"ts":"2026-09-02T14:40:12Z","cmd":"claim-issue","req_id":"a1b2c3","endpoint":"PUT /rest/api/3/issue/KARAOKE-42","http_status":204,"duration_ms":423}`.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Пользователь может установить Jira локально и завести первую задачу за ≤30 минут с момента старта (с учётом скачивания Docker-образа ~1 GB).
- **SC-002**: Агент может получить список задач, назначенных на него, через CLI за ≤5 секунд при размере проекта ≤1000 задач.
- **SC-003**: Полный цикл "пользователь создал задачу → агент взял → агент выполнил → агент написал отчёт → агент закрыл" занимает ≤времени выполнения самой задачи (накладные расходы Jira-интеграции — ≤10% от времени работы).
- **SC-004**: 100% задач, закрытых агентом, содержат комментарий-отчёт с непустой секцией "Что сделано" и ≥1 ссылкой на изменённый файл (если задача предполагала правки кода).
- **SC-005**: Перезапуск docker-контейнеров Jira и Postgres сохраняет ≥99% данных (задачи, проекты, комментарии, пользователи).
- **SC-006**: 0 секретов Jira (`JIRA_TOKEN`, пароли) попадает в git-историю (проверяется `git ls-files | grep -iE 'jira.*(\.env$|\.key$|\.pem$)'` — должен быть пустым).
- **SC-007**: Документация `docs/jira-setup.md` (или эквивалент) позволяет новому пользователю развернуть Jira и выполнить первую команду `jira.sh list-projects` без дополнительных вопросов.
- **SC-008**: Проверка состояния Jira (healthcheck) занимает ≤3 секунд и возвращает HTTP 200 при работающей Jira, ошибку подключения при недоступной.
- **SC-009**: Бэкап Postgres выполняется автоматически ≤1 раз в сутки (в 03:00 локального времени), последние 7 дампов хранятся в `jira-backups`, восстановление из произвольного дампа завершается ≤10 минут для БД объёмом ≤1 GB.
- **SC-010**: При восстановлении из дампа (DR drill) ≥99% задач, проектов, комментариев и пользователей восстанавливаются корректно (проверяется через `list-projects` + `list-issues --project KARAOKE --limit 1000` после restore).
- **SC-011**: Каждый вызов `tools/jira.sh` создаёт ровно одну запись в `logs/jira-agent.log` в формате JSON, пригодном для парсинга (`jq` без ошибок); старые логи старше 7 дней автоматически сжимаются и удаляются через `logrotate`.
- **SC-012**: При получении HTTP 429 от Jira API CLI выполняет retry с backoff 2s/4s/8s (суммарно ≤14 секунд ожидания), и только при исчерпании всех попыток возвращает ошибку пользователю.

## Assumptions

- **Окружение**: машина `nsa-i9` (или любая Linux с Docker 20+ и ≥8 GB свободной RAM), Docker Compose v2, JDK 11/17 уже установлены.
- **Сеть**: пользователь имеет стабильное подключение к интернету для однократного скачивания Docker-образа Atlassian Jira (~1 GB) при первой установке. После — работает полностью offline.
- **Хранилище**: ≥10 GB свободного места на диске для Docker-образов и Postgres-данных Jira.
- **Безопасность**: Jira слушает только на `127.0.0.1` / `localhost` (не expose в публичную сеть). Если нужен внешний доступ — через reverse-proxy с TLS (вне scope MVP).
- **Лицензия**: Jira Data Center используется для разработки и личного использования; для production-коммерческого — нужна лицензия Atlassian (вне scope MVP).
- **Совместимость**: версия Jira ≥9.0 (последний LTS на момент установки); Postgres 13+. Совместимость проверяется в матрице `deploy/jira-docker-compose.yml`.
- **AI-аккаунт**: в Jira заводится один технический пользователь `ai-agent` (НЕ реальный сотрудник), с правами `jira-developers`. Доступ к задачам — через project permissions.
- **API-токен**: генерируется через UI Jira (`Profile → Personal Access Tokens`) или через REST API (`/rest/api/3/myself` → API token).
- **Cron / polling**: MVP запускается вручную (`jira.sh fetch-assigned`) или по простому systemd-timer / cron раз в N минут. Webhook-интеграция — факультативно (FR-014).
- **Репозиторий**: код CLI-утилиты `tools/jira.sh` коммитится в Karaoke-репо, **но** `.env.local-jira` — в `.gitignore` (NON-NEGOTIABLE, см. Constitution § VIII).
- **Связь с Karaoke-проектом**: Jira — отдельный сервис, не интегрированный в Karaoke-приложение; используется только как внешний task-tracker для AI-агента.
- **Машинно-специфичные правила**: на `nsa-i9` / `nsa` действуют исключения AGENTS.md (Pass 282) — пересборка `karaoke-app` разрешена, перезапуск запрещён без согласия. К Jira это не относится (это новый сервис).
- **Backup**: cron-задача для `tools/jira-backup.sh` регистрируется на уровне ОС (`crontab -e` пользователя) или через systemd-timer; не требует root-прав (хватит прав на запись в named-volume). Пароль Postgres для `pg_dump` берётся из того же `.env.local-jira` (отдельная переменная `JIRA_DB_PASSWORD`).
- **Logrotate**: конфиг `/etc/logrotate.d/jira-agent` (или `~/.logrotate.d` для пользовательского crontab-варианта) с правилом `daily / rotate 7 / compress / missingok / notifempty`.
- **Rate-limit**: лимиты Atlassian Jira DC REST API — до 100 req/min per token (рекомендация, не жёсткий лимит); CLI polling настроен на ≤1 req/30s (default), чтобы не упираться в потолок даже при множественных задачах.
