# Research: Облегчённый редактор песен в админке → локальная БД admin-машины

**Feature**: 232-admin-song-editor-local-db
**Date**: 2026-08-15
**Spec**: [spec.md](./spec.md)

## Резюме

Фича меняет логику выбора БД в **двух методах** существующего контроллеля
`karaoke-app/.../controllers/SongEditorController.kt` для режима `mode='song'`:

| Метод | Текущее поведение | Целевое поведение |
|-------|-------------------|-------------------|
| `editById` (`POST /api/songeditor/edit/byId`, строки 732–830) | Song читается из `WORKING_DATABASE` (всегда), задание резолвится из `db` (target) | Song читается из `Connection.local()` (= `WORKING_DATABASE` на admin-машине) — то же поведение по факту, но семантически привязано к LOCAL, а не к глобальному `WORKING_DATABASE` |
| `editSave` (`POST /api/songeditor/edit/save`, строки 837–901) | Song читается из `db` (target), пишется в `db` (target) | Song читается и пишется в `Connection.local()`, параметр `target` игнорируется для `mode='song'` |

Поскольку `WORKING_DATABASE = Connection.local()` в karaoke-app (см.
`karaoke-app/.../Constants.kt:204`), на admin-машине это **одна и та же БД**.
Реальное расхождение возникает только в `editSave` при `target='remote'` —
именно там правки уходят на серверную БД, а должны оставаться в локальной.
В `editById` Song уже читается из LOCAL, но контракт надо зафиксировать
явно (через `Connection.local()`), чтобы не зависеть от глобального
синглтона `WORKING_DATABASE` (который может быть перенаправлен, например,
через закомментированные `// val WORKING_DATABASE = Connection.REMOTE`).

## Решённые вопросы (NEEDS CLARIFICATION → Resolved)

Все 3 вопроса разрешены в секции `Clarifications` спеки до начала Phase 0.
Здесь фиксируется, **почему** выбрано именно такое решение.

### Q1: Скоуп — только `mode='song'` или также `mode='assignment'`?

**Решение**: только `mode='song'`. `mode='assignment'` остаётся target-aware.

**Rationale**: задание редактора (assignment) живёт в той БД, где идёт
рабочий цикл редактора — на проде это SERVER-БД, на admin-машине — LOCAL.
`assignmentsTarget` в webvue3 store позволяет админу переключаться между
LOCAL/SERVER. Если бы мы тоже зафиксировали `mode='assignment'` за LOCAL,
админ потерял бы возможность просматривать/править черновики, живущие на
SERVER (типичный сценарий «редактор на сайте правит черновик → админ
апрувит его»). См. также LiveDoc `livedocs/domain/editorial.md` и спеку
182-editor-self-assign-tasks.

**Альтернативы рассмотрены**:
- Фиксить оба режима за LOCAL → отклонено: ломает реальный рабочий цикл редакторов.
- Ввести новый параметр `songTarget=local|remote` (отдельно от `target`) → отклонено: лишняя сложность API для фичи, которая должна быть «что вижу — то и сохраняю» для редактирования песни.

### Q2: Поведение при `assignmentsTarget='remote'`

**Решение**: при `mode='song'` параметр `target` игнорируется; Song
всегда в `Connection.local()` независимо от текущего `assignmentsTarget`.

**Rationale**: `editorAssignmentDefaultTarget` по умолчанию = 'remote'
(см. `webvue3/.../SongEditor/store.js:145` — fallback `'remote'` если
свойство не 'local'). Это значит, что прямо сейчас в админке редактор
песни по умолчанию пытается писать на сервер. Эту дефолтность для
**заданий** оставляем (админ смотрит задания, живущие на SERVER), а для
**песни** — убираем (правки должны жить в LOCAL до явного sync).

**Альтернативы рассмотрены**:
- Изменить дефолт `editorAssignmentDefaultTarget` на 'local' → отклонено: это сломает сценарий «задания на SERVER» (по умолчанию все задания станут невидимы).
- Добавить отдельный `songTarget` параметр → отклонено: лишний параметр в API; пользовательское ожидание «правки в LOCAL» должно соблюдаться всегда, без дополнительного переключателя.

### Q3: Затрагивать ли другие target-aware эндпоинты?

**Решение**: нет. Только `/api/songeditor/edit/byId` и `/edit/save` в
`mode='song'`. Все остальные эндпоинты `SongEditorController`
(digest, statusbysongids, assign, revoke, delete, approve, reject и т.п.)
остаются без изменений.

**Rationale**: минимальный, точечный фикс. Каждый из этих эндпоинтов имеет
свою семантику target (см. комментарий в шапке контроллера, строки 47–56):
- `digest/byId` — просмотр (должен уважать target);
- `assign/reject/delete` — пишут в ту БД, где реально идёт работа пользователя;
- `approve` — применяет разметку ВСЕГДА в LOCAL (только там есть локальный диск для .srt/рендера) — это уже ровно то поведение, которое мы фиксируем для редактирования песни, но для approve это исторический контракт, не предмет этой фичи.

**Альтернативы рассмотрены**:
- Переписать весь контроллер на единый target-handling → отклонено: выходит за скоуп, ломает другие контракты.

## Зависимости и Best Practices

- **Spring `@RequestParam(required = false)`** — параметр `target` остаётся в сигнатуре для обратной совместимости, но его значение игнорируется серверной стороной для `mode='song'`. Это согласуется с тем, как уже сделано в `editSave` (строки 859–877) для другого target-aware поведения.
- **`Connection.local()`** — фабрика из `Connection.kt:79`, возвращает singleton-обёртку над JDBC. На admin-машине `APP_WORK_ON_SERVER=false`, поэтому используются `DB_LOCAL_*` credentials (см. `Connection.kt:61-62`); URL — `localhost:8832` или `karaoke-db:5432` в зависимости от `APP_WORK_IN_CONTAINER`. Поведение полностью совпадает с `WORKING_DATABASE` на admin-машине, но контракт становится явным.
- **Обратная совместимость API** — фронтенд (`webvue3/.../SongKaraokeEditorModal.vue:100,177,251`) шлёт `target` в params, и после фикса это не сломает работу: сервер просто проигнорирует значение. Никаких изменений в JS-коде не требуется.

## Edge Cases и обработка

- **Песня отсутствует в LOCAL-БД** (есть только в SERVER-БД, sync ещё не качал): сейчас `editById` вернёт `found=false` (через существующую ветку в строках 760, 774). После фикса поведение остаётся таким же, но FR-005 спеки требует **отличимый** код ошибки (`song_not_found_in_local_db` или эквивалент), чтобы UI мог показать пользователю понятное сообщение. Это **опциональное** улучшение UX, не блокер фичи — реализация по усмотрению (см. tasks.md).
- **Поведение на прод-сервере** (где `karaoke-web` дёргает этот же код, если эндпоинт доступен через nginx): на проде `Connection.local()` = `karaoke-db:5432` (единственная локальная БД этого окружения), `Connection.remote()` = `188.119.64.111:8832` через nginx-stream-proxy. После фикса `mode='song'` всегда пишет в `karaoke-db:5432`, что совпадает с текущим поведением `WORKING_DATABASE` на проде. Никаких регрессий на проде не ожидается.

## Решения, не требующие дальнейшего исследования

- **Использовать существующий `Connection.local()`** — не вводить новый глобал, не менять `WORKING_DATABASE`. Это минимальное изменение.
- **Сохранить параметр `target` в API** — не ломать фронтенд, не вводить новые параметры.
- **Не менять SQL-схему** — фича runtime-only.
- **Не добавлять новые эндпоинты** — фича точечная.
