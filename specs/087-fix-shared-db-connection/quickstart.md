# Quickstart: проверка изоляции соединений с БД по потокам и retry очереди

**Feature**: [spec.md](./spec.md) | **Data model**: [data-model.md](./data-model.md)

Автотестов для `KaraokeConnection`/`KaraokeProcessWorker` в CI нет и не
предполагается (см. `Testing` в `plan.md` — нужен реальный PostgreSQL).
Проверка — вручную на `dev-pc`/`dev` (допуски в «Ограничения и доступы
агента» `constitution.md`: локальные пересборка/перезапуск `karaoke-app` и
операции с локальной БД без отдельного согласия пользователя).

## Предусловия

- Локальный стек поднят (`db`, `karaoke-app`, `webvue3`).
- После правок — пересобрать и перезапустить **только** модуль `app`:

```bash
cd deploy
bash do.sh build_app
bash do.sh start_app
```

- В очереди заданий (раздел «Процессы» в `webvue3`) должно быть хотя бы
  одно активное задание (или несколько ожидающих), чтобы главный цикл
  `doStart()` реально обращался к БД на каждой итерации — например,
  поставить любое лёгкое задание с низким приоритетом и запустить очередь.

## Сценарий 1 — кратковременный обрыв БД не роняет несвязанные операции (US1, FR-001/FR-002)

1. Убедиться, что очередь запущена (`isWork=true`) и в ней есть активность.
2. Открыть в браузере/curl несколько независимых запросов к админке (любые
   `GET`/`POST` эндпоинты, использующие `WORKING_DATABASE`, например список
   песен или дайджест картинок).
3. Имитировать кратковременный сетевой сбой до БД — приостановить контейнер
   `karaoke-db` (сеть «зависает», TCP-соединения не рвутся, а «висят» —
   максимально похоже на реальный инцидент) на **дольше `socketTimeout=30`**
   из JDBC URL (`Connection.kt`), например на 35-40 секунд:

   ```bash
   docker pause karaoke-db
   sleep 40
   docker unpause karaoke-db
   ```

4. **Ожидаемый результат**: в логе `karaoke-app` во время паузы возможны
   единичные ошибки/таймауты у тех потоков, что в этот момент реально
   обращались к БД (это нормально — сеть действительно недоступна) — но
   **после** `docker unpause`:
   - новый HTTP-запрос к админке (на любом потоке пула Tomcat) отрабатывает
     штатно, без «Соединение уже было закрыто»;
   - очередь заданий не остаётся «зависшей» из-за состояния соединения
     другого потока (см. Сценарий 2 — восстанавливается сама).

## Сценарий 2 — очередь сама возобновляется после сбоя (US2, FR-005/FR-006)

1. Повторить сбой из Сценария 1 (`docker pause karaoke-db` на 35-40с, затем
   `docker unpause`) при запущенной очереди с ожидающими заданиями.
2. **Ожидаемый результат**: в логе `karaoke-app` видны записи о повторных
   попытках `doStart()` с **увеличивающейся** паузой между ними (не подряд
   без задержки); в течение ~1-2 минут после `docker unpause` очередь
   возобновляет обработку ожидающих заданий **без клика оператора** —
   проверить по `POST /api/processes/workerstatus` (`isWork: true`,
   `stopAfterThreadIsDone: false`) и по факту, что задания реально
   переходят `WAITING → WORKING`.
3. **Более длительный сбой** (проверка предела попыток, FR-006): повторить
   с `docker pause` на весь кумулятивный интервал retry и дольше (по
   умолчанию плана — сумма пауз между попытками, ориентир из `research.md`).
   **Ожидаемый результат**: после исчерпания попыток очередь корректно
   останавливается (`isWork=false`, как и раньше по specs/029), в разделе
   мониторинга webvue3 появляется алерт `RenderQueueStalledCheck` — клик
   «Решить проблему» восстанавливает работу (уже существующее поведение,
   не должно быть сломано).

## Сценарий 3 — число соединений с БД не растёт неограниченно (SC-003, FR-004)

1. До правки — записать текущее число соединений от `karaoke-app`:

   ```bash
   docker exec karaoke-db psql -U postgres -d karaoke -t -c \
     "select count(*) from pg_stat_activity where application_name != '' or client_addr is not null;"
   ```

2. Выполнить десятки последовательных и несколько параллельных запросов к
   разным эндпоинтам админки (можно через `webvue3` — открыть несколько
   разделов подряд).
3. **Ожидаемый результат**: число соединений от `karaoke-app` стабилизируется
   в разумных пределах (примерно равно числу реально задействованных
   потоков Tomcat/очереди, не числу выполненных HTTP-запросов) и не растёт
   монотонно с каждым новым запросом.

## После проверки

- Обновить `docs/features/async-process-queue.md` (FR-009 `constitution.md`)
  — задокументировать новые инварианты: соединение с БД изолировано по

  число раз перед остановкой.
- Свериться с `server.tomcat.threads.max` в `application.yml` и
  `max_connections` PostgreSQL (`research.md` — ёмкость), задать
  консервативное значение при необходимости.
- Прогнать стандартный пред-коммитный чек-лист (`ktlint`, KDoc coverage,
  `pre-commit run --all-files`) перед PR — см. `CLAUDE.md`.
