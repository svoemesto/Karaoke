# Feature Specification: Переименование параметров/переменных типа Song с имени `settings` на `song`

**Feature Branch**: `102-rename-song-settings-vars`

**Created**: 2026-08-02

**Status**: Draft

**Input**: User description: "Обнови локальный мастер и сделай рефакторинг кода - в нём ещё осталось недоделанное от переименования Settings в Song где переменные класса Song всё ещё называются settings, например: fun getVKPictureBase64(settings: Song): String должно быть fun getVKPictureBase64(song: Song): String"

## Clarifications

### Session 2026-08-02

- Q: Кроме параметров/переменных с типом ровно `Song`, в коде нашлись производные имена вроде `settingsId: Long`, `settingsList: List<Song>`, `KaraokeProcessDTO.settingsId`, `HealthReportDTO.settingsId`/`settingsFileName` — причём поля `settingsId`/`settingsFileName` в `HealthReportDTO` сериализуются в JSON и читаются фронтендом (webvue3: SongsTable.vue, HealthReport/store.js и др.). Входят ли такие производные имена (не имеющие типа ровно `Song`) в область этого рефакторинга? → A: Полный охват включая DTO+фронтенд — переименовывать `HealthReportDTO.settingsId`/`settingsFileName`, `KaraokeProcessDTO.settingsId` и т.п. на `song*`-эквиваленты вместе с соответствующей правкой webvue3.
- Q: Копая глубже, нашлись «проводные» (wire-level) идентификаторы `settingsId`, чьё имя определяется именно именем Kotlin-параметра/строковым литералом: (1) `@RequestParam(required = true) settingsId: Long` в `MainController.kt` (`POST /changesettingsstatus`) без явного `name=`, вызывается из legacy-файла `settings_context.js`; (2) ручные map-ключи вида `"settingsId" to settingsId` в `SseNotification.kt`, уходящие во фронтенд через SSE (читаются в `webvue3/src/components/Songs/store.js:1779` как `userEventData.settingsId`). БД-колонка `settings_id` при этом осознанно НЕ переименовывалась ещё при самом переименовании класса Settings→Song (прецедент `deploy/karaoke-db/28_rename_settings_to_songs.sql`, research.md §5.1) — это применимо и здесь, миграция БД в область не входит. Как поступить с wire-level HTTP/SSE именами? → B: Переименовать везде, включая фронтенд-потребителей (`settings_context.js`, SSE-слушатель в `store.js`).
- Q: Нашёлся ещё один, более крупный очаг legacy-админ-интерфейса: `POST /songs_update` (и аналогичный второй метод рядом) в `MainController.kt` принимает ~30 отдельных `@RequestParam settings_xxx: String` (`settings_id`, `settings_songName`, `settings_author`, `settings_year` и т.д. — суммарно ≈60 таких параметров в двух методах) из трёх legacy Thymeleaf-шаблонов (`songs.html`, `songs2.html`, `area_center_column.html`). Включаем этот участок в задачу? → Включить (по ранее выбранному принципу полного охвата).
- Q: Как разбить работу на PR с учётом того, что часть мест (JSON DTO-поля, HTTP-параметры, SSE-ключи) требует синхронного деплоя backend+frontend? → Один большой PR — все изменения (backend модули, webvue3, legacy Thymeleaf-шаблоны) единым PR.

### User Story 1 - Понятное имя параметра при чтении кода (Priority: P1)

Разработчик открывает функцию, работающую с объектом `Song` (например,
`getVKPictureBase64`), и видит параметр/переменную с именем `song`, а не
устаревшим `settings`, оставшимся после исторического переименования класса
`Settings` в `Song`.

**Why this priority**: Несовпадение имени переменной и её типа — источник
путаницы при чтении и сопровождении кода, особенно в больших файлах
(`Utils.kt`, `HealthReport.kt`, `MainController.kt`), где счёт параметров и
локальных переменных идёт на десятки. Это прямой запрос пользователя и
единственная цель фичи.

**Independent Test**: Открыть любой из затронутых файлов и убедиться, что
все параметры и локальные переменные, объявленные с типом `Song` (явно или
через вывод типа из фабричных методов `Song`), названы `song` (или
осмысленным производным именем при коллизии, см. Edge Cases), а не
`settings`.

**Acceptance Scenarios**:

1. **Given** функция `fun getVKPictureBase64(settings: Song): String` в
   `UtilsPictures.kt`, **When** применяется рефакторинг, **Then** сигнатура
   становится `fun getVKPictureBase64(song: Song): String`, и все обращения
   к параметру внутри тела функции (`settings.xxx`) заменены на `song.xxx`.
2. **Given** локальная переменная `val settings = Song.getById(...)` внутри
   функции контроллера, **When** применяется рефакторинг, **Then** переменная
   переименована в `song`, и все её использования ниже по коду обновлены.
3. **Given** переименованный код, **When** выполняется сборка проекта
   (`./gradlew build`) и статический анализ (`ktlintCheck`), **Then** сборка
   и линтер проходят без новых ошибок, поведение функций не меняется.

### User Story 2 - Переименование распространяется на производные имена, включая контракт с фронтендом (Priority: P1)

Разработчик, читающий код после рефакторинга, видит, что не только
параметры/переменные/поля с типом ровно `Song`, но и связанные с ними
производные идентификаторы — DTO-поля (`HealthReportDTO.settingsId` →
`songId`, `HealthReportDTO.settingsFileName` → `songFileName`,
`KaraokeProcessDTO.settingsId` → `songId`), HTTP-параметры, биндящиеся по
имени Kotlin-параметра (`@RequestParam settingsId` в `/changesettingsstatus`
и `@RequestParam settings_xxx` в `/songs_update`), и SSE-ключи
(`"settingsId" to settingsId` в `SseNotification.kt`) — тоже переименованы
на `song`-эквиваленты. Вместе с ними обновлены все потребители этих
контрактов: webvue3 (`SongsTable.vue`, `HealthReport/store.js`,
`HealthReport/components/*.vue`, `Songs/store.js`), legacy-файл
`settings_context.js` и три legacy Thymeleaf-шаблона (`songs.html`,
`songs2.html`, `area_center_column.html`).

**Why this priority**: Без синхронной правки потребителей переименование
DTO-полей и wire-параметров сломает соответствующие функции немедленно
(например, `POST /changesettingsstatus` начнёт получать 400 «missing
required parameter», а SSE-обработчик в `Songs/store.js` перестанет находить
`id` песни в событии). Это прямое следствие решения пользователя
(см. Clarifications) о полном охвате рефакторинга и требует единого,
синхронного изменения backend+frontend.

**Independent Test**: Открыть `POST /changesettingsstatus`,
`POST /songs_update` и SSE-поток обновлений health-report, убедиться, что
запрос/шаблон/фронтенд используют одно и то же новое имя (`songId`,
`song_xxx`), и что старое имя (`settingsId`, `settings_xxx`) нигде в этой
цепочке не осталось ни на backend, ни на frontend.

**Acceptance Scenarios**:

1. **Given** `HealthReportDTO.settingsId`/`settingsFileName`, **When**
   применяется рефакторинг, **Then** поля переименованы в `songId`/
   `songFileName`, и все обращения к ним в webvue3
   (`HealthReportTableBody.vue`, `HealthReport/store.js`,
   `HealthReportTableHeader.vue`) обновлены на новые имена.
2. **Given** `@RequestParam(required = true) settingsId: Long` в
   `MainController.kt` (`/changesettingsstatus`), **When** применяется
   рефакторинг, **Then** параметр и его имя в запросе становятся `songId`, и
   `settings_context.js` отправляет запрос с ключом `songId`.
3. **Given** SSE map `"settingsId" to settingsId` в `SseNotification.kt`,
   **When** применяется рефакторинг, **Then** ключ становится `"songId"`, и
   `webvue3/src/components/Songs/store.js` читает событие по ключу `songId`.
4. **Given** 54 параметра `settings_xxx` (по 27 в каждом) в двух методах `MainController.kt`
   (`/songs_update` и аналогичный), **When** применяется рефакторинг,
   **Then** все параметры переименованы в `song_xxx`, и три Thymeleaf-шаблона
   (`songs.html`, `songs2.html`, `area_center_column.html`) отправляют формы
   с новыми именами полей.

### User Story 3 - Не затронуты понятия "настроек", не связанные с сущностью `Song` (Priority: P2)

Разработчик, читающий код после рефакторинга, видит, что идентификаторы,
которые не имеют отношения к сущности `Song` — ни по типу, ни по контракту
(например, `KaraokePlatform.settingsFieldPublicationId`/
`settingsFieldVersionNumber` — конфигурация полей публикации per-платформе,
не значение и не производная от `Song`; `LS_SETTINGS_KEY` в
`karaoke-public/src/player/KaraokePlayer.js` — настройки плеера пользователя,
никак не связанные с сущностью `Song`), — остались без изменений. Также
физическое имя колонки БД `settings_id` (и любые другие физические
объекты БД, ссылающиеся на устаревшее имя) остаётся без изменений.

**Why this priority**: Слепое переименование по текстовому совпадению слова
`settings` без проверки смысловой связи с `Song` повредило бы не связанные с
задачей части кода (конфигурацию платформ, пользовательские настройки
плеера) или потребовало бы недопустимой в рамках этой задачи миграции БД —
это отдельный, более рискованный класс ошибок, чем недостаточное
переименование.

**Independent Test**: После рефакторинга проверить, что
`KaraokePlatform.settingsFieldPublicationId`/`settingsFieldVersionNumber`,
`karaoke-public`-настройки плеера и физическое имя колонки БД `settings_id`
(маппинг `@KaraokeDbTableField(name = "settings_id")` в `KaraokeProcess.kt`)
остались без изменений.

**Acceptance Scenarios**:

1. **Given** `KaraokePlatform.settingsFieldPublicationId`/
   `settingsFieldVersionNumber` (конфигурация полей per-платформе, не
   значение типа `Song` и не часть найденного DTO/wire-контракта, связанного
   с `Song`), **When** применяется рефакторинг, **Then** имена остаются без
   изменений.
2. **Given** настройки плеера в `karaoke-public` (`LS_SETTINGS_KEY` и
   аналогичные), **When** применяется рефакторинг, **Then** они остаются без
   изменений — `karaoke-public` не затрагивается этой задачей вовсе.
3. **Given** физическая колонка БД `settings_id` (аннотация
   `@KaraokeDbTableField(name = "settings_id")` в `KaraokeProcess.kt`),
   **When** переименовывается Kotlin-свойство `settingsId` → `songId`,
   **Then** строковый аргумент аннотации остаётся `"settings_id"`, и никакая
   SQL-миграция физического имени колонки не создаётся.

### Edge Cases

- Что если в одной и той же функции уже есть переменная/параметр с именем
  `song` (например, значение другого типа или другой объект `Song`), и
  переименование `settings` → `song` создаст конфликт имён? → Такой
  параметр/переменная должны получить другое осмысленное уникальное имя
  (например, `songArg`, `targetSong`, `parentSong` — по смыслу использования),
  а не быть пропущены молча.
- Что если `settings` — это деструктурированный компонент лямбды или
  parameter в scope-функции (`let`, `also`, `apply`, `run`) со значением
  типа `Song`? → Тоже подлежит переименованию по тем же правилам.
- Что если `settings` используется как имя поля класса/data class (например,
  `val settings: Song` в конструкторе `SongRenderContext` или
  `HealthReport`)? → Поле переименовывается в `song` вместе со всеми местами
  создания объекта (именованные аргументы `settings = ...`) и обращения к
  полю (`obj.settings` → `obj.song`) по всей кодовой базе.
- Что если параметр/поле, производное от `Song` по смыслу (например,
  `settingsId: Long`, хранящий `Song.id`), используется как ключ HTTP-запроса
  (`@RequestParam`) или JSON/SSE-поле, читаемое фронтендом? → Переименовать
  вместе с контрактом (см. User Story 2) и синхронно обновить всех известных
  потребителей (webvue3, `settings_context.js`, legacy Thymeleaf-шаблоны).
  Если в процессе поиска обнаружится потребитель, не найденный на этапе
  спецификации (например, ещё один SSE-слушатель или внешний скрипт), он
  тоже подлежит обновлению — пропуск потребителя недопустим, т.к. оставит
  контракт в несогласованном состоянии.
- Что если имя со словом `settings` не связано со значением/идентификатором
  `Song` ни по типу, ни по контракту (например,
  `KaraokePlatform.settingsFieldPublicationId`, настройки плеера в
  `karaoke-public`)? → Не переименовывается (см. User Story 3) — критерий
  включения не «текст settings», а «значение представляет объект/идентификатор
  Song и/или является частью найденного в этой задаче DTO/HTTP/SSE-контракта,
  связанного с Song».
- Что если переименование Kotlin-свойства, замапленного на колонку БД через
  `@KaraokeDbTableField(name = "...")` (например, `KaraokeProcess.settingsId`
  → `songId`, колонка `settings_id`), потребует правки SQL? → Не требует:
  переименовывается только Kotlin-имя свойства, строковый аргумент аннотации
  и физическое имя колонки остаются как есть (прецедент —
  `deploy/karaoke-db/28_rename_settings_to_songs.sql`, где физические
  имена колонок сознательно не трогали при рефакторинге самого класса).
- Что если `settings: Song` объявлен в файле модуля `karaoke-web`, а не
  только `karaoke-app`? → Оба модуля входят в область работ (обнаружены
  вхождения также в `karaoke-web/.../PublicPlayerController.kt` и др.).
- Что если backend и frontend (webvue3) деплоятся не одновременно из-за
  особенностей CI/CD? → Ветка/PR должны мержиться и разворачиваться как один
  атомарный шаг (см. FR-016) — раздельный деплой создаст временное окно, где
  часть эндпоинтов (`/changesettingsstatus`, `/songs_update`, health-report
  SSE) вернёт ошибку из-за несовпадения имён параметров/ключей между старым
  и новым фронтендом/бэкендом.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Во всех Kotlin-файлах модулей `karaoke-app` и `karaoke-web`
  каждый параметр функции с объявленным типом `Song` и именем `settings`
  ДОЛЖЕН быть переименован в `song` (или в другое однозначное имя при
  конфликте, см. Edge Cases), включая обновление всех использований этого
  параметра внутри тела функции.
- **FR-002**: Каждая локальная переменная (`val`/`var`) с типом `Song`
  (явным или выводимым из присваиваемого выражения) и именем `settings`
  ДОЛЖНА быть переименована в `song`, включая обновление всех
  использований ниже по коду в той же области видимости.
- **FR-003**: Каждое свойство класса/data class с типом `Song` и именем
  `settings` (например, в конструкторах `HealthReport`, `SongRenderContext`)
  ДОЛЖНО быть переименовано в `song`, включая обновление всех точек
  создания объекта (именованные аргументы) и всех обращений к полю по
  всей кодовой базе.
- **FR-004**: Идентификаторы `settings`/`settings*`, не представляющие
  значение или идентификатор `Song` и не входящие ни в один из контрактов,
  перечисленных в FR-010…FR-013 (например,
  `KaraokePlatform.settingsFieldPublicationId`/`settingsFieldVersionNumber`,
  настройки плеера в `karaoke-public`), НЕ ДОЛЖНЫ быть переименованы и
  должны остаться без изменений.
- **FR-005**: Физические имена объектов базы данных (имена колонок, включая
  `settings_id`, и любые другие физические идентификаторы БД), НЕ ДОЛЖНЫ
  изменяться этим рефакторингом; строковые аргументы аннотаций маппинга
  (например, `@KaraokeDbTableField(name = "settings_id")`) остаются как
  есть даже при переименовании соответствующего Kotlin-свойства.
- **FR-006**: После рефакторинга проект ДОЛЖЕН успешно собираться
  (`./gradlew build` для затронутых модулей) без новых ошибок компиляции.
- **FR-007**: После рефакторинга проверка `ktlintCheck` ДОЛЖНА проходить
  без новых нарушений, вызванных переименованием.
- **FR-008**: Рефакторинг НЕ ДОЛЖЕН изменять логику/поведение функций —
  единственное изменение — это имена идентификаторов, ключей контрактов и
  связанные с ними обращения.
- **FR-009**: При конфликте имён (в области видимости уже существует
  идентификатор `song`, отличный по смыслу от переименовываемого) ДОЛЖНО
  быть выбрано другое явное, осмысленное имя вместо `song`, а не пропуск
  переименования.
- **FR-010**: Поля DTO, сериализуемые в JSON и хранящие значение/
  идентификатор `Song` под именем `settings*` (`HealthReportDTO.settingsId`,
  `HealthReportDTO.settingsFileName`, `KaraokeProcessDTO.settingsId` и любые
  аналогичные, обнаруженные при реализации), ДОЛЖНЫ быть переименованы на
  `song*`-эквивалент вместе со всеми местами создания/чтения DTO в Kotlin и
  со всеми обращениями к этим JSON-ключам в webvue3
  (`SongsTable.vue`, `Songs/store.js`, `HealthReport/store.js`,
  `HealthReport/components/HealthReportTableBody.vue`,
  `HealthReport/components/HealthReportTableHeader.vue`, и любые другие
  найденные при реализации).
- **FR-011**: HTTP query/form-параметры контроллеров, чьё имя в запросе
  определяется именем Kotlin-параметра (`@RequestParam` без явного `name=`)
  и хранит значение/идентификатор `Song` под именем `settings*`
  (например, `settingsId` в `POST /changesettingsstatus`, `settings_id`,
  `settings_songName`, `settings_author` и т.д. — все 54 параметра (по 27 в
  каждом) в двух методах `/songs_update`-семейства в `MainController.kt`), ДОЛЖНЫ быть
  переименованы на `song*`/`song_xxx`-эквивалент вместе с обновлением всех
  вызывающих сторон: `karaoke-app/src/main/resources/static/settings_context.js`
  и Thymeleaf-шаблонов `songs.html`, `songs2.html`, `area_center_column.html`.
- **FR-012**: Строковые ключи, вручную формируемые для передачи данных о
  `Song` через SSE (например, `"settingsId" to settingsId` в
  `SseNotification.kt`), ДОЛЖНЫ быть переименованы на `song*`-эквивалент
  вместе с обновлением кода, читающего эти события на фронтенде
  (`webvue3/src/components/Songs/store.js` и любой другой найденный при
  реализации SSE-слушатель).
- **FR-013**: Прочие производные идентификаторы (локальные переменные,
  параметры функций и свойства), чьё имя содержит `settings` и которые по
  контексту явно хранят значение/идентификатор/список `Song` (например,
  `settingsId: Long`, `settingsList: List<Song>`, `settingsLocal`,
  `settingsByAuthor`, `settingsByAlbum`), ДОЛЖНЫ быть переименованы на
  `song*`-эквивалент, даже если объявленный тип — не буквально `Song`
  (`Long`, `List<Song>`, `Map<...>` и т.п.).
- **FR-014**: Модуль `karaoke-public` НЕ входит в область этой задачи —
  найденные в нём идентификаторы `settings*` относятся к пользовательским
  настройкам плеера и не связаны с сущностью `Song`.
- **FR-015**: После рефакторинга ни один известный на момент планирования
  потребитель переименованных DTO-полей/HTTP-параметров/SSE-ключей
  (перечисленные в FR-010…FR-012 файлы webvue3, `settings_context.js`,
  три Thymeleaf-шаблона) НЕ ДОЛЖЕН обращаться к старому (`settings*`) имени
  контракта — рассинхронизация имени на одной из сторон недопустима.
- **FR-016**: Все изменения этой задачи (оба backend-модуля, webvue3,
  legacy Thymeleaf-шаблоны) ДОЛЖНЫ быть доставлены одним PR и задеплоены
  одним атомарным шагом, чтобы не возникало окна с несовпадающими именами
  контракта между backend и frontend.

### Key Entities

- **Параметр/переменная/поле типа `Song`**: место в Kotlin-коде модулей
  `karaoke-app` и `karaoke-web`, где объявлен идентификатор с типом `Song`
  под историческим именем `settings`, требующее переименования в `song`.
- **Производный идентификатор `Song`**: параметр/переменная/поле, чей тип не
  равен буквально `Song` (`Long`, `List<Song>`, `Map<...>` и т.п.), но
  значение по контексту представляет `Song`/её идентификатор
  (`settingsId`, `settingsList`); переименовывается наравне с прямыми
  Song-типизированными идентификаторами (FR-013).
- **DTO/HTTP/SSE-контракт, связанный с `Song`**: поле DTO, HTTP-параметр или
  SSE-ключ с именем `settings*`, хранящий значение/идентификатор `Song` и
  пересекающий границу backend↔frontend; переименовывается синхронно с
  всеми известными потребителями (FR-010…FR-012, FR-015).
- **Не связанный с `Song` идентификатор `settings`**: параметр/переменная/
  поле/ключ с именем `settings*`, который не представляет значение/
  идентификатор `Song` и не входит ни в один найденный DTO/HTTP/SSE-контракт
  (например, конфигурация платформы публикации, настройки плеера); не
  входит в область изменений (FR-004).
- **Физический объект БД**: имя колонки/таблицы/индекса в PostgreSQL,
  ссылающееся на устаревшее имя (`settings_id` и т.п.); не переименовывается
  этой задачей (FR-005) независимо от переименования связанного
  Kotlin-свойства.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Поиск по кодовой базе не находит ни одного параметра функции
  вида `settings: Song` — 0 совпадений после рефакторинга (при первичном
  сканировании обнаружено 54 такие сигнатуры в 14 файлах).
- **SC-002**: Поиск по кодовой базе не находит ни одной локальной переменной
  или поля класса с типом `Song`, объявленных как `settings` (при
  первичном сканировании — 227 объявлений `val`/`var settings` в 30
  файлах).
- **SC-003**: Полная сборка проекта и статический анализ (`ktlintCheck`,
  `npm run lint:check` для webvue3) проходят успешно на 100% затронутых
  модулей после рефакторинга, без ручных доработок помимо самого
  переименования.
- **SC-004**: Ни один тест из существующего набора (если есть покрывающие
  затронутые функции) не изменил результат выполнения после рефакторинга.
- **SC-005**: Поиск по кодовой базе не находит ключей/полей `settingsId`,
  `settingsFileName` в `HealthReportDTO`/`KaraokeProcessDTO` и в
  соответствующих файлах webvue3 (`SongsTable.vue`, `Songs/store.js`,
  `HealthReport/store.js`, `HealthReport/components/*.vue`) — 0 совпадений
  после рефакторинга.
- **SC-006**: `POST /changesettingsstatus` и оба метода `/songs_update`-
  семейства принимают параметры под новыми (`song*`/`song_xxx`) именами;
  `settings_context.js` и три Thymeleaf-шаблона (`songs.html`, `songs2.html`,
  `area_center_column.html`) отправляют запросы с этими новыми именами —
  ручная проверка через UI подтверждает, что легаси-формы продолжают
  сохранять песню без ошибок.
- **SC-007**: Всё изменение доставлено и задеплоено одним PR — нет
  промежуточного состояния, в котором backend и frontend расходятся по
  именам контракта.

## Assumptions

- Переименование затрагивает оба backend-модуля (`karaoke-app`,
  `karaoke-web`) и модуль `webvue3` (там, где он потребляет переименованные
  DTO/HTTP/SSE-контракты); модуль `karaoke-public` не затрагивается — его
  идентификаторы `settings*` относятся к пользовательским настройкам плеера
  и не связаны с сущностью `Song` (FR-014).
- Существующие вызовы с именованными аргументами вида `settings = someSong`
  относятся к внутренним Kotlin-вызовам и подлежат переименованию вместе с
  соответствующим параметром/полем (FR-001/FR-003).
- Физическая схема базы данных не меняется этой задачей (FR-005) — по
  прецеденту `deploy/karaoke-db/28_rename_settings_to_songs.sql`
  (`specs/011-album-song-rename`), где при самом переименовании класса
  Settings→Song физические имена колонок сознательно не трогали.
  SQL-миграция в рамках этой задачи не создаётся.
- Задача является техническим рефакторингом без изменения бизнес-логики,
  но затрагивает internal HTTP/SSE-контракт между backend и frontend
  (FR-010…FR-012), поэтому per-feature документ (`docs/features/<slug>.md`)
  не создаётся, но в `docs/architecture-notes.md` будет добавлена запись о
  факте переименования и о том, что PR правил оба backend-модуля и webvue3
  одновременно; коммит(ы) будут добавлены в `.git-blame-ignore-revs` по
  аналогии с прежними массовыми механическими рефакторингами.
- Список файлов-потребителей DTO/HTTP/SSE-контрактов (FR-010…FR-012)
  составлен по результатам разведки на этапе спецификации; при реализации
  требуется финальный grep-проход по каждому переименованному
  контрактному имени, чтобы не пропустить потребителя, не найденного на
  этом этапе (см. Edge Cases).
- Несмотря на масштаб (35+ файлов Kotlin + несколько файлов webvue3 +
  3 Thymeleaf-шаблона), всё изменение доставляется одним PR (FR-016) —
  по решению пользователя, т.к. часть переименований требует синхронного
  деплоя backend и frontend.
