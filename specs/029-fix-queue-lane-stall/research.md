# Research: Устранение зависания очереди заданий по лейнам

**Feature**: [spec.md](./spec.md) | **Plan**: [plan.md](./plan.md)

Technical Context не содержит открытых `NEEDS CLARIFICATION` — стек и
архитектура уже зафиксированы существующим кодом. Задача Phase 0 для этой
фичи — диагностика первопричины (это баг-фикс), а не выбор технологий.
Ниже — находки по коду `KaraokeProcessWorker.kt`/`KaraokeProcess.kt`
(текущее состояние на момент создания плана) и решение по подходу.

## Кандидат A — гонка данных вокруг общих полей `KaraokeProcessWorker` (главная причина)

**Находка**: `threadsMap`, `isWork`, `stopAfterThreadIsDone`, `withoutControl`
— поля `companion object` (`KaraokeProcessWorker.kt:427-445`), то есть
процесс-wide синглтон-состояние. `threadsMap` — обычный `mutableMapOf()`,
без синхронизации.

Кто их мутирует:
- Поток, исполняющий бесконечный цикл `doStart()` (строки 558-922) — читает
  и пишет `threadsMap` на каждой итерации (создание/запуск новых
  `KaraokeProcessThread`, строки 853-901).
- HTTP-эндпоинт `/api/processes/workerstartstop`
  (`ApiController.getProcessWorkerStartStop`, `ApiController.kt:5631-5639`)
  вызывает `KaraokeProcessWorker.start(...)` **напрямую, без обёртки в
  отдельный `Thread`** — значит, `doStart()`'s `while(isWork)` цикл
  физически выполняется на потоке Tomcat/Spring-обработчика этого запроса.
- Другой HTTP-запрос (`/api/processes/workerforcestop`,
  `ApiController.getProcessWorkerForceStop`) на **другом** потоке вызывает
  `KaraokeProcessWorker.forceStop()` (`KaraokeProcessWorker.kt:933-966`),
  которая без какой-либо синхронизации: взводит `forceStopped` на живых
  потоках, `threads.forEach { ... kp.save() }`, `threadsMap.clear()` — то
  есть очищает ту же карту, которую поток `doStart()` может в этот момент
  читать/писать (например, между `threadsMap[threadId] = KaraokeProcessThread(...)`
  и последующим `.start()`, строки 870-881).

**Почему это похоже на первопричину**: жалоба пользователя — «периодически»
(классический признак состояния гонки, не детерминированного бага) и
«особенно если процессы в разных лейнах» (чем больше лейнов работает
параллельно, тем чаще происходят одновременные записи в `threadsMap` на
одной итерации цикла, тем выше шанс поймать неудачное чередование потоков
с конкурентным вызовом `stop()`/`forceStop()`/повторным `start()`).
Без синхронизации возможны потери записи в map (visibility) — новая запись
для лейна пишется, но `doStart()`-поток не видит её как «живую» на
следующей итерации, либо запись затирается `threadsMap.clear()` уже после
фактического `.start()` потока, из-за чего условие
`threadsIds.contains(threadId) && threadsMap[threadId]!!.isAlive` считает
лейн свободным, хотя реальный поток жив (или наоборот — считает лейн
занятым, хотя запись устарела).

**Decision**: заменить `threadsMap` на потокобезопасную коллекцию
(`java.util.concurrent.ConcurrentHashMap`) и защитить составные
read-modify-write операции над состоянием воркера (`isWork`,
`stopAfterThreadIsDone`, переход к следующему заданию лейна) единой
блокировкой/монитором на время критической секции — так, чтобы `forceStop()`
и очередная итерация `doStart()` не могли интерливиться на полпути
операции. Дополнительно — оставить `start()` неблокирующим для
HTTP-потока (выполнять `doStart()`-цикл в собственном демон-потоке, как уже
сделано для `TelegramUpdatesConsumer.start()`), чтобы вызывающий
HTTP-обработчик не занимал поток Tomcat навсегда и чтобы количество
одновременных «доступов» к `doStart()`-состоянию было предсказуемым (один
воркер-поток, а не потенциально несколько, если `/workerstartstop` дёрнут
повторно до того как предыдущий вызов «занял» цикл).

**Alternatives considered**:
- Оставить `mutableMapOf()`, добавить `@Synchronized` только на
  `forceStop()`/`doStop()` — отклонено: не устраняет гонку, т.к. основной
  цикл `doStart()` всё равно пишет map без блокировки на каждой итерации;
  половинчатая синхронизация не даёт гарантий visibility.
- Полностью переписать очередь на `ExecutorService`/coroutines per lane —
  отклонено как избыточное для точечного фикса: увеличивает blast radius
  (Principle IV описывает текущую модель как основу для всех типов заданий),
  риск регрессии выше пользы; текущая модель «один поток на лейн +
  потокобезопасная карта» достаточна.

## Кандидат B — необработанное исключение при старте subprocess не переводит задание в терминальный статус

**Находка**: в ветке non-`runFunctionWithArgs` (`KaraokeProcessThread.run()`,
`KaraokeProcessWorker.kt:160-178`) вызов `processBuilder.start()` (строка 178)
находится **вне** `try/catch` — блок `try` начинается только на строке 191.
Если `start()` бросает исключение (например, недоступен docker-бинарь,
некорректные args), исключение всплывает необработанным из `Thread.run()`;
JVM печатает stack trace через `uncaughtExceptionHandler`, поток умирает, но
`karaokeProcess.status` остаётся `"WORKING"` навсегда — запись не попадает ни
в `DONE`, ни в `ERROR`, ни обратно в `WAITING`.

**Эффект на прогресс очереди**: сама очередь лейна не блокируется — `doStart()`
видит, что поток для `threadId` не `isAlive`, и на следующей итерации
запускает **следующее** `WAITING`-задание того же лейна (т.к.
`getProcessesToStart()` выбирает `WAITING`-записи, а «зависшая» запись уже не
`WAITING`). Но: (1) это ровно механизм, который объясняет уже накопившиеся в
БД «фантомные» `WORKING`-записи (Assumptions/FR-006 спеки), и (2) в
комбинации с Кандидатом A (тот же `threadsMap[threadId] = ...; .start()`
паттерн, который гонка может «потерять») может усугублять видимость бага.

**Decision**: расширить `try/catch` так, чтобы он охватывал и запуск
процесса (`processBuilder.start()`), не только чтение stdout — при любом
исключении на этом пути задание переводится в `ERROR` (или `WAITING` при
`forceStopped`), симметрично уже существующей обработке в ветке
`runFunctionWithArgs` (строки 138-159).

**Alternatives considered**: периодический «уборщик» зависших `WORKING`-записей
без правки самого источника исключения — отклонено как полумера: не
устраняет причину, только маскирует симптом с задержкой (уборщик сработает
не раньше своего интервала).

## Кандидат C — периодическое восстановление «осиротевших» `WORKING`-записей

**Находка**: `KaraokeProcess.setWorkingToWaiting()` (`KaraokeProcess.kt:586-607`)
уже существует и переводит все `WORKING` → `WAITING`, но вызывается только в
двух местах: при явном `start()` воркера (`KaraokeProcessWorker.kt:472-475`)
и внутри `forceStop()` как backstop (строка 961). Между перезапусками
приложения (пока `karaoke-app` продолжает работать без рестарта) такого
переразбора не происходит — если запись всё же осиротеет (Кандидат B) без
рестарта воркера, она провисит в `WORKING` неограниченно долго и будет
обнаружена только вручную (через UI таблицы «Процессы»).

**Decision**: новая проверка мониторинга (см. `data-model.md`/`contracts/`)
не просто оповещает, но и в рамках своего `resolveAction` перепроверяет и
возвращает такие осиротевшие записи лейна в `WAITING`, используя тот же
принцип, что и `setWorkingToWaiting()` — точечно, по конкретному `threadId`,
а не глобально по всей таблице (чтобы не трогать реально выполняющиеся
задания в других лейнах).

**Alternatives considered**: расширить сам `MonitoringService.tick()`
(раз в минуту) до безусловного `setWorkingToWaiting()` по всем «мёртвым»
`threadId` — отклонено: `MonitoringService` уже сознательно построен вокруг
модели «alert + one-click resolve» (см. `RenderQueueStalledCheck`), полностью
автоматическое вмешательство в статусы заданий без пути отката повышает
риск гонки с легитимно работающим лейном (см. Edge Case про одновременный
форс-стоп и восстановление, FR-007).

## Итоговый подход

1. Синхронизировать доступ к общему состоянию `KaraokeProcessWorker`
   (Кандидат A) — это единственное изменение, напрямую покрывающее FR-001/
   FR-002/FR-007 (надёжный автостарт, независимость лейнов, отсутствие
   дублирующего запуска при восстановлении).
2. Расширить `try/catch` вокруг запуска subprocess (Кандидат B) — покрывает
   FR-003 (терминальный статус при непредвиденном сбое).
3. Добавить `LaneStalledCheck` (по образцу `RenderQueueStalledCheck`) с
   точечным восстановлением осиротевших `WORKING`-записей лейна в
   `resolveAction` (Кандидат C) — покрывает FR-004/FR-005/FR-006.

Все три пункта — правки внутри уже существующих файлов/паттернов, без новых
зависимостей, без миграций схемы БД, без изменений фронтенда.
