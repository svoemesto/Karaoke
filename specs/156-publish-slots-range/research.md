# Research: Расширение диапазона свободных слотов публикации

Технический контекст полностью определён существующим кодом и стеком проекта —
неразрешённых `NEEDS CLARIFICATION` в Technical Context плана нет. Ниже
зафиксированы решения по конкретным техническим вопросам, возникшим при чтении
текущей реализации.

## Вопрос 1: Как хранить/вычислять 13 часовых слотов вместо 7 `UNION ALL`-подзапросов?

**Decision**: Заменить список из 7 почти идентичных SQL-подзапросов (`Utils.kt:4769-4867`,
по одному `UNION ALL subqueryNN` на час) одним запросом с `GROUP BY publish_time`,
возвращающим `MAX(TO_DATE(publish_date, 'DD.MM.YY'))` для каждого из 13 часов
(`10:00`…`22:00`), плюс дальнейшую обработку в Kotlin.

**Rationale**:
- Убирает копипасту из 7 (→13, если бы просто добавили ещё блоков) почти одинаковых
  подзапросов — на 13 часов пришлось бы 13 блоков по ~8 строк SQL, что хуже читается
  и легче сломать (уже есть опечатка `UNION all`/`UNION ALL` в разном регистре в
  текущем коде — маркер копипасты).
- Один сгруппированный запрос соответствует Principle II конституции («пакетная
  загрузка, не по одной в цикле») лучше, чем текущие 7 отдельных подзапросов.
- Часы, для которых ещё нет ни одной записи, просто отсутствуют в результирующем
  `Map<String, LocalDate?>` (используем `getOrDefault`/`?:` → `null`), что упрощает
  реализацию FR-003 («никогда не занимался → предложить сегодня/завтра») — не нужно
  придумывать SQL-трюк с `LEFT JOIN` на сгенерированный список часов.

**Alternatives considered**:
- Оставить 13 отдельных `UNION ALL`-подзапросов (просто скопировать текущий паттерн
  ещё 6 раз) — отклонено: расширяет уже существующую копипасту, не даёт естественного
  способа отличить «час никогда не использовался» без доп. `LEFT JOIN`.
- Полностью перенести вычисление даты в SQL (одним запросом с `CASE`/`GENERATE_SERIES`
  по часам и сравнением с `NOW()`) — отклонено: усложняет читаемость SQL ради логики,
  которая тривиально и явно выражается в Kotlin (`LocalDateTime` арифметика), а
  тестировать/читать Kotlin-код с датами проще, чем эквивалентный PL/pgSQL.

## Вопрос 2: Как гарантировать «строго в будущем» (FR-004) единообразно для всех веток (есть история / нет истории)?

**Decision**: Единый цикл в Kotlin для каждого из 13 часов `H`:
1. `lastDate = map[H]` (может быть `null`).
2. `candidate = (lastDate?.plusDays(1) ?: LocalDate.now()).atTime(H, 0)`.
3. `while (candidate <= LocalDateTime.now()) candidate = candidate.plusDays(1)`.
4. Форматировать `candidate` как `dd.MM.yy HH:mm` (как сейчас) и добавить в результат.

**Rationale**: Один и тот же цикл покрывает все сценарии из spec.md без ветвления
по «был ли слот занят раньше»: если история есть и найденный кандидат уже в
прошлом/наступил — цикл дотянет его до ближайшего будущего дня; если истории нет —
стартовая точка «сегодня» либо сразу проходит проверку (час ещё не наступил →
предлагаем сегодня), либо цикл сдвигает на завтра (час уже прошёл). Это то же самое
правило, что описано в acceptance-сценариях User Story 2 (месяц назад → +1 день всё
ещё в прошлом → цикл довозит до завтра; никогда не было → сегодня/завтра).

**Alternatives considered**:
- Отдельная явная ветка `if (lastDate == null) {...} else {...}` с дублированием
  логики сравнения с `now()` — отклонено: две копии одной и той же проверки
  «в будущем ли», больше шансов рассинхронизировать поведение при будущих правках.
- Вычисление кандидата через `max(candidate, now)` без цикла — отклонено: не решает
  случай «кандидат раньше сегодняшнего часа H, но позже полуночи» (например,
  H=10:00, сейчас 12:00, кандидат — сегодня 10:00: `candidate < now`, но
  `max(candidate, now)` дало бы `now` = 12:00, а не «10:00 следующего дня», как
  требует FR-004/acceptance-сценарий 1 User Story 2); цикл с шагом «+1 день»
  корректно обрабатывает это, так как всегда добавляет ровно сутки, сохраняя час H.

## Вопрос 3: Нужны ли новые зависимости/импорты?

**Decision**: Использовать `java.time.LocalDate`, `java.time.LocalDateTime` (уже
доступны в JDK 17, стандартная библиотека, дополнительных Gradle-зависимостей не
требуется). В `Utils.kt` пока импортированы только `Instant`/`DateTimeFormatter`/
`Timestamp` — добавить `import java.time.LocalDate` и `import java.time.LocalDateTime`.

**Rationale**: Проект уже использует `java.time.*` в других местах кодовой базы
(стандартная практика Kotlin/JDK 17), никакого нового стороннего стека не вводится.

**Alternatives considered**: Продолжать оперировать `java.sql.Timestamp`/
`SimpleDateFormat`, как в части текущего кода, — отклонено: `LocalDate`/
`LocalDateTime` дают более безопасную (immutable, no timezone footguns в рамках
одного JVM) арифметику дат для цикла «+1 день, пока не в будущем», чем ручная работа
с `Calendar`/`SimpleDateFormat`.
