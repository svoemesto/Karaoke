# Research: Исправление автоподстановки найденного текста песни

## Контекст

Технический контекст полностью определён существующей кодовой базой — новых
технологий/библиотек не требуется. Ниже — решения по конкретным вопросам HOW,
не покрытым напрямую в spec.md (там — только WHAT/WHY).

## Вопрос 1: Как согласовать определение "текста ещё нет" во всех местах?

**Найденный текущий разнобой** (подтверждён чтением кода):

- `Song.haveSourceText` (`karaoke-app/.../model/Song.kt:382`) — **правильная**
  реализация: `sourceText != "" && sourceText != "[\"\"]"`. Используется как
  гейт "запускать ли поиск вообще" в `ApiController.getSearchSongTextAll`.
- `UtilsAI.kt:226` (движки SEARXNG/FOURGET, функция
  `getLyricsSearchViaSearchTool`) — **неправильная**: `settings.sourceText.isBlank()`
  не ловит `'[""]'`, поэтому подстановка молча не срабатывает для этого
  представления.
- `KaraokeProcessWorker.kt:627` (обработка завершённого асинхронного
  Yandex-запроса) — та же неправильная проверка `settings.sourceText.isBlank()`.
- `getYandexSearch(..., async=false)` (синхронный Yandex, `UtilsAI.kt:351-378`)
  — проверки нет вообще, потому что для этой ветки не реализован шаг
  подстановки (см. Вопрос 2).

**Decision**: заменить обе проверки `settings.sourceText.isBlank()` на
`!settings.haveSourceText`, переиспользуя уже существующий корректный
computed-property вместо дублирования литералов `""`/`"[\"\"]"` в новом месте.

**Rationale**: единственный источник истины уже есть в `Song.kt`; дублирование
тех же двух строковых литералов в третьем месте воспроизвело бы тот же класс
бага при следующем изменении формата "пустого" значения.

**Alternatives considered**:
- Продублировать проверку `sourceText != "" && sourceText != "[\"\"]"` инлайном
  в каждом месте — отклонено: это и есть текущий баг (рассинхронизация копий
  одной и той же логики).
- Ввести общий regex/нормализатор для произвольных "пустых" представлений —
  отклонено как избыточное для двух явно подтверждённых автором значений
  (см. Assumptions в spec.md).

## Вопрос 2: Почему YANDEX_SYNC не подставляет найденный текст вообще?

**Находка**: в отличие от веток SEARXNG/FOURGET (инлайновая логика в
`getLyricsSearchViaSearchTool`) и асинхронной Yandex-ветки (обработка в
`KaraokeProcessWorker.checkSearchAsync`), синхронная Yandex-ветка
(`getYandexSearch(..., async=false)`) только сохраняет `SearchAsync` с
`done=true` и заполненным `rawData` — сама не разбирает `rawData` в
`SearchResult` и не вызывает подстановку. Разбор `rawData` в `SearchResult`
(`SearchResult.getSearchResultsForSearchAsync`) в проде сегодня вызывается
только из фонового воркера для асинхронной ветки.

**Decision**: выделить общий шаг "разобрать законченный `SearchAsync` в
`SearchResult` + подставить первый непустой текст, если `!haveSourceText`" в
одну переиспользуемую функцию и вызывать её из всех трёх точек завершения
поиска:
1. конец синхронной Yandex-ветки (`getYandexSearch`, после сохранения
   `savedResult` с `rawData`) — сейчас эта точка отсутствует, добавляется;
2. конец обработки завершённого асинхронного Yandex-запроса
   (`KaraokeProcessWorker.kt:600-636`) — сейчас инлайн, заменяется на вызов
   общей функции;
3. SEARXNG/FOURGET (`UtilsAI.kt:210-231`) — сейчас инлайн со своим сбором
   `variants`/`searchedRightResults` (другой источник кандидатов — не через
   `SearchResult.getSearchResultsForSearchAsync`, а напрямую через
   `lyricsFinderService.extractLyricsFromUrl`); эта ветка использует
   собственный список готовых `SearchResult`, поэтому переиспользует только
   финальный шаг "подставить первый непустой текст, если `!haveSourceText`",
   не весь разбор.

**Rationale**: соответствует FR-003 spec.md ("автоподстановка должна
срабатывать одинаково независимо от движка"); минимизирует дублирование кода
условия из Вопроса 1 — оно теперь существует в одном месте.

**Alternatives considered**:
- Оставить YANDEX_SYNC без подстановки, исправить только
  `isBlank()`→`haveSourceText` там, где подстановка уже есть — отклонено:
  прямо противоречит FR-003 и подтверждённому пользователем сценарию
  (Edge Cases spec.md, пункт про YANDEX_SYNC).
- Синхронно скрейпить страницы по ссылкам из Yandex-ответа в отдельном
  фоновом потоке (по аналогии с Principle IV конституции про
  async-очередь) — отклонено как избыточное усложнение: Principle IV
  конституции покрывает тяжёлые медиа-операции (ffmpeg/melt/Demucs), а не
  лёгкие HTTP-скрейпинг-запросы; SEARXNG/FOURGET уже делают тот же скрейпинг
  синхронно в том же HTTP-хендлере без нарушения принципа.

## Вопрос 3: Нужны ли изменения схемы БД или новых таблиц?

**Decision**: нет. Поля `tbl_songs.source_text`, `tbl_search_async`,
`tbl_search_results` не меняются по структуре — меняется только код,
интерпретирующий существующее значение `source_text`.

## Вопрос 4: Как проверить исправление без полноценного CI (тесты в основном `@Disabled`)?

**Decision**: ручная проверка (см. `quickstart.md`) через выставление
`source_text = '[""]'` конкретной тестовой песне в БД и запуск поиска для неё
через UI/`/api/songs/searchsongtextall`, для каждого из 4 движков по очереди.
Соответствует зафиксированному в конституции правилу «Тесты» — существующие
интеграционные тесты не являются надёжной проверкой в CI, проверка делается
пользователем вручную.
