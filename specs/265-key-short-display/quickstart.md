# Quickstart: Валидация фичи краткого отображения тональности

**Feature**: 265-key-short-display
**Date**: 2026-08-30
**Related**: [spec.md](./spec.md), [plan.md](./plan.md), [research.md](./research.md), [data-model.md](./data-model.md), [contracts/key-display-contract.md](./contracts/key-display-contract.md)

Руководство для ручной end-to-end валидации фичи. CI-тестов в проекте нет (см. AGENTS.md, раздел «Тесты»), интеграционные `@Disabled` — для проверки не подходят. Валидация выполняется пользователем вручную в браузере.

## Предпосылки

- Локально запущенные:
  - **Backend `karaoke-app`** (admin-машина) — для отдачи playerdata.
  - **`webvue3` dev-сервер** (`cd webvue3 && npm run dev`) или собранный контейнер через `deploy/do.sh build_webvue3` + `start_webvue3`.
  - **`karaoke-public` dev-сервер** (`cd karaoke-public && npm run dev`) или собранный контейнер через `deploy/do.sh build_public` + `start_public`.
- В БД есть хотя бы **5 песен** с разными формами поля `key` (см. таблицу ниже) и 1 песня с **пустым** `key`.
- Современный браузер с поддержкой HTML5 Canvas (Chrome 90+, Firefox 90+, Safari 14+, Edge 90+).
- DevTools браузера (для проверки DOM/canvas).

## Подготовка

1. Убедиться, что ветка `265-key-short-display` активна:
   ```bash
   git branch --show-current
   # → 265-key-short-display
   ```
2. В БД подготовить 6 песен (или найти существующие) с полем `key`:

   | Песня | `key` (исходное) | Ожидаемая короткая форма |
   |-------|------------------|---------------------------|
   | Тест 1 | `"G minor"` | `"Gm"` |
   | Тест 2 | `"A major"` | `"A"` |
   | Тест 3 | `"F# minor"` | `"F#m"` |
   | Тест 4 | `"Bb minor"` | `"A#m"` |
   | Тест 5 | `"Am"` (уже короткий) | `"Am"` (идемпотентно) |
   | Тест 6 | `""` (пусто) | (строка скрыта) |

3. Перезапустить локальные контейнеры, если правки уже внесены:
   ```bash
   cd deploy
   bash do.sh build_webvue3       # если менялся webvue3
   bash do.sh build_public        # если менялся karaoke-public
   ```
   (Один из двух, в зависимости от того, какая копия плеера правилась в этой итерации.)

## Сценарии валидации

Каждый сценарий = 1 SC (Success Criterion из спеки). Сценарии можно проходить в любом порядке.

### SC-001 — Сплэш публичного плеера показывает короткую тональность

1. Открыть `https://<local-host>/player/<id_тест_1>` (песня с `key = "G minor"`).
2. Дождаться отрисовки сплэша (≈0.5 сек).
3. **Ожидается**: в нижней части сплэша строка `Key: «Gm», bpm: <bpm>` (а НЕ `Key: «G minor», bpm: <bpm>`).
4. Повторить для тест 2, тест 3, тест 4 (с `"A major"`, `"F# minor"`, `"Bb minor"`):
   - Тест 2: `Key: «A», bpm: <bpm>`
   - Тест 3: `Key: «F#m», bpm: <bpm>`
   - Тест 4: `Key: «A#m», bpm: <bpm>` (flat→sharp нормализация)

### SC-002 — Header.metadata публичного плеера показывает короткую тональность

1. На странице `/player/<id_тест_1>` (песня с `key = "G minor"`) запустить воспроизведение ▶.
2. **Ожидается**: в блоке метаданных хедера (поверх видео-области, левый верхний угол) строка `Тональность: Gm` (а НЕ `Тональность: G minor`).
3. Повторить для тест 2 (`"A major"`) — `Тональность: A`; для тест 3 (`"F# minor"`) — `Тональность: F#m`.

### SC-003 — Сплэш админ-плеера (online) показывает короткую тональность

1. В админке открыть `/player/<id_тест_2>` (песня с `key = "A major"`).
2. Дождаться отрисовки сплэша.
3. **Ожидается**: строка `Key: «A», bpm: <bpm>`.

### SC-003a — Сплэш админ-плеера (MP4 render) показывает короткую тональность

1. В админке открыть `/player/<id_тест_2>` и инициировать MP4-рендер (через UI рендера — кнопка/меню зависит от реализации).
2. Дождаться завершения рендера.
3. Скачать mp4-файл и проиграть его.
4. **Ожидается**: в начале видео (на сплэш-кадре) видна строка `Key: «A», bpm: <bpm>`.

### SC-004 — Header.metadata админ-плеера показывает короткую тональность

1. В админке открыть `/player/<id_тест_3>` (песня с `key = "F# minor"`).
2. Запустить воспроизведение.
3. **Ожидается**: в блоке метаданных хедера строка `Тональность: F#m` (а НЕ `Тональность: F# minor`).
4. Повторить для тест 4 (`"Bb minor"`) — `Тональность: A#m` (flat→sharp нормализация).

### SC-005 — Меню «Тональность» и бейдж transpose НЕ изменились

1. Открыть `/player/<id_тест_1>` (публичный или админский).
2. Кликнуть ☰ (Меню) → «Тональность».
3. **Ожидается**: пункты подменю имеют формат `(+N) <note>` или `(+N) <note>m` — например, `(+0) Gm`, `(+3) Am`, `(-1) F#m` (со скобками со сдвигом первым). Не изменились по сравнению с master.
4. Выбрать `(+3) Am` (или любой ненулевой сдвиг).
5. **Ожидается**: в правом верхнем углу экрана — синий бейдж `Am (+3)` (формат «note +m shift в скобках»). Не изменился по сравнению с master.

### SC-006 — Пустой `data.key` — поведение как раньше

1. Открыть `/player/<id_тест_6>` (песня с пустым `key`).
2. Дождаться сплэша.
3. **Ожидается**: строка содержит только `bpm: <bpm>` (без `Key: «…»`). Регрессии нет.
4. Запустить воспроизведение.
5. **Ожидается**: в блоке метаданных хедера НЕТ строки `Тональность:`. Регрессии нет.

### SC-007 — Нераспознанный `data.key` — fallback «как есть»

1. В БД установить одной из песен `key = "C maj7"` (или другой нераспознанный формат).
2. Открыть `/player/<id_этой_песни>`.
3. **Ожидается**: на сплэше строка `Key: «C maj7», bpm: <bpm>` (исходное значение, fallback). Регрессии нет.
4. **Ожидается**: в header.metadata `Тональность: C maj7` (исходное значение, fallback).

### SC-008 — Идемпотентность: `Gm` на входе → `Gm` на выходе

1. В БД установить одной из песен `key = "Gm"` (уже короткий формат).
2. Открыть `/player/<id_этой_песни>`.
3. **Ожидается**: на сплэше `Key: «Gm», bpm: <bpm>` (а НЕ `Key: «Gm (+0)», bpm: <bpm>` — сдвиг не показывается на сплэше).
4. **Ожидается**: в header.metadata `Тональность: Gm`.

## Если что-то пошло не так

- **Виджеты ломаются** → проверить, что helper добавлен в обе копии; без одной из копий будет ошибка `KaraokePlayer._shortKey is not a function`.
- **Строка не сокращается** → проверить, что `_shortKey` вызывается в правильной точке; возможно, `this.data.key` не доходит (проверить `Network` → playerdata).
- **Бемоли не нормализуются** → проверить, что `_parseKey` корректно обрабатывает вход (существующая логика, не должна была сломаться).
- **Baseline растёт** → исправить новые ESLint-нарушения ДО merge (FR-013, NON-NEGOTIABLE).
