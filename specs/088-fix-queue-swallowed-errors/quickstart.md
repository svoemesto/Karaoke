# Quickstart: проверка единообразной обработки сбоев БД в очереди

**Feature**: [spec.md](./spec.md) | **Data model**: [data-model.md](./data-model.md)

Автотестов нет (обе функции требуют реального PostgreSQL). Проверка —
вручную на `dev-pc`/`dev`, тем же способом, что и в
specs/087-fix-shared-db-connection/quickstart.md (`docker pause`/`unpause karaoke-db`).

## Предусловия

- Локальный стек поднят (`db`, `karaoke-app`).
- После правок — пересобрать и перезапустить **только** модуль `app`:

```bash
cd deploy
bash do.sh build_app
bash do.sh start_app
```

- В очереди должно быть хотя бы одно `WAITING`-задание, очередь запущена
  (`POST /api/processes/workerstartstop`, проверить `POST /api/processes/workerstatus` → `isWork: true`).

## Сценарий 1 — сбой именно в `getCountWaiting`/`getProcessesToStart` теперь тоже роняет и восстанавливает цикл (US1, FR-001/FR-002/FR-003)

Это прямое воспроизведение пробела, найденного при верификации specs/087
(T010): раньше `docker pause karaoke-db` на несколько минут не ронял
`doStart()` вообще, если сбой «доставался» именно этим двум функциям.

1. `docker pause karaoke-db` на **несколько минут** (например, 3-4 минуты —
   достаточно долго, чтобы почти наверняка захватить момент, когда цикл
   вызывает именно `getCountWaiting()`/`getProcessesToStart()`, а не только
   `.save()`).
2. **Ожидаемый результат**: в логе `karaoke-app` появляются записи
   `ProcessWorker: главный цикл очереди упал с необработанным исключением
   (попытка N/5)` — так же, как раньше появлялись только при сбое в
   `.save()`. `docker unpause karaoke-db`.
3. **Ожидаемый результат**: очередь автоматически возобновляет обработку
   (`isWork: true`, задания переходят `WAITING → WORKING`) без клика
   оператора — тем же путём, что уже проверен в specs/087.

## Сценарий 2 — создание задания из UI не ломается при сбое БД в уведомлении (US1, FR-004)

1. Через `webvue3` (или `POST /api/song/...`, любой путь, ставящий новое
   задание в очередь) создать новое задание в момент, когда `karaoke-db`
   приостановлена (`docker pause`) — сама вставка строки задания либо
   успеет пройти до паузы, либо тоже упадёт (это не покрывается этой
   фичей — недоступность БД во время самой записи задания законно
   приводит к ошибке создания); важно проверить именно шаг **после**
   вставки — отправку уведомления о количестве ожидающих.
2. **Ожидаемый результат**: если вставка строки задания прошла успешно, то
   даже при сбое БД на следующем шаге (подсчёт количества ожидающих для
   уведомления) сам HTTP-ответ о создании задания не должен становиться
   ошибкой из-за этого конкретного шага — поведение как до этой фичи.
3. Дополнительно (code-review, не обязательно живой прогон): подтвердить,
   что `KaraokeProcess.kt:744` (внутри `createDbInstance()`) действительно
   не изменился в рамках этой фичи и по-прежнему вызывает `getCountWaiting()`
   без `throwOnError = true`.

## Сценарий 3 — мониторинг и `forceStop()`/per-job уведомление не регрессируют (FR-005)

1. Подтвердить по коду (без обязательного живого прогона): `RenderQueueStalledCheck.kt:18`,
   `LaneStalledCheck.kt:42`, `KaraokeProcessWorker.kt:204`, `:536` и `:1090`
   по-прежнему вызывают `getCountWaiting()`/`getProcessesToStart()` без
   `throwOnError = true`.
2. Опционально — живой прогон: вызвать `forceStop()` во время `docker pause
   karaoke-db`, убедиться, что HTTP-ответ на `/api/processes/workerforcestop`
   не становится 500 из-за финального уведомления (сама принудительная
   остановка при этом может быть частично ограничена недоступностью БД —
   это не регрессия этой фичи, а следствие самой недоступности БД).
