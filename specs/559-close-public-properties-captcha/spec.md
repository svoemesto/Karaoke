# Feature Specification: 559 — Закрыть анонимный доступ к публичным настройкам и fail-open проверку капчи (BR-019 + BR-518)

**Feature Branch**: `559-close-public-properties-captcha`

**Created**: 2026-10-24

**Status**: Draft

**Input**: User description: "Устранить два связанных S1-дефекта аудита кода (#336): BR-019 — весь префикс `/api/properties/**` на `karaoke-web` (запись в `tbl_public_settings` и чтение всех значений, включая серверный ключ капчи) доступен анонимно, так как в `SecurityConfig` всё помечено `permitAll()`, а перехватчик авторизации этот путь не покрывает; BR-518 — проверка капчи fail-open: при пустом серверном ключе `validate()` возвращает «проверка пройдена», и регистрация проходит без капчи. ### Ключевая находка pre-flight (факты, которых нет в карточке находки)

1. **Авторизации у `/api/properties/**` нет вообще.** `SecurityConfig` в `karaoke-web` помечает `permitAll()` и `/api/**`, и `anyRequest()`; перехватчик авторизации (`SiteAuthInterceptor`) зарегистрирован только для `/api/public/account/**`, `/api/public/auth/me`, `/api/public/auth/logout`, `/api/siteusers/**`. Следовательно, «закрыть» префикс — это добавить проверку в цепочку, которой сейчас нет, а не снять `permitAll` (это сломало бы публичный сайт).
2. **Секрет капчи лежит в той же таблице, что и kill-switch.** Таблица `tbl_public_settings` содержит и публичные настройки (`newsAutoPublishKillSwitch`, шаблоны новостей), и секрет `yandexSmartCaptchaServerKey`. Значит «закрыть только опасные ключи» — это не «убрать колонку», а разделить доступ по ключам.
3. **Легитимный административный путь записи в эту таблицу уже существует и не проходит через публичный префикс:** админка `webvue3` («Настройки сайта») пишет через `POST /api/publicsettings/update` на `karaoke-app` с `target=local|remote` (прод-БД включительно). Публичный эндпоинт `POST /api/properties/setproperty` на `karaoke-web` — это второй, операционный путь (curl с прод-хоста для kill-switch по quickstart спек 124/125), а не единственный.
4. **Два независимых кеша с разными TTL.** Ключ капчи читает сервис конфигурации капчи с кешем **5 минут** и без инвалидации по записи; публичное свойство читается с кешем **60 секунд** и с dirty-флагом, который гасится записью через публичный эндпоинт. Запись в таблицу **не** сбрасывает кеш ключа капчи — поэтому «отравление» держится до 5 минут даже после того, как публичная запись закрыта.
5. **Fail-open не единственный сценарий.** Пустой серверный ключ → проверка «пройдена». Ключ, подменённый на чужую пару → внешний валидатор отвечает «ok» → тоже «пройдена». Значит проверка «ключ не пуст» не закрывает нишу; закрывать надо именно запись.
6. **На публичном сайте ключ капчи отдаётся отдельно и легально** (`GET /api/public/auth/config` → клиентский ключ), поэтому публичную форму регистрации можно оставить работающей, не открывая общий дайджест настроек.

| **#362** (BR-518) | Проверка капчи fail-open: при незаконной/пустой конфигурации серверного ключа регистрация проходит без капчи | Поведение самой проверки капчи и место хранения секрета | FR-009 … FR-014 |

**Правило раздельной поставки:** правка **#359** закрывает «вход» (запись), правка **#362** закрывает «поведение при неверной конфигурации» и место хранения секрета. Починка только #359 оставляет fail-open включённым при любой ошибочной/пустой конфигурации (в т.ч. из-за ручной правки БД, отката деплоя или уже отравленного значения). Починка только #362 оставляет публичную запись в прод-БД, т.е. возможность подменить ключ на «свою» рабочую пару (fail-open по сути, а не по пустому значению) и менять поведение сайта через kill-switch. **Требуются обе.**

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Анонимный посетитель не может изменить публичные настройки сайта (Priority: P1)

Анонимный посетитель интернета (любой IP, без учётной записи, без ключа) пробует изменить настройку сайта — например, выключить авто-публикацию новостей или задать собственное значение ключа проверки капчи. До правки такой запрос принимался и значение попадало в рабочую базу сайта. После правки запрос отклоняется, значение в базе не меняется, попытка видна в журнале.

**Why this priority**: это вход в цепочку. Пока он открыт, любые другие защиты (в том числе fail-closed у капчи) обходятся подменой ключа. Остальные сценарии защищают от регрессии и от «половинчатой» починки.

**Independent Test**: с внешнего адреса без учётной записи выполнить один запрос на изменение любого значения публичной настройки → ожидается отказ, значение в базе не изменилось, в журнале есть запись об отказе; проверяется отдельно, без участия администратора.

**Acceptance Scenarios**:

1. **Given** анонимный клиент с внешнего адреса, **When** он отправляет запрос на изменение значения публичной настройки (любой ключ, любой текст), **Then** сервис отклоняет запрос, значение в базе не меняется, клиент получает отказ и не «успех».
2. **Given** анонимный клиент, **When** он отправляет запрос на изменение значения публичной настройки с ключом проверки капчи, **Then** отказ тот же, и в ответе нет текста ошибки базы данных и нет имён таблиц.
3. **Given** запрос отклонён, **When** администратор смотрит журнал, **Then** в журнале есть запись об отказе с указанием времени и источника, но без содержимого присланного запроса и без значения настройки.
4. **Given** анонимный клиент, **When** он запрашивает список всех публичных настроек (дайджест), **Then** в ответе нет серверного секрета проверки капчи (ни в явном виде, ни частично), а при полном закрытии префикса — отказ.

### User Story 2 — Регистрация не проходит без действующей проверки капчи (Priority: P1)

Посетитель сайта открывает форму регистрации и вводит данные. Если проверка капчи настроена и работает, регистрация требует решенную капчу. Если капча по какой-то причине не настроена (ключ пуст, ключ подменён, конфигурация не доехала до сервера), регистрация **не должна** проходить «просто так» — вместо этого посетитель получает внятный отказ, а администратор — запись в журнале. Массовая регистрация аккаунтов без капчи перестаёт быть возможна.

**Why this priority**: вторая половина цепочки. Даже после закрытия публичной записи пустой или подменённый ключ (из-за ручной правки, отката конфигурации или уже отравленного значения) оставил бы обход. Уязвимость без этой половины остаётся эксплуатируемой.

**Independent Test**: два независимых проверки: (1) при настроенной капче — регистрация без решенной капчи отклоняется, с решенной — проходит; (2) при незаконной конфигурации (ключ отсутствует/пуст) — регистрация отклоняется, а не проходит.

**Acceptance Scenarios**:

1. **Given** проверка капчи настроена и работает, **When** посетитель отправляет регистрацию без токена капчи, **Then** регистрация отклоняется, аккаунт не создаётся, посетитель получает внятный отказ.
2. **Given** проверка капчи настроена и работает, **When** посетитель отправляет регистрацию с действующим токеном капчи, **Then** аккаунт создаётся, действующий сценарий сайта не сломан.
3. **Given** серверный ключ проверки капчи не настроен или пуст (незаконная конфигурация), **When** посетитель отправляет регистрацию, **Then** регистрация отклоняется — обход «пустой ключ = проверка пройдена» невозможен; в журнале есть запись о том, что проверка не настроена (без значения ключа).
4. **Given** посетитель не может решить капчу, **When** он повторяет попытки, **Then** каждое отклонение видно в журнале, а количество созданных аккаунтов остаётся в ожидаемых пределах (нет всплеска регистраций без капчи).

### User Story 3 — Легитимный административный путь настроек продолжает работать (Priority: P2)

Администратор сайта должен и дальше управлять публичными настройками: посмотреть их список, изменить значение (в том числе ключ проверки капчи при его ротации), включить и снять kill-switch авто-публикации новостей по регламенту (curl с прод-хоста). Правка не должна ломать эти операции: они либо работают как раньше, либо получают новый, явно описанный и проверяемый порядок.

**Why this priority**: закрывая публичную запись, легко сломать рабочую операцию (ротация ключа капчи, аварийное включение kill-switch во время sync-окна). Это регрессионный риск операционного характера, важнее косметики.

**Independent Test**: из административного контура (админская машина) изменить значение публичной настройки и включить/снять kill-switch → изменения применяются, читаются обратно и наблюдаемы в поведении сайта.

**Acceptance Scenarios**:

1. **Given** администратор работает в административной панели, **When** он открывает список публичных настроек и меняет значение, **Then** изменение применяется к рабочей базе (в т.ч. к прод-базе при выбранном контуре) и новое значение читается обратно.
2. **Given** администратору нужно аварийно включить kill-switch авто-публикации, **When** он выполняет предусмотренную регламентом операцию, **Then** kill-switch переключается и его состояние видно, а при снятии — авто-публикация работает как раньше.
3. **Given** значение настройки изменено легитимным путём, **When** потребитель настройки читает её, **Then** новое значение видно без длительного ожидания (в пределах согласованного владельцем окна).

---

### User Story 4 — Отказы видны и не выдают деталей (Priority: P3)

Администратор должен видеть попытки анонимного доступа к настройкам и отказы регистрации из-за неверной конфигурации проверки, при этом наружу не должны утекать ни значения настроек, ни серверный секрет, ни технические детали базы.

**Why this priority**: полезно для эксплуатации и для проверки, что защита вообще включена, но не блокирует устранение уязвимости — поэтому P3.

**Independent Test**: один отклонённый запрос на запись + одна отклонённая регистрация → в журнале обе попытки видны; в ответах клиенту нет ни секрета, ни текста ошибки базы.

**Acceptance Scenarios**:

1. **Given** отклонённая попытка анонимной записи настройки, **When** открыт журнал приложения, **Then** в нём есть запись об отказе (категория безопасности) с временем и источником, без содержимого запроса и без значения настройки.
2. **Given** отклонённая регистрация, **When** открыт журнал приложения, **Then** в нём видно, что проверка капчи не пройдена или не настроена, без значения серверного ключа.
3. **Given** любой из отказов, **When** получен ответ клиенту, **Then** в теле ответа нет текста ошибки базы данных, нет имён таблиц и нет значений настроек.

---

### Edge Cases

- **Секрет проверки капчи не настроен (пустой/отсутствует в конфигурации)** → регистрация отклоняется, а не пропускается; публичная форма показывает внятное сообщение «регистрация временно недоступна» (или виджет капчи не рендерится и отправка отклоняется) — в журнале отдельная запись о неверной конфигурации. Секрет при этом нигде не публикуется и не подставляется в текст ошибки.
- **Кэш настроек с TTL: ключ капчи кэшируется на 5 минут и не сбрасывается записью.** Значение, записанное до закрытия публичной записи, остаётся действующим до истечения этого окна. Поэтому «закрыли запись» ≠ «ключ уже чист»: нужен либо сброс кеша при старте/изменении, либо перенос ключа в конфигурацию (читается при старте, кеш не нужен).
- **Гонка записи и кеша.** Два независимых кеша (публичное свойство — 60 секунд с dirty-флагом; ключ капчи — 5 минут без инвалидации) не связаны между собой: запись в таблицу гасит только первый. Дополнительно возможна гонка «проверка актуальности кеша → чтение из базы»: значение, записанное в этот промежуток, может быть подхвачено с задержкой до следующего обновления кеша. Наблюдаемое следствие: после исправления ключа конфигурации возможен остаточный эффект в пределах окна кеша — это окно должно быть измеримо и не больше согласованного.
- **Внешняя проверка капчи недоступна** (прокси/сеть/таймаут/MTU-разрыв) → проверка не проходит, регистрация отклоняется (fail-closed), а посетитель получает внятный отказ; в журнале видно, что внешний сервис недоступен, без значения ключа. Отличать этот случай от «капча не настроена» обязательно: сейчас оба случая приводят к тихому пропуску.
- **Ключ не пустой, но подменён на чужую пару** → внешний валидатор отвечает «успешно», проверка проходит. Это доказывает, что проверка «ключ не пуст» не является защитой; закрытие публичной записи — обязательная часть решения.
- **Публичный дайджест после правки.** Если префикс закрывается целиком, админская панель продолжит работать (она ходит в другой сервис по своему маршруту), а операционный curl-регламент kill-switch — перестанет работать; новый порядок должен быть описан владельцем до развёртывания, иначе аварийное действие во время sync-окна невозможно.
- **В таблице уже есть записи, оставленные анонимным клиентом** (неизвестно когда и какие). До закрытия публичной записи требуется инвентаризация текущих значений, в первую очередь ключа проверки капчи и kill-switch; порядок действий при найденном «отравленном» значении — на усмотрение владельца (см. «Решения, требующие владельца»).

## Requirements *(mandatory)*

### Functional Requirements

**Задача #359 (BR-019) — периметр публичных настроек**

- **FR-001** (#359): Система MUST отклонять любой запрос на изменение значения публичной настройки, выполненный без действующего разрешения администратора, и MUST NOT изменять значение в рабочей базе при таком запросе.
- **FR-002** (#359): Система MUST NOT отдавать анонимному клиенту значение серверного секрета проверки капчи ни через дайджест всех настроек, ни через чтение одного значения по ключу — ни целиком, ни частично, ни в виде производных значений.
- **FR-003** (#359): Система MUST отклонять запрос на изменение публичной настройки без указания того, что именно запрещено правилами проекта (без перечисления внутренних имён и допустимых ключей), и MUST возвращать клиенту отказ, различающий «нет прав» и «внутренняя ошибка».
- **FR-004** (#359): Каждый отклонённый запрос на изменение публичной настройки MUST попадать в журнал приложения с указанием времени и источника запроса; содержимое запроса и значение настройки в журнал MUST NOT попадать.
- **FR-005** (#359): Должен оставаться рабочим административный сценарий просмотра и изменения публичных настроек, существующий в проекте (административная панель), — включая изменение настроек в рабочем контуре сервера, где развёрнута публичная часть сайта.
- **FR-006** (#359): Правка MUST NOT оставлять иных публично доступных путей записи в ту же таблицу настроек — в том числе через дублирующие или служебные эндпоинты, доступные с публичного периметра.
- **FR-007** (#359): Должен существовать автоматический регрессионный тест, который падает на текущем коде и проходит после правки: анонимный запрос на изменение настройки отклоняется и значение не меняется; легитимный административный сценарий изменения — работает.
- **FR-008** (#359): До развёртывания закрытия должна быть выполнена инвентаризация текущих значений публичных настроек (в первую очередь — секрета проверки капчи и ключей-переключателей) с фиксацией подозрительных значений; порядок дальнейших действий по найденным значениям определяет владелец (см. «Решения, требующие владельца»).

**Задача #362 (BR-518) — проверка капчи**

- **FR-009** (#362): При незаконной конфигурации проверки капчи (серверный ключ отсутствует или пуст) система MUST NOT считать проверку пройденной: регистрация MUST быть отклонена.
- **FR-010** (#362): Проверка MUST быть fail-closed: любая ошибка, таймаут или недоступность внешнего сервиса проверки MUST приводить к отказу в регистрации, а не к её разрешению.
- **FR-011** (#362): Серверный секрет проверки капчи MUST храниться вне таблицы, доступной для публичного изменения (конфигурация приложения либо отдельное хранилище, недоступное с публичного периметра — конкретный вариант определяет владелец, см. развилку 3); значение MUST NOT попадать в репозиторий, сборку, ответы и журналы.
- **FR-012** (#362): Публичный (клиентский) ключ проверки капчи MUST оставаться доступным публичной форме регистрации — закрытие публичных настроек не должно ломать показ капчи на сайте.
- **FR-013** (#362): Изменение конфигурации проверки MUST вступать в силу без многоминутного ожидания: система MUST NOT продолжать использовать устаревшее значение дольше согласованного окна (окно задаётся владельцем), в том числе после перезапуска сервиса.
- **FR-014** (#362): Администратор MUST иметь возможность узнать, настроена ли проверка капчи (в журнале/в диагностике сервиса), без публичного раскрытия самого секрета и без возможности раскрытия через публичный дайджест настроек.

**Связка двух задач**

- **FR-015** (связка): Ни один из двух сценариев обхода — «пустой ключ» и «подменённый ключ» — MUST NOT приводить к успешной регистрации без проверки: закрытие публичной записи и fail-closed-поведение проверки действуют совместно.
- **FR-016** (связка): Каждая из двух правок MUST поставляться так, чтобы её результат был проверяем отдельно: закрытие публичной записи проверяется попыткой анонимной записи, fail-closed-поведение проверки — попыткой регистрации при незаконной конфигурации. Починка только одной части цепочки MUST считаться незавершённой.
- **FR-017** (связка): Приведённые в разделе «Edge Cases» окна (кэш ключа проверки, гонка записи и кеша) MUST быть измеримы и не превышать согласованного владельцем значения; остаточное окно между исправлением и фактическим прекращением обхода MUST быть отражено в Success Criteria.
- **FR-018** (связка): Правка MUST NOT менять формат и семантику публичных ответов сайта, не относящихся к защищаемым путям (в частности, формат отказа регистрации и ответа конфигурации публичной формы MUST остаться прежними).
- **FR-019** (связка): Все отказы по защищаемым путям MUST возвращаться в едином формате ошибок, принятом в проекте для этого сервиса, и MUST NOT содержать текста ошибки базы данных, имён таблиц, значений настроек и секретов.
- **FR-020** (связка): Правка MUST NOT вносить значения секретов в репозиторий, конфигурационные файлы под контролем версий и журналы; новый секрет/переменная окружения задаётся при развёртывании вне репозитория.

### Key Entities

- **Публичная настройка**: пара «ключ — значение» в небольшой таблице настроек рабочей базы; часть ключей влияет на публичное поведение сайта (публикация новостей, шаблоны текстов, внешние ключи), часть является секретом (серверный ключ проверки капчи).
- **Серверный секрет проверки капчи**: симметричное значение, которым сервер подтверждает проверку у внешнего сервиса; в отличие от клиентского ключа, не предназначен для показа посетителю.
- **Проверка капчи**: действие сервера, подтверждающее, что регистрацию инициировал человек; имеет три исхода — пройдена, не пройдена, невозможна (внешний сервис недоступен).
- **Разрешение администратора на изменение настроек**: подтверждение, что запрос на изменение публичной настройки сделан из административного контура проекта (существующий административный сценарий либо отдельно согласованный порядок операционного доступа).
- **Журнал отказов**: записи о несостоявшихся попытках изменить настройку или зарегистрироваться без действующей проверки — с временем, источником и причиной, без содержимого запросов и секретов.

- **SC-002** (#359): 0 случаев выдачи серверного секрета проверки капчи анонимному клиенту (ни в полном, ни в частичном виде) за 7 суток наблюдения после развёртывания.
- **SC-003** (#359): Легитимный административный сценарий изменения публичных настроек (просмотр, изменение, чтение обратно) остаётся рабочим: 0 неуспешных операций, вызванных правкой, за 7 суток; доля успешных операций не ниже уровня до правки.
- **SC-004** (#362): При настроенной и работающей проверке — 0 регистраций, прошедших без действующей проверки, за 7 суток наблюдения; 100 % таких попыток отклонены с внятным кодом отказа.
- **SC-005** (#362): При незаконной конфигурации проверки (серверный ключ отсутствует/пуст) — 0 регистраций, прошедших без проверки, за 7 суток наблюдения; 100 % отказов видны в журнале в течение 60 секунд с момента попытки.
- **SC-006** (#362): Остаточное окно между исправлением и фактическим прекращением обхода (с учётом кеша ключа) — не более 5 минут; измеряется по времени от развёртывания до момента, когда ранее записанное значение перестаёт использоваться, и подтверждается отказом на пробную регистрацию.
- **SC-007** (#362): 100 % отказов регистрации из-за недоступности внешнего сервиса проверки видны в журнале в течение 60 секунд; 0 случаев, когда внешний сервис недоступен, а регистрация прошла.
- **SC-008** (связка): 100 % отклонённых попыток анонимного доступа к настройкам и отказов регистрации видны в журнале в течение 60 секунд; 0 ответов клиенту, содержащих текст ошибки базы данных, имена таблиц или значения настроек.
- **SC-009** (связка): Автоматические регрессионные тесты закрывают оба независимых сценария (анонимная запись — отказ; регистрация при незаконной конфигурации — отказ) и падают на коде до правки; легитимный административный сценарий тестами покрыт и проходит после правки.
- **SC-010** (связка): Проверки проекта проходят полностью (линтеры, guard-ы, сборка) — 7 из 7.
- **SC-011** (связка): Публичная форма регистрации на сайте работает: успешных регистраций с действующей проверкой — не ниже уровня до правки, 0 новых отказов сайта, вызванных закрытием настроек, за 7 суток.

## Assumptions

- **Аутентификации в `karaoke-web` для этого пути нет.** Проверка авторизации в этом сервисе делается перехватчиком (Bearer-токен пользователя сайта → 401 без токена), а не сессией админки; поэтому «административное разрешение» для изменения настроек — это либо существующий административный контур проекта (админская машина), либо отдельно согласованный порядок операционного доступа. Какая из двух схем выбирается — решение владельца (см. развилку 2).
- **Легитимный административный путь изменения настроек в рабочем контуре сервера уже существует и не проходит через публичный префикс** (административная панель → служебный сервис с выбором локальной/удалённой базы). Это означает: закрытие публичного эндпоинта не отнимает у администратора способность управлять настройками — при условии, что операционный порядок (аварийное включение переключателя с сервера) будет переопределён владельцем.
- **Операционный регламент «включить переключатель одной командой с сервера» существует и используется в аварийных сценариях** (окно синхронизации данных). Его нельзя просто отменить без замены — иначе в аварии не будет быстрого способа остановить нежелательную публикацию. Порядок замены — решение владельца (развилка 5).
- **Клиентский ключ проверки капчи публичен по устройству сайта** (виджет на публичной форме) и отдельного внимания не требует; серверный ключ — единственный секрет в рассматриваемой таблице.
- **Внешний сервис проверки капчи доступен через отдельный прокси-маршрут на сервере**, и его недоступность — реальный (хоть и редкий) сценарий, который сегодня приводит к отказу в регистрации; правка не должна превращать его в тихий пропуск.
- **Таблица настроек остаётся в рабочей базе и продолжает использоваться** для несекретных настроек (переключатели, шаблоны текстов) — задача не про удаление таблицы, а про разделение доступа.
- **Два независимых кеша (60 секунд и 5 минут) — разные механизмы с разными правилами инвалидации**; сведение их к одному не является частью задачи, но отсутствие связи между ними — известное свойство, на которое опирается оценка остаточного окна (SC-006).
- **Публичный API сайта в части регистрации не меняется**: формат отказа и формат ответа конфигурации формы остаются прежними, меняется только то, при каких условиях регистрация разрешается.
- **Развёртывание на боевой контур — отдельное решение владельца**; до него правка проверяется в тестовом окружении, где доступны те же сценарии (пустой ключ, недоступный внешний сервис, анонимный запрос).

## Решения, требующие владельца

1. **Развилка 1 — что именно закрывать в публичном префиксе настроек.**
   - Вариант (a): закрыть **только запись** (изменение значений), чтение оставить, но исключить секретные ключи из выдачи (белый список публичных ключей).
   - Вариант (b): закрыть **весь префикс** для анонимных клиентов (и запись, и чтение, и дайджест) — проще и безопаснее, но операционный доступ к настройкам с сервера (регламент аварийного переключения) перестаёт работать без замены.
   - Вариант (c): оставить чтение по белому списку публичных ключей, запись закрыть полностью.
   - Требует решения владельца: какой вариант утверждён. **Рекомендация агента: (a) или (c)** — чтение несекретных настроек само по себе не создаёт эксплуатируемого обхода, а полное закрытие ломает операционный регламент; секрет при этом исключается из выдачи в любом случае (FR-002).
2. **Развилка 2 — чем подтверждается разрешение на запись.**
   - Вариант (a): **общий секрет в заголовке** по образцу уже работающего защищённого канала в этом же сервисе + сетевой фильтр по адресу админской машины на уровне прокси (образец принят в спеке 554 / #357). Плюс: не зависит от наличия пользователей-администраторов. Минус: появляется ещё один секрет в конфигурации; нужен регламент выдачи/ротации.
   - Вариант (b): **разрешение пользователя сайта** (перехватчик существующей авторизации + проверка административной роли) по образцу защищённых административных эндпоинтов этого сервиса. Плюс: без нового секрета. Минус: административная панель проекта не работает через этот сервис и без своей авторизации — потребуется отдельный сценарий входа.
   - Вариант (c): **запись только через существующий административный контур** (админская машина → служебный сервис с выбором удалённой базы), публичная запись удаляется целиком. Плюс: минимум новых механизмов. Минус: операционный регламент с сервера нужно заменить.
3. **Развилка 3 — где должен жить серверный ключ проверки капчи, если он больше не в публично изменяемой таблице.**
   - Вариант (a): **переменная окружения** сервиса (читается при старте) — соответствует правилам проекта о секретах (только окружение, дефолт невалидный) и убирает кэш-окно в 5 минут. Плюс: конфигурация проверяется при старте. Минус: ротация ключа требует перезапуска сервиса.
   - Вариант (b): **отдельное хранилище секретов, недоступное публичному периметру** (например, отдельная таблица без публичного доступа или файл только на сервере). Плюс: ротация без перезапуска. Минус: новая сущность и новая точка отказа.
   - Вариант (c): **оставить ключ в текущей таблице**, закрыв публичную запись и исключив ключ из выдачи. Плюс: минимум изменений. Минус: **не закрывает BR-518 полностью** — «пустой ключ» из-за ошибки конфигурации, отката или ручной правки по-прежнему приводит к пропуску проверки (если не закрывать fail-open отдельной правкой).
   - **Требует решения владельца; вариант (c) допустим только вместе с полноценной правкой fail-closed (FR-009).**
4. **Развилка 4 — что делать с уже существующими записями в таблице настроек (в т.ч. возможно оставленными анонимным клиентом).**
   - Вариант (a): **полная инвентаризация и чистка**: снимок текущих значений, проверка ключа проверки капчи и переключателей, удаление неопознанных ключей, добавленных анонимно, с отчётом владельцу.
   - Вариант (b): **точечная проверка** только критичных ключей (секрет проверки капчи, переключатели), остальное — как есть.
   - Вариант (c): **без действий**, полагаясь на то, что после закрытия записи новые подмены невозможны.
   - Требует решения владельца; порядок (сначала инвентаризация, потом закрытие записи) и то, считается ли обнаруженное отравленное значение инцидентом безопасности с отдельной ротацией ключа.
5. **Развилка 5 — судьба операционного регламента «включить/снять переключатель одной командой с сервера».**
   - Вариант (a): перенести регламент на административный контур (панель) и обновить документацию (quickstart) под него.
   - Вариант (b): сохранить отдельный защищённый операционный путь (по развилке 2) с отдельным описанием и отдельным секретом.
   - Вариант (c): оставить как есть и не закрывать запись — **несовместимо с FR-001**, приводится для полноты списка.
6. **Развилка 6 — как именно вести себя при незаконной конфигурации проверки капчи (FR-009).**
   - Вариант (a): **регистрация отклоняется** с отдельным внятным кодом отказа (например, «проверка не настроена»), сайт показывает посетителю сообщение о временной недоступности регистрации.
   - Вариант (b): **регистрация явно отключается флагом** (эндпоинт регистрации недоступен целиком, включая легитимных посетителей) — как прямо предлагает карточка находки; внятнее для посетителя, но требует отдельного переключателя и процедуры включения.
   - Требует решения владельца: какой код отказа и какое сообщение видит посетитель.

## Out of Scope

- Остальные публичные дефекты аудита #336 волны A (BR-011 решён в #357; BR-018, BR-123 и прочие — отдельные задачи).
- Прочие потребители таблицы настроек (шаблоны новостей, переключатели публикации) — их регламент доступа не меняется, кроме общего правила «публичная запись закрыта» из FR-001.
- Дефект соседней правки в том же контроллере: закрытие переиспользуемого соединения с базой при записи настройки (избыточные переподключения к базе) — отдельная задача, не связанная с безопасностью.
- Удаление таблицы настроек, перенос остальных её ключей в конфигурацию, изменение модели «ключ — значение».
- Изменение внешнего сервиса проверки капчи, его прокси-маршрута и таймаутов.
- Усиление защиты самого публичного сайта от автоматической регистрации (лимиты, поведение при большом числе аккаунтов) — отдельный вопрос, не входящий в разрыв этой цепочки.
- Разбор уже накопленного ущерба (существующие аккаунты, созданные без проверки) — отдельная процедура, если владелец её сочтёт нужной.
- Правки в других модулях (административная панель, публичный сайт), кроме необходимых для соблюдения FR-005 и FR-012.
