# Research: Единообразная обработка сбоев БД в главном цикле очереди

**Feature**: [spec.md](./spec.md) | **Plan**: [plan.md](./plan.md)

Technical Context не содержит открытых `NEEDS CLARIFICATION` — стек и
архитектура зафиксированы существующим кодом. Задача Phase 0 — выбор
конкретного, наименее рискованного механизма устранения несогласованности,
найденной живьём при верификации specs/087-fix-shared-db-connection.

## Кандидат A — параметр `throwOnError: Boolean = false` в обеих функциях (выбран)

**Находка**: у `getCountWaiting()`/`getProcessesToStart()` (`KaraokeProcess.kt:479-506`,
`:750-814`) ровно **6** вызывающих мест во всём проекте:

| Вызывающее место | Контекст | Внутри `doStart()`? |
|---|---|---|
| `KaraokeProcessWorker.kt:955` (через приватный `getKaraokeProcessesToStart()`, строка 648) | главный цикл `doStart()` | ДА |
| `KaraokeProcessWorker.kt:979` | главный цикл `doStart()` | ДА |
| `KaraokeProcessWorker.kt:1028` | главный цикл `doStart()` | ДА |
| `KaraokeProcess.kt:744` | `createDbInstance()` — уведомление сразу после вставки новой строки задания (вызывается из HTTP-пути создания задания) | НЕТ |
| `KaraokeProcessWorker.kt:204` | `KaraokeProcessThread.run()` — уведомление в начале выполнения ОТДЕЛЬНОГО job-потока (не главный цикл) | НЕТ |
| `KaraokeProcessWorker.kt:1090` | `forceStop()` — уведомление в конце принудительной остановки (HTTP-путь) | НЕТ |
| `KaraokeProcessWorker.kt:536` | `start()` — уведомление сразу при старте очереди, **до** `Thread { ... }` (синхронно на HTTP-потоке `/api/processes/workerstartstop`) | НЕТ (найдено при сверке T004 — не было учтено в первом проходе планирования) |
| `RenderQueueStalledCheck.kt:18`, `LaneStalledCheck.kt:42` | проверки мониторинга, вызываются `MonitoringService.tick()` | НЕТ (уже отдельно защищены, см. ниже) |

Ровно 3 места нуждаются в «громком» поведении (все — внутри `doStart()`),
остальные 6 (включая 2 проверки мониторинга) должны продолжать работать как
сегодня.

**Decision**: добавить обеим функциям необязательный параметр
`throwOnError: Boolean = false`:
- `connection == null` → при `throwOnError=true` бросить
  `SQLException("Невозможно установить соединение с базой данных ${database.name}")`
  вместо `return 0L`/`return emptyMap()`.
- `catch (e: SQLException)` вокруг запроса → при `throwOnError=true`
  пробросить `e` дальше (`throw e`) вместо `e.printStackTrace()` и
  возврата накопленного (нулевого/пустого) результата.
- `finally`-блок закрытия `Statement`/`ResultSet` не меняется — их
  собственный `catch (e: SQLException) { e.printStackTrace() }`
  сохраняется независимо от `throwOnError` (закрытие ресурсов не должно
  маскировать/подменять основную ошибку, но и не обязано быть «громким» —
  это технические детали освобождения ресурсов, не бизнес-сбой).

Переиспользуется `java.sql.SQLException` (не заводится новый тип) — это
именно тот тип, который уже пробрасывает `.save()`, и именно его уже ловит
`catch (e: Exception)` в retry-обёртке `KaraokeProcessWorker.start()`
(specs/087) — новых правок в retry-механизме не требуется, он подхватывает
новый источник ошибок автоматически.

На стороне `KaraokeProcessWorker.kt` — 3 правки: `getKaraokeProcessesToStart()`
(строка 648, приватный wrapper) и оба прямых вызова `getCountWaiting()`
(строки 979, 1028) передают `throwOnError = true`. Остальные 4 существующих
вызывающих места (`KaraokeProcess.kt:744`, `KaraokeProcessWorker.kt:204`,
`:536`, `:1090`) не трогаются вовсе — ни единой строки — сохраняя дефолт
`false` и побайтово прежнее поведение (FR-004/FR-005). `:536` — то же
рассуждение, что и для `:1090`: синхронный HTTP-путь (нажатие кнопки
старта очереди), не главный цикл.

**Мониторинг не требует правок**: `RenderQueueStalledCheck`/`LaneStalledCheck`
и так уже используют дефолтный (нетребующий) режим — их поведение при сбое
БД не меняется этой фичей. Отдельно отмечено для полноты: даже если бы они
были переведены на `throwOnError=true`, это было бы БЕЗОПАСНО, поскольку
`MonitoringService.tick()` уже оборачивает вызов `check.run()` в
`try { ... } catch (e: Exception) { listOf(checkFailureAlert(check, e)) }`
(`MonitoringService.kt:46-47`) — но раз в этом нет необходимости для
выполнения FR-001-003 (обе проверки и так не участвуют в главном цикле
очереди), трогать их не нужно, чтобы минимизировать blast radius.

**Alternatives considered**:
- **Убрать внутренний `catch` совсем (всегда пробрасывать)** — отклонено:
  напрямую нарушило бы FR-004/FR-005 (сломало бы 3 незащищённых
  вызывающих места без отдельных правок в каждом из них) — пришлось бы
  добавлять try/catch на каждое из 3 мест, что больше правок и больше
  blast radius, чем один параметр с дефолтом.
- **Отдельные throwing-варианты функций** (например,
  `getCountWaitingOrThrow()`) вместо параметра — отклонено как
  избыточное дублирование кода (SQL-запрос и разбор `ResultSet`
  продублировались бы в двух функциях на каждую); параметр с дефолтом
  достигает того же результата без дублирования тела функции.
- **Не трогать `getCountWaiting`/`getProcessesToStart`, а обернуть места
  их вызова внутри `doStart()` во внешний try/catch, который сам
  детектирует «подозрительно нулевой результат» и искусственно кидает
  исключение** — отклонено: не отличает «БД реально недоступна» от
  «легитимно 0 заданий ожидает» (пустая очередь — нормальное, частое
  состояние), дало бы ложные срабатывания retry на пустой очереди.

## Итоговый подход

1. `KaraokeProcess.getCountWaiting()`/`getProcessesToStart()`: добавить
   `throwOnError: Boolean = false` (Кандидат A) — покрывает FR-001/FR-002/FR-003
   при `throwOnError=true`, полностью сохраняет сегодняшнее поведение при
   значении по умолчанию.
2. `KaraokeProcessWorker.kt`: 3 вызова внутри `doStart()` переводятся на
   `throwOnError = true`; 3 других существующих вызывающих места и оба
   мониторинг-чека не трогаются — покрывает FR-004/FR-005.

Один пункт — точечная правка в рамках уже существующих файлов/паттернов,
без новых зависимостей, без миграций схемы БД, без изменений фронтенда/
HTTP-контракта.
