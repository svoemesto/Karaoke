# Quickstart: проверка выбора похожей версии с аудиоданными

**Feature**: `129-copy-family-audio`
**Контракт**: [contracts/select-family-song.md](./contracts/select-family-song.md)
**Модель**: [data-model.md](./data-model.md)

## Предварительные условия

- Локальное admin-окружение Karaoke уже запущено пользователем: `karaoke-app`, локальная PostgreSQL и админская SPA доступны.
- Есть две тестовые песни с существующими аудиофайлами: текущая и кандидат.
- Тест выполняется только на локальной БД/стенде; production ID и production URL не использовать.
- Установлены JDK 17, Gradle wrapper, Node/npm и зависимости `webvue3`.
- В shell заданы только локальные переменные окружения, без вывода секретов:

```bash
export ADMIN_BASE_URL="http://<локальный-хост-и-порт>"
export CURRENT_ID="<числовой-id-текущей-песни>"
export CANDIDATE_A_ID="<числовой-id-кандидата-a>"
export CANDIDATE_B_ID="<числовой-id-кандидата-b>"
```

## Статические проверки

Из корня репозитория:

```bash
./gradlew :karaoke-app:compileKotlin
./gradlew ktlintCheck
(cd webvue3 && npm run lint:check && npm run format:check && npm run build)
```

Ожидаемый результат: все команды завершаются с кодом 0; новые ошибки форматирования, ESLint и компиляции отсутствуют.

## Основной UI-сценарий: успешная сверка

1. Открыть таблицу «Песни», открыть `SongEdit` для `CURRENT_ID`.
2. Запомнить исходные значения трёх аудиополей и открыть «Похожие версии песни».
3. Нажать «Сверить» у `CANDIDATE_A` и записать показанные процент и signed-сдвиг.
4. Нажать на строку кандидата.
5. Проверить без повторного открытия редактора:
   - «Аудио-родитель» равен `CANDIDATE_A_ID`;
   - «Аудио-схожесть» равна проценту из результата сверки, включая 0;
   - «Аудио-сдвиг» равен signed-сдвигу в миллисекундах, включая отрицательный знак;
   - текст и маркеры по-прежнему скопированы, а существующие `rootId`/status-правила не изменились.
6. Закрыть и снова открыть редактор той же песни.

Ожидаемый результат: три поля сохраняют те же значения после повторного открытия, а повторный клик не создаёт лишнего изменения или ошибки.

## Замена кандидата и защита от устаревших метрик

1. Вновь открыть «Похожие версии песни» для `CURRENT_ID`.
2. Выполнить сверку `CANDIDATE_B` и выбрать его строку.
3. Сравнить все три поля с результатом сверки B.

Ожидаемый результат: ID, процент и сдвиг одновременно относятся к B; ни одно значение A не осталось. В таблице песен `A-root` после SSE/обновления также отображает новый ID.

## Выбор без сверки

1. Подготовить текущую песню с ненулевыми аудиоданными A.
2. Открыть «Похожие версии песни» и выбрать `CANDIDATE_B`, не нажимая «Сверить».
3. Проверить редактор и повторно открыть песню.

Ожидаемый результат: `audioParentId = CANDIDATE_B_ID`, `audioSimilarityPercent = 0`, `audioDeltaMs = 0`; старые метрики A не сохраняются; текст и маркеры копируются по прежнему правилу.

## Нулевые и отрицательные результаты

- Для тестовой пары, у которой backend сверки возвращает `0%` и `0 мс` с `ok=true`, выбрать строку и проверить, что оба нуля переданы и сохранены как результат `done`, а не обработаны как отсутствие сверки.
- Для пары с отрицательным результатом, например `-250 мс`, выбрать строку и убедиться, что в поле сохраняется `-250`, а не `250`.

Если в локальном наборе нет подходящих аудиопар, сценарий выполняется на тестовых записях/фикстурах, подготовленных пользователем локально; не подменять результат на production-данных.

## Ошибки и недопустимые действия

1. Нажать строку текущей песни в модалке.
   - Ожидается: выбор недоступен, три аудиополя не изменяются.
2. Отправить запрос с одной метрикой вместо пары, используя числовые локальные ID:

```bash
curl -sS -X POST "$ADMIN_BASE_URL/api/song/selectfamilysong" \
  --data-urlencode "id=$CURRENT_ID" \
  --data-urlencode "idAnother=$CANDIDATE_A_ID" \
  --data-urlencode "deltaMs=-250"
```

   - Ожидается: non-2xx/ошибка валидации, в БД нет нового частичного набора.
3. Имитировать недоступность endpoint или сетевой отказ во время выбора.
   - Ожидается: модалка остаётся открытой, появляется toast, текущие поля не получают частичные значения, повторный выбор возможен.

## Прямая проверка HTTP-контракта

Сначала получить результат сверки:

```bash
curl -sS -X POST "$ADMIN_BASE_URL/api/song/comparewaveform" \
  --data-urlencode "id=$CURRENT_ID" \
  --data-urlencode "idAnother=$CANDIDATE_A_ID"
```

Если ответ содержит `"ok": true`, взять из него `similarityPercent` и `deltaMs`, затем выполнить выбор:

```bash
export COMPARE_PERCENT="<similarityPercent-из-ответа>"
export COMPARE_DELTA_MS="<deltaMs-из-ответа>"

curl -sS -X POST "$ADMIN_BASE_URL/api/song/selectfamilysong" \
  --data-urlencode "id=$CURRENT_ID" \
  --data-urlencode "idAnother=$CANDIDATE_A_ID" \
  --data-urlencode "audioSimilarityPercent=$COMPARE_PERCENT" \
  --data-urlencode "deltaMs=$COMPARE_DELTA_MS"
```

Ожидаемый JSON содержит `rootId`, `idStatus`, `audioParentId`, `audioSimilarityPercent`, `audioDeltaMs`; последние три совпадают с выбранным кандидатом и результатом сверки.

Для выбора без сверки выполнить тот же запрос, опустив оба параметра метрик. Ожидаемый ответ содержит ID кандидата и `0/0`.

## Проверка персистентности в локальной БД

После успешного HTTP/UI выбора выполнить запрос к локальной БД с числовым `CURRENT_ID`:

```bash
psql "$LOCAL_DATABASE_URL" -Atc \
  "SELECT audio_parent_id, audio_similarity_percent, audio_delta_ms FROM tbl_songs WHERE id = $CURRENT_ID;"
```

Ожидаемый результат: одна строка с теми же тремя значениями, что показаны в редакторе и возвращены endpoint. `LOCAL_DATABASE_URL` должен указывать только на локальную БД и не выводиться в логи.

## Критерии завершения проверки

- Успешная сверка сохраняет ID, процент и signed-сдвиг одной операцией.
- Выбор без сверки очищает старые метрики в `0/0`.
- Валидные нулевые и отрицательные результаты не теряются.
- Self-selection и частичный запрос отклоняются без частичного сохранения.
- Текст, маркеры, root/status и публичный frontend не получили регрессий.
- Статические проверки завершаются успешно.
