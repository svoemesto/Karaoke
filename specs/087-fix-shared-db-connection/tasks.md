## Phase 3: User Story 1 - Параллельная работа очереди и админки не роняет друг друга при кратковременном сбое сети до БД (Priority: P1) 🎯 MVP

**Goal**: Каждый поток выполнения (HTTP-поток Tomcat, поток очереди заданий) получает и переиспользует собственное физическое соединение с БД вместо одного общего на всё приложение — кратковременный сетевой сбой перестаёт «протекать» между несвязанными параллельными операциями.

**Independent Test**: Сценарии 1 и 3 из `specs/087-fix-shared-db-connection/quickstart.md` — приостановить `karaoke-db` (`docker pause`) на дольше `socketTimeout=30`, убедиться, что после `docker unpause` новые запросы из других потоков отрабатывают штатно без «Соединение уже было закрыто»; убедиться, что число соединений с БД не растёт неограниченно при большом количестве последовательных запросов.

## Phase 4: User Story 2 - Очередь заданий сама возобновляет работу после сбоя, не дожидаясь ручного вмешательства оператора (Priority: P2)

**Goal**: Если главный цикл очереди (`KaraokeProcessWorker.doStart()`) аварийно завершается непредвиденной ошибкой — очередь автоматически пытается возобновить работу ограниченное число раз с нарастающей паузой, прежде чем перейти в уже существующий режим «остановлено, ждёт ручного клика по алерту `RenderQueueStalledCheck`».

**Independent Test**: Сценарий 2 из `specs/087-fix-shared-db-connection/quickstart.md` — вызвать аварийное завершение главного цикла (например, длительной приостановкой `karaoke-db`), убедиться, что очередь возобновляется сама в течение ~1-2 минут без клика оператора при кратковременном сбое; при сбое длиннее суммарного окна retry — убедиться, что очередь корректно останавливается (не уходит в бесконечный быстрый цикл падений) и существующий алерт/ручное восстановление по-прежнему работают.

### Implementation for User Story 2

- [X] T009 [US2] Обернуть `Thread { try { doStart(...) } catch (e: Exception) {...} finally {...} }` в `KaraokeProcessWorker.start()` (`karaoke-app/src/main/kotlin/com/svoemesto/karaokeapp/KaraokeProcessWorker.kt`, строки 520-541) в ограниченный цикл повторных попыток с нарастающей паузой (например: до 5 попыток, пауза 2с → 5с → 15с → 30с → 60с между ними) — при падении `doStart()` и неисчерпанных попытках: подождать паузу и вызвать `doStart()` заново внутри того же демон-потока (не создавая новый `Thread`), не сбрасывая `isWork` между попытками. Только после исчерпания всех попыток — выполнить существующий `finally` (`isWork=false`, `stopAfterThreadIsDone=false`, `sendStateMessage()`), чтобы `RenderQueueStalledCheck` подхватил как и раньше (FR-006, отказоустойчивый резерв не убирается). Реализовано как `MAX_START_ATTEMPTS=5`/`START_RETRY_BACKOFF_MS` (2с→5с→15с→30с→60с) + внутренний `while(true)`-цикл ретраев внутри внешнего `try/finally` (важно: `Thread.sleep()` между попытками сам может бросить `InterruptedException` — без внешнего `try/finally` вокруг всего ретрай-цикла это исключение ушло бы мимо блока очистки, оставив `isWork=true` навсегда; добавлен). Проверка `!isWork` перед каждой повторной попыткой — если оператор вызвал `forceStop()` во время паузы, ретраи не продолжаются. `BUILD SUCCESSFUL`.
- [X] T010 [US2] Ручная проверка: Сценарий 2 из `specs/087-fix-shared-db-connection/quickstart.md` на dev-pc — кратковременный сбой (короче суммарного окна retry) → очередь возобновляется сама без клика оператора, видны логи повторных попыток с увеличивающейся паузой; длительный сбой (дольше суммарного окна) → корректная остановка (`isWork=false`) и работающий алерт/ручное восстановление через `RenderQueueStalledCheck`.

  Запущен воркер на реальной очереди (3099 `WAITING`) и дважды воспроизведён `docker pause karaoke-db` на 35-40с: оба раза в логе — **та же самая ошибка, что и в исходном инциденте с admin-машины** (`SocketTimeoutException: Read timed out` из `KaraokeProcess.save()`), поймана retry-враппером, залогирована `попытка N/5`, выдержана нарастающая пауза (2с, затем 5с), `doStart()` перезапущен в том же потоке и очередь автоматически возобновила обработку заданий за секунды — без клика оператора, `isWork` не сбрасывался. Отдельные потоки уже выполнявшихся заданий (`Thread-27`/`Thread-26`) во время сбоя падали каждый сам по себе, не утаскивая за собой главный цикл — подтверждает изоляцию по потокам (US1) вживую на реальном сценарии.

  Третий прогон (пауза на 4.5 минуты, цель — исчерпать все 5 попыток) вскрыл важный нюанс: `KaraokeProcess.getCountWaiting()`/`getProcessesToStart()` (`KaraokeProcess.kt:490-498`, `:779` и рядом) содержат **собственный** `catch (e: SQLException) { e.printStackTrace() }`, который проглатывает ошибку и не пробрасывает её выше — в отличие от `.save()`, у которого такого перехвата нет (см. оригинальный лог инцидента). В этом конкретном окне сбоя `doStart()` ни разу не упал (`isWork` оставался `true` все 4.5 минуты), просто тихо получал пустые/нулевые результаты от этих двух вызовов, поэтому ветка «попытки исчерпаны → `isWork=false`» в этом прогоне вживую не сработала — не потому что сломана (логика проверена код-ревью: `attempt >= MAX_START_ATTEMPTS` → `break` → `finally` безусловно выставляет `isWork=false`, идентично уже проверенному safety-net из specs/029), а потому что конкретно эти два DB-вызова в `doStart()` защищены отдельным, более старым перехватом ошибок, который эта фича не трогала (вне scope FR-005/FR-006 — они про аварийное завершение `doStart()`, а не про то, что часть вызовов внутри него по своей собственной, более ранней логике не бросает исключение наружу вовсе). Это существующее (не внесённое этой фичей) несовпадение в обработке ошибок между разными DB-вызовами внутри одного цикла — потенциальный кандидат для отдельного follow-up, не для этой спеки. После проверки БД разблокирована, воркер остановлен, состояние стенда возвращено к исходному (`isWork=false`).

**Checkpoint**: User Story 1 и 2 работают одновременно и независимо друг от друга.
