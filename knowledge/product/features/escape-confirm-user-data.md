# Feature: Экранирование пользовательских данных в подтверждениях админки

**Spec**: [`specs/558-escape-song-name-confirm/spec.md`](../../../specs/558-escape-song-name-confirm/spec.md)

**Created**: 2026-10-24
**Last updated**: 2026-10-24
**Source**: OpenProject #360 — «S1: 25 обработчиков подтверждения собирают `customConfirmParams.body` интерполяцией имени песни (BR-123)»
**Feature Key**: `escape-confirm-user-data`

## Что делает

Два рубежа на пути пользовательских данных к экрану администратора:

1. **Экранирование при сборке текста подтверждения.** В 43 местах сборки
   `customConfirmParams` (8 семейств значений: имя песни — 25 в `SongEdit.vue`,
   имя автора — 5 в `HomeView.vue`, слово и словарь — 4 в `HomeView.vue`,
   e-mail пользователя сайта — 3 в `SiteUserEdit.vue`, выделенный текст песни — 2
   в `SubsEdit.vue`, параметры Smart Copy — 2 в `SmartCopyModal.vue`,
   имя картинки — 1 в `PictureEdit.vue`, отчёт двуx-БД синхронизации — 1
   в `SyncTable.vue`) значение оборачивается в `escapeHtml(...)` **в момент входа
   в HTML-буфер**.
2. **Текстовый режим по умолчанию в общем компоненте.** `CustomConfirm.vue` выводит
   `header`/`body` через `v-text` (`textContent`). Сырая разметка принимается
   только при явном `params.allowHtml === true`.

Плюс автоматическая проверка `tools/check-confirm-escape.py` (в pre-commit и CI),
которая находит места сборки текста подтверждения из пользовательских данных и
падает на них.

## Зачем

Аудит кода #336 (дефект **BR-123**, severity **S1**): пользовательские данные
(имя песни, имя автора, e-mail публично зарегистрированного пользователя сайта,
имя картинки, выделенный фрагмент текста песни, текст ошибки синхронизации,
параметры Smart Copy) попадали в HTML через `v-html` в общем компоненте
подтверждения `webvue3/src/components/Common/CustomConfirm.vue`. Администратор
открывал подтверждение — и разметка из имени песни (например `<img src=x
onerror=…>`) выполнялась как код в его сессии: в origin админки, откуда доступны
все административные действия без дополнительного подтверждения.

Самый опасный источник — e-mail: он задаётся публичным посетителем сайта при
регистрации (никаких прав в системе не нужно), а администратор увидит его
в карточке пользователя при бане, разбане или удалении.

Правило линтера `vue/no-v-html` в проекте выключено, поэтому «только правка мест
вызова» оставляла ловушку для новых вызовов. Отсюда гибрид: экранирование на
входе **и** текстовый режим по умолчанию — новое подтверждение без явного
`allowHtml: true` не может выполнить чужой код в принципе.

## Как работает

### Общий компонент — `webvue3/src/components/Common/CustomConfirm.vue`

```html
<div :style="styleHeader" v-if="params.allowHtml" v-html="params.header" />
<div :style="styleHeader" v-else v-text="params.header" />
<div :style="styleBody" v-if="params.allowHtml" v-html="params.body" />
<div :style="styleBody" v-else v-text="params.body" />
```

`v-text` пишет через `textContent` — разметка в значении не создаёт элементов и
не выполняет сценариев. Структура DOM и стили (`styleHeader`/`styleBody`) не
меняются, поэтому оформление подтверждения сохраняется.

### Сборка текста — экранирование на входе

```js
this.customConfirmParams = {
  allowHtml: true,
  header: 'Подтвердите удаление песни',
  body: `Удалить песню <strong>«${escapeHtml(this.song.songName)}»</strong>?`,
  timeout: 10,
  callback: this.doDeleteSong,
}
```

Экранирование применяется **точно один раз** и только к пользовательскому
значению — статичная разметка (`<strong>`, `<br>`, `<hr>`) остаётся разметкой.
Это правило проекта: «экранирование на входе, а не на выходе»
(`knowledge/domains/integration/components/song-public-dto.md`, прецедент спеки
#215). Экранировать готовую HTML-строку целиком нельзя — сломается оформление.

### Флаг `allowHtml`

Инвариант: **`allowHtml: true` объявлен тогда и только тогда, когда в `header`
или `body` есть статичная разметка.** Блоки с чистым текстом остаются в
текстовом режиме — им флаг не нужен, а текстовый режим безопаснее.

### Модуль экранирования

`webvue3/src/utils/escapeHtml.js` — каноническая реализация
(`& < > " '`). `webvue3/src/utils/highlightWords.js` реэкспортирует её, поэтому
существующие импорты (`SubsEdit.vue`, `highlightWords.test.js`) не сломались.

### Проверка

`tools/check-confirm-escape.py` проверяет три инварианта:

| Правило | Что проверяет |
| --- | --- |
| **R1** | общий компонент не принимает сырую разметку по умолчанию |
| **R2** | `allowHtml: true` ⇔ в `header`/`body` есть статичная разметка |
| **R3** | в блоке с разметкой каждое пользовательское значение обёрнуто в `escapeHtml(...)` |

Выражения, которые пользовательскими данными не являются (счётчики,
идентификаторы, значения из закрытых перечислений), перечислены явно в
`config/frontend/confirm-safe-expressions.txt` — с причиной по каждой строке.
Всё, чего в списке нет, считается пользовательскими данными.

Проверка подключена в `.pre-commit-config.yaml` (хук `confirm-escape-guard`) и
в `.github/workflows/lint.yml` (job `confirm-escape-guard`). Собственный
«до/после»-тест guard'а — `tools/check-confirm-escape-fixtures.sh`: на уязвимом
снимке кода guard обязан упасть, на исправленном — пройти.

### Регресс-контроль (прецедент спеки #215)

`webvue3/src/utils/__tests__/escapeHtml.test.js` (запуск: `npm run test:unit`
в `webvue3`):

- для значения **без спецсимволов** результат экранирования побайтово совпадает
  с исходным значением (baseline совпадает);
- значение с `&` даёт ровно одну `&amp;` — двойного экранирования (`&amp;amp;`)
  нет;
- `null`/`undefined` дают пустую строку, а не «undefined» на экране.

## Инварианты

- **Экранирование ровно один раз.** Компонент подтверждения НЕ экранирует
  значение на выходе. Если экранирование окажется и в сборке, и в компоненте —
  на экране появится `&amp;` вместо `&`.
- **Экранирование только в HTML-режиме.** В текстовом режиме значение
  экранировать НЕЛЬЗЯ: `v-text` показывает строку как есть, и `&amp;` будет
  виден буквально.
- **Пользовательские данные не меняются.** Правка носит характер отображения:
  имя песни, e-mail, имя картинки, имя автора, словарь и прочие значения
  остаются в базе ровно теми же.
- **Формат подтверждения не меняется.** Заголовки, кнопки, таймауты и действия
  по кнопке подтверждения прежние; оформление (жирное начертание значения,
  переносы строк, цветные рамки заголовка) сохраняется.
- **Публичный периметр не затронут.** `karaoke-public` использует `v-html`
  только к серверно-экранированным полям `formattedText*`; в Thymeleaf-шаблонах
  нет ни одного `th:utext`.

## Известные ловушки

- **«Всё под `v-html` — значит, всё безопасно».** Неверно: `v-html` на
  пользовательском значении = выполнение чужого кода в сессии админа. Раньше
  компонент утверждал в комментарии, что «message должен быть подготовленным,
  не пользовательским вводом» — это было фактически неверно.
- **Экранировать готовую HTML-строку.** Не работает: съедает `<strong>`/`<br>`.
  Экранировать нужно значение ДО входа в HTML-буфер.
- **Экранировать в текстовом режиме.** Тоже не работает: показывает `&amp;`
  буквально. В текстовом режиме экранирование не применяется.
- **Забыть `allowHtml: true`.** Оформление подтверждения пропадёт (тег будет
  показан как текст). Ловится проверкой R2.
- **Лишний `allowHtml: true`.** Расширяет доверенную поверхность без нужды.
  Тоже ловится проверкой R2.
- **Правило `vue/no-v-html` выключено** и остаётся выключенным (отдельная
  задача: 14 мест в проекте, часть требует перехода на санитайзер). Защиту
  обеспечивает `tools/check-confirm-escape.py`, а не линтер.
- **Значение, спрятанное в промежуточной переменной** (`scope` в `HomeView.vue`,
  `body` в `SmartCopyModal.vue`, `lines` в `SyncTable.vue`), — экранируется
  там, где оно **входит** в HTML-буфер, а не там, где объявлено.
- **Двойное экранирование.** Если значение экранировано при сборке и потом
  ещё раз на выходе — на экране будет `&amp;` вместо `&`. Компонент на выходе
  не экранирует ничего.
