# Feature Specification: Надёжное превью публикации ВК через прикрепление обложки фото

**Feature Branch**: `132-vk-photo-preview-attachment`
**Created**: 2026-08-04
**Status**: Draft
**Input**: User description: "Несмотря на все ухищрения в публикации ВК так и не появляется превью от бота. Ещё раз подробно изучи документацию https://dev.vk.com/ru/reference. Предложи варианты, как сделать превью в публикации новости на стене. В крайнем случае можно загружать картинку в момент публикации, подумай как это сделать (если не получится с превью). В общем - публикация должна быть оформлена красиво."

## Контекст и текущее поведение

На 04.08.2026 при автоматической публикации новостей в группу ВКонтакте
(см. `specs/121-vk-news-auto-publish`, `docs/features/vk-news-auto-publish.md`)
обнаружена устойчивая проблема: **посты, опубликованные ботом, не получают
графическое превью** (картинку-обложку), несмотря на все ранее принятые меры.

### Что было сделано (и почему не помогло)

| Дата | Мера | Результат |
|------|------|-----------|
| 02.08.2026 | Настройка nginx `rewrite` по User-Agent VK-парсера (`vkShare`, `vkim`, `VKBot`, `VKShareBot`) на endpoint `/api/public/og/song` (см. `specs/121`, раздел «Инварианты») | Работает при ручной публикации в UI ВКонтакте; бот-публикации НЕ триггерят повторный парсинг |
| 02.08.2026 | Получен user-token через Implicit Flow Standalone-приложения VK со scopes `video,photos,wall,offline` (см. `ApiController.kt:7065`) | Токен сохранён в `KaraokeProperties.vkUserAccessToken`, используется для `video.save` |
| 03.08.2026 | Полноценные Open Graph мета-теги (`og:image`, `og:title`, `og:description`, `og:type`) на endpoint `/api/public/og/song` (см. `PublicOgSongController.kt`) | При ручной публикации превью появляется; при бот-публикации — нет (см. ниже гипотезы) |
| 03.08.2026 | Откат размера PNG с 1200×630 на 537×240 | Гипотеза «большой размер ломает парсер» не подтвердилась |
| 03.08.2026 | `specs/130-vk-preview-generation` — синхронный прогрев PNG-кэша `/api/public/song-vk-image/{id}` перед `wall.post` (через `VkPreviewWarmupClient`), чтобы бот ВК не ждал первой генерации картинки | Гипотеза «бот не дожидается генерации» не подтвердилась: PNG-кэш готов, а сниппет всё равно не создаётся |
| 03.08.2026 | `specs/123-vk-og-preview-fix` — фиксация гипотез и решение через `photos.saveWallPhoto` (отложено: на тот момент предполагалось, что user-token с scope `photos` нужно получать через модерацию Standalone-приложения) | Не реализовано, но user-token с нужным scope **уже** есть — см. ниже |

### Главная проблема

Метод VK API `wall.post` при вызове от имени бота (через `POST /method/wall.post`)
**НЕ** выполняет парсинг URL в тексте поста для генерации сниппета. Вместо
этого он полагается на закэшированные сниппеты (если URL ранее парсился при
ручной публикации) или не показывает превью вообще. Это документировано
поведение VK API для бот-публикаций — оно отличается от поведения ручной
публикации через UI ВКонтакте, при которой ВК сам парсит OG-мета-теги при
создании поста.

**Следствие**: при бот-публикации (`wall.post` с `owner_id=-<groupId>`)
пост в группе ВКонтакте содержит:
- ✅ Текст поста (по шаблону `vkTemplateAir` / `vkTemplatePremium`)
- ✅ URL на страницу песни (`https://sm-karaoke.ru/song?id=<id>`)
- ✅ Видео демо-MP4 (через `video.save` + `attachments=video<owner>_<video_id>`)
- ❌ Графическое превью (сниппет с обложкой песни) — **отсутствует**

Пост выглядит «голо» в ленте: текст + ссылка без визуальной привлекательности.

### Ключевое наблюдение, которое меняет решение

В `ApiController.kt:7065` уже **настроен** user-token через Implicit Flow
со scopes `video,photos,wall,offline`. Этот токен **уже** имеет scope
`photos` и пригоден для вызова методов `photos.*` (включая
`photos.getWallUploadServer` и `photos.saveWallPhoto`). Дополнительная
модерация Standalone-приложения **не требуется** — токен уже валиден.

В `specs/123-vk-og-preview-fix` (от 03.08.2026) был сделан неверный вывод
о необходимости запрашивать модерацию. На тот момент user-token ещё не
был настроен. Сейчас (после фикса 02.08.2026) он есть и работает для
`video.save` — а значит, **должен** работать и для `photos.*`.

### Цель фичи

Обеспечить **100%**-е появление графического превью (картинки-обложки)
во всех новых постах бота ВКонтакте, **независимо** от того, как VK
обрабатывает URL в тексте. Публикация должна выглядеть оформленной и
заметной в ленте группы.

## Изученные варианты решения

Изучена официальная документация VK API по адресу https://dev.vk.com/ru/reference
(раздел «Стена» → `wall.post`, «Фотографии» → `photos.getWallUploadServer` /
`photos.saveWallPhoto`, «Документы» → `docs.*`). Документация требует
JavaScript для отображения, поэтому исследование проведено по спецификации
методов, существующему коду и опыту (FR-019 spec 121, заметки в
`docs/features/vk-news-auto-publish.md`, раздел «Известные ловушки»).

### Вариант A — Прикрепить обложку фото через `photos.*` (✅ ОСНОВНОЙ)

**Метод**: перед `wall.post` загрузить PNG-обложку песни как фото группы
через `photos.getWallUploadServer` → POST multipart на `upload_url` →
`photos.saveWallPhoto` → передать `attachments=photo<owner>_<id>,video<owner>_<video_id>`
(или только `photo...` для публикаций без видео) в `wall.post`.

**Преимущества**:
- ✅ VK **не парсит URL** для прикреплённых фото — берёт их прямо из API-параметра `attachments`.
- ✅ Работает **одинаково** для бот-публикации и ручной публикации.
- ✅ User-token с scope `photos` **уже есть** — никакой модерации не требуется.
- ✅ Превью появляется в 100% случаев (если шаг выполнен успешно).
- ✅ Превью-фото становится первым прикреплением поста — VK отображает его
  как сниппет на стене и в ленте подписчиков (стандартное поведение ВК).
- ✅ Видео остаётся вторым прикреплением (отображается как видеоплеер ниже).

**Ограничения**:
- Требует user-token с scope `photos` — **уже есть**.
- Требует multipart-загрузку на `upload_url` (HTTP POST, поле `photo`).
- Каждый пост = +1 фото в альбоме группы. За месяц при 3 постах/день это
  ~90 фото; за год ~1000. Можно потом удалять через `photos.delete` (опционально).
- При сбое VK API (5xx, тайм-аут) — нужен retry.

### Вариант B — Прикрепить как документ через `docs.*` (⚠️ FALLBACK)

**Метод**: загрузить обложку как документ (тип `image`) через
`docs.getWallUploadServer` → POST multipart → `docs.save` → `attachments=doc<owner>_<id>`.

**Преимущества**:
- ✅ Работает с **community-token** (право `docs` доступно сообществам).
- ✅ Не требует user-token.

**Недостатки**:
- ❌ Документы с MIME image отображаются в посте как файл-документ (с
  иконкой «документ»), а НЕ как сниппет-превью.
- ❌ Менее привлекательно визуально: вместо большой картинки-превью —
  маленькая иконка файла.
- ❌ VK может не использовать документ-картинку как превью поста (зависит от версии API).

**Применяем как fallback** — если `photos.*` методы вернут ошибку
(например, `error_code=27` «Group authorization failed»), пробуем `docs.*`.

### Вариант C — Повторный парсинг через `wall.edit` (⚠️ ЭКСПЕРИМЕНТАЛЬНЫЙ)

**Метод**: после `wall.post` вызвать `wall.edit` с тем же текстом — это
**может** триггернуть повторный парсинг VK URL в тексте и обновление сниппета.

**Недостатки**:
- ❌ Поведение VK API в этом случае **не документировано** и может меняться.
- ❌ Если не сработает — пост останется без превью.
- ❌ Лишний запрос к VK API.

**Не применяем** в первой версии — оставляем как запасной вариант на случай,
если и `photos.*`, и `docs.*` не дадут превью.

### Вариант D — Загрузка URL в первый комментарий (⚠️ ОГРАНИЧЕННЫЙ)

**Метод**: `wall.post` без URL → `wall.createComment(owner_id, post_id, message="<URL>")` — VK парсит URL в комментариях отдельно, и сниппет появляется в комментарии, а не в самом посте.

**Недостатки**:
- ❌ Превью появляется **в комментарии**, а не в самом посте.
- ❌ VK может блокировать комментарии от ботов в группе.

**Не применяем**.

### Вариант E — Опубликовать через Selenium/Playwright как UI-действие (❌ СЛОЖНО)

**Метод**: использовать headless Chromium для имитации действий пользователя в UI ВКонтакте.

**Недостатки**:
- ❌ Сложно реализовать и поддерживать.
- ❌ Хрупко: VK может менять UI.
- ❌ Требует логина от владельца группы.

**Не применяем**.

### Выбранное решение

**Вариант A** (`photos.saveWallPhoto` + `attachments=photo...`) — основной
путь. **Вариант B** (`docs.save` + `attachments=doc...`) — fallback для
случая, когда `photos.*` вернёт ошибку авторизации (`error_code=27`).

В обоих случаях публикация должна пройти успешно даже при сбое обоих
методов — пост будет создан с видео (если есть), но без превью-картинки.
Это **деградация, а не отказ** — администратор увидит предупреждение
в `vkAutoPublishLastError` и сможет повторить.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Пост бота ВКонтакте содержит графическое превью (Priority: P1)

Администратор или плановый планировщик запускает публикацию песни в группу
ВКонтакте. Посетитель группы ВКонтакте видит в ленте полноценный пост:
**заголовок, обложку песни (картинка-превью), описание, ссылку на страницу
песни и опционально видео-демо**. Пост визуально выделяется в ленте и
привлекает внимание — рядом с другими постами без превью он сразу
узнаётся как анонс караоке-песни.

**Why this priority**: Это центральная цель фичи — без превью пост
выглядит «голым» и не выполняет свою задачу (привлечь внимание к песне).
Все остальные user-stories — про надёжность и обработку ошибок.

**Independent Test**: Запустить публикацию песни с пустым `Song.idVk`
(через `POST /api/song/publishToVkNow?id=<id>&type=air`). Дождаться
успешного завершения. Открыть пост в группе ВКонтакте (UI или через
`wall.getById` через VK API) и убедиться, что:
1. Пост содержит текст.
2. Пост содержит прикреплённое фото (`photo<owner>_<id>`).
3. В UI ВКонтакте пост отображается с большой картинкой-превью (сниппетом).
4. Если есть видео — оно присутствует как второе прикрепление.

**Acceptance Scenarios**:

1. **Given** для песни нет опубликованного поста ВКонтакте (`Song.idVk` пуст),
   **When** администратор запускает AIR-публикацию (или срабатывает плановый тик),
   **Then** бот создаёт пост в группе ВКонтакте, который содержит:
   текст, URL на страницу песни, прикреплённое фото (обложка песни),
   и опционально — прикреплённое видео демо-MP4.
2. **Given** пост успешно опубликован, **When** посетитель открывает группу ВКонтакте,
   **Then** он видит пост с большим графическим превью (картинкой обложки альбома + название песни),
   а не «голый» текст с ссылкой.
3. **Given** PNG-обложка ещё не сгенерирована, **When** бот запускает публикацию,
   **Then** перед `wall.post` бот синхронно генерирует обложку (через прогрев, как сейчас),
   чтобы фото было готово к моменту загрузки на VK.
4. **Given** PNG-обложка не может быть сгенерирована (нет MinIO-картинок альбома/автора),
   **When** бот запускает публикацию, **Then** бот **не** публикует пост без обложки
   (см. User Story 2) или использует fallback (см. User Story 4).

### User Story 2 - Безопасная обработка ошибки загрузки фото (Priority: P1)

Если по какой-то причине обложку не удалось загрузить в VK (сбой
`photos.getWallUploadServer`, тайм-аут загрузки файла, ошибка
`photos.saveWallPhoto`), бот должен корректно обработать эту ситуацию:
либо использовать fallback (User Story 4), либо отложить публикацию
до устранения причины. Администратор должен увидеть внятное сообщение
об ошибке.

**Why this priority**: Без обработки ошибок бот может молча создавать
посты без превью (деградация фичи), или падать с неинформативной
ошибкой (невозможно диагностировать).

**Independent Test**: Имитировать ошибку `photos.saveWallPhoto` (например,
временно установить `vkUserAccessToken` в невалидное значение через
Properties UI). Запустить публикацию. Убедиться, что:
1. Состояние `vkAutoPublishState` стало `SEND_FAILED`.
2. `vkAutoPublishLastError` содержит понятное описание ошибки с префиксом
   `photo upload failed:` или `wall.post failed:` (если fallback сработал).
3. `Song.idVk` остался пустым (пост не создан).
4. После восстановления токена повторная публикация успешна.

**Acceptance Scenarios**:

1. **Given** `photos.getWallUploadServer` возвращает ошибку (5xx, сетевая),
   **When** бот запускает публикацию, **Then** бот НЕ создаёт пост,
   `vkAutoPublishState` = `SEND_FAILED`, `vkAutoPublishLastError` содержит
   причину с префиксом `photo upload failed:`.
2. **Given** загрузка файла на `upload_url` не удалась (HTTP не 200),
   **When** бот запускает публикацию, **Then** бот НЕ создаёт пост и
   записывает причину с тем же префиксом.
3. **Given** `photos.saveWallPhoto` возвращает ошибку (например,
   `error_code=27` «Group authorization failed»), **When** бот запускает публикацию,
   **Then** бот пробует fallback через `docs.*` (User Story 4).
4. **Given** загрузка фото провалилась, **When** администратор повторяет
   публикацию, **Then** бот повторяет все шаги (включая загрузку фото)
   с нуля; ранее загруженные фото (если они остались) могут быть переиспользованы,
   но **не** обязаны (транзиентный кеш).

### User Story 3 - Сохранение существующего поведения идемпотентности (Priority: P1)

Все ранее реализованные инварианты автопубликации ВКонтакте должны
продолжать работать: идемпотентность по `Song.idVk`, прогрев PNG,
rate limit, ретраи VK API, отдельный lock по `song.id`. Никаких регрессий.

**Why this priority**: Без идемпотентности — дубли постов; без прогрева —
первая публикация может занять минуты; без rate-limit — VK забанит группу;
без ретраев — единичный сбой сети ломает публикацию.

**Independent Test**: Запустить повторную публикацию песни, у которой
`Song.idVk` уже заполнен. Убедиться, что бот пропускает её (FR-008
из specs/121). Запустить одновременно два тика scheduler'а для одной
песни. Убедиться, что создаётся ровно один пост. Проверить, что rate-limit
(3 поста/час) продолжает работать (вторая попытка в одной минуте не
приводит к двум постам подряд).

**Acceptance Scenarios**:

1. **Given** песня уже опубликована в ВКонтакте (`Song.idVk` заполнено),
   **When** запускается любой следующий тик планировщика или ручной вызов,
   **Then** повторный пост **не** создаётся (FR-008 specs/121).
2. **Given** две публикации одной песни запускаются одновременно,
   **When** они обрабатываются, **Then** создаётся ровно один пост
   (process-local lock по `song.id` сохраняется).
3. **Given** rate-limit превышен (>=3 постов за последний час),
   **When** планировщик пытается опубликовать ещё одну песню,
   **Then** публикация откладывается на следующий тик (FR-006 specs/121).
4. **Given** `wall.post` вернул транзиентную ошибку (5xx, 429),
   **When** бот запускает публикацию, **Then** бот делает до 3 ретраев
   с backoff (FR-009 specs/121); после успешного ретрая загруженное фото
   остаётся валидным для прикрепления.

### User Story 4 - Fallback через документ-картинку (Priority: P2)

Если `photos.*` методы возвращают ошибку авторизации (`error_code=27`
«Group authorization failed») — это может произойти, если user-token
потерял scope `photos` или был отозван VK, — бот пытается использовать
`docs.*` методы как fallback: загружает обложку как документ (тип `image`)
через `docs.getWallUploadServer` + `docs.save` + `attachments=doc<owner>_<id>`.

**Why this priority**: Fallback повышает надёжность: даже при потере
user-scope `photos` пост будет создан с прикреплённой картинкой (хоть
и в форме документа). Качество превью ниже, чем у `photos.*`, но
лучше, чем отсутствие превью.

**Independent Test**: Имитировать ошибку `photos.saveWallPhoto` (например,
подменить user-token на токен без scope `photos`). Запустить публикацию.
Убедиться, что бот пробует `docs.*` методы, и если они работают —
пост создаётся с прикреплённым документом.

**Acceptance Scenarios**:

1. **Given** `photos.saveWallPhoto` вернул `error_code=27` или аналогичную
   ошибку авторизации, **When** бот запускает публикацию, **Then** бот
   пробует `docs.getWallUploadServer` → загрузка → `docs.save` и
   использует `attachments=doc<owner>_<id>` в `wall.post`.
2. **Given** `docs.*` методы тоже не сработали, **When** бот запускает
   публикацию, **Then** бот создаёт пост **без** прикреплённой картинки
   (только текст + URL + опционально видео), записывает предупреждение
   в `vkAutoPublishLastError` с префиксом `photo attach failed:`.
3. **Given** ни `photos.*`, ни `docs.*` не сработали, **When** администратор
   повторяет публикацию после устранения причины, **Then** пост создаётся
   с превью (если причина устранена).

### User Story 5 - Размер и качество превью-картинки (Priority: P2)

PNG-обложка песни, которая загружается в VK как превью, должна иметь
**оптимальный размер** для VK — 1200×630 px (стандарт Open Graph, который
ВКонтакте рекомендует для сниппетов). Текущий размер 537×240 — допустимый
минимум, но приводит к менее качественному отображению (картинка
растягивается).

**Why this priority**: Визуальное качество превью — это восприятие
бренда. Большая, чёткая картинка с обложкой альбома + название песни
делает пост заметным и профессиональным.

**Independent Test**: Открыть endpoint `/api/public/song-vk-image/{id}` —
убедиться, что PNG теперь имеет размер 1200×630 (а не 537×240).
Сохранить PNG, проверить разрешение через `identify` или `file` —
должно быть `1200x630`. Запустить публикацию — убедиться, что загруженное
в VK фото имеет правильный размер (через `photos.getById` или визуально в ВК).

**Acceptance Scenarios**:

1. **Given** endpoint `/api/public/song-vk-image/{id}` вызван первый раз,
   **When** он генерирует PNG, **Then** размер изображения — 1200×630 px
   (а не 537×240 как раньше).
2. **Given** PNG-кэш `/tmp/vk_<id>.png` уже существует, **When** endpoint
   вызван повторно, **Then** отдаётся кэшированный файл (без перегенерации),
   и его размер — 1200×630 px.
3. **Given** PNG обложки имеет размер 1200×630, **When** бот загружает
   его в VK через `photos.saveWallPhoto`, **Then** VK принимает файл
   без ошибок (`photos.saveWallPhoto` имеет лимит на размер файла,
   но 1200×630 PNG ~ 100-300 КБ укладывается).

### Edge Cases

- **PNG-обложка не сгенерировалась** (нет картинки альбома/автора в MinIO) —
  бот НЕ создаёт пост (как и сейчас при сбое прогрева), `vkAutoPublishState` =
  `SEND_FAILED` с префиксом `preview prewarm failed:`.
- **`photos.getWallUploadServer` возвращает пустой `upload_url`** —
  бот пробует `docs.*` fallback (User Story 4).
- **Загрузка на `upload_url` возвращает неожиданный JSON** (не содержит
  поля `server`, `photo`, `hash`) — бот записывает ошибку с подробностями
  и НЕ создаёт пост.
- **VK API возвращает `error_code=29` (rate limit)** при `photos.*` или
  `docs.*` методах — бот применяет backoff и ретраит (в рамках существующего
  retry-механизма VK API).
- **`photos.saveWallPhoto` возвращает массив из нескольких фото** (бывает
  при загрузке нескольких файлов в одном запросе, мы загружаем один) —
  бот берёт **первый** элемент массива.
- **Караоке-группа ВКонтакте не имеет прав `photos` в настройках группы**
  (например, для группы без подтверждения) — `photos.*` методы вернут
  ошибку; fallback на `docs.*`.
- **Загруженное фото случайно попало в «запрещённые»** (модерация ВК) —
  VK удалит фото автоматически; пост останется без превью; администратор
  увидит это в UI ВКонтакте и сможет повторить публикацию после
  корректировки обложки.
- **Параллельные публикации разных песен** — каждая публикация загружает
  своё фото; конфликтов между разными песнями нет (lock по `song.id`
  на публикацию + `photos.*` принимает любые уникальные файлы).
- **Изменение обложки песни между двумя публикациями одной песни** —
  если `Song.idVk` пуст (например, после перепубликации), бот загрузит
  текущую обложку, а не устаревший файл из кэша; переиспользование
  ранее загруженных в VK фото **не** предполагается.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: При публикации поста в группу ВКонтакте (AIR или PREMIUM)
  бот ДОЛЖЕН перед `wall.post` загрузить PNG-обложку песни как фото
  группы через методы VK API `photos.getWallUploadServer` →
  `photos.saveWallPhoto` (с user-token, имеющим scope `photos`),
  и передать полученный идентификатор в `wall.post` через
  параметр `attachments=photo<owner>_<id>` (вместе с видео, если
  видео присутствует).
- **FR-002**: PNG-обложка, загружаемая в VK как фото, ДОЛЖНА иметь
  размер **1200×630 px** (стандарт Open Graph, рекомендуемый VK для
  сниппетов) — изменение относительно текущего 537×240. PNG-обложка
  генерируется существующим endpoint `/api/public/song-vk-image/{id}`
  с обновлёнными параметрами размера.
- **FR-003**: Endpoint `/api/public/song-vk-image/{id}` ДОЛЖЕН продолжать
  работать в прежнем режиме (прогрев PNG-кэша через
  `VkPreviewWarmupClient`, атомарная запись, проверка PNG magic-signature)
  — эти инварианты из `specs/130-vk-preview-generation` сохраняются.
  Меняется только параметр размера PNG (537×240 → 1200×630).
- **FR-004**: Бот ДОЛЖЕН передавать в `wall.post` параметр `attachments`
  в виде списка прикреплений через запятую, в порядке:
  1. `photo<owner>_<id>` (всегда первое — VK берёт первое прикрепление
     как превью поста);
  2. `video<owner>_<video_id>` (если есть демо-MP4 и был успешно
     загружен через `video.save`).
  Если видео нет — только `photo<owner>_<id>`. Если видео есть, но фото
  не удалось загрузить (fallback тоже не сработал) — только `video...`.
- **FR-005**: Загрузка фото через `photos.*` методы ДОЛЖНА использовать
  **user-token** (`vkUserAccessToken` в `KaraokeProperties`), а не
  community-token — это документированное ограничение VK API
  (`error_code=27 "Group authorization failed: method is unavailable with group auth"`).
  Если user-token пуст или не имеет scope `photos` — бот ДОЛЖЕН попробовать
  fallback через `docs.*` (FR-006), затем — отправить пост без фото
  (с предупреждением).
- **FR-006**: Если `photos.*` методы вернули ошибку `error_code=27`
  («Group authorization failed») или `error_code=15` («Access denied»)
  или `error_code=5` («User authorization failed»), бот ДОЛЖЕН
  попробовать fallback через `docs.*` методы:
  `docs.getWallUploadServer` → POST multipart с полем `file` →
  `docs.save` → `attachments=doc<owner>_<id>`. Fallback использует
  **community-token** (право `docs` доступно сообществам по умолчанию).
- **FR-007**: Если и `photos.*`, и `docs.*` (fallback) не дали загруженного
  прикрепления, бот ДОЛЖЕН опубликовать пост **без** превью-картинки
  (только текст + URL + опционально видео), записав предупреждение
  в `vkAutoPublishLastError` с префиксом `photo attach failed: <причина>`.
  Публикация **не** должна полностью проваливаться из-за отсутствия фото —
  пост создаётся в деградированном виде (без превью).
- **FR-008**: Существующая идемпотентность по `Song.idVk` (FR-008 specs/121)
  ДОЛЖНА сохраняться: если `Song.idVk` уже заполнено — бот пропускает
  публикацию, никакие шаги (включая загрузку фото) не выполняются.
- **FR-009**: Существующий process-local lock по `song.id`
  (specs/130-vk-preview-generation, `VkAutoPublishService.songLocks`)
  ДОЛЖЕН покрывать новый шаг загрузки фото: между проверкой
  `Song.idVk`, прогревом PNG, загрузкой фото и `wall.post` не должно
  быть гонки с параллельной публикацией той же песни.
- **FR-010**: Существующий rate-limit (FR-006 specs/121, настройка
  `vkAutoPublishRateLimitPerHour`) ДОЛЖЕН применяться к публикациям
  с превью так же, как к публикациям без превью: одна попытка загрузки
  фото + одна попытка `wall.post` = один пост в rate-limit-счётчик.
- **FR-011**: Существующий прогрев PNG (`specs/130-vk-preview-generation`,
  `VkPreviewWarmupClient.warmup(songId)`) ДОЛЖЕН предшествовать загрузке
  фото: сначала убеждаемся, что PNG готов и валиден (HTTP 200 +
  PNG magic-signature), затем загружаем файл в VK через `photos.*`.
  Это исключает ситуацию, когда VK получит битый/пустой PNG.
- **FR-012**: Существующая retry-логика VK API (FR-009 specs/121,
  3 попытки с backoff 30с→2мин→5мин) ДОЛЖНА покрывать новые методы
  `photos.*` и `docs.*` (если они доступны через тот же `VkApiClient.send`).
  Non-retryable коды (`4`, `5`, `15`, `100`) сохраняются; для `photos.*`
  также `27` (Group authorization failed) — non-retryable и **триггер
  fallback** на `docs.*` (FR-006).
- **FR-013**: Все загруженные в VK фото/документы НЕ сохраняются в БД —
  это transient-объекты, привязанные к конкретному посту. Если пост
  удаляется из ВКонтакте вручную — фото остаётся в альбоме группы
  (это документированное поведение VK API). Если потребуется очистка —
  отдельная задача (backlog, не входит в первую версию).
- **FR-014**: Существующий `vkPreviewWarmupEnabled` (настройка из
  specs/130) ДОЛЖЕН продолжать работать — если прогрев отключён,
  бот всё равно пытается загрузить фото в VK, но без предварительного
  prewarm (файл может не существовать → загрузка на VK вернёт ошибку →
  бот запишет `photo upload failed:` и попробует fallback).
- **FR-015**: НЕ ДОЛЖНО быть структурных изменений в `Song` / `tbl_songs` —
  поле `Song.idVk` остаётся единственным признаком «опубликовано в ВКонтакте».
  Никаких новых полей в БД, никаких миграций.
- **FR-016**: НЕ ДОЛЖНО быть структурных изменений в `News` / `tbl_news` —
  для редкого случая (новость без `song_id`) идемпотентность остаётся
  через существующий `vkAutoPublishState` в `News.playerReadinessFlags`
  (FR-004a specs/121).
- **FR-017**: Существующая обработка ретраев `video.save` (FR-019 specs/121)
  ДОЛЖНА остаться — если `video.save` не удался, бот пробует повторно
  (до 3 раз), затем публикует без видео (только фото + текст).

### Key Entities *(include if feature involves data)*

- **Фото превью песни (Photo Attachment)** — файл PNG 1200×630,
  загруженный через `photos.saveWallPhoto` в группу ВКонтакте. Идентификатор
  в формате `photo<owner_id>_<photo_id>` (например, `photo-123456_789012`),
  используется в параметре `attachments` метода `wall.post`. Время жизни
  привязано к посту; в БД не персистится (transient). Создаётся при каждой
  публикации заново (если `Song.idVk` пуст).
- **Документ-картинка (Doc Attachment)** — fallback-прикрепление, файл
  PNG 1200×630, загруженный через `docs.save` как документ с типом `image`.
  Идентификатор в формате `doc<owner_id>_<doc_id>`. Используется только
  если `photos.*` методы не сработали.
- **Публикация ВКонтакте (Vk Post)** — пост в группе ВКонтакте, содержащий
  текст (по шаблону `vkTemplateAir` / `vkTemplatePremium`), URL на страницу
  песни, прикреплённое фото (FR-001) и опционально прикреплённое видео
  (FR-017 specs/121). Идентификатор в `Song.idVk` (формат `-<groupId>_<postId>`).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: В контрольной серии из 20 новых AIR-публикаций **100%** постов
  в группе ВКонтакте содержат графическое превью (сниппет с обложкой),
  видимое в UI ВКонтакте.
- **SC-002**: В 100% контрольных сценариев с PREMIUM-публикацией (если
  у бота есть демо-MP4 + PNG обложки) пост содержит и превью, и видео.
- **SC-003**: В 100% сценариев с временным сбоем `photos.*` методов
  (например, `error_code=27`) бот успешно использует fallback через
  `docs.*`, и пост создаётся с прикреплением (хоть и в форме документа).
- **SC-004**: В 100% сценариев с одновременным запуском двух публикаций
  одной песни создаётся **ровно один** пост (lock + идемпотентность
  по `Song.idVk`).
- **SC-005**: В 100% сценариев с ошибкой `wall.post` (5xx, rate-limit)
  бот делает ретрай с backoff и НЕ оставляет систему в неконсистентном
  состоянии (`Song.idVk` пуст, состояние `SEND_FAILED` с описанием).
- **SC-006**: Среднее время от запуска публикации до появления поста
  в ВКонтакте не увеличивается более чем на **+3 секунды** по сравнению
  с текущим поведением (только видео) — загрузка одного PNG через
  `photos.*` методы занимает <<1 секунды при нормальной сети.
- **SC-007**: Размер загружаемой PNG-картинки — **1200×630 px** (проверяется
  через `file` / `identify` после сохранения с VK через `photos.getById`).
- **SC-008**: Администратор в **100%** сценариев может отличить ошибку
  загрузки фото от ошибки VK API по `vkAutoPublishLastError`:
  `photo upload failed:` / `photo attach failed:` / `doc upload failed:`
  vs `wall.post failed:` / `video.save failed:`.

## Assumptions

- User-token с scope `photos` уже настроен в `KaraokeProperties.vkUserAccessToken`
  (получен 02.08.2026 через Implicit Flow Standalone-приложения со scopes
  `video,photos,wall,offline` — см. `ApiController.kt:7065`).
- Standalone-приложение VK НЕ требует отдельной модерации для использования
  user-token с scope `photos` — это документировано поведение VK API
  (в отличие от предположения, сделанного в `specs/123-vk-og-preview-fix`
  03.08.2026).
- Endpoint `/api/public/song-vk-image/{id}` будет расширен с 537×240 до
  1200×630. Логика прогрева, атомарной записи и проверки PNG magic-signature
  (`specs/130-vk-preview-generation`) сохраняется без изменений.
- PNG-кэш `/tmp/vk_<id>.png` останется в `karaoke-web` (эфемерный, в
  контейнере); перегенерация при рестарте — допустимое поведение.
- Группа ВКонтакте `svoemestokaraoke` имеет права `photos` (настраивается
  в «Управление → Работа с API → Ключи доступа» вместе с `wall` и `video`)
  — это документировано в `docs/features/vk-news-auto-publish.md`.
- VK API поддерживает фото-превью размером 1200×630 — это рекомендуемый
  размер для сниппетов в документации VK API (стандарт Open Graph).
- Загрузка PNG через `photos.*` методы занимает <<1 секунды при нормальной
  сети и НЕ блокирует UI пользователя (асинхронная публикация).
- Администратор готов мириться с тем, что каждая публикация = +1 фото
  в альбоме группы (≈1000 фото/год при текущем темпе 3 поста/день).
  Очистка через `photos.delete` — отдельная задача (backlog).

## Границы первой версии

**Входит**:
- Загрузка PNG-обложки через `photos.getWallUploadServer` + `photos.saveWallPhoto`.
- Передача `attachments=photo<owner>_<id>,video<owner>_<video_id>` (или только `photo`) в `wall.post`.
- Fallback на `docs.*` методы при `error_code=27` / `15` / `5` от `photos.*`.
- Расширение PNG endpoint `/api/public/song-vk-image/{id}` с 537×240 до 1200×630.
- Сохранение всех существующих инвариантов (идемпотентность, lock, rate-limit, retry, прогрев).

**Не входит** (backlog):
- Очистка ранее созданных постов без превью (требует отдельного механизма).
- Очистка альбома группы ВКонтакте от ранее загруженных фото (`photos.delete`).
- Автоматическая перепубликация исторических постов с превью.
- Поддержка нескольких фото в одном посте (carousel) — VK API позволяет,
  но не входит в первую версию.
- UI-индикатор «превью загружено» в карточке песни в `webvue3` —
  можно добавить позже (на базе существующего `vkAutoPublishLastError`).

## Clarifications

### Session 2026-08-04 (initial, from /speckit.specify)

- **Q1 (каким способом реализовать превью)** — **A. photos.saveWallPhoto + attachments**:
  загружать PNG через `photos.*` методы и прикреплять к посту через `attachments=photo...`.
  Это **самое надёжное** решение (VK берёт фото из API, не парся URL),
  и user-token с нужным scope **уже** есть (получен 02.08.2026, в отличие
  от предположения в `specs/123`).
- **Q2 (что делать, если photos.* не сработает)** — **A. fallback на docs.* методы**:
  если `photos.*` вернёт ошибку авторизации (`error_code=27 / 15 / 5`),
  пробуем `docs.getWallUploadServer` + `docs.save` с community-token
  (право `docs` доступно сообществам). Это даёт второй шанс на превью.
- **Q3 (если оба способа не сработают)** — **A. публикация без превью, но НЕ отказ**:
  пост создаётся в деградированном виде (только текст + URL + опционально видео),
  с предупреждением в `vkAutoPublishLastError`. Это лучше, чем полная
  неудача публикации.
