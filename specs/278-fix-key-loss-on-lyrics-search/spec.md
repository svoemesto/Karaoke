# Feature Specification: Fix Key/Tone Loss During Lyrics Search in Add-Files-From-Folder

**Feature Branch**: `278-fix-key-loss-on-lyrics-search`

**Created**: 2026-08-30

**Status**: Draft

**Input**: User description: "Админка, главна страница, «Добавить файлы из папки». Запускается кортеж заданий, среди которых у песни определяется тональность. Так же запускается поиск текста для песни, но не через механизм процессов. Если тональность через процессы находится раньше, чем начался поиск текста для песни, то если текст находится, то при этом найденное ранее значение тональности в песне теряется, перезатирается пустым значением, и его ещё раз приходится находить. Надо найти место, где при поиске текста теряется найденная тональность и исправить."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Тональность не теряется при добавлении файлов из папки (Priority: P1)

Администратор на главной странице админки нажимает «Добавить файлы из папки» с папкой, содержащей несколько аудиофайлов. Для каждого файла создаётся новая песня, в очередь ставится процесс определения тональности (`KEY_BPM_FROM_FILE`), и одновременно запускается поиск текста на Яндекс.Музыке через Playwright (синхронно, может занимать десятки секунд на файл). Если процесс `KEY_BPM_FROM_FILE` успевает определить тональность раньше, чем завершается поиск текста, то при нахождении текста найденная ранее тональность **НЕ ДОЛЖНА** теряться или перезатираться пустым значением. Администратор видит в карточке песни уже определённую тональность (key/BPM) и найденный текст одновременно.

**Why this priority**: Это критичный баг, ломающий рабочий процесс импорта. Каждый новый файл из папки требует повторного ручного запуска определения тональности, что умножает время оператора и создаёт дублирующиеся процессы в очереди.

**Independent Test**: Запустить «Добавить файлы из папки» с папкой из 3+ файлов, где KEY_BPM_FROM_FILE успевает отработать за время `findYandexSongLyrics`. После завершения всех операций открыть карточку любой обработанной песни: тональность (song_tone) и BPM (song_bpm) НЕ должны быть пустыми, если процесс KEY_BPM_FROM_FILE их нашёл. Их не нужно запускать повторно вручную.

**Acceptance Scenarios**:

1. **Given** папка с 3 аудиофайлами в формате `YYYY (NN) [Автор] - Песня.flac` и пустой таблицей `tbl_songs`, **When** администратор нажимает «Добавить файлы из папки» и подтверждает, **Then** для каждого файла создаётся песня, в очередь ставится процесс `KEY_BPM_FROM_FILE`, и синхронно запускается `findYandexSongLyrics`. Если KEY_BPM_FROM_FILE успевает найти тональность (например, за 10 сек) до завершения поиска текста (например, 30 сек), то после `newSong.saveToDb()` тональность остаётся заполненной в `tbl_songs.song_tone`/`song_bpm`.

2. **Given** песня только что добавлена из папки, KEY_BPM_FROM_FILE завершился успешно и записал `song_tone="Am", song_bpm=120`, **When** синхронно находился текст песни и сохраняется через `newSong.saveToDb()`, **Then** в `tbl_songs` остаются `song_tone="Am"`, `song_bpm=120`, `source_text="<найденный текст>"`. Ручной повторный запуск определения тональности НЕ требуется.

3. **Given** песня только что добавлена, KEY_BPM_FROM_FILE завершился с ошибкой (тональность не определена), **When** синхронно находился текст песни и сохраняется, **Then** в `tbl_songs` сохраняется `source_text="<текст>"`, `song_tone=""`, `song_bpm=0` — без побочных эффектов, как и раньше.

### User Story 2 - Другие параллельные процессы (Demucs и т.п.) не теряют свои результаты (Priority: P2)

Администратор добавляет файлы из папки. Помимо `KEY_BPM_FROM_FILE`, параллельно в очередь ставится процесс `DEMUCS2` (стем-сепарация, тоже в `Song.createFromPath`). Аналогичная проблема может проявиться и для него: если Demucs успевает обновить поля `audio_song`/`audio_music`/`audio_vocals`/`audio_drums`/`audio_bass` к моменту `newSong.saveToDb()` после поиска текста — эти поля не должны перезатираться.

**Why this priority**: Demucs работает значительно дольше KEY_BPM_FROM_FILE, поэтому гонка менее вероятна, но архитектурно это та же проблема — единое исправление должно покрыть все случаи.

**Independent Test**: Запустить добавление файлов из папки, дождаться завершения DEMUCS2 для одного из треков. После сохранения текста проверить, что `audio_song`/`audio_vocals` не сброшены в пустые значения.

**Acceptance Scenarios**:

1. **Given** DEMUCS2 успешно завершился и записал URL'ы стемов в `tbl_songs.audio_song`/`audio_music`/`audio_vocals`, **When** синхронно находился текст песни и сохраняется через `newSong.saveToDb()`, **Then** URL'ы стемов остаются заполненными (не сброшены в пустую строку).

---

### Edge Cases

- **Что если между `applyDuplicateOriginal` (или `applyAudioParentMarkers`) и `findYandexSongLyrics` процесс `KEY_BPM_FROM_FILE` уже записал тональность?** — должен применяться тот же механизм защиты (reload из БД перед saveToDb), что и для основного пути Яндекс→saveToDb.
- **Что если `findYandexSongLyrics` бросает исключение (Playwright упал, таймаут)?** — `newSong.saveToDb()` не вызывается, тональность из процесса сохраняется как есть (процесс сам делал `saveToDb` через свой экземпляр Song).
- **Что если фоновый lyricsSearchExecutor (`lyricsSearchExecutor.submit`) тоже сохраняет текст параллельно с KEY_BPM_FROM_FILE?** — перезагрузка из БД перед сохранением покрывает и этот случай.
- **Что если песня уже существовала в БД, и при импорте мы её пропустили (уже импортирована)?** — этот код-путь не затрагивается, баг только про вновь созданные песни.
- **Что если процесс KEY_BPM_FROM_FILE для ЭТОЙ песни ещё не запущен (например, очень быстрый Яндекс нашёл текст раньше)?** — `this.key == ""`, `savedSong.key == ""`, в diff не попадает — поведение не меняется.
- **Что если несколько песен импортируются разом, и для одной из них KEY_BPM отработал в фоне, пока мы обрабатываем другую?** — гонка остаётся per-song, после `findYandexSongLyrics` мы перезагружаем КОНКРЕТНУЮ эту песню и пишем только то, что у нас в памяти изменилось по сравнению с актуальным состоянием.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: В `ApiController.doCreateFromFolder` (`karaoke-app/src/main/kotlin/com/svoemesto/karaokeapp/controllers/ApiController.kt:5390`) перед `newSong.saveToDb()` после успешного `findYandexSongLyrics` объект `newSong` ДОЛЖЕН быть перезагружен из БД (`Song.loadFromDbById(id = newSong.id, ...)`) с тем, чтобы актуальное состояние (включая `key`/`bpm`, установленные параллельным процессом `KEY_BPM_FROM_FILE`, и URL'ы стемов, установленные `DEMUCS2`) было базой для `getDiff`. После перезагрузки присваиваются `sourceText` и при необходимости `idStatus`, затем вызывается `saveToDb()`.
- **FR-002**: Аналогичная защита ДОЛЖНА быть применена к путям `applyDuplicateOriginal` (если он делает `saveToDb`) и `applyAudioParentMarkers` → `setSourceMarkers` → `saveToDb()` (Song.kt:3626-3653). Перед записью `sourceMarkers`/`resultText`/`formattedTextSong`/`formattedTextTabs`/`formattedTextChords` объект ДОЛЖЕН быть перезагружен из БД, чтобы не перезатереть параллельно найденные `key`/`bpm`/URL'ы стемов.
- **FR-003**: Перезагрузка объекта из БД перед `saveToDb()` ДОЛЖНА выполняться через `Song.loadFromDbById(id, database = WORKING_DATABASE, storageService, storageApiClient)`, чтобы сохранить консистентность с паттерном, который уже используется в `Song.saveToDb()` для строки 5180.
- **FR-004**: Поведение `Song.saveToDb()` (`karaoke-app/src/main/kotlin/com/svoemesto/karaokeapp/model/Song.kt:5169`) НЕ ДОЛЖНО быть изменено — это основной низкоуровневый механизм записи, который используется из 46 мест (см. blast radius в `Song.kt` / `KaraokeProcess.kt`). Корректная защита от race condition — перезагрузка объекта перед `saveToDb()` в вызывающем коде, а НЕ модификация самого `saveToDb()` (это сломает существующие 46 вызывающих мест, которые корректно работают).
- **FR-005**: После применения фикса должно быть проверено, что в `tbl_songs` для импортированной песни заполнены и `source_text` (если Яндекс нашёл), и `song_tone`/`song_bpm` (если KEY_BPM_FROM_FILE нашёл), без необходимости повторного запуска определения тональности вручную.
- **FR-006**: Фикс ДОЛЖЕН также покрывать случай, когда `findYandexSongLyrics` бросает исключение — в этом случае `saveToDb()` не вызывается, и процесс `KEY_BPM_FROM_FILE` уже сделал свою запись ранее. Существующий `try/catch` вокруг `findYandexSongLyrics` (ApiController.kt:5451-5460) уже обеспечивает эту защиту, никаких дополнительных изменений не требуется.
- **FR-007**: Фикс ДОЛЖЕН сохранить существующую семантику `textResolved = true` (ApiController.kt:5465) — после успешного `findYandexSongLyrics` НЕ ДОЛЖЕН запускаться фоновый `lyricsSearchExecutor.submit` (ApiController.kt:5473-5488), так как текст уже найден.

### Key Entities

- **Song**: доменная сущность с полями `key` (song_tone), `bpm` (song_bpm), `source_text` (sourceText), `id_status`, аудио-стемы (`audio_song`/`audio_music`/`audio_vocals`/`audio_drums`/`audio_bass`), и т.д. Хранится в `tbl_songs`. Параллельный доступ через `KaraokeProcessWorker` (async) и контроллеры (`doCreateFromFolder` — sync).
- **KaraokeProcess**: запись в `tbl_processes`, представляющая фоновое задание (`KEY_BPM_FROM_FILE`, `DEMUCS2`, и т.д.). При завершении процесса обновляет соответствующие поля `Song` через свой собственный экземпляр `Song.saveToDb()`.
- **YandexLyricsSearchOutcome**: результат поиска текста на Яндекс.Музыке (`Found(text)` или `NotFound(reason)`). Возвращается синхронной функцией `findYandexSongLyrics()`.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: При добавлении 3+ файлов из папки, для которых процесс `KEY_BPM_FROM_FILE` успевает отработать за время синхронного `findYandexSongLyrics`, в `tbl_songs` для 100% обработанных песен `song_tone`/`song_bpm` остаются заполненными и не требуют повторного запуска определения тональности.
- **SC-002**: После применения фикса повторный запуск `KaraokeProcessTypes.KEY_BPM_FROM_FILE` для песен, где процесс уже отработал и `findYandexSongLyrics` тоже завершился, не наблюдается (отсутствуют новые записи в `tbl_processes` с `process_command = 'KEY_BPM_FROM_FILE'` для этих песен, проверено через `SELECT`).
- **SC-003**: Фикс покрывает race condition для всех 3 точек `saveToDb()` в `doCreateFromFolder` (для `applyAudioParentMarkers` через `setSourceMarkers` и для блока Яндекс-поиска). В каждой из этих точек добавлена перезагрузка из БД.
- **SC-004**: Никакие регрессии в существующих 46 точках вызова `Song.saveToDb()` (включая `KaraokeProcessThread.run`, `HealthReport`, `UtilsAI`, `VkAutoPublishService`, `TelegramAutoPublishService` и т.д.) — фикс локальный для `doCreateFromFolder` и `setSourceMarkers` и не трогает сам `saveToDb()`.
- **SC-005**: После применения фикса при массовом импорте папки из 10 файлов ровно 10 новых песен появляются в `tbl_songs` с одновременно заполненными `source_text` (если Яндекс нашёл) и `song_tone`/`song_bpm` (если KEY_BPM_FROM_FILE нашёл), без необходимости ручного вмешательства.

## Assumptions

- Восстановление параллельных результатов через перезагрузку объекта из БД перед `saveToDb()` — наиболее безопасный и минимально-инвазивный подход, не затрагивающий низкоуровневый `Song.saveToDb()` (который используется в 46+ местах).
- Предполагается, что `Song.loadFromDbById()` уже корректно работает и не имеет собственных race condition (используется в `saveToDb()` для загрузки savedSong, проверено в production на 18k+ песен).
- Параллельные процессы, обновляющие поля песни (KEY_BPM_FROM_FILE, DEMUCS2, SHEETSAGE, и т.д.), делают это через свой собственный экземпляр `Song` и `saveToDb()` — это уже работающий паттерн, который не должен быть изменён.
- Поведение `applyDuplicateOriginal` (ApiController.kt:5415) проверяется отдельно в рамках реализации фикса (FR-002). Если эта функция также делает `saveToDb()` — для неё применяется тот же паттерн перезагрузки; если нет — не трогаем.
