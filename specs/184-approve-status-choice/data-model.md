# Phase 1 — Data Model: выбор статуса песни при апруве задания (5 или 6)

**Feature**: [spec.md](./spec.md) | **Plan**: [plan.md](./plan.md) | **Research**: [research.md](./research.md)

**Изменений схемы БД нет.** Ни одной новой таблицы, колонки, индекса или миграции
(см. research D-8). Ниже — сущности, которых касается фича, и правила переходов,
которые фиксирует эта спека.

---

## 1. `Song` (`tbl_songs`) — существующая, схема не меняется

| Поле | Тип (Kotlin / SQL) | Роль в фиче |
|---|---|---|
| `id` | `Long` / `bigint` | идентификация песни (`aRead.songId`) |
| `idStatus` | `Long` / `integer` (`SongField.ID_STATUS`) | **единственное изменяемое поле**; было — всегда `6`, теперь `5` или `6` по выбору админа |
| `newsAvailableAnnounced` | `Boolean` | НЕ трогаем: выставляется внутри `saveToDb()` → `markNewsAvailableIfReady()` только при `idStatus == 6L` (`Song.kt:5128`) |
| `newsPremiumPublishPending` | `Boolean` | НЕ трогаем: тот же гейт `idStatus == 6L` (`Song.kt:5143`) |
| `sourceMarkers*` / `sourceText*` | `String` | применяются из черновика при апруве — **независимо** от выбранного статуса |

### Правила перехода `idStatus` при апруве

Пусть `T` = запрошенный статус (`idStatus` параметр, `null` → `6`),
`C` = текущий `song.idStatus` до апрува.

| Условие | Действие | Результат `id_status` |
|---|---|---|
| `C < T` | `fields[ID_STATUS] = T` + `saveToDb()` | `T` |
| `C == T` | ничего (diff пуст) | `T` |
| `C > T` | ничего + лог `downgrade IGNORED` | `C` (не понижается) |

**Инварианты**:
- `INV-1`: апрув никогда не понижает `id_status` (следствие `if (C < T)`).
- `INV-2`: апрув никогда не выставляет значение вне `{5, 6}` — валидация `T ∈ {5,6}`
  выполняется до любых записей (`invalid_idstatus`, см. [contracts/approve-endpoint.md](./contracts/approve-endpoint.md)).
- `INV-3`: разметка (маркеры/текст/`.srt`) применяется при любом валидном `T` —
  выбор статуса не влияет на приёмку работы редактора.
- `INV-4`: `T = 5` ⇒ `newsAvailableAnnounced` и `newsPremiumPublishPending` не
  становятся `true` этим апрувом (следствие гейта `idStatus == 6L` в
  `markNewsAvailableIfReady`, research D-4) ⇒ новость не создаётся ни в LOCAL,
  ни на SERVER после push.

### Место `5` и `6` в 7-стадийном жизненном цикле (specs/022)

```text
0 … 3        4                 5                    6
│            │                 │                    │
проект       проект            маркеры проверены   ГОТОВА
создан/…     проверен          (маркеры одобрены,   (караоке-видео
                               видео НЕ рендерится, отрендерено,
                               НЕ публикуется)      доступно подписчикам)
                                    ▲                    ▲
                                    └── новый выбор ─────┘
                                        при апруве
```

## 2. `SongAssignment` (`tbl_song_assignments`) — существующая, схема не меняется

| Поле | Роль в фиче |
|---|---|
| `id` | параметр `id` эндпоинта `/approve` |
| `songId` | связь с `Song`, статус которой выбирается |
| `adminStatus` | `approved` после успешного апрува — **не зависит** от выбранного статуса песни |
| `reviewedAt`, `reviewComment` | как сейчас (`reviewComment` очищается) |

**Инварианты**:
- `INV-5`: `adminStatus = 'approved'` выставляется одинаково при `T = 5` и `T = 6`.
  «Одобрено в 5» — это НЕ отдельный статус задания (осознанно: иначе пришлось бы
  расширять `SongAssignmentStatus` и ломать sync/фильтры таблицы заданий).
- `INV-6`: идемпотентность (specs/094) сохраняется — если `adminStatus` уже
  `approved`, любой повторный вызов с любым `T` возвращает `already_approved`
  и НЕ меняет ни `id_status` песни, ни поля задания (короткое замыкание стоит
  ДО валидации и применения `T`).

### Отсутствующее по решению: история выбора

Колонка вида `tbl_song_assignments.approved_id_status` (для аудита «в каком статусе
одобрили») **не вводится** — spec Assumptions: «никаких дополнительных таблиц
аудита не вводится», журналирование через лог `[approve/feature-184]` достаточно
(US3). Если история понадобится — отдельная фича с миграцией + пересозданием
`recordhash`-триггера (constitution III).

## 3. UI-состояние `ReviewModal` (Vue, не персистится)

| Поле | Тип | Источник / дефолт | Роль |
|---|---|---|---|
| `selectedIdStatus` | `5 \| 6` | `data()`, дефолт `6` | выбор админа; сбрасывается в 6 при смене `a` (watcher — research D-7) |
| `songIdStatus` (computed) | `number \| null` | `a.idStatus` из ответа `/byId` (FR-011) | текущий статус песни; `null` — поле не пришло (старый бэкенд) |
| `canChooseIdStatus` (computed) | `boolean` | `songIdStatus === null \|\| songIdStatus < 5` | показывать radio (US2) |

**Правила отображения (US2)**:

| `songIdStatus` | Что показывается |
|---|---|
| `null` (поле отсутствует) | radio-group, default 6 (backward-compatible fallback, FR-007) |
| `0…4` | radio-group, default 6 |
| `5` | read-only бейдж «idStatus: 5 (маркеры проверены)» + подсказка «для перевода в 6 используйте SongEdit» |
| `>= 6` | read-only бейдж «idStatus: 6 (готово)» |

## 4. Побочные сущности, которых фича НЕ касается (зафиксировано намеренно)

| Сущность | Почему не меняется |
|---|---|
| `tbl_processes` (`RENDER_MP4_DEMO`) | процесс просто **не создаётся** при факт. статусе < 6; сам формат задачи и лейн (`threadId=0`, `prior=5`) не меняются |

| `SyncRegistry` | новых sync-сущностей нет |
| `KaraokeProperties` | новых настроек нет (выбор — разовое решение админа в UI, не глобальный дефолт) |
