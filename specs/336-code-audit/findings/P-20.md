## Сверки (спорное, без severity)

1. **`stats-zero-on-error` — зеркало уже заведённых записей.** `StatsByEvents` возвращает `0`/пустой список при `SQLException` и при `getConnection() == null`: `StatBySong.kt:224, 234–236, 431–440, 526–530, 563–564, 703–712` (и однотипно во всех методах). Это тот же механизм и то же семейство `stats`, что `BR-016` (`zero-cache-on-db-error:stats`, karaoke-web) и `BR-185` (`stats-zero-on-error:stats`, P-15, `MonetizationStats.kt`), поэтому **новая запись не заводилась**. Следствие здесь: `/api/stats/by-song|webevents|top-listened|top-users|by-type|by-detail` отдают `200` с нулями/пустым списком вместо `503` (контракт `StatsController.kt:26–33`), т.е. `DbOverloadBanner` не показывается. Прошу лида либо расширить локации `BR-185`, либо выдать отдельный BR (модуль другой — `karaoke-app`, а не karaoke-web).
2. **`StemJob.loadPendingCleanup` — N+1 с малым радиусом.** `ids.mapNotNull { getById(...) }` (`StemJob.kt:324`) выполняет отдельный `SELECT` на каждый id вместо одного `WHERE id IN (…)` (ADR-0001). Но `cleanup()` (`StemJobPollScheduler.kt:192–208`) идёт раз в 5 минут, а число просроченных/помеченных заданий обычно единицы, поэтому материального следствия не доказано — формальное нарушение правила без поведенческого ущерба.
3. **`Uuids` id = `hashCode()` ключа — возможны коллизии.** `id = listOf(typeName, voiceId, childId, elementId).hashCode()` (`karaoke-app/.../Uuids.kt:12`). Для ключей из трёх элементов (`elementId = -1`) хеш равен `const + 961*voiceId + 31*childId - 1`, т.е. `(voice 0, строка 31)` и `(voice 1, строка 0)` дают одинаковый id: у дуэтной песни длиннее 31 строки два разных продюсера получат один `uuid`. Последствие не доказано: `uuid` пишется в MLT-проект как идентификатор продюсера (`MltProp.kt:156–163`, `MkoMainBin.kt:216–219`), а рендер идёт через `melt` по `id`, не по `uuid`. Требует решения: это дефект (сломанный проект для kdenlive) или осознанное «глобальное» пространство имён.
4. **`Uuids.loadList` — интерполяция аргументов в SQL.** `where += "id=${args["id"]}"`, `where += "uuid = '${args["uuid"]}'"` (`Uuids.kt:112–113`) — при внешнем источнике аргументов это инъекция. Сейчас единственный вызов — `load(id)` с `Int.toString()` (`:156`), внешнего входа нет; отмечаю как defense-in-depth, не дефект.
5. **`SongVoiceLineElement.fontSize`: рассинхрон элемента и слогов.** Сеттер считает `valueWithCoeff` (0.75 для `COMMENT`), но присваивает `_fontSize = value`, а слогам раздаёт `valueWithCoeff`; строка `_fontSize = valueWithCoeff` закомментирована (`SongVoiceLineElement.kt:52–57`). Поэтому `h()`/`h(songVersion)` считают высоту по не масштабированному размеру, а `mltText()` рендерит масштабированный (`:94–101, 107–112`). Следствие — только геометрия комментария (высота слоя), данных не касается; рубрика § 2 исключает косметику UI, поэтому записи нет.
6. **`Subscription`: уникальность держится на контроллере, не на модели.** В `Subscription.kt` нет ни проверки, ни уникального ключа для `(site_user_id, scope, id_song)`; защита от повторной покупки — `isSubscribedToSong` в контроллерах перед `createNew` (`PublicSubscriptionController.kt:145`, `PublicCartController.kt:58,104`), т.е. тот же check-then-act, что P-20-04, но на денежном пути. Два параллельных клика «Купить» до вставки первого PAID-ряда могут дать две PENDING-записи и два платежа; проверить это в рамках порции нельзя (сценарий целиком в karaoke-web), поэтому — сверка, а не находка. `countPaid` (`Subscription.kt:276–291`) считает PAID-ряды, т.е. дубликат исказил бы и акцию NTH_FREE.
7. **`StemJob.loadAllWithUserInfo`: ошибка БД выглядит как «заданий нет».** `catch (e: SQLException) { println(...) }` и возврат частичного/пустого `result` (`StemJob.kt:259–262`) — админ-таблица «Минусовки» покажет пустой список без признака ошибки; та же ветка не логирует стек (ADR local-0005).
8. **`getWebEvents`: statement второго запроса не закрывается при исключении.** `st2`/`rs2` (`StatBySong.kt:312–322`) закрываются только в успешной ветке; исключение внутри цикла оставляет statement открытым до пересоздания thread-local соединения. Редкий путь, поэтому только сверка.
9. **`getSummary`: 11 последовательных скалярных запросов** (`StatBySong.kt:897–927`, каждый — новый `Statement` на том же соединении) на один загруз дашборда; кеш 60 с ограничивает частоту. Не дефект по рубрике (нет доказанного влияния), но кандидат на агрегацию одним запросом.
