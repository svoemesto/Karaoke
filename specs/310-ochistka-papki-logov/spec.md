## User Scenarios & Testing *(mandatory)*

### User Story 1 — Автоматическая очистка старых логов (Priority: P1)

Администратор Karaoke-сервера хочет, чтобы лог-файлы KaraokeProcess старше определённого возраста удалялись автоматически, без ручного вмешательства и без риска переполнения диска.

**Why this priority**: переполнение диска на сервере ломает production (не пишутся новые логи, не выполняются другие операции записи). Это блокирующий инцидент.

**Independent Test**: создать набор лог-файлов разного возраста в папке логов; запустить любой процесс, который записывает новый лог; проверить, что старые файлы исчезли.

**Acceptance Scenarios**:

1. **Given** папка логов содержит файлы возрастом 5, 20, 60 и 100 дней, **When** процесс записывает новый лог-файл, **Then** в папке остаются только файлы возрастом ≤ 30 дней; файлы 60 и 100 дней удалены; свежий лог-файл записан.
2. **Given** папка логов содержит только свежие файлы (≤ 30 дней), **When** процесс записывает новый лог, **Then** ничего не удаляется; новый файл появляется.
3. **Given** папка логов содержит файл, который залочен другим процессом, **When** процесс записывает новый лог, **Then** этот файл НЕ удаляется (ошибка логируется), остальные файлы удаляются штатно; новый лог записывается успешно.
4. **Given** папка логов пуста или не существует, **When** процесс записывает новый лог, **Then** процесс записи завершается успешно; отсутствие папки не считается ошибкой.

---

### User Story 2 — Сохранение свежести логов для отладки (Priority: P2)

Разработчик хочет, чтобы логи, которым меньше порога (30 дней), оставались доступны для диагностики недавних проблем; при этом совсем старые логи безболезненно исчезали.

**Why this priority**: качество диагностики, не блокирующее. Если порог слишком мал, логи исчезают до того, как разработчик успевает их посмотреть.

**Independent Test**: проверить, что лог-файлы возрастом 1, 5, 14 дней не удаляются при записи нового лога; файл возрастом 31 день удаляется.

**Acceptance Scenarios**:

1. **Given** лог-файл возрастом 14 дней, **When** процесс записывает новый лог, **Then** 14-дневный файл остаётся на диске.
2. **Given** лог-файл возрастом ровно 30 дней, **When** процесс записывает новый лог, **Then** этот файл удаляется (граница — strict >, файл с mtime == threshold удаляется).
3. **Given** лог-файл возрастом 31 день, **When** процесс записывает новый лог, **Then** файл удаляется.

---

### Edge Cases

- Что если в папке логов лежат файлы других типов (например, скрытые файлы, временные .tmp)? Спека ограничивает cleanup регулярными файлами; прочие объекты игнорируются.
- Что если mtime файла в будущем (clock skew, NFS-монтирование)? Такие файлы НЕ удаляются (защита от случайного стирания).
- Что если в папке логов тысячи файлов? Cleanup должен отрабатывать за разумное время (≤ несколько секунд), не блокировать основной процесс.
- Что если cleanup упал по любой причине? Запись нового лога должна пройти успешно — очистка НЕ блокирует основной pipeline.

## Functional Requirements

### FR-1 — Автоматическое удаление старых логов
Система автоматически удаляет лог-файлы в папке логов KaraokeProcess, возраст которых превышает **30 дней** (от текущего момента до `mtime` файла). Удаление происходит **в фоне при записи нового лога** — без внешних триггеров (cron, scheduled task).

### FR-2 — Только регулярные файлы логов
Удаляются **только** регулярные файлы (regular files). Подкаталоги, символические ссылки, сокеты, специальные файлы игнорируются.

### FR-3 — Защита от clock skew
Файлы с `mtime` в будущем (позже текущего момента) НЕ удаляются. Это защищает от случайного стирания при рассинхронизации часов или NFS-монтировании с чужого хоста.

### FR-4 — Fail-open
Если в процессе очистки возникает ошибка (например, файл залочен другим процессом, нет прав, нет места на диске), ошибка логируется, но **не блокирует запись нового лога**. Per-file ошибки изолируются — один залоченный файл не мешает удалению остальных.

### FR-5 — Отсутствие папки логов не считается ошибкой
Если папка логов не существует в момент очистки, операция завершается без ошибки. Это покрывает редкий сценарий первого запуска или ручной очистки папки администратором.

### FR-6 — Unit-тесты cleanup-логики
Создать новый test class `karaoke-app/src/test/kotlin/com/svoemesto/karaokeapp/KaraokeProcessCleanupTest.kt` с тестами, покрывающими:
- SC-2 (свежие логи ≤ 30 дней сохраняются, старые > 30 дней удаляются): файл с mtime = now − 25 дней остаётся, файл с mtime = now − 31 день удаляется.
- FR-3 (clock skew защита): файл с mtime в будущем (например, now + 1 час) не удаляется.
- FR-4 (fail-open, per-file isolation): один залоченный файл не мешает удалению остальных; все ошибки логируются через `println` в stderr.

Тесты используют JUnit 5 + `@TempDir`, проверяют через `Files.exists(path)`. Coverage SC-2, FR-3, FR-4 — обязательно.

## Success Criteria

### SC-1 — Диск не переполняется
При типичной нагрузке (100 процессов KaraokeProcess в день, каждый создаёт 1 лог-файл) папка логов не превышает 3000 файлов (100 процессов × 30 дней). Размер папки остаётся в пределах 100 МБ (при среднем размере файла 30 КБ).

### SC-2 — Свежие логи не теряются
Все лог-файлы возрастом ≤ 30 дней сохраняются при записи любого нового лога. Это подтверждается юнит-тестом: файл с mtime = now − 25 дней не удаляется; файл с mtime = now − 31 день удаляется.

### SC-3 — Запись нового лога не блокируется
100% записей новых логов завершаются успешно, даже если cleanup упал (залоченные файлы, permission denied, прочее). Измеряется через лог: 0 случаев «cleanup error» → 0 случаев «лог не записан».

### SC-4 — Cleanup отрабатывает за разумное время
Один цикл cleanup (при записи одного лога) обрабатывает 1000 файлов в папке за ≤ 1 секунды на типичном серверном железе.

## Assumptions

Зафиксированы reasonable defaults для неспецифицированных деталей work package #57:

- **Порог возраста (30 дней)**: industry-standard default для log rotation. Если администратор захочет другой порог — это будет отдельная спека с явным work package.
- **Триггер (при записи нового лога)**: отзывчиво и без внешних зависимостей. Не требует отдельного cron/daemon/scheduled task.
- **Fail-open поведение**: основной pipeline (запись логов) важнее побочной очистки. Ошибки очистки — побочный эффект, не блокер.
- **Только лог-файлы**: cleanup не трогает прочие объекты в папке (subdirs, symlinks, etc.) — это естественное ограничение для «cleanup логов».
- **Без runtime-конфигурируемости через env var**: согласовано с владельцем 2026-09-06. Изменение порога = релиз кода. (Урок спеки #309 v1 → v3: не выдумывать требования, которых нет в work package.)

## Out of Scope

Явно **не входит** в эту спеку:

- Runtime-конфигурируемость порога через env var (отдельная спека, если понадобится)
- Архивация логов в другое место (S3, NFS) перед удалением — отдельная фича
- Ротация/сжатие больших логов — отдельная фича
- Мониторинг/алерты на заполнение диска — отдельная инфраструктурная задача
- Log shipping в централизованный стек (ELK, Loki) — отдельная фича
- UI/CLI для управления очисткой вручную — нет в требованиях
