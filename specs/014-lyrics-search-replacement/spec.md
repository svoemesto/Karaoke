# Feature Specification: Замена поискового движка для поиска текстов песен

**Feature Branch**: `014-lyrics-search-replacement`

**Created**: 2026-07-27

**Status**: Draft

**Input**: User description: "Заменить поиск SearXNG на какой-нибудь другой - этот не справляется."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Пайплайн находит тексты песен там, где раньше находил мало или ничего (Priority: P1)

Оператор запускает импорт/обработку песни без готового текста. Система автоматически
ищет в вебе страницы с текстом песни (автор + название), скачивает и анализирует их
через LLM. Сегодня для заметной доли песен поисковый бэкенд (SearXNG) возвращает
слишком мало ссылок или вообще ничего, из-за чего песня остаётся без автоматически
найденного текста.

**Why this priority**: Это единственная причина всей задачи — без решения этой проблемы
замена бессмысленна. Напрямую влияет на долю песен, для которых текст находится
автоматически, а не вручную.

**Independent Test**: Прогнать набор запросов (автор + название), на которых текущий
SearXNG-бэкенд сегодня возвращает 0 или почти 0 ссылок, через новый бэкенд и убедиться,
что доля запросов с хотя бы одним полезным URL-кандидатом заметно выросла.

**Acceptance Scenarios**:

1. **Given** песня, для которой поиск через текущий бэкенд возвращал 0-1 URL,
   **When** пайплайн выполняет шаг поиска текста песни через новый бэкенд,
   **Then** возвращается заметно больше URL-кандидатов, пригодных для скрейпинга.
2. **Given** новый поисковый бэкенд недоступен или отвечает с ошибкой,
   **When** выполняется поиск,
   **Then** ошибка логируется, а вызывающему коду возвращается пустой список ссылок
   (пайплайн не падает и не блокируется), как и в текущей реализации.
3. **Given** новый поисковый бэкенд успешно отвечает,
   **When** выполняется поиск,
   **Then** запрос и ответ не выходят за пределы самостоятельно хостируемой
   инфраструктуры проекта (без обращения к платному/внешнему SaaS-поиску).

---

### User Story 2 - Смена бэкенда не требует правок в местах вызова (Priority: P2)

Существующие вызывающие места (`LyricsFinderService`, поток `getSearXNGSearch` в
`UtilsAI.kt`) продолжают работать без изменений: на входе — поисковый запрос строкой,
на выходе — список URL. Адрес нового поискового сервиса задаётся конфигурацией
(по аналогии с текущим `searxng.base-url`), а не зашивается в код.

**Why this priority**: Позволяет безопасно откатиться или снова сменить бэкенд в
будущем, не трогая логику скрейпинга и LLM-анализа, которая от источника ссылок не
зависит.

**Independent Test**: Указать в конфигурации адрес нового поискового бэкенда,
перезапустить приложение и убедиться, что поиск текстов песен использует именно его,
а остальной пайплайн (скрейпинг, LLM-анализ) не изменился и не потребовал правок.

**Acceptance Scenarios**:

1. **Given** в конфигурации приложения указан адрес нового поискового бэкенда,
   **When** приложение стартует и выполняет поиск текста песни,
   **Then** используется именно сконфигурированный бэкенд, без изменений кода вызывающих
   мест.

---

### Edge Cases

- Что происходит, если новый бэкенд тоже не находит ничего для конкретной песни (она
  реально плохо ищется в вебе)? Система должна вести себя так же, как сегодня: пустой
  список, песня остаётся доступной для повторного/ручного поиска, пайплайн не падает.
- Что происходит при временной недоступности нового бэкенда (сервис не поднят,
  перезапускается)? Ошибка логируется, возвращается пустой список — как и сегодня для
  SearXNG.
- Как ведёт себя поиск для запросов с не-русскими названиями/именами исполнителей?
  Не должен деградировать по сравнению с сегодняшним поведением SearXNG.
- Поиск обложек альбомов (`AlbumCoverService.searchSearxngImages`) не затрагивается —
  явно вне рамок этой задачи и продолжает использовать SearXNG без изменений.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система ДОЛЖНА заменить поисковый бэкенд, используемый для поиска
  ссылок с текстами песен (сегодня — SearXNG через `SearchTool.searchUrls`), на другой
  поисковый движок.
- **FR-002**: Новый поисковый бэкенд ДОЛЖЕН быть самостоятельно хостируемым
  (self-hosted) — без обращения к платным/внешним SaaS-поисковым API, чтобы сохранить
  принцип «self-contained автопайплайн» (см. `.specify/memory/constitution.md`,
  Principle I).
- **FR-003**: Для представительной выборки песен, на которых текущий бэкенд сегодня
  возвращает мало или ноль URL-кандидатов, новый бэкенд ДОЛЖЕН возвращать заметно
  больше пригодных для скрейпинга ссылок.
- **FR-004**: Интерфейс поиска для существующих вызывающих мест (вход — строка
  запроса, выход — список URL) ДОЛЖЕН остаться неизменным, чтобы `LyricsFinderService`
  и поток `getSearXNGSearch` (`UtilsAI.kt`) не требовали правок.
- **FR-005**: Адрес/точка подключения нового поискового бэкенда ДОЛЖЕН быть вынесен в
  конфигурацию (property/переменная окружения), а не зашит в код.
- **FR-006**: Система ДОЛЖНА логировать ошибки поиска (бэкенд недоступен, статус не
  200, таймаут) и возвращать пустой список вместо падения — сохраняя сегодняшнее
  защитное поведение.
- **FR-007**: Поиск обложек альбомов (`AlbumCoverService.searchSearxngImages` в
  `AlbumCoverFinder.kt`) ЯВНО вне рамок этой задачи и не изменяется — продолжает
  использовать SearXNG.

### Key Entities

Задача не вводит новых постоянных сущностей данных — заменяется только поисковый
бэкенд за существующим интерфейсом (запрос → список URL). Существующие сущности
(`SearchAsync`, `SearchResult`), в которые сохраняются результаты поиска, не меняют
структуру.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: На контрольной выборке песен, где текущий бэкенд сегодня возвращает 0-1
  URL, доля песен с хотя бы одним найденным URL-кандидатом после замены заметно
  выше, чем до замены.
- **SC-002**: Среднее число найденных URL-кандидатов на поисковый запрос по этой же
  выборке — выше, чем до замены.
- **SC-003**: Замена бэкенда не потребовала изменений в вызывающем коде — только
  изменение конфигурации (адреса бэкенда).
- **SC-004**: При недоступности нового поискового бэкенда пайплайн обработки песен не
  падает и не блокируется — ошибка видна в логах, песня остаётся в очереди для
  повторной попытки.
- **SC-005**: Поиск обложек альбомов продолжает работать через SearXNG без изменений
  и без регрессий.

## Assumptions

- Замена ограничена поиском текстов песен (`SearchTool.searchUrls` /
  `LyricsFinderService`); поиск обложек альбомов сознательно не трогаем в этой задаче
  (решение пользователя).
- Конкретный продукт-замена (какой именно самостоятельно хостируемый поисковый
  движок/мета-поисковик использовать) — техническое решение, которое принимается на
  этапе планирования (`/speckit-plan`), а не в этой спецификации.
- Основная проблема сегодняшнего SearXNG — малое количество или пустые результаты по
  многим запросам (не недоступность инстанса и не низкое качество/нерелевантность уже
  найденных ссылок).
- Методология и размер контрольной выборки запросов для измерения SC-001/SC-002
  (сколько песен, как отбираются «плохо ищущиеся» примеры) определяются на этапе
  планирования/тестирования.
- Конфигурация нового бэкенда организована по аналогии с текущим `searxng.base-url`
  (Spring `@Value`-property с дефолтным значением).
- Формат ответа нового бэкенда может отличаться от SearXNG JSON API — интеграционный
  код внутри `SearchTool`/аналога адаптирует его к списку URL; вызывающие места этого
  не видят (FR-004).
