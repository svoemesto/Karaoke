# Выборочный запуск CI-проверок по зонам интереса

> **Status**: active
> **Feature Key**: selective-ci-checks
> **Last Updated**: 2026-11-01

> **Профиль B** — второй профиль формата в SSoT Karaoke (наряду с профилем A —
> компонентом домена). Проверяется `tools/check-feature-doc.sh`, а не
> `tools/lint-knowledge.py`. Формат задан FR-009 (Constitution § VI).
> Шаблон: `knowledge/templates/product-feature.md`; индекс ветки —
> `knowledge/product/README.md`.

## Что делает

CI на каждый PR запускает **только те проверки, чья зона интереса затронута
правкой**. Правка документации не запускает сборку Kotlin и e2e; правка одного
фронтенда не запускает проверки второго; правка `deploy/` не запускает тесты
модулей.

При этом прогон оставляет **след**: агрегат `ci-summary` перечисляет, какие
проверки были применимы, а какие — **неприменимы** (и по каким зонам они не
применились). Пропущенная проверка не выглядит как «зелёная»: у неё нет
статуса «пройдена», у неё статус «неприменима».

## Зачем

Каждый полный прогон CI на этом проекте — это 8 тяжёлых исполнений (сборки
Kotlin, npm-сборки и тесты двух SPA, unit-тесты модулей, e2e) независимо от
содержания правки. По замеру на 170 прогонах (KARAOKE-373) PR, меняющий
только документацию, тратил 495.6 минуты занятости раннеров впустую, а среднее
wall-clock PR-гейта составляло 8.8 минуты.

Это влияет не только на скорость: пока тяжёлые джобы идут, очередь на merge
ждёт, а раннер занят. Правило выборочного запуска сокращает ожидание в типичных
правках и оставляет полный прогон там, где он действительно нужен — в страховых
прогонах по расписанию и при ручном требовании.

Фича **не** меняет состав проверок: те же guard'ы, тот же код возврата, тот же
смысл «проверка не выполнилась» (код 2) ≠ «нарушений нет».

## Как работает

1. Правило живёт в одном месте — манифест зон `config/ci/checks.yml`: для
   каждой CI-проверки указана её зона интереса (пути, которые она реально
   инспектирует) и доказательство зоны (`файл:строка`).
2. На каждый прогон CI первым идёт служебный джоб `changes`: он считает
   изменённые пути и публикует список применимых проверок.
3. Каждая проверка запускается только если её зона затронута. Если изменён
   путь, который не попал ни в одну зону, — запускается **полный набор**
   («сомнение → запуск»).
4. В конце прогона агрегат `ci-summary` собирает применимые и неприменимые
   проверки и их результаты в один статус.
5. Merge-гейт принимает решение **по агрегату**: все контексты `ci-summary`
   должны быть зелёными; ни одного такого контекста — отказ (значит, CI не
   отработал).

Пользовательский сценарий для автора PR: он ничего не настраивает — список
запущенных проверок виден в прогоне, а причины пропуска — в агрегате.

## Инварианты

1. **Правило одно.** Маппинг «правка → проверки» живёт только в манифесте;
   workflow, pre-commit и документация его не дублируют.
2. **Сомнение → запуск.** Неизвестный путь даёт полный набор проверок; смягчить
   это можно только словом владельца.
3. **Пропуск ≠ успех.** Неприменимая проверка не «зелёная»: след обязателен.
4. **История git не пропускается.** Проверка прямых коммитов в master
   выполняется всегда.
5. **Страховка есть.** Полный набор запускается по расписанию и по ручному
   требованию.
6. **Две копии CI-конфигурации не разъезжаются**: набор проверок и условия
   запуска в них идентичны, расхождение ловит гейт.
7. **Зоны измеримы**: у каждой зоны есть доказательство; мёртвая зона — ошибка.

## Известные ловушки

- **«Зона шире, чем чтение проверки».** Очевидное расширение зоны («нужно же
  ещё и это») делает таблицу зон размытой и правило перестаёт срабатывать.
  Зона = пути, по которым проверка способна вынести вердикт; остальное — в
  остаток (см. `known_unmapped`).
- **«Пропущенная проверка — значит, зелёная».** Forgejo не умеет статус
  `skipped`: джоб отдаётся как `success`. Поэтому решение принимает не по
  статус-чекам отдельных джобов, а по агрегату.
- **«Нашлось 30 статусов из 33 — значит, все зелёные».** Без параметра
  `limit` Forgejo отдаёт только часть выборки: красный контекст может не
  попасть в список. Сбор статус-чеков — постраничный, со сверкой
  `X-Total-Count`.
- **«Пересчёт применимости невозможен — значит, всё хорошо».** Нет: невозможный
  пересчёт — это отказ гейта, а не «зелёно».
- **«Файл правила лежит вне зон — значит, его правка ничего не запустит».**
  Файлы самого правила объявлены в `watch` служебных записей: их правка
  запускает полный набор.
