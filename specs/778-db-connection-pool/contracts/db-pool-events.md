# Contract: События наблюдаемости пула соединений

**Feature**: `specs/778-db-connection-pool/spec.md` | **План**: [plan.md](../plan.md)

События пишутся существующим механизмом `AppLog.warn(category, code, event, fields, error)` — тем же, что используют рейпер (`DB-REAP-001/002`) и ошибки подключения (`DB-CONNECT-001`). Формат — одна строка с `key=value`, разбирается существующим парсером журналов.

## События

### DB-POOL-002 — исчерпание пула

| Поле | Тип | Смысл |
|---|---|---|
| `target` | String | Роль БД: `LOCAL` / `SERVER` |
| `waiting` | Int | Потоков ждут слот |
| `busy` | Int | Слотов занято |
| `maxPoolSize` | Int | Потолок пула |
| `timeoutMs` | Long | Сколько ждали |

**Когда**: все слоты заняты дольше `acquire-timeout-ms` (5000) → ожидающий поток получает отказ.

**Зачем** (FR-008): отличить **отказ приложения** (пул исчерпан) от **отказа БД** (`DB-CONNECT-001`, `FATAL: sorry, too many clients already`). Разные коды → разная диагностика и разная реакция.

**Уровень**: WARN.

### DB-POOL-003 — долгое удержание handle

| Поле | Тип | Смысл |
|---|---|---|
| `target` | String | Роль БД |
| `heldMs` | Long | Сколько handle удерживается |
| `thresholdMs` | Long | Порог детектора |
| `thread` | String | Имя потока-владельца |
| `stack` | String | Стек вызовов места взятия handle (усечённый) |

**Когда**: handle взят и удерживается дольше порога детектора утечки.

**Зачем** (FR-009): показать **конкретное место в коде**, удерживающее соединение. Без этого пул лишь меняет симптом.

**Уровень**: WARN. **Действие не предпринимается** — событие наблюдательное: handle живого потока не отбирается (FR-012).

**Порог по умолчанию — 6 часов** (`karaoke.db.pool.leak-threshold-ms`), и за один
проход пишется не более **5** событий (остальные — сводной строкой
`db.pool.leak.summary`). Основание — замер на стенде 2026-11-15 (4 часа работы
пула): при пороге 15 минут детектор дал **1364 события**, и все они были от
**нормально живущих** потоков — под сохранённым ThreadLocal-контрактом (ADR-0009)
handle живого потока держится столько, сколько жив поток, и это норма, а не
утечка. Настоящий сигнал возврата аренд — `DB-POOL-004`.

### DB-POOL-004 — handle возвращён в пул рейпером

| Поле | Тип | Смысл |
|---|---|---|
| `target` | String | Роль БД |
| `returned` | Int | Сколько handle'ов возвращено |
| `ownerAlive` | Int | Сколько handle'ов у живых владельцев (не тронуто) |

**Когда**: рейпер прошёл по реестру и вернул handle'ы мёртвых владельцев.

**Зачем**: подтверждение, что механизм FR-003 работает — иначе пул исчерпается так же, как сегодня БД. Это **ключевая метрика** фичи: ненулевое значение означает, что возвращение по смерти потока происходит.

**Уровень**: WARN (только если `returned > 0`).

## Существующие события (сохраняются)

| Код | Событие | Отношение к пулу |
|---|---|---|
| `DB-CONNECT-001` | `db.connect.failed` | Отказ подключения к БД. **Отличается** от `DB-POOL-002` (отказ приложения) — это и есть различение FR-008 |
| `DB-REAP-001` | `db.reap.idle` | Уборка. В пуловом режиме — число возвращённых handle'ов; в режиме без пула — число закрытых каналов (прежнее поведение) |
| `DB-REAP-002` | `db.reap.failed` | Сбой уборки. Сохраняется |
| `DB-CLOSE-001` | `db.close.failed` | Сбой закрытия соединения. Сохраняется |
| `DB-CERT-001` | `db.cert.rejected` | Отказ по сертификату (спека 733). Сохраняется |

## Запрос наблюдаемости

| Что | Где |
|---|---|
| Всего физических каналов | `pg_stat_activity` в контейнере БД, группировка по `client_addr` |
| Занято/свободно/ожидают | метрики `HikariPoolMXBean` (через `PoolProvider`) |
| События пула | `docker logs <container> | grep "db.pool"` |
| Утечки | `docker logs <container> | grep "db.pool.leak"` |

## Критерий различения отказов

| Симптом | Код | Источник | Что делать |
|---|---|---|---|
| Сайт отдаёт 503, в логах БД нет ошибок | `DB-POOL-002` | приложение | увеличить `KARAOKE_DB_POOL_MAX_*` или найти держателя |
| Сайт отдаёт 503, в логах БД `too many clients` | `DB-CONNECT-001` | БД | увеличить `max_connections` **или** снять утечку |
| Соединения растут со временем, пул не исчерпан | — | утечка handle'ов | `DB-POOL-003` покажет место; проверить рейпер (`DB-POOL-004` = 0 → рейпер не работает) |
