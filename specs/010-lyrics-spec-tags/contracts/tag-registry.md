# Контракт: синтаксис спецтега и реестр тег→маркер

Этот документ — единственный источник правды для синтаксиса и семантики спецтегов. Он реализуется **независимо в ЧЕТЫРЁХ местах** — по аналогии с тем, как уже сегодня независимо дублируется логика слогоделения (`getSyllables`/`splitSyllables`/`split_text_into_words`) между всеми четырьмя:

1. **Backend** (Kotlin): `karaoke-app/.../model/SpecTags.kt` + `WhisperMarkerAligner.kt`. Полная реализация контракта (парсинг + реестр + алиасы → маркер).
2. **Admin-редактор** (Vue/JS): `webvue3/src/components/Songs/edit/SubsEdit.vue` (`getSyllables`/`getProcessedSourceText`, зона слогоделения). Полная реализация (+ кнопки быстрой вставки, FR-011).
3. **Публичный краудсорсинг-редактор** (Vue/JS): `karaoke-public/src/composables/useKaraokeEditor.js` (`splitSyllables` — "точная копия `getSyllables` из `SubsEdit.vue`", см. комментарий в файле) + `karaoke-public/src/views/EditorWorkView.vue`. Полная реализация (+ кнопки быстрой вставки).

   ⚠️ **Легко забыть при следующих изменениях этого контракта.** Задание, открываемое волонтёром в `EditorWorkView.vue`, — это прямая копия официального `sourceText` песни из `tbl_settings` (см. `PublicSongEditorController.kt` — чистый passthrough, сам не парсит текст). Значит текст задания **уже может содержать спецтеги**, расставленные админом в `webvue3`, даже если волонтёр их никогда не печатал сам. `karaoke-web`/`PublicSongEditorController.kt` при этом не нужно менять — он только сохраняет/читает `sourceText`+`SourceMarker` как непрозрачный JSON, слогоделение не выполняет.

4. **Форс-алаймент сервис** (Python, `alignment-ml/syllables.py`, функция `split_text_into_words`, вызывается из `align.py`/`serve.py` за HTTP `AlignmentServiceClient`-ом при клике "Точные маркеры" в `SubsEdit.vue`). **ЧАСТИЧНАЯ реализация** — этому месту НЕ нужен реестр/алиасы (он не строит маркеры, только тайминг слогов по словам), но оно **ОБЯЗАНО** согласованно с местом 1 решать "пуста ли строка после снятия тегов", иначе итоговое число слогов, которое возвращает `align_syllables`, не совпадёт с тем, что даёт `WhisperMarkerAligner.buildTargetWords` — и `buildMarkersFromSyllableTimes` вернёт `null` (в UI это видно как "Число слогов в тексте не совпало с результатами выравнивания (внутренняя ошибка)"). Обнаружено постфактум — пользователь буквально воспроизвёл эту ошибку на реальном тексте с тегами уже после того, как места 1-3 были реализованы и задеплоены.

Все четыре реализации ДОЛЖНЫ согласованно распознавать границы тега на одном и том же тексте (для мест 1-3 — идентичный итоговый маркер; для места 4 — идентичное число/границы "слов", даже без знания реестра) — расхождение — это баг. **При правке этого контракта — грамматики, реестра или набора алиасов — искать и обновлять все четыре места**, не только backend+фронтенды (история этой фичи: первая версия затронула только 1-2; третье место (`karaoke-public`) нашлось по прямому вопросу пользователя; четвёртое (`alignment-ml`) — по реальной ошибке в проде "Точные маркеры" уже после деплоя первых трёх).

**Практический чек-лист "я меняю грамматику/реестр тегов" — где искать все места**:
- `grep -rn "SPEC_TAG_REGEX\|SpecTags\b" karaoke-app webvue3 karaoke-public` — места 1-3 (Kotlin/JS).
- `grep -rn "_SPEC_TAG_RE\|_strip_spec_tags" alignment-ml` — место 4 (Python).
- Если меняется именно ГРАММАТИКА (не реестр/алиасы) — обновить регэксп во всех четырёх; если меняется только реестр/алиасы — местам 2 и 4 (webvue3-подобная строгая копия реестра нужна только местам 1-3; месту 4 реестр не нужен вообще, только грамматика).

## Грамматика

```
tag       := "~" name [ ":" value ] "~"
name      := \p{L}+                  ; одна или более Unicode-букв (латиница и/или кириллица)
value     := [^~]*                   ; любые символы, кроме "~", до закрывающей тильды
```

Регекс-реализация (референс): `~(\p{L}+)(?::([^~]*))?~`

Сопоставление `name` с реестром/алиасами — **регистронезависимое** (`Куплет`, `куплет`, `КУПЛЕТ` — одно и то же имя; сравнение по нижнему регистру).

**Область применения**: тег распознаётся только тогда, когда он — единственное содержимое строки после `trim()` (т.е. `line.trim() == "~имя~"` или `line.trim() == "~имя:значение~"`). Тег внутри строки, где есть ещё какой-либо другой текст, не распознаётся этой версией контракта — строка обрабатывается как обычная строка лирики (тег остаётся видимым как обычный текст, никак не обрабатывается).

**Несколько тегов на границе**: несколько последовательных строк, каждая из которых содержит один тег, между двумя строками с реальной лирикой — все теги применяются, каждый даёт свой маркер, в порядке следования строк.

## Реестр v1

| Тег | Значение | Валидация значения | `Markertype` | `label` итогового `SourceMarker` |
|---|---|---|---|---|
| `newline` | нет (без значения) | значение не ожидается; если указано — тег не распознан | `NEWLINE` | `""` |
| `group` | обязательное, целое число | целое число в диапазоне, уже используемом ручными group-маркерами в `SubsEdit.vue` (см. текущие `GROUP|0`..`GROUP|4`); нецелое/вне диапазона → тег не распознан | `SETTING` | `"GROUP|<значение>"` |
| `comment` | обязательное, произвольный текст | непустая строка после `trim()`; пустая → тег не распознан | `SETTING` | `"COMMENT|<значение>"` |

Время маркера при авто-разметке вычисляется так же, как сегодня для `NEWLINE` — интерполяцией между концом предыдущей строки и началом следующей (см. `newLineMarkerTime`, `WhisperMarkerAligner.kt:539-549`), независимо от того, какой конкретно тег/маркер вставляется на этой границе.

## Алиасы v1

Алиас — тег без значения, чьё имя резолвится в конкретную параметризованную форму базового тега из таблицы выше. Алиас и его целевая форма ДОЛЖНЫ давать идентичный `markertype`+`label` (это существенно для дедупликации, см. «Инварианты» ниже).

| Алиас | Эквивалентен | `Markertype` | `label` |
|---|---|---|---|
| `Куплет` | `group:0` | `SETTING` | `"GROUP\|0"` |
| `Припев` | `group:1` | `SETTING` | `"GROUP\|1"` |
| `Бридж` | `group:2` | `SETTING` | `"GROUP\|2"` |
| `Приговор` | `group:3` | `SETTING` | `"GROUP\|3"` |

Для `group:4` алиаса в v1 нет — доступен только через числовую форму `~group:4~`.

**Алиас не принимает значение** — `~Куплет:2~` не распознаётся как валидный тег (обрабатывается как нераспознанный, см. ниже), даже если `"Куплет"` сам по себе есть в таблице алиасов.

## Поведение при нераспознанном теге

Имя тега не входит в таблицу выше, ИЛИ значение не проходит валидацию для своего имени → тег **не распознан**:

- Строка обрабатывается как обычная (не как отсутствие текста) — если это была единственная содержимая строки, она даёт то же поведение, что обычная пустая строка (маркер `NEWLINE` по умолчанию при авто-разметке; никакого автодобавления при ручном пересчёте, если такого маркера ещё нет — ручной пересчёт не создаёт `NEWLINE` из простой пустой строки, только из явного `~newline~`, см. Edge Cases в `spec.md`).
- Никаких исключений/ошибок процесса разметки/форс-алаймента.

## Инварианты, которые обе реализации ДОЛЖНЫ соблюдать

1. Отсутствие тегов в тексте → идентичный существующему (до этой фичи) результат.
2. Распознанный тег без соответствующего маркера на этой позиции → маркер добавляется.
3. Распознанный тег с уже существующим на этой позиции маркером (того же `markertype`+`label`) → дубликат не создаётся.
4. Существующий маркер без соответствующего тега в тексте → маркер не изменяется и не удаляется.
5. Тег невидим для сопоставления с ASR/Whisper (не считается спетым словом/слогом).

## Расширение реестра (для будущих тегов и алиасов)

Новая строка базового реестра = (имя тега, правило валидации значения, целевой `Markertype`, функция построения `label`). Новая строка таблицы алиасов = (имя алиаса, имя целевого тега, фиксированное значение). Ни код распознавания границы строки (backend: гэп `lineIndex`; frontend: ординальный индекс слога), ни обработка уже существующих тегов/алиасов не должны меняться при добавлении новой записи.
