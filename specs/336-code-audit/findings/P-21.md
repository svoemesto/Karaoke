### P-21-01: karaoke-app/src/main/kotlin/com/svoemesto/karaokeapp/services/HealthReportBatchPool.kt:368–376 — LEAK (S2)
- Что не так: `wakeupWorkers()` и `wakeupWaitingWorkers()` при каждом `enqueue`/`enqueueWaiting` добавляют в `Executors.newFixedThreadPool` **новые** задачи `workerLoop()`, но сама задача — бесконечный цикл: при пустой очереди она не выходит, а спит 50 мс и продолжает (`continue`). Поэтому все 10 (и 20) потоков пула навсегда заняты первыми submit'ами из `start()`, а каждая последующая «побудка» кладёт 10 (20) новых задач в **неограниченную** очередь executor'а (`LinkedBlockingQueue`), которые никогда не будут выполнены. Очередь растёт детерминированно на каждой загрузке страницы «Песни» и на каждом WAITING-файле — до перезапуска процесса, без верхней границы.
- Доказательство:
  «`private fun wakeupWorkers() {` / `// 10 новых submit'ов: если worker уже работает — он возьмёт следующую` / `// песню сам; если простаивает — выполнит одну итерацию и снова уснёт.` / `repeat(POOL_SIZE) { executor.submit { workerLoop() } }` / `}`» (services/HealthReportBatchPool.kt:368–372, SHA 1977838a);
  «`if (id == null) {` / `    Thread.sleep(WORKER_IDLE_SLEEP_MS)` / `    continue` / `}`» (services/HealthReportBatchPool.kt:381–384).
- Путь: `POST /api/song/healthReportListBatch?songIds=…` (`ApiController.kt:7851–7860`) → `healthReportBatchPool.enqueue(ids)` → `wakeupWorkers()` (+10 задач в очередь executor'а); `waitingWorkerLoop()` после каждого файла → `enqueue(listOf(task.songId))` → снова +10; `enqueueWaiting(...)` → `wakeupWaitingWorkers()` (+20). Холодный кеш хранилища на странице из ~100 песен даёт сотни WAITING-задач, то есть тысячи так и не выполненных `FutureTask` за одну загрузку страницы.
- Поправка: запускать воркеры один раз (`@PostConstruct`) и будить их через `LinkedBlockingQueue`/`Semaphore`/`Condition`, а не submit'ом новых циклов; либо хранить в пуле только короткоживущие задачи, а не сам цикл. Дополнительно — контроль `executor.queue.size()` в метрике/логе.

### P-21-02: karaoke-app/src/main/kotlin/com/svoemesto/karaokeapp/propertiesfiledictionary/PropertiesFileDictionary.kt:25–31 — DATA (S2)

Параллельные `set()` из разных HTTP-потоков (фронт шлёт `/api/setwebvueprop` на каждое изменение фильтров) дают ту же порчу: два `writeText` по одному файлу без лока.

KDoc класса называет это осознанным («кэшируем и его, чтобы не долбить внешний сервис»), поэтому без severity: вопрос — намеренно ли негативный результат транзиентного сбоя хранится вечно, или его надо отличать от «страны нет» (например, `NULL`/`resolved_at` с TTL).

Это противоречит KDoc `KaraokeConnection.closeThreadConnection` («не вызывать из переиспользуемых потоков»), но одновременно делает JDBC-пинг честным; вопрос — намеренный churn или нет.
