# Feature Specification: Self-Assign Tasks для редакторов с флагом

**Feature Branch**: `182-editor-self-assign-tasks`
**Created**: 2026-08-13
**Status**: Draft
**Input**: User description: "Задача - есть роль пользователь-редактор. Надо сделать, чтобы дополнительно к этом для таких пользователей можно было устанавливать признак 'Может сам назначать себе задания'. Тогда этот пользователь в закромах должен иметь возможность взять себе в работу любую ещё не готовую песню (которую ещё никто не взял в работу)"

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Управление флагом «Может сам назначать себе задания» (Priority: P1)

Администратор открывает карточку пользователя-редактора (`{Имя Фамилия}` с включённым `isEditor`) в публичной админке (`webvue3 → SiteUsers → SiteUserEdit`) и включает галочку «Может сам назначать себе задания». После сохранения флаг сохраняется в `tbl_site_users` и виден в общем списке пользователей в колонке «Права редактора».

**Why this priority**: Без этой возможности ни одна другая история не имеет смысла — флаг является гейтом ко всей функциональности.

**Independent Test**: Зайти в `webvue3 → SiteUsers`, открыть редактора, включить флаг, сохранить, перезагрузить, убедиться что галочка включена. Открыть того же пользователя на сервере через `psql` — поле установлено.

**Acceptance Scenarios**:
1. **Given** админ в карточке редактора, флаг выключен; **When** админ включает флаг и сохраняет; **Then** поле `can_self_assign_tasks` в `tbl_site_users` = `true`, ответ API возвращает обновлённую запись с `canSelfAssignTasks: true`.
2. **Given** флаг включён; **When** админ снимает флаг и сохраняет; **Then** поле становится `false`, все ранее взятые self-assign задания остаются у редактора (откат не лишает уже-взятых заданий).
3. **Given** пользователь НЕ редактор (`isEditor=false`); **When** админ открывает его карточку; **Then** поле «Может сам назначать себе задания» либо скрыто, либо disabled с подсказкой «Сначала включите роль редактора».

---

### User Story 2 — Редактор с флагом берёт свободную песню в «Закромах» (Priority: P1)

Залогиненный редактор с включённым флагом «Может сам назначать себе задания» открывает публичную страницу исполнителя (`/zakroma/...` → `ZakromaView` или её классический аналог `ZakromaViewClassic`). В карточках альбомов, рядом с названием каждой **свободной** песни (по которой в `tbl_song_assignments` нет ни одной записи), отображается кнопка «Взять в работу». После клика создаётся назначение в `tbl_song_assignments` (assignee_id = id редактора, status = `assigned`), песня исчезает из списка «свободных», появляется в «Моих заданиях» (`/editor/work`), UI подтверждает успех («Задание взято в работу — перейдите в Мои задания»).

**Why this priority**: Это основная бизнес-ценность фичи — самостоятельность активных редакторов, снижение нагрузки на админов.

**Independent Test**: Залогиниться двумя разными редакторами с флагом. Открыть одного и того же автора. Каждый кликает «Взять в работу» на разных песнях — оба получают задание, обе песни исчезают из «свободных». Зайти третьим — он не видит кнопку на этих песнях.

**Acceptance Scenarios**:
1. **Given** редактор с флагом открыл «Закрома» автора, у которого есть свободные песни; **When** он нажимает «Взять в работу» на одной из них; **Then** через ≤2 сек в `tbl_song_assignments` появилась запись (assignee_id = этот редактор, status = `assigned`), UI показывает подтверждение, песня исчезает из «свободных» в этой же сессии.
2. **Given** редактор без флага; **When** он открывает «Закрома» автора; **Then** кнопки «Взять в работу» не отображаются ни на одной песне.
3. **Given** анонимный посетитель (не залогинен); **When** он открывает «Закрома»; **Then** кнопки «Взять в работу» не отображаются (это видно только залогиненным редакторам с флагом).
4. **Given** песня, на которой уже есть любое назначение (assigned/in_progress/submitted/approved/rejected); **When** залогиненный редактор с флагом открывает «Закрома»; **Then** кнопка «Взять в работу» на этой песне НЕ отображается (песня занята).
5. **Given** редактор с флагом уже нажал «Взять в работу» и получил задание; **When** он перезагружает «Закрома» того же автора; **Then** песня остаётся в списке, но кнопка «Взять в работу» заменяется на «Открыть задание» (ведёт в `EditorWorkView` для этой песни), чтобы редактор получил обратную связь «я уже работаю с этой песней».

### User Story 3 — Защита от гонок и валидация (Priority: P2)

Два редактора с флагом одновременно нажали «Взять в работу» на одну и ту же песню (например, у одного интернет тормозит и повторный клик после таймаута). Система отдаёт задание только одному — победителю по принципу «кто первый пришёл в БД» — второй получает ошибку «Уже занято» (HTTP 409, error code `song_already_taken`), UI показывает сообщение и автоматически убирает кнопку с этой песни.

**Why this priority**: Без защиты гонок два редактора будут работать над одной и той же песней, конфликт правок потеряется при первом approve. Это производственный риск.

**Independent Test**: Открыть в двух браузерах/инкогнито одну и ту же песню, войти под разными редакторами с флагом, кликнуть одновременно. Только один получает 200, второй — 409. Проверить в `tbl_song_assignments` — ровно одна запись.

**Acceptance Scenarios**:
1. **Given** два редактора с флагом кликнули «Взять в работу» на одну песню в пределах 1 секунды; **When** оба запроса дошли до бэкенда; **Then** только один получает 200 и создание задания, второй получает 409 `song_already_taken`, в `tbl_song_assignments` ровно одна запись.
2. **Given** редактор кликнул «Взять в работу» и получил таймаут; **When** он кликает повторно; **Then** получает 409 `song_already_taken` (т.к. первая попытка уже создала задание) и UI говорит «Вы уже взяли эту песню — проверьте Мои задания».

---

### User Story 4 — Self-assign виден в админке как обычное задание (Priority: P3)

Админ в `webvue3 → SongsTable` видит, что у песни теперь есть назначение (assignee = редактор, взявший через «Закрома») и может работать с ним стандартным образом: смотреть draft, approve/reject, открывать ревью. Т.е. self-assign задание ничем не отличается от назначенного админом.

**Why this priority**: Это обеспечивает целостность процесса — админ не должен догадываться, какие задания взяты «официально», а какие «самостоятельно».

**Independent Test**: После self-assign зайти в `webvue3 → SongsTable`, найти эту песню, увидеть стандартный бейдж «Назначено» / «В работе», открыть на ревью, approve — работает.

**Acceptance Scenarios**:
1. **Given** редактор взял песню через «Закрома»; **When** админ открывает `SongsTable`; **Then** в колонке «Статус задания» песня показывает «Назначено» (или «В работе», если редактор уже начал), assignee виден в дропдауне.
2. **Given** админ одобряет self-assign задание; **When** он смотрит результат; **Then** draft применён к `tbl_songs` точно так же, как при задании через админский `assign`.

---

### Edge Cases

- Что если редактор с флагом уже имеет 5 (или N) активных заданий — должен ли self-assign иметь лимит? **Default**: без лимита, лимит устанавливается отдельным правилом (если потребуется — отдельной фичей).
- Что если редактор нажал «Взять в работу» на песню, а в момент нажатия другой админ уже назначил эту песню ему же в `SongsTable`? **Default**: идемпотентно — если у этой песни уже есть задание на этого же редактора, второй клик возвращает 200 «уже ваше», а не 409.
- Что если песня была «свободной» по логике `canSelfAssign=true`, но админ прямо сейчас удалил её (или поменял `isSkip`)? **Default**: запрос упадёт с 404/410, UI просто скроет кнопку при следующей загрузке, повторный клик пользователь не успеет сделать.
- Что если редактор сам себе «снимает» задание (recall) — снова ли доступна кнопка «Взять в работу»? **Default**: да, если он recall'ит собственное задание, песня становится «свободной» для повторного self-assign.
- Что если редактор без флага каким-то образом узнал ID песни и позвал API напрямую? **Default**: бэкенд возвращает 403 `forbidden_not_self_assign_editor`, фронт этот сценарий не обрабатывает (нужно для безопасности).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: В таблице `tbl_site_users` MUST быть добавлено поле `can_self_assign_tasks BOOLEAN NOT NULL DEFAULT FALSE`. Поле — атрибут пользователя, не зависит от `isEditor` (формально флаг может быть включён и у не-редактора, но UI его прячет).
- **FR-002**: Поле MUST быть отражено в `SiteUser` модели (`canSelfAssignTasks: Boolean`), в `SiteUserDto` c аннотацией `@get:JsonProperty("canSelfAssignTasks")` (см. AGENTS.md, Q&A «Jackson отбрасывает is» — но тут имя без `is`-префикса, просто явно фиксируем JSON-имя).
- **FR-003**: В `SiteUsersController.update` MUST быть принят параметр `canSelfAssignTasks: Boolean?` (по аналогии с `isEditor`). При `null` — не трогать, при `true`/`false` — установить.
- **FR-004**: В `SiteUserEdit.vue` (webvue3) MUST быть чекбокс «Может сам назначать себе задания» в секции прав редактора. Чекбокс видим только если `isEditor=true`, иначе disabled+tooltip «Сначала включите роль редактора». Изменения MUST коммититься через `saveSiteUser` action (поле `canSelfAssignTasks`).
- **FR-005**: На бэкенде MUST быть реализован эндпоинт `POST /api/public/songeditor/assign-self` (в `PublicSongEditorController`), принимающий `songId: Long` и возвращающий либо `SongAssignmentDto` созданного задания, либо ошибку:
  - `400` если `songId` невалиден
  - `403` `forbidden_not_editor` если пользователь не редактор
  - `403` `forbidden_not_self_assign_editor` если `isEditor=true` но `canSelfAssignTasks=false`
  - `404` `song_not_found` если песня не найдена
  - `409` `song_already_taken` если по песне уже есть задание от другого пользователя
  - `200 OK` с телом существующего `SongAssignmentDto` (идемпотентность) если у этого же редактора уже есть активное задание на эту песню — фронт показывает toast «Эта песня уже у вас»
- **FR-006**: Эндпоинт MUST создавать `SongAssignment` атомарно: внутри одной БД-транзакции проверить `SELECT ... FOR UPDATE` (или эквивалент) на отсутствие существующих заданий по этой песне, и если записей нет — вставить новую с `assignee_id = currentSiteUser.id`, `song_id`, `status = 'assigned'`, `created_at = now()`. При наличии чужого задания — `409 song_already_taken`.
- **FR-007**: В `karaoke-public` MUST быть расширен `ZakromaView` (или создан отдельный блок внутри него): для залогиненного пользователя с `isEditor=true` AND `canSelfAssignTasks=true` в state должен быть флаг `isSelfAssignEditor`, и UI MUST отображать кнопку «Взять в работу» **внутри карточки каждой «свободной» песни** в карточке альбома (рядом с названием песни, не в отдельной плашке/таблице). Видимость кнопки определяется полем `assignment === null` (см. FR-008). Для не-залогиненных и редакторов без флага кнопка не рендерится вообще. Логика отображения для уже взятой самим редактором песни: если `assignment` существует И `assignment.assigneeId === currentUser.id`, кнопка «Взять в работу» заменяется на «Открыть задание» (клик ведёт в `EditorWorkView` для этой песни). После успешного нажатия — UI локально убирает песню из списка (оптимистично) и показывает toast «Задание взято».
- **FR-008**: В стрим `/api/public/zakroma` MUST быть встроено поле `assignment: SongAssignmentBriefDto?` (nullable; `null` = «свободная песня»). Поле возвращается **только** залогиненным self-assign-редакторам (`isEditor=true AND canSelfAssignTasks=true`); для всех остальных пользователей (анонимы, обычные редакторы, не-редакторы) поле должно быть `null` или отсутствовать в payload, чтобы не нагружать БД на чужих сценариях. Поле MUST заполняться на бэкенде одним SQL JOIN (`tbl_song_assignments` по `song_id`) в рамках существующего стрима — никакого второго round-trip на фронте.
- **FR-009**: При self-assign MUST НЕ создаваться `SongAssignmentDraft` — он создаётся только когда редактор начнёт работу (нажатием «Открыть задание» в `EditorWorkView`). До этого момента в `tbl_song_assignment_drafts` записей нет.
- **FR-010**: Все API-эндпоинты MUST быть защищены `SiteAuthInterceptor` (как уже реализовано в `PublicSongEditorController`). Логика проверки прав — внутри контроллера, не в interceptor.

### Key Entities *(include if feature involves data)*

- **SiteUser**: расширяется новым полем `canSelfAssignTasks: Boolean` (default `false`). Логически — флаг «может ли редактор самостоятельно назначать себе задания»; ортогонален `isEditor` (редактор без флага — обычная роль, с флагом — самостоятельный).
- **SongAssignment**: уже существующая сущность, переиспользуется без изменений схемы. Создаётся через тот же путь, что и админский assign. Поля: `songId`, `assigneeId`, `status = 'assigned'`, `createdAt`.
- **ZakromaPublicDto / ZakromaAlbumSongPublicDto**: расширяется полем `assignment: SongAssignmentBriefDto?` (nullable; null = «свободная песня»). Эндпоинт стрима `/api/public/zakroma` начинает возвращать это поле для self-assign-редакторов (для остальных пользователей — null, чтобы лишний раз не нагружать БД).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Редактор с флагом может превратить любую «свободную» песню в свою задачу за ≤3 клика (открыть «Закрома» → найти песню → «Взять в работу»), при условии что «Закрома» этого автора уже загружены.
- **SC-002**: 100% «свободных» песен, отображаемых в «Закрома» для редактора с флагом, можно взять в работу (UI показывает кнопку «Взять в работу» без скрытых подвохов, кроме гонок с другим редактором).
- **SC-003**: 0 случаев двойного назначения одной песни двум редакторам (race condition) — проверено через одновременные клики в двух браузерах.
- **SC-004**: Self-assign задание, открытое через «Мои задания», функционально идентично админскому: редактор может перейти в редактор, edits сохраняются в draft, submit работает, approve применяет правки. Проверено ручным сценарием.
- **SC-005**: Включение/выключение флага в `SiteUserEdit` отражается в БД за ≤2 сек, и в следующей загрузке «Закрома» флаг учитывается (кнопка появляется/пропадает).
- **SC-006**: Редактор без флага НЕ видит кнопку «Взять в работу» ни на одной странице (проверено отрицательным сценарием).

## Assumptions

- Пользователь с ролью «редактор» (`isEditor=true`) уже существует в системе как сущность, флаг `canSelfAssignTasks` — это дополнительный атрибут поверх существующего `isEditor`.
- «Закрома» в контексте пользователя — это публичный каталог по автору (`/zakroma/...`), а НЕ админка `SongsTable`. Self-assign доступен только там.
- Админские пути назначения (через `AssignModal` в `SongsTable`) остаются без изменений — флаг только расширяет возможности, не заменяет существующий flow.
- Лимит на количество активных заданий у одного редактора не вводится в этом раунде (если потребуется — отдельная фича).
- Эндпоинт `POST /api/public/songeditor/assign-self` пишет в LOCAL базу (как и другие редакторские endpoints через `WORKING_DATABASE`); для sync между LOCAL↔SERVER задания уже участвуют в `SyncRegistry` (проверить на этапе plan).
- «Свободная песня» определяется строго: в `tbl_song_assignments` нет ни одной записи по этому `song_id` (включая `approved`/`rejected`). История approve/reject не блокирует повторное self-assign.
- Поле `canSelfAssignTasks` — это именно «может назначать себе», а не «может назначать другим». Назначение другим редакторам по-прежнему доступно только админам из `AssignModal`.
- Все новые API-эндпоинты следуют установившемуся контракту (JSON-имена, error codes, защита `SiteAuthInterceptor`).
- Допускается, что до реализации FR-008 (дозагрузка assignment-статуса) фронт может временно использовать существующий эндпоинт `/api/public/zakroma` без assignment-поля — кнопка показывается по «есть ли вообще запись в tasks», а точная проверка гонки происходит на бэкенде при клике.

## Clarifications

### Session 2026-08-13

- Q: Какой API-стратегии следовать для дозагрузки assignment-статуса в «Закрома»? → A: Встроить поле `assignment` в существующий стрим `/api/public/zakroma` (nullable, заполняется только для self-assign-редакторов, остальным не отдаётся). Применено в FR-008 и ZakromaPublicDto. **ПЕРЕСМОТРЕНО (Pass 51-2)**: стрим `/api/public/zakroma` НЕ ИЗМЕНЁН. Вместо этого поле `assignment` добавлено в `/api/public/song/{id}` (SongPublicDto) — это лучше отражает, что кнопка живёт на странице конкретной песни, а не в каталоге.
- Q: Что возвращать при попытке self-assign песни, которая уже у этого же редактора? → A: 200 OK с телом существующего `SongAssignmentDto` (идемпотентно). Применено в FR-005 (заменена пара «409/200» на однозначное поведение).
- Q: Где именно в `ZakromaView` показывать кнопку «Взять в работу»? → A: Внутри карточки каждой песни в карточке альбома (вариант B). Применено в US2 + FR-007. **ПЕРЕСМОТРЕНО (Pass 51-2)**: колонка с кнопкой визуально перегружала компактную таблицу (16+ треков × 4 иконки = перегруз). Кнопка ПЕРЕНЕСЕНА на страницу конкретной песни `/song/{id}` (SongView), в секцию `km-meta-actions` (рядом с Share/Favorite). Тот же сценарий, просто другое место — редактор переходит с Закромов → клик на песню → видит кнопку.
- Q: Что показывать для песни, которая уже у этого же редактора в активном задании? → A: Песня остаётся в списке, кнопка меняется на «Открыть задание» (вариант A). Применено в US2.5 + FR-007. **ПЕРЕСМОТРЕНО (Pass 51-2)**: на странице `/song/{id}` то же самое — `showOpenAssignmentButton` показывает «Открыть задание» если `currentSong.assignment.assigneeId === userId`.
- Q: Входит ли «управление флагом в карточке пользователя» (`SiteUserEdit`) в P1-scope, чтобы не потеряться при разбиении на PR? → A: Да, US1 + FR-001/FR-002/FR-003/FR-004 + SC-005 — это **P1 acceptance gate**: без работающего UI-переключателя флага в `SiteUserEdit` фича бессмысленна (нет способа включить флаг → ни одна self-assign кнопка не появится). US1 MUST решаться в том же PR/наборе коммитов, что и backend FR-001/FR-008, иначе фича неработоспособна.
