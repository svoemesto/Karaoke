# Local ADR-0017: Выборочный запуск CI-проверок по зонам интереса

* **Status**: Accepted
* **Date**: 2026-11-01
* **Deciders**: владелец Karaoke (спека 692, issue KARAOKE-363, карта решений KARAOKE-364)

> **Note**: this is a **local** ADR — describes a specific subsystem
> convention (vs global ADR-0001..0008 which describe project-wide decisions).

## Context

Каждый PR прогонял полный набор CI: 8 тяжёлых исполнений (сборки Kotlin, npm-сборки
и тесты двух SPA, unit-тесты модулей, e2e) независимо от того, что правка вообще
затронула. Замер по 170 прогонам (KARAOKE-373, `baseline-metrics.md`) показал:

- PR, меняющий только документацию (15.3 % прогонов), запускал все тяжёлые
  проверки: 495.6 минут занятости раннеров на пустую работу;
- PR, меняющий только инфраструктуру (30.6 %), — то же самое;
- среднее wall-clock PR-гейта — 8.8 минуты, суммарно 460.1 минуты на 52 прогона.

Цена понятна: каждая минута тяжёлого джоба — это минута, в течение которой
очередь на merge ждёт, а раннер `nsa-i9` занят.

При этом «просто не запускать тяжёлое, если правка его не касается» в лоб не
работает: зона интереса проверки — это её **реальный предмет**, а не каталог
«на всякий случай». Проверка, которая обходит весь репозиторий, не имеет
единственной зоны: её результат зависит от всего, и любая правка потенциально
может её сломать.

## Решения владельца

- **Д-1**: правило живёт в **одном** месте — `config/ci/checks.yml`
  (манифест зон). Ни workflow, ни pre-commit не дублируют маппинг
  «правка → проверки».
- **Д-2**: зона проверки = пути, которые проверка **реально инспектирует**
  (по внутренним паттернам её реализации), а не то, что видно в строке `run:`.
  Проверка, способная вынести вердикт по всему репозиторию, не получает зону
  `**`: иначе таблица зон размывается и правило перестаёт срабатывать.
- **Д-3**: FR-004 остаётся **строгим**: изменённый путь вне объединения зон ⇒
  полный набор проверок («сомнение → запуск»). Смягчение правила — не решение
  инженера, а слово владельца.
- **Д-4**: зоны покрывают не всё: остаётся 125 tracked-файлов, которые не читает
  ни одна CI-проверка (IDE-конфигурация, `.specify/`, экспериментальный
  `alignment-ml/`, плагин DSH). Секция `known_unmapped` в манифесте — место,
  где такие пути перечисляются явно; **по умолчанию она пуста**, и тогда
  поведение строго по FR-004.
- **Д-5**: пропущенная проверка — это не «зелёная» проверка. Forgejo не умеет
  статус `skipped`: джоб отдаётся как `success` с описанием «Has been skipped».
  Единственный сигнал для решения — агрегат `ci-summary`.
- **Д-6**: проверка истории git (`check-direct-commits`) **не пропускается
  никогда**: она не про файлы, а про историю.
- **Д-7**: расписание и ручной полный прогон — страховка: раз в неделю и по
  требованию запускается весь набор.

## Decision

1. **Манифест зон** — `config/ci/checks.yml`: полный реестр job-id обеих копий
   CI-конфигурации (35 записей). Инвариант «джоб ↔ запись» тотальный, без
   списков исключений. У каждой записи с зонами — `evidence` вида `файл:строка`.
2. **Единая реализация правила** — `tools/ci-checks.py` (режимы
   `--emit-outputs`, `--summary`, `--list`, `--local`, `--self-test`).
3. **CI**: джоб `changes` считает применимые проверки и публикует их как
   outputs; каждая проверка запускается под условием
   `needs.changes.outputs.all == 'true' || needs.changes.outputs.<id> == 'true'`.
   Агрегат `ci-summary` (needs на все проверки, `if: always()`) — единственный
   сигнал для merge-гейта.
4. **Merge-гейт** (`tools/merge-pr.sh`) принимает решение по агрегату
   `ci-summary`, собирает статус-чеки постранично со сверкой `X-Total-Count`
   (без `limit` Forgejo отдаёт 30 контекстов из 33 — усечение скрыло бы
   красный контекст) и пересчитывает применимость правилом; если пересчёт
   невозможен — отказ, а не «зелёно».
5. **Согласованность** — `tools/check-ci-checks-manifest.sh`: джоб ↔ запись,
   идентичность `if:`/`needs:` между копиями, мёртвые зоны, `watch` без
   catch-all, `known_unmapped` без пересечений с зонами. Гейт зарегистрирован
   целиком (скрипт + джоб в обеих копиях + pre-commit-хук + `--self-test`).

## Rationale

* **Альтернатива «мягкий FR-004»** (неизвестный путь игнорировать): отклонена —
  это тихий обход гейта: дефект в зоне, которую никто не описал, проходит
  незамеченным.
* **Альтернатива «зона = каталог по имени»** (например, `backend/**` для всех
  backend-проверок): отклонена — тяжёлые сборки тогда никогда не пропускаются,
  и выигрыш исчезает.
* **Альтернатива «зона = то, что видно в `run:`»**: отклонена по фактам: у
  `check-recordhash-consistency.py` в `run:` нет ни одного пути, а он читает
  канонический дамп; у `check-secret-in-argv.sh` в `run:` тоже нет путей, а
  он обходит все tracked `*.sh`.
* **Альтернатива «правило в каждой копии workflow»**: отклонена — две копии
  разъедутся (сегодня это ловит `check-ci-workflow-sync.sh`).

## Consequences

1. **Запрет**: правило применимости не дублируется в workflow, pre-commit или
   компонентах — единственный носитель `config/ci/checks.yml` + `tools/ci-checks.py`.
2. **Инвариант**: список зон измерим — покрытие путей репозитория печатается
   гейтом, мёртвая зона — ошибка, `evidence` обязателен.
3. **Required Update**: изменение состава CI-проверок обязано менять манифест
   в том же PR, иначе `check-ci-checks-manifest.sh` красный.
4. **Измеримость**: `tools/measure-selective-ci.py` считает оба варианта
   (строгий FR-004 и с `known_unmapped`) одной командой — решение владельца
   опирается на пересчитываемые числа, а не на пересказ.
5. **Открытый вопрос (владелец)**: при строгом FR-004 на базовом окне выпадает
   80.8 % тяжёлых исполнений (база — 93.9 %), то есть критерий «≥90 %» не
   достигается; с явно перечисленными `known_unmapped` — 91.7 %. Спека не
   менялась: выбор между вариантами — за владельцем.
