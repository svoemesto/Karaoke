## Сверки

1. **`body` CustomConfirm из выделенного текста (5144, 5181).** `addWordToDict`/`removeWordFromDict` подставляют `selectedText.toLowerCase()` (текст выделения в `contenteditable`, то есть текст песни из БД) в `body`, а `CustomConfirm` рендерит `body` через `v-html` (`Common/CustomConfirm.vue:6`). Это **тот же корень**, что P-61-07 (`SongEdit`, 25 обработчиков + `header`/`body`), и отдельного BR не требует — предлагаю добавить как ещё две location в запись P-61-07. Reachability здесь ниже, чем у P-61-07: payload должен быть не просто сохранён в тексте, а **выделен админом** и подтверждён кнопкой «добавить слово»; атакующий не управляет выделением. Доказательство: «`          body: `Добавить слово «<strong>${selectedText.toLowerCase()}</strong>»?`,`» (5144), «`          body: `Удалить слово «<strong>${selectedText.toLowerCase()}</strong>»?`,`» (5181), автор — Ilya (boss), коммит `5618d19c5` (2026-09-30).

2. **BPM/CALC без валидации (4378, 4552, 4608).** `addMarker` для `CALC|…` считает BPM как `Math.round(60 / ((currentTime - bpmMarker.time) / 4))`, без нижней границы интервала и без проверки результата; `createBeatMarkers` строит beat-маркеры циклами `while (currentTime > 0)` / `while (currentTime < nextBpmMarkerTime)` с шагом `noteLength32 = 60/bpm/8`. Если CALC-маркер поставлен в миллисекундах от BPM-маркера, BPM получается астрономическим, шаг — доли миллисекунды, и цикл создаёт сотни тысяч/миллионы маркеров (зависание вкладки и память). Трактовки: (а) дефект — нет валидации пользовательского ввода, «Точные маркеры»/CALC должен ограничивать BPM разумным диапазоном и числом генерируемых маркеров; (б) не дефект — CALC-маркер ставится только вручную и «неправильная» постановка — ошибка пользователя. Путь: `addSettingMarker` (4247) → тип `CALC|` → `doAddSettingMarker` (4275) → `addMarker` (4304–4309, 4367–4383). Доказательство: «`        let bpm = Math.round(60 / ((this.currentTime - bpmMarker.time) / 4))`» (4378), «`          let currentTime = bpmMarker.time - noteLength32` / `          let counter = 1` / `          while (currentTime > 0) {`» (4550–4552). Нужен вердикт владельца: граница «минимальный интервал между BPM и CALC» — продуктовая или защитная.

3. **Копирование/удаление маркеров в регионе и beat-сетка (3652–3712).** `pasteMarkersInRegionToNewPlace` копирует и `beat`-маркеры как обычные (со сдвигом времени), не вызывая `createBeatMarkers`; `deleteMarkersInRegion` удаляет `beat`-маркеры в диапазоне, тоже без пересчёта сетки. После Save в БД остаётся сдвинутая/дырявая beat-сетка при неизменном BPM-маркере. Трактовки: (а) так и задумано — beat-маркеры это обычные маркеры, пользователь сам решит, что с ними делать; (б) дефект — производные beat-маркеры должны пересчитываться из BPM (как в `addMarker`/`deleteMarker`, где `isBpm` вызывает `createBeatMarkers`, 4503–4505). Доказательство: «`            if (needAdd) {` / `              newMarker.region = this.createRegionMarker(newMarker)` / `              this.sourceMarkers.push(newMarker)`» (4591–4593) и отсутствие `createBeatMarkers()` в 3652–3712. Без severity до вердикта.

4. **`getStringsForAllNotesInSong` в computed (5768–5838).** Метод вызывается из computed `lstIndexesTabsVariant` (2225–2232), то есть в фазе render, и делает `20 × markersList × uniqueNotes` проходов с `filter()` на каждый маркер (5781–5818). На песнях с нотами это квадратично по числу маркеров и пересчитывается на каждое изменение `sourceMarkers` (нажатие клавиши). Замер не делал: в выборке read-only API (песни 1/12/98/107) маркеров с `note` нет, поэтому эффект не наблюдаем; если лид считает класс важным — нужен замер на песне с нотами (`indexTabsVariant`/«Ноты»). Пока без severity, чтобы не дублировать P-62-10 (там замеренный PERF в `specTagAnchors`).

5. **`doChordsAdd`/`changeDiffBeats` — мёртвый код с проглоченной ошибкой (4676–4817).** Все входы в эти методы закомментированы в шаблоне (1068–1080), поэтому в отчёт не включены (rubric §2: мёртвый код без риска). Отмечаю на случай, если кнопки вернут: `changeDiffBeats` в `catch` заполняет `customConfirmParams`, но не выставляет `isCustomConfirmVisible` (4807–4811) — ровно дефект P-62-03 (часть 1), только в другой ветке.

6. **Форма chord-метки в БД: `label` или `chord` (4137–4140, 4712–4719, 3223).** Сейчас в данных сосуществуют две формы: старые chord-метки хранят аккорд в `label` (песни 12/120 — 226 меток, `chord` отсутствует) и новые метки получают `chord` через поле «Chord:» (template:344–349) — в выборке 400 песен 40 меток с `chord`. `getRegionContentFromMarker` поддерживает только вторую (P-62-19), `getFormattedChords` — обе (1698–1703, 1728). Трактовки: (а) дефект — рендерер обязан читать обе формы, данные мигрировать не нужно; (б) данные нужно нормализовать миграцией (`label` → `chord` для markertype='chord'), а код может остаться строгим. Это решение о миграции прод-данных — только словом владельца (rubric §7); P-62-19 фиксирует падение независимо от выбора.
