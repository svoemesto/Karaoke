# Feature Specification: устранение спама PROCESS_COUNT_WAITING в SSE-канале

**Feature Branch**: `177-fix-process-count-waiting-spam`
**Created**: 2026-08-12
**Status**: Draft
**Input**: User description: "Админка. При обновлении страницы идёт запрос на бэк по адресу http://localhost:7906/api/subscribe?tabId=... и в ответ идёт непрерывный трафик таких одинаковых сообщений: `{"userId":1,"payload":{"type":"PROCESS_COUNT_WAITING","data":{"countWaiting":0}},"timestamp":...}`. Зачем этот спам?"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - В SSE-канал больше не идёт дублирующих одинаковых сообщений (Priority: P1)

Администратор открывает/обновляет любую страницу админки. Браузер устанавливает
SSE-подписку на `/api/subscribe?tabId=...`. В канал поступают только те
сообщения типа `PROCESS_COUNT_WAITING`, которые несут **новое** значение
`countWaiting` (отличное от последнего отправленного). При простое очереди
(нет ни одного процесса со статусом `WAITING`, не относящегося к команде
`tail`) фронт **не** получает повторных одинаковых событий.

**Why this priority**: Это самый шумный и бесполезный трафик в SSE-канале
админки. Событие `PROCESS_COUNT_WAITING` задумано как «количество заданий
в очереди изменилось — обновите бейдж в UI», а не как периодический
heartbeat. Сейчас фронт получает одно и то же значение (чаще всего `0`)
десятки раз в секунду. Это:
- забивает сетевой канал и процессорные циклы на сериализацию/десериализацию
  SSE-фреймов;
- затрудняет диагностику реальных событий (нужное сообщение тонет в шуме);
- маскирует «дрейф» счётчика (когда значение *должно* измениться, оператор
  видит то же `0` и не понимает, дошло ли обновление).

**Independent Test**: Открыть DevTools → Network → EventStream на любой
странице админки. Убедиться, что за 5 минут простоя (нет действий в UI,
очередь пустая) приходит **0** (или, как минимум, на 2 порядка меньше)
сообщений `PROCESS_COUNT_WAITING`. Затем запустить любое длительное
задание (например, рендер) — бейдж в UI должен отобразить ненулевое
значение в течение 1–2 секунд.

**Acceptance Scenarios**:

1. **Given** SSE-подписка установлена, очередь пуста (`countWaiting == 0`),
   **When** проходит 60 секунд без действий пользователя и без появления
   новых заданий, **Then** в SSE-канале **нет** сообщений
   `PROCESS_COUNT_WAITING` с `countWaiting == 0`.
2. **Given** SSE-подписка установлена, в очереди появилось WAITING-задание
   (не `tail`), **When** бэкенд зафиксировал создание процесса в БД,
   **Then** фронт получает **ровно одно** сообщение
   `PROCESS_COUNT_WAITING` с актуальным `countWaiting > 0` (в пределах
   одной «пачки» изменений, без дублей).
3. **Given** SSE-подписка установлена, **When** одно и то же значение
   `countWaiting` пересчитывается несколько раз подряд без фактического
   изменения состояния очереди, **Then** в SSE-канал отправляется **не
   более одного** сообщения на каждое уникальное значение
   (т.е. подряд идущие одинаковые значения подавляются).

### User Story 2 - Heartbeat «очередь жива» отдельно от счётчика (Priority: P2)

Если бэкенд считает важным сигнализировать о том, что воркер очереди
*работает* (а не только о количестве заданий), он делает это отдельным
SSE-событием с явным heartbeat-таймером, а не повторной рассылкой
`PROCESS_COUNT_WAITING`. Например, существующий `PROCESS_WORKER_STATE`
(флаг `isWork`) уже передаётся при старте/остановке — этого достаточно
для индикации «жив/мёртв», а `PROCESS_COUNT_WAITING` остаётся
событием-об-изменении-числа.

**Why this priority**: P1 покрывает главную боль (спам). Но если в коде
была заложена *намерение* использовать повторные `PROCESS_COUNT_WAITING`
как «liveness ping» (т.е. «очередь опрашивается, я тут»), эту роль
следует выделить в отдельное событие — чтобы убрать двусмысленность
и не потерять полезный сигнал при чистом подавлении дублей.

**Independent Test**: В коде бэкенда проверить, что в цикле `doStart`
нет периодического вызова `sendCountWaitingMessage`, не привязанного к
фактическому изменению числа WAITING-заданий. Если такой вызов
существует — он должен быть либо удалён, либо заменён на отдельное
heartbeat-событие (например, `PROCESS_WORKER_TICK`) с явным интервалом.

**Acceptance Scenarios**:

1. **Given** воркер очереди работает (`isWork == true`), очередь пуста,
   **When** проходит N секунд, **Then** в SSE-канал не уходит
   `PROCESS_COUNT_WAITING` (если только число реально не изменилось).
2. **Given** воркер очереди работает (`isWork == true`), **When**
   разработчик хочет видеть «жив ли воркер» в UI, **Then** он
   использует уже существующее событие `PROCESS_WORKER_STATE` либо
   отдельное heartbeat-событие — но **не** `PROCESS_COUNT_WAITING`.

---

### Edge Cases

- **Что если в UI открыто несколько вкладок админки?** Подавление дублей
  делается на стороне бэкенда (один фактический вызов `sendCountWaitingMessage`
  вместо многих), а не на стороне клиента. Это значит, что и вторая, и
  третья вкладки получат корректное (одно) сообщение на каждое изменение
  — не нужно слать «по одному на каждую подписку».
- **Что если подписчик отвалился (закрыл вкладку)?** `SseNotification`
  и `SNS` уже должны корректно отписывать мёртвые SSE-сессии. Это
  поведение не меняется. Подавление дублей работает на стороне
  продьюсера события, а не подписчика.
- **Что если в момент подавления происходит реальное изменение, а потом
  обратное (например, WAITING → WORKING → WAITING)?** Если итоговое
  значение совпало с последним отправленным, фронт не получит
  промежуточного сигнала. Это допустимо: для UI важно конечное
  состояние, а промежуточные флуктуации (задание забрали в работу и
  сразу же завершили) не несут полезной информации.
- **Что если при отправке `SNS.send` упал с исключением (например,
  мёртвый подписчик не убран из реестра)?** Текущий код в
  `sendCountWaitingMessage` уже ловит исключение и пишет в stdout.
  Подавление дублей не должно это ломать.
- **Что если `countWaiting == 0`, но в коде создаётся «tail»-процесс
  (команда `tail`)?** В `createDbInstance` уже есть условие
  `process.command != "tail"` перед вызовом `sendCountWaitingMessage`.
  Учитывать это при подавлении (не считать tail-процессы как
  повод слать событие).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Бэкенд MUST отправлять SSE-событие
  `PROCESS_COUNT_WAITING` только в случае, когда значение
  `countWaiting` реально изменилось относительно последнего
  отправленного значения по тому же типу события (в рамках одного
  жизненного цикла бэкенда). Подряд идущие одинаковые значения MUST
  быть подавлены на стороне продьюсера.
- **FR-002**: Подавление дублей MUST охватывать все 5 текущих
  call-sites `sendCountWaitingMessage`:
  `KaraokeProcess.createDbInstance`,
  `KaraokeProcess.run`,
  `KaraokeProcess.forceStop`,
  `KaraokeProcessWorker.start`,
  `KaraokeProcessWorker.doStart`.
- **FR-003**: Цикл `doStart` главного потока воркера очереди MUST NOT
  периодически (на каждой итерации `while (isWork)` или на каждом
  «тике») вызывать `sendCountWaitingMessage` без привязки к факту
  изменения числа WAITING-заданий. Если в коде есть периодический
  вызов, он MUST быть либо удалён, либо заменён на отдельный
  heartbeat с явным интервалом (см. US2).
- **FR-004**: Источник истины для «последнего отправленного значения» —
  in-memory volatile-переменная в `KaraokeProcessWorker` (или в
  существующем компоненте, рассылающем SSE). Состояние сбрасывается
  при рестарте бэкенда (это нормально — после рестарта первое
  вычисленное значение будет отправлено).
- **FR-005**: Реальные изменения `countWaiting` (например, +1 при
  создании нового WAITING-процесса и −1 при переходе в WORKING/DONE)
  MUST доходить до фронта **в течение 1–2 секунд** с момента
  изменения в БД (текущий уровень отзывчивости сохраняется).
- **FR-006**: Фронт (webvue3) MUST продолжать корректно обновлять
  бейдж счётчика по единственному пришедшему сообщению
  `PROCESS_COUNT_WAITING`. Никаких изменений на стороне клиента
  для базового сценария не требуется.
- **FR-007**: При штатном запуске воркера (`KaraokeProcessWorker.start`)
  бэкенд MUST отправить **одно** начальное сообщение
  `PROCESS_COUNT_WAITING` с актуальным значением после
  `deleteDone`/`setWorkingToWaiting` (чтобы фронт узнал реальный
  счётчик, даже если значение совпало с последним перед остановкой
  воркера — после остановки продьюсер должен сбросить «последнее
  отправленное значение»).
- **FR-008**: Существующее поведение рассылки `PROCESS_WORKER_STATE`
  (флаг `isWork`) MUST остаться без изменений — это отдельный
  канал сигнализации «жив ли воркер» и не зависит от FR-001.

### Key Entities *(include if feature involves data)*

- **PROCESS_COUNT_WAITING** (SSE-event payload): `{ countWaiting: Long }`.
  Означает «количество заданий со статусом `WAITING`, ожидающих
  запуска воркером». Не включает задания с командой `tail`.
- **Last sent count**: in-memory состояние в `KaraokeProcessWorker` —
  последнее фактически отправленное значение `countWaiting`.
  Используется для подавления дублей (FR-001).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: При простое админки в течение 5 минут с пустой очередью
  (`countWaiting == 0`) в SSE-канал `/api/subscribe` приходит **0**
  сообщений `PROCESS_COUNT_WAITING` (сейчас — тысячи за 5 минут).
- **SC-002**: При появлении нового WAITING-задания в очереди бейдж
  в UI обновляется в течение **1–2 секунд** (текущий уровень
  отзывчивости сохраняется; не регрессируем).
- **SC-003**: Суммарный объём трафика SSE-канала
  `PROCESS_COUNT_WAITING` за час простоя снижается **не менее чем
  в 100 раз** (эмпирически — с ~10–20 сообщений/сек до ≤1 сообщения
  за 5 минут при пустой очереди).
- **SC-004**: После ручного запуска воркера (`/api/processes/startWorker`)
  бэкенд отправляет **ровно одно** начальное сообщение
  `PROCESS_COUNT_WAITING` (а не серию повторов), даже если
  актуальный счётчик равен последнему известному UI значению.
- **SC-005**: Изменения модели данных БД, DTO, фронтовых компонентов,
  отображающих бейдж — **не требуются**. Это чисто серверный фикс
  в `KaraokeProcessWorker` / `KaraokeProcess`.

## Assumptions

- **Источник шума — повторные вызовы `sendCountWaitingMessage`** в
  цикле `KaraokeProcessWorker.doStart` или в смежных хуках
  (`createDbInstance`, `run`, `forceStop`, `start`). Подтверждено
  codegraph'ом (5 call-sites).
- **`countWaiting == 0` в спаме** объясняется тем, что в текущий
  момент в БД нет WAITING-заданий (или есть только `tail`-процессы,
  которые код уже не учитывает), но цикл продьюсера всё равно
  периодически пересчитывает значение и шлёт его.
- **UI уже умеет реагировать на одиночное сообщение** — нет
  необходимости вводить heartbeat, чтобы «поддерживать» бейдж.
  Бейдж обновляется только по факту изменения.
- **Рестарт бэкенда** сбрасывает in-memory состояние «последнего
  отправленного значения» — это нормально, первое вычисленное
  значение после рестарта будет отправлено (FR-007).
- **Множественные подписчики (несколько вкладок админки)** —
  каждый получает копию одного и того же отправленного сообщения;
  подавление работает на стороне продьюсера, не на стороне
  подписчика. Никаких изменений в логике fan-out не требуется.
- **Другие SSE-события** (`RECORD_CHANGE`, `RECORD_ADD`,
  `RECORD_DELETE`, `PROCESS_WORKER_STATE`, `MESSAGE`, и т.п.)
  выходят за рамки этой фичи — они либо уже подавляются
  соответствующим образом, либо должны подавляться в отдельных
  спецификациях.
- **Локальное окружение админки** — фича разрабатывается и
  проверяется на admin-машине (с реальным `karaoke-app`); на проде
  `karaoke-app` не развёрнут, поэтому регрессия на публичном сайте
  исключена по построению.
