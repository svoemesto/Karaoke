# Отчёт: Механизм allow-list прод-хоста — один текущий адрес, источник адреса — прод

**Спека**: `specs/731-allowlist-single-address/spec.md` (спека 731, Issue ID `none` — по решению владельца)
**Ветка**: `731-allowlist-single-address`
**Дата**: 2026-11-08

## Инцидент

Владелец 2026-11-08, 15:50: «и снова сменился айпишник, и снова на это не отреагировало
приложение правильно!». В логах `karaoke-app` — десятки `DB-CONNECT-001` к
`188.127.240.124:5433` в минуту: прод-БД закрыта для админ-машины.

Разбор — по журналу механизма `/var/log/admin-ip-allowlist.log`, по stream-журналу
nginx на прод-хосте и по логам контейнера.

## Три причины

1. **Механизм не применял правку ни разу.** Внешние IP-сервисы расходились:
   `api.ipify.org` и `ifconfig.me` отвечали через VPN-туннель с ротацией
   (`195.178.4.144…166`), остальные четыре — через адрес ISP (`95.31.39.146`).
   Правило «все источники должны совпасть» давало `sources_disagree` → отказ.
2. **Откат ломал конфиг прод-хоста.** При провале контрольной проверки
   `rollback_change remote "${PROD_CONF}" "${BACKUP_PATH}"` восстанавливал бэкап
   **последнего** файла в **первый**: `/etc/nginx/nginx.conf` получал содержимое
   файла сайта, `nginx -t` падал («"server" directive is not allowed here»).
   Обнаружено и восстановлено вручную 2026-11-08, 16:00.
3. **Список разросся до 9–10 адресов** — «про запас» по решению 2026-10-07; доступ
   оставался открытым для всех, кто когда-либо был админ-машиной.

## Что сделано

### Правка 1 — адрес берётся у прод-хоста (FR-001…FR-003)

- `detect_prod_seen_address` — `SSH_CLIENT` в SSH-сессии к проду: прод знает наш
  адрес на том канале, который мы и чиним.
- `current_address` — единая точка определения: прод → внешние сервисы (запасной
  путь). Расхождение внешних сервисов больше не блокирует правку.
- `confirm_address` (перепроверка перед применением) — из того же источника.

**Проверено фактами:** stream-журнал nginx на проде показал, что и хост, и
контейнер приложения приходят к `188.127.240.124:5433/9000` с одного адреса
`95.31.39.146` — того же, что прод видит на SSH-канале.

### Правка 2 — в списке ровно один текущий адрес (FR-004…FR-006)

- `prepare_new_config` (stream-блоки) и `prepare_new_allow_config` (HTTP-локации)
  заменяют весь список allow-адресов в блоке на одну строку `allow <текущий ip>;`.
  Правила вида `allow 10.0.0.0/8;` (подсети) не трогаются.
- `address_allowed` — файл «правильный», только если в каждом блоке с `deny all;`
  ровно один allow и он текущий.
- `verify_diff` — сравнение содержимого без allow-строк (побайтно) + отдельная
  проверка итога.

### Правка 3 — откат из своего бэкапа (FR-007, FR-008, FR-010)

- `apply_change` запоминает свой бэкап и способ записи.
- `rollback_applied` откатывает **каждый** изменённый файл **из его бэкапа**,
  тем же способом записи, которым файл был изменён.

## Предложение владельцу: механизм без правки конфига при смене IP

**Суть.** Сейчас при смене внешнего адреса админ-машины правку конфига на прод-хосте
делает автоматика (каждые 10 минут). Владелец просит механизм, при котором правка
не нужна вовсе. Три варианта — от простого к правильному:

**A. Постоянный туннель между админ-машиной и продом (рекомендую).**
На проде поднимается WireGuard/Amnezia-пир, админ-машина — клиент с постоянным
внутренним адресом (например `10.77.0.2`). В allow-list прод-хоста — **один
неизменный адрес `10.77.0.2`** (или `allow 10.77.0.0/24`), и он никогда не
меняется: публичный IP админ-машины может плавать сколько угодно.
nginx при этом продолжает смотреть в адрес, который не зависит от провайдера.
Плюс: канал шифруется, и `5433`/`9000` можно вообще не публиковать наружу —
прод-БД слушает только loopback, доступ идёт по туннелю.

**B. Обратный SSH-туннель вместо allow-list.**
Админ-машина держит постоянный SSH-туннель (`autossh`) к проду, и nginx на проде
разрешает подключения только с `127.0.0.1`. Список адресов пустой и не меняется
никогда. Дешевле варианта A (не нужен второй VPN-сервис), но канал держится
процессом, который надо сторожить, и он не шифрует трафик к самой БД по
содержимому (туннель — да, но адресные пространства).

**C. Аутентификация вместо allow-list по IP.**
Для БД — `pg_hba.conf` с требованием TLS-сертификата клиента (mTLS), для MinIO —
уже есть ключи SigV4. Тогда allow-list по IP не нужен вовсе: подключиться может
только тот, у кого есть ключ. IP-фильтр остаётся как дополнительный слой, но
перестаёт быть единственным.

**Рекомендация:** A (постоянный туннель) + C (mTLS для БД) вместе: адрес в
allow-list становится постоянным, а идентификация перестаёт зависеть от IP вообще.
Тогда правка конфига на проде при смене адреса не нужна никогда.

**Что для этого нужно от владельца:** решение по варианту, разрешение на
установку WireGuard/Amnezia-пира на прод-хосте и время на настройку (пир +
переключение nginx на внутренний адрес + контрольная проверка).
