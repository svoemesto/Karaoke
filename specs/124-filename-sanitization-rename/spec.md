# Feature Specification: Санитайзинг имён файлов при импорте и переименование при редактировании

**Feature Branch**: `124-filename-sanitization-rename`

**Created**: 2026-08-03

**Status**: Draft

**Input**: User description: "Санитайзинг имён файлов, импорт и переименование. Сейчас при импорте песен из папки возникают определенные проблемы. Например, если имя файла содержит восклицательный знак, то для такой песни "падает" демукс. Нужно чтобы имена файлов при импорте правильно санитарировались, но при этом в названии песни символы оставались. Если изначально файл называется "2012 (01) [Ария] - Дай жару!.mp3", имя у песни должна быть "Дай жару!", а имя файла (после декодирования во флак) стать "2012 (01) [Ария] - Дай жару.flac". Так же, если в SongEdit у песни редактируется имя файла, то одновременно с этим должен переименовываться файл на диске, аудиостемы на диске, в локальном и удалённом хранилище - в общем все сущности, зависящие по шаблонам от имени файла."

## Clarifications

### Session 2026-08-03

- Q: Как система обрабатывает частичный отказ каскада переименования (FR-007/FR-008), если часть файлов/объектов уже переименована под новое имя, а часть — нет? → A: Best-effort вперёд + явная ошибка — не откатывать уже переименованное, пометить песню статусом ошибки, требовать повтора/ручного докручивания оставшегося.
- Q: Как система реагирует, если переименование файла песни (SongEdit) запрошено, пока над этой песней уже идёт фоновая обработка (например, ещё считаются стемы)? → A: Блокировать переименование — отклонить сохранение с сообщением дождаться завершения текущей обработки, пользователь повторяет попытку позже.
- Q: В каких пределах проверяется уникальность имени файла при поиске коллизии (FR-005, FR-011)? → A: В пределах одной папки/альбома (rootFolder) — совпадение проверяется только среди песен, физически хранящихся в той же папке.
- Q: Как именно система разрешает коллизию имени файла при импорте (два файла из одной папки после санитайзинга дали бы одинаковое имя)? → A: Автоматически генерировать уникальное имя (например, числовой суффикс) для второго файла — импортируется без ручного вмешательства.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Импорт песен с "проблемными" символами в имени файла (Priority: P1)

Администратор запускает импорт песен из папки. Среди исходных файлов есть файл с именем вида `2012 (01) [Ария] - Дай жару!.mp3`. Сегодня такой файл импортируется, но последующая обработка (в частности, разделение на стемы) падает из-за восклицательного знака в имени файла, потому что имя файла нигде не приводится к безопасному виду при импорте, а название песни, которое видит пользователь, при этом не должно потерять символ `!`.

**Why this priority**: Это блокирующий баг — конкретные песни физически не проходят пайплайн обработки (падает разделение на стемы), пока администратор не переименует файл вручную ещё до импорта. Без исправления часть каталога невозможно обработать автоматически.

**Independent Test**: Положить в папку импорта файл `2012 (01) [Ария] - Дай жару!.mp3` внутри альбомной папки `2012 - Название альбома`, запустить импорт из папки и убедиться, что: (а) созданная песня получает имя файла на диске `2012 (01) [Ария] - Дай жару.flac` (без `!`), (б) название песни в карточке — `Дай жару!` (с `!`), (в) последующая обработка (разделение на стемы) не падает и завершается успешно.

**Acceptance Scenarios**:

1. **Given** в папке импорта лежит файл `2012 (01) [Ария] - Дай жару!.mp3` в альбомной папке `2012 - Название альбома`, **When** запускается импорт из папки, **Then** создаётся новая песня, у которой поле «Название» равно `Дай жару!`, а имя файла на диске (после перекодирования в FLAC) — `2012 (01) [Ария] - Дай жару.flac`.
2. **Given** песня с именем файла, из которого удалены проблемные символы, только что импортирована, **When** запускается очередная стадия автоматической обработки (разделение на стемы и далее по цепочке), **Then** обработка проходит без ошибок, связанных с именем файла.
3. **Given** исходный файл содержит другие потенциально проблемные для файловой системы/командной строки символы (например, `?`, `:`, `*`, кавычки), **When** запускается импорт, **Then** эти символы удаляются/заменяются в имени файла на диске, но сохраняются в названии песни.
4. **Given** два разных исходных файла в одной альбомной папке после санитайзинга дали бы одинаковое имя файла, **When** запускается импорт, **Then** второй файл автоматически получает уникальное имя файла (например, с числовым суффиксом) и импортируется без ручного вмешательства, не перезаписывая и не путаясь с первым.

### User Story 2 - Переименование файла песни через SongEdit каскадно переименовывает все связанные сущности (Priority: P2)

Администратор открывает карточку существующей песни в SongEdit и меняет значение поля «Имя файла». Сегодня это только обновляет значение в базе данных и создаёт файл метаданных с новым именем, но сам аудиофайл на диске, уже посчитанные аудиостемы, файл проекта видеоредактора, субтитры и объекты в локальном и удалённом (MinIO) хранилище остаются под старым именем — из-за этого песня становится "битой": часть файлов ищется по новому имени и не находится.

**Why this priority**: Важная функциональность для приведения в порядок уже импортированных песен (в том числе с историческими проблемными именами), но не блокирует основной пайплайн импорта — можно жить без неё, вручную поправляя файлы, пока не реализован User Story 1.

**Independent Test**: Взять существующую песню, у которой уже посчитаны аудиостемы и она загружена в локальное и удалённое хранилище, изменить в SongEdit поле «Имя файла» на новое значение и сохранить. Убедиться, что все связанные файлы на диске и объекты в обоих хранилищах теперь находятся под новым именем, а под старым именем ничего не осталось.

**Acceptance Scenarios**:

1. **Given** песня, у которой на диске есть аудиофайл, аудиостемы, файл проекта видеоредактора и файл субтитров, **When** пользователь меняет «Имя файла» в SongEdit и сохраняет, **Then** все перечисленные файлы на диске переименовываются в соответствии с новым именем, а файлов под старым именем не остаётся.
2. **Given** та же песня уже загружена в локальное и удалённое (MinIO) хранилище, **When** пользователь меняет «Имя файла» и сохраняет, **Then** соответствующие объекты хранилища тоже становятся доступны под новым именем (переименованы/перемещены), а старые ключи хранилища для этой песни не остаются "висящими".
3. **Given** пользователь вводит в поле «Имя файла» значение с символами, которые считаются проблемными для файловой системы/командной строки, **When** он сохраняет изменение, **Then** к новому значению применяются те же правила санитайзинга, что и при импорте, прежде чем оно используется как реальное имя файла.
4. **Given** у песни ещё не все производные файлы существуют (например, аудиостемы ещё не посчитаны), **When** пользователь переименовывает файл песни, **Then** система переименовывает то, что уже существует, и не завершается ошибкой из-за отсутствующих файлов.
5. **Given** переименование не удалось выполнить полностью (например, часть файлов переименована, а на каком-то шаге произошла ошибка), **When** это происходит, **Then** система не откатывает уже переименованные файлы назад, а помечает песню статусом ошибки и показывает её пользователю; оставшиеся файлы/объекты доводятся до нового имени повторной попыткой, песня не должна тихо "потеряться" в рассинхронизированном состоянии.

---

### Edge Cases

- Что происходит, если после санитайзинга новое имя файла совпадает с именем файла уже существующей песни (в той же папке/альбоме)?
- Что происходит, если пользователь вводит в «Имя файла» пустую строку или строку, полностью состоящую из "проблемных" символов (после санитайзинга получается пустое имя)?
- Что происходит, если пользователь вводит в «Имя файла» символы пути (`/`, `\`) — попытка выйти за пределы папки песни?
- Переименование блокируется (FR-013), если над песней в момент сохранения уже выполняется фоновая обработка (например, идёт разделение на стемы) — какое именно сообщение/статус видит пользователь при отклонённой попытке?
- Что происходит, если объект в удалённом хранилище (MinIO) для песни ещё не существует (загрузка ещё не завершилась) на момент переименования?
- Как обрабатываются кириллические и прочие не-ASCII символы — они должны сохраняться и в имени файла, и в названии песни (проблемными считаются только символы, реально ломающие файловую систему/команды, а не любые не-латинские буквы).
- Что происходит с уже полученными внешними ссылками/embed (Sponsr, VK, симлинки), которые могли ссылаться на файл по старому имени?

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: При импорте песен из папки система MUST формировать имя файла на диске для каждой импортируемой песни так, чтобы из него были удалены/заменены символы, которые ломают файловые операции и обработку в пайплайне (например `!`, `?`, `:`, `*`, кавычки), — до того, как файл перекодируется в FLAC и запускается любая последующая обработка.
- **FR-002**: Санитайзинг имени файла при импорте MUST не влиять на название песни, которое видит пользователь: название сохраняет оригинальные символы из исходного имени файла (включая `!` и подобные), даже если они были удалены из имени файла на диске.
- **FR-003**: Санитайзинг имени файла при импорте MUST не удалять символы, структурно значимые для распознавания номера/автора/названия по шаблону имени файла (например скобки `(` `)` и квадратные скобки `[` `]`, используемые в шаблоне «Порядковый (Номер) [Автор] - Название»).
- **FR-004**: Все артефакты, создаваемые в рамках импорта и последующей автоматической обработки одной песни (перекодированный FLAC-файл, аудиостемы, файлы для дальнейших шагов пайплайна), MUST использовать одно и то же — уже санитайзированное — имя файла, без расхождений между отдельными шагами.
- **FR-005**: Если после санитайзинга два разных исходных файла в рамках одного импорта, находящиеся в одной и той же папке/альбоме, получили бы одинаковое имя файла, система MUST автоматически присвоить второму (и последующим конфликтующим) файлу уникальное имя файла (например, с числовым суффиксом), чтобы оба файла были импортированы без ручного вмешательства администратора. Совпадение имени файла у песен из разных папок/альбомов конфликтом не считается.
- **FR-006**: В SongEdit при сохранении изменённого значения поля «Имя файла» система MUST применить к новому значению те же правила санитайзинга, что и при импорте, прежде чем это значение станет фактическим именем файлов на диске и в хранилищах.
- **FR-007**: При сохранении нового значения «Имя файла» в SongEdit система MUST переименовать под новое имя все существующие на диске файлы, чьё имя шаблонно образуется из старого имени файла песни: основной аудиофайл, все существующие аудиостемы, файл проекта видеоредактора, файл субтитров и файл метаданных песни.
- **FR-008**: При сохранении нового значения «Имя файла» в SongEdit система MUST перенести/переименовать под новое имя соответствующие объекты песни в локальном хранилище и в удалённом (MinIO) хранилище, если они там существуют, так, чтобы объекты не остались доступны только под старым именем.
- **FR-009**: Переименование по FR-007/FR-008 MUST корректно обрабатывать отсутствие отдельных производных файлов/объектов (например, аудиостемы ещё не посчитаны или загрузка в удалённое хранилище ещё не выполнена) — отсутствие одного из артефактов не должно приводить к ошибке всей операции переименования.
- **FR-010**: Если в процессе переименования (FR-007/FR-008) происходит ошибка на одном из шагов, система MUST не откатывать уже успешно переименованные файлы/объекты назад к старому имени (best-effort вперёд), а вместо этого явно пометить песню статусом ошибки и сообщить о ней пользователю; оставшиеся непереименованными файлы/объекты MUST быть доведены до нового имени через повтор операции (повторное сохранение/явный retry), а не тихо забыты.
- **FR-011**: Система MUST отклонять или блокировать сохранение нового «Имя файла», которое после санитайзинга совпадает с именем файла другой уже существующей песни в той же папке/альбоме (rootFolder), либо после санитайзинга оказывается пустым. Совпадение с именем файла песни из другой папки/альбома конфликтом не считается.
- **FR-012**: Санитайзинг (и при импорте, и при переименовании через SongEdit) MUST сохранять не-ASCII буквы (кириллицу и т.п.) без изменений — удалению/замене подлежат только символы, реально проблемные для файловой системы или команд обработки, а не любые "нестандартные" буквы.
- **FR-013**: Если над песней в момент попытки сохранить новое «Имя файла» уже выполняется фоновая обработка (например, ещё считаются аудиостемы), система MUST отклонить сохранение переименования и сообщить пользователю, что нужно дождаться завершения текущей обработки, прежде чем переименование станет возможным.

### Key Entities *(include if feature involves data)*

- **Песня (Song)**: имеет отдельно название (отображаемое пользователю, может содержать любые символы) и имя файла (используется как основа для реальных файлов на диске и ключей хранилища, должно быть санитайзировано).
- **Производные файлы песни**: аудиофайл (FLAC), аудиостемы (по одному файлу на каждый выделяемый инструмент/голос), файл проекта видеоредактора, файл субтитров, файл метаданных — все именуются по шаблону на основе имени файла песни.
- **Объекты хранилища**: копии аудиофайла/стемов/производных материалов песни в локальном и удалённом (MinIO) хранилище, ключ которых также строится по шаблону на основе имени файла песни.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% файлов с ранее проблемными символами в имени (например, `!`), помещённых в папку импорта, успешно проходят весь автоматический пайплайн обработки без сбоев, вызванных именем файла.
- **SC-002**: 100% импортированных песен получают название, точно совпадающее с распознанным из исходного имени файла фрагментом названия, включая все исходные символы (без потери `!` и подобных).
- **SC-003**: После переименования файла песни через SongEdit 100% ранее существовавших связанных файлов на диске и объектов в обоих хранилищах доступны под новым именем без ручного вмешательства администратора.
- **SC-004**: После успешного переименования файла песни через SongEdit не остаётся ни одного файла на диске или объекта хранилища, всё ещё доступного только под старым именем.
- **SC-005**: При попытке сохранить «Имя файла», которое приводит к конфликту с другой песней или к пустому значению после санитайзинга, пользователь получает понятное сообщение об ошибке в 100% случаев, а данные песни не повреждаются.

## Assumptions

- Санитайзинг распространяется только на символы, реально проблемные для файловой системы/команд обработки (например `!`, `?`, `:`, `*`, кавычки, символы пути); конкретный итоговый перечень символов и правило их замены (удаление vs. замена на аналог) уточняется на этапе планирования на основе уже существующей в проекте логики очистки имён файлов.
- Правило санитайзинга единое и для импорта, и для ручного переименования через SongEdit — не предполагается отдельных наборов правил для разных путей.
- Массовое (автоматическое, без явного действия пользователя) исправление уже импортированных ранее песен с несанитайзированными/проблемными именами файлов не входит в объём этой фичи — такие песни приводятся в порядок по одной через ручное переименование в SongEdit (User Story 2), которое эта фича делает безопасным и полным.
- Переименование, инициированное через SongEdit, выполняется как реакция на сохранение конкретной песни (единичная операция для одной песни за раз), а не как массовая пакетная операция над множеством песен одновременно.
- Внешние ссылки/embed на сторонних площадках (Sponsr, VK и т.п.), созданные до переименования и указывающие на конкретные пути/URL, не пересоздаются автоматически этой фичей; предполагается, что актуальные для показа пользователю ссылки и плееры используют текущие данные песни, а не закэшированные пути.
